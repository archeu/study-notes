改库和发消息怎么一起成功：RocketMQ 的事务消息、定时消息、顺序消息

这三样 Kafka 都没有现成的，要靠 outbox 表、扫表任务、消费端车道自己拼。RocketMQ 把它们做进了 Broker。事务消息：消息先存进 Broker，但消费者看不见；订单库提交以后才放出来；生产者中途死了，Broker 会回头问“这一单到底成没成”。定时消息：Broker 把消息先停在一个时间轮上，到点再投。顺序消息：发送时按订单号选定一个队列，消费时把这个队列锁住，一次只交给一个线程。三样都只管到“消息怎么进出 Broker”，消费端的幂等还得自己做。

①为什么学：交易靶场里有三件事，Kafka 都给不了现成的

在全景第 1 站，支付回调到了，订单服务要把 9527 改成 PAID，再发一条“已支付”，两件事得一起成功。下单 30 分钟还没付款的单要自动取消，得有一条“30 分钟后才到”的消息。在第 2 站，9527 的“已支付”“已发货”“已退款”要按顺序生效。

②老办法行不行：能做，但每样都要自己拼

先用已经会的东西各做一遍。第一张卡片的两个数，是本机 RocketMQ 5.5.1 上让进程死在中间跑出来的，代码见 ⑤。

不懂精华时的典型误用“上了事务消息，就是分布式事务了，下游积分加失败，订单也会回滚。”不会。事务消息只保证一件事：本地事务提交了，消息最终一定投出去；本地事务没提交，消息一定不投。消息投出去以后，积分服务失败了就重试，重试不成就进死信，上游的订单不会因此回滚。它管的是“发”，不管“收”和“下游做没做成”，消费端照样是至少一次，照样要去重。

③选谁：三件事各有几种做法

RocketMQ 不是每一项都必选。下面三张表各回答一件事，最后一行是本页学的。

同一单按顺序生效

做法顺序怎么来的并行度
Kafka：key 分区 + 一条条处理同一单进同一个分区，一个分区一个消费者分区数；要更高就自己写车道
RocketMQ 5.x FIFO 消息（gRPC 客户端）发送时设消息组（messageGroup），Broker 保证同一组一次只交出一条按消息组并行，不受队列数限制（按文档）
RocketMQ 顺序消息（remoting 客户端）发送时按订单号选队列，消费时锁住队列，一个队列一次一个线程队列数；一个消费者实例里多个队列并行

选择规则：已经在用 Kafka、团队又不想多维护一套 MQ，就用 outbox + 定时扫表或 ZSet，顺序用 key 分区。交易链路选的是 RocketMQ，就直接用它的三样，少写一张 outbox 表、一个扫表任务。本页学 RocketMQ 5.5.1 的这三样，用的是 remoting 客户端（rocketmq-client，rocketmq-spring 用的也是它），直连 NameServer 和 Broker；5.x 新的 gRPC 客户端放在 ⑥ 第三圈。

④原理：消息先停在 Broker 的系统 topic 里，条件满足了再放进真正的 topic

三样东西用的是同一招：消息先写进一个消费者不会订阅的系统 topic，Broker 记着它真正要去哪；等本地事务有了结论、或者时间到了，再把它重新写进真正的 topic，消费者这时才看得见。顺序消息不用这一招，它靠的是选队列和锁队列。

先知道这些
  • Topic 和队列：RocketMQ 的 topic 分成若干个队列（MessageQueue），相当于 Kafka 的分区；同一个队列里的消息有先后，队列之间没有。
  • CommitLog：一个 Broker 上所有 topic 的消息都追加写进同一串 CommitLog 文件，每个队列另有一个只记位置的索引（ConsumeQueue）。消息写下去就不能改，只能追加。和 Kafka 每个分区一份日志的对照见 Kafka 存储与零拷贝。
  • NameServer 和组：NameServer 只管路由（哪个 topic 在哪个 Broker）。生产者属于生产者组，消费者属于消费者组；同一个消费者组里，一个队列同一时刻只分给一个实例。

事务消息：半消息 + 回查

三个细节决定了后面的坑，都在客户端和 Broker 的源码里：

  • executeLocalTransaction 抛了异常或者返回 null，客户端都按 UNKNOW 处理，不会替你回滚（DefaultMQProducerImpl.sendMessageInTransaction）。本地事务失败，要自己返回 ROLLBACK_MESSAGE，就像 ⑤ 里的 9528。
  • 第 ④ 步 endTransaction 是 oneway 发的，不等回应；包丢了生产者也不知道，靠回查兜底。
  • Broker 每次回查前先把回查次数加一，再去找同组里在线的实例（TransactionalMessageServiceImpl.needDiscard、AbstractTransactionalMessageCheckListener.sendCheckMessage）。组里一个在线的都没有，这一次就白查了，次数照样算。

为什么这样设计：本地事务不能等 Broker，Broker 也不能等生产者

半消息 + 回查RocketMQ 选的

赢在哪：本地事务和平常一样，提交前不用等 Broker 投票，生产者随时可以死。要求只有一条：回查时能从库里查出“这一单成没成”。

两阶段提交（XA）被放弃的

输在哪：MQ 要实现 XA 参与者，订单行锁要跨两次网络往返，协调者本身又成了要高可用的单点。决定胜负的约束和上一页一样：MySQL 和 Broker 是两个系统，没有共同的事务。半消息、outbox 都选了“最终一致”：outbox 把消息搬进库，半消息把“等结论”这件事交给 Broker。

定时消息：18 个延迟级别，和 5.0 起的时间轮

按时间分格，或者按延迟分队列RocketMQ 选的两种

赢在哪：CommitLog 只能追加，消息写下去就不再挪动。这两种结构都把“排序”变成了“放进对的格子”：延迟级别靠“同一个队列延迟相同”，时间轮靠“同一格到期时间相同”。

一个按到期时间排序的集合被放弃的

输在哪：它要求存储能在中间插入，和 CommitLog“只追加”的约束正好相反。量小时它最灵活，所以 Redis 方案在小系统里一直有人用。

顺序消息：发送时选队列，消费时锁队列

锁队列RocketMQ 选的

Kafka 的消费端只给到“一个分区一个实例”，实例里怎么并行要自己写车道，车道之间做完的先后又会让位点提交变麻烦（上一页 ⑥ 第三圈）。RocketMQ 把“一个队列一个线程”做进了客户端，换来的是并行度上限就是队列数。

按条并发 + 业务层排序被放弃的

不是错的设计，是另一种取舍：上一页的版本号守卫就属于这一类，对“改状态”很好用。RocketMQ 两种都给：要顺序就用 Orderly，不要就用 Concurrently。

// 1. 事务消息：同一个监听器里，一个方法做本地事务，一个方法回答回查
TransactionMQProducer p = new TransactionMQProducer("order-tx-pg");
p.setTransactionListener(new TransactionListener() {
    public LocalTransactionState executeLocalTransaction(Message m, Object arg) {
        try { pay(orderId); return COMMIT_MESSAGE; }               // UPDATE … SET status='PAID' 并提交
        catch (SQLException e) { return ROLLBACK_MESSAGE; }       // 别让异常抛出去：抛出去 = UNKNOW
    }
    public LocalTransactionState checkLocalTransaction(MessageExt m) {
        return "PAID".equals(statusOf(m.getKeys())) ? COMMIT_MESSAGE : UNKNOW;  // 查主库
    }
});
p.sendMessageInTransaction(new Message("order-paid", tag, "9527", body), null);

// 2. 定时消息（5.0 起）：到点的绝对时间；4.x 只能 m.setDelayTimeLevel(1..18)
m.setDeliverTimeMs(createdAt + 30 * 60_000L);

// 3. 顺序消息：发送端按订单号选队列，消费端用 Orderly
producer.send(m, (mqs, msg, id) -> mqs.get(Math.floorMod((Long) id, mqs.size())), 9527L);
consumer.registerMessageListener((MessageListenerOrderly) (msgs, ctx) -> { apply(msgs); return SUCCESS; });

回查接口怎么写才不会误判、回查查满 15 次以后去哪了，放到 ⑥-3、⑥-4；定时消息最长 3 天、精度 1 秒、到点要不要再查一次库，放到 ⑥-5；顺序消费里一条消息一直失败会怎样，放到 ⑥-7。

⑤跑起来：交易靶场的订单服务，对着 RocketMQ 5.5.1 跑三组

    pay(id, /*commit=*/ mode.equals("half-commit-die"));      // 9530 只执行 UPDATE、不提交

}
// 父进程是同一个生产者组的另一个实例，负责回答回查
public LocalTransactionState checkLocalTransaction(MessageExt msg) {
    String st = status(db, idOf(msg));
    return "PAID".equals(st) ? COMMIT_MESSAGE
         : now() - msg.getBornTimestamp() > 10_000 ? ROLLBACK_MESSAGE : UNKNOW;
}

    第一圈 · 注意事项：不知道就会出事故

    1以为用了事务消息，消费端就不会重复← ④ 只管“发”
    现象
    支付链路换成事务消息以后，积分服务的去重表被删了，“反正一单只发一条”。一次重平衡后，积分又多发了一批。
    根源
    事务消息保证的是“库提交了 ⇔ 消息最终投出去”，一条半消息最多变成一条真消息。消费端的“处理完、位点还没提交就崩了”和 Kafka 一模一样，照样至少一次。
    做法
    消费端去重照做，写法见幂等消费与顺序消息；消息 key 用业务单号，去重表以它为主键。
    2本地事务失败时把异常抛出去← ④ 异常 = UNKNOW
    现象
    余额不足、订单已取消这类失败，消息过了半分钟才被回滚，日志里每单多一次回查；回查接口写得不严时，甚至被 COMMIT 出去。
    根源
    客户端捕获 executeLocalTransaction 抛出的异常后，按 UNKNOW 结束事务，不会替你回滚，结论只能等回查。
    做法
    方法里自己 try/catch，明确失败返回 ROLLBACK_MESSAGE；只有“说不清”（比如提交时连接断了）才返回 UNKNOW。
    3回查写成“查不到 PAID 就 ROLLBACK”← ④ 回查
    现象
    大促时偶尔有订单已经付了款，下游却从没收到消息，查日志发现这条半消息被回查 ROLLBACK 了。
    根源
    回查最早在半消息存在 6 秒后就来。本地事务那时可能还没提交（慢 SQL、锁等待），或者回查查的是还没同步过来的从库，都会看到 NEW。把“看不到”当成“没成功”，就把一笔成功的支付回滚了。
    做法
    回查只查主库；本地事务里顺手写一行事务记录（以 transactionId 或订单号为主键）；查不到时，没超过本地事务最长耗时就返回 UNKNOW，超过了再 ROLLBACK。⑤ 里用的“超过 10 秒”只是演示。
    4回查找不到人，或者一直答 UNKNOW← ④ 先计数、再找人
    现象
    发布时整组下线了几分钟，或者把生产者组改了名；又或者回查方法根本没实现。库里已经 PAID 的订单，消息永远没到。
    根源
    Broker 先把回查次数加一，再找同组在线的实例；找不到就算白查。查满 transactionCheckMax=15 次（默认 30 秒一轮，大约 7.5 分钟），半消息被移到 TRANS_CHECK_MAX_TIME_TOPIC，不再投递。回查按生产者组找人，组名改了，旧的半消息就没人认领。
    做法
    生产者组名当成接口一样固定下来；滚动发布，别整组同时下线；监控 TRANS_CHECK_MAX_TIME_TOPIC 的消息数，有就报警并人工补发。实验台的“整组下线”能看到这个过程。
    5把定时消息当成精确闹钟、长期提醒← ④ 时间轮
    现象
    “30 天后自动确认收货”发不出去，报 timer message illegal；或者取消消息到点直接取消，把刚付了款的单也取消了。
    根源
    定时消息最长 timerMaxDelaySec = 3 天（⑤ 实测 4 天被拒），精度 1 秒，只会晚不会早。它只负责“到点送达”，不知道这段时间里订单变成了什么样。
    做法
    超过 3 天的用数据库记到期时间 + 定时任务，快到期了再发 MQ；消费端到点再查一次库，用 WHERE status='NEW' 条件更新，就像 ⑤ 里没被取消的 100 单。
    64.x 想要“7 分钟后”，去改 messageDelayLevel← 历史原因
    现象
    为了一个业务把 Broker 的 messageDelayLevel 改了，别的服务发的“第 5 级”从 1 分钟变成了别的时长。
    根源
    延迟级别是 Broker 级的配置，所有 topic、所有生产者共用；5.0 之前开源版只有这 18 档。
    做法
    升到 5.x 用 setDeliverTimeMs；还在 4.x 就只用默认的 18 档，凑不出来的时长用“多级接力”或者定时任务。
    7顺序消费里一条消息一直失败，整个队列卡住← ④ 锁队列
    现象
    一单的 SHIPPED 因为数据问题一直抛异常，同一队列里其他几百单的状态全停了，堆积告警只报了一个队列。
    根源
    顺序消费失败时在本地暂停 1 秒再试同一条（suspendCurrentQueueTimeMillis），remoting 客户端默认重试次数是 Integer.MAX_VALUE。后面的消息不能越过它，否则就不是顺序了。
    做法
    设 maxReconsumeTimes，超过后客户端把它发回 Broker、进死信队列，并报警；业务上分清“重试能好”和“重试也没用”，后者直接记下来、返回成功。
    8以为发送端选了队列，就万事大吉← ④ 选队列
    现象
    扩容时把 topic 从 8 个队列加到 16 个，或者一个 Broker 挂了，那一阵子有订单显示“已退款”后又变回“已发货”。
    根源
    id % 队列数 里的队列数变了，同一单前后两条进了不同队列；Broker 挂了时，路由里少了它的队列，mqs.size() 变小，同样会换队列。和 Kafka 加分区是同一个坑。
    做法
    队列数一开始就留够，扩容放在低峰、先停写；顺序消息宁可发送失败、由上游重试，也不手动换队列；覆盖型事件再加一道版本号守卫兜底。

    第二圈 · 使用规范

    事务消息只用在“改库 + 发消息”这一处

    普通的通知、日志用普通消息。事务消息每条至少多写两次 CommitLog（半消息、OP 记录），还要回查。防的是性能被白白吃掉。

    本地事务里写一行可回查的记录

    回查靠它判断，查主库。防的是 ⑥-3。

    生产者组名固定，发布滚动进行

    组名写进配置，不随版本变；同组至少两个实例在线。防的是 ⑥-4。

    监控两个系统 topic

    TRANS_CHECK_MAX_TIME_TOPIC 有消息就报警；顺序消费组的死信队列 %DLQ%组名 有消息也报警。

    定时消息的消费端到点再查一次库

    条件更新，处理完就幂等。防的是 ⑥-5。

    选队列用 Math.floorMod 和稳定的业务 ID

    订单号是 long，hashCode() 可能是负数，直接 % 会越界。防的是发送时偶发的 IndexOutOfBounds。

    顺序消费设上限、配死信

    maxReconsumeTimes 设成十几次，超过就进死信并报警。防的是 ⑥-7。

    消费端一律幂等

    三种特殊消息都不改变“至少一次”。防的是 ⑥-1。

    第三圈 · 深处：5.x 的新客户端、事务消息的存储代价、半消息被查几次

    5.x 的 gRPC 客户端：消息类型绑在 topic 上

    RocketMQ 5 推荐的新客户端 rocketmq-client-java 经过 Proxy 访问 Broker。topic 建的时候声明类型（普通、FIFO、定时、事务），生产者发的消息要和它对上；顺序不再靠选队列，而是给消息设一个消息组（messageGroup），同一组按顺序投，消费者组要开启顺序消费。本页用的 remoting 客户端仍然能连 5.x 的 Broker，rocketmq-spring 也还用它，所以老项目升级 Broker 时，客户端可以先不动。

    事务消息在 Broker 里至少写三次

    半消息写一次，COMMIT 时真消息再写一次，再记一条 OP。检查任务每轮要把半消息队列和 OP 队列对着读一遍；每回查一次，这条半消息就被重新写回半消息队列一次，回查次数记在它的属性里。所以大量长期 UNKNOW 的半消息，会让检查越来越慢、CommitLog 越来越大。⑤ 两遍跑完，半消息队列里已经写了 12 条，其实只发了 8 条事务消息。

    回查时机的几个参数

    transactionTimeOut=6000：半消息存在不满 6 秒不查；transactionCheckInterval=30000：检查任务的周期；transactionCheckMax=15：最多查几次。单条消息可以用属性 CHECK_IMMUNITY_TIME_IN_SECONDS 把“不满多久不查”调长，适合本地事务本来就慢的业务，比调全局参数安全。半消息存在超过 CommitLog 保留期（默认 72 小时）也会被丢弃。

    版本和这一页有关的变化
    3.x开源版的事务消息去掉了回查，只剩半消息
    4.3.0事务消息连同回查重新开源：TransactionMQProducer、TransactionListener
    4.x延迟消息只有 18 个级别（messageDelayLevel，Broker 级配置）
    5.0任意时刻的定时消息（时间轮，timerWheelEnable 默认开）；Proxy 和 gRPC 客户端；topic 的消息类型、FIFO 消息组
    5.5.1本页实测版本；事务回查的三个默认值仍是 6 s、30 s、15 次，定时消息仍是 1 秒精度、最长 3 天

    这一层没有尽头

    • 5.x gRPC 客户端实测：建 FIFO 和事务类型的 topic，用消息组代替选队列，比较并行度
    • 时间轮源码：TimerMessageStore 怎么把一格的消息取出来、Broker 重启后怎么恢复、同一秒的消息太多时怎么流控
    • 事务消息的高可用：主从切换时半消息和 OP 记录怎么同步，切换后回查会不会重复
    • RocketMQ 的消费重试和死信：重试 topic、延迟级别 3 起步的退避、Pop 消费模式
    • J09 分布式事务：本地消息表、事务消息、TCC、Seata 的 AT 模式放在一起比
    • 怎么选：Kafka、RocketMQ、RabbitMQ、Redis Stream（J08 下钻的最后一个）

    ↺回到第⑤步：改一改交易靶场

    1. 回查偷懒（⑥-4）：把父进程的 checkLocalTransaction 改成永远返回 UNKNOW，等 8 分钟以上。先猜 9529 会被回查几次、最后去了哪，再用 mqadmin topicStatus -t TRANS_CHECK_MAX_TIME_TOPIC 确认。
    2. 毒消息（⑥-7）：在 orderly 里让订单 10003 的 SHIPPED 一直返回 SUSPEND_CURRENT_QUEUE_A_MOMENT，10 秒后数一数同一个队列里还有多少单没处理完；再设 maxReconsumeTimes=3 重跑，看它进了哪个 topic。
    3. 取消和支付撞车（⑥-5）：把 delay 的取消语句去掉 AND status='NEW'，猜付了款的 100 单会怎样；再想一想：取消消息先到、支付回调后到时，支付那边的 UPDATE 该怎么写。
    1. 用一句话说出这一页的精华

    RocketMQ 把“等条件满足再投”做进了 Broker：事务消息的条件是本地事务的结论，结论没来就回查；定时消息的条件是时间，靠时间轮；顺序消息则靠“发送时按业务 ID 选队列、消费时一个队列一个线程”。三样都不改变消费端的至少一次。

    2. 老办法（先提交再发、outbox）疼在哪？

    先提交再发，死在中间就丢消息（⑤ 的 9531）；先发再提交，死在中间就有一条库里没有的“已支付”（9532）。outbox 能解决，但每个服务要自己建表、写投递线程、清理。事务消息把“等结论、问结论”交给了 Broker，代价是要写一个能从库里查出结论的回查方法。

    3. 头号坑“回查误判成 ROLLBACK”的根源是哪条原理？

    ④ 回查：半消息存在满 6 秒就可能被查，Broker 并不知道本地事务还在不在跑。回查方法只能看到库里此刻的样子，看到 NEW 不等于失败。所以要查主库、要有一行事务记录，看不清时答 UNKNOW。

    4. 预测：9529 那种情况（库已提交、COMMIT 没发出去），但同组只有这一个实例，它 3 分钟后才重启。积分服务什么时候收到？

    大约 3 分钟出头。重启前的那几次回查都找不到人，白查，但回查次数照样累加（④ 先计数、再找人）。重启以后的下一轮检查（最多再等 30 秒）查到 PAID，答 COMMIT。3 分钟只用掉 6～7 次，离 15 次还远；要是 9 分钟后才重启，15 次早就用完，消息已经被移走了。可以在实验台里选“没有别的实例”“5 分钟后重启”对照着看。

    5. 预测：把 order-status 从 8 个队列扩到 16 个，消费端仍是顺序消费、发送端仍按 id % mqs.size() 选队列。扩容那一刻会出什么事？

    扩容前已经发了 PAID、扩容后才发 SHIPPED 的订单，两条可能落在不同队列（模数从 8 变 16），两个队列由不同线程甚至不同实例处理，SHIPPED 可能先生效，状态短暂倒退或最终停错。和 Kafka 加分区同一个坑（④ 选队列）。扩容后发的新订单不受影响。

    6. 放回全景：第 1 站换成事务消息以后，第 1 站前后各发生了什么？这一页讲的东西坏了，整条链路会怎样？

    第 1 站之前是支付回调到达订单服务；之后是第 2 站按订单号决定进哪个队列（RocketMQ 里就是选队列），再往后是落盘、复制、三个消费组各自消费。换成事务消息以后，第 1 站不再需要 outbox 表和投递线程，改成“半消息 → 本地事务 → COMMIT”，投递线程的活由 Broker 的回查接手。回查坏了（误判 ROLLBACK、整组下线超过 7.5 分钟），就是库里已付款、下游永远没收到：积分不加、库存不扣、通知不发，而且 Kafka 页里那些 LAG 监控全是正常的，只有 TRANS_CHECK_MAX_TIME_TOPIC 里有痕迹。选队列坏了（不选、扩容），第 2 站的顺序保证就没了，订单视图会出现“已退款又变回已发货”。第 8 站的去重仍然要做，事务消息管不到那里。

    档位：标准。RocketMQ 5.5.1 单节点（NameServer + Broker，remoting 客户端直连，没起 Proxy），rocketmq-client 5.5.1、H2 2.4.240（MySQL 模式），JDK 17.0.21，本机 2 核 ARM。Broker 只把堆从 8 GB 改成 1 GB、CommitLog 文件从 1 GB 改成 100 MB，事务和定时相关的参数都是默认值。代码按 JDK 17 编译，写法没有用到 8 以后的语法；H2 2.x 需要 Java 11，所以没有按 JDK 8 跑。
