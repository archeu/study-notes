进 JVM 看一眼：Arthas 线上诊断

指标、日志、链路都是事先埋好的，只能看到埋了点的地方。全景第 9 站要回答的“谁攥着连接、它在等什么”，哪个埋点都没覆盖到。Arthas 不用重启，attach 到正在跑的 JVM 里：读线程栈、读任意对象的字段、反编译线上实际加载的类；需要计时的时候，再临时改写某个方法的字节码，统计每一次调用里各花了多少时间、参数和返回值是什么，用完还原。本机复现了全景那一幕：5 秒 attach 上去，几条命令看到 10 个对账线程在事务里等渠道，trace 显示 20 秒里 100% 花在 queryOrder 上。

①为什么学：埋点看不到的地方，现场又不能丢

全景第 9 站，03:24：大盘说 order-3 的池子 10/10，日志说拿不到连接，可占着连接的是对账线程，它们不在下单请求的链路里，也没打日志。这时候要回答三件事，而且不能重启：一重启，线程栈和池子的状态就没了，对账任务还可能换到别的实例上接着跑。

此刻谁在干什么线程栈、对象的字段
一次调用里时间花在哪每一行调用各多久
线上跑的是不是这版代码反编译已加载的类

②老办法：jstack、加日志重发、远程调试

老办法能做到放到第 9 站
jstack / jcmd Thread.print此刻所有线程的栈，JDK 自带能看到 10 个线程卡在 socket 读上，这一步其实够用（JVM 排查那页就靠它）。但它只是一张快照：看不出每次调用花多久，也读不了池子对象里的数
加日志、加计时，重新发布想看什么都能打发布要十几分钟；发布就是重启，现场没了，问题可能也跟着暂时消失
远程调试（JDWP 断点）能看任何变量断点一停就是整个线程停住，在生产上等于制造故障；还要提前带调试参数启动
jmap 堆转储所有对象都在几个 G 的文件，转储时进程可能停顿几秒到几十秒，拿回来还得慢慢分析

缺的是：在不停机、不重新发布的前提下，临时给某个方法加上计时和打印，看几次就撤掉；再加上随手读一读任意对象。Arthas 的精华就在这两件事上。

不懂这一点时的典型误用：把 Arthas 当成“高级 jstack”，只会 thread；或者反过来，一上来就对一个每秒调几千次的方法 trace，不加次数限制，增强进去的计时代码和满屏输出把本来就吃紧的服务压得更慢。

③选谁

工具擅长不擅长
jstack、jcmd、jstatJDK 自带，人人会用；线程栈、GC 统计看不到方法耗时、参数，读不了对象
JFR（JDK Flight Recorder）持续低开销录制：CPU 采样、锁、IO、GC 事件，事后分析不能“临时看一下某个方法的参数”
async-profilerCPU、分配、锁的火焰图，开销小采样看整体热点，看不到单次调用的细节
Arthas交互式：线程、对象、反编译，临时增强方法看耗时、参数、返回值、异常；内置 async-profiler要 attach 进进程，有一定风险和开销；生产上使用要有规矩（⑥）
BTrace、greys早期的同类工具BTrace 要写脚本；greys 已停止维护，Arthas 就是从它演化来的

选择规则：只要一张快照，jstack 就够；CPU 高、要看热点，用 async-profiler 出火焰图（Arthas 里的 profiler 命令就是它）；要持续录、事后分析，开 JFR；要在活着的进程里看某一类调用的耗时、参数、返回值，用 Arthas。本页学 Arthas 4.3.5。

④原理：attach 进去，读的直接读，要计时的临时改字节码

先知道这些
  • Attach API：JDK 提供的“给正在跑的 JVM 加载一个 agent”的接口。同一个用户的进程才能 attach，目标 JVM 用 Unix socket 接收指令，所以工具要用 JDK，光有 JRE 不行。
  • Instrumentation：agent 拿到的一个接口，能列出所有已加载的类，能 retransformClasses：把某个类的字节码改掉，让新进入的调用走新代码。链路那页的 agent 在类加载时改，Arthas 是在类已经加载好之后改。

attach 以后，进程里多了什么

trace 怎么知道每一行花了多久

原来的方法
@Transactional
public void reconcileOne(long orderId) {
    jdbc.queryForList(...);              // #26
    Map r = payChannel.queryOrder(orderId);  // #27
    jdbc.update(...);                    // #29
}
trace 增强以后，相当于示意
public void reconcileOne(long orderId) {
    Spy.atEnter(...);
    t = nanoTime(); jdbc.queryForList(...);  Spy.invoke(#26, nanoTime() - t);
    t = nanoTime(); payChannel.queryOrder(); Spy.invoke(#27, nanoTime() - t);
    t = nanoTime(); jdbc.update(...);        Spy.invoke(#29, nanoTime() - t);
    Spy.atExit(...);   // 汇总成一棵树，打给客户端
}

trace 在方法入口、出口和方法里的每一次调用前后插入计时；watch 只在入口或出口插一下，把参数、返回值、异常按你写的表达式（OGNL）取出来。默认只展开一层：想知道 queryOrder 里面又慢在哪，就再 trace 它。改写的是类，对所有线程生效；而正在执行的那一帧还是旧代码，所以只看得到增强以后才进入的调用。下面这个时间线就是这个规则：

什么时候敲 trace，结果多久才出来

场景：10 个对账线程，每个线程一笔接一笔，每笔都在等渠道。⑤ 里每笔 20 秒，任务开始后第 41 秒左右敲的 watch。

为什么这样设计

改字节码，不用断点

断点要让线程停下来等人看，生产上停一个线程就是一个卡住的请求。改字节码不停任何线程，每次调用只多花一点计时的时间，结果攒好了再推给客户端。代价：只看得到之后进入的调用；调用很频繁时，这点开销会被放大（⑥ 坑 1）。

自己的类加载器、只监听本机

Arthas 自带的 Netty、OGNL 等库用独立的类加载器加载，不会和应用里同名的库冲突；服务端默认只监听 127.0.0.1，要从别处连，得显式改地址或者经过 tunnel。被放弃的设计：把诊断代码直接塞进应用的 classpath，版本冲突和安全问题都会更多。

默认有次数和还原

-n 到了次数命令就退出，stop 会还原所有增强过的类。诊断是临时的，所以默认就往“少看几次、用完还原”这边偏，不让它变成常驻的监控。常驻的需求交给指标和链路。

⑥细节·规范·优化

第一圈 · 不知道就会出事的

1对每秒几千次的方法 trace，不加限制← ④ 每次调用多走计时代码
现象
本来就慢的服务更慢了，客户端被成千上万条输出刷屏。
根源
增强改的是类，所有线程的每一次调用都要多走计时和汇总；调用越频繁，开销越大。
做法
先用 -n 限次数；用条件只看想看的：trace … '#cost > 1000'（只看超过 1 秒的）、watch … 'params[0] == 31'；先 trace 外层，确定慢在哪一行，再往里一层。
2查完直接关了终端，没有 stop← ④ 默认有还原
现象
几天后发现那个方法还慢一点点，进程里多了一个监听 3658 的端口和几个 arthas 线程。
根源
退出客户端不等于卸载：服务端还在目标进程里。还没跑完的 watch、trace 留着增强过的类；-n 跑完的会自己撤销监听，但服务端和端口都还在。
做法
用完执行 stop（关服务端并还原增强过的类）；只想撤掉增强、继续用就 reset；把“已 stop”写进事故时间线。
3敲了 watch，一直不出结果⑤ 实测← ④ 只看得到之后进入的调用
现象
⑤ 里 watch 等了 40 秒。调用更慢、或者调用很少（一天跑一次的任务），可能一直等不到。
根源
正在执行的那一帧用的是旧字节码，增强只对新进入的调用生效。
做法
慢调用正在卡着的时候，先用 thread、stack 看现场；trace、watch 用来看后面的调用。想复现，就主动再触发一次。
4容器里 attach 不上← ④ Attach API 的前提
现象
镜像里只有 JRE，或者用 root 去 attach 一个以普通用户运行的进程，报“Unable to attach”；有的进程启动参数里带了 -XX:+DisableAttachMechanism。
根源
attach 要用 JDK 的工具，要同一个用户，还要目标 JVM 允许。
做法
在镜像里留一个带 JDK 的诊断层，或者用临时容器（kubectl debug）共享进程命名空间；以和应用相同的用户执行。多台机器用 Arthas tunnel 统一接入。
5在生产上用 redefine、retransform 热改代码← ④ retransformClasses
现象
线上“修好了”，重启以后问题又回来；或者三台机器里只改了一台，行为不一致。
根源
热替换只在这个进程的内存里，重启就没了；JVM 也只允许改方法体，不能加字段、加方法。
做法
只在止血时用，用了就当成一次线上变更：记录、通知，尽快发正式版本替换。
6vmtool 把几百万个对象捞出来← ④ 只读命令也要遍历堆
现象
vmtool --action getInstances --className java.lang.String，进程卡住、内存涨。
根源
按类找实例要遍历堆，结果还要在进程里组装成对象列表。
做法
只对实例很少的类用（数据源、连接池、单例的 Bean），加 --limit；--action forceGc 别在高峰用。

第二圈 · 团队里怎么定

  1. 先只读，后增强：dashboard、thread、vmtool、jad 先看一圈，确定要看哪个方法，再 trace、watch。防的是：一上来就增强，开销加在最紧张的时候。
  2. 增强命令必须带 -n 或条件。防的是：坑 1。
  3. 用完 stop，写进时间线：几点 attach、做了什么、几点 stop。防的是：坑 2，也方便复盘时说清楚当时的操作。
  4. 生产使用要有入口和权限：通过堡垒机或 tunnel 接入，留审计；redefine、ognl 调写方法这类会改状态的命令要审批。防的是：诊断工具被当成后门。
  5. 先留现场再止血：要重启之前，先 thread 或 jstack 留一份线程栈，必要时 heapdump。防的是：全景预测题 4 说的“现场没了，根因要等下次”。

第三圈 · 再往深一点

CPU 高的时候：profiler 出火焰图

这一次 CPU 不高。CPU 高的时候，thread -n 3 能找到最忙的线程，但一张栈只是一个瞬间；profiler start、等 30 秒、profiler stop --format html 用内置的 async-profiler 采样出火焰图：越宽的格子，占的 CPU 越多。它只采样，不改字节码，开销比 trace 小得多。

monitor 和 tt

monitor -c 5 类 方法 每 5 秒统计一次调用数、成功失败数、平均耗时，像一个临时的指标。tt -t 类 方法 把每次调用的参数、返回值都存下来，之后可以按编号查看，甚至用同样的参数重放一次（重放会真的执行，生产慎用）。

ognl 和 vmtool 能做的事

读 Spring 容器里任意 Bean 的字段、调它的 getter：比如读 HikariCP 的配置看 maximumPoolSize 是不是真的 10，读 Nacos 动态配置的当前值。能调方法也就能改状态，所以第二圈把它列进了要审批的命令。

和 JFR 怎么配合

JFR 适合一直开着：开销很低，出事以后把前几分钟的录制导出来看锁、IO、GC 和 CPU 采样。Arthas 适合出事时上去问具体问题。两者不冲突：先看 JFR 录下的整体情况，再用 Arthas 盯某个方法。

  2. 只看慢的：把第 6 条改成 trace … reconcileOne '#cost > 10000' -n 1，渠道调回 50 毫秒后再调成 20 秒，看什么时候才有输出。（坑 1）
  3. 不 stop 会怎样：去掉最后的 stop，跑完以后 ss -ltnp | grep 3658，再 attach 一次看 jobs。（坑 2）

自测

1. 用一句话说出这一页的精华

Arthas 用 Attach API 把 agent 加载进正在跑的 JVM，只读的命令直接读线程和对象，trace、watch 这类命令用 retransformClasses 临时改写方法字节码去计时、取参数，用完还原；所以能在不停机、不发布的情况下看到埋点没覆盖的地方。

2. 老办法（jstack、加日志重发、远程调试）各疼在哪？

jstack 只有一张快照，没有耗时和对象状态；加日志要发布，发布就是重启，现场没了；远程调试的断点会把线程停住，在生产上等于制造故障。

3. 坑 3（watch 一直不出结果）的根源是 ④ 的哪一条？

增强只对新进入的调用生效：正在执行的那一帧用的是旧字节码。敲命令时正卡着的那批调用看不到，要等下一批开始并结束。

4. 预测：⑤ 里如果渠道不是慢，而是对账线程在等一把 synchronized 锁，第 2、3 条命令会看到什么？

第 2 条里对账线程的状态会是 BLOCKED（不是 RUNNABLE）；第 3 条的栈顶会是业务方法，下面写着 “waiting to lock …”，能看到锁对象和持有者线程。thread -b 可以直接找出挡住最多线程的那个持锁者。

5. 预测：对 JdbcTemplate.update 做 trace 而且不加 -n，凌晨对账时会怎样？白天高峰呢？

凌晨调用少，开销不明显，输出会持续到你手动结束；白天高峰每秒几千次 update 都要多走计时、汇总和输出，CPU 和延迟都会上升，客户端被刷屏。所以高频方法一定要加 -n 或条件。

6. 放回全景：第 9 站前后各是什么？如果那晚没有 Arthas，只能用 jstack，能走到同样的结论吗？

前面是第 8 站：问“变了什么”，找到 03:00 的对账任务；后面是第 10 站，关任务开关止血。只用 jstack 也能看到 10 个对账线程在事务里等 socket 读，“事务里调远程”这个结论能推出来；但看不到每笔要等多久（20 秒还是 30 秒）、读不到池子里 4 个在等，要靠指标和渠道侧的数据来补。结论差不多，证据弱一些，时间也会长一些。

档位：标准。本机跑过（2 核 ARM 虚拟机，JDK 17，Spring Boot 3.5.16，Arthas 4.3.5）：./run.sh 完整一次，⑤ 的每一段输出都来自这次运行（节选时删去了部分栈帧和完整包名）；调试时还手动跑过一次，渠道延迟 60 秒，超过 30 秒读超时，看到对账线程因为异常被换成了新线程（线程名编号变大）。④ 的时间线模拟在 node 里跑过，⑤ 里 watch 等了 40 秒和它一致。

按文档：Arthas 服务端默认监听 127.0.0.1 的 3658（telnet）和 8563（http）；stop 关闭服务端并重置增强过的类，reset 只重置增强；trace 默认跳过 JDK 方法，支持 #cost 条件；jad 用 CFR 反编译；profiler 基于 async-profiler。JVM 的类重定义只能修改方法体。
