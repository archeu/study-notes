慢在哪一段：链路追踪，OpenTelemetry 和 SkyWalking

指标告诉你 order-3 的下单慢了，链路告诉你慢在哪一段：一个请求经过的每一次 HTTP 调用、每一条 SQL、每一次跨线程，都记成一个 span，按父子关系拼成瀑布图。在 Java 里接链路，用不着改业务代码：启动时挂一个 -javaagent，它在类加载时往 Tomcat、Spring MVC、HTTP 客户端、JDBC、线程池里织入开始和结束计时的代码，并在 HTTP 头里替你传 traceparent。读瀑布图的要点在空白：一段时间没有任何子 span 盖住，说明时间花在进程自己里面。全景第 6 站那 3 秒就是这样一段空白，本机实测复现了一次。

①为什么学：大盘说“order-3 慢”，还得知道“慢在哪一段”

全景第 6 站：值班在链路库里筛出 order-3 上超过 2 秒的 trace，一条 POST /api/orders 3.01 秒，下面只有一个 2 毫秒的子 span，之后 3 秒空白。值班由此判断：不是 MySQL 慢，也不是下游慢，时间花在 order-svc 进程自己里面。这样就省了一轮“先去查数据库”。换到 AI 主线也一样：值班助手一次回答调了几次模型、几次工具，每次花了多久、用了多少 token，靠的也是这棵树。

它回答慢在哪一段哪一跳、哪条 SQL、哪个线程
它要求上下文一路传下去跨线程、跨进程、跨消息
它的代价按请求 × 跳数存所以要采样

②老办法：每个服务打耗时日志，各看各的 P99

缺的是同一个请求在所有服务里的完整时间线。拿到它要两样东西：每一段都计时（插桩），每一段都知道自己属于哪个请求、父亲是谁（传上下文）。这两样都得覆盖到框架和第三方库里，手写是写不全的。

不懂这一点时的典型误用：网关、订单接了链路，库存服务没接，或者中间一个 Nginx 把 traceparent 头丢了。链路库里于是有两棵各自完整、互相不认识的树，看着都正常，跨服务那一跳却恰好断在最想看的地方。

③选谁

方案怎么接好处代价
OpenTelemetry Java agent-javaagent:opentelemetry-javaagent.jar，OTLP 发给 Collector 或任何兼容后端不改代码；标准协议，后端随便换（Jaeger、Tempo、SkyWalking、云厂商）agent 要跟着框架版本升级；插桩出来的 span 多，要控制
Micrometer Tracing（Spring 原生）加依赖，Spring Boot 自动配置，桥到 OTel 或 Brave和 Spring 的 Observation、指标一体；三件套那页用的就是它只覆盖 Spring 认识的组件，JDBC、线程池要自己补
SkyWalkingSkyWalking Java agent + OAP 服务端 + UI，存储用 BanyanDB 或 ES国内用得多；自带服务拓扑、告警、性能剖析，一套全有自有协议（头是 sw8），和 Prometheus、OTel 生态是两套
Zipkin / Brave老牌，Spring Cloud Sleuth 时代的默认简单新项目已少用

选择规则：新项目用 OpenTelemetry：不想改代码挂 agent，Spring Boot 3 原生偏好用 Micrometer Tracing 桥到 OTel，二选一，别两个同时开（⑥ 坑 5）；团队已经有 SkyWalking 的继续用，新版本的 OAP 也能接收 OTLP。本页学 OpenTelemetry Java agent 2.33.1，后端用 Jaeger 2.23.0，SkyWalking 只在 ⑥ 里讲它和 OTel 差在哪。

④原理：类加载时织入计时代码，上下文跟着请求走，span 攒一批发出去

先知道这些
  • -javaagent：JVM 启动参数，指定一个 jar。JVM 先跑它的 premain，它拿到 Instrumentation 以后，就能在每个类加载时改它的字节码。类加载那页讲过类是什么时候加载的。
  • span、trace_id、traceparent：见 三件套 ④。这一页不重讲结构，只讲它们是谁、在哪一刻生成和传递的。

agent 做了三件事

span 从 JVM 到你眼前

读瀑布图：看自身耗时，找空白

一个 span 的时长里，被子 span 盖住的部分是“在等别人”，没被盖住的叫自身耗时：花在这个进程自己的代码里，或者在等某个没被插桩的东西，比如锁、连接池、GC。下面三条 trace，前两条是 ⑤ 实测的，第三条是为了对比编的“下游慢”。点一下每个 span，看它的自身耗时：

为什么这样设计

插桩放在 agent 里，不放在业务代码里

要覆盖的是框架和第三方库：Tomcat 收请求、HTTP 客户端发请求、JDBC、线程池。这些代码你改不了，只能在类加载时织入。被放弃的设计：每个团队在业务代码里手写打点，覆盖不全，名字和属性也不统一。代价：agent 和框架版本绑在一起，框架大版本升级时，要先确认 agent 支持。

上下文走标准的 HTTP 头

W3C traceparent 是标准，网关、Nginx、云负载均衡、别的语言写的服务都认得它，一棵树才能跨过它们不断开。被放弃的设计：每家 APM 一种头（Zipkin 的 X-B3-*、SkyWalking 的 sw8），混用时链路在边界上断掉。

应用只管发，处理交给 Collector

应用里只做最便宜的事：计时、攒批、异步发 OTLP。采样策略、脱敏、转发到哪个后端，都放在 Collector 里改，不用重新发布应用。尾部采样也只能在这里做：要等一棵树的所有 span 都到齐，才知道它慢不慢、错没错。

最少的写法

启动参数代码和依赖一行都不用改
OTEL_SERVICE_NAME=order-svc \
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318 \      # Collector 或 Jaeger
OTEL_METRICS_EXPORTER=none OTEL_LOGS_EXPORTER=none \     # 这里只要链路
java -javaagent:opentelemetry-javaagent-2.33.1.jar -jar order-svc.jar

# 日志里打出 trace_id（agent 放进 MDC 的键是 trace_id、span_id）
logging.pattern.level=%5p [trace_id=%X{trace_id}]

采样率、自己加 span、MQ 和异步怎么续上、SkyWalking 和它差在哪，都放到 ⑥。

⑤跑起来：两个服务挂上 agent，span 进 Jaeger，再把全景第 6 站复现一次

看懂这次运行
  • 6 个 span、2 个服务、3 个线程拼成一棵树，SQL 也有 span：这些都是 agent 加的，代码没动过。
  • 通知那条 INSERT 跑在普通 JDK 线程池的 pool-4-thread-1 上，照样挂在下单的根 span 下面，日志里的 trace_id 也一样：agent 插桩了 ThreadPoolExecutor，提交任务时把上下文包了进去。三件套那页用 Micrometer 时，同样的线程池要自己加装饰器。
  • 慢的那条只有 12 毫秒被子 span 盖住，3 秒全是自身耗时；ERROR 日志里的 trace_id 和 Jaeger 里那条是同一个，一跳就能从链路到日志。这就是全景第 6、7 站。

⑥细节·规范·优化

第一圈 · 不知道就会出事的

1全采太贵，按比例采又会漏掉慢的那条← ④ Sampler 在根上决定
现象
agent 默认 parentbased_always_on 全采，量 = 请求数 × 跳数；改成 parentbased_traceidratio 1%，凌晨那几条 3 秒的请求有 99% 的概率没被留下。
根源
头部采样在请求一进来就决定，那时还不知道它会慢、会错。
做法
应用里全采或高比例采，在 Collector 用 tail_sampling 处理器：错误的、超过阈值的全留，其余按比例留（全景第 6 站的配置）。
2经过 MQ，链路断成两棵树← ④ 传上下文
现象
下单发一条“订单已创建”消息，消费者那边的 span 自成一棵新树，查不到它是被哪一单触发的。
根源
上下文跨进程要靠载体：HTTP 用头，消息要放进消息的属性或 header。客户端库不在 agent 的支持列表里，或者自己封装了发送和消费，就没人放、没人取。
做法
先查 agent 支持的库和版本（Kafka、RabbitMQ、RocketMQ 等都有插桩）；自己封装的，用 OpenTelemetry API 的 propagator 手动 inject、extract。批量消费时，一条消息对应多个上游，用 span link 而不是父子关系。
3看到空白，就以为是“链路没接全”← ④ 自身耗时
现象
⑤ 那条 3 秒的 trace，第一反应是“少了 span，agent 有问题”，于是去折腾配置。
根源
空白就是自身耗时：等锁、等连接池、GC、CPU 计算这些都不会有子 span。它说明时间花在本进程里，正好是一个线索。
做法
空白处去对同一个 trace_id 的日志（⑤ 那行“拿不到连接”）、同一时刻的指标（连接池、GC），还不够就上 Arthas 看线程（J13 下一页）。
4网关、Nginx 把头丢了或重新生成← ④ 走标准的 HTTP 头
现象
从网关往后的 trace 都是新的根，App 带来的 trace_id 在网关就断了；或者网关自己生成一个新的 traceparent 覆盖了上游的。
根源
链路是一跳一跳传下去的，中间任何一跳不转发或者覆盖这个头，后面就接不上。
做法
网关和代理要么也接 OTel（Spring Cloud Gateway 挂 agent 就行），要么至少原样透传 traceparent、tracestate。
5Micrometer Tracing 和 agent 同时开← ④ 改字节码
现象
一个请求出现两套 span，或者 trace_id 在日志里有两个键：traceId（Micrometer，三件套那页）和 trace_id（agent，本页实测），日志平台上的查询只认其中一个。
根源
两套东西各自插桩、各自生成上下文、各自写 MDC。
做法
一个服务只选一套；全公司统一日志里的字段名，必要时在日志格式里做映射。
6span 属性里放了手机号、整段 SQL 参数历史原因
现象
链路库成了另一个能查到用户隐私的地方；或者自己加 span 时把订单号拼进 span 名字，后端按名字建的索引炸开。
根源
span 属性会原样存进后端，而名字被很多后端当成维度。agent 默认会把 SQL 里的字面量替换成 ?，自己加的属性没人替你脱敏。
做法
名字用模板，ID 放属性；敏感字段不进属性，或者在 Collector 用处理器统一脱敏。

第二圈 · 团队里怎么定

  1. 资源属性写全：service.name、service.version、deployment.environment，用 OTEL_RESOURCE_ATTRIBUTES 统一配。防的是：测试环境和生产的 trace 混在一起，分不清是哪个版本。
  2. 中间放一层 Collector：应用只发给本机或本集群的 Collector。防的是：换后端、改采样、加脱敏都要重新发布所有应用。
  3. trace_id 回给调用方：放进响应头，错误页上也显示。防的是：用户报障时说不清是哪一次。
  4. agent 版本跟着框架走：升级 Spring Boot、HTTP 客户端、MQ 客户端大版本前，先查 agent 的支持列表。防的是：升级以后某一类 span 悄悄消失。
  5. 自己加的 span 要有理由：只给业务上关心的一段加（比如“风控校验”），用 @WithSpan 或 API。防的是：一个请求几百个 span，又贵又难看。

第三圈 · 再往深一点

Collector 的尾部采样

processors:
  tail_sampling:
    decision_wait: 10s          # 等这么久，让一棵树的 span 到齐
    policies:
      - { name: errors, type: status_code, status_code: { status_codes: [ERROR] } }
      - { name: slow,   type: latency, latency: { threshold_ms: 2000 } }
      - { name: rest,   type: probabilistic, probabilistic: { sampling_percentage: 10 } }

代价：Collector 要在内存里攒 10 秒的 span；同一个 trace 的 span 必须落到同一个 Collector 实例上，多实例时前面要按 trace_id 做负载均衡。

SkyWalking 和 OpenTelemetry 差在哪

SkyWalking 是一整套：Java agent（同样是字节码插桩）、OAP 服务端（接收、分析、告警）、UI 和存储。它用自己的 sw8 头，自带服务拓扑图、端点级指标、按 trace 剖析线程栈。OpenTelemetry 只定标准、做采集，存储和界面交给 Jaeger、Tempo 或云厂商。已经有 SkyWalking 的团队不必迁移；新建的、要和 Prometheus、多语言打通的，选 OTel。

agent 的开销在哪

启动时要扫描、改写大量类，启动会慢一些、元空间多占一些；运行时每个 span 是几个对象加一次入队，业务线程上很轻，导出在后台线程。真正要盯的是 span 数量：一个请求如果有上百条 SQL（N+1 查询），span 和导出量都会跟着暴涨。

版本差异

OTel Java agent 1.x → 2.x默认 OTLP 协议从 gRPC 换成 http/protobuf（端口 4317 → 4318）；HTTP 语义约定换成稳定版，属性名变了（如 http.method → http.request.method）
Jaeger 1.x → 2.x2.x 基于 OpenTelemetry Collector 重写；本机 2.23.0 上旧的 /api/traces 返回 404，查询要走 /api/v3/traces（实测）

自测

1. 用一句话说出这一页的精华

agent 在类加载时给框架和库织入开始、结束 span 的代码，用 ThreadLocal 里的 Context 和 traceparent 头把上下文传过线程和进程，结束的 span 批量用 OTLP 发出去；读瀑布图时看自身耗时，空白说明时间花在本进程里。

2. 老办法（各服务打耗时日志）最大的问题是什么？

拿不到同一个请求在所有服务里的完整时间线：P99 各算各的不能相加，日志按时间对不上，手写打点覆盖不到框架和线程池。

3. 坑 3（看到空白以为链路没接全）的根源是 ④ 的哪一条？

自身耗时：span 的时长里没被子 span 覆盖的部分，就是花在本进程里的时间，等锁、等连接池、GC 都不会有子 span。空白是线索，不是故障。

4. 预测：把 notifyPool 换成自己 new Thread(...).start()，通知那条 INSERT 还在同一棵树里吗？

不一定。上下文要在“提交任务”时被捕获，agent 插桩的是 Executor 一类的提交入口；直接 new Thread 有没有被覆盖，要看 agent 的插桩范围，不能想当然。可以照 ↺ 练习 3 的办法实测：没被覆盖的话，INSERT 会成为一棵新树的根，日志里的 trace_id 也会是空的或者另一个。

5. 预测：Collector 尾部采样设成“错误和超过 2 秒的全留，其余 10%”，⑤ 那条 3 秒的 trace 一定能查到吗？如果有两台 Collector 呢？

一台时一定能：它会等 decision_wait，把整棵树攒齐，看到根 span 3 秒就留下。两台时，order-svc 的 span 和 product-svc 的 span 可能落到不同的 Collector，各自只看到半棵树，判断就不准，甚至只留下一半。所以前面要按 trace_id 做负载均衡，让同一棵树进同一台。

6. 放回全景：第 6 站前后各是什么？如果 order-svc 没接链路，那晚会怎样？

前面是第 5 站，大盘缩到 order-3 的连接池；后面是第 7 站，按 trace_id 查日志。没有链路，第 5 站之后就不能马上排除“MySQL 慢”和“下游慢”，值班多半会先去查数据库慢日志、库存服务的大盘，多花几分钟；第 7 站也没有 trace_id 可搜，只能按实例和时间翻日志。

档位：标准。本机跑过（2 核 ARM 虚拟机，JDK 17，Spring Boot 3.5.16，opentelemetry-javaagent 2.33.1，Jaeger 2.23.0 内存存储）：./run.sh 完整一次，⑤ 的输出、trace_id、span 时长都来自这次运行；④ 读瀑布图里的前两条 trace 用的是这次的时长，开始时间按瀑布图位置换算，第三条是编的对照。模拟逻辑在 node 里跑过。

按文档：agent 默认采样器 parentbased_always_on，BatchSpanProcessor 默认每 5000 ms 导出一次，2.x 默认 OTLP 协议 http/protobuf；agent 的 logback MDC 插桩写入 trace_id、span_id（实测看到 trace_id）；Collector contrib 的 tail_sampling 处理器支持按状态码、延迟、概率等策略；SkyWalking 的跨进程头是 sw8。实测：Jaeger 2.23.0 旧查询接口 /api/services、/api/traces 返回 404，/api/v3/* 可用。
