一个请求，三样数据：日志、指标、链路三件套

同一个下单请求，可以用三种方式记下来。指标把成千上万次请求压成几个数：便宜，能拿来告警，但细节没了。日志一次事件记一行：细节都在，可量随流量一起涨。链路把一个请求在各个进程里经过的每一段连成一棵树，告诉你时间花在了哪一段。这三样单拿出来都不新鲜，要紧的是把它们串起来：同一个 trace_id 同时出现在日志的字段里、指标的 exemplar 里、链路的每个 span 上，出事时就能从一样数据跳到另一样。

全景：凌晨三点，告警响了 · 第 1、7 站地图：J13 · 日志、指标、链路三件套

这一页的位置J13 第 1 个知识点，后面 Prometheus、链路追踪、Arthas 几页都建立在这三样数据上。会用到 ThreadLocal（链路上下文在进程里靠它传）和 Spring Boot 自动配置（加个依赖，指标和链路就自己接上了）。

①为什么需要：告警响的那一刻，手里得已经有数据

在全景第 1 站，order-svc 平时就要往外送三样数据，因为出了事再去加日志、接监控已经晚了。到第 7 站，值班的人拿着链路里看到的 trace_id 去日志里搜，一下就搜到了那行“拿不到连接”。全景里每一次缩小范围，都要回答下面这几个问题里的一个：

有没有事、多严重指标错误率 33%，只在 order-3
时间花在哪一段链路3 秒里没有子 span
那一刻发生了什么日志拿连接超时，waiting=38
怎么从一样跳到另一样trace_id三样数据共用的钥匙

②没有它会怎样：凌晨三点，SSH 进三台机器 grep

老办法：每台机器写一个文本文件 order.log，想到哪打到哪，比如 log.info("下单成功")。告警是用户打电话来报的。

痛点归起来就两条：缺一个能一直算、又便宜的“数”，以及缺一根把同一个请求的所有记录串起来的“线”。指标补的是第一条，链路和 trace_id 补的是第二条。日志本身没被换掉，只是从随手写的文本，变成了带字段、带 trace_id、集中存放的结构化日志。

不懂这一点时的典型误用：三样东西各接各的。日志进 ELK，指标进 Prometheus，链路进 SkyWalking，三边的 ID 对不上，出了事还是在“对时间”。也有只接了指标、告警响了却没有日志可查细节的。三件套真正值钱的地方在 ID 串起来以后，单接上三个系统还不够。

③相邻方案：谁来产出这三样数据

做法怎么做好处代价
只有日志，指标从日志里算ELK 把日志收上来，聚合查询算错误率只维护一套成本随流量线性涨；告警要扫日志，延迟以分钟计；跨服务仍然串不起来
APM 一体：SkyWalkingJava agent 挂到进程上，自动采链路、指标，关联日志不改代码；Java 生态成熟，自带界面自有协议和存储；和 Prometheus 体系是两套
OpenTelemetry一个标准：API、SDK、Java agent、Collector、OTLP 协议，三种信号都管厂商中立，后端可换；agent 零代码组件多；Java agent 靠字节码增强，版本要跟着框架走
Micrometer（Spring 原生）指标门面 + Observation API + Micrometer Tracing（桥接到 OpenTelemetry 或 Brave）Spring Boot 3 自动配置；一次埋点同时得到指标和 span只管 JVM；导出链路还是要走 OTLP

选择规则：Spring Boot 3 的新服务，用 Micrometer 出指标，Micrometer Tracing 桥到 OpenTelemetry 出链路，再加 Spring Boot 自带的结构化日志；多语言、不想改代码的老项目，挂 OpenTelemetry Java agent；团队已经在用 SkyWalking，就继续用。本页用 Spring Boot 原生这一套，因为它最能看清楚三样数据是怎么生出来、怎么串起来的。OpenTelemetry agent 和 SkyWalking 放到 链路追踪那一页去比。

④原理：三种数据形状，一根线把它们串起来

先知道这些
  • MDC：SLF4J 给每个线程配的一个小 Map，底下就是 ThreadLocal。往里放的键值对，日志框架打每一行时都会带上，比如 traceId。
  • HTTP 头：请求最前面那几行 名字: 值。跨进程传 trace 上下文，靠的就是在头里多加一行。
  • Actuator：Spring Boot 的运维端点，/actuator/prometheus 就是它暴露出来的。

同一批 5 个请求，三种记法

凌晨这 5 单里有 4 单 30 毫秒左右就成功了，第 4 单等了 3 秒才失败。三样数据分别把它们记成了下面这样：

指标日志链路
记的是什么聚合以后的数：计数、当前值、耗时分布一次事件一个请求经过的每一段（span），连成一棵树
回答的问题有没有事、多严重、趋势怎样那一刻具体发生了什么时间花在哪、调用了谁、在哪一跳出的错
成本跟什么走时间序列的条数，基本不随流量变随流量线性涨随流量 × 跳数涨，所以要采样
能拿来告警吗主力：规则每 15 秒算一次能，但贵、慢不适合，被采样过
最小单位名字 + 一组标签 = 一条时间序列一行带字段的记录（JSON）span：trace_id、span_id、父 span_id、名字、开始时间、时长、属性

指标：进程里只是几个累加的数

应用里，一个计数器就是内存里一个不断累加的 double；计时器多几个数：次数、总耗时、最大值，开了直方图还有每个桶的计数。Prometheus 来拉的时候，应用把此刻的累计值交出去；“每秒多少次”“P99 多少”都是 Prometheus 拿前后两次的差算出来的（下一页讲）。所以指标的成本只跟有多少条序列有关：orders_placed_total{channel="app"} 是一条，标签值每多一种，就多一条。⑤ 里整个 order-svc 实测是 479 条。

链路：span 是一段计时，父子关系靠传上下文

一个 span 就是“谁在什么时候开始、做了多久、做的是什么”。同一个请求里的所有 span 共用一个 trace_id，每个 span 记住自己的父亲是谁，于是能拼回一棵树。难点在于让下一段知道“我的父亲是谁”：

进程里：放在 ThreadLocal

当前 span 存在当前线程的上下文里（Micrometer Tracing 下面是 OpenTelemetry 的 Context）。新开的 span 先看当前有没有，有就认它做父亲。顺带把 traceId、spanId 写进 MDC，日志就有了这两个字段。代价：换了线程，上下文不会自己跟过去（⑥ 坑 1）。

跨进程：写进 HTTP 头

出站时客户端在请求头里加一行 traceparent（W3C Trace Context，Spring Boot 3 默认），收到请求的一方从头里读出来，新 span 的父亲就是上一跳的 CLIENT span。MQ 消息、RPC 也是同样的办法：放进消息属性或 RPC 附件。

traceparent: 00-a1bb075617fdf788abafd29a3066e0c5-f4bc00e1928ce754-01
版本 00 · trace_id，32 位十六进制 · 父 span_id，16 位十六进制（这里是 ⑤ 里 RestClient 那个 CLIENT span） · 标志位 01 = 已采样

为什么非得是三样，不能只要一样

  
逼出这个设计的约束是：值班要的三种能力，成本特征完全不同。秒级发现要一直在算，所以必须便宜，最好和流量无关；看到细节要每次事件都留，成本没法不随流量涨；看清路径要把上下文跨线程、跨进程传下去。没有哪一种数据形状能同时做到便宜和详细。下面按 order-svc 白天 300 次/秒估一下一天的量：

  
  

    
放弃 A：全部打日志，指标从日志里算
告警要先把日志收上来再聚合，延迟以分钟计；量随流量涨，存得越久越贵；跨服务的请求还是串不起来，因为没人传上下文。

    
放弃 B：全部用链路，100% 采样
每个请求 × 每一跳都存，最贵；一旦为了省钱开采样，从链路里算出的错误率就不准了，告警没法建在它上面。

    
选中：三种形状，加一个共享的 ID
指标管发现，便宜、全量、和流量无关；链路管路径，采样；日志管细节，按级别控制量。trace_id 让三样可以互相跳：指标的 exemplar → 链路 → 日志。

⑥细节·规范·优化

  

  
第一圈 · 不知道就会出事的

  

    
1换了线程，日志里的 traceId 没了⑤ 实测← ④ 进程里靠 ThreadLocal
      
现象
./run.sh async：通知那一行在 raw-1 线程上打出，JSON 里没有 traceId、spanId 字段；同样的代码放进 ctx-1，就带着。全景第 9 站那 10 个对账线程，如果业务里还有异步任务，链路也会在这里断开。
根源
上下文和 MDC 都挂在提交任务的那个线程上，线程池里的工作线程看不到。
做法
线程池加 setTaskDecorator(new ContextPropagatingTaskDecorator())（Spring 6.1+），@Async 用的池也一样；CompletableFuture.supplyAsync 不传线程池时用公共 ForkJoinPool，同样会丢。

    

    
2订单号放进了指标标签⑤ 实测← ④ 名字 + 标签 = 一条序列
      
现象
./run.sh cardinality：下了 200 单，orders_placed_by_id_total 有 200 条序列，全部序列从 479 涨到 679。一天下 100 万单，就是 100 万条，Prometheus 的内存和查询都扛不住。
根源
每一种标签值组合都是一条独立的时间序列，要各自存储、各自索引。
做法
标签只放取值有限的东西：状态码、uri 模板、实例、渠道。订单号、用户 ID 放日志字段或 span 属性。用 Observation 时写成 highCardinalityKeyValue，只进 span，不进指标。

    

    
3日志里有 traceId，链路库里却查不到实测← ④ 链路要采样
      
现象
不设采样率（Spring Boot 默认 0.1）连下 40 单：120 行业务日志全都带着 traceId，可拿最后一单的 traceId 去查 span 树，结果是“没有这个 trace”。用户拿着日志里的 ID 来报障，查不到。
根源
上下文照样生成、照样传，只是没被采中的 span 不记录、不导出。
做法
知道默认值是 10%，按流量定采样率；更好的做法是在 Collector 做尾部采样，错误的和慢的全留，其余按比例留（全景第 6 站就是这么配的）。

    

    
4计数器叫 orders.created，导出来成了 orders_total⑤ 实测历史原因
      
现象
⑤ 里计数器最早叫 orders.created，/actuator/prometheus 里却找不到 orders_created_total，只有 orders_total。告警规则按自己以为的名字写，就永远不会响。
根源
推不出来，是命名规则：Prometheus Java 客户端 1.x（Spring Boot 3.3 起用它）会把名字末尾的 _total、_created、_bucket、_info 当成保留后缀去掉，计数器再统一加上 _total。
做法
名字别用这几个词结尾；写完告警规则，先去 /actuator/prometheus 里确认名字真的存在。

    

    
5URL 自己拼字符串，uri 标签跟着炸← ④ 名字 + 标签 = 一条序列
      
现象
⑤ 用模板写法 uri("/api/products/{sku}", sku)，客户端指标的标签是模板（实测 uri="/api/products/{sku}"）。把 sku 直接拼进 URL 字符串，标签就可能变成一个个具体路径，一个商品一条序列。
根源
观测只能拿到你交给它的那个字符串；不知道哪一段是变量，就没法合并。
做法
HTTP 客户端一律用模板加参数的写法；服务端 Spring MVC 自动用路由模板，不用管。

    

    
6异常只打了 message，ERROR 被 DEBUG 淹没← ④ 日志记的是一次事件
      
现象
全景第 7 站搜到的那行如果只有“下单失败”，就看不出是拿连接超时；线上开着 DEBUG，一秒几万行，那一行根本找不到。
根源
日志的价值在于那一刻的细节和能被搜到的字段；没有细节就只剩一个数，那是指标该干的活。
做法
log.error("下单失败 order={}", id, e) 把异常对象放最后，堆栈才会打出来；线上默认 INFO，排查时临时调级别（Actuator 的 /loggers 能在线改）。

    

  


  
第二圈 · 团队里怎么定

  
    
    
  1. 日志字段统一：时间、级别、服务、实例、traceId、spanId、logger、线程、消息，全公司一个格式。防的是：每个服务一种格式，日志平台上没法统一搜。
    2. 
    
  2. 级别有含义：ERROR 要有人处理，WARN 是能自愈的异常，INFO 记业务关键节点，DEBUG 线上默认关。防的是：ERROR 天天刷屏，真出事时没人看。
    3. 
    
  3. 不打敏感信息：密码、token、完整手机号、身份证号一律不进日志。防的是：日志平台成了泄露源。
    4. 
    
  4. 标签有白名单：每个自定义指标的标签在评审时就定下来，取值都要是有限的。防的是：坑 2。
    5. 
    
  5. 出厂就带的指标：每个服务至少有请求量、错误、耗时直方图（RED），连接池、线程池，JVM。防的是：出了事才发现大盘上没有连接池（全景第 5 站）。
    6. 
    
  6. trace_id 回给调用方：放进响应头或错误页，用户和客服报障时直接带上。防的是：拿着“大概几点下的单”去日志里大海捞针。
    7. 
  


  
第三圈 · 再往深一点

  

    

      
exemplar：从指标的一个点跳到一条链路实测

      
开了直方图又开了链路时，Micrometer 会给直方图的桶挂上一个“样本”：落进这个桶的某一次请求的 trace_id。只有用 OpenMetrics 格式抓取才看得到：

Observation：埋一次点，交给几个处理器

      
Observation 只负责说“这件事开始了、结束了、出错了”，真正干活的是挂在 ObservationRegistry 上的处理器：一个记计时器（指标），一个开关 span（链路），一个往 MDC 里放 ID（日志）。所以 ⑤ 的 order.insert 一次埋点，就同时出现在指标和链路里。

      
lowCardinalityKeyValue 既进指标标签也进 span；highCardinalityKeyValue 只进 span。坑 2 的正解就是这个区别。

    

    

      
头部采样和尾部采样

      
头部采样：入口那一刻就决定采不采，结果写进 traceparent 的标志位，下游跟着走，便宜，但入口时还不知道这个请求会不会慢、会不会错。尾部采样：所有 span 先送到 Collector，等整棵树到齐再决定，可以“错误和慢的全留”，代价是 Collector 要缓存、要有状态。

自测

  

    
1. 用一句话说出这一页的精华
指标、日志、链路是同一个请求的三种记法：指标压成几个数，便宜、能告警；日志一次一行，有细节；链路一棵树，看路径。三样各管一摊，靠同一个 trace_id（日志字段、exemplar、span）串起来，才能从发现一路跳到细节。

    
2. 老办法（每台机器一个文本日志）最疼的是哪两条？
没有一个便宜、能一直算的“数”，所以算不出错误率、做不了告警；没有一根把同一个请求的记录串起来的“线”，所以看不出慢在哪一段，换线程、跨服务就彻底断了。

    
3. 坑 1（换线程丢 traceId）的根源是 ④ 的哪一条？
进程里的上下文放在 ThreadLocal（OpenTelemetry Context、MDC）里，只属于提交任务的那个线程；工作线程看不到，要靠装饰器在提交时拍快照、在执行时恢复。

    
4. 预测：把坑 2 的订单号从计数器标签改成 highCardinalityKeyValue，下 200 单，时间序列从 479 涨到多少？
基本不涨（只多了 Observation 自己那个计时器的一组序列，和单数无关）。高基数的键值只写进 span 属性，不进指标标签，所以序列条数和订单数无关；代价转移到了链路存储上，而链路本来就是按请求计费、按采样控制的。

    
5. 预测：采样率保持默认 0.1，用户拿着响应里的 traceId 来报障，你能查到什么？
日志一定查得到：MDC 里的 ID 不管有没有采中都在。链路大概率查不到，十单里只留一单。所以要么把采样改成尾部采样（错误和慢的全留），要么排查时先靠日志。

    
6. 放回全景：第 1 站和第 7 站之间隔了哪几站？如果第 1 站的日志没带 trace_id，第 7 站会怎样？
中间是第 2～6 站：Prometheus 抓取、告警、接警、大盘、链路。第 6 站从链路里拿到 trace_id，第 7 站拿它去搜日志。如果日志里没有这个字段，第 7 站只能按 order-3 加 03:19 前后的时间去翻，几百行“拿不到连接”里分不清哪一行属于这个请求；排查能做，但会慢好几分钟。如果对账线程的日志也没有 trace_id（坑 1），第 9 站就只能靠 Arthas 看线程栈。
