并查集：账户一对对合并成团伙，查“是不是一伙”几乎 O(1)

每伙人选一个代表，每个账户只记“我的上级是谁”，一路往上找到的就是代表；两个账户代表相同就是一伙。合并两伙，只要把一个代表挂到另一个代表下面。两个小规矩让它几乎 O(1)：小的挂到大的下面（树高最多 log₂n），查一次就把路上的人直接挂到代表下面（路径压缩）。它只回答“是不是一伙”，不回答“怎么连上的”，这正是它快的原因。

①要解决的问题：边一条条来，随时问“是不是一伙”

在全景第 4 站，风控的关联关系是一条条“事件”：“1024 和 2001 在同一台设备上登录了”“3002 给 7777 转了钱”。每来一条，两个账户所在的两伙就并成一伙；每张订单进来，都要问一句“1024 和黑名单里的 7777 是不是一伙”。一天几百万条关联事件，下单时这一问必须是微秒级。

②朴素做法：每次都 BFS，或者给每个人记团伙编号

做法合并查询疼在哪
维护邻接表，每次查询 BFS（第 16 课）O(1) 加边O(点 + 边)一伙越大查得越慢；本机只做 20 万条边、每 1 万条才 BFS 一次就 231 ms
每个账户记团伙编号 group[i]O(n)：把一伙人的编号全改掉O(1)合并两大伙时要扫全部账户
只记上级 parent[i]，不讲究怎么挂O(树高)O(树高)挂法不好会排成一条链，本机 3 万个账户查一轮 4.5 亿步
  • 第二行查询最快，痛在合并要改一整伙；第三行合并很快，痛在树可能很高。
  • 缺的那一块：合并时控制树高（小的挂到大的下面），查询时顺手把树压平（路径压缩）。两者合起来，两边都几乎是 O(1)。
不懂精华时的典型误用：合并时直接写 parent[a] = b，没先找到 a 的代表。a 原来那一伙的其他人还挂在旧代表下面，a 被单独“拽走”了。本机实测：先并 0—1、再并 1—2，问 0 和 2 是不是一伙，答 false（坑 1）。

③几种思路：同一个问题的四个版本

α(n) 是反阿克曼函数，增长极慢：实际能遇到的 n 它都不超过 4。所以工程上当成常数（Tarjan 1975 的结论，这里按文献写）。

本页学两个优化都开的并查集：代码只有十几行。适用条件很明确：关系只会合并、不会拆开，只问“是不是一伙”。要“怎么连上的”回第 16 课 BFS；要拆开关系，见坑 4。

④关键洞察：一伙人一棵树，代表就是树根

先知道这些
  • 树高与查找：沿父指针往上走的步数 = 节点深度。第 13 课 递归与二叉树遍历。
  • 账户号映射成下标：账户号是稀疏的 long，先用 HashMap<Long, Integer> 编成 0..n−1，再用数组。第 8 课 哈希表。

洞察 1 · 只记“上级”，往上走到头就是代表

parent[i] 存账户 i 的上级，根的上级是它自己。find(x)：一直往上走到 parent[r] == r。union(a, b)：先 find 到两个根，再把一个根挂到另一个根下。树长什么样无所谓，只要“同一伙在同一棵树里”。这就是它比维护整张图便宜的地方：不记边，只记归属。

洞察 2 · 小的挂到大的下面：树高最多 log₂n

每个根记一下这伙有多少人（size）。合并时，人少的那伙的根挂到人多的那伙的根下。一个账户的深度只在“它所在的小伙被挂到大伙下面”时加 1，而每次这样，它所在的伙至少翻倍；伙的大小不会超过 n，所以最多翻倍 log₂n 次，深度 ≤ log₂n。100 万个账户最深 20 层。

洞察 3 · 路径压缩：查一次，路上的人都直接挂到代表下

find 找到根以后，再把刚才走过的每个账户的 parent 直接改成根。下次再查它们，一步就到。和按大小合并一起用，均摊下来每次操作是 O(α(n))。

为什么这样设计：只答“是不是一伙”

并查集

  • 两个 int 数组，合并和查询几乎 O(1)
  • 边来一条处理一条，不用存边
  • 不知道“怎么连上的”：树的形状和真实关联无关
  • 只能合并，不能拆开

图 + BFS（第 16 课）

  • 能给出路径、跳数、只看几跳
  • 能删边
  • 每次查询 O(点 + 边)，一伙越大越慢
  • 要存下所有边
决定胜负的约束：问题只要一个“归属”。“是不是一伙”只关心等价类，不关心边，所以可以把边扔掉、把树随便重排（压缩、挂到大的下面），这些重排在图上都是不允许的。真实风控常常两者并用：并查集在同步路径上秒答“是不是一伙”，审核员要看证据时再离线跑 BFS 找路径。
完整的并查集两个数组、两个方法
int[] parent = new int[n], size = new int[n];   // 初始：parent[i] = i，size[i] = 1

int find(int x) {                               // 迭代，不怕深
    int r = x;
    while (parent[r] != r) r = parent[r];
    while (parent[x] != r) { int nx = parent[x]; parent[x] = r; x = nx; }   // 路径压缩
    return r;
}

boolean union(int a, int b) {
    int ra = find(a), rb = find(b);              // 一定先找根
    if (ra == rb) return false;
    if (size[ra] < size[rb]) { int t = ra; ra = rb; rb = t; }
    parent[rb] = ra; size[ra] += size[rb];       // 小的挂到大的下面
    return true;
}

读出来的结论
  • 最坏输入下裸的版本排成一条 3 万层的链，查一轮走 4.5 亿步；按大小合并以后，新账户（1 个人）总被挂到老的大伙下面，树高只有 1。

⑥边界和变体

第一圈 · 注意事项

1合并时没先找根实测← ④ 洞察 1
现象
写成 parent[a] = b：先并 0—1（1 挂到 0 下），再并 1—2 时把 1 改挂到 2 下，0 被丢在原地。问 0 和 2 是不是一伙，答 false。
根源
“一伙”是一整棵树；只有根代表整棵树，挪一个中间节点只是把它（和它下面的）拽走了。
做法
合并永远是 parent[find(b)] = find(a)，根挂根。
2不讲究挂法，树排成链实测← ④ 洞察 2
现象
新账户一个个并进一大伙，每次都把大伙挂到新账户下面：3 万个账户排成 3 万层，查一轮 4.5 亿步、1 秒多。
根源
挂法决定树高；大的挂到小的下面，大伙里每个人的深度都 +1。
做法
按大小（或按秩，即树高的上界）合并：小的挂到大的下面。
3find 写成递归← ④ 洞察 3
现象
教材里常见的 return parent[x] == x ? x : (parent[x] = find(parent[x]));，在没按大小合并、树已经很深时，第一次 find 就栈溢出（和第 13 课的退化树一样）。
根源
递归深度 = 当前树高。路径压缩是在“递归返回时”做的，压缩之前要先走到底。
做法
两遍循环：第一遍找根，第二遍把路上的都改成根（⑤ 的写法）；或者确保按大小合并，深度 ≤ log₂n。
4想把一伙拆开← ④ 为什么这样设计
现象
风控误判，要解除“1024 和 2001 同设备”这条关联，发现并查集里没有“拆”的操作。
根源
并查集扔掉了边，也打乱了树的形状，没法知道拆掉一条关联后哪些人该分出去。
做法
关联要撤销时，从保存的边重建（每晚一次）；离线场景可以把操作倒过来做（先删光，再按时间倒序加边）；真要实时增删，用图 + BFS 或更复杂的动态连通性结构。
5直接拿账户号当数组下标← ④ 先知道这些
现象
账户号是 19 位的雪花 ID，new int[maxId] 直接 OOM；或者强转成 int 撞号，两个无关账户被算成一伙。
根源
并查集要求点编号是 0..n−1 的紧凑整数。
做法
先用 HashMap<Long, Integer> 给账户发下标（⑤ 的 Ids）；新账户来了就追加，数组按需扩容。

第二圈 · 使用规范

  • union 里先 find 再挂根：防坑 1。
  • 两个优化都开，find 写成迭代：防坑 2、坑 3。
  • 原始的关联边另外存一份：用来重建（坑 4）和给审核员找路径（第 16 课 BFS）。
  • 点编号先压缩成 0..n−1：防坑 5。
  • 多线程时由一个线程负责合并：find 的路径压缩会写 parent，读也是写；其他线程读快照，或者用带锁 / CAS 的版本。

第三圈 · 变体和深处

数团伙、找最大的一伙

初始 n 伙，每次真正合并成功就减一，随时知道还有几伙（LC 547）；size[find(x)] 就是 x 所在那伙的人数，风控可以只看“超过 50 人的团伙”。⑤ 里 100 万账户 100 万条边最后剩 161,515 伙。

带权并查集：记“和代表差多少”

每个点再存一个“相对代表的偏移”，find 时沿路累加。能回答“A 的余额比 B 多多少”“A 和 B 是同一方还是对立方”这类关系，LC 399（除法求值）是经典题。

Kruskal 最小生成树

边按权重从小到大排序（第 10 课），依次加入，如果两端已经是一伙（会成环）就跳过。判断“已经是一伙”就是并查集。比如用最便宜的专线把所有机房连起来。

为什么是 α(n)

按秩合并 + 路径压缩的均摊上界是 O(m·α(n))，Tarjan 1975 年证明，而且这个界是紧的。证明要用到秩的分组和势能分析，面试只需要知道结论：比 log 还慢得多，当常数用。

面试官会怎么问

并查集的两个优化分别解决什么？

按大小 / 按秩合并控制树高（≤ log₂n），防止合并顺序不好排成链；路径压缩让查过的点直接挂到根，后面再查一步到位。两者一起，均摊 O(α(n))。

冗余连接（LC 684）：一棵树多加了一条边，找出它。

按顺序把边加进并查集，第一条两端已经是一伙的边就是多出来的（它让图成了环）。

什么时候用并查集，什么时候用 BFS / DFS？

边是动态增加的、只问连通性，用并查集；要路径、跳数，或者要删边，用图遍历。静态图上数连通分量两个都行。

下一圈

  • 可撤销并查集：只按秩合并、不压缩，用栈记下每次合并，可以按相反顺序撤销（离线分治里用）。
  • 动态连通性：同时支持加边和删边的在线结构（Holm 等人的算法），复杂度 O(log² n) 均摊。
  • 有向图上的“依赖”：并查集只管无向的“一伙”，有方向的先后关系看第 18 课的拓扑排序。

↺回到⑤：改一改

  1. 只拦大团伙：给 UnionFind 加 groupSize(x)，下单检查改成“1024 和黑名单一伙、且这伙超过 5 人才拦”。⑤ 的数据里 1024 那伙 7 人，5005 那伙 1 人。（第三圈“数团伙”）
  2. 新账户随时加入：把固定大小的数组改成可扩容的（Arrays.copyOf 翻倍），Ids.of 碰到没见过的账户号就发一个新下标。（坑 5）

自测

1. 用一句话说出这一页的精华

每伙一棵树、根是代表，find 往上走到根，union 根挂根；小的挂到大的下面控制树高，查一次就压平路径，两者合起来几乎 O(1)。它只答“是不是一伙”，所以能扔掉边、随便重排树。

2. 每次查询都 BFS，痛点在哪？

每次 O(点 + 边)，一伙越大越慢，还得存下所有边；风控每张单都要问一次，扛不住。

3. 为什么按大小合并能保证树高 ≤ log₂n？

一个点的深度只在它所在的小伙挂到大伙下面时加 1，此时它所在的伙至少翻倍；最多翻倍 log₂n 次。

从 ④ 洞察 2 推出。

4. 预测：⑤ 的六条关联之后再查一次 same(3002, 1024)，parent 数组会怎么变？

find(3002) 走 3002 → 2002 → 1024，路径压缩把 3002 直接挂到 1024 下：parent 变成 [0, 0, 0, 0, 0, 0, 0, 7]，所有人都直接挂在 1024 下。答案是 true。

从 ④ 洞察 3 推出。

5. 预测：关联事件的顺序反过来（先 2002—4001，最后 1024—2001），最后谁是 1024 那一伙的代表？“是不是一伙”的答案会变吗？

代表可能换成别人（取决于每次谁大、一样大时谁挂谁），parent 数组也会不同；但“谁和谁一伙”完全一样，1024 和 7777 仍然一伙。并查集只保证归属，不保证形状。

从 ④ 为什么这样设计推出。

6. 放回全景：第 4 站前后各发生了什么？并查集出问题，整条链路会怎样？

前面第 3 站把订单交过来，后面第 5 站撮合。风控在同步路径上只做 same(下单账户, 黑名单)：合并写错（坑 1）会漏判，团伙放行，第 5 站撮合出对倒成交；树退化（坑 2）让这一问变成毫秒级，入口队列积压、所有人下单变慢。关联事件的合并在另一个线程里异步做，不阻塞下单。

档位：标准。本机跑过（2026-11-18，2 核 Neoverse-N1 虚机，OpenJDK 17.0.21，--release 8 编译）：⑤ 的每一步合并和最后的 parent 数组，最坏输入下四个版本的树高、步数和耗时，100 万条边的流式合并和 BFS 对比，⑥ 坑 1 的现象。按文献、没有本机实测：α(n) 的均摊上界（Tarjan 1975）、动态连通性的复杂度。按定义推出：坑 3～5。
