设计题：LRU、LFU 与限流，行情快照缓存和每账户每秒 20 单

设计题考的不是新算法，而是把已经学过的结构拼起来，让每个操作都是 O(1)：LRU = 哈希表 + 双向链表，LFU = 哈希表 + 按次数分的桶 + 一个最小次数，每账户限流 = 哈希表 + 懒补充的令牌桶 + LRU 淘汰账户。再往上一层是取舍：LRU 怕扫描，LFU 怕热点漂移。

①要解决的问题：容量有限，该踢谁；人数很多，怎么分别限

②不用它会怎样

做法会怎样
缓存用普通 HashMap，只放不删1 万个交易对的快照迟早全进来；换成订单号、用户 id 当 key，就是 OOM
满了随便踢一个 / 踢最早进来的（FIFO）BTC-USDT 最早进来，最先被踢，下一秒又要重建；⑤ 实测 FIFO 命中率 34%，LFU 50%
每次踢“最久没用的”：遍历所有 key 找最旧的时间戳每次 put O(n)；第 3 课的估算：缓存 10 万个、每秒几千次 put 就不行了
每个账户一个定时任务，每秒把令牌补满几百万个定时任务；不活跃的账户也在被补
限流表 HashMap<账户, 桶>，只加不删来过的账户越来越多，表只涨不跌
不懂精华时的典型误用：把 LRU 写成“HashMap 存值 + 每个值带一个最近访问时间”，淘汰时找最小时间。功能对，复杂度错了：精华在于让“最旧的那个”永远在链表尾巴上，不用找。

③几种流派：踢谁的问题

策略踢谁押的是怕什么
FIFO最早进来的什么都不押把常用的也按时踢掉
LRU最久没被用的最近用过的，马上还会用（时间局部性）一次扫描把热数据全挤走
LFU被用次数最少的用得多的，以后也用得多过去的热点赖着不走，新热点进不来
W-TinyLFU（Caffeine）新来的要和将被踢的比“近期频次”，赢了才进近期频次，用计数草图 + 定期减半实现复杂，自己不写，用库

本页手写 LRU 和 LFU：面试必考，也是理解 Caffeine 为什么要那样设计的前提。生产里的本地缓存直接用 Caffeine；限流算法怎么选看 限流算法那页，本页只用令牌桶。

④核心取舍：每个操作 O(1)，靠两个结构互相指

先知道这些
  • 双向链表 + 哨兵：知道节点就能 O(1) 摘下、O(1) 插到头部；head、tail 两个哨兵让边界不用判空。见 第 4 课。
  • 哈希表：按 key O(1) 找到东西，但没有顺序。见 第 8 课。

取舍 1 · LRU：哈希表负责“找到”，链表负责“排队”

哈希表的值不是缓存的值，而是链表节点。get：哈希表找到节点 → 从链表里摘下 → 插到头部。put 满了：直接摘链表尾巴（就是最久没用的）→ 从哈希表里删它的 key（所以节点里要存 key）。

取舍 2 · LFU：再加一层“按次数分桶”，最小次数能直接维护

取舍 3 · 每账户限流：懒补充的令牌桶，账户表也要淘汰

懒补充：不用定时任务

每个桶只存两个数：剩余令牌 tokens、上次时间 last。请求来时先补：tokens = min(20, tokens + (now − last) × 20/秒)，再扣 1。不来请求的账户不花任何 CPU。（算法本身见 限流算法 · 懒计算。）

账户表本身是个缓存

HashMap<账户, 桶> 会被“来过一次的账户”撑大。把它做成 LRU，最久没来的先踢。踢掉不会放错：被踢说明很久没来，它的桶早就补满了；下次来时新建一个满桶，结果一样。

核心取舍：LRU 押“最近”，LFU 押“常用”

LRU

  • 新热点一来就能进，适应快
  • 结构简单，一张哈希表一条链表
  • 报表扫一遍 500 个冷门交易对，容量 100 的缓存被冲干净

LFU

  • 扫描进来的次数都是 1，热门的次数几千，扫描冲不动
  • 昨天的热门攒了几万次，今天没人看也踢不掉；新热点要从 1 爬起
  • 还要多存次数和桶
决定胜负的约束：访问模式。热点稳定、偶有扫描：LFU 赢；热点常变：LRU 赢。真实流量两样都有，所以 Caffeine 的 W-TinyLFU 两个都要：一个小的 LRU 窗口接住新来的，主区按“近期频次”（定期减半，让旧热点过气）决定谁留下。
LRU 的核心四行完整的在 ⑤
Map<K, Node> map;  Node head, tail;           // 两个哨兵
V get(K k)  { Node n = map.get(k); if (n == null) return null;
              unlink(n); addFirst(n); return n.val; }   // 读也要挪：读就是写
void put(K k, V v) { ...; if (map.size() == cap) { Node old = tail.prev;
              unlink(old); map.remove(old.key); } ... }  // 节点里要存 key

⑤套进场景：手写三个，再比命中率

⑤LruCache · LfuCache · HitRate · AccountLimiter完整代码 →
// 每账户令牌桶：LinkedHashMap 按访问顺序 + removeEldestEntry，就是一个 LRU 账户表
this.buckets = new LinkedHashMap<Long, Bucket>(16, 0.75f, true) {
    protected boolean removeEldestEntry(Map.Entry<Long, Bucket> e) { return size() > maxAccounts; }
};
public synchronized boolean tryAcquire(long account, long nowNanos) {
    Bucket b = buckets.get(account);
    if (b == null) { b = new Bucket(capacity, nowNanos); buckets.put(account, b); }
    b.tokens = Math.min(capacity, b.tokens + (nowNanos - b.last) * perNano);   // 懒补充
    b.last = nowNanos;
    if (b.tokens >= 1) { b.tokens -= 1; return true; }
    return false;
}

  C 热点漂移         FIFO  34.4%   LRU  39.1%   LFU  25.9%
账户 1024 在同一毫秒连发 30 单：放行 20，拒绝 10
0.5 秒后再发 30 单：放行 10（这 0.5 秒补了 10 个令牌）

读出来的结论
  • 稳定的 Zipf 热点下 LFU 比 LRU 高 10 个百分点：频次比“最近一次”更能代表以后。
  • 加报表扫描（每 1000 次正常访问夹一次 500 个冷门交易对，命中率只算正常访问），LRU 掉 2.5 个点，LFU 纹丝不动。
  • 热点在中途整体换一批，LFU 跌到 26%：前一半攒的次数让旧热点赖在缓存里。没有“最好的策略”，只有“适合这种流量的策略”。

⑥反例和误用

第一圈 · 套上了名字，没满足约束

1多线程下只给 put 加锁← ④ 取舍 1
现象
高并发读行情时链表指针错乱：节点丢失、size 和链表长度对不上，甚至遍历死循环。
根源
LRU 的 get 也要把节点挪到头部，读就是写。ReadWriteLock 的读锁允许并发读，正好让两个 get 同时改链表。
做法
整体一把锁（synchronized）；要高并发就用 Caffeine：它把“读了谁”先记进缓冲区，再由单线程批量调整顺序。
2LinkedHashMap 忘了 accessOrder = true← ④ 取舍 1
现象
写了 removeEldestEntry，命中率却和 FIFO 一样。
根源
默认构造是按插入顺序，get 不挪位置，“最老的”就是最早插入的。
做法
new LinkedHashMap<>(16, 0.75f, true)，见 LinkedHashMap 那页。
3LFU 的旧热点赖着不走实测← ④ 核心取舍
现象
热点漂移时 LFU 命中率 26%，比 FIFO 还低。
根源
次数只增不减：过去的热门攒了几千次，新热点从 1 开始，一进来就是“次数最少”，最先被踢。
做法
给次数加衰减：定期全体减半（Caffeine 的做法），或者只数最近一个窗口内的次数。
4限流用 currentTimeMillis 算时间差← ④ 取舍 3
现象
NTP 把系统时间往回调了几秒，now − last 变成负数，令牌被扣成负的，这个账户几秒内一单都下不了。
根源
懒补充依赖时间差，墙上时钟会被回拨。
做法
用 System.nanoTime()（单调递增）；补充量再加一道 max(0, …)。

第二圈 · 使用规范

  • 缓存一定有上限和淘汰：按条数或按字节，防的是 key 空间无界（订单号、用户 id）时的 OOM。
  • 限流按账户隔离、表也要有上限：防一个账户刷单拖累所有人，也防账户表无限涨。
  • 手写只在面试和学习时：生产用 Caffeine（本地缓存）和成熟的限流组件，它们处理了并发、统计、过期。
  • 先测访问模式再选策略：拿真实的访问日志回放，比较几种策略的命中率，⑤ 的 HitRate 就是最小版本。

第三圈 · 设计题的通用套路

“O(1) 找到” + “O(1) 维护顺序”

哈希表找节点，节点同时挂在一个有序结构上（链表、桶、堆）。LRU、LFU、带过期的缓存（再挂一个按过期时间的堆，第 6 课）、“插入删除随机取都 O(1)”（数组 + 哈希表存下标）都是这个形状。

先问清楚的四件事

容量按条数还是字节？要不要线程安全？要不要过期时间？淘汰时要不要回调（比如写回数据库）？面试时先问，答案决定结构。

分布式限流

多台网关共享“每账户 20 单”：计数放 Redis，用 Lua 脚本把“补令牌 + 扣令牌”做成原子操作，见 限流算法 · 分布式。

Redis 的近似 LRU

Redis 不维护全局链表，淘汰时随机抽几个 key，踢里面最久没用的（maxmemory-samples）。用一点精度换掉每次访问改链表的开销。

实验台：同一份流量，三种淘汰策略

先猜：热点在中途整体换一批交易对，LFU 的命中率和 LRU 比？

浏览器里现算：1 万个交易对，Zipf 分布，10 万次正常访问；“扫描”每隔若干次插入 500 个冷门交易对的顺序读取，进缓存但不计入命中率；“漂移”在一半处把热门整体换成另一批。和 ⑤ 的 Java 版同一个模型，随机数不同，数字会差一点。

下一圈

  • W-TinyLFU 的 Count-Min Sketch：几 KB 内存近似记几百万个 key 的频次，定期减半。
  • ARC、LIRS：数据库和文件系统里自适应地在“最近”和“常用”之间调权重。
  • 带过期的 LRU：每条加 TTL，过期的优先踢，再挂一个按到期时间的堆或时间轮。

↺回到⑤：改一改

  1. 线程安全的 LRU：给 LruCache 的 get / put 加 synchronized，开 8 个线程各做 10 万次随机 get / put，最后检查 map 大小和链表长度一致；再去掉锁跑一次看会坏成什么样。（反例 1）
  2. LFU 加衰减：每 1 万次访问把所有次数减半（桶要重建），重跑 HitRate 的“热点漂移”，LFU 应该明显回升。（反例 3）
  3. 令牌桶加突发上限：把容量改成 5、速率仍是每秒 20：同一毫秒连发 30 单只放 5 单，但持续每 50 ms 一单仍然全放。体会“容量管突发，速率管平均”。（取舍 3）

自测

1. 用一句话说出这一页的精华

设计题就是把哈希表（O(1) 找到）和一个能 O(1) 维护顺序的结构（链表、次数桶）互相指起来；LRU 押最近、LFU 押常用，前者怕扫描，后者怕热点漂移。

2. LRU 只用 HashMap 加时间戳差在哪？

淘汰时要遍历找最旧的，O(n)；双向链表让最旧的永远在尾巴上，不用找。

3. 为什么 LRU 的 get 也要加锁（不能用读锁）？

get 要把节点挪到链表头，会改指针，读就是写；读锁允许多个 get 并发改链表。

4. 预测：LRU 链表的节点里不存 key，只存 value，会出什么问题？

淘汰时从链表尾巴拿到节点，却不知道它在 HashMap 里的 key，删不掉；HashMap 里留下一个指向已摘除节点的条目，下次 get 到它会操作一个不在链表上的节点，size 也对不上。

从 ④ 取舍 1 推出：两个结构互相指，链表要能反查哈希表。

5. 预测：每账户限流的账户表上限设成 1000，而某一秒有 5000 个活跃账户在下单，会怎样？

账户在表里不停被挤出、再以“满桶”重新进来，限流基本失效：一个刷单的账户只要被挤出一次，就又拿到 20 个令牌。上限要大于同时活跃的账户数，被踢的才都是“很久没来”的。

从 ④ 取舍 3 推出：“踢掉不会放错”的前提是被踢的账户桶已经补满。

6. 放回全景：第 11 站的快照缓存被报表扫描冲掉，影响谁？第 4 站限流失效呢？

快照缓存被冲掉：行情接口要回源重算快照，延迟上升、数据库压力变大，但撮合（第 5 站）不受影响。第 4 站限流失效：刷单的订单涌进第 3 站的定长队列，队列满了，正常用户的单也被拒，影响一路传到撮合。

档位：标准。本机跑过（2026-11-21，2 核 Neoverse-N1 虚机，OpenJDK 17.0.21，--release 8 编译）：⑤ 的全部输出（LRU、LFU 的操作序列，三种访问模式的命中率，令牌桶和账户表上限）。按公开资料：Caffeine 用 W-TinyLFU（窗口 LRU + 频次草图，计数定期减半）；Redis 的近似 LRU 和 maxmemory-samples（Redis 文档 “Key eviction”）。没有在本机跑多线程下的链表损坏，反例 1 的现象是按原理推的。实验台是浏览器里现算的。
