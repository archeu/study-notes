字符串：KMP 与 Trie，输入 BT 就补全交易对

两件事：Trie 把一堆字符串按公共前缀合成一棵树，“以 BT 开头的有哪些”就是走两步再看子树；KMP 在一段文字里找一个模式串，失配时主串指针从不后退，最坏也只要 O(n + m)。实测下来它们都不是默认首选：补全用有序表就够，找子串先用 indexOf；它们的用处在逐字输入、多个模式、恶意输入这些地方。

①要解决的问题：网关上的两件字符串小事

②朴素做法：全表 startsWith，逐位对齐比

做法复杂度实测（⑤）
补全：每个代码都 startsWith每次 O(N × L)，N 是代码个数5 万个代码 × 10 万次查询：39 秒，每次约 0.4 ms
找子串：每个起点都从头比一遍最坏 O(n × m)100 万个 A 里找 999 个 A 加一个 B：比较 9.99 亿次
  • 补全全表扫：代码越多越慢，而且大多数代码第一个字符就对不上，白看。
  • 朴素匹配：失配后起点只挪一格，已经比对过的信息全扔了。
  • 缺的那一块：补全要“按前缀分组好、直接跳到那一组”；匹配要“记住已经比过的，失配时不退回去”。
不懂精华时的典型误用：听说 KMP 是 O(n + m)，就把所有 indexOf 换成手写 KMP。⑤ 实测正常日志上 indexOf 比手写 KMP 快 3～4 倍：JDK 的 indexOf 虽然是朴素算法，但被 JIT 换成了内建实现，而正常文本几乎碰不到最坏情况。

问题做法好在差在
前缀补全有序表 + 二分：TreeMap.subMap(p, p+'￿') 或排序数组现成、省内存；实测最快每次查询从根重新找

本页学 Trie 和 KMP：它们是“前缀”和“匹配”两类问题里最基础的结构；但默认先用 TreeMap 和 indexOf，碰到逐字输入、多模式、外部可控输入时再换。

④关键洞察：把“公共部分”只存一次、只比一次

先知道这些

  • 字符和下标：c - 'A' 把字母变成 0～25，当数组下标用，见 第 1 课。

洞察 1 · Trie：节点就是前缀，子树就是“所有以它开头的”

洞察 2 · KMP：失配时主串不动，模式串按 next 数组往回跳

失配时，已经匹配上的那一段（比如 ABAB）是知道的。它的某个后缀如果恰好等于模式串的某个前缀（AB），就可以直接把模式串挪过去，从这个前缀之后接着比，主串指针一格都不用退。

洞察 3 · next 数组：模式串自己跟自己做一次 KMP

next[j] = 模式串前 j+1 个字符里，“既是前缀又是后缀”的最长长度（不算整段）。它只和模式串有关，和主串无关，所以预先算一次，O(m)。算法本身就是 KMP：拿模式串去匹配它自己，失配时也按已经算好的 next 往回跳。

为什么这样设计

KMP：主串只往前

  • 每一步要么 i 前进，要么 j 后退；j 后退的总次数不超过前进的总次数，合计 ≤ 2n
  • 不需要回看主串：数据从网络一个字节一个字节来也能匹配
  • 代价：每个字符多一次 next 查表和分支，正常文本上不如内建的朴素比较快

朴素 + 硬件加速（String.indexOf）

  • 先找首字符、再逐位比，JIT 能换成内建实现
  • 正常文本很少在“比到一半才失配”，几乎线性
  • 最坏 O(nm)，输入可被构造时有风险
决定胜负的约束：输入的“恶意程度”和“能不能回看”。内容可控、整段在内存里：indexOf。内容来自外部、或者是流：KMP 保证最坏线性。Trie 同理：查询从头来、代码表不大，TreeMap 够用；逐字输入、要挂计数、要同时匹配很多模式时，Trie 的“节点 = 前缀”才值钱。
KMP细节放到 ⑥
int[] nx = next(p);
for (int i = 0, j = 0; i < t.length(); i++) {
    while (j > 0 && t.charAt(i) != p.charAt(j))
        j = nx[j - 1];          // 失配：j 跳，i 不动
    if (t.charAt(i) == p.charAt(j)) j++;
    if (j == p.length()) return i - j + 1;
}
return -1;

class Node { Node[] next = new Node[37]; String word; }
void insert(String s) {
    Node cur = root;
    for (char c : s.toCharArray()) {
        int k = idx(c);
        if (cur.next[k] == null) cur.next[k] = new Node();
        cur = cur.next[k];
    }
    cur.word = s;               // 标记：到这里是完整代码
}

// 补全：先沿前缀走到节点，再在子树里按下标顺序 DFS，收够 limit 个就停
List<String> complete(String prefix, int limit) {
    Node cur = root;
    for (int i = 0; i < prefix.length() && cur != null; i++) cur = cur.next[idx(prefix.charAt(i))];
    List<String> out = new ArrayList<String>();
    if (cur != null) dfs(cur, out, limit);
    return out;
}

读出来的结论
  • 补全：Trie 比全表扫快 140 倍，但比 TreeMap 区间慢近 3 倍，还多出 27 万个节点（每个节点一个 37 格引用数组，估算约 50 MB）。只做“整段前缀查一次”，有序表更划算。
  • 匹配：最坏输入下 indexOf 比 KMP 慢 100 倍；正常日志（找一个不存在的单号，要扫完整份）上 indexOf 反而快 3～4 倍。
  • KMP 的比较次数正好在 2n 以内（1999001 < 2×10⁶），和 ④ 的设计分析一致。

⑥边界和变体

第一圈 · 注意事项

1Trie 每个节点一个大数组，内存吃不消实测← ④ 洞察 1
现象
5 万个代码建出 27 万个节点；字符集换成 Unicode，每个节点 65536 格就完全不能用。
根源
节点数 ≈ 所有代码的字符总数减去共享部分；每个节点为所有可能的字符预留位置，大多数是空的。
做法
字符集小用数组；字符集大用 HashMap<Character, Node> 或排序的小数组；只读的字典可以压成双数组 Trie 或把单孩子链合并（基数树）。
2没想到的字符：小写、空格、下划线← ④ 洞察 1
现象
用户敲了小写 bt，或者代码里有 _，idx() 抛异常或数组越界。
根源
数组版 Trie 把字符直接当下标，字符集是写死的。
做法
入口先规范化（toUpperCase(Locale.ROOT)、去空格），再查；不认识的字符直接返回空结果，不抛异常。
3next 数组差一位← ④ 洞察 3
现象
照着两本书各抄一半，死循环或漏匹配。
根源
next 有两种约定：本页的 next[j] 是“前 j+1 个字符”的值，失配时跳 next[j−1]；另一种整体右移一位、next[0] = −1，失配时跳 next[j]。两种都对，混用就错。
做法
选一种，在注释里写清 next[j] 的含义，用 "ABABC" → [0,0,1,2,0] 这种小例子当单元测试。
4外部可控的长输入上用 indexOf / contains实测← ④ 设计
现象
100 万字符、模式 1000 字符，一次 indexOf 约 0.5 秒。
根源
JDK 17 的 StringLatin1.indexOf 源码就是“找首字符、再逐位比”的朴素算法（标了 @IntrinsicCandidate，JIT 会换成内建实现，但最坏复杂度不变）。
做法
先限制输入和模式长度；真要在不可信的大输入里找，用 KMP 或多模式的 AC 自动机。

第二圈 · 使用规范

  • 补全先上 TreeMap.subMap 或排序数组 + 二分：实现最短、内存最省；有逐字输入或前缀计数需求再换 Trie。
  • 补全一定要限条数：输入一个 B 可能匹配几千个，DFS 收够 10 个就停，防的是一次按键扫半棵树。
  • 字符串比较前先规范化：大小写、全角半角、首尾空格，防同一个代码被当成两个。

第三圈 · 这两样东西在哪里

AC 自动机：Trie + KMP

同时找几千个敏感词：把词建成 Trie，再给每个节点配一个“失配指针”（就是 KMP 的 next 搬到树上）。扫一遍文本，所有词一起找出来，O(文本长度 + 命中数)。

最长前缀匹配

路由表按 IP 前缀查“最具体的那条”、网关按 URL 前缀找路由规则，都是在 Trie 上走到走不动为止，记下路上最后一个完整规则。

Boyer-Moore

从模式串右端往左比，失配时按“坏字符”一次跳一大段，正常文本上常常只看 n/m 个字符。grep 类工具用它的变种。

Rabin-Karp

给每个长度为 m 的窗口算一个滚动哈希（第 8 课的哈希 + 第 11 课的滑动窗口），哈希相等再逐位比。适合同时找多个等长模式、或者找重复的片段。

实验台：朴素匹配和 KMP 各比较多少次

先猜：主串是 10 万个随机的 0 和 1，模式串是 20 个随机的 0 和 1，朴素匹配的比较次数大约是？

浏览器里现算：“最坏”的模式串是 m−1 个 A 加一个 B；“随机 0/1”的模式串也是随机 0/1；“随机报文”是 BUY,BTC-USDT,价格,c-单号 这样的行，模式串取一个不存在的单号。比较次数和 ⑤ 的 Java 版用同样的计法。

下一圈

  • AC 自动机：多模式匹配，敏感词过滤、日志告警关键字。
  • 后缀数组 / 后缀自动机：一个长串里所有子串的问题（最长重复子串），面试很少，竞赛常见。
  • Z 函数、Manacher：和 next 数组同一类“利用已经比过的信息”的技巧，分别求公共前缀和回文。

↺回到⑤：改一改

  1. 逐字输入：给 SymbolTrie 加一个会话对象，记住当前节点；每敲一个字只从当前节点走一步。模拟用户逐字敲 BTC-USDT 8 次刷新，和 TreeMap 每次从头查比总耗时。（洞察 1）
  2. 前缀计数：每个节点加一个 count，插入时路上全加 1；“以 BT 开头的有几个”变成 O(L)。TreeMap 要怎么做才能一样快？（第二圈）
  3. 流式匹配：把 kmp 改成一个对象，每次喂一个 byte，返回是否刚好匹配完；用它在分块读入的日志里找单号，块边界上的匹配也不能漏。（设计）

自测

1. 用一句话说出这一页的精华

Trie 把公共前缀只存一次，查前缀只走前缀长度那么多步；KMP 用 next 数组记住“已配上的部分里有多少能复用”，失配时主串不退。两者都不是默认首选，在逐字输入、多模式、不可信输入时才值得。

2. 朴素匹配浪费在哪？

失配后起点只右移一格、从头再比，已经比对过的信息全扔了；最坏 O(nm)。

3. 为什么实测里 TreeMap 补全比 Trie 快？

TreeMap 区间查询只要一次 O(log N) 定位再顺序取 10 个；Trie 虽然走前缀只要 L 步，但要在子树里 DFS，每个节点扫 37 格数组，节点又多又分散，缓存不友好（第 2 课）。

4. 预测：模式串是 "AAAAA"（全相同），next 数组是什么？要在 n 个 A 里找出所有出现位置，KMP 大约比较几次？

next = [0,1,2,3,4]。每次配上后令 j = next[4] = 4 接着找，之后每来一个 A 只比一次就又配上一个，总共约 n 次比较，n − 4 个位置全找出来。

从 ④ 洞察 3 推出：前 j+1 个 A 的最长相等前后缀是 j 个 A。

5. 预测：Trie 的字符集从 37 个改成只支持 A-Z（26 个），内存和查询速度怎么变？

每个节点的数组小约 30%，内存跟着降；查询走前缀的步数不变，DFS 每个节点少扫 11 格，略快。但带数字和横杠的代码就存不进去了。

从 ④ 洞察 1 推出：节点数取决于代码本身，每个节点的大小取决于字符集。

6. 放回全景：第 1 站之后是第 2 站去重。如果网关把 btc-usdt 和 BTC-USDT 当成两个交易对，会怎样？

第 1 站把小写的查不到内部编号，订单要么被拒，要么被当成新交易对；如果有人给小写的单独建了簿子，第 5 站会出现两本 BTC-USDT 的订单簿，买卖单互相看不见、撮合不上。规范化必须在第 1 站做。

档位：标准。本机跑过（2026-11-21，2 核 Neoverse-N1 虚机，OpenJDK 17.0.21，--release 8 编译）：⑤ 的全部输出。按源码（已核对）：JDK 17 java/lang/StringLatin1.java 的 indexOf(byte[], int, byte[], int, int) 是“找首字符再逐位比”的循环，标了 @IntrinsicCandidate。估算：Trie 每个节点约 190 字节（对象头 + 37 格压缩引用数组），27 万个约 50 MB，没有用 JOL 实测。实验台是浏览器里现算的。
