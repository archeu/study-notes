数组为什么快：连续内存、缓存行和 O(1) 下标

数组快在两层。第一层：下标能直接算出地址，取第 k 个是 O(1)。第二层：元素挨着放，CPU 从内存一次搬 64 字节，还能提前搬，扫一遍几乎不用等内存。两层都靠“等长、连续”，代价是中间插入要挪、容量要先定。

①要解决的问题：400 万笔金额，取第 k 个，再全加一遍

一天 400 万笔订单金额。两件事天天做：按位置取（分页取第 k 页、二分查找跳到中间），从头扫到尾（对账求和、过滤、统计）。两件都要快。

同样的大 O，本机实测的差距（⑤ 的程序跑出来的，JDK 17）：

按下标读，都是 O(1)5 倍顺序 9.2 ms，随机 46 ms
同一个二维数组14 倍按行 13 ms，按列 177 ms
取第 200 万个6.9 msLinkedList 一次；ArrayList 不到 0.1 µs

2 核 ARM（Neoverse-N1）虚机，粗测：热身 3 次后取 5 次里最快的一次，不是 JMH。跑了两遍，相差不到 2%。看倍数，不看绝对值。

②朴素做法：每个数一个盒子，盒子里记着下一个在哪

不用提前知道有多少个，来一个就新建一个盒子挂到后面，这就是链表（Java 的 LinkedList）。插入删除只改两根指针，看起来很灵活。

  • 按位置取是 O(n)：LinkedList.get(2000000) 要从近的一头走 200 万步，实测一次 6.9 ms。
  • 扫一遍也慢：400 万个求和，实测 14.7 ms，int[] 只要 2.7 ms，同样是 O(n)。
  • 费内存：JOL 实测 100 万个整数，LinkedList<Integer> 占 40 MB，int[] 只占 4 MB。每个节点有对象头、前后两根指针，还要再指向一个 Integer 对象。
  • 真正的长处：已经拿着某个节点时，在它旁边插入、删除是 O(1)，不用挪别的元素。
不懂精华时的典型误用：“要经常插入，所以选 LinkedList。”可是 list.add(i, x) 得先走到第 i 个，这一步本身就是 O(n)；而数组那边挪元素用的是一整块内存拷贝，快得多。LinkedList 的作者 Joshua Bloch 2015 年在推特上说过，他自己写的这个类，他从来不用。

④关键洞察：地址能算，数据挨着，CPU 就不用等

先知道这些
  • 内存是一大排编了号的字节：编号就是地址，CPU 按地址读写。第 1 课 机制 1 讲过。
  • 时间单位：1 ns（纳秒）= 十亿分之一秒。2.5 GHz 的 CPU 走一拍是 0.4 ns。
  • 缓存：放在 CPU 旁边的一小块高速存储，存着最近用过的内存内容的副本。命中（hit）就快，没命中（miss）就要去主存取。

机制 1 · O(1) 下标：地址是算出来的

  • 两个前提：每个元素一样大（才能乘），元素挨着放（才能加）。少一个，就只能一个一个数过去。
  • 下标为什么从 0 开始：下标就是“离起点隔了几个元素”，第一个元素隔了 0 个。
  • 越界检查：Java 每次 a[i] 都拿 i 和头里的 length 比一下，越界抛 ArrayIndexOutOfBoundsException。C 语言不查，越界就读到别人的内存。

机制 2 · 存储层级：CPU 等一次主存，够它干上百件事

打个比方：L1 是桌面，L2 是身后的书架，末级缓存是楼下的资料室，主存是城另一头的仓库。比方失效的地方：书是一本一本拿的，而缓存一次搬一整块（下一节），还会自己提前去搬。

机制 3 · 缓存行和预取：一次搬 64 字节，还会提前搬

  • 顺序扫数组：每 16 个 int 只有 1 次 miss，而且这次 miss 多半也被预取提前藏掉了。
  • 随机按下标读：下标计算仍是 O(1)，但几乎每次都 miss。实测比顺序慢 5 倍。
  • 链表：比随机还糟。下一个节点的地址存在当前节点里，必须等当前这次读回来，才能发下一次读；CPU 没法同时等好几个 miss，预取器也猜不到。

实验台：缓存模拟器

先猜：8 行 × 32 列的 int 矩阵（每个矩阵行正好是 2 个缓存行），缓存只装得下 4 个缓存行，不开预取。按列遍历一遍，256 次访问 miss 几次？

命中miss缓存行的起点（16 个 int）

估算模型：缓存全相联、LRU 淘汰；命中按 1 ns、miss 按 100 ns 算，取 机制 2 的量级。真实 CPU 有多级缓存、能同时等好几个 miss、预取器也更聪明，所以只看倍数和规律。试试缓存 8 行时开关预取：预取也会帮倒忙。

机制 4 · Java 里的三种“数组”

  • 对象数组多一跳：读 list.get(i) 先读引用，再顺着引用去读 Integer 对象。对象刚按顺序创建时多半挨着，所以实测只慢 2.3 倍；把引用打乱后（对象还在原地），慢到 17 倍。
  • 二维数组按列走：每一步都跳到另一个行对象，4096 行就要碰 4096 个不同的缓存行，等回到第一行时它早被挤出 L1 了。

为什么非得连续、等长

数组：连续、等长

  • 地址算得出：按位置取 O(1)
  • 搬来的每个缓存行都用满，预取器猜得中
  • 没有额外指针，int[] 每个元素就 4 字节
  • 代价：中间插入删除要挪后面所有元素，O(n)
  • 代价：长度创建时就定死，变长要换一块更大的再整体拷贝

链表：哪有空放哪

  • 不用提前知道大小，拿着节点时增删 O(1)
  • 地址算不出：按位置取 O(n)
  • 每一步都要等上一次读回来，缓存和预取都帮不上
  • 每个元素多背对象头和指针，Java 里 10 倍内存
决定胜负的约束：主存比 CPU 慢约 100 倍，而且只能按 64 字节一块来搬。谁能让搬来的每一块都用满、让 CPU 提前知道下一个地址，谁就赢；这时同一个大 O 的常数能差十几倍。数组为此付出的代价是“挪”和“扩容”，可这两件事也是在连续内存上整块拷贝（System.arraycopy），本身就很快。ArrayList 把扩容定为每次 1.5 倍，摊下来每次 add 仍是 O(1)（坑 4）。

一条口诀

内层循环走最后一维：g[i][j] 里 j 在内层，读的就是同一个行对象里挨着的元素。反过来写，算法一样、结果一样，在 4096×4096 上实测慢 14 倍。

⑤手推一遍：先算地址和 miss，再让程序对答案

  1. 1 算地址int[] a 的起点是 0x1000，a[5] 在哪？0x1000 + 16（对象头）+ 5 × 4 = 0x1000 + 36 = 0x1024。（机制 1）
  2. 2 一行装几个缓存行 64 字节：int 装 16 个，long / double 装 8 个，压缩指针下的引用（4 字节）装 16 个。（机制 3）
  3. 3 顺序扫的 missint[1000] 一共 16 + 4000 = 4016 字节，起点对齐时占 63 个缓存行。扫一遍 1000 次访问，最多 63 次 miss，约 6%；有预取还更少。
  4. 4 二维按列int[4096][4096] 按列走一遍第 0 列，要碰 4096 个行对象各一个缓存行：4096 × 64 B = 256 KB，比 L1 的 64 KB 大。等走第 1 列时（和第 0 列在同一个缓存行里），这些行早被挤出 L1。所以按列几乎每次都 L1 miss，按行每 16 次才一次。预测：慢一个数量级。（机制 4）
  5. 5 链表取中间LinkedList.get(2000000) 要沿着 next 走 200 万步，每一步都得等上一步读回来。如果每步都要等主存（约 100 ns），一次就是 200 ms；如果节点碰巧挨着、多在缓存里，每步几 ns，一次几 ms。

读出来的结论
  • 手推对上了：二维按列慢 14 倍，是一个数量级；JOL 打出的 int[] 头正好 16 字节，元素从偏移 16 开始。
  • 链表取中间：一次 6.9 ms，折合每步约 3.5 ns，说明这些刚建好的节点在堆里基本挨着、多数在缓存里。真实系统里节点散开以后只会更慢。
  • “打乱”的威力：ArrayList<Integer> 只是把引用打乱，对象一个没动，就从 6.3 ms 变成 45 ms，比链表还慢。快慢取决于访问顺序和内存位置合不合拍，不取决于叫什么数据结构。
  • 步长实验：k 从 1 到 16，改的元素少了 16 倍，时间只从 32 ms 降到 9.7 ms，因为碰到的缓存行没变少（k = 8 和 16 几乎一样）；k 超过 16 以后，碰到的行变少，时间才继续降。这就是“按行搬运”留下的指纹。

⑥边界和变体

第一圈 · 注意事项

1把 LinkedList 当“插入快的 List”实测← ④ 机制 3
现象
分页时 list.get(i) 越翻越慢；for (int i…) list.get(i) 的循环变成 O(n²)。实测 get(2000000) 一次 6.9 ms。
根源
地址算不出来，只能沿着指针走；每一步都依赖上一步读回来的值，缓存和预取都帮不上。
做法
默认用 ArrayList；要队列、栈、双端队列用 ArrayDeque（环形数组）。遍历 List 一律用 for-each 或迭代器，不用下标。
2大量数字装进 List<Integer>实测← ④ 机制 4
现象
100 万个数占 20 MB（int[] 4 MB）；求和慢 2.3 倍，对象散开后慢 17 倍；GC 也要多扫 100 万个对象。
根源
泛型只能装对象，每个数被装箱成 16 字节的 Integer，数组里只剩引用，数据本身不再连续。
做法
热点路径、大批量数字用 int[] / long[]，或 IntStream；需要可变长的原始类型集合时，可以用 fastutil、Eclipse Collections 这类库的 IntArrayList。
3二维数组按列遍历实测← ④ 机制 4
现象
同一段逻辑，只是把 g[i][j] 写成了 g[j][i]，4096×4096 上慢 14 倍。
根源
Java 的二维数组是数组的数组，行内连续、行间不连续；按列每一步换一个行对象、一个缓存行，搬来的 64 字节只用 4 字节。
做法
内层循环走最后一维；确实要按列处理时，先转置一份，或者改用一维数组 a[i * cols + j] 并让内层循环走连续的那一维。
4ArrayList 不预设容量← ④ 为什么连续
现象
一次装 400 万条，内存曲线一阵一阵往上跳，Young GC 变多。
根源
数组长度定死，装满就换一个 1.5 倍大的再整体拷贝。默认容量 10，涨到 400 万要扩容三十多次，旧数组全成了垃圾。摊还下来每次 add 仍是 O(1)，但拷贝和垃圾是实打实的。
做法
知道大概数量就 new ArrayList<>(expected)；批量装用 ensureCapacity。（这一条按源码推算，没有单独测时间。）

第二圈 · 使用规范

  • List 默认 ArrayList，队列默认 ArrayDeque：防 O(n) 的按位置访问和指针追逐。
  • 大批量数字用原始类型数组：防 5 倍内存和装箱后的散乱布局。
  • 多维数据内层循环走最后一维：防按列跳行。
  • 能预估大小就预设容量：防反复扩容拷贝。
  • 遍历 List 用 for-each：换成哪种实现都不会退化成 O(n²)。
  • 性能结论用 JMH 测：本页的粗测够看倍数，但要写进设计文档、做取舍时，用 JMH 防 JIT 把代码优化掉或测进热身时间。

第三圈 · 优化和深处

伪共享：挨着放也会坑你

两个线程各改各的 long，可这两个变量落在同一个缓存行里，每次写都要让对方的那一行失效，缓存行在两个核之间来回搬。解法是在中间垫满 64 字节以上。JDK 用 @Contended 做这件事，比如 LongAdder 背后的 Striped64.Cell（JDK 17 源码第 124 行）。业务代码里要用，得加 -XX:-RestrictContended。

JIT 让数组更快

int[] 求和 400 万个只要 2.7 ms，约 6 GB/s。HotSpot 的 C2 对这种计数循环会做两件事：把每次的越界检查提到循环外（range check elimination），以及用 SIMD 指令一次加好几个 int（向量化）。链表和装箱的 List 都吃不到这两样。（按 HotSpot 的公开资料，本页没有反汇编验证。）

按列为什么不止慢 4 倍

L1 miss 后多数还能在 L2 找到，光算 L1 和 L2 的延迟差，解释不了 14 倍。另外几个原因：按行的循环能向量化，按列不能；按列每一步跨 16 KB，4096 行分布在 4096 个内存页上，CPU 里缓存页表的 TLB 装不下，还得额外查页表。大页（-XX:+UseLargePages）能缓解后者。

对象数组 vs 每个字段一个数组

400 万个 Order 对象放进数组，求总金额时每读一个金额都要带上整个对象。改成 long[] amounts、int[] status 各一个数组，求和只扫金额那一列，缓存行全是有用数据。这就是列式存储（ClickHouse、Parquet）快的原因之一。

自测

1. 用一句话说出这一页的精华

数组等长、连续，所以下标能算出地址（O(1)），扫的时候每个缓存行都用满、预取器猜得中；同样的大 O，数据摆法能让常数差十几倍。

2. 链表输在哪？

按位置取要一个个走过去，O(n)；扫的时候下一个地址藏在当前节点里，只能一步一步等内存，缓存和预取都帮不上；Java 里每个元素还多背对象头和指针。

3. 二维数组按列慢，根源是哪条原理？

缓存按 64 字节一行搬，而 Java 的二维数组每一行是单独的对象。按列每一步换一行、一个缓存行，搬来的 64 字节只用 4 字节，回头再用时早被挤掉。

④ 机制 3 + 机制 4。

4. 预测：元素个数一样，顺序扫一个很大的 long[] 和一个 int[]，谁慢？慢多少？

long[] 慢，大数组上接近 2 倍。一个缓存行只装 8 个 long，miss 次数和要搬的字节都翻倍；数组远大于缓存时，瓶颈是从主存搬数据。

从 ④ 机制 3 推出：时间跟着碰到的缓存行数走。

5. 预测：把 4096×4096 换成 64×64 的 int[][]，按列还慢 14 倍吗？

差距会小得多。64×64×4 = 16 KB，整个数组都装得进 64 KB 的 L1，按列虽然跳来跳去，回头时数据还在缓存里。

从 ④ 机制 2、3 推出：只有数据比缓存大，访问顺序才要命。

6. 预测：HashMap 的桶是数组，get 为什么还是比 int[] 下标慢不少？

数组里存的是 Node 引用，Node 里又引用 key 和 value 对象；一次 get 要先算哈希，再跳到 Node、跳到 key 去比 equals，一路好几次可能 miss 的读。

从 ④ 机制 4 推出：引用多一跳，就多一次可能的 miss。

7. 连回第 1 课：为什么一个 Java 数组最多大约 21 亿个元素？

下标和 length 都是 int，32 位补码最大 231−1，约 21 亿；JDK 实际的软上限还要再减 8。

从 第 1 课机制 2 推出。
