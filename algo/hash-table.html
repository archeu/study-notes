哈希表：从 hashCode 到冲突和扩容

哈希表的全部本事是一句话：把 key 算成数组下标，于是“找”变成了“直接去那一格看”。代价是冲突：不同的 key 会算到同一格，而且冲突一定会发生。怎么处理冲突（拉链还是往后找空格）、表要留多空（负载因子）、满了怎么搬（扩容），决定了它是 O(1) 还是退化成一条长链。

①要解决的问题：这一单见过没有

  • 最后一行已经摸到答案了：数组按下标访问是 O(1)（第 2 课），只是 key 太大，当不了下标。
  • 那就把 key 压到一个小范围里：下标 = f(key) mod 表长。这个 f 就是哈希函数。
  • 压完了，不同的 key 会落到同一格：这就是冲突。剩下的全部问题都是围绕冲突的。
不懂精华时的典型误用：以为“哈希表就是 O(1)”，于是 key 的哈希值分布不好（比如雪花 ID 的低位全是 0）也照用，结果所有 key 挤在几格里，查一次要探几千次（坑 2，本机实测 2 万个 ID 放进去用了 451 ms，先打散只要 1 ms）。

③几种思路：撞了以后去哪

思路撞了怎么办谁在用好在哪输在哪
拉链法同一格挂一条链HashMap、ConcurrentHashMap装得再满也不会“没地方”，删除简单每个元素一个节点对象；key 是 long 还要装箱
开放寻址（线性探测）往后一格一格找空格ThreadLocalMap、IdentityHashMap、各种原语集合库没有节点对象，数组连续，缓存友好负载因子必须低；删除要留墓碑
布隆过滤器不存 key，只置几个位Redis 布隆、缓存穿透几个比特一个元素只能答“肯定没见过 / 可能见过”，幂等不能只靠它
TreeMap不哈希，比大小盘口（第 14 课）有序，能范围查O(log n)，节点对象

本页从拉链讲到开放寻址：拉链法的 JDK 实现（扰动、2 的幂、树化）在 HashMap 那页讲过，这里只用一句话带过；篇幅给开放寻址，因为它暴露了哈希表最本质的两件事：冲突怎么找，删除为什么难。key 是 long、量大、只问在不在时，选它。要不确定性的“可能见过”也能接受，先过一层布隆过滤器。

④关键洞察：把 key 算成下标，再为冲突留余地

先知道这些
  • 取模和 2 的幂：表长是 2k 时，x mod 2k 就是 x & (2k−1)，只留低 k 位。第 0 课：取模。
  • 排列组合：算“没有任何两个撞上”的概率要用到连乘。第 0 课：排列组合。
  • hashCode / equals 契约：equals 相等的两个对象，hashCode 必须相等。HashMap 那页的 定位三步。

洞察 2 · 冲突躲不掉：生日悖论

把 n 个 key 均匀扔进 m 格，一次都不撞的概率是 m(m−1)…(m−n+1) / mⁿ，n 稍微大一点它就掉得很快：

8 格放 4 个59%至少撞一次
365 天 23 个人50.7%有两人同一天生日
大约在n ≈ √m撞的概率过半
所以必须设计撞了以后怎么办

8 格放 4 个：1 − 8·7·6·5 / 8⁴ = 1 − 1680/4096 ≈ 59%。所以“哈希函数够好就不会冲突”是错的，冲突处理不是边角，是主体。

洞察 3 · 负载因子 α 决定一次要找几格

负载因子 α = 元素个数 / 格子数。拉链法的平均链长就是 α。线性探测撞了往后找，被占的格子会连成一片（聚集），越满越长。Knuth 算过平均要探几格：找得到的约 ½(1 + 1/(1−α))，找不到的约 ½(1 + 1/(1−α)²)。本机 220 格实测：

α找得到：实测 / 公式找不到：实测 / 公式
0.251.16 / 1.171.39 / 1.39
0.501.51 / 1.502.50 / 2.50
0.752.50 / 2.508.53 / 8.50
0.905.58 / 5.5051.88 / 50.50
0.9510.45 / 10.50195.10 / 200.50

“找不到”的代价涨得快得多：幂等场景里大部分单都是新单，查的恰恰是“找不到”。所以开放寻址的 α 一般压在 0.5～0.75，而拉链法的 HashMap 用 0.75 链长也才 0.75。

机制 · 线性探测：插入、查找、删除

规则只有三条：插入从 home 格往后找第一个空格（或墓碑）；查找从 home 格往后找，碰到它就是有，碰到空格就是没有；删除不能把格子清空，要留一块墓碑。为什么？看动画的最后两步。

机制 · 扩容：翻倍，全部重新放，墓碑顺手清掉

扩容一次要把 n 个都重放一遍，是 O(n)。但每次翻倍，搬运总量是 n + n/2 + n/4 + … < 2n，摊到每次插入是 O(1)（第 3 课的摊还）。拉链法的 HashMap 扩容时每个节点只看一位就知道去哪，见 HashMap 那页的扩容。

为什么这样设计

开放寻址：key 直接放在数组里

  • 一个 long 就是 8 字节加 1 字节状态，没有对象头、没有指针
  • 探测是连续内存，一个缓存行装 8 个 long
  • 代价：α 要低，表要留空；删除只能留墓碑，墓碑多了要重建

拉链：每个元素一个节点

  • α 到 1 也不怕，删除就是摘链表节点
  • value 可以是任何对象，泛型通用
  • Java 里每个节点 32 字节 + key 装箱 24 字节：本机实测 62.7 字节一个 Long
  • 链表节点散在堆里，一次查找可能好几次缓存未命中
决定胜负的约束：JDK 要做一个什么类型都能放的通用 Map，泛型只能放对象，节点反正要有，拉链最稳。交易系统里 key 是 long、量大、追求延迟和内存，把对象拿掉才是大头，所以撮合、行情这类代码常用 long 原语的开放寻址表。
key 自己要写对的两个方法细节放到 ⑥
// equals 相等 ⇒ hashCode 必须相等；参与的字段不能再改
record OrderKey(long userId, long clientSeq) { }   // JDK 16+，自动生成两个方法

// 知道要放多少个就预先给够（JDK 19+）
Map<Long, Order> m = HashMap.newHashMap(5_000_000);
// JDK 8～18：new HashMap<>((int) (n / 0.75f) + 1)

三个参数，一句话一个

哈希函数决定会不会挤成一堆；负载因子决定一次平均找几格；表长是 2 的幂让取模变成一次按位与，代价是只看低位，所以前面必须打散。

⑤手推一遍：网关的已见集合

手写一个 LongOpenHashSet：long[] keys 放单号，byte[] state 记“空 / 有人 / 墓碑”。客户端单号先编码成 long（比如用户号左移 32 位拼上客户端序号）。代码按 JDK 8 写法，--release 8 编译，JDK 17 运行。

⑤LongOpenHashSet.java（核心）完整代码 →
public boolean add(long key) {                 // 已经有了返回 false = 重复单
    int i = home(key), firstTomb = -1;
    while (state[i] != EMPTY) {
        if (state[i] == TOMB) { if (firstTomb < 0) firstTomb = i; }
        else if (keys[i] == key) return false;
        i = (i + 1) & mask;                        // 线性探测：往后一格，到头绕回 0
    }
    int at = firstTomb >= 0 ? firstTomb : i;       // 墓碑可以复用
    if (state[at] == EMPTY) used++;
    keys[at] = key; state[at] = FULL; size++;
    if (used > maxLoad * keys.length) resize();   // 墓碑也占位，一起算
    return true;
}

public boolean contains(long key) {
    for (int i = home(key); state[i] != EMPTY; i = (i + 1) & mask)
        if (state[i] == FULL && keys[i] == key) return true;
    return false;                                  // 碰到空格才能说“没有”
}

public boolean remove(long key) {                 // 找到后改成墓碑，不清空
    for (int i = home(key); state[i] != EMPTY; i = (i + 1) & mask)
        if (state[i] == FULL && keys[i] == key) { state[i] = TOMB; size--; return true; }
    return false;
}

int home(long key) { return (int) (fmix64(key) & mask); }   // 先打散再取低位

⑥边界和变体

第一圈 · 注意事项

1开放寻址删除时直接清空格子实测← ④ 线性探测
现象
删掉 11 以后，再查 27 答“没有”，重复单 27 被放进去第二份。幂等失效，用户被下了两单。
根源
查找的规则是“碰到空格就停”。27 当初是被挤过 4 号格才落到 6 号的，把 4 号清空，等于把它的路截断了。
做法
删除改成墓碑：查找跳过它、插入可以复用它；墓碑和元素一起算进负载，多了就重建（扩容时顺手清掉）。或者用“往回挪”的删除法（第三圈）。
2雪花 ID 不打散，全挤在一格实测← ④ 洞察 1
现象
2 万个雪花 ID 直接 key & mask 放进 219 格的表，平均每次 add 探测 10000.5 次，用了 451 ms；先用 fmix64 打散，每次 1.0 次，1 ms。
根源
雪花 ID 是“时间戳 | 机器号 | 序列号”，序列号在低 12 位。流量低时每毫秒只有一单，序列号全是 0，低 19 位就只剩机器号那几位，全部一样。表长是 2 的幂时，下标只看低位。
做法
取下标前先把高位混进低位：fmix64、乘一个大奇数取高位（Fibonacci hashing），至少也要 h ^ (h >>> 32)。HashSet<Long> 同一批 ID 用了 15 ms，没出事，因为 Long.hashCode 把高低 32 位异或，HashMap 又做了一次 h ^ (h >>> 16)。
3为了省内存把负载因子拉到 0.9 以上实测← ④ 洞察 3
现象
α = 0.95 时，一次“没见过”的查询平均要探 195 格，α = 0.5 时只要 2.5 格。
根源
线性探测会聚集，未命中的代价按 1/(1−α)² 涨。幂等查重绝大多数是新单，查的正是“未命中”。
做法
线性探测的 α 上限定在 0.5～0.75；内存紧就换更紧凑的布局（第三圈的 Robin Hood、SwissTable），不要硬拉 α。
4key 放进去以后又改了字段← ④ 洞察 1
现象
用一个可变对象当 key，放进去后改了参与 hashCode 的字段，再 contains 就找不到，remove 也删不掉，内存慢慢漏。
根源
下标是放进去那一刻按旧 hashCode 算的。字段一改，新 hashCode 指向另一格，原来那格里的它再也没人找得到。
做法
key 用不可变对象：record、String、Long。只重写 equals 不重写 hashCode 也是同一类事故，见 HashMap 那页的坑。
5new HashMap(n) 放 n 个，照样扩容← ④ 扩容
现象
以为 new HashMap<>(n) 能装 n 个不扩容。n = 700 万时，放到第 629 万个左右还是扩了一次，几百万个节点整体搬家，开盘那一分钟出现一次明显的停顿。
根源
构造参数是桶数（向上取到 2 的幂），扩容看的是 size > 桶数 × 0.75。700 万向上取到 223 = 838 万格，阈值 838 万 × 0.75 = 629 万，装不下 700 万。
做法
JDK 19+ 用 HashMap.newHashMap(n)，它按负载因子替你换算；更早的版本写 (int) (n / 0.75f) + 1。
6已见集合只进不出← ④ 洞察 3
现象
幂等集合一个月没清，几亿个单号把堆撑爆；或者撤单时只从价位链表摘了节点，订单号到节点的 Map 里忘了删（全景第 6 站的“常出的事”）。
根源
哈希表不会自己过期。n 只涨，表就跟着一次次翻倍，每次扩容的停顿也越来越长。
做法
按交易日滚动：今天一张表、昨天一张表，后天把前天的整张扔掉；跨天重试的窗口要覆盖到。撤单写成一个方法，链表和 Map 一起删。

第二圈 · 使用规范

  • key 不可变，equals 和 hashCode 一起写：防坑 4。有 record 就用 record。
  • 知道规模就预先给够容量：防坑 5 的扩容停顿，用 newHashMap(n) 或自己换算。
  • 自己写哈希表时，取下标前先打散：防坑 2，尤其是 ID、时间戳、价格这类低位有规律的 key。
  • 开放寻址：删除留墓碑，α ≤ 0.75，墓碑计入负载：防坑 1、坑 3。
  • 只进不出的集合要有过期策略：防坑 6，按天滚动或者带 TTL。
  • 多线程共享用 ConcurrentHashMap：普通 HashMap 并发写会丢数据，JDK 7 还会死循环，见 ConcurrentHashMap 与阻塞队列。

第三圈 · 变体和深处

Robin Hood 和往回挪的删除

Robin Hood hashing：插入时谁离自己 home 格更远，谁就占这一格，被挤走的继续往后找。探测长度变得很平均，查找可以提前停。删除时把后面的元素往回挪一格（backward shift），就不需要墓碑了。

SwissTable：一次比 16 格

Google Abseil 的 flat_hash_map：每格配 1 字节控制字（7 位哈希片段 + 状态），用 SIMD 一条指令比 16 个控制字，命中了才去比真正的 key。α 可以拉到 0.875。Rust 的标准 HashMap 也基于这个设计。

渐进式 rehash：Redis 不一次搬完

Redis 的字典扩容时同时保留新旧两张表，之后每次读写顺带搬一个桶，搬完再丢掉旧表。单次操作的延迟一直很小，代价是搬家期间要查两张表。JDK 的 HashMap 是一次搬完的。

哈希碰撞攻击

攻击者构造大量 hashCode 相同的 key（比如 "Aa" 和 "BB" 的 String hashCode 相同，拼起来能造出成千上万个），让拉链退化成长链。JDK 8 起链长到 8 且表够大就树化，最坏变 O(log n)。详见 HashMap 那页的深处。

面试官会怎么问

开放寻址和拉链法各适合什么场景？

拉链：通用、元素是对象、删除频繁、负载可以高，JDK HashMap 就是。开放寻址：key 是原语或很小、追求内存和缓存命中、能接受较低负载，ThreadLocalMap、IdentityHashMap 和各种原语集合库是。

开放寻址为什么不能直接删除？

查找靠“碰到空格就停”判断不存在。直接清空会截断后面那些被挤过来的元素的探测路径，它们就再也找不到了。所以留墓碑，或者把后面的往回挪。

负载因子为什么不设成 1？

拉链法设成 1 链长也才 1，但扩容更晚、空间换时间的余地小，JDK 取 0.75 是折中。开放寻址设成 1 就是表满了，插入找不到空格；接近 1 时未命中的探测次数按 1/(1−α)² 爆炸。

自测

1. 用一句话说出这一页的精华

把 key 算成数组下标，查找就变成直接去那一格看；冲突躲不掉，所以要用好的哈希函数把 key 打散，用低负载因子给冲突留余地，满了翻倍扩容，摊下来仍是 O(1)。

2. 直接寻址（boolean[单号]）缺的是什么？

单号太大，当不了下标。哈希就是把大 key 压到一个小范围，代价是会冲突。

3. 开放寻址删除为什么要留墓碑？是哪条规则决定的？

查找规则是“碰到空格就停，判定为没有”。清空一格会截断被挤过它的元素的路径。

从 ④ 线性探测的三条规则推出。

4. 预测：表长从 2 的幂改成一个素数（比如 1009），用 % 取下标，不打散的雪花 ID 还会全挤一格吗？

不会挤成一格。对素数取模会用到 key 的所有位，雪花 ID 的时间戳部分每单都不同，余数就分散开了。这正是 Hashtable 用素数长度的原因；代价是 % 比 & 慢，扩容也不能“看一位”。

从 ④ 洞察 1 推出：&(m−1) 只看低位，% 素数看全部位。

5. 预测：一张开放寻址表反复“插入一个、删除一个”，元素数一直很少，查询却越来越慢，为什么？

每删一个就多一块墓碑，墓碑不算元素却挡着路：查找遇到墓碑要继续往后找，“找不到”要一直走到真正的空格。墓碑占满后几乎没有空格，未命中查询接近全表扫描。所以墓碑要计入负载，多了就重建。

从 ④ 线性探测和洞察 3 推出。

6. 放回全景：第 2 站前后各发生了什么？查重坏了，整条链路会怎样？

前面是第 1 站网关把报文解析成订单对象，后面是第 3 站把订单按到达顺序放进入口队列交给撮合线程。查重漏判（比如坑 1、坑 6），重复单进了撮合，用户被下两单，清算对账（第 10 站）会发现两笔成交对应同一个客户端单号；查重太慢（坑 2、坑 3），网关处理不过来，第 3 站的队列积压，所有单的延迟一起涨。
