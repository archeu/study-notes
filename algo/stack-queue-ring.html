栈、队列和环形数组：一块数组首尾相接，两头都是 O(1)

栈和队列不是新的存储结构，是两条进出规则：栈只许在一头进出，后进先出；队列一头进、另一头出，先进先出。栈放在数组上天生 O(1)；队列两头都在动，数组前面空出来的格子用不上，难点在这里。环形数组的解法是让下标走到末尾就绕回 0：一块定长数组反复用，入队、出队都是 O(1)，不搬数据，也不分配新对象。代价是多了一件要想清楚的事：头尾指针重合时，到底是空还是满。

①要解决的问题：订单先来先撮合，规则里的括号要配对

交易靶场的撮合引擎前面有个入口：网关线程收到订单就放进去，撮合线程一张张取出来撮合，先到的先撮合。另一处，风控规则是一串带括号的表达式，上线前要检查括号配没配对：最后打开的括号必须最先关上。两件事都只在容器的“头”上进出，从不碰中间。

  • 入队、出队每次都是 O(1)：不管排了几张，做一次的代价一样。
  • 平稳运行时不分配新对象：撮合线程最怕 GC 停顿，每张单 new 一个节点，就是在给 GC 送活。
  • 容量有上限：撮合跟不上时，入口要能告诉网关“慢一点”，而不是一直排下去，把内存和延迟一起吃光。

假设场景：靶场按“行情突发时每秒几十万张”设计入口，这是设计目标的量级，不是实测。

④关键洞察：规则、绕回、空满、扩容

先知道这些
  • 数组下标 O(1)：地址 = 起点 + 下标 × 元素大小，算一下就到（第 2 课）。
  • 摊还：偶尔一次扩容很贵，摊到前面每次操作头上还是 O(1)（第 3 课）。
  • 补码：-1 在二进制里是全 1（第 1 课），洞察 5 要用。
  • 取模 %：除完剩下的余数。7 % 4 = 3，8 % 4 = 0，所以一个数一直加 1 再对 4 取模，会 0 1 2 3 0 1 2 3 地转圈。

洞察 1 · 栈和队列是规则，不是结构

洞察 2 · 栈放在数组上，天生 O(1)

数组栈的全部满了扩容放到洞察 6
Object[] a = new Object[16];
int top = 0;                     // 下一个空位

void push(Object x) { a[top++] = x; }
Object pop() {
  Object x = a[--top];
  a[top] = null;                 // 让 GC 能回收，见 ⑥ 坑 6
  return x;
}

为什么不用绕回

栈的进和出在同一头。top 往上走一格，下一次 pop 又把它拉回来，底下的格子一直被占着，从来不会“空在前面”。所以只要一个下标、一块数组，push、pop 都是 O(1)。

JVM 的线程栈也是这个样子：一块连续内存加一个栈顶指针，调一层方法压一帧，返回弹一帧。第 4 课递归溢栈，就是 top 顶到了这块内存的尽头。

洞察 3 · 队列放在数组上：让下标绕回来

队列的两个下标都只往后走，走过的格子就空在身后。办法是：下标走到末尾就回到 0，把数组想成首尾相接的一个圈。写成代码只有一行：i = (i + 1) % n。下面同一串操作做两遍，上排下标只往后走，下排绕回来。

绕回以后，两个下标都只做“加 1 再绕回”，出队不搬数据，入队用的是早先空出来的格子。一块 4 格的数组，能一直转下去。

洞察 4 · 空和满长得一样：都是 head 和 tail 指着同一格

多记一个 count

  • 空是 count == 0，满是 count == n，n 格全能用
  • 每次进出多改一个字段
  • 谁在用：ArrayBlockingQueue（字段 items、takeIndex、putIndex、count）

永远留一个空格

  • head == tail 只表示空；放完发现 tail 追上 head，立刻扩容
  • n 格只装 n−1 个，空格用 null 当记号
  • 谁在用：ArrayDeque（源码注释：“The array always has at least one null slot”）

序号不回绕

  • head、tail 用 long 一直往上加，槽 = 序号 % n；size = tail − head
  • long 每秒加 10 亿次也要 292 年才溢出
  • 谁在用：本页的 OrderRing、LMAX Disruptor 的 sequence
根子在哪：4 格的环里，元素个数有 0～4 共 5 种可能，head 和 tail 的“槽位差”却只有 0～3 共 4 种。4 个格子装不下 5 种状态，必须再找 1 点信息：多一个字段、少用一格，或者让下标不回绕。

洞察 5 · 绕回的两种写法：取模，或者 & (n − 1)

n 是 2 的幂时，& 就是取模

8 是 1000，7 是 0111。i & 7 只留下最低 3 位，正好是除以 8 的余数，而且一条与运算比除法便宜。负数也对：-1 的补码全是 1，与上 7 得 7。Java 的 % 结果符号跟着被除数走，-1 % 8 是 -1（本机实测）。

代价是容量只能取 2 的幂。JDK 8 的 ArrayDeque 和 Disruptor 都这么做；JDK 9 起的 ArrayDeque 换成了“比一下，到头就归零”：if (++i >= n) i = 0;，不用除法，容量也不必是 2 的幂。

洞察 6 · 满了要扩容：先把圈拆直

为什么撮合入口用定长的环，不用会长的队列

定长环形数组，满了拒绝

  • 启动时分配一块数组，运行中一次 new 都没有
  • 满了 offer 返回 false：这就是给上游的“慢一点”（背压）
  • 连续内存，预取帮得上忙（第 2 课）
  • 代价：容量要事先定；满了怎么办要写清楚

可扩容的环（ArrayDeque）

  • 单线程里的默认选择：栈、队列、BFS 都用它
  • 满了就扩：撮合跟不上时它一直长，问题被藏起来
  • 不是线程安全的，跨线程不能直接用

无界链表队列

  • 每张单一个节点，出队变垃圾，GC 越忙撮合越慢
  • LinkedBlockingQueue 不给容量就是 Integer.MAX_VALUE：排到内存耗尽才出事
  • 排得越长，后面的单等得越久，延迟和内存一起涨
决定胜负的约束：只动两头、运行中零分配、必须有上限。三条同时满足的只有定长环形数组。LMAX 交易所开源的 Disruptor，撮合入口用的就是这套思路。

⑤OrderRing.java（核心）完整代码 →
public class OrderRing {
  private final long[] slots;   // 订单号；long[] 不装箱，整个队列只有这一块数组
  private final int mask;       // 容量 − 1，容量必须是 2 的幂
  private long head, tail;      // 只增不减的序号

  public OrderRing(int capacity) {
    if (capacity <= 0 || Integer.bitCount(capacity) != 1)
      throw new IllegalArgumentException("容量要是 2 的幂：" + capacity);
    slots = new long[capacity];
    mask = capacity - 1;
  }

  public boolean offer(long orderId) {
    if (tail - head == slots.length) return false;   // 满：交给调用方决定
    slots[(int) (tail & mask)] = orderId;
    tail++;
    return true;
  }

  public long poll() {
    if (tail == head) return -1;                     // 空
    int i = (int) (head & mask);
    long id = slots[i];
    slots[i] = 0;
    head++;
    return id;
  }
}

读出来的结论
  • ArrayList 的 remove(0)：n 从 1 万到 10 万，每对操作从 0.95 µs 涨到 13 µs，跟着 n 涨，O(n) 的样子。

⑥边界和变体

第一圈 · 注意事项

1用 java.util.Stack 当栈实测历史原因
现象
同样 push 1、2、3，Stack 的 for-each 打出 [1, 2, 3]，ArrayDeque 打出 [3, 2, 1]（⑤ StackDemo 实测）。还能 add(0, x)、get(i)，从中间改。
根源
JDK 1.0 的设计：Stack extends Vector，继承来一整套按下标操作的方法，栈的规则（洞察 1）守不住；每个方法都 synchronized，单线程也白付锁的开销。它的 javadoc 自己写着应优先用 Deque。
做法
Deque<T> stack = new ArrayDeque<>()，只用 push/pop/peek。
2往 ArrayDeque 里放 null实测← ④ 洞察 4
现象
addLast(null) 直接 NullPointerException；LinkedList 却能放。
根源
ArrayDeque 用“永远留一个空格”分空满，空格的记号就是 null：pollFirst 取出 null 就当队列空了。允许放 null，就分不清“取到一个 null”和“队列空了”。
做法
用一个哨兵对象代替 null，或者换成 Optional。
3自己写的环，只看 head == tail← ④ 洞察 4
现象
放满的那一刻，判空也返回 true：撮合线程以为没单可取，或者下一张直接盖掉最老的那张。
根源
回绕的下标只有 n 种差值，装不下 0～n 共 n+1 种个数。
做法
三选一：加 count、留一格、序号不回绕。写一个每步都检查 0 ≤ size ≤ n 的不变式，像 ⑤ 那样。
4往回退一格写成 (i − 1) % n实测← ④ 洞察 5
现象
从 0 往回退（addFirst、pollLast）时下标变成 -1，ArrayIndexOutOfBoundsException。
根源
Java 的 % 结果符号跟着被除数，-1 % 8 == -1。
做法
写 (i - 1 + n) % n；容量是 2 的幂时写 (i - 1) & (n - 1)；或者像 JDK 17 那样 if (--i < 0) i = n - 1;。
5扩容时直接 Arrays.copyOf← ④ 洞察 6
现象
扩容后出队顺序乱了，中间还冒出空位。
根源
环里的元素通常是两段，直接复制，绕回的那一段留在了数组开头，head 后面却是新开的空格。
做法
复制后把 head 到旧末尾那段挪到新数组末尾，或者从 head 开始按逻辑顺序一个个搬到新数组的 0 号位。
6出队后不把槽清空← ④ 洞察 3
现象
队列里早就没东西了，堆里那批订单对象却一直收不掉。
根源
环形数组的格子是反复用的：出队只挪了 head，旧引用还留在格子里，直到这一格被下一圈盖掉。容量 6.5 万的环，最多能拖住 6.5 万个已经出队的对象。
做法
出队时 es[h] = null（ArrayDeque.pollFirst 和数组栈的 pop 都这么做）。Disruptor 是另一条路：格子里的事件对象预先建好、永远复用，只改字段。
7用无界队列连接快慢两端← ④ 为什么用定长
现象
撮合卡了几秒，入口队列越排越长，延迟和堆一起涨，最后 OOM。线程池同样：Executors.newFixedThreadPool 内部用的是不给容量的 LinkedBlockingQueue。
根源
无界等于“永远不会满”，生产比消费快时没有任何信号回到上游。
做法
给容量，并写清满了怎么办：put 阻塞等、offer(e, 时间, 单位) 超时、拒绝并让网关限流。见 线程池下一圈。

第二圈 · 使用规范

  • 栈和队列默认 ArrayDeque，变量声明成 Deque / Queue：它的 javadoc 写着当栈用比 Stack 快、当队列用比 LinkedList 快。防的是同步开销、节点垃圾和破坏规则的下标方法。
  • 一个队列只用一套方法：要么 offer/poll/peek（失败返回 false / null），要么 add/remove/element（失败抛异常）。栈只用 push/pop/peek。防的是 push（加在头）和 offer（加在尾）混用，同一个 ArrayDeque 两头进，顺序就乱了。
  • 跨线程用 BlockingQueue，并且给容量：ArrayDeque 和 OrderRing 都不是线程安全的。ArrayBlockingQueue 是同一个环加一把锁，见 阻塞队列。防的是并发下 head/tail 被改乱，以及坑 7。
  • 满了的策略写进代码和注释：阻塞、超时、拒绝、丢最旧，各有场景（行情快照可以丢最旧，订单不能丢）。防的是“默认无界”把问题推迟到线上。
  • 深度跟着输入涨的递归，改成循环加一个 ArrayDeque 栈：显式栈在堆上，几百万层也放得下。防的是第 4 课的 递归溢栈。

Disruptor：把环形数组用到极致

容量 2 的幂、long 序号不回绕、& 取槽位，就是本页的 OrderRing。再加两条：格子里的事件对象启动时建好，运行中只改字段，一个对象都不 new；生产者和消费者的序号各自独占一条缓存行（前后填充），免得两个核抢同一行，见 伪共享 和 第 2 课缓存行。

两个栈拼一个队列（面试题）

入队压进栈 A；出队时 B 空了，就把 A 整个倒进 B，再从 B 弹。倒一次是 O(n)，可每个元素一辈子只被倒一次，摊到每次还是 O(1)，正是 第 3 课的摊还。它能用，但比环形数组多一倍搬运，真实系统里很少这么写。

自测

1. 用一句话说出这一页的精华

栈和队列是进出规则；栈在数组上只动一个下标，天生 O(1)；队列两头都动，让下标走到末尾回到 0，一块定长数组就能两头 O(1)、零分配，代价是要额外记一点信息来分清空和满。

2. 用数组做队列，三种朴素做法各疼在哪？

remove(0) 每次把后面全挪一遍，O(n)，实测 10 万张时每对 13 µs；头下标只往后走，空出的格子不复用，到头就假溢出；LinkedList 两头 O(1)，但每张单一个 24 字节节点，出队成垃圾。

3. 自己写环形队列最容易错在哪？根源是哪条原理？

只用 head == tail 判断，空和满分不开。根源是洞察 4：回绕的下标差只有 n 种，个数却有 n+1 种，必须多记一点信息。

4. 预测：new OrderRing(6) 会怎样？换成用 % 取槽位呢？

构造函数抛 IllegalArgumentException：& (n − 1) 只有在 n 是 2 的幂时才等于取模，6 − 1 = 5 是 101，i & 5 永远到不了槽 2 和 3。改成 % 6 就能用任意容量，只是每次多一次除法（序号非负，不会有负数问题）。

从 ④ 洞察 5 推出。

5. 预测：同一个 ArrayDeque，先 push(1)、push(2)，再 offer(3)，然后 poll 三次，出来什么顺序？

2、1、3。push 是 addFirst，加在头上，队列变成 [2, 1]；offer 是 addLast，加在尾上，变成 [2, 1, 3]；poll 从头取。这就是“一个队列只用一套方法”的原因。

从 ④ 洞察 1（规则只管从哪头进出）和最少的语法推出。

6. 预测：撮合线程卡住 2 秒，网关每秒送来 10 万张，入口是容量 65,536 的环。会发生什么？换成不给容量的 LinkedBlockingQueue 呢？

环大约 0.66 秒就满了，之后 offer 返回 false，网关拿到信号去限流或拒单，内存一点不涨。换成无界链表队列，2 秒里排进 20 万个节点，每个节点 24 字节以上，再加订单对象；排在最后的单要等前面 20 万张撮合完，延迟跟着涨，卡得再久就是 OOM。

从 ④ 为什么用定长的环推出：有上限才有背压。

7. 预测：JDK 17 里 new ArrayDeque<>() 连续 addLast，第几个元素会触发第一次扩容？

第 17 个。默认数组长 17（16 + 1 个空格），放进第 17 个后 tail 绕回 0 追上 head，立刻 grow，长度 17 + 19 = 36（小于 64 时翻倍再加 2）。本机实测一致。
