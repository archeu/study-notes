从电灯开关到“你好”：计算机怎样表示数据

计算机里只有一种东西：一串开或关的比特。它是整数、小数还是“你好”，全看按什么约定去读。位数定下能表示的范围，约定定下运算的代价；算法里 O(1) 的下标、log n 次的二分、哈希的取模，都从这里长出来。

①要解决的问题：机器只是电路，它怎么记住“订单 9527，19.99 元，张三”

你写下一个订单对象。它进了内存以后，没有“字段”、没有“文字”，只剩一排字节；每个字节又只是 8 个开关。

不懂这一层，下面这些天天能碰到的怪事就只能死记。它们都来自同一个原因，⑤ 里会亲手推出来：

0.1 + 0.2≠ 0.3得到 0.30000000000000004

四个数都是 ⑤ 的程序在本机 JDK 17 上打印出来的。算法课从这里开始，因为算法的“代价”就是数对这些比特做了几次操作；不知道一个数占几位、怎么存，就没法判断一个算法快不快、会不会算错。

②朴素做法：照人的习惯，用十进制造机器

最自然的想法是让机器像人一样数数：一位有 0 到 9 十种状态。三百年里真有人这么造，也真有人一直在推二进制。两条路线并排看：

  • 齿轮做十进制：每个轮子要精确地停在 10 个位置之一，进位靠机械联动。巴贝奇的差分机设计在 1822 年，他生前没能造完。
  • 电子管做十进制：ENIAC 的每个十进制位是一圈 10 个触发器（环形计数器），同一时刻只有一个“亮”。10 个元件只表示 10 种状态；同样 10 个元件做成二进制，能表示 210 = 1024 种。
  • 最根本的：一根导线要分出 10 档电压，档和档挨得很近，一点噪声就读错。③ 里画给你看。
  • 十进制的好处只有一个：和人的习惯一样，输入输出不用换算。可换算只在进出机器时做一次，计算却要做亿万次。
不懂精华时的典型误用：把 int 当成数学里的整数、把 double 当成实数，以为“只是写法不同”。二进制真正的约束是位数固定：32 位就只有 232 个值，超出去就绕回来，除不尽就舍入。上面四块怪事都是从这里来的。

③几种思路：一个元件该分几档

做法一个元件分几档抗干扰电路怎么设计结局
十进制（ENIAC 那样）10 档，或者 10 个元件只用 1 个档挨得近，或者元件浪费进位、比较都要专门设计1960 年代后逐渐退出
三进制（苏联 Setun，1958）3 档中间档要稳住，难没有现成的逻辑代数可用理论上省元件约 5%，只造了约 50 台
二进制2 档：有电 / 没电两档离得最远，余量最大直接套布尔代数：与、或、非此后所有通用计算机

本页学二进制：元件只需要分清“有/没有”，噪声余量最大，又能直接用布尔代数设计电路。代价是同一个数要多写几位（十进制 3 位的 999，二进制要 10 位），这点代价远小于可靠和便宜带来的好处。

④关键洞察：比特没有意思，意思来自约定

先知道这些
  • 位置计数法：1999 = 1×1000 + 9×100 + 9×10 + 9×1，每一位的“权”是 10 的幂。二进制一样，只是权换成 2 的幂：1101 = 8 + 4 + 0 + 1 = 13。
  • 十六进制：4 个二进制位正好是 0～15，用 0～9、A～F 一个字符写完。所以 1 个字节（8 位）写成两个十六进制字符，0x25 = 0010 0101。
  • 比特（bit）：binary digit 的缩写，一个 0 或 1。这个词是统计学家 Tukey 起的，香农 1948 年的论文让它流行开来。

为什么一字节是 8 位

早年的机器有 6 位字符、36 位字的。1964 年 IBM System/360 定成 8 位：够放一个英文字符（256 种），也能塞两个十进制数字，还是 2 的幂，地址好算。后来的机器都跟着它走。“byte”这个词是 IBM 的 Buchholz 在 1956 年起的。

左边这张表就是“1 + 1 = 10”：和写 0，进 1。把很多个这样的电路串起来，低位的进位接到高位，就能加 32 位、64 位的数。

为什么负数非用补码不可

下面表格里的 −3 分别按三种约定来写，所以图案不一样。三者是什么、怎么换算、为什么补码能让减法变加法，单独讲在 第 1 课补充 · 原码、反码、补码。

先说清楚“好的负数表示法”要满足什么。一个 int 的格子数是固定的，这里用 4 位举例，一共 16 种图案，要从里面挑一部分来代表负数。挑法好不好，看三条要求：

  1. 要求 1 · 直接相加就对CPU 里的加法器只会做一件事：把两串 0 和 1 按位相加，超出 4 位的进位直接丢掉，它不管哪个数是正、哪个是负。如果负数按某种约定存好以后，把 3 和 −3 交给这个加法器，出来的正好是 0，那正数、负数、加法、减法就能共用这一个电路。做不到的话，就得另造一套“先看正负号、再比大小、再决定加还是减”的电路，CPU 又大又慢。加法是 CPU 里用得最多的运算，所以这一条最要紧。
  2. 要求 2 · 0 只有一种写法如果除了 0000 还有另一个图案也表示 0，那么判断“是不是 0”“两个数相不相等”都要多查一种情况，还白白浪费掉一个图案。
  3. 要求 3 · 正负大致各占一半16 种图案，一半给负数、一半给 0 和正数，能表示的范围才对称、够用。

下面拿这三条逐个检查原码、反码、补码。都用 4 位，都拿 −3 举例：

为什么补码直接加就对？关键在“超出 4 位的进位丢掉”。4 位最多到 1111（15），再加 1 变成 1 0000，丢掉最前面的 1 就回到 0000，就像钟走满一圈回到起点。所以这个加法器其实是一个 16 格的钟：只能往前走，满 16 就绕回来。在这样的钟上，往回走 3 格和往前走 13 格停在同一个地方（13 + 3 = 16，正好一圈），就像墙上的钟往回拨 3 小时等于往前拨 9 小时。补码把 −3 存成 13 的图案 1101，于是“加上 −3”在加法器眼里就是“往前走 13 格”，绕完正好落在对的位置。

为什么不用另造减法器？a − b 就是 a + (−b)。在补码里，−b 等于“b 每一位取反，再加 1”：取反用一排非门就能做，加 1 交给加法器最低位的进位输入。所以减法 = 一排非门 + 同一个加法器，不需要第二套电路。原码做不到，因为原码里加上一个负数本来就算不对（要求 1）。

一句话：三种约定都能“表示”负数，差别在于表示出来以后，那个只会按位相加的加法器能不能直接算对。只有补码能，而加法是 CPU 里用得最多的运算，所以选它。代价是最小的那个负数没有对应的正数：4 位里是 −8，int 里是 −2147483648，于是 Math.abs(Integer.MIN_VALUE) 还是负数（坑 1）。从零慢慢推一遍，看 第 1 课补充 · 原码、反码、补码。

机制 3 · 小数：把科学计数法搬进二进制（IEEE 754）

  • 为什么 0.1 存不准：0.1 = 1/10，分母里有 5。二进制小数只能精确表示分母是 2 的幂的数（1/2、1/4、3/8……），就像十进制写不完 1/3 = 0.333…。
  • 精度有多少：尾数 52 位加上隐含的 1，一共 53 位有效二进制数字，约 15～17 位十进制。所以 253 以内的整数都能精确存，再往上就开始跳着存（坑 4）。
  • float 是同样的结构缩成 32 位：1 + 8 + 23，有效位 24 位，约 7 位十进制。

Java 定死的约定

整数类型全是补码，只有 char 无符号；float / double 是 IEEE 754；String 对外是一串 UTF-16 的 char。这些在 JLS 里写死，和你跑在什么 CPU 上无关。C 语言里 int 多宽要看平台，Java 不用操这个心。

⑤手推一遍：13、−13、0.1、“你”，再让 Java 对答案

拿纸笔推四个数，每个对应 ④ 的一条机制。推完再跑程序核对；先推后看，错的地方就是没懂的地方。

  1. 1 十进制转二进制13 不停除以 2 记余数：13→余 1，6→余 0，3→余 1，1→余 1。余数倒着读：1101。补满 8 位：0000 1101。验算：8 + 4 + 1 = 13。（机制 2）
  2. 2 求 −13每位取反：1111 0010；再加 1：1111 0011，写成十六进制是 F3。验算：0000 1101 + 1111 0011 = 1 0000 0000，第 9 位丢掉，正好是 0。（补码）
  3. 3 0.1 转二进制小数部分不停乘 2 记整数位：0.2→0，0.4→0，0.8→0，1.6→1，1.2→1，0.4→0，0.8→0，1.6→1……从 0.4 开始又转回来了，所以 0.1 = 0.0001 1001 1001…₂，写不完。规格化成 1.1001 1001… × 2−4，指数存 −4 + 1023 = 1019。（机制 3）
  4. 4 “你”转 UTF-8码点 U+4F60 = 0100 1111 0110 0000，在 U+0800～U+FFFF 之间，用 3 字节模板。16 位按 4、6、6 切开：0100 | 111101 | 100000，填进去：1110 0100 10 111101 10 100000 = E4 BD A0。（机制 4）
  5. 5 换个读法字节 41 42 43 44：当 ASCII 是 “ABCD”；当大端 int 是 0x41424344 = 1094861636；倒过来当小端 int 是 0x44434241。同一串比特，读法不同，结果完全不同。

// 把低 n 位按 4 位一组打出来：bin(13, 8) = "0000 1101"
static String bin(long v, int n) {
    StringBuilder sb = new StringBuilder();
    for (int i = n - 1; i >= 0; i--) {
        sb.append((v >>> i) & 1);              // 右移到最低位，再只留这一位
        if (i % 4 == 0 && i > 0) sb.append(' ');
    }
    return sb.toString();
}

⑥边界和变体

第一圈 · 注意事项

1整数溢出不报错实测← ④ 机制 2
现象
累加金额、计数、乘法算容量时，结果突然变成负数；Math.abs(Integer.MIN_VALUE) 还是负数。
根源
n 位只有 2n 格，加法器把第 n+1 位的进位直接丢掉，结果自动对 2n 取模，在钟面上绕了一圈。补码范围不对称，−231 没有对应的正数。
做法
可能超范围的用 long；不允许出错的用 Math.addExact / multiplyExact / toIntExact（JDK 8 起），溢出就抛 ArithmeticException；求绝对值用 Math.absExact（JDK 15 起）。
2byte 是有符号的实测← ④ 机制 2
现象
从文件、网络读到字节 0xC8，打印出来是 −56；用几个字节拼 int 时高位莫名全是 1。
根源
Java 的 byte 也是补码，1100 1000 最高位是 1 就是负数。转成 int 时做“符号扩展”：把最高位复制到前面 24 位。
做法
当无符号读写成 b & 0xFF 或 Byte.toUnsignedInt(b)；拼多字节整数直接用 ByteBuffer.getInt()。
3金额用 double实测← ④ 机制 3
现象
0.1 + 0.2 得 0.30000000000000004；对账差几分钱；new BigDecimal(0.1) 打出一长串。
根源
二进制小数写不完 1/10，存进去的就已经是近似值；new BigDecimal(double) 忠实地把这个近似值展开了。
做法
金额存成以“分”为单位的 long，或用 BigDecimal，构造时用 new BigDecimal("0.1") 或 BigDecimal.valueOf(0.1)；比较用 compareTo，不用 equals（2.0 和 2.00 的 scale 不同）。
4大 long 传到前端变了实测← ④ 机制 3
现象
后端返回雪花 ID 1859273618293211137，浏览器里 JSON.parse 之后变成 1859273618293211100，按 ID 查不到数据（node 实测）。
根源
JavaScript 的数字都是 double，只有 53 位有效位；超过 253 的整数只能跳着存。本机实测 (double)(2^53 + 1) 得到 253。
做法
ID 在 JSON 里序列化成字符串（Jackson 用 ToStringSerializer，或字段直接用 String）。ID 怎么生成见 分布式 ID。
5乱码：浣犲ソ、ä½ å¥½、锟斤拷实测← ④ 机制 4
现象
“你好”的 UTF-8 字节按 GBK 读成“浣犲ソ”，按 ISO-8859-1 读成“ä½ å¥½”；更惨的是先按 UTF-8 解坏、变成替换符 U+FFFD（字节 EF BF BD），再按 GBK 读，两个连在一起就是“锟斤拷”。
根源
字节本身没坏，写的人和读的人用了不同的编码。“锟斤拷”那种已经把原字节换掉了，救不回来。
做法
getBytes、new String、InputStreamReader、Files.readString 全都显式写 StandardCharsets.UTF_8。JDK 18 起默认字符集才固定为 UTF-8（JEP 400）；JDK 8 / 17 的默认值跟着操作系统走，Windows 中文版上就是 GBK。
6length() 不是字符数实测← ④ 机制 4
现象
"😀".length() 是 2；按 length() 截断昵称，把 emoji 劈成两半，显示成问号；MySQL 用 utf8 字符集的列存 emoji 报 Incorrect string value。
根源
String 数的是 UTF-16 单元，U+FFFF 以上的码点占 2 个。MySQL 的 utf8 其实是 utf8mb3，每个字最多 3 字节，放不下 4 字节的 emoji。
做法
数字符用 codePointCount，截断用 offsetByCodePoints；库表和连接都用 utf8mb4。

第二圈 · 使用规范

  • 金额一律 long 分或 BigDecimal(String)：防对账差几分钱。
  • 所有字节和字符串互转都写明 StandardCharsets.UTF_8：防换一台机器就乱码。
  • 数据库、连接串用 utf8mb4：防 emoji 写不进去。
  • 对外协议写明字节序和每个字段几个字节：防两端各按各的理解解析。
  • 计数器、累加和默认用 long，关键路径用 xxxExact：防静默溢出。
  • 超过 253 的整数 ID 在 JSON 里用字符串：防前端精度丢失。

第三圈 · 优化和深处

字节序：多字节数先放哪头

int 0x41424344 有 4 个字节。大端把高位字节放在低地址（41 42 43 44），小端反过来（44 43 42 41）。x86 和常见的 ARM 都是小端；网络协议约定大端（“网络字节序”）；Java 的 DataOutputStream 和 ByteBuffer 默认大端。本机实测同样 4 个字节，大端读 1094861636，小端读 1145258561。

Java 的 String 在内存里怎么存

JDK 8 是 char[]，每个字符 2 字节。JDK 9 起（JEP 254，紧凑字符串）改成 byte[] value 加一个 coder：全是 Latin-1 字符时每字 1 字节（LATIN1 = 0），否则按 UTF-16 存（UTF16 = 1）。对外 API 没变，纯英文字符串省一半内存。JDK 17 源码 String.java 第 156、4556 行。

JDK 里的位运算

HashMap.hash() 是 h ^ (h >>> 16)，把高 16 位混进低位，再用 (n - 1) & hash 取桶，这就是 ④ 的“取模 = 留低位”（详见 HashMap 图解）。Arrays.binarySearch 算中点用 (low + high) >>> 1（JDK 17 Arrays.java 第 1154 行）。2006 年 Joshua Bloch 写文指出“几乎所有二分查找都有这个溢出 bug”，JDK 自己的实现也中过。

一个比特当一条记录：位图

1 亿个用户今天签没签到，每人只要 1 位：1 亿 ÷ 8 = 12.5 MB。用 Set<Long> 存要几个 GB。Java 有 BitSet，Redis 有 SETBIT；布隆过滤器就是位图加几个哈希（布隆过滤器与 HyperLogLog）。表示方式选对了，算法和空间一起变。

自测

1. 用一句话说出这一页的精华

计算机里只有固定位数的比特，意思全来自读它的约定：位数定范围，约定定运算和误差；溢出、舍入、乱码都是“位数有限”或“约定不一致”的直接后果。

2. 十进制机器输在哪？

一个元件要可靠地分出 10 档，档挨得近，噪声一大就读错；用 10 个元件表示一位（ENIAC）又太浪费。二进制只分有和没有，余量最大，还能直接套布尔代数设计电路。

3. 整数溢出为什么不报错？

加法器把放不下的最高位进位直接丢掉，这正是补码“加减共用一套电路”的设计；对硬件来说这不是错误，而是对 2n 取模。要报错只能软件自己查，比如 Math.addExact。

从 ④ 机制 2 和“为什么负数非用补码不可”推出。

4. 预测：byte b = 127; b++; 之后 b 是多少？

−128。0111 1111 加 1 是 1000 0000，8 位补码里最高位是 1、权是 −128。

从 ④ 机制 2 的钟面推出：从最大的正数再走一格，越过缝到最小的负数。

5. 预测：float f = 16777217; 打印出来是多少？

1.6777216E7。16777217 = 224 + 1，float 只有 24 位有效位，最低那个 1 存不下，舍入到 224。

从 ④ 机制 3 推出：double 的边界在 253，float 的在 224。

6. 预测：一个只有 “Hello 123” 的 UTF-8 文件，用 GBK 打开会乱码吗？

不会。这些字符都在 0x00～0x7F 之内，UTF-8 和 GBK 在这一段都和 ASCII 一样，字节完全相同。乱码只会出在汉字这类多字节字符上。

从 ④ 机制 4 的 UTF-8 模板推出：1 字节的那一档就是 ASCII。

7. 预测：10 亿个有序数做二分查找，最多比几次？

30 次。230 ≈ 10.7 亿，10 亿的二进制是 30 位，每比一次去掉一位。

从 ④ 机制 5“log₂ n = 位数”推出。
