链表与空间换时间：多存几根指针，撤单就是 O(1)

链表把元素散放在内存里，靠每个节点存着的引用串起来。地址算不出来，所以按位置找是 O(n)；可一旦手里拿着那个节点，插入、删除只是改两三根指针，O(1)。“拿着节点”不是白来的：多存一根 prev、再加一张“订单号 → 节点”的哈希索引，每张单从 28 字节涨到 98 字节。这就是空间换时间：多花的每一块内存，都要说得出它让哪个操作变快了，也要算得过这笔账。

①要解决的问题：一个价位上排着几万张挂单，撤单要从中间删

交易靶场的订单簿里，同一个价格的挂单排成一队，先来先成交。行情热的时候一个价位能排几万张，而且撤单很频繁。这个队列要做三件事，要求每件都是 O(1)：不管队伍多长，做一次的代价都一样。

新单O(1)排到队尾
成交O(1)从队头取
撤单O(1)?按订单号从中间删
内存算得过多花的要说得出买了什么

假设场景：交易靶场 J 线的撮合引擎。真实交易所的订单簿也常用“每个价位一条双向链表 + 订单号索引”，这一页从零推出为什么。

②朴素做法：用 ArrayList 排队，撤单就“删掉再挪”

最顺手的写法是一个 ArrayList<Long> 装订单号：新单 add 到尾，成交 remove(0)，撤单 remove(id)。新单没问题，后两个都要挪。

ArrayList 撤光 1 万张30 ms随机顺序
撤光 4 万张545 msn ×4，时间 ×18
换成 LinkedList1104 ms反而慢一倍
双链表 + 索引5 ms本页要做的

数字是 ⑤ 里 CancelBench 的实测，2 核 ARM 虚机、JDK 17，只看比值。

  • 撤单 O(n)：找要从头比，删完还要挪；n 翻倍，撤光全部单的总时间约 ×4，是 O(n²)。
  • 成交 remove(0) 也是 O(n)：拿走第一个，后面全部前挪。
  • 新单 add 摊还 O(1)，内存最省：每张单 28 字节（一个 4 字节引用 + 一个 24 字节的 Long）。
不懂精华时的典型误用：听说“链表插删 O(1)”，就把 ArrayList 换成 LinkedList。实测更慢：LinkedList.remove(id) 照样要从头一个个找，而且每走一步都是一次指针跳转。O(1) 的前提是手里已经拿着那个节点，这一页的核心就是怎么拿到它。

本页学双向链表 + 哈希索引：只在两头进出，用 ArrayDeque；要按 key 从中间删、而且删得频繁，才值得多付 3.5 倍内存，去换“手里拿着节点”。这个“付内存买速度”的判断本身，就是这一页的另一半：空间换时间。

④关键洞察：散放、改指针、拿着节点、哨兵，再把空间也数进来

先知道这些
  • 引用就是地址：Java 的对象变量里存的是对象在堆里的位置。开着压缩指针（堆小于 32 GB 时默认开）一个引用占 4 字节。第 2 课讲过数组靠“地址能算”才快：数组为什么快。
  • 大 O 数的是次数：n 翻倍，活儿变几倍。这一课把同样的数法用到内存上：大 O 是怎么数出来的。
  • 对象头：每个 Java 对象前面有 12 字节的头，整个对象再补齐到 8 的倍数。所以一个 Long 是 12 + 8 = 20，补齐到 24 字节。

洞察 1 · 散放：节点在哪都行，靠 next 一个牵一个

  • 按位置找第 i 个：O(n)。每一步都要等上一个节点从内存读回来，才知道下一个在哪，缓存和预取帮不上。
  • 反过来，散放也有好处：插一个新节点不用挪任何人，找个空地方放下，改几根 next 就接进队伍了。

洞察 2 · 插删就是改指针：先让新节点指好，再让邻居指向它

双向链表每个节点有两根指针：next 指后一个，prev 指前一个。两头各放一个不存数据的哨兵节点（洞察 4 讲为什么）。下面一步步撤掉 #103、再挂上 #105，数一数一共改了几根指针。

准备点“下一步”。

撤单改了 2 根指针，追加改了 4 根，次数和队伍有多长无关，所以是 O(1)。顺序有讲究：追加时如果先执行 tail.prev = x，再去读 tail.prev 当“原来的最后一个”，读到的就是 x 自己，链就接歪了（坑 3）。

洞察 3 · O(1) 有前提：手里得拿着那个节点

洞察 4 · 哨兵：多放两个空节点，头尾的特殊情况全没了

JDK 17 LinkedList.unlink（无哨兵，节选）first / last 可能是 null
if (prev == null) {      // 删的是第一个
    first = next;
} else {
    prev.next = next;
    x.prev = null;
}
if (next == null) {      // 删的是最后一个
    last = prev;
} else {
    next.prev = prev;
    x.next = null;
}
OrderQueue.unlink（两个哨兵）没有分支
// head、tail 永远在，prev、next 永远不是 null
x.prev.next = x.next;
x.next.prev = x.prev;
x.prev = x.next = null;  // 断开旧节点

哨兵换来的是一条不变式

head.next 永远是第一张真单，tail.prev 永远是最后一张；没有单时 head.next == tail。对每个真节点 x，x.prev 和 x.next 都不是 null。有了这条，删头、删尾、删唯一一个、删中间，都是同一段代码。付出的是两个永远不存数据的节点，固定 64 字节，O(1) 的空间。

洞察 5 · 空间也要数：数“除了输入，额外开了多少”

空间复杂度和时间复杂度一个数法：n 翻倍，额外要的内存变几倍。输入本身（那 n 张单）不算，算的是你为了干活另外开的：新数组、哈希表，还有递归时一层层压上去的栈帧。最容易漏掉的就是最后这个。

额外空间典型来源例子
O(1)只用几个变量，“原地”改循环反转链表、双指针、数组原地交换
O(log n)递归，但每层把问题砍掉一个比例递归二分、快排平均情况的递归深度
O(n)多开一份和输入一样大的东西哈希表索引、拷一份数组、深度为 n 的递归
O(n²)两两之间都存一份n × n 的距离表、邻接矩阵

洞察 6 · 空间换时间：多存的每一块，都在给某个操作抄近路

空间换时间之前，先问三句：① 买的是哪个操作，它有多频繁？② 多出来的字节 × n，放得下吗（10 万张单多 7 MB，没事；1 亿条就是 7 GB）？③ 多了一份数据，谁保证两份永远一致？第三句最常被忘，见 坑 6。

为什么这样设计：JDK 里双向和单向链表都有

双向：LinkedList、LinkedHashMap、AQS 等待队列

  • 拿着任何一个节点，都能 O(1) 把它摘掉，也能往回走
  • LinkedHashMap 就靠它做 LRU：命中一次，把节点摘下来挪到尾巴
  • 代价：每个节点多一根引用，插删要改 4 根而不是 2 根

单向：HashMap 的桶、ConcurrentLinkedQueue

  • HashMap 删一个键，本来就是从桶头走过去找的，走的时候手里一直拿着前一个，用不着 prev
  • 无锁队列靠 CAS，一次只能原子地改一个引用；单向入队只改一根 next，双向要同时改两根，没法一步做完
  • 要“凭节点摘掉自己”就做不到
决定胜负的约束：需不需要“不经遍历，直接拿着节点摘掉它”。需要，就付 prev 的空间（撤单、LRU）；不需要，因为总是从头走过来，或者并发下一次只能原子地改一根，单向更省也更简单。

最少的语法

    final long id;
    Node prev, next;   // 引用就是“下一个在哪”

// 遍历：只能一个个走
for (Node x = head.next; x != tail; x = x.next) { … }

⑤OrderQueue.java（核心）完整代码 →
private final Node head = new Node(-1, 0);   // 哨兵
private final Node tail = new Node(-1, 0);   // 哨兵
private final Map<Long, Node> index = new HashMap<>();

public void add(long id, int qty) {          // 新单：O(1)
    Node x = new Node(id, qty);
    Node p = tail.prev;                       // 先记住原来的最后一个
    x.prev = p;  x.next = tail;               // ① 新节点先指好两边
    p.next = x;  tail.prev = x;               // ② 两边再指向它
    index.put(id, x);
}
public boolean cancel(long id) {              // 撤单：O(1) 平均
    Node x = index.remove(id);                // 找到它：查索引
    if (x == null) return false;
    unlink(x);                                // 摘掉它：改 2 根
    return true;
}
public Node pollFirst() {                     // 成交：O(1)
    Node x = head.next;
    if (x == tail) return null;
    index.remove(x.id);
    unlink(x);
    return x;
}

跑计时之前先猜：随机顺序撤光 4 万张单，ArrayList、LinkedList、双链表 + 索引，谁最慢？

LinkedList 最慢，比 ArrayList 还慢一倍。两者都是 O(n²)：每撤一张都要从头找。可 ArrayList 找的时候是顺着一块连续内存扫（第 2 课的缓存行和预取），删后的“挪”是一次 System.arraycopy；LinkedList 每走一步都要等一次指针跳转。O(1) 的 unlink 救不了 O(n) 的找。

读出来的结论
  • ArrayList 和 LinkedList 撤单都是 n 翻倍、时间 ×4，O(n²)；双链表 + 索引 n 涨 8 倍、时间涨不到 3 倍，总量是 O(n)，每张 O(1)。小 n 时它的时间主要花在建 10 万个对象上。

⑥边界和变体：链表的坑、复杂度速查、空间换时间清单

第一圈 · 注意事项

1LinkedList.remove(Object) 不是 O(1)实测← ④ 洞察 3
现象
为了“删得快”把 ArrayList 换成 LinkedList，撤光 4 万张单从 545 ms 变成 1104 ms。contains、indexOf 同理。
根源
删除 = 找到 + 摘掉。摘掉是 O(1)，按值找还是从 first 一个个 equals，O(n)，而且每步一次指针跳转，比扫数组还慢。
做法
要按 key 删就加索引拿到节点（本页的 OrderQueue）；遍历中顺手删用 iterator.remove()。
2在 LinkedList 上用下标循环实测← ④ 洞察 1
现象
for (int i = 0; i < list.size(); i++) list.get(i)，4 万个元素 689 ms；迭代器不到 1 ms。方法签名收的是 List，调用方传进来一个 LinkedList，就中招了。
根源
链表的第 i 个地址算不出来，get(i) 每次都要走过去。JDK 会从近的一端走（index < size >> 1 就从头），最多 n/2 步，n 次加起来还是 O(n²)。
做法
遍历一律用增强 for 或迭代器。真要按下标随机访问，先判断 list instanceof RandomAccess，不是就先拷进 ArrayList。
3改指针的顺序写反，链断了← ④ 洞察 2
现象
插入后正着走对，反着走少了一截；或者后半条链直接丢了，只剩前几张单。
根源
每一行赋值都会覆盖一个旧地址。先执行 p.next = x，原来 p 后面那个节点的地址就没了，再写 x.next = p.next 只能拿到 x 自己。规则：先让新节点指好两边（只写新节点的字段），再改邻居。
做法
把邻居先存进局部变量（Node p = tail.prev;），再按“新节点 → 邻居”的顺序写；单测里正着走一遍、反着走一遍，两边个数要相等。
4删头、删尾、删唯一一个时 NullPointerException← ④ 洞察 4
现象
中间删得好好的，一删第一张或最后一张就 NPE，或者 first 还指着已经删掉的节点。
根源
没有哨兵时，头尾节点的 prev 或 next 是 null，要单独分支（看 JDK 的 unlink 那两个 if），漏一个就错。
做法
自己写链表就放两个哨兵；测试至少覆盖空表、一个元素、删头、删尾四种。
5递归处理长链表，StackOverflowError实测← ④ 洞察 5
现象
测试时链表几百个节点，递归反转、递归求长度都没事；线上 10 万个节点直接 StackOverflowError。
根源
递归深度 = 链表长度，额外空间 O(n)，全压在只有几 MB 的线程栈上。加大 -Xss8m 本机能撑过 10 万，100 万照样溢出：只是把上限往后推。
做法
深度跟着输入涨的递归改成循环，额外空间回到 O(1)。树也一样：平衡树深度 log n，递归没事；退化成一条链的树，深度就是 n。
6索引和链表不同步← ④ 洞察 6
现象
成交时只从链表摘掉、忘了从索引删：内存只涨不降，已经成交的单还能“撤”一次，第二次 unlink 时 x.prev 已是 null，NPE。
根源
空间换时间多存了一份数据，就多了一条要守的不变式：“索引里的单 = 链表里的单”。多存的那份不会自己跟着变。
做法
两份数据封装在同一个类里，只通过 add / cancel / pollFirst 改，不把 Node 和 index 交出去；checkInvariants() 放进单测。
7增强 for 里调 list.remove，ConcurrentModificationException历史原因：fail-fast 约定
现象
单线程也会抛 ConcurrentModificationException。
根源
不是链表原理推出来的，是集合框架的约定：迭代器记着 modCount，发现集合被“绕过自己”改过，就立刻失败，免得接着走到已经摘掉的节点上。
做法
用 iterator.remove()，或者 list.removeIf(...)。

第二圈 · 使用规范

  • 列表默认 ArrayList，队列和栈默认 ArrayDeque：ArrayDeque 的 javadoc 原话是当栈用比 Stack 快、当队列用比 LinkedList 快。防的是“听说链表插删快”就换。
  • 只有“拿着节点摘掉它”是高频操作时，才用链表，而且往往要自己配一个索引：防坑 1。
  • 遍历用增强 for 或迭代器，边走边删用 iterator.remove()：防坑 2、坑 7。
  • 自己写链表：两个哨兵 + 一个 checkInvariants() 进单测：防坑 3、坑 4。
  • 多存的那份数据和原数据封在一个类里一起改：防坑 6。
  • 递归深度跟输入涨的，改循环：防坑 5。
  • 空间换时间写进设计时算一笔账：每条多几字节 × 预计最大条数 = 多少内存，和堆大小比一比。
  • 不要在多线程之间直接共享：OrderQueue 和 LinkedList 都不是线程安全的。javadoc 的建议是用 Collections.synchronizedList 包一层；撮合这类场景常见的做法是一个交易对只由一个线程处理。

第三圈 · 更深的地方

LRU 就是本页的结构 + 一个动作

LinkedHashMap 的节点比 HashMap 多两根 before、after，串成一条双链表。开了 accessOrder 后，每次 get 都会调 afterNodeAccess，源码注释就一句 // move node to last：把节点摘下来挂到尾巴。再覆盖 removeEldestEntry，满了就踢掉头上那个。和 OrderQueue 一样：哈希表负责找到，双链表负责 O(1) 挪动。详见 HashMap 的亲戚们。

摘掉以后为什么要把指针置 null

JDK 的 unlink 摘完会把 x.item、x.next、x.prev 都置 null。clear() 的注释说得直白：断开节点之间的链接“不是必需的”，但当丢弃的节点分散在新老两代时能帮分代 GC，而且就算外面还有迭代器拿着某个节点，内存也一定能释放。否则一个被谁拿着的旧节点，会顺着 next 拖住后面一整串。

反过来：时间换空间的快慢指针

判断一条链表有没有环，最直接的是用 HashSet 记住走过的节点：O(n) 时间、O(n) 额外空间。Floyd 的做法是两个指针，一个一次走一步、一个走两步，有环就一定会相遇：时间还是 O(n)，额外空间只有 O(1)。同一个问题，两种取舍。快慢指针还能 O(1) 空间找到中点。

JDK 里的链表地图

双向：LinkedList（first/last，无哨兵）、LinkedHashMap（before/after）、AQS 等待队列（prev/next，源码注释写着 next 只在可唤醒时才保证非空，正确性靠 prev）。
单向：HashMap 桶里的 next、ConcurrentLinkedQueue（volatile next + CAS）。详见 AQS 源码。

下一圈

  • 栈和队列、环形数组：ArrayDeque 怎么用一块数组做到两头 O(1)，为什么它比 LinkedList 快。见 第 5 课。
  • 跳表：在有序链表上叠几层“快车道”，用多一倍左右的指针换 O(log n) 查找，Redis 的 ZSet 用它。
  • LRU 的改进：LRU 怕一次全表扫描把热数据冲掉，Caffeine 的 W-TinyLFU 怎么用一点额外空间记频率。
  • 无锁队列：Michael-Scott 队列怎么只用 CAS 改一根 next 就做到线程安全，ConcurrentLinkedQueue 的来历。
  • 展开链表：每个节点放一小段数组，在“连续”和“好插入”之间折中，Redis 的 quicklist 就是这样。
  • 前缀和与差分：最典型的预计算，区间查询和区间修改各自 O(1)。

↺回到⑤：改一改 OrderQueue 和 SpaceCost

  1. 加一个 touch(id)：把这张单摘下来挂到队尾。先猜要改几根指针，再写。做对了，你就手写了一个 LRU 的核心，和 new LinkedHashMap<>(16, 0.75f, true) 做的是同一件事。（洞察 2、第三圈）
  2. 去掉哨兵：重写 add 和 unlink，数一数多了几个 if，再用 checkInvariants() 跑一遍手推那段。做对了，空表、删头、删尾都不会 NPE。（坑 4）
  3. 把 HashMap 换成数组：订单号是连续整数时，用 Node[]，下标 = 订单号 − 起始号。先猜每张单省多少字节，再跑 SpaceCost。按推算会从 98.5 降到 36 左右（32 B 节点 + 4 B 数组槽）：省掉了 HashMap.Node、Long 键和空槽。（洞察 6）
  4. 加大栈再试递归：用 -Xss8m 跑 SpaceCost。本机实测 10 万个节点能过，100 万个还是溢出。（坑 5）

自测

1. 用一句话说出这一页的精华

链表插删 O(1) 的前提是手里拿着节点；为了拿到它，要多存 prev 和一张索引，这就是用空间换时间，多花的每一块都要说得出买了哪个操作。

2. 用 ArrayList 做挂单队列，撤单慢在哪？

两次 O(n)：从头比对找到这张单，删掉后把后面的元素整体前挪。撤光 n 张就是 O(n²)，实测 n 翻倍时间约 ×4。

3. 换成 LinkedList 为什么反而更慢？根源是哪条原理？

remove(Object) 还是要从头一个个找，O(n)；O(1) 的只是找到之后的摘掉。而且链表每走一步都是一次指针跳转，缓存帮不上，所以比扫连续数组还慢一倍。

从 ④ 洞察 3（找到 + 摘掉）和洞察 1（地址算不出来）推出。

4. 预测：单向链表 + 哈希索引，能做到 O(1) 撤单吗？

不能。索引能 O(1) 拿到 #103，但要把它摘掉得改 #102 的 next，而单向链表不知道前一个是谁，只能从头找。除非索引里存的是“前一个节点”，可那样前一个节点被删时，后一个的索引也要跟着改，又多了一份要同步的数据。

从 ④ 洞察 3 和“为什么这样设计”推出。

5. 预测：每个价位一个 OrderQueue，10 万个价位，每个价位只挂 1 张单。平均每张单占多少字节，还是 98.5 吗？

远不止。每个 OrderQueue 自己就有两个 32 B 的哨兵、一个 HashMap 对象和它默认 16 个槽的表，这些是固定开销，平均到 1 张单上全算它的。本机 JOL 实测约 316 字节一张。大 O 只说“随 n 怎么涨”，n 很小、结构很多的时候，常数项才是大头。

从 ④ 洞察 4（哨兵是固定的 O(1) 空间）和洞察 6（逐块数字节）推出。

6. 预测：把 OrderQueue 的 add 写成先 tail.prev = x;，再 Node p = tail.prev; x.prev = p; p.next = x;，会怎样？

p 读到的是 x 自己：x.prev 指向自己，p.next = x 也是 x 指自己。原来的最后一张单的 next 还指着 tail，正着走看不到 x，反着走从 tail 进到 x 就原地打转。

从 ④ 洞察 2 推出：每次赋值都覆盖一个旧地址，要先记住邻居再改。

7. 预测：一个递归函数，每次把链表从中间分成两半，各自递归下去（比如链表归并排序）。100 万个节点会栈溢出吗？

不会。每层砍掉一半，递归深度只有 log₂(100 万) ≈ 20 层。额外的栈空间是 O(log n)，不是 O(n)。会溢出的是“每次只往前挪一个节点”的递归。

从 ④ 洞察 5 和第 3 课洞察 3（按比例砍半就是 log n）推出。
