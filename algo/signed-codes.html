原码、反码、补码：负数在机器里怎么存，减法为什么能变成加法

机器里只有 0 和 1，没有“−”号。原码、反码、补码是三种“用 0 和 1 表示负数”的约定：正数三种写法完全一样，只有负数不同。原码最好懂，但加法器算不对；反码改好了一半；补码让负数 −x 就存成 2ⁿ − x，于是减法变成加法，一个加法器管所有加减。今天的 CPU 和 Java 的整数只用补码。

全景：撮合引擎的一天 · 第 1 站地图：J01 · 数据结构与算法接在：第 1 课 · 机制 2深度：懂机制

这一页的位置第 1 课只用一小节带过了原码、反码、补码，太快了。这一页从零讲：先讲清“为什么需要约定”，再按历史顺序一个个推出来，每一步都看它解决了什么、还剩什么问题。全程只用 4 位（16 种图案），因为 4 位能一眼看全；32 位的 int 道理完全一样。学完再看 位运算那页的 ~ 和 >> 会顺很多。

①要解决的问题：4 个开关，没有“负号”这个开关

先知道这些（会了可以跳过）
  • 二进制：每一位只能是 0 或 1，从右往左每位的“权”是 1、2、4、8……。0101 = 0×8 + 1×4 + 0×2 + 1×1 = 5。
  • 4 位有几种图案：每位 2 种，4 位 2 × 2 × 2 × 2 = 16 种，从 0000 到 1111。只表示非负数时就是 0～15，这叫无符号数。
  • 位数是固定的：CPU 的一个 int 就是 32 个格子，不能临时多加一格。算出来超过 4 位的部分，没有地方放。

第 3 件为什么最要紧：CPU 里最常用的运算就是加法（算地址、循环计数、价格加减都是它）。如果“正数加负数”要另造一套电路、先判断再计算，CPU 就又大又慢。在全景第 1 站，"101.00" 被转成 long 的 10100 分；之后每一笔“价格变动 −50 分”“仓位 −2 手”，都要靠这套约定存下来、加对。

②朴素做法：原码，拿最高位当正负号

人写负数是“符号 + 大小”：−3 就是“负号”加“3”。照搬过来：最高位当符号（0 正、1 负），剩下 3 位存大小（绝对值）。这就是原码（sign-magnitude，“符号-大小”）。

先说清楚：−3 到底是 1011 还是 1101？都是，看用哪种约定。原码里 −3 写成 1011（这一节一直用原码）；补码里 −3 写成 1101（④ 会推出来）。你平时见到的、Java 和 CPU 里真正存的是补码 1101。同一个数有不同写法，同一个图案也有不同读法：1011 按原码读是 −3，按补码读是 −5。

看起来很好。但把它交给只会“按位相加、多出的进位丢掉”的加法器，就出事了（⑤ 实测）：

算式原码按位相加按原码读出来应该是
3 + (−3)0011 + 1011 = 1110符号 1、大小 110 = 6 → −60
5 + (−3)0101 + 1011 = 1 0000 → 丢掉进位 000002
2 + (−5)0010 + 1101 = 1111−7−3
(−2) + (−3)1010 + 1011 = 1 0101 → 0101+5（连符号都错了）−5
  • 加法器不能直接用：符号位被当成普通的数位一起加了。要算对，硬件得先看两个数的符号：同号就把大小相加、符号照抄；异号就先比谁的大小大，用大的减小的，符号跟大的走。这需要比较器、减法器、一堆判断。
  • 有两个 0：0000 是 +0，1000 是 −0。两个图案表示同一个数，比较“等不等于 0”要两种都查，还白白浪费了一个图案。
  • 优点：人读着最直观；求相反数只改一位。
一句话：原码的问题不在“能不能表示负数”，而在“表示出来以后，加法器算不对”。下面两种约定都是为了修这个。

④关键洞察：负数 −x 存成“16 − x”，减法就变成了加法

洞察 1 · 三者的定义和换算：从 +x 出发，一步一步变过去

记住一句话：正数三种码都一样，就是它本身的二进制。只有负数 −x 要“变”，三种码的变法都从 +x 的二进制出发：

−x 的写法规则−3−5−1−7
+x普通二进制0011010100010111
原码+x 的最高位改成 11011110110011111
反码+x 每一位取反1100101011101000
补码反码 + 11101101111111001

反过来，从补码读出是负几：同样“取反再加 1”。1101 → 取反 0010 → 加 1 0011 = 3，所以 1101 是 −3。取反加一做两次回到原样，因为 16 − (16 − x) = x。

三者的关系，一行记住：原码 → 改符号位；反码 → 全部取反；补码 → 全部取反再加 1。反码是从原码走到补码的中间一步：它已经想到“负数要把位翻过来”，只差最后那个“+1”。

只取反、不加 1 会得到什么？得到的是 −x − 1，比 −x 小 1。比如 +3 = 0011，只取反是 1100，按补码读是 −4；再加 1 才是 −3（1101）。所以“取反加一”和 位运算那页写的“~x = −x − 1”是同一个等式：−x = ~x + 1，把 +1 移到另一边就是 ~x = −x − 1。Java 里 ~3 是 −4，~3 + 1 才是 −3。JDK 的 Arrays.binarySearch 没找到时返回 -(插入点 + 1)，它正好等于 ~插入点，所以拿返回值 r 算插入点可以写 ~r。

洞察 2 · 为什么补码能让加法器算对：16 格的钟

先想一个生活里的例子。墙上的钟只有 12 格。现在 5 点，要拨回 3 小时，有两种拨法：往回拨 3 格，或者往前拨 9 格，都停在 2 点。因为钟只有 12 格，往前多走一圈等于没走：9 = 12 − 3，往前 9 等于往回 3。在一个会绕圈的钟上，减去 3 和加上 (12 − 3) 是一回事。

4 位的加法器正好就是一个 16 格的钟：1111（15）再加 1，第 5 位的进位没地方放、被丢掉，变回 0000。所以在 4 位里，减 3 = 加 13（16 − 3）。补码就是把 −3 直接存成 13 的图案 1101：这样“加上 −3”在加法器眼里就是“加 13”，绕一圈正好停在对的位置。

洞察 3 · 名字的来历：反码 = 15 − x，补码 = 16 − x

“每一位取反”在数值上是什么？4 位全是 1 的 1111 是 15。用 15 去减任何一个 4 位数，每一位都是“1 减 0 得 1，1 减 1 得 0”，不会借位，结果正好是每一位翻过来。所以：

数值上英文名中文“补”的意思
反码 −x15 − x（对 1111 求补）ones' complement：对“全 1”求补和 x 加起来正好凑满 1111
补码 −x16 − x（对 2⁴ 求补）two's complement：对 2 的 n 次方求补和 x 加起来正好凑满一圈 1 0000，丢掉进位就是 0

“取反再加 1”不是一条要背的规则，它就是 15 − x + 1 = 16 − x 的电路做法：取反（15 − x）用非门一步完成，不用做减法；再加 1 用的还是那个加法器。补码的“补”，就是“补到满一圈”。32 位的 int 同理，−x 存成 2³² − x。

洞察 4 · 另一种读法：最高位的权是 −8

不想“取反加一”时，可以这样直接读补码：普通二进制里最高位的权是 +8，补码里把它改成 −8，其余位照旧。

图案位权：−8421加起来
11011 → −81 → 401 → 1−8 + 4 + 1 = −3
10001 → −8000−8
11111 → −81 → 41 → 21 → 1−1
011101 → 41 → 21 → 17

这也说明了范围为什么是 −8～7：最小是只有 −8 那一位（1000），最大是除了它全是 1（0111）。−8 没有对应的 +8，因为 +8 需要 1000，而这个图案已经给了 −8。这是补码唯一的“代价”。

那为什么 1000 给了 −8，而不是 +8？

  1. 1 它本来两个都是在 16 格的钟上，1000 正好在 0 的对面：从 0 往前走 8 格到它，往回走 8 格也到它。对加法器来说，“+8”和“−8”是同一个位置（8 + 8 = 16，满一圈绕回 0），图案完全一样。按补码的规则求它的相反数，1000 取反得 0111，加 1 又回到 1000：它的相反数就是它自己（⑤ 实测）。所以读成哪个，加法都照样对，纯粹是约定。
  2. 2 总有一边要多一个16 个图案，0 占掉一个，剩下 15 个是奇数，没法平分：要么负数 8 个、正数 7 个，要么反过来。1000 就是多出来的那一个，必须分给某一边。
  3. 3 给负数，“最高位 = 正负号”才没有例外最高位是 1 的图案有 8 个（1000～1111）。把 1000 读作 −8，这 8 个就全是负数，“看最高位就知道正负”对全部 16 个图案都成立。读作 +8，就出现一个“最高位是 1 却是正数”的例外。
1000 读作 −8（实际的选择）1000 读作 +8（假设）
范围−8～7−7～8
判断是不是负数只看最高位：是 1 就是负数最高位是 1、而且不是 1000 才是负数：要多比较一次
按位权读数最高位的权固定是 −8，16 个图案用同一个公式：1000 = −8，1101 = −8 + 4 + 1 = −31000 要单独按 +8 读，公式有例外
4 位扩成 8 位把最高位往左复制：1000 → 1111_1000 = −8，照样对1000 是正数要补 0，1001 是负数要补 1：“复制最高位”这条规则失效

“最高位就是正负号”在 CPU 里用得极多：比较大小、判断溢出、>> 右移补什么、byte 转成 int 时左边补 0 还是补 1，看的都是这一位。把 1000 给 −8，硬件在这些地方都只看一根线；给 +8，每个地方都要多一个特例。所以多出来的那一个给了负数。Java 里一样：Integer.MIN_VALUE 的图案是 1 后面跟 31 个 0，它 < 0，>>> 31 得 1；(byte) 0x80 是 −128，扩成 int 是 0xffffff80，还是 −128（⑤ 实测）。代价就是这个最小值没有对应的正数，-MIN_VALUE 还是它自己（⑥ 坑 1）。

为什么最后选了补码

回到 ① 里定的三条要求，把三种约定放在一起逐条对一遍（例子都是 4 位）：

要求原码反码补码
1 · 交给加法器直接相加，结果就对 不能。3 + (−3) 算出 −6（② 的表）。符号位被当成普通数位一起加了，硬件只好另造“比符号、比大小、再加或减”的电路。 差一点。−x 存成 15 − x，比满一圈（16）少 1。所以每当结果越过钟面顶上那道缝、丢掉一个进位时，答案就少 1，要把那个进位再加回最低位（叫“循环进位”）。5 + (−3) 先得 1，补上才是 2。 能。−x 存成 16 − x，正好一整圈。加法器满 16 丢掉进位，本来就是在钟面上绕圈，所以直接加、直接丢就对（洞察 2 的动画）。
2 · 0 只有一种写法 不能。0000 和 1000 都是 0。 不能。0000 和 1111 都是 0。 能。只有 0000。
3 · 正负大致各一半 −7～7，两个 0 占掉两个图案。 −7～7，同上。 −8～7。代价是 −8 没有对应的 +8（洞察 4）。
附带的好处 人读最直观：看最高位定正负，后面直接是大小。 求相反数只要每位取反，不用加 1。 减法也不用另造电路：a − b = a + (b 取反 + 1)，取反用一排非门，加 1 交给加法器的进位输入。判断正负只看最高位。
一句话：加法器只会“按位加、丢进位”，也就是只会在 16 格的钟面上往前走。谁把 −x 放在“从 0 往回走 x 格”的那个位置上，谁就能直接用这个加法器。那个位置就是 16 − x，只有补码是这么放的；反码放在 15 − x，差一格；原码放的位置和钟面没关系。

⑤手推一遍，再让 Java 对答案

先自己推：同一组加法，三种约定各加一次

  1. 5 + (−3) 补码0101 + 1101 = 1 0010，第 5 位的 1 丢掉，0010 = 2。对。
  2. 5 + (−3) 反码0101 + 1100 = 1 0001，丢掉进位得 0001 = 1，少了 1；把丢掉的那个进位加回最低位，0010 = 2，才对。这就是反码多出来的那一步。
  3. 5 + (−3) 原码0101 + 1011 = 1 0000 → 0000 = 0。错，见 ②。
  4. 6 + 3 补码0110 + 0011 = 1001 = −7。错了，但不是补码的错：9 超出了 4 位能表示的 −8～7，这叫溢出。在钟面上就是从 7 越过底下那条红线走到了负数那半圈。
⑤SignedCodes.java完整代码 →
// 三种约定把十进制 x 写成 4 位图案（MASK = 0b1111，SIGN = 0b1000）
static int encSignMagnitude(int x) { return x >= 0 ? x : (SIGN | -x); }   // 原码：符号位 | 大小
static int encOnes(int x)          { return x >= 0 ? x : (~(-x)) & MASK; } // 反码：+x 取反
static int encTwos(int x)          { return x & MASK; }                     // 补码：Java 本来就是补码，截低 4 位即可

// 对全部 2^32 个 int 验证“相反数 = 取反加一”
int x = Integer.MIN_VALUE;
while (true) { if (-x != ~x + 1) bad++; if (x == Integer.MAX_VALUE) break; x++; }

Java 的 int 就是 32 位补码：
  -3 = 11111111111111111111111111111101，~3 + 1 = -3

原码今天还在哪：double 的符号位
  0.0 == -0.0 → true；Double.valueOf(0.0).equals(-0.0) → false；1 / 0.0 = Infinity，1 / -0.0 = -Infinity
读出来的结论
  • 补码那一列，加法器直接加、丢进位，四道题全对；反码要多做一步“把进位加回来”；原码四道全错。
  • Java 的整数就是补码：-x 和 ~x + 1 在全部 42 亿个 int 上一个不差。
  • -MIN_VALUE 还是它自己：−2³¹ 没有对应的 +2³¹（洞察 4 的“代价”）。
  • 原码没有消失：double 用“符号位 + 大小”，所以真的有 −0.0，== 说它等于 0.0，equals 说不等。
到这里已经能交差了：给一个负数，能写出它的原码、反码、补码；给一个补码，能读出是几；能说清补码为什么让减法变成加法。
已知还没处理的细节：坑 1 最小值没有相反数，坑 2 溢出不报错，坑 3 同一个字节两种读法，坑 4 double 的 −0.0。

⑥边界和变体

第一圈 · 注意事项

1Math.abs 返回负数实测← ④ 洞察 4
现象
Math.abs(Integer.MIN_VALUE) = −2147483648。拿它做“哈希值取绝对值再取模”分桶，会得到负的下标。
根源
补码范围是 −2³¹～2³¹−1，最小值的相反数 2³¹ 放不下；取反加一又绕回它自己。
做法
分桶用 Math.floorMod(h, n) 或 (h & 0x7fffffff) % n；要报错用 Math.absExact（JDK 15 起）。
2溢出不报错，悄悄绕圈实测← ④ 洞察 2
现象
Integer.MAX_VALUE + 1 得到最小的负数；成交额累加到 21 亿多突然变负。
根源
补码加法就是在钟面上走，越过“7 → −8”那条线，加法器不会喊，只会继续走。这正是补码电路简单的代价。
做法
金额、数量用 long；要在溢出时报错用 Math.addExact / multiplyExact，见第 1 课坑 1。
3同一个字节，有符号和无符号读出来不一样实测← ④ 洞察 1
现象
报文里的字节 0xFF，Java 的 byte 读出来是 −1；(byte) 200 是 −56。
根源
图案只是 1111_1111，是 255 还是 −1 全看约定。Java 的 byte 固定按补码读，没有无符号 byte。
做法
要当无符号数用时 b & 0xFF 或 Byte.toUnsignedInt(b)，见 位运算 · 坑 3。

现象
0.0 == -0.0 是 true，但 Double.valueOf(0.0).equals(-0.0) 是 false；1 / -0.0 是负无穷。把 double 当 HashMap 的 key，0.0 和 −0.0 是两个 key。
根源
IEEE 754 浮点数的符号用的就是原码的办法（一位符号 + 大小），于是继承了“两个 0”。
做法
金额别用 double（第 1 课坑 3）；非要比较时用 == 或先加 0.0 归一。

第二圈 · 使用规范

  • 只在“读位”的时候想补码：平常写 a - b 就好，不用自己“取反加一”；看十六进制、读字节、写位运算时才需要它。
  • 边界值单独测：凡是取绝对值、取相反数、做差的代码，单测里放上 Integer.MIN_VALUE。
  • 注释写明是有符号还是无符号：协议里的 4 字节整数，文档写清“uint32”还是“int32”，读的人才知道要不要 & 0xFFFFFFFFL。

第三圈 · 往深一点

减法器在哪

CPU 算 a − b 时，把 b 每位取反（非门）再让加法器的最低位进位输入为 1，等于加上 ~b + 1 = −b。所以“减法”只是加法器多接了一排非门和一个进位，这就是补码省掉的那套电路。

反码今天还在：网络校验和

IPv4、TCP、UDP 的校验和是“反码求和”（RFC 1071）：16 位一组相加，溢出的进位绕回最低位，最后取反。它的好处是和字节序无关、增量更新方便。

第四种：移码（偏置）

把每个数加上一个固定偏置再存：4 位偏置 8 时，−8 存成 0000、0 存成 1000、7 存成 1111。好处是图案的大小顺序就是数的大小顺序。double 的指数部分就是这么存的（偏置 1023）。

为什么判断正负只看最高位

补码里最高位为 1 的图案恰好是 −8～−1，为 0 的是 0～7，所以“是不是负数”就是看一位，CPU 里叫符号标志。>> 右移时补的也是这一位，见 位运算。

自测

  

    
1. 用一句话说出原码、反码、补码是什么
三种用 0 和 1 表示负数的约定：正数三者相同；负数 −x，原码是 +x 改符号位，反码是 +x 全部取反（= 15 − x），补码是反码加 1（= 16 − x）。

    
2. 原码到底差在哪？
它能表示负数，但交给只会按位相加的加法器，结果不对（3 + (−3) 得 −6），硬件要先比符号、比大小、再加或减；而且有 +0 和 −0 两个零。

    
3. 为什么“加上 1101”等于“减去 3”？
4 位加法器满 16 就绕回 0（进位丢掉），所以它算的是“对 16 取模”。1101 是 13 = 16 − 3，加 13 等于往前走 13 格，在 16 格的钟上就停在“往回走 3 格”的位置。

    
4. 预测：8 位补码里 −1 是什么图案？−128 呢？
−1 = 256 − 1 = 255 = 1111_1111；−128 = 256 − 128 = 128 = 1000_0000。
从 ④ 洞察 3 推出：n 位补码的 −x = 2ⁿ − x。

    
5. 预测：如果 CPU 用反码，x - x 会得到什么图案？
x − x = x + (−x) = x + (15 − x) = 15 = 1111，也就是反码的 −0。结果“等于 0”，但图案不是 0000，判断是否为 0 要查两种图案。
从 ④ 洞察 3 推出：反码的 −x 是 15 − x，差一个 1 才满一圈。

    
6. 放回全景：第 1 站把用户填的“价格变动 −50 分”存进一个 byte，会怎样？
byte 是 8 位补码，范围 −128～127，−50 存得下，图案是 256 − 50 = 206 = 1100_1110。但只要变动超过 ±127 分（1.27 元）就会溢出绕圈，比如 −200 存进去变成 56，价格方向都反了。所以价格、金额一律用 long。

    
7. 为什么补码里 1000 是 −8，不是 +8？
在 16 格的钟上 1000 正好在 0 的对面，+8 和 −8 是同一个位置，加法怎么读都对；15 个非零图案没法平分，总得有一边多一个。把它给负数，“最高位是 1 就是负数”对所有图案都成立，判断正负、右移、byte 转 int 都只看最高位，不用特判。
从 ④“那为什么 1000 给了 −8”推出。
