①要解决的问题：100 万分给哪几个策略

第二个问题来自第 1 站网关：用户敲了 BTC-UDST，系统里没有这个交易对。要在已上线的交易对里找“最像”的那个，提示“你是不是要 BTC-USDT”。“最像”用编辑距离衡量：最少改几个字符能变过去。

②朴素做法：按收益率贪心，或者全试一遍

做法结果疼在哪
按收益率从高到低投（第 19 课）只投 A，赚 30A 占了 6 份，剩 4 份谁都投不进；B + C 正好 10 份、赚 38。2000 组随机数据里错 360 组（⑤ 实测）
每个策略投 / 不投全试（第 20 课）38，对2ⁿ：策略库里 50 个策略就是 10¹⁵ 种
按“前 i 个、剩 w 份”记表38，对n × W 格，50 个策略 × 1000 份 = 5 万格
  • 贪心错的根源和第 19 课的怪面额一样：投了 A，剩下的 4 份被“堵死”了，这一步影响了以后能做什么。
  • 如果钱可以按比例投（投 4 份给 B 就赚 16），按收益率贪心就是对的，这叫“分数背包”。整数约束是贪心失灵的原因。
不懂精华时的典型误用：资金按“元”建表。预算 100 万元就是 100 万列，再乘以几百个策略就是几亿格。背包的复杂度和预算的数值成正比，粒度要先想好（④ 洞察 4）。

③几种思路

问题做法为什么
钱可以按比例投按收益率贪心没有“堵死”：剩多少就按比例投多少，交换论证成立
每个策略投 / 不投0-1 背包 DP状态 (前 i 个, 剩 w)，O(nW)
同一个东西可以用无数次（面额凑钱）完全背包 DP同上，只是遍历顺序反过来（洞察 2）
预算数值太大（W 上亿）、策略很少（n ≤ 40）折半枚举（meet in the middle）2^(n/2) 两半各自枚举再二分拼，第 20 课“下一圈”
两个串之间的差别序列 DP（编辑距离、LCS）状态 (a 走到 i, b 走到 j)，O(nm)

本页学 0-1 背包、完全背包和编辑距离：三个最常用的 DP 形状，面试里的 DP 题大多是它们的变形。

④关键洞察：状态里装“已经考虑到哪”和“还剩多少”

先知道这些
  • DP 四问：状态、转移、起点、顺序和答案。见 第 21 课。
  • 二维数组的内存：long[n][W] 占 8 × n × W 字节，见 第 2 课。

洞察 1 · 0-1 背包：第 i 个策略，投还是不投

状态 dp[i][w]：只考虑前 i 个策略、预算 w 份时的最大收益。“前 i 个”保证每个策略只被决定一次；“剩多少”决定了以后还能投什么，这两个数之外的历史都无关。转移只有两条：

转移第 i 个策略要 cost 份、赚 gain
dp[i][w] = max( dp[i-1][w],                      // 不投：预算原样留给前 i-1 个
                dp[i-1][w - cost] + gain )       // 投：先扣掉 cost，剩下的给前 i-1 个
// 起点：dp[0][w] = 0（一个策略都没有，赚 0）；答案：dp[n][W]

洞察 2 · 压成一维要倒着填，正着填就成了“可以重复投”

第 i 行只用到第 i−1 行，表可以只留一行 dp[w]。问题是：更新 dp[w] 要用“上一行的” dp[w − cost]。从大到小填，用到的 dp[w − cost] 还没被这一轮改过，是上一行的；从小到大填，它已经被这一轮改过，等于同一个策略又投了一次。

倒序：0-1 背包

for (w = W; w >= cost; w--)
每个策略最多投一次。用在：策略分资金、选哪几个任务进有限的机器时间。

正序：完全背包

for (w = cost; w <= W; w++)
同一个东西能用无数次。用在：面额凑钱、拆单手数。第 19 课 {1,3,4} 凑 6 的最少枚数就是它。

洞察 3 · 序列 DP：两个串各走到哪，状态就是 (i, j)

编辑距离 dp[i][j]：a 的前 i 个字符变成 b 的前 j 个字符，最少几步。看两个串的最后一个字符：相同就不用动，不同就三选一（替换、删 a 的、插 b 的），各自退回一个更小的子问题。

洞察 4 · 为什么这样设计：O(nW) 是“伪多项式”

按预算建表

  • n 个策略 × W 份，每格 O(1)
  • W 是“份数”，粒度可以自己定
  • 代价：W 看的是数值，不是位数。预算从 10 份细到 100 万份，时间、内存都 ×10 万

按策略组合枚举

  • 和预算数值无关
  • 2ⁿ，n = 50 就跑不完
决定胜负的约束：0-1 背包是 NP 难问题，没有“对 n 和预算位数都是多项式”的算法。DP 能快，是因为它把复杂度押在了预算的数值上：数值小（按 10 万一份）时极快，数值大（按 1 元一份）时就慢。工程上的对策是先定粒度，把预算和资金都换成整数份。

⑤手推一遍，再看规模

手推就是 ④ 的分步动画：dp[10] 最后是 38，来自上一行的 dp[5] = 20 加上 C 的 18。下面是 Java 版，加上 2000 组对拍、预算粒度和编辑距离。

// 0-1 背包，一维倒序
static long oneD(int[] cost, int[] gain, int W) {
    long[] dp = new long[W + 1];
    for (int i = 0; i < cost.length; i++)
        for (int w = W; w >= cost[i]; w--)
            dp[w] = Math.max(dp[w], dp[w - cost[i]] + gain[i]);
    return dp[W];
}
// 编辑距离
for (int i = 1; i <= n; i++)
    for (int j = 1; j <= m; j++) {
        int same = a.charAt(i - 1) == b.charAt(j - 1) ? 0 : 1;
        dp[i][j] = Math.min(dp[i-1][j-1] + same, Math.min(dp[i-1][j] + 1, dp[i][j-1] + 1));
    }

读出来的结论
  • 一维正序算出 40：B 被投了两次（5 + 5 份、20 + 20），这正是完全背包的答案，不是 0-1 背包的。

⑥边界和变体

第一圈 · 注意事项

10-1 背包内层写成正序实测← ④ 洞察 2
现象
预算 10，B 被投了两次，算出 40，比真实最优 38 多。
根源
正序时 dp[w − cost] 已经是这一轮更新过的值，包含了“已经投过这个策略”的情况。
做法
0-1 背包倒序，完全背包正序；拿不准就先写二维版对拍。
2算“有多少种”时，两层循环换了位置← ④ 洞察 2
现象
{1,3,4} 凑 6：外层面额、内层金额得 4 种；外层金额、内层面额得 9 种。
根源
外层面额时，每种面额按固定顺序加入，[1,1,4] 和 [4,1,1] 只算一次（组合）；外层金额时，每一步都能选任何面额，顺序不同算不同（排列）。
做法
先问业务要组合还是排列：拆单方案（不管顺序）用外层面额；下单序列（顺序有关）用外层金额。
3预算按“元”甚至“分”建表实测← ④ 洞察 4
现象
200 个策略、预算 100 万份就要 400 ms（⑤ 实测）；100 万元按元算正好是这 100 万份，再按分算（第 1 课的价格就存分）就是 1 亿份，要 40 秒和 800 MB。
根源
O(nW) 里的 W 是数值，不是位数。
做法
资金按业务能接受的最小单位取整（1 万、10 万）；W 实在大、n 小，就换折半枚举。
4两个长串的编辑距离开满二维表实测← ④ 洞察 3
现象
1 万 × 1 万字符，二维 int 表 381 MB；10 万字符就是 37 GB。
根源
每格只看上一行和本行，整张表大部分用完就没用了。
做法
只要距离：留两行，内存 O(m)。要具体改法：用 Hirschberg 分治，或者像 git diff 那样换 Myers 算法（只在差别小的对角带上搜）。

第二圈 · 使用规范

  • 先写二维，再压一维：二维版不会写错循环方向，拿来对拍压缩版。
  • “恰好装满”和“不超过”起点不同：不超过用 dp[w] = 0；恰好装满除 dp[0] = 0 外都填负无穷，否则会把“装不满”的方案当成合法。
  • 要输出选了哪几个，就留二维表：一维压缩丢了“从哪来的”，倒推不回去。

第三圈 · 这几种形状在哪里出现

拼写纠错、模糊搜索

输入框“你是不是要”、日志里的相似错误归类，都用编辑距离。只要“距离 ≤ 2 的”时，可以只填对角线附近的一条带，O(n·k)。

diff 和对账

两份成交流水按行比对，找“多了哪几行、少了哪几行”，是 LCS。git diff 默认用 Myers 算法，它和 LCS 求的是同一件事，但在差别小时快得多。

多重背包、多维背包

每个策略最多投 k 份：把 k 拆成 1、2、4…（二进制拆分），变成 log k 个 0-1 物品。资金和人力两种限制：状态多一维 dp[w][h]。

最长上升子序列

价格序列里最长的一段“不一定连续、但一路上涨”的点：dp 是 O(n²)，加第 9 课的二分是 O(n log n)。面试高频。

实验台：8 个策略分资金

先猜：把 0-1 背包的内层循环改成正序，算出的收益和正确答案比？

浏览器里现算：每组 8 个策略由固定种子生成（资金 3～12 份，收益是资金的 3～4.5 倍，收益率相近时贪心最容易被“堵死”）；0-1 背包用二维表并倒推选了谁；“正序”是 ⑥ 坑 1 的错误写法；贪心按收益率从高到低。

下一圈

  • 带依赖的背包：策略 B 要求先投基础设施 A，树形 DP。
  • Myers diff：git diff 为什么不用 O(nm) 的 LCS 表。
  • DP 优化：单调队列优化多重背包、四边形不等式，竞赛方向，后端基本用不到。

↺回到⑤：改一改

  1. 输出投了谁：用二维版 twoD，从 dp[n][W] 往回看：dp[i][w] ≠ dp[i−1][w] 说明投了第 i 个。⑤ 的例子应输出 B、C。（第二圈）
  2. 恰好用完预算：改起点为负无穷，求“10 份正好花完”的最大收益，再把预算改成 7 份，看看是不是“无解”。（第二圈）
  3. 两行编辑距离：把 EditDistance 改成只留两行，1 万 × 1 万字符时内存从 381 MB 降到不到 1 MB，结果仍是 196。（坑 4）

自测

1. 用一句话说出这一页的精华

背包的状态是“前 i 个、剩多少”，序列的状态是“两个串各到哪”；其余照第 21 课的四问填表，0-1 背包压成一维要倒序。

2. 按收益率贪心错在哪？什么时候它又是对的？

投了收益率最高的 A，剩下的预算被“堵死”，B + C 更好。钱可以按比例投（分数背包）时，剩多少投多少，不存在堵死，贪心就对。

3. 0-1 背包一维写正序为什么会多算？

正序更新 dp[w] 时，dp[w − cost] 已经是本轮更新过的、可能已包含这个策略，等于同一个策略投了不止一次。

4. 预测：资金粒度从 10 万一份细化到 1 万一份，DP 的耗时大约变成几倍？答案会变吗？

约 10 倍（W 变成 10 倍）。答案可能变好：更细的粒度下，原来“差几万投不进”的组合现在能投了；但如果所有资金本来就是 10 万的整数倍，答案不变。

从 ④ 洞察 4 推出：复杂度 O(nW)，W 跟数值走。

5. 预测：编辑距离只允许“替换”，不允许插入和删除，会变成什么？

两个串长度必须相等，答案就是对应位置不同的字符个数（汉明距离），不需要 DP，O(n) 一遍。三条转移只剩左上那一条，表退化成对角线。

从 ④ 洞察 3 推出：去掉上、左两条箭头，dp[i][j] 只依赖 dp[i−1][j−1]。

6. 放回全景：第 1 站网关加了“你是不是要 BTC-USDT”提示，对撮合有什么影响？

没有直接影响：纠错只在报文解析失败时跑，给用户返回提示，订单不会进第 2 站。要注意的是别在热路径上对每个报文都跑编辑距离；交易对几百个，查一次几百 × 8 × 8 格，只在失败分支做就够。

档位：标准。本机跑过（2026-11-21，2 核 Neoverse-N1 虚机，OpenJDK 17.0.21，--release 8 编译）：⑤ 的全部输出。坑 2 里“外层金额得 9 种”是手算的（f[6] = f[5] + f[3] + f[2] = 6 + 2 + 1），坑 3 里“1 亿份 40 秒、800 MB”是按实测的 100 万份 400 ms 线性外推的，都没有在本机跑。按公开资料：git diff 默认算法是 Myers（git 文档 diff.algorithm）。实验台是浏览器里现算的。
