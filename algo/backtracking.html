回溯：把所有选择走一遍，走不通就退回来

回溯是“把所有方案一个不漏地列出来”的标准写法：做选择 → 递归往下 → 撤销选择，沿着一棵决策树做 DFS。它本身是指数级的，能不能用全看剪枝：一条路刚看出不可能，就别往下走了。

①要解决的问题→ ②朴素做法→ ③几种思路→ ④关键洞察→ ⑤手推一遍→ ⑥边界和变体→ ↺回到⑤

全景：撮合引擎的一天 · 第 12 站地图：J01 · 数据结构与算法上一课：第 19 课 · 贪心深度：会用

这一页的位置第五圈第二课。第 19 课的贪心每步只走一条路；回溯每步把所有路都走一遍，是“证明不了贪心时”的保底办法。它就是 第 13 课的递归加上“撤销”，走的是 第 16 课 DFS 的路线。下一课 DP 会在回溯上再加一步：把重复走的子树记下来。

①要解决的问题：要“所有方案”，一个不能漏

回测站有两类需求，答案不是一个数，而是一份清单：

②朴素做法：嵌套 for 循环，或者先全生成再过滤

做法疼在哪
每张单一层 for 循环挂单张数是运行时才知道的，for 写几层？4 张写 4 层，100 张写不出来
二进制枚举：0 到 2ⁿ−1，每一位表示吃不吃能写，但每个子集都要算一遍；n = 30 就是 10 亿个，大多数早就超了 8 手
先生成全部组合，再过滤“短 = 50、长 = 10”这种明显不合法的组合也先造出来；参数一多，内存先爆
回溯：递归一层做一个选择，不合法当场退回层数跟着数据走；一条路刚超就不往下走，整棵子树都省了
  • for 循环的层数写死在代码里；递归的层数由数据决定，这是回溯要用递归的原因。
  • 先全生成再过滤，浪费的不是一个组合，而是“以这个前缀开头的所有组合”。
  • 缺的那一块：边生成边检查，前缀一不行，整棵子树一起扔。
不懂精华时的典型误用：把回溯当成“万能暴力”，n = 40 也照样上。回溯不改变指数级的本质，只是让常数小很多；只要个数或最优值、不要具体清单时，该换第 21、22 课的 DP。

③几种思路

思路能给出所有方案多快适合
二进制枚举能永远 2ⁿ，不能剪枝n ≤ 20、写起来最短
回溯（本课）能最坏指数级，剪枝后常常小几个数量级要清单、约束多、n 到几十
动态规划（第 21、22 课）一般只给个数或最优值多项式（状态数 × 选择数）只要“多少种”“最多多少”
贪心（第 19 课）只给一个方案最快能证明不后悔

本页学回溯：题目要“所有方案”“所有排列”“所有合法组合”时用它；只要一个数时先想 DP。

④关键洞察：一棵决策树，DFS 走一遍，能剪就剪

先知道这些
  • 递归和调用栈：每调一层，参数和局部变量压一帧，返回时弹掉。见 第 13 课。
  • 子集个数：n 个东西，每个选或不选，共 2ⁿ 个子集；n 个东西排成一排有 n! 种。见 第 0 课 · 排列组合。

洞察 1 · 方案 = 决策树上的一条路；回溯 = 在树上做 DFS

树的每一层做一个选择（“下一张吃哪张”），从根走到某个节点，路上的选择就是一个方案。代码里不用真的建树：递归调用就是往下走一层，返回就是退回父节点。路径上的选择放在一个共享的 path 里，往下走时加一个，退回来时删掉，这个“删掉”就是“回溯”二字的来历。

洞察 2 · 剪枝：在“走进去之前”就判死

可行性剪枝

加上这张就超了 8 手：不进去。先把挂单升序排好，这张超了，后面的更大更超，直接 break，一整排兄弟节点一起省掉。

界限剪枝

当前 6 手，剩下的全吃也凑不到 8：整棵子树里不可能有答案，直接返回。剩下的总和用后缀和预先算好（第 12 课反过来）。

去重

挂单 [2,3,3,5] 凑 5，两张 3 手单会给出两个 [2,3]。排好序后，同一层里和前一个数量相同的就跳过：i > start && a[i] == a[i-1]。

剪枝的效果是乘法：在第 k 层剪掉一个节点，省掉的是它下面整棵子树，最多 2ⁿ⁻ᵏ 个节点。所以越早剪越值：排序、预算后缀和这些准备工作，都是为了让判断能在浅层就做出来。

洞察 3 · 为什么要“撤销”：所有层共用一个 path

为什么这样设计：递归 + 共享状态 + 前置判断

回溯

  • 层数由数据决定，代码长度固定
  • 前缀一不合法，整棵子树不生成
  • 内存 O(深度)，答案边找边输出
  • 代价：最坏仍是指数级；递归太深会栈溢出

先全生成、再过滤

  • 逻辑分两段，好理解
  • 不合法的也全造出来，时间 2ⁿ 跑满
  • 全放在内存里，内存也是 2ⁿ
决定胜负的约束：方案数本身可能是指数级的，没法比它更快；能省的只有“注定失败的那部分”。回溯的全部设计（排序、后缀和、同层去重、共享 path）都在做一件事：让失败尽早被发现，并且不为它付内存。
回溯模板剪枝的细节放到 ⑥
void dfs(int start, int sum) {
    if (sum == target) { res.add(new ArrayList<>(path)); return; }  // 存副本
    for (int i = start; i < a.length; i++) {        // a 已升序
        if (i > start && a[i] == a[i - 1]) continue; // 同层去重
        if (sum + a[i] > target) break;              // 超了，后面更大
        path.add(a[i]);                              // 做选择
        dfs(i + 1, sum + a[i]);                      // 往下
        path.remove(path.size() - 1);                // 撤销
    }
}

⑤手推一遍，再看剪枝省了多少

手推就是 ④ 的分步动画：[2,3,5,6] 凑 8，走 9 个节点，找到 {2,6} 和 {3,5}。下面把同样的代码跑在随机挂单上（每张 1～40 手，凑 60 手）。

// 不剪枝：每个子集都是一个节点，共 2^n 个
static void plain(int[] a, int start, int sum, int target, List<Integer> path, List<List<Integer>> res) {
    nodes++;
    if (sum == target) res.add(new ArrayList<Integer>(path));
    for (int i = start; i < a.length; i++) {
        path.add(a[i]);
        plain(a, i + 1, sum + a[i], target, path, res);
        path.remove(path.size() - 1);
    }
}

读出来的结论
  • n = 24 时剪枝把 1677 万个节点砍到 1325 个，差四个数量级。凑 60 手、每张平均 20 手，三四张就超了，可行性剪枝在第三四层就把树砍断。
  • “种数”两边不一样不是错：随机挂单里有相同数量，不去重时“第 1 张 5 手 + …”和“第 2 张 5 手 + …”算两种，去重后按“数量组合”算一种。要哪种由业务定（见 坑 4）。
  • 两个坑的输出很典型：存了引用，最后全是空列表；忘了撤销，列表越来越长。
到这里已经能交差了：任何“列出所有组合 / 子集 / 排列”的需求，都能套 ④ 的模板写出来。

⑥边界和变体

第一圈 · 注意事项

1res.add(path)：结果全是空列表实测← ④ 洞察 3
现象
找到 2 个答案，打印出来是 [[], []]。
根源
所有答案存的是同一个 path 对象的引用；搜索结束时它被撤销回空了。
做法
res.add(new ArrayList<>(path))，存副本。
2忘了撤销：路径越来越长实测← ④ 洞察 3
现象
答案变成 [2, 3, 5, 6, 6, 5, …]，还会漏掉正确答案。
根源
退回父节点时没把自己那一步删掉，兄弟节点接着在脏的 path 上加。
做法
add 和 remove 成对写在递归调用的两边；用 sum + a[i] 这种传值参数的量不用撤销。
3没排序就用 break 剪枝← ④ 洞察 2
现象
挂单 [6,2,3] 凑 5：第一张 6 超了就 break，[2,3] 根本没机会试，答案为空。
根源
“这张超了，后面更超”只在升序时成立。
做法
先 Arrays.sort；不能排序时（比如要保留原顺序）只能 continue，不能 break。
4重复组合：该不该去重实测← ④ 洞察 2
现象
[2,3,3,5] 凑 5，得到两个 [2,3]。
根源
两张 3 手单在树上是不同的分支，但数量组合相同。
做法
按“数量组合”算：排序 + 同层跳过相同。按“具体哪几张单”算（成交要落到订单号上）：不能去重，两张 3 手单是两个方案。
5正则也是回溯，写坏了一个请求占满一个 CPU实测← ④ 洞察 1
现象
JDK 17 上 (x?)(a+)+b\1 匹配 26 个 a 加一个 c，耗时 2.5 秒；每多两个字符慢 4 倍。
根源
java.util.regex 是回溯引擎：(a+)+ 把 n 个 a 切成几段有 2ⁿ⁻¹ 种切法，失败前要全试。JDK 11 起的 Pattern 会记下“从位置 i 开始的这个循环已经失败过”（源码 Loop.posIndex、localTCNCount），所以普通的 (a+)+b 只要 0.1 ms；但正则里一有反向引用 \1，这个记忆就关掉（hasGroupRef）。JDK 8 的源码里没有这个记忆。
做法
别写嵌套量词；用户输入先限长；网关这类要处理外部输入的地方，正则要过一遍 ReDoS 检查。

第二圈 · 使用规范

  • 先估算规模再动手：n 个元素的子集 2ⁿ、排列 n!，n = 20 的子集约 100 万、排列约 2.4×10¹⁸。防的是把排列当子集估。
  • 状态能传值就传值：sum、start 用参数传，不放成员变量，少一处要撤销的地方。
  • 给搜索设上限：节点数或耗时超过阈值就停下报警，防“正常数据跑 1 ms、某天数据跑一小时”。
  • 深度可能上万时改显式栈：JDK 17 默认栈大约一万层就溢出，见 第 13 课。

第三圈 · 回溯的几种形状

子集 / 组合

本课的形状：for (i = start; …)，往下传 i + 1，每个元素最多用一次。传 i 就是“可以重复用”（同一价位可以吃多次）。

排列

顺序有关（下单的先后）：每层从 0 开始扫，用 boolean[] used 标记用过的；去重时条件变成 a[i]==a[i-1] && !used[i-1]。

棋盘类：N 皇后、数独

每层放一行，用三个集合（列、两条对角线）O(1) 判断冲突；再进一步用位运算，8 皇后 92 个解瞬间出来。

回溯 + 记忆 = DP 的入口

正则那个优化就是“记下从位置 i 开始失败过”。如果子树的结果只取决于少数几个参数（位置、剩余手数），就能记下来复用，这就是第 21 课的记忆化搜索。

实验台：剪枝能省多少

先猜：24 张随机挂单（每张 1～40 手）凑 60 手，剪枝 + 去重后要走多少个节点？（不剪枝是 1677 万）

浏览器里现算：固定种子生成挂单，不剪枝的节点数是 2ⁿ（每个子集一个节点，按公式算，不真跑），其余三列真的递归一遍数节点。和 ⑤ 的 Java 版用的随机数不同，数字不会一模一样。

下一圈

  • 分支限界：求最优方案时，用“当前最好答案”当界限剪枝，再用堆决定先走哪个分支（第 6 课 + 本课）。
  • 迭代加深、双向搜索：n = 40 时把挂单分成两半各自枚举 2²⁰，再用第 8 课的哈希表或第 11 课的双指针拼起来（meet in the middle）。
  • RE2 / 线性时间正则：不用回溯、用自动机匹配，保证线性时间，代价是不支持反向引用。

↺回到⑤：改一改

  1. 参数组合：用同一个模板枚举 ① 的均线参数（短 × 长 × 止损），在选“长周期”那一层就剪掉“长 ≤ 短”。做对了输出 30 种，节点数比 48 少。（洞察 2）
  2. 可以重复吃：同一价位的挂单可以吃多次（递归传 i 而不是 i + 1）。[2,3,5,6] 凑 8 应该有 4 种：{2,2,2,2}、{2,3,3}、{2,6}、{3,5}。
  3. 设上限：给 pruned 加一个节点上限，超过 100 万就抛异常，n = 32、每张最多 5 手时看它会不会触发。（第二圈）

自测

1. 用一句话说出这一页的精华

回溯是在决策树上做 DFS：做选择、往下、撤销；它天生指数级，靠尽早剪枝把注定失败的子树整棵扔掉。

2. 嵌套 for 循环和“先生成再过滤”各差在哪？

for 的层数写死在代码里，数据一变就写不出来；先生成再过滤会把不合法前缀开头的整棵子树都造出来，时间和内存都是 2ⁿ。

3. res.add(path) 为什么得到一堆空列表？

所有层共用一个 path，存进去的是同一个引用；搜索结束时 path 撤销回空，所有“答案”都指向它。

4. 预测：把挂单改成降序排列，break 剪枝还对吗？

不对。降序时这张超了，后面的更小，可能不超，break 会漏答案；只能改成 continue，或者把条件反过来写成“这张加上也不够就 break”之类的配套判断。

从 ④ 洞察 2 推出：break 的前提是“后面的只会更大”。

5. 预测：要的不是组合清单，只要“凑 60 手一共有多少种组合”，n = 200，还用回溯吗？

不用。方案数本身可能是天文数字，一个个数一定超时。只要个数时，“从第 i 张开始、还差 s 手”这两个数就决定了子树里有多少种，用 dp[i][s] 记下来，O(n × target) 就算完，这是第 22 课的 0-1 背包计数。

从 ④ 第三圈“回溯 + 记忆”推出：子树结果只取决于 (i, s)。

6. 放回全景：第 1 站网关用一个写坏的正则校验用户输入，会怎样？

一条精心构造的报文能让一个网关线程卡几秒甚至更久，后面的订单排队，第 3 站的定长队列可能空着、第 2 站的去重也等着；几个这样的请求就能拖垮网关。这是正则的回溯问题，不是撮合的问题。

档位：标准。本机跑过（2026-11-21，2 核 Neoverse-N1 虚机，OpenJDK 17.0.21，--release 8 编译）：⑤ 的全部输出，以及坑 5 的正则耗时。按源码（已核对）：JDK 17 java/util/regex/Pattern.java 的 Loop.posIndex、localTCNCount、hasGroupRef 注释“Turn off the stop-exponential-backtracking optimization if there is a group ref”；jdk8u 的 Pattern.java 里没有 localTCNCount，jdk11u 里有（没有在 JDK 8 上实测）。实验台数字是浏览器里现算的。
