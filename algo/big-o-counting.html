大 O 是怎么数出来的：操作次数、最坏和平均、摊还与 log n

大 O 不是计时，是数次数：找到最内层那个操作，数它随 n 执行多少次，再只留涨得最快的那一项。它回答的问题是“数据量翻倍，活儿变成几倍”。同一段代码要说清按哪种输入数：最坏是保证，平均要假设输入，摊还是一串操作的总账；log n 只出现在“每一步砍掉一半”的地方。

这一页的位置第 1 课讲了数据怎么变成比特，第 2 课讲了数组为什么能 O(1) 取下标。前两课一直在用 O(1)、O(n)、log n，这一课把这些记号本身讲清楚：它们是怎么数出来的，能说明什么，说明不了什么。

①要解决的问题：测试 1 万笔都很快，上线 400 万笔会怎样

对账任务：每笔订单要在支付流水里找到自己那一笔。两个同事各写了一版，测试环境 1 万笔，一个 24 毫秒，一个 2 毫秒，看起来都没问题。上线后一天 400 万笔，n 涨了 400 倍。问题是：不上线，能不能先算出它们会变成多慢？

要会的第 1 件事数看着代码，数出操作次数怎么随 n 涨
第 2 件挑输入说清按最好、最坏、平均还是摊还在数
第 3 件认 log n知道它从哪来，为什么几乎不涨
第 4 件验证用“n 翻倍看几倍”在本机核对

面试问“这段代码复杂度是多少”，考的就是前三件；代码评审里说“这里会 O(n²)”，是在第一件上提前拦住事故。

②朴素做法：掐表，或者逐行精确计数

最直接的办法是跑一遍、看耗时。另一个办法是把每条语句执行几次都算出来，写成 3n² + 5n + 7 这样的精确式子。两个都能用，但都答不了①的问题。

做法能告诉你什么疼在哪
掐表计时这台机器、这份数据、这个 n 下要多久换机器、换数据、换 n 就不算数；1 万笔时 24 ms 和 2 ms 都“很快”，看不出谁会爆
精确计数每条语句执行几次太细：一次 a[i]+a[j] 在不同 CPU、JIT 下代价不同，系数 3 和 5 没有意义；式子越长越看不出重点
  • 掐表只给一个点，可①要的是一条线：n 往大了走，时间怎么走。
  • 小 n 时谁快，常常由常数决定，不由涨势决定。⑤ 的实测里，O(n) 的 HashSet 在 100 万时比 O(n log n) 的排序还慢 4 倍。
  • 写代码之前、评审时、面试时，手边没有 400 万笔数据可跑。
  • 精确计数的方向是对的：数次数，不数秒。只是数得太细，需要一个“该扔就扔”的规则。
不懂精华时的典型误用：“本地 1 万条测过了，才 24 毫秒。”这句话说明不了上线后的任何事。要问的是：n 翻倍，它变成 2 倍还是 4 倍？

③几种思路：数到多细，怎么核对

思路做法什么时候用局限
单点计时跑一次看几毫秒已经确定量级，最后量一下常数不能外推
精确计数 T(n)每条语句的次数加起来算法论文、极端优化依赖机器，太细

双倍法实测n 取 1×、2×、4×、8×，看耗时比值上线前核对大 O 有没有估错比值会被缓存、GC 带偏一点，看量级

④关键洞察：数次数、只看涨势、挑输入、认出砍半

先知道这些
  • 基本操作：一次比较、一次加法、一次数组下标读写，耗时和 n 无关，记作 1 次。下标为什么是常数时间，见第 2 课：地址是算出来的。
  • log₂ n：n 能对半砍几次才剩 1。1024 砍 10 次，100 万砍 20 次，40 亿砍 32 次。它是 2 的乘方倒过来：第 1 课里 32 个比特能编 2³² ≈ 43 亿个号。
  • 1 + 2 + … + (n−1) = n(n−1)/2：n 个人两两握手的次数。

洞察 2 · 只看涨势：扔掉常数和小项，就是大 O

T(n) = ½n² − ½n。n 一大，½n 那一项占比越来越小；系数 ½ 取决于机器和编译器，不是算法本身的性质。两样都扔掉，剩下 n²，记作 O(n²)。

1,000500,0005000.1%
1,000,0005 × 10¹¹5 × 10⁵0.0001%，扔掉没影响

正式的说法

T(n) = O(f(n))：存在常数 c 和 n₀，只要 n ≥ n₀，就有 T(n) ≤ c · f(n)。也就是“n 够大以后，T 被 f 的某个倍数压住”。所以 ½n² − ½n = O(n²)，取 c = 1 就行。

三个记号

O 是上界（不比它快涨），Ω 是下界（不比它慢涨），Θ 是上下都压住。严格说 n 也是 O(n²)，但没人这么用：日常和面试说的 O，意思基本都是 Θ，即“正好是这个量级”。

扔掉常数以后，几种常见量级的差距只剩涨势。按每秒 10⁸ 次基本操作粗估：

洞察 3 · log n：每一步砍掉一个固定比例

二分查找每看一次中间元素，就能扔掉一半。n 个砍到 0 个，要砍 log₂ n + 1 次左右。点“下一步”看 16 个元素怎么砍：

图比屏幕宽，左右滑动看全图 →

准备点“下一步”。

同一个道理换个形状，就是 n log n：归并排序把 n 个拆成两半、再两半……一共 log₂ n 层，每一层把所有元素合并一遍，是 n 次。

  • 底数不重要：log₂ n = log₁₀ n × 3.32，只差常数倍，所以统一写 O(log n)。B+ 树每页几百个分叉，底数是几百，3～4 层就装下上千万行，但它仍然是 O(log n)。
  • 认出 log n 的信号：循环变量乘或除一个常数（i *= 2、n /= 10），递归每次只进一半，树的高度（TreeMap 红黑树、堆）。
  • 只砍掉一个不算：每步把规模从 n 变成 n−1（比如每次去掉最大的一个），要走 n 步，是 O(n)。必须按比例砍。

洞察 4 · 同一段代码，输入不同次数不同：最好、最坏、平均

按什么数意思靠什么成立
最坏所有输入里最慢的那个什么都不靠，对任何输入都是保证
平均按某种输入分布求期望靠一个假设：输入是“随机”的、哈希是均匀的。假设被打破，平均就不成立
最好最走运的输入几乎没用，只能说明下限

JDK 的文档也是这么分开写的。HashMap 的 javadoc 原文：“constant-time performance for the basic operations (get and put), assuming the hash function disperses the elements properly”。后半句就是平均成立的前提；所有 key 撞进同一个桶时，JDK 7 及以前一个桶是链表，get 退化成 O(n)。JDK 8 起，一个桶超过 8 个（TREEIFY_THRESHOLD = 8）且表长至少 64 时，桶转成红黑树，最坏变成 O(log n)。

洞察 5 · 摊还：贵的那一次，摊到前面所有便宜的头上

ArrayList.add 大多数时候放进去就完了，偶尔数组满了要扩容，把旧元素全搬一遍，那一次是 O(n)。只看最坏就得说“add 是 O(n)”，这太悲观了：贵的那一次很少来。看一串 add 的总账：

摊还 ≠ 平均

平均要假设输入是随机的，运气差就不成立。摊还不靠运气：任何一串 n 次操作，总量都不超过 c·n。它是对一整串操作的最坏保证。ArrayList 的 javadoc 正是这么说的：“The add operation runs in amortized constant time, that is, adding n elements requires O(n) time.”

前提：按倍数扩

每次扩到 r 倍（r > 1），搬的总数约 n/(r−1)：2 倍约 n，1.5 倍约 2n，1.1 倍约 10n，都是 O(n)，摊到每次是 O(1)。每次只加固定个数 k，搬的总数约 n²/(2k)，摊到每次是 O(n)。JDK 17 的 ArrayList 每次扩 1.5 倍：oldCapacity >> 1。

纠正上一课：第 2 课的“下一圈”写过“1.5 倍、2 倍都行，1.1 倍就不行”，不准确。1.1 倍也是摊还 O(1)，只是常数到了 10 左右；真正不行的是按固定个数扩。⑤ 里有实测的搬运次数。

为什么这样设计：大 O 为什么偏要扔掉常数

渐进记号：只留涨势

  • 换 CPU、换语言、换 JDK 都成立，十年前的分析今天还能用
  • 写代码之前就能用，不用先有数据
  • 直接回答“n 翻倍会怎样”
  • 代价：看不见常数和缓存。第 2 课里同样是 O(n) 的两段代码差了 17 倍

精确计时或精确计数

  • 对眼前这台机器最准
  • 换一台机器、升一次 JDK 就作废
  • 回答不了 n 涨 400 倍以后的事
  • 系数太多，比较两个算法时看不出谁注定会输
决定胜负的约束：数据量会涨几个数量级，硬件和实现的常数只差几倍到几十倍。所以先用大 O 定量级，挑出不会爆的写法；同一量级里再比常数。JDK 自己就是这么做的：JDK 17 的 Arrays.sort(int[]) 是 O(n log n) 的双轴快排，但递归切到只剩几十个元素的小区间时，改用 O(n²) 的插入排序，因为 n 很小时常数说了算（源码：最左边的小区间少于 MAX_INSERTION_SORT_SIZE = 44 个，其余小区间在 MAX_MIXED_INSERTION_SORT_SIZE = 65 个上下）。
看代码数量级：速查边界情况放到 ⑥

四步口诀

1 找最内层的基本操作。
2 数它执行几次：顺序相加，嵌套相乘，调用的方法展开。
3 扔掉常数和低阶项。
4 说清按哪种输入：最坏、平均，还是一串操作摊还。

⑤手推一遍：先在纸上数，再让程序数，最后计时核对

三段代码，先按 ④ 的四步口诀在纸上推出答案，再跑两个程序对答案：Count 只数次数，不计时，哪台机器跑都一样；Doubling 用双倍法计时。

  1. 1 两两配对第 i 行内层跑 n−1−i 次，加起来 n(n−1)/2。预测：n 翻倍，次数 ×4，耗时也 ×4 左右。
  2. 2 二分查找每看一次剩一半，找不到时最多看 ⌊log₂ n⌋ + 1 次。预测：100 万看 20 次，400 万看 22 次；n 翻倍只多看 1 次。
  3. 3 一路 add按倍数扩容，搬运总数约 n/(r−1)。预测：1.5 倍时每次 add 平均搬 2 个左右；每次 +10 时，100 万次 add 一共要搬约 5 × 10¹⁰ 个。
  4. 4 跑 Count对次数：应该和公式一个不差。
  5. 5 跑 Doubling对涨势：O(n²) 的比值接近 4，O(n log n) 略大于 2，O(n) 接近 2。偏离多少、为什么偏，正好是大 O 管不到的那部分。

// 不计时，只数次数：在最内层放一个计数器
static long pairSumCompares(int[] a, int target) {
    long ops = 0;
    for (int i = 0; i < a.length; i++)
        for (int j = i + 1; j < a.length; j++) {
            ops++;                                   // 基本操作：一次相加比较
            if (a[i] + a[j] == target) return ops;
        }
    return ops;
}

static long binarySearchSteps(int[] a, int x) {
    long ops = 0;
    int lo = 0, hi = a.length - 1;
    while (lo <= hi) {
        ops++;                                       // 看一次中间元素
        int mid = (lo + hi) >>> 1;
        if (a[mid] < x) lo = mid + 1;
        else if (a[mid] > x) hi = mid - 1;
        else return ops;
    }
    return ops;
}

// 动态数组：和 ArrayList 一样从容量 10 起步，满了按 g 扩容，数一共搬了几个
static long[] grow(int n, Growth g) {
    long copies = 0, grows = 0, maxOne = 0;
    int cap = 10, size = 0;
    for (int k = 0; k < n; k++) {
        if (size == cap) {
            copies += size; maxOne = Math.max(maxOne, size); grows++;
            cap = Math.max(g.next(cap), cap + 1);
        }
        size++;
    }
    return new long[]{copies, grows, maxOne, cap};
}

读出来的结论
  • 次数和公式一个不差：n(n−1)/2、(n+1)/2、⌊log₂ n⌋+1 都对上了。400 万个订单里二分，最多看 22 次。
  • O(n²) 和 O(n log n) 的比值很稳：×4 和 ×2.1，跑两遍一样。O(n log n) 多出来的 0.1 正是 log 那一项：log(2n)/log(n) 在 n = 100 万时约 1.05。
  • O(n) 的 HashSet 反而最不稳：比值 2.2～2.7，两遍差得也多；而且 100 万时比 O(n log n) 的排序慢 4 倍。原因不在大 O：每个元素装箱成 Integer、散落在堆上，表越大越装不进缓存，GC 也越忙。这就是第 2 课讲的常数和缓存。
  • 按倍数扩容，平均每次只搬 1～10 个；按固定个数扩，100 万次 add 搬了 500 亿个，第 99,999 次扩容一次搬了近 100 万个。
到这里已经能交差了：看一段代码能说出它的量级和按哪种输入算，能用双倍法在本机核对。
已知还没处理的细节：藏在方法调用里的循环（坑 1），小数据测不出问题（坑 2），平均被打成最坏（坑 3），摊还 O(1) 的那一次很慢（坑 4），量级一样快慢不一样（坑 5）。

⑥边界和变体：大 O 骗人的地方，和它更深的地方

第一圈 · 注意事项

1一行代码，里面是一个循环← ④ 洞察 1
现象
循环里写了 list.contains(x)、list.remove(0)、str += s，代码只有一层循环，数据一多却按 n² 变慢。
根源
数次数时要把调用展开：ArrayList.contains 从头比到尾，remove(0) 要把后面的全往前挪，String 不可变，每次 += 都复制一遍已有的内容。外层 n 次 × 里面 n 次。
做法
查找换 HashSet / HashMap，从头部取换 ArrayDeque.pollFirst()，拼字符串用 StringBuilder。拿不准的方法先看 javadoc 里写的复杂度。
2小数据上测过，就以为没问题← ④ 洞察 2
现象
①的写法 A：1 万笔 24 毫秒，上线 400 万笔约 1 小时。
根源
大 O 说的是 n 够大以后的涨势。n 小时常数和低阶项说了算，O(n²) 完全可能比 O(n) 快。
做法
先问生产上 n 的上限是多少，按量级估；性能测试至少取 3 个规模，看比值，不看单点。
3平均 O(1)，被人打成最坏← ④ 洞察 4
现象
接口收外部传来的字符串当 HashMap 的 key，有人专门构造一批哈希值相同的 key，CPU 打满。自己写的 hashCode() 返回常数，也是同样的后果。
根源
“平均 O(1)”成立的前提是哈希均匀。前提被打破，所有 key 进同一个桶：JDK 7 是链表，O(n)；JDK 8 起超过 8 个转红黑树，O(log n)，而且 key 要实现 Comparable 才排得好。
做法
hashCode() 用 Objects.hash 或 IDE 生成；外部输入限制个数和长度；做 key 的类型尽量实现 Comparable。
4摊还 O(1)，但偏偏那一次很慢实测← ④ 洞察 5
现象
撮合、行情这类按毫秒算延迟的代码里，平均很快，偶尔一次 add 卡一下。⑤ 里 1.5 倍扩容、加到 100 万时，最大一次搬了 81 万个元素。
根源
摊还是一串操作的总账，不保证每一次都便宜。贵的那一次一个不少，只是隔得远。
做法
知道大概规模就预设容量：new ArrayList<>(n)；HashMap 按 n / 0.75 + 1 给初始容量。要每一次都有上限的场景，用预分配的环形数组。
5量级一样，快慢差十几倍实测← ④ 设计取舍
现象
⑤ 里 O(n) 的 HashSet 在 100 万时比 O(n log n) 的排序慢 4 倍；第 2 课里同为 O(n) 的两种遍历差 17 倍。
根源
大 O 扔掉了常数，而常数里装着装箱、指针跳转、缓存不命中、GC。这是有意的取舍，不是大 O 错了。
做法
大 O 用来排除注定会爆的写法；量级相同的候选，用实测（最好是 JMH）定胜负。
6两个规模硬合成一个 n← ④ 洞察 1
现象
对 n 个订单逐个查 m 个商户的规则，写成“O(n²)”，评审时吓到人；或者反过来，m 其实会涨到和 n 一样大，却当成常数。
根源
次数是 n × m，两个变量要分开写成 O(n·m)。只有 m 有固定上限（比如最多 20 条规则），它才算常数。
做法
每个变量写清含义和上限：“O(n·m)，n 是订单数，m ≤ 20”。

第二圈 · 使用规范

  • 循环里调方法，先查它的复杂度：防坑 1，O(n²) 大多藏在一行调用里。
  • 对外接口写死数据量上限（分页 size 最大值、批量接口最多几条）：n 不受控，任何 O(n²) 都会被放大成事故。
  • 复杂度的注释写上变量含义和上限：防坑 6，“O(n·m)，m ≤ 20”比“O(n²)”有用。
  • 已知规模就预设容量：防坑 4 的扩容毛刺，也省掉多余的搬运和垃圾。
  • 性能回归用双倍法，至少 3 个规模：防坑 2，单点数字说明不了涨势。
  • 说复杂度时带上“最坏 / 平均 / 摊还”：防坑 3、4，“HashMap 是 O(1)”这句话少了前提。

第三圈 · 更深的地方

递归的复杂度：画递归树

递归没法直接数循环，就写成递推式再画树。④ 的归并排序是 T(n) = 2T(n/2) + n：log₂ n 层，每层 n，得 n log n。二分查找是 T(n) = T(n/2) + 1：log₂ n 层，每层 1，得 log n。遍历二叉树是 T(n) = 2T(n/2) + 1：越往下节点越多，总数被最底层的 n 个叶子主导，得 n。把这三种情况总结成公式，就是“主定理”。

排序为什么不可能比 n log n 更快

n 个数有 n! 种排列，排序就是找出是哪一种。每次比较只有“大 / 小”两种结果，最多排除一半可能。所以至少要比 log₂(n!) ≈ n log₂ n − 1.44n 次。这是所有靠比较的排序的下界 Ω(n log n)。计数排序不靠比较，能做到 O(n + k)：JDK 17 给 byte[] 排序，超过 64 个元素就改用计数排序（MIN_BYTE_COUNTING_SORT_SIZE）。

摊还的三种证法

聚合法：直接算 n 次的总量再除以 n，④ 用的就是它。记账法：每次 add 收 3 块钱，1 块付自己，2 块存起来，扩容时搬每个元素花 1 块，钱永远够用。势能法：把“存的钱”定义成数据结构状态的函数，适合并查集、伸展树这类复杂结构。三种方法结论一样，难度递增。

JDK 文档里的复杂度承诺

ArrayList：get / set 常数时间，add 摊还常数时间。HashMap：get / put 常数时间，前提是哈希均匀。TreeMap：“guaranteed log(n)”，是最坏情况保证。Arrays.sort(int[])：JDK 8 的文档写 O(n log n) on many data sets，最坏仍可能 n²；JDK 14 起（JDK-8226297）递归过深就切到堆排序，文档改成 all data sets。

实验台：扩容策略和摊还

先猜：一路 add 100 万次，“每次扩到 1.1 倍”和“每次多 1000 个”，平均每次 add 谁搬得多？

模型和 ⑤ 的 Count 完全一样：容量从 10 起，满了才扩，扩一次就把现有元素全搬一遍。n = 100 万时的数字和 Java 实测逐个相同。“空着的比例”是最后容量里没用上的部分，是按倍数扩要付的空间代价。

下一圈

  • 空间复杂度：额外用了多少内存，“用空间换时间”什么时候划算。
  • 主定理完整版：T(n) = aT(n/b) + f(n) 的三种情况。
  • 随机化和期望复杂度：快排随机选轴、跳表随机层高，和“平均”有什么不同。
  • 外存模型：数据在磁盘上时数的是 I/O 次数，B+ 树为什么按页设计。
  • 势能法实战：并查集的反阿克曼函数，几乎是常数却不是常数。
  • P 和 NP：有些问题目前只知道指数级的解法，工程上怎么绕开（近似、启发式、限规模）。

↺回到⑤：改一改 Count 和 Doubling

  1. 先猜再数：在 Count 里加一段 for (i = 1; i < n; i *= 2) for (j = 0; j < i; j++) ops++;，先猜是 O(n log n) 还是 O(n)，再跑。做对了会看到 n 翻倍、次数也只翻倍：1 + 2 + 4 + … 不到 2n。（洞察 1、3）
  2. 把藏着的循环揪出来：在 Doubling 里加两种清空队列的写法，ArrayList.remove(0) 和 ArrayDeque.pollFirst()，n 从 5 万翻倍到 40 万。做对了会看到前者比值接近 4，后者接近 2。（坑 1）
  3. 预设容量：给 grow 加一个初始容量参数，传 n 进去再跑第 4 段。做对了会看到搬运次数、扩容次数都是 0。（坑 4）

自测

1. 用一句话说出这一页的精华

大 O 是数最内层操作随 n 执行多少次，只留涨得最快的那一项；说的时候要讲清按最坏、平均还是摊还在数。

2. 为什么不能只靠掐表来判断一段代码快不快？

计时只给一个点：这台机器、这份数据、这个 n。它回答不了 n 涨 400 倍以后会怎样，而且小 n 时谁快往往由常数决定。

3. HashMap 被构造的 key 打满 CPU，根源是哪条原理？

“平均 O(1)”依赖哈希均匀这个关于输入的假设；输入被人控制时假设不成立，只剩最坏情况。JDK 8 的树化把最坏从 O(n) 压到 O(log n)。

从 ④ 洞察 4 推出：平均要靠输入分布，最坏什么都不靠。

4. 预测：O(n log n) 的排序，100 万个要 0.08 秒，200 万个大约要多久？

约 0.17 秒，是 2.1 倍左右，不是正好 2 倍：2 × log(2×10⁶) / log(10⁶) = 2 × 21/20 = 2.1。⑤ 的实测比值是 2.08。

从 ④ 洞察 2 和 3 推出：n 那一项给 ×2，log n 那一项多给一点。

5. 预测：把 ArrayList 的扩容改成每次 ×1.1，add 还是摊还 O(1) 吗？

还是。搬运总数约 n/(r−1) = 10n，摊到每次约 10 个，是常数；代价是扩容更频繁、单次延迟毛刺更多。改成每次 +1000 才会变成摊还 O(n)。

从 ④ 洞察 5 推出：按倍数扩，搬运量是等比数列，总和是 n 的常数倍。

6. 预测：while (n > 0) n /= 10; 跑几次？复杂度是多少？

跑的次数是 n 的十进制位数，约 log₁₀ n + 1 次，O(log n)。底数是 10 还是 2 只差常数倍。

从 ④ 洞察 3 推出：每一步按固定比例缩小，就是 log。

7. 预测：二分查找的数据从 400 万涨到 800 万，最坏要多看几次？

只多 1 次（22 → 23）。数据翻倍，二分多砍一刀就回到原来的规模。

从 ④ 洞察 3 推出。

档位：标准。本机跑过（2026-11-18，2 核 Neoverse-N1 虚机，OpenJDK 17.0.21，--release 8 编译）：⑤ 的全部计数（确定性，任何机器一样）和双倍法计时（粗测非 JMH，热身 3 次取 5 次最快，跑两遍：O(n²) 和 O(n log n) 的比值两遍一致，HashSet 的比值两遍相差到 15%）。按源码核对（JDK 17 java.base）：ArrayList 的 javadoc 和 grow，HashMap 的 javadoc、TREEIFY_THRESHOLD、MIN_TREEIFY_CAPACITY，TreeMap 的 javadoc，DualPivotQuicksort 的插入排序阈值、堆排序兜底和计数排序阈值；JDK 8（jdk8u 源码）的 Arrays.sort 文档和 DualPivotQuicksort；JDK-8226297 提交在 JDK 14 GA 里（GitHub 比对）。估算：①的耗时（按 ⑤ 实测速度外推）、④ 增长表（按每秒 10⁸ 次）。
