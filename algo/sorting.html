排序：快排、归并、TimSort 和稳定性

比较排序最少也要 n log n 次比较，快排和归并都做到了，差别在把活放在哪：快排先划分、递归完就排好，原地但不稳定；归并先递归、最后合并，要额外空间但稳定。JDK 给基本类型用双轴快排，给对象用 TimSort，因为对象要稳定、比较又贵；真实流水往往“几乎有序”，TimSort 能把它当成几段现成的有序片段直接合并。

①要解决的问题：两份几千万条的流水，逐条对上

在全景第 10 站，夜里要拿撮合流水和账务流水对账：每个成交号两边都该有，金额要一致。两份都是几千万条，顺序各不相同。先各自按成交号排好，两根指针从头一起往前走，一遍就能找出“这边有、那边没有”和“金额不一致”。同一成交号可能有两条（先成交、后更正），排完必须保持原来的先后。

②朴素做法：两层循环逐条找，或者冒泡、插入排序

做法次数（n = 3000 万）疼在哪
不排序，每条去另一份里找n² ≈ 9 × 1014一秒 10 亿次也要十天以上
先冒泡 / 插入排序约 n²/2 次比较同样是平方级；只在几十个元素时比快排快
放进 HashMap 按号查约 n 次能做，但 3000 万条对象要几 GB 内存；数据比内存大就不行，见 ③
先排序，再双指针约 n log₂n ≈ 7.5 × 108几秒；数据比内存大也能做（外部排序）
  • 冒泡、插入排序慢在“每次只消除一个逆序”：相邻交换一次，只把一对顺序反了的元素理顺。乱序数组里有约 n²/4 对逆序。
  • 快的排序都是一次比较能决定很多对的相对顺序：快排的一次划分，让左边每个都小于右边每个。
不懂精华时的典型误用：以为“排序就是排序”，拿任意排序去排带更正记录的流水。用了不稳定的排序，同一成交号的“成交”和“更正”可能颠倒，对账把一对本来一致的记录报成两条金额不一致（坑 2，⑤ 里实测）。

本页学快排、归并和 TimSort：快排和归并是两种“分而治之”的极端，懂了它们，TimSort、堆排序、外部排序都是在上面加东西。对账要稳定，所以最后落在 TimSort（对象）或者“先编码成 long 再排”（基本类型）。

④关键洞察：活放在“分”还是放在“合”

先知道这些
  • 递归：函数调用自己处理一个更小的问题，最小的问题直接答。第 13 课会专门讲，这里只用到“左半排好、右半排好”。
  • log₂(n!)：n 个元素有 n! 种排列。第 0 课 排列组合、对数。

洞察 1 · 两种分而治之

机制 · 划分（Lomuto）：一个指针看，一个指针圈地

拿最后一个当基准。i 是“小于基准”那块地的右边界，j 从左往右看每个数：比基准小，就把它换进这块地（i++ 后交换）。看完后把基准换到 i + 1，它就到了最终位置。

图比屏幕宽，左右滑动看全图 →

准备点“下一步”。

一次划分 O(n)。基准如果每次都落在中间，递归 log₂n 层，总共 O(n log n)；如果每次都落在一端（比如输入已经有序、又总拿最后一个当基准），递归 n 层，退化成 O(n²)，递归深度 n 还会把栈撑爆（坑 1）。所以真实实现都随机选基准，或者取几个数的中位数。

洞察 2 · 比较排序最少要 log₂(n!) ≈ n log₂n 次比较

洞察 3 · 稳定：相等的元素，排完保持原来的先后

机制 · TimSort：找现成的有序片段，再合并

为什么这样设计：基本类型用快排，对象用 TimSort

基本类型：双轴快排

  • 值相等就是完全一样，稳定不稳定看不出来
  • 原地排序，不要 O(n) 的缓冲区
  • 比较是一条 CPU 指令，很便宜，快排常数小
  • JDK 17 的实现还会先找 run（数据几乎有序时直接合并）、递归太深换堆排序兜底

对象：TimSort（归并系）

  • 对象有身份，相等的也分得出来，要稳定
  • 比较要调 compareTo / Comparator，很贵；归并系的比较次数比快排少
  • 业务数据常常几乎有序，TimSort 能利用
  • 要最多 n/2 个引用的临时数组
决定胜负的约束：对象排序必须稳定（Arrays.sort(Object[]) 和 Collections.sort 的文档都写着 guaranteed to be stable），而且比较贵、搬引用便宜，所以选比较次数少、稳定的归并系；基本类型没有稳定性问题、比较便宜，选原地、常数最小的快排。
JDK 里的排序细节放到 ⑥
Arrays.sort(long[] a);                 // 双轴快排，不稳定（无所谓）
Arrays.sort(T[] a, Comparator c);      // TimSort，稳定
list.sort(Comparator.comparingLong(Rec::tradeId)
              .thenComparing(Rec::seq)); // 多关键字
Arrays.parallelSort(long[] a);         // 分段并行，用 ForkJoin 公共池

“稳定”的另一种拿法

基本类型数组没有稳定排序。要对 long 记录稳定排序，把原始位置拼进 key：key = tradeId << 20 | 序号（序号不超过 220），再用 Arrays.sort(long[])。相等的成交号按序号排，等于稳定。

static int partition(long[] a, int lo, int hi) {
    long pivot = a[hi];
    int i = lo - 1;                              // [lo, i] 都 < pivot
    for (int j = lo; j < hi; j++)
        if (a[j] < pivot) { i++; swap(a, i, j); }
    swap(a, i + 1, hi);                          // 基准到最终位置
    return i + 1;
}

读出来的结论
  • 随机数据：long[] 排 500 万个约 0.43 秒；同样的数装进 Long[] 用 TimSort 要 4.6 秒，慢 10 倍。慢的不是算法，是 500 万个散在堆里的 Long 对象：每次比较都要跟一次指针，缓存几乎全失效。

⑥边界和变体

第一圈 · 注意事项

1自己写快排，输入本来就有序实测← ④ 划分
现象
总拿最后一个当基准：2 万个有序数要 80 ms（比较约 2 亿次），10 万个直接 StackOverflowError；换成随机基准，10 万个 16 ms。
根源
有序输入时基准每次都是最大的，划分只切掉一个元素，递归 n 层、每层 O(n)。
做法
随机选基准或三数取中；先递归短的那一半、长的那一半用循环（递归深度压到 log n）；最稳的是直接用 Arrays.sort，它有堆排序兜底。
2需要稳定的地方用了不稳定的排序实测← ④ 洞察 3
现象
⑤ 的对账：同号 103 的“成交”“更正”被快排颠倒，双指针错配，多报两条金额不一致。
根源
快排的交换是跨距离的，会越过相等的元素，把它们的先后换掉。
做法
对象用 Arrays.sort(T[], c) / List.sort（稳定）；基本类型把序号拼进 key；或者比较器里加上第二关键字（序号、时间）让它根本没有“相等”。
3比较器不满足约定实测← ④ TimSort
现象
2000 个元素、随机返回结果的比较器，20 次排序里 12 次抛 IllegalArgumentException: Comparison method violates its general contract!，没抛的那些结果是乱的。
根源
TimSort 的合并和跳跃查找默认“a < b、b < c 则 a < c”，前后矛盾时它在合并中发现 run 的长度对不上，就抛异常。真实代码里多半是减法比较器溢出、或者比较的字段在排序中途被别的线程改了。
做法
用 Long.compare、Comparator.comparingLong，不用减法（第 6 课的 坑 3）；排序期间别改参与比较的字段。
4能用 long[] 却用了 Long[] / List<Long>实测← ④ 为什么这样设计
现象
500 万个随机成交号，long[] 0.43 秒，Long[] 4.6 秒。
根源
对象数组里存的是引用，比较时要跳到堆里读值，缓存命中率极低；还多了 500 万个对象的内存和 GC 压力。
做法
排序键是数字时，先抽成 long[]（需要稳定就拼上序号），排好再按序号回查记录。
5数据比内存大，还想一次 Arrays.sort← ④ 洞察 1
现象
3 亿条流水、几十 GB，读进来就 OOM。
根源
内存排序要把全部数据放进数组。归并的“合并”只需要顺序读每一段，这一点可以搬到磁盘上。
做法
外部排序：每次读能放进内存的一块，排好写成一个临时文件；再把 k 个文件用一个大小为 k 的堆（第 6 课）做多路归并。数据库的 ORDER BY 超过排序缓冲区时就是这么做的。
6成交号存成 String，按字典序排实测← ④ 洞察 2：比的是什么
现象
"9" "10" "100" "11" "2" 排成 10 100 11 2 9。一边是数字、一边是字符串的两份流水，双指针一走就错位。
根源
排序只保证“按比较器的顺序”，String 的比较器是逐字符比。
做法
两份流水统一成同一种类型、同一个比较器再对账；字符串 id 要么定长补零，要么转成 long。

第二圈 · 使用规范

  • 不自己写排序：JDK 的实现处理了退化、run、小段插入、递归深度。自己写只为学习和对拍。
  • 比较器用 comparingLong / thenComparing 组合：防坑 3 的减法溢出，也让多关键字一目了然。
  • 对账、分页这类要“确定顺序”的地方，比较器加上唯一的第二关键字：防坑 2，结果和排序算法无关。
  • 数字键抽成基本类型数组再排：防坑 4。
  • 估一下数据量再选内存排序还是外部排序：防坑 5。几千万条 long 是几百 MB，可以内存排；几亿条带对象的记录不行。

第三圈 · 变体和深处

双轴快排为什么比单轴快

两个基准把数组切成三段，递归层数变少，扫描同样的数据时内存访问更少。JDK 7 起用于基本类型；JDK 14 重写过一次（加了 run 检测、堆排序兜底、并行合并），JDK 17 源码里能看到 tryMergeRuns、heapSort、插入排序门槛 44。

快速选择：只要第 k 个

Top K、中位数只要一个位置，不用全排。划分一次后只往 k 所在的那一半递归，平均 O(n)。和第 6 课的堆比：堆是 O(n log k)、适合流式数据；快速选择要整个数组在手里。

基数排序：成交号固定 64 位

按每 8 位一轮、分 8 轮做计数排序，每轮稳定，总共 O(8n)，不比较。数据量很大、key 是定长整数时可能比快排快，代价是 O(n) 的缓冲区，对缓存不友好。

逆序对：归并排序的副产品

合并时每次从右边取元素，左边还剩几个，就有几对逆序。一遍归并数出“流水里有多少对前后颠倒”，用来衡量数据有多乱，也是面试常客（剑指 Offer 51、LC 315）。

面试官会怎么问

快排最坏 O(n²)，为什么实际还最快？

随机基准下最坏情况概率极小；平均比较次数约 1.39 n log₂n，但它原地、顺序扫描、交换少，常数和缓存表现都好。JDK 还用堆排序兜底，把最坏情况限制在 O(n log n)。

Arrays.sort 为什么对 int[] 和 Integer[] 用不同算法？

int 没有身份，稳定性无意义，选原地、常数小的双轴快排；对象要稳定（文档保证），而且比较要调方法、很贵，选比较次数少、稳定的 TimSort。

比较排序的下界为什么是 n log n？

n 个元素有 n! 种排列，每次比较只有两种结果，最多把候选砍一半，至少要 log₂(n!) ≈ n log₂n 次才能确定是哪一种。

下一圈

  • 多路归并和败者树：外部排序里 k 很大时比堆更省比较。
  • 并行排序：parallelSort 的分段和合并，多核机器上什么时候值得。
  • 排序网络和 SIMD 排序：固定小规模、无分支的排序，数据库和向量化引擎里在用。
  • 双指针：排好序以后的事，第 11 课。

↺回到⑤：改一改

  1. 让快排稳定地对账：不改快排，只改比较器：在 BY_ID 后面加上原始序号（读流水时记下来），再用 quickSortObj 排，⑤ 的两条误报应该消失。（坑 2，规范第 3 条）
  2. long 版的稳定排序：把 tradeId << 20 | 序号 编进 long[]，Arrays.sort 后再拆出序号回查记录，和 TimSort 的对账结果对比，应该一模一样。（④ 卡片“稳定的另一种拿法”）
  3. 数逆序对：在 mergeSort 的合并里加一个计数器，统计 SortBench 里“几乎有序”数据有多少对逆序，再对比随机数据（约 n²/4）。（第三圈）

自测

1. 用一句话说出这一页的精华

比较排序下界是 n log n，快排把活放在划分（原地、不稳定），归并把活放在合并（要空间、稳定）；JDK 按“要不要稳定、比较贵不贵”给基本类型用快排、给对象用能利用现成顺序的 TimSort。

2. 冒泡、插入排序慢在哪？

每次相邻交换只消除一对逆序，乱序数组有约 n²/4 对逆序，所以是平方级。

3. 对账误报的根源是哪条原理？

不稳定：快排的划分会跨过相等的元素交换，把同号的成交和更正颠倒。

从 ④ 洞察 1、洞察 3 推出。

4. 预测：⑤ 的手写快排如果固定拿“中间那个”当基准，有序输入还会退化吗？

不会：有序时中间那个正好是中位数，每次对半分。但能构造出专门针对“取中间”的输入让它退化（所谓 killer 序列），所以真实实现用随机或三数取中，再加深度限制兜底。

从 ④ 划分后的那段推出：退化的条件是基准每次落在一端。

5. 预测：一份已经按成交号排好的流水，再追加 1000 条乱序的，整体用 List.sort 排，大概是什么复杂度？

接近 O(n)：前面那一大段是一个长 run，后面 1000 条补成几个短 run，主要代价是一次大的合并，跳跃查找还能整块搬。

从 ④ TimSort 的机制推出。

6. 放回全景：第 10 站前后各发生了什么？排序出问题，整条链路会怎样？

前面是第 9 站定时撤单（到点撤掉的单也会写进流水），后面是第 11 站报表（当天成交额 Top 10、按用户汇总）。第 10 站排序不稳定或比较器错了，对账报出一堆假差异，运营要人工核；排序退化或 OOM，夜间批跑不完，第二天开盘前清算结果出不来，账户资金无法更新。

档位：标准。本机跑过（2026-11-18，2 核 Neoverse-N1 虚机，OpenJDK 17.0.21，--release 8 编译）：⑤ 的划分和对账输出、500 万个成交号的四种排序耗时、⑥ 坑 1、2、3、4、6 的现象。按 JDK 17 源码核对：DualPivotQuicksort 的插入排序门槛 44、tryMergeRuns 和 heapSort 兜底，TimSort 的 MIN_MERGE = 32、MIN_GALLOP = 7、临时数组最多 n/2、“Comparison method violates its general contract!”，Arrays.sort(Object[]) 和 Collections.sort 文档里的稳定性保证。按公开资料、没有本机实测：快排平均 1.39 n log₂n 次比较、外部排序、双轴快排的历史。
