二叉搜索树与红黑树：撤单多、要盘口，为什么换 TreeMap

堆只认得“最优那一个”，撤掉中间一档要先线性找；二叉搜索树把每一档都放在有序的位置上，找、删、按序列出前 5 档都是 O(树高)。问题是有序插入会把树拉成一条链。红黑树的办法是：插入后用旋转（不改中序顺序）和变色把树高压在 2·log₂(n+1) 以内。它其实是一棵 2-3-4 树换了个画法，这也是它为什么“松一点”的平衡：比 AVL 少转几次。

①要解决的问题：撤单多，还要随时列出前 5 档

在全景第 5 站，撮合要不停地问“卖盘最优价是谁”。第 6 课用堆做到了 O(1) 看、O(log n) 进出。但真实盘口还有两件事：撤单（在很多市场里，大部分挂单最后是被撤掉的，撤的往往是中间某一档）和盘口展示（按价格从优到劣列出前 5 档）。堆对这两件事都不擅长。

②朴素做法：堆上撤单，或者不平衡的树

做法撤一档前 5 档疼在哪
堆（第 6 课）+ remove(Object)O(n)：先线性找弹 5 次再放回本机 5 万档撤 2 万档 868 ms
堆 + 延迟删除（第 7 课的做法）O(1) 标记要跳过死档死档沉在堆底，内存只涨不跌（第 7 课坑 4）
不平衡的二叉搜索树（第 13 课）O(树高)O(树高 + 5)价格一路涨，树高 = n，退化成链表
平衡的二叉搜索树（红黑树）O(log n)O(log n + 5)树高有上界
  • 二叉搜索树本身就够了，缺的只是“别被插入顺序拉成链”。行情偏偏常常单边走，有序插入是常态，不是极端情况。
  • 缺的那一块：每次插入、删除之后，在不改变中序顺序的前提下把树“拧”矮一点。这个动作叫旋转。
不懂精华时的典型误用：用 TreeMap<价格, 订单> 直接存订单。TreeMap 的 key 不能重复，同价第二张单会把第一张覆盖掉，同价不再先来先成交，还悄悄丢了单（坑 1，本机实测）。key 是价位，value 要是这一档的订单队列。

③几种思路：怎么让二叉搜索树一直矮

结构平衡有多严插入 / 删除时调整谁在用
AVL 树左右子树高度差 ≤ 1，树高约 ≤ 1.44·log₂n删除时可能一路旋转到根查多改少的场景
红黑树树高 ≤ 2·log₂(n+1)插入最多 2 次旋转，删除最多 3 次TreeMap、TreeSet、HashMap 的树化桶、Linux CFS 调度器
跳表概率平衡，期望 O(log n)不旋转，改几层指针Redis ZSet、ConcurrentSkipListMap（第 15 课）
B+ 树所有叶子同一层节点满了分裂MySQL 索引（第 15 课）

本页学红黑树：JDK 的有序 Map 就是它，盘口直接用 TreeMap。撮合引擎是单线程的，不需要并发版本；要多线程共享一个有序 Map，换第 15 课的 ConcurrentSkipListMap。

④关键洞察：旋转不改顺序；红黑树是 2-3-4 树换了个画法

先知道这些
  • 二叉搜索树和中序：左小右大，中序遍历就是从小到大。第 13 课 递归与二叉树遍历。
  • 红黑树的三条规则：根和空节点是黑的；红节点的孩子必须是黑的；从任一节点到它下面每个空节点，经过的黑节点一样多。Java 板块 日常算法 ⑤ 逐条演示过。

洞察 1 · 旋转：换了父子关系，中序顺序一点没变

洞察 2 · 红节点 = 和父亲挤在同一个大节点里

机制 · 一路上涨的价位插进来，树怎么被拧矮

插入的新节点先涂红（不改变任何路径上的黑节点数），只可能违反“红不能连红”。修复看叔叔（父亲的兄弟）：叔叔红，就变色，问题往上推两层；叔叔黑，就在祖父处旋转一次（内侧时先多转一次）再变色，结束。和第 13 课同样的 7 个价位、同样的顺序：

为什么这样设计：红黑树，而不是 AVL

红黑树：松一点的平衡

  • 插入最多 2 次旋转，删除最多 3 次，其余都是变色（只改一个布尔值）
  • 每个节点只多 1 位颜色
  • 代价：树高最多 2·log₂n，查找比 AVL 多走几层

AVL：严格的平衡

  • 树高约 1.44·log₂n，查找更快一点
  • 删除后可能沿路径一直旋转到根
  • 每个节点要存高度或平衡因子
决定胜负的约束：通用的有序 Map 改和查一样多，盘口更是“撤单、挂单”比“查”还频繁。每次修改的调整代价有常数上限，比查找时多走几层更重要，所以 JDK 的 TreeMap、Linux 的调度器都选了红黑树。查多改少的只读索引才轮到 AVL 或干脆排序数组 + 二分（第 9 课）。
盘口要用的 TreeMap 方法都是 O(log n)
TreeMap<Long, ArrayDeque<Order>> asks = new TreeMap<>();
asks.firstKey();                 // 最优卖价
asks.pollFirstEntry();           // 吃掉整档
asks.ceilingKey(p);              // 第一个 ≥ p 的价位（第 9 课的 lowerBound）
asks.headMap(limit, true);       // 价格 ≤ limit 的所有档：视图，不拷贝
TreeMap<Long, …> bids = new TreeMap<>(Comparator.reverseOrder()); // 买盘降序

为什么 value 是一个队列

key 是价位，同一价位的多张单按先来后到排在一个 ArrayDeque 里：价格优先靠树，时间优先靠队列。撤单时用 HashMap<订单号, 订单> 找到它，再从所在档的队列里删；档空了才从树里删价位（第 8 课的哈希表 + 这一课的树）。

⑤手推一遍：TreeMap 卖盘，加上真实树高和撤单测速

三个类：AskBook 是能交差的卖盘；RbTree 是只有插入的红黑树（和 TreeMap.fixAfterInsertion 同一套情况划分），打印每一步修复，和 ④ 的动画对得上；BookBench 用反射量真实 TreeMap 的树高、测撤单。代码按 JDK 8 写法，--release 8 编译，JDK 17 运行。

⑤AskBook.java（核心）完整代码 →
final TreeMap<Long, ArrayDeque<Order>> levels = new TreeMap<>();   // 价位 → 同价队列
final Map<Long, Order> byId = new HashMap<>();                         // 订单号 → 订单

public void add(Order o) {
    levels.computeIfAbsent(o.price, k -> new ArrayDeque<>()).addLast(o);
    byId.put(o.id, o);
}
public boolean cancel(long id) {
    Order o = byId.remove(id);
    if (o == null) return false;
    ArrayDeque<Order> q = levels.get(o.price);
    q.remove(o);                                    // 档内线性删，档内单数通常很少
    if (q.isEmpty()) levels.remove(o.price);        // 整档空了，价位从树里删：O(log n)
    return true;
}

⑥边界和变体

第一圈 · 注意事项

1拿价格直接当订单的 key实测← ④ 为什么 value 是队列
现象
TreeMap<Long, String> 先放 10050 → #2，再放 10050 → #4，结果只剩 #4。同价单少了一张，先来的反而没了。全景第 5 站的“常出的事”就是这个。
根源
二叉搜索树里 key 相等就是同一个节点，put 会替换 value。
做法
key 是价位、value 是同价队列；或者 key 用（价格, 序号）这样唯一的组合，比较器先比价格再比序号。
2比较器说“相等”，equals 说“不等”实测← ④ 洞察 1：树只看比较结果
现象
new BigDecimal("100.5") 和 new BigDecimal("100.50")：TreeSet 里只剩 1 个，HashSet 里有 2 个。同一批价位进两种集合，数出来不一样。
根源
TreeMap / TreeSet 只用 compareTo（或比较器）判断相等，BigDecimal.compareTo 认为两者相等，equals 还比较精度（scale），认为不等。文档把这叫“和 equals 不一致”。
做法
价格统一存 long（分）；非要 BigDecimal，进集合前先 stripTrailingZeros() 或 setScale 成同一精度。
3遍历 headMap 视图时修改原 map实测← ④ TreeMap 方法
现象
遍历 asks.headMap(limit) 吃档时，顺手 asks.remove(下一档)，抛 ConcurrentModificationException。
根源
视图不拷贝，和原 map 共用同一棵树；迭代器发现树被别人改过（modCount 变了）就快速失败。
做法
用迭代器自己的 it.remove()，或者循环里用 pollFirstEntry() 一档一档吃，不在遍历中途改结构。
4key 放进去以后被改了← ④ 洞察 1
现象
用可变对象当 key，放进去后改了参与比较的字段：get 找不到、remove 删不掉，中序输出不再有序。
根源
节点的位置是插入那一刻按比较结果定的，改了字段，“左小右大”就被破坏，查找会走错方向。和第 8 课哈希表的坑 4 同一类事。
做法
key 用不可变的 Long、String、record；改价 = 先删再按新价插入。
5多个线程共享一个 TreeMap← ④ 插入时的旋转
现象
行情线程在读、撮合线程在写，偶尔读到不一致的结构，甚至迭代器死循环或抛异常。
根源
插入、删除要改好几根指针（旋转），中间状态对别的线程可见。TreeMap 不是线程安全的。
做法
撮合单线程独占盘口，对外发布快照；必须共享就用 ConcurrentSkipListMap（第 15 课），别用 Collections.synchronizedSortedMap 套一层再跨线程遍历。

第二圈 · 使用规范

  • 盘口 = TreeMap<价位, 队列> + HashMap<订单号, 订单>：价格优先、时间优先、按号撤单各有各的结构。防坑 1。
  • 价格存 long，比较器和 equals 保持一致：防坑 2。
  • 吃档用 pollFirstEntry / 迭代器 remove：防坑 3。
  • key 不可变，改价 = 删 + 插：防坑 4。
  • 写清楚哪个线程拥有这棵树：防坑 5。

第三圈 · 变体和深处

删除比插入难在哪

删掉一个黑节点，经过它的路径少了一个黑，违反“黑节点一样多”。修复要看兄弟和兄弟的孩子，分 4 种情况，最多 3 次旋转。在 2-3-4 树视角里就是：大节点空了，向兄弟借一个键，借不到就和兄弟合并。JDK 的 fixAfterDeletion 就是这几种情况。

左倾红黑树（LLRB）

Sedgewick 提出的简化版：规定红链接只能向左，对应 2-3 树（不是 2-3-4 树），插入代码只有十几行。教材里常见，工程里用得少，JDK 用的是经典红黑树（《算法导论》那一套）。

HashMap 里也有红黑树

JDK 8 起，一个桶的链表长到 8 个、且表长 ≥ 64 时，桶变成红黑树（TreeNode），最坏查找从 O(n) 变 O(log n)，防的是哈希碰撞攻击。见 HashMap 那页的树化。

顺序统计：第 k 档是谁

每个节点多存一个“子树大小”，就能 O(log n) 回答“第 k 小的价位”和“价格 p 排第几”。TreeMap 没有这个字段，要第 k 档只能从头走 k 步；Redis 的跳表在每层指针上记了跨度，所以 ZSet 能 O(log n) 按排名取（第 15 课）。

面试官会怎么问

为什么 TreeMap 用红黑树而不是 AVL？

红黑树每次插入最多 2 次旋转、删除最多 3 次，修改的调整代价有常数上限；AVL 更矮，但删除时可能一路旋转到根。通用 Map 改得多，红黑树整体更划算。

红黑树的树高为什么是 O(log n)？

“每条路径黑节点数一样”保证全黑的最短路径长 b，“红不连红”保证最长路径最多 2b；黑节点构成一棵完全平衡的 2-3-4 树，b ≤ log₂(n+1)，所以树高 ≤ 2·log₂(n+1)。

盘口用堆还是 TreeMap？

只要最优价、没有撤单，堆最省；要撤中间某档、要按序列出前几档，用 TreeMap（或排好序的价位数组，价位范围固定时更快）。生产撮合引擎还常用“价格 → 下标”的数组加位图，价格档位离散且范围有限时 O(1)。

自测

1. 用一句话说出这一页的精华

二叉搜索树让每一档都有序可查，红黑树用不改中序顺序的旋转加变色把树高压在 2·log₂(n+1) 以内；它是 2-3-4 树的二叉画法，修改的调整代价有常数上限，所以盘口和 TreeMap 都用它。

2. 堆做盘口，痛点在哪？

只有堆顶有序：撤中间一档要先线性找 O(n)，列前 5 档要弹出再放回。

3. 为什么旋转不会把树搞乱？

旋转前后中序都是 A < x < B < y < C，“左小右大”对每个节点仍成立，只是父子关系变了。

从 ④ 洞察 1 推出。

4. 预测：把 ④ 动画里的 7 个价位倒过来、从大到小插入，最后的树高是多少？形状呢？

树高也是 4，形状是 ⑤ 结果的镜像：对称的输入走对称的修复（左右互换）。根是 10200；左孩子是红的 10100，它下面是 10050（再下面挂着红的 10020、10080）和 10150；右孩子 10300。

从 ④ 机制推出：修复只看叔叔颜色和内外侧，左右对称。

5. 预测：一棵红黑树有 n 个价位，黑高（从根到空节点经过的黑节点数）是 b，n 至少是多少？

至少 2b − 1。只看黑节点，它们构成一棵每条路径都是 b 层的完全二叉树（红的都去掉）；所以 b ≤ log₂(n+1)，再乘上“红不连红”的 2 倍，就是树高上界。

从 ④ 洞察 2 推出。

6. 放回全景：第 5 站前后各发生了什么？盘口的树出问题，整条链路会怎样？

前面是第 4 站风控放行，后面是第 6 站把没成交完的部分挂进价位、撤单从价位里摘掉。盘口用 TreeMap 时，同价覆盖（坑 1）会让先来的单凭空消失，用户投诉；没做平衡（第 13 课）时，单边行情里每次找最优价都要走 O(n)，撮合延迟随行情越走越高，第 3 站的入口队列开始积压。
