堆和优先队列：订单簿按价格排队，最优价 O(1) 看、O(log n) 进出

撮合时只关心一件事：现在最优的是哪一张。全排好序太贵，每挂一张单都要搬半个数组；完全不排序，每次找最优都要扫一遍。二叉堆只维持一半的顺序：每个父亲不比孩子差，别的不管。这点顺序刚好够让最优的那张一直待在数组第 0 格，挂单和取走只沿一条从根到叶的路径走，最多 log₂n 步，100 万张单也就 20 层。代价是：除了第 0 格，别的位置都不保证有序。

这一页的位置第 4 课的链表和第 5 课的环形数组，排队规则都是“先来先走”。订单簿多了一条规则：价格优先，价好的先成交，同价才看先后。这一课讲能做到“谁优先谁先走”的结构：二叉堆，以及 JDK 里的 PriorityQueue。你点名要的“算法里常用的函数”放在 ⑥ 第二圈，每一条都在本机跑过。

①要解决的问题：新来一张卖单，簿里出价最高的买单是谁

交易靶场的撮合线程里，买簿挂着几万张买单，按到达顺序一张张进来，价格高低不一。来了一张卖单，规则是：先找出价最高的买单成交；同样高的几张，先来的先成交。卖簿反过来，要价最低的先成交。

这类“谁优先谁先走”的队列叫优先队列（priority queue）。它只规定三个动作：放进去、看最优、取走最优。定时任务（最早到期的先跑）、Top K、最短路径，都是同一个问题换了个比较规则。

手里有的就是第 2 课的数组。两种用法都能做，疼的地方正好相反。

不懂精华时的典型误用：拿 PriorityQueue 当“自动排好序的列表”，直接打印或 for-each 遍历，以为看到的是价格顺序。它只保证第 0 个是最优的，见 坑 1。

④关键洞察：只维持父子之间的顺序，最优的就一直在第 0 格

先知道这些
  • 二叉树：每个节点最多两个孩子，最上面那个叫根。这里不用写 Node 类和指针，下面会看到它整个放在一块数组里。
  • 数组下标 O(1)：知道下标就能直接算出地址，见 第 2 课。
  • log₂n：n 一直对半分，分几次到 1。100 万大约是 20，见 第 3 课。

洞察 1 · 形状：一层层从左往右填满的树，正好放进一块数组

形状是靠“只在末尾加、只从末尾删”保住的：放新元素一律放 [size]，删元素一律拿走 [size-1]。所以树永远是满的，高度永远是 ⌊log₂n⌋+1，不需要红黑树那样的旋转来保持平衡。

洞察 2 · 顺序：只管父子，最小的自然在根上

每条父子边都满足父亲 ≤ 孩子（小顶堆；反过来就是大顶堆）。沿着任何一条路往上走，数只会越来越小，所以根就是全体里最小的。这就是全部的顺序：[1] 和 [2] 谁大不知道，[2] 和 [3] 谁大也不知道。数组 101 103 108 105 104 是合法的堆，但不是有序数组。

洞察 3 · 进出：只修一条从根到叶的路

放进去和取出来，都会在某一处弄坏堆序。坏的地方只在一条父子链上，所以只沿这条链修：放进去往上浮，取出来往下沉。下面是卖簿（要价低的优先，小顶堆）挂五张单、再成交两张。

取走时为什么拿末尾那个来填坑，而不是让较小的孩子一路补上去？孩子补上去，会在树的中间留下一个洞，形状就不再是“从左往右填满”，下标公式全部失效。拿末尾的填，形状一步就修好了，剩下只是修顺序。

为什么这样设计

有序数组：全序

  • 谁都能直接读，盘口直接出
  • 每挂一张要搬它后面的所有元素：O(n)

二叉堆：只排父子

  • 一个元素只影响它到根的一条路：O(log n)
  • 一块数组，没有指针，形状天然平衡
  • 除了堆顶，什么都不保证

红黑树 TreeMap：全序 + 指针

  • 查、插、删、范围、遍历都是 O(log n) 或更好
  • 每个元素一个 40 字节的 Entry（第 4 课实测），插入要变色、旋转，指针跳来跳去不连续
决定胜负的约束：只需要“最优的那一个”。全序是在为用不到的信息付钱；堆只保留推出“根最优”所需要的那部分顺序（父 ≤ 子，一路传递上去），所以每次只修一条路径。形状交给“只动末尾”来保证，就省掉了树的指针和平衡操作，整个结构是一块连续数组。

先记住这几句

offer / peek / poll 三件套够用。add / element / remove() 是同一件事的“抛异常版”。比较器决定谁在堆顶，同价谁先，也只能写在比较器里。遍历顺序、撤单、线程安全、建堆为什么是 O(n)，都放到 ⑥。

⑤PriceHeap.java（核心两段）完整代码 →
long[] a = new long[4]; int size;

void offer(long price) {                 // 上浮
    if (size == a.length) a = Arrays.copyOf(a, size * 2);
    int k = size++;                      // 先占末尾那一格
    while (k > 0) {
        int parent = (k - 1) >>> 1;
        if (a[parent] <= price) break;   // 父亲不比我大，停
        a[k] = a[parent];                // 父亲挪下来，空位往上走
        k = parent;
    }
    a[k] = price;                        // 最后只写一次
}

long poll() {                            // 下沉
    long top = a[0], x = a[--size];      // 末尾那个来填坑
    int k = 0, half = size >>> 1;         // 下标 < half 的才有孩子
    while (k < half) {
        int c = 2 * k + 1, r = c + 1;
        if (r < size && a[r] < a[c]) c = r;   // 挑较小的孩子
        if (x <= a[c]) break;
        a[k] = a[c];
        k = c;
    }
    if (size > 0) a[k] = x;
    return top;
}

⑤OrderBook.java（撮合部分）完整代码 →
// 价格用 long 存“分”，不用 double（第 1 课：0.1 存不准）
Comparator<Order> BID = Comparator.comparingLong((Order o) -> o.price).reversed()
                                  .thenComparingLong(o -> o.seq);  // 价高优先，同价先来优先
Comparator<Order> ASK = Comparator.comparingLong((Order o) -> o.price)
                                  .thenComparingLong(o -> o.seq);  // 价低优先
PriorityQueue<Order> bids = new PriorityQueue<>(BID), asks = new PriorityQueue<>(ASK);

void match(Order in, boolean isBuy) {
    PriorityQueue<Order> opp = isBuy ? asks : bids;
    while (in.qty > 0 && !opp.isEmpty()) {
        Order best = opp.peek();                         // O(1) 看对手最优价
        boolean cross = isBuy ? best.price <= in.price : best.price >= in.price;
        if (!cross) break;                               // 价格对不上，停
        long q = Math.min(in.qty, best.qty);
        in.qty -= q; best.qty -= q;                      // 改数量不影响排序
        if (best.qty == 0) opp.poll();                   // O(log n) 取走
    }
    if (in.qty > 0) (isBuy ? bids : asks).offer(in);     // 剩下的挂进自己那边
}

⑥边界和变体：堆只保证堆顶，别的都要自己补

第一圈 · 注意事项

1打印、for-each、toArray 都不是有序的实测← ④ 洞察 2
现象
入 105 103 108 101 104，toString 和 for-each 都是 [101, 103, 108, 105, 104]；逐个 poll 才是 [101, 103, 104, 105, 108]。
根源
迭代器按数组下标走，数组里只有父子有序。javadoc 原话：不保证按任何特定顺序遍历。
做法
要有序就逐个 poll（会清空），或复制一份 Arrays.sort(pq.toArray())；要经常有序地看，换 TreeMap。
2同价不保证先来先得实测← ④ 洞察 3
现象
比较器只比价格，8 张同价单按 #1…#8 放进去，出来是 #1 #8 #7 #6 #5 #4 #3 #2。
根源
下沉时拿末尾元素填到堆顶，它一下子越过了中间所有同价的单。堆不是稳定的：相等的元素谁先出，取决于它们在数组里被挪成了什么样。
做法
把先后写进比较器：.thenComparingLong(o -> o.seq)，seq 用单调递增的到达序号，不要用时间戳（同一毫秒会重复）。
3比较器用减法，溢出后顺序乱了实测历史写法 · 第 1 课补码
现象
(a, b) -> a - b 放入 2000000000、-2000000000、0、1，poll 出来是 [0, 1, 2000000000, -2000000000]，最小的排到了最后。
根源
和堆无关，是 int 溢出：2000000000 - (-2000000000) 超过 int 上限，算出 -294967296，符号反了。这是老教材留下的写法，价格、时间戳、ID 都可能踩到。
做法
一律用 Integer.compare(a, b)、Long.compare、Comparator.comparingLong(...)；大顶堆用 Comparator.reverseOrder()，不写 b - a。
4挂着的单直接改价，堆不知道实测← ④ 洞察 3
现象
卖簿里 #1@101、#2@103、#3@105，把 #3 的价改成 99，peek 还是 #1@101。
根源
堆只在 offer、poll 的那一刻上浮或下沉。对象在堆里被改了，没人去修它那条路径，堆序已经坏了，后面的 poll 结果都不可信。
做法
改单 = 先 remove(o) 再 offer(o)。比较器用到的字段做成 final；能改的只有数量这类不参与排序的字段（⑤ 里就是这样）。
5撤单 remove(Object) 是 O(n)← ④ 洞察 1
现象
撤单多的时段，撮合线程的耗时跟着簿的大小线性涨。
根源
数组里只有“下标 → 元素”，没有“元素 → 下标”。要删一张单，得先从头扫到尾找到它（源码 indexOf 是一个 for 循环），找到后删本身才是 O(log n)。javadoc 写明 remove(Object)、contains 是线性时间。
做法
三条路：① 懒删除：单子上打个 cancelled 标记，轮到它在堆顶时直接 poll 扔掉；死单太多时 removeIf(o -> o.cancelled) 一次清掉（源码里是压缩数组后整体重建堆，O(n)）。② 带下标的堆：元素里记住自己在第几格，见第三圈。③ 撤单很多就换 TreeMap。

第二圈 · 使用规范

  • 比较器写全：主键 + 平局规则：防同价乱序（坑 2）和不同 JDK 下结果不一样。
  • 比较器只用 compare 系列，不用减法：防溢出（坑 3）。
  • 参与比较的字段不可变：防堆序被悄悄弄坏（坑 4）。
  • 跨线程用 PriorityBlockingQueue 或单线程撮合：PriorityQueue 不是线程安全的，javadoc 明说。撮合引擎通常本来就是单线程，入口用第 5 课的环形队列交给它。
  • 已有一批数据时，用构造函数一次建堆：new PriorityQueue<>(list) 是 O(n)，逐个 offer 或 addAll 是 O(n log n)（第三圈）。
  • 不放 null：offer(null) 抛 NPE（实测）。poll 返回 null 的意思就是“空了”。

第三圈 · 优化和深处

一次建堆为什么是 O(n)，不是 O(n log n)

构造函数 new PriorityQueue<>(collection) 先把元素原样抄进数组，再从最后一个有孩子的节点 (n >>> 1) - 1 往前，逐个下沉（源码 heapify()）。一半节点是叶子，一步不用走；四分之一最多走 1 层；八分之一最多 2 层……加起来不超过 n。逐个 offer 是让每个元素从底往上浮，深的节点多，总量是 n log n。addAll 继承自 AbstractQueue，就是循环 add，走的是后者。

Top K：100 万笔成交里找最大的 10 笔

维护一个大小为 10 的小顶堆：堆顶是入选者里最小的那个，新来的比它大就 poll 掉它再 offer。每笔最多 log 10 ≈ 3 层，总共 O(n log K)，内存只有 10 格。全排序要 O(n log n)，还要把 100 万笔都放进内存。找最小的 K 个就反过来用大顶堆。详见 数据结构与算法那页的 Top K。

PriorityQueue 里面的三个细节（JDK 17 源码）

① 默认容量 11，满了按 oldCapacity < 64 ? oldCapacity + 2 : oldCapacity >> 1 扩：小的时候翻倍再加 2，大了每次加一半，和 ArrayList 的 1.5 倍同一个思路（第 3 课的摊还）。② 上浮和下沉都不真交换：把父亲（或孩子）挪过来，空位一路移动，最后只写一次，和 ⑤ 的手写版一样。③ 下沉只在 k < size >>> 1 时循环：后一半全是叶子。

带下标的堆：线程池的定时任务就是这么撤的

ScheduledThreadPoolExecutor 没用 PriorityQueue，自己写了一个堆 DelayedWorkQueue：每个 ScheduledFutureTask 里有个 heapIndex 字段，上浮、下沉挪动它时顺手更新。任务被取消时直接按 heapIndex 找到格子，O(log n) 删掉，不用扫（要打开 setRemoveOnCancelPolicy(true)，默认只标记不删，就是坑 5 的懒删除）。java.util.Timer 的 TaskQueue 也是堆，从下标 1 开始存，孩子是 2n、2n+1。

真实订单簿：为什么多是“按价位聚合”，不是一张单一个堆元素

每步“挂一张 + 取最优一张”，只有 2000 个价位N = 1 千1 万10 万100 万
二叉堆：一张单一个元素83 ns≈ 140 ns0.3～0.5 µs1.0～1.2 µs
TreeMap<价格, 张数>：按价位聚合0.2～0.26 µs≈ 105 ns≈ 110 ns≈ 135 ns

实测 同一次 HeapBench（② 那张表）。堆的层数跟挂单数涨：100 万张单 20 层，每层都是一次跳到别处内存的比较。TreeMap 最多只有 2000 个键，红黑树高度在 11～22 层之间（log₂2000 ≈ 11，最坏 2 倍），N 再大也不变。这不是“红黑树比堆快”：两边存的东西不一样多。真正起作用的是“按价位聚合”这个建模决定，换成堆按价位存（堆里放价格、旁边一个 HashMap<价格, 队列>）同样会变快，只是撤空一个价位时又碰上坑 5。

自测

1. 用一句话说出这一页的精华

只要“随时拿到最优的那一个”，就不必全排序：二叉堆只维持父子之间的顺序，最优的一直在数组第 0 格，放进和取出都只修一条从根到叶的路径，O(log n)。

2. 不排序的数组和有序数组，各疼在哪？

不排序：放进去 O(1)，找最优要扫一遍 O(n)。有序：取最优 O(1)，每放一张要搬后面的元素 O(n)。撮合时放和取一样频繁，哪头 O(n) 都不行。

3. 为什么打印 PriorityQueue 看到的不是排好序的？

迭代器按数组下标走，堆只保证每个父亲不比孩子差，兄弟、叔侄之间没有顺序。

从 ④ 洞察 2 推出。

4. 预测：把 1 到 7 按从小到大依次放进小顶堆，每次上浮几层？最后数组是什么？

每次都是 0 层：新元素的父亲一定比它小。最后数组就是 [1, 2, 3, 4, 5, 6, 7]。有序数组一定是合法的堆，反过来不成立。

从 ④ 洞察 3 推出：上浮只在“父亲比我大”时发生。

5. 预测：反过来，7 到 1 依次放进小顶堆，最后放进去的 1 上浮几层？最后数组是什么？

每个新元素都比堆里所有的小，一路浮到根。1 放在下标 6，经过下标 2 到下标 0，上浮 2 层。最后数组 [1, 4, 2, 7, 5, 6, 3]。

从 ④ 洞察 1 的下标公式推出：6 的父亲是 (6−1)/2 = 2，2 的父亲是 0。

6. 预测：[1, 3, 2, 7, 2, 4] 是不是合法的小顶堆？

不是。下标 4 的 2，父亲是下标 (4−1)/2 = 1 的 3，父亲比孩子大了。注意 [0] 的 1 确实是最小的，但“根最小”不等于“是堆”。

从 ④ 洞察 1、2 推出。

7. 预测：一个 PriorityQueue 依次 offer 105 103 108 101 104，打印是 [101, 103, 108, 105, 104]。poll 一次之后再打印，是什么？

[103, 104, 108, 105]。末尾的 104 填到 [0]，和较小的孩子 103 换，到了 [1] 后唯一的孩子 105 不比它小，停。

从 ④ 洞察 3 推出，和 ⑤ PriceHeap 的输出一致：PriorityQueue 用的是同一套上浮、下沉。
