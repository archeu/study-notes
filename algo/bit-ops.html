位运算与逻辑运算：订单标志位、1 亿账户打卡和移位的坑

位运算把一个整数当成一排开关，32 位一起处理：& 取出 / 清掉，| 打开，^ 翻转，移位挪动。逻辑运算（&& || !）只对 true / false 做判断，而且会短路。前者是“一次算 32 个比特”，后者是“控制要不要算下一个条件”，这是两者最根本的区别。

洞察 1 · 六个运算符：每一位各自算，互不影响

运算规则（每一位）例：a = 1100，b = 1010记法
a & b 与两个都是 1 才是 11000拿 b 当“筛子”：只留 b 为 1 的位，其余清 0
a | b 或有一个 1 就是 11110把 b 为 1 的位打开，其余不动
a ^ b 异或不同才是 10110把 b 为 1 的位翻转；x ^ x = 0，x ^ 0 = x
~a 取反每位反过来…0011（32 位全反）~x 不是 −x：−x 要“取反再加 1”，~ 只做了取反，少加了那个 1，所以 ~x 比 −x 小 1，即 ~x = −x − 1。例：~3 = −4，~0 = −1
a << k 左移整体左挪 k 位，右边补 01 << 3 = 1000不溢出时 = 乘 2ᵏ
a >> k 算术右移右挪 k 位，左边补符号位−8 >> 1 = −4= 除以 2ᵏ 并向下取整
a >>> k 逻辑右移右挪 k 位，左边补 0−8 >>> 1 = 2147483644把 int 当无符号数看

洞察 3 · 逻辑运算：对 true / false 判断，而且会短路

&& || !

操作数和结果都是 boolean。短路：a && b 在 a 为 false 时不再算 b；a || b 在 a 为 true 时不再算 b。所以 s != null && s.length() > 0 是安全的。

& | ^ 用在 boolean 上

Java 允许，结果也是 boolean，但两边都算，不短路。s != null & s.length() > 0 在 s 为 null 时抛 NPE（⑤ 实测）。布尔的 ^ 就是“不相等”。

& | ^ 用在整数上

这才是位运算：32 位各自算，结果是整数。Java 不允许把整数当条件：if (f & M) 编译不过，必须写 (f & M) != 0。C 语言可以，所以 C 里更容易写错。

一句话分清：位运算 = 一次算 32 / 64 个比特，两边都要算；逻辑运算 = 只算一个真假，能提前知道结果就不算后面。短路不只是快，还是一种控制流：后一个条件可以依赖前一个条件成立（先判空再取长度）。

洞察 4 · 几个技巧，都来自补码

写法效果（v = 1011_0100）为什么用在
v & (v − 1)1011_0000：去掉最低位的 1减 1 把最低位的 1 变 0、它右边的 0 全变 1，再“与”一下这一段全清掉数 1 的个数；判断 2 的幂：n > 0 && (n & (n − 1)) == 0
v & −v0000_0100：只留最低位的 1−v = ~v + 1：最低位的 1 和右边保持不变，左边全反树状数组的 lowbit
h & (n − 1)，n 是 2 的幂等于 h 对 n 取模（h ≥ 0）n − 1 是低位全 1 的掩码，只留低几位HashMap 取桶；负数时也给出 0～n−1，% 会给负数
(lo + hi) >>> 1不溢出的中点和溢出成负数后，按无符号右移正好还原二分，Arrays.binarySearch
for (mask = 0; mask < 1 << n; mask++)n 个东西的全部 2ⁿ 个子集第 i 位是 1 = 选第 i 个回溯的另一种写法、状态压缩 DP
a ^ b ^ a = b成对的抵消，落单的留下x ^ x = 0，异或满足交换律、结合律找唯一落单的单号；校验和（分库校验）

为什么这样设计：一条指令，32 个结果

位掩码 / BitSet

  • CPU 的与、或、异或是一条指令同时处理整个寄存器（64 位）
  • 集合运算变成一条指令：交集 a & b，并集 a | b，差集 a & ~b
  • 一个比特存一个是 / 否，内存是 boolean 的 1/8
  • 代价：只能用小整数编号；位的含义靠约定，读代码要查常量

boolean 字段 / Set<对象>

  • 可读，编号可以是任何对象
  • “全都开了吗”要逐个比较；Set 里每个元素一个对象、一个节点
决定胜负的约束：编号是不是小而连续的整数。是（枚举的 ordinal、0～1 亿的账户号），一个比特就能代表一个元素，位运算就是最紧凑最快的集合；不是（UUID、字符串），只能哈希，或者接受误判用布隆过滤器。

⑤手推一遍，再让 Java 对答案

手推：f 从 0 开始，打开 IOC（位 0）和 POST_ONLY（位 2）得 0000_0101；关掉 IOC：~IOC = 1111_1110，与一下得 0000_0100；翻转 REDUCE_ONLY（位 3）得 0000_1100。和 ④ 的分步动画一致。

boolean fok = (f & FOK) != 0;         // 测试
f &= ~IOC;                            // 关掉
f ^= REDUCE_ONLY;                     // 翻转

⑥边界和变体

第一圈 · 注意事项

1移位距离会被取模：1 << 32 == 1实测← ④ 洞察 1
现象
想要第 32 号开关，1 << 32 得到 1，和 IOC 撞了；1 << 33 得 2。
根源
Java 规范（JLS 15.19）：int 移位只取距离的低 5 位（0～31），long 取低 6 位（0～63）。32 & 31 = 0，所以等于没移。这是规范定的，不是溢出。
做法
超过 31 个开关用 long 和 1L << k（注意那个 L）；超过 64 个用 EnumSet 或 BitSet。
2拿 >> 当除以 2，负数差 1实测← ④ 洞察 1
现象
-7 >> 1 = -4，-7 / 2 = -3。
根源
>> 是向下取整（往负无穷），/ 是向零取整，见 第 0 课 · 取整。正数两者一样，负数差 1。
做法
算价格、金额用 / 或 Math.floorDiv，意思写在代码里；别为了“快”写 >>，JIT 会自己把除以常量 2 优化好。
3byte / short 先变成 int 再运算实测← ④ 洞察 1
现象
报文里一个字节 0xF0，b >>> 4 得 268435455，不是 15。
根源
位运算前 byte 先按符号扩展成 int：0xF0 是 −16，变成 0xFFFFFFF0，再右移就带着一串 1。第 1 课坑 2讲的是同一件事。
做法
解析字节一律先 & 0xFF：(b & 0xFF) >>> 4。
4优先级：移位比加减低，位运算比比较低实测← ④ 洞察 1
现象
x << 1 + 1 是 x << 2；f & M == M 是 f & (M == M)，Java 里直接编译报错（int & boolean）。
根源
历史原因：Java 沿用了 C 的优先级表，& ^ | 排在 == 后面，移位排在 + - 后面。
做法
位运算一律加括号：(f & M) == M、(x << 1) + 1。
5在 boolean 上写成 & / |，不短路实测← ④ 洞察 3
现象
s != null & s.length() > 0 抛 NPE；ok | expensiveCheck() 每次都调用后面的方法。
根源
用在 boolean 上的 & | 是“逻辑但不短路”，两边都求值。
做法
条件判断一律用 && ||；真需要两边都执行（比如两个校验都要记日志）时再用 &，并写注释。
6改了开关的位置，老数据全读错← ④ 洞察 2
现象
有人在 IOC 前面插了一个新开关，所有常量往后挪一位；库里的老订单 flags = 5 从“IOC + POST_ONLY”变成了另外两个开关。
根源
存进数据库、发到网络的 flags 只是一个数，位的含义只存在代码里。EnumSet 用 ordinal()，枚举调换顺序一样会错。
做法
位的位置当协议：只能在末尾追加，不能插入、删除、调换；持久化用显式常量，不要直接存 ordinal()。

第二圈 · 使用规范

  • 每个掩码一个有名字的常量，写成 1 << k：防魔法数字 0x14 没人看得懂。
  • 业务代码优先 EnumSet：可读、类型安全，内部就是 long 位图；手写 int 掩码留给热路径和对外协议。
  • 别为了“快”把 * 2、/ 2、% 8 改成移位和与：JIT 会做这种替换；手写反而在负数上出错（坑 2）。
  • 打日志用 Integer.toBinaryString，排查时一眼看出哪几位开着。

第三圈 · JDK 里的位运算

EnumSet

JDK 17 RegularEnumSet：add 是 elements |= 1L << ordinal，contains 是 (elements & (1L << ordinal)) != 0，addAll 是 elements |= es.elements。EnumSet.noneOf 在枚举超过 64 个时换成 JumboEnumSet（long[]）。

HashMap.tableSizeFor

把容量向上取到 2 的幂。JDK 8 是五次 n |= n >>> k（k = 1, 2, 4, 8, 16），把最高位的 1 往右“抹满”；JDK 17 改成 -1 >>> Integer.numberOfLeadingZeros(cap - 1)，一条指令数前导零。⑤ 实测两种写法结果相同（10→16、17→32、100→128）。

Integer.bitCount

JDK 17 源码是 5 行“分组相加”（先每 2 位数，再每 4 位、8 位……），标了 @IntrinsicCandidate，CPU 有数 1 的指令时 JIT 直接换成那条指令。

BitSet

long[] words，第 i 位在 words[i >> 6]（除以 64），位内偏移是 1L << i（坑 1 的“取低 6 位”在这里正好就是 i % 64，源码就是靠这条规则省掉了取模）。

自测

  

    
1. 用一句话分清位运算和逻辑运算
位运算把整数当一排比特，每位各算一次，两边都求值，结果是整数；逻辑运算只对 boolean 判真假，&& || 能提前知道结果就不算后面（短路）。

    
2. 为什么右移有 >> 和 >>> 两种，左移只有一种？
右移在最高位空出位置，最高位是符号位，要选补符号位（保负号）还是补 0（当无符号）；左移空出的是最低位，只能补 0。

    
3. 测试开关为什么写 (f & M) != 0，不写 (f & M) == 1？
f & M 的结果是 0 或者 M 本身；M 不是第 0 位时（比如 POST_ONLY = 4），结果是 4，不等于 1。

    
4. 预测：(1 << 31) >> 31 和 (1 << 31) >>> 31 各是多少？
1 << 31 是 1000…0 = −2147483648。算术右移 31 位，左边全补 1，得全 1 = −1；逻辑右移 31 位，左边补 0，只剩最低位 1 = 1。
从 ④ 洞察 1 推出：两种右移只差在补什么。

    
5. 预测：-1 & 0xFF、(byte) 200 各是多少？
-1 是 32 个 1，与上 0xFF 只留低 8 位，得 255。200 = 1100_1000，截成 byte 后最高位是 1，按补码读是 200 − 256 = −56。
从 ④ 洞察 1 和第 1 课的补码推出。

    
6. 放回全景：第 1 站把开关存成 flags，第 5 站撮合时读错了一位（POST_ONLY 读成 IOC），会怎样？
本该只挂单的单被当成“能成交就成交、剩下撤掉”：如果对手价合适，它会立刻吃单成交，用户付了吃单手续费；剩下的直接撤了，用户以为在簿上挂着，实际没有。所以 flags 的位定义要在网关和撮合之间共用一份常量，并且只追加不改动（坑 6）。

  








  
档位：标准。本机跑过（2026-11-21，2 核 Neoverse-N1 虚机，OpenJDK 17.0.21，--release 8 编译）：⑤ 的全部输出；内存是 GC 后用 Runtime 前后差估算的，误差几 MB。按源码（已核对 JDK 17 java.base）：RegularEnumSet 的 long elements 和 add / contains / addAll 的写法，EnumSet 按 64 个分 Regular / Jumbo，BitSet 的 long[] words 和 ADDRESS_BITS_PER_WORD = 6，Integer.bitCount 标 @IntrinsicCandidate，HashMap.tableSizeFor（JDK 8 的写法取自 jdk8u 源码）。按规范：移位距离取低 5 / 6 位是 JLS 15.19，⑤ 的 1 << 32 = 1 也印证了。
