二分查找：边界怎么写才不出错

二分不是“找某个值”，而是找一条分界线：先定一个判定，让数组变成“假假假……真真真”，再每次砍掉一半，直到只剩分界线。用左闭右开 [lo, hi)、判定为真就 hi = mid、为假就 lo = mid + 1，这一种写法就够用所有边界题，3000 万笔里找起点只要 25 次比较。

①要解决的问题：3000 万笔里，20:00 从哪一笔开始

在全景第 8 站，运营要查“20:00～20:05 的成交”。成交流水按时间追加写，天然有序。要做的是找两个位置：第一笔不早于 20:00 的，和第一笔晚于 20:05 的，中间那一段读出来就是答案。盘口里找“第一个不低于某价的档位”也是同一件事。

②朴素做法：从头扫，或者“凭感觉”写二分

做法本机实测疼在哪
从下标 0 往后扫到第一个 ≥ 20:00每次约 10.3 msO(n)，查晚上的时段要扫过白天的几千万笔
凭感觉写二分能跑，偶尔错差一、死循环、溢出、重复元素返回了中间那个
一种固定写法的二分每次约 1 µsO(log n)，边界由不变式保证
  • 二分的想法 1946 年就有人公开了，第一个没有 bug 的版本据说到 1962 年才出现（Knuth《计算机程序设计艺术》第 3 卷里的说法）；2006 年 JDK 的 Arrays.binarySearch 还被发现有 (low + high) / 2 溢出的 bug。
  • 常见写法有好几套：while (lo <= hi) 还是 <，hi = mid 还是 mid − 1，返回 lo 还是 hi。混着用就会错。
  • 缺的不是“二分的想法”，而是一条说得清的不变式：每一步之后，什么东西一定成立。
不懂精华时的典型误用：把二分当成“找等于 x 的那个”。时间段查询要的是“第一个 ≥ 20:00”，20:00:00 整可能一笔都没有，也可能有三笔。拿 Arrays.binarySearch 去找 20:00:00，没有就得到一个负数，有三笔就随便给你其中一笔的下标（坑 3）。

③几种思路：有序的东西怎么查

思路查一次前提什么时候用
从头扫O(n)无几十个元素以内，扫比二分还快
数组上二分O(log n)已排序、能按下标随机访问数据只追加或很少改：成交流水、K 线、日终快照
插值查找均匀时 O(log log n)，不均匀退化到 O(n)key 是数值、分布均匀很少用：成交时间扎堆（开盘、整点），不均匀
TreeMap.subMapO(log n)树结构边插边删边查，比如盘口，第 14 课
B+ 树索引 / 跳表O(log n)，一次读一页数据在磁盘或 RedisMySQL 按时间查成交、ZSet 排行榜，第 15 课

本页学数组上的二分：数据已经有序地躺在数组里、又不常改，二分最省，一次分配都没有。数据边改边查，二分的数组插入要 O(n) 挪动，就该换树了。后面几种树，查找那一步的思路都是这一页的二分。

④关键洞察：二分找的是“由假变真”的那条线

先知道这些
  • 为什么是 log n 次：每次砍掉一半，n 砍到 1 要 log₂n 次。第 3 课 log n 与砍半。
  • 左闭右开：[lo, hi) 包含 lo、不包含 hi，长度 = hi − lo，lo == hi 就是空区间。Java 的 subList、substring 都是这个约定。

洞察 · 先把问题改写成一个单调的判定

不变式 · lo 左边全是假，hi 和它右边全是真

  1. 开始lo = 0, hi = n。还没看过任何格，“lo 左边”和“hi 右边”都是空的，不变式成立。hi = n 表示“也许全是假”，答案就是 n。
  2. 每一步看 mid = (lo + hi) >>> 1。真：hi = mid，mid 自己可能就是答案，所以留着。假：lo = mid + 1，mid 肯定不是答案，跳过它。
  3. 结束lo == hi：左边全假、右边（含 hi）全真，hi 就是第一个真。返回 lo（和 hi 一样）。
  4. 为什么会停lo < hi 时 lo ≤ mid < hi，两个分支都让区间至少缩 1，所以一定会停。mid 向下取整，才保证 mid < hi。

两个边界够用所有查法

lowerBound(x) = 第一个 ≥ x，upperBound(x) = 第一个 > x，两段代码只差一个等号。常见的问法都能拼出来：

要找写法⑤ 的例子
第一个 ≥ xlowerBound(x)20:00 起点 → 4
第一个 > xupperBound(x)20:05 之后第一笔 → 13
最后一个 ≤ xupperBound(x) − 120:05 之前最后一笔 → 12
最后一个 < xlowerBound(x) − 120:00 之前最后一笔 → 3
等于 x 的有几个upperBound(x) − lowerBound(x)20:00:00 整有 3 笔
时间段 [a, b] 的成交[lowerBound(a), upperBound(b))[4, 13)，共 9 笔
时间段 [a, b)[lowerBound(a), lowerBound(b))[4, 11)，共 7 笔

结果可能是 0 或 n：lowerBound 返回 n 表示“都比 x 小”，减 1 得到 −1 表示“没有”。用之前先判断，别直接拿去当下标（坑 4）。

为什么这样设计：左闭右开，而不是闭区间

左闭右开 [lo, hi)，找第一个真

  • 只有一种“找”：第一个真。等于、小于、插入点都改判定，不改框架
  • 结束时 lo == hi，返回谁都一样，不用想
  • 答案可以是 n（全假），“找不到”和“插在最后”是同一个值
  • 区间长度 hi − lo，和 subList、substring 一个约定

闭区间 [lo, hi]，找等于 x 的

  • while (lo <= hi)、hi = mid − 1、lo = mid + 1，找到就 return
  • 找不到时要另外想清楚 lo 和 hi 各停在哪
  • 要找“第一个”等于 x 的，找到后还得继续往左缩，又是一套新边界
  • 三种情况（小于、等于、大于）三个分支，哪个写错都难查
决定胜负的约束：真正要的几乎从来不是“等于 x 的那个”，而是“一个位置”（起点、插入点、边界）。把每个问题都改写成“第一个真”，就只需要背一套代码、一条不变式。Arrays.binarySearch 是闭区间找等于的那一派，所以它在重复元素、找不到时的返回值上都要另外记规则。
JDK 自带的二分细节放到 ⑥
int i = Arrays.binarySearch(a, x);   // 找到：某个等于 x 的下标
                                     // 找不到：-(插入点) - 1，一定是负数
int ins = i >= 0 ? i : -i - 1;       // 统一成插入点

Collections.binarySearch(list, x);   // 同样的约定，list 要能随机访问
Arrays.binarySearch(bids, x, Collections.reverseOrder()); // 降序数据

// 要“第一个 ≥ x”，自己写 lowerBound（⑤），或者用 TreeMap.ceilingKey
背下这 6 行就够只换 ok(mid)
int lo = 0, hi = n;
while (lo < hi) {
    int mid = (lo + hi) >>> 1;
    if (ok(mid)) hi = mid;
    else lo = mid + 1;
}  // lo = 第一个 ok 为真的下标

⑤手推一遍：查 20:00～20:05 的成交

成交时间存成 long[]（这里用“当天第几秒”，实际是毫秒时间戳）。代码按 JDK 8 写法，--release 8 编译，JDK 17 运行。

⑤TradeLog.java（核心）完整代码 →
/** 第一个 >= t 的下标；都比 t 小就返回 n。 */
public static int lowerBound(long[] a, long t) {
    int lo = 0, hi = a.length;      // lo 左边都 < t，hi 及右边都 >= t
    while (lo < hi) {
        int mid = (lo + hi) >>> 1;
        if (a[mid] >= t) hi = mid;
        else lo = mid + 1;
    }
    return lo;
}
/** 第一个 > t 的下标：只差一个等号。 */
public static int upperBound(long[] a, long t) { /* 同上，a[mid] > t */ }

int from = lowerBound(times, hms(20, 0, 0));
int to   = upperBound(times, hms(20, 5, 0));
for (int i = from; i < to; i++) out(trades[i]);     // [from, to) 连续读

⑥边界和变体

第一圈 · 注意事项

1(lo + hi) / 2 溢出实测← ④ 不变式·每一步
现象
在 [0, Integer.MAX_VALUE) 上找 20 亿，第 2 步 lo = 1073741824，lo + hi 超过 int 上限变成负数，mid 算成 −536870912，下标越界。
根源
两个 int 相加可能超过 231 − 1（第 1 课 补码溢出）。数组超过 10 亿元素才会碰到，所以藏了很多年：JDK 的 Arrays.binarySearch 2006 年才修。
做法
(lo + hi) >>> 1（无符号右移把溢出的那一位当成正数，JDK 现在就这么写）或 lo + (hi − lo) / 2。
2lo = mid 少了 + 1，死循环实测← ④ 不变式·为什么会停
现象
在 10 20 30 40 里找第一个 ≥ 35，走到 lo = 2, hi = 3 后，mid 一直是 2，lo = mid 一直是 2，10 次都没停。
根源
“会停”靠的是每一步区间至少缩 1。mid 向下取整时可能等于 lo，这时 lo = mid 一点都没缩。
做法
判定为假时 mid 一定不是答案，写 lo = mid + 1。如果某种写法非要 lo = mid，mid 就得向上取整，那是另一套模板，别混用。
3Arrays.binarySearch 遇到重复元素实测← ④ 为什么这样设计
现象
100 200 200 200 200 200 200 300 里找 200，Arrays.binarySearch 返回 3，lowerBound 返回 1。拿 3 当起点，会漏掉前两笔。
根源
它是“找等于”的闭区间写法，碰到等于就返回；JDK 文档写明有多个相等元素时“不保证找到的是哪一个”。
做法
要起点用 lowerBound，要终点用 upperBound；只有确定元素不重复（比如成交号）时才用 Arrays.binarySearch。
4找不到时的负数返回值当下标用实测← ④ 两个边界
现象
100 200 300 里找 250，返回 −3，直接 a[-3] 抛 ArrayIndexOutOfBoundsException。
根源
JDK 把“找不到”和“该插在哪”编码进一个负数：−(插入点) − 1。减 1 是为了让插入点 0 也是负数。
做法
int ins = i >= 0 ? i : -i - 1; 统一成插入点再用；自己写的 lowerBound 返回 n 时也要先判断。
5买盘是降序的，却按升序二分实测← ④ 洞察·判定要单调
现象
买盘价格 101.20、101.10、101.00、100.90、100.80，找 100.90 返回 −1（“不存在”），它明明在下标 3。
根源
升序的判定“a[i] ≥ x”在降序数组上不是“先假后真”，二分的前提没了，结果是乱的，而且不报错。
做法
传 Collections.reverseOrder()，或把判定改成 a[i] ≤ x。数组的排序方向写进变量名或注释。
6Collections.binarySearch 用在 LinkedList 上实测← ④ 不变式·每一步要按下标跳
现象
20 万个元素，ArrayList 每次 1.3 µs，LinkedList 每次 935 µs。
根源
二分每一步要跳到 mid，链表跳到第 k 个要走 k 步。JDK 文档写明：不支持随机访问的大列表，会做“基于迭代器的二分”，O(n) 次链接遍历、O(log n) 次比较。
做法
要二分就放数组或 ArrayList；数据本来在链表里，就别用二分，或者换 TreeMap。
7时间段的端点算不算实测← ④ 两个边界
现象
“20:00～20:05 的成交”，闭区间是 9 笔，左闭右开是 7 笔：20:05:00 整的两笔一边算一边不算。两个系统对账，就差了这两笔。
根源
右端用 upperBound 还是 lowerBound，就是“含不含端点”的选择，代码不会提醒你。
做法
团队统一用左闭右开 [from, to)，接口参数名写成 fromInclusive、toExclusive。下一个时段从上一个的 to 开始，正好不重不漏。

第二圈 · 使用规范

  • 只用一套模板：左闭右开、找第一个真：防坑 2 和各种差一。别的问法都改判定，不改框架。
  • 中点写 (lo + hi) >>> 1：防坑 1。
  • 判定写成一个有名字的方法或 lambda：ok(mid) 一眼能看出单调不单调，防坑 5。
  • 区间一律 [from, to)：防坑 7 的对账差异。
  • 手写二分配一个对拍测试：随机生成有序数组，和从头扫的结果比 1 万次。差一的错误靠肉眼很难看出来。

第三圈 · 变体和深处

二分答案：在“答案”上二分

清算要在 8 小时内跑完 n 批任务，每小时最少处理多少条才来得及？“速度 v 来得及”是单调的：v 够了，更大的 v 也够。于是在 v 的取值范围上找第一个“来得及”，判定里算一遍总耗时。LC 875、1011、410 都是这个套路。

不完全有序也能二分

旋转过的有序数组（LC 33）、找峰值（LC 162）：每次比较后，能确定答案在哪一半就能二分，不要求整体有序。关键是写出“答案一定在这一半”的理由。

浮点数二分：按次数停

在连续区间上二分（比如求一个价格使得某个函数等于 0），用 while (hi − lo > eps) 容易因为浮点精度停不下来。固定跑 60～100 次更稳：每次减半，100 次后区间已经比 double 的精度还小。

数据很大时：缓存比次数重要

3000 万个元素 25 次比较却要 1 µs，时间几乎都花在缓存未命中上。按“二分时访问的顺序”重新排数组（Eytzinger 布局）、或者先在一张小的稀疏索引上二分再落到一小段里，能让前几跳留在缓存里。B+ 树的思路也是这个（第 15 课）。

面试官会怎么问

在有重复元素的有序数组里，找 x 第一次和最后一次出现的位置（LC 34）。

第一次 = lowerBound(x)，要先检查它 < n 且 a[它] == x；最后一次 = upperBound(x) − 1。两次二分，O(log n)。

while 里写 lo < hi 还是 lo <= hi？

取决于区间约定。左闭右开 [lo, hi) 时 lo == hi 是空区间，用 <；闭区间 [lo, hi] 时 lo == hi 还有一个元素，用 <=。混用就会漏看一个或者死循环。

mid 为什么写成 (lo + hi) >>> 1？

防溢出。lo + hi 超过 int 上限会变成负数，无符号右移把它当成 32 位无符号数除以 2，结果正好是正确的中点（lo、hi 都非负时成立）。

自测

1. 用一句话说出这一页的精华

二分找的是“由假变真”的分界线：把问题改写成单调的判定，用左闭右开、真就 hi = mid、假就 lo = mid + 1，结束时 lo 就是第一个真。

2. 从头扫的痛点是什么？凭感觉写二分的痛点又是什么？

从头扫是 O(n)，3000 万笔每次约 10 ms。凭感觉写二分没有不变式，差一、死循环、溢出、重复元素这些错要一个个撞上才知道。

3. 为什么判定为假时写 lo = mid + 1，而不是 lo = mid？

假的 mid 一定不是答案，可以跳过；更重要的是 mid 向下取整可能等于 lo，写 lo = mid 区间就不缩了，会死循环。

从 ④ 不变式的“为什么会停”推出。

4. 预测：把 lowerBound 里的 a[mid] >= t 改成 a[mid] > t，在 ⑤ 的数据上找 20:00:00，返回几？

返回 7，也就是 upperBound(20:00:00)：第一个晚于 20:00:00 的是 20:01:30，下标 7。改的只是判定，框架不变，结果就从“第一个 ≥”变成“第一个 >”。

从 ④ 洞察推出：二分找的是判定的第一个真。

5. 预测：数组长度从 3000 万变成 30 亿（用 long 下标），二分最多比较几次？

32 次：231 ≈ 21 亿 < 30 亿 < 232 ≈ 43 亿，所以 ⌈log₂ 30 亿⌉ = 32。数据多了 100 倍，比较只多 7 次。

从 ④ 的“每次砍一半”推出。

6. 放回全景：第 8 站前后各发生了什么？二分写错了，整条链路会怎样？

前面是第 7 站行情：成交更新 K 线和窗口最高价，同时追加进成交流水；后面是第 9 站定时：挂到 20:30 的单到点自动撤。第 8 站的二分错了，撮合和成交本身不受影响，但运营查到的成交少几笔或多几笔（坑 3、坑 7），对账（第 10 站）时和账务对不上；死循环的话，查询线程卡死，查询接口超时。
