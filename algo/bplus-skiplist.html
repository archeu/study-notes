B+ 树与跳表：两种多层索引，一个省磁盘，一个省旋转

红黑树在内存里够快，但换个场景就不合适了：数据在磁盘上，每走一层就是一次读盘，二叉树太高；数据要多线程同时改、还要按排名取，旋转牵一发动全身。B+ 树把一个节点做成一整页、放几百上千个 key，树高压到 3～4 层，叶子串成链表专门扫范围；跳表在一条有序链表上随机长出几层“快车道”，不旋转，插入只改前后几根指针，带上跨度就能按排名查。

这一页的位置第三圈“树”的最后一课。数据库这一侧，索引与 B+ 树 拆过真实的 InnoDB 页；Redis 这一侧，数据结构与编码 讲过 ZSet 什么时候用跳表。这一页站在算法层把两者放在一起：同样是“多层索引”，为什么一个要矮胖、一个要随机。

①要解决的问题：磁盘上查一段时间，Redis 里取排行榜

在全景第 8 站有两类查询离开了撮合引擎的内存：运营查“13:00～13:05 的成交”，数据在 MySQL 里，几亿行，按成交时间建了索引；客户端要看“今天成交额排行榜”、“我排第几”，数据在 Redis 的 ZSet 里，几百万个用户，每笔成交都在改分数。第 5 站如果撮合要多线程共享盘口，也会遇到同样的问题。

②朴素做法：把红黑树搬到磁盘上，或者给 TreeMap 加锁

做法疼在哪
红黑树存在磁盘上，一个节点一次读1 亿行树高约 27～50 层，查一个 key 读几十次盘；每次只用到一页里的一个 key，其余 16 KB 白读
有序数组 + 二分（第 9 课）查得快，但插一行要挪后面所有行，磁盘上更是灾难
TreeMap + 一把大锁所有线程排队；旋转会改到离插入点很远的节点，很难只锁一小块
TreeMap 取“第 k 名”没有子树大小，只能从头走 k 步，O(k)
  • 磁盘的代价单位是“页”而不是“比较”：读一页 16 KB 和读一个 key 花的时间差不多。二叉树一页只用一个 key，浪费了扇出。
  • 缺的那一块：让一次读盘尽量多地缩小范围，一个节点放上千个 key，一次读把范围缩到千分之一。
  • 另一边缺的：不靠旋转的平衡。改一处只动它前后的几根指针，并发和排名都好做。
不懂精华时的典型误用：以为 B+ 树的“快”是因为 log n。B+ 树和红黑树都是 O(log n)，区别在底数：底数 2 时 1 亿是 27 层，底数 1000 时是 3 层。磁盘上每层一次 IO，这个常数就是 9 倍的耗时。同理，跳表也不比红黑树“快”，单线程下本机实测 TreeMap 还快一些（⑤），它赢在别处。

③几种思路：多层索引的几种长法

结构每层缩小多少怎么保持平衡范围查询谁在用
红黑树（第 14 课）一半旋转 + 变色中序走，节点散在堆里TreeMap
B 树几百分之一节点满了分裂要在各层之间上下跳早期文件系统、部分数据库
B+ 树几百分之一节点满了分裂，所有叶子同一层叶子串成链表，顺着读MySQL InnoDB、大多数关系库
跳表期望 1/p（Redis 是 4 倍）插入时抛硬币决定层数最底层就是有序链表Redis ZSet、ConcurrentSkipListMap、LevelDB / RocksDB 的内存表
LSM 树—先写内存、批量合并到磁盘要合并多层写多读少：RocksDB、HBase

本页学 B+ 树和跳表：数据在磁盘、按页付费，选 B+ 树；数据在内存、要并发改或按排名取、想要简单，选跳表。两者都把“最底层”做成一条有序的链，所以范围查询都是“先找起点，再顺着走”，和第 9 课的二分找起点是同一个思路。

④关键洞察：B+ 树拼底数，跳表拼随机

先知道这些
  • 页：磁盘和数据库按块读写，InnoDB 默认一页 16 KB。读一页里的 1 个 key 和读满页的代价差不多。索引与 B+ 树。
  • 对数换底：log_b n = log₂n / log₂b，底数从 2 变成 1024，层数变成 1/10。第 0 课 幂和对数。

洞察 1 · B+ 树：一个节点一页，扇出上千，树高 = log扇出n

每个节点最多几个 key4161281200
100 万笔成交时的树高13743
查 13:00～13:05（1.9 万笔）读了几个节点9,6282,41130535

⑤ 的 IndexBench 本机实测。范围查询读的节点 ≈ 树高 + 结果数 / 每片叶子装了几个。教学版分裂时对半分，顺序插入的叶子只有半满；真实数据库对递增插入有专门的分裂策略，页会更满，读的页更少。

洞察 2 · 数据只放叶子，叶子串成链：范围查询只下一次树

B 树的内部节点也放数据，范围查询要在各层之间来回跳。B+ 树把数据全挪到叶子，内部节点只放路标，带来两个好处：内部节点更小，同样一页能放更多路标，扇出更大、树更矮；叶子按顺序串起来，范围查询下一次树找到起点，剩下全是顺序读，正好是磁盘最喜欢的访问方式。这就是第 9 课“二分找起点、再顺着读”的磁盘版。

洞察 3 · 跳表：有序链表上随机长几层快车道

最底层（L1）是一条按分数排好的链表。每插入一个节点，抛硬币决定它有几层：Redis 每多一层的概率是 1/4，所以大约每 4 个节点有 1 个长到 L2，每 16 个有 1 个长到 L3……查找从最高层开始，能往右就往右，右边的太大了就往下一层，和“先坐快车、再换慢车”一样。每根指针上记着跨度 span（跨过了几个节点），一路加起来就是排名。

机制 · p 取 1/4 还是 1/2：比较次数一样，指针少一半多

每多一层的概率 p每个节点平均指针数 1/(1−p)期望层数 log1/pn（n = 100 万）每次查找期望比较 ≈ (1/p)·log1/pn
1/22约 20约 40
1/4（Redis、JDK 也接近）1.33（本机实测 1.33）约 10（本机最高 10 层）约 40（本机实测 36.1）

(1/p)·log1/pn 在 p = 1/2 和 1/4 时都等于 2·log₂n：层数少了一半，但每层平均要往右多走一倍。比较次数不变、指针省了三分之一，所以 Redis 选 1/4（server.h 里 ZSKIPLIST_P 0.25、最多 32 层）。JDK 的 ConcurrentSkipListMap 是每个节点 1/4 的概率有索引，往上每层再减半。

为什么这样设计

B+ 树

  • 代价按页算：扇出上千，3～4 次 IO
  • 叶子链表，范围扫描是顺序读
  • 节点大、分裂合并复杂；并发要靠页级锁、latch 协议

跳表

  • 插入只改前后几根指针，局部、容易做成无锁（CAS）
  • 带上 span 就能按排名，代码比平衡树短得多
  • 平衡是概率性的；节点散在内存里，缓存不友好

红黑树

  • 单线程内存里最快（⑤ 实测 get 约快一倍）
  • 旋转会改到远处的节点，并发难
  • 不带子树大小就不能按排名
决定胜负的约束：代价单位和改动的局部性。磁盘上一次 IO 比几千次比较还贵，就把节点做大、把树压矮，这是 B+ 树；内存里要并发、要排名、要简单，就放弃“确定的平衡”换“改动只影响邻居”，这是跳表。Redis 作者给过选跳表的理由：实现简单、范围操作方便、内存占用可以调（就是 p）。

⑤手推一遍：教学版 B+ 树和带 span 的跳表

两个教学实现，只做插入和查询：BPlusTree（key 是成交时间，叶子串成链表）、SkipList（仿 Redis：p = 1/4、最多 32 层、指针带 span）。IndexBench 用 100 万条数据量树高、读的节点数、跳表的层数分布，再拿 TreeMap 和 ConcurrentSkipListMap 单线程比一比。代码按 JDK 8 写法，--release 8 编译，JDK 17 运行。

⑤BPlusTree.rangeCount（核心）完整代码 →
public int rangeCount(long lo, long hi) {
    Node x = root;
    while (!x.leaf) { nodesVisited++; x = x.kids[upper(x, lo - 1)]; }   // 下一次树：节点内二分选孩子
    int cnt = 0;
    for (int i = lower(x, lo); x != null; x = x.next, i = 0) {           // 顺着叶子链表读
        nodesVisited++;
        for (; i < x.n; i++) { if (x.keys[i] > hi) return cnt; cnt++; }
    }
    return cnt;
}
⑤SkipList.rank（核心）完整代码 →
public int rank(long score, String member) {
    Node x = head; int r = 0;
    for (int i = level - 1; i >= 0; i--) {               // 从最高层往下
        while (x.next[i] != null && (x.next[i].score < score
                || (x.next[i].score == score && x.next[i].member.compareTo(member) <= 0))) {
            r += x.span[i];                              // 跨过几个节点，排名就加几
            x = x.next[i];
        }
        if (x.member != null && x.member.equals(member)) return r;
    }
    return 0;
}

⑥边界和变体

第一圈 · 注意事项

1对索引列套了函数，B+ 树用不上← ④ 洞察 1
现象
WHERE DATE_FORMAT(trade_time, '%H:%i') BETWEEN '13:00' AND '13:05' 全表扫描，而 trade_time >= … AND trade_time < … 只读几页。
根源
B+ 树按 trade_time 本身排序，函数的结果不是按这个顺序排的，没法在树里二分找起点。
做法
条件写成索引列本身的范围；非要用函数就建函数索引（MySQL 8.0.13 起支持）。更多见 索引与 B+ 树 ⑥。
2深分页：LIMIT 1000000, 20← ④ 洞察 2
现象
翻到第 5 万页越来越慢。ZSet 用 ZRANGE … 1000000 1000019 倒是不慢。
根源
InnoDB 的 B+ 树节点不记子树大小，跳过前 100 万行只能顺着叶子数过去；Redis 跳表的 span 记了跨度，按排名能直接跳。
做法
数据库改成“记住上一页最后一个 key”：WHERE trade_time > 上一页最后一条 LIMIT 20（游标分页），每页都只下一次树。
3排行榜分数相同，名次跳来跳去← ④ 洞察 3
现象
两个用户成交额都是 300 万，刷新一下名次互换了，用户以为系统出错。
根源
ZSet 分数相同时按 member 的字典序排（⑤ 的 less 也是这样），不是按“谁先到”。“名次稳定”需要一个确定的第二关键字。
做法
把时间编进分数：score = 成交额 × 10k + (MAX − 达到时间)，注意 double 只有 53 位有效位，总位数别超；或者在应用层二次排序。
4把 ConcurrentSkipListMap 当成能拍快照的 TreeMap← ④ 为什么这样设计
现象
边写边遍历前 5 档，偶尔看到“一档已经撤了、另一档还没进来”的中间状态；用 size() 判断盘口有没有变化，结果不准。
根源
它的迭代器是弱一致的：不抛 ConcurrentModificationException，但也不保证看到某一瞬间的完整快照；size() 在并发修改时只是近似值（JDK 8 里还要遍历一遍）。
做法
需要一致的快照就由写线程定时复制一份发布；判断变化用版本号而不是 size()。
5小 ZSet 也以为是跳表← ④ p 的取舍
现象
几十个元素的 ZSet，按跳表估内存和复杂度，和实际对不上。
根源
元素少、值短时 Redis 用紧凑的 listpack 顺序存，O(n) 但 n 很小、内存省；超过阈值才转成跳表 + 哈希表。
做法
用 OBJECT ENCODING key 看实际编码；阈值和各版本的变化见 Redis 数据结构与编码。

第二圈 · 使用规范

  • 范围条件写在索引列本身上：防坑 1。
  • 分页用游标，不用大 OFFSET：防坑 2。
  • 排行榜要有确定的第二关键字：防坑 3。
  • 单线程用 TreeMap，多线程共享才用 ConcurrentSkipListMap：⑤ 实测单线程 TreeMap 更快；并发场景别指望它给一致快照，防坑 4。
  • 估内存先确认编码：防坑 5。

第三圈 · 变体和深处

三层能装多少行

粗算：主键 BIGINT 8 字节 + 页号 6 字节，一个内部页大约放 16 KB / 14 B ≈ 1100 个路标；叶子放整行，行 1 KB 时一页约 15 行。三层 ≈ 1100 × 1100 × 15 ≈ 1800 万行。行越小、装得越多。真实数字按 索引与 B+ 树 里拆页的结果为准。

跳表为什么好做无锁

插入是“先接最底层、再从下往上接索引层”，每一步只是把一根指针从 A 改成 B，可以用 CAS；删除先给节点打标记，再把它从各层摘掉。ConcurrentSkipListMap 就是这样做的，不需要锁住整棵树。红黑树一次插入要同时改好几个节点的颜色和指针，没法拆成一串单指针 CAS。

LSM 树：写多的时候

先把写入放进内存里的有序结构（RocksDB 默认就是跳表），满了整体刷成磁盘上的有序文件，后台再合并。写变成顺序写，读要查好几层。成交流水这种只追加的数据很适合。

B+ 树的分裂和页填充

⑤ 的教学版对半分裂，顺序插入时叶子半满；真实数据库对递增主键会在插入点附近分裂，页几乎填满，这也是“主键用自增”的原因之一。随机主键（UUID）会到处分裂、页又散又空。

面试官会怎么问

MySQL 为什么用 B+ 树而不是红黑树、哈希、B 树？

红黑树太高，磁盘上每层一次 IO；哈希不支持范围和排序；B 树内部节点也放数据，扇出更小，范围查询要跨层跳。B+ 树扇出大、树矮，叶子链表让范围扫描变顺序读。

Redis ZSet 为什么用跳表不用红黑树？

范围操作（ZRANGEBYSCORE）找到起点后顺着最底层走即可；带 span 后按排名 O(log n)；实现简单，改动局部；内存可以通过 p 调。性能和平衡树同一量级。

跳表查找的期望复杂度？最坏呢？

期望 O(log n)，每次查找约 (1/p)·log1/pn 次比较；最坏 O(n)（所有节点都只有 1 层），但概率随 n 指数级变小。

自测

1. 用一句话说出这一页的精华

B+ 树把一个节点做成一页、扇出上千，把磁盘 IO 压到 3～4 次，叶子串成链表专门扫范围；跳表用随机层数代替旋转，改动只影响邻居，好做并发、带 span 能按排名；两者底层都是一条有序的链。

2. 红黑树放到磁盘上，痛点在哪？

树高 27 层以上，每层一次读盘；每次读一页只用到一个 key，扇出被浪费。

3. 深分页慢的根源是哪条原理？

B+ 树叶子链表能顺序读，但节点不记子树大小，跳过前 N 行只能一行行数过去。

从 ④ 洞察 2 推出（对比洞察 3 的 span）。

4. 预测：⑤ 的 B+ 树把每节点的 key 上限从 1200 改成 12000，100 万笔时树高和读的节点数怎么变？

树高从 3 降到 2（12000 × 6000 左右的半满叶子已经远超 100 万）；范围查询读的节点数从 35 降到个位数（每片叶子装的多了 10 倍）。代价是节点变大，一个节点要读的字节也多了 10 倍，在磁盘上就超过一页了。

从 ④ 洞察 1 推出：树高 = log扇出n。

5. 预测：跳表里插入一个新用户，最坏要改几根指针？平均呢？

它有几层就改几层的前驱指针，加上更高层的 span 各加 1。平均 1/(1−p) = 1.33 层，所以平均只改一两根；最坏是 32 层。红黑树插入也要改常数个节点，但可能是离插入点很远的祖先。

从 ④ 洞察 3 和 p 的取舍推出。

6. 放回全景：第 8 站前后各发生了什么？索引出问题，整条链路会怎样？

前面第 7 站行情把成交写进流水（异步落 MySQL）、给排行榜加分（Redis ZINCRBY）；后面第 9 站定时撤单。第 8 站的查询如果用不上索引（坑 1）或深分页（坑 2），MySQL 的 IO 被打满，同一个库上的成交落库也变慢，延迟传回第 7 站的异步写入；排行榜同分乱跳（坑 3）只影响展示。撮合本身在内存里，不受影响。
