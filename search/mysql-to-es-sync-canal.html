下单 1 秒后商家才搜得到：MySQL 到 ES 的同步（binlog、Canal、一致性）

ES 里那份订单不是谁“写”进去的，而是从 MySQL 的 binlog 里“抄”过去的：Canal 装成一台从库，向 MySQL 要 binlog，把每一行的变更解析出来交给同步程序，同步程序写进 ES、写成功了再告诉 Canal“这批处理完了”（ack）。这条链路的性质决定了一切：它是异步的（实测提交到搜得到约 1 秒，大头是 ES 的 refresh），至少一次的（没 ack 就重发，所以写 ES 要幂等），只在分区内有序的（并行消费要按订单号分区、写入带版本号）。binlog 被清理掉了就接不上，只能全量重灌。

①为什么需要：ES 里的订单要一直跟着 MySQL 变

在全景第 10 站，这一步要解决：1024 下单、付款、商家发货，每一次变化都发生在 MySQL 的 8 张分片表里；商家后台搜的是 ES。ES 里的那一份要做到：

不漏

订单服务、退款服务、运营脚本、DBA 的手工 SQL 改的，都要过去。

不乱

同一单先付款后发货，ES 里最后必须是“已发货”，不能被晚到的“已付款”盖回去。

不拖累下单

ES 慢了、挂了，下单照常；恢复以后自己追上来。

②没有它会怎样：在代码里顺手写 ES，或者定时扫表

做法疼在哪
下单代码里同步写 ESES 慢一点，下单就慢一点；ES 挂了，要么下单失败，要么吞掉异常漏写。两个系统没有共同事务：MySQL 回滚了，ES 却写进去了。别的服务和手工 SQL 改的数据，ES 永远不知道。
代码里发 MQ，消费者写 ES不拖累下单了，但“写库成功、发消息失败”仍然会漏（要本地消息表兜底，见 分布式事务）；同样管不到别的写入方。
定时任务按 updated_at 扫表延迟是扫描间隔（分钟级）；删除的行扫不到；同一秒内改两次分不清；每次扫描都在线上库跑范围查询；分片以后要扫 8 张表。

缺的那一块：一个“已经提交的变更”的可靠来源，覆盖所有写入方、按提交顺序排好、不用改业务代码。MySQL 自己就有：binlog，主从复制靠的就是它。

不懂精华时的典型误用同步程序拿到变更就 ack，再异步写 ES：ES 写失败的那些变更 Canal 不会再给，ES 永远少了它们。至少一次的前提是“处理成功了才 ack”。

③相邻方案：几种读 binlog 的工具

形态适合注意
Canal 1.1.8阿里开源，独立的 server 装成从库；客户端 TCP 直连，或者 server 直接投递到 Kafka / RocketMQMySQL 为主的国内团队最常见；还有 canal-adapter 能直接写 ES只支持 MySQL 系；1.1.8 才认识 MySQL 8.4 的新语法（⑤ 和源码）
DebeziumKafka Connect 的一组连接器，变更写进 Kafka已经有 Kafka Connect；要同时接 MySQL、PostgreSQL、Oracle 等绑定 Kafka 生态
Flink CDCFlink 的源连接器，全量 + 增量一体同步途中要做转换、关联、聚合（比如订单拼上商品名再写 ES）要养 Flink 集群
云厂商 DTS托管的同步 / 迁移服务不想自己运维同步链路按量付费，排查时看不到内部

选择规则：只是 MySQL → ES / Kafka 的搬运 → Canal；已经在 Kafka Connect 上 → Debezium；途中要加工 → Flink CDC。交易靶场用 Canal，生产形态是 Canal → Kafka（按订单号分区）→ 同步程序 → ES；⑤ 为了少一个组件，同步程序用 Canal 的 TCP 客户端直连，机制一样。

④原理：一行变更怎么从 binlog 走到 ES

先知道这些 binlog：MySQL 在事务提交时按提交顺序写的变更日志，从库靠它复制，见 redo、undo、binlog。 从库怎么拿 binlog：从库用一个有 REPLICATION SLAVE 权限的账号连上主库，说“从某个文件的某个位置开始给我”，主库的 dump 线程就一条条推过来，见 主从复制。

机制 1：ROW 格式的 binlog 里有什么

  • 一次 UPDATEUPDATE t_order SET status = 'SHIPPED', version = 3 WHERE id = 20001 提交后，binlog 里是一组事件：Table_map（是哪张表、各列什么类型）、Update_rows（这一行改之前的全部列 + 改之后的全部列）、Xid（事务提交）。
  • ROW + FULLbinlog_format=ROW、binlog_row_image=FULL 是 MySQL 8.4 的默认值（⑤ 查过），所以同步程序拿到的是完整的行，不用再回库查。如果有人把 row_image 改成 MINIMAL，“改后”只剩被改的列，同步程序就拼不出完整文档。
  • 位点“读到哪了”用 binlog 文件名 + 偏移量表示，比如 binlog.000002:1329（开 GTID 时也可以用 GTID 集合）。续传、重放、校验都靠它。

机制 2：Canal 装成一台从库

MySQL 8.4 删除了 SHOW MASTER STATUS（改名为 SHOW BINARY LOG STATUS）。Canal 在没有记录位点、要找“当前位置”时会发这条语句：1.1.8 的源码里先判断 atLeastMySQL84() 再选语法，1.1.7 的同一个方法只会发老语句。⑤ 实测 1.1.8 连 8.4.13 一次连上，日志里是 find start position successfully … binlog.000002。

机制 3：至少一次，所以要幂等

  • 先写再 ack同步程序拿到一批，写进 ES 成功了才 ack(batchId)；写失败就 rollback，下次 Canal 再给同一批。所以不会丢，但会重复：ES 写成功、ack 之前进程挂了，重启后这一批会再来一遍。
  • 幂等文档 _id 就用订单号，每次写整行（index 覆盖），重复写一次结果不变；删除也是幂等的。不要用“ES 里 +1”这类增量操作。
  • 先 ack 再写的后果就是 ② 的典型误用：写失败的变更再也拿不回来。

机制 4：binlog 是有序的，并行消费以后就不一定了

binlog 里 9527 的“已付款（v2）”一定排在“已发货（v3）”前面。只要从头到尾一个线程按顺序写，ES 里最后就是 v3。可吞吐不够时大家会并行：Canal 投递到 Kafka 的多个分区、同步程序开多个线程。同一单的两条变更一旦进了不同分区（或者被不同线程处理），谁先写进 ES 就看运气。两道防线：

按订单号分区

Canal 投递 Kafka 时配 canal.mq.partitionHash=order_db.t_order:id，同一单永远进同一个分区，分区内有序。代价：一个大商家的热点订单会让某个分区更忙。

外部版本号

写 ES 时带 version = 行里的 version、version_type = external：只有版本更大的才写得进去，晚到的旧版本被 ES 以 409 拒掉。这是最后一道防线，前提是表里有单调递增的版本列。

机制 5：binlog 不是永远都在

  • 保留期MySQL 8.4 默认 binlog_expire_logs_seconds = 2592000（30 天），过期的 binlog 文件会被自动删除；磁盘紧张时 DBA 还会手动清。
  • 接不上Canal 停的时间超过保留期，或者它记着的那个文件已经被清掉，重启后按 meta 里的位点去要，主库回一个 1236 错误。⑤ 的 purge 演练原样复现了这个错误。
  • 只能全量重灌建一个新索引 orders_v2；先记下当前 binlog 位点，再从 MySQL 的 8 张表全量导一遍；导完从记下的位点开始回放增量（写入幂等，重叠部分无害）；校验通过后把别名 orders 切到新索引。和第 3 页“binlog 路线的迁移”是同一个结构。
  • 平时就要对账每天比一次 ES 和 MySQL：按天、按商家数行数，抽样比内容。同步链路出过错、被跳过的变更，只有对账能发现。

最少的写法

同步程序的主循环canal.client 1.1.8
CanalConnector c = CanalConnectors.newSingleConnector(new InetSocketAddress("127.0.0.1", 11111), "orders", "", "");
c.connect();
c.subscribe("order_db\\.t_order");
c.rollback();                                          // 从上次 ack 的位置接着拿
while (running) {
    Message msg = c.getWithoutAck(1000, 100L, TimeUnit.MILLISECONDS);
    if (msg.getId() == -1 || msg.getEntries().isEmpty()) continue;
    try {
        bulkToEs(toDocs(msg.getEntries()));            // _id = 订单号；version = 行里的 version，version_type = external
        c.ack(msg.getId());                            // 写成功才 ack
    } catch (Exception e) {
        c.rollback(msg.getId());                       // 下次再拿到同一批
    }
}

实验看到了什么对应
e2e提交到搜得到：中位 0.8 秒，最慢 1.6 秒；其中 Canal 那一段中位 90 ms，ES refresh 那一段中位 585 ms，是大头机制 2、上一页机制 4
order同步程序打乱写入顺序：不带版本 148 / 300 单停在旧状态；带外部版本号 0 单，ES 拒掉了 144 次晚到的旧版本机制 4
outage同步程序停 10 秒，Canal 替它攒着：恢复后第一批就拿到 166 条积压，429 ms 追平机制 3
purgeCanal 停着时改的 10 单、所在的 binlog 被清掉：Canal 每隔十几秒重试同一个位点，一直报 1236；之后新写的订单也同步不过来，那 10 单的变更永久丢了机制 5

到这里已经能交差了：商家下单后约 1 秒能搜到；同步程序挂了、重启了都能接上；写入带版本，乱序也不怕。已知还没处理的：binlog 被清理就只能全量重灌（坑 4）；删除留下的版本“墓碑”（坑 5）；表结构变了同步程序跟不上（坑 6）。

⑥细节

第一圈 · 不知道就会出事

1拿到就 ack，写失败的变更永远丢了← ④ 机制 3
现象
ES 抖了一下，那几秒的 bulk 失败了；同步程序已经 ack，Canal 不会再给，这些订单在 ES 里永远是旧的。
根源
ack 的含义是“这批我处理完了，可以丢了”。
做法
写成功才 ack，失败 rollback；写入做成幂等（_id = 订单号、写整行）。走 Kafka 时同理：处理成功才提交 offset。
2并行消费，旧状态盖住新状态← ④ 机制 4
现象
⑤ order：打乱顺序写，300 单里 148 单停在“已付款”，实际已发货。
根源
binlog 全局有序，但同一单的变更一旦跨分区、跨线程，到达 ES 的顺序就不确定。
做法
Kafka 按订单号分区（canal.mq.partitionHash）；写 ES 带外部版本号（⑤：148 → 0）；表里要有单调递增的 version 列。
3binlog 格式被改成了 STATEMENT 或 MINIMAL← ④ 机制 1
现象
（按文档）STATEMENT 格式下 binlog 里只有 SQL 文本，Canal 拿不到行；MINIMAL 下“改后”只有被改的列，同步程序写进 ES 的文档缺字段。
根源
行级同步依赖 ROW + FULL 的前后镜像。
做法
把 binlog_format=ROW、binlog_row_image=FULL 写进数据库规范和巡检；同步程序启动时自检这两个变量。
4Canal 停太久，binlog 被清掉，静悄悄地停摆← ④ 机制 5
现象
⑤ purge：Canal 一直报 errno = 1236 … Could not find first log file name in binary log index file，同步程序收不到任何变更，ES 不再更新；Canal 停机期间那 10 单的变更找不回来了。进程活着、端口通着，只看存活探针发现不了。
根源
Canal 只能从它记住的位点续传，那个文件已经不在主库上了。
做法
监控“同步延迟”（最新一条变更的提交时间到现在）而不只是进程存活；binlog 保留期远大于最长可能的停机时间；接不上就按机制 5 全量重灌，别手工把位点改到最新（那等于承认中间的变更丢了）。
5带外部版本号时，删除留下“墓碑”，同一个 id 重建写不进去← ④ 机制 4
现象
⑤ 第一次跑 order 时踩到的：两轮实验复用了同一批订单号。上一轮的 DELETE 带着 version 3 写进 ES（文档本来不在，也记下了“这个 id 删到了版本 3”），新一轮的 v1、v2、v3 全被 409 拒掉，900 次冲突、300 单一单都没写进去。
根源
ES 会把删除的版本号保留一段时间（index.gc_deletes 默认 60 秒），用来拒绝比它旧的写入；外部版本号要求严格更大。
做法
版本号在一个 id 的整个生命周期里只增不减，删除后重建不要从 1 重新开始；订单号这类本身就不复用的 id 不受影响。
6表加了一列，同步程序和 ES mapping 没跟上← ④ 机制 1
现象
（按机制推演）DBA 给 t_order 加了 remark，binlog 里的行多了一列；同步程序如果按位置取列就错位，ES 用 strict mapping 就整批写失败、反复 rollback 卡住。
根源
同步链路两端都有一份“表结构”，DDL 只改了源头。
做法
同步程序按列名取值、忽略不认识的列；DDL 流程里加一步“先改 ES mapping 和同步程序，再改表”；Canal 的 tsdb 用来记录表结构历史，回放老位点时能用当时的结构解析。

第二圈 · 团队里怎么做

  • 同步延迟当一等指标同步程序每处理一批，就上报“这批里最早一条的提交时间到现在”；超过 10 秒告警。防的是坑 4 这种“进程活着但不干活”。
  • 每天对账按天、按商家比 MySQL 和 ES 的单数，抽样比内容；差异自动补（按订单号回 MySQL 读，重写 ES）。防的是任何一环漏掉的变更。
  • 全量重灌是常备脚本建新索引、记位点、全量导出、回放增量、校验、切别名，写成一键脚本并定期演练。防的是坑 4 发生时临时手写。
  • Canal 账号最小权限只给 REPLICATION SLAVE, REPLICATION CLIENT, SELECT，只订阅需要的库表。防的是同步链路变成数据泄露的口子。

第三圈 · 深处

  • 延迟都花在哪⑤ 的 0.8 秒里，MySQL 推 binlog 加 Canal 解析中位 90 ms，同步程序批量写 ES 中位 42 ms，剩下的都是 ES 等 refresh。想更快，先看 refresh（代价见上一页），再看同步程序的批大小和等待时间（getWithoutAck 的批 1000 条、超时 100 ms）。
  • 分片库怎么接交易靶场的订单在 2 个库 8 张表，要么一个 Canal 实例订阅一个库（两个实例），用正则 order_db\.t_order_\d+ 匹配同一个库里的多张表；要么用 ShardingSphere 的 CDC 功能按逻辑表输出。同一单只会在一张表里变化，所以按订单号分区依然成立。
  • 主从切换以后位点是“文件名 + 偏移量”，换了主库就不认了；开启 GTID 后 Canal 可以用 GTID 续传（canal.instance.gtidon=true），主从切换不丢位置。
  • canal-adapterCanal 官方的 adapter 能按配置把表直接映射到 ES 索引（含简单的关联），不用自己写同步程序；复杂转换还是自己写或用 Flink CDC。

自测

1. 用一句话说出这一页的精华

MySQL 到 ES 的同步是“抄 binlog”：Canal 装成从库读 ROW 事件，同步程序写成功才 ack（至少一次，所以写入要幂等），并行时按订单号分区、写入带版本号防乱序；它是异步的（约 1 秒），binlog 被清理就只能全量重灌，平时要监控延迟、每天对账。

2. 在下单代码里顺手写 ES，疼在哪？

ES 慢或挂会拖累、甚至搞挂下单；两边没有共同事务，回滚、失败都会不一致；别的服务和手工 SQL 改的数据同步不到。

3. 坑 2 的根源是 ④ 的哪条？为什么外部版本号能解决？

机制 4：binlog 有序，但跨分区、跨线程后到达 ES 的顺序不确定。外部版本号让 ES 只接受比当前更大的版本，晚到的旧变更被 409 拒掉，不管到达顺序如何，最后停在最大版本。

4. 预测：⑤ 的 outage 如果停的不是同步程序，而是 Canal server 本身（停 10 秒再启动），结果有什么不同？

基本一样：Canal 的位点在 meta.dat 里（每秒落盘），重启后从同步程序最后 ack 的位置附近续传，最多重复几条（幂等写入无害）。只要这 10 秒里 binlog 没被清理，就能追平。区别是重启 Canal 要多花几秒建立复制连接。

5. 预测：DBA 为了省磁盘，把 binlog_expire_logs_seconds 从 30 天改成 1 小时。平时没事，哪天会出事？

Canal 或同步链路停超过 1 小时的那天（比如周末出故障、升级 Canal 时卡住）：重启后它记住的 binlog 已经被删，就是 ⑤ 的 purge，只能全量重灌。保留期是同步链路的“最长可停机时间”。

6. 放回全景：第 10 站前后各发生了什么？第 4 站搬运 1.2 亿行时，如果 ES 是从新库的 binlog 同步的，会怎样？

之前：订单写进 MySQL 的分片表、产生 binlog；之后：第 11 站 ES 把文档 refresh 成可搜的 segment，第 9 站商家搜到。搬运 1.2 亿行会在新库产生 1.2 亿条 INSERT 的 binlog，Canal 和同步程序要全部消化，ES 的同步延迟会飙到小时级，商家搜不到新订单。所以迁移期间 ES 继续从旧库同步，切写那天再把同步源切到新库（或者搬运期间暂停同步、事后全量重灌）。
