商家 301 搜“键盘”：Elasticsearch 的倒排索引、分片、写入和查询

MySQL 的 B+ 树按“一行的某个字段值”排好序，适合“给我 id = 9527 的那一行”；Elasticsearch 反过来，先把每段文字切成词，再记下每个词出现在哪些文档里（倒排索引），适合“哪些订单的标题里有‘键盘’”，还能按相关度排序、任意字段组合过滤。代价有两个：数据是从 MySQL 同步过来的另一份副本；写进去要等一次 refresh（默认每秒一次）才搜得到，所以它是“近实时”的，只能用来“找”，不能用来做决定。

①为什么学：商家 301 要的三种查法，订单库都不擅长

在全景第 9 站，商家 301 打开后台：

按商家筛

“本店、待发货、最近 7 天”。shop_id 不是分片键，订单库要问遍 8 张表（上上页）。

搜文字

“标题里有‘键盘’”“收货人姓张”。MySQL 的 LIKE '%键盘%' 用不上 B+ 树索引，只能一行行扫。

随意组合、按相关度排

状态、金额区间、时间、关键词任意组合，再按“最相关”或时间排序，翻几页。MySQL 要为每种组合建联合索引，组合一多就建不过来。

②老办法：LIKE、全文索引、异构索引表

老办法行不行
WHERE title LIKE '%键盘%'能用但很慢：前面有 %，B+ 树按值排序帮不上忙，只能全表扫描；分片以后还要扫 8 张表。也没有“相关度”这回事。
MySQL FULLTEXT 索引（ngram 解析器）能做中文分词和全文检索；但它在订单库里，和下单抢同一台机器的 CPU 和 IO；分片以后同样要 8 张表各查一遍再合并；排序、聚合、高亮的能力弱。
按 shop_id 再分一份的异构索引表解决“按商家筛”，解决不了“搜文字”和“任意组合”。

缺的那一块，就是 ES 的精华：为“找”专门建一份数据结构（倒排索引），和负责“写对”的订单库分开。订单库继续按用户分片、保证事务；ES 按自己的方式分片、保存一份可以随便搜的副本。

不懂精华时的典型误用把 ES 当成第二个数据库：发货、退款这些操作直接以 ES 里的状态为准。ES 的数据是异步同步过来的，比 MySQL 晚一两秒，偶尔还会丢一条、乱一次序；它只负责“找到候选的订单号”，做决定之前要回 MySQL 按订单号查一次。

③选谁：ES、OpenSearch，还是数据库里的全文检索

是什么适合注意
Elasticsearch 9.x基于 Lucene 的分布式搜索引擎，REST API全文检索、多条件过滤、聚合、日志检索；国内电商后台搜索最常见许可证在 2021 年改过（现在 AGPL / Elastic License 等可选），云上托管要看厂商
OpenSearchAWS 主导、从 Elasticsearch 7.10 分出来的开源版本同上，用 AWS 托管服务时常见API 大体兼容 7.x，新功能两边各走各的
MySQL FULLTEXT / PostgreSQL tsvector数据库自带的倒排索引数据量小、不想多养一个系统和业务抢资源；分片以后要逐片查；中文分词能力有限
ClickHouse / Doris列存分析库“近 30 天销售额前 10”这类聚合报表不擅长按相关度的全文检索

选择规则：要全文检索和多条件组合查询 → 搜索引擎（ES / OpenSearch）；只要聚合报表 → OLAP；数据量小 → 数据库自带的全文索引。交易靶场的商家后台既要搜文字、又要多条件过滤，选 Elasticsearch，本页学它。

④原理：倒排索引、分片、一次写入和一次搜索

先知道这些 Lucene：ES 底下的 Java 搜索库。ES 的一个分片（shard）就是一个完整的 Lucene 索引；ES 在它上面加了分布式：分片、副本、路由、集群。 文档：ES 存的一条 JSON，比如一单订单。索引（index）是一类文档的集合，相当于一张表；mapping 相当于表结构，规定每个字段怎么建索引。

机制 1：倒排索引，先切词，再记“词 → 哪些文档”

B+ 树是“按值找行”，倒排索引是“按词找文档”。位置信息让它还能做短语查询：“机械键盘”要求“机械”和“键盘”在同一文档里相邻。分词器决定了词典里有什么：默认的 standard 分词器把中文一个字切一个词，搜“键盘”就变成“键”或“盘”，会混进“键帽”“硬盘”（⑤ 实测 58340 单 vs 41862 单）；内置的 cjk 分词器两个字一组，好得多；生产上常装 IK、smartcn 这类按词典切词的插件。

    机制 2：text 和 keyword，查询和过滤

    text：先分词再建索引

    标题、收货人、商品描述。用 match 查，查询词也会被同一个分词器切开，结果按相关度（BM25）打分排序。

    keyword：整个值当一个词

    shop_id、status、订单号。用 term 精确匹配，放在 filter 里：不打分、结果能缓存，还能排序和聚合（靠列式的 doc values）。

    不建 mapping 直接写，ES 会猜：字符串一律猜成 text（再加一个 .keyword 子字段）。⑤ 实测：status = "WAIT_SHIP" 被切成小写的 wait_ship，term 查 "WAIT_SHIP" 查到 0 条，查 status.keyword 才是 1 条。所以订单索引一定要先建 mapping。

    机制 3：分片和路由

    • 分片一个索引拆成几个主分片，分散到不同节点上；每个主分片可以有副本，挂在别的节点。⑤ 建了 3 个主分片（单节点所以 0 副本）。
    • 路由文档去哪个主分片：shard = hash(_routing) % 主分片数，_routing 默认是文档 _id。⑤ 写 10 万单，3 个分片各分到 33231、33219、33550 个，很均匀。
    • 主分片数定了就不能直接改改了，公式里的除数就变了，每个文档该在哪都变了。要么重建索引（reindex），要么用 _split 按整数倍拆。和订单库“表数一次规划够”是同一个道理（第 1 页机制 4）。
    • 和订单库分片的区别订单库按 user_id 分片，为的是“我的订单”只查一张表；ES 按 _id 散开，搜索默认问所有分片。也可以指定 routing = shop_id，让一个商家的订单都在一个分片，商家查询只问一个分片；代价是大商家会让那个分片变胖（第 1 页试验台里的 47%）。

    机制 4：一次写入，为什么 1 秒后才搜得到

    被放弃的设计：每写一条就能搜到

    每个文档写完立刻生成一个能搜的 segment。segment 是不可变的，这样就会产生海量只有一两条文档的小 segment：每次搜索要挨个查，合并它们又要消耗大量 IO。

    ES 的选择：攒一秒，写成一个 segment

    不可变的 segment 不用加锁、能被操作系统缓存、容易压缩；代价是写入和可见之间有最多约 1 秒的间隔。translog 保证这一秒里的数据宕机不丢，refresh 负责“能搜到”，flush 负责“落盘”，三件事分开。

    决定胜负的约束：倒排索引按词组织，改一个文档会牵动很多词的倒排表，原地更新代价太高，所以 Lucene 的 segment 只追加、不修改。“近实时”是这个设计的直接后果；更新一个文档，其实是标记旧版本删除、再写一个新版本。

    机制 5：一次搜索：先查后取（query then fetch）

    • query协调节点把查询发给每个分片（主或副本中的一个）。每个分片在自己的 segment 里找出排名前 from + size 的文档，只回文档号和排序值。
    • 归并协调节点把各分片的结果合起来排序，挑出全局的第 from 到 from + size 名。和 跨片分页一模一样：翻得越深，每个分片要交出来的越多。
    • fetch再去对应分片取这几条文档的内容（_source），返回给客户端。
    • 深分页上限所以 ES 默认 from + size 不能超过 10000（index.max_result_window），⑤ 实测超过直接 400；要往后翻用 search_after（ES 版的游标），导出全部用 point in time + search_after。

    ⑥细节·规范·优化

    第一圈 · 不知道就会出事

    1没建 mapping，精确字段被猜成了 text← ④ 机制 2
    现象
    ⑤：term status = "WAIT_SHIP" 查到 0 条。字段已经建好就不能改类型，只能重建索引。
    根源
    动态映射把字符串都当 text，分词时转了小写。
    做法
    先建 mapping；用索引模板（index template）统一管理；生产索引设 "dynamic": "strict"，多一个没声明的字段就报错。
    2中文用默认分词器，搜出一堆不相干的← ④ 机制 1
    现象
    ⑤：搜“键盘”，standard 分词命中 58340 单，比 cjk 的 41862 多出 1.6 万，全是“键帽”“硬盘”。
    根源
    standard 一个字一个词，“键盘”被拆成“键”或“盘”。
    做法
    至少用 cjk；商品、地址这类要按词切的，装 IK / smartcn 插件并维护自定义词典；改分词器要重建索引。
    3翻页超过 1 万条直接报错← ④ 机制 5
    现象
    ⑤：from = 10000, size = 10 返回 400 Result window is too large。
    根源
    每个分片要交出 from + size 条，越深越贵，所以默认封顶 10000。
    做法
    页面上只给“下一页”，用 search_after；导出用 point in time + search_after。不要靠调大 max_result_window 解决。
    4写完马上搜，搜不到← ④ 机制 4
    现象
    ⑤：写入后要 0.5～0.9 秒才搜得到。商家刚改完备注、刷新列表，看到的还是旧的。
    根源
    refresh 每秒一次，之前的文档还在内存缓冲里。
    做法
    “刚改完要看到”的场景，在前端先展示本地结果，或者这一次直接查 MySQL；确实需要时单次写入带 refresh=wait_for（⑤：每次写要多等约 0.87 秒）。不要每次写都带 refresh=true，那会产生大量小 segment。
    5拿 ES 里的数据做决定← ② 精华
    现象
    根据 ES 里“已支付”去发货，可这一单一秒前刚退款，ES 还没同步到。
    根源
    ES 是 MySQL 之后的一份异步副本，晚一两秒，还可能因为同步出错而不一致。
    做法
    ES 只返回候选订单号；任何写操作（发货、退款、改价）之前，按订单号回 MySQL 读一次再判断。
    6主分片数拍脑袋定，要改只能重建← ④ 机制 3
    现象
    （按文档）一开始 1 个主分片，数据长到几百 GB 才发现太大；或者一开始 50 个，每个只有几百 MB，集群元数据和搜索开销都很大。
    根源
    路由公式里除的是主分片数，它变了文档位置就全变了。
    做法
    按 3 年数据量估，官方建议单个分片几十 GB 以内；按时间滚动的数据（日志、历史订单）用按月索引 + 别名，新索引可以换分片数。

    第二圈 · 团队里怎么用

    • 索引模板 + 别名业务代码只认别名 orders，背后是 orders_v1；改 mapping 时建 orders_v2、全量重灌、校验，再把别名切过去。防的是坑 1、2、6“只能重建”时要停服。
    • filter 放能缓存的条件商家、状态、时间范围放 filter，只有关键词放 must。防的是给不需要打分的条件也算分，浪费 CPU。
    • 只存要搜和要展示的字段订单详情回 MySQL 查，ES 里不放大字段（地址全文、商品快照）。防的是索引膨胀、同步变慢。
    • 不开放任意深度的翻页产品上用“加载更多”。防的是坑 3。

    第三圈 · 优化和深处

    • 相关度：BM25默认打分是 BM25：一个词在这单里出现越多、在所有订单里越少见，分越高；标题越短，命中的词分量越重。AI 地图站 06 的关键词检索用的就是它，和向量检索混合（hybrid search）时，BM25 负责“字面一致”。
    • doc values排序、聚合不用倒排索引，用按列存的 doc values（写入时同时生成）。这就是 keyword 和数值字段能高效排序、聚合的原因；text 字段默认没有，不能直接排序。
    • 批量写入调优全量重灌时临时把 refresh_interval 设成 -1、副本数设成 0，灌完再改回来；bulk 每批几 MB。⑤ 单节点 bulk 10 万单用了 11.5 秒。
    • 更新 = 删除 + 新增改一单的状态，旧版本在 segment 里标记删除，新版本写进新 segment，合并时才真正清掉。订单状态变化频繁时，索引里会有不少“已删除”的文档，看 _cat/indices 的 docs.deleted。

    自测

    1. 用一句话说出这一页的精华

    ES 先分词、再记“词 → 哪些文档”（倒排索引），专门用来“找”；它按 _id 把文档路由到分片，写入先进内存缓冲和 translog，每秒 refresh 成一个不可变的 segment 才能搜到，搜索先查各分片的前 N 名再取内容；它是订单库之后的一份近实时副本，只负责找，不负责做决定。

    2. MySQL 的 LIKE '%键盘%' 疼在哪？

    前缀是通配符，B+ 树按值排序帮不上，只能全表扫；没有相关度；分片以后还要每张表各扫一遍。

    3. 坑 4（写完搜不到）的根源是 ④ 的哪条？为什么 ES 不做成写完立刻可见？

    机制 4：文档先进内存缓冲，refresh（默认 1 秒）才生成能搜的 segment。segment 不可变，每写一条就生成一个会产生海量小 segment，搜索和合并都扛不住，所以攒一秒写一个。

    4. 预测：把 orders 的主分片从 3 个改成 6 个（不重建），会发生什么？

    不允许直接改（主分片数是建索引时定的）。假设能改，hash(_id) % 6 和 % 3 的结果不同，大部分文档按新公式应该在别的分片，按 id 取文档会找不到。所以只能 reindex，或者用 _split 拆成 3 的整数倍（每个旧分片拆成两个，文档位置可推算）。

    5. 预测：商家查询改成 "from": 9990, "size": 20，会怎样？如果 3 个分片换成 30 个，同样 from: 9000, size: 20，协调节点要处理多少条？

    第一个：from + size = 10010 > 10000，直接 400。第二个：每个分片交出 9020 条的文档号和排序值，30 个分片共 27 万条在协调节点归并，只为 20 条：和订单库跨片分页同一个问题，分片越多越贵。

    6. 放回全景：第 11 站前后各发生了什么？ES 的 refresh 被人误设成 30 s，商家会看到什么？

    之前：第 10 站 Canal 把 binlog 转成消息，同步程序 bulk 写进 ES；之后：第 9 站商家后台查到订单号，再回 MySQL 取详情。refresh 30 s：同步链路照常，但写进去的订单最多要 30 秒才搜得到，商家看到“新订单迟迟不出现”；排查时会先怀疑 Canal 和 Kafka 延迟，其实同步早就完成了，卡在 ES 的可见性上。

    档位：标准。本机跑过（2 核 ARM 虚拟机，JDK 17，Elasticsearch 9.5.5 单节点容器，堆 1 GB）：⑤ 的七组实验各跑 1 次，nrt 3 跑了 3 次；页面上的分片文档数、分词结果、命中数、可见延迟、报错信息都来自这些输出。倒排索引演示台是简化模拟（node 里跑过，分词结果和 _analyze 实测对过）。坑 5、6 按文档和机制推演。

    按文档（Elasticsearch 9.x）：index.refresh_interval 默认 1 s，index.search.idle.after 默认 30 s（实测 include_defaults 也是这两个值）；index.max_result_window 默认 10000；index.translog.durability 默认 request；文档路由 shard = hash(_routing) % 主分片数，_routing 默认 _id；默认打分 BM25；主分片数建索引后不能改，可用 _split / _shrink / reindex。
