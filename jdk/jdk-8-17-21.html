从 8 到 25，Java 改了什么、为什么改

8、17、21、25 不是四个孤立的版本，而是一条线上的四个长期支持（LTS）站点：17 包含了 9 到 16 的全部改动，21 包含 18 到 20，25 又包含 22 到 24。这些改动可以归成四条主线：写代码更省事（record、模式匹配）、并发更便宜（虚拟线程）、GC 停顿更短（G1、ZGC）、平台更好维护（模块和强封装，删掉旧东西）。前三条是升级的好处，第四条是升级时踩坑的来源。21 到 25 这一段，主要是把虚拟线程补完整、让启动和内存更省。25 之后，27 是 2026 年 9 月的普通版本，下一个长期支持版计划是 2027 年 9 月的 29（③ 末尾）。

假设场景团队的老服务还跑在 JDK 8 + Spring Boot 2 上，新项目要上 Spring Boot 3，它最低要 JDK 17；新同事写的代码里出现了 record、var、switch 里的 ->；面试也常问“8 到 17 有什么变化”；2025 年 9 月又出了新的长期支持版 25。本页按你的要求没有在本机运行任何代码，版本和行为都按 JEP、OpenJDK 源码和发行商文档核对，代码示例标了“未在本机运行”。

①为什么学：四个版本，跨了十一年

8 是 2014 年的，25 是 2025 年的。中间 Java 换了发布节奏，每半年出一个版本，每两三年挑一个做长期支持。

工作要用

Spring Boot 3 和 4 最低都要 JDK 17（Boot 4.1.2 的 class 文件版本是 61，即 17）。官方文档写明 Boot 3.5 支持到 25、Boot 4.1 支持到 27。

看得懂新代码

record、sealed、switch 模式匹配、文本块、var、虚拟线程，在 8 上全都不存在；25 又多了 ScopedValue、void main()。

升级不出事故

升级时 JVM 起不来、反射报错、类找不到，大多来自“平台治理”这条线。知道它为什么改，就知道去哪改。

②老办法：留在 JDK 8，靠第三方库补

很多团队就是这么过来的：语言缺什么，就引一个库补上。能做，但有几样补不上。

疼在哪

库能补的是 API 和语法糖；补不上的是要改编译器、JVM、类库内部的东西：编译器检查、线程实现、GC、字符串的内存布局。还有一样最实际：框架生态已经往前走了。

所以升级的精华：拿到只有平台自己能做的改进，同时还清“平台治理”这条线欠下的账。

典型误用以为升级就是换个 JDK 安装包、改一下 JAVA_HOME。8 到 17 中间有一整段“删旧东西、关后门”的改动（模块强封装、删 Java EE 模块、删 CMS 和老 GC 参数），不知道它们为什么删，就只能见一个错改一个（⑥ 第一圈）。

③选谁：长期支持版怎么挑

生产只用长期支持版（LTS），中间版本只有半年的更新。LTS 不是语言规范里的概念，是各家发行商（Oracle、Eclipse Temurin、Amazon Corretto、阿里 Dragonwell 等）承诺给这个版本出几年补丁。

选择规则：新项目优先 25（支持期最长，虚拟线程的钉住问题也解决了），某个关键依赖还不支持 25 就用 21；要用 Spring Boot 3 / 4 的至少 17；老项目卡在 8 的，跳过 11 直接规划到 17、21 或 25，因为 9 到 17 的坑反正都要过一遍。本页学 8 → 17 → 21 → 25 这一段改了什么、为什么，最后简单看一眼 25 之后的 27 和 29。

25 之后：27 和 29

27：最新版本，但不是 LTS

2026 年 9 月 15 日发布，只维护到 28 出来（约半年），生产一般不用。它和 26 加起来，值得知道的是这几样：

  • G1 在任何环境都是默认 GC（27，JEP 523）：以前 1 个 CPU 或内存小于 1792 MB 时会自动选 Serial，小容器里尤其常见。
  • 紧凑对象头默认打开（27，JEP 534）：25 里要手动开，27 起对象头默认就是 8 字节。
  • JDK 自带的 HttpClient 支持 HTTP/3（26，JEP 517）；TLS 1.3 加了抗量子的混合密钥交换（27）。
  • 反射改 final 字段会打警告（26，JEP 500），以后会直接报错：强封装的下一步，靠反射改 final 字段的序列化、注入框架要注意。
  • 结构化并发到 27 还是预览（第 7 次），还没转正。

29：计划中的下一个 LTS

Oracle 的支持路线图把 29 标为下一个长期支持版，计划 2027 年 9 月发布，并注明 27～29 的 LTS 安排和日期都可能调整。目前 28 还在开发中，29 的特性列表还没有公布。

能确定的只有一点：29 会包含 26～28 的全部改动。上面 27 这几样到时都会进来；现在还在预览的结构化并发、Lazy Constants（原 Stable Values）、原始类型模式能不能在 29 转正，要等它的特性列表定下来，本页不做猜测。

④原理：一种发布方式，四条主线

先看 Java 现在怎么出版本（这决定了 8、17、21、25 的关系），再看 8 到 25 的改动分成哪四条线、每样新东西是为了解决什么问题，最后看几处“为什么非这样设计不可”，其中机制 5 专讲 21 到 25 这一段。

先知道这些

JDK、JRE、JVM

JVM 执行字节码；JRE = JVM + 类库；JDK = JRE + javac 等工具。9 起官方不再单独发 JRE，用 jlink 按需裁一个运行时。

JEP

JDK Enhancement Proposal，每个新特性的提案和编号，比如 JEP 444 是虚拟线程。本页的“哪个版本”都按 JEP 写的目标版本。

预览特性

先放进版本里让大家试，编译和运行都要加 --enable-preview，下个版本可能改、也可能删。转正之后才算数。

LTS

发行商对某个版本的长期补丁承诺，不是语言特性。11、17、21 和 8 在语言上没有“特殊”，只是补丁出得久。

地基8 之前：5、6、7 只记这几样今天还在起作用的

（堆、栈、元空间这些“内存放在哪”的问题见 JVM 内存结构，和这里说的“内存模型”是两回事。）6、7 不单独做对比：主流的免费发行版早就不再给它们出更新，Spring Boot 2.0 起最低就要 8。但 8 以后的很多东西是盖在下面这几样上的，Java 内存模型其实是 5 定下的。

JDK 5（2004）

  • Java 内存模型（JSR 133）：规定多线程下一个线程的写，另一个线程什么时候、按什么顺序能看到（happens-before），volatile、synchronized、final 的语义都由它定义。AQS、ConcurrentHashMap、虚拟线程都建立在它上面；9 的 VarHandle 又补了更细的内存顺序。详见 Java 内存模型。
  • java.util.concurrent（JSR 166）：线程池、Lock、原子类、并发集合。见 AQS、线程池。
  • 泛型、注解、枚举、自动装箱：Spring、MyBatis 的注解驱动都从这来。

JDK 6（2006）

  • synchronized 的锁优化：HotSpot 加入偏向锁和自适应自旋，和已有的轻量级锁一起，构成面试常问的“锁升级”，让没有竞争的 synchronized 几乎不花钱。偏向锁在 15 默认关闭，18 起参数作废，19 起再写这个参数 JVM 就起不来（⑥ 坑 1）。
  • JDBC 4.0：数据库驱动靠 ServiceLoader 自动注册，不用再写 Class.forName。
  • 脚本引擎 API（JSR 223）：后来的 Nashorn 就挂在它下面，15 被删。

JDK 7（2011）

  • invokedynamic（JSR 292）：把“调用哪个方法”推迟到运行时再决定的字节码指令。8 的 lambda 就是靠它实现的，不再为每个 lambda 生成一个匿名内部类的 class；9 的字符串拼接也改用了它。
  • Fork/Join：带工作窃取的 ForkJoinPool。8 的 parallelStream、CompletableFuture 的默认线程池、21 虚拟线程的调度器，用的都是它。
  • try-with-resources、<> 菱形、multi-catch、switch 字符串；NIO.2 的 Path、Files。字符串常量池从永久代挪到堆，为 8 删永久代铺了路。

机制 1发布方式：从“等大特性”到“半年一班车”8、17、21、25 的关系由它决定

以前：版本等最大的那个特性到 JDK 9 为止

现在：每半年发一班车从 JDK 10 起

决定这个设计的约束：大特性的完成时间没法预测。绑在一起发，小改进跟着等；拆成定期发车，每个特性单独上车，语言新语法还能先以“预览”身份收反馈。后果有两个：一是 17、21、25 只是其中几班车，17 = 8 + 9～16 所有班车的内容，21 = 17 + 18～20，25 = 21 + 22～24；二是不少特性在中间版本里已经出现过预览，到 LTS 才转正（record 14、15 预览，16 转正）。

机制 3为什么是 record + sealed + 模式匹配，而不是 Lombok设计对比

  • Lombok 的 @Data 是在编译时改语法树，生成的是普通类：编译器不知道它“只是数据”，没法拿它做解构，更没法做穷尽检查。它还要用 javac 的内部 API，所以每次升级 JDK 都要跟着升 Lombok（⑥ 第三圈）。
  • Visitor 模式也能保证“每种都处理到”，但要给每个类型加 accept 方法，新增一种操作要改所有类。
  • record 是语言层面的声明：字段就是全部状态、不可变，所以模式匹配能安全地把它拆开（case Paid(var id, var cents)）。
  • sealed 告诉编译器“就这几种”，switch 模式负责按类型分支。三样拼在一起，就是函数式语言里的代数数据类型：新增一种情况时，编译器把所有该改的地方列出来。

机制 521 → 25：有了虚拟线程，为什么还要 ScopedValue设计对比

21 让线程变便宜，一个请求开几十个子任务成了常态。ThreadLocal 是为“少量、长寿、池化”的平台线程设计的，放到“海量、短命、层层派生”的虚拟线程上，三个毛病一起放大。

ThreadLocal：每个线程一份可变副本

ScopedValue：一段作用域里的只读绑定

决定这个设计的约束：线程数从几百涨到上百万，而且父子任务层层派生。可变、无限寿命、继承时复制，这三点在少量平台线程上无所谓，在海量虚拟线程上就变成了内存和正确性问题。ScopedValue 的答案是只读、限定作用域、共享不复制。它和结构化并发（25 仍是预览）是一对：子任务的生命周期不超过父任务，父任务绑定的值就能安全地给所有子任务共享。注意只有 StructuredTaskScope 里 fork 出来的子任务会继承绑定，普通线程池、executor 开的线程读不到（⑥ 坑 12）。ThreadLocal 没被弃用，池化平台线程上的缓存类用途照样可以用。

坑 1换上新 JDK，JVM 直接起不来← ④ 机制 2 GC 线
现象
Unrecognized VM option 'PrintGCDateStamps'，接着 Error: Could not create the Java Virtual Machine.
根源
9 起 GC 日志统一成 -Xlog，PrintGCDateStamps 这类老参数被删；UseCGroupMemoryLimitForHeap 在 11 里已不认识；CMS 在 14 被删时只是警告并忽略，15 起 -XX:+UseConcMarkSweepGC 也成了不认识的参数（按 jdk11u、14u、15u 的 arguments.cpp 核对）。偏向锁的 -XX:+UseBiasedLocking、-XX:BiasedLockingStartupDelay=0 在老的调优脚本里很常见：15 弃用、18 作废、19 起不认识（jdk17u 的过期表）。而 MaxPermSize 只打警告，不影响启动。

坑 12线程池里的任务读不到 ScopedValue← ④ 机制 5
现象
把 ThreadLocal 换成 ScopedValue 后，提交到线程池或 executor 的任务里 USER.get() 抛 NoSuchElementException。
根源
绑定只在 where(…).run(…) 这条调用链上有效，只会被结构化并发里 fork 出来的子任务继承。普通线程池的线程活得比这段作用域还久，所以故意不继承。
做法
要传给线程池任务的值显式当参数传（⑤ 的写法）；等结构化并发转正后，用 StructuredTaskScope 派生子任务。读之前不确定有没有绑定，用 isBound() 判断。

第三圈

更深一层

为什么每升一次 JDK，Lombok 都要跟着升

Lombok 不是普通的注解处理器：标准注解处理器只能生成新文件，不能改已有的类；Lombok 要在你的类里加 getter，只能拿到 javac 内部的语法树直接改。javac 的内部 API 不保证兼容，加上 16、17 的强封装，每个新 JDK 都可能让旧 Lombok 失效。record 是语言自己提供的，不存在这个问题。

默认 GC 换了，升级后要看什么

  • 8 默认 Parallel（吞吐优先），9 起默认 G1（停顿优先）。同样的堆，升级后吞吐可能略降、停顿明显变短，压测要两样都看。
  • 21 的 ZGC 要分代的话，得加 -XX:+UseZGC -XX:+ZGenerational；23 起分代成了默认，24 删了不分代的模式，25 上 ZGenerational 只打警告、被忽略（jdk25u 源码核对）。
  • 25 的紧凑对象头默认不开，要加 -XX:+UseCompactObjectHeaders，对象多而小的服务值得压测对比一下堆占用；27 起默认打开。
  • 25 及以前，容器里 JVM 只拿到 1 个 CPU、或内存小于 1792 MB 时，会自动选 Serial GC，规格太小的 Pod 要显式指定 GC；27 起（JEP 523）不管机器多小都默认 G1。

为什么 17 和 21 都要“删东西”

每一样留在 JDK 里的东西都有维护成本：CMS 拖累 GC 代码重构，SecurityManager 让每个敏感操作都要多一层权限检查，Nashorn 要追 JS 标准。Java 的承诺是“公开 API 尽量兼容”，所以删之前都会先弃用、打警告，给几个版本的缓冲。升级时看一眼 jdeprscan 的输出，就能提前知道下一次会坏什么。

17 → 21、21 → 25，各值不值得升

语言上主要是模式匹配补齐了（record 模式、switch 模式），API 上是 SequencedCollection；真正的分量在运行时：虚拟线程和分代 ZGC。如果服务是“大量阻塞 IO + 线程池不够用”，或者大堆、对停顿敏感，21 的收益最直接；如果都不是，17 → 21 的升级风险也很小（主要是坑 5、7、8，外加用了 SecurityManager 的会在 18 起报错）。21 → 25 是“把虚拟线程补完整”：synchronized 不再钉住、ScopedValue 转正，外加 AOT 缓存和紧凑对象头省启动时间和内存，支持期也最长（到 2031 年）；要处理的主要是坑 9～11。

练习 3 · 先猜，再看线程数

把 8 版的 1000 个查询（每个阻塞 1 秒）分别用固定 200 线程池和 21 的虚拟线程跑，先猜两者大约各要几秒。

用到：坑 8、三高 · Little 定律

1. 用一句话说出 8、17、21、25 的关系和升级的精华。

它们是半年一班车里的四个长期支持站点，17 包含 9～16、21 包含 18～20、25 包含 22～24 的全部改动；升级拿到的是只有平台能做的改进（编译器检查、虚拟线程、GC、字符串布局），要还的是“平台治理”那条线的账（强封装、删模块、删旧参数）。

2. 留在 JDK 8 靠第三方库补，痛在哪？

库只能补 API 和语法糖，补不了要改编译器、JVM、类库内部的东西（穷尽检查、虚拟线程、新 GC、压缩字符串）；而且 Spring Boot 3 / 4 最低要 17，框架生态已经往前走了。

4. 预测：JDK 8 的服务，启动脚本里有 -XX:+UseConcMarkSweepGC -XX:MaxPermSize=256m，直接换 JDK 14 和 JDK 17 各会怎样？

14：两个参数都只打“Ignoring option …”警告，JVM 照常启动，GC 悄悄变成默认的 G1。17：CMS 参数在 15 起已经不认识，JVM 报 Unrecognized VM option 起不来；MaxPermSize 仍只是警告。

5. 预测：sealed interface Shape permits Circle, Square，某处 switch 写了 default -> 0。后来加了 Triangle，这个 switch 会怎样？

照样编译通过，Triangle 走进 default 返回 0，悄悄算错。写了 default，编译器就认为你已经处理了“其他所有情况”，穷尽检查帮不上忙。这就是第二圈说“不写 default”的原因。

6. 预测：一个小工具在中文 Windows 上用 new FileReader("a.txt") 读 GBK 编码的文件，JDK 8 和 JDK 21 上结果一样吗？

不一样。8 上默认编码跟系统走（GBK），能正常读；21 上默认是 UTF-8（18 起），读 GBK 文件会乱码。显式指定编码就两边一致。

8. 预测：Maven 项目把 Lombok 只写在 dependencies 里（scope 是 provided），分别用 JDK 21 和 25 编译会怎样？

21：照常编译，只多一条 Note，提醒以后可能默认不跑类路径上的注解处理器。25：Lombok 不会被执行，所有靠它生成的 getter、构造器都不存在，编译报找不到符号。写进 annotationProcessorPaths 两边都正常。

9. 预测：在 ScopedValue.where(USER, "u-42").run(…) 里，用 newVirtualThreadPerTaskExecutor 提交一个任务，任务里调 USER.get() 会怎样？换成 21 的写法、用 InheritableThreadLocal 呢？

ScopedValue：抛 NoSuchElementException，executor 开的线程不继承绑定，只有结构化并发 fork 的子任务继承。InheritableThreadLocal：能读到，因为新建线程时把父线程的值整份复制了一份；这正是机制 5 说的“海量线程时代太贵、也难推理”的那种行为。

10. 预测：同一个服务开着虚拟线程，代码里 synchronized 包着一次 JDBC 查询，分别跑在 21 和 25 上，高峰时有什么区别？

21：阻塞时载体线程被钉住，载体线程数等于 CPU 核数，几个慢查询就能让所有虚拟线程都跑不了。25：24 起 synchronized 里阻塞也能卸载，不会整体卡住；但并发查询数照样受连接池限制，排队还是会发生。

11. 预测：一个 1 核、1 GB 内存的容器，启动参数里没指定 GC，跑在 JDK 21、25、27 上分别用的是哪个 GC？

21 和 25：Serial。JVM 判断这不是“服务器级”机器（只有 1 个 CPU，内存也小于 1792 MB），不选 G1。27：G1，JEP 523 去掉了这条判断，任何环境都默认 G1。三个版本上只要显式写了 -XX:+UseG1GC 或别的 GC，就都按你写的来。

12. 预测：JDK 8 时代的调优脚本里有 -XX:BiasedLockingStartupDelay=0，拿到 17 和 21 上各会怎样？

17：打一行弃用警告，照常启动（偏向锁 15 起默认关，这个参数也没什么用了）。21：19 起这个参数已不认识，JVM 报 Unrecognized VM option 起不来。和 CMS 参数是同一个套路：弃用 → 作废只警告 → 过期就报错。
