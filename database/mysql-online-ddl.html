orders 加一列，支付接口全卡住了：表结构设计与大表变更（Online DDL）

改表难的地方不在“改”，在两件事：改的时候还能不能写，以及开工前后那一下要独占整张表。MySQL 8 的 ALTER 有三种做法：只改表定义的 INSTANT、在 InnoDB 里边改边记增量的 INPLACE、一行行抄到新表的 COPY。哪怕是 35 ms 就做完的 INSTANT，也要先拿到表上的元数据锁；前面有一个没提交的事务，它就得等，后面所有读写跟着它一起等。实测一个没提交的 SELECT 加一条 INSTANT 加列，让 40 个付款和查询请求每个都等了 4 秒多（最慢 4.75 s），而 ALTER 自己只要 35 ms。到了从库，DDL 还要从头再做一遍。

①为什么需要：表要改，付款不能停

全景里那条付款 UPDATE 不碰表结构，它默认 orders 一直是那几列。可业务会变：优惠券上线要加 coupon_id，运营要按下单时间查要加索引，某个字段当初建小了要改类型。交易靶场的 orders 有 100 万行，线上同类的表常常是几千万行。改表这段时间里，每 20 ms 就有一笔付款要写这张表，从库也在给订单页供读。

所以这一页讲两件事：一是建表时把类型选对，很多改表本来不必发生；二是不得不改时，怎么改才不卡业务、不拖从库。

②没有它会怎样：抄一张新表，抄完之前不许写

MySQL 5.5 以前，几乎所有 ALTER 都是一个做法：建一张新结构的空表，把旧表一行行抄过去，再换名字。抄的这段时间里旧表只能读，不能写。今天 8.4 里这个做法还在，叫 ALGORITHM=COPY，改列类型时只能用它。

缺的那一块：改表的这段时间里，新进来的写得有地方去，要么记下来回头补到新表（INPLACE 的 row log、gh-ost 的 binlog），要么压根不碰数据只改定义（INSTANT）。不懂这一点的典型误用：听说 8.0 支持 Online DDL，就以为 ALTER 都不锁表，在高峰期直接跑 MODIFY 改类型，结果整段时间写全卡。或者知道它不锁表，却没想到它开工前要等所有用过这张表的事务结束（④-3）。

③相邻方案：在库里改，还是在库外改

同一个需求有五种做法。前三种是 MySQL 自己的 ALGORITHM，一条 ALTER 做完；后两种是外部工具，在库外建一张影子表，用一堆普通的小 DML 把数据搬过去。

做法改的是什么期间能写吗主库耗时（100 万行，实测）从库
INSTANT只改数据字典里的表定义，不碰一行数据能31～35 ms几乎不落后
INPLACE在 InnoDB 里建索引或重建表，期间的写记进 row log 回头补多数能（LOCK=NONE）加索引 3.8～4.3 s，重建表 7.2～8.6 s主库做完才开始做，落后约同样久
COPYserver 层逐行抄进一张新表不能，只能读11.0～11.5 s同上

选择规则：先问能不能 INSTANT（加列、删列、改名、改默认值），能就直接做；不能时看表多大、从库能接受落后多久：几百万行以内、落后几秒能接受，用 INPLACE；表很大、或者从库延迟要压在一两秒以内，用 gh-ost。COPY 只在别无选择时用，并且放在低峰期。本页学 MySQL 自己的三种算法和元数据锁，gh-ost 的原理放在 ④-5 对照。

④原理：改定义、边改边记、整张抄

先看建表时的每个选择将来要付什么代价，再看三种算法各自碰了哪些东西，然后是改表最容易出事的那把锁，最后看 DDL 到了从库会怎样，以及外部工具为什么要绕开这条路。

先知道这些
  • InnoDB 的表就是一棵按主键排序的 B+ 树（聚簇索引），整行数据都在叶子页里；二级索引另外一棵树，叶子里存主键。详见索引与 B+ 树。
  • 元数据锁（MDL）：保护表定义的锁，和行锁是两回事。任何读写一张表的语句都先拿这张表的共享 MDL，在事务里拿到的要到事务结束才放；ALTER 要拿排他 MDL。事务、MVCC 与锁里提过一句，这页讲透。
  • DDL 会隐式提交：执行前先把当前会话没提交的事务提交掉，自己也不能回滚。在 binlog 里它是一条语句（Query 事件），不是行事件。

④-2 三种算法：碰到哪一层

ALTER TABLE … ALGORITHM= 后面能写三个值。区别在于这次改动碰到了哪一层：只碰数据字典（表定义），还是要在 InnoDB 里重写 B+ 树，还是要经过 server 层一行行抄。不写 ALGORITHM 时，MySQL 按 INSTANT → INPLACE → COPY 的顺序挑第一个支持的。

INSTANT 能和行数无关，是因为它把“补默认值”推迟到了读的时候：数据字典里记着这张表经历过几次加列删列（行版本），新写的行在行头里带上版本号，读到老版本的行时按定义补上缺的列。代价是每张表最多攒 64 个版本，⑤ 实测第 65 次报 4092；重建一次表就清零。

INPLACE 的关键是 row log（在线变更日志）：建新树要好几秒，这几秒里付款照常写旧表，InnoDB 把这些改动另外记一份，新树建完后补进去，最后短暂独占一下表再把剩下的补完、切换过去。row log 有上限 innodb_online_alter_log_max_size（默认 128 MB），写得太猛、超了，整条 DDL 失败回滚（⑥ 坑 5）。

④-3 元数据锁：开工和收尾要独占一下

不管哪种算法，ALTER 都要改表定义，改的那一刻不能有别人正拿着旧定义在读写。所以它的元数据锁分三段：开始时拿共享可升级（SHARED_UPGRADABLE，别人照常读写），收尾时（INPLACE 开头准备时也有一下）升级成排他（EXCLUSIVE）。排他锁要等这张表上所有已经授予的共享锁都放掉，而事务里拿到的共享锁要到事务结束才放。

为什么后来的读写不能插队？如果共享锁可以一直插到排他请求前面，一张热表上永远有人在读写，ALTER 就永远拿不到锁（饿死）。MySQL 选择让排他请求优先，代价就是它等待的这段时间里整张表停摆。所以真正危险的不是 ALTER 慢，而是它等：等多久由前面最长的那个事务决定，lock_wait_timeout 默认是 31536000 秒，也就是一年。

解法写在锁的规则里：既然排队的时长等于 ALTER 等锁的时长，那就给 ALTER 设一个很短的 lock_wait_timeout，等不到就放弃、过一会儿重试，把“全表停摆”压成每次最多一两秒（⑤ 实测最慢 0.71 s）。开工前先查有没有长事务（information_schema.INNODB_TRX），更是省事。

④-4 到了从库：主库做完，从库从头再做一遍

DDL 在 binlog 里是一条语句。从实测看，它在主库执行完以后才到从库：COPY 改类型在主库用了 11 s，主库做完后，从库又过了 11.5～12.4 s 才放完。从库用 applier 把这条 ALTER 原样再执行一遍，于是两段时间首尾相接：

INSTANT 在从库上同样是几毫秒，所以没有这个问题（⑤ 实测从库晚 1～2 ms）。INPLACE 和 COPY 在从库上要多久，主库上就差不多多久。复制页里大事务的那条规律在这里又出现了一次：一个不可分的大单元，从库只能整段重放。

④-5 为什么这样设计：一条 DDL，还是一万个小 DML

既然 INPLACE 在主库上已经能边改边写，为什么还有人用 gh-ost 这种外部工具？

库内 Online DDL MySQL 自带

  • 一条语句，引擎内排序、批量建树，最快；不用装工具、不用额外权限。
  • row log 只记变更，主库上写几乎不受影响（⑤ 实测付款最慢 40～62 ms）。
  • 在 binlog 里是一个不可分的单元：从库要整段重放，落后的时间等于执行时间。
  • 开始了就停不下来、调不了速，只能 KILL 掉回滚、从头再来。

gh-ost 库外，影子表

  • 建一张新结构的影子表 _orders_gho，按主键分块（默认每块 1000 行）把旧行抄过去；增量伪装成从库读 binlog 回放过去。
  • 每一块都是普通的小事务，从库正常复制；可以按从库延迟自动限流、随时暂停。
  • 比库内慢；要 ROW 格式、FULL 行镜像的 binlog，额外的连接和磁盘；不支持外键和触发器。
  • 最后切换（cut-over）还是要短暂锁表、RENAME，前面有长事务一样会等。

决定胜负的约束：复制按 binlog 里的单元重放，单元有多大，从库就要卡多久。库内 DDL 的单元是整条 ALTER，gh-ost 把它拆成成千上万个小单元，用总耗时更长，换从库延迟可控、过程可暂停。表小、从库延迟能接受时库内 DDL 赢；表大、读写分离对延迟敏感时 gh-ost 赢。两边共同的弱点是那一瞬间的排他锁，所以 ④-3 的规矩（短超时 + 重试、先查长事务）在两边都要守。

最少的写法

改表前后的几条命令（8.4）显式写 ALGORITHM 和 LOCK：做不到就报错，不会悄悄退化成 COPY
-- 1. 开工前：有没有长事务？
SELECT trx_mysql_thread_id, trx_started, NOW() - trx_started AS secs
  FROM information_schema.INNODB_TRX ORDER BY trx_started LIMIT 5;

-- 2. 等不到锁就放弃，不要让整张表陪着等
SET SESSION lock_wait_timeout = 2;

-- 3. 显式指定算法
ALTER TABLE orders ADD COLUMN coupon_id BIGINT NULL, ALGORITHM=INSTANT;
ALTER TABLE orders ADD INDEX idx_created (created_at), ALGORITHM=INPLACE, LOCK=NONE;
ALTER TABLE orders MODIFY qty BIGINT NOT NULL, ALGORITHM=COPY;          -- 只能这样：期间不能写

-- 4. 卡住了：谁在等、谁挡着
SELECT waiting_pid, waiting_query, blocking_pid, sql_kill_blocking_connection
  FROM sys.schema_table_lock_waits;

row log 上限、建索引的并行线程、gh-ost 的参数、行版本用完怎么办，这些细节放到 ⑥。

五件事一眼可见：

  • INSTANT 加列、VARCHAR 小扩长都是几十毫秒以内，和 100 万行无关，从库也几乎不落后。
  • INPLACE 建索引、重建表要几秒，但期间 135～257 笔付款照常完成，最慢 62 ms（平时最慢 17 ms）。
  • 可从库在主库做完以后又花了 3～6 秒才放完，这几秒里订单页读从库看到的都是旧状态。

第一圈 · 注意事项

坑 1一条 35 ms 的 ALTER，让整张表停摆← ④-3 排他锁优先，后来的都排队实测
现象
白天发了一条“肯定很快”的加列，接口大面积超时，连接池被占满，监控里一片 Waiting for table metadata lock。实测 40 个请求每个等了 4.2～4.8 s。
根源
ALTER 的排他锁在等一个没结束的事务；为了不让 ALTER 饿死，后来的共享锁请求都排在它后面。等多久取决于最长的那个事务，lock_wait_timeout 默认一年。
做法
改表前查 INNODB_TRX 里有没有长事务；会话里 SET lock_wait_timeout=1～3，失败就重试（实测最慢降到 0.71 s）；已经堵上了，查 sys.schema_table_lock_waits，先 KILL 掉那条 ALTER 就能立刻放行，再处理长事务。
坑 2以为 Online DDL 都能写← ④-2 改类型只能 COPY实测
现象
“8.0 支持在线改表”，于是高峰期跑了 MODIFY qty BIGINT，11 s 里付款一笔都写不进去；或者把 VARCHAR(50) 扩到 VARCHAR(100)，以为只改定义，结果是 COPY。
根源
改类型要把每一行重新编码，InnoDB 不支持就地做；VARCHAR 的长度前缀在 255 字节处从 1 字节变 2 字节，跨过去也要改每一行。
做法
永远显式写 ALGORITHM=INSTANT 或 ALGORITHM=INPLACE, LOCK=NONE：做不到时直接报 1846，而不是悄悄退化成 COPY。报错了再决定是低峰期 COPY 还是上 gh-ost。
坑 3主库几秒做完，从库落后同样久← ④-4 从库整段重放实测
现象
主库加索引“只卡了 50 ms”，大家很满意；接下来几秒（大表是几十分钟）订单页读到的全是旧状态，读写分离的路由层可能把从库判成不健康。
根源
DDL 在 binlog 里是一条语句，主库做完才到从库，从库再做一遍；一条 DDL 不能拆给多个 worker。
做法
表大、延迟敏感就用 gh-ost（按 --max-lag-millis 限流）；或者先在从库上逐台做（关掉 sql_log_bin），最后切主再做旧主库。改表期间把延迟大的从库摘出读流量（复制页坑 2）。
坑 4INSTANT 第 65 次突然报错← ④-2 行版本最多 64 个实测
现象
一张经常加列删列的表，某次发版的 ALGORITHM=INSTANT 报 4092 Maximum row versions reached；不写 ALGORITHM 的话不报错，却悄悄重建了整张表。
根源
每次 INSTANT 加列、删列都让行版本 +1，8.4 上限 64（9.1.0 起 255）；只有重建表能清零（实测重建后回到 0）。
做法
监控 information_schema.INNODB_TABLES.TOTAL_ROW_VERSIONS，接近上限时找低峰期 OPTIMIZE TABLE 或 INPLACE 重建一次。
坑 5建了一小时的索引，最后回滚了← ④-2 row log 有上限手册
现象
大表 INPLACE 加索引，期间正好有大促或批量任务猛写，DDL 跑到最后失败，前面的工夫全白费。
根源
并发写记在 row log 里，超过 innodb_online_alter_log_max_size（默认 128 MB）就报 DB_ONLINE_LOG_TOO_BIG，整条 DDL 回滚。
做法
避开写高峰；预估这段时间的写入量，必要时临时调大这个参数（它也决定了收尾时要补多少、锁多久）；超大表直接上 gh-ost。
坑 6上了 gh-ost，切换那一下还是卡了← ④-5 外部工具也要排他锁文档
现象
数据抄了两小时都很平稳，最后 cut-over 时接口抖了几秒，或者反复重试切不过去；有外键、有触发器的表，gh-ost 直接拒绝。
根源
切换要锁住原表再原子 RENAME，同样要等长事务；锁等待超过 --cut-over-lock-timeout-seconds（默认 3 s）就放弃重试。gh-ost 文档写明不支持外键和触发器；pt-online-schema-change 自己就靠触发器，外键要用 --alter-foreign-keys-method 另外处理。
做法
切换选低峰，切之前同样查长事务；能 INSTANT 的改动别上工具（工具总要把整张表抄一遍）。

第三圈 · 优化和深处

深 1INSTANT 凭什么不碰数据手册 + 实测

8.0.29 起，INSTANT 加列和删列都记在数据字典里，每做一次表的行版本 +1。之后新写的行带着当时的版本号；读到旧版本的行时，InnoDB 按字典补上缺的列（默认值），或者跳过已经删掉的列。所以一行数据可能几年都是老格式，直到它被更新或者表被重建。它的边界都来自“老格式的行要能被读懂”：上限 64 个版本（9.1.0 起 255），ROW_FORMAT=COMPRESSED、有 FULLTEXT 索引的表、临时表不支持，加列后行大小超限也会拒绝。

深 2INPLACE 建索引的三段：扫、排、建手册

先扫一遍聚簇索引取出 (created_at, id)，按新索引的键排序，再从叶子往上批量建树，比一条条插入快得多；最后把 row log 里攒下的并发改动补进去。8.0.14 起扫描可以并行（innodb_parallel_read_threads，默认按逻辑 CPU 数 / 8、至少 4），8.0.27 起排序和建树可以并行（innodb_ddl_threads 默认 4，innodb_ddl_buffer_size 默认 1 MB，每个线程分一份）。虚拟列上的索引、全文索引、空间索引不走并行。调大它们能缩短主库时间，从库重放也会跟着快一点，但从库落后的本质（整段重放）不变。

深 3gh-ost 怎么把一条 ALTER 拆开文档

gh-ost 先建一张新结构的空表 _orders_gho，再同时做两件事：按主键范围一块一块地把旧行抄过去（--chunk-size 默认 1000 行）；伪装成从库读 binlog，把这段时间里的增删改回放到影子表（所以要求 ROW 格式、FULL 行镜像）。每一块都是普通的小事务，从库照常复制；从库延迟超过 --max-lag-millis（默认 1500）就暂停抄写。追平以后做 cut-over：一个连接锁住原表，另一个连接发原子 RENAME 把两张表对调，锁等待超过 --cut-over-lock-timeout-seconds（默认 3 s）就放弃重试。和 pt-online-schema-change 的差别在于增量怎么来：pt-osc 在原表上挂 AFTER INSERT/UPDATE/DELETE 三个触发器，每笔业务写都要同步多写一次影子表；gh-ost 读 binlog，业务写路径上什么都不多做。截至 2026-11，gh-ost 最新版是 v1.1.11（2026-08）。

版本和改表有关的变化

面试官会怎么问

线上大表加一个字段，你怎么做？

先看能不能 INSTANT（8.0.29 起加列、删列基本都能），能就显式写 ALGORITHM=INSTANT。不管哪种算法，开工前都查长事务，设短的 lock_wait_timeout 并准备重试，因为它们都要短暂拿排他元数据锁。要重建表的改动（改类型、改字符集）按表的大小和从库延迟要求，在低峰期 INPLACE/COPY 或者用 gh-ost。改表先于发版，加列先加可空的，代码兼容新旧两种结构。

Online DDL 会锁表吗？

分两种锁说。数据上，INPLACE 加索引期间允许读写，并发改动记在 row log 里，最后补进去；COPY 期间只能读。元数据锁上，所有算法开始和结束都要短暂拿排他锁，这时候如果有长事务，ALTER 会等，而且后面所有读写都排在它后面，这才是线上最常见的“锁表”。

执行一条 ALTER 后全站卡住，怎么排查？

SHOW PROCESSLIST 看到大量 Waiting for table metadata lock；sys.schema_table_lock_waits 看谁在等、谁挡着；information_schema.INNODB_TRX 找开了很久没提交的事务。止血最快的是 KILL 掉那条 ALTER，后面的请求立刻放行；然后找到长事务是谁开的。

gh-ost 和 pt-online-schema-change 有什么区别？

都是影子表加分块拷贝加最后换名。增量的来源不同：pt-osc 用触发器，业务每写一笔就同步多写一笔，写放大、锁竞争都在业务事务里；gh-ost 伪装成从库读 binlog 异步回放，能暂停、能按从库延迟限流，切换过程也可控，但要求 ROW 格式的 binlog，不支持外键和触发器。

主键用自增还是 UUID？

InnoDB 的表就是按主键排的 B+ 树。自增主键每次插在最右边，页填满了再开新页；随机 UUID 插在中间，频繁页分裂、页填充率低、buffer pool 命中差，而且每个二级索引里都多带一份 36 字节的主键。需要全局唯一时用趋势递增的分布式 ID（雪花之类），或者有序的 UUID（v7）存成 BINARY(16)。

对照深 3 和实验台里 gh-ost 那一档的估算

自测

1. 用一句话说出这一页的精华。

ALTER 有三种做法：INSTANT 只改定义，INPLACE 边改边把并发写记进 row log，COPY 整张抄、期间只能读；不管哪种，都要短暂拿排他元数据锁，前面有长事务它就等，后面所有读写跟着等；到了从库还要整段再做一遍。

2. 没有 Online DDL 时，改表的痛点是什么？

整张表抄一遍，期间不能写，时间和行数成正比：100 万行就要 11 s，大表是几分钟、几十分钟；只能停机窗口做，或者靠应用双写迁移。

3. 头号坑“一条很快的 ALTER 让整张表停摆”，根源是哪条原理？

④-3：ALTER 要升级成排他元数据锁，必须等已授予的共享锁全部放掉，而事务里的共享锁到事务结束才放；为了不让 ALTER 饿死，后来的读写都排在它后面。

4. 预测：会话 A 不开事务，只跑一条 30 s 的报表查询 SELECT … FROM orders，这时发 INSTANT 加列，会怎样？

照样堵 30 s。语句执行期间也持有共享元数据锁，ALTER 等它，后面的付款和查询排在 ALTER 后面。区别只是：事务里的锁到事务结束才放，单条语句的锁到语句结束就放。

5. 预测：orders 有 1000 万行，INPLACE 加索引。主库上的付款和读从库的订单页各会怎样？

主库：期间付款照常，偶尔慢几十毫秒（row log 兜着）。从库：主库做完以后，从库要再做一遍，按 ⑤ 的比例外推是 30 s 以上（数据放不进内存会更久），这期间订单页读到的是加索引之前的旧状态，后面的付款在从库排队。

6. 预测：order_no VARCHAR(20)（utf8mb4）要扩到 VARCHAR(80)，能 INPLACE 吗？扩到 VARCHAR(60) 呢？

80 × 4 = 320 字节，跨过 255，长度前缀从 1 字节变 2 字节，只能 COPY，期间不能写。60 × 4 = 240 字节，没跨，INPLACE 只改定义，几毫秒。

7. 放回全景：ALTER 在等元数据锁时，全景里那条付款 UPDATE 会怎样？这条 DDL 到了从库，第 11 站又会怎样？

第 4 站解析完要打开表，这时就要拿 orders 的 SHARED_WRITE 元数据锁，比第 6 站的行锁还早。排他请求在等，它就停在第 4 站的 Waiting for table metadata lock，第 1 站借出的连接一直不还；这样的请求一多，HikariCP 的池子被占满，连别的表的接口也借不到连接。反过来，一个 @Transactional 里慢吞吞的付款事务也能把 ALTER 挡住：它的共享锁要到第 9、10 站提交时才放。到了第 11 站，从库的 applier 拿到这条 ALTER 要从头执行一遍，后面的付款事件都在 relay log 里排队，订单页读从库看到的是旧状态。

标准档。实测 的数字来自本机：2 核 ARM，JDK 17.0.21，Connector/J 9.7.0，Docker 里两个 MySQL 8.4.13 容器（同一台机器、同一个 Docker 网络，GTID 异步复制，buffer pool 512 MB，其余默认），100 万行 orders，每个实验跑了两遍。其余来自 MySQL 8.4 参考手册（Online DDL 操作表、Online DDL 性能与并发、并行线程与内存、ALTER TABLE、日期时间类型、utf8mb3、InnoDB 限制）、mysql-server 8.4 源码（lock_wait_timeout 默认值 LONG_TIMEOUT 和 innodb_online_alter_log_max_size 默认值都取自源码），以及 gh-ost 文档（requirements-and-limitations、cut-over、command-line-flags）和 pt-online-schema-change 3.x 源码。“DDL 在主库做完后才到从库、从库只能一个线程做”在手册里没有专门的原文，是按实测和复制原理推断的。实验台里 1000 万、1 亿行的数字和 gh-ost 那一档是估算。
