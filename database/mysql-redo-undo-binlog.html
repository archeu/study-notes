commit 返回了，数据页还是旧的：redo、undo、binlog 与两阶段提交

付款提交后 120 秒，页 75 还是脏页，磁盘上的数据文件写的还是 CREATED。commit 敢返回，是因为它的承诺不落在数据页上，而落在两本顺序追加、提交时刷盘的日志上：InnoDB 的 redo，崩溃后靠它把页重做出来；server 层的 binlog，从库照着它改。改之前的旧值记在 undo 里，用来回滚和给别人读旧版本。两本日志靠两阶段提交对齐：重启时，处于 prepare 状态的事务，binlog 里有它的 Xid 就提交，没有就回滚。实测在提交途中 kill -9 了三次，三次都是这样落地的。

①为什么需要：commit 返回了，页还在内存里

在全景第 8、9 站，这一步要解决：commit() 3 ms 就返回了，等于承诺“之后不管出什么事，9527 都是 PAID”。可第 12 站实测，提交后 120 秒页 75 还是脏页，磁盘上的 orders.ibd 里写的仍是 CREATED。这时候断电，承诺靠什么兑现？同时还有两件事要办到：从库要收到同一个改动；没提交的事务改了一半，要能撤回去。

②没有它会怎样：三种笨办法

先不用日志，只用“改内存”和“写文件”两件事，看能不能兑现 commit 的承诺。

只改内存 commit 立刻返回

  • 最快，提交什么都不用写。
  • mysqld 一崩，内存里的 PAID 没了。用户手里有“支付成功”，库里是 CREATED。
  • 改了一半的事务，没处找回旧值。

提交时把页写回 force：commit 等数据页落盘

  • 崩溃后数据文件就是对的。
  • 一次付款只改了几十字节，却要随机写一整个 16 KB 的页；事务碰了 N 个页（主键、二级索引、undo）就写 N 个。
  • 页写到一半断电，磁盘上是半新半旧的“撕裂页”，谁也修不了。

两个文件各写各的 引擎记一本，复制记一本

  • 各管各的：一本用来恢复，一本发给从库。
  • 崩在两次写之间：主库有、从库没有，或者反过来。
  • 拿 binlog 做按时间点恢复，恢复出来的库和崩溃前对不上。

缺的那一块：提交时只写小的、顺序追加的日志并刷盘，页以后慢慢写（这叫 WAL：先写日志）；改之前把旧值留一份；两本日志要用同一个“这个事务算不算数”的判定。这三件事，就是 redo、undo 和两阶段提交。一次付款实测只写了约 550 字节 redo（UPDATE 232～264 字节，COMMIT 291～317 字节），是一个页的 1/30，而且是接着上一条往后写。

③相邻方案：别的系统怎么让“提交了就不丢”

都要回答同一个问题：提交那一刻，什么东西必须已经在磁盘上。

做法谁在用提交时刷盘的是代价
回滚日志 + 提交时写回数据页SQLite 默认的 rollback journal 模式数据文件本身（旧页先抄进 journal）每次提交随机写整页；适合单机、写少

④原理：三本账，一个提交

先看 redo 怎么让“页以后再写”变得安全，再看 undo 留下的旧值干什么用，然后是 server 层的 binlog，最后是把 redo 和 binlog 对齐的两阶段提交，以及崩溃后怎么对账。

先知道这些
  • 页和 buffer pool：InnoDB 按 16 KB 的页读写数据，修改都在内存的 buffer pool 里做，改过、还没写回磁盘的页叫脏页。见索引与 B+ 树。
  • write 和 fsync：write() 只把数据交给操作系统的 page cache，mysqld 崩了它还在，整机断电就没了；fsync() 返回才算真落到磁盘。fsync 慢，所以要少做、成批做。
  • 版本链：每行带着最后改它的事务 ID 和一个指向旧版本的指针。见事务、MVCC 与锁。
  • LSN（log sequence number）：redo 写到第几个字节，只增不减，全库所有事务共用一条。

④-1 redo：先写日志，页以后再说

UPDATE 改页 75 的同时，生成一条 redo 记录：“页 75 的这个位置改成了这些字节”。它先进 log buffer，提交时写进 redo 文件并 fsync。页 75 本身留在内存，由后台的 page cleaner 找时间写回 orders.ibd。崩溃后，InnoDB 从检查点开始把 redo 重放一遍，内存里丢掉的修改就回来了。

两个容易漏的点。第一，LSN 是全库共用的：别的事务、后台的 purge 写的 redo 都往同一条上加，所以⑤里同一条 UPDATE，有一次量出来是 232 字节，另一次混进了后台的写入，量出来 964 字节。第二，redo 记的是页上的修改，不分是数据页还是 undo 页，所以 undo 也受 redo 保护，这一点 ④-2 马上用到。

④-2 undo：旧值留一份，管回滚，也管别人读旧版本

④-3 binlog：server 层的账，给从库和“按时间点恢复”

MySQL 分两层：server 层负责连接、解析、优化、复制；存储引擎（InnoDB）负责存数据。binlog 在 server 层，记的是“哪张表、哪一行、改前改后各是什么”（ROW 格式，8.4 默认），跟引擎无关。事务执行时，事件先攒在这个会话自己的 binlog cache 里（默认 32 KB，超了溢出到临时文件），提交时一次性写进 binlog 文件，所以一个事务的事件在 binlog 里连成一段，不和别的事务交错。从库拿到的、按时间点恢复重放的，都是这一段。

④-4 两阶段提交：两本账，一个判定

redo 和 binlog 是两个文件，没法一次 fsync 同时写好。MySQL 的办法是让 InnoDB 先“预提交”，再把 binlog 写好，最后才正式提交，并且规定：一个事务算不算数，看 binlog 里有没有它完整的 Xid 事件。

    ④-5 为什么这样设计：两本日志，而不是一本

    PostgreSQL 只有一本 WAL，恢复和复制都用它，根本不需要两阶段提交。MySQL 多付一次 fsync，是被它的分层逼出来的。

    MySQL：redo + binlog 两本，两阶段提交对齐

    • binlog 在 server 层，和引擎无关：从库可以换引擎、换页大小、换版本，照样回放“哪一行改成什么”。Canal、Debezium 这类 CDC 直接读它。
    • redo 贴着页写，恢复时按页重放，快，而且和 SQL 怎么写无关。
    • 代价：每次提交 redo 和 binlog 各要落盘，中间还要有 prepare 这一步；两本日志的格式、保留期、配置都得分别管。

    PostgreSQL：一本 WAL 放弃的另一种

    • 一次 fsync，没有两本账对不上的问题。
    • WAL 是物理的：流复制要求从库同一个大版本、同样的物理布局；要拿“哪一行改成什么”，得另开逻辑解码（logical decoding）。
    • PG 10 起的逻辑复制，也是从这同一本 WAL 里解码出来的：一本日志，两种读法。

    决定胜负的约束：MySQL 的 server 层从一开始就要挂多种存储引擎（MyISAM 没有事务、没有 redo），复制只能建在 server 层的 binlog 上；InnoDB 是作为其中一种引擎接进来的，自带 redo。两本日志的用途不同、格式不同，却必须对“这个事务算不算数”说同一句话，两阶段提交就是这句话。所以 redo 管“页能不能恢复”，binlog 管“事务在不在”。

    第一圈 · 注意事项

    坑 1为了快，把双 1 改成 2 和 0← ④-4 承诺落在刷过盘的日志上全景实测
    现象
    压测时提交太慢，改成 innodb_flush_log_at_trx_commit=2、sync_binlog=0，全景实测 300 次自动提交 p50 从 4.19 ms 降到 1.20 ms。平时一切正常，直到某次宿主机断电。
    根源
    2 是提交时只 write()，每秒 fsync 一次：mysqld 崩溃不丢，整机断电丢最近约 1 秒；0 连 write 都不做，mysqld 崩了也丢。sync_binlog=0 是交给操作系统决定什么时候刷，断电时 redo 和 binlog 各丢各的，可能主库没有、从库却有。
    做法
    管钱的库保持双 1（默认值）。要快靠组提交（并发越高摊得越薄，深 1）和更快的盘。能从别处重建的库（报表库、测试库）才放松。
    坑 2redo 容量太小，写入一阵一阵地卡← ④-1 检查点追不上 LSN实测
    现象
    批量写的时候延迟忽高忽低，磁盘写得很忙，可数据量并不大。
    根源
    redo 一圈太短，checkpoint age 很快顶到上限，InnoDB 只能加速刷脏页来推检查点；同一个页刚写回又被改脏，再写一遍。下表是同样 30 万行、每批 5000 行的更新。
    做法
    看高峰期每分钟 LSN 涨多少，常见的经验是让容量装得下高峰期约一小时的 redo。8.0.30 起可以在线改：SET GLOBAL innodb_redo_log_capacity = 2*1024*1024*1024。
    坑 3一个开着的报表事务，让 undo 越积越多← ④-2 purge 要等最老的快照实测
    现象
    History list length 一直涨；某些查询莫名变慢；undo 表空间越来越大。
    根源
    RR 下报表事务第一次读就拍了快照，只要它不结束，之后提交的所有旧版本都不能删。实测：它开着时 9527 被改了 2 万次，3 秒后 History list length 13 → 20000；它读 9527 要沿链往回走 2 万步，13.7～15.2 ms，新连接读 0.4～1.0 ms。它一提交，0.6 秒内清到 0。
    做法
    监控 History list length 和 innodb_trx 里最早的 trx_started；报表走从库、用短事务；连接池里别留着开了事务没提交的连接。
    坑 4一个事务改 30 万行← ④-3 binlog 提交时一次写实测
    现象
    提交那一下很慢，从库延迟突然跳高；它要是崩在半路，重启后还要在后台回滚很久。
    根源
    binlog cache 只有 32 KB，30 万行的事件溢出到临时文件，提交时一次写出 46 MB 再 fsync（整条语句 2.4～3.0 s）。从库要把这 46 MB 收齐才能回放这个事务。kill 0 那次，恢复要用 undo 撤 30 万行。
    做法
    按主键分批，每批几千行一提交（坑 2 的实验就是 5000 行一批）。max_binlog_cache_size 可以给单个事务的 binlog 设上限，超了直接报错。
    坑 5没收到 OK，不等于没提交← ④-4 分界线在 binlog 上实测
    现象
    应用的 commit() 抛了连接断开的异常，重试一次，结果扣了两次款。
    根源
    kill B 那次，客户端连接断了，没收到 OK，可 binlog 已经写完整，重启后事务被提交（qty 9 → 10）。崩在分界线右边，事务就在。
    做法
    把“提交时出错”当成结果未知：先按订单号查一次再决定；付款用条件更新 WHERE status='CREATED' 加幂等号，重试也只生效一次（见两次付款同时到）。

    第三圈 · 优化和深处

    深 1组提交：一次 fsync 带走一组事务源码

    8.4 的 MYSQL_BIN_LOG::ordered_commit 把提交分成三段排队：flush 段由队首的线程把这一组的 redo prepare 记录刷盘（ha_flush_logs），再把各自的 binlog cache 依次写进文件；sync 段一次 fsync binlog；commit 段让 InnoDB 按 binlog 里的顺序逐个提交。并发越高，一组里的事务越多，每个事务分到的 fsync 越少。全景页 300 次串行提交测到的 4.19 ms，是没人分摊的最坏情况。binlog_group_commit_sync_delay（默认 0）可以让 sync 段多等几微秒，凑更大的组，代价是每个提交都慢这么多。

    深 2doublewrite：redo 修不了撕裂的页手册 + 源码

    redo 记的是“在这个页上改几个字节”，前提是页本身完整。16 KB 的页写到一半断电，磁盘上半新半旧，校验和对不上，redo 无从下手。所以 page cleaner 写页之前，先把页顺序写进 doublewrite 文件（8.0.20 起是单独的 #ib_16384_0.dblwr 这类文件，本机数据目录里就有两个），再写到 .ibd 的原位置；恢复时发现撕裂页，就从 doublewrite 里拿完整的副本。8.4 的 innodb_doublewrite 默认 ON。

    深 3恢复的时间花在哪实测

    错误日志按顺序是：找到最新检查点 → Doing recovery: scanned up to log sequence number …（扫 redo）→ Applying a batch of 4921 redo log records（重放）→ 列出要回滚的事务 → Recovering after a crash using binlog → XA 恢复（prepare 的事务按 binlog 定生死）→ 截 binlog → 开始接受连接，未提交事务的回滚在后台继续（Starting in background the rollback of uncommitted transactions）。所以重启慢，主要是检查点之后的 redo 多；而能连上不代表回滚做完了。

    面试官会怎么问

    redo log 和 binlog 有什么区别？只留一个行不行？

    redo 是 InnoDB 的，记页上的物理修改，循环写，用于崩溃恢复；binlog 是 server 层的，记行的改前改后（ROW），按文件追加、按天过期，用于复制和按时间点恢复。只留 binlog 不行：它不能修页，也不知道哪些页已经写回；只留 redo 不行：它跟页布局绑定，循环覆盖，从库和 CDC 用不了（④-3、④-5）。

    为什么要两阶段提交？崩溃恢复时怎么判断一个事务要不要提交？

    两个文件不能一次写好，崩在中间就会主从不一致。InnoDB 先写 prepare 并刷盘，再写 binlog 并刷盘，最后写 commit。恢复时：没有 prepare 的事务用 undo 回滚；prepare 了的，binlog 里有它的 Xid 就提交，没有就回滚，并截掉 binlog 尾部不完整的部分（④-4，⑤ 实测）。

    commit 之后数据页还没写回磁盘，断电了怎么办？

    提交前 redo 已经 fsync。重启后从检查点开始重放 redo，把页改回最新。页写到一半的撕裂由 doublewrite 兜底（④-1、深 2）。

    undo 什么时候删？长事务有什么危害？

    提交后的 undo 要等到最老的活跃快照也用不到它，才由 purge 线程删。长事务（尤其 RR 下开着的读事务）会让 History list length 一直涨，undo 表空间变大，读旧版本的查询沿着很长的版本链走（坑 3 实测 2 万步 14 ms）。

    innodb_flush_log_at_trx_commit 设成 0、1、2 有什么区别？

    1：每次提交 write + fsync；2：提交时 write，每秒 fsync，mysqld 崩溃不丢，断电丢约 1 秒；0：提交时什么都不做，每秒 write + fsync，mysqld 崩溃也可能丢约 1 秒（坑 1）。

    ↺回到⑤：拿刚学的东西改靶场

    都在 LogLab.java 和 crash.sh 上改。先写下猜测再跑。

    1. 把报表事务换成 RC

    在 purge() 里把报表事务的隔离级别改成 READ COMMITTED，重跑 purge。猜：History list length 还会涨到 2 万吗？报表事务读 9527 还要 14 ms 吗？

    对照坑 3：purge 等的是“还开着的快照”，不是“还开着的事务”

    2. 让大事务变小

    把 crash.sh 的 BIG 改成分批：每 5000 行一提交，在第 30 批时 kill。猜：重启后 9527 的 qty 变没变？错误日志里还有“300000 rows to undo”吗？

    对照坑 4：每批是独立的事务，崩溃只影响正在提交的那一批

    3. 量一下组提交

    写一个 gc 段：1 个、8 个、32 个线程各做 2000 次自动提交的单行 UPDATE，前后各读一次 Innodb_os_log_fsyncs。猜：每次提交平均几次 redo fsync？

    对照深 1：线程越多，一次 fsync 带走的事务越多

    自测

    1. 用一句话说出这一页的精华。

    commit 的承诺落在提交时刷过盘的 redo 和 binlog 上，而不在数据页上；undo 留旧值管回滚和 MVCC；redo 和 binlog 用两阶段提交对齐，重启时 prepare 了的事务按 binlog 里有没有 Xid 决定提交还是回滚。

    2. 提交时直接把数据页写回，痛在哪？

    一次只改几十字节，却要随机写整个 16 KB 页，碰几个页写几个；页写到一半断电还会撕裂。redo 只写几百字节、顺序追加。

    3. 头号坑“为了快改成 2 和 0”，根源是哪条原理？

    ④-4：commit 能承诺不丢，是因为分界线左右的东西已经 fsync 过。2 和 0 把 fsync 交给了每秒一次的后台线程和操作系统，分界线之后的东西断电时还只在内存里。

    4. 预测：binlog 已经 fsync，InnoDB 还没写 commit 记录，整机断电。重启后 9527 是什么？从库呢？

    主库 PAID：redo 里有 prepare，binlog 里有完整的 Xid，恢复时提交。从库也会收到（binlog 里有）。应用没收到 OK，要按结果未知处理。

    从 ④-4 的分界线推出；可以在实验台第 5 格验证。

    5. 预测：innodb_flush_log_at_trx_commit=2、sync_binlog=1，应用收到 OK 后整机断电，会怎样？

    如果断电发生在提交后 1 秒内：binlog 已 fsync，从库会有这条付款；可 InnoDB 的 prepare 记录只 write 到了操作系统缓存，还没等到每秒一次的 fsync，丢了。重启后 InnoDB 根本不知道这个事务，主库是 CREATED，从库是 PAID，主从对不上。两个参数只放松一个，同样会出事。

    从 ④-4 推出：恢复规则只对“redo 里有 prepare”的事务查 binlog。页面上没有这个组合，实验台只给了双 1 和 2 + 0。

    6. 预测：一个事务开着（RR，已经读过一次），另一个连接把 9527 改了 10 万次。这个事务再读 9527，会比实测的 14 ms 快还是慢？它提交以后呢？

    更慢，大约是版本链长度的倍数（10 万步，按实测比例估算约 70 ms，没有实测）；它提交后，purge 很快把链清掉，再读就回到 1 ms 以内。

    从 ④-2 和坑 3 推出。

    7. 放回全景：第 8、9 站前后各发生了什么？redo 或 binlog 出了问题，整条链路会怎样？

    第 7 站把旧值写进 undo；第 8 站改 buffer pool 里的页 75、写 redo，binlog 先攒在 cache；第 9 站两阶段提交，redo prepare 和 binlog 都落盘后才回 OK（第 10 站），锁也在这里放掉；第 11 站从库拿到的就是这 5 个事件；第 12 站页 75 很久以后才写回。redo 太小时，第 8 站每条写入都可能被迫等刷页，持锁时间变长，第 6 站排队、第 1 站连接池被占满；binlog 不刷盘（sync_binlog=0）时，断电后第 11 站的从库和主库对不上，读从库的订单页看到的是另一个世界。

    标准档。实测 的数字来自本机：2 核 ARM，JDK 17.0.21，Connector/J 9.7.0，Docker 里的 MySQL 8.4.13（buffer pool 512 MB，其余默认），交易靶场 100 万行 orders；代码在 study-labs。标“全景实测”的来自全景页。两阶段提交的流程、恢复规则、redo 刷脏阈值、purge 线程默认值核对自 mysql-server 8.4 源码（sql/binlog.cc、sql/binlog/recovery.cc、storage/innobase/handler/ha_innodb.cc、log0constants.h、log0files_capacity.cc、trx0trx.cc）和 8.4 参考手册的 Redo Log 一节。实验台是按这些规则推演的模拟；“整机断电”没有实测，按最坏情况算。
