换上 8.4，付款服务连不上库了：MySQL 8.0 升级 8.4 LTS

8.0 在 2026 年 4 月随 8.0.46 停止维护，下一站是第一个长期支持版 8.4 LTS。升级本身很顺：换镜像、同一个数据目录，8.4 启动时自己把数据字典和系统表升好，实测 10 秒就能连。出事的是周边四样东西：老账号（mysql_native_password 默认不加载，付款服务直接报 1524）、老命令（SHOW MASTER STATUS、START SLAVE 都删了）、默认值（刷盘、自适应哈希、临时表一批都换了）、约束（外键不能再指向非唯一索引）。另外这扇门只能往前走：升过的数据目录，8.0 拒绝启动。所以要先跑检查、在 8.0 上先把账号和脚本改掉，再先升从库、切换、最后升旧主库，切换之前旧主库一直是退路。

①什么时候用得上：8.0 停更了，靶场要换到 8.4

在全景第 11 站，主库把付款那条 UPDATE 的 binlog 推给从库，从库照着改一遍。这一步要解决的是：底下的 MySQL 8.0 已经不再出补丁，交易靶场的一主一从要换到 8.4，付款不能停，复制不能断，出了问题还要能退回去。全景实测时已经在 8.4.13 上踩到两处：SHOW MASTER STATUS 报语法错，复制命令全改叫 SOURCE / REPLICA。

停更意味着之后发现的安全漏洞和 bug 都不会在 8.0 上修了。靶场的情况：一主一从、GTID 复制，orders 表 10 万行，付款服务用 Connector/J 连主库，账号是几年前建的；运维脚本、监控里有一堆 SHOW SLAVE STATUS。

②常见笨办法：改个镜像 tag，主从一起重启

8.0 到 8.4 看起来只是小数字变了，最省事的做法是把 mysql:8.0 改成 mysql:8.4，两台一起重启。下面是 ⑤ 里分步做时撞上的东西，合在一起就是一起重启的结果。

缺的那一块：大版本升级换的不只是二进制，还有一批约定：账号用什么方式认证、哪些语句还认、没写进配置的参数取什么值。而且数据目录一旦被新版本改过，就回不去了。所以要先把会变的东西查出来、在旧版本上先改掉，再一台一台换，换的过程中始终留一台旧版本当退路。不懂这一点的典型误用：把 8.0 → 8.4 当成补丁升级，选在业务低峰期一起重启，结果付款全挂，回滚时才发现回不去。

③工具和路线：一台怎么升，一组怎么换

手册给了三类升级方式。单台机器上怎么从 8.0 变成 8.4，是“原地”还是“导出再导入”；一组主从怎么换，是“滚动”还是“另起一组”。另外还有一个所有路线都要先用的工具：升级检查。

做法怎么做停写多久回退适合
原地升级（in-place）停 8.0，用 8.4 的程序启动同一个数据目录，启动时自动升级这一台重启的时间（实测约 10 s）不能原地回 8.0；要先备份或留着别的实例单机、测试环境；滚动升级里的每一台
导出导入（dump / load）mysqldump 或 Shell 的 util.dumpInstance 导出，在新的 8.4 实例里导入和数据量成正比，大库几小时旧实例原封不动顺便换机器、换字符集；数据不大
滚动升级（先从后主）从库一台台原地升 8.4，追平后切换，旧主库最后升级、挂回来当从库只有切换那一下（几秒）切换前随时退；切换后只能靠导出或复制回滚本页：交易靶场的一主一从
另起一组（蓝绿）新建 8.4 实例，从 8.0 主库复制追平，切换流量只有切换那一下旧的一组原封不动，最好退机器富余、要求退路最宽

选择规则：线上有从库就用滚动升级，每一台的动作就是原地升级；有余力就另起一组，退路最宽。导出导入留给数据小、或者正好要换机器的情况。不管哪条路线，第一步都是 MySQL Shell 的升级检查 util.checkForServerUpgrade()：连上 8.0，列出会出问题的账号、外键、变量和默认值。本页学滚动升级，单台的原地升级是它的一部分。

④背后的机制：启动时自己升级，复制只能往新走，四类约定换了

先看 8.4 启动时对数据目录做了什么，为什么它只能往前；再看复制为什么允许“旧主新从”，这决定了滚动的顺序；最后把 8.4 换掉的约定分成四类，其中最容易炸的认证单独拆开讲。

先知道这些
  • LTS 和创新版：8.1 起 MySQL 分两条线。创新版大约每季度一个，加新功能、也删旧东西，只支持到下一个创新版出来；LTS 每两年左右一个，同一个 LTS 里的补丁版本只修 bug，按 5 年 Premier + 3 年 Extended 支持。生产库跟 LTS 走。
  • 数据字典：8.0 起，库、表、列、索引这些元数据都存在 mysql 库的 InnoDB 表里，表结构本身带版本号。新版本的程序要先把它升成自己认识的格式才能用。
  • GTID 复制：每个事务一个全局编号，从库按“还缺哪些编号”找主库要，切换主库时不用算 binlog 位点。详见主从复制、读写分离与复制延迟。

④-1 8.4 启动时自己升级，升完就回不去

8.0.16 起这件事由服务器自己做（--upgrade=AUTO 是默认），8.4 把旧的 mysql_upgrade 工具删了。手册要求升级前：有 XA 事务先 XA RECOVER 处理掉；innodb_fast_shutdown 不能是 2，要用快关或慢关（⑤ 用的是慢关 =0）。

只能往前升 MySQL 的选择

  • 新版本可以自由改数据字典表、系统表、redo 和 undo 的格式，不用考虑旧程序读不读得懂。
  • 同一个 LTS 里只修 bug、不改格式，所以 8.4.x 之间可以原地降级，补丁回滚很便宜。
  • 跨 LTS 回退只能靠导出导入或复制，而且手册说只限“新功能还没用上”的回滚。

新旧双向兼容 没有选

  • 换回旧版本就能回滚，升级没有心理负担。
  • 每个格式都要让好几年前的旧程序也能读，格式改不动；或者新版本写一份旧格式，多一层转换和测试。
  • 新功能（比如新的数据字典字段）在旧版本里没有对应物，回退时只能丢掉。

决定胜负的约束：数据库的磁盘格式要跟着功能一起演进，而回退是低频事件。所以 MySQL 把“能回退”的承诺缩到同一个 LTS 之内，跨 LTS 的退路交给运维流程（留一台旧版本、或者备份）。PostgreSQL 的 pg_upgrade 也是单向的，思路一样。

④-2 复制只保证“旧主新从”，所以先升从库

复制就是从库把主库发来的 binlog 事件重放一遍（全景第 9～11 站）。新版本能读懂旧版本写的事件和语句，这是升级本来就要保证的兼容；反过来，旧版本没义务懂新版本的语法、新的事件类型、新的默认行为。手册的原话：支持“从旧源复制到新从库”，前提是这两个版本之间本身支持升级；“新源到旧从库可能能跑，但一般不受支持”。所以顺序只能是从库先升，主库最后升。回退正好反过来：要先降主库，再降从库。

还有一层：从库重放的是主库的每一条语句。主库上 8.4 能执行的东西，如果从库的配置不支持，从库的 SQL 线程就停下来。⑤ 的最后一步就撞上了一次：新主库上把账号改回 mysql_native_password，没开这个插件的从库重放到这一条，报 1524 停了。

账号和语法这两类是“改名、删旧”，8.0 已经提前几年给出了新写法和弃用警告；默认值和约束是“按现在的硬件和规范重定规矩”。四类里只有账号这一类会让业务直接停摆，所以下面单独拆开。

④-4 caching_sha2_password：第一次登录要一条安全的路

老的 mysql_native_password 存的是没加盐的两遍 SHA-1，算得快，库里的哈希一旦泄露，很容易被暴力破解。caching_sha2_password 存加盐、多轮的 SHA-256，算一次很贵；为了不让每次登录都这么贵，服务器在内存里缓存一份摘要，命中了就走便宜的挑战-应答。代价是没命中时，密码得真的送到服务器，所以要一条安全的路：TLS，或者 RSA 加密。这就是 8.0 时代 useSSL=false 的老 URL 在这里“时好时坏”的原因：有人走 TLS 登录过一次，缓存热了就好；数据库一重启又坏。

最少要会的几条前三块在 8.0.46 上就能先做；SHOW BINARY LOG STATUS 只有 8.2 起才有
-- 升级检查（用 8.4 的 MySQL Shell 连 8.0）
mysqlsh --uri root@db-8.0:3306 -- util check-for-server-upgrade --target-version=8.4

-- 账号：在 8.0 上就改成 caching_sha2_password，应用 URL 去掉 useSSL=false
ALTER USER pay_native@'%' IDENTIFIED WITH caching_sha2_password BY '…';

-- 复制：8.0.22 / 8.0.23 起就有新写法
CHANGE REPLICATION SOURCE TO SOURCE_HOST='…', SOURCE_AUTO_POSITION=1, GET_SOURCE_PUBLIC_KEY=1;
START REPLICA;   SHOW REPLICA STATUS\G   STOP REPLICA;   RESET REPLICA ALL;

-- 8.2 起才有：8.0.46 上 SHOW BINARY LOG STATUS 实测是语法错误
SHOW BINARY LOG STATUS;          -- 原 SHOW MASTER STATUS
RESET BINARY LOGS AND GTIDS;     -- 原 RESET MASTER

参数默认值、删掉的变量清单、检查工具的每一项，放到第⑥步。

⑤跟着做一遍：交易靶场一主一从，8.0.46 → 8.4.13

一个脚本起两台 8.0.46（GTID 复制，orders 10 万行），故意带上老库常见的三样东西：用 mysql_native_password 建的付款账号、用 CHANGE MASTER TO 搭的复制、一个指向非唯一索引的外键。然后按 ④-2 的三个阶段走一遍，每一步都用付款服务的两个账号、三种 JDBC URL 各连一次。

怎么跑需要 Docker（拉 mysql:8.0.46、mysql:8.4.13）、JDK 8+、Maven；整段约 3 分钟
cd java/database/mysql-84-upgrade
DOCKER="sudo docker" ./run.sh          # 六段依次跑完，输出写到终端，变量对比和检查报告在 target/out/
DOCKER="sudo docker" ./run.sh clean    # 删容器、数据卷和网络

完整代码 → run.sh 是升级剧本，ConnectMatrix.java 是付款服务的连接矩阵。

到这里已经能交差了：跑检查；在 8.0 上先把账号改成 caching_sha2_password、把应用 URL 改成走 TLS、把脚本改成 REPLICA 写法；从库慢关机换 8.4，追平后切换，旧主库最后升。还没处理的细节：默认值换了以后性能会不会变（⑥ 默认值）、配置文件里写了已删除的变量（坑 5）、切换以后怎么回退（坑 6）、连接池里的老连接（坑 7）。

⑥刻意练习：先认坑，再照清单练

升级是一年做一两次的事，靠的是清单和演练，不是记忆。先把会出事的八处认清，每处都能点回 ④；然后是一份升级清单；第三圈挑三个点往下挖；最后是四道由易到难的练习，每道都写了做对了会看到什么。

第一圈 · 不知道就会出事故的坑

坑 1老账号整片登录失败← ④-3 账号类约定实测
现象
切到 8.4 后付款服务所有连接都报 1524 Plugin 'mysql_native_password' is not loaded，连接池建不起来，接口全挂；换 TLS、换驱动版本都没用。
根源
账号上记着它用哪个插件认证；8.4 默认不加载这个插件，这个账号就没有任何办法登录。升级检查只给 Warning，不算 Error。
做法
在 8.0 上就 ALTER USER … IDENTIFIED WITH caching_sha2_password，同时改应用 URL（坑 2）。--mysql-native-password=ON 只当救火开关，主从一起开（坑 8），9.0 起没有这个开关了。
坑 2改完账号，时好时坏← ④-4 缓存没命中要安全通道实测
现象
账号改成 caching_sha2_password 后，测试时连得上，数据库一重启又报 Public Key Retrieval is not allowed；有时某台应用能连、另一台不能。
根源
URL 里的 useSSL=false：缓存热的时候走快速认证，不需要安全通道；缓存冷了要完整认证，没 TLS、没公钥，驱动拒绝。谁先走 TLS 登录过一次，决定了别人能不能连。
做法
去掉 useSSL=false，让 Connector/J 默认走 TLS（要校验证书再配 sslMode=VERIFY_CA）。实在不能上 TLS 的内网，才用 allowPublicKeyRetrieval=true：公钥是明文要来的，中间人能换掉它。
坑 3监控和运维脚本静悄悄地失效历史原因：术语替换实测
现象
复制延迟告警不响了（采集脚本里的 SHOW SLAVE STATUS 报 1064，被当成“取不到值”吞掉）；备份脚本取 binlog 位点失败；切换脚本里的 CHANGE MASTER TO 跑不了。
根源
MySQL 从 8.0.22 起把 MASTER / SLAVE 换成 SOURCE / REPLICA，旧写法弃用了几年，8.4 删除。这不是机制推出来的，是命名上的历史包袱。
做法
升级前在所有仓库、cron、监控配置里 grep -iE 'MASTER|SLAVE'；在 8.0 上就改成 REPLICA 写法。只有取 binlog 位点要按版本分支：8.0 用 SHOW MASTER STATUS，8.4 用 SHOW BINARY LOG STATUS（练习 2）。
坑 4老外键能用，照着建一个新的就报错← ④-3 约束类约定实测
现象
升级很顺，几周后上线一张新表，外键照抄老表的写法，报 6125 Missing unique key；或者在 8.4 上导入一份老库的建表语句，卡在同一处。
根源
restrict_fk_on_non_standard_key 默认 ON：升级时已有的外键只记一条弃用警告，新建的一律检查被引用的列上有没有完整的唯一索引。
做法
按检查报告的 foreignKeyReferences 一项项改：被引用列没有重复就改唯一索引，否则改成引用主键（练习 3）。
坑 5配置文件里一个删掉的变量，8.4 起不来← ④-3 删掉的变量实测
现象
换了镜像，容器立刻退出：[ERROR] [MY-000067] unknown variable 'expire-logs-days=7'，接着 Aborting。
根源
my.cnf 里的每个选项 mysqld 都要认识，不认识就拒绝启动。8.4 删了 expire_logs_days、master_info_repository、default_authentication_plugin、binlog_transaction_dependency_tracking 等一批。
做法
升级检查带上配置文件路径（--config-path），它的 removedSysVars 会对照；换成新变量，比如 binlog_expire_logs_seconds。加 loose- 前缀只会降成一条 Warning（实测），能临时救命，但掩盖了问题。
坑 6想回滚，发现回不去← ④-1 只能往前升实测
现象
切换到 8.4 后发现一条慢 SQL，想退回 8.0：拿 8.0 启动数据目录，报 Cannot downgrade from 80413 to 80046。
根源
8.4 启动时已经把数据字典和系统表升成新格式；同一个 LTS 之外不保证旧程序能读。
做法
切换前做完所有验证：让 8.4 从库先挂在 8.0 主库下面跑几天、接一部分读流量。切换后的回退只能是导出导入，或者另起 8.0 实例从 8.4 复制（不受支持，要自己演练过，练习 4）。升级前一定有一份备份。
坑 7切换后还有写打到旧主库← ④-2 切换推出
现象
切换完成，大部分付款正常，少数报 ERROR 1290 … --super-read-only，持续几十分钟才消失。
根源
连接池里的老连接还连着旧主库。改了 DNS 或 VIP，已经建好的 TCP 连接不会跟着走；HikariCP 默认 maxLifetime 30 分钟才换掉一条连接。
做法
切换时让应用重建连接池（HikariCP 的 softEvictConnections()，或者滚动重启），或者走 ProxySQL / MySQL Router 这类中间层，由它切。
坑 8主库上能做的事，从库重放不了← ④-2 从库重放每一条语句实测
现象
主库开了 --mysql-native-password=ON 救火，顺手把一个账号改回 native；几秒后从库 Replica_SQL_Running: No，LAST_ERROR_NUMBER: 1524，读从库的订单页开始读到旧数据。
根源
ALTER USER 进了 binlog，从库照样执行；从库没开这个插件，执行失败，SQL 线程停下。
做法
主从的插件、sql_mode、关键参数保持一致；临时开关主从一起开、一起关。

第三圈 · 往下挖三处

1. 默认值换了哪些，为什么。同一台机器（2 核 ARM、11 GB 内存），同样的启动参数，8.0.46 和 8.4.13 的 SHOW GLOBAL VARIABLES 对比，去掉路径和版本号后 43 处不同。和性能有关的：

变量8.0.468.4.13改动方向
innodb_io_capacity / _max200 / 200010000 / 20000按 SSD 的 IOPS 估后台刷脏的速度；机械盘、IOPS 小的云盘要显式调小
innodb_flush_methodfsyncO_DIRECT数据页不再经过操作系统页缓存，避免内存里存两份
innodb_use_fdatasyncOFFON刷盘时不必连文件元数据一起刷，少一次写
innodb_adaptive_hash_indexONOFF高并发下维护这个哈希的锁常成热点；点查多的库可以压测后再打开
innodb_change_bufferingallnonechange buffer 为机械盘的随机读设计，SSD 上收益小
innodb_log_buffer_size16 MB64 MB大事务少落一次盘
innodb_doublewrite_pages4128双写缓冲一批写更多页
innodb_purge_threads41按 CPU 数算：16 核以内 1 个，更多 4 个
temptable_use_mmap / temptable_max_mmapON / 1 GBOFF / 0内部临时表超出内存后不再用 mmap 文件，直接落 InnoDB 磁盘表

实测 的是两列取值（target/out/vars-diff.txt）；最后一列是按改动方向和常见调优经验写的解释，不是手册原话。innodb_buffer_pool_instances、innodb_page_cleaners、innodb_read_io_threads 在 8.4 改成按 CPU 和内存算，这台 2 核、256 MB buffer pool 的机器算出来和 8.0 一样，所以没出现在对比里；大机器上会不同。

2. 从库的并行回放。binlog_transaction_dependency_tracking 在 8.4 删了，检查报告的说法是默认从 COMMIT_ORDER 变成 WRITESET：主库按“两个事务改的行有没有交集”来标记哪些事务能在从库上并行回放，而不只看它们是不是同一批提交的。改不同订单的付款更容易并行，全景第 11 站的复制延迟会更小一些（按机制推出，没有实测）。

3. 下一站 9.7。mysql_native_password 在 9.0 就删了，9.7 LTS 里没有救火开关。8.4 是最后一个还能打开它的 LTS，所以坑 1 的修法必须在 8.4 期间彻底做完。8.4 到 9.7 照样是“检查 → 先升从 → 切换”这一套，手册明确支持 8.4.x LTS 到 9.7.x LTS，不支持跳过 LTS。

自测

1. 用一句话说出这一页的精华。

8.0 → 8.4 的数据目录升级是自动的、单向的；出事的是账号插件、MASTER/SLAVE 语法、默认值和外键约束这四类约定。所以先检查、在 8.0 上先改，再先升从库、切换、最后升旧主库，切换前旧主库一直是退路。

2. “改镜像 tag，主从一起重启”这个做法，痛点在哪？

不是起不来，而是起来以后付款服务登录失败、脚本报语法错、默认值悄悄变了；而且所有机器同时变成 8.4，数据目录回不了 8.0，连一台能退的都没有。

3. 头号坑“老账号整片登录失败”，根源是哪条原理？

④-3 的账号类约定：账号上记着认证插件，8.4 默认不加载 mysql_native_password，这个账号就无从认证。和 TLS、驱动版本都无关，所以换 URL、换驱动救不了。

4. 预测：账号已经改成 caching_sha2_password，URL 是 useSSL=false。白天一直正常，夜里数据库重启后，第一个请求会怎样？如果之前有一台管理后台走 TLS 登录过同一个账号呢？

重启清空了缓存，完整认证需要安全通道，没有 TLS 也没有公钥，驱动报 Public Key Retrieval is not allowed。管理后台走 TLS 登录过之后，缓存里有了这个账号的摘要，之后 useSSL=false 也能走快速认证连上，直到下次重启或 FLUSH PRIVILEGES。推导自 ④-4。

5. 预测：为了省事，先把主库升到 8.4，从库留在 8.0。付款照常写，会发生什么？

这是“新主旧从”，手册说一般不受支持。普通的行事件也许还能回放，但只要主库写出 8.0 不认识的东西（新语法的语句、新的事件或默认行为），从库的 SQL 线程就会停下，读从库的订单页开始读旧数据；而且主库已经回不了 8.0。推导自 ④-1、④-2。

6. 放回全景：升级做在第 11 站这台从库上。第 9、10 站（主库写 binlog、提交返回）和第 11 站之后会怎样？如果升级没处理好账号，或者脚本还在用老命令，整条链路会怎样？

阶段 1 里主库还是 8.0，第 1～10 站完全不变，付款照常提交；第 11 站换成 8.4 的从库照样收 binlog、回放，订单页读从库也照常。真正的风险在切换后：第 1 站借连接时就失败（1524），付款请求根本到不了第 4 站，连接池被建连接失败拖住，接口超时；脚本用老命令则是复制延迟的监控失明，第 11 站落后了也没人知道。

标准档。实测 的数字和输出来自本机：2 核 ARM、11 GB 内存，Docker 里的 mysql:8.0.46 和 mysql:8.4.13 两个容器（同一个 Docker 网络，GTID 异步复制，buffer pool 256 MB，其余默认），orders 10 万行；Connector/J 9.7.0 和 5.1.49，JDK 17；升级检查用 8.4.13 镜像自带的 MySQL Shell 8.4.10。全程跑了三遍，修了两处脚本问题（检查命令的参数、容器主机名），页面上的输出取第三遍；“删掉的变量让 8.4 起不来”另起容器单独跑过一次。

按文档：8.0.46 是 8.0 最后一版（2026-04-21）；8.4.0 GA 于 2024-04-30，LTS 按 5 年 Premier + 3 年 Extended 支持（具体截止日是推算）；9.7.0 于 2026-04-21 发布，LTS 之间不能跳；8.4 → 8.0 只能导出导入或复制、只限回滚用途；复制支持旧源到新从库，新源到旧从库一般不受支持，升级从库先、降级主库先；mysql_native_password 8.0.34 弃用、8.4 默认关闭、9.0 删除；8.4 删除的语句和变量清单、InnoDB 默认值变化、caching_sha2_password 的缓存清空时机，均出自 MySQL 8.4 参考手册的 “What Is New in MySQL 8.4 since MySQL 8.0” 和各插件章节；升级前的 XA 和 innodb_fast_shutdown 要求出自 “Upgrading MySQL Binary or Package-based Installations on Unix/Linux”。推出：坑 7（连接池老连接）、WRITESET 对复制延迟的影响。
