订单表拆成 8 张：分库分表与 ShardingSphere

拆分要解决的，是一台主库的写入上限和一张大表的运维时间（建索引、备份恢复），不是“行数多了点查变慢”：1.2 亿行的 B+ 树也就 4 层。拆分的代价是从此每条 SQL 都要先回答“在哪张表”，所以最关键的决定是分片键：选查得最多、分布最均匀、写进去就不会变的那个字段。ShardingSphere-JDBC 在 JDBC 这一层把一条逻辑 SQL 解析、路由、改写成几条真实 SQL，再把结果归并回来，业务代码还以为只有一张 t_order。

①要解决的问题：订单表 1.2 亿行，到底是哪里扛不住

在全景第 1 站，这一步要回答：要不要拆。常听到的理由是“单表超过 2000 万就该拆”。先看这个数字从哪来，再看交易靶场真正顶到的是什么。

右边三条有个共同点：都和一台机器上放了多少数据、进了多少写有关，加索引、加缓存、加从库都缓解不了。这才是拆分要解决的问题：把数据和写入分到多台机器、多张表上，让每一份都回到“能在一小时内恢复、几分钟内加完索引、一台主库扛得住”的大小。

②不用它会怎样：先把便宜的招用完

拆分是最贵的一招：要改 SQL、做迁移、多养一层中间件，以后每个需求都要先问“带没带分片键”。所以先看便宜的招各能解决什么。

便宜的招能解决解决不了
优化 SQL、补索引慢查询（多数“表大了变慢”其实是这个）写入峰值、恢复时间；补索引本身就要 2 小时 40 分
冷数据归档把一年前的订单挪进历史库，主表从 1.2 亿降到 3000 万，加索引、恢复都快了写入峰值；业务要求“查近 3 年订单”时，归档的边界就不好划
读写分离（J06）读多写少：读分给从库写入：每台从库要回放全部写入，主库的写一点没少
加缓存（J07）热点读：商品详情、订单状态写入，以及“我的订单”这类每个人都不一样的列表
升级机器CPU、内存、磁盘都翻倍，最省心有上限也越来越贵；数据量照样涨，恢复时间照样变长
MySQL 分区表一张逻辑表在磁盘上拆成多个分区，按分区删旧数据很快所有分区还在同一台实例上，写入和恢复问题都还在；分区键必须在每个唯一索引里

交易靶场先做了归档、读写分离和缓存，读的问题解决了；剩下的“写入集中在一台主库”和“单实例数据量太大”，只有把数据分到多台机器才能解决。这就是分库分表的精华：它是唯一能同时分摊写入和数据量的办法，代价是把“数据在哪”这件事交给了每一条 SQL。

不懂精华时的典型误用表一大就拆，拆完发现 90% 的 SQL 没带分片键，每条都被改写成查 8 张表：数据库的总压力变成原来的好几倍，慢的那条 SQL 还是慢。拆分只对“带着分片键的查询”和“分得开的写入”有好处。

③几种流派：怎么拆、按什么规则、在哪一层做

分片规则怎么算好处代价
取模 / 哈希user_id % 8，或先哈希再取模分布均匀，写入也均匀扩容要改模数，一半左右的数据要换表；范围查询要问遍所有表
范围按时间（每季度一张）或按 id 区间扩容只要加新表，旧数据不动；按时间查只碰一两张新数据全写最后一张，写入热点；“我的订单”跨所有季度
映射表（目录）查一张“user_id → 表号”的表想怎么挪就怎么挪，能单独搬走一个大客户每次路由多一次查询，映射表自己要高可用、要缓存
一致性哈希哈希环，加节点只挪相邻一段缓存集群常用数据库里少见：表的数量通常一次规划好，扩容按“整张表挪库”做（见 ④ 机制 4）
在哪一层做代表适合代价
应用里（JDBC 层）ShardingSphere-JDBCJava 服务、要性能：直连数据库，没有多一跳只支持 Java；每个应用实例都连所有库，连接数相乘；规则改了要所有实例一起生效
独立代理ShardingSphere-Proxy、Vitess、MyCat多语言、DBA 想要统一入口，客户端当成一个 MySQL多一跳网络；代理自己要集群化、要扛住全部流量
数据库原生TiDB、OceanBase、GoldenDB，PostgreSQL 的 Citus不想改 SQL、不想自己迁移换一套数据库和运维，行为和 MySQL 不完全一样（J11 第 6、7 页）

选择规则：只有 Java 服务、团队能管住每条 SQL → 应用层分片；多语言或要统一入口 → 代理；不想动 SQL 和迁移 → 分布式数据库。交易靶场全是 Java，选 ShardingSphere-JDBC，规则用取模。本页学它。

④核心取舍：分片键、库表规则，和一条 SQL 在 ShardingSphere 里的五步

先知道这些 逻辑表和真实表：业务 SQL 里写的 t_order 是逻辑表，数据库里真实存在的是 t_order_0～t_order_7。ShardingSphere 的配置 actualDataNodes 就是列出“逻辑表对应哪些库里的哪些真实表”。 数据源：ShardingSphere-JDBC 对外是一个普通的 DataSource，里面包着两个真正的连接池（ds_0、ds_1）。MyBatis、JPA 拿到的就是这个外壳，所以上层代码不用改。 主键：拆完以后各张表的自增 id 会重复，主键要由应用生成全局唯一的号，见 分布式 ID。

机制 1：一条逻辑 SQL 的五步（ShardingSphere-JDBC 5.5.3，⑤ 实测的真实输出）

关键在第 ② 步：路由只能用解析时看得见的分片条件。user_id = ?、user_id IN (?, ?) 看得见，能算出具体的表；条件里没有分片键、分片键套了函数、或者是 INLINE 算法算不了的范围，就只能退回“所有表都问一遍”（全路由）。⑥ 的坑 2、3、4 都从这里来。

机制 2：分片键的三条标准

1. 覆盖最多的查询

带分片键的查询只碰一张表。交易靶场 80% 的订单查询（我的订单、订单详情）带着 user_id，所以选它。商家查询吃亏，交给 ES（第 4 页）。

2. 分布均匀，写入也均匀

每张表的数据量和写入量要差不多。按 shop_id 分，大商家所在的表会胖一截；按时间分，新订单全写最后一张。

3. 写进去就不变

值一改，这行就该换到另一张表。ShardingSphere 直接拒绝：Can not update sharding value（⑤ 第 9 条）。所以不能选订单状态这种会变的字段。

还有一条常被忘记的：同一个实体的相关表用同一个分片键。t_order 和 t_order_item 都按 user_id 分，同一个用户的订单和明细落在同一个库，JOIN 和本地事务都还能用。ShardingSphere 里把它们配成“绑定表”（bindingTables），JOIN 时就不会两两组合出 8 × 8 条路由。

机制 3：库号和表号要来自同一个余数（⑤ 实测，1 万个用户各一单）

道理很简单：user_id % 2 和 user_id % 4 不是两次独立的抽签，前者完全由后者决定。所以先算一个总的槽号 slot = user_id % 表总数，表号就是槽号，库号由槽号推出来，每张真实表在全局只出现一次。

机制 4：拆几张，为什么是 2 的幂，为什么“表多建、库少放”

  • 表数按 3 年后每张表的行数倒推：每天 60 万单、热数据留 12 个月（更早的归档），约 2.2 亿行，8 张表每张 2700 万左右，加索引、恢复都在可控范围。
  • 库数按写入倒推：大促峰值 3200 行/秒，两台主库各 1600，留出余量。库数决定写入能力，表数决定单表大小，两者可以分开定。
  • 2 的幂以后扩到 4 个库时，库号改成 slot % 4：t_order_0、t_order_4 还在 ds_0，t_order_2、t_order_6 整张搬到新的 ds_2。每一行的表号不变，只是整张表换了库，不用逐行重新路由。
  • 代价表数一旦要变（8 → 16），一半的行要换表，那就是再做一次第 3 页的迁移。所以表数要一次规划够，库数可以先少放。

机制 5：为什么分片放在应用里（以及什么时候不该）

应用里：ShardingSphere-JDBC

改写完直接用连接池连真实库，没有多一跳，延迟和单库差不多。代价：每个应用实例都要连所有库。订单服务 6 个实例 × 每个库一个 20 连接的池，每台 MySQL 就有 120 个连接；库多了、实例多了，连接数是乘出来的。

代理：ShardingSphere-Proxy

应用只连代理，代理再连真实库，连接数由代理收敛；任何语言都能用，DBA 可以直接连代理查数据。代价：每条 SQL 多一跳网络，代理要做成集群并扛住全部流量，它挂了所有服务都连不上库。

决定胜负的约束：多一跳网络和多一个要高可用的组件，值不值得换来连接数收敛和多语言。交易靶场只有 Java、实例不多，选 JDBC；同一套规则以后也能原样搬到 Proxy 上。

⑥反例和误用

第一圈 · 不知道就会出事

1库和表各取各的余数，一半的表永远是空的← ④ 机制 3 同一个余数
现象
⑤ spread：库 % 2、表 % 4，每个库里有两张表 0 行，另外两张各 2500 行。容量白白少了一半，热点翻倍。
根源
两个模数有公因子，库号已经决定了表号的奇偶。
做法
先算总槽号 slot = key % 表总数，表号 = 槽号，库号由槽号推（slot % 库数）；上线前插一批数据，数一遍每张真实表的行数。
2SQL 没带分片键，悄悄变成问 8 张表← ④ 机制 1 路由只看得见条件
现象
⑤ 第 3、5 条：只按订单号、按商家查，都是 8 张表（同库的 4 张合成一条 UNION ALL）。功能全对，测试环境数据少也不慢，上线后数据库总负载翻几倍。
根源
路由只能用解析出来的分片条件，没有就全路由。
做法
接口能拿到 user_id 就带上（第 4 条回到 1 条）；只拿订单号的，用订单号基因或映射表（下一页）；按商家查的交给 ES。测试环境开 sql-show，把“一条逻辑 SQL 变成几条”当成检查项。
3分片键被函数或表达式包住← ④ 机制 1 解析
现象
⑤ 第 8 条：WHERE user_id + 0 = ? 结果正确，但问了 8 张表。实际代码里常见的是 CAST(user_id AS CHAR) = ?、ORM 生成的类型转换。
根源
解析器认得出“列 = 值”，认不出“表达式 = 值”，算不出路由。和 MySQL 里索引列套函数就用不上索引是同一个道理。
做法
分片键只写成 列 = ? 或 列 IN (…)。
4分片键上的范围查询直接报错← ④ 机制 1 路由
现象
⑤ 第 7 条：user_id BETWEEN … 抛 Unsupported SQL operation … allow-range-query-with-inline-sharding is false。
根源
取模算法没法从一个范围推出“哪几张表”（范围跨过的余数可能是全部）。INLINE 算法默认拒绝，免得你在不知情时全路由。
做法
业务上真需要范围的，改用按范围设计的算法（比如按时间的 INTERVAL）；只是偶尔要的，打开 allow-range-query-with-inline-sharding: true，接受它全路由。
5想改分片键的值← ④ 机制 2 写进去就不变
现象
⑤ 第 9 条：Can not update sharding value for table 't_order'；改成原值（第 10 条）才允许。
根源
值一改，这一行应该住在另一张表；一条 UPDATE 做不到“从这张表删、往那张表插”。
做法
分片键选不会变的字段。业务上真要“把订单转给另一个用户”，写成删除加插入两步，并想清楚中间失败怎么办。
6还用 AUTO_INCREMENT 当主键← J09 分布式 ID
现象
（按机制推演，没单独跑）8 张表各自从 1 开始自增，t_order_0 和 t_order_1 里都有 id = 1。按 id 查会查出两单，迁移时主键冲突。
根源
自增计数器是每张表自己的，表和表之间互不知道。
做法
应用生成全局唯一的号：号段或雪花（J09）。ShardingSphere 也内置了 SNOWFLAKE 等 key 生成策略。订单号最好再嵌入分片位（基因法），下一页讲。
75.5.3 只加了 shardingsphere-jdbc，启动就报错历史原因：5.5.3 起插件拆包
现象
⑤ 搭环境时依次撞到四个：Invalid tag: !SHARDING；StorageUnit 里的 NullPointerException；SPI-00001 … ContextManagerBuilder；SPI-00001 … PrivilegeProvider with type 'ALL_PERMITTED'。sql-show 也没输出，因为 logger 名字变成了 org.apache.shardingsphere.sql（老文章里是 ShardingSphere-SQL）。
根源
5.5.3 的 shardingsphere-jdbc 只带内核，官方文档“可选插件”一页列出了分出去的包。
做法
一次配齐：shardingsphere-sharding-core、-broadcast-core（用全局表时）、-jdbc-dialect-mysql、-infra-data-source-pool-hikari、-standalone-mode-core + -standalone-mode-repository-memory、-authority-simple；用 jdbc:shardingsphere:classpath: 的 URL 再加 -infra-url-classpath。⑤ 的 pom.xml 可以直接抄。
8选了一个分布不均的分片键← ④ 机制 2 均匀
现象
试验台：按 shop_id 分，最大那张表比平均多 47%；按季度分，所有新订单写同一张；雪花号原样取模，低峰时只落 2 张表。
根源
分片只保证“同一个键去同一张表”，不保证每张表一样多：键本身的分布不均，表就不均。
做法
选取值多、每个值的数据量都小的键（用户 ID 比商家 ID 好）；用雪花号分片前先哈希，或者嵌入基因；上线后监控每张真实表的行数和写入量。

第二圈 · 团队里怎么写

  • DAO 签名访问分片表的方法，参数里显式带上分片键（findOrders(long userId, …)）。防的是坑 2：没带分片键的写法在 code review 里一眼可见。
  • 测试开 sql-show集成测试里统计“一条逻辑 SQL 变成几条真实 SQL”，超过 1 条的列出来逐条确认。防的是坑 2、3 这种“结果对、只是慢”的问题。
  • 规则只此一份分片规则放在配置中心或共享的配置文件里，所有服务、迁移任务、对账脚本用同一份。防的是迁移脚本自己算了一套路由，和应用对不上。
  • 主键全局生成主键由应用生成，带分片基因。防的是坑 6。
  • 不做跨库事务同一个用户的订单和明细在同一个库，靠本地事务；需要跨用户、跨库的写（比如转单），走 J09 的最终一致方案。防的是把 XA 当成默认，吞掉性能。
  • DDL 统一下发加字段、加索引通过 ShardingSphere 的逻辑 DDL 或统一工具对 8 张表一起做，并核对每张表的结构一致。防的是“7 张表加上了、1 张没加”。

第三圈 · 深处

  • UNION ALL 合并⑤ 里有个细节：只按订单号、按商家查时，同一个库的 4 张表被合成了一条 UNION ALL；跨片分页那条却是一张表一条。源码（RouteSQLRewriteEngine）里的条件是：SELECT 语句、同一个库路由到不止一张表、没有 DISTINCT、子查询、JOIN、ORDER BY、分页和加锁子句。合并以后每个库只要一个连接、一次往返；上限由 max-union-size-per-datasource 控制（默认不限，设成 1 就不合并）。另一个相关参数 max-connections-size-per-query（默认 1）管的是一次查询在每个库最多用几个连接，调大以后各张表并行查，换来更快、付出更多连接，文档要求这时驱动支持流式读取。
  • 连接数应用层分片的连接数 = 实例数 × 库数 × 每个池的大小。订单服务从 6 个实例扩到 30 个、库从 2 个扩到 8 个时，每台 MySQL 看到的连接数会涨 5 倍，要先算 max_connections。这是很多公司在实例多了以后改用 Proxy 的原因。
  • 扩容的两种路表数不变、整张表挪库（机制 4），只要拷贝和切换；表数要变时（8 → 16），一半的行要换表，等于再做一次在线迁移。所以规划时宁可表多一些。
  • 分区表配分表MySQL 分区表和分库分表可以叠加：每张真实表再按月分区，删旧数据用 DROP PARTITION，比 DELETE 快得多。前提是每个唯一索引都包含分区键。

自测

1. 用一句话说出这一页的精华

分库分表是唯一能同时分摊写入和数据量的办法，代价是每条 SQL 都要先回答“在哪张表”；所以分片键要选覆盖最多查询、分布均匀、写入后不变的字段，ShardingSphere 在 JDBC 层替你解析、路由、改写、执行、归并。

2. 读写分离、加缓存、升级机器，为什么都替代不了拆分？

读写分离只分摊读，每台从库照样要回放全部写入；缓存只挡热点读；升级机器有上限、越来越贵，而且数据量涨了恢复时间照样变长。只有把数据分到多台主库，写入能力和单实例数据量才同时降下来。

3. 坑 2（全路由）的根源是 ④ 的哪条？

机制 1 第 ② 步：路由只能用解析时看得见的分片条件。条件里没有分片键，就只能所有表都问一遍。

4. 预测：靶场的规则下，执行 SELECT COUNT(*) FROM t_order WHERE user_id IN (1024, 1032, 1040)，会发出几条真实 SQL？

1 条。1024、1032、1040 对 8 取余都是 0，都在 ds_0.t_order_0；路由对 IN 的每个值分别算，结果合并成同一张表。（⑤ 的代码里第 6b 条就是它，实测 1 条：ds_0 ::: SELECT COUNT(*) FROM t_order_0 WHERE user_id IN (?, ?, ?)。）

5. 预测：两年后要从 2 个库扩到 4 个库，表还是 8 张。按机制 4 的做法，哪些行要换表？

一行都不用换表。库号从 slot % 2 改成 slot % 4，t_order_2、t_order_6 整张搬到 ds_2，t_order_3、t_order_7 整张搬到 ds_3；表名和每行所在的表不变，只是整表复制再切换。如果一开始是“库 % 2、表 % 4”那种各取各的规则，就做不到这么干净。

6. 放回全景：第 2 站前后各发生了什么？如果第 2 站选错了分片键（比如选了 shop_id），后面哪几站会出问题？

之前：第 1 站确认单表扛不住、便宜的招已经用完；之后：第 3 站开始双写，按这个规则往新表里写。选了 shop_id：第 6 站 1024 的“我的订单”要问 8 张表，而这是 App 里最多的查询；大商家所在的表又胖又热；第 9 站倒是不用 ES 了。最糟的是规则一旦随第 3～5 站的迁移落地，想换分片键就要再迁一次。

档位：标准。本机跑过（2 核 ARM 虚拟机，JDK 17，ShardingSphere-JDBC 5.5.3，MySQL 8.4.13 容器，HikariCP 6.3.3）：⑤ 的 12 条 SQL 和 spread 各跑 1 次，页面上的真实 SQL 和报错信息都来自这次输出。分片键试验台是模拟（node 里跑过）；坑 6 按机制推演，没单独跑。

按文档和源码：ShardingSphere 5.5.3 文档“可选插件”（分片、广播、方言、连接池、单机模式仓库、权限实现都是单独的包）、“属性配置”（sql-show 的 logger 是 org.apache.shardingsphere.sql，max-connections-size-per-query 默认 1）；源码 SQLLogger、StorageUnit、RouteSQLRewriteEngine（UNION ALL 合并的条件，max-union-size-per-datasource 默认不限）。B+ 树层数按 16 KB 页、约 1170 个指针估算。

按设计：分片规则、靶场的行数和写入峰值、查询占比，是交易靶场的设计数字。
