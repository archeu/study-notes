1.2 亿行搬进 8 张表，App 不停：不停机数据迁移

不停机迁移的核心只有一句话：在任何时刻，都有一边保存着完整、最新的数据，而且读写开关能拨回去。为此把迁移拆成几个可以单独回退的阶段：先双写（旧表为主），再分批搬历史，再校验到差 0，然后先切读、后切写，切写以后旧表还要被反向双写一段时间。最容易出事的不是哪个阶段本身，而是阶段之间的竞态：搬运读到的旧值覆盖了双写刚写好的新值，两次更新到达新表的顺序反了。所以写新表要带版本保护，搬运永远不覆盖，最后靠校验兜底。

①要解决的问题：数据要搬，流量不能停，错了要能退

在全景第 3～5 站，这一步要解决三件事同时成立：

1. 不停服

迁移要好几周（搬 1.2 亿行、校验、灰度），这期间每秒都有人下单、付款、发货。不能挂“系统维护中”。

2. 不丢、不错

搬的时候旧表还在变：一单从“待支付”变成“已支付”，新表最后也必须是“已支付”，不能停在搬运那一刻的旧值。

3. 随时能退

新表、新代码、新的分片 SQL 都可能有没测到的问题。任何一步发现不对，都要能在几秒内回到旧表，而且回去时数据是完整的。

地图上这一站“怎么算过关”的第一条就是它：迁移的任何时刻都能回滚，说出靠什么。

②不用它会怎样：停机迁移算一笔账

停机迁移的一步要多久 / 风险
停写、导出 1.2 亿行按 ⑤ 里实测的搬运速度（4000～6500 行/秒，批间限速、2 核虚拟机、同时有业务流量）粗算，1.2 亿行光搬就要 5～8 小时；生产机器快几倍，也还是小时级的停服。
校验停着机校验，越仔细停得越久；为了赶时间往往只比行数。
切换一次全切：新代码、新表、新 SQL 同时上线，任何一处有问题都影响所有人。
回滚切过去以后新产生的订单只在新表里，回到旧表就丢了这部分。所以实际上“切了就回不去”，只能硬着头皮修。

停机迁移的问题不只是停多久，更在于它把所有风险压在一个不可逆的时刻。不停机迁移把这个时刻拆成很多个小步，每一步都可逆，每一步都有数据说明能不能往下走。

不懂精华时的典型误用把“双写”当成迁移的全部：代码里写两遍，搬完数据就切。双写本身不保证一致（两个库没有共同的事务），搬运和双写之间还有竞态；没有校验和回滚开关的双写，只是把停机迁移的风险换了个时间点爆发。

③几种流派：增量怎么跟上

搬历史数据（全量）的做法都差不多：按主键分批读、写。差别在搬运期间的变化（增量）怎么同步过去。

增量同步怎么做好处代价
应用双写写旧表的代码后面再写一遍新表（经过 ShardingSphere）完全可控；切写以后改成“新为主、反向写旧”就是现成的回滚通道要改所有写入点；漏一个写入点（批处理、运维脚本）就漏数据；两库没有共同事务
binlog 增量同步（CDC）读旧库的 binlog，按新规则写进 8 张表（Canal、阿里云 DTS、Debezium）业务代码不用改；所有写入（包括手工 SQL）都会被捕获；顺序和 binlog 一致多一套同步链路要运维；切写以后的反向同步要再搭一条；延迟要盯
中间件自带的迁移ShardingSphere-Proxy：MIGRATE TABLE → CHECK MIGRATION → COMMIT MIGRATION（全量 + 增量 + 校验）一条命令串起全量、增量和校验要上 Proxy 和它的集群模式；切换窗口里要短暂停写
停机迁移停写、导出、导入、切换最简单，没有一致性问题停服小时级，切了就回不去（②）

选择规则：写入点集中、团队能改代码 → 应用双写；写入点分散、多个服务和脚本都写这张表 → binlog 同步。交易靶场的订单写入都在 order-svc 的一个 Repository 里，用应用双写，本页学它；binlog 那条路的机制在第 5 页（MySQL 到 ES 的同步）细讲，两者的竞态和校验思路是一样的。

④核心取舍：每一步都有一边是完整的，开关能拨回去

先知道这些 新表的规则：user_id % 8，2 库 8 表，见 第 1 页。迁移的写入都经过 ShardingSphere，校验直接查 8 张真实表。 主键由应用生成：两边用同一个 id，才能逐行对上。如果新表自己 AUTO_INCREMENT，迁移就无从比对，见 分布式 ID。 配置中心：读写开关放在 Nacos 这类配置中心，所有实例同时生效，见 Nacos。

机制 1：七个阶段，谁是主、读哪边、怎么退

为什么先切读、后切写：读没有副作用，切错了拨回去，什么都没坏；写一旦以新表为主，新表上产生的数据就要想办法回到旧表。为什么切写以后还要反向双写：它让“回到旧表”在 D+3 到 D+14 之间仍然是无损的。停写旧表是整个迁移唯一不可逆的一步，所以放在最后，而且要等新表在全量流量下稳定跑过一段时间。

机制 2：搬运和双写之间的竞态

naive：谁后到谁算

双写用普通 upsert，搬运也用 upsert 覆盖。⑤ 实测：迁移期间改了 7024 次状态，校验找出 95 行状态倒退。

safe：新的才算，搬运不碰已有的

双写带版本保护：IF(VALUES(version) > version, …)；搬运用 INSERT IGNORE：新表已经有这一行，说明双写写过，比搬运手里的更新。⑤ 实测：状态倒退 0 行。

决定胜负的约束：两个库之间没有共同的事务，写入到达新表的顺序不可控。所以不能靠“先后顺序”保证正确，只能让每次写入自己判断“我是不是更新的那个”：版本号（或更新时间）就是这个判断的依据，搬运则干脆约定“永远让位于双写”。即便如此，新库写失败这种事还会发生，只能靠机制 3 的校验兜底。

机制 3：分块校验，先粗后细

  • 分块按主键切成块（⑤ 每块 1 万个 id），每块在旧表算一次 COUNT(*) 和 BIT_XOR(CRC32(CONCAT_WS('#', id, user_id, status, version, amount_cents)))。
  • 新表合并同一个 id 范围在新库的 8 张真实表各算一次：行数相加，校验和再异或一次。异或满足交换律和结合律，8 份结果怎么合都等于“把这些行放在一张表里算”，所以两边能直接比，不用把行拉出来。
  • 逐行比只有对不上的块才把两边的行拉出来逐行比，分出“缺行”“版本更旧”“其他不一致”，以旧表为准修复，再校验一遍。
  • 流量还在跑时正在被改的行两边可能暂时不一致（双写还没到）。生产上对不上的块隔几秒再比一次，两次都对不上的才算真问题；⑤ 为了数字干净，是停了流量再校验的。
  • 只比行数不够⑤ 里状态倒退的行，行数一点不差，只有校验和能发现。

机制 4：开关怎么做

  • 放在配置中心migration.read.newPercent、migration.write.primary 两个开关放在 Nacos，所有实例几百毫秒内同时变；不要放在各实例的本地配置里，否则会有实例读新、有实例读旧。
  • 按用户灰度user_id % 100 < 读比例 的用户读新表。同一个用户每次落在同一边，不会这次看到新表、下次看到旧表。
  • 影子读灰度用户读新表的同时，再读一次旧表对比，不一致就打点报警（结果仍以新表返回，或者干脆先以旧表返回）。⑤ 切读 10% 时对比了 209 次，不一致 0 次。
  • 切写写主拨到新表以后，代码变成“先写新表，再反向写旧表”。反向写失败同样只记日志、靠校验补。

    if (sw.writePrimary() == OLD) {
        oldDao.update(o);                         // 主：失败就抛，下单失败
        try { newDao.upsertIfNewer(o); }          // 跟随：版本更大才覆盖

    } else {
        newDao.upsertIfNewer(o);                  // 切写以后反过来
        try { oldDao.upsertIfNewer(o); } catch (Exception e) { compensationLog.add(o.getId(), e); }
    }
}

⑥反例和误用

第一圈 · 不知道就会出事

1搬运用旧值覆盖了双写写好的新值← ④ 机制 2
现象
⑤ naive：95 行订单在新表里停在更早的状态（比如已发货变回已支付）。行数一点不差。
根源
搬运读出一批到写进去之间有时间差，这期间旧表上的行被改了，双写已经把新值写进新表，搬运又用手里的旧值覆盖。
做法
搬运只插不改（INSERT IGNORE）：新表已有的行一定是双写写的，比搬运手里的新。
2同一单两次更新，到达新表的顺序反了← ④ 机制 2
现象
旧表上 v3、v4 依次提交，写新表时 v4 先到、v3 后到，新表停在 v3。⑤ naive 的 95 行倒退里有一部分是这种（热点订单被连着改），另一部分是坑 1；这一轮没有把两者分开计数，↺ 练习 1 可以分开量。
根源
两个库没有共同事务，旧表提交和写新表之间有网络抖动，两个线程的写入在新表上的先后不可控。
做法
新表写入带版本保护：ON DUPLICATE KEY UPDATE status = IF(VALUES(version) > version, VALUES(status), status), …, version = GREATEST(version, VALUES(version))，version 放最后改。
3以为“写失败记日志、事后重放”就够了← ④ 机制 3
现象
⑤ 两轮都注入了写失败，最后各缺 3 行、2 行，只有校验找出来了。生产上还会有日志本身没写成功、重放顺序不对、重放时又失败的情况。
根源
补偿日志和业务写入也不在一个事务里，它只能减少不一致，不能消除。
做法
补偿日志照做，但切换的依据是校验结果，不是“日志都重放完了”。
4读写一起切，或者切写的同时停写旧表← ④ 机制 1
现象
切换后发现新表有问题，想回去，旧表从切换那一刻起就没再更新，回去等于丢掉这段时间的订单。
根源
跳过了“读已切、写未切”和“写已切、旧表被反向双写”两个可回退的阶段。
做法
先切读、观察；再切写，同时打开反向双写；新表在全量流量下稳定跑一两周、反向双写的旧表校验也一直对得上，才停写旧表。
5流量没停时校验，报了一堆“不一致”← ④ 机制 3
现象
（按机制推演）校验读旧表那一刻和读新表那一刻之间，正好有行被改了，看起来对不上，其实双写马上就到。
根源
两边不是在同一个快照上比的。
做法
对不上的块隔几秒重比，两次都对不上才算；逐行修复前再读一次旧表；或者跳过最近几秒内更新过的行（看 updated_at）。
6搬运太快，把主库或从库打满← ③ 全量搬运
现象
搬运按主键全速扫，主库 IO 和 CPU 冲高，下单变慢；从库回放跟不上，读从库的接口读到旧数据。
根源
搬运和业务共用同一个库。
做法
从从库读、往新库写；每批之间停顿（⑤ 停 30 ms），盯着主从延迟和主库负载动态调速，大促期间暂停。
7漏了一个写入点← ③ 应用双写的代价
现象
订单服务双写了，可还有一个对账任务、一个运维脚本直接 UPDATE t_order，这些修改只进了旧表。
根源
应用双写只覆盖改过的那段代码。
做法
迁移前用 binlog 或 performance_schema 统计有哪些账号、哪些应用在写这张表；收拢写入点，收不拢的改用 binlog 增量同步。

第二圈 · 团队里怎么做

  • 迁移手册每个阶段写清：进入条件（比如“校验差 0 且持续 24 小时”）、操作、观察指标、回滚动作、谁有权拍板。防的是凭感觉往下走。
  • 开关演练正式切换前，在预发和生产各演练一次“拨过去、拨回来”，确认所有实例同时生效。防的是关键时刻开关不灵。
  • 持续校验校验不是做一次：从开始双写到停写旧表，每天跑全量分块校验，切读后加上影子读对比。防的是坑 3、5。
  • 迁移期间冻结表结构两边都不做 DDL；必须做的，新旧两边一起做、校验字段一起改。防的是 CONCAT_WS 里少了一列、校验悄悄失效。

第三圈 · 深处

  • 为什么是版本号而不是时间用 updated_at 比较也行，但两个应用实例的时钟可能差几毫秒，同一毫秒内的两次更新也分不出先后。单调递增的版本号由旧表的行锁保证顺序，更可靠，这和 时钟与超时那页讲的是一回事。
  • binlog 路线怎么防竞态按 binlog 顺序回放天然保证了同一行的先后；全量搬运和增量回放之间的衔接，靠“先记下 binlog 位点、再开始全量，全量完成后从位点回放增量，回放要幂等”。gh-ost、ShardingSphere 的迁移任务、各家 DTS 都是这个结构。
  • 反向双写的另一个用处切写以后，旧表还能继续服务那些暂时没改造完的报表、对账程序，让它们慢慢迁。

自测

1. 用一句话说出这一页的精华

任何时刻都有一边完整、最新，读写开关能拨回去：双写（旧为主）→ 搬历史 → 校验到差 0 → 先切读 → 再切写（旧表被反向双写）→ 最后才停写旧表；写新表带版本保护、搬运只插不改、切换以校验结果为准。

2. 停机迁移最大的问题是什么？

不只是停服几个小时，而是把全部风险压在一个不可逆的时刻：切过去以后新订单只在新表，回到旧表就会丢，等于没有回滚。

3. 坑 1 的根源是 ④ 的哪条？为什么 INSERT IGNORE 能解决？

机制 2：搬运读出和写入之间旧表被改，双写已写入新值，搬运用旧值覆盖。INSERT IGNORE 让搬运在新表已有该行时什么都不做；而新表已有的行只可能是双写写的，一定不比搬运手里的旧。

4. 预测：safe 模式下，如果双写对“新表里还没有这一行”的情况用的是 UPDATE … WHERE id = ?（不是 upsert），会出什么问题？

搬运还没搬到的行，UPDATE 影响 0 行，什么都没写；之后搬运用 INSERT IGNORE 插入它读到的版本。如果搬运是在这次更新之前读的，就插入了旧值，而且以后不会再被纠正（直到下一次更新或校验）。所以双写要用 upsert 写整行：行不存在就插入当前最新值。

5. 预测：D+5 已经切写，发现新表上一批订单金额算错了（新代码的 bug），回滚到旧表能解决吗？

能回，但要先修数据：反向双写把新表上算错的金额也写进了旧表，直接拨回去，旧表上也是错的。要先用校验找出这批行、按正确逻辑修好两边，再决定是否回滚（推演台里选“切写 + 新表数据不对”）。

6. 放回全景：第 4 站前后各发生了什么？如果第 4 站的校验只比了行数，第 5 站切读时会怎样？

之前：第 3 站打开双写（旧表为主）；之后：第 5 站先切读再切写。只比行数：状态倒退的那些行（⑤ naive 是 95 行）不会被发现，切读后灰度用户看到“已发货的订单变回已支付”；影子读能报出来，如果连影子读也没做，就要等用户投诉，这时如果已经切写，问题就更难退回。

档位：标准。本机跑过（2 核 ARM 虚拟机，JDK 17，ShardingSphere-JDBC 5.5.3，MySQL 8.4.13 容器，旧表 20 万行）：⑤ 的 naive、safe 各完整跑 1 次，页面上的计数、速度、校验结果都来自这次输出。回滚推演台是按 ④ 阶段表写的纯函数（node 里跑过）。坑 5、6、7 按机制推演。

按文档：ShardingSphere-Proxy 数据迁移（MIGRATE TABLE、CHECK MIGRATION、COMMIT MIGRATION）；MySQL 8.4 的 INSERT … ON DUPLICATE KEY UPDATE 里 VALUES() 仍可用（已标为弃用）；BIT_XOR、CRC32。

按设计：迁移日程、灰度比例、批大小和限速、注入的失败率，是交易靶场的设计数字。
