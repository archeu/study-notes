为什么新建一个连接这么贵

打通一条连接，两边要来回好几趟，数据库那头还得专门安排一个线程或进程来伺候它。

1TCP 握手来回一趟网络

MySQL：一个连接一个线程

连接 1 → 线程连接 2 → 线程连接 3 → 线程…

线程比进程轻，但每个也要占内存和调度。默认 max_connections = 151。

PostgreSQL：一个连接一个进程

连接 1 → 进程连接 2 → 进程连接 3 → 进程…

每个后端进程都要占几 MB 内存，建得更慢。默认 max_connections = 100，连接多的场景常在前面再加一层 PgBouncer。

池子开多大：不是越大越好

先算清楚“要多少”，再想清楚“数据库扛多少”。两个数里取小的。

要多少：利特尔法则

同时占用的连接数 = 每秒请求数 × 每次占用多久
1000 次/秒 × 5 ms平均只占 5 个连接，池子 10 个绰绰有余 1000 次/秒 × 205 ms要占 205 个，因为事务里多了一个 200 ms 的外部调用

反过来算上限：10 个连接、每次占 205 ms，每秒最多只能服务 10 ÷ 0.205 ≈ 49 次。

扛多少：数据库的核数

连接数 ≈ CPU 核数 × 2 + 有效磁盘数

这是 HikariCP 文档引用的、来自 PostgreSQL 社区的经验公式。8 核 + SSD 的库，起步十几到二十个就够了。

这是整个数据库的总数。10 台应用实例各开 20 个，数据库那头就是 200 个。

CPU 就那么几个核

8 核同一时刻最多真正跑 8 个查询，多出来的连接只是在排队，还要来回切换。

锁和缓冲区更挤

同时改的人越多，抢同一把锁、同一块内存页的冲突越多，每个人都变慢。

内存被吃掉

PostgreSQL 每个连接一个进程，排序、哈希还各自要 work_mem，几百个连接能把内存吃光。

事务怎么吃掉连接

Spring 在进入 @Transactional 方法时就借走连接，直到提交才还（MyBatis 第 02 篇）。方法里干的所有事，哪怕跟数据库无关，都算在占用时间里。

整个方法包在事务里

只把写库那两步包进事务

方法
调支付接口 200 ms（事务外）
占着连接

每次只占 6 ms，同一个池子能多扛三十多倍

事务里别做慢事

调 HTTP 接口、发消息、上传文件、复杂计算，都挪到事务外面。事务里只留读写数据库的几步。

单条查询不用包事务

不加 @Transactional，MyBatis 每条 SQL 借一下就还。加了事务，还要多一次开始和提交的来回。

readOnly 不是白给的

readOnly = true 让数据库少做点事，比如 InnoDB 不用分配事务 ID；但驱动可能多发一条设置语句。多条查询要看到一致的数据时再用。

数据库那一头：提交、版本和锁

一个事务在数据库里的成本，主要是三样：提交时等日志落盘、改过的数据留着旧版本、改过的行一直锁着。

插 1000 行，每行自己一个事务

1000 次提交 = 1000 次等日志写到磁盘。MySQL 默认 innodb_flush_log_at_trx_commit=1，PostgreSQL 默认 synchronous_commit=on，都是每次提交都要落盘。

1000 行放进一个事务，批量发

只落盘 1 次。再配上批量改写（MySQL 的 rewriteBatchedStatements=true，PostgreSQL 驱动的 reWriteBatchedInserts=true），网络来回也少了。

JDK 8 和 JDK 17

连接池和事务的原理两边完全一样。变的是 HikariCP 的版本，以及虚拟线程带来的一个误会。

Spring Boot 2

JDK 8+
  • 默认连接池就是 HikariCP，Boot 2.7 用的是 4.0.3，也是支持 JDK 8 的最后一个版本
  • 配置写在 spring.datasource.hikari.*

Spring Boot 3

JDK 17+
  • HikariCP 5.x 起要求 JDK 11+，Boot 3 用的是 5.x 及以后的版本，配置项不变
  • JDK 21 的虚拟线程能让 Tomcat 同时挂起成千上万个请求，但数据库连接还是那几个。开了虚拟线程，池子照样是瓶颈：等连接的从几十个线程变成几千个虚拟线程
没变的：连接贵，所以要池池子不是越大越好事务从头占到尾提交要落盘长事务拖累整个库

常踩的坑

看到慢或者报错，先问两件事：连接够不够用？每个连接被占了多久？

Connection is not available, request timed out after 30000ms

池子被借光了，30 秒没等到。查慢 SQL、长事务、连接泄漏，最后才考虑加大池子。

Connection leak detection triggered for … on thread …

有人借了连接没还，多半是自己 dataSource.getConnection() 后没放进 try-with-resources。日志后面跟着借走时的调用栈。

池子从 20 加到 200，反而更慢了

数据库的核数没变，多出来的连接只是在抢 CPU 和锁。先把每次占用的时间降下来。

平时好好的，一到高峰全部超时

事务里调了外部接口，对方一慢，连接全被占着。把外部调用挪出事务。

Too many connections / FATAL: sorry, too many clients already

实例数 × 每个实例的池子大小，超过了数据库的上限（MySQL 默认 151，PostgreSQL 默认 100）。扩容时别忘了这笔账。

Possibly consider using a shorter maxLifetime value.

连接在池子里放太久，被数据库（MySQL 默认 wait_timeout 8 小时）或中间的防火墙悄悄断了。max-lifetime 要比它们都短。

导入 10 万行要好几分钟

每行一个事务、每行一次网络来回。放进一个事务分批提交，打开批量改写参数。

导出报表时 OutOfMemoryError

驱动默认把整个结果集读进内存。用流式读取（fetchSize），或者按主键分批查。

库越来越慢，查不出是哪条 SQL

看看有没有开了很久没提交的事务：MySQL 查 information_schema.innodb_trx，PostgreSQL 查 pg_stat_activity 里的 idle in transaction。

接了 PgBouncer 后报 prepared statement "S_1" does not exist

事务池模式下，同一个会话的语句可能落到不同的后端连接上。升级到支持预编译语句的 PgBouncer（1.21+）并配好，或在 JDBC 里设 prepareThreshold=0。
