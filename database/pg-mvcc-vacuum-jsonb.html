订单表一行没加，PG 里却胖了一倍：PostgreSQL 的多版本、VACUUM、索引类型和 JSONB

同一张 100 万行的 orders，整表 UPDATE qty = qty + 1 一次：PostgreSQL 里表从 159 MB 涨到 319 MB，两个索引也各涨一倍。因为 PG 从不原地改一行，它写一个新版本，旧版本留在表里，等 VACUUM 来清。MySQL 把旧版本放进 undo，表本身不胖。这一页的精华是：PG 把 MySQL 的 undo 搬进了表本身。回滚和读旧版本因此变得简单，代价是表里会积垃圾，得有人一直扫。不懂这一点，把 MySQL 的习惯原样搬过来（长事务、反复改同一行、哪一列都建索引），表和索引就会越来越胖，查询越来越慢。

①为什么需要：同一条付款 UPDATE，旧值去了哪

在全景第 7 站，InnoDB 改 9527 之前先把旧值 CREATED 写进 undo，这样别人还能读到旧版本，回滚也有据可查。交易靶场给 J06 的任务里有一句“把同一张表导进 PostgreSQL，跑同样的 SQL”。导过去以后，同一条付款 UPDATE，旧值放在哪？AI 项目里常用的 pgvector、Dify 这类平台，底下都是 PG，迟早要碰上它。

整表 UPDATE 一次159 → 319 MB表；主键索引 21 → 43 MB
VACUUM（0.7～1.2 s）319 MB一点没缩，空出 50.4% 可复用
VACUUM FULL（3.8 s，锁表）159 MB重写整张表才缩回去
报表事务开着时2 万个删不掉dead but not yet removable

②没有它会怎样：把 MySQL 的习惯原样搬到 PG

这里的“老办法”就是你在 MySQL 上养成的用法。它们在 MySQL 上没事，搬到 PG 上各有各的疼法。

长事务、连接上挂着没提交的事务

  • MySQL 上也不好，但主要是 undo 变长、旧快照读得慢。
  • PG 上它开着的这段时间里，整个库作废的旧版本 VACUUM 一个都删不掉。实测：报表事务开着，9527 被改 2 万次，VACUUM 报告 20000 are dead but not yet removable。
  • 不光它自己慢，新连接按主键读 9527 也要扫 412 个页，平时只要 4 个。

反复改同一行、改带索引的列

  • InnoDB 原地改，计数器、状态字段改多少次，表都不变大。
  • PG 每改一次写一个新元组。页满了，新元组去别的页，每个索引都要再插一条。实测：一行改 2 万次，表多出 409 页（3.2 MB），VACUUM 之后也不还。

以为 VACUUM 就是 OPTIMIZE TABLE

  • 想让表变小，跑一下 VACUUM 就行？
  • VACUUM 只是把死元组的位置标成可复用，表的文件一字节不缩（实测 319 MB → 319 MB）。真要缩，得 VACUUM FULL 或 pg_repack，前者整个过程锁表。
  • 反过来，把 autovacuum 关掉“省性能”，就是在攒越来越大的账。

缺的那一块：MySQL 里旧版本放在 undo，由 purge 线程在后台默默清掉，你几乎感觉不到它。PG 里旧版本就在表里，谁来清、什么时候清、什么在挡着清，是用 PG 必须懂的事。

③相邻方案：旧版本可以放在哪

只要支持“读不挡写”的 MVCC，旧版本就得存在某个地方。主流做法有两种。

原地改 + undo
InnoDB、Oracle		新版本写进表，旧的留着
PostgreSQL 的堆表
UPDATE 做什么改行；旧值写进 undo，行里留回滚指针插一个新元组，旧元组写上 xmax
读旧版本沿 undo 链往回拼，越旧越远（MySQL 页实测：链长 2 万时旧快照读要 14.21 ms）旧版本就是一个完整的元组，直接读
回滚按 undo 把改动逐条撤回去，大事务回滚很慢只在提交日志（pg_xact）里记一笔“中止”，新元组自然作废，瞬间完成
表会不会胖基本不会，undo 另算会，死元组留在表里，要 VACUUM
索引二级索引存主键，改非索引列不碰索引索引存 ctid，新元组换了位置就要改每个索引（除非 HOT）
谁来清purge 线程，基本不用管页内修剪 + VACUUM / autovacuum，要会调、会监控

还有别的做法，比如 SQL Server 的快照隔离把旧版本放进 tempdb 里的 version store。PG 社区也试过 undo 式的存储（zheap 项目），没有进主线。选择规则：你没得选，用 PG 就是堆表这一套。本页学 PG 的这种，并且一直拿 InnoDB 对照。

④原理：元组、可见性、谁来清、HOT、索引和 JSONB

先知道这些
  • 堆表（heap）：PG 的表是一堆 8 KB 的页，行按写入的先后放进有空位的页，没有 InnoDB 那样“表就是主键 B+ 树”的聚簇索引。主键索引和别的索引一样，叶子里存的是行的物理位置。InnoDB 的聚簇索引见索引与 B+ 树。
  • ctid：行的物理位置，写作 (页号, 槽位号)，比如 (194,21)。PG 里一行数据的每个版本叫一个元组（tuple）。
  • xid：事务号，32 位，每个写事务领一个。pg_xact（以前叫 clog）记着每个 xid 是提交了还是中止了。
  • 快照：和 InnoDB 的 ReadView 一回事，记下“拍快照那一刻，哪些事务已经提交”。见事务、MVCC 与锁。

④-1 每个元组自带“出生”和“死亡”的事务号

页的开头是一排槽位指针（line pointer），从前往后长；元组从页尾往前放。每个元组头上有三样东西：t_xmin 是插入它的事务，t_xmax 是删除或取代它的事务（0 表示还活着），t_ctid 指向它的下一个版本（自己就是最新版时指向自己）。UPDATE 等于“给旧元组写上 xmax，再插一个新元组”。

④-2 看得见哪个版本：拿 xmin、xmax 对快照

读一行时，PG 把这一行能找到的每个元组都拿来对一遍快照：

  • xmin 已提交，并且在我的快照之前，这个元组对我“出生”了。
  • xmax 是 0，或者那个事务中止了，或者它在我的快照里还没提交，这个元组对我还“活着”。
  • 两条都满足才看得见。所以付款事务（xid 759）没提交时，另一个连接读到的是 (194,21) CREATED：xmax 759 还没提交。
回滚为什么瞬间完成
事务中止，只需要在 pg_xact 里把 759 标成“中止”。新元组的 xmin 是中止的事务，谁也看不见；旧元组的 xmax 是中止的事务，等于没被删。表里一个字节都不用改回去。InnoDB 回滚要按 undo 一条条撤，MySQL 那页实测 30 万行的事务崩溃后要在后台回滚很久。

④-3 谁来清：页内修剪、VACUUM、VACUUM FULL

一个旧元组什么时候能清？要等到所有还开着的快照都不可能再看它。PG 只用一个数字判断：所有会话里最老的那个快照的 xmin，叫 xmin horizon。旧元组的 xmax 比它还早，就是“死透了”，能清；否则就是 dead but not yet removable。

页内修剪 prune

读或改到一个快满的页时，顺手把页里死透了的元组腾空。只动这一页，不碰索引；有索引条目指着的，只剩一个槽位指针。实测 COMMIT 后另一个连接读一次 9527，旧槽位就从“正常”变成了“死”。

VACUUM

扫表（只扫有变动的页），把死透的元组标成空位，删掉指向它们的索引条目，更新空闲空间图（FSM）和可见性图（VM）。不锁读写，不缩文件，只截掉表尾整页空的部分。

autovacuum

后台进程自动跑 VACUUM 和 ANALYZE。死元组数超过 50 + 0.2 × 行数 就触发，100 万行的表要攒到约 20 万个。18 起多一个上限 autovacuum_vacuum_max_threshold（默认 1 亿）。

VACUUM FULL

把活着的元组拷到一个新文件，索引全部重建，旧文件扔掉，表才真的变小。整个过程拿 ACCESS EXCLUSIVE 锁，这张表读写全停。实测 100 万行 3.8 s。

④-4 HOT：新版本留在同一页、索引一条都不加

每次 UPDATE 都给每个索引插一条，代价太大。PG 8.3 起有 HOT（heap-only tuple）：没改任何索引列，并且旧元组所在的页还放得下新元组，新元组就放在同一页，索引不动；顺着页内的 t_ctid 链就能从索引指着的老元组走到新元组。两个条件缺一个，就退回普通更新。

④-5 xid 只有 32 位：冻结和“回卷”

xid 是 32 位的，转一圈约 42 亿，PG 按“前 21 亿算过去、后 21 亿算未来”来比大小。一个很老的元组，它的 xmin 迟早会从“过去”转到“未来”，突然对所有人不可见。所以 VACUUM 还有一件事：把足够老的元组冻结（freeze），标成“对谁都算过去”。某张表最老的未冻结 xid 超过 autovacuum_freeze_max_age（默认 2 亿），哪怕关着 autovacuum，也会强制跑一次防回卷的 VACUUM；真要逼近 21 亿，PG 会拒绝再分配新 xid，库只能读不能写。InnoDB 的事务号是 48 位，没有这件事。

④-6 为什么这样设计

PG：多版本放在堆里 选了它

  • 源头：1980 年代的 POSTGRES 存储系统本来就是“不覆盖写”的设计，旧数据不覆盖，还能按时间回查（time travel，后来去掉了）。PG 在 2001 年的 7.1 才加上 WAL。
  • 回滚和崩溃恢复都简单：不用 undo，中止的事务在 pg_xact 记一笔就完事。
  • 任何版本都是完整元组，读旧版本不用往回拼。
  • 代价：表和索引会胖，要一直有 VACUUM 跟着清；每次非 HOT 更新要改所有索引，写放大。2016 年 Uber 从 PG 换回 MySQL 的那篇文章，主要理由之一就是这个写放大。

InnoDB：原地改 + undo 没选的那种

  • 表紧凑，改非索引列不碰二级索引（二级索引存的是主键，不是物理位置）。
  • 旧版本要沿 undo 链往回拼，链越长越慢；回滚要真的去撤；undo 本身也要 purge，长事务一样会让它胀起来。
  • 多一套日志（undo 也要写 redo）、多一个后台线程，实现更复杂。

决定胜负的约束：旧版本总得有地方放，也总得有人清。InnoDB 把它放进一个专门的地方，自动清；PG 放在原处，把“清”这件事交给 VACUUM。所以用 PG 时，“什么挡住了 VACUUM”是头号问题，用 MySQL 时它藏在 History list length 后面。

④-7 索引类型：不止 B-tree

InnoDB 基本只有 B+ 树（另有全文、空间索引）。PG 的索引是可插拔的“访问方法”，自带 6 种，扩展还能加（pgvector 的 HNSW、IVFFlat 就是这样加进来的）。下表的大小和耗时都是 100 万行 orders 上的 实测。

类型擅长什么本机实测
B-tree（默认）等值、范围、排序、唯一约束。18 起支持 skip scan，多列索引不带前导列也能用一部分created_at 上 21.4 MB；查一小时内的订单 0.86 ms（Index Only Scan，读 14 个页）。不建索引全表扫 67 ms
BRIN数据按顺序写入的大表（时间、自增 id）：每一段页只记最小值和最大值同一列只有 24 KB，是 B-tree 的约 1/900；查询 2.59 ms，要多读 313 个页再过滤掉 11696 行
GIN一个值里有很多“元素”：JSONB、数组、全文检索JSONB 包含查询从 165 ms 到 2.17 ms，见 ④-8
GiST / SP-GiST几何、范围类型、排除约束（比如“同一会议室时间段不能重叠”）、最近邻没测
Hash只有等值；10 起才写 WAL，一般用 B-tree 就够没测
部分索引
任何类型都能加 WHERE		只给一小部分行建索引，比如只索引待付款订单(user_id) WHERE status='CREATED'，1% 的行：136 KB，全量的 user_id 索引 11.1 MB
表达式索引索引一个表达式的结果，比如 lower(email)、JSONB 里的某个字段。MySQL 8.0.13 起也有（函数索引）((ext->'coupon'->>'code'))：6.6 MB，查询 1.71 ms

④-8 JSONB：拆开存的 JSON，配 GIN 查

json 类型原样存文本，每次查都要重新解析。jsonb 写入时就解析成二进制：去掉空白，键排好序，重复的键只留最后一个，查的时候直接定位。GIN 索引把每个文档拆成很多“键”，查询时先在 GIN 里找到含这些键的行，再回表核对。

最少的语法PostgreSQL 18；pageinspect、pgstattuple 是自带的扩展，要 CREATE EXTENSION
SELECT ctid, xmin, xmax, * FROM orders WHERE id = 9527;     -- 每行都有这几个隐藏列
SELECT n_live_tup, n_dead_tup, last_autovacuum
  FROM pg_stat_user_tables WHERE relname = 'orders';         -- 死元组多不多、上次什么时候清的
VACUUM (VERBOSE) orders;                                      -- 手动清，看 removed / not yet removable
ALTER TABLE orders SET (fillfactor = 90);                     -- 给 HOT 留空间（之后写入的页才生效）
CREATE INDEX ON orders USING gin (ext jsonb_path_ops);        -- JSONB 包含查询
SELECT count(*) FROM orders WHERE ext @> '{"channel":"app"}';
CREATE INDEX ON orders USING brin (created_at);               -- 按时间追加的大表
CREATE INDEX ON orders (user_id) WHERE status = 'CREATED';    -- 部分索引

放到 ⑥ 的细节：长事务怎么防、autovacuum 怎么调、fillfactor 定多少、JSONB 查询怎么写才能走索引、回卷怎么监控、版本差异。

坑 1一个没提交的事务，让整个库的旧版本都清不掉← ④-3 xmin horizon实测
现象
n_dead_tup 一直涨，autovacuum 跑了又跑，表还是越来越大；热点行的查询越来越慢。
根源
VACUUM 只能清比最老快照更早死掉的版本。实测报表事务开着、9527 被改 2 万次：20000 are dead but not yet removable；新连接按主键读 9527 从 4 个页涨到 412 个页（下图）。挡住 horizon 的不只是长事务，还有忘了提交的 idle in transaction 连接、没人消费的复制槽、从库开了 hot_standby_feedback 时从库上的长查询、没处理的两阶段提交事务。
做法
设 idle_in_transaction_session_timeout（比如 60s），17 起还有 transaction_timeout；监控 pg_stat_activity 里 age(backend_xmin) 最大的会话，以及 pg_replication_slots；报表走从库或用短事务。Java 里别在事务中间等外部调用。
坑 2以为 VACUUM 跑完表会变小← ④-3 VACUUM 只标空位实测
现象
一次大批量 UPDATE / DELETE 之后，磁盘报警；手动 VACUUM，大小纹丝不动。
根源
VACUUM 只把死元组的位置记进空闲空间图，留给以后的写入复用；只有表尾整页都空了才截掉。实测 319 MB → 319 MB，free_percent 50.4%，再整表改一遍，大小还是 319 MB。
做法
平时不需要缩：表在稳定的大小上复用空间就好。真要缩：VACUUM FULL（锁表，实测 100 万行 3.8 s，按表大小涨）或者 pg_repack 扩展（只在开头和结尾短暂加锁）。大批量删除改成分区表直接 DROP 分区。
坑 3热点行、计数器、索引太多：表和索引一直长← ④-4 HOT 的两个条件实测
现象
库存、余额、计数器这类一行被改成千上万次的表，体积远大于行数应有的大小，索引也一样。
根源
默认 fillfactor 100，页装满了，新版本只能去别的页，每个索引都要加一条。实测 fillfactor 100 改 1 万行 status，HOT 0 次；90 时 9092 次。改了有索引的列（user_id），HOT 一次都没有。
做法
频繁更新的表设 fillfactor 80～90；不给经常变的列建索引；看 pg_stat_user_tables 的 n_tup_hot_upd / n_tup_upd。高频计数先在 Redis 或内存里攒，再批量写回。
坑 4JSONB 建了 GIN，查询还是全表扫← ④-8 GIN 只认特定操作符实测
现象
建了 USING gin (ext)，可 WHERE ext->'coupon'->>'code' = 'C7' 还是 Parallel Seq Scan，112 ms。
根源
GIN 的 jsonb 操作符类只支持 @> ? ?| ?& @? @@。->> 取出来的是普通文本，GIN 里没有这样的键。
做法
写成 ext @> '{"coupon":{"code":"C7"}}'（实测 2.17 ms）；或者给这个字段建表达式索引（实测 1.71 ms）。天天按它查、按它排序的字段，干脆拆成普通列。
坑 5xid 回卷：库突然只能读不能写← ④-5 32 位 xid 和冻结按文档
现象
日志里先出现 “must be vacuumed within N transactions” 的警告，最后写入全部报错，库进入只读保护。
根源
冻结跟不上 xid 的消耗：autovacuum 被关、被长事务或复制槽挡住，或者大表的防回卷 VACUUM 太慢。
做法
别关 autovacuum；监控 SELECT datname, age(datfrozenxid) FROM pg_database，超过 10 亿就要查原因；写入量大的库给 autovacuum 更多资源（autovacuum_vacuum_cost_limit、worker 数）。
坑 6连接开得和 MySQL 一样多历史原因 · 每连接一个进程按文档
现象
几十个服务实例各开 50 个连接，PG 内存吃紧，FATAL: sorry, too many clients already（默认 max_connections=100）。
根源
PG 每个连接 fork 一个后端进程，不是线程；这和多版本无关，是早年的架构选择。见连接池与事务性能。
做法
应用侧池子开小（核数 × 2 起步），实例多时前面加 PgBouncer（事务模式下注意服务端预编译语句的限制）。

第二圈 · 使用规范

autovacuum 不关，大表单独调

默认按 20% 的行数触发，10 亿行的表要攒 2 亿个死元组才动。大表设 ALTER TABLE … SET (autovacuum_vacuum_scale_factor = 0.01)，或者靠 18 的 autovacuum_vacuum_max_threshold 封顶。

表胖了才清、一清就清很久。

连接上设超时

idle_in_transaction_session_timeout、statement_timeout，17 起再加 transaction_timeout；HikariCP 的 leakDetectionThreshold 帮你找借了连接不还的代码。

忘了提交的连接挡住整个库的 VACUUM。

频繁更新的表留 fillfactor

80～90，配合“经常变的列不建索引”。改完 fillfactor 只影响之后写入的页，老页要 VACUUM FULL 或 pg_repack 重写一遍才生效。

非 HOT 更新的写放大和表膨胀。

按查询选索引类型

等值和范围用 B-tree；按时间追加的日志、流水用 BRIN；JSONB、数组用 GIN（只查包含就用 jsonb_path_ops）；热的小子集用部分索引。

索引比表还大，或者建了却用不上。

JSONB 放扩展字段，不放核心字段

金额、状态、用户 id 这类要约束、要关联、要排序的，用普通列；渠道、优惠券、标签这类结构多变的，放 JSONB。查询写成 @>。

没有类型和约束的核心数据，和走不上索引的查询。

盯这几个指标

n_dead_tup 和 last_autovacuum、n_tup_hot_upd / n_tup_upd、age(backend_xmin) 最大的会话、age(datfrozenxid)、复制槽的 restart_lsn。

膨胀、回卷都是慢慢攒出来的，等报错就晚了。

第三圈 · 往深处挖

VACUUM 会跳过索引清理

14 起，有死槽位指针的页少于表的 2% 时（vacuumlazy.c 里的 BYPASS_THRESHOLD_PAGES），VACUUM 不扫索引，留到下次。⑤ 里的 index scan bypassed 就是它，所以那个死槽位指针还在。扫一遍 21 MB 的主键索引只为删一条，不划算。

可见性图让 Index Only Scan 成立

索引里没有 xmin/xmax，光看索引不知道行对你可不可见。VACUUM 维护可见性图（VM），标出“整页都对所有人可见”的页，这些页就不用回表。④-7 里 B-tree 查一小时只读了 14 个页，靠的就是刚 VACUUM 过。频繁更新的表 VM 常被打掉，Index Only Scan 会退化。

GIN 的 pending list

GIN 一行要插很多个键，很贵。默认 fastupdate=on：新条目先追加进一个待处理列表（gin_pending_list_limit 默认 4 MB），VACUUM 或列表满了再批量并进索引。代价是查询要多扫这个列表，偶尔某次插入要负责合并而变慢。

17、18 里的 VACUUM

17 换了 VACUUM 存死元组位置的内存结构（TidStore），内存少得多，大表不再因为内存不够而反复扫索引；17 去掉了 old_snapshot_threshold。18 加了异步 I/O（顺序扫描、VACUUM 都能用），VACUUM 会“顺手多冻结一些”全可见的页（VACUUM VERBOSE 输出里的 eagerly scanned），减轻以后的防回卷扫描。

第二圈：autovacuum 的触发阈值。

自测

1. 用一句话说出这一页的精华。

PG 不原地改行，每次 UPDATE 写一个新元组，旧元组带着 xmin/xmax 留在表里，等 VACUUM 在没有快照需要它时清掉；相当于把 InnoDB 的 undo 搬进了表本身，换来简单的回滚和读，代价是膨胀和清理。

2. 把 MySQL 的习惯搬到 PG，最疼的是哪几个？

长事务或 idle in transaction 挡住整个库的 VACUUM；反复改同一行、改有索引的列让表和索引一直长；以为 VACUUM 会缩表；关掉 autovacuum 攒出回卷风险。

3. 为什么一个开着的报表事务会让别的表也清不掉？

PG 用一个全局的 xmin horizon 判断能不能清：所有会话里最老的快照。它不区分你的快照会不会读那张表，只要它开着，之后死掉的版本都算“可能还有人要”（④-3）。

4. 预测：fillfactor 90 的表，把 status 列也建上索引，再每 10 行改一行 status，HOT 会有几次？

0 次。HOT 的条件之一是没改任何索引列，status 有了索引，每次更新都要给所有索引加条目。空出来的那 10% 只能让新元组放在同一页，省不掉索引写入（④-4）。

5. 预测：报表事务开着时发 VACUUM FULL orders，会发生什么？

它会一直等锁。报表事务读过 orders，持有 ACCESS SHARE 锁直到事务结束；VACUUM FULL 要 ACCESS EXCLUSIVE。更糟的是，它排在队列里以后，后面所有读写 orders 的请求都排在它后面，整张表看起来像卡死了（④-3，实验台里可以试）。

6. 预测：一个只在表尾追加、从不更新的日志表（按时间写入），死元组和 VACUUM 还重要吗？BRIN 合适吗？

几乎没有死元组，VACUUM 主要还要做冻结和维护可见性图（13 起插入也会触发 autovacuum，就是为了这个）。数据按时间顺序落在连续的页里，正是 BRIN 的最好情况：几十 KB 的索引就能把一个时间范围缩到少数几段页（④-5、④-7）。

7. 放回全景：第 7 站在 PG 里换成什么？这一步坏了，整条链路会怎样？

第 6 站拿到行锁后，第 7 站不再写 undo，而是在堆里插入新元组、给旧元组写 xmax；第 8 站写的是 PG 的 WAL，第 9 站提交只在 pg_xact 记一笔。这一步“坏”的典型样子是膨胀：长事务挡住清理，第 5 站沿索引找行要走越来越多的版本，第 12 站要写回磁盘的页也越来越多，所有经过这张表的 SQL 一起变慢。

标准档。实测 的数字来自本机：2 核 ARM，JDK 17.0.21（--release 8），pgJDBC 42.7.14，Docker 里的 PostgreSQL 18.7（shared_buffers=512MB，其余默认，orders 表关了 autovacuum 方便复现），交易靶场 100 万行 orders；代码在 study-labs。MySQL 一侧的对照数字来自日志那页的实测。autovacuum 阈值、冻结、回卷、GIN pending list 按 PostgreSQL 18 文档；版本变化按各版本发行说明（7.1、13、14、17、18 已核对原文）。实验台是简化模型。
