代码没改，行为变了：从 MySQL 换到 TiDB 要注意的四件事

TiDB 说 MySQL 的协议、语法也基本一样，所以最危险的是那些语句能跑、结果却不同的地方。四件事都能从上一页的架构推出来：每台 TiDB server 各自缓存一段自增 ID，所以 id 不连续；数据按主键范围切 Region，所以递增主键会让写入挤在最后一块；事务要在内存里攒齐再两阶段提交，所以事务有大小上限；隔离靠快照和行锁、没有间隙锁，所以 SELECT … FOR UPDATE 挡不住插入。本页把同样的 SQL 在 MySQL 8.4 和 TiDB 8.5.8 上各跑一遍，结果都是实测。

①为什么需要：迁移前就要知道哪几处会悄悄变

在全景第 12 站，交易靶场如果选了 TiDB，订单服务的代码一行不改、连接串换一下就能跑。真正的风险是那些“能跑但不对”的地方：

代码里的老习惯在 TiDB 上
id BIGINT AUTO_INCREMENT，对账脚本靠 id 连续发现漏单id 不连续，重启一台 TiDB 就跳几万：对账报一堆“漏单”
主键自增、大促时加机器扛写入新订单全写在最后一个 Region，加机器没用
归档任务 DELETE FROM t_order WHERE created_at < ? 一次删几千万行事务太大被拒，或者把 TiDB server 的内存吃光
用 SELECT … FOR UPDATE 锁住一个范围，防止别人往里插（比如同一用户同一时段只能有一单）挡不住，并发插入直接成功

②没有它会怎样：只看“兼容 MySQL”就迁

功能测试都会通过：每条 SQL 都能执行，结果在单线程、小数据下也对。问题只会在多台 TiDB server、大数据量、高并发下出现，也就是上线以后。四个问题里，自增 ID 和大事务会直接报错或报警，比较好发现；写热点表现为“加了机器写入还是上不去”，容易被误判成容量问题；隔离级别的差别最隐蔽，它不报错，只在并发时偶尔多插进一行，表现成“偶发的重复下单”。

不懂精华时的典型误用看到 TiDB 的 @@transaction_isolation 也是 REPEATABLE-READ（⑤ 实测），就以为和 InnoDB 一样。名字一样，实现不同：TiDB 的 RR 是快照隔离，没有间隙锁。

③相邻方案：这四件事在其他几家

自增 ID写热点大事务间隙锁
MySQL 8.4（InnoDB）单机计数，连续（回滚会留空洞）不存在（单机）受 undo、binlog、内存限制，但没有硬上限RR 下有，挡插入
TiDB 8.5每台 server 缓存一段，不连续；AUTO_ID_CACHE = 1 可连续按主键范围分片，递增主键会热；AUTO_RANDOM 打散单事务有上限（内存配额、单行 6 MiB）没有
自己分库分表（第 1～3 页）每张表各自自增，会重复，必须全局发号按哈希分片不热；按时间范围分会热单个分片里是 MySQL，没有跨分片事务单个分片里有

OceanBase、GoldenDB 在这四点上各有自己的做法，迁移时同样要逐项查对应版本的文档；本页只实测 TiDB。

④原理：四件事都是上一页那张架构图的直接后果

先知道这些 TiDB 架构：无状态的 TiDB server × N、按主键范围切成 Region 的 TiKV、发时间戳的 PD，见 上一页机制 1。 InnoDB 的间隙锁：RR 下锁住索引上的“空隙”，别的事务不能往里插，见 MVCC 与锁。

机制 1：自增 ID 是每台 TiDB server 各领一段

为什么默认要缓存：如果每台 TiDB server 每次插入都去存储层要一个号，自增列就成了全集群的串行点，插入吞吐被它卡死。缓存一段是用“连续性”换“吞吐”。AUTO_ID_CACHE = 1（v6.4 引入中心化分配，v6.5 起保证递增）把连续性要回来，代价是每个号都多一次网络往返。更根本的做法是不依赖数据库自增：用 J09 的号段或雪花在应用里发号。

机制 2：按范围分片 + 递增主键 = 表尾热点

TiKV 按主键排序存放，Region 是连续的一段，所以“下一个主键比所有现有的都大”就意味着“下一行写进最后一个 Region”。AUTO_RANDOM 在 BIGINT 主键的高位放几个随机的分片位（默认 5 位），新行就散到整个主键空间。⑤ 里还有一个细节：每个 Region 分到的行数都是 500 的倍数，⑤ 每 500 行一个事务，所以看起来同一个事务插入的行拿到的是同一组分片位（一个事务的行落在同一个 Region），打散是按事务、不是按行。没有整数主键的表，用 SHARD_ROW_ID_BITS 打散隐藏的 _tidb_rowid。

按范围切（TiDB）

范围查询、按主键顺序扫描很便宜，Region 能按大小自动分裂、合并；代价是递增键会写热点。

按哈希切（第 1 页的取模）

写入天然均匀；代价是范围查询要问遍所有分片，扩容要重新哈希、搬一半数据。

决定胜负的约束：TiDB 要能自动分裂、合并、搬迁数据块，这只有按范围切才做得到（一段连续的 key 可以从中间劈开；哈希桶不行）。所以热点不是 bug，是这个设计的代价，要靠选主键来避开。

机制 3：大事务要在 TiDB server 的内存里攒齐

  • 为什么有上限TiDB 的事务在提交前，所有改动都缓存在执行它的那台 TiDB server 的内存里，提交时再两阶段写到各个 Region。一个事务改几千万行，就要在一台机器的内存里放下它们，还要一次性对很多 Region 加锁。
  • 两道限制单个事务的总大小：v6.5 起主要由会话内存配额 tidb_mem_quota_query 管，配置项 txn-total-size-limit（默认 100 MiB）只有显式设置时才按它来（⑤ 的 tidb2 显式设成了 10 MiB，报 [8004] Transaction is too large）；单个键值对：txn-entry-size-limit 默认 6 MiB（⑤：一行 7 MB 报 [8025] entry too large）。
  • Pipelined DMLSET tidb_dml_type = 'bulk' 让自动提交的大 DML 边执行边往 TiKV 刷，不受事务大小限制（⑤：tidb2 上同一条 30 MB 的 INSERT 能过了）。v8.0 引入，v8.5 仍是实验特性，文档不建议生产使用。
  • 正确的做法归档、批量修数据这类操作本来就该分批：每批几千行一个事务、按主键范围推进，和 MySQL 上的最佳实践一样，只是在 TiDB 上从“建议”变成了“必须”。

机制 4：同叫 REPEATABLE-READ，TiDB 是快照隔离，没有间隙锁

TiDB 的 REPEATABLE-READ 实际是快照隔离：普通读读事务开始时的快照（所以 T1 第二次普通读还是两行），FOR UPDATE 是“当前读”，读最新提交的版本并加行锁（所以看到了 15）。它只锁已经存在的行，不支持间隙锁。InnoDB 在 RR 下用 next-key 锁把范围和间隙都锁住，防住了幻读插入。依赖“锁范围防插入”的业务逻辑（同一用户同一时段只能下一单、号段不重叠），在 TiDB 上要改成唯一约束或者锁一行“占位”记录。READ-COMMITTED 只在悲观事务模式下生效。

最少的写法

迁到 TiDB 的订单表四件事各一行
CREATE TABLE t_order (
  id BIGINT PRIMARY KEY AUTO_RANDOM,          -- 机制 2：写入打散（或者由应用发号，见 J09）
  order_no VARCHAR(24) NOT NULL UNIQUE,       -- 业务上看的“单号”另起一列，别指望 id 连续
  user_id BIGINT NOT NULL, slot INT NOT NULL, created_at DATETIME(3) NOT NULL,   -- slot：比如“用户 + 下单时段”
  KEY idx_user_created (user_id, created_at),
  UNIQUE KEY uk_user_slot (user_id, slot)     -- 机制 4：用唯一约束代替“锁范围防插入”
);
-- 机制 3：归档按主键范围分批，每批一个事务
DELETE FROM t_order WHERE created_at < '2025-11-01' LIMIT 5000;   -- 循环到影响 0 行

⑥细节

第一圈 · 不知道就会出事

1对账靠 id 连续，换库后天天报漏单← ④ 机制 1
现象
⑤：两台 TiDB 交替插入就是 1、30001、2、30002；重启一台跳到 60001。
根源
每台 TiDB server 缓存一段号，重启丢掉没用完的那段。
做法
对账按业务单号和时间范围比，不按 id 连续；确实要连续用 AUTO_ID_CACHE = 1（v6.5 起保证递增），并接受每个号多一次网络往返。
2ORDER BY id 当成按时间排序、MAX(id) 当成最新一单← ④ 机制 1、2
现象
⑤：默认模式下 tidb2 先发的 30001 比 tidb1 后发的 3 大；换成 AUTO_RANDOM 后 id 和时间完全无关。
根源
id 不再是全局单调的。
做法
按时间排序就用 created_at（建索引）；“最新一单”按 created_at 取。
3自增主键的写入挤在一个 Region，加机器没用← ④ 机制 2
现象
⑤：AUTO_INCREMENT 的 2 万行全部落在第 0 个 Region（leader 只在 tikv3）；AUTO_RANDOM 分到 8 个。
根源
按主键范围分片，新 key 永远比旧 key 大。
做法
写多的表用 AUTO_RANDOM、应用发号先哈希、或者 SHARD_ROW_ID_BITS；新表上线前用 SPLIT TABLE 预切 Region，避免刚上线时只有一块。递增的二级索引（比如 created_at）也会热，同样要留意。
4一次删几千万行，事务太大← ④ 机制 3
现象
⑤：显式设了 10 MiB 上限的 tidb2，30 MB 的 INSERT 报 [8004] Transaction is too large；任何配置下，一行超过 6 MiB 报 [8025] entry too large。默认配置下限制换成了会话内存配额，事务再大一点就会被内存配额终止或拖垮 TiDB server。
根源
事务提交前全部改动缓存在一台 TiDB server 的内存里。
做法
分批（每批几千行一个事务）；大字段（图片、长文本）放对象存储，库里只存地址；tidb_dml_type = 'bulk' 在 v8.5 仍是实验特性，只用在可以重跑的离线任务上。
5靠 FOR UPDATE 锁范围防插入，在 TiDB 上失效← ④ 机制 4
现象
⑤：MySQL 里 T2 被挡了 3 秒后超时；TiDB 里 T2 13 ms 就插进去了，T1 的 FOR UPDATE 读到了 3 行。业务上就是“同一时段下了两单”“号段重叠”。
根源
TiDB 只锁已存在的行，不支持间隙锁；RR 实际是快照隔离。
做法
用唯一约束兜底（UNIQUE (user_id, slot)）；或者先锁一行一定存在的“占位”记录（比如用户行）再判断；迁移前在代码里搜 FOR UPDATE 逐个确认它是不是在锁范围。

第二圈 · 迁移前怎么排查

  • 搜代码MAX(id)、ORDER BY id、FOR UPDATE、LAST_INSERT_ID() 后再做计算的地方，逐个确认依赖的是哪种行为。防的是坑 1、2、5。
  • 看表结构所有 AUTO_INCREMENT 主键的大表、所有按时间递增的二级索引，列出来决定用 AUTO_RANDOM、应用发号还是保持不变。防的是坑 3。
  • 看批处理归档、修数、导入任务，确认都是分批提交。防的是坑 4。
  • 并发回放把生产流量（或压测脚本）在 TiDB 上回放一遍，对比结果和错误码；单线程功能测试发现不了坑 3、5。
  • 前端精度AUTO_RANDOM 和雪花的 id 都超过 253，JavaScript 的 Number 接会丢精度，接口里 id 用字符串。

第三圈 · 深处

  • 乐观事务TiDB 也支持乐观事务（tidb_txn_mode = 'optimistic'）：执行时不加锁，提交时才检查冲突，冲突就整个事务失败要重试。v3.0.8 起新建集群默认悲观，行为更接近 MySQL；从老集群升级上来的要确认一下是哪种。
  • 写偏斜快照隔离挡不住“两个事务各读一行、各改另一行”的写偏斜（比如“至少一个值班”的约束）。MySQL 的 RR 在普通读时同样挡不住，要靠 FOR UPDATE；TiDB 下用 FOR UPDATE 锁住两行即可。
  • Region 的预切和 placement除了 SPLIT TABLE，建表时可以用 PRE_SPLIT_REGIONS 配合 SHARD_ROW_ID_BITS 一次切好；Placement Rules 能指定某张表的 leader 放在哪个机房，接上一页的两地三中心。

自测

1. 用一句话说出这一页的精华

TiDB 兼容 MySQL 的协议和语法，但四处行为来自它的架构：每台 server 缓存一段自增号所以 id 不连续，按主键范围分片所以递增主键写热点，事务在一台 server 内存里攒齐所以有大小上限，RR 是快照隔离、没有间隙锁所以 FOR UPDATE 挡不住插入；迁移前要逐项排查、用 AUTO_RANDOM、分批、唯一约束来改写。

2. 只看“兼容 MySQL”就迁，疼在哪？

功能测试全过，问题都在多台 server、大数据量、高并发下才出现：id 跳号、加机器写不上去、批处理报错、偶发的重复插入。

3. 坑 3（写热点）的根源是 ④ 的哪条？为什么 TiDB 不改成按哈希分片？

机制 2：按主键范围分片，递增键总写最后一个 Region。TiDB 需要自动分裂、合并、迁移数据块，连续范围可以从中间劈开，哈希桶做不到，所以选了范围，把热点留给主键设计来解决。

4. 预测：订单表用应用发的雪花 id（J09）做主键、不打散，在 TiDB 上会热吗？

会：雪花 id 高位是时间戳，整体随时间递增，新订单同样落在表尾的 Region。要么先哈希、要么把分片位放到高位（类似 AUTO_RANDOM），要么用 AUTO_RANDOM 让数据库来做。

5. 预测：在 TiDB 上，T1 先普通读范围（两行）、再 FOR UPDATE 读同一范围，中间 T2 插入并提交了一行。T1 的两次读结果一样吗？MySQL 呢？

TiDB 不一样：普通读读快照（两行），FOR UPDATE 当前读看到新行（三行），⑤ 实测正是如此。MySQL 的普通读也是快照（两行）；但如果 T1 的第一次读就是 FOR UPDATE，间隙锁会挡住 T2，所以 ⑤ 里两次读都是两行。

6. 放回全景：第 12 站“另一条路”上，第 2 站（定分片键）和第 7 站（订单号基因）还需要吗？

不再需要自己定分片键和基因来路由，数据库按主键范围自动分片、任意条件都能查。但主键的选择从“分片键”变成了“打散写入”：第 2 站的问题换了个样子还在，就是坑 3；第 7 站的订单号仍然要全局唯一，由发号器或 AUTO_RANDOM 保证。

档位：标准。本机跑过（2 核 ARM 虚拟机，JDK 17，TiDB / TiKV / PD v8.5.8 小集群，MySQL 8.4.13 容器）：⑤ 的四组实验各跑 1 次，页面上的 id、行数、错误码和报错原文都来自这次输出。主键选型台是规则表加实测锚点（node 里跑过）。

按文档（TiDB v8.5）：默认每台 TiDB 缓存 30000 个自增 ID、只在单台内单调；AUTO_ID_CACHE = 1 v6.4 引入中心化分配、v6.5 起保证递增；AUTO_RANDOM 默认 5 个分片位、只能用于 BIGINT 聚簇主键；递增主键的插入只落在一个 Region；txn-total-size-limit 默认 100 MiB、v6.5 起不再推荐（事务内存计入 tidb_mem_quota_query，显式设置时仍生效）；txn-entry-size-limit 默认 6 MiB；Pipelined DML（tidb_dml_type = 'bulk'）v8.0 引入、v8.5 仍是实验特性；RR 实际是快照隔离、不支持间隙锁、RC 只在悲观模式生效、v3.0.8 起新建集群默认悲观。MySQL 8.4 文档：RR 下的 next-key 锁会阻止往 BETWEEN 10 AND 20 里插入 15。
