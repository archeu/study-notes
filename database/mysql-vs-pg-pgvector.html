工单库要加“找相似故障”：MySQL 还是 PostgreSQL，pgvector 凭什么

值班助手收到一条新告警，想翻出“过去 90 天、付款服务、最像的三张故障单”。故障单在数据库里，相似要靠向量。这一页先回答老问题：新项目选 MySQL 还是 PG，再回答新问题：为什么 AI 项目里 PG 越来越常见。精华是：选库先看数据长什么样、团队熟什么，不看谁跑分快；PG 在 AI 项目里赢，是因为它允许第三方往库里加新类型、新运算符和新索引。pgvector 就这样把向量变成了业务表里的一列：和业务数据同一个事务，一条 SQL 里既过滤又找相似。

①为什么学：故障单库要加一个“找相似”

J06 前九页一直在 MySQL 和 PG 之间对照：索引、MVCC、日志、复制、DDL、升级、VACUUM。两边都见过了，才谈得上选。真实的触发点往往是 AI 需求：AI 地图站 06 要给值班助手建知识库，第一件事就是问“向量放哪”。招聘上也是这个信号：J06 统计的 25 份 Java 后端 JD 里只有 3 份提 PostgreSQL，AI Agent 那 26 份里有 5 份，大多因为 pgvector 和 Dify 这类平台。

②老办法行不行：业务库是 MySQL，向量怎么办

交易靶场和多数 Java 项目的业务库是 MySQL。手上的老办法有两条，都能做，都不完美。

A. 向量存进 MySQL，距离在 Java 里算

  • MySQL 9.0（2024-07）起有 VECTOR 类型，能存。8.4 LTS 只能存成 BLOB 或 JSON。
  • 社区版没有算距离的函数：手册写明 DISTANCE() “只给 OCI 上的 MySQL HeatWave 和 MySQL AI 用，不在 Commercial 和 Community 版本里”。到 2026-10 的 9.7.4 还是这样。
  • VECTOR 列“不能做任何键”，也就没有向量索引。
  • 结果：SQL 只能先按服务、时间过滤，把候选行的向量全拉回 Java，逐个算余弦再排序。1 万行没事，100 万行时每次查询要搬 4 GB（1024 维 × 4 字节 × 100 万）。

B. MySQL 放业务，再加一个专用向量库

  • Milvus、Qdrant、Weaviate 这类库专做向量检索，量大、并发高时很强。
  • 一张故障单变成两份数据：MySQL 里一行，向量库里一个点。写入要么双写（一边成功一边失败怎么办），要么接 binlog 同步（和 复制延迟那页一样，刚写的查不到）。
  • 过滤条件（服务、时间、权限）得在向量库里再存一遍元数据，两边要一起改。
  • 多一套要部署、备份、监控、扩容的系统。

缺的那一块：向量其实只是这张故障单的又一列。它应该和这一行同生共死（同一个事务），和服务、时间一起过滤（同一条 SQL），由同一个库负责索引、备份和复制。能做到这一点的库，AI 项目的第一版就最省事。

不懂精华的典型误用“PG 先进，为了向量把整个业务库从 MySQL 迁过去”
为什么错
pgvector 的好处来自“向量和业务数据在一起”，不来自 PG 跑得更快。业务库在 MySQL 上运转良好、团队的 DBA 经验、分库分表、binlog 同步都围着 MySQL，迁库的风险远大于向量带来的收益。向量量不大时，常见做法是旁边加一个 PG + pgvector 只放知识库，或者等用到再说。反过来的误用也有：把 pgvector 当成“装在 PG 里的 Milvus”，不知道它的索引是先取候选、再过滤，带条件查询会少行（坑 1）。

③选谁：先选库，再选向量放哪

两个问题分开答。第一个是关系库本身的选型，前九页讲的差异在这里汇总；第二个是向量的去处。

第一问：MySQL 还是 PostgreSQL

为什么 AI 项目里 PG 更常见

一库多用业务表、JSONB 元数据、全文检索、向量放在一个库里，第一版只运维一个系统。
框架默认Spring AI 有 PgVectorStore，也有 MariaDB 的，没有 MySQL 的；LangChain 有 PGVector；Dify 的元数据库默认是 PG，向量库可选 pgvector（默认是 Weaviate）。
MySQL 那边空着Oracle MySQL 社区版到 9.7.4 还没有距离函数和向量索引，这些功能放在 HeatWave 和 MySQL AI 里。
托管服务都带AWS、Google Cloud、Azure 的托管 PostgreSQL 都提供 pgvector，CREATE EXTENSION vector 一句开启。

本页学 PostgreSQL + pgvector：它是“向量和业务数据在一起”这条路上最成熟、生态最全的一个。MariaDB 走的是同一条路；专用向量库在⑥的“下一圈”里。

④原理：PG 留了插槽，pgvector 把向量插进去

要回答“为什么 MySQL 社区版没有、PG 有”，得看 PG 怎么允许别人往库里加东西。答案落在三张图上：扩展插进了哪几个槽，一条相似查询在库里怎么走，以及这样设计赢在哪、输在哪。

先知道这些
  • embedding（向量）：模型把一段文字变成一串固定长度的小数，bge-m3 给 1024 个。意思越近，两串数的方向越接近。向量化是模型的事，数据库只负责存和找。
  • 余弦距离：1 − 两个向量夹角的余弦。0 表示方向完全一样，越大越不像。pgvector 里写作 a <=> b。
  • 精确找 和 近似找：精确找是把每一行的距离都算一遍再排序，一定对，行多了就慢。近似找（ANN）先建一张“近邻图”，顺着图走，只看一小部分，快很多，但可能漏掉真正最近的几个。漏的比例用召回率量：真正最近的 10 个里找回了几个。
  • 堆表、元组、HOT、VACUUM：PG 的行怎么存、UPDATE 怎么写新版本，见上一页，这里直接用。

默认 40。大一点，看得更多、召回更高、更慢。它也是“一次最多吐几个候选”，所以 LIMIT 不该大于它。

为什么这样设计：谁有资格给库加一种新索引

PG：类型、运算符、索引都可扩展 选了它

  • 源头：1986 年 Stonebraker 设计 POSTGRES 时，目标之一就是让用户能扩展数据类型、运算符和访问方法（索引），当时想的是地理、图像这类关系模型装不下的数据。PostGIS 是第一个大赢家，pgvector 是第二个。
  • 新需求不用等官方：向量火起来以后，第三方的扩展先跟上；2023 年 0.5.0 加 HNSW，2024 年 0.8.0 加 iterative scan，都没等 PG 发大版本。
  • 新索引自动继承 WAL、MVCC、复制、权限：从库上天然有一份向量索引，回滚了天然看不见。
  • 代价：扩展要被装进进程，写错了能拖垮整个库；云厂商只允许白名单里的扩展、版本自己定；扩展只能在 PG 给的框架里发挥。例子：PG 的索引扫描只支持按运算符升序吐结果，所以内积运算符 <#> 返回的是负内积，好让“越大越像”变成“越小越靠前”。

MySQL：可插拔的是整个存储引擎 没选的那种

  • 插件接口（handler）换的是整个存储引擎：MyISAM 换 InnoDB、加一个 MyRocks。对 2000 年代的 Web 场景，这个粒度正合适：简单、快、可靠。
  • 数据类型、索引种类由 server 层和 InnoDB 定。InnoDB 的索引就是 B+ 树，外加空间索引和全文索引；第三方没法往 InnoDB 里加一种“近邻图”索引。
  • 所以向量检索只能等官方做：Oracle 把距离函数和向量索引放进了 HeatWave 和 MySQL AI；社区版到 9.7.4 只有类型。MariaDB 自己动手，在 11.7 里加进了核心。

决定胜负的约束：新的数据形态出现时，谁能最快给它配上索引。PG 把这个权力交给了任何人，于是向量一火，pgvector 就把它变成了“又一列 + 又一种索引”，业务数据一步也不用挪。MySQL 把权力留在官方，换来的是更简单、更可控的核心。

最少的语法PostgreSQL 13+（pgvector 0.8.7；0.9.0 起要 15+）；参数和细节放到 ⑥
CREATE EXTENSION vector;                                  -- 每个库执行一次
CREATE TABLE tickets (
  id bigserial PRIMARY KEY, service text, created_at timestamptz,
  embedding vector(1024)                                  -- 维数要和模型一致
);
INSERT INTO tickets(service, created_at, embedding)
  VALUES ('payment', now(), '[0.012,-0.031, … ]');        -- 文本形式传进来
SELECT id, embedding <=> $1 AS dist                     -- <=> 余弦距离，越小越像
  FROM tickets WHERE service = 'payment'
 ORDER BY embedding <=> $1 LIMIT 3;                     -- 走索引要 ORDER BY 距离 + LIMIT
CREATE INDEX ON tickets USING hnsw (embedding vector_cosine_ops);  -- 运算符类要和 <=> 对上
SET hnsw.ef_search = 100;                                 -- 召回不够时调大（⑥）
SET hnsw.iterative_scan = relaxed_order;                  -- 带过滤少行时打开（⑥）

⑥细节·规范·优化

16 行时一切都好。行多了要建 HNSW，坑就从“近似”和“先索引后过滤”这两件事里冒出来。另一半坑来自“它住在 PG 里”：页大小、内存、MVCC 都照 PG 的规矩来。

第一圈 · 注意事项

坑 1建了 HNSW，带 WHERE 的查询只回来几行，甚至 0 行← ④-2 过滤在索引之后实测
现象
LIMIT 10 只回 4 行；按租户过滤时经常一行没有。没建索引时好好的。
根源
HNSW 一次最多吐 ef_search（40）个候选，Filter 在后面扔掉不满足条件的。实测 10 万行：条件命中 10%，平均回 4.3 行；命中 1%，平均 0.4 行（下表）。
做法
pgvector 0.8.0+：SET hnsw.iterative_scan = relaxed_order，不够就接着走图，实测都回满 10 行。条件很窄（一个租户、一个文档）时，先用 B-tree 把这些行取出来再精确排序：召回 100%，还更快。也可以按租户建部分索引或分区。
坑 2索引建了，EXPLAIN 里是 Seq Scan← ④-1 运算符类按文档
现象
建了索引，查询还是全表算距离，行多了几十毫秒起步。
根源
计划器只认“ORDER BY 某个运算符 + LIMIT”，而且运算符要属于建索引时的运算符类：vector_cosine_ops 只服务 <=>，查询写 <-> 就用不上；写成 ORDER BY 1 - (a <=> b) DESC（相似度倒序）也用不上；不写 LIMIT 也用不上。
做法
查询照抄索引的运算符，按距离升序，带 LIMIT；上线前对每条向量查询看一次 EXPLAIN，要看到 Index Scan using …hnsw。
坑 33072 维的向量建不了索引← ④-1 一切都住在 8 KB 页里按文档
现象
换了一个大模型（比如 3072 维），CREATE INDEX … USING hnsw 报维度超限。
根源
列最多 16000 维，但能建索引的：vector 2000 维，halfvec 4000 维，bit 64000 维。三个数一算就明白：2000 × 4 字节 = 4000 × 2 字节 = 64000 位 = 8000 字节，一个索引元组要放进一个 8 KB 页。
做法
用 halfvec（16 位浮点，空间减半，召回通常几乎不变）；或者让模型输出低维（不少模型支持指定维数）；或者对表达式建索引：USING hnsw ((embedding::halfvec(3072)) halfvec_cosine_ops)。
坑 4建索引慢、报共享内存不够← ④-1 借用 PG 的建索引框架实测
现象
本页实验第一次跑就报 could not resize shared memory segment … No space left on device；或者看到 NOTICE: hnsw graph no longer fits into maintenance_work_mem，建索引慢到几个小时。
根源
HNSW 的图在 maintenance_work_mem 里建，放不下就退化成边建边写盘；并行建索引时图放在共享内存里，Docker 默认的 /dev/shm 只有 64 MB。实测 10 万 × 128 维：建图 13.9 s，索引 79 MB，比表（56 MB）还大。
做法
建索引的会话里临时调大 maintenance_work_mem；容器加 --shm-size；先灌数据再建索引；大表用 CREATE INDEX CONCURRENTLY，不挡写入。
坑 5换了 embedding 模型，搜出来全是乱的← ④ 向量化是模型的事推导
现象
新单子用新模型算，老单子是旧模型算的，距离毫无意义；或者维数不同直接报错。
根源
不同模型的向量不在同一个空间里，数据库分不出来，它只管算数。
做法
表里记 embedding_model；换模型 = 新加一列全量重算、建好索引、切流量、删旧列，按一次数据迁移来做。
坑 6故障单的状态一天改几十次，HNSW 越来越慢← 上一页 ④-4 HOT推导
现象
向量没变，只改 status、assignee，HNSW 索引却一直长，VACUUM 也变慢。
根源
PG 的 UPDATE 写新元组。不是 HOT 更新时（改了有索引的列，或者页里没空），每个索引都要插一条新条目，HNSW 也不例外，插一条就要在图上查一次、连几条边；旧条目等 VACUUM 来修图。
做法
经常改的字段别建索引、给表留 fillfactor；或者把向量放进 1:1 的子表 ticket_embeddings(ticket_id, embedding)，业务行怎么改都不碰它。

第二圈 · 使用规范

先精确，量大了再建索引

几万行以内，精确扫描几十毫秒、召回 100%（实测 10 万 × 128 维 46 ms）。建了 HNSW 就要接受近似，并回答“带条件时怎么办”。

为了快而丢了正确性，自己还不知道。

每条向量查询都看一次 EXPLAIN

看到 Index Scan using …hnsw 加 Filter，就要想到坑 1；看到 Seq Scan + Sort，就要想到坑 2。

索引白建，或者结果悄悄变少。

记下模型和维数

列名或旁边一列写清 bge-m3 / 1024；维数用 vector(1024) 写死，插错维数直接报错。

不同模型的向量混在一起。

窄条件按租户切

多租户知识库：小租户走“B-tree 先过滤 + 精确排序”，大租户才走 HNSW；租户少而固定时，部分索引 WHERE tenant = 7 或按租户分区。

小租户永远搜不全。

两个库并存就别双写

业务在 MySQL、知识库在 PG 时，用 outbox 表或 binlog CDC 把变更送过去，并接受几秒延迟。

一边成功一边失败的孤儿数据。

上云先看扩展版本

托管 PG 的 pgvector 版本由云厂商定；iterative_scan 要 0.8.0，PG 18 要 0.8.1。SELECT extversion FROM pg_extension WHERE extname = 'vector'。

文档里的参数在你的库上不存在。

第三圈 · 往深处挖

HNSW 还是 IVFFlat

README：HNSW “速度和召回的权衡比 IVFFlat 好，但建得慢、更占内存”；IVFFlat “建得快、省内存，查询表现差一些”。IVFFlat 先把向量聚成 lists 个桶（建议行数 / 1000），查时看 ivfflat.probes 个桶（默认 1），所以要先有数据再建，数据分布变了要重建。HNSW 可以建在空表上，边插边长。

strict_order 和 relaxed_order

iterative scan 有两种：strict_order 保证按距离严格有序，relaxed_order 允许小范围乱序、召回更好；IVFFlat 只有 relaxed。最多看 hnsw.max_scan_tuples（默认 20000）个候选，条件比 LIMIT / 20000 还窄时仍会凑不满，实验台的“小租户 0.01%”就是这种。

1024 维的向量其实不在表里

4100 字节超过了 PG 的 TOAST 阈值（约 2 KB），vector 类型的存储方式是 external：实测 16 行的 tickets，主表 8 kB，TOAST 表 96 kB。精确扫描时每行都要去 TOAST 取一次；UPDATE 别的列时 TOAST 指针原样复用，不重写向量。HNSW 索引里另存一份向量，所以索引常比表大。

为什么计划器不“聪明一点”

计划器按代价选路，它估得出 HNSW 便宜，却不知道 HNSW 会在 Filter 之后“少给”。iterative scan 是在执行器这一侧补救：不够就接着走。所以窄条件下，与其指望计划器，不如用 SQL 写清楚意图（CTE、部分索引）。

面试官会怎么问

“你们为什么用 MySQL / PG？换成另一个行不行？”

先说数据和团队：交易型、高频改同一行、团队和中间件都围着 MySQL，就用 MySQL，旧版本进 undo，不用操心 VACUUM；数据形态杂（JSON、地理、向量）、SQL 复杂、要扩展，选 PG。再说代价：PG 要懂 VACUUM 和连接池，MySQL 的 DDL 要靠 Online DDL 工具。最后落一句：换库的成本主要在人和周边工具，不在 SQL。

“pgvector 和 Milvus 怎么选？”

看量和一致性。千万级以内、要和业务条件一起查、要事务一致，pgvector：一份数据，一条 SQL，备份和复制照旧。上亿、高 QPS、要 GPU 或量化、检索是核心业务，用专用向量库，代价是第二份数据和同步。很多团队从 pgvector 起步，量上去了再拆。

“带过滤的向量查询为什么会少返回结果？怎么办？”

近似索引先按 ef_search 取一批候选，过滤在后面。命中 10% 时默认 40 个候选平均只剩 4 个。办法：pgvector 0.8 的 iterative scan 不够就接着扫；条件很窄时先用 B-tree 过滤再精确排序；或者按租户建部分索引、分区。本页实测 1% 的条件：默认 0.4 行，iterative 10 行召回约 80%，先过滤再精确 10 行召回 100%、1.5 ms。

自测

1. 用一句话说出这一页的精华。

选库先看数据和团队；PG 在 AI 项目里常见，是因为它允许第三方加类型、运算符和索引，pgvector 借此把向量变成业务表的一列，和业务数据同事务、同一条 SQL 过滤加排序。

2. 业务库在 MySQL，向量的两种老办法各疼在哪？

存进 MySQL：社区版没有距离函数和向量索引，只能把候选向量搬回 Java 算。另加向量库：两份数据，双写或同步，过滤字段要存两遍，多一套系统要运维。

3. 为什么 MySQL 社区版没有向量索引，PG 却能由第三方做出来？

PG 的索引访问方法是开放接口（IndexAmRoutine），类型、运算符、运算符类也能由扩展注册；MySQL 能插拔的是整个存储引擎，InnoDB 的索引种类由官方定，只能等官方做，而官方把它放进了 HeatWave。

4. 头号坑“带条件少行”的根源是哪条原理？

④-2：HNSW 索引扫描先吐出至多 ef_search 个候选，Filter 在索引之后执行。候选数固定，条件越窄，过关的越少。

5. 预测：tenant 条件命中 1%，把 ef_search 从 40 调到 400，不开 iterative scan，平均能回几行？

约 4 行（400 × 1%），LIMIT 10 仍然凑不满，而且每次查询多看了 10 倍的候选。调 ef_search 是在加大候选池，治标；要凑满得开 iterative scan，或者先过滤再精确。推自 ④-2 的“候选 × 命中比例”。

6. 预测：同一个事务里插入一张故障单（带向量）但还没提交，另一个连接用 HNSW 查相似，会看到它吗？

看不到。HNSW 的图里可能已经有这个新点，但索引只给出候选的位置，回堆表时要做 MVCC 可见性判断（④-2 第 3 步），未提交的元组对别的快照不可见。这正是“住在 PG 里”的好处，专用向量库得自己处理这件事。

7. 放回全景：第 7 站在 PG 里是“写新元组”。给 tickets 改一次 status，这一站会发生什么？向量会被重写吗？

第 7 站在堆里写一个新元组；1024 维的向量在 TOAST 里，没改就复用指针，不重写。如果是 HOT 更新（status 没索引、页里有空），所有索引都不动；否则每个索引包括 HNSW 都要插新条目，第 8 站的 WAL 也跟着变多，VACUUM 之后还要修 HNSW 图。所以经常改的业务行和向量最好分开放（坑 6）。
