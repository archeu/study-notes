100 万行里找 9527，只读了 3 页：索引与 B+ 树

交易靶场的 orders 表有 100 万行，表空间文件 7680 个页、120 MB。按主键找订单 9527，InnoDB 只拿了 3 个页；按一个没索引的列找，要拿 5430 次（本页实测）。索引的精华是两句话：索引是一棵按键排好序、以 16 KB 的页为节点的矮胖树，一次查找只读树高那么几页；InnoDB 里表本身就是主键那棵树，二级索引的叶子只存主键值。回表、覆盖索引、最左前缀，都能从这两句推出来。不懂这两句，就会建了索引却越查越慢。

全景：一条 UPDATE 从应用到磁盘 · 第 4、5、12 站地图：J06 · 索引与 B+ 树：聚簇索引、回表、覆盖索引、最左前缀

①为什么需要：在 120 MB 里找一行 71 字节

在全景第 5 站，这一步要解决：UPDATE … WHERE id = 9527 到了 InnoDB，要从 100 万行里找到这一行。麻烦在于，磁盘和内存缓存（buffer pool）都不按行存取，只按页：一次至少 16 KB。所以问题变成了：最少读几个页，才能找到它？

②没有它会怎样：一页页翻，或者排好序二分

先用已经会的办法想一遍。最直接的是从头翻到尾；聪明一点，把行按 id 排好序存成一个大文件，二分查找。两种都能找到，但都不够好。

③相邻方案：哈希、二叉树、B 树、LSM 树

能“快速找到一行”的结构不止一种。比的是三件事：等值查、范围查和排序、放在磁盘上一次查找读几页。

结构等值查范围查、ORDER BY100 万行查一次读几页写入谁在用
哈希表1 次不行：哈希后顺序就乱了≈ 1快Memory 引擎；InnoDB 的自适应哈希索引（8.4 默认关）
平衡二叉树（红黑树）log₂N可以≈ 20快内存里：Java 的 TreeMap
B 树logmN可以，但要在层间上上下下3（行一长就变高）中老一代文件系统、部分数据库
B+ 树logmN叶子连成链表，顺着走3（实测）中InnoDB、PostgreSQL、Oracle、SQL Server 的默认索引
LSM 树要查好几层可以，要合并多层不定很快（顺序写）RocksDB、MyRocks、TiKV、HBase

选择规则：数据在磁盘上、既要等值又要范围和排序、读多写少，用 B+ 树；只有等值、全在内存里，用哈希；写入量远大于读、能接受读放大，看 LSM 树。订单表三条都符合第一种，本页学 InnoDB 的 B+ 树。为什么不是 B 树、为什么叶子要连成链表，放到 ④-6 讲。

④原理：一棵矮胖树，两种叶子

先看一棵树长什么样、为什么只有 3 层；再看页里面怎么找；然后是 InnoDB 的两种树（聚簇索引、二级索引），回表、覆盖索引、最左前缀都从这里来；最后说为什么非这样设计不可。

先知道这些
  • 页（page）：InnoDB 存数据的最小单位，默认 16 KB（innodb_page_size）。读一行，也要把它所在的整页读进来。
  • buffer pool：InnoDB 在内存里缓存页的地方，命中就不读盘。全景第 5 站冷启动时读了 3 次盘，就是这里没命中。见 全景 J06。
  • 贵的是“拿页”，不是比较：在一页里比较几百个键是微秒级，拿一个不在内存里的页要一次随机 IO（SSD 上约 0.1 ms，机械盘约 10 ms）。所以设计目标只有一个：少拿页。

④-1 一棵 B+ 树：上面几层只放路标，数据全在最底层

真名对一下：最上面那页叫根页，中间叫非叶子节点（内节点），最底层叫叶子节点；页头里有个 PAGE_LEVEL 字段，叶子是 0，往上加 1。根页的位置是固定的，建索引时定下来，写在数据字典里（INNODB_INDEXES.PAGE_NO：主键是 4，idx_user 是 5）。

④-2 到了页里：页目录二分，再走几步链表

④-3 两种树：聚簇索引存整行，二级索引存主键

InnoDB 每张表至少一棵树：主键那棵，叶子里是整行，表就是这棵树，所以叫聚簇索引（clustered index）。另外每建一个索引就多一棵树，比如 idx_user(user_id)，它的叶子里只有 (user_id, id)：索引列加主键值，叫二级索引（secondary index）。

PRIMARY（聚簇索引）实测 3 层
叶子：4526 页，每页 221 行
内容：id, user_id, sku_id, qty, amount_cents,
      status, created_at, paid_at
      + 事务 id、回滚指针（MVCC 用）
排序：按 id
idx_user（二级索引）实测 3 层
叶子：2048 页，每页平均 488 条
内容：user_id, id   ← 只有这两列
排序：先按 user_id，相同再按 id
要别的列：拿 id 回主键树再找一次

“拿 id 回主键树再找一次”就叫回表。二级索引查到几条，就回表几次，每次都是从主键根页重新下降 3 页。反过来，如果要的列二级索引的叶子里都有，就不用回表，这叫覆盖索引，EXPLAIN 的 Extra 里显示 Using index。下面的演示把这几种走法放在一起走一遍。

④-6 为什么这样设计

  
两个问题：为什么是 B+ 树而不是 B 树；为什么二级索引存主键值，而不是行在磁盘上的地址。

  

    

      
B 树 每个节点都放整行


    

    

      
B+ 树 上面只放路标，数据都在叶子


    

  

  
决定胜负的约束：磁盘按页读，一次查找的成本 ≈ 树高。树高由扇出决定，扇出 = 一页能放几条记录。把数据挪出内节点，内节点就只剩“键 + 子页号”，扇出最大、树最矮；代价是每次查找都要走到叶子，但反正要读那一行，本来就得到叶子。

  

    

      
堆表 + 索引存地址 PostgreSQL、MyISAM 的做法


    

    

      
聚簇 + 二级索引存主键 InnoDB 的做法


    

  

  
决定胜负的约束：B+ 树的行不是钉死在某个位置的：页满了要分裂，一半的行搬到新页。如果二级索引存的是物理地址，每搬一行，所有二级索引都要跟着改。InnoDB 让二级索引存主键这个“逻辑地址”，用回表多读几页换来写入时的稳定；也因此，主键越短、越有序越好（⑥ 坑 4）。PostgreSQL 走另一条路，用 HOT 更新等手段减少改索引，下钻第 9 步再对照。

第一圈 · 注意事项

  

    
坑 1回表太多，走索引比全表扫还慢← ④-3 每次回表都从根下降实测
      
现象
⑤ 的第 ⑤ 条：user_id BETWEEN 1 AND 20000 命中 10 万行，走 idx_user 拿页 40 万次、258 ms；不用索引全表扫只拿 4812 次、185 ms。优化器估计 21 万行，还是选了索引。

      
根源
每条二级索引记录回表一次，就是一次从主键根页开始的 3 页下降，而且 id 是乱序的，前后两次很少落在同一页。全表扫是顺着叶子链表一页一页读，每页 221 行一次拿完。

      
做法
命中行数占比大的查询，要么让索引覆盖（第 ⑦ 条，236 次、18.7 ms），要么分批、加更有区分度的条件；上线前看 EXPLAIN 的 rows，别默认“走索引就快”。

    

    
坑 2联合索引缺了最左列，整棵树用不上← ④-4 先按第一列排实测
      
现象
有了 (user_id, created_at)，按 created_at = … 查，EXPLAIN 是 type=ALL rows=995720：全表扫。

      
根源
树整体只按 user_id 有序，created_at 只在同一个 user_id 里有序，单看 created_at 没法二分。

      
做法
按查询建索引：哪些查询要用，就让它们的等值列排在最左。8.0.13 起有跳跃扫描（skip scan），但条件很窄：查询只用到索引里的列、最左列取值很少；本例 user_id 有 20 万个值，没选它。

    

    
坑 3范围列放在前面，后面的列只能过滤← ④-4 最多一个范围列实测
      
现象
user_id BETWEEN 1024 AND 1100 AND created_at = …：key_len=16 看起来两列都用了，rows 却是 381。

      
根源
user_id 一取范围，范围内各个 user_id 的 created_at 各自有序，合起来不有序，第二列没法再二分，只能在索引里逐条比（ICP）。

      
做法
联合索引按“等值列在前、范围列和排序列在后”排。这条查询该建的是 (created_at, user_id)。

    

    
坑 4主键用随机 UUID：页分裂、页半满、二级索引变胖← ④-6 二级索引存主键实测一半
      
现象
插入变慢、表和索引变大。本页实测了一半：主键按顺序插，叶子每页 221 行，按行长估算约 97% 满；idx_user 的 user_id 是乱序插入的，叶子平均 488 条，按每条约 21 字节估算只有约 64% 满。随机主键的聚簇索引也会这样，而且每行都更大。

      
根源
新值插进树的中间，页满了就对半分裂，两页各半满；顺序插入时 InnoDB 能识别出是往末尾追加，新页从插入点开始，老页保持满的。另外每个二级索引的叶子都带着主键，CHAR(36) 的 UUID 比 BIGINT 多 28 字节，乘以每个二级索引的每一条。

      
做法
主键用自增 BIGINT，或时间有序的 ID（雪花算法、UUIDv7）；非要 UUID，存成 BINARY(16)。业务唯一键另建唯一索引。

    

    
坑 5对索引列套函数、类型对不上，索引就失效← ④-1 树按原值排序按文档
      
现象
WHERE DATE(created_at) = '2026-11-01'、WHERE phone = 13800000000（phone 是 VARCHAR）都会退化成全表扫。

      
根源
树按列的原值排序。函数算出来的值顺序和原值不一样，字符串和数字比较时要先把每行的字符串转成数字，都没法在树上二分。

      
做法
改写成对原列的范围：created_at >= '2026-11-01' AND created_at < '2026-11-02'；参数类型和列类型一致。8.0.13 起也可以建函数索引。下一个知识点“执行计划与 SQL 调优”专门讲。

    

  


  
第二圈 · 使用规范

  

    
主键：短、有序、不改
自增 BIGINT 或趋势递增的 ID；不用业务字段（手机号、订单号字符串）当主键。
防页分裂、二级索引膨胀，以及改主键时整行搬家。

    
联合索引：等值在前，范围和排序在后
“我的订单按时间倒序”建 (user_id, created_at)，查和排一次搞定。
防缺最左列、范围截断和 Using filesort。

    
有了 (a, b)，就别再单建 (a)
本页的 idx_user 就是 idx_user_created 的前缀。删之前先 ALTER INDEX … INVISIBLE 观察几天，没问题再删（8.0 起）。
防冗余索引：每多一棵树，每次写入就多改一棵、多一批脏页（全景第 8、12 站）。

    
列表和热点查询只取要的列
能让索引覆盖就覆盖，EXPLAIN 里看到 Using index。
防大量回表（坑 1）。

    
区分度低的列不单独建索引
status 只有两三种值，单独建索引几乎用不上，要用就放进联合索引里。
防白白多一棵树。

    
建索引、改 SQL，前后都看 EXPLAIN
看 type、key、key_len、rows、Extra 五列；大表加索引走 Online DDL（下钻第 6 步）。
防“以为走了索引”。

  


  
第三圈 · 优化和深处

  

    
树高怎么算，“2000 万行”从哪来

      
    
        
  • 能装的行数 ≈ 根的条数 × 内节点扇出层数−2 × 叶子每页行数。按本表实测平均值，3 层能装到约 754 × 754 × 221 ≈ 1.26 亿行（估算）。
    • 
        
  • 流传的算法：内节点 16 KB ÷（8 字节键 + 6 字节指针）≈ 1170，叶子按每行 1 KB 装 16 行，1170 × 1170 × 16 ≈ 2190 万。说的是“1 KB 的行、3 层”，不是硬上限。
    • 
        
  • 多一层也只多拿 1 页，上面几层通常常驻 buffer pool。真正变慢的原因多半是热数据装不下 buffer pool，下降时频繁读盘。
    • 
      

    
页为什么不满：分裂和合并

      
    
        
  • 随机插入页满时对半分裂，长期看页大约半满到七成满；本页 idx_user 实测约 64%（估算）。
    • 
        
  • 删得多了，页的数据少于 MERGE_THRESHOLD（默认 50%）时，InnoDB 会尝试和相邻页合并（按文档）。
    • 
        
  • CREATE INDEX 这种排序建索引按 innodb_fill_factor 填页，默认 100，实际给每页留 1/16 空间（按文档）。
    • 
        
  • 想把页重新压紧：OPTIMIZE TABLE（InnoDB 上就是重建表），大表要走 Online DDL。
    • 
      

    
锁和索引是一回事（全景第 6 站）

      
    
        
  • InnoDB 的行锁加在索引记录上。按主键改，锁主键树上那一条；按二级索引改，二级索引记录和回表到的主键记录都要锁。
    • 
        
  • 条件上没有索引，UPDATE 要扫整棵主键树，可重复读下扫过的记录都会加锁，相当于锁表。见 MVCC 与锁。
    • 
      

    
脏的是整页（全景第 12 站）

      
    
        
  • 改 9527 的 71 字节，页 75 整页变脏，刷回去写 16 KB，再加 doublewrite 一份。
    • 
        
  • 主键有序时，新行集中写在最右边几页，脏页少；随机主键让插入散到成千上万个页，脏页和刷盘量一起涨。
    •

特性什么时候有对索引的影响

    
      
索引条件下推 ICP5.6联合索引后面的列能在索引里先过滤，少回表（Using index condition）

      
降序索引8.05.7 能写 DESC 但会忽略；8.0 起真按降序存，混合排序 ORDER BY a ASC, b DESC 也能用上

      
不可见索引8.0先 INVISIBLE 观察再删，本页 ⑤ 就是这样屏蔽 idx_user 的

      
跳跃扫描、函数索引8.0.13缺最左列时有条件地能用（坑 2）；INDEX ((DATE(created_at)))（坑 5）

      
自适应哈希索引8.4 默认关8.0 默认开：热点页自动建哈希。8.4 起 innodb_adaptive_hash_index=OFF（本机 8.4.13 核对）

      
change buffer8.4 默认关8.0 默认缓冲二级索引的写；8.4 起 innodb_change_buffering=none（本机 8.4.13 核对）

    
  

  

  
8.4 的两个默认值、innodb_page_size=16384、innodb_fill_factor=100、optimizer_switch 里 skip_scan=on、index_condition_pushdown=on，都是在本机 MySQL 8.4.13 上用 SHOW VARIABLES 读出来的；其余版本号按 MySQL 官方文档。

练习 4 · 1000 万行

自测

  

    
1. 用一句话说出这一页的精华。
索引是一棵按键排好序、以 16 KB 页为节点的矮胖树，一次查找只读树高那么几页；InnoDB 里表就是主键那棵树，二级索引叶子只存主键值，所以要别的列就得回表。

    
2. 没有索引时，全表扫和“排好序的大文件二分”各疼在哪？
全表扫要把 4526 个叶子页全读一遍（实测拿页 5430 次、345 ms），UPDATE 时还会把扫过的行都锁上。排序文件二分每次只排除一半，100 万行要约 20 次随机读，而且插入要挪动后面所有数据。B+ 树一页放几百个分界点，数据分散在页里，插入只改一页。

    
3. 为什么走索引反而比全表扫慢？根源是哪条原理？
④-3：二级索引叶子只有主键值，每条都要回表，一次回表就是从主键根页下降 3 页，而且是随机的。10 万行就是 40 万次拿页；全表扫顺着叶子链表读，每页一次拿 221 行，只要 4812 次。

    
4. 预测：主键从 BIGINT 换成 CHAR(36) 的 UUID，idx_user 会怎样？
变大，而且不止一点。每条二级索引记录从约 21 字节（记录头 5 + user_id 8 + id 8）变成约 49 字节以上，叶子每页从几百条降到两三百条，页数翻倍多；乱序的 UUID 还让主键树本身频繁分裂、页半满（④-6 二级索引存主键，坑 4）。

    
5. 预测：给 orders 单独建一个 (status) 索引，SELECT * FROM orders WHERE status = 'CREATED' 该不该走它？
不该。数据里 10% 是 CREATED，也就是 10 万行，走索引就是 10 万次回表，跟 ⑤ 第 ⑤ 条一样会比全表扫慢（坑 1）。区分度这么低的列，单独建索引意义不大，要么放进联合索引，要么让查询带上更有区分度的条件。

    
6. 预测：orders 涨到 1000 万行，按主键找一单要拿几页？
还是 3 页。叶子约 1000 万 ÷ 221 ≈ 4.5 万页，内节点每页 754 条左右，需要约 60 个内节点页，根页放 60 条路标绰绰有余。按 ④-6 的估算，这种行长要到上亿行才会长到第 4 层。

    
7. 放回全景：第 5 站前后各发生了什么？如果 UPDATE 的条件是没有索引的 sku_id，整条链路会怎样？
前一站（第 4 站）优化器根据有哪些索引决定走 PRIMARY；后一站（第 6 站）在找到的那条索引记录上加 X 锁，然后第 7、8 站写 undo、改页、写 redo，第 12 站把整页刷回磁盘。换成 sku_id：第 4 站只能选全表扫（type=ALL），第 5 站从 3 页变成扫 4526 个叶子页，冷启动时大量读盘；第 6 站可重复读下扫过的每条记录都加 next-key 锁，等于锁表，别的用户付款在第 6 站排队；第 3 站的连接被长时间占着，第 1 站 HikariCP 借连接开始超时。

  







  
档位：标准。实测：本机 2 核 ARM，Docker 里一个 MySQL 8.4.13 容器，JDK 17.0.21 跑 IndexLab（按 JDK 8 写法编译），orders 100 万行；树的形状读自 FLUSH TABLES … FOR EXPORT 后拷出的 orders.ibd，拿页次数是 Innodb_buffer_pool_read_requests 的增量（预热后 5 次取最小，跑了两轮结果一致）。页内结构、页分裂、版本差异按 MySQL 8.4 官方文档；8.4 的默认值在本机核对。
