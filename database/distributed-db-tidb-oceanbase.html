不自己拆，换个数据库：TiDB、OceanBase、GoldenDB 替你做了什么

前五页自己做的事：定分片键、改写 SQL、搬数据、跨片查询、靠 MySQL 主从保高可用，分布式数据库把它们收进了数据库内部。TiDB、OceanBase 是原生分布式：数据自动切成小块，每块 3 个（或 5 个）副本用 Raft / Paxos 保持一致，多数副本写下才算提交，坏一台机器不丢已提交的数据。GoldenDB 走另一条路：底下还是一个个分片数据库，上面加计算节点做路由，加一个全局事务管理器（GTM）保证跨分片的一致。金融行业看中的是两件事：多副本强一致（RPO = 0）和国产化。代价是：每次写入多一次网络多数派、事务多一次取时间戳，而且“兼容 MySQL”不等于行为和 MySQL 一样（下一页）。

①为什么需要：把第 2～8 站交给数据库

在全景第 12 站，换一种问法：如果当初不自己拆，订单表 1.2 亿行、写入 3200 行/秒、恢复要 4 小时这几个问题，能不能让数据库自己解决？

全景里自己做的事分布式数据库里谁来做
第 2 站 定分片键、2 库 8 表按主键范围自动切成很多 Region（TiDB 默认每块 256 MiB 左右就分裂），数据多了自动再切，PD 自动把它们均衡到各台机器
第 3～5 站 双写、搬运、校验、切换扩容就是加机器，数据块自动搬过去；不用改应用、不用切开关
第 6～8 站 改写路由、跨片查询、归并SQL 层（TiDB server）按 Region 路由、把过滤和聚合下推到存储节点、再汇总；跨块的 JOIN、分页、唯一约束都和单库一样能写
主从复制保高可用每块 3 副本，Raft 多数派提交：坏一台不丢已提交的数据，几秒到十几秒内自动选出新 leader
跨库事务（自己不敢做）内置分布式事务：全局时间戳 + 两阶段提交，对应用就是普通的 BEGIN … COMMIT

②没有它会怎样：自己拆的那套，哪几处一直疼

  • SQL 被限制不带分片键就全路由、深分页吃内存、跨片 JOIN 做不了、唯一索引只管一张表（第 2 页）。每个新需求都要先问“带没带 user_id”。
  • 扩容是一次迁移8 张表变 16 张，一半的行要换表，就是再走一遍双写、搬运、校验、切换（第 3 页）。
  • 高可用靠主从复制MySQL 默认异步复制：主库宕机时最后一批还没传到从库的提交会丢，金融场景不能接受；半同步能缓解，但退化成异步的那一刻同样会丢。
  • 没有跨库事务转单、合并支付这种跨用户的写，只能靠 J09 的最终一致方案，代码复杂。
不懂精华时的典型误用以为换成分布式数据库就“和 MySQL 一样、还能无限扩展”，把单机 MySQL 的用法原样搬过去：自增主键、一次删几千万行的大事务、依赖间隙锁的并发控制。分布式数据库替你做了分片和高可用，但写入路径变长了、几个关键行为和 InnoDB 不一样，这些坑在下一页。

③相邻方案：三种架构，金融行业怎么选

一致性分片谁在用（公开资料）适合
TiDB 8.5Region 级 Raft，多数派提交；PD 发 TSO，Percolator 式两阶段提交按主键范围自动分裂、合并、均衡互联网和不少传统行业；开源MySQL 生态、要水平扩展、还想跑分析（TiFlash 列存）
OceanBase 4.x日志流级 Paxos表分区 → Tablet，分布在各 OBServer阿里巴巴自研，在蚂蚁集团（支付宝）内部大规模使用金融核心、既有 MySQL 也有 Oracle 迁移需求（企业版）
GoldenDB数据节点多副本 + GTM 全局事务按分片键分到数据节点（和自己拆类似）中兴官网：2019 年在中信银行信用卡新核心系统投产银行核心、要求国产化和厂商服务
云上共享存储（Aurora、PolarDB）存储层多副本不分片：一个写节点 + 多个只读节点各云厂商读多写少、数据量还在单写节点能扛的范围

选择规则：单机 MySQL 还扛得住 → 别换；读多写少 → 云上共享存储；写也要水平扩展、团队熟 MySQL → TiDB / OceanBase；银行核心、要国产化和原厂服务 → OceanBase / GoldenDB 等。交易靶场本页用 TiDB 做实验：开源、Docker 就能起一个真集群。

④原理：以 TiDB 为例，一条 INSERT 和一次 COUNT 怎么走

先知道这些 Raft：一组副本选一个 leader，写入先到 leader，leader 把日志发给其他副本，多数副本写下就算提交；leader 失联，剩下的多数重新选一个。见 Raft 共识。 两阶段提交：跨多个参与者的事务先让大家“准备好”，再统一“提交”。见 分布式事务。

机制 1：Region 就是分片，PD 就是“分片规则 + 搬运工”

  • RegionTiKV 把整张表按主键排好序，切成连续的小段，每段叫一个 Region（v8.4 起默认长到约 256 MiB 就分裂，之前是 96 MiB）。⑤ 里 2 万行的 t_order 起初只有 1 个 Region，SPLIT TABLE … REGIONS 4 以后变成 4 个。这就是全景第 2 站的“2 库 8 表”，只是数量由数据库自己决定，而且是按范围切的。
  • 副本每个 Region 默认 3 个副本（PD 的 max-replicas = 3），一个 leader、两个 follower，分别放在不同的 TiKV 上，组成一个 Raft 组。⑤：每个 Region 的副本都在 store 1、2、5 上。
  • PD记录每个 Region 在哪、谁是 leader，自动做分裂后的均衡、leader 迁移、坏节点上副本的补齐；同时发全局递增的时间戳（TSO）。它就是第 1 页的“分片规则”加上第 3 页的“搬运”，而且一直在后台做。
  • 按范围切的代价主键单调递增时，新数据永远写在最后一个 Region：一个 Raft 组、一个 leader 承担全部写入，这就是“写热点”，下一页实测。

机制 2：一次写入要多数副本点头

MySQL 主从：主库写完就回成功

异步复制下，主库提交后才把 binlog 发给从库。主库在这中间宕机，切到从库，最后那批提交就没了（RPO > 0）。好处是写入只等本机磁盘，快。

Raft / Paxos：多数副本写下才回成功

每次提交都等一次“leader → 最快的那个 follower”的网络往返。任何一台坏掉，剩下的多数里一定有这条日志（RPO = 0）；leader 坏了要选主，有十几秒的写停顿（⑤ 实测 13.9 s）。

决定胜负的约束：“已提交的数据一条都不能丢”值不值得用每次写入多一次网络往返、故障时十几秒的停顿来换。对银行账务，答案是值得，这就是金融核心系统选它们的第一个原因；第二个原因是国产化要求。副本放在同城三个机房时，网络往返只有一两毫秒；放到异地，每次提交都要多付几十毫秒，所以两地三中心通常让多数派落在同城。

机制 3：分布式事务：全局时间戳 + 两阶段提交

  • 取开始时间事务开始时向 PD 要一个全局递增的时间戳 start_ts（⑤：470480353399668741，高位是物理时间 2026-11-15 10:55:17 UTC）。之后的读都读“这个时间点之前已提交的版本”，这就是快照隔离（下一页讲它和 MySQL 的差别）。
  • 预写提交时，把要改的每个 key 写一个带锁的新版本，其中一个 key 当“主锁”，其余锁都指向它；这些 key 可能在不同的 Region、不同的 TiKV 上。
  • 提交再要一个 commit_ts，先把主锁提交；主锁一提交，整个事务就算成功，其他 key 的锁可以异步清理（读到残留锁的人会去看主锁的状态）。这套做法来自 Google 的 Percolator。
  • 代价比单机 MySQL 多了两次取时间戳、一次多数派复制和跨节点的两阶段；单行写入的延迟是毫秒级，比单机 InnoDB 高：⑤ 里单线程每 20 ms 写一行，每秒约 40 次，每一秒里最慢的那次在 6～12 ms（2 核虚拟机，3 个 TiKV 挤在同一台机器上，只看量级）。

机制 4：计算下推：TiDB server 不把整张表拉回来

⑤ 的 EXPLAIN ANALYZE SELECT COUNT(*) … WHERE shop_id = 301：过滤（Selection）和部分计数（StreamAgg）都标着 cop[tikv]，在 4 个 Region 上各自算（cop_task: {num: 4 …}），TiDB server 只拿回 4 个部分计数再加起来。这正是第 2 页 ShardingSphere 做的“改写 + 归并”，区别是 TiKV 能执行算子，归并前的数据量小得多。

⑥细节

第一圈 · 不知道就会出事

1应用的超时比选主还短，leader 一切换就报错← ④ 机制 2
现象
⑤：杀 leader 后一次写入要 13.9 秒才返回。如果应用的 socket 读超时是 5 秒，这次写入在应用看来是失败，可它其实最后成功了：重试就会写两次。
根源
选主期间 TiDB 在内部等待、重试，不会立刻报错。
做法
读超时要大于选主时间；写操作做成幂等（订单号唯一），超时后先查再决定是否重试；关键链路配好熔断（J10）。
2副本数和机房数不对，坏一个机房就停写← ④ 多数派计算器
现象
3 副本都在同一个机房（或者 2 个在 A、1 个在 B），机房 A 一断电，多数派没了，整个集群停写。
根源
多数派要 > N/2；容忍一个机房坏，就要求任何一个机房里的副本都不超过半数。
做法
3 副本放 3 个机房；两地三中心用 5 副本按 2 + 2 + 1 放，并用 label 告诉 PD 每台机器在哪个机房。
3数据量不大也上分布式，延迟和成本都变高← ④ 机制 3
现象
几千万行、写入几百每秒的库换成 TiDB，单次写入从亚毫秒变成几毫秒，机器从 2 台变成 6～9 台（PD、TiKV、TiDB 各几台）。
根源
每次提交多了取时间戳、多数派复制、两阶段提交。
做法
先看单机 MySQL + 读写分离 + 归档能不能撑住（第 1 页 ②）；分布式数据库的收益在“单机真的放不下、写不动”以后才明显。
4“兼容 MySQL”当成“行为一样”← ④ 机制 1、3
现象
代码一行没改就上线：自增 id 不连续了、热点表写不上去、批量删除报事务太大、以前靠间隙锁防住的并发插入防不住了。
根源
协议和语法兼容，但存储按范围分片、事务是快照隔离加乐观或悲观锁，和 InnoDB 的实现不同。
做法
迁移前按下一页逐项排查，并用 TiDB / OceanBase 官方的兼容性检查工具扫一遍 SQL。

第二圈 · 团队里怎么用

  • 先做容灾演练上线前按 ⑤ 的做法逐个杀 TiKV、杀 PD leader、断一个机房，记下每种情况的停写时长，写进应急手册。防的是坑 1、2 在生产上第一次出现。
  • 监控 Region 和热点盯 leader 是否均衡、有没有持续热点 Region、PD 调度是否积压。防的是“加了机器，写入还是上不去”。
  • 连接走负载均衡多个 TiDB server 前面挂负载均衡，应用不直连某一台；TiDB server 是无状态的，坏一台换一台。

第三圈 · 深处

  • 读也可以分散默认读走 leader；TiDB 支持 follower read（tidb_replica_read），让读分摊到 follower 上，代价是要先和 leader 确认一次进度。
  • TiFlash 列存TiDB 可以给表加列存副本（通过 Raft Learner 异步同步），分析查询走列存、交易查询走行存，同一份数据两种格式，就不用 ES / 数仓那条同步链路做聚合了。
  • GTM 的瓶颈GoldenDB 这类“分片 + 全局事务管理”的架构，每个全局事务都要和 GTM 打交道，GTM 自己要做成高可用并扛住事务并发；TiDB 的 PD 发 TSO 时也是批量分配来降低开销。中心化的“全局顺序”是这类系统共同的设计焦点。

下一圈

  • 从 MySQL 换过去要注意自增 ID、写热点、大事务、隔离级别四处差异，本机实测对比：下一页。
  • OceanBase 实测官方 Docker 镜像 oceanbase/oceanbase-ce（MODE=mini）要求至少 2 核 8 GB，本机跑不动，留到有更大机器时。

↺回到⑤：改一改

  1. 杀两台：同时杀掉 tikv1、tikv2，写入会怎样？读呢？再启动其中一台，多久恢复写入？（机制 2、坑 2）
  2. 加一台：再起一个 tikv4，看 TIKV_STORE_STATUS 里 Region 数和 leader 数怎么慢慢均衡过去。（机制 1：PD 调度）
  3. 短超时：把 JDBC 的 socketTimeout 改成 5000，重跑 failover-leader，数一数应用看到的“失败”，再查表看那几行到底写进去没有。（坑 1）
  4. 大一点的表：灌 200 万行，看 Region 什么时候自己分裂（不手动 SPLIT）。（机制 1）

自测

1. 用一句话说出这一页的精华

分布式数据库把分片、搬迁、路由归并、多副本高可用和分布式事务收进数据库内部：TiDB 按主键范围切 Region、每块 3 副本 Raft 多数派提交、PD 调度并发全局时间戳；GoldenDB 是分片库加 GTM；金融选它们是为了 RPO = 0 和国产化，代价是写入路径更长、选主有停顿、行为和 MySQL 不完全一样。

2. MySQL 异步主从的高可用疼在哪？

主库提交后才把 binlog 发给从库，主库在这中间宕机，切到从库就丢了最后那批已提交的数据（RPO > 0）。

3. 为什么杀 follower 毫无影响，杀 leader 却卡 13.9 秒？用 ④ 的哪条解释？

机制 2：写入只需要多数副本写下。杀一个 follower，leader 加另一个 follower 仍是 3 个里的 2 个；杀 leader，剩下两个要先发现它失联、再选出新 leader，TiDB 再重试，这段时间写不进去。

4. 预测：5 副本按 2 + 2 + 1 放在两地三中心，异地机房 C 和同城机房 A 同时坏了，还能写吗？

不能：剩下机房 B 的 2 个副本，不到 5 的多数 3 个，停写（但已提交的数据都还在 B 上）。两地三中心只保证坏一个机房能继续写。

5. 预测：订单表在 TiDB 上用 id BIGINT AUTO_INCREMENT 做主键，大促时加了 3 台 TiKV，写入能力会线性涨吗？

不会：主键单调递增，新订单都写在最后一个 Region，这个 Region 的 leader 只在一台 TiKV 上，加机器分摊不了它。要用 AUTO_RANDOM 之类把写入打散（下一页实测）。

6. 放回全景：第 12 站替代了哪几站？如果交易靶场当初选了 TiDB，第 9～11 站（ES 同步）还需要吗？

替代了第 2～8 站：分片、迁移、路由、跨片查询都由数据库自己做。按商家查在 TiDB 里能直接写（全表分布式扫描或二级索引），但全文检索和多条件相关度排序仍然是 ES 的强项，所以第 9～11 站多半还在，只是同步源从 Canal 换成 TiDB 的 TiCDC；只做聚合报表的话可以改用 TiFlash。

档位：标准。本机跑过（2 核 ARM 虚拟机，JDK 17，TiDB / TiKV / PD v8.5.8 镜像，1 PD + 3 TiKV + 2 TiDB）：⑤ 的 tour 和两次 failover 各跑 1 次。多数派计算器是纯函数（node 里跑过），停顿时长用 ⑤ 的实测锚点。OceanBase、GoldenDB 没有在本机跑。

按文档：TiDB v8.5（region-split-size v8.4.0 起默认 256 MiB、此前 96 MiB；PD max-replicas 默认 3；TiDB 层无状态，cop[tikv] 表示在 TiKV coprocessor 里执行；PD 分配 TSO；事务模型来自 Percolator）；OceanBase V4.3.5 文档（单机分布式一体化架构，分区 → Tablet → 日志流，日志流副本间 Paxos 复制；社区版不支持 Oracle 语法兼容；Docker 镜像要求至少 2 核 8 GB）；中兴 GoldenDB V6 白皮书（计算节点、数据节点、管理节点、全局事务管理节点四部分，GTM 生成全局事务号、维护活跃事务快照）与中兴官网 2019-12-23 新闻（中信银行信用卡新核心系统投产）。
