明明有索引，它偏不走：执行计划与 SQL 调优

交易靶场的 orders 表上线一周，慢查询里冒出三条：按订单号查 0.51 s、后台翻页 0.84 s、按天对账 0.23 s。三条要用的列上都有索引，EXPLAIN 却都是 type=ALL（本页实测）。精华是两句话：执行计划是优化器按统计信息“估”出来的最便宜走法，不是执行记录。索引没用上只有两种原因：写法让它没法在排好序的 B+ 树上定位，或者它算过之后觉得回表太多、不如全表扫。调优就是用 EXPLAIN 分清是哪一种，再对症改。分不清，就会一慢就加索引，加了照样不走。

①什么时候用得上：同一个第 4 站，1 行还是 99.6 万行

在全景第 4 站，这一步要解决：SQL 解析完以后，有好几种执行方式，优化器要挑一种。挑出来的那一种就叫执行计划。付款那条 UPDATE … WHERE id = 9527 很好挑；条件一换，挑的结果就可能从读 3 页变成扫整张表。

交易靶场这周的三条慢 SQL

按订单号查 · 一天几万次509 ms扫 100 万行，回 1 行
后台订单列表 · 第 45001 页840 ms扫 190 万行，回 20 行
按天对账 · 每天几次231 ms扫 100 万行，回 1 行
按 id、按用户查 · 各 300 次0.1～0.5 ms对照：这两条是好的

数字来自 ⑤ 的实测：本机 Docker 里的 MySQL 8.4.13，100 万行，performance_schema 的平均耗时和每次扫描行数。三条用到的列 order_no、created_at 上都建了索引。

②常见笨办法：不看计划就动手

下面四种做法都很常见，有时也能碰巧见效。共同的毛病是：不知道优化器实际选了哪条路、为什么选它。

慢了就加索引

给 created_at、order_no 都建上索引。

三条照样全表扫：一条是列上套了 DATE()，一条是拿数字比字符串列，一条是要扔掉 90 万行。加索引解决不了写法问题，还拖慢每次写入。

凭感觉改写

SELECT * 改成列名、IN 改 EXISTS、换个 ORM 写法。

没有测量，改完不知道快没快，也不知道为什么。碰巧快了，下次遇到同类问题还是不会。

FORCE INDEX 硬压

“它不走索引？那就逼它走。”

今天对，数据一变就错。实测：命中 30% 的行时强制走 idx_user 要 799 ms，全表扫只要 213 ms。

加缓存、加机器

前面挡一层 Redis，或者升配置。

把扫 100 万行的 SQL 藏起来了。缓存一失效，数据库照样被打满；UPDATE 走全表还会在全景第 6 站锁一大片，缓存挡不住。

缺的那一块：先拿到证据：优化器实际选了哪条路、估了多少行、为什么这么估。执行计划就是这份证据。一个典型误用：看到 possible_keys 里有索引，就以为“用上了”。那一列只是候选，真正用的是 key。

③工具和路线：找、看、量、问、改

MySQL 自带的工具就够用。它们回答的问题不一样，按顺序用。

工具回答什么代价什么时候用
慢查询日志哪些语句超过了 long_query_time，每条扫了多少行写文件，开着也便宜常开。默认关着，阈值默认 10 s（本机 8.4.13 核对），生产一般设 0.5～1 s
performance_schema 语句摘要把参数换成 ? 归成一类（指纹），按总耗时排8.4 默认开着找“最该治的那条”。sys.statement_analysis 是它的现成视图
EXPLAIN选了哪个索引、什么访问方式、估多少行不执行，毫秒级每条可疑 SQL、每条新 SQL 上线前
EXPLAIN ANALYZE每一步估了多少行、实际多少行、花了多久真的执行一遍EXPLAIN 看着没问题却还是慢；怀疑估算不准（8.0.18 起）
optimizer_trace每种候选走法的行数和代价，为什么淘汰输出很长“明明有索引，它偏不走”，想知道它怎么算的

④背后的机制：优化器怎么估价，索引为什么“失效”

先看优化器怎么在几种走法里挑；再看索引“失效”的两类原因：用不上、不划算；然后是最关键的一张图，分界点在哪；最后说为什么非要“估代价”，以及怎么读 EXPLAIN。

先知道这些
  • B+ 树按列的原值排好序：能从根下到叶子找到起点，再顺着叶子往后读。见上一页 ④-1。
  • 回表：二级索引的叶子只有“索引列 + 主键”，要别的列，得拿主键再去主键树里找一次。见上一页 ④-3。
  • EXPLAIN 不执行 SQL：它输出的是优化器的计划和估算。EXPLAIN ANALYZE 才会真的跑一遍。

④-1 优化器怎么挑：列出走法 → 估行数 → 算代价 → 取最小

行数有两个来源，后面 ⑥ 会用到：

  • index dive：有范围或等值条件时，从根下到范围两端的叶子，估中间有多少行。准，但每个范围要下潜两次。
  • 索引统计：ANALYZE TABLE 时每个索引采样若干页（默认 20 页），算出表大概多少行、每个值平均重复几次。便宜，但粗。n_rows = 990792 就是这么来的。

④-2 索引“失效”的第一类：写法让它用不上

B+ 树能帮忙的前提是：条件能翻译成“在排好序的叶子上，从这里读到那里”。条件写成 列 比较 常量，列保持原值，就能翻译；对列做了加工，或者比较规则和排序规则对不上，就翻译不了。

前导通配 LIKE '%09527'、OR 的一边没有索引，是同一个道理：要找的行不挨在一起，树帮不上忙。⑥ 的实验台里每一种都有实测。

④-3 第二类：用得上，但不划算。分界点在哪？

能用索引时，优化器还要比代价。走索引的代价随命中行数线性涨（每行一次回表），全表扫的代价基本固定。两条线总会交叉。下面是在 100 万行上真测的：同一个 SUM(amount_cents)，命中比例从 0.5% 到 30%，分别强制走索引、强制全表扫。

user_id 和主键顺序无关

命中的行散在 4526 个叶子页里，每次回表大多跳到另一页。真实分界 约 7.6%。优化器到 10% 还在走索引：270 ms 对 207 ms，估得太乐观。

created_at 和主键同序

订单按时间先后插入，时间相邻的行就在相邻的页上，回表是顺着往后读。真实分界 约 16.4%。优化器 15% 就放弃了：选的全表扫 253 ms，走索引 231 ms，估得太悲观。

为什么两个索引的分界点一样：trace 里同样估 5000 行时，两个索引的代价是 1750.26 和 1749.91，几乎相同。MySQL 8.4 默认的代价模型把每次回表都按读一个页算，不看这些行是挤在同几页上，还是散在几千页里。所以它在两条线之间选了一个折中点。离分界点远的地方它总是对的，选错只会发生在分界点附近，而那里两种走法本来就差不多快。数据不在内存里时，随机回表要读盘，真实分界会更靠左（估算，本页没测冷数据）。

④-4 为什么这样设计：按代价选，不按规则选

按规则选 “有索引就用，主键优先”

  • 不需要统计信息，计划稳定可预测。
  • 命中 30% 时也走索引：799 ms 对 213 ms，慢 3.7 倍；50% 时 1329 ms 对 220 ms，慢 6 倍。
  • 同一条 SQL，参数从 1024 换成 BETWEEN 1 AND 60000，它不知道该换走法。

按代价选 MySQL、PostgreSQL、Oracle 现在的做法

  • 命中 1 行走索引，命中 30% 走全表扫，同一条 SQL 自动换。
  • 数据涨了、分布变了，计划跟着变。
  • 代价是“估”出来的：统计信息旧了、估错了，计划就错（⑥ 第三圈）。

决定胜负的约束：最快的走法取决于数据（命中多少行、这些行在页上怎么分布），而不取决于 SQL 文本。只看文本的规则没法同时把 user_id = 1024 和 user_id BETWEEN 1 AND 60000 都选对。Oracle 早年用规则优化器，后来也改成了按代价。

那为什么不干脆数清楚有多少行？数清楚就等于把查询执行一遍。所以优化器只“估”：一个范围下潜两次（约几页），IN 列表超过 200 个值（eq_range_index_dive_limit）就连下潜都省了，改用统计信息里的平均值；统计信息每个索引只采 20 页。估得便宜，代价就是估不准，这正是 ⑥ 第三圈要处理的事。

④-5 读 EXPLAIN：先看这几列

type 是访问方式，从好到差大致是：

const主键或唯一索引等值，最多 1 行：id = 9527 eq_ref联表时按主键一对一：延迟关联里的 o ref普通索引等值：user_id = 1024 range索引上的一段：created_at 区间 index整棵索引从头扫到尾 ALL整张表从头扫到尾
possible_keys / key候选的索引 / 实际用的索引。候选里有、实际没用，多半是不划算或类型转换。
key_len用到的索引键有多少字节，看联合索引用到了前几列。
rows估计要读的行数。是估的，可能差几倍。
filtered读出来的行里，估计有百分之几能过剩下的条件。
ExtraUsing index 覆盖索引不回表；Using index condition 在索引里先过滤；Using where 取出来再过滤；Using filesort 额外排序；Using temporary 用了临时表。

先猜：

第一圈 · 注意事项

坑 1列上套函数、做运算← ④-2 树按原值排序实测
现象
DATE(created_at) = … 428 ms，user_id + 0 = 1024 368 ms，都是 ALL，possible_keys 为 NULL。
根源
树里存的是列的原值，优化器不会把函数反推成原值的区间。
做法
把加工挪到常量那边，写成区间。实在要按函数查，8.0.13 起可以建函数索引 INDEX ((DATE(created_at)))，查询要写成一模一样的表达式。
坑 2字符串列拿数字比← ④-2 比较规则对不上实测
现象
order_no = 2026110100009527 502 ms，ALL，警告 1739。加引号 0.71 ms。
根源
字符串和数字比，两边都转浮点数；等于这个数的字符串不止一种写法，在树上不挨着。
做法
Java 实体的类型和列对齐：订单号、手机号、身份证号这类“长得像数字的字符串”一律用 String。反方向（数字列拿字符串比）不受影响。联表时两边列的字符集或排序规则不同，也会触发同样的转换（按手册）。
坑 3前导通配← ④-2 只能按前缀定位实测
现象
LIKE '%09527' 522 ms，ALL；LIKE '2026110100009%' 3.9 ms，range。
根源
字符串按前缀排序，后缀相同的值散在整棵树里。
做法
按前缀查；要按后缀查，存一列反转后的值再建索引；真要全文搜索，用全文索引或搜索引擎。
坑 4OR 的一边没有索引← ④-2 有一边要全扫实测
现象
user_id = 1024 OR sku_id = 88 385 ms，ALL；换成两边都有索引的 OR order_no = …，0.62 ms，index_merge。
根源
sku_id 那一半只能全表扫才找得全，既然要扫，就一起扫了。
做法
两边都建索引（走 index_merge 取并集），或者拆成两条 SQL 用 UNION ALL。
坑 5命中太多，优化器主动不走← ④-3 分界点实测
现象
user_id BETWEEN 1 AND 60000（30%）走 ALL，607 ms；possible_keys=idx_user，key=NULL。
根源
这不是 bug：30% 的行一行一次回表，比全表扫贵（强制走索引实测 799 ms 对 213 ms）。
做法
别 FORCE INDEX。只要索引里的列时，用覆盖索引免掉回表；否则分批、加更有区分度的条件，或者问问业务为什么要一次拿 30 万行。
坑 6深分页← ④-3 回表代价实测
现象
LIMIT 900000, 20 795 ms，ALL + filesort；LIMIT 20 0.56 ms。
根源
offset 的行要先产出、再扔掉。走 idx_created 要回表 90 万次，优化器宁可全表扫加排序。
做法
列表接口用游标分页（1.8 ms）；时间可能重复时游标用 (created_at, id) 两列，否则会漏行。一定要跳页时用延迟关联（198 ms），并限制最大页数。

第三圈 · 优化和深处

深 1估算为什么偏、偏多少实测 + 源码
  • 范围普遍高估约 2 倍：命中 1% 估 18564 行，实际 10001；对账估 162404，实际 86400。index dive 在范围两端是精确的，中间那一大段是按上层节点的页数推算出来的。
  • 封顶一半：30% 和 50% 都估成 495396，正好是 990792 的一半。MySQL 8.4 源码 btr0cur.cc：if (n_rows > table_n_rows / 2 && !is_n_rows_exact) n_rows = table_n_rows / 2; 在优化器眼里，50% 和 90% 一样。
  • 表行数是采样的：n_rows 990792，真实 100 万；每个索引采 20 页（innodb_stats_persistent_sample_pages），改动超过 10% 自动重算（innodb_stats_auto_recalc）。批量导入后马上查，统计可能还是旧的，手动 ANALYZE TABLE。
  • IN 列表 ≥ 200 个值不再逐个下潜，改用平均重复次数。数据倾斜时（某个大客户占一半订单）会差很多。
深 2让它估对、选对：从轻到重按手册
  • ANALYZE TABLE：先确认统计信息是新的。
  • 直方图（8.0.3 起）：ANALYZE TABLE orders UPDATE HISTOGRAM ON status，主要给没有索引的列提供分布，影响 filtered 和联表顺序。
  • 改写或函数索引：让条件变成树能用的样子（坑 1～4）。
  • 优化器提示：SELECT /*+ INDEX(orders idx_created) */ …，8.0.20 起有索引级的 INDEX / NO_INDEX，只作用于这一条语句。
  • FORCE INDEX：最后的手段，写注释。
深 3EXPLAIN ANALYZE 怎么读、什么时候别用实测
  • 从最里层读起，找“估计 rows”和“实际 rows”差十倍以上的节点：计划多半就是在那里选歪的。
  • loops 大于 1 时，rows 和 time 是每次循环的平均值，总量要乘回去。
  • 它真的执行：一条要跑 10 分钟的报表，EXPLAIN ANALYZE 也要跑 10 分钟。生产上先 EXPLAIN；写语句改写成等价的 SELECT 再分析。
深 4代价常量能改，但别先改它实测 + 按手册
  • 常量在 mysql.server_cost、mysql.engine_cost 两张表里，改完 FLUSH OPTIMIZER_COSTS 生效，影响所有 SQL。
  • ④-3 里 user_id 的分界点偏右，是因为模型不分随机还是顺序回表；调大读页代价会让 created_at 那种顺序回表也跟着吃亏。
  • 先改写、加覆盖索引，个别语句用提示；全局常量留给“整个实例的硬件和默认假设差太远”的情况。

面试官会怎么问

建了索引为什么不走？你怎么判断是哪种原因？

两类。一类是写法让索引用不上：列上套函数或运算、字符串列拿数字比、前导 %、OR 的一边没索引，树没法定位起点（④-2）。另一类是能用但不划算：命中行多，回表代价超过全表扫（④-3）。判断：EXPLAIN 看 possible_keys，NULL 就是写法问题；有候选但 key 为 NULL，先 SHOW WARNINGS 找 1739 类型转换警告，没有就开 optimizer_trace 比两边的代价。

EXPLAIN 的 rows 准吗？什么时候会很不准？

是估计。范围靠 index dive，本页实测高估约 2 倍；超过表一半的范围被截成一半；IN 超过 200 个值改用平均值，数据倾斜时偏得厉害；统计信息是采样的，批量导入后可能还是旧的。要看真实行数用 EXPLAIN ANALYZE。

LIMIT 1000000, 20 为什么慢？怎么优化？

offset 的行要先产出再扔掉；走索引要回表 100 万次，优化器多半改成全表扫加排序。优化：游标分页，用上一页最后一条的排序键做条件，只读 20 行；要跳页用延迟关联，先在覆盖索引里翻页拿 id 再回表；产品上限制最大页数。

练习 4 · 冷数据的分界点

重启容器时加 --innodb-buffer-pool-load-at-startup=OFF，每个比例跑前都重启一次，再跑 cross 段。先猜：user_id 的分界点往左还是往右移？

自测

1. 用一句话说出这一页的精华。

执行计划是优化器按统计信息估出来的最便宜走法；索引没用上，要么是写法让它没法在有序的树上定位，要么是它估算后觉得回表太多不划算。调优就是用 EXPLAIN 分清是哪种，再对症改。

2. “慢了就加索引”疼在哪？

不知道是哪一类原因。写法问题（函数、类型转换、前导 %）加多少索引都用不上；不划算的问题，加普通索引也不会被选。白白拖慢写入。靶场里三条慢 SQL 用到的列本来就有索引。

3. 为什么字符串列拿数字比会失效，数字列拿字符串比就没事？根源是哪条原理？

④-2。字符串和数字比较按浮点数比：字符串列那边，'02026…'、'2026….0' 这些不同的字符串都等于同一个数，在按字符串排序的树上不挨着，只能逐行转换。数字列那边，只要把常量 '1024' 转成数字一次，就能按数字顺序在树上定位。

4. 预测：user_id BETWEEN 1 AND 30000（命中 15%）优化器选什么？谁快？

选全表扫：估 31.8 万行，走索引的代价约 111148，超过全表扫的 101718。这次选对了：实测强制走索引 398 ms，全表扫 208 ms。user_id 的真实分界在 7.6% 左右，15% 已经离它很远（④-3）。

5. 预测：订单涨到 1000 万行，游标分页那条和 LIMIT 9000000, 20 各会怎样？

游标分页几乎不变：从 idx_created 下到起点读 20 行、回表 20 次，树高最多多一层。offset 版本大约慢 10 倍：要全表扫 1000 万行、排序、扔掉 900 万行（坑 6）。

6. 预测：user_id BETWEEN 1 AND 100000（50%）和 BETWEEN 1 AND 180000（90%），EXPLAIN 的 rows 会差多少？

一样，都是 495396。范围估算超过表行数一半就被截成一半（深 1，btr0cur.cc）。好在两种情况都会选全表扫，截断不影响结果。

7. 放回全景：第 4 站前后各发生了什么？执行计划选错了，整条链路会怎样？

前一站（第 3 站）连接线程收到 SQL；第 4 站先由解析器变成语法树、打开表，再由优化器挑走法；后一站（第 5 站）InnoDB 按计划沿 B+ 树找页，第 6 站在找到的记录上加锁。如果 UPDATE 的条件写成了 DATE(created_at) = … 或者字符串列拿数字比，第 4 站只能选全表扫：第 5 站扫 4526 个叶子页，冷数据时大量读盘；第 6 站可重复读下扫过的每一行都加 next-key 锁，别的付款请求在这里排队；事务变长，第 3 站的连接被占住，第 1 站 HikariCP 借不到连接，开始超时。

档位：标准。实测：本机 2 核 ARM，Docker 里一个 MySQL 8.4.13 容器（buffer pool 512 MB，数据全在内存），JDK 17.0.21 跑 PlanLab（按 JDK 8 写法编译），orders 100 万行。慢查询来自 mysql.slow_log 和 events_statements_summary_by_digest，代价来自 optimizer_trace，耗时是预热后 3 次取最快。范围估算封顶一半读自 MySQL 8.4 源码 storage/innobase/btr/btr0cur.cc；类型转换规则、直方图、优化器提示和版本号按 MySQL 8.4 官方手册；8.4 的默认值在本机核对。没测冷数据，④-3 关于冷数据的那句是估算。
