9527 在哪张表：分片以后的跨片查询、分页与全局表

拆完以后，每张表只知道自己那一份。所以凡是“需要全局视野”的事都变难了：不带分片键的查询要问遍所有表，跨片分页要每张表都多取前面那些行再在内存里比，聚合和 JOIN 要改写或者干脆做不了，唯一约束只在一张表里有效。办法只有两类：让查询重新带上分片信息（基因、映射表、绑定表、全局表），或者把这类查询挪出分片库（游标分页、ES、离线数仓）。

①为什么需要：拆完以后，四种查询各碰几张表

在全景第 7、8、9 站，这一步要解决：分片键是 user_id，可业务里不是每个查询都带着它。

第一行是分片想要的样子；后三行都是“全局视野”的查询。它们功能上都对，只是成本被放大了：客服那条是 8 倍的查询次数，运营那条是几十万行被拉进应用内存。这一页要做的，是让后三行尽量变回第一行，变不回来的就挪走。

②没有它会怎样：全路由的四种代价

什么查询不处理会怎样（⑤ 实测，80 万行、8 张表）
只拿订单号问遍 8 张表才找到 1 行；如果对老单号硬套基因，去 t_order_7 找 9527，0 行，返回“订单不存在”。
跨片深分页翻到 offset 100000：每张表取 100020 行，一次查询 2.4 秒、JVM 分配 2.7 GB；同一页用游标翻，23 ms、0.7 MB。
聚合AVG 不能把 8 个平均数再平均，要改写成 SUM 和 COUNT；GROUP BY … ORDER BY cnt LIMIT 3 每张表都去掉了 LIMIT，所有分组全拉回来。
JOIN 和唯一约束订单和明细没配绑定表，一次 JOIN 变成 32 条 SQL；两个用户各插一单 order_no = 'DUP-1'，都成功了：唯一索引只管自己那张表。
不懂精华时的典型误用以为 ShardingSphere “支持分页”就万事大吉，运营后台照旧给一个能跳到任意页的分页条。测试环境每张表几千行，一切正常；上线后有人翻到几千页，订单服务的堆被一个查询吃掉几个 GB，Full GC 拖慢了所有下单请求。

③相邻方案：每种难题都有“带回分片信息”和“挪出去”两类办法

难题带回分片信息挪出分片库交易靶场的选择
只有订单号基因法：订单号最低几位放 user_id % 8；映射表：订单号 → user_id，按订单号再分片ES 里按订单号搜新单号用基因；老单号走广播（低频），量大了再建映射表
跨片分页按用户的列表本来就带分片键，只碰一张表游标（created_at < 上一页最后一条）；ES search_after；离线数仓运营后台不许跳页，只有“下一页”；报表走数仓
按商家查异构索引表：按 shop_id 再存一份（只存订单号和排序字段）ESES（第 4、5 页）
JOIN绑定表（同一个分片键）；全局表（每库一份）；冗余字段应用里查两次再拼；联邦查询（ShardingSphere sql-federation）订单和明细配绑定表，地区、类目配全局表
全局唯一唯一键里带分片键，或者唯一值本身就带分片信息（基因）单独一张按该值分片的唯一表，或者用 Redis 先占位订单号全局唯一靠号段 / 雪花发号，不靠索引

选择规则：高频的查询让它带回分片信息，低频的允许全路由，重的（深分页、全文、聚合报表）挪出分片库。

④原理：路由看得见什么、结果怎么归并、哪些 SQL 会被改写

先知道这些 路由：上一页机制 1，ShardingSphere 只能用解析出来的分片条件算出去哪几张表，看不见就全路由。 雪花号：时间戳 + 机器号 + 序列号拼成的 64 位整数，见 分布式 ID。它的低位是序列号，所以原样取模分布很差。

机制 1：订单号基因，让“只有订单号”也能算出表

基因法的本质是把分片键的一部分信息编进另一个常用的查询键里。它只对拆分以后新发的号有效：老订单号是按顺序发的，9527 % 8 = 7，可 9527 属于用户 1024，在 t_order_0。所以算法里一定要有一条“老号段走另一条路”的分支：广播、映射表，或者在迁移时给老订单补一张“订单号 → user_id”的映射。

机制 2：结果怎么归并，为什么深分页会吃内存

归并本身很省：8 份结果各自已经按 created_at 排好，优先队列每次只比 8 个队头（OrderByStreamMergedResult）。贵在“8 份结果从哪来”：ShardingSphere 默认每个库只给一次查询 1 个连接（max-connections-size-per-query = 1），而 ds_0 要查 4 张表，只能一条接一条执行；为了让连接腾出来，前一条的结果要整个读进内存（源码里的 CONNECTION_STRICTLY → JDBCMemoryQueryResult）。这就是 ⑤ 里 2.7 GB 的来历。

机制 3：全局视野法的代价，和游标为什么便宜

  • 改写谁是全局第 100001 名，只看每张表的前 100020 名就够，少看一行都可能漏，所以 LIMIT 100000, 20 被改写成每张表 LIMIT 0, 100020。代价 = 分片数 × (offset + size)，随页码线性涨，随分片数线性涨。
  • MySQL 那边也变了每张表的 LIMIT 0, 20 走 idx_created 倒序扫描，读 20 行就停；到了 LIMIT 0, 1020，优化器判断回表 1020 次不如全表扫描加排序，改成了 Using filesort（⑤ 的 EXPLAIN）。所以第 51 页就已经比第 1 页慢十几倍。
  • 游标WHERE created_at < '上一页最后一条' ORDER BY created_at DESC LIMIT 20：每张表从索引的这个位置往后读 20 行，和翻到第几页无关。代价是不能跳页，只能一页一页往后翻；排序字段要唯一（不唯一就带上 id 一起比）。

换算系数来自 ⑤ 的实测（JDK 17、ShardingSphere 5.5.3）：每拉进 JVM 一行，分配约 3.5 KB（2743 MB ÷ 800160 行；是累计分配量，包括很快变成垃圾的部分）。“走 filesort”的门槛 1020 行是本机 10 万行一张表时的实测，表越大门槛越不一样。页码滑块按对数刻度，从第 1 页到第 50000 页。

机制 4：聚合和排序会被改写（⑤ 的真实 SQL）

  • AVG8 个平均数不能再平均（每张表行数不同）。AVG(amount_cents) 被改写成同时取 COUNT(amount_cents) AS AVG_DERIVED_COUNT_0 和 SUM(amount_cents) AS AVG_DERIVED_SUM_0，归并时用总和除以总数。
  • GROUP BY + LIMITGROUP BY shop_id ORDER BY cnt DESC LIMIT 3：每张表的前 3 名合起来不一定是全局前 3 名（一个商家可能在每张表都排第 4），所以每张表的 LIMIT 被改成了 LIMIT 2147483647，所有分组都拉回来，在内存里合并计数再排序。分组多时，这就是第二个吃内存的地方。
  • COUNTCOUNT(*) 各表相加即可，最便宜；COUNT(DISTINCT x) 要看 x 和分片键的关系，不同表里可能有同一个值。

机制 5：JOIN 只能在同一个库里做，绑定表把组合数从 4 × 4 降到 1 × 1

为什么 ShardingSphere 不自己看出 t_order_0 只和 t_order_item_0 有关？因为两张逻辑表的分片规则只是“碰巧长得一样”，框架不能假定同一个 user_id 一定落在同号的表上。bindingTables 就是你向它保证：这两张表分片键相同、规则相同、表号一一对应。跨库的 JOIN（比如按 user_id 分的订单表 JOIN 按 shop_id 分的商家表）在 SQL 层做不了，要么冗余字段，要么应用里查两次，要么打开联邦查询（sql-federation，把数据拉到 ShardingSphere 里算，慢，适合低频）。

  gene_table:

    props: { strategy: COMPLEX, algorithmClassName: labs.….GeneShardingAlgorithm, target: table }
GeneShardingAlgorithm.doSharding（核心）ComplexKeysShardingAlgorithm
Collection<Comparable<?>> users = m.get("user_id"), ids = m.get("id");
if (users != null)        users.forEach(u -> slots.add(((Number) u).longValue() % 8));
else if (ids != null) for (Comparable<?> i : ids) {
    long id = ((Number) i).longValue();
    if (id < GENE_MIN) return available;          // 老单号没有基因：广播
    slots.add(id % 8);
}
else return available;                            // 两个都没有：全路由

⑥细节

第一圈 · 不知道就会出事

1老订单号没有基因，硬算会查错表← ④ 机制 1
现象
⑤ A：9527 按基因去 t_order_7，0 行，用户看到“订单不存在”。
根源
基因只对拆分后新发的号成立；老号是顺序发的，低位和用户无关。
做法
算法里按号段区分新老（⑤ 用 GENE_MIN）；老号低频就广播，高频就在迁移时建一张“订单号 → user_id”的映射表，先查映射再按 user_id 路由。
2深分页一个查询吃掉几 GB 内存← ④ 机制 2、3
现象
⑤ B：offset 100000 时一次查询分配 2.7 GB、2.4 秒；同时 MySQL 那边每张表都在 filesort 10 万行。几个人同时翻，订单服务就开始 Full GC。
根源
全局视野法每张表都要取 offset + size 行；每个库 1 个连接查 4 张表时，结果要整个读进内存再归并。
做法
产品上不提供跳页，只有“下一页”（游标）；必须跳页的，限制最大页码；导出、报表走离线数仓；全文和组合条件的翻页交给 ES 的 search_after。
3GROUP BY + LIMIT 把所有分组拉回来← ④ 机制 4
现象
⑤ C：“销量前 3 的商家”，每张表的 LIMIT 被改成 2147483647。商家有 2 万个时，每张表回 2 万行，内存里合并 16 万行。
根源
局部前 3 名合起来不等于全局前 3 名，只能全拿。
做法
这类统计不要在线上分片库实时算：预聚合到一张按商家分片的统计表，或者交给 OLAP。
4唯一索引只在一张表里唯一← ② 每张表只知道自己
现象
⑤ E：两个用户各插一单 order_no = 'DUP-1'，都成功，全局有两行。
根源
UNIQUE KEY 是每张真实表自己的 B+ 树，表和表之间不检查。
做法
全局唯一的值由发号器保证（号段、雪花），不依赖索引；必须靠数据库保证的（比如手机号注册），按这个值单独建一张分片表来占位。
5忘了配绑定表，JOIN 变成笛卡尔积路由← ④ 机制 5
现象
⑤ D：订单 JOIN 明细，32 条 SQL，其中 24 条注定查不到数据。
根源
两张逻辑表的规则一样，框架也不能假定它们一一对应。
做法
同一个分片键、同样规则的主子表，一律配 bindingTables；字典表配全局表。
6一条 INSERT 带多个用户，被拆到两个库，不再是原子的← 上一页机制 1 路由
现象
（按机制推演，没单独跑）INSERT … VALUES (用户 1024 …), (用户 1025 …) 被改写成两条，分别发往 ds_0 和 ds_1；一边成功一边失败时，没有本地事务能把两边一起回滚。
根源
两个库是两个 MySQL 实例，各自提交。
做法
批量写按分片键分组，每组一个本地事务；真的要跨库原子，走 J09 的分布式事务方案，或者 ShardingSphere 的 XA（有性能代价）。

第二圈 · 团队里怎么写

  • 列表接口面向用户的列表都带 user_id；面向运营的列表只给“下一页”，返回游标（最后一条的 created_at 和 id）。防的是坑 2。
  • 新老号段拆分那天起发的号都大于一个固定值，代码里用常量 GENE_MIN 区分，并写进分片算法的单元测试。防的是坑 1。
  • 绑定表清单新增一张跟着订单走的子表（明细、物流、评价），评审时检查是否加进 bindingTables。防的是坑 5。
  • 报表不走在线库聚合排序、导出全量订单走离线数仓或 OLAP，在线分片库只做按 key 的读写。防的是坑 2、3。

第三圈 · 深处

  • 连接数换内存把 max-connections-size-per-query 调到 ≥ 4，每张表各用一个连接，结果就能流式读取（MEMORY_STRICTLY → JDBCStreamQueryResult），归并时只在内存里放 8 个队头。代价是一次查询占 8 个连接；而且 MySQL 驱动默认会把整个结果集读进客户端，要配合 useCursorFetch 或 fetchSize = Integer.MIN_VALUE 才真正流式。线上更稳的做法仍是不让深分页发生。
  • 二次查询法一种减少深分页传输量的技巧：先每张表 LIMIT offset/N, size 找到最小时间，再用这个时间到每张表取一个范围，算出精确位置。实现复杂、对数据分布敏感，ShardingSphere 没有内置；知道有这条路即可。
  • 异构索引表按 shop_id 再分一套表，只存 (shop_id, created_at, order_id)：商家查询先在这里分页拿订单号，再按订单号（基因）回主表取详情。写入时要同时维护两份，常用 binlog 异步同步（和第 5 页 ES 的同步同一个套路）。

下一圈

  • 不停机迁移把 1.2 亿行搬进 8 张表，搬之前先把这一页的查询都改好：第 3 页。
  • ES 的分页ES 里也有“from + size 越翻越贵”，默认上限 1 万条，search_after 就是 ES 版的游标：第 4 页。
  • 联邦查询打开 ShardingSphere 的 sql-federation，跨库 JOIN 能跑了，看它把多少数据拉进内存。

  3. 强制走索引：把分页 SQL 改成 FORCE INDEX(idx_created)（ShardingSphere 能透传吗？），比较 offset 1000 的耗时。（机制 3）
  4. 唯一占位：建 t_order_no(order_no PRIMARY KEY) 按 order_no 分片，插订单前先插它，重跑 unique。（坑 4）

自测

1. 用一句话说出这一页的精华

拆完以后每张表只知道自己那一份，凡是要全局视野的查询（无分片键、深分页、聚合、JOIN、唯一）都会被放大；高频的让它带回分片信息（基因、映射表、绑定表、全局表），低频的允许全路由，重的挪出分片库（游标、ES、数仓）。

2. 为什么 LIMIT 100000, 20 要改写成每张表 LIMIT 0, 100020，不能每张表 LIMIT 12500, 20？

全局第 100001 名可能全部来自同一张表（比如那段时间的订单恰好都在 t_order_3），每张表只取均摊的一段就可能漏掉；只有每张表都把前 100020 名交出来，才能保证归并结果正确。

3. 坑 2 的 2.7 GB 是 ④ 的哪两条机制叠出来的？

机制 3：全局视野法每张表取 offset + size 行，一共 80 万行；机制 2：每个库 1 个连接查 4 张表，结果要整个读进内存（CONNECTION_STRICTLY）。

4. 预测：把 8 张表扩到 64 张（库不变），同样翻到 offset 100000，JVM 分配大约多少？游标呢？

全局视野：64 × 100020 ≈ 640 万行，按每行 3.5 KB 约 21 GB，基本等于 OOM。游标：64 × 20 = 1280 行，约 4 MB。分片越多，全局视野法越不可用。（计算器里拖到 64 试试。）

5. 预测：SELECT COUNT(DISTINCT user_id) FROM t_order 在靶场的规则下，各表的结果直接相加对不对？换成 COUNT(DISTINCT shop_id) 呢？

user_id 对：分片键相同的行一定在同一张表，不同表里不会有同一个用户，各表去重后相加就是全局去重数。shop_id 不对：同一个商家的订单散在 8 张表，相加会重复计数。能不能直接加，取决于去重的字段和分片键的关系。

6. 放回全景：第 8 站前后各发生了什么？运营后台的深分页没改，迁移切读那天会怎样？

之前：第 7 站按订单号查（基因 / 广播）；之后：第 9 站商家查询交给 ES。没改深分页：切读前它查的是旧单表，LIMIT 100000, 20 只在 MySQL 里数行（实测单表 61 ms）；切读到新表后，同一个查询变成 8 × 100020 行进 JVM，订单服务的内存和 GC 突然恶化，而这时最容易误判成“新库有问题”去回滚。所以跨片查询要在迁移前改好。

档位：标准。本机跑过（2 核 ARM 虚拟机，JDK 17，ShardingSphere-JDBC 5.5.3，MySQL 8.4.13 容器，8 张表 × 10 万行）：⑤ 的 A～E 各跑 1 次，分页每格取 3 次里最快的；EXPLAIN 也是同一个容器。计算器是用实测系数的纯函数（node 里跑过）。坑 6 按机制推演，没单独跑。

按源码（ShardingSphere 5.5.3）：AbstractExecutionPrepareEngine（每个库的 SQL 数大于 max-connections-size-per-query 时用 CONNECTION_STRICTLY）、ExecuteQueryCallback（连接限制模式用 JDBCMemoryQueryResult，否则 JDBCStreamQueryResult）、OrderByStreamMergedResult、ComplexKeysShardingAlgorithm 和 ClassBasedShardingAlgorithm。
