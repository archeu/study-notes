付完款跳回订单页，还是待付款：主从复制、读写分离与复制延迟

从库没有什么魔法：它把主库 binlog 里的事件拉过来、排好队、再做一遍。默认是异步的，主库提交时不等从库，所以从库永远慢一点。平时慢 3～6 ms，一个 30 万行的大事务能让它慢 4 秒，回放线程一停就是一直慢下去。读写分离的难点全在这“慢一点”上：哪些读能接受旧值，不能接受的要么读主库，要么在从库上等自己那笔事务的 GTID 回放完再读。实测付款后立刻读从库，200 次里 199～200 次读到 CREATED。

①为什么需要：一台主库扛不住，也不能只有一台

在全景第 11 站，这一步要解决：第 9 站写进 binlog 的那 5 个事件，要送到另一台机器上再做一遍。为什么要有另一台？订单页、订单列表、后台报表都是读，读的量是写的很多倍，全压在主库上，CPU 和连接都会先满；主库所在的机器坏了，还得有一份几乎一样新的数据能顶上。可读分出去以后，马上撞上一个新问题。

付款后立刻读从库199～200 / 200次读到 CREATED
隔 5 ms 再读1～2 / 200隔 20 ms 起 0 次
30 万行大事务4.1 s心跳量出的最大延迟
等自己的 GTID 再读0 / 200中位多等 3.9～4.1 ms

实测 Docker 里一主一从两个 MySQL 8.4.13，GTID 异步复制，交易靶场 100 万行 orders，跑了两遍，数字是两遍的范围。代码在 ⑤。

②没有它会怎样：三种笨办法

不用复制，只靠已经会的东西，能不能既分担读、又有一份备用数据？

一台主库，加机器配置 读写都在一起

  • 没有延迟，读到的永远是最新的。
  • 读量涨上来，CPU、连接数、buffer pool 一起被抢，写也跟着慢。
  • 机器坏了就停服，恢复靠备份，按小时算。

每晚 mysqldump 一份 备份当备库

  • 简单，还顺便有了备份。
  • 主库挂了，丢的是从上次备份到现在的所有订单。
  • 导出导入 100 万行要几分钟，1 亿行要几小时；导出的那份也不能拿来分担白天的读。

应用双写两个库 代码里写两遍

  • 两个库都是“最新”的，看起来不用等。
  • 一边成功一边失败怎么办？要么回滚另一边，要么补偿，等于自己写分布式事务。
  • 两个请求并发改同一行，两边的执行顺序可能相反，最后的值不一样。

缺的那一块：要有一份按主库提交顺序排好的改动记录，另一台机器照着它从头做一遍，顺序和内容都由主库说了算。MySQL 已经有这份记录，就是 binlog（上一页 ④-3）。不懂这一点的典型误用：以为从库是“实时镜像”，把付款结果、库存扣减后的余量也放在从库上读，然后在高峰期出一堆“扣了钱订单还是待付款”的客诉。

③相邻方案：一份数据放在几台机器上，有几种做法

都要回答同一个问题：主库说“提交成功”的那一刻，别的机器上有没有这笔数据。

做法传的是什么主库提交时等不等别人主库突然挂了从库读到旧值
MySQL 异步复制（8.4 默认）binlog 事件（ROW：哪一行改前改后）不等最近几毫秒的提交可能只在旧主库上会，平时几毫秒
MySQL 半同步（插件）同上等至少一个从库收到并写进 relay log，不等它回放不丢（AFTER_SYNC）；等超时（默认 10 s）后退回异步会，和异步一样
MySQL Group Replication同上，组内先用 Paxos 达成一致等多数成员同意不丢，自动选新主默认会；可以让读等到一致
共享存储（Aurora、PolarDB）redo 发给存储层，只读节点共享同一份数据等存储层多数副本写好不丢，切换快会，AWS 说 Aurora 通常在 100 ms 以内
PostgreSQL 流复制物理 WAL 记录默认不等；可配同步，remote_apply 等到备库回放可见异步时可能丢异步时会；remote_apply 不会

选择规则：大多数 Java 后端碰到的 MySQL 是“一主几从，异步复制”，读写分离也建在它上面，所以本页学这一套，GTID 打开。半同步放到 ⑥ 深 2，它解决的是“主库挂了丢不丢”，不解决“从库读到旧值”。表里后三行是另一个量级的部署，到 J06 后面和高可用那一站再学。

④原理：拉过来，排好队，再做一遍

先看一笔付款怎么从主库走到从库，再看 GTID 怎么给每笔事务编号，然后把延迟拆开看它从哪来，最后是读写分离怎么对付这段延迟，以及为什么默认不等从库。

先知道这些
  • binlog：server 层按提交顺序追加的改动记录。ROW 格式记的是“哪一行，改前什么、改后什么”。事务进行中先攒在会话自己的 binlog cache 里，提交时才整笔写进文件。详见上一页 ④-3。
  • 一笔付款在 binlog 里是 5 个事件：Gtid、Query(BEGIN)、Table_map、Update_rows、Xid（全景第 9 站实测）。
  • 8.4 改了名字：master / slave 换成 source / replica，CHANGE MASTER TO、SHOW SLAVE STATUS、SHOW MASTER STATUS 在 8.4 里已经是语法错误。

④-1 三个线程，两份日志

主库上每连进来一个从库，就有一个 Binlog Dump 线程读 binlog、往外推。从库这边，receiver 线程（以前叫 IO 线程）只管收，收到就追加进本地的 relay log（中继日志）；applier（以前叫 SQL 线程）再从 relay log 里取出事务回放。8.4 默认是多线程回放：一个 coordinator 分发，4 个 worker 并行执行。收和放拆成两拨线程，是为了回放慢的时候，接收不被拖住，事件先落在从库的磁盘上。

④-2 GTID：每笔事务一个全局编号

没有 GTID 时，从库靠“主库的文件名 + 偏移量”记自己读到哪；换一台主库，文件名和偏移全变了，对不上。GTID 给每笔事务一个编号：主库的 server_uuid:序号，例如这次实测的一笔付款是 10c1bce0-…:5420。每台库都记着自己执行过的编号集合 gtid_executed，比如 …:1-6014。从库连上主库时说“我有 1-6014”，主库就从 6015 开始发（SOURCE_AUTO_POSITION=1）。

编号还带来一个好用的能力：等某一笔到了再读。WAIT_FOR_EXECUTED_GTID_SET('…:5420', 1) 在从库上阻塞，直到这笔回放完（返回 0）或 1 秒超时（返回 1）。读写分离的“写后读”就靠它（④-4）。8.4 里 GTID 仍然默认关闭，要显式打开 gtid_mode=ON 和 enforce_gtid_consistency=ON。

④-3 延迟从哪来：传、排队、回放

复制延迟 = 这笔事务在从库上提交的时刻 − 它在主库上提交的时刻。拆开是三段：网络上传的时间；在 relay log 里排队等前面的事务；自己回放的时间。小事务三段加起来几毫秒。大事务两头吃亏：

多线程回放能并行的，是互不相干的不同事务：主库给每笔事务算出它碰过哪些行（writeset），两笔没碰同一行，从库就可以同时放。8.4 里这个算法是唯一的选择（⑥ 深 1）。

④-4 读写分离：把每一次读送到对的库

路由要有人做。放在应用里：Spring 的 AbstractRoutingDataSource 按“当前事务是不是只读”选数据源，或者用 Connector/J 的 jdbc:mysql:replication://，setReadOnly(true) 时自动走从库；ShardingSphere-JDBC 也做这件事。放在中间代理里：ProxySQL、MySQL Router，应用只连一个地址。不管放在哪，都要回答同一个问题：刚写完的这个用户，下一次读能不能去从库。三种常见答法：

写后一段时间读主库 粘住主库

  • 简单：在会话或用户上记个时间戳，1 秒内的读都走主库。
  • 窗口是拍脑袋定的：大事务让延迟到 4 s 时，第 2 秒的读又回到从库，照样读到旧值。

等自己的 GTID 因果一致读

  • 写完拿到自己那笔的 GTID，读之前在从库上等它到，读到的一定包含自己的写。
  • 实测多等的时间就是延迟本身：中位 3.9～4.1 ms。
  • 要传 GTID（会话追踪或另查一次），要设超时；超时后读主库还是报错，得先想好。

这类读只读主库 按业务划分

  • 付款结果、库存余量、余额这类“读了要据此做决定”的，直接走主库，最稳。
  • 划进来的读越多，主库分出去的压力越少；要靠规范管住，不能人人都标“走主库”。

④-5 为什么这样设计：主库不等从库

既然延迟这么麻烦，为什么不让主库等从库改完再返回？

异步：提交不等从库 MySQL 默认

  • 主库的提交耗时、吞吐和从库无关；从库慢了、断了、在重建，主库照常写。
  • 从库可以放在跨机房、跨地域，几十毫秒的网络往返不进每一次提交。
  • 从库读到旧值；主库突然挂了，最后几笔已提交的事务可能只在它身上。

同步：等从库回放完 放弃的另一种

  • 从库读到的永远是最新的，切主也不丢。
  • 每次提交多一次网络往返，外加从库的回放时间；一个 30 万行的事务要等从库再做 3.9 s。
  • 从库一卡，主库的所有写都卡住：本来加从库是为了高可用，结果多了一个让主库停摆的理由。

决定胜负的约束：OLTP 主库的写延迟和可用性最值钱，不能让别的机器拖住。所以默认异步，把“读到旧值”交给读的一方处理（④-4）；要“挂了不丢”就退一步用半同步：只等从库收到，不等它回放，多花一次网络往返（⑥ 深 2）。另一个取舍是传什么：MySQL 传的是 server 层的 binlog，和引擎、页格式、小版本无关，Canal、Debezium 也能伪装成从库来读；代价是从库要把 SQL 层的活再干一遍，回放可能比主库执行还慢（实测 3.9 s 对 2.1 s）。PostgreSQL 直接传物理 WAL，从库照着改页，便宜，但要求同一个大版本，备库也只能读。

最少的写法

搭一主一从（8.4）主库和从库都要 --gtid-mode=ON --enforce-gtid-consistency=ON，server_id 各不相同
-- 主库：一个复制账号
CREATE USER 'repl'@'%' IDENTIFIED BY 'repl';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'%';          -- 权限名还叫 SLAVE

-- 从库：指向主库，按 GTID 自动定位
CHANGE REPLICATION SOURCE TO SOURCE_HOST='repl-src', SOURCE_USER='repl', SOURCE_PASSWORD='repl',
  SOURCE_AUTO_POSITION=1, GET_SOURCE_PUBLIC_KEY=1;     -- 未加密连接 + caching_sha2_password 要这个
START REPLICA;
SET GLOBAL super_read_only = ON;                      -- 谁都别在从库上写（坑 3）
SHOW REPLICA STATUS\G      -- Replica_IO_Running / Replica_SQL_Running / Seconds_Behind_Source / Last_SQL_Error

-- 写后读：在从库上等主库那笔事务回放完，最多 1 秒
SELECT WAIT_FOR_EXECUTED_GTID_SET('10c1bce0-df14-11f1-bc62-0242ac160002:5420', 1);   -- 0 = 到了，1 = 超时

并行回放的线程数、半同步、延迟监控这些细节放到 ⑥。

if (gap > 0) sleep(gap);
if ("CREATED".equals(one(r, READ))) old++;     // 从库：SELECT status FROM orders WHERE id=9527

  隔  5 ms 读从库：  2 / 200 次读到 CREATED（1%）
  隔 20 ms 读从库：  0 / 200 次读到 CREATED（0%）
  隔 50 ms 读从库：  0 / 200 次读到 CREATED（0%）

[stale] 修法二 等自己的 GTID（例如 10c1bce0-df14-11f1-bc62-0242ac160002:5420）：0 次读到 CREATED，0 次超时；等 + 读 中位 4.1 ms，p99 11.5 ms

到这里已经能交差了：读写分离的路由按“写后读走主库，或等 GTID”配好，付完款跳转订单页不会再显示待付款。已知还没处理的细节：延迟突然涨到秒级怎么办（坑 2），延迟该看哪个数（坑 4），从库被人写坏（坑 3），主库挂了丢不丢（深 2）。

⑥细节：大事务、监控、从库被写、无主键表

第一圈的坑都能从 ④ 推出来，旁边的标记点回去。标“实测”的在本机跑过。

第一圈 · 注意事项

坑 1写完立刻读从库← ④-5 主库提交不等从库实测
现象
付款、下单、改地址之后，页面显示的还是旧值；用户重复操作。测试环境从来复现不了，因为测试库没配从库，或者流量小、延迟只有零点几毫秒。
根源
异步复制下，commit 返回时从库还没改。实测立刻读 199～200/200 次是旧值。
做法
“读了要据此做决定”的读走主库；写后读用 GTID 等待或粘住主库（④-4 实验台）；接口本身也要幂等，WHERE status='CREATED' 影响 0 行就当“已付过”。
坑 2一个大事务，延迟涨到秒级、分钟级← ④-3 提交时才发 + 一个事务只能一个 worker实测
现象
凌晨跑一条“把 30 万行 qty+1”的批量脚本，订单页上的数据突然全都旧了几秒。实测心跳延迟从 0 一路涨到 4.1 s，拆成 60 批后最大 0.4～0.9 s。
根源
大事务在主库执行时从库收不到；提交后从库要用一个 worker 从头放到尾，后面所有事务排队等它提交。
做法
批量改按主键范围分批提交，每批几千行，批之间可以 sleep；DDL 用 Online DDL 或 gh-ost 这类工具，也要盯延迟（J06 第 7 个知识点）。
坑 3有人在从库上写了一笔，复制停了← ④-1 回放按 ROW 事件里的主键找行实测
现象
运维手滑，或者某个服务配错连到了从库，删了一行。之后主库一改这行，从库报 1032，Replica_SQL_Running=No，Seconds_Behind_Source 变成 NULL，后面的改动全都停在 relay log 里：实测主库把 9540 改成 PAID，从库一直是 CREATED。
根源
Update_rows 事件说“把主键 9530 那行改成…”，从库找不到这行就只能停下。从库自己的那次删除还多出一个从库自己 UUID 的 GTID（实测 gtid_executed 里多了一段），这种“只有从库有的事务”以后切主时会被当成要同步出去的数据。
做法
所有从库 super_read_only=ON：实测连 root 删除都报 1290，而复制回放照常进行。修复靠对账补数据（pt-table-checksum / pt-table-sync 这类工具），不要随手跳过出错的事务。
坑 4拿 Seconds_Behind_Source 当真实延迟← ④-1 它只看 applier 手上的事件手册 + 实测
现象
监控上一直是 0，用户却读到旧值；或者主从之间网络慢，它也显示 0。实测大事务时它最大 4～5，和心跳差不多，但只有整秒精度，坑 3 那种停了的情况是 NULL。
根源
手册的定义：从库当前时间减去正在回放的事件在主库上的原始时间戳；relay log 放完了就是 0。receiver 落后、收得慢，它看不见。
做法
用心跳表：主库每秒写一次当前时间，从库上 NOW(6) - ts 就是端到端延迟（pt-heartbeat 的做法，本页 bigtx 就是这么量的）；或者看 performance_schema.replication_applier_status_by_worker 里每笔事务的原始提交时间和回放结束时间。NULL 要单独报警。
坑 5表没有主键，从库回放慢得离谱← ④-1 回放要先找到那一行手册
现象
一张日志表没建主键，主库上一条 DELETE … WHERE created_at < ? 删了 1 万行，几百毫秒；从库上延迟一路涨。
根源
ROW 事件里只有行的内容。有主键时从库按主键直接定位；没有主键也没有非空唯一索引时，从库要扫表找匹配的行（手册：“a table scan for each row to be modified on the replica”，8.x 会先把事件里的行建成哈希表，一批行扫一遍，依然要扫）。
做法
每张表都要有主键。主库上开 sql_require_primary_key=ON 直接挡住建表；或用 sql_generate_invisible_primary_key 让 MySQL 自动补一个隐藏主键。
坑 6事务里的读被路由到了从库← ④-4 路由按“这次读能不能接受旧值”推论
现象
一个 @Transactional 方法先查库存（被路由到从库），再扣减（主库），扣出负数。
根源
路由只看了“这条是 SELECT”，没看它在一个读写事务里。从库的值可能是旧的，而且不受主库上锁的保护。
做法
只有 readOnly=true 的事务、或者没有事务的读才走从库；读写事务里所有语句都走主库。Spring 里路由数据源要包一层 LazyConnectionDataSourceProxy，否则取连接时还拿不到只读标志。

第三圈 · 优化和深处

深 1多线程回放：哪些事务能并行手册

主库在 binlog 的 Gtid 事件里给每笔事务写两个数：last_committed 和 sequence_number，从库的 coordinator 据此判断谁和谁能同时放。8.0 默认按“同一组提交的事务互不冲突”算（COMMIT_ORDER），可选 WRITESET：按事务改过的行的哈希判断，没碰同一行就能并行，哪怕是同一个会话先后提交的。8.0.35 起弃用这个开关，8.4 里删了，一律按 writeset 算。8.0.27 起从库默认 4 个 worker、LOGICAL_CLOCK、replica_preserve_commit_order=ON（之前默认单线程）。按提交顺序提交保证从库上任何时刻看到的状态，都是主库曾经有过的状态，代价是坑 2 里的排队。

深 2半同步：只等“收到”，不等“回放”手册

插件 rpl_semi_sync_source / rpl_semi_sync_replica（8.0.26 起的新名字，旧名 master/slave 在 8.4 仍可装但已弃用）。主库提交时等至少一个从库回 ACK：事件已写进 relay log。等的位置 rpl_semi_sync_source_wait_point 默认 AFTER_SYNC：binlog 刷盘后、InnoDB 提交前等，其他会话在 ACK 回来前看不到这笔，主库挂了切过去的从库一定有它。另一个值 AFTER_COMMIT 是先在主库提交再等，别的会话可能读到一笔后来随着主库一起丢掉的数据。等不到 ACK 超过 rpl_semi_sync_source_timeout（默认 10000 ms）就退回异步，所以要监控它有没有退化。半同步不改变从库读到旧值这件事。

深 3GTID 怎么回到应用手里实测

本页的修法二没有在提交后再查一次 @@gtid_executed，而是用了会话状态追踪：session_track_gtids=OWN_GTID 让服务器在 OK 包里顺带回这笔事务的 GTID，Connector/J 连接加 trackSessionState=true 后，从 getServerSessionStateController() 读出来，不多一次往返。ProxySQL 的因果一致读也是这个思路：代理记下每个连接最后的 GTID，转发读之前挑一台已经有它的从库。

面试官会怎么问

主从复制的过程？

主库提交时把事务写进 binlog；每个从库对应主库的一个 Binlog Dump 线程，把事件推过去；从库 receiver 线程写 relay log，applier（coordinator + worker）按事务回放，按主库提交顺序提交（④-1）。

复制延迟有哪些原因，怎么排查？

三段：传、排队、回放。常见原因：大事务和大 DDL（提交后才发、一个 worker 放到底）、无主键表（扫表）、从库机器弱或在跑报表、单线程回放、网络。看心跳延迟和 replication_applier_status_by_worker，再查 relay log 里卡在哪笔事务（坑 2、4、5）。

读写分离怎么保证读到自己刚写的数据？

写后读走主库（固定窗口或标记），或者拿到写事务的 GTID，在从库上 WAIT_FOR_EXECUTED_GTID_SET 等到再读，超时走主库；业务上关键的读直接走主库（④-4）。

半同步复制能解决读到旧值吗？

不能。它只等从库收到 relay log，不等回放；解决的是主库挂了已提交事务丢不丢（深 2）。

对照坑 5：从库每批行事件要扫一遍表

自测

1. 用一句话说出这一页的精华。

从库把主库 binlog 里的事务拉过来、按提交顺序再做一遍；默认异步，主库不等它，所以从库永远慢一点，读写分离要决定哪些读能接受这一点旧，不能接受的读主库或等自己的 GTID。

2. 不用复制，只靠每晚备份或应用双写，痛在哪？

备份：挂了丢一天，恢复几小时，白天也分担不了读。双写：一边成功一边失败要自己补偿，并发时两边执行顺序可能不同。缺的是一份由主库定好顺序的改动记录。

3. 头号坑“写完立刻读从库读到旧值”，根源是哪条原理？

④-5：主库提交不等从库。commit 返回时，事件可能还在路上、在 relay log 里排队、或者正在回放。

4. 预测：把从库的 replica_parallel_workers 调到 16，坑 2 那个 30 万行大事务的最大延迟会降吗？

基本不会。一个事务只能由一个 worker 从头放到尾；后面的小事务就算被别的 worker 先改完，也要等它提交（preserve commit order）。能降延迟的是把大事务拆小。

从 ④-3 推出。

5. 预测：从库的 applier 因为 1032 停了 10 分钟，receiver 还在跑。这时 Seconds_Behind_Source 显示什么？读写分离一律读从库的用户看到什么？

NULL（applier 没在跑）。用户看到的是 10 分钟前的数据，而且越来越旧；relay log 一直在涨。按“等 GTID，超时读主库”的路由，每次读都多等满超时，然后落到主库。

从 ④-1 和坑 3、坑 4 推出；实验台“回放线程停了”那一格可以验证。

6. 预测：开了半同步（AFTER_SYNC），付完款立刻读从库，还会读到 CREATED 吗？

会。半同步只保证从库收到了事件（写进 relay log），不保证已经回放。读到旧值的比例和异步差不多，只是主库提交慢了一次网络往返。

从深 2 和 ④-3 的“传、排队、回放”三段推出。

7. 放回全景：第 11 站前后各发生了什么？复制出了问题，整条链路会怎样？

第 9 站两阶段提交把这笔付款的 5 个事件写进 binlog 并刷盘，第 10 站应用收到 OK、连接还回池子；第 11 站 Binlog Dump 线程把事件推给从库，receiver 写 relay log，worker 按主键把从库的 9527 改成 PAID。第 11 站慢了，主库和应用一切正常，出问题的是读从库的那些页面：订单页显示待付款，用户再点付款，第 6 站的条件更新影响 0 行；第 11 站停了（1032），从库上的数据冻结在出错那一刻，靠 Seconds_Behind_Source 报警可能根本报不出来，要靠心跳和 Replica_SQL_Running。

标准档。实测 的数字来自本机：2 核 ARM，JDK 17.0.21，Connector/J 9.7.0，Docker 里两个 MySQL 8.4.13 容器（同一台机器、同一个 Docker 网络，GTID 异步复制，buffer pool 512 MB，其余默认），交易靶场 100 万行 orders；每段跑了两遍，写的是两遍的范围。主从在同一台机器上，几乎没有网络时间，也在抢同样的 2 个核，真实部署里延迟会多出一段网络往返，回放和主库的快慢比例也会不同。代码在 study-labs。线程模型、Seconds_Behind_Source 的定义、并行回放和半同步的默认值、8.4 删掉的语句、super_read_only、无主键表的回放、WAIT_FOR_EXECUTED_GTID_SET 的返回值核对自 MySQL 8.4 参考手册和 8.0 / 8.4 发行说明；Connector/J 复制连接和 Spring LazyConnectionDataSourceProxy 核对自各自的官方文档；PostgreSQL 的 remote_apply 核对自 PostgreSQL 文档。实验台是按实测分布做的模拟，不是实测。
