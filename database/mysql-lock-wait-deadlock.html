①为什么需要：第 6 站来了两个人

在全景第 6、7 站，这一步要解决：付款那条 UPDATE 改 9527 之前，先给它加 X 锁，再把旧值写进 undo。只有一个请求的时候，这一步很平静。用户手一抖点了两次，两个事务同时要改同一行：只能有一个改成功，只能扣一次款，另一个得知道“已经付过了”。

写法 1 · 先查后改扣款 2 次B 等了 206 ms，照样改了 1 行
写法 2 · 条件更新扣款 1 次B 等了 204 ms，改了 0 行
写法 3 · FOR UPDATE扣款 1 次B 等了 205 ms，读到 PAID
没索引的 UPDATE · RR1,009,174 把改 1 行，锁住整张表

实测 本机 Docker 里的 MySQL 8.4.13，交易靶场 100 万行 orders，默认隔离级别 RR；A 拿着锁 200 ms 后提交。代码在 ⑤。

第一圈（旧页）讲了版本链、Read View 的判断规则、四种行锁和锁地图。这一圈把它们放进全景第 6 站，回答三个第一圈没实测的问题：后到的事务等到锁以后看到什么，一条 UPDATE 到底锁了多少，等不到锁、互相等的时候，事务还剩下什么。

②没有它会怎样：有锁，照样扣了两次

最常见的写法是“先查状态，是待付款就改成已付款，然后扣款”，外面套一个 @Transactional。两个请求挨得很近时，它会扣两次款：

缺的那一块：“判断”和“修改”要发生在同一把锁里，并且判断用的是最新版本。@Transactional 只保证 A、B 各自要么全做要么全不做，不保证它们之间不打架；RR 也帮不上忙，它让 B 的普通 SELECT 一直读同一张旧快照。

③相邻方案：怎么让第二次付款失败

都是“把判断放进锁里”，区别在锁在哪、锁多久、冲突时调用方看到什么。

选择规则：一行数据的状态流转，用条件更新并检查影响行数；必须先读后算再写，才用 FOR UPDATE；再在扣款流水上加唯一键兜底。本页学的是这几种做法共同依赖的机制：第 6 站的锁，等锁的人醒来后看到什么，以及锁的范围。

④原理：两种读、等锁醒来、锁的范围

三件事：同一个事务里为什么会看到两个答案；排队的人醒来以后做什么；一条语句锁多少由什么决定。最后说 InnoDB 为什么这样设计。

先知道这些（第一圈讲过）
  • 版本链：每行带着最后改它的事务 ID 和指向 undo 里旧版本的指针。见第一圈 · 隐藏列和版本链。
  • Read View（快照）：RR 下第一条普通 SELECT 拍一张，用到事务结束；拿它判断版本链上哪个版本看得见。见第一圈 · 照片规则。
  • 行锁加在索引记录上：记录锁、间隙锁、临键锁，提交或回滚才放。见第一圈 · 锁有哪几种。

④-1 同一个事务，两个答案：快照读和当前读

快照只管普通 SELECT。只要语句要加锁（UPDATE、DELETE、FOR UPDATE、FOR SHARE），它就读最新的版本。所以“用 SELECT 查到 CREATED，再据此决定扣款”是把判断放在了快照上，而修改发生在最新版本上，两者对不上。

④-2 等锁的人醒来以后：重新读、重新判断

④-3 锁住多少：扫过哪些索引记录，就锁哪些

InnoDB 不是“锁满足条件的行”，而是在执行时沿着索引扫到哪条记录，就给哪条加锁。所以范围取决于 WHERE 能用哪个索引、隔离级别是什么：RR 下扫到的都锁上，还锁记录之间的间隙，一直到提交；RC 下 MySQL 判断完 WHERE，不满足的那条立刻放掉，也不锁间隙。

④-4 为什么这样设计：等到锁后接着改，而不是报错

逼出这个设计的约束是：修改只能落在最新版本上。如果 B 按自己快照里的 CREATED 去改，A 的修改就被覆盖了（丢失更新）。所以 B 必须看最新版本。剩下的问题是：B 发现最新版本和自己的快照不一样时，该怎么办？

InnoDB RR 和 RC 都是这样

  • 等到锁，读最新版本，重新判断 WHERE，接着执行。
  • 应用不用写重试，冲突多的时候也只是排队。
  • 代价：RR 的“快照”对写语句不成立。同一个事务里 SELECT 说 CREATED，UPDATE 说 0 行（④-1）。

PostgreSQL RR 放弃的另一种

  • 等到锁，发现这行在快照之后被别人改过，直接报 could not serialize access due to concurrent update（40001）。
  • 事务看到的一直是同一张快照，前后一致。
  • 代价：应用必须捕获并重试整个事务。PostgreSQL 的 RC 则和 InnoDB 一样，重新判断后接着改。

乐观锁 不等

  • WHERE id=? AND version=?，冲突时改 0 行。
  • 读和写可以隔很久，中间不持锁。
  • 代价：在 InnoDB 里，UPDATE 那一刻照样要等行锁。它省掉的是“读完到写之前”那段持锁时间，不是锁本身。

决定胜负的约束：OLTP 里大多数冲突只是两个请求挨得太近，排队一下就能各自正确完成。InnoDB 选了“让应用少写重试”，代价是 RR 下读和写可能看到不一样的东西。所以在 MySQL 里，判断要写进 UPDATE 的 WHERE，而不是写在 SELECT 后面的 if 里。

最少的写法

条件更新 + 检查影响行数JDBC；MyBatis 的 <update> 返回值、JdbcTemplate 的 update() 返回值同理
int n = jdbc.update(
    "UPDATE orders SET status='PAID', paid_at=NOW(6) WHERE id=? AND status='CREATED'", orderId);
if (n == 0) {
    return PayResult.ALREADY_PAID;   // 别人先付了，或者状态不对：不扣款
}
payments.insert(orderId, amount);   // 只有改了 1 行的那个事务走到这里

核心：写法 2LockLab.pay() 节选
String sb = one(b, "SELECT status FROM orders WHERE id=9527");          // B 先看一眼：CREATED
int ra = upd(a, "UPDATE orders SET status='PAID', paid_at=NOW(6) WHERE id=9527 AND status='CREATED'");
if (ra == 1) upd(a, PAY_SQL);                                            // A 扣款
Future<Integer> fb = POOL.submit(() ->                                   // B 的同一条 UPDATE，会被挡住
        upd(b, "UPDATE orders SET status='PAID', paid_at=NOW(6) WHERE id=9527 AND status='CREATED'"));
Thread.sleep(HOLD_MS);                                                   // A 拿着锁 200 ms
a.commit();
int rb = fb.get();                                                       // B 醒来：0
if (rb == 1) upd(b, PAY_SQL);

    第一圈 · 注意事项

    坑 1先查后改，重复扣款← ④-1 快照读实测
    现象
    两个请求都读到 CREATED，都扣了款；9527 只是 PAID 了一次，看不出异常，对账时才发现两条流水。
    根源
    判断用的是快照，修改用的是最新版本。B 等到了锁，但 WHERE 里没有能挡住它的条件。
    做法
    条件更新 + 检查影响行数；或者 FOR UPDATE 读。换成 RC 没用：B 的 SELECT 在 A 提交前执行，照样读到 CREATED。
    坑 2条件更新了，却不看影响行数← ④-2 醒来后重新判断
    现象
    UPDATE 没报错，代码往下走去扣款。改 0 行不是异常，JDBC 不会抛。
    根源
    “已经付过了”只体现在返回值 0 上。
    做法
    MyBatis 的 mapper 方法返回 int 并判断；JPA 的 @Modifying 查询同理。0 行时按“已处理”返回，别当成失败重试。
    坑 3没索引的 UPDATE，锁了整张表← ④-3 扫到哪锁到哪实测
    现象
    WHERE sku_id=88 AND status='CREATED' 只改了 1 行，717 ms；data_locks 里 1,009,174 条 X 锁（100 万条记录加每页一个 supremum）。期间改 10 号单、插新订单全部等到超时。普通 SELECT 不受影响。
    根源
    没索引只能沿主键扫全表，RR 下扫到的每条都加临键锁，不满足条件也不放。
    做法
    UPDATE、DELETE 的条件列建索引，上线前 EXPLAIN 看 type 不是 ALL（执行计划页）。批量清理按主键分段做。
    坑 4走了索引，也会挡住别人的插入← ④-3 RR 锁间隙实测
    现象
    WHERE user_id=1024 AND status='CREATED' 只改 1 单，却锁了 1024 的全部 6 单，外加 1024 前后的间隙：插一单 user 1024、甚至 user 1023 的新订单都等到 1205。
    根源
    idx_user 是非唯一索引，RR 下扫到的 6 条都加临键锁，最后再锁到下一条 (1025, 103296) 前的间隙，见下图。
    做法
    能按主键改就按主键改：先按 user_id 查出 id，再逐个条件更新。或者这类业务用 RC：实测只剩 2 把锁，插入都通过。
    坑 5等锁超时，事务还开着默认值：只回滚这一条语句实测
    现象
    批量取消先取消了 9530，再取消 9527 时等了 1 秒报 1205。代码 catch 住后接着 COMMIT：9530 变成 CANCELLED，9527 还是 PAID，只做了一半。
    根源
    innodb_rollback_on_timeout 默认 OFF，1205 只回滚等锁的那条语句，事务里之前的修改和锁都还在（实测 trx_state=RUNNING、rows_modified=1）。
    做法
    捕获 1205 后先 rollback()，再重试整个事务。Spring 里异常抛出 @Transactional 方法就会整体回滚；危险的是在事务方法里面 catch 住继续走。
    坑 6按相反顺序改两行，死锁← 深 3 等待图实测
    现象
    A 合并付款按 9527 → 9530，B 批量取消按 9530 → 9527。B 的第二条 28 ms 就报 1213，B 整个事务回滚，A 接着改完。
    根源
    两个事务各拿一把、各等对方那一把，等待成环，等多久都等不到。
    做法
    多行一律按主键排序后再改；捕获 1213 后重试整个事务（它已经被回滚了）。
    坑 7日志里 status 是 CREATED，UPDATE 却改了 0 行← ④-1 两种读实测
    现象
    排查重复请求时，B 的日志先打了一行“订单状态 CREATED”，紧接着 UPDATE 返回 0，看起来像数据库出了错。
    根源
    日志里的状态来自快照，UPDATE 看的是最新版本。同一事务里两者可以不同，这是设计如此。
    做法
    要打“改之前的真实状态”，用 FOR SHARE 读，或者在 0 行之后再查一次并注明是当前读。

    状态流转一律条件更新

    WHERE id=? AND status=?，按影响行数走分支。

    重复扣款、重复发货

    流水表加唯一键兜底

    payments 上 UNIQUE(order_id) 或幂等号，重复插入报 1062。

    条件写漏、跨服务重试时的重复记账

    UPDATE、DELETE 的条件必须走索引

    上线前 EXPLAIN；能按主键改就按主键改。

    一条语句锁住整张表（坑 3）

    多行按主键排好序再改

    批量付款、批量取消、转账两边，都先排序。

    相反顺序加锁造成的死锁（坑 6）

    事务里不调外部接口

    实测 B 等的时间 ≈ A 持锁的时间。支付网关、HTTP 调用放到事务外。

    一个慢调用让所有改这一行的请求排队

    重试整个事务，不是重试一条语句

    1205 先 rollback；1213 已经回滚了。Spring 里重试要包在 @Transactional 方法外面，加次数上限和随机退避。

    半截提交（坑 5）、重试风暴

    等锁上限按会话设

    接口超时 3 秒，就让这类事务 SET SESSION innodb_lock_wait_timeout = 2，不去改全局的 50 秒。

    请求早超时了，数据库还在替它等锁

    认得这两个异常

    spring-jdbc 7.0.10 的 sql-error-codes.xml：1205 → CannotAcquireLockException，1213 → DeadlockLoserDataAccessException，都是 PessimisticLockingFailureException 的子类。驱动层两者的 SQLState 都是 40001（实测）。

    把可重试的锁冲突当成系统错误报给用户

    第三圈 · 优化和深处

    深 1锁 100 万行，只用了 1 MB实测 + 手册

    InnoDB 不是每行一个锁对象，而是每个事务、每个页、每种模式一个锁结构，里面用位图标记这一页上哪些记录被锁（每条记录 1 位）。实测坑 3 那条语句：trx_lock_structs=9175：主键 9174 个叶子页各一个，加表上的 IX 一个（锁条数里多出的 9174 也是每页一个 supremum），trx_lock_memory_bytes 约 1048 KB。所以 InnoDB 不需要“锁太多了就升级成表锁”，代价在别处：data_locks 要把位图展开成 100 万行，查了 4.6 秒。

    深 2RC 为什么只剩 1 把锁：semi-consistent read实测 + 手册

    手册：RC 下 UPDATE 遇到已被锁住的行，InnoDB 先返回最新提交的版本，让 MySQL 判断 WHERE；不满足就不去等这把锁；不满足条件的行，判断完就放锁。所以 RC 下没索引的 UPDATE 不挡别人。但它照样扫了 100 万行，锁照样先加再放：实测 1164～1196 ms，比 RR 的 717 ms 还慢，锁结构也一样分配了 9175 个。RC 减少的是冲突，不是工作量。

    深 3死锁检测：等待图上找环实测 + 手册

    事务要等锁时，InnoDB 沿“谁在等谁”的图找环；找到就挑一个回滚。手册：挑“小”事务，小是按插入、更新、删除的行数算的；这次 A、B 各改了 1 行，回滚的是后来造成环的 B。等待链超过 200 个事务、或要看的锁超过 100 万把，直接当死锁处理。高并发抢同一行时检测本身会拖慢系统，手册建议的退路是 innodb_deadlock_detect=OFF，靠 innodb_lock_wait_timeout 兜底。

    深 4现场怎么查：三张视图和一段日志实测

    sys.innodb_lock_waits 直接给出等的语句、挡路的连接号和 KILL 47 这样的建议；data_locks 看谁拿着哪些锁；information_schema.innodb_trx 看事务开了多久、锁了多少行。注意：innodb_trx 读的是一份最多每 0.1 秒刷新一次的缓存，连着查两次可能读到旧的。本页实验第一次跑时就踩到了：刚建的事务查不到，加 150 ms 间隔才对。

    面试官会怎么问

    RR 下 UPDATE 读的是快照吗？两个事务同时改一行会怎样？

    不是。UPDATE 是当前读：先拿行锁，再读最新提交的版本。后到的事务排队等，前一个提交后它醒来，对最新版本重新判断 WHERE：还满足就改，不满足就改 0 行。所以同一事务里普通 SELECT 和 UPDATE 可能看到不同的值（④-1、④-2）。

    怎么防止重复支付？

    数据库这一层：条件更新 WHERE status='CREATED' 并检查影响行数，流水表上加唯一键兜底；接口这一层：幂等号。先查后改不行，因为判断用的是快照（坑 1）。

    一条 UPDATE 会锁多少行？什么时候会锁全表？

    扫过的索引记录都锁。主键等值只锁一条；非唯一索引在 RR 下锁所有等值记录加前后间隙；没索引就全表扫，RR 下每条都锁、不提前放，等于锁表。RC 会放掉不满足条件的行，但扫描量不变（④-3、深 2）。

    Lock wait timeout 和 Deadlock 有什么区别，代码里怎么处理？

    1205 是等太久，默认只回滚那条语句，事务还开着，必须先 rollback 再重试；1213 是等待成环，InnoDB 立刻回滚其中一个整个事务，直接重试整个事务即可。两者 SQLState 都是 40001。预防死锁靠固定加锁顺序、缩短事务（坑 5、坑 6）。

    自测

    1. 用一句话说出这一页的精华。

    加锁的语句读最新版本，后到的事务等前一个提交后对最新版本重新判断 WHERE；所以防重复要把判断写进 UPDATE 的条件并看影响行数。锁的范围由扫过的索引记录决定，没索引就锁全表。

    2. 先查后改的痛点在哪？

    判断用的是普通 SELECT 读到的快照，修改发生在最新版本上。B 被锁挡了一下，可醒来后 WHERE 里没有能挡住它的条件，于是又改一次、又扣一次。

    3. 头号坑“没索引的 UPDATE 锁全表”，根源是哪条原理？

    ④-3：InnoDB 在扫描时给经过的每条索引记录加锁，RR 下不满足条件也不放、还锁间隙。没索引只能沿主键扫完 100 万条，就锁了 100 万条。

    4. 预测：把隔离级别换成 RC，写法 1 还会扣两次吗？

    会。B 的普通 SELECT 在 A 提交前执行，RC 下读到的也是 CREATED；B 的 UPDATE 等到锁后读最新版本，可 WHERE 只有 id=9527，照样改 1 行。RC 只改变快照拍的时机，挡不住“判断在锁外”。

    从 ④-1、④-2 推出。

    5. 预测：A 在事务里调支付网关花了 2 秒，B 的等锁上限是 1 秒，写法 2 会怎样？用户看到什么？

    B 等 1 秒报 1205，只回滚那一条 UPDATE，事务还开着；应用应当 rollback。钱只扣了 1 次（A 的），可 B 这次请求返回的是错误，用户可能以为付款失败又点一次；第三次请求到达时 A 已提交，条件更新改 0 行，返回“已支付”。根治是把网关调用移出事务。

    从 ④-2 第 3 步和坑 5 推出。

    6. 预测：RR 下 UPDATE … WHERE user_id=1024 AND status='CREATED' 持锁期间，另一个会话插一单 user 1025、id 为 1000003 的订单，会被挡吗？

    不会。在 idx_user 上它排在 (1025, 103296) 后面，被锁的间隙到 (1025, 103296) 为止。被挡的是排在 (1023, 最大 id) 和 (1025, 103296) 之间的位置，也就是所有 user 1024 的新单，以及 id 比现有 1023 订单都大的 user 1023 新单。

    从坑 4 的锁地图推出，这一条没有实测。

    7. 放回全景：第 6、7 站前后各发生了什么？这一页讲的东西出了问题，整条链路会怎样？

    前一站（第 5 站）沿 B+ 树找到 9527 所在的叶子页；第 6 站给 9527 加 X 锁，第 7 站把旧值写进 undo，第 8 站改页并写 redo，第 9 站两阶段提交时才放锁。如果 UPDATE 没走索引，第 6 站锁住整张表，别的付款都卡在这一站；它们占着的连接不还，第 1 站 HikariCP 的池子被占满，新请求借不到连接，30 秒后超时。如果写成先查后改，链路每一站都“正常”，第 9 站提交了两次扣款，第 11 站从库也收到两条流水，只有对账能发现。
