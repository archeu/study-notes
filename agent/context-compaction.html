②没有它会怎样：继续堆，或者从头砍

做法会发生什么
什么都不管，继续堆每轮更慢更贵；越过模型窗口后请求直接被拒（API 报错，循环中断）；没越过之前，模型也越来越抓不住中间的关键行。
按条数砍掉最早的消息（滑动窗口）最早的那条正好是你的问题和 3 条记忆，砍掉以后模型不知道自己在查什么；从中间砍还会把 tool_use 和它的 tool_result 拆开，API 直接拒收。
把每次工具结果按字数截短能用一阵，但截掉的是哪段全凭运气；GC 日志的关键一行可能正好在被截掉的中间。
本页：先清旧结果，再摘要，大材料交给子 agent按“丢了会不会答错”来决定丢什么，不是按位置、按条数。
不懂精华时的典型误用：以为“压缩”就是“摘要”，每轮都让模型把历史总结一遍。结果是每轮多一次模型调用、缓存每轮都失效，摘要里的数字还一轮比一轮走样。摘要是最后一招，不是第一招。

③相邻方案：五种腾地方的办法

要求滑动窗口清旧工具结果摘要（compaction）子 agent 隔离记到外面（笔记、记忆）
省多少看砍多少多：工具结果是大头最多：整段换成几百 token材料根本不进来看记多少
丢什么最早的问题和规矩旧结果的原文，留一行要点摘要没写的，全丢，没法找回子 agent 的中间过程不丢，要用时再读回来
要不要多调一次模型不要不要，纯代码要，读一遍全部历史要，另起一个循环要写、要取
结果可预期吗可预期，但常常错可预期看模型写得怎样看子 agent 答得怎样看写和取的规则
适合闲聊Agent 循环的第一招很长的任务，清完还不够大而独立的子任务跨会话（站 05 后几页）

本页学中间三种，按顺序用：能不进来的不进来（子 agent），进来了的旧结果先清，清完还不够才摘要。滑动窗口在 Agent 里基本不用；“记到外面”是后面几页的主题。

Anthropic 的《Effective context engineering for AI agents》（2025-09）把长任务的办法归成三类：compaction（摘要后继续）、structured note-taking（写到上下文之外的笔记）、sub-agent architectures（子 agent 带着干净的上下文去做一件事）。它把“清旧工具结果”称为最安全、最轻的一种 compaction。

④原理：三招各动了上下文的哪一块

先知道这些
  • 每轮整段重发、不变的在前：见上一页 上下文工程。这一页的三招都只动 messages，不碰系统提示和工具说明。
  • tool_use 和 tool_result 成对：模型在 assistant 消息里提出调用，你在下一条 user 消息里用同一个 id 送回结果。见 一次工具调用的来回。
  • 循环和轮数上限：见 Agent 循环。

Java 老朋友：上下文压缩 ≈ GC。像的地方：空间不够时回收，回收的是“以后大概用不到的”；清旧工具结果像回收已经没人引用的对象，摘要像 G1 的 Compaction（把活下来的东西挤到一起）。不像的地方才是重点：GC 靠可达性分析，保证不回收还会被用到的对象；上下文里没有“引用”，哪段以后还要用，只能猜。猜错了不会报错，模型只会答错，或者再花一轮去查。

机制 1 · 清旧工具结果：留调用、留要点，丢原文

  • 动哪里：只动较早的 tool_result 的正文。tool_use（模型调了什么、带什么参数）原样保留，id 配对不破，模型还知道“这个我查过”。
  • 留什么：值班助手的约定是每个工具结果第一行写“要点：……”，由工具代码自己算出来（Full GC 几次、最长多久）。清理时只留这一行。要点是工具写的，不是模型写的，所以数字可靠。
  • 什么时候清：越过阈值才清，一次多清一些，最近的 N 个不动（模型可能还在用）。
  • 代价：改了前面的内容，从改动处往后的缓存全部失效，下一次请求要重新写缓存。所以不能每轮都清，要攒着一次清一大批。

机制 2 · 摘要：多调一次模型，用交接单替换整段历史

  • 怎么做：把整段历史加一段“写交接摘要”的要求发给模型；拿到摘要后，新的 messages 只剩第一条（记忆和问题，原样）加一份摘要，然后接着跑循环。
  • 摘要要有格式：已确认的事实（带原始数字）、已排除的方向、还没查的、下一步。没格式的摘要，模型常常只写“GC 比较频繁”。
  • 代价：多一次完整读历史的调用；摘要没写进去的东西就永远没了，而写不写是模型决定的。

机制 3 · 子 agent：大材料在另一个窗口里读

  • 怎么做：主 agent 不调“读直方图”，而是开一个新的上下文：一句任务 + 材料。子 agent 读完只交回结论，主上下文多出来的只有这几百 token。
  • 为什么省：压缩是“进来了再丢”，隔离是“一开始就不进来”。19.7K 的材料只在子 agent 的窗口里存在一次，读完就丢，不会在主循环里每轮重发。
  • 代价：子 agent 看不到主上下文：不知道“只读”“晚高峰不 dump”，也不知道前面已经排除了什么，这些都要在任务里写明；它的前缀和主 agent 不同，缓存不共享。

为什么这样设计：先清、再压，不是每轮都压

阈值触发、分层：清 → 摘要，大材料隔离

  • 最常用的一招是纯代码，零额外调用，结果可预期，数字由工具写。
  • 摘要只在清完还不够时才做，有损的操作做得最少。
  • 代价：要定阈值、要让工具写要点、要设计子任务的输入。

每轮都让模型总结一遍

  • 每轮多一次读全部历史的调用，钱和时间翻倍。
  • 每轮改写历史，缓存每轮都失效。
  • 摘要的摘要，数字一轮比一轮走样，像反复有损压缩的图片。
决定胜负的约束：上下文里没有“引用关系”，哪段以后要用只能猜，所以每一次腾地方都可能丢掉要用的东西；而每一次改写前面的内容，都会让缓存失效。两条加起来：能不进来就不进来，必须丢时先丢最确定没用的，丢的次数越少越好。
compact.py（节选）阈值和保留个数放到 ⑥
def clear_old_tool_results(messages, keep=1):
    out = copy.deepcopy(messages)
    results = [b for m in out if m["role"] == "user"
               and isinstance(m["content"], list)
               for b in m["content"] if b.get("type") == "tool_result"]
    for b in results[:-keep]:            # 最近 keep 个不动
        first = b["content"].splitlines()[0]  # 工具写的“要点：”
        b["content"] = f"[已清理] {first}"   # tool_use 原样保留
    return out

读出来的结论
  • 省多少：清旧结果从 11,905 降到 2,802（少 76%），一次模型调用都不用；摘要降到 1,606（少 87%），但要多读一遍全部历史，本机花了 1045 秒。多省的那 1,200 token，代价是一次完整调用。
  • 摘要会编：摘要里对的数字（14 次、2311 ms、92%）都来自工具自己写的“要点”行；模型自己“总结”出来的部分，编了两个数，还把 10:42 当成晚高峰。下一轮起，这些就成了上下文里的“事实”（坑 2）。
  • 子 agent 省得最多，也最“无知”：主上下文只多 156 token，最大的类和字节数都对；但它看不到主上下文，不知道今天刚上线了缓存，来源猜错了。任务里要把已知情况写给它（坑 3）。
  • 追问分不出高下：同一个问题，1.7B 小模型对着原样历史也把 Full GC 14 次答成 2 次，三种办法都没答对“最长那次几点”。这组追问只说明小模型找细节本来就弱，不能用来比较三招；换成 Claude 再跑一次才有意义（↺ 练习）。

⑥细节

第一圈 · 注意事项

1砍掉了 tool_use，留下了它的 tool_result← ④ 机制 1
现象
自己写的“删掉最早几条消息”上线后，偶尔整轮请求被 API 拒收，循环中断。
根源
每个 tool_result 都要对上前一条 assistant 消息里同 id 的 tool_use。按条数砍，砍在一对的中间，剩下的那一半就成了孤儿。
做法
只清正文、不删消息；真要删就成对删，并且保证第一条仍是 user 消息（问题和记忆）。
2摘要把要紧的细节丢了实测← ④ 机制 2
现象
⑤ 的实测：摘要里出现了工具从没给过的“41 次”“平均等待 199ms”，还把 10:42 写成“当前为晚高峰”。压缩之后，这些就成了上下文里的“事实”。
根源
摘要写什么由模型决定，没写进去的就永远没了；上下文里没有引用关系，模型也不知道你后面会问哪一条。
做法
摘要要求里点名“必须带原始数字和时间”；先清后摘要（工具写的要点不经过模型）；关键事实另外写进笔记或记忆，不只放在摘要里。
3子 agent 不知道主 agent 的规矩← ④ 机制 3
现象
全景第 6 站的反例：子 agent 为了“看清楚”，自己去做了一次 heap dump，正赶上晚高峰。
根源
子 agent 是全新的上下文，主 agent 的系统提示、3 条记忆、前面排除过的方向，它一样都没有。
做法
子 agent 默认只给只读工具，或者干脆不给工具、只给材料；任务里写明约束和“已经排除了什么”；返回格式固定（结论 + 证据数字）。
4每轮都清一点，缓存每轮都失效← ④ 机制 1
现象
上了清理以后，上下文变短了，账单却没降，甚至涨了。
根源
清理改写了前面的内容，从改动处往后都要重新写缓存（写缓存比普通输入还贵一点）；每轮清一点，就每轮付一次写缓存的钱。
做法
阈值定高一些，一次清一大批（Claude API 用 clear_at_least 规定一次至少清多少，不够就不清）。

第二圈 · 使用规范

  • 工具结果第一行写要点，由工具代码算：防清理和摘要把数字弄丢、弄错。
  • 第一条 user 消息（问题、记忆）永远不清、不压：防模型忘了自己在查什么。
  • 摘要用固定格式：事实带数字 / 已排除 / 没查的 / 下一步：防“GC 比较频繁”这种空话。
  • 子任务的输入写全约束，输出固定格式：防子 agent 越权，也方便主 agent 引用。
  • 记录每次腾地方前后的 token 数和清掉了什么：出了错能回头查是哪次压缩丢的。

第三圈 · 优化和深处

Claude API 上的现成做法（按文档）

  • context editing（beta，context-management-2025-06-27）：clear_tool_uses_20250919 由服务端清旧工具结果，参数 trigger（默认 10 万输入 token）、keep（默认保留最近 3 次）、clear_at_least、exclude_tools、clear_tool_inputs（默认 false，只清结果、保留调用）。清掉的结果换成一段占位文字。另有 clear_thinking_20251015 清思考块。
  • compaction（beta，compact-2026-01-12）：服务端在接近阈值（默认 15 万 token）时把前面的内容摘要成一个 compaction 块。要把整个 response.content 追加回 messages，只取文字会把这个块弄丢。
  • 官方的成本建议也是：清理是腾窗口的工具，不是省钱的工具；摘要只在足够长的会话里才划算。

在 Claude Code 里见过的样子

Claude Code 的 /compact 和接近上限时的自动压缩，就是机制 2：它会把对话换成一份摘要，保留架构决定、没解决的 bug、实现细节（Anthropic 博客原话），然后接着干活。你会发现压缩之后它偶尔“忘了”前面说过的某个细节，原因就是 坑 2。

Claude Code 派出去读代码、搜文件的子任务，就是机制 3。

自测

1. 用一句话说出这一页的精华

腾地方的办法都是有损的：能不进来的交给子 agent，进来了的先清旧工具结果（只留工具写的要点），清完还不够才让模型摘要；丢的次数越少越好。

2. 按条数砍掉最早的消息，为什么在 Agent 里不行？

最早那条是问题和记忆，砍掉后模型不知道在查什么；砍在 tool_use 和 tool_result 中间，API 直接拒收。

3. “上下文压缩 ≈ GC”这个比方，在哪里失效？

GC 用可达性分析，保证不回收还会被用到的对象；上下文里没有引用关系，哪段以后要用只能猜，猜错了不报错，只会答错。这就是坑 2 的根源。

4. 预测：把清理的 keep 从 1 改成 0（连最新那次工具结果也清掉），下一轮会怎样？

模型刚要的结果还没来得及读完整就只剩一行要点，它很可能再调一次同一个工具，多一轮，刚省下的 token 又加回来了。最近的结果是模型“正在用”的，相当于还被引用着的对象。

从 ④ 机制 1“最近的 N 个不动”推出。

5. 预测：在 Claude API 上把清理阈值设得很低，每轮都触发，上下文和账单各会怎样？

上下文一直很短，但每次清理都改写了前面的内容，缓存从改动处往后失效，每轮都要付写缓存的钱，账单可能比不清还高。

从 ④ 机制 1 的代价和上一页“缓存只认前缀”推出。

6. 放回全景：第 5、6 站前后各发生了什么？这一页讲的东西坏了，整条链路会怎样？

前面是第 4 站：循环每轮把工具结果堆进上下文，到第 4 轮 24.6K。后面是第 7 站：根据所有证据交结论。压缩丢了关键数字，第 7 站要么证据里出现编出来的数，要么多跑几轮重新查；子 agent 不带约束，可能在晚高峰做 heap dump；子 agent 的结论没交回或格式乱，第 7 站就缺“OrderSnapshot 占 2.1 GB”这条最关键的证据。

从全景第 4～7 站和本页 ④ 三个机制推出。
