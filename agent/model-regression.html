换模型、升级模型怎么回归

换模型走的是和改提示词同一条链路，只是第 1 站改的是模型名。不同的是：几乎每条回答都会变，噪声更大；质量、成本、延迟三样一起动，要先写好“什么情况算能换”的规则再跑；提示词是照着旧模型调出来的，新模型可能要配新提示词；云端的模型别名还会悄悄换掉底下的版本，所以模型版本要钉死，每天的基线要接着跑。

全景：改了一句提示词之后 · 下一圈地图：站 09 · 换模型、升级模型怎么回归深度：懂机制

这一页的位置站 09 的最后一个知识点。前面八页的东西原样再用一遍：50 条评测集、判分、trace、轨迹、版本（模型名在发布包里）、门禁、线上指标。站 02 的怎么选模型讲的是“选哪个”，这一页讲“换了以后怎么证明没变坏”。

①为什么需要：换模型是一次“全量改动”

值班助手早晚要换模型：新模型更便宜、更快、更聪明，或者旧模型要下线了。这一步要回答的问题和第 7 站一样：换完是变好还是变坏？可难度大得多：改一行提示词，大部分用例的回答几乎不变；换模型，每一条的回答、轮数、话多话少都会变。

②没有它会怎样：看排行榜、看厂商公告、试几条

  • 看公开榜单：新模型在通用基准上高几分，可值班助手考的是“看日志、别怪 GC”，榜单上没有这道题。
  • 看厂商说“兼容、更强”：工具调用的格式、话多话少、拒答的习惯都可能变，站 04 以来调好的提示词未必还管用。
  • 试几条：和改提示词时一样，只是抛了几次硬币；而且换模型的硬币翻得更多。
  • 只比质量：新模型答得好一点，可输出多了一倍、慢了一倍，成本和 P95 都超了。
  • 用别名不钉版本：代码里写的是“最新版”，某天云端悄悄换了底下的模型，分数掉了，没人改过任何东西。
不懂精华时的典型误用：换模型当成改配置，改个名字、跑一下冒烟、看着能用就上线。换模型是对每一条用例的全量改动，回归要比改提示词更重：全套评测、两边多跑几遍、三个方向一起判，必要时连提示词一起调。

③相邻方案：几种证明“能换”的办法

做法能证明什么证明不了什么
公开基准、厂商评测通用能力的大致排序在你的任务、你的提示词上好不好
离线评测集回归（本页）在 50 道自己的题上，质量、成本、延迟各变了多少；逐条配对，知道哪类变好、哪类变坏题目之外的线上情况
影子流量（shadow）线上真实请求同时发给新模型，只记录不展示，成本和延迟很真实没有标准答案，质量还要另外判；花双份的钱
灰度 + 线上指标真实用户的反应慢、样本少（线上指标那页的实验台）

本页做离线回归，它是换模型的第一道关：便宜、能逐条配对、能按类型拆开。过了这一关，再用影子流量看真实的成本延迟，最后灰度。

④原理：翻面更多、三样一起动、提示词跟着模型、版本要钉死

先知道这些
  • 配对和噪声线：见为什么必须评测。换模型时同样适用，只是翻面会多得多。
  • 发布包：模型名、温度都在里面，换模型就是发一个新包。见版本管理。
  • 门禁：候选和基线逐条配对，按规则判红绿。见评测进 CI。

机制 1 · 换模型，每枚硬币的正反面概率都重新洗一遍

改提示词时，大部分用例的通过概率 p 只动一点，翻面集中在少数几条。换模型时，每条用例的 p 都重新决定：新模型擅长的那类整体上去，不擅长的整体下来，加上两个模型各自的随机性，翻面的条数会多得多，噪声线 2√(b+c) 跟着变宽。配对比较依然成立，只是要看清楚：净变化超出噪声线的，才算新模型在这个指标上真的不同；在线内的，什么也说明不了，要么多跑几遍，要么加用例。

机制 2 · 质量、成本、延迟一起动：先写规则，再看数字

换模型的动机各不相同：换小模型是为了省钱、变快，可以接受质量“不显著变差”；换大模型是为了质量，可以接受成本涨一些。所以“能不能换”不是一个分数，是一条预先写好的规则，比如：

换的目的能换的规则（跑之前写好）
降本提速（换小模型）每个质量分项都没有超出噪声的变坏；耗时或成本至少降 30%；安全红线不新增
提质量（换大模型）关键分项（说中、没怪错）有超出噪声的变好；成本不超过 2 倍，P95 不超过可接受的上限
旧模型下线（被迫换）和旧模型比没有超出噪声的变坏；变坏的类型要列出来，配新提示词再评一次

先写规则，是为了防止“看到数字再编理由”：换小模型后质量掉了，就说“省了钱值得”；成本涨了，又说“质量好了值得”。

机制 3 · 提示词是给某个模型调的：换模型可能要连提示词一起换

站 04 以来的工具说明、SOP、“不要猜数字”这些话，都是看着 Qwen3-1.7B 的毛病一条条加进去的。新模型的毛病不一样：更小的模型可能连工具都不会调，更大的模型可能话太多、调工具太勤。所以换模型的回归有两组：新模型 + 旧提示词（看能不能直接换），新模型 + 为它调过的提示词（看它的上限）。两组都要和“旧模型 + 旧提示词”这个基线配对比。

机制 4 · 钉死版本，夜里接着跑基线

云端模型常有两种名字：带日期或版本号的具体快照，和“最新版”这类别名。别名指向的模型会被厂商换掉，你的分数会在没人改代码的情况下变。所以发布包里写具体快照的名字；夜里照旧用基线跑一遍评测，和缓存的基线比，差出噪声就报警。厂商公布下线时间表以后，提前用这一页的方法回归，而不是等到下线那天。

为什么这样设计

同一套评测 + 预先写好的三维规则

  • 评测集、判分、门禁一行不改，换模型和改提示词用同一把尺子，结果可比。
  • 规则先写，三个方向一起判，“值不值得换”不再随看到的数字改口。
  • 逐条配对、按类型拆开，能说清新模型强在哪类、弱在哪类，也就知道提示词该往哪改。
  • 代价：换模型翻面多，往往要多跑几遍才能下结论；连提示词一起调，评测要跑好几组。

被放弃的：看榜单、试几条、直接灰度

  • 榜单测的不是你的任务和你的提示词。
  • 试几条的样本太少，换模型的噪声又更大。
  • 直接灰度：线上成功率要好几天才看得出来，成本和延迟的变化却第一天就砸在账单上。
决定胜负的约束：模型是 agent 里影响面最大的一个零件，换它等于同时改了每一条用例的行为；又因为换模型的理由各不相同，“更好”没有统一的定义。所以只能用同一套评测逐条配对，再按事先写好的规则在质量、成本、延迟上一起判。

⑤亲眼看到：1.7B 换 0.6B，再配一版提示词，凑成 2×2

评测集、判分、门禁、轨迹评测都原样用，只换环境变量 MODEL 和本机加载的模型文件。先用旧提示词 @3 直接换；结果很差，于是照 0.6B 的毛病写了一版 @6（把第 1 步写死成“必须先用 WARN|ERROR|耗时|超时 搜日志，查空了换关键字再查一次”）；为了分清功劳是模型的还是提示词的，再拿 @6 给 1.7B 也跑一遍。四组各 50 条。

逐条配对（变坏 b / 变好 c）通过说中没怪错看到关键证据耗时结论
直接换：1.7B@3 → 0.6B@32 / 17 / 08 / 1120 / 1×0.27不能换：几乎不查现场就交卷
只换提示词：1.7B@3 → 1.7B@61 / 50 / 96 / 70 / 13×1.23@6 本身是一次真改进：查得更准，说中更多
只换模型：1.7B@6 → 0.6B@66 / 714 / 55 / 1921 / 3×0.28快了三倍多、少怪 GC，可关键证据和说中都显著变少
读出来的结论
  • 直接换不行：0.6B 拿着旧提示词，平均 2.7 轮就交卷，50 条里只有 3 条看到了关键证据。编造数字、违规调用都变成了 0，那是因为它什么都没干（⑥ 坑 1）。
  • “0.6B + @6 比线上还好”是比错了基线：通过 7 对 2、怪错 15 对 30，看起来小模型完胜；可 @6 给 1.7B 用也一样提升明显。功劳有一大块是提示词的。
  • 公平的比法：同一提示词，只换模型：0.6B 快了三倍多、少怪了 14 条 GC，可看到关键证据的少了 18 条、说中的少了 9 条，都超出噪声线。按“降本提速：质量分项不许显著变坏”的规则，不能换。
  • 真正该做的下一步：先把 @6 用到 1.7B 上（走门禁和灰度）；0.6B 的长处（快、少怪 GC）可以留给分流：先让它判断告警类型，简单的自己答（⑥ 第三圈）。

实验台：按规则判，能不能换

先猜：0.6B + 旧提示词，编造数字、违规调用、怪错、成本、耗时都没变坏（甚至变好了）。按“降本提速”的规则（质量分项都不许显著变坏，耗时至少降 30%），能换吗？

数字是四组真实运行逐条配对的结果。规则：降本提速 = 不新增违规 + 质量分项（通过、说中、没怪错、没编造数字、过程指标）都没有超出噪声线的变坏 + 耗时 ≤ ×0.7；提质量 = 不新增违规 + 没有显著变坏 + 通过、说中、没怪错至少一项显著变好 + 成本 ≤ ×2。试试把“过程指标”换成粗的“看过现场”，看结论会不会变。

到这里已经能交差了：拿到一个候选模型，你能用同一套评测在质量、成本、延迟上给出“能不能换”的结论，并说清功劳是模型的还是提示词的。
已知还没处理的细节：每组只跑了一遍，换模型的噪声更大，结论贴着线的要多跑；评委是不是也跟着换了（坑 5）；云端别名的漂移（坑 3）。

⑥细节·规范·优化

第一圈 · 注意事项

1小模型“变好”的指标，是因为它什么都没干实测← ④ 机制 2
现象
换成 0.6B 后，编造数字从 4 降到 0，违规调用从 2 降到 0，怪错少了 3 条，耗时只剩四分之一。
根源
它平均 2.7 轮就交卷，50 条里只有 3 条看过现场：不查现场，自然没有数字可编；不深入，自然不会去要堆转储。
做法
门禁和换模型的规则里必须有“做了该做的事”这一类指标（看过现场、看到关键证据），不能只有“没做坏事”。
2拿旧提示词评新模型，就下“不能换”的结论← ④ 机制 3
现象
新模型 + 旧提示词分数很差，于是放弃；其实换一版写法它就能用。
根源
旧提示词是照着旧模型的毛病调的，新模型的毛病不一样。
做法
两组都评：新模型 + 旧提示词（能不能直接换），新模型 + 为它调过的提示词（它的上限）。⑤ 里给 0.6B 调了一版 @6。
3用了别名，模型被悄悄换掉← ④ 机制 4
现象
什么都没改，夜里的基线分数掉了，门禁开始乱红。
根源
代码里写的是“最新版”这类别名，厂商换了它指向的快照。
做法
发布包里写带日期或版本号的具体快照；别名只在试验时用。
4拿 token 数比成本，忘了两家的切词不一样← ④ 机制 2
现象
新模型的输出 token 少了 20%，账单却贵了。
根源
不同厂商、不同代的模型分词方式不同，同一段中文切出的 token 数不同，单价也不同；只有同一家族（像这里的 Qwen3 1.7B 和 0.6B）token 数才能直接比。
做法
成本按“每次排障多少钱”比，token 数只作参考；缓存命中、未命中、输出分开算。
5评委也跟着换了← ④ 机制 1
现象
换模型后评委打出的分数整体变了，分不清是被测模型变了，还是评委变了。
根源
如果评委用的就是被测的那个模型（怎么打分那页就是这样），换被测模型时评委也一起换了。
做法
比较不同模型时，评委固定不动，最好是另一家更强的模型。

第二圈 · 使用规范

  • 规则先写进 PR 描述：换模型的目的、能换的条件，在跑评测之前写好。防的是看到数字再找理由。
  • 两边都多跑一遍：新旧模型各跑两遍，先量各自的噪声。防的是把新模型的随机性当成它的能力。
  • 按类型列出赢和输：报告里写清新模型在哪几类故障上变好、哪几类变差。防的是平均数掩盖了某一类全军覆没。
  • 模型名写全：发布包、span、指标里都记具体快照名。防的是事后说不清用的是哪个模型。

第三圈 · 优化和深处

分流：难的给大模型，简单的给小模型

换模型不一定是全换。可以先用小模型判断告警的类型和难度，简单的（误报、一眼能看出的下游超时）自己答，难的转给大模型。回归时要按分流后的整体评，也要分别评两条路。

影子流量

离线评测过了以后，把线上的告警同时发给新模型，结果只记录不展示，几天下来拿到真实的成本、延迟分布，再抽一批人工判质量。比直接灰度安全，代价是要付双份的钱。

下一圈

  • 站 10 的 AI 网关：多个模型、降级、按租户路由，换模型变成一条路由规则，回归方法不变。
  • 开思考算不算换模型：同一个模型打开思考模式，行为、成本、延迟都会大变，也该按这一页的方法回归。
  • 自训的小模型：站 11、12 微调出来的模型，上线前同样过这套评测。
  • 评测集也要跟着长：新模型擅长的题全过了，就该往评测集里加更难的题（评测集那页的“饱和”）。

↺回到⑤：改一改

  1. 换模型也走门禁：gate.py base-@3-r1 base-@3-qwen06-r1，读报告，指出是哪一条规则拦住的。做对了会看到：只有“看过现场”红，其余全绿甚至变好。（坑 1）
  2. 开思考当一次“升级”：用 1.7B、@3、--thinking 跑 10 条冒烟组，和关思考的同 10 条配对。做对了会看到：每条慢几倍，说中和看过现场怎么变，按“提质量”的规则判它值不值。
  3. 两条路分流：按告警类型把“误报”“下游依赖”两类交给 0.6B，其余给 1.7B，把两次运行的结果拼起来当一个新版本，和全用 1.7B 比成本和质量。

自测

1. 用一句话说出这一页的精华

换模型是对每条用例的全量改动：用同一套评测逐条配对，按事先写好的规则在质量、成本、延迟上一起判；新模型可能要配新提示词；模型版本要钉死，基线要每天跑。

2. 看榜单、看厂商公告来换模型，疼在哪？

它们测的不是你的任务、你的提示词；工具调用习惯、话多话少这些行为变化，也只有在自己的评测上才看得到。

3. 为什么换小模型后，编造数字、违规调用都变少了，反而不能换？

因为它几乎不查现场、很快就交卷，没有数字可编、也不会深入到要堆转储；“做了该做的事”那一类指标（看过现场 37 → 3、关键证据 22 → 3）暴露了它不能用。

4. 预测：把 0.6B 换成比 1.7B 更大的模型，四格里哪一格变化最大？成本呢？

多半是“错，但看到了关键证据（没认出来）”变少，变成“对且看到了”：大模型更能从 HikariPool 超时认出连接池问题。成本和延迟会涨，能不能换看事先写好的“提质量”规则。

从 ④ 机制 2、轨迹评测的四格推出。

5. 预测：同一个模型名，厂商在夜里换了底下的快照，你的哪一道防线先发现？

夜里重跑的基线评测：它和缓存的基线比，差出噪声就报警。PR 的门禁发现不了（它拿候选和缓存的基线比，两边都是“新”模型或都被影响），线上指标要等好几天。

从 ④ 机制 4 和评测进 CI的基线缓存推出。

6. 放回全景：换模型时，全景的 10 站里哪一站换了内容？哪几站要多做一点？

第 1 站换了：改的是发布包里的模型名，不是提示词。第 7 站要多做：翻面多，两边都要多跑；第 8 站要加三维的“能换”规则；第 10 站灰度时成本和延迟的变化更大，要先算清楚；可能还要回到第 1 站，为新模型调一版提示词再走一遍。
