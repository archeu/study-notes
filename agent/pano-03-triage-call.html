场景：值班助手要一个“能直接用”的分诊结果

谁
值班助手的告警分诊服务 triage，站 02 那次的同一个故障：order-04 在 20:12:43 有一次 1873 ms 的 Full GC。
什么时候
2026-11-08 20:16:02，告警“order-04 接口 P99 2.1s（阈值 800ms），持续 3 分钟”。
做了什么
用官方 Python SDK 发一次 Messages 请求：系统提示写规则和一个示例，用户消息里用标签包好告警和 3 行 GC 日志，要求只输出 JSON。流式收回，用 Pydantic 校验，不合格就带着错误原因重发。
期望
{"type": "GC", "level": "P1", "cause": "…Full GC 停顿 1.8 秒…", "first_check": "…"}，字段齐、取值合法、内容对。

实测 第一次：首字 9.55 秒，总共 13.45 秒，校验通过。但 type 是“支付”：日志里明明是 Full GC，它照抄了系统提示里示例的类别。同样的请求再发一次，前缀命中缓存，首字 0.07 秒、总共 1.44 秒，这回答成了“前端”。

实测用的是官方 anthropic SDK 2.12.0，base_url 指向本机 llama-server（它实现了 Claude 的 /v1/messages 和 SSE 格式），背后是 2 核 CPU 上的 Qwen2.5-0.5B。代码和连 Claude 时一样，只是换个地址和 key；速度和答题质量远不如 Claude。标“实测”的都是这个组合的数字，Claude 的行为标“按文档”。

1值班助手：组装提示词

系统提示写不变的东西：角色、要输出的四个字段和取值范围、一个示例。用户消息里放这次的材料，用 <alert>、<gc_log> 标签包好，问题放在最后。实测 系统提示 254 字，用户消息 456 字。

为什么要它模型只看得到这一次请求里的文字。说不清要什么格式、材料和指令混在一起，它就只能猜。

往下一层提示词基本功：说清楚、给例子、用标签分隔

常出的事示例被照抄：实测 示例里的类别是“支付”，模型对这条 GC 告警也答了“支付”。示例要多样，至少覆盖几种类别。

2模型抽象层：这一类调用用哪个模型

业务代码只说“我要分诊”，抽象层按配置决定用哪个模型、什么参数、出错时换谁：比如 triage → claude-sonnet-5-5，备用 claude-haiku-5-5。本机实测时这一行写成本机的 qwen2.5-0.5b，其他代码一字不改。

为什么要它模型几个月一换代，价格常调，某家服务也会出故障。写死在业务代码里，换一次要改一片（站 02 “怎么选模型”）。

往下一层换模型只改一层：模型抽象层 待做 · Java 版：用 Spring AI ChatClient 写同一个服务 待做

常出的事抽象层把各家参数一刀切：给 Claude Opus 5.5 传 temperature 会直接 400（按文档），要按模型能力过滤参数。

3SDK：拼成一个 Messages 请求

SDK 把 model、system、messages（每条带 role：user 或 assistant）、max_tokens、stream 拼成 JSON。发之前可以用 count_tokens 量长度：实测 455 个 token。

为什么要它接口是无状态的：服务端不记得上一轮，多轮对话就是每次把全部历史重新发一遍。第 9 站的重试正是这样做的。

往下一层Messages API：角色、system、多轮其实是无状态的

常出的事以为服务端记得上下文，只发最新一句，模型答非所问；或者历史越积越长，又慢又贵（站 02 上下文窗口）。

4HTTP：发出去，带着超时和重试

SDK 用 HTTPS 发 POST /v1/messages。客户端配了 60 秒超时、最多自动重试 2 次；按 SDK 文档，它会对 408、409、429 和 5xx、以及连接错误重试，并带退避。

为什么要它模型调用是一个又慢又会失败的远程调用：一次几秒到几分钟，网络、限流、过载都可能出错。不设超时，线程会一直挂着。

往下一层出错怎么办：429 限流、过载、超时，退避加抖动 · 补给：HTTP 客户端与连接池：超时怎么配

常出的事超时设得比生成时间还短：长回答写到一半被掐断，重试又从头写，钱花了两遍。长输出要开流式（第 7 站）。

5网关：限流和排队

请求先过账号的限流：每分钟请求数、每分钟输入和输出 token 数，超了就回 429，并在 retry-after 头里告诉你等几秒；整体过载时回 529（按文档）。本机服务没有限流，这一站在实测里一闪而过。

为什么要它模型的算力是共享的，服务端必须按账号限量，否则一个人的突发流量会拖垮所有人。

往下一层出错怎么办：429 限流、过载、超时，退避加抖动 · 补给：响应时间为什么越压越长（重试反馈环）

常出的事所有实例被限流后同时立刻重试，下一秒又一起撞上限流（惊群）。要退避，还要加随机抖动。

6模型：先查缓存，再读输入、写输出

服务端先看这段前缀有没有缓存好的 KV（站 02 注意力那一页）：有就跳过，只算后面的部分。然后就是站 02 讲的那个循环。实测 第一次 455 个 token 全部要读，首字等了 9.55 秒；同样前缀第二次，缓存读 454 个，首字 0.07 秒。

为什么要它值班助手每次都带同样的系统提示和示例，不缓存就每次重读、每次全价。Claude 命中部分按输入价的 5%～10% 计（按文档）。

往下一层省钱：提示词缓存和批处理 · 回顾：注意力和 KV 缓存

常出的事系统提示开头放了当前时间或请求号：前缀每次都变，缓存一次也命中不了（站 02 实测 293 个 token 全部重算）。

7SSE：一边写一边推回来

开了 stream，服务端每写出一点就推一个事件：message_start → content_block_start → 一串 content_block_delta → content_block_stop → message_delta（带 stop_reason 和用量）→ message_stop。实测 一共 95 个 SSE 事件，其中 90 个是文字增量。

为什么要它不流式就要等整段写完才收到第一个字节：长回答几十秒没反应，HTTP 客户端或网关可能先超时。

往下一层流式输出：SSE 一边生成一边推 · 补给：HTTP 流式与 SSE

常出的事中间的 Nginx 开着响应缓冲，事件被攒成一大块才发给浏览器，“流式”形同虚设。

8收齐：看 stop_reason 和 usage

SDK 把事件拼回一个完整的 Message：content 是一组块，stop_reason 说明怎么停的，usage 记着输入、缓存读写、输出各多少 token。实测 end_turn，输入 455，输出 92。

为什么要它max_tokens 截断、拒答（refusal）、要调工具（tool_use）时，正文都不能当成完整回答用。

往下一层Messages API：角色、system、多轮其实是无状态的

常出的事不看 stop_reason，把截断的半个 JSON 交给第 9 站，解析失败后又盲目重试。

9Pydantic：校验，不合格就带着错误重来

先从回答里抠出 JSON，再用 Pydantic 模型校验：四个字段都在、type 和 level 在规定的取值里。不合格就把它的回答和错误原因作为新的两轮消息加进去，重发（第 3 站：整段历史重发）。Claude 还能用 output_config.format 直接约束输出符合 JSON Schema（按文档）。

为什么要它生成方会出错，调用方必须校验：这就是 Java 里 DTO 加 @Valid，只是对方能“改了再交”。

往下一层结构化输出：JSON Schema、Pydantic 校验、失败重试

常出的事以为“校验通过 = 结果对”：实测 第一次 JSON 完全合格，type 却是“支付”。格式能校验，内容要另外核对（站 02 幻觉那一页）。

10记录、返回；不急的改走批处理

把 usage、耗时、模型名、重试次数写进日志和监控，再把分诊结果返回给值班页面。夜里批量生成的复盘报告不急，可以攒起来走批处理接口，价格打五折（按文档）。

为什么要它不记 usage 就不知道钱花在哪、缓存命中了没有；不记重试次数就看不出提示词和模型在变差。

往下一层省钱：提示词缓存和批处理 · Java 版：用 Spring AI ChatClient 写同一个服务 待做

常出的事只记“成功 / 失败”，不记 token：月底账单翻倍，查不出是哪个接口、哪类请求。

预测题

1. 系统提示的第一行改成“现在是 20:16:02，你是值班告警分诊助手……”，每次调用会怎样？

前缀每次都不同，第 6 站的缓存一次也命中不了：每次都要从头读完整个提示，首字从 0.07 秒回到 9.55 秒这一档（本机），Claude 上输入按全价计。结果本身不一定变，账单和延迟变了。

从第 1、6 站推出：缓存只认逐字相同的前缀。

2. 晚高峰 20 个分诊实例同时被限流，都配了“立刻重试 3 次”，会看到什么？

第 5 站返回 429，20 个实例在同一时刻重试，又一起撞上限流，三轮下来全部失败，告警分诊出现一片空白；监控上 429 的次数是请求数的 4 倍。要按 retry-after 等，并加随机抖动错开。

从第 4、5 站推出。

3. 把 max_tokens 从 300 改成 20，会在哪一站出问题？用户看到什么？

第 6 站写到第 20 个 token 就停，第 8 站 stop_reason 是 max_tokens，拿到的是半个 JSON；第 9 站解析失败，按重试逻辑再发，结果还是截断，三次后放弃，值班页面显示“分诊失败”。正确做法是第 8 站看到 max_tokens 就报警，而不是交给第 9 站盲目重试。

从第 6、8、9 站推出。

4. 关掉流式（第 7 站），一次诊断要写 3000 个 token，会怎样？

要等整段写完才收到第一个字节。Claude 上可能要几十秒，用户面对空白；如果 HTTP 超时或中间网关的超时比这短，请求在第 4 站就被掐断，SDK 重试又从头写，钱花两遍。

从第 4、7 站推出。

5. 校验全部通过，就能保证分诊结果可以直接发给值班的人吗？

不能。第 9 站只查形状和取值范围；本页实测第一次就是“格式完全合格、类别是错的”。类别、原因这些内容要靠更好的提示词和示例（第 1 站）、先查证据（站 06），关键字段还要用程序核对（站 02 幻觉）。

从第 1、9 站推出。
