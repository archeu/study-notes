token、分词和计费：同一段日志要花多少钱

token 是模型的计量单位：上下文窗口按它算，速度按它算，钱也按它算。分词器把文字切成词表里有的片段：常见的词一个 token，数字、时间戳、ID 几乎一个字符一个。实测同样是一行字，Java 栈每个 token 能装 4 个字符，UUID 只装 1 个。所以按字数估成本会差好几倍，算 Claude 的数要用 Claude 自己的 count_tokens。

①为什么需要：值班助手每问一次，账单上记的是什么

在全景第 2 站和第 10 站，这一步要解决两件事：61 行 GC 日志进模型之前被切成了多少块；问完一次，账单上按什么算钱。值班助手一天要问几千次，这两个数决定了它用不用得起。

这一页学完要能做到地图上“怎么算过关”的第二条：给一个调用场景，估得出大概花多少钱。

②没有它会怎样：按字数估，差好几倍

不懂分词时，最自然的估法是“字数 ÷ 某个系数”。拿 ⑤ 里实测的几行文字对一下（本机 Qwen2.5 的分词器）：

英文句子66193.4717，差一点
JSON 一条订单79421.8820，少估一半
GC 日志一行112781.4428，少估 64%
中文句子30231.308，少估 65%
UUID36351.039，少估 74%
  • 值班助手发的恰好是最“费 token”的那几类：时间戳、GC 编号、内存数字、订单号。按英文的经验系数估，日志的成本会少算一半以上。
  • 按“中文一个字一个 token”估也不对：常用词“订单”“服务”“是因为”各只占一个 token，而前面带空格的“变”被拆成了两段字节，占两个。
  • 唯一准的办法是用同一个模型的分词器真切一遍：本机用 /tokenize，Claude 用 count_tokens 接口。
不懂精华时的典型误用：拿 OpenAI 的 tiktoken 或者“字数 × 系数”给 Claude 做预算。Claude 的文档明说 tiktoken 在一般文本上就少算 15%～20%，代码和非英文少得更多；而且每家、甚至同一家不同代的模型词表都不一样。

本页学字节级 BPE：Qwen、GPT、Llama 这些模型公开的分词器都是这一路（Claude 的分词器没有公开，只能通过 count_tokens 看结果）。原理一样，各家的词表不一样。

④原理：词表是“合并”出来的，钱是按块数收的

先知道这些
  • UTF-8：英文字母和数字一个字节，常用汉字三个字节，表情符号四个字节。“变”是 e5 8f 98。
  • token id：词表里每一项的编号。模型只认编号，上一页的循环里接上的也是编号。

机制 1 · BPE：从 256 个字节开始，反复合并最常挨在一起的一对

这解释了 ② 那张表：Java 包名、英文单词在语料里出现得极多，早就被合并成大块；UUID、订单号是随机的，没有哪一对常见到值得合并，只能一个字符一块。

还有一条额外的规则：切之前，Qwen 的分词器会先把数字拆成一位一位的（实测 1873 切成 1、8、7、3），所以日志里的数字一律一位一个 token。不是所有分词器都这样，有的允许最多三位一组，这也是各家 token 数对不上的原因之一。

机制 2 · 中文和罕见字符：退回到字节，永远切得出来

实测 “订单服务在 20:15 变慢，是因为一次很长的 GC 停顿。”切成 23 个 token：

订单服务在 20:15␣ e5 8f98慢，是因为一次很长的 GC␣ e5819c顿。

“订单”“是因为”是一个 token；可是“ 变”（前面带空格）这个组合在语料里不够常见，被切成了两段字节，“ 停”更碎，切成三段。虚线框就是字节回退：词表里没有现成的片段，就退回到 UTF-8 字节，所以字节级 BPE 没有“未知字”。代价是这样的字更贵，而且单个 token 可能只是半个字，上一页 ⑤ 里服务端不肯吐出“半个字”就是这个原因。

机制 3 · 计费：输入、输出分开数，各乘各的单价

账单上的一项数的是什么Opus 5.5 单价（美元 / 百万 token）返回的 usage 字段
输入系统提示 + 工具定义 + 全部对话历史 + 这次的问题，统统切成 token4input_tokens
输出模型写出的每个 token，包括它的“思考”，哪怕思考内容不显示给你20output_tokens
写入提示缓存第一次把一段前缀存进缓存（5 分钟有效）5（输入价 × 1.25）cache_creation_input_tokens

批处理不急的请求攒成一批，异步跑上面各项打 5 折—

价格按 Claude 官方文档（2026-11 核对）：Sonnet 5.5 是 2 / 10，缓存命中 0.10；Haiku 5.5 是 0.1 / 0.5（提示不超过 10 万 token 时）。缓存和批处理放到站 03 的“省钱”那一页细讲。

两点最容易漏：一是输入不只是你的问题，系统提示、工具说明、前面几轮的对话每次都要重发、重新计费；二是输出包括思考，Opus 5.5 的思考关不掉，只能用 effort 调深浅（推理模型那一页）。

为什么这样设计：词表不能太小，也不能太大

十几万项的子词词表

  • 常见文字切得粗：同一段话 token 少，模型转的圈少、窗口装得多、钱花得少。
  • 罕见文字退回字节：任何输入都能表示，不会有“未知字”。
  • 代价：词表每一项在模型的输入端和输出端各占一行参数。本页的模型 151936 × 896 ≈ 1.36 亿个数，约占它 4.9 亿参数的四分之一（输入输出共用一张表时）。第 6 站每圈要给 15 万多个候选打分，也是这张表的大小决定的。

两个极端

  • 只用 256 个字节：参数省了，但一行日志 112 块，回答也要多写好几倍的圈，又慢又贵，窗口还装不下多少东西。
  • 词表大到每个词一项：表本身大得放不下，绝大多数项一年见不到几次，学不好；而且新词（新的类名、订单号）照样表示不了。
决定胜负的约束：模型每多处理一个 token 都要完整算一遍，所以序列越短越好；但词表每多一项都要占参数、每圈都要打分。十几万项是两头折中出来的结果，各家取的点不同，所以同一段文字在不同模型上的 token 数不同，单价也就不能直接比，要比“这段文字一次多少钱”。

def slim(log):
    """时间戳只留时分秒，去掉每行都一样的 [info][gc] 和括号里的原因，只留 >100ms 的停顿"""
    out = []
    for line in log.splitlines():
        m = re.match(r"\[2026-11-08T(\d\d:\d\d:\d\d)\.\d+\+0800\]\[info\]\[gc\] GC\(\d+\) "
                     r"(Pause \w+).*? (\d+M->\d+M)\(1024M\) ([\d.]+)ms", line)
        if m and float(m.group(4)) > 100:
            out.append(f"{m.group(1)} {m.group(2)} {m.group(3)} {float(m.group(4)):.0f}ms")
    return "堆上限 1024M，只列停顿超过 100ms 的 GC：\n" + "\n".join(out)

⑥细节：算钱时最常漏掉的几块

第一圈 · 注意事项

1拿别家的分词器给 Claude 估数← ④ 机制 1
现象
用 tiktoken 估出来 4000，上线后账单上是 5000 多。换一代模型，同样的提示词 token 数又变了。
根源
词表是各家用各自的语料合并出来的，合并顺序不同，切法就不同。Claude 的文档写明：Opus 4.7 起的新分词器，同样的文字大约是旧分词器的 1～1.35 倍 token。
做法
预算和超长检查都用 count_tokens，传和真实调用同一个 model；换模型时重新量一遍，不沿用旧数。
2只算了问题，没算系统提示、工具说明和历史← ④ 机制 3
现象
值班助手改成多轮追问，第 10 轮的账单是第 1 轮的十倍。
根源
模型每次调用都是从头读一遍前文，API 不替你记住上一轮（站 03 讲“多轮其实是无状态的”）。每轮新增 500 token，10 轮下来输入累计是 500 × (1+2+…+10) = 27500，不是 5000。
做法
按“这一次请求的完整内容”估，不按“这次新说的话”估；长对话用提示缓存（命中部分只收 5%）、定期压缩历史。
3看到的回答只有 50 个字，输出却收了 2000 个 token← ④ 机制 3
现象
usage.output_tokens 远大于回答的长度。
根源
思考也是一圈一圈写出来的 token，按输出单价收；默认不显示思考内容，但照样计费。Opus 5.5 的思考关不掉。
做法
简单任务把 effort 调到 low；成本统计一律以 usage 为准，不按回答字数推算。
4“不超过 100 字”和 max_tokens: 100 不是一回事← ④ 机制 2
现象
要求“100 字以内”，同时设 max_tokens: 100，回答在半句话处被截断。
根源
中文平均 1.3 个字一个 token，带数字和时间就更碎；而且有思考时，思考也算在 max_tokens 里。
做法
长度要求写进提示词；max_tokens 只当保险丝，留出几倍余量，再检查 stop_reason（上一页坑 2）。

第二圈 · 使用规范

  • 日志先过滤再发：只发和问题相关的时间段、相关的行，重复的前缀去掉。防的是把钱花在“贵文字”上，也防关键行被淹没（上下文窗口那一页实测）。
  • 每次调用都把 usage 落库：按功能、按模型、按天汇总。防的是月底才发现账单翻倍。
  • 请求发出前先查长度：超过预算的输入直接截断或拒绝，并打日志。防的是一条异常的超长日志把单次费用顶到几十倍。
  • 价格写进配置，不写死在代码里：模型一换代、价格一调整，改配置就行。防的是成本报表悄悄算错。

第三圈 · 为什么价格长这样

输出为什么比输入贵 5 倍

输入几千个 token 一次并行读完，输出一圈只出一个，每圈都要把模型权重完整读一遍（上一页）。占用的机器时间不一样，价格就不一样。

缓存命中为什么只收 5%

命中的那段前缀，服务端已经算好了每一层的中间结果（KV 缓存），不用再算，只要读出来。Opus 5.5 命中价 0.20，是输入价 4 的 5%（注意力和 KV 缓存）。

数字一位一个 token

Qwen 把数字拆成单个数字，好处是 1873 和 1874 共用同一套“数字 token”，做加减比较时更规整；代价就是日志里数字特别费 token。别家有的三位一组，token 少一些。

比价要比“这段文字一次多少钱”

各家词表不同，同样的日志在 A 模型 5000 个 token、在 B 模型可能 6000 个。单价低的不一定便宜，拿自己的真实请求在各家都量一遍再比。

自测

1. 用一句话说出这一页的精华

钱、窗口、速度都按 token 算；分词器把常见片段合成一个 token、罕见的退回字节，所以日志、ID、数字特别费 token，按字数估会差好几倍，要用同一模型的分词器真量。

2. 为什么“4 个字符 1 个 token”在 Java 栈上准，在 UUID 上差了 4 倍？

Java 包名和英文单词在语料里极常见，早被合并成大块；UUID 是随机的十六进制，没有哪一对常见到值得合并，只能一个字符一块。

从 ④ 机制 1 推出

3. 预测：把日志里的时间戳从 [2026-11-08T20:12:43.207+0800] 改成 20:12:43，每行大约省多少 token？

原时间戳 30 个字符，按本页实测几乎一个字符一个 token，约 30 个；改成 8 个字符，约 8 个。每行省 20 个左右，61 行省一千多，占整个请求的四分之一上下。

从 ④ 机制 1（数字一位一个 token）推出；可以在 ⑤ 里改一行验证。

4. 预测：同一段 5000 token 的日志，问 10 个不同问题，每次只换问题、日志放在前面。打开提示缓存后，第 2～10 次的输入费用大约变成原来的多少？

日志这段前缀一字不差，第 2 次起命中缓存，按 5% 计（Opus 5.5）；只有问题那几十个 token 按原价。所以输入费用降到原来的 5% 多一点。第 1 次要多付 25% 的写入费。顺序反过来（问题在前、日志在后）就一次也命中不了。

从 ④ 机制 3 的计费表推出；缓存要求“前缀一字不差”，站 03 细讲。

5. 为什么不干脆用 256 个字节当词表，省掉十几万行参数？

序列会长好几倍：模型每处理一个 token 都要完整算一遍，回答要多转好几倍的圈，窗口也装不下多少内容。省下的参数远抵不过慢和贵。

从 ④ 为什么这样设计 推出

6. 放回全景：第 2 站前后各发生了什么？如果分词器坏了，把每个字都切成单个字节，整条链路会怎样？

第 2 站之前是第 1 站值班助手拼好请求；之后是第 3 站检查装不装得下窗口、第 4 站查向量表。全切成字节后，5008 个 token 会变成七八千甚至更多：第 3 站可能装不下 8192 的窗口直接报错；装得下的话，第 5 站读输入更慢，第 10 站按 token 计费的账单也跟着涨，而且模型从没在这种切法上训练过，回答会变得很差。

档位：标准。本机跑过（2 核 ARM，llama.cpp b12618 里 Qwen2.5-0.5B-Instruct 的分词器，Python 3.13，2026-11-22）：⑤ 的各类文字切法、61 行 GC 日志原样和瘦身后的 token 数。按文档（Claude API 文档，2026-11 核对）：各模型单价、缓存写入 1.25 倍和命中价、批处理半价、count_tokens 和 usage 字段、tiktoken 少算和新分词器 1～1.35 倍的说法、思考按输出计费。估算：⑤ 和实验台的美元数是“Qwen 的 token 数 × Claude 单价”，不是 Claude 的真实账单。
