一次只写一个 token：下一个词预测

模型只会做一件事：给定前文，算出下一个 token 的概率表。一段回答，是把这件事循环做出来的：挑一个，接到末尾，再算下一个，直到写出结束符。它不会先想好整句再往外写，也不查任何东西。输出慢、输出贵、能流式、开头错了一路错、数字会编，都从这个循环来。

①为什么需要：28 个 token 是怎么写出来的

在全景第 6、8、9 站，这一步要解决：模型读完值班助手发来的 4950 个 token（系统提示、61 行 GC 日志、一个问题）之后，怎么把“是的，订单服务 20:15 变慢，是 order-04 的 GC 导致的。”这 28 个 token 写出来，又怎么知道该停了。

为什么一个后端工程师要懂到这一层：调用模型时你天天碰到的几件事，都只有从这个圈才解释得通。

  • 输出比输入贵好几倍（Claude Opus 5.5 输入每百万 token 4 美元，输出 20 美元，按文档），因为输入能一次读完，输出只能一圈一个。
  • 能“流式”：每转一圈就多一个 token，服务端可以立刻推给你，不用等整段写完。
  • 回答会被截成半句：圈数到了 max_tokens 就硬停，stop_reason 会告诉你是哪种停法。
  • 数字会编：每一圈只问“接下来写什么像”，没有哪一步去日志里数 Full GC 有几次。

②没有它会怎样：用老办法回答“是不是 GC 导致的”

在大模型之前，让程序“看日志说话”有两条老路。拿全景里那个问题试一下：

要求规则模板（if 日志含 X 就说 Y）n-gram 统计（看前 2 个词猜下一个）下一个 token 预测（大模型）
问法换一种也能答不能：“是不是 GC”“GC 有关系吗”“为啥卡了”要各写一条规则能：它只管往下接，不挑问法能：问法只是前文的一部分
把隔得很远的两处联系起来能，但只认规则里写死的那几处不能：只看最后 2 个词，“20:15 变慢”和 30 行之前的 “Pause Full 1873ms” 连不上能：每一圈都读整段前文（第 5 站的注意力）
写出通顺的一句话能，但句子是模板拼的，一字不变不能：每 3 个词通顺，整句前言不搭后语能
说的每个数都对能：数字是程序从日志里取的不能不保证：全景第 10 站它答“10 次 Full GC”，实际 1 次

n-gram 是“下一个词预测”的老前辈：统计语料里“GC 导致”后面最常跟什么。想法和今天一样，差在能看多远：它只看最后两三个词，看得再远，组合数就爆炸，语料里根本见不到。大模型把“看前文”换成了一个训练出来的函数，能看整段，这就是精华。

不懂精华时的典型误用：以为模型像规则引擎一样“在日志里查到了”才回答，把它说的数字直接写进值班报告。它做的只是一圈一圈地往下接最像的 token，规则模板那一列唯一的“能”（数字都对），它恰恰不保证。

③相邻方案：一定要一个一个写吗

做法怎么出字今天用在哪
自回归（从左到右，一次一个）每圈出 1 个 token，下一圈把它当前文Claude、GPT、Qwen、DeepSeek 等主流对话模型都是这种（按各家公开的模型说明）
填空式（BERT 这类）遮住中间几个词，一次猜出来，两边的字都能看到适合“读懂”：分类、抽取、做向量（站 06 检索用的 Embedding 模型多是这一路），不适合写长回答
扩散式语言模型先出一整段草稿，再并行地一轮轮改有公司在做，主打出字快；截至 2026 年还不是主流对话模型的做法（按公开资料，未在本机验证）

本页学自回归：你会调用的模型几乎都是它，API 里的流式、max_tokens、stop_reason、输出单价都是照着它设计的。

④原理：一个只读的大函数，加一个 while 循环

先知道这些
  • token：模型词表里的一个片段，有一个编号。本页的模型词表有 151936 项，“是不是”是一个 token，一个时间戳会切成二三十个。怎么切、怎么计费是下一个知识点。
  • 打分再换成概率：模型给词表里每个 token 打一个分（logit），再用 softmax 换成概率：pi = ezi / Σ ezj。指数让高分更突出，除以总和让全部加起来是 1。这只是“把分数归一化”，不用记公式。
  • 参数：函数里的几亿到几千亿个数字，训练时调好，调用时不再改。本页的模型约 5 亿个（Qwen 官方写 0.49B）。

机制 1 · 循环：一圈只出一个 token

下面是 ⑤ 那段脚本真实跑出来的前几圈（温度 0）。每一圈看三样：现在的前文、模型给的前 3 名候选、挑中谁。

准备点“下一步”。

注意两件事。第一，每一圈的输入都是“全部前文”，不是只有上一个 token；所以写到后面，它还能“看见”开头的日志。第二，挑中的那个就定了，后面的圈只能顺着它往下写，没有哪一步回头去改前面的字。

机制 2 · f 是什么：前文进去，151936 个分数出来

用 Java 的话说，它就是一个巨大的纯函数 Map<Token, Double> next(List<Token> prefix)。比方失效的地方有两处：它内部没有一行 if 写着“看到 Pause Full 就说是 GC”，全靠几亿个数字相乘相加；而且在服务端，同一个前文的分数会因为浮点运算顺序有极小的差别（采样那一页细讲）。

机制 3 · 它是怎么学会的：千亿道“猜下一个”的题

这张图解释了本站后面两页的根子：训练只奖励“和语料里的下一个 token 一样”，从来没有一道题问“这句话是真的吗”。所以它学到的是“写得像”，碰到语料里常见的说法（“一共有 N 次 Full GC”）就顺手接上一个看着合理的数，这就是幻觉的出发点。

机制 4 · 停下：结束符也是一个 token

自己停：挑中了结束符

结束符就在词表里（这个模型是 <|im_end|>，编号 151645）。后训练时每段示范回答都以它收尾，所以模型学会了“话说完了，下一个最像的就是结束符”。Claude API 里这时 stop_reason 是 end_turn。

被停：圈数到了上限

调用方给的 max_tokens 是保险丝，到了就不再转，不管句子写没写完，stop_reason 是 max_tokens。还有一种是写出了你指定的 stop_sequences，stop_reason 是 stop_sequence（按 Claude API 文档）。

为什么这样设计：一次只写一个

自回归：一个一个写

  • 写下一个 token 时，前面写了什么全都看得见，整句自然前后一致：前面写了“是的”，后面不会冒出“不是”。
  • 训练极省事：任何一段文字，每个位置都是现成的题和答案（机制 3），全网文本都能当教材，一次计算并行出分。
  • 一个目标通吃所有任务：问答、写代码、调工具、输出 JSON，都是“往下接”。
  • 代价：生成时只能串行，一圈一个 token。写 300 个 token 就要把模型完整跑 300 遍，这是输出慢、输出单价高的根本原因。

一次把整句写出来

  • 每个位置同时决定自己写什么，互相看不到对方的选择：第 1 个位置倾向“是”，第 2 个位置倾向“不是”的后半截，拼出来就是乱的。
  • 要整句一起对，就得反复改几轮（扩散式就是这么做的），工程上更复杂，主流对话模型没走这条路。
  • 好处是快：一次出很多字。
决定胜负的约束：语言里后一个词强烈依赖前面写了什么。把“整句的概率”拆成“每一步在前文条件下的概率连乘”（链式法则）是精确的拆法，不是近似；按这个拆法训练又最便宜。代价只落在生成速度上，于是业界去优化速度（KV 缓存、投机解码，见 ⑥），而不换掉这个拆法。

最少的语法

生成循环的骨架完整版在 ⑤
ids = tokenize(prompt)
# 每一圈：前文 → 概率表 → 挑一个 → 接上
for _ in range(max_tokens):
    probs = model(ids)          # 第 6 站
    tid = pick(probs)           # 第 7 站
    if tid == END: break        # 第 9 站
    ids.append(tid)             # 第 8 站
    yield tid                   # 流式：写一个推一个

调用 API 时，这个圈露在哪

  • max_tokens：最多转几圈。
  • stop_sequences：写出这些字就停。
  • stream: true：每转一圈推一次。
  • 返回的 stop_reason：是怎么停的。
  • usage.output_tokens：一共转了几圈，按它收钱。

挑法（温度）放到采样那一页。

⑤亲眼看到：自己写这个循环

不用 SDK，直接让本机的模型服务每次只算 1 个 token（n_predict: 1），把前 5 名候选和概率拿回来，挑第一名接到末尾，自己转这个圈。值班助手的输入缩成 3 行 GC 日志（读 4950 个 token 在这台机器上要两分多钟）。

  1. 1 起模型服务llama.cpp 的 llama-server，加载 Qwen2.5-0.5B-Instruct 的 4 位量化文件（483 MB），监听 8090 端口。编译和下载步骤在 README。
  2. 2 拼出前文系统提示 + 日志 + 问题，按模型的对话模板拼成一段文字，再切成 297 个 token。对模型来说，“对话”就是这段要续写的文字。
  3. 3 转圈每圈调一次 /completion，挑中的 token id 追加到前文，直到挑中结束符 <|im_end|>（编号 151645）或写满 120 个。
⑤main.py（核心部分）完整代码 →
def next_token(ids):
    # 第 6 站：前文 → 下一个 token 的概率表（只要前 5 名）
    r = post("/completion", {"prompt": ids, "n_predict": 1, "n_probs": 5,
                             "temperature": 0, "cache_prompt": True})
    return [(c["id"], c["token"], math.exp(c["logprob"]))
            for c in r["completion_probabilities"][0]["top_logprobs"]]

ids = tokenize(chat_prompt(SYSTEM, LOG + "\n\n" + QUESTION))
end_id = tokenize("<|im_end|>")[0]
for i in range(1, MAX_NEW + 1):

读出来的结论
  • 手写循环和服务端“一口气写完”结果一字不差：服务端内部就是这个圈，没有别的魔法。
  • 第 1 圈要读 297 个输入 token；之后每圈只“重算 1 个 token”，因为前面的中间结果都在 KV 缓存里。本机读输入约每秒 48 个，写输出每秒 24～25 个。
  • 开头被写成“不是”，它没法删，只能接着写出“不是，是 GC 导致的”这种自相矛盾的话，然后陷进“时间差”的重复里，直到被截断。
  • 结束符也只是一个普通 token。不理它，模型会继续“像训练语料那样”往下写：下一段对话的“Human:”，连日志都照着前文抄了一行。
  • 说得有板有眼的“依据”是编的。每一圈只问“接下来写什么像”，没有哪一圈去日志里查过 20:14 有没有记录。

还有一个意外收获：在服务器里先跑过另一个问题、缓存里留着一段相同前缀时，同样温度 0，第 24 圈的概率变成“多”0.147 对“慢”0.146，翻了过来，整句变成“……比20:14的多，且20:14的GC时间比20:13的多。”，第 44 个 token 就停了（实测）。两次只是前文分几批算不同，浮点运算的顺序就变了。温度 0 也不保证每次一样，采样那一页专门讲。

到这里已经能交差了：你能说清模型一次只写一个 token、怎么停，并且能用一段 50 行的脚本把这个圈亲手转出来。
已知还没处理的细节：开头一错一路错（坑 1），截断（坑 2），输出慢（坑 3），数字靠不住（坑 4），自己拼对话时忘了停止符（坑 5）。

⑥细节：这个圈带来的坑

第一圈 · 注意事项

1开头一错，一路错实测← ④ 机制 1
现象
⑤ 里把开头强制写成“不是”，模型删不掉它，只能接出“不是，是 GC 导致的”这种自相矛盾的话，后面越写越乱。真实调用里第一个 token 是按概率抽的，⑤ 里“不是”有 0.205，温度不为 0 时每五次大约就有一次抽到它。
根源
挑中的 token 就定了，后面每一圈都把它当成既成事实往下接；没有哪一步回头检查前面写得对不对。
做法
让结论写在依据后面：提示词里要求“先逐字引用相关的日志行，再下结论”。先写出的证据会变成后面每一圈的前文，结论就有了依据。推理模型把这件事做成了内置的“先思考”。
2回答被截成半句，程序却当成完整的← ④ 机制 4
现象
要它输出一段 JSON，max_tokens 给小了，拿回来的是半个 JSON，解析时报错；更糟的是一段截断的文字被当成完整结论写进了报告。
根源
到了 max_tokens 循环就硬停，不管句子写完没有。
做法
每次都检查 stop_reason：不是 end_turn（或你预期的 stop_sequence、tool_use）就别当完整结果用；max_tokens 按预期长度留出余量。
3以为输出长度不影响耗时实测← ④ 为什么这样设计
现象
同样的输入，让它“一句话回答”和“详细分析”，耗时差了好几倍；用户等的主要是输出。
根源
输入一次并行读完，输出一圈一个。⑤ 里本机读输入每秒 48 个 token，写输出每秒只有 24～25 个。
做法
估耗时用“首 token 时间 + 输出 token 数 ÷ 输出速度”；限制输出长度（“一句话”“只给 JSON”）；长输出一定开流式（站 03）。
4让它数数、查数，它就编← ④ 机制 3
现象
全景第 10 站：问“有几次 Full GC”，答“10 次”，实际 1 次。
根源
函数 f 里没有计数器，也没有去日志里查的步骤；它只是在“一共有”后面接一个训练语料里最像的数。
做法
确定性的事（数数、查值、算钱）交给代码：先用程序 grep 出 Full GC 的行，再让模型解读；或者让它调工具（站 04）。
5自己拼对话、用续写接口时，模型替用户把下一句也写了实测← ④ 机制 4
现象
⑤ 的 --ignore-end：回答写完后，模型接着写出“Human: [2026-11-08T20:12:03…”，替用户编了下一轮提问。
根源
“停”只是挑中了结束符这个 token；循环不在它这里退出，模型就照训练语料的样子接着写下一段对话。
做法
用 Messages / Chat 这类对话接口，服务端会套好模板、认结束符；自己用纯续写接口（/completion、vLLM 的 /v1/completions）时，一定传 stop（停止符列表）。

第二圈 · 使用规范

  • 依据在前，结论在后：输出格式里先放引用、再放判断。防的是坑 1：开头抽错了没法改。
  • 每个调用都检查 stop_reason：在统一的调用层里检查，截断时打日志、按需重试或调大上限。防的是坑 2。
  • 明确告诉它写多长：“一句话”“不超过 3 条”，再配一个留了余量的 max_tokens。防的是坑 3 的慢和贵。
  • 数字不信模型，信程序：报告里每个数字都要能追到原文的一行。防的是坑 4。

第三圈 · 为什么输出慢，业界怎么提速

每出一个 token，要把全部参数读一遍

算一个 token 大约要做 2 × 参数量次乘加（这是常用的估算口径）。更要命的是读：每一圈都要把全部权重从内存读进计算单元，这个模型 4 位量化后约 0.4 GB，每秒能转几圈，主要看内存带宽而不是算力。读输入时几千个 token 共用这一次读取，所以快得多。

KV 缓存：前文不重算

每一圈的输入是“全部前文”，但前文里每个 token 在每层的中间结果（K、V）上一圈已经算过，存起来直接用，这一圈只算新来的那一个。⑤ 的输出里“重算 1 个 token”就是它。细节在注意力和 KV 缓存。

投机解码：小模型先猜，大模型一次验

让一个小模型先连猜 4～8 个 token，大模型一次把这几个位置都算出来，对得上的直接收下。大模型一次读权重能验好几个 token，出字更快，而结果的分布和大模型自己写的一样（按 llama.cpp、vLLM 文档的说法）。

服务端批处理：多个请求一起转

一次读权重，同时给几十个用户各算一个 token，吞吐上去了。副作用是你的请求和谁拼在一起不固定，浮点运算顺序跟着变，温度 0 也可能不逐字一样（采样那一页）。

自测

1. 用一句话说出这一页的精华

模型只会“给定前文，算下一个 token 的概率表”，回答是把它循环调用出来的：挑一个、接上、再算，直到结束符或 max_tokens。

2. n-gram 也是“猜下一个词”，它差在哪？

只能看最后两三个词，看得再远组合数就爆炸、语料里见不到；隔得远的两处（“20:15 变慢”和几十行前的 Full GC）联系不起来。大模型用一个训练出来的函数读整段前文。

3. 为什么输出单价比输入贵、输出也比输入慢？

输入可以一次并行读完，几千个 token 共用一次读权重；输出只能一圈一个，每个 token 都要把模型完整跑一遍、权重读一遍。

从 ④ 为什么这样设计 推出

4. 预测：让模型“先给结论，再列依据”和“先列依据，再给结论”，哪种结论更可靠？为什么？

后一种。结论写在后面时，前面写出的依据已经是前文，每一圈都能看到；结论写在前面时，它是在没有任何依据写出来的情况下抽出来的，后面的依据只能顺着结论去凑。

从 ④ 机制 1 推出：挑中的就定了，后面只能顺着写。

5. 预测：同一个请求，把 max_tokens 从 1000 改成 50，费用和耗时会怎么变？回答一定变短吗？

只有当回答本来超过 50 个 token 时才有影响：那时会在第 50 个停下，stop_reason 变成 max_tokens，输出费用和耗时按 50 个算。本来就只写 28 个的回答，不受影响，模型也不会因为上限小就主动写短，它根本不知道上限是多少。

从 ④ 机制 4 推出：max_tokens 是循环外面的保险丝，不在前文里。

6. 放回全景：第 6 站前后各发生了什么？如果第 8 站“接上”这一步坏了（比如挑中的 token 没接到前文里），整条链路会怎样？

第 6 站之前是第 5 站读完输入、存下 KV 缓存；之后是第 7 站从概率表里挑一个。第 8 站不接上，下一圈的前文和上一圈一模一样，算出的概率表也一样，温度 0 时会一直挑同一个 token，直到 max_tokens 截断：输出是同一个字重复几百遍，stop_reason 是 max_tokens，费用按满额算。
