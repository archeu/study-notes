三种能力：工具、资源、提示词模板

MCP 服务端能摆出三样东西，区别不在“装的是什么”，而在谁决定什么时候用：工具由模型在推理中途决定调，资源由应用或用户决定附上，提示词模板由用户点了才展开。全做成工具，就是把本该人来拿主意的事也交给了模型，还要每一轮为它付 token。

①为什么学：值班助手要搬上服务端的，不止“动作”

在全景第 5 站，Claude Code 列 oncall 的清单时，拿回来的不只 tools/list：还有 resources/list 和 prompts/list。值班助手要搬到服务端的东西有三类，性质完全不同：

②老办法：全做成工具，或者全塞进系统提示

站 04 的值班助手只有工具这一种手段。把手册和开场白也硬塞进去，有两种做法，对照三条要求看：

要求全做成工具（get_runbook()、start_triage()）全塞进系统提示
不用的时候不花 token差一点：手册内容不花，但两个工具的定义每一轮都跟着发。不能：手册常驻，每一轮都要付它的 token，聊别的事也一样。
该用的时候一定用上不能保证：要模型自己想起来调 get_runbook，想不起来就不看手册；想起来了也多花一轮（站 04 实测一轮 4～10 秒）。能：一直在。
你能直接点名用它不能：你只能在提问里写“请先调 get_runbook”，求模型去调。不能：它在不在不由你。
  • 把“由人决定的事”交给了模型：排障开场白本来是你一点就该展开的固定话术，做成工具后，要不要按手册走变成了模型的判断。
  • 工具清单越长，模型越容易挑错：MCP 规范把工具定位成“模型控制”，清单里每多一个本不该由模型决定的东西，都在稀释它的注意力。
不懂精华时的典型误用：照着“文件读写”的直觉，把“读一份文档”做成资源以后，就以为模型会自动看到它。资源是应用控制的：在 Claude Code 里，要你用 @ 点名，或者模型主动去读，它才进上下文（坑 4）。

③选谁：按“谁决定什么时候用”来分

这样东西谁决定什么时候用做成在 Claude Code 里长什么样
排查中途要做的动作：查日志、解析 GC、写工单评论模型工具：tools/list、tools/call模型自己调 mcp__oncall__search_logs，调之前过权限检查

一段每次都要说的开场白或流程你提示词模板：prompts/list、prompts/get，带参数斜杠命令 /mcp__oncall__triage order-svc 20:16

选择规则：先问“谁按下按钮”。模型在推理中途按的，做工具；你或应用按的，看它是“一份数据”（资源）还是“一段要模型照做的话”（提示词模板）。拿不准的，大多该做成工具，因为三种里只有工具一定被所有客户端支持。

最后一句的依据：Claude Code 三种都支持，但不少客户端只实现了工具。资源和提示词模板做成了，在那些客户端里就等于没有。

④原理：三种能力各自的一来一回

先知道这些
  • 上一页的三方：主机（Claude Code）、客户端（一个服务端一个）、服务端。三种能力都是服务端摆出来、客户端去取，见 MCP 的三方。
  • Java 比方：工具像一个 POST 接口（调了就做事），资源像一个只读的 GET 地址（按 URL 取一份内容），提示词模板像一张预先存好的查询模板（填两个参数就能用）。比方失效的地方：调不调工具不是前端写死的，是模型临场决定的。
  • JSON Schema：描述 JSON 长什么样的标准，工具的参数和结构化结果都用它。Python SDK 从类型注解生成，不用手写。

机制 1 · 谁按按钮：三种能力的触发方不同

MCP 规范的原话：提示词模板是用户控制的，资源是应用控制的，工具是模型控制的；还说“控制”指的是谁决定什么时候用，不是谁写的内容。对工具，规范另外要求：应当始终有人能拒绝一次工具调用。

机制 2 · 工具：定义五件套，结果三种出错

五件套各管什么

  • name：1～128 个字符，只用字母、数字、_ - .，同一个服务端里不重名。
  • description 和 inputSchema：给模型看的说明书，站 04 那页讲过怎么写。
  • outputSchema：结果的结构。有了它，结果里多一份 structuredContent，程序能直接取字段。
  • annotations：只读吗、有破坏性吗、能重复调吗、会碰外部世界吗。全是提示，规范要求客户端把不可信服务端的提示当作不可信（坑 3）。

预料之中：参数格式不对（since 写成“8点”）工具执行错误：isError: true，写一句人话，让模型能改了重试服务端 raise ToolError(...) → isError: true“since 要写成 HH:MM（例如 20:06），收到的是 '8点'”
没预料到：代码里冒出一个异常（坏正则）同上，也该是 isErrorSDK 只回一句笼统的话，详情只在服务端日志里“Error executing tool search_logs”，不知道哪里错了

机制 3 · 资源：一个 URI 一份内容，模板按参数取

  • 固定资源：oncall://runbook/order-svc，resources/list 列得出来。URI 的协议名自己定，规范里举的例子有 file://、https://、git://。
  • 资源模板：oncall://gc-log/{date}，用 RFC 6570 的写法，resources/templates/list 列出来，客户端填好 date 再去 resources/read。日志、工单这种“有无数份”的东西都该这么做。
  • 内容是 text 或 blob（base64 的二进制，比如截图），带 mimeType。不存在的资源，规范要求回 -32602，不能回一个空的 contents。
  • 资源还可以带 annotations：给谁看（user / assistant）、多重要（0～1）、最后修改时间，主机据此决定怎么用。

机制 4 · 提示词模板：参数进去，一串消息出来

prompts/get 带上名字和参数，服务端回一串 messages，每条有 role（user 或 assistant）和内容。内容可以是文字、图片，也可以嵌一份资源，比如把值班手册直接嵌进开场白里。Claude Code 把它们当成你这一轮说的话发给模型。缺了必填参数，规范说回 -32602。

为什么这样设计：为什么不全做成工具

三种能力，按“谁决定”分开

  • 该你拿主意的事（按不按手册走）留在你手里，一个斜杠命令就展开，不靠模型“想起来”。
  • 资源不占工具清单：一百份工单是一个模板，不是一百个工具；不读就不花 token。
  • 结果的身份清楚：资源和模板进上下文时是“你给的”，工具结果是“模型查到的”，主机可以分开对待。
  • 代价：客户端要实现三套界面（@ 选资源、斜杠命令、工具调用），不少客户端只做了工具。

只有工具一种

  • 简单，所有客户端都支持。
  • 每样东西的定义都进每一轮的工具清单，清单越长，模型越容易挑错、越贵。
  • “读手册”“按流程走”都变成模型的判断，你只能在提问里求它去调。
决定胜负的约束：模型的上下文和注意力是整条链路里最贵的东西，而“要不要用”这个决定交给模型，就多一次犯错的机会。所以凡是不必由模型临场决定的，都不该进工具清单。

读出来的结论
  • 工具的定义是“常驻成本”：3 个工具 1356 B，不管这一轮用不用，都跟着每次调模型发出去。手册做成资源，不读就一个字节都不花。
  • 返回 pydantic 模型就有了 outputSchema 和 structuredContent；为了照顾只看文字的客户端，SDK 还把同一份数据以 JSON 文字放进 content。返回 str 的工具也有一个 outputSchema（包成 {"result": …}）。
  • 出错时，模型能不能自己改正，取决于服务端有没有把原因写成人话：ToolError 能，没接住的异常不能。
  • SDK 和规范有两处对不上：不存在的工具回成了 isError，缺模板参数回了 -32603。客户端两种情况都要能处理。

⑥细节

第一圈 · 注意事项

1没接住的异常，模型只看到“出错了”实测← ④ 机制 2
现象
模型传了一个坏正则，结果只有一句 “Error executing tool search_logs”。它不知道是正则写错了，换个说法再调一次，还是错，白白多绕几轮。
根源
工具执行错误要以 isError 结果回给模型，内容就是它改正的唯一线索。SDK 对没接住的异常只回笼统的一句（为了不把内部细节漏给对面），详情只写在服务端日志里。
做法
能预料的失败都换成 raise ToolError("正则写错了：缺右括号，例如应写成 耗时\\(")：说清哪里错、正确的样子。
2按规范写客户端，碰上 SDK 的另一种回法实测← ④ 机制 2
现象
你的客户端只在 error.code == -32602 时提示“没有这个工具”，碰上 mcp 2.3.0 的服务端，收到的却是一个 isError 结果；缺模板参数时收到 -32603。
根源
规范把“不存在的工具”“缺必填参数”归为协议错误，实现没完全照做。这类不一致在一个刚改版的协议里很常见。
做法
客户端两条路都处理：协议错误和 isError 结果都要能展示给人、也能交给模型。服务端那边，自己检查参数，主动回清楚的错误。
3看到 readOnlyHint 就自动放行← ④ 机制 2
现象
主机写了条规则：“标了只读的工具不用问人”。一个第三方服务端把 delete_index 也标成了 readOnlyHint: true。
根源
annotations 是服务端自己写的提示，协议不验证。规范原话：除非来自可信的服务端，客户端必须把它们当作不可信。
做法
放行规则写在主机自己的配置里（Claude Code 的 permissions.allow），按“服务端 + 工具名”放；annotations 只拿来做界面提示。第 6 页细讲。
4以为做成资源，模型就会自动看到← ④ 机制 1
现象
把值班手册做成资源以后，模型排障时从来不按手册的顺序走。
根源
资源由应用控制：主机决定什么时候把它放进上下文。Claude Code 的做法是你用 @ 点名，或者模型自己想到去调读资源的工具；两样都没发生，手册就不在上下文里。
做法
每次都要遵守的流程，做成提示词模板（你一点就带上），或者写成 Skill（第 7 页）；资源留给“需要时才翻”的材料。

第二圈 · 使用规范

  • 工具名用“动词_名词”：search_logs、add_comment，只用字母、数字、_ - .。防的是：名字看不出动作，模型挑错；带空格、中文的名字有的客户端直接拒收。
  • 只读的工具就标只读：read_only_hint=True，会改东西的标 destructive_hint。防的是：界面没法提示你哪些调用要多看一眼。它是提示不是保证，坑 3 说过。
  • “有无数份”的东西做成资源模板：oncall://gc-log/{date}、tickets://incident/{id}。防的是：做成一个 get_xxx(id) 工具，又多一个常驻的工具定义。
  • 大结果不要整个塞回去：日志超过 20 行就截断并说明，或者在工具结果里放一个 resource_link，指向完整内容的资源。防的是：一次结果塞满上下文（全景第 10 站）。
  • 列表的顺序固定：规范要求 tools/list 顺序确定。防的是：顺序一变，发给模型的工具前缀就变，提示缓存命中不了（站 03 提示缓存）。

第三圈 · 优化和深处

structuredContent 什么时候值得用

结果要给程序继续处理（主机画图、下一个工具接着用、评测脚本对答案）时用：有 outputSchema，客户端能校验、能直接取字段。只给模型读的结果，文字就够；结构化结果对模型并不更好读，反而因为同时放了两份，多花一点 token。

参数补全：completion/complete

模板和资源模板的参数，服务端可以提供补全：你敲 /mcp__oncall__triage o，客户端发 completion/complete，服务端回 ["order-svc"]，一次最多 100 个，按相关度排序。服务端要在能力里声明 completions。

列表可以缓存了（2026-07-28）

新协议要求 tools/list、resources/list、resources/read 等结果带 ttlMs 和 cacheScope：客户端可以缓存多久、能不能跨用户共享（private 就是不同令牌之间不能共享）。全景页实测的 oncall 回的是 ttlMs: 0、private，也就是“别缓存”。

资源的注解给主机用

audience: ["user"] 表示这份内容是给人看的、别塞给模型；priority 0～1 表示多重要，主机挑上下文时可以参考；lastModified 帮主机判断要不要重读。这些都是服务端写的，主机按自己的规则决定信不信。

自测

1. 用一句话说出三种能力怎么分

看谁决定什么时候用：模型临场决定的做工具，应用或你决定附上的数据做资源，你主动发起的固定话术做提示词模板。

2. “全做成工具”的老办法，疼在哪？

每样东西的定义都常驻工具清单，每一轮都付 token、稀释模型的注意力；本该你拿主意的事（按不按手册走）变成了模型的判断，你只能在提问里求它去调。

3. 头号坑“模型只看到 Error executing tool”，根源是哪条？

④ 机制 2：工具执行错误以 isError 结果回给模型，内容是它改正的唯一线索；SDK 对没接住的异常只给笼统的一句，原因必须由你用 ToolError 写出来。

4. 预测：把值班手册从提示词模板改成资源，什么都不做，排障时模型会按手册走吗？

多半不会。资源要你 @ 点名或模型主动去读才进上下文；没人这么做，手册就不在。模板是你一点就展开的，每次都在。

从 ④ 机制 1（谁按按钮）推出。

5. 预测：给 oncall 加 30 个 get_incident_xxx 这样的“按编号取一份东西”的工具，和改成一个资源模板 tickets://incident/{id} 比，每一轮调模型差在哪？

30 个工具的名字、说明、schema 每一轮都跟着发（⑤ 里 3 个工具就有 1356 B），模型还要在一堆相似的工具里挑；资源模板不进工具清单，不读不花钱。代价是模型要读它得通过主机的读资源工具，或者由你点名。

从 ⑤ 的实测和 ④ 为什么这样设计推出。

6. 放回全景：第 5 站前后各发生了什么？如果第 5 站只列了工具、没列资源和模板，整条链路会怎样？

前面是第 4 站协商出对方有哪些能力，后面是第 6 站把工具说明装进上下文。只列工具时，排障照样能跑：第 6～10 站都只用工具。损失的是你那一侧：@ 里看不到值班手册，也没有 /mcp__oncall__triage 这个命令，按手册排障只能靠你自己打字。

从全景第 4～6 站和 ④ 机制 1 推出。
