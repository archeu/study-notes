多租户、权限、审计、脱敏

三个团队共用一个值班助手，模型却是同一个，它分不清“这是谁的数据”。精华是一句话：“谁在问”要由代码一路带到每一个取数据的地方，在那里检查，而不是交给模型判断。具体是四件事：租户标签跟着请求走到底；工具用提问者的范围取数据，不用 agent 自己的大权限；知识库在检索那一步就按租户过滤；审计只记元数据、首尾相扣改不了；脱敏放在知道字段含义的地方。

这一页的位置站 10 第 7 个下钻知识点。上一页的结论是“识别不全，靠权限兜底”，这一页就是那个兜底：权限具体放在哪、怎么带过去。AI 网关那页的工具白名单和脱敏是第一道，这一页讲执行处的最后一道。

①为什么需要：一个助手，三个团队的数据

在全景第 ①、⑤、⑧ 站，这一步要解决：接入服务认出“这是支付团队的告警”，可到了 worker 里，调查要查日志、搜知识库、建工单，每一步都在碰数据。支付团队的调查不该读到交易团队的日志，搜索团队的人不该在知识库里搜到支付团队记下的应急账号；谁在什么时候让 agent 做了什么，要查得到、改不了；手机号、卡号不能原样出公司。

②没有它会怎样：一个大权限的服务账号，加一句“只查自己的”

最省事的写法：worker 用一个能读所有日志、所有笔记的服务账号；系统提示里写一句“只查当前团队的数据”。⑤ 里把同样的工具提议交给这种执行器：

  • 支付团队的调查，模型提议 search_logs(order-04)（交易团队的机器）：执行器照查不误，交易团队的日志进了支付团队的报告。模型为什么会这么提议？可能是推理走偏，也可能是上一页那种注入。
  • 搜索团队搜“pay-02 连接池”：知识库把支付团队的笔记整条交了出来，里面有一个应急账号和密码。
  • “只查自己的”写在提示词里，是在请模型遵守权限；模型会被说服，也会出错，这句话没有任何强制力。
  • 换成按租户收紧的执行器：第一个直接拒绝（order-04 不属于 pay），第二个什么也没搜到。工具提议一模一样，交出去的数据不一样。
不懂精华时的典型误用：把权限检查放在模型前面（“我在提示词里告诉它了”）或者只放在入口（“接入服务验过 token 了”），而真正取数据的那一步用的是 agent 自己的大权限。这在安全里有个名字：糊涂的代理人。

③相邻方案：隔离到什么程度，用谁的身份

做法隔离强度成本适合
每个团队一套部署（独立网关、worker、知识库）最强：数据物理分开三套机器、三套运维，额度也要分三份合规要求硬隔离的客户（私有化）
共享一套，每一层带租户标签、在取数据处检查强：只要每个取数据的点都查一套部署公司内部的几个团队：全景这一夜
共享计算、按团队分数据（各自的知识库索引、各自的工单项目）较强：查错了也只是查不到中等数据量大、团队多
只在入口验身份，后面全用服务账号弱：入口之后谁都能读所有数据最省事不适合，② 就是它

另一条轴是“工具用谁的身份去取数据”：用 agent 自己的服务账号（一个大权限），还是代表提问的人（拿他那个团队、那个角色的范围；站 07 的 MCP 的 OAuth 讲过“代表用户去调”）。

本页学共享部署 + 租户标签一路带下去 + 工具代表提问者取数据：检查放在每个取数据的地方（日志按机器归属、知识库按笔记归属、工单按项目），而不是只在入口或提示词里。合规要求硬隔离时，再升级到每个团队一套部署。

④原理：“谁在问”是一条要一路带下去的线

先知道这些
  • 租户、角色：租户是“哪个团队”，角色是“这个团队里的什么人”（只读、值班、负责人）。权限 = 团队能用的 ∩ 角色能用的。
  • RBAC：按角色给权限，Spring Security 那一套。补给页：Spring Security 认证与授权。
  • 检索时过滤：知识库按元数据（属于哪个团队）在检索那一步就过滤掉，站 06 的 RAG 流水线 讲过元数据。

机制 1 · 租户标签跟着请求走到底

跟着支付团队的一个事件走一遍，看“谁在问”这条线在每一站是怎么带过去的、在哪里被检查。

准备点“下一步”。

两处最容易断：一是跨进程，租户要写进任务消息和检查点，worker 从这里读，不靠“记得”；二是跨线程。Python 的 contextvars 在 create_task 和 asyncio.to_thread 里会跟着走，在 loop.run_in_executor 里不会（⑤ 实测：线程里拿不到租户，直接 LookupError）。Java 的 ThreadLocal 进线程池也一样丢，要靠 TaskDecorator 或 TransmittableThreadLocal 带过去（补给页 Spring @Async 与线程池）。

机制 2 · 糊涂的代理人：用提问者的范围取数据

agent 是一个“代理人”：它替支付团队去查数据。如果它手里拿的是能读所有机器的服务账号，那么谁能让它提议一次 search_logs(order-04)（推理走偏、或者一句注入），谁就借到了它的大权限。解法是让工具按提问者的范围取数据：执行器从上下文拿到 tenant=pay，先查“order-04 属于谁”，不是 pay 就拒绝；更彻底的是每个团队一组只读凭据，或者像站 07 那样拿代表用户的令牌去调。

机制 3 · 过滤放在检索那一步，缓存键里带租户

知识库是三个团队混在一起的。“先全搜出来，再让模型别提别人的”不行：笔记已经进了上下文，模型可能复述，注入可能把它引出去。过滤要在检索那一步做（按笔记的 tenant 元数据），模型根本见不到别人的笔记。同样的道理适用于一切缓存：结果缓存、网关的响应缓存，键里必须有租户，否则 A 团队查过的结果，B 团队同样的问题会直接命中。

机制 4 · 审计：首尾相扣，只记元数据

每次工具调用记一行：时间、团队、用户、工具、参数、结果是放行还是拒绝、结果的哈希。每一行再带上上一行的哈希，像链条一样扣起来：有人想把一次越权从 denied 改成 ok，被改的那一行内容变了，下一行记着的“上一行哈希”就对不上（⑤ 实测：改第 2 行，校验在第 3 行断开）。要藏住篡改，就得把后面每一行都改掉，所以最后一行的哈希要定期存到改不了的地方。审计里不记原文，只记哈希，否则审计日志自己就成了泄露源（网关那页的坑 8）。

机制 5 · 脱敏放在知道字段含义的地方

网关只能对着自由文本猜：16 位以上的数字都当卡号，于是 trace 4111111111111111 被误打码，而带空格的 6222 0202 0011 2233 446 原样出了门（⑤ 实测）。工具那一侧知道日志格式：卡号要过 Luhn 校验位、trace 后面的数字不动、手机号留前三后四方便核对。两层都要：工具侧负责准，网关负责兜底。需要原文的场景（比如人工核对退款），用可逆的令牌：上下文里只放 card_tok_8f2a，原文存在只有授权的人能换回的地方。

为什么这样设计

每个取数据的地方都按“谁在问”检查

  • 模型被骗、被带偏，提议了越权的调用，到执行器这里也会被拒。
  • 检查是确定的代码，和提示词怎么写无关；可以单元测试（⑤ 的 test_tenancy.py）。
  • 代价：每类数据都要标归属（机器、笔记、工单项目），租户要穿过进程和线程。

入口验一次，后面信任模型

  • 代码最少，入口有 Spring Security 一样的东西就算“有权限”了。
  • 入口之后，所有取数据的动作都由模型提议、用大权限执行，任何一次走偏都是越权。
  • 提示词里的“只查自己的”没有强制力，也测不了。
决定胜负的约束：决定“下一步取什么数据”的是一个会被说服、会出错的模型。凡是由它提议的动作，都必须在执行的地方用确定的代码重新检查一次“谁在问、能不能给”。

Java 老朋友：租户拦截器和 ThreadLocal

像：MyBatis-Plus 的 TenantLineInnerInterceptor、Hibernate 的 @Filter 给每条 SQL 自动加 tenant_id = ?，就是“过滤放在取数据那一步”；租户放在 ThreadLocal 里一路带，进线程池要 TaskDecorator。@PreAuthorize 对应执行器里的角色检查。

不像：Java 里决定调哪个 DAO 的是你写死的代码；这里决定调哪个工具、传什么参数的是模型，所以“参数里的租户”不能信，只能信上下文里的。

⑤亲眼看到：同一个工具提议，两种执行器交出了什么

没有模型：模型“提议”的工具调用（就是 tool_use 块里的 name 和 input）直接写在 demo.py 里，因为要看的不是模型会不会提议，而是提议了以后执行器交出什么。每个提议都交给两种执行器各跑一次：不分租户（大权限服务账号）和按租户收紧。

读出来的结论
  • 实验 1、2 的提议一模一样，差别全在执行器：大权限的服务账号把交易团队的日志、支付团队的应急账号原样交了出去。
  • 实验 3：权限 = 团队能用的 ∩ 角色能用的。负责人能提 heap_dump，但也只是“提”，接下来要人批。
  • 实验 4：网关式正则一处误伤（trace 号被打码）、一处漏网（带空格的卡号原样出门）；工具侧按字段脱敏两处都对。
  • 实验 5：改的是第 2 行，断在第 3 行，因为第 3 行记着第 2 行原来的哈希。
  • 实验 6：租户上下文在线程池里丢了。这种 bug 不会报错，只会让某个工具“以没有租户的身份”去查，最危险的是代码里拿不到租户时回落成“不过滤”。
到这里已经能交差了：租户从上下文取、在每个取数据的地方检查，知识库检索时就过滤，审计首尾相扣，脱敏在工具侧按字段做。
已知还没处理的细节：缓存键漏了租户（坑 3）；模型传来的租户参数（坑 5）；应用日志里的原文（坑 8）。

⑥细节

第一圈 · 注意事项

1服务账号能读所有团队的数据实测← ④ 机制 2
现象
支付团队的报告里出现了交易团队机器的日志。
根源
工具用的是 agent 自己的大权限，谁能让它提议一次，谁就借到了这份权限。
做法
执行器按提问者的范围检查（机器归属）；能做到的话每个团队一组只读凭据，或者用代表用户的令牌。
2知识库先全搜、再让模型别提实测← ④ 机制 3
现象
搜索团队的人问了一句，拿到了支付团队的应急账号。
根源
过滤放在了模型后面；笔记一旦进了上下文，就可能被复述或被注入引出去。
做法
检索时按 tenant 元数据过滤（向量库的过滤条件）；密码一类的东西根本不该进知识库，进密钥库。
3缓存键里没有租户← ④ 机制 3
现象
两个团队问了同一句话，后问的那个拿到了前一个团队的结论和证据。
根源
结果缓存按“问题文本”做键，没带租户。
做法
所有缓存（检索结果、工具结果、网关响应）的键都以租户开头；写个测试专门测“同一问题、不同租户”。
4租户上下文进线程池就丢了实测← ④ 机制 1
现象
大部分工具正常，偏偏放进线程池跑的那个（比如同步的 SDK 调用）拿不到租户。
根源
run_in_executor 不复制 contextvars；Java 的 ThreadLocal 进线程池也一样。
做法
用 asyncio.to_thread 或 contextvars.copy_context().run(...)；拿不到租户时拒绝，绝不回落成“不过滤”。
5让模型在工具参数里传租户← ④ 机制 1
现象
工具定义里有个 tenant 参数，模型被日志里的一句话骗着填了 trade，于是查到了交易团队的数据。
根源
参数是模型写的，等于让被检查的人自己填身份。
做法
工具定义里不暴露租户和用户；执行器只从上下文取。
6审计能被改，或者记了原文实测← ④ 机制 4
现象
出事以后翻审计，关键那一行写着 ok；或者安全检查在审计里翻出了几千个手机号。
根源
普通的日志文件谁都能改；为了排查方便把请求体整个记了下来。
做法
每行带上一行的哈希，最后一行的哈希定期存到只追加的地方；审计只记元数据和内容哈希。
7脱敏只靠网关的正则实测← ④ 机制 5
现象
trace 号被打成了卡号，带空格的真卡号却出了门。
根源
自由文本里只能按形状猜。
做法
工具侧按字段脱敏（Luhn、号段、字段名）；网关的正则留作兜底；要原文的地方用可逆令牌。
8应用日志和 trace 里有原文← ④ 机制 5
现象
上下文、审计都干净，worker 的应用日志里却把每一个 tool_result 整个打印了出来，日志平台所有人可见。
根源
调试时加的一行 logger.info(result)；追踪系统（站 09）默认也会记下输入输出。
做法
应用日志只记长度和哈希；追踪系统对输入输出做同样的脱敏，或者只在单独授权的环境里开。

第二圈 · 使用规范

  • 租户写进任务消息和检查点，worker 从这里读：防跨进程时丢。
  • 执行器从上下文取租户，拿不到就拒绝：防线程池里静悄悄地“不过滤”。
  • 每类数据都标归属，检查放在取数据的那一步：防糊涂的代理人。
  • 知识库检索时过滤，缓存键以租户开头：防跨团队串数据。
  • 审计首尾相扣、只记元数据：防改记录、防审计本身泄露。
  • 脱敏在工具侧按字段做，网关兜底：防误伤和漏网。

第三圈 · 优化和深处

数据库里的行级安全

检查点、调查结果放在 Postgres 时，可以开行级安全（RLS）：每个连接先 SET app.tenant = 'pay'，策略规定只能看到 tenant = current_setting('app.tenant') 的行。哪怕某处代码忘了加 WHERE，也查不到别人的。

一个索引加过滤，还是每个团队一个索引

知识库共用一个向量索引、按元数据过滤，最省；但过滤和近似最近邻一起用时，召回可能下降（站 06 讲过 HNSW 的过滤问题）。团队少、数据多时，每个团队一个索引既快又隔离得干净。

可逆令牌和加密

需要原文的场景（退款核对），用令牌化：上下文和日志里只有 card_tok_8f2a，原文在一个单独授权、单独审计的服务里，换回原文的每一次都记一笔。再往上是每个团队一把数据密钥。

合规：留多久、出不出境

审计和调查记录留多久、能不能发到境外的供应商，是法务和合规定的规则，不是技术选择。网关那一层可以按租户强制“这个团队只能用境内部署的模型”，和下一页的私有化接上。

自测

1. 用一句话说出这一页的精华

“谁在问”由代码带着走到每一个取数据的地方并在那里检查：租户从上下文取，工具按提问者的范围取数据，知识库检索时就过滤，审计首尾相扣，脱敏在知道字段的地方做。

2. 入口已经验过 token 了，为什么还会越权？

入口之后，取数据的动作由模型提议、用 agent 的大权限执行；模型走偏或被注入一次，就是一次越权。这叫糊涂的代理人。

从 ④ 机制 2 推出。

3. 为什么知识库要在检索时过滤，而不是让模型别说？

笔记一旦进了上下文，就可能被复述、被注入引出去；提示词没有强制力。检索时过滤，模型根本见不到。

从 ④ 机制 3 推出。

4. 预测：审计改了第 5 行（共 8 行），校验会在第几行断？如果连第 6～8 行也一起重算了哈希呢？

第 6 行：它记着第 5 行原来的哈希。如果第 6～8 行都重算了，文件内部又对得上了；能发现，靠的是事先存到别处的“最后一行哈希”和现在的对不上。所以哈希链要配一个改不了的锚点。

从 ④ 机制 4 推出。

5. 预测：执行器里写成“拿不到租户就不过滤”，实验 6 那种情况会怎样？

放进线程池跑的那个工具拿不到租户，就按“不过滤”执行，相当于自动换成了大权限的服务账号：查得到所有团队的数据，而且不报任何错。正确的回落是拒绝。

从 ④ 机制 1、2 推出。

6. 放回全景：租户是在第 ① 站认出来的，它要经过哪几站才到第 ⑧ 站？哪一站丢了会怎样？

第 ① 站从 token 认出租户，写进第 ② 站的任务消息；第 ③ 站 worker 读出来放进上下文、写进检查点；第 ⑤ 站网关按虚拟 key 再认一次、选白名单；第 ⑧ 站执行器从上下文取它检查。第 ② 站的消息里没写，worker 就不知道这是谁的事件；第 ③ 站的线程里丢了，执行器要么拒绝（对），要么不过滤（越权）。

从全景第 ①②③⑤⑧ 站和 ④ 机制 1 推出。

档位：标准。本机跑过（2026-11-28，Python 3.13.18）：⑤ 的 6 个实验和 3 个测试。按 Python 文档：asyncio.to_thread 和 create_task 会复制当前的 contextvars，loop.run_in_executor 不会（实验 6 和它一致）。Luhn 校验位、哈希链是通用做法；MyBatis-Plus 的租户插件、Hibernate 的 @Filter、Postgres 行级安全只做了对照，没有在本页实测。
