记忆怎么忘：衰减、过期，按用户隔离和隐私

“忘”是三件不同的事，要分开做：有寿命的（临时安排）到点删；经历降权、归档，不轻易删，因为它是唯一的一份，删了没处找回；隐私和别的团队的东西，根本不该被看到：写入时脱敏、夜里再扫，读取时永远带团队条件。本机模拟 90 天：一刀切“30 天全删”把 85 天前那次 P0 删了；只在写入时脱敏，40 个手机号还剩 18 个；漏一个团队条件，34 条别组的记忆就进来了。

全景：第二天再问同一个服务 · 第 9、2 站地图：站 05 · 记忆怎么忘：衰减、过期，按用户隔离和隐私深度：懂设计

这一页的位置记忆怎么写管进来，记忆怎么取管挑出来；这一页管出去，以及谁能看到。下一页用评测检查这三件事有没有做对。

①要解决的问题：每晚 02:00，记忆表要瘦身、要干净

在全景第 9 站，每晚 02:00 的任务要做三件事：删掉过期的（“下午找备班”）、给很久没用的降分不删、抹掉日志里带出的客户手机号。在第 2 站，记忆永远按 team 存、按 team 取。

②不用它会怎样：什么都不忘

⑤ 的模拟：交易组 90 天写入 298 条记忆，其中 40 条日志片段带着客户手机号。什么都不做，到 11-09 凌晨：

  • 298 条全在，表只会越来越长；召回时要和 44 条“两个月前、不重要”的旧病历竞争名额（上一页的打分会把它们排后，但它们一直在占计算和候选位）。
  • 26 条早已过期的临时安排还在。“下午 3 点前找备班”一周后再被取到，会被当成长期安排。
  • 40 个客户手机号原样躺在记忆里，任何一次召回都可能把它放进上下文、进模型、进日志。
  • 召回时只要漏写一次团队条件，交易组的人就能看到 34 条风控组的记忆（⑤ 实测）。
不懂精华时的典型误用：把记忆当缓存，给所有记录配一个统一的 TTL。缓存删了能回源重建，记忆删了就再也没有了：⑤ 里“30 天全删”把 85 天前那次 P0 大事故也删了，而那恰恰是最该记住的。

③几种流派：什么时候、按什么忘

要求永不忘统一 TTL（像 Redis expire）满了才淘汰（像 LRU / LFU）按类型分策略：过期 + 衰减归档 + 脱敏
表不会无限长不能：298 条只增不减能：剩 91 条能：到上限就删能，但慢：259 条 + 13 条归档
大事故、规矩不丢能不能：P0 被删了差一点：很久没被用到的 P0 会被淘汰能：重要的不归档，规矩不自动忘
临时安排准时消失不能：26 条过期的还在差一点：30 天后才删不能：不看寿命能：按各自的 expires 删
隐私不留不能：40 个手机号差一点：最近 30 天的还在不能能：写入脱敏 + 夜里扫，残留 0
出了问题能回查能不能：删了就没了不能能：冷表可查，删除留记录

本页用“按类型分策略”：有寿命的按寿命删，经历只降权和归档，隐私和隔离不靠“忘”而靠“不让看到”。规则一句话：删除只用在“必须消失”的东西上（到期、隐私、被要求删除）；其余的，让它排在后面就够了。

④核心取舍：该消失的准时消失，该留的降权不删

先知道这些
  • Redis 的过期和淘汰：过期是给 key 定寿命（惰性删除 + 定期删除），淘汰是内存满了按 LRU / LFU 挑一批删。见 Redis 过期删除与内存淘汰。
  • 召回打分里的新近项：越久分越低，见 记忆怎么取。

Java 老朋友：记忆系统 ≈ 缓存 + 淘汰策略。TTL、惰性加定期清理、按热度淘汰，你在 Redis 里都见过。不像的地方决定了设计：缓存是数据库的副本，删了能回源重建，所以可以大胆删；记忆是那次经历唯一的一份，删了就没了，所以默认是“降权”而不是“删除”。反过来，缓存里很少有“必须删”的东西，记忆里却有：过期的安排、客户的手机号、被要求删除的内容。

机制 1 · 过期：给“有寿命”的东西写好寿命

  • 寿命在写入时定：临时记忆必须带 expires（上一页的写入流水线没有它就不写）。情景、语义、规矩没有寿命。
  • 两道保险：夜里的任务删掉 expires <= now 的；白天召回也带 expires > now 的条件，防夜里那次没跑或还没到 02:00。和 Redis 的“定期删除 + 惰性删除”一个思路。

机制 2 · 衰减和归档：排在后面，而不是消失

  • 衰减在召回时发生：上一页的新近项本身就是衰减，越老越排后，不用改表。
  • 归档才改表：本页规则是“衰减分（重要性 × 0.5天数/30）低于 0.05、重要性低于 7、30 天没被用过”三条同时满足，才挪进冷表。冷表默认不参加召回，但能查、能恢复。
  • 两种东西不参加衰减：重要性高的（P0 事故）和规矩。规矩只能由人撤销。
  • 代价：表瘦得慢。⑤ 里 90 天只归档了 13 条；门槛松一点能多归档，但越松越可能把以后用得上的挪走。

机制 3 · 隐私和隔离：不靠“忘”，靠“看不到”

  • 最好不进来：写入时脱敏（手机号、身份证号、邮箱换成占位符），只记排障需要的信息，这就是“最小必要”。
  • 漏进来的夜里扫：写入时的规则要快、要保守，夜里可以用更宽、更慢的规则再扫一遍。⑤ 里写入时只认 11 位连写，“138-1234-5678”这种带横线的写法全漏了，40 个里剩 18 个；夜里那遍补上了。
  • 被要求删除时删干净：原条目、合并出来的条目、摘要、向量、操作日志里的副本都要找到。所以上一页说的“每次写入记操作日志、带来源”在这里派上用场。
  • 隔离是读的条件，不是删的对象：每一次读都带 team。只写在应用代码里，漏一处就全漏；更稳的是在数据库这一层强制（PostgreSQL 的行级安全策略，或者按团队分库）。

为什么这样设计：两股方向相反的力

按类型分策略，降权多于删除

  • 经历不可回源，所以只降权、只归档；大事故和规矩永远在。
  • 必须消失的（过期、隐私、删除请求）用专门的机制准时、彻底地删。
  • 代价：三套机制、两张表、一份操作日志；表瘦得慢。

统一 TTL

  • 一行配置，表的大小可预期。
  • 价值不随时间均匀下降：85 天前的 P0 比昨天的误报值钱得多，统一 TTL 先删它。
  • 对隐私又太慢：手机号要在第 30 天才消失。
决定胜负的约束：一股力要“留”：经历只有一份，价值不随时间均匀下降。另一股力要“删”：过期安排会误导，个人信息不能留，别人的东西不能看。一个统一的 TTL 同时满足不了两边，所以拆成三个机制，各管一边。

def nightly(db, now):
    db.execute("DELETE FROM memories WHERE kind='temporary' "
               "AND expires <= ?", (now,))                 # 过期
    for mid, imp, created, last_used in episodic(db):
        score = imp / 10 * 0.5 ** (age(created, now) / 30)
        if score < 0.05 and imp < 7 and idle(last_used, now) > 30:
            move_to_archive(db, mid)                          # 归档，不删
    for mid, text in all_rows(db):                            # 隐私：宽规则再扫
        db.execute("UPDATE memories SET text=? WHERE id=?",
                   (PHONE_WIDE.sub("[手机号已脱敏]", text), mid))

三个问题分辨该用哪个

它有没有寿命？有：过期。

它还值不值得想起？越来越不值：衰减、归档。

它该不该被这个人看到？不该：隔离和脱敏，跟时间无关。

⑤套进场景：同样 90 天，四套策略

用 SQLite 在内存里模拟值班助手的记忆表：2026-08-11 到 11-08，交易组每天写 2～4 条病历，三成多的日子有一条临时安排（一到三天后过期），约一成二的病历里带着日志片段里的客户手机号（四成写成 138-1234-5678 这种带横线的格式），第 6 天有一次 P0，第 21 天有一条规矩；风控组也在同一张表里。每晚跑一次遗忘任务，11-09 凌晨看结果。不需要模型，不到一秒。

读出来的结论
  • 一刀切最省地方，也最危险：表只剩 91 条，但 85 天前那次 P0 没了；最近 30 天写进来的手机号还在（3 个）。
  • 写入时的脱敏规则不够：只认 11 位连写，带横线的 18 个漏网。夜里用更宽的规则再扫一遍才清零。
  • 本页做法表瘦得慢：只归档了 13 条，“两个月前、不重要”的病历还有 31 条在活跃表里。这是故意的保守：它们在召回时本来就排在后面，挪走它们的收益小，挪错的代价大。
  • 隔离和“忘”无关：风控组的 34 条一条都没删，也不该删；只要读的时候带上团队条件，交易组就看不到。
到这里已经能交差了：临时记忆按 expires 删，情景记忆只在“分数低、不重要、久没用”时归档，写入时脱敏、夜里再扫，读取永远带团队条件。
已知还没处理的细节：统一 TTL 删掉大事故（坑 1），脱敏规则漏格式（坑 2），隔离只写在应用层（坑 3），删除请求删不干净（坑 4），只靠夜间任务（坑 5），规矩被自动忘掉（坑 6）。

⑥反例和误用

第一圈 · 注意事项

1给所有记忆一个统一的 TTL实测← ④ 机制 2
现象
⑤ 里 30 天全删：85 天前那次 P0 没了；下次再有人发布时动 DDL，助手不知道“上次锁表导致全量下单失败 40 分钟”。
根源
经历的价值不随时间均匀下降，而且不可回源。时间只该影响排序，不该单独决定删不删。
做法
TTL 只给有寿命的临时记忆；情景记忆只归档不删，重要性高的不归档。
2写入时的脱敏规则漏格式实测← ④ 机制 3
现象
⑤ 里 40 个手机号剩 18 个，全是“138-1234-5678”这种写法。
根源
写入路径要快，规则往往只覆盖最常见的格式；个人信息的写法千奇百怪（带横线、空格、全角数字、拆成两段）。
做法
写入时一道、夜里一道更宽的；脱敏规则本身也要有测试用例；能不记的字段干脆不记（日志片段只留错误码，不留原文）。
3团队隔离只写在应用代码里实测← ④ 机制 3
现象
⑤ 里漏写一次条件，交易组就看到 34 条风控组的记忆；新加的一个“按服务查记忆”的接口正好忘了写。
根源
隔离是“每一次读都要满足”的约束，靠每个开发者在每条 SQL 里记得写，迟早漏。
做法
在数据库这一层强制：PostgreSQL 开行级安全（ENABLE ROW LEVEL SECURITY + 按 team 的 POLICY），注意表的属主默认不受约束，要加 FORCE ROW LEVEL SECURITY；或者按团队分库、分 schema。召回结果再加一道断言。
4删除请求只删了原条目← ④ 机制 3
现象
客户要求删除自己的信息，记忆表里那条删了，但它早被合并进另一条病历、写进过一份摘要、向量还在索引里。
根源
记忆会被合并、摘要、复制；不记来源，就找不到它的“后代”。
做法
每条记忆记来源（从哪次会话、由哪几条合并而来）；删除按来源链一起找；向量索引里同步删除或标记；删除本身记一条审计日志（只记“删了什么类型、为什么”，不记内容）。
5过期只靠夜里那次任务← ④ 机制 1
现象
15:00 过期的“找备班”，到夜里 02:00 之前一直会被取到；某天夜里任务失败，它又活了一天。
根源
删除是定时做的，过期是随时发生的，中间有空窗。
做法
召回时也带 expires IS NULL OR expires > now；夜里的任务只负责真正把它清出去。和 Redis 的惰性删除加定期删除一样。
6规矩衰减到 0 被自动删了← ④ 机制 2
现象
全景里说的反例：一条半年没被用到、但很要紧的规矩“支付服务禁止重启”悄悄消失了。
根源
规矩的价值在于“该用的时候一定在”，平时用不到正说明它在起作用；按使用频率衰减它，方向是反的。
做法
程序性记忆不参加衰减和归档，只能由人显式撤销；撤销也进历史。

第二圈 · 使用规范

  • 每条记忆写清：类型、团队、来源、寿命（有就写）、重要性：遗忘任务的每个判断都靠这几个字段。
  • 删除只用于：过期、隐私、删除请求；其余只归档：防“删了才发现还要用”。
  • 隔离在存储层强制，应用层再断言：防一个新接口漏写条件。
  • 遗忘任务也要有监控：每晚删了几条、归档几条、脱敏几处，突然变成 0 或暴涨都要告警。

第三圈 · 优化和深处

法规层面的“必须忘”（按法规原文的大意）

个人信息保护法要求处理个人信息“最小必要”，并在第四十七条列了应当主动删除的情形，比如处理目的已实现、保存期限已届满、个人撤回同意。对值班助手来说就是：客户手机号这类信息对排障没用，就不该进记忆；进了，就要能按请求删干净、能证明删了。具体合规要求以法务意见为准。

归档门槛怎么定

⑥ 的实验台可以看到：门槛越松，表越瘦，但被挪走的里面可能有以后用得上的。归档的代价是“下次要多一步去冷表查”，删除的代价是“永远没了”，所以归档可以比删除激进得多。真正的门槛要用评测来定：把冷表里的记忆拿回来，看召回质量有没有变好（下一页）。

先猜：只在写入时用正则脱敏（只认 11 位连写），不做夜间扫描，90 天后 40 个手机号还剩多少？

下一圈

  • 容量上限：每个团队最多 N 条活跃记忆，满了按衰减分挪走最低的，像 LFU。
  • 个人层级的隔离：值班的你说的规矩，换个人值班还算不算；按人、按团队、按全公司三层。
  • 向量库里的删除：软删除标记、定期重建索引，删除后多久才真正查不到。

↺回到⑤：改一改

  1. 召回时也过滤过期：给 recall 加上 expires IS NULL OR expires > now，再模拟“某天夜里任务没跑”，看过期临时会不会被取到。（坑 5）
  2. 加一个删除请求：随便挑一个模拟数据里的手机号，写 erase(db, phone)：活跃表、冷表都要删，返回删了几条，并写一条不含原文的审计记录。（坑 4）
  3. 换成 PostgreSQL 行级安全：用 Docker 起一个 PostgreSQL 17（postgres:17，做完删掉容器和镜像），给 memories 开 RLS，用 SET app.team = 'trade' 查一遍，再故意不带条件查，确认看不到风控组。（坑 3）

自测

1. 用一句话说出这一页的精华

“忘”分三件事：有寿命的到点删，经历只降权和归档（它不可回源），隐私和别人的东西靠“写入脱敏 + 夜里再扫 + 读时强制隔离”做到看不到；删除只用于必须消失的东西。

2. 什么都不忘，痛在哪？

表无限长、过期的临时安排被当成长期安排、客户手机号原样留着随时可能进上下文；再加上任何一处漏写团队条件，别组的记忆就能被看到。

3. 坑 1（统一 TTL 删掉 P0）的根源是哪条原理？

④ 机制 2：经历是唯一的一份、不可回源，而且价值不随时间均匀下降；时间只该影响排序和归档，不该单独决定删除。

4. 预测：把归档门槛从“衰减分 < 0.05”放宽到“< 0.3”，会发生什么？

重要性 5 的病历大约一个月就会掉到 0.25 以下，大量一两个月前的普通病历被挪进冷表，活跃表明显变瘦；但“同一个服务上个月也出过类似的事”这种线索会更常取不到。P0 和重要性 7 以上的仍然不受影响，因为还有“重要性低于 7”这一条。

从 ④ 机制 2 的公式（重要性 × 0.5天数/30）和三条同时满足的规则推出。

5. 预测：夜间脱敏任务把一条记忆里的手机号换成了占位符，这条记忆的向量要不要重算？

要。向量是按原文算的，原文里有手机号，向量里也编码了它的一部分信息；而且召回时用的是旧向量，和新文本对不上。脱敏、合并、更新之后都要重算向量，或者至少把旧向量删掉。

从 ④ 机制 3“删干净要找到所有副本”推出：向量也是一种副本。

6. 放回全景：第 9 站和第 2 站各和这一页有什么关系？这一页讲的东西坏了，整条链路会怎样？

第 9 站是每晚的遗忘任务：清过期的“找备班”、给旧病历降分归档、抹掉手机号。第 2 站是每次召回：永远带团队条件，并且也过滤掉过期的。坏了的走向：统一 TTL，第 2 站取不到那次 P0，第 7 站给不出“上次锁表”的提醒；过期没清，第 3 站把一周前的“找备班”放进上下文；脱敏漏了，手机号进了模型和日志；隔离漏了，第 7 站的答案里出现风控组的服务。

从全景第 2、3、7、9 站和本页 ④ 三个机制推出。

档位：标准。实测（2026-11-24，Python 3.13 自带的 sqlite3，内存库）：⑤ 的四套策略、隔离对比和实验台的 18 种组合，都是 memory-forget/main.py 对同一份 90 天模拟数据（固定随机种子）跑出来的。数据是假的，比例是设定的。按文档：Redis 的惰性删除和定期删除（见仓库 Redis 那页）；PostgreSQL 行级安全的 ENABLE / FORCE ROW LEVEL SECURITY 和表属主默认不受约束（PostgreSQL 文档）；个人信息保护法的最小必要原则和第四十七条应当删除的情形（法规原文大意，合规以法务意见为准）。
