Java 版：用 Spring AI ChatClient 写同一个服务

Spring AI 的 ChatClient 就是 Java 里的“模型抽象层”：业务注入 ChatClient.Builder，链式写 .prompt().system().user().call()；.entity(Triage.class) 直接拿结构化结果，.stream().content() 拿 Flux；用哪家模型由 starter 和 spring.ai.* 配置决定。实测同一份代码：Anthropic 模块连本机的 Claude 格式接口，文字、结构化、流式都通；只切配置到 OpenAI 兼容的另一个模型，应用照样启动、调用，可那个模型把推理过程写进了回答，entity() 三次全部解析失败。框架换得了接口，换不了模型的行为。

④原理：starter 装出一个 ChatModel，ChatClient 在它上面做文章

先知道这些
  • 自动装配：starter 带着 @AutoConfiguration 类，按类路径和配置条件创建 Bean（Spring Boot 自动配置）。
  • Reactor 的 Flux：一个会陆续发出多个元素的异步序列，blockLast() 等它结束。

机制 1 · 装配：starter → ChatModel → ChatClient.Builder

  1. 1 starterspring-ai-starter-model-anthropic 带来 AnthropicChatModel（2.x 里它包着官方 Anthropic Java SDK，⑤ 的依赖里就是 anthropic-java-core 3.8.0），读 spring.ai.anthropic.*：base-url、api-key、max-retries、chat.model、chat.max-tokens。
  2. 2 选一家两个模型 starter 都在类路径上时，spring.ai.model.chat=anthropic 或 openai 决定哪个 ChatModel 被装配，其余的不装（按 Spring AI 文档）。
  3. 3 ChatClient.Builder框架再装一个原型作用域的 ChatClient.Builder，业务注入它、设好默认 system 等，build() 出自己的 ChatClient。业务代码从头到尾不出现“Anthropic”或“OpenAI”。

机制 2 · 一次调用：链式拼 Prompt，最后一步才真正发请求

chat.prompt().system(…).user(…) 只是在拼一个 Prompt；.call() 也还没发，只是声明“要同步调”；到 .content()、.chatResponse()、.entity() 时才真正调用 ChatModel（按 Spring AI 文档）。ChatResponse 的 metadata.usage 就是站 03 一直在看的用量。中间可以挂 advisor（对话记忆、检索增强），像 AOP 的拦截链一样在请求前后加工。

机制 3 · entity()：在提示词后面加一段格式说明，再用 Jackson 解析

.entity(Triage.class) 会根据 record 的字段生成一段“请按这个 JSON Schema 输出”的说明附在提示词里，拿回文字后用 Jackson 解析成 Triage。这是 结构化输出那页的第 1 层和第 3 层（提示词 + 解析），默认不是约束解码，所以模型不听话时就解析失败（⑤ 的 OpenAI 那一轮）。对支持原生结构化输出的模型，文档给了 AdvisorParams.ENABLE_NATIVE_STRUCTURED_OUTPUT 这类开关，把 schema 交给服务端约束。

为什么这样设计：框架级的抽象和自己写的薄层，差在哪

Spring AI 的 ChatClient

  • 和 Spring 的配置、装配、profile 一体：换家就是换 starter 或 profile。
  • 记忆、检索、工具调用、观测都有现成的组件，站 04～06 会用到。
  • 代价：Claude 的新参数要等框架跟进；默认的结构化输出靠提示词，不是约束；出了问题要多看一层源码。

上一页的薄抽象层

  • 百来行，完全可控，各家特性直接透传。
  • 记忆、检索、工具、观测都要自己写；Java 项目里还要自己做配置绑定。
决定胜负的约束：在 Spring 项目里，“和现有配置、装配、监控体系融为一体”的价值很大，框架替你省下的代码远多于它挡住的特性；挡住的那部分（比如某个 Claude 新参数），可以在少数地方直接用官方 SDK 补上。

⑤跑起来：同一份 Java 代码，两份配置

  1. 1 依赖Spring Boot 4.2.0（spring-boot-dependencies 导入）、Spring AI 2.1.0（spring-ai-bom 导入），spring-boot-starter 加两个模型 starter：spring-ai-starter-model-anthropic、spring-ai-starter-model-openai。JDK 17。
  2. 2 默认配置spring.ai.model.chat=anthropic，base-url 指向本机 llama-server（它实现了 Claude 的 /v1/messages）。OpenAI 模块也在类路径上，用 spring.ai.model.embedding=none 等关掉它的其他模型类型，免得要 key。
  3. 3 换一家openai profile：spring.ai.model.chat=openai，base-url 指向本机第二个 llama-server（Qwen3-0.6B）。代码一行不动。
  4. 4 做三件事普通调用看用量；entity(Triage.class)，取值不合规就再要一次（最多 3 次）；stream().content() 记首段时间。
⑤TriageApp.java（核心）完整代码 →
@Bean
CommandLineRunner demo(ChatClient.Builder builder) {
    return args -> {
        ChatClient chat = builder.defaultSystem(SYSTEM).build();
        ChatResponse resp = chat.prompt().user(alert + " 用一句话回答是什么类型的问题。").call().chatResponse();
        print(resp.getResult().getOutput().getText(), resp.getMetadata().getUsage());

        for (int attempt = 1; attempt <= 3; attempt++) {
            try {
                Triage t = chat.prompt().user(alert).call().entity(Triage.class);
                if (t != null && t.valid()) break;          // 自己查取值范围
            } catch (RuntimeException e) { /* 解析失败，再来 */ }
        }

        chat.prompt().user(alert + " 用三句话说明排查步骤。").stream().content()
            .doOnNext(piece -> ...).blockLast();
    };
}

读出来的结论
  • 三件事都通：Anthropic 模块下，文字、entity()、Flux 流式都和 Python 版一样工作，用量里还带着 cacheReadInputTokens。（第一次的类别对了，cause 和 firstCheck 却是把告警原文抄了一遍：形状对、内容浅，和结构化输出那页一样。）
  • 换家只改配置：切 profile 后同一个 jar 连上了 OpenAI 兼容的另一家，业务代码没动。
  • 换家不等于换完：这个模型把推理过程写进了回答（175 个 token 里全是“好的，用户给了……”），entity() 的 Jackson 解析连败 3 次。这正是抽象层那页的误用 3：备用模型没在评测集上跑过。
  • 两个过程中撞上的坑（都写进了 ⑥）：用 spring.ai.openai.chat.extra-body 透传 enable_thinking: false，Spring 把它绑成了字符串 "false"，服务端回 400，换成 YAML 写也一样；删掉旧的配置文件后，target/classes 里还留着旧文件，没 clean 就还在生效。

⑥细节：用 Spring AI 时的坑

第一圈 · 注意事项

1配置里透传的参数，类型变成了字符串实测← ④ 机制 1
现象
spring.ai.openai.chat.extra-body.chat_template_kwargs.enable_thinking=false，服务端回 400：“expected boolean, got string”；改用 YAML 写 false 也一样。
根源
extra-body 绑定成 Map<String, Object> 时，配置值统一成了字符串，原样塞进请求体。
做法
需要布尔、数字这类有类型要求的透传参数，在代码里用选项对象设置（OpenAiChatOptions 等），或者把开关放到服务端；配置里只放字符串值。
2换了模型，entity() 全部解析失败实测← ④ 机制 3
现象
切到另一个模型后，回答前面多了一大段推理，Jackson 解析连败三次。
根源
entity() 默认靠提示词里的格式说明，模型不照做就失败；不同模型对同一份格式说明的服从度差很多。
做法
每个要用的模型都在评测集上跑过 entity() 的成功率；支持原生结构化输出的模型打开原生模式；解析失败要有带原因的有限次重试（结构化输出 ④）。
3Claude 的新参数，框架还没跟上← ④ 为什么这样设计
现象
想设 Opus 5.5 的 effort 或某个新的 beta 功能，Spring AI 的选项里找不到。
根源
框架要先抽象、再发版；而按 Claude 文档，Opus 5.5 还不接受 temperature，配置里的 spring.ai.anthropic.chat.temperature 要留空。
做法
先查当前版本的选项类有没有；没有就在少数调用处直接用官方 Anthropic Java SDK（Spring AI 2.x 里它本来就在类路径上）。
4两个模型 starter 同时在，启动报错或者装错← ④ 机制 1
现象
加了第二个 starter 后，注入 ChatClient.Builder 时出现多个候选，或者悄悄用了另一家；OpenAI 模块还要求给嵌入模型配 key。
根源
每个 starter 默认都会装配自己支持的所有模型类型。
做法
显式写 spring.ai.model.chat=…，用不到的类型写 spring.ai.model.embedding=none 等关掉（⑤ 的配置）；需要同时用两家时，自己声明两个 ChatClient Bean 并加限定名。

第二圈 · 使用规范

  • 业务只注入 ChatClient：不直接用某家的 ChatModel 实现类，换家才真正只改配置。
  • 每类任务一个 ChatClient Bean：默认 system、默认选项、advisor 各自配置，对应上一页的“按任务配置”。
  • key 从环境变量来：spring.ai.anthropic.api-key=${ANTHROPIC_API_KEY}，不进代码库。
  • 改了资源文件就 mvn clean：⑤ 里删掉的旧配置文件还躺在 target/classes，继续生效，差点误判。

自测

1. 用一句话说出这一页的精华

Spring AI 用 starter 装出一个 ChatModel、在上面提供 ChatClient 的链式 API（调用、entity 结构化、Flux 流式），换家靠 starter 和配置；但换家只换了接口，模型行为必须重新评测。

2. 为什么 entity() 在一个模型上成功、在另一个上全部失败？

默认的 entity() 靠提示词里的格式说明再解析，不是约束解码；第二个模型把推理过程写进了回答，Jackson 解析不了。

从 ④ 机制 3 推出，⑤ 实测

3. 业务代码里为什么不出现 AnthropicChatModel？

直接依赖某家的实现类，换家就要改代码；只注入 ChatClient（或 ChatModel 接口），换家才是改配置。

从 ④ 机制 1 和第二圈推出

4. 预测：把 spring.ai.anthropic.chat.model 改成 claude-opus-5-5，又在配置里写了 temperature=0，连真正的 Claude 会怎样？

按 Claude 文档，Opus 5.5 不接受 temperature，请求会 400，而 400 不会被重试。要把 temperature 留空。

从坑 3 和站 02 采样页推出

5. 预测：Spring AI 的 Anthropic 模块里，max-retries 设成 5，你的业务代码外面再包 3 次重试，一次 529 最多变成几次请求？

6 × 3 = 18 次（SDK 每次最多发 6 次，外面 3 轮）。重试只在一层做（出错那页的误用 1）。

从 ④ 机制 1（重试由 SDK 的 max-retries 管）推出

6. 放回全景：Spring AI 版的分诊服务里，全景的 10 站分别落在哪？

第 1 站：defaultSystem 和 user() 拼提示词；第 2 站：starter + spring.ai.model.chat 选模型；第 3、4、5 站：ChatModel 里的官方 SDK 拼请求、发 HTTP、按 max-retries 重试；第 6 站在服务端；第 7 站：stream().content() 的 Flux；第 8 站：ChatResponse 的结果和用量；第 9 站：entity() 加你自己的取值校验和重试；第 10 站：用量进日志或 Micrometer。
