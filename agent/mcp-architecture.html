MCP 的三方：主机、客户端、服务端

MCP 把“agent 用别人写的工具”拆给三方：主机管对话和权限，客户端一个只连一个服务端，服务端只负责把能力摆出来。三方之间说的是 JSON-RPC，从 2026-07-28 版起没有握手，每个请求自带版本。精华是：工具写一次，谁的 agent 都能接，而服务端永远看不到整段对话。

①为什么需要：工具写一次，谁的 agent 都能接

在全景第 1、4 站，这一步要解决的是：Claude Code 一启动就要连上两个别人写的服务端（Python 的 oncall、Spring AI 的 tickets），弄清它们会什么；而同样两个服务端，你自己的值班助手明天也要能连。没有统一的说法，每接一对就得写一套胶水代码。

Claude Code 能直接用吗不能。工具在你的 Python 进程里，Claude Code 摸不到。能，但要先给 Claude Code 写一层适配，Cursor 再写一层。能。.mcp.json 里加一行。
工具说明和参数格式谁维护每个 agent 各写一份；Anthropic 叫 input_schema，别家叫 parameters，格式还不一样。接口文档有一份（OpenAPI），转成模型能读的工具格式还是靠各家适配。服务端一份，客户端用 tools/list 在运行时取。
加一个工具要改谁改 agent，重新发版。改服务，再改每一个适配。只改服务端，客户端下次列清单就看到了。
工具慢了、崩了会怎样拖住甚至拖垮 agent 进程。隔离在服务里。隔离在服务端进程里。
读本机文件、跑 jstack 这种工具能，同一个进程。差一点：为了本机工具也得起 HTTP 服务、开端口、做登录。能。stdio 子进程，不开端口。
不懂精华时的典型误用：把 MCP 当成又一种 RPC 框架，把内部微服务之间的调用也改成 MCP。MCP 的精华是“让模型发现并调用别人写的工具”：服务之间互调不经过模型，用原来的 HTTP、gRPC 就好，多一层只是多一份开销。

③相邻方案：它们各解决什么

方案解决什么和 MCP 的关系
OpenAPI + 各家函数调用描述一个 HTTP 接口；模型侧的“函数调用”各家格式不同。能描述接口，但不管“运行时发现”“本机进程”“权限在谁手里”。很多 MCP 服务端内部就是去调 REST 接口。
LSP（语言服务器协议）编辑器和语言服务之间的标准：一个编辑器接所有语言，一个语言服务接所有编辑器。MCP 的规范自己说受了它的启发：同样是 JSON-RPC、同样是“M × N 变 M + N”、同样能跑在 stdio 上。
框架里的工具抽象（Spring AI 的 @Tool、LangChain tools）在一个程序里，把函数变成模型能调的工具。只在这个框架、这个进程里有效。Spring AI 和 LangChain 都能把这些工具再暴露成 MCP 服务端，或者去连 MCP 服务端。
A2A（agent 对 agent）两个 agent 之间委托任务、交换结果。MCP 是“agent 用工具”，A2A 是“agent 找 agent 帮忙”，层次不同，可以一起用。
MCPagent 和外部工具、数据之间的标准接口。Claude Code、Cursor、VS Code 等主流客户端都支持；官方 SDK 有 Python、Java、TypeScript 等。

本页学 MCP：要让“别人写的工具”接进“别人写的 agent”，只有一个两边都认的标准接口，才能做到哪一边改了，另一边都不用跟着改。

④原理：三方、一种消息格式、一次连接的一生

先知道这些
  • JSON-RPC 2.0：一种很小的远程调用约定。一条消息就是一个 JSON 对象：请求带 id、method、params；响应带同一个 id，里面是 result 或 error；通知没有 id，对方不回。它不管消息怎么送（管道、HTTP 都行），两个方向都能发。
  • Java 比方：MCP ≈ JDBC。DriverManager 管连接，驱动实现标准接口，业务代码不关心对面是 MySQL 还是 PostgreSQL。比方失效的地方：JDBC 驱动是你挑的可信 jar，跑在你自己的进程里；MCP 服务端可能是别人写的、跑在别的进程甚至别的公司，它写的工具说明还会进模型的上下文。
  • 站 04 学过：模型只会“提议”调用（tool_use），真正去执行的是你的代码，见 工具调用的一来一回。MCP 管的就是“你的代码”这一段怎么标准化。

机制 1 · 三方各管什么：主机在中间，服务端互相看不见

谁全景里是谁管什么不管什么
主机 HostClaude Code 进程对话历史、调模型、权限检查；创建客户端；把各家工具合并成一张表，决定什么进上下文。不实现任何工具。
客户端 Client主机里的一个连接对象，一个服务端一个拉起或连上服务端；协商版本；发请求、按 id 配对响应。不做决定：调不调、调哪个，由模型提议、主机放行。
服务端 Serveroncall 进程、tickets 服务摆出工具、资源、模板；执行调用，回结果。看不到整段对话，看不到别的服务端，也不知道对面是哪个模型。

规范的四条设计原则：服务端要极容易写；服务端要能自由组合；服务端不能读到整段对话，也不能“看进”别的服务端（对话历史留在主机，跨服务端的交互由主机控制）；功能可以一点点加。后面的“两个服务端之间没有线”“一个服务端一个客户端”，都是从第三条来的。

机制 2 · 消息：JSON-RPC 的三种，按 id 配对

实测⑤ 的迷你主机抓到的四种消息2026-11-26 · mcp 2.3.0
// 请求：有 id。新协议下 _meta 里带版本、能力、自报家门
→ {"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"search_logs",
   "arguments":{"keyword":"ERROR","since":"20:06"},
   "_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28", …}}}
// 响应：同一个 id，result 二选一 error。新协议的 result 必带 resultType
← {"jsonrpc":"2.0","id":3,"result":{"content":[{"type":"text","text":"20:13:10 ERROR …"}],
   "isError":false,"resultType":"complete", …}}
// 错误响应：老服务端不认识 server/discover
← {"jsonrpc":"2.0","id":1,"error":{"code":-32601,"message":"Method not found: server/discover"}}
// 通知：没有 id，对方不回
→ {"jsonrpc":"2.0","method":"notifications/initialized"}
  • 请求和响应靠 id 配对，不靠先后顺序：同时发出两个请求，慢工具的结果可以后到。MCP 规定 id 不能是 null，字符串和数字都行，Claude Code 两种都用（实测："server-discover-probe-1" 和 0）。
  • 方法名就是“动词”：server/discover、tools/list、tools/call、resources/read、prompts/get……第 2 页讲后几个。
  • 错误码沿用 JSON-RPC 的（-32601 方法不存在、-32602 参数不对），MCP 自己加了几个，比如 -32022“协议版本不支持”。

机制 3 · 一次连接的一生：新协议先探测，老协议要握手

同一个主机可以同时讲两个年代的协议。下面是 ⑤ 那个迷你主机真实发出的顺序：oncall 用新版 SDK 写的，gateway 是手写的老服务端。

为什么这样设计：2026-07-28 为什么去掉握手

新：每个请求自带版本和能力（无状态）

  • 远程服务端可以放在负载均衡后面随便加机器：任何一台都能接任何一个请求，不用粘性会话。
  • 服务端重启不丢东西，因为本来就没有“会话”；客户端也可以不探测，直接发 tools/call。
  • 代价是每个请求多带一段 _meta：实测 tools/list 从 65 B 变成 260 B，Claude Code 发的约 511 B。和模型一轮几千个 token 比，可以忽略。
  • 跨调用的状态要自己传：服务端发一个句柄（比如导出任务号），下次当普通参数带回来。

老：先握手，再在会话里说话

  • 每个请求很短；在 stdio 上一对一，握手一次就够，这里没有问题。
  • 在 HTTP 上，握手结果绑在接住它的那台机器上（Mcp-Session-Id），后面的请求必须回到同一台，扩容、发布、宕机都要处理会话迁移。
  • 会话丢了，客户端要从握手重来，正在进行的事也没了。
决定胜负的约束：越来越多的 MCP 服务端是远程部署的公共服务（工单、监控、各家 SaaS），它们要像普通 HTTP 服务一样横向扩展。为此每个请求多带几百字节，是划算的买卖。
最少的代码：用官方 SDK 当客户端细节放到 ⑥

    r = await c.call_tool("search_logs", {"keyword": "ERROR", "since": "20:06"})

⑤亲眼看到：100 行标准库写一个迷你主机

不用任何框架，自己当一回“主机”：配置里两个服务端，一个服务端建一个客户端，各自探测版本、需要时回退握手，把工具加上前缀合成一张表，再各调一次。oncall 就是全景页那个 Python 服务端；gateway 是 40 行手写的老协议服务端，它也有一个叫 search_logs 的工具。

⑤mini_host.py（节选）完整代码 →
class StdioClient:                       # 一个客户端 = 一个子进程 + 一对管道
    def request(self, method, params=None, timeout=5.0):
        if self.era == "modern":
            params["_meta"] = META           # 新协议：每个请求自己带齐版本和能力
        rid = self.next_id; self._write({"jsonrpc": "2.0", "id": rid, "method": method, "params": params})
        while True:
            msg = self.inbox.get(timeout=timeout)
            if msg.get("id") == rid: return msg   # 按 id 配对

    def connect(self):
        self.era = "modern"
        try:
            r = self.request("server/discover", timeout=3.0)
            if "result" in r and MODERN in r["result"]["supportedVersions"]: return
        except queue.Empty: pass                  # 超时也算“不是新协议”
        self.era = "legacy"                       # 回退：老协议握手，只做一次
        self.request("initialize", {"protocolVersion": "2025-11-25", ...})
        self.notify("notifications/initialized")  # 通知：没有 id

# 主机：一个服务端一个客户端；工具加前缀合并
clients = {name: StdioClient(name, cmd) for name, cmd in SERVERS.items()}
for name, c in clients.items():
    for t in c.request("tools/list")["result"]["tools"]:
        tools[f"mcp__{name}__{t['name']}"] = (c, t["name"])

读出来的结论
  • 同一个主机里，两个客户端各讲各的年代：oncall 走新协议，gateway 探测失败后回退到握手。这就是 Claude Code 的做法（全景页抓到了它对老服务端的同样回退）。
  • 两个服务端都有 search_logs，合并后靠 mcp__服务端__ 前缀分开，Claude Code 的工具名就是这么来的。
  • “你的问题”只在主机里。oncall 自始至终只收到 3 条消息，没有一条带着对话内容，也不知道 gateway 存在。
  • 两个进程是一起拉起的：gateway 没有在 oncall 的 676 ms 启动之后再排队等。启动慢的是 Python 加载 SDK，不是协议。

⑥细节

第一圈 · 注意事项

1客户端钉死新版本，连老服务端实测← ④ 机制 3
现象
官方 SDK 用 Client(server, mode="2026-07-28") 连 gateway：没有一句“版本不对”，而是 ListToolsResult 校验失败，缺 cacheScope 等 3 个字段。这个老服务端不查握手，照样回了老格式的结果。
根源
新老两个年代的消息格式不通用，只有“两种都会”的一方主动探测、回退才行。规范的兼容表：新对老失败，老对新失败，两种都会的客户端对老服务端可以。
做法
客户端用 mode="auto"（默认）：先 server/discover，任何错误或超时都回退 initialize，规范要求回退不能只认某一个错误码。服务端用新版 SDK，两种开头都接。
2拿 clientInfo 当身份← ④ 机制 3
现象
服务端看到 "clientInfo": {"name": "claude-code"}，就放开写操作。任何程序都能在这里写 claude-code，⑤ 的迷你主机自报的是 mini-host，改一个字符串就能冒充。
根源
规范原话：clientInfo 和 serverInfo 是发送方自己报的，协议不验证，不应该拿来做安全决定。
做法
身份靠传输层：stdio 靠“谁拉起的这个进程”，HTTP 靠 OAuth 令牌（第 5 页）。clientInfo 只用来打日志、做统计。
3在服务端内存里记“这个客户端上一步做了什么”← ④ 为什么这样设计
现象
tickets 服务端在内存里存“当前在看的工单”，第二次调用 add_comment 不传工单号。扩到两台后，时灵时不灵。
根源
新协议没有会话，下一个请求可能落到另一台机器。stdio 虽然一对一，但开两个 Claude Code 窗口就是两个 oncall 进程，内存也不共享。
做法
跨调用要用的东西做成显式参数：服务端返回一个句柄（工单号、导出任务号），模型下次当普通参数传回来。
4按先后顺序而不是按 id 配响应← ④ 机制 2
现象
模型一轮要了两个工具（站 04 的并行工具调用），客户端把先到的响应当成第一个请求的结果，日志查询的结果被当成了 GC 分析。
根源
JSON-RPC 只保证 id 对得上，不保证顺序：慢的工具后回来。id 也不一定是递增整数，Claude Code 就混用字符串和数字。
做法
发请求时记下“id → 等待者”，收到响应按 id 原样查表。⑤ 的迷你主机是一问一答的，偷了这个懒，↺ 练习 3 就是把它补上。

第二圈 · 使用规范

  • 一个服务端只管一件事：oncall 管排障的只读工具，tickets 管工单。防的是：一个服务端挂了所有工具一起没；权限也没法分开给。
  • 服务端名字短而且别改：名字会变成 mcp__oncall__ 前缀，写进每个人的放行名单。改名等于让所有人的放行规则失效。
  • 写好 instructions：server/discover（或 initialize）结果里的 instructions，Claude Code 会放进给模型的系统提示。oncall 写了“时间参数用 HH:MM，告警前 10 分钟开始查”，能省掉模型一轮试错（站 04 那次就是把 since 填成了告警时间）。
  • 服务端两个年代都接，客户端先探测再回退：用新版 SDK 基本自动做到。防的是坑 1。
  • stdout 只走协议，日志写 stderr：全景页实测过，一段没换行的输出能吃掉一整条响应。第 3 页细讲。

第三圈 · 优化和深处

为什么用 JSON-RPC，不用 REST

REST 的“URL 加动词”绑死在 HTTP 上，stdio 管道里没有 URL。JSON-RPC 只规定消息长什么样，同一套消息能跑在管道和 HTTP 上；它两个方向都能发，LSP 已经在编辑器里验证了十年。代价是 HTTP 层的缓存、网关规则看不懂请求体，所以 2026-07-28 版在 HTTP 上额外要求 Mcp-Method、Mcp-Name 这样的请求头，让网关不拆包也能路由和限流（第 3 页）。

服务端要反过来问客户端怎么办

老协议里，服务端可以向客户端发请求：让它调模型（sampling）、让用户填个表（elicitation）、问工作目录（roots）。新协议不许服务端主动发请求，改成在结果里返回 resultType: "input_required" 和要补的东西，客户端补齐后带着 inputResponses 重发原请求。服务端依然不用记状态。sampling 和 roots 在新协议里已标为弃用。

能力协商就是功能开关

服务端在 capabilities 里没声明 resources，客户端就不会发 resources/list。新功能（长任务 tasks、界面 ui）以 extensions 的形式加进来，对面不认识就当没有。这就是设计原则第四条“功能可以一点点加”：双方不用同时升级。

Claude Code 的探测细节

全景页的实测里，Claude Code 连一个新服务端发了两次 server/discover：一次带字符串 id 当探测，另一次带数字 id 0，中间还开了一条 subscriptions/listen 订阅“工具清单变了”的通知。对一段没换行的脏输出，它等了约 3 s 没收到探测回复，按“超时就当老协议”回退到了 initialize。

下一圈

  • 长任务扩展（tasks）：服务端先回一个句柄，客户端过一会儿用 tasks/get 来取结果。
  • MCP 和 A2A 怎么分工：一个值班 agent 把“改配置”委托给另一个 agent 时，中间走哪个协议。
  • 一个远程服务端同时服务几百个主机：限流、计费、审计放在哪一层（站 10 AI 网关）。

↺回到⑤：改一改迷你主机

  1. 同名工具：在 SERVERS 里把 gateway 再配一份，名字叫 gateway2。合并表里会出现三个 search_logs，各带前缀。再把前缀去掉，看哪个工具被悄悄覆盖了。
  2. 超时回退：让 gateway 收到 server/discover 时什么都不回（直接 continue）。迷你主机会等 3 s 再回退握手，和全景页里 Claude Code 的表现一样。（坑 1）
  3. 按 id 配对：现在的 request() 一问一答，丢掉了 id 对不上的消息。改成维护一张“id → Future”的表，同时给 oncall 发两个 tools/call，在服务端让第一个故意 sleep 1 秒，确认两个结果没有串。（坑 4）

自测

1. 用一句话说出 MCP 三方设计的精华

工具写一次、谁的 agent 都能接；主机在中间握着对话和权限，客户端一对一连服务端，服务端只看得到发给自己的请求。

2. 站 04 那种“工具写在 agent 里”的做法，最疼的是哪一点？

工具锁在一个进程里：Claude Code、Cursor 这些别的 agent 用不了；加一个工具要改 agent、重新发版；工具格式还得按每家模型各写一份。

3. 头号坑“钉死新版本连老服务端”，根源是哪条原理？

④ 机制 3：新老两个年代没有共同的消息格式，兼容只能靠“两种都会”的一方先探测、再回退。钉死一个版本，就放弃了回退。

4. 预测：开两个 Claude Code 窗口，都用同一份 .mcp.json 里的 oncall。一共有几个 oncall 进程？一个窗口调的 search_logs，另一个窗口的 oncall 知道吗？

两个进程；不知道。stdio 是一个客户端拉起一个子进程，一对一，两个窗口是两个主机、两个客户端、两个服务端进程，互不相通。

从 ④ 机制 1（一个服务端配一个客户端）和坑 3 推出。

5. 预测：把 oncall 换成只会 2026-07-28 的服务端，一个只会老协议的旧客户端去连它，会怎样？

连不上。旧客户端只会发 initialize，只认新协议的服务端不认识这个开头；规范说得很直白：老客户端没有“向前兼容”的办法。所以过渡期服务端要两种都接。

从 ④ 机制 3 和规范的兼容表推出。

6. 放回全景：第 4 站前后各发生了什么？如果第 4 站协商失败，整条链路会怎样？

前面是第 2、3 站：进程拉起来了、HTTP 连上并拿到了令牌；后面是第 5 站列工具清单。协商失败，客户端就不知道该用哪个年代的格式说话，第 5 站拿不到工具清单，第 6 站模型的 tools 里就没有这些工具。你问排障问题，模型只能说“我没有查日志的工具”，Claude Code 的 /mcp 里这个服务端显示失败。

从全景第 4～6 站和 ④ 机制 3 推出。
