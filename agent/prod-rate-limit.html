限流和配额：供应商的速率上限、自己的令牌桶

供应商用三个连续补充的令牌桶限你：每分钟请求数、输入 token、输出 token，从缓存读的输入不算。精华是三句话：按 token 限，不按请求数限；自己的桶要比供应商更早说“等一下”（留一成余量，也不攒太多）；份额是保底，不是天花板，闲着的让给别人。能同时跑几个调查，是额度除以每个调查的用量算出来的。

①为什么需要：三个团队抢一份额度

在全景第 ④、⑦ 站，这一步要解决：交易、支付、搜索三个团队共用一个组织的额度。供应商只认总数，不管是谁用的。20:00 一开闸，16 个 worker 同时开跑，每个调查每分钟要 3 万未缓存输入 token，合起来 48 万，比额度多出两成；搜索团队的调查还有一轮要带 4 万 token 的日志。

一个调查每分钟3 万未缓存输入（6 轮 × 5k）
供应商额度40 万ITPM，本页假设
同时能跑12个调查 = 36 万 ÷ 3 万
worker 有16个，多的 4 个要等

要的是四件事：不撞供应商的墙（少吃 429）；一个团队吃不光别人的份；闲着的份额不浪费；P0 先拿。

②没有它会怎样：只靠 429 和 SDK 自带的重试

最省事的做法：什么都不限，让供应商回 429，官方 SDK 自己会重试（默认 2 次，照 retry-after 等）。⑤ 把那一夜按 30 倍速重演，87 个事件、16 个 worker，结果是这样：

A 只靠 429 + SDK 重试605（多发 83 个）223 次，交易团队吃了 180 次32 个3 个
B 自己限请求数（每分钟 72 个）52329 次，搜索团队吃了 26 次7 个0
E 全局 token 桶 + 公平排队522（一次没多发）000
  • 只靠 429：供应商的桶空了，16 个 worker 一起撞墙、一起等 retry-after、再一起撞，重试 2 次用完的那一轮就失败；32 个事件没查完，其中 3 个是 P0。
  • 谁流量大谁吃 429 最多：交易团队请求最多，180 次 429 落在它头上，最要紧的 P0 恰恰在交易里。
  • 只限请求数：每分钟 72 个请求按平均 5k 算是 36 万，可搜索团队那一轮一个请求就是 4.5 万 token。请求数没超，token 照样把供应商的桶打空。
  • 按 token 限、在自己这边排队：522 个请求一个没被拒，P0 3.5 分钟内全部做完（⑤ 实测）。
不懂精华时的典型误用：照搬 Java 里限 QPS 的习惯，在网关上配“每秒 N 个请求”。对模型供应商来说一个请求可以差 10 倍大，限请求数等于没限。

③相邻方案：限什么、在哪限、怎么分

做法不撞供应商的墙请求大小不一样一个团队吃不光闲着的份额能借
只靠 429 + 重试不能：撞了才知道不管不能：流量大的吃得多，也被拒得多—
限并发（信号量 12 个）差一点：请求大小平均时能不能：12 个里碰上几个 4.5 万的就超不能能
限请求数（每分钟 72 个）差一点：⑤ 实测 29 次 429不能：大请求和小请求算一样不能能
按 token、按团队死分三个桶能：⑤ 实测 0 次 429能能不能：交易排长队时，搜索那份空着也借不走，⑤ 里做完要 20.3 分钟
按 token 的全局桶 + 加权公平排队能：0 次 429能能：额度紧时按 5 : 3 : 2 分能：只有一家在排队时它能用满，9.1 分钟做完
在供应商那边给每个团队开工作区、设额度能：硬隔离能能不能：各自的上限是死的；而且组织总额度照样管着它们

本页学按 token 的全局桶 + 加权公平排队：供应商按 token 限你，你就按 token 限自己；桶只开一个，额度紧时按权重分，不紧时谁要谁用。供应商那边的工作区限额适合当最后一道硬保险（比如给实验性的团队封顶），不适合当日常的分配手段。

④原理：供应商的三个桶，和自己的那一个

先知道这些
  • 令牌桶：桶里攒令牌，按固定速率往里补，补满为止；请求拿走令牌才放行，拿不到就等或被拒。补给页：限流算法：令牌桶、漏桶、滑动窗口。
  • token：模型计费和限速的单位，中文和英文折算的比例不一样。站 02：token 和计费。
  • 前缀缓存：请求开头一字不差的那一段，供应商算过一次就存着，下次直接读，按一成的价收钱。站 03：提示词缓存。

机制 1 · 供应商的三个桶：什么算、什么不算

三条容易想错的地方，文档里都写了：

  • 桶是连续补的，不是每到整分钟清零；而且可能按比一分钟更短的间隔卡：文档举的例子是“每分钟 60 个可能按每秒 1 个来执行”。所以一分钟的额度不能在第一秒全用掉。
  • 缓存读不算 ITPM：4k 前缀命中缓存，这一轮只扣 5k。缓存不光省钱，也直接把能同时跑的调查数从 6 个抬到 12 个。写缓存的那一次照算。
  • OTPM 只看真生成的：max_tokens 设大设小不影响额度，设小了只会把回答截断。另外，用量突然猛涨时，没超额度也可能先收到 429（文档叫 ramp limit），建议每分钟最多加一档地放量。

机制 2 · 自己的桶：预扣、多退少补、可以欠账

调用之前，自己并不知道这次会扣多少输入：前缀命中没有，要等响应里的 usage 才知道。所以分两步：先按估算预扣（这一轮新增的字数 ÷ 4，假定前缀命中），回来再按真实数字补差（input_tokens + cache_creation_input_tokens）。桶容量只放 10 秒的量，比供应商的短窗口还小；单个请求比桶还大时（搜索那 4.5 万），等桶满了就放行，余额变成负数，后面的请求替它还账。

bucket.py：预扣和补差细节放到 ⑥
est = len(new_text) / 4                 # 预估：假定前缀命中
await bucket.acquire(tenant, est, prio)  # 不够就在这里等
resp = await client.messages.create(...)
u = resp.usage
actual = u.input_tokens + u.cache_creation_input_tokens
bucket.settle(tenant, est, actual)       # 多退少补

# acquire 里：大请求等桶满就放行，余额可以成负数
need = min(n, self.cap)
while self.tokens < need:
    await sleep((need - self.tokens) / self.rate)
self.tokens -= n

Java 老朋友：Guava RateLimiter

像：acquire(permits) 一次可以拿多个令牌；拿得比桶里多时，Guava 的做法也是“先放行，让下一个请求替它等”，和这里的欠账一样。

不像：Java 里一个请求值几个 permit 是事先知道的；这里要先估、回来再补，估错了（比如缓存没命中）就会多放出去，⑥ 坑 5 就是这么来的。另外 Guava 只管一个进程，多副本要共享一个桶（⑥ 坑 6）。

机制 3 · 份额是保底，不是天花板：一个桶 + 公平排队

最直觉的分法是按 5 : 3 : 2 开三个桶。问题在于 worker 是共用的：交易的 52 个事件在自己的 18 万里排长队时，搜索的 7.2 万可能正空着，却借不过来。⑤ 实测这样做完要 20.3 分钟。改成一个 36 万的全局桶，排队的请求先按优先级（P0 最先），同一优先级里挑“已用量 ÷ 权重”最小的那个团队：额度紧时就是 5 : 3 : 2，只有一家在排队时它能用满。同样的流量 9.1 分钟做完，429 依然是 0。

一个全局桶 + 加权公平排队

  • 总量只在一个地方卡，永远不超过 36 万，也就不撞供应商的墙。
  • 额度紧时按权重分，交易吃不光支付和搜索的份；不紧时谁要谁用，一点不浪费。
  • 优先级是排队顺序的第一键，P0 不管属于谁都先拿。
  • 代价：要一个“发令牌的人”（一个协程或 Redis 里的一段脚本），排队逻辑比三个独立的桶复杂。

按团队死分三个桶

  • 实现最简单，每个团队互不影响，也不撞墙。
  • 闲着的份额借不走：搜索没活时那 20% 白白空着，交易的 P1、P2 却在排队。
  • 共用 worker 池时更糟：worker 拿着交易的事件在等交易的桶，搜索的事件连 worker 都分不到。
决定胜负的约束：额度是整个组织共用的一份、按 token 计，而三个团队的流量此起彼伏。要同时做到“不超总数”和“不浪费”，只能在一个地方数总数，再按权重决定排队顺序。

机制 4 · 能同时跑几个：额度 ÷ 每个调查的用量

把上面几条合起来，就得到全景里那个数：并发上限 = 自己的桶 ÷ 一个调查每分钟的未缓存输入 = 36 万 ÷ (6 轮 × 5k) = 12。worker 再多，也只是多几个人在桶前面排队。下面的计算器用的是全景那一夜的到达节奏（不算 20:03 那次 529），改一个数看看 87 个事件要多久做完。

实验台：额度、余量、缓存，决定这一夜多久做完

先猜：账号降了一档，额度从 40 万变成 20 万，其他不变。87 个事件全部做完要多久（原来 8 分钟）？

按全景的设定逐分钟推算（估算，不是实测）：每个调查 6 轮、每轮 9k 输入（前缀 4k）、输出 400，调查本身 1 分钟；每分钟能开工的个数 = 并发上限，P0 先、P1 次、P2 最后。单价按全景页的假设：输入每百万 $3、缓存读 $0.30、输出 $15。“不留余量”在这里看起来更快，代价是估算一有偏差或别的服务也在用同一份额度，就开始吃 429（⑥ 坑 4）。

⑤亲眼看到：把那一夜按 30 倍速重演 5 遍

假供应商（FastAPI）照文档的规则实现三个桶：容量各放 10 秒的量，ITPM 只收没命中缓存的输入，带 cache_control 的前缀 5 分钟内命中缓存，超了回 429 和 retry-after。调用方用官方 anthropic SDK（max_retries=2）。87 个事件按全景的节奏到达，16 个 worker，每个调查 6 轮；搜索团队的调查第 3 轮多带 4 万 token 的日志。时间压缩 30 倍：场景里的 1 分钟，墙上 2 秒。

client = anthropic.AsyncAnthropic(base_url="http://127.0.0.1:18720",
                                  api_key="sk-fake", max_retries=2)
fb = FairBucket(360_000, {"trade": 5, "pay": 3, "search": 2})   # 做法 E

async def call(inc, rnd):
    system = [{"type": "text", "text": PREFIX,                  # 4k 固定前缀
               "cache_control": {"type": "ephemeral"}}]
    content = ROUND + (BIGLOG if inc["tenant"] == "search" and rnd == 3 else "")
    est = len(content) / 4
    await fb.acquire(inc["tenant"], est, PRIO[inc["prio"]])     # 在自己这边排队
    resp = await client.messages.create(model="main", max_tokens=1024, system=system,
                                        messages=[{"role": "user", "content": content}])
    u = resp.usage
    fb.settle(inc["tenant"], est, u.input_tokens + u.cache_creation_input_tokens)

⑥细节

第一圈 · 注意事项

1只限请求数实测← ④ 机制 1
现象
请求数一直在配额内，供应商照样回 429，错误信息说超的是输入 token。⑤ 里 B 吃了 29 次。
根源
供应商三个桶里最先空的往往是 ITPM，而一个请求的输入可以从 5k 到 4.5 万。
做法
按 token 限；请求数只当一个次要的上限。
2按团队死分额度实测← ④ 机制 3
现象
没有一次 429，可这一夜要 20 分钟才做完，P95 14.8 分钟；看板上搜索团队的额度用了不到一半。
根源
份额被当成了天花板：闲着的份额借不走；共用 worker 池时，worker 还会被拿着等桶的事件占住。
做法
一个全局桶，权重只决定额度紧时的排队顺序。
3自己的桶攒满一分钟← ④ 机制 1
现象
平时没事，每次放量的头几秒一串 429，之后又好了。
根源
容量等于一分钟额度的桶，允许第一秒就放出整分钟的量；供应商可能按更短的间隔卡，这一波突发会撞墙。
做法
桶容量只放几秒的量（⑤ 用 10 秒），速率不变。
4把额度用到 100%← ④ 机制 4
现象
大部分时间正常，偶尔一阵 429，查不出是谁。
根源
组织额度不只这一个服务在用（评测任务、别的团队的脚本也算），自己的预估也有误差。
做法
留一成余量；把响应头里的 anthropic-ratelimit-input-tokens-remaining 记进看板，余额长期贴底就该申请提额。
5预估假定缓存一定命中实测← ④ 机制 2
现象
有人在系统提示里加了当前时间，429 突然冒出来（⑤ 的 D：29 次），做完的时间也长了一半。
根源
预扣只扣了新增的 5k，实际每次要扣 9k；补差发生在调用之后，这期间多放出去的请求已经打到供应商了。
做法
看板盯着缓存命中率，掉下去就报警；预估改用最近一段时间的真实命中率加权，而不是一律假定命中。
6每个副本各开一个本地桶← ④ 机制 2
现象
单副本压测一切正常，上线扩到 3 个副本，429 一片。
根源
3 个副本各自以为自己有 36 万，加起来 108 万。
做法
桶放在一个共享的地方：AI 网关只部署一组并在网关里限（下下页）；或者桶放进 Redis，用一段 Lua 脚本原子地补令牌和扣令牌。
7开闸时一下子放满← ④ 机制 1
现象
20:00 整点，用量从几乎为零跳到满额，额度没超也收到 429。
根源
文档写明用量猛涨会触发 ramp limit，建议每分钟最多加一档地放量；缓存读的 token 不算进 ramp。
做法
大促前半小时开始预热，或者桶的速率从一半起、每分钟往上加一档。
8把 max_tokens 设小来“省额度”← ④ 机制 1
现象
报告时不时在半句话处断掉，额度却一点没省。
根源
OTPM 只按真生成的 token 扣，和 max_tokens 无关；设小只会截断。
做法
max_tokens 按“最长的正常回答”设；要省输出，改提示词让它写短。

第二圈 · 使用规范

  • 按 token 限，桶只开一个：防请求大小不一打穿额度、防死分浪费。
  • 桶的速率 = 额度 × 0.9，容量 = 几秒的量：防误差和突发撞墙。
  • 预扣 + 按 usage 补差，大请求允许欠账：防大请求永远等不到。
  • 排队顺序：优先级第一，权重第二：防 P0 被别的团队的 P2 挡住。
  • worker 并发上限 = 额度 ÷ 每个任务的用量：防多出来的 worker 只会排队，还在扩容时被误当成“扩不够”。
  • 余额、429 次数、缓存命中率进看板：防额度问题只在出事以后才被发现。

第三圈 · 优化和深处

分布式的桶：Redis 加一段 Lua

多副本共享一个桶，最常见的是把“上次补令牌的时间”和“余额”放在 Redis 一个键里，Lua 脚本里补、判、扣一步做完。另一种写法 GCRA 只存一个“理论到达时间”，省一次读写。不管哪种，每次调用都多一次网络往返（亚毫秒到 1 毫秒），比起几秒的模型调用可以忽略。

按响应头自适应

供应商在每个成功的响应里报余额和补满时间。可以像 TCP 那样做加性增、乘性减：余额充足时把自己的速率慢慢往上调，收到 429 就砍一半。好处是额度变了（提额、降档、别的服务在抢）也不用改配置；代价是会在边界上来回试探。

额度按模型分

额度是按模型类别给的，备用模型有自己的一份。下一页降级到备用模型时，要给它也开一个桶，而且通常小得多：全景里切到备用模型后每分钟只能做 5 个。

不急的活走批处理

Message Batches 有自己的一套额度，所有模型共用，而且不受 ramp limit 管。离线评测、批量打标签这类活从实时额度里搬出去，大促夜的实时额度就全留给调查。

下一圈

  • Redis + Lua 的分布式令牌桶：三个网关副本共享一个桶，测一次调用多花多少延迟。
  • 加性增、乘性减：让桶跟着响应头里的余额自己调速。
  • 按“钱”限而不是按 token 限：每个团队每天的预算，超了降级到小模型。
  • 长上下文请求（几十万 token）怎么在桶里排队，才不会一次饿死一大片小请求。

↺回到⑤：改一改

  1. 让供应商允许攒满一分钟：把 fake_provider.py 的 WINDOW 从 10 改成 60，再跑。先猜 A 的 429 会少多少、E 有没有变化。（坑 3）
  2. 不留余量：E 的全局桶从 36 万改成 40 万，看 429 是不是从 0 变成几个、做完快了多少。（坑 4）
  3. 换一种预估：D 里不假定前缀命中，按“前缀 + 这一轮”预扣。做对了会看到 429 降到 0，代价是缓存正常时也多扣、并发变小。（坑 5）
  4. 日志再大一倍：搜索的大日志从 4 万涨到 8 万 token，B 和 E 各会怎样？

自测

1. 用一句话说出这一页的精华

按 token 限、只开一个全局桶、速率留一成余量、容量只放几秒；额度紧时按团队权重和优先级排队，不紧时谁要谁用；并发上限 = 额度 ÷ 每个任务的用量。

2. 只靠 SDK 的自动重试，到底缺什么？

重试是“撞了墙再说”，16 个 worker 会一起撞、一起等、再一起撞，重试次数用完就失败（⑤ 里 32 个事件）；而且谁流量大谁被拒得多，分不出 P0 和 P2、交易和搜索。

3. 为什么限请求数在这里不管用？

供应商最先卡住的通常是输入 token 的桶，一个请求的输入能差 10 倍。请求数没超，token 早超了。

从 ④ 机制 1 推出。

4. 预测：前缀缓存命中率从 100% 掉到 0，能同时跑的调查从几个变成几个？

每个调查每分钟的未缓存输入从 3 万变成 5.4 万，36 万 ÷ 5.4 万 = 6.67，只能跑 6 个，砍掉一半。缓存读不算 ITPM，所以缓存既是钱的问题，也是吞吐的问题。

从 ④ 机制 1、4 推出。

5. 预测：把 worker 从 16 个加到 32 个，用做法 E，这一夜会快多少？

几乎不会快：并发上限是 12，多出来的 worker 都在全局桶前面排队。反而是每个调查从领到任务到做完的时间变长了，因为更多调查在“半路等令牌”。

从 ④ 机制 4 推出。

6. 放回全景：第 ④ 站前后是什么？如果第 ④ 站的桶配成了 40 万、容量一整分钟，第 ⑥、⑦ 站会怎样？

前面是第 ③ 站的 worker 领到任务，后面是第 ⑤ 站网关选模型、第 ⑥ 站可靠性层、第 ⑦ 站供应商。桶不留余量又攒满一分钟，20:00 开闸的头几秒就会把一整分钟的量放出去，撞上供应商的短窗口和 ramp limit；第 ⑦ 站回一串 429，第 ⑥ 站按 retry-after 重试，重试又和新请求一起撞。看板上 429 突增，P0 的报告也被拖慢。

从全景第 ④⑥⑦ 站和 ④ 机制 1、2 推出。

档位：标准。本机跑过（2026-11-28，2 核 ARM，Python 3.13.18，anthropic 2.12.0，FastAPI 0.165.0）：⑤ 的 5 种做法，A、B、C 各三遍，E、D 各两遍；假供应商的规则是照文档写的模拟，不是真实的供应商，数字只用来比较几种做法。按文档（已核对原文）：Claude API rate-limits 页（令牌桶连续补充、可能按更短间隔执行、三种额度、缓存读不算 ITPM、写缓存算、OTPM 只算真生成的且与 max_tokens 无关、ramp limit、额度按模型类别、工作区限额、响应头和 RFC 3339 的 reset、Message Batches 有自己的额度且不受 ramp 管），2026-11-28 查；SDK 2.12.0 的重试逻辑看的是本地源码（_base_client.py：默认 2 次，先读 retry-after-ms 再读 retry-after，没有就从 0.5 秒起指数退避、最多 8 秒）。额度 40 万和单价是全景页的场景设定。
