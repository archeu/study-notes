状态图和检查点：长任务断点续跑

检查点就是每一步结束时 state 的一张快照，再加上这一步里每个任务各自交出的改动（pending writes）。有了快照，进程死了、人走开了，都能从最后一步接着跑；有了每个任务的改动，同一步里三个子 agent 失败一个，只重跑那一个。代价是存储：默认每一步都存整份 state，长对话的检查点按轮数的平方长。

①为什么需要：一条线程，三处会断

在全景第 6 站，这一步要解决的是：值班助手这条线程从告警进来到建出工单要十几分钟，中间至少有三处会断。每一处断了，前面花掉的时间和 token 都不该白费。

②没有它会怎样

  • notes 超时，只能从头再跑：再分诊一次、三个子 agent 全部重查。用真模型时这一步要一两分钟，token 再花一遍；全景实测里有检查点时只重跑了 notes 一个（执行次数 logs 1、metrics 1、notes 2）。
  • 停下等人时，state 只在内存里：这 13 分钟里进程不能退出，发一次版、OOM 一次，所有等批准的线程全丢，张三点“批准”的那一下找不到对象。
  • 出了事没法回看：不知道 summarize 拿到的是哪几段结论，也没法“回到那一步，改一下再跑”。
  • InMemorySaver 能解决第一条，解决不了后两条：它也是内存，进程一退就没了。
不懂机制时的典型误用：开发时用 InMemorySaver 一切正常，上线照搬；或者在节点里自己把 state 写进 Redis，以为这就是“检查点”，结果并行任务的部分成功、等人恢复都没覆盖到。

③相邻方案

方案存什么同一步里失败一个停下等人代价
自己存“走到第几步”step 编号 + 自己挑的字段，存 Redis 或 MySQL不能：要么整步重跑，要么自己给每个任务记结果能，但恢复逻辑全自己写每加一个节点都要改存盘代码
每步发一条消息Kafka、Redis Stream 里的消息就是进度能：每个子 agent 一条消息，各自确认别扭：等人十几分钟，消息要么一直不确认，要么另存状态状态散在消息里，没法整体回看
工作流引擎Flowable 的流程实例表；Temporal 的事件历史能能，这正是它们的本行另一套服务；Temporal 还要求代码确定（第 1 页）
LangGraph 检查点每步一张 state 快照 + 每个任务的改动能：成功任务的改动已经存了，只重跑失败的能：interrupt 存进检查点，进程可以退出存储随 state 大小和步数长（⑥ 坑 2）

本页讲 LangGraph 的检查点：它就是嵌在 agent 进程里的、按 superstep 存盘的小号工作流引擎。Java 那边最像的是 InnoDB：buffer pool 里的脏页定期刷盘（快照），刷盘之间的改动先记在 redo log 里（待提交写入）。

④原理：快照 + 每个任务的改动

先知道这些
  • superstep：LangGraph 按步走（这套“步内并行、步间同步”的模型来自 Google 的 Pregel，也叫 BSP）。每一步先算出该跑哪些节点，并行跑完，再把它们的改动一起合进 state。
  • channel 和版本号：state 的每个键在框架里叫一个 channel。每次被写，它的版本号就变大；每个节点记着自己上次跑时见过的版本。哪个节点的输入版本变新了，下一步就轮到它。
  • 三个 id：thread_id 是一条线程（全景里是告警指纹 alert-7f3a）；checkpoint_id 是这条线程里的某一步，按时间排序；checkpoint_ns 区分子图，主图是空串。
  • Java 比方：像 InnoDB。快照像刷到磁盘的数据页，pending writes 像 redo 里还没合进数据页的改动。比方失效的地方：redo 是为了崩溃后把已提交的事务重做一遍；pending writes 是同一步里已经跑完的任务交出的结果，存它是为了不重跑这些任务。

机制 2 · 存了什么：一行快照里的五样东西

存在哪字段是什么恢复时拿来干什么
checkpoints 表的 checkpoint 列channel_values每个键当时的值（alert、plan、findings……）重建 state
channel_versions每个键最后一次被写时的版本号和下一行比，看谁的输入变新了
versions_seen每个节点上次跑时见过的各键版本算出下一步该跑哪些节点（next）
id、ts这一步的 id 和时间按时间找最新的一行
checkpoints 表的其他列parent_checkpoint_id、metadata上一步是谁；step、source（input / loop / update / fork）把历史连成一棵树，能回看、能分叉
writes 表channel、value这一步里每个任务交出的改动，以及 __error__、__interrupt__、Send 出去的任务已经交了的任务不再跑；中断请求也存在这里

⑤ 实测全景那条线程：五行快照从 382 字节长到 2856 字节，因为每一行都存整份 channel_values；writes 表里能看到 notes 的 __error__ 和它重试后的 findings 挂在同一行快照上。

机制 3 · 恢复、中断和时间旅行，都是“读一行快照 + 挂着的 writes”

  • 接着跑：invoke(None, cfg) 读这条线程最新的快照，按 versions_seen 算出该跑谁；writes 表里已经交了结果的任务直接用结果，不再执行。
  • 中断：节点里的 interrupt() 抛出一个异常，框架把请求存成一条 __interrupt__ write。Command(resume=值) 把值也存成一条 write，然后从头重跑这个节点，interrupt() 这次直接返回那个值。
  • 时间旅行：拿历史里某一行的 checkpoint_id 去 invoke，就从那一步往下长出一条新枝；update_state(cfg, 改动, as_node=…) 先在那里补一行“当作某个节点写的”快照，再从它往下跑。旧的那条枝还在，⑤ 里能看到两个 step 3 指向同一个父亲。

为什么这样设计：快照 + 本步改动

只存快照

  • 读回最快：一行就是整个 state。
  • 同一步里部分成功的结果没处放：notes 超时，logs 和 metrics 的结果跟着丢，三个全部重跑。

只存改动（事件日志）

  • 存储最省：每步只记变了什么。
  • 读回要从头重放：线程越长越慢，而每一步开头都要读回一次。

LangGraph：快照 + 本步改动

  • 读回只要一行快照加几条 writes。
  • 同一步能部分成功：交了的任务不重跑。
  • 代价：每步都存整份 state，长对话的存储按轮数平方长（⑤ 实测 200 轮 10.5 MB）。
决定胜负的约束：每一步开头都要读回 state，所以读必须快，于是存快照；同一步里的任务各自完成，所以每个任务的结果要单独存，于是有 writes 表。存储的账是后来才付的：1.2 里新加的 DeltaChannel（beta）对单个键改成“只存改动、每 100 次改动存一次快照”，用读回时的重放换存储（⑤ 实测：277 KB 对 10.5 MB，读回 3.1 ms 对 0.6 ms）。这和数据库“redo 日志 + 定期 checkpoint”是同一个思路。

读出来的结论
  • 一个 superstep 一行快照；每一行都是整份 state，所以越往后越大（382 → 2856 字节）。
  • notes 的错误和它重试后的结果，挂在同一行快照、同一个任务 id 下面；logs 和 metrics 的结果早就在那里，重试时直接拿来用。
  • 中断请求不是快照的一部分，而是挂在最新快照上的一条 __interrupt__ write。
  • 分叉不改旧数据：新枝和旧枝共用一个父亲，旧的那条还能回看。
  • 每轮加 600 字节、跑 200 轮：默认 reducer 的检查点表 10.5 MB（轮数翻 4 倍，体积翻 15 倍），DeltaChannel 277 KB；代价是读回从 0.6 ms 变成 3.1 ms。

⑥细节

第一圈 · 注意事项

1分叉时不写 as_node，子 agent 全部重跑实测← ④ 机制 3
现象
回到“三个子 agent 刚交回来”那一步补一段结论，本想接着汇总，结果三个子 agent 又全跑了一遍，token 再花一次。
根源
update_state 要知道这次改动“算谁写的”，才能按版本号算出下一步。不写 as_node，框架自己猜；在 Send 扇出之后它猜成了 triage，新快照的 next 是三个 investigate（本机探针）。
做法
分叉一律写 as_node，写完先看 graph.get_state(new_cfg).next 对不对，再 invoke。
2长对话把检查点库撑大实测← ④ 机制 2
现象
每轮加一条 600 字节的消息，200 轮的检查点表 10.5 MB；一天几百条告警线程，库很快到几十 GB。
根源
每行快照存整份 channel_values，总量是 1 + 2 + … + N，按轮数平方长。Postgres 版按“键 + 版本号”单独存 blob（checkpoint_blobs 表），没变的键不重复存，但每步都在变的 messages 照样每次整份。
做法
state 里放结论，不放原始日志；对话按站 05 的压缩裁短；可以试 DeltaChannel（beta，磁盘格式还可能变）；定期删旧线程（坑 5）。
3发版改了节点名，等批准的线程静默“结束”实测← ④ 机制 3
现象
线程停在 approve 等批准。新版本把节点改名成 approval，旧线程的 next 变成空的；张三点批准，resume 不报错，直接返回旧的 state，写操作永远不会执行（本机探针）。
根源
快照里记的是“下一步是名叫 approve 的节点”，图本身不存。新图里找不到这个名字，框架就认为没有下一步了。
做法
节点名当成接口，发版不改；必须改时，先等旧线程跑完，或者写迁移脚本用 update_state 把它们挪到新节点；上线前拿几条真实的旧线程试恢复。
4state 里放了存不下的对象实测← ④ 机制 2
现象
节点把数据库连接对象、锁放进 state，一存盘就报 TypeError: Type is not msgpack serializable: Conn（锁是 _thread.lock）。
根源
每一步都要把整个 state 序列化进库。默认序列化器认得基本类型、消息、Pydantic 模型和 dataclass，认不得普通类的实例和系统资源。
做法
state 里只放数据；连接、客户端在模块级建好，或者通过 runtime context 传进节点。
5只增不删按源码← ④ 机制 2
现象
半年后检查点库成了最大的一张表，大部分是早就处理完的告警。
根源
框架每一步都插入新行，从不自己删；分叉还会多出整条枝。
做法
线程结束、审计落库以后调 saver.delete_thread(thread_id)；按保留期跑定时清理。审计要的东西另存（第 6 个下钻页），别指望检查点当审计日志。

第二圈 · 使用规范

  • 开发用 InMemorySaver 或 SqliteSaver，生产用 PostgresSaver：多个进程要能恢复同一条线程，库得是共享的。
  • thread_id 用业务键：告警指纹、工单号，重发的请求才能找回同一条线程。
  • state 只放结论和引用：原始日志放对象存储，state 里存路径，防坑 2。
  • 节点名、state 的键名当成对外接口：改名要有迁移，防坑 3。
  • 分叉写 as_node，先看 next 再跑：防坑 1。
  • 线程结束就清：防坑 5。

第三圈 · 优化和深处

检查点库是一个代码执行入口

langgraph-checkpoint 源码的说明写得很直白：默认的宽松模式下，检查点里存的任意可调用对象会在读回时被导入并执行；能直接写这个库的人，就可能借此执行代码。生产环境设 LANGGRAPH_STRICT_MSGPACK=true，只允许内置白名单里的类型，或者给序列化器传 allowed_msgpack_modules。这和站 07 讲的“不可信输入”是同一类问题。

Postgres 版的四张表

checkpoints（每步一行，不含大字段）、checkpoint_blobs（主键是线程 + 键名 + 版本号，没变的键不重复存）、checkpoint_writes（等同 SQLite 的 writes）、checkpoint_migrations（表结构版本）。来自 langgraph-checkpoint-postgres 3.2.1 源码。存盘时机由 durability 决定，见第 1 页坑 5。

下一圈

  • Pregel 循环源码（pregel/_loop.py、pregel/_checkpoint.py）：版本号怎么比、哪些任务能跳过。
  • 同一个 thread_id 被两个进程同时 invoke 会怎样，开源版有没有锁；官方服务端的“多任务策略”。
  • DeltaChannel 转正以后，默认的 messages 会不会改成只存改动。

自测

1. 用一句话说出检查点是什么

每个 superstep 结束时 state 的快照，加上这一步里每个任务交出的改动；有了它，失败、中断、换进程都能从最后一步接着跑，交过结果的任务不重跑。

2. 没有检查点时，notes 超时会多花什么？

整个流程从头再跑：再分诊一次，三个子 agent 全部重查，token 和时间都翻倍；停下等人的线程在进程重启后也全丢了。

3. 为什么 notes 重试时 logs 和 metrics 不重跑？

它们交的结果已经作为 writes 挂在这一步的快照上。恢复时框架先读快照和 writes，已经有结果的任务直接用结果。

从 ④ 机制 1 推出。

4. 预测：同一步里三个子 agent 都超时了，检查点库里多了什么？重试时谁会跑？

没有新快照，writes 表里多三条 __error__，挂在 step 1 上（本机探针实测）。重试时三个都要跑，因为没有一个交出了结果。

从 ④ 机制 1 推出：只有交了结果的任务能跳过。

5. 预测：一条消息 1 KB，对话跑到 100 轮，默认 reducer 的检查点表大约多大？

每行存整份：第 k 行约 k KB，总共约 1 + 2 + … + 100 ≈ 5000 KB，约 5 MB，和 ⑤ 里 200 轮 × 600 字节 ≈ 10.5 MB 是同一个量级。

从 ④ 机制 2 和 ⑤ 的 growth 推出。

6. 放回全景：第 6 站前后各发生了什么？检查点库挂了（Postgres 连不上），整条链路会怎样？

前面是第 5 站三个子 agent 各自查完，后面是第 7 站汇总。库连不上时每一步的存盘都会失败，图跑不下去；已经停在第 8 站等批准的线程也读不回来，张三点批准时找不到它。检查点库是这条链路的单点，要按数据库的标准做高可用。

从全景第 6、8、9 站推出。

档位：标准。本机跑过（2026-11-26，2 核 ARM，Python 3.13.18，langgraph 1.2.24，langgraph-checkpoint 4.3.2，langgraph-checkpoint-sqlite 3.1.3）：⑤ 的三个脚本；探针：不写 as_node 时的 next、节点改名后恢复、普通类和锁存盘报错、delete_thread 存在。按源码核对：SQLite 两张表的建表语句、Checkpoint 的字段、DeltaChannel 的说明和默认快照频率 100、langgraph-checkpoint-postgres 3.2.1 的四张表、LANGGRAPH_STRICT_MSGPACK 的安全说明、序列化器支持 Pydantic 和 dataclass。没有核对的：多个进程同时 invoke 同一线程的行为。
