省钱：提示词缓存和批处理

值班助手每次调用都带着同一大段前缀（规则、示例、排障手册），只有最后的告警不同。提示词缓存让服务端把这段前缀算好的 KV 留几分钟，下次一字不差地再来就直接读：Claude 命中部分只收输入价的 5%～10%，首字也快得多。批处理则是把不急的请求攒起来异步跑，所有 token 五折。实测 1900 token 的前缀，第 1 次首字 43 秒，后面 9 次 0.6 秒左右，按 Claude 价格算省 77%；可要是前缀开头放了请求号，缓存一次都命不中，开着缓存反而多花 23%。

①为什么需要：每次都为同一段手册付全价

在全景第 6 站，服务端要读完整个输入才能开始写；第 10 站按输入 token 结算。值班助手的分诊提示词里，排障手册和示例占了 1900 个 token，每条告警只有十几个 token。不做缓存，每次都为那 1900 个 token 付全价、等它被重读一遍。

②没有它会怎样：只能“少发”

老办法省得了吗代价
删减手册和示例省一点提示词质量下降，分诊更容易错（提示词那页）
换便宜的模型单价降了质量跟着降，诊断这类难任务不能换（选模型那页）
多条告警合成一次调用前缀只付一次一条告警要等凑齐一批；一次输出太长，一条错全部重来
提示词缓存前缀从第二次起按 5%～10% 计第一次贵 25%；前缀要一字不差；5 分钟内没人用就过期
批处理所有 token 五折异步，多数一小时内完成，最长 24 小时（按文档）：只适合不急的
不懂精华时的典型误用：照着文档在请求里加上 cache_control，就以为省钱了；没去看 usage.cache_read_input_tokens。前缀里只要有一个每次都变的东西（时间、请求号、乱序的 JSON），缓存就一次也不命中，还要每次多付 25% 的写入费（⑤ 实测多花 23%）。

③相邻方案：几种省钱手段，各适合什么

手段省多少（按 Claude 文档）前提
提示词缓存（5 分钟）命中部分：Opus / Sonnet 5.5 是输入价的 5%，其他多数模型 10%；写入 1.25 倍同样的前缀在 5 分钟内再来；前缀至少 512 token（Opus 5.5 等新模型）
提示词缓存（1 小时）命中同上；写入 2 倍两次请求间隔在 5～60 分钟之间
批处理（Message Batches）全部 token 五折不需要马上要结果；单批最多 10 万个请求
调低 effort少写思考 token任务不需要深想（推理模型那页）
换小模型 / 规则单价差几十倍在评测集上量过够用

本页学缓存和批处理：它们是“免费的午餐”：不改提示词、不换模型、不降质量。按 Claude 的成本优化指南，先拿这些不损失质量的手段，再考虑 effort 和换模型。

④原理：缓存的是前缀的 KV，批处理换的是“不急”

先知道这些
  • KV 缓存只认前缀：前面任何一个字变了，后面所有位置的 K、V 都作废（站 02 注意力 ④ 机制 3）。
  • 计费的四个数：input_tokens（没命中的输入）、cache_creation_input_tokens（写入）、cache_read_input_tokens（命中）、output_tokens（token 和计费）。

机制 1 · 拼接顺序决定缓存边界：tools → system → messages

按 Claude 文档，服务端按 tools、system、messages 的顺序把请求拼成一段前文，缓存就是这段前文的前缀。你可以在某个块上打 cache_control 断点（最多 4 个），也可以在请求顶层写一个 cache_control 让服务端自动在最后一个可缓存的块上打。规则只有一条：断点之前的内容一字不差，下次才能命中。

放在哪值班助手里放什么会不会变
tools工具定义（站 04）固定，而且顺序固定
system角色、输出格式、示例、排障手册固定 ← 断点打在这里
messages 前面多轮时的历史只增不改，自动缓存会跟着往后挪
messages 最后这次的告警、当前时间、请求号每次都变 ← 只能放这里

机制 2 · 计价：写一次贵一点，读多次便宜很多

Opus 5.5（美元 / 百万 token）单价相对输入价
普通输入41
写入缓存（5 分钟）51.25
写入缓存（1 小时）82
命中缓存0.200.05

所以 5 分钟档只要命中一次就回本：1.25 + 0.05 = 1.3，小于两次全价的 2。反过来，一次都不命中时开缓存比不开贵 25%。命中会刷新计时；连续有流量时，5 分钟档的条目可以一直活着（按文档）。缓存按模型隔离，换模型就是全新的缓存。

机制 3 · 批处理：把“立刻要”换成“过一会儿给”

Message Batches 接口一次收下最多 10 万个请求（每个和普通 Messages 请求一样，带一个你起的 custom_id），服务端在空闲算力上慢慢跑，多数一小时内完成、最长 24 小时，结果保留 29 天，所有 token 五折（按文档）。服务端能把它们塞进流量低谷，于是愿意打折。结果的顺序不保证，要按 custom_id 对回去。

为什么这样设计：为什么缓存只给几分钟、批处理要等几小时

短时缓存 + 异步批处理

  • KV 很占显存（站 02：一个 token 可能几百 KB），只能留一小会儿；短时间内重复出现的前缀正好最值得留。
  • 命中刷新计时，持续使用的前缀会一直留着，冷门的自然淘汰：和 LRU 缓存一个思路。
  • 批处理让服务端自己安排时间，把算力用在低谷，所以能打折。
  • 代价：缓存要求逐字相同、会过期；批处理不能实时。

长期缓存 / 全部实时

  • 每个用户的每段前缀都长期存着，显存和存储撑不住；命中率反而低。
  • 全部实时，服务端只能按峰值备机器，成本没法降。
决定胜负的约束：模型服务最贵的资源是加速卡的显存和算力。缓存用“短期占一点显存”换“少算一大段”，批处理用“时间上的灵活”换“填满低谷”。两者都把成本优势分给了愿意配合的调用方。

⑤亲眼看到：命中前后的延迟和成本（过关题 2）

这台机器没有 Claude 的 key，所以延迟用本机 llama-server 实测（它和 Claude 一样会自动复用相同前缀的 KV，并在 usage 里报 cache_read_input_tokens），成本用实测的 token 数乘 Claude 的单价换算。前缀约 1900 token：输出格式说明 + 排障手册；10 条不同的告警依次发。另一组在系统提示开头加上请求号（每次不同）。

⑤main.py（换算成本）完整代码 →
PRICE = {"Opus 5.5": (4.0, 5.0, 0.20, 20.0), ...}   # 输入、写入、命中、输出

def cost(r, model, cached):
    pin, pwrite, pread, pout = PRICE[model]
    if not cached:                                     # 不开缓存：全按输入价
        return ((r["fresh"] + r["read"]) * pin + r["out"] * pout) / 1e6
    var = min(15, r["fresh"])                          # 这次的告警
    return (r["read"] * pread + (r["fresh"] - var) * pwrite   # 没命中的前缀：按写入价
            + var * pin + r["out"] * pout) / 1e6

读出来的结论
  • 延迟：命中后首字从 43 秒降到 0.6 秒左右（本机小模型，读输入慢，所以差得格外大；Claude 上绝对值小得多，但“读输入占大头、缓存能砍掉它”的形状一样）。
  • 成本：10 次里 9 次命中，输入的 89% 走了缓存读取价，按 Opus 5.5 算总价省 77%（剩下的钱主要是第一次的写入和每次的输出）。
  • 前缀一变全白搭：请求号放在开头，3 次全部冷读，开着缓存每次都按 1.25 倍写入、一次也读不到，多花 23%。
  • 一个意外的旁证：第一次跑 break 时请求号是固定的 req-1000～1002，重跑时和上一轮一字不差，于是全部命中了服务端还留着的缓存（首字 0.1 秒）。改成用时间戳生成请求号，才测出真实情况。
到这里已经能交差了：你能把提示词按“固定在前、变化在后”组织，打开缓存，并用 usage 证明它命中了、省了多少；也知道哪些调用该走批处理。
已知还没处理的细节：前缀里藏着变量（坑 1），前缀太短（坑 2），间隔超过 5 分钟（坑 3），批处理当实时用（坑 4）。

⑥细节：缓存悄悄失效的几种方式

第一圈 · 注意事项

1前缀里藏着每次都变的东西实测← ④ 机制 1
现象
cache_read_input_tokens 一直是 0，账单还比不开缓存高。
根源
请求号、当前时间、用户名、用 HashMap 拼出来顺序不定的 JSON、按条件增减的工具列表，只要在断点之前，前缀就每次不同。
做法
易变的东西全部挪到 messages 最后；序列化排序键；工具集合固定。上线后把命中率（命中 ÷ 总输入）放进监控，掉到 0 就报警。
2前缀太短，缓存不生效也不报错← 产品规则
现象
加了 cache_control，写入和命中都是 0。
根源
按 Claude 文档，前缀短于模型的最小值不会缓存（Opus 5.5、Sonnet 5.5、Haiku 5.5 等是 512 token，部分老模型是 1024～4096），也不报错。
做法
只给够长的稳定前缀打断点；换模型时查一下它的最小值。
3请求间隔比缓存寿命长← ④ 机制 2
现象
一个用户隔 20 分钟问一次，次次都是写入，从来没命中。
根源
5 分钟档到期就没了；只有命中才会刷新计时。
做法
间隔在 5～60 分钟的，用 1 小时档（写入 2 倍，至少命中两次才划算）；持续有流量的服务，5 分钟档会被一直刷新，最划算。
4把批处理当实时接口用← ④ 机制 3
现象
分诊改成走批处理省一半钱，结果告警半小时后才分诊完。
根源
批处理是异步的，多数一小时内完成、最长 24 小时（按文档），不承诺多快。
做法
只把不急的放进批处理：夜里的复盘报告、历史工单的批量打标签、评测集跑分（站 08）；结果按 custom_id 对回去，失败的单独重跑。

第二圈 · 使用规范

  • 提示词分三段：固定区（tools、system）→ 增长区（历史）→ 易变区（这次的输入）。防坑 1。
  • 每次调用记下四个用量：输入、写入、命中、输出；按接口算命中率和“每次调用的实际单价”。防坑 1、3。
  • 同一类调用固定一个模型：缓存按模型隔离，在几个模型之间轮着用，谁都攒不起缓存。
  • 调用分成“要实时的”和“能等的”两条路：能等的统一进批处理队列。防坑 4，也和限流那页的“削峰”配合。

第三圈 · 更深一层

预热

按 Claude 文档，可以在真正的请求到来之前，用 max_tokens: 0 发一次只为写缓存的请求，让第一个用户也享受命中的延迟；持续空闲时也能用它“续命”。预热本身要付写入费。

多轮对话的缓存

多轮时历史只增不改，顶层的自动缓存会把断点跟着往后挪，每一轮都能命中前面所有轮次（Messages API 那页实测了每轮的缓存读在增长）。中途改了历史里的一个字，从那里往后全部失效。

实验台：缓存和批处理，一个月能省多少

先猜：前缀 1900 token，但开头放了请求号（每次都变）。开着 5 分钟缓存，一个月的输入费用比不开缓存多还是少？

口径：每月 30 天、每天 2000 次调用；每次除前缀外还有 15 个输入 token、40 个输出 token。命中规则按文档简化：间隔短于寿命就命中，否则每次都是写入；写入 1.25 倍（5 分钟）或 2 倍（1 小时）。批处理按文档“所有 token 五折”直接乘 0.5，并假设缓存照样命中，这是理想情况。

自测

1. 用一句话说出这一页的精华

把不变的放前面、打上缓存，5 分钟内再来就按 5%～10% 计、首字也快；不急的请求走批处理五折；前缀里只要有一个每次都变的字，缓存就白开还多花钱。

2. 为什么缓存只能按前缀匹配？

每个位置的 K、V 都依赖它前面所有的 token；前面变了，后面的计算结果全都不一样，只能重算。

从 ④ 机制 1 和站 02 注意力 ④ 推出

3. 5 分钟档为什么只要命中一次就回本？

写入 1.25 倍 + 命中 0.05 倍（Opus 5.5）= 1.3 倍，小于不开缓存的两次全价 2 倍。

从 ④ 机制 2 推出

4. 预测：值班助手白天每 30 秒一条告警、夜里一小时一条，用哪个缓存档？

白天 5 分钟档：持续命中、持续刷新，写入最便宜。夜里间隔一小时以上，两个档都过期，缓存基本没用，开着反而每次多付写入费；可以按时段切换，或者夜里干脆不打断点。

从 ④ 机制 2 和坑 3 推出；实验台可以算

5. 预测：把分诊的模型从 Sonnet 5.5 换成 Opus 5.5 的那一刻，缓存会怎样？

全部失效：缓存按模型隔离，Opus 那边是空的，第一批请求全部冷读、全部付写入费，首字时间也回到冷读的水平。

从 ④ 机制 2 推出

6. 放回全景：缓存在第几站起作用？如果第 1 站的提示词把当前时间放到了 system 开头，第 6 站和第 10 站会怎样？

在第 6 站（模型先查缓存再读输入），钱在第 10 站结算。时间放在 system 开头：第 6 站每次都冷读整个前缀，首字时间回到冷读的水平；第 10 站每次都按 1.25 倍付写入费、一次读不到，比不开缓存还贵。

档位：标准。本机跑过（2026-11-22，2 核 ARM，官方 anthropic SDK 2.12.0 → llama.cpp b12618，Qwen2.5-0.5B-Instruct Q4_K_M）：固定前缀 10 次的新算、缓存读和首字时间；前缀开头放请求号 3 次的同样数据；成本是实测 token 数乘 Claude 单价换算的，不是 Claude 的真实账单。按文档（Claude API，2026-11）：缓存的计价倍数、5 分钟和 1 小时档、命中刷新计时、最小可缓存长度、tools → system → messages 的顺序、最多 4 个断点、按模型隔离、预热；批处理的五折、容量、完成时间和结果保留期、custom_id。批处理没有在本机运行。
