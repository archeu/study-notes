RAG 流水线：切块、向量化、检索、重排、生成

模型的权重里没有你的运维手册。RAG 的做法是：每次提问，先从自己的资料里找出最相关的几段，连同问题一起交给模型，让它照着写、标出处。知识放在检索库里，不在权重里：资料随时能改，答案能点回原文；代价是检索拿到的是“最像的”，不是“对的”，漏了，模型就只能说不知道，或者编。

①为什么需要：模型没见过你的手册

在全景第 3～10 站，这一段要解决的是：你问“本地缓存上线前必须配置哪两项？”，答案只写在交易组的 order-svc 运维手册 v3.2 §4.3 里。Qwen3-1.7B 训练时用的是公开文本，这份手册它从来没见过。

②没有它会怎样：闭卷答，答得又快又笃定

同一个模型、同样的问题，一次直接问（闭卷），一次先检索出 3 片资料再问。下面是本机原样的回答：

问题（标准答案）闭卷给前 3 片资料（RAG）
本地缓存上线前必须配置哪两项？
（maximumSize 和 expireAfterWrite）		“缓存过期时间配置和缓存策略配置。”泛泛而谈，没有一个参数名。“maximumSize（或 maximumWeight）和 expireAfterWrite [1]。”
想临时停用本地缓存，改哪个开关？
（order.cache.local.enabled）		“cache.disable または cache.off”：编了两个开关名，还混进了日语。“资料里没有提到具体改哪个开关……”正确的那片（附录 C 扫描页）排第 5，没进前 3。说不知道，比编一个强。

能不能不检索，把整个知识库塞进提示？这个库 31 片约 2.7K token，本机读一遍要 70 秒左右，每问一次都要重读；一个真实团队的知识库有几百份文档、几百万 token，任何模型的上下文窗口都装不下。估算，按本机实测的读提示速度 38 token/s。

  • 闭卷：模型对私有资料一无所知，却照样给出具体的数字和名字，读的人分不出真假。
  • 整本塞进提示：资料一多就装不下；装得下也是每问一次就为整个库付一次钱、等一次。
  • RAG：每次只搬最相关的几片（这里 3 片约 330 token），答案带编号，能点回手册原文核对。
  • RAG 的代价也在表里：检索没取到对的那片，模型就没东西可照着写。
不懂精华时的典型误用：以为接了 RAG，模型就“学会了”手册。它什么都没学会：每次提问都是重新查、重新读。检索漏了，答案就漏了；所以 RAG 的质量首先是检索的质量。

③相邻方案：让模型用上私有资料，有四条路

评判要求来自值班助手这一站：资料每周在改，答案要能点回原文，资料不出公司，每次提问的成本可控，资料量会涨到成千上万页。

要求整本塞进提示微调：把资料训练进权重RAG：先检索再生成工具直接查：调 API 查结构化数据
资料改了马上生效能：下次提问就用新的不能：每改一次重训一次，小时到天级能：新片入库就能查到（增量同步）能：查的是实时数据
答案能点回原文差一点：资料在提示里，但模型不一定说用了哪段不能：知识化进参数，说不出出自哪里能：每片带编号和页码能：返回值就是证据
资料量上万页不能：超出上下文窗口能，但每次重训成本跟着涨能：每次只取几片能，但只适合有接口的结构化数据
每次提问的成本高：每问一次付一次全库的 token低：提示里没有资料中：几片资料，加一次检索和重排中：要几轮工具调用
适合的资料一两份短文档风格、格式、领域说法（站 11）手册、故障单、笔记这类非结构化文本监控指标、工单状态、数据库里的行
值班助手怎么选不选不选：事实会变，又要出处选：手册、故障单走 RAG并用：实时指标走站 04 的工具

本页学 RAG：资料是非结构化文本、会变、要出处，就走 RAG；数据在系统里、有接口，就让 agent 调工具去查。站 06 第 9 页会把 RAG 也做成一个工具，交给 agent 决定什么时候查。

④原理：两段路，五个动作

先知道这些
  • Embedding（向量化）：一个模型把一段文字变成一串定长的数（这里 1024 个），意思近的两段，数也近。站 02 讲过：Embedding：文本变向量，意思近的靠得近。
  • 余弦相似度：两个向量夹角的余弦，1 是方向完全一样，0 是不相干。向量先归一化成长度 1，点积就是余弦：够用的数学：向量、点积和概率。
  • token 和上下文窗口：模型按 token 读和写，一次能读的总量有上限，读得越多越慢越贵：上下文窗口。
  • 片（chunk）：检索的单位，一般是文档里的一节或几段。这一页直接用全景那份切块代码，怎么切得好留给“清洗、切块策略和元数据”那页。

机制 1 · 两段路：资料进来时建索引，每次提问时查

RAG 分成两段，时间上不在一起：索引阶段只在资料进来或变了时做一次；查询阶段每次提问都做。两段之间只靠一样东西相连：同一个 Embedding 模型。资料用它变成向量存起来，问题也用它变成向量去比。

准备点“下一步”。

“五个动作”就是页面标题里的切块、向量化、检索、重排、生成；拼提示是生成的前半步。重排是可选的，⑤ 的最小案例先不用它，再用它对照。

机制 2 · 检索找的是“最像的”，不是“对的”

检索只做一件事：算问题向量和每一片向量的余弦，按大小排。它不知道哪片“对”，只知道哪片“像”。“想临时停用本地缓存，改哪个开关？”这个问题，所有讲本地缓存的片都很像：

Java 老朋友：RAG ≈ 先查缓存再回源

像：先去外部存储取东西，再拼出答案；存储里的东西改了，答案跟着变，不用改调用方（模型）。

不像：缓存按 key 精确命中，没命中就是 null；检索按远近找“最像的 k 个”，永远会返回 k 个，哪怕没有一个相关，也不会告诉你“没命中”。

所以有两件事要自己做

一是让对的那片尽量排进前面：混合检索、重排、改写查询，站 06 后面几页的事。二是承认会漏：资料不相关时，要有办法说“不知道”，而不是硬答。⑥ 的坑 1、坑 2 都是这件事。

机制 3 · 模型只照提示写：资料进上下文，规则管住它

生成这一步没有任何“检索专用”的魔法：资料和问题被拼成一段普通的提示，模型照旧一个 token 一个 token 往下续写。它之所以会照着资料答，是因为提示里有资料、有规则；它之所以还会编，是因为它的权重里本来就有一套“一般情况下”的说法。

三条规则各管一件事

  • “只根据下面的资料”：把模型从凭记忆答拉回照资料答。
  • “句末写出处编号”：每句话都能点回某一片，读者能核对，评测也能逐句查。
  • “资料里没有就说没有”：给模型一个不编的出口；② 里第 2 题它就是走了这个出口。
  • 规则是提示，不是约束：小模型照样会漏标、标错，全景里它还加了一句资料里没有的“避免缓存雪崩”。要靠 ⑥ 和评测页去查。

为什么这样设计

逼出 RAG 的是三条约束：权重改起来又慢又贵，上下文窗口有上限、按 token 收钱，答案要有出处。把知识放到模型外面、每次只搬一小部分进来，是同时满足三条的唯一办法。

知识在外面，提问时检索（RAG）

  • 手册改了，重新切块、算向量就行：全景里一份 12 页的手册入库约 25 秒。
  • 每句话能指回某一片，片上有文档、版本、页码。
  • 每次只搬几片进提示：这里 3 片约 330 token，和库有多大无关。
  • 代价：多了检索这一环，检索漏了答案就漏了；多一次 Embedding 调用，加重排的话再多几十次打分。

知识在里面：微调进权重

  • 手册每改一次，就要重新训练、重新评测、重新发布一个模型。
  • 答案说不出出处：知识被压进几十亿个参数里，没有“第几页”。
  • 微调更擅长学“怎么说”（格式、语气、领域用词），学“哪个开关叫什么”这种具体事实不可靠，还可能把别的能力弄坏（站 11）。
决定胜负的约束：资料会变，而且要出处。只要这两条有一条成立，事实就该放在模型外面；微调留给“说话方式”。

为什么检索要分两步：先粗筛，再精排

每次提问的开销31 片（本页）31 万片（中等团队）
向量检索：1 次 Embedding + N 次点积几十毫秒，几乎全在 Embedding 那一次暴力点积几百毫秒起；用 HNSW 索引只看一小部分（第 4 个知识点）
交叉编码给全部片打分31 对 × 0.6 秒 ≈ 19 秒31 万对 × 0.6 秒 ≈ 52 小时，不可能
先粗筛 20 段，再精排20 对 ≈ 12 秒（本机 CPU；GPU 上是百毫秒级）还是 20 对：精排的开销和库多大无关

0.6 秒一对是本机 2 核 CPU 实测（全景那次 80 对 47.7 秒）；31 万对是按它乘出来的 估算。

# ① 切块（索引阶段，资料不变就只做一次）
def load_chunks():
    chunks = []
    for name in DOCS:                                   # 手册 v3.2、两张故障单、三篇笔记
        d = kb.doc_of(kb.DATA / name)
        chunks += kb.chunk(d, kb.clean(kb.parse(d)))
    return chunks

# ② 向量化：服务端已经归一化，点积就是余弦
def embed(texts):
    r = post(EMBED + "/v1/embeddings", {"input": texts})
    return np.array([x["embedding"] for x in sorted(r["data"], key=lambda x: x["index"])])

# ③ 检索：问题前面加一句任务说明（Qwen3-Embedding 的用法），和每一片比
def retrieve(q, chunks, M, k=3):
    qv = embed([f"Instruct: {kb.QUERY_TASK}\nQuery:{q}"])[0]
    sims = M @ qv
    top = np.argsort(-sims)[:k]
    return [(chunks[i], float(sims[i])) for i in top]

# ③' 重排（可选）：问题和每段成对读，重新打分
def rerank(q, hits, k=3):
    r = post(RERANK + "/v1/rerank", {"query": q, "documents": [c.text for c, _ in hits]})
    order = sorted(r["results"], key=lambda x: -x["relevance_score"])[:k]
    return [(hits[x["index"]][0], round(x["relevance_score"], 3)) for x in order]

# ④ 拼提示 ⑤ 生成
def build_messages(q, hits):
    src = "\n\n".join(f"[{i}] （{c.doc_key} {c.version} {c.section.split(' › ')[-1]}）{c.text}"
                      for i, (c, _) in enumerate(hits, start=1))
    rule = "只根据下面的资料回答，句末写出处编号，比如 [1]；资料里没有就说“资料里没有”。用中文简短回答。"
    return [{"role": "system", "content": rule}, {"role": "user", "content": f"资料：\n{src}\n\n问题：{q}"}]

def generate(messages, max_tokens=200):
    r = post(GEN + "/v1/chat/completions", {"messages": messages, "temperature": 0, "max_tokens": max_tokens,
                                            "chat_template_kwargs": {"enable_thinking": False}})
    return r["choices"][0]["message"]["content"].strip(), r.get("timings", {})

1检索永远返回 k 片，不会说“没命中”实测← ④ 机制 2
现象
问“改哪个开关”，前 3 片全是讲本地缓存的，余弦 0.60～0.65，看上去都很相关，没有一片写着开关名。
根源
检索按“像不像”排名，取前 k 个。它没有“命中 / 没命中”的概念；余弦挤在一起时，也没有一条阈值能分开对错。
做法
先多取（10～20 片）再重排，用重排分做阈值：本例对的那片是唯一正分（+1.20），其余都是负分。全部低于阈值时不调生成模型，直接答“知识库里没找到”，或者改写问题再查一轮（全景第 6 站那条虚线）。阈值要用评测集定，不同重排模型的分数尺度不一样。
2资料不相关时，小模型会复读到 max_tokens实测← ④ 机制 3
现象
Qwen3-1.7B 先正确地说了“资料里没有”，然后把这句话换着说法写了十几遍，直到 200 token 的上限。
根源
生成就是一个 token 一个 token 地续写：提示里没有能照着写的东西，规则又不许它编，小模型最容易落进的就是重复自己刚写的话。
做法
资料为空或全部低分时不让模型写（坑 1 的阈值）；max_tokens 按答案长度设紧（单问答 100 token 左右就够）；llama.cpp 可以加 repeat_penalty。换更大的模型复读会少很多，但前两条照样要做。
3问题少了那句任务说明实测← ④ 机制 1
现象
30 个问题直接拿原话去算向量，前 1 片命中率从 0.77 掉到 0.70（2 题掉出第一名）；前 3 片都是 0.90。
根源
两段路靠同一个 Embedding 模型相连，但问题和片在模型眼里是两种角色。Qwen3-Embedding 是“看指令”的模型，模型卡要求问题前面写 Instruct: …\nQuery:…，片不加。这种约定每个模型不一样。
做法
照模型卡写问题的格式（有的模型要 query: / passage: 前缀，有的什么都不要）；换 Embedding 模型时重读模型卡、重跑评测。
4片离开原文，就丢了上下文实测← ④ 机制 1
现象
“11 月 8 日那次 Full GC 是什么原因？”正确的片排第 3；“OrderDetailCache 打算怎么修？”排第 8，前面是手册 §4.3 和 Caffeine 笔记。
根源
每一片单独算向量。故障单“根因”那一片只有“按月导出一次把 41 万行……”，日期在另一片“基本信息”里；片名里的编号写的是 20261108，问题里说的是“11 月 8 日”。
做法
算向量时在片前面带上文档标题和章节（本页已经这样做了，见 embed_text()），还可以带日期、服务名这类元数据；或者检索小片、交给模型时换成它所在的整节（父子块，第 7 个知识点）。
5引用编号会挂错实测← ④ 机制 3
现象
重排后答案的内容完全对（order.cache.local.enabled），出处却写成 [2]；开关在 [1] 里。同一个问题另一次运行写的是 [1]。
根源
“句末写编号”只是提示里的一条规则，模型是在续写文字，不是在查表；编号对不对没有任何机制保证。
做法
生成后逐句回查：编号存在吗，这一片里有没有句子的关键内容（全景第 11 站，评测页会做得更严）；对不上的句子标出来或重写。也可以让模型直接摘抄原文片段当引用，再用字符串匹配核对。

第二圈 · 使用规范

  • 每次回答都记下检索结果：问题、每片的 id 和分数、重排分、最终提示、回答。防的是答错了分不清是检索错还是生成错。
  • 检索和生成分开评测：先量正确的片在不在前 k（命中率），再量答案是不是都有依据（忠实度）。防的是把检索问题当成提示词问题去调。
  • 每一片记下 Embedding 模型名，换模型就全量重算。防的是新旧向量混在一个库里（全景预测题 4）。
  • 片带出处元数据：文档、版本、章节、页码；提示里给模型看编号，给读者看出处。防的是答案说不清出自哪一版。
  • k、重排留几片、分数阈值、max_tokens 写进配置，改了先跑评测再上线。防的是凭一两个问题的感觉调参。

第三圈 · 优化和深处

k 的账：多取一片，多付一片的 token

提示长度 ≈ 规则和问题（约 73 token）+ k × 每片平均 86 token。k 从 3 到 8，命中率从 0.90 到 1.00，提示变成 2.3 倍；本机 CPU 上每多 100 token 多读约 2.6 秒。下面的实验台用的就是这 30 题的实测排名。

资料放在哪个位置

长提示里，模型对开头和结尾的内容用得最好，中间的容易被忽略（Liu 等，Lost in the Middle，2023）。所以按分数从高到低放、最相关的放最前面；片多的时候别指望第 7 片还能被认真读。按文档

小库的命中率是虚高的

这里只有 31 片，k=8 已经是全库的四分之一，命中率到 1.00 不稀奇。库到 3 万片时，讲本地缓存的片会有几百个，前 k 名更挤，同样的 k 命中率会掉。评测集要跟着库一起长大。

本机的时间花在哪

每次运行 rag_min.py 都重算 31 片的向量，约 25 秒；索引应该存下来（全景里的 pgvector），每次提问只算一个问题向量。重排 0.6 秒一对、生成 10 token/s 是 2 核 CPU 的数，换 GPU 后重排降到毫秒级，大头变成生成。

实验台：k 取几

先猜：只走向量检索，把 k 从 3 提到 8，30 个问题的命中率和提示长度各会怎样？

实测 命中率和每道题的排名来自 rag-pipeline/main.py（30 题、31 片、只走向量检索、不重排）；提示长度 = 73 + k × 86.2 token，读提示时间按本机实测 38.4 token/s 算，是估算。

下一圈

  • 长上下文 + 提示词缓存：库只有几十万 token 时，整本塞进去再缓存前缀，可能比 RAG 更简单；什么时候划算。
  • GraphRAG：先从资料里抽出实体和关系建成图，回答“这半年哪些故障和本地缓存有关”这种跨很多文档的问题。
  • 先判断要不要查（自适应 RAG、Self-RAG）：闲聊和常识题不检索，事实题才检索；第 9 个知识点 Agentic RAG 接着讲。
  • RAG 和微调一起用（RAFT 等）：用“带干扰资料”的样本微调，让模型学会从几片里挑出对的那片。
  • 多模态 RAG：图表、截图直接算向量，不先 OCR 成文字。

↺回到⑤：改一改

  1. 加一道阈值：--rerank 时，重排最高分小于 0 就不调生成模型，直接返回“知识库里没找到”。问“pay-svc 的 P99 告警阈值是多少？”（库里没有），应该秒回而不是写一段。（坑 1）
  2. 拿掉任务说明：把 retrieve() 里的 Instruct: … 去掉，跑 main.py，看 k=1 的命中率是不是掉到 0.70。（坑 3）
  3. 给故障单的片补日期：在 embed_text() 里把故障的开始时间写成“2026 年 11 月 8 日”，看 Q27～Q29 的排名。（坑 4）
  4. 治复读：max_tokens 改成 80，再通过 extra 字段传 repeat_penalty: 1.1，用不带重排的那次再问一遍开关的问题。（坑 2）

自测

1. 用一句话说出这一页的精华

知识放在模型外面的检索库里，每次提问只把最像的几片搬进提示，让模型照着写、标出处；资料能随时改、答案能核对，代价是检索拿到的是“最像的”不是“对的”，漏了答案就漏了。

2. 不用 RAG 的两种老办法，各疼在哪？

闭卷：模型没见过私有资料，却照样给出具体的数字和名字（实测编了“24 小时内回滚”和一个日语开关名）。整本塞进提示：资料一多就超出上下文窗口；装得下也是每问一次为整个库付一次 token、等一次（31 片本机读一遍约 70 秒）。

3. 为什么检索会把“讲本地缓存的笔记”排在“写着开关名的附录 C”前面？

检索只按向量的远近排，问题里“本地缓存”这层意思和笔记很像，“开关名”这件具体的事在余弦里只占一小部分；前 6 名的余弦差不到 0.09。它不判断对错，也永远会返回 k 片。

从 ④ 机制 2 推出。

4. 预测：库从 31 片涨到 3 万片，k 还是 3，前 3 片命中率会怎样？

多半会掉。讲同一主题的片多了几百倍，余弦本来就挤在一起，前 3 名被“也很像”的片占掉的机会更大。要靠重排、混合检索、元数据过滤把对的那片捞回来，并且用更大的评测集来量。

从 ④ 机制 2（按像不像排、分数挤）推出。

5. 预测：Embedding 模型换成另一家的，只重算了问题的向量，片的向量没动，会怎样？

检索结果会变得毫无道理：两个模型的向量空间不一样，新问题向量和旧片向量之间的余弦没有意义。不会报错，命中率直接塌。换模型要全量重算片的向量。

从 ④ 机制 1 推出：两段路只靠同一个 Embedding 模型相连。

6. 预测：重排后只留 1 片，开关那题和“为什么没回滚”那种题各会怎样？

开关那题照样对：附录 C 是唯一正分，第 1 名就是它。“为什么没回滚”要两片拼起来：手册 §4.2 讲 30 分钟规则，故障单时间线讲 10:00 发布、10:42 告警；只留 1 片，模型只能看到一半，要么写“资料里没有”，要么用自己的话补另一半。

从 ④ 机制 3 推出：模型只看提示里有的东西。

7. 放回全景：第 8 站前后各发生什么？Embedding 服务挂了，整条链路会怎样？

第 7 站把检索语句和过滤条件交给第 8 站；第 8 站之后，第 9 站重排、第 10 站生成。Embedding 挂了，向量那一路没了：全景用的是混合检索，还剩 BM25 一路，只能找字面一样的词，换了说法的问题会漏；如果只有向量一路，第 9 站没有候选，第 10 站拿到 0 片。全景实测里 0 片时模型照样写了三句，还编了 [3][4][5]，所以第 10 站之前必须判空。

从全景第 7～10 站和本页坑 1 推出。

档位：标准。实测 2026-11-25，本机 2 核 ARM、11 GB：llama.cpp b12618 跑 Qwen3-Embedding-0.6B Q8_0、bge-reranker-v2-m3 Q8_0、Qwen3-1.7B Q4_K_M；Python 3.13、numpy；闭卷和 RAG 对照 3 题，30 题的向量检索排名，去掉任务说明的对照。按文档（已核对）：Qwen3-Embedding 模型卡对查询指令的要求；Liu 等 Lost in the Middle（2023）。31 万片的耗时是按本机实测速度乘出来的估算。
