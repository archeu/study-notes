Embedding：文本变向量，意思近的靠得近

Embedding 模型把一整段文字变成一个固定长度的向量（本页的模型是 1024 个数），训练目标是让意思相近的两段文字向量方向相近。于是“找相似故障”变成了“找余弦最大的向量”。实测“数据库连不上了，下单一直转圈”和“MySQL 连接池耗尽”一个词都不重合，余弦却排第一；而按字重合，GC 提问的第二名竟是“支付网关 502”。但它分不清“是”和“不是”。

①为什么需要：值班时想知道“以前有没有遇到过这种事”

在全景第 4 站，模型里已经有了“token 变向量、意思近的靠得近”的思想；这一页要解决的是它在工程上的用法：值班助手收到“订单服务 20:15 变慢，疑似 GC 导致”，要从几千条历史工单里找出描述同一类故障的那几条，交给模型参考。历史工单是不同的人、用不同的说法写的。

④原理：读完整段，压成一个向量；训练时把配对的拉近

先知道这些
  • 向量、余弦：方向越一致余弦越接近 1；向量归一化成长度 1 后，点积就等于余弦（够用的数学 ④）。
  • 注意力：每个位置能从前文取信息（注意力 ④）。

机制 1 · 两种“向量”：全景第 4 站的是“每个 token 一个”，Embedding 模型给的是“整段一个”

机制 2 · 怎么学会“意思近就靠近”：对比学习

机制 3 · 余弦是“相对”的：看排名，不看绝对值

⑤ 里所有分数都挤在 0.33～0.69 之间，连“首页白屏”和 GC 提问都有 0.39。这很常见：同一种语言、同一个领域的文本，向量本来就大致朝一个方向。所以用排名取前几条，而不是定一个“大于 0.8 才算相似”的死门槛；真要定门槛，得在自己的数据上量出来。

为什么这样设计：为什么压成一个定长向量

一段文字 → 一个定长向量

  • 离线一次算好存起来，在线只要算提问那一个向量，再做几千次点积，毫秒级。
  • 向量库能建近似最近邻索引，几百万条也能快速找（站 06）。
  • 代价：一整段压成 1024 个数，细节会丢：否定词、具体数字、编号都可能被“抹平”。

每次让模型把提问和每条工单放在一起读

  • 两段文字一起过注意力，能看到彼此，判断更准（这叫“重排模型”，站 06 用在第二步）。
  • 每条工单都要和每个提问一起算一遍，几千条就是几千次模型调用，不能预先算好。
决定胜负的约束：检索要在毫秒内从海量文本里挑出几条，只有“提前算好、在线只做点积”的方式扛得住。精度不够的部分，交给第二步的重排或者大模型。

⑤亲眼看到：8 条工单、3 个提问、两个坑

本机第三个 llama-server（8092 端口）以向量模式加载 Qwen3-Embedding-0.6B（640 MB，Q8 量化），启动参数 --embeddings --pooling last。8 条历史工单涵盖 GC、数据库、支付、前端四类；3 个提问故意换了说法。

⑤main.py（核心）完整代码 →
def embed(texts):
    r = post("/v1/embeddings", {"input": texts})
    return [d["embedding"] for d in r["data"]]          # 每段 1024 个数，长度已是 1

tv = embed(TICKETS)                                     # 离线：工单各算一次
for q, v in zip(QUERIES, embed(QUERIES)):               # 在线：提问算一次
    cos = [dot(v, t) for t in tv]                       # 归一化后点积 = 余弦
    top3 = sorted(range(len(TICKETS)), key=lambda i: -cos[i])[:3]

读出来的结论
  • 换了说法也找得到：三个提问按余弦的第一名都是对的那一类，包括几乎没有共同字的“数据库连不上 → 连接池耗尽”“付完钱没付款 → 回调超时”。
  • 按字重合被常见词带偏：GC 提问的第一名是“堆内存打满…订单服务重启”（沾了“订单服务”），第二名是毫不相干的“支付网关 502”。
  • 否定几乎看不出来：“是 GC”和“不是 GC”余弦 0.972，比“是 GC”和“是数据库”（0.876）还近。
  • 指令前缀要照模型说明写：用说明里的英文模板，GC 提问的第一名变成最贴切的 Full GC 工单，领先也更明显；我自己写的中文指令让两个提问的第一名都跑偏成“慢 SQL”。前缀是模型训练时见过的格式，乱改会伤效果。
  • 分数挤在一起：所有余弦都在 0.33～0.69，“首页白屏”也有 0.39。只能看排名，不能拍脑袋定门槛。

⑥细节：向量检索的坑

第一圈 · 注意事项

1“是”和“不是”、“超过”和“没超过”几乎一样实测← ④ 机制 2
现象
“是 GC 导致的”和“不是 GC 导致的”余弦 0.972；找“排除了 GC 的故障”，找回来的全是 GC 故障。
根源
对比学习按“话题相关”配对，否定句和肯定句谈的是同一件事；一整段压成一个向量，一个“不”字的分量很小。
做法
向量只负责召回“同一话题”的候选，结论性的判断（是不是、超没超）交给大模型读原文，或者用结构化字段过滤。
2查询和文档的写法和模型说明不一致实测← ④ 机制 2
现象
自己写的中文指令前缀让 3 个提问里的 2 个找错了第一名。
根源
模型训练时见过的是某种固定格式（查询加指令、文档不加）；输入格式变了，向量就落到它没练过的地方。
做法
照模型说明写前缀；查询和文档各用各的格式；任何改动都在一小批真实提问上量一下排序再上线。
3拿向量找订单号、错误码、类名← ④ 为什么这样设计
现象
搜“ORD-20261108-000123”，排第一的是另一个订单号。
根源
向量编码的是“意思”，两个订单号意思完全一样（都是订单号），细节在压缩时被抹平。
做法
精确值用关键词或数据库条件查；混合检索：关键词一路、向量一路，合并后重排（站 06）。
4换了 Embedding 模型，旧向量还在用← ④ 机制 1
现象
升级了向量模型，新提问用新模型算，库里还是旧模型的向量，检索结果一塌糊涂，也不报错。
根源
每个模型的向量空间各不相同，维度一样也不能互相比；维度不一样时向量库会直接报错，反倒容易发现。
做法
向量库里记下“哪个模型、哪个版本算的”；换模型就全量重算，新旧两套并行，切换前对比检索效果。

第二圈 · 使用规范

  • 向量和原文一起存，并记模型名：检索出来要把原文交给大模型；模型名用来防坑 4。
  • 先切块再算：一条很长的工单（几千字的复盘）压成一个向量，细节全丢；按段落切块分别算。（站 06 细讲切块）
  • 召回宁多勿少，再精排：向量取前 20，再用重排模型或大模型挑出前 3。防的是余弦分数挤在一起时排错。
  • 用自己的数据评估：攒几十个“提问 → 应该找到的工单”，每次改动都量一下命中率（站 08）。

第三圈 · 更深一层

存储和速度

1024 维 float32 一条 4 KB，100 万条约 4 GB（⑤ 实测的维度）。几千条直接全量点积就行；几百万条要用近似最近邻索引（HNSW 等），用一点点准确率换几个数量级的速度（pgvector 那页）。

维度能裁剪

有的模型训练时让向量的前几百维也能单独用（套娃式表示），存储紧张时只存前 256 维。Qwen3-Embedding 的说明里支持自定义输出维度（按模型说明，本页没测）。

重排模型

把提问和候选放在一起读、直接打一个相关分，比向量准，比大模型便宜；常用在召回之后的第二步（站 06）。

多语言

好的多语言向量模型里，“Full GC pause”和“Full GC 停顿”会靠得很近，中英混写的工单也能互相找到。

自测

1. 用一句话说出这一页的精华

Embedding 模型把一整段文字压成一个定长向量，训练时把意思相关的对拉近，于是“找相似”变成“找余弦最大”；它擅长换了说法的同义内容，不擅长否定、数字和编号。

2. 全景第 4 站的向量表和 Embedding 模型的向量有什么不同？

向量表是每个 token 一个、还没看过上下文的起点向量，用来给后面的层当输入；Embedding 模型读完整段（经过所有层），再汇总成整段一个向量，专门用来比较。

从 ④ 机制 1 推出

3. 为什么余弦 0.6 不一定说明“很像”？

同语言、同领域的文本向量本来就大致同向，⑤ 里连毫不相干的“首页白屏”都有 0.39；分数的绝对值意义不大，要看排名，门槛要在自己数据上量。

从 ④ 机制 3 推出

4. 预测：把查询写成“排除 GC 之后，订单服务为什么还慢”，向量检索的前 3 里会有 GC 工单吗？

很可能有，甚至排第一。“排除 GC”和“GC 导致”谈的是同一个话题，否定词在向量里分量很小（⑤ 实测 0.972）。这种查询要靠大模型读候选原文来排除。

从 ④ 机制 2 和坑 1 推出

5. 预测：工单从 8 条涨到 100 万条，每次检索还能一条条算点积吗？

100 万 × 1024 次乘加约 10 亿次，CPU 上要零点几秒到一秒，还要把 4 GB 向量读一遍；值班场景勉强，在线高并发不行。要用近似最近邻索引，只看一小部分候选。

从 ④ 为什么这样设计 和第三圈推出（估算）

6. 放回全景：Embedding 在全景里出现在哪？如果值班助手的检索那一步找错了工单，后面会怎样？

全景第 4 站的向量表是同一个思想；值班助手真正用 Embedding 是在第 1 站之前：先检索相似工单，再把它们和日志一起拼进请求。找错了工单，第 1 站拼进去的就是错的参考资料，第 6～8 站模型会认真地“照抄”这些错误证据（幻觉那页：先查再答只能防编，防不了查错），第 10 站核对时要特别看引用的工单是不是同一类故障。
