工具调用的一来一回：模型提议，你的代码执行

模型自己什么都执行不了。它只会在回答里写一张调用单（tool_use 块：工具名 + 参数 + 一个 id），然后停下来；你的代码照单执行，把结果写成 tool_result、带着同一个 id 送回去，它才接着往下说。底下仍然是“预测下一个 token”，调用单只是一段约定好格式的文字。

①为什么需要：模型够不着你的系统

全景第 3 站：值班的你问“order-svc 为什么变慢了”。答案在 GC 日志里，可日志在你的机器上，模型在另一头，它读不到文件、连不上 JVM。站 03 的分诊是你先把 3 行 GC 日志贴进提示词；可这一次你不知道它需要哪份数据，要它看了第一份再决定查第二份。

②没有它会怎样：自己约定格式、自己解析

假设 API 不支持工具，你在提示词里写：“需要查 GC 时，回复一行 CALL parse_gc_log since=20:00”，再用正则从回答里抠出来。能跑，但要对照几条要求看看：

要求自己约定文本格式 + 正则原生工具调用（tool_use）
调用能被可靠地认出来不能保证：模型可能写成 call parse_gc_log(20:00)、包进代码块、或者夹在一段解释中间能：单独一个 tool_use 块，stop_reason 明确等于 "tool_use"
参数类型对得上不能：全是字符串，since=20:00 还是 since="20:00" 全靠猜能：input 已经是按 JSON Schema 解析好的对象（加 strict: true 还保证严格符合）
一次要两个工具难：两行 CALL 要自己切分，哪个结果对哪个调用说不清能：每个块有自己的 id，结果带 tool_use_id 对号
模型停在该停的地方不能：它常常写完 CALL 接着自己编一个“查询结果”往下讲能：提议完就停，等你送回结果
出错能告诉模型能，但要自己发明格式能：is_error: true，模型知道是失败而不是数据
不懂精华时的典型误用：以为“模型会调用工具”，于是把 restart_service 也放进 tools，指望模型自己掂量。其实执行的永远是你的代码：调不调、拦不拦、记不记日志，全在你这一边。

③相邻方案：让模型拿到外部数据的几种做法

做法谁决定查什么适合不适合
先查好、全塞进提示词（站 03 分诊）你，提前定死要什么数据事先就知道，一次调用不知道它需要什么；数据太多塞不下
文本协议 + 正则（ReAct 早期写法）模型模型或接口不支持工具时的退路见 ②：格式飘、参数无类型、会自问自答
原生工具调用模型提议，你执行下一步查什么要看上一步的结果每查一次多一轮请求，慢一些、贵一些
服务端工具（web_search、code_execution）模型提议，Anthropic 执行通用能力：搜网页、在托管沙箱里跑代码碰不到你的内网、你的 JVM

本页学原生工具调用（客户端工具）：数据和动作都在你这边、而且查什么要看上一步结果时，用它。事先就知道要什么的，仍然直接塞进提示词，一次调用最便宜。

④原理：两种块、四条消息、一段约定好的文字

先知道这些
  • Messages API 是无状态的：服务端不记得上一轮，每次请求都把整段对话（messages）重发一遍。讲过：Messages API。
  • content 是一串“块”：一条消息不是一个字符串，而是块的列表，常见的有 text、thinking（模型的思考）、image。这一页再加两种：tool_use 和 tool_result。
  • 模型只会一个 token 一个 token 地往后写：讲过：下一个词预测。工具调用没有改变这一点。

机制 1 · 两种块：调用单和回执

Java 比方：tool_use 像一次 RPC 的请求报文，tool_result 像响应报文，id 像请求号。比方失效的地方：RPC 是调用方自己发起、自己等结果；这里“调用方”是模型，可它发完请求就结束了这次回应，结果要等你下一次请求才送回去。

模型回的 assistant 消息stop_reason = "tool_use"
{"role": "assistant", "content": [
  {"type": "thinking", "thinking": "用户要 20:00 以后的 GC……"},
  {"type": "tool_use",
   "id": "RBbkhukvKrc6…",      // 这张调用单的号
   "name": "parse_gc_log",           // 照 tools 里的名字
   "input": {"since": "20:00"}}      // 已解析好的 JSON 对象
]}
你送回的 user 消息下一次请求里新加的一条
{"role": "user", "content": [
  {"type": "tool_result",
   "tool_use_id": "RBbkhukvKrc6…",  // 回答的是哪张单
   "content": "7 次停顿，最长 1966ms；Full GC 3 次……",
   "is_error": false}               // 失败时写 true
]}

字段按 Claude 官方文档“Handle tool calls”核对过：content 可以是字符串，也可以是 text / image / document 块的列表；is_error 可省略。

机制 3 · 掀开盖子：调用单就是一段约定好格式的文字

API 收到 tools 以后，会把它们写成文字放进提示词开头（Claude 官方文档说的是“用工具定义、工具配置和你的 system 拼出一段专门的系统提示”）；模型在后训练里学会了：需要工具时，按约定格式写一段调用。服务端认出这段文字，把它解析成 tool_use 块，并就此结束这次回应。本机 llama-server 可以把这两层都打出来：

所以有三件事可以直接推出来：工具说明越长，每一轮都越贵（本机量过：1 个工具 +181 token，5 个 +585）；模型可能写错参数、调一个不存在的工具，因为它只是在“写字”；id 由服务端编号，所以只能原样抄回去，不能自己编。

为什么这样设计：模型只提议，执行留给你

选中的：模型提议，你的代码执行

  • 权限、网络、密钥都留在你这边：模型提供方不需要能连你的内网，也不需要你的数据库密码。
  • 每次执行前你都能插一手：校验参数、拦截危险操作、先问人、记审计日志（全景第 4～6 站）。
  • 一次回应在“提议”处结束，服务端不用挂着连接等你执行；执行要 5 秒还是要等人点头 5 分钟，都不占它的资源。
  • 代价：每调一次工具就多一次完整请求，messages 整段重发，慢一点、贵一点。

被放弃的：模型方直接调你的接口

  • 你得把内网接口暴露给模型提供方，还要给它凭证；出了事很难说清是谁执行的。
  • 模型生成的参数不可信，直接打到你的接口上，等于把一个会被提示词注入的调用方放进内网。
  • 没有“执行前”这个环节，审批和限权只能靠提示词，而提示词拦不住。
决定胜负的约束：模型的输出不可信，而能力（数据、权限）在你这边。所以执行必须发生在你的代码里，API 只负责把“想做什么”结构化地交给你。例外是 web_search、code_execution 这类通用的服务端工具：它们不碰你的系统，才由 Anthropic 执行。

⑥细节：消息怎么拼才不出错

第一圈 · 注意事项

1只读了 text，用户收到一句“我先查一下”← ④ 机制 2
现象
接口返回“好的，我来查一下 GC 日志。”然后就没有然后了。
根源
回应 1 可能同时有 text 和 tool_use（Claude 常先说一句再调用）。它是“半场”，不是答案；看 stop_reason 才知道该执行工具还是该交给用户。
做法
先分支 stop_reason：tool_use 去执行；end_turn 才取文字；max_tokens 见坑 6。
2回执和调用单对不上，API 直接 400← ④ 机制 1
现象
第二次请求报 400，说有 tool_use 没有紧跟着的 tool_result，或者某个 tool_result 找不到对应的调用。
根源
文档要求：assistant 那条里的每一个 tool_use，都要在紧跟着的那条 user 消息里有一个 tool_use_id 相同的结果，中间不能插别的消息。常见写法错误：只回了一个结果、把 id 写成自己生成的、忘了先把 assistant 那条放回去。
做法
遍历 r.content 生成结果，id 直接用 b.id；assistant 消息原样（含 thinking）放回，不要只放文字。
3在结果前面加了一句话，400按文档← ④ 机制 1
现象
user 消息写成 [text "以下是结果", tool_result …]，请求被拒。
根源
文档原话：含结果的 user 消息里，tool_result 块必须排在最前面，文字只能放在所有结果之后。这是格式规定，推不出来。
做法
要补充说明（“回答简短些”），放在结果后面。
4参数不对，TypeError 把整个助手打挂← ④ 机制 3
现象
模型传了 {"start": "20:00"}，parse_gc_log(**input) 抛异常，进程退出。
根源
调用单是模型“写”出来的字，schema 只是说明，不是约束：名字、参数都可能写错。
做法
执行前校验，错了包成 is_error: true 送回，写清错在哪、该怎么改，模型通常会改了再调；想从源头杜绝，给工具加 strict: true（schema 要 additionalProperties: false）。
5工具失败就不回，或者回一句“failed”← ④ 机制 1
现象
日志服务超时，代码跳过了这条结果，下一次请求 400；或者回了 “failed”，模型换着法子重试了 6 次。
根源
每张调用单都要有回执，失败也一样；模型只能根据回执的文字决定下一步。
做法
is_error: true + 说人话的原因和建议（“日志服务超时，30 秒后可重试，或先看 GC 日志”）；循环里限制重试次数（停止条件）。
6调用单写到一半被截断← ④ 机制 3
现象
max_tokens 设得小（或思考太长），回应停在调用单中间，stop_reason 是 max_tokens，参数缺一截。
根源
调用单和思考都是输出 token，一起占 max_tokens 的额度。本机这次思考就写了几百 token。
做法
见到 max_tokens 不执行任何工具，调大额度重发这一轮。

第二圈 · 使用规范

  • assistant 消息原样放回，含 thinking 块：防坑 2；Claude 的思考块带签名，改了或删了会让后面的请求出错或丢掉推理。
  • 同一轮的所有结果放进同一条 user 消息：防坑 2；官方还提醒，拆成几条送回，模型以后会越来越少一次要多个工具（并行工具调用）。
  • tool_choice 默认 auto：模型自己决定调不调。none 禁止调用；any / tool（强制调用）在 Claude Opus 5.5、Sonnet 5.5、Fable 5.1/5.2 上会直接 400，那里要“强制”只能用 auto + 提示词点名 + strict: true。
  • tools 列表固定顺序、不要每轮变：tools 排在缓存前缀的最前面，改一个字后面全失效（提示词缓存）。
  • 执行函数只认你自己的表：IMPL[b.name] 查不到就回 is_error，绝不 getattr(module, name) 或 eval。

第三圈 · 优化和深处

Tool Runner：SDK 替你写这个来回

anthropic SDK 有 client.beta.messages.tool_runner：用 @beta_tool 装饰你的函数，它负责调模型、执行、拼 tool_result、循环到不再要工具。站 04 故意手写，是为了看清它替你做了哪些事；做产品时可以用它，审批、拦截都有钩子。

工具说明的成本怎么压

工具多了以后，说明本身就是一大块输入：本机 5 个工具 585 token。办法有三层：说明写准而不是写长（工具怎么设计）；靠缓存让重复的说明按缓存价计费；工具上百个时用“工具搜索”按需加载（站 07 的 MCP 和 Skills 再讲）。

自测

  

    
1. 用一句话说出这一页的精华
模型只写调用单（tool_use，带 id）并停下，你的代码执行后把回执（tool_result，带同一个 id）放进下一次请求；执行权和判断权都在你这边。

    
2. 不用工具调用，自己在提示词里约定“CALL xxx”格式，最疼的是哪两点？
认不准（格式飘、混在文字里）和停不住（写完 CALL 自己编结果往下讲）；参数也没有类型。

    
3. 为什么 tool_use 的回应一定会结束这次回应，而不是在服务端等你执行完？
执行发生在你那边，可能要几秒，也可能要等人审批；API 无状态，没有理由挂着连接等。所以回应在“提议”处结束，结果放进下一次请求。
从 ④ 机制 2 和“为什么这样设计”推出。

    
4. 预测：把 ⑤ 的 max_tokens 改成 50，第一次回应会怎样？
大概率 stop_reason = "max_tokens"：思考还没写完额度就用光了，根本没写到调用单；就算写到了，参数也可能缺一截。这时不能执行任何工具。
从 ④ 机制 3 推出：思考和调用单都是输出 token。

    
5. 预测：同一个问题，工具从 1 个加到 30 个，哪些数字会变？
每轮输入 token 变多（本机 5 个就 +585），首字变慢、更贵；模型选错工具的概率变大。答案本身不一定更好。
从 ④ 机制 3 推出：工具说明是写进提示词的文字。

    
6. 放回全景：第 7 站把 tool_result 的 id 写错了，第 3 站之后整条链路会怎样？
第 8 站准备进下一轮时，请求被 API 以 400 拒绝；循环如果没处理这个异常，整个排查中断，值班的你什么结论都拿不到。所以第 4 站分派和第 7 站打包要一起测。
