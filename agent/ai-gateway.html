AI 网关：模型管理、token 限流、工具过滤

AI 网关是 worker 和供应商之间的一个进程：对 worker 它就是供应商，对供应商它是唯一的客户。精华有两句：真 key、额度、选模型、工具权限都收进这一处，换模型、改额度只改一个地方；它和普通 API 网关最大的不同是要读懂请求体和响应体：模型名、tools、usage、流式事件都在里面，看不懂这些，就只能按请求数限流、按路径路由。

①为什么学：三个团队、一把真 key、一份额度

在全景第 ⑤、⑧ 站，这一步要解决：交易、支付、搜索三个团队都要调模型。如果每个服务自己拿真 key、自己选模型、自己限流记账，会写出三种样子；key 漏了查不出是谁漏的；搜索团队偷偷用上了最贵的模型，月底才发现。

②老办法：Spring Cloud Gateway / Nginx 行不行

Java 后端的第一反应：前面已经有 API 网关了，加几条路由和限流规则不就行？逐条对一下：

要做的事信息在哪普通 API 网关
认是谁请求头里的 key能：本来就会
选模型、降级到备用请求体里的 model差一点：路由按路径和头，要改写请求体才能换模型
按 token 限流输入在请求体里，输出要等响应不能：只会按请求数限
按团队记账响应体的 usage；流式时在最后一个事件里不能：要解析流式响应
工具过滤请求体的 tools、响应体的 tool_use不能：两头都要读懂、改写
脱敏请求体里的消息正文差一点：能改写，但要懂消息的结构（文本块、工具结果块）

能做的只有“认是谁”。剩下的都要读懂 LLM 的请求体和响应体：这一块就是 AI 网关的精华，它是一个懂协议内容的代理，不只是转发字节。

不懂精华时的典型误用：在 Nginx 上给模型调用配“每秒 20 个请求”，按 URL 统计“调用次数”当成本。大促夜一个带 4 万 token 日志的请求和一个 1 千 token 的请求在它眼里一样，额度和账单都对不上。

③选谁：现成的网关，还是自己写

候选是什么适合要留意
LiteLLM 代理Python 写的代理，把上百家供应商统一成 OpenAI 格式；虚拟 key、预算、按 key 的 tpm/rpm 限额、降级Python 栈、小团队，要很快接很多家模型虚拟 key 和预算要接数据库；2026-03-24 PyPI 上的 1.82.7、1.82.8 被投毒（CI 里被攻破的扫描工具偷走了发布令牌），装了就会偷环境里的凭据
Envoy AI Gateway建在 Envoy Gateway 上的 K8s 网关：从请求体里取出模型名做路由；按响应里的 token 数做全局限流（Redis）已经在 K8s 上、流量大要先会 Envoy Gateway 那一套 CRD
Kong、Higress 的 AI 插件在已有的 API 网关上加 AI 代理、按 token 限流等插件；Higress 是阿里开源、Envoy 内核公司已经在用这个网关部分高级插件要企业版，按版本核对
托管网关（Cloudflare AI Gateway、Portkey 等）别人运维的网关，带缓存、看板不想自己运维流量和日志经过第三方，私有化场景不行
自己写一个最小网关FastAPI 200 来行：⑤ 的 gateway.py学原理；或者规则很特殊（工具白名单、脱敏规则跟业务绑死）上生产要补：多副本、共享状态、熔断、监控

本页先自己写一个最小网关：每一层都看得见，换哪款现成的都知道它在做什么。生产上的选择规则：在 K8s 上、流量大，用 Envoy AI Gateway 或 Higress；Python 栈、要快，用 LiteLLM，但锁死版本、校验哈希，因为网关手里有所有的 key，它的依赖是最值得攻击的地方（⑥ 坑 7）。

④原理：一个懂 LLM 协议的代理

先知道这些
  • Messages 请求和响应：请求体里有 model、messages、tools；响应体里有 content（文字块或 tool_use 块）、stop_reason、usage。站 03：Messages API。
  • 流式事件：message_start 带输入 token 数，最后的 message_delta 才带最终的输出 token 数。站 03：SSE 流式。
  • 工具调用：模型只“提议”调哪个工具，执行的是你的代码。站 04：agent 循环。

机制 1 · 一个请求过网关的九层

跟着 ⑤ 里支付团队那个请求走一遍：它带着 3 个工具（包括 heap_dump），消息里是那条藏着注入的支付回调日志。

机制 2 · 为什么必须读懂请求体和响应体

普通网关只看“这个请求去哪、是谁发的”；AI 网关要的信息全在内容里。最麻烦的是流式：输出 token 数在最后一个 message_delta 事件里才确定。网关只能一边把字节原样转给 worker，一边解析事件，等流结束再记账；中途断了，这一次的账就要按已收到的部分补记。按 token 限流也因此是“先放行、回来再扣”：Envoy AI Gateway 的做法也一样，token 数从响应里取出来，再记进全局限流的计数里。上一页的“预扣 + 补差”就是在这一点上更进一步。

机制 3 · 虚拟 key：真 key 只在一处

网关给每个团队发一把虚拟 key（vk-pay-19c2），只在网关里认；真 key 只放在网关进程的环境变量里（线上放 K8s Secret 或密钥库）。好处一连串：换真 key 不用动任何 worker；吊销一个团队只删一行配置；审计里每一笔都知道是谁。一个实测到的细节：anthropic SDK 2.x 把 key 放在 Authorization: Bearer 里发，老版本和别的客户端用 x-api-key，网关两种都要认（⑤ 第一次跑就在这里 401 了）。

机制 4 · 工具过滤要做两次，最后一道在执行处

  • 去程删：请求里的 tools 按白名单过滤，模型根本不知道有 heap_dump 这个工具。
  • 回程查：模型仍可能“编”出一个没给它的工具名，或者被日志里的话带偏（⑤ 里假模型就这么干了）；回复里的每个 tool_use 再对一遍白名单，不在的换成一段说明文字。
  • 执行处兜底：工具是 worker 执行的，不是网关。网关这两道是纵深防御，worker 的工具执行器还要按租户再查一次权限，写操作还要人批（站 08），这是第 7 个知识点的事。

为什么这样设计

一个集中的网关

  • 额度、真 key、账本都是整个组织一份，只有放在一处才数得清、管得住。
  • 换模型、调额度、改白名单、吊销 key，只改网关的配置，几十个 worker 不用重新发布。
  • 代价：多一跳（⑤ 实测 p50 多 2.1 毫秒，比起几秒的模型调用可以忽略）；它成了单点，要多副本，限流和账本要放进共享存储。

每个服务里放一个 SDK 中间件

  • 没有额外一跳，也没有单点。
  • 每个服务都要拿真 key；中间件升级要所有服务一起发布。
  • 限流和账本还是要一个共享的地方，否则三份各算各的，等于没有。
决定胜负的约束：供应商给的额度、账单、真 key 都是“整个组织一份”，而用它的服务有很多个。共享的东西必须有一个地方来管，多一跳几毫秒的代价比几秒的模型调用小两三个数量级。

Java 老朋友：Spring Cloud Gateway

像：一层层的 GlobalFilter 就是这里的九层；RequestRateLimiter 加 Redis 就是共享的限流；按租户的路由谓词就是模型权限。

不像：Spring Cloud Gateway 默认不读请求体（要 ModifyRequestBodyGatewayFilterFactory，还得把整个体缓存下来），流式响应边转发边解析更麻烦；它的限流按请求数，不懂 token。所以 Java 栈也多半在它后面再放一个专门的 AI 网关。

读出来的结论
  • 多一跳的代价是 p50 多 2.1 毫秒、p99 多 2.6 毫秒（两个 Python 进程同在一台 2 核机器上）。和一次几秒的模型调用比，这点可以不算。
  • 工具过滤两道都用上了：去程删掉了 heap_dump，假模型被日志带偏还是“提议”调它，回程又拦了一次。同样的请求换成交易团队，heap_dump 在白名单里，就原样放过，接下来要靠 worker 那边的人工审批。
  • 预算是“先放行、回来记账”：第 1 次请求本身就花了 $0.0012，超过了 $0.0005 的预算，第 2 次才被挡下。要严格不超，就要像上一页那样预扣。
  • 主模型 529 时，worker 的代码一行没改，响应头里看得到这次用的是 backup。
到这里已经能交差了：worker 只拿虚拟 key，网关一处管模型、预算、脱敏、工具、记账和审计。

⑥细节

第一圈 · 注意事项

1网关只部署一个进程← ④ 为什么这样设计
现象
网关重启那 20 秒，所有团队的所有调查一起停。
根源
集中管理的代价就是它成了单点。
做法
至少两个副本放在负载均衡后面；无状态部分随便扩，有状态的（令牌桶、账本、熔断状态）放进共享存储。
2多副本各记各的账← ④ 为什么这样设计
现象
扩到 3 个副本后，搜索团队的预算被花超了将近 3 倍。
根源
⑤ 的账本在进程内存里，每个副本都以为预算还有。
做法
账本和令牌桶放进 Redis（原子地加减），或者按副本数把额度切开；审计日志汇到一处再对账。
3流式中途断开，这一笔没记账← ④ 机制 2
现象
看板上的 token 数比供应商的账单少一截，差的都是流式请求。
根源
输出 token 在最后的 message_delta 里才确定；worker 中途断开，网关的转发循环提前结束，记账那一行没跑到。
做法
记账放进 finally：没拿到最终数字就按已转发的输出估算，标成“估算”；每天和供应商的用量报表对一次账。
4只过滤请求，不查回复实测← ④ 机制 4
现象
白名单里明明没有 heap_dump，worker 还是收到了一个 heap_dump 的 tool_use。
根源
模型可以“编”出没给它的工具名，也可能被消息里的话带偏。
做法
回程也按白名单查一遍；worker 的工具执行器再查一次，执行处才是最后一道。
5脱敏正则误伤或漏网← ④ 机制 2
现象
trace id、订单号这种 16 位以上的数字被打成了“[卡号]”，模型没法引用；带空格的卡号“6222 0202 …”又原样出了门。
根源
正则只认形状，不认意思。
做法
卡号加 Luhn 校验位判断，手机号限定号段；能在工具那一侧结构化脱敏（知道哪个字段是手机号）就别等到网关对着自由文本猜。第 7 个知识点细讲。
6网关改写了供应商的错误← ④ 机制 2
现象
供应商过载时，worker 收到的是 500 而不是 529，上游的熔断和重试判断全错了。
根源
网关把下游错误一律包成自己的 500。
做法
原样透传供应商的状态码和错误类型（overloaded_error、rate_limit_error 和 retry-after 头）；网关自己的错误用自己的类型，分得清是谁的错。
7网关的依赖被投毒← ④ 机制 3
现象
2026-03-24，PyPI 上的 LiteLLM 1.82.7、1.82.8 带着窃取凭据的代码；装了的机器，环境变量里的各家 key 都可能已经泄露。
根源
网关手里有所有的真 key，是整套系统里最值钱的目标；攻击者先攻破了它 CI 里用的扫描工具，偷走了发布令牌。
做法
锁死版本并校验哈希（uv.lock 本身就带哈希）；网关只许连供应商的地址；真 key 放密钥库、定期轮换；出事时按审计日志判断哪些 key 要换。
8审计日志里记了原文← ④ 机制 1
现象
脱敏做得好好的，安全检查却在审计日志里翻出了几千个手机号。
根源
为了方便排查，审计把请求体整个记了下来，而且记在脱敏之前。
做法
审计只记元数据（租户、模型、删了哪些工具、打码几处、用量、耗时）和内容的哈希；要原文排查，走单独审批的取证流程。

第二圈 · 使用规范

  • worker 永远只拿虚拟 key，真 key 只在网关：防 key 散落、泄露了查不出来。
  • worker 用模型别名（triage、investigate），不写真模型名：防换模型要改几十个服务。
  • 工具白名单按租户配，去程删、回程查：防一个团队的权限被另一个团队的请求用到。
  • 供应商的错误原样透传：防上游的重试和熔断判断错。
  • 有状态的东西放共享存储，网关至少两个副本：防单点、防账本分裂。
  • 网关依赖锁版本、校验哈希，出网只许连供应商：防供应链投毒把所有 key 一锅端。

第三圈 · 优化和深处

统一成一种格式，还是原样透传

LiteLLM 这类网关把各家都转成 OpenAI 格式，接入方便；代价是各家独有的东西可能丢掉或变形：提示词缓存的 cache_control、思考块、引用。值班助手只用一家时，原样透传 Messages 格式最稳；要多家混用，再在网关里做“格式翻译 + 每家单独评测”。

灰度新模型

别名让灰度变得很简单：investigate 先让 5% 的流量走新模型，评测分数和看板都没变坏再放大。站 09 的 换模型怎么回归 讲的离线评测，到这里接上了线上灰度。

网关层的缓存

完全相同的请求直接返回上次的结果，能省钱，但 agent 的请求几乎不会完全相同（历史在变、时间在变）；按“意思相近”命中的语义缓存更危险，可能把别的事件的结论安到这个事件上。供应商的前缀缓存省得多、也不会答错，优先用它。

MCP 工具也走网关

工具越来越多是 MCP 服务端提供的（站 07）。一些新网关（比如 agentgateway）把 MCP 流量也接进来，在同一处按租户过滤工具、做鉴权和审计，模型调用和工具调用的账就在一本里。

  1. 按 token 限流：把上一页的 FairBucket 搬进网关，替换第 3 层只有预算的检查。做对了会看到：按 5 : 3 : 2 排队，一个团队打不光整份额度。

自测

1. 用一句话说出这一页的精华

AI 网关是懂 LLM 协议内容的代理：真 key、额度、选模型、工具权限、记账审计都收进一处；它必须读懂请求体和响应体（模型名、tools、usage、流式事件），这是普通 API 网关做不到的。

2. 已经有 Spring Cloud Gateway 了，为什么还要 AI 网关？

它能认 key，但模型名、工具、token 用量都在请求体和响应体里，流式时 usage 在最后一个事件里；普通网关不读、不改这些，只能按请求数限流、按路径路由。

3. 为什么工具过滤要做两次，还不够？

去程删掉，模型就不知道这个工具；但模型仍可能编出工具名或被注入带偏，所以回程再查。工具最终是 worker 执行的，执行处还要按租户再查一次权限，网关这两道只是纵深防御。

从 ④ 机制 4 推出。

4. 预测：网关把供应商的 529 都包成 500 返回给 worker，会怎样？

如果 worker 那边的熔断只认 529、或者对 500 和 529 用不同的重试策略，判断就全乱了；更糟的是 retry-after 头丢了，被限流时 worker 不知道该等多久。错误要原样透传。

从 ④ 机制 2 和上一页 ④ 机制 3 推出。

5. 预测：网关扩到 3 个副本，预算检查还写在进程内存里，搜索团队一天能花掉多少？

最多接近 3 倍的预算：每个副本各自以为还有钱。再加上“先放行、回来记账”，每个副本还能多放出一笔请求。要共享账本，最好再加预扣。

从 ④ 为什么这样设计 和 ⑤ 的预算实验推出。

6. 放回全景：第 ⑤ 站前后是什么？如果网关挂了 1 分钟，整条链路会怎样？

前面是第 ④ 站的租户令牌桶（就在网关里），后面是第 ⑥ 站可靠性层和第 ⑦ 站供应商，回程经过第 ⑧ 站的护栏。网关挂了：worker 的调用全部连不上，按截止时间等待或转人工；第 ② 站的积压上涨；看板（第 ⑩ 站）这一分钟没有账。所以网关要多副本，worker 对“连不上网关”要有和“供应商 529”同样的处理。

从全景第 ②④⑤⑥⑩ 站推出。

档位：标准。本机跑过（2026-11-28，2 核 ARM，Python 3.13.18，anthropic 2.12.0，FastAPI 0.165.0，httpx 0.28.1）：⑤ 的 9 个实验；看过 SDK 2.12.0 的源码：_client.py 里 api key 走 Authorization: Bearer。按文档：Envoy AI Gateway 的 usage-based rate limiting（从响应取 token 数、经 Envoy Gateway 全局限流和 Redis 计数、模型名从请求体取出）。按多家安全公司的事件报告（Snyk、Trend Micro、JFrog 等，2026-03）：LiteLLM 1.82.7、1.82.8 被投毒，来源是被攻破的 CI 扫描工具偷走了发布令牌。Kong、Higress 的 AI 插件只做了概述，没有逐项核对版本。
