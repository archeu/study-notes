混合检索：关键词 BM25 加向量，再重排

关键词检索认字面：开关名、版本号、表格里的参数，一个字都不能差；向量检索认意思：换了说法也找得到。两路各有各的盲区，所以都走一遍，用 RRF 按名次合成一份候选，再让重排模型把问题和每一段放在一起读、重新排。实测前 1 片命中率：只走关键词 0.70，只走向量 0.77，两路按分数加权 0.83，再重排 0.90；代价是重排在本机 CPU 上每个问题 12 秒。

①为什么需要：有的问题要字面一样，有的问题换了说法

在全景第 8、9 站，这一段要解决：同一个知识库，要同时接住两种问题。“改哪个开关”要找到写着 order.cache.local.enabled 的那张表；“什么情况下会直接打电话叫值班的人”，手册原文写的却是“P1 同时电话呼叫值班人”。

实测 2026-11-25，本机 2 核 ARM：31 片、站 06 评测集 30 题；BM25 是 jieba 分词 + 手写公式（k1 = 1.2，b = 0.75），向量是 Qwen3-Embedding-0.6B，重排是 bge-reranker-v2-m3。30 题里差一题就是 3.3 个百分点，0.73 和 0.77 之间只差一道题。

②没有它会怎样：只走一路，总有一类题接不住

把 30 道题按类型拆开看前 1 片命中率，两路的强项和弱项一目了然：

题型（题数）只走 BM25只走向量为什么
答案在表格里（4）0.750.25表格的片里是一串参数名和数字，“-XX:HeapDumpPath | /data/dump”这种文字，意思很难被向量抓住；问题里的“OOM”“自动”却能和表里“OOM 时自动留现场”那一行字面对上。
换了说法（13）0.691.00“打电话叫值班的人”对“电话呼叫值班人”，“晚上八点”对“19:00–22:00”：字不一样，意思一样。
原词（6）0.831.00两路都行；BM25 偶尔被常见词带偏。
扫描页（3）1.000.67开关名、群名这类专有名词，字面一对就准。
故障单（3）0.000.00“11 月 9 日”在片里写成“10:00、10:42”，故障编号又只在标题里：两路都接不住，问题出在切块（上一页坑 3），检索救不了。
  • 只走向量（前三页的做法）：表格题 4 道只对 1 道；开关名那题排第 5。
  • 只走关键词（Java 里最熟的 Elasticsearch 用法）：换说法的 13 道错了 4 道，“打电话叫值班的人”被故障单里的“值班”二字带到第 9。
  • 两路都走再合并：一路漏了，另一路多半能捞回来，前 3 片命中两路各是 0.90，按分数加权合并后 0.97。
  • 两路都漏的（故障单 3 道），合并也救不回来：检索的上限是切块定的。
不懂精华时的典型误用：上了向量检索就把关键词检索拆掉，觉得“语义检索更高级”。向量最弱的恰恰是运维资料里最多的东西：开关名、命令、参数、错误码、表格。

③相邻方案：怎么把两路合起来，要不要再精排

评判要求：两类问题都接得住；不用为每个库调参；延迟可控（值班时等不了半分钟）；能在 PostgreSQL 或 Elasticsearch 里落地。

做法两类问题要调参吗每个问题的耗时（本机）30 题前 1 片
只走 BM25换说法的接不住k1、b（一般不动）0.45 ms（31 片）0.70
只走向量表格、专有名词接不住不用255 ms（几乎全是给问题算向量）0.77
两路 + RRF（按名次）能基本不用（k = 60 是通用默认）同上0.73
两路 + 分数加权（归一化后）能要：权重 α 要按库调同上0.83（α = 0.5）
两路 + RRF + 交叉编码重排能，而且排得最准重排留几段、分数阈值再加 12 秒（CPU 上 20 对；GPU 上百毫秒级）0.90
学习型稀疏向量（SPLADE、BGE-M3 稀疏）能：模型学出“哪些词重要”，还会扩展同义词不用没测没测
大模型当重排能，还能顺便解释提示词没测：每段一次生成，比交叉编码更贵没测

前五行 实测，后两行 按文档。重排的输入是 RRF 前 20，所以它的上限被 RRF 的前 20 定住：前 20 里没有对的那片，重排也没办法。

本页学“BM25 + 向量 + RRF + 交叉编码重排”：两路保召回，RRF 不用调参，重排保准确；延迟交给“只给前 20 重排”和硬件去控制。分数加权在这批数据上比 RRF 好，但它的权重换一个库就得重调。

④原理：两路各打各的分，按名次合并，再成对精排

先知道这些
  • 倒排索引：每个词记下它出现在哪些片里、出现几次，关键词检索就是查这张表。Elasticsearch 的核心：倒排索引与分片。
  • 分词：英文按空格就能切，中文要靠分词器（这里是 jieba）把“本地缓存必须设置容量上限”切成“本地 / 缓存 / 必须 / 设置 / 容量 / 上限”。关键词检索的“词”就是分词器切出来的东西。
  • 双塔和交叉编码：向量检索是双塔，问题和片各自变成向量再比；重排是交叉编码，问题和片拼在一起读一遍出一个分。RAG 流水线那页画过对比图。

机制 1 · BM25 打分：词频会饱和，少见的词值钱，长片要打折

BM25 给“问题里的每个词”在一片里算一个分，加起来就是这一片的分。每个词的分是三样东西的乘积：

BM25（Elasticsearch / Lucene 的默认打分）k1 = 1.2，b = 0.75
分(词, 片) = IDF(词) × tf × (k1 + 1) / (tf + k1 × (1 − b + b × 片长 / 平均片长))

IDF(词) = ln(1 + (N − df + 0.5) / (df + 0.5))     # N 片里有 df 片含这个词

“想临时停用本地缓存，改哪个开关？”在附录 C 那片上的得分，逐词拆开（实测，这一片 85 个词，平均 55.3 个）：

词几片里有（df）IDF这片里几次（tf）得分
想、临时、停用、哪个0—00：库里没有这些词，问题里的口语全都白说了
改13.0600：最值钱的词，可这片里没有
本地91.2111.00
缓存111.0210.84
开关51.7632.48：出现 3 次，但片比平均长 54%，打了折
合计4.32，第 1 名

Java 老朋友：BM25 ≈ Elasticsearch 的 _score

像：Elasticsearch 5.0 起默认的相关度打分就是 BM25，explain=true 里看到的 idf、tf 和 dl / avgdl（片长和平均片长）就是上面三样。

不像：ES 按字段、按分片各算各的 IDF；我们这里是 31 片的小库，一个词多出现在一两片里，IDF 就变很多，小库的 BM25 分数很不稳。

它看不见的东西

BM25 只数“同一个词”：问题说“停用”，原文写“关掉”；问题说“打电话叫人”，原文写“电话呼叫”，它一分都不给。词被分词器切错了，它也照单全收（⑥ 坑 1）。这些正是向量那一路擅长的。

机制 2 · RRF：两路的分数没法比，那就只比名次

BM25 的分数没有上限（这批数据里 0～9.4），余弦在 0.4～0.8 之间挤着，直接相加等于只听 BM25 的。RRF（Reciprocal Rank Fusion）干脆扔掉分数，只用名次：

RRFk = 60 是论文里的默认值，各家实现基本沿用
RRF(片) = Σ 每一路  1 / (k + 这一路里的名次)          # 没进这一路前 20 的，这一路贡献 0

§4.3 本地缓存规范：BM25 第 3，向量第 1  →  1/63 + 1/61 = 0.03227   # 第 1
附录 C 降级开关  ：BM25 第 1，向量第 5  →  1/61 + 1/65 = 0.03178   # 第 2

这就是 RRF 的脾气：两路都排得不错的，赢过一路第一、一路第五的。它不知道 BM25 那边附录 C 领先了 1 分（4.32 对 3.24），也不知道向量那边几名之间只差 0.08。好处是不用调参、两路换什么打分都能合；代价是丢掉了“差多少”。实测在这批题上 RRF 前 1 片 0.73，反而比只走向量（0.77）低一道题；按分数归一化后加权（α = 0.5）是 0.83。k 越大，名次之间的差距越小，越像“两路投票”。

机制 3 · 重排：问题和每一段放在一起读

前面两路都是“各算各的”：BM25 数词，向量比两个各自算好的点。重排模型（这里是 bge-reranker-v2-m3，交叉编码器）把“问题 + 一段”拼成一个输入，整个读一遍，输出一个相关分（logit，可以是负数，0 附近是分界）。问题里的每个词都能“看到”段落里的每个词，所以它能判断“这段写的是不是这个问题要的东西”，而不只是“像不像”。

数字都是 实测。重排的分数和 RAG 流水线页那次（+1.20）不一样，是因为这次送进去的段落前面带了标题路径、候选也不同：重排分数只在同一次排序里比较才有意义。

为什么这样设计：一个漏斗，越往下越贵、越准、越少

漏斗：便宜的广撒网，贵的精挑（选）

  • 两路互补，前 20 里漏掉对的那片的情况很少（这批题前 5 片就有 0.97）。
  • 重排只碰 20 段，开销和库多大无关。
  • 多了一次模型调用和一段延迟；重排模型也要部署和维护。

一步到位

  • 只用一路：总有一类题接不住（②）。
  • 全库都交给重排：31 片就要 19 秒，几十万片不可能。
  • 只靠大模型自己从一大堆资料里挑：提示变长、变贵，还会被不相关的段落带偏。
决定胜负的约束：越准的打分越贵。所以每一层只负责把对的那片“留在候选里”，把排准的事留给下一层；最后一层（重排）贵，但只看 20 段。

def hybrid(conn, q, teams=("trade", "public"), k=20):
    bm  = BM25(allowed_rows(conn, teams)).search(q, k)          # 关键词一路
    vec = vector_search(conn, embed([q], query=True)[0], k, teams)  # 向量一路
    return rrf([bm, vec]), bm, vec

def rrf(lists, k=60):
    score, rows = Counter(), {}
    for lst in lists:
        for rank, r in enumerate(lst, start=1):
            score[r["id"]] += 1 / (k + rank)
            rows.setdefault(r["id"], r)
    return [rows[i] | {"rrf": round(s, 4)} for i, s in score.most_common()]

def rerank(q, rows, top_n=5):
    r = post(RERANK_URL + "/v1/rerank",
             {"query": q, "documents": [x["section"] + "\n" + x["text"] for x in rows], "top_n": top_n})
    return [rows[x["index"]] | {"rerank": x["relevance_score"]} for x in r["results"]]

读出来的结论
  • 重排最准（前 1 片 0.90，MRR 0.931），它把“打电话叫值班的人”从 RRF 的第 4 拉到第 1，把开关那题从第 2 拉到第 1。
  • RRF 本身没有带来提升：前 1 片 0.73，比只走向量还少一道题；它的价值在“前 5 片里都有”（0.97），给重排留够候选。
  • 分数加权这次比 RRF 好（0.83），因为它保留了“领先多少”；但 α 是对着这 30 道题调出来的，换一个库要重来。

⑥细节

第一圈 · 注意事项

1开关名、故障编号被分词器切碎实测← ④ 机制 1
现象
jieba 把 order.cache.local.enabled 切成 order / cache / local / enabled，把 INC-20261109-02 切成 inc / 20261109 / 02。搜整个开关名时，所有含 cache、enabled 的片都来分一杯羹；三个开关名在 BM25 眼里几乎一样。
根源
BM25 只认分词器切出来的“词”；通用分词器按标点切英文，不知道点号连起来的是一个整体。
做法
给分词器加自定义词典（开关名、服务名、错误码）；或者同一字段再建一份“不分词”的索引（Elasticsearch 的 keyword 子字段、n-gram），查询里识别出标识符时走精确匹配。
2常见词把 BM25 带偏实测← ④ 机制 1
现象
“OrderDetailCache 打算怎么修？”BM25 第 1 名是 HikariCP 笔记，因为它标题里有“怎么看”的“怎么”；“打电话叫值班的人”被故障单里“交易组值班”的“值班”带到第 9。
根源
IDF 本该把常见词压下去，但 31 片的小库里，“怎么”只在 1 片里出现，反而成了最稀有、最值钱的词。小库的 IDF 很不稳。
做法
用中文停用词表去掉“怎么、什么、哪个、的”这类疑问词和虚词；库小的时候 IDF 可以用一个更大的语料来算；让问题改写那一步（第 7 个知识点）先把口语转成文档里的说法。
3两路分数直接相加← ④ 机制 2
现象
BM25 分在 0～9.4，余弦在 0.4～0.8，加起来排序几乎只取决于 BM25；换个库，BM25 的量级又变了。
根源
两个分数的尺度、分布都不一样，没有共同的单位。
做法
要么只看名次（RRF），要么每个问题内部各自归一化到 0～1 再加权（本页“加权”那行，α 要用评测集调）。
4RRF 把“领先很多”和“领先一点”看成一样实测← ④ 机制 2
现象
开关那题，BM25 里附录 C 领先第 3 名 1 分多，向量里落后第 1 名 0.08；RRF 把“两路都还行”的 §4.3 排在了它前面。30 题前 1 片：RRF 0.73，只走向量 0.77。
根源
RRF 只用名次，分数里“差多少”的信息全扔了；k = 60 又把第 1 名和第 5 名的差距压得很小（1/61 对 1/65）。
做法
RRF 后面接重排（本页的做法），让重排来定先后；或者给更可信的一路加权重；或者改用分数加权。改了都要跑评测集。
5重排太慢实测← ④ 机制 3
现象
本机 CPU 上每个问题重排 20 段要 12.3 秒，比检索本身慢 50 倍；全景里写一节报告查 4 次，光重排就 48 秒。
根源
每一对都要把问题和段落一起过一遍模型，没有任何东西能提前算好。
做法
只给前 20 重排（再少就要看召回）；放 GPU 上（百毫秒级）；多对一起批量算；同一问题和段落的分数可以缓存；两路前几名一致时可以跳过重排。
6重排偏爱“通用答案”实测← ④ 机制 3
现象
“11 月 9 日 P99 升高时是怎么止血的？”重排第 1 名是手册 §3.1（“止血：能关掉可疑功能的，先用降级开关关掉”），+1.90；真正记着那天怎么止血的故障单时间线只排第 3。
根源
重排判断的是“这段话是不是在回答这个问题”，§3.1 确实在讲怎么止血；它不知道“11 月 9 日”对应哪张故障单，而时间线那一片里又没有日期。
做法
能用元数据过滤的先过滤（故障编号、时间范围，第 7 个知识点）；片里带上日期和编号（上一页坑 3）；这类“查某一次事件”的问题，交给 agent 先确定是哪张故障单再查（第 9 个知识点）。

第二圈 · 使用规范

  • 两路各取 20～50 个候选再合并，重排只看合并后的前 20 左右。防的是候选太少漏掉、太多重排扛不住。
  • 记下每一路的名次和分数，答错时先看是哪一路漏了、合并时被谁挤掉、重排给了多少分。防的是只看到最终结果，不知道该修哪一层。
  • 分词词典跟着术语表一起维护：新开关、新服务名上线就加进去。防的是坑 1。
  • 重排分数设阈值，全部低于阈值时回答“没找到”或者改写再查。防的是把不相关的段落硬塞给模型（RAG 流水线页坑 1）。
  • 评测按题型拆开看：表格题、换说法的题、专有名词题各自的命中率。防的是总分没变、某一类题悄悄变差。

第三圈 · 优化和深处

BM25 放在哪

本页的 BM25 是 30 行 Python，每次查询都重新数一遍，只适合学习。生产上：Elasticsearch / OpenSearch 本来就是倒排 + BM25，8.x 起同一个索引还能存向量做 kNN，混合检索一个系统就够；PostgreSQL 自带的全文检索打分不是 BM25，中文还要装分词扩展，要 BM25 可以用 ParadeDB 这类扩展。按文档

学习型稀疏向量

SPLADE、BGE-M3 的稀疏输出：模型给每个词一个权重，还会补上原文没有、但意思相关的词（“停用”补出“关闭”）。它像 BM25 一样能走倒排索引，又带一点语义，常被当作关键词那一路的升级。按文档

重排的几种选择

交叉编码器（本页）最常用；ColBERT 一类“后期交互”把段落的每个词向量提前存好，查询时再细比，介于双塔和交叉编码之间；大模型当重排最灵活也最贵。选哪个，看延迟预算和评测分数。按文档

小样本的数字要打折

30 道题里一道题就是 3.3 个百分点：RRF 的 0.73 和向量的 0.77 只差一道题，加权的 0.83 也只多两道。下结论之前要么加题，要么看几次运行是否一致；评测页（第 6 个知识点）会专门讲。

实验台：RRF 的 k 和两路的权重

先猜：RRF 时给 BM25 那一路的权重从 0.5 调到 0.8（向量 0.2），30 题前 1 片命中率会？

实测 两路对 30 道题的完整排名来自 hybrid-search/main.py（hybrid.json），融合在浏览器里现算：分数 = w / (k + BM25 名次) + (1 − w) / (k + 向量名次)，每路只取前 20。权重 0.5、k = 60 就是 ⑤ 里那行 rrf。

下一圈

  • Elasticsearch 一套搞定：同一个索引里 BM25 + dense_vector kNN + RRF，和本页的 Python 拼装对比。
  • 自定义词典：给 jieba 加上开关名、服务名，看 Q22、Q29 的 BM25 排名。
  • BGE-M3 的稀疏向量：同一个模型同时出稠密和稀疏向量，一次调用两路。
  • 重排模型的选择和蒸馏：更小的重排模型能不能把 12 秒降到 2 秒，命中率掉多少。

↺回到⑤：改一改

  1. 加停用词：在 kb.tokenize() 里去掉“怎么、什么、哪个、哪里、能不能、的”，重跑 main.py，看 Q29、Q03 的 BM25 排名。（坑 2）
  2. 加自定义词典：jieba.add_word("order.cache.local.enabled") 之类，三个开关名、故障编号都加进去，看开关那题 BM25 的分数差距。（坑 1）
  3. 只在有分歧时重排：两路的第 1 名相同就不重排，数一数 30 题里能省掉几次重排、命中率掉不掉。（坑 5）
  4. 给重排加阈值：重排最高分小于 0 的题，打印出来看看是不是都是“前 20 里本来就没有”。（第二圈）

自测

1. 用一句话说出这一页的精华

关键词认字面、向量认意思，盲区正好错开，所以两路都走；两路分数没法比，就用 RRF 按名次合并；最后让交叉编码器把问题和每一段放在一起读、重新排，它最准也最贵，所以只给前 20。

2. 只走一路的老办法，各疼在哪？

只走向量：表格、开关名这类“字面必须一样”的题接不住（表格题 4 道对 1 道）。只走 BM25：换了说法的题接不住（13 道错 4 道），还会被常见词带偏。

3. 为什么 BM25 的分数和余弦不能直接相加？

尺度不一样：BM25 没有上限，这批数据在 0～9.4；余弦挤在 0.4～0.8。直接相加，排序几乎只由 BM25 决定。要么只比名次（RRF），要么各自归一化后再加权。

从 ④ 机制 1、2 推出。

4. 预测：问题是“order.cache.local.enabled 关掉后会怎样？”，BM25 会把三个开关所在的那一片排第 1 吗？三个开关之间分得清吗？

会排得很靠前：order、cache、local、enabled 这几个词在附录 C 那一片里都出现。但分词后三个开关名只差 export / cache / recommend 一个词，BM25 只能凭这一个词区分，而“cache”在讲本地缓存的片里到处都是，对手很多；整串当一个词索引才能精确命中。

从 ④ 机制 1（BM25 只认切出来的词）和坑 1 推出。

5. 预测：把 RRF 的 k 从 60 改成 1，会怎样？

第 1 名的分量变得极重（1/2 对第 5 名的 1/6），融合结果几乎就是“哪一路的第 1 名排第 1”；两路第 1 名不同时，谁赢取决于第 2 名。k 越大越像两路平均投票，越小越像“谁第一听谁的”。可以在实验台上试。

从 ④ 机制 2 的公式推出。

6. 放回全景：第 8、9 站前后各发生什么？如果第 9 站的重排服务挂了，报告会怎样？

第 7 站给出检索语句和过滤条件；第 8 站两路检索、RRF 合并；第 9 站重排、留前几段；第 10 站拿它们写报告。重排挂了，退回 RRF 的前几名：开关那题第 1 名会变成 §4.3 本地缓存规范，附录 C 落到第 2；如果第 10 站只取前 1～2 段，“怎么止血”那句就可能找不到开关名。所以重排挂掉时要多取几段，或者干脆报警，而不是静默降级。
