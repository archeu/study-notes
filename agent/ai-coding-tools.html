用 AI 编程工具干活：你出需求和验收标准，它跑循环，你审结果

Claude Code 这类工具本身就是一个 agent：模型提议“读这个文件、改那一行、跑一下测试”，外面那层程序（harness）真正去执行，结果送回模型，再决定下一步，直到做完。精华：它能干多好，取决于两件你负责的事。一是它看得见什么：项目文件、CLAUDE.md、你给的上下文。二是它能不能自己验证：有没有一条命令（通常是测试）能告诉它做对了没有。不懂这一点的典型用法，是在网页聊天框里贴代码、再把回答复制回来，这时你自己成了工具执行者；或者一句话甩过去、不审就全盘接受。

②常见笨办法：要么你当它的手，要么你当它的橡皮图章

笨办法一 网页聊天，复制粘贴
你：（贴 main.py 的 60 行）
    这里为什么会 500？
它：可能是 fetch 没处理……
你：（复制它的代码，粘回去，
     跑测试，再贴报错回去）
它看不到你的项目，看不到测试结果。读文件、跑命令、贴结果全是你在做，你就是那个“工具执行者”。
笨办法二 一句话甩过去，全盘接受
你：加个缓存
它：（改了 6 个文件，引入一个新依赖，
     顺手重命名了两个函数）
你：看着挺多的，应该没问题吧
    git commit -am "add cache"
没说缓存什么、多久过期、怎么算做完；也没看 diff。错了往往要过很久才发现。
该有的样子 你定目标和验收，它跑循环
你：tests/test_api.py 里
    test_summary_marks_hung_host 失败了，
    httpx.ReadTimeout 没被 fetch 接住。
    改 main.py 让它通过，别动测试，
    跑 uv run pytest 确认全绿。
它：（跑测试 → 读报错 → 读 main.py
     → 加 2 行 → 再跑 → 10 passed）
你：（看 diff，确认只加了一个 except）
需求里有：在哪、为什么错、不许动什么、怎么算做完。它自己能验证，你只审最后那几行改动。
  • 笨办法一的问题：模型最擅长的“读一堆文件找关联、跑一下看结果”被你手工替代了，又慢又容易漏。
  • 笨办法二的问题：没有验收标准，它只能猜“做完”长什么样；不审 diff，猜错的部分就混进了代码。
  • 缺的那一块就是这页的精华：让它看得见（项目、规矩）、让它验证得了（测试、命令），你守住两头：需求和审查。

① 让它先读懂

“这个项目做什么、怎么跑测试？”先看它的理解对不对，不对就纠正，或者写进 CLAUDE.md。

② 先有验收标准

有测试就指定测试；没有就先让它（或你）写一个会失败的测试。大改动先用 Plan 模式出方案。

③ 让它跑循环

改代码、跑测试、看结果、再改。中途方向不对就按 Esc 打断，直接说哪里不对。

④ 你审 diff 再提交

git diff 逐行看：只改了该改的？有没有顺手多做？测试有没有被改松？

3两张安全网：checkpoint 管文件，权限模式管动作

checkpoint：改文件之前先拍快照

它每次改文件前都保存一份原样。改坏了，按两次 Esc 回到之前的状态，或者直接说“撤销刚才的改动”。

只管本地文件。推送代码、改数据库、调外部 API、发布页面、删除线上的东西，这些都撤不回来。所以这两天每次 git push 和发布前，都要先确认要推什么。

它和 git 是两回事：checkpoint 是会话里的后悔药，git 提交才是长期记录。练习里每完成一步就提交一次。

权限模式：Shift+Tab 切换

模式它可以不问你就做什么
Manual什么都要问：改文件、跑命令都先征求同意
Accept edits改文件、mkdir、mv 这类不问，其他命令还问
Plan只读、只出方案，不改源文件
Auto后台有个分类器审查，拦下有风险的动作，其余直接做

常用又安全的命令（uv run pytest、git status）可以写进 .claude/settings.json 的允许列表。刚上手建议 Manual 或 Accept edits，大改动先切 Plan。

4交给它还是自己来：两条标准

标准一：能不能自动验证

有测试、有类型检查、有一条命令能说“对”或“不对”，它就能在循环里自己纠错。验证不了的（“这个设计好不好”“这个阈值该设多少”），它只能猜，你得自己判断。

标准二：错了能不能撤回

改本地文件，错了有 checkpoint 和 git；推送、发布、删数据、动生产配置，错了就收不回来。撤不回来的事，要么你亲手做，要么它做之前你逐字看过。

5为什么这样设计：给模型整个项目和一个终端，而不只是补全下一行

agent：看得见全局，能自己验证Claude Code、Cursor 的 Agent

  • 能跨文件找关联、能跑测试看结果，改错了自己发现、自己再改。

补全：只看光标附近，猜下一行Tab 补全一类

  • 快、打扰少，你始终在掌控每一个字。
  • 不知道项目里别处有什么，不会跑测试，对不对全靠你当场判断。
  • Cursor 文档写明：项目规则对 Tab 补全不起作用。

决定胜负的约束：写代码最难的不是敲字，而是“找到该改哪儿”和“确认改对了”。补全帮不上这两件事，agent 可以，前提是它能读整个项目、能执行验证命令。所以这类工具都在往“给模型一个终端”的方向走，同时用 checkpoint 和权限把风险关在笼子里。

⑤跟着做一遍：复盘那次修 bug，每一步看什么

值班助手的代码已经整理成一个独立的 git 仓库：~/claude/oncall-helper（就在这台机器上，一次提交，10 个测试从零跑通 实测）。下面把 pytest 那一页修 bug 的过程拆成 6 步，每步写清“它做了什么”和“你该看什么”。⑥ 的练习就在这个仓库里做。

0准备：装 uv、拿到依赖、确认测试能跑
curl -LsSf https://astral.sh/uv/install.sh | sh     # 这台机器上还没装 uv
cd ~/claude/oncall-helper
uv sync                                              # 按 uv.lock 装依赖，含开发依赖 pytest
uv run make_logs.py                                  # 生成 logs/（已被 .gitignore 忽略）
uv run pytest -q                                     # 应该看到 10 passed
claude                                               # 在这个目录里启动 Claude Code
步它做了什么你该看什么
1 需求收到：“让 test_summary_marks_hung_host 通过，别动测试，跑 uv run pytest 确认”。需求里有没有“在哪、怎么算做完、什么不许动”。缺哪样，它就会猜哪样。
2 先看失败跑 pytest -q：1 failed, 9 passed，报错 httpx.ReadTimeout: agent hung。它是不是先复现了问题，而不是一上来就改代码。没复现的修复，等于没验证。
3 定位看出 fetch 只接住了 asyncio.timeout 抛的 TimeoutError。它说的原因你认不认可。这里要你懂 asyncio 的超时，否则判断不了它对不对。
4 改在 fetch 里加一个 except httpx.HTTPError，记成这一台出错。改动范围：只动了 main.py 的两行？测试文件一个字没动？
5 验证再跑 pytest -v：10 passed；覆盖率 96%。看到的是真实输出，不是它嘴上说“应该能过了”。
6 审查、提交（你来做）git diff，确认后提交。异常类选得太宽了吗？httpx.HTTPError 会不会把不该吞的错误也吞了？这是你的判断，不是它的。
 
$ git diff main.py
     except TimeoutError:
         return HostGc(host=host, error="timeout 1s")
+    except httpx.HTTPError as e:                  # httpx 自己的超时、连不上：也记成这一台出错
+        return HostGc(host=host, error=type(e).__name__)
     return parse(host, r.text)
  • 审两行，一处，测试没动：范围对。
  • 审httpx.HTTPError 是 httpx 所有请求异常的父类，超时、连不上、协议错误都会被记成“这一台出错”。对值班助手合理：一台机器出问题，不能拖垮整个汇总。
  • 审但它没处理“日志代理返回 500”这种情况（不抛异常），pytest 页预测题 5 推出过。这就是下一条需求，可以留给练习 4。

规范

和 AI 结对时，团队里的几条约定

先有能跑的验证，再让它改

没有测试的代码，先让它补测试并看着测试失败一次。

它说“改好了”，其实没人验证过。

需求写清四样

在哪、要什么结果、什么不许动、怎么算做完。

它替你猜，猜的方向未必是你要的。

每次提交前自己看 diff

提交信息里写的是你认可的改动；看不懂的改动不提交，先问它为什么。

不理解的代码进了仓库，出事时没人说得清。

撤不回的动作你来确认

推送、发布、删数据、改生产配置，执行前逐字看一遍。

checkpoint 管不到的地方出事。

做完练习 3、4 后，翻回 ⑤ 的表格逐行对照：你的需求里四样都有吗？它先复现了吗？你看 diff 时发现过什么？把发现写进 CLAUDE.md，下一次就不用再说。

1. 用一句话说出这一页的精华。

AI 编程工具是一个 agent：模型提议工具调用、外面的程序执行、结果送回，循环到做完；它能干多好，取决于它看得见什么（项目、CLAUDE.md）和能不能自己验证（测试、命令），你守住需求和审查两头。

2. 在网页聊天里贴代码、复制回答，痛在哪？

模型看不到项目、跑不了测试，读文件、执行命令、贴结果全由你手工完成，你成了工具执行者；而且它没法自己验证，对不对全靠你当场判断。

3. 为什么长期规矩要写进 CLAUDE.md，而不是在对话开头说一遍？是 ④ 哪条？

④-2：每个新会话都从空的上下文开始，长对话还会被压缩成摘要，早先的细节指令可能丢；CLAUDE.md 每次会话开头都会加载。

4. 预测：你让它“修好这个 bug”，但项目里没有任何测试。它最可能怎么“验证”？会出什么问题？

它可能只是读一遍改过的代码就说“应该好了”，或者自己临时写个脚本跑一下。没有可重复的测试，修复的正确性只能靠你判断，下次有人改动时也不会有人发现它又坏了。所以先补一个会失败的测试。

从 ④-4 的标准一（能不能自动验证）推出。

5. 预测：在 Accept edits 模式下，它改坏了 main.py 又执行了 git push。按两次 Esc 能撤回什么，撤不回什么？

能撤回本地 main.py 的改动；撤不回已经推到远端的提交（还得另做一次提交或回滚）。而且 Accept edits 模式下 git push 这种命令本来就会先问你，按了同意就是你的决定。

从 ④-3：checkpoint 只管本地文件，权限模式管动作。

6. 放回全景：站 01 的 10 站里，哪些是这次“和 AI 结对”时你最需要自己懂的？为什么？

第 5～7 站（asyncio）和第 8 站（解析和异常）。⑤ 里那个 bug 的根源是“超时有两种、异常类不同”，看懂它要懂事件循环怎么超时、httpx 的异常层级；审查 except httpx.HTTPError 吞得太宽还是正好，也要懂第 8 站解析失败时会怎样。工具能替你写代码，但审查需要你懂原理，这也是前面 7 页要一页页讲透的原因。
