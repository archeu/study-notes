LangGraph 上手：把站 04 的循环画成一张图

LangGraph 把 agent 写成一张状态图：state 是一张共享的表，节点是读它、返回改动的普通函数，边说明下一步去哪。站 04 那个 while 循环，画出来只是两个节点加一条条件边；多出来的存盘、并行、停下等人，都长在这张图上。LangChain 只剩下给它供料的那一层：消息、模型、工具。

②老办法：站 04 的手写循环

站 04 的值班助手 v1 是 100 多行 Python：调模型，模型要工具就调工具，结果包成 tool_result 送回去，到上限就停（Agent 循环）。上一页已经把它和框架逐项对照过，这里只记两条结论：

  • 一个进程从头跑到尾的简单 agent，手写循环每一行都看得见，完全够用。
  • 站 08 要的并行、每步存盘、停下等人、从断点接着跑，全得自己补，补完就是一个小号工作流引擎（上一页 ②）。
不懂精华时的典型误用：把 while 循环原样塞进一个 LangGraph 节点里。图上只有一个节点，框架的存盘点只在开头和结尾，中间几轮模型调用一轮也没存，等于没用框架。

④原理：一张表、几个函数、几条边

先知道这些
  • 四种消息：SystemMessage、HumanMessage、AIMessage（可能带 tool_calls）、ToolMessage（带 tool_call_id）。它们就是 Claude API 里 system、user、assistant 的 tool_use、user 的 tool_result 换了个名字，见工具调用的一来一回。
  • 聊天模型：ChatAnthropic(...).bind_tools(tools) 以后，每次 .invoke(消息列表) 都带上工具说明书，返回一条 AIMessage。
  • 工具：@tool 把函数签名和文档字符串变成 JSON Schema 说明书，写法的讲究见工具怎么设计。
  • Java 比方：StateGraph 像用代码写的流程定义，compile() 像部署，invoke() 像启动一个流程实例，thread_id 就是流程实例 id。比方失效的地方：流程引擎的节点每次结果一样，这里的 model 节点每次可能不一样。

机制 1 · state 和 reducer：节点只交改动，框架负责合进去

state 是一张所有节点共享的表。节点不直接改它，而是返回“我要改哪几个键”；每个键挂一个 reducer，决定新值怎么和旧值合并。对话的键用 add_messages：追加，同 id 的消息替换。没挂 reducer 的键，后写的直接覆盖。

机制 2 · 图怎么跑：一次真实运行，在图上走一遍

站 04 的 while 循环画成图，只有两个节点：model 调模型，tools 调工具；一条条件边 tools_condition 看最新那条 AIMessage 有没有 tool_calls，有就去 tools，没有就到 END。下面每一步都来自 ⑤ 那次本机实测（Qwen3-1.7B）。

为什么这样设计：模型和工具拆成两个节点

把站 04 的 while 循环原样塞进一个节点也能跑。为什么现成的 agent 都拆成 model 和 tools 两个节点、中间一条条件边？

一个节点里写 while 循环

  • 整个循环是一个 superstep，框架只在开头和结尾存盘；第 3 轮崩了，前两轮的模型调用全部重来。
  • 没法在“模型要调工具、工具还没调”的那一刻停下来问人。
  • 工具重试只能连模型一起重试，又多花一次 token。

两个节点 + 条件边

  • 每次模型调用、每批工具调用之间都是 superstep 边界，都存盘：⑤ 实测 3 次模型、2 批工具，存了 7 个检查点。
  • interrupt_before=["tools"] 一行就能在调工具前停下（↺ 练习 1）。
  • 重试、超时可以只挂在 tools 节点上，模型不跟着重跑。
  • 代价：多了一层“边和节点”的概念，调试要看 state 在节点之间怎么变。
决定胜负的约束：框架只在节点和节点之间存盘、停下、重试。想在哪一刻有这些能力，那一刻就得是节点的边界。这也是 LangGraph 当初从 LangChain 的“链”（LCEL）里单独长出来的原因：链只能从前往后流，agent 却是一个要绕回去的环，还要在环上存盘。

⑥细节

第一圈 · 注意事项

1state 的键没写 reducer，被后一个节点整个覆盖实测← ④ 机制 1
现象
自己定义 class S(TypedDict): messages: list，两个节点先后返回 {"messages": ["x"]}，最后 state 里只剩 ['x']，用户的问题没了（本机探针）。换成 MessagesState，同样的写法得到 ['q', 'x', 'x']。
根源
没写 reducer 的键，默认是“后写的覆盖先写的”。节点返回的是改动，不是追加。
做法
对话用 MessagesState 或 Annotated[list, add_messages]；其他要累积的键写 Annotated[list, operator.add]。
2工具一抛异常，整张图就失败实测← ④ 机制 2
现象
日志服务超时，search_logs 抛 TimeoutError，invoke 直接抛出，模型根本没机会换个办法查。
根源
ToolNode 默认只把“参数校验失败”包成 ToolMessage 还给模型，其他异常原样抛出（_default_handle_tool_errors，langgraph 1.2.24 源码）。这和站 04 的做法（出错也包成 is_error 的 tool_result 送回去）不一样。
做法
ToolNode(TOOLS, handle_tool_errors=True)，实测会回给模型 Error: TimeoutError('日志服务超时')；或者在工具函数里自己 try/except，返回一句人话。
3以为 recursion_limit 数的是“轮”实测← ④ 机制 2
现象
想“最多 6 轮”，设了 recursion_limit=6，结果三轮就报 GraphRecursionError。
根源
上限数的是 superstep。一轮“模型 → 工具”是两步：model 一步，tools 一步。不设的话默认 10007（上一页坑 1）。
做法
轮数 × 2 再加 1～2；接住 GraphRecursionError，返回“没查完，已查到……”。create_agent 可以用 ModelCallLimitMiddleware 直接按模型调用次数限。
4照着旧教程 import create_react_agent历史原因
现象
from langgraph.prebuilt import create_react_agent 还能用，但会报弃用警告。
根源
LangGraph 1.0 起，现成的 agent 搬到了 LangChain：from langchain.agents import create_agent（源码里的弃用说明写着 LangGraphDeprecatedSinceV10）。网上 2025 年以前的教程大多还是旧写法。
做法
新代码用 create_agent；旧代码升级时顺手换掉，参数名也有变化（prompt 改成了 system_prompt）。

第二圈 · 使用规范

  • state 的每个键都想清楚 reducer：覆盖、追加还是合并，写在类型标注里，防坑 1。
  • 节点只返回改动，不原地改 state：原地 append 看起来也生效，但绕过了 reducer，存盘和并行时出的问题很难查。
  • 模型和工具在模块级建一次，节点里只调用：节点会被反复调用，每次新建客户端是白花的连接。
  • 工具出错返回一句人话，不往外抛：让模型有机会换个办法，防坑 2。
  • 每次 invoke 都带 thread_id 和 recursion_limit：防坑 3，也让检查点能找回来。
  • 调试时用 stream_mode="updates"：每一步打印“哪个节点改了什么”，比只看最终结果好查得多。

第三圈 · 优化和深处

create_agent 的中间件

现成 agent 留了钩子：before_agent、before_model、after_model、wrap_model_call、wrap_tool_call。LangChain 1.5.2 自带十几个：HumanInTheLoopMiddleware（调工具前问人）、SummarizationMiddleware（压缩上下文）、ModelCallLimitMiddleware、ToolRetryMiddleware、PIIMiddleware……像 Servlet 的 Filter 链，也像 Spring AI 的 Advisors（第 7 个下钻页细讲）。

流式和子图

stream_mode 有 values（每步完整 state）、updates（每步改动）、messages（模型逐 token 输出，做界面用）、custom（节点里自己发进度）。一张编译好的图可以整个当成另一张图的节点，叫子图：全景里的每个子 agent 就可以是一张子图，第 4 个下钻页用到。

自测

1. 用一句话说出 LangGraph 是什么

把 agent 写成状态图的运行时：state 是共享的表，节点是返回改动的函数，边定下一步；存盘、并行、停下等人都长在这张图上。

2. LangChain、LangGraph、create_agent 是什么关系？

LangChain 核心提供消息、模型、工具这些接口；LangGraph 是跑状态图的运行时；create_agent 是 LangChain 1.x 用 LangGraph 拼好的现成 agent（model + tools 两个节点）。

3. 自定义的 messages 键丢了用户的问题，根源是哪条原理？

没写 reducer 的键，默认是覆盖。节点返回的是改动，后写的那个把整个列表换掉了。

从 ④ 机制 1 推出。

4. 预测：模型一次要了两个工具（search_logs 和 parse_gc_log），ToolNode 是先后调还是同时调？这一步算几个 superstep？

同时调：ToolNode 用线程池对每个 tool_call 执行一次（源码里是 executor.map）。整个 tools 节点只算一步，两个 ToolMessage 在这一步结束时一起追加进 messages。

从 ④ 机制 2 和上一页机制 2推出。

5. 预测：把 tools_condition 换成一条普通边 model → tools，会怎样？

图没有出口了：模型给出结论（没有 tool_calls）以后还是会进 tools 节点；ToolNode 找不到工具调用就什么也不做，图回到 model，一直转到撞上 recursion_limit（本机探针：GraphRecursionError）。条件边就是 while 循环里的那个 break。

从 ④ 机制 2 推出。

6. 放回全景：第 2 站前后各发生了什么？这一页的图放进全景大图，对应哪一部分？

前面是第 1 站 n8n 把告警 POST 进来，后面是第 3 站主 agent 分诊。这一页的 model + tools 小循环，就是全景第 5 站每个子 agent 内部在跑的东西；全景那张大图是在外面再套一层：分诊、并行、汇总、等批准。
