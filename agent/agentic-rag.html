让 agent 自己决定查什么（Agentic RAG）

前五页的 RAG 都是“用户问一句、代码查一次”。可“为什么没按手册回滚”要查故障时间线和回滚规定两处，查几次、查什么，事先不知道。Agentic RAG 把检索做成一个工具，交给模型在循环里自己决定。核心取舍是灵活和可控：让模型决定，就要承受它不查、乱查、查一次就停；本机 1.7B 模型 4 道题里有 3 道一次都没查就答了。所以设计的重点不在“放权”，而在放多少、用代码兜住什么。

①要解决的问题：一个问题要查好几处

在全景第 6 站，写复盘报告的 agent 要先决定去知识库查什么。很多问题光凭一次检索答不了，因为答案分散在不同的文档里：

题问题要拼的资料
A1INC-20261109-02 为什么没有按手册回滚，而是用了降级开关？故障单时间线 + 手册 §4.2（+ 附录 C）
A211-09 那次故障违反了运维手册哪条规定？规定原文怎么写？故障单根因 + 手册 §4.3

②不用它会怎样：用户原话只查一次

前五页的做法：拿用户的原话检索一次，前 4 片交给模型。本机实测（实测，Qwen3-1.7B）：

题拿到了要拼的资料吗回答（原样节选）对吗
A1§4.2 有，时间线没有“因为 OrderDetailCache 没有设置最大值和过期时间，导致 P99 翻倍，无法直接回滚”错：理由是编的
A2都没有；拿到的是修订记录“违反了 §2 P99 阈值由 1000 ms 改为 800 ms 的规定”错：把“修订记录”当成了被违反的规定
A3只拿到 11-09 的时间线只讲了 11-09 的缓存问题错：只看到一半
A4附录 C 有“订单详情改查 Redis [S1]，修改开关后 1 分钟内生效 [S1]”对
  • 单跳的问题（A4）一次就够：资料在一处，原话和它也像。
  • 多跳的问题，原话像的是“其中一处”，另一处根本进不了前 4 片；模型拿着半份资料，用自己的话补完另一半。
  • 原话里“违反了规定”这几个字，和修订记录里“§2 P99 阈值由 1000 ms 改为 800 ms”更像，检索把它排了上来，模型就顺着说成了“违反了 §2”。
不懂精华时的典型误用：以为加大 k（一次多取几片）就能解决多跳。原话不像的那一处，取前 10 片也未必进得来；进来了也混在一堆不相干的片里。多跳问题缺的是“换一个问法再查一次”，不是“多拿几片”。

③几种流派：谁来决定查什么、查几次

流派谁决定查什么查几次多跳可预测本机 1.7B（4 题对几题）
固定流水线代码：用户原话1 次不能最好1 / 4（只有单跳那题）
人写的检索计划代码：按题型写好的模板固定几次能，只要题型事先知道好2 / 4 对，另 1 题部分对
先列计划再查模型列一次，代码执行2～3 次能，靠计划质量中1 / 4：计划写得太空泛
检索当工具（agent 循环）模型，每一轮重新决定模型定，代码设上限能，还能根据查到的再查最差0 / 4：3 题一次都没查
查完自检再补查（Self-RAG、CRAG 一类）模型或小判别器判断“资料够不够”不够就再查能中没测
先分类再路由代码或小模型判断题型，走不同的检索按路由按路由好没测

④核心取舍：放多少权给模型，代码兜住什么

先知道这些
  • Agent 循环：模型提议调工具，代码执行，结果送回，直到模型不再要工具（站 04）。这里唯一的工具是 search_kb。
  • 工具说明书：工具的名字、描述、参数，模型靠它决定用不用、怎么用（工具怎么设计）。
  • tool_choice：调用时告诉模型“必须调一个工具”（{"type": "any"}）或“必须调这个工具”。是 API 层的约束，按文档；本机 llama-server 的 /v1/messages 实测没有强制执行（⑤）。
  • 停止条件：步数、预算、超时三道闸（停止条件）。

取舍 1 · 检索变成工具：查什么、查几次，交给模型

把“检索”从流水线里的一个固定步骤，变成模型手里的一个工具：模型读问题，决定要不要查、拿什么话去查；看到结果后，再决定再查一次还是可以回答了。这和站 04 的值班助手调 search_logs 是同一个循环，只是工具换成了知识库。

取舍 2 · 控制权是一条光谱，不是二选一

取舍 3 · 放了权，就要用代码兜底

  • 上限：最多查 4 次，查满就把工具收走，只能回答（本页代码就是这样写的，见 ⑤）。防的是查个不停。
  • 至少查一次：第一轮用 tool_choice 逼它调工具；服务端不支持时，代码检查“没调工具就回答了”，把回答退回去、再提示一次。防的是不查就答。
  • 引用只认工具返回过的编号：回答里出现 [S3] 而工具从没返回过 S3，直接判不合格。防的是编出处。
  • 同一句不查第二次：检索语句去重。防的是原地打转。
  • 回答前自检：问题里的每一问（“为什么没回滚”“用了哪个开关”）是不是都有资料撑着，没有就再查一次。这一步本身也要模型来判，又是一层不确定。

取舍 4 · 工具说明书，决定它查不查、查什么

模型只能从说明书里知道这个工具能查到什么。全景第 6 站实测过：只告诉模型“要写复盘报告”，它列的检索语句全是“故障 INC-20261109-02 的……”，没有一条去查手册里的规定；说明书里写清“库里有手册的哪几章、有哪两张故障单”，它才会去查规定。本页 search_kb 的说明书：

agentic-rag/main.py 里的工具定义
TOOL = {"name": "search_kb",
  "description": "在交易组知识库里检索，返回最相关的 3 段，每段带编号 [S1]、[S2]……。"
                 "知识库里有：order-svc 运维手册 v3.2（告警阈值、故障处置、发布与回滚、本地缓存规范、"
                 "JVM 参数、附录 C 降级开关）、故障单 INC-20261108-01 和 INC-20261109-02"
                 "（时间线、根因、修复）、学习笔记。"
                 "一次只查一件事；问题涉及“规定”和“事件”两方面时，要分别查。",
  "input_schema": {"type": "object",
                   "properties": {"query": {"type": "string", "description": "检索语句，一件事"}},
                   "required": ["query"]}}

说明书写得再清楚，也只是“建议”：实测里 1.7B 模型照样不查，或者把用户原话整句塞进 query（⑤）。说明书解决的是“会用工具的模型知道该怎么用”，解决不了“模型不会用工具”。

核心取舍：灵活还是可控

检索当工具，模型决定

  • 能处理事先没想到的问题，能根据查到的内容决定下一步查什么（真正的多跳）。
  • 强依赖模型的工具使用能力：本机 1.7B 4 题对 0 题。
  • 每多查一次多一轮模型调用，延迟和成本不可预测；评测也更难（要评“查得对不对”）。

代码决定查什么

  • 可预测、可评测、便宜：模型只负责最后写答案。
  • 小模型也能用：本机人写检索计划那组 2 / 4 对，另 1 题部分对。
  • 只能处理想到过的题型；问题一变形，模板就失效。
决定胜负的约束：两件事——问题的形状事先知不知道，模型会不会用工具。形状已知（复盘报告的几节、固定的几类值班问题），就让代码决定查什么；形状未知、而且手上的模型确实会用工具，才把决定交给模型，并且用上限、至少查一次、引用校验这些代码兜底。

⑤套进场景：4 道题、6 种做法，本机实测

同一个知识库（31 片，BM25 + 向量 + RRF），同一个 Qwen3-1.7B，同一个回答提示，只换“谁决定查什么”。对错由人逐条判（只看回答对不对，不看措辞）：

做法A1 为什么没回滚A2 违反了哪条A3 两次的共同点A4 开关后查哪（单跳）每题平均
A 原话查一次错（理由是编的）错（说成 §2 阈值）错（只看到 11-09）对21 秒
B 先列计划再查错（说成导出开关）错（说成回滚规定）错（说成都是缓存）对19 秒
C agent 循环没查就答，编了 [S3]查 1 次（原话），错没查，说找不到没查，说找不到12 秒
D 第一轮必须查仍然没查（服务端没执行 tool_choice）查 1 次（原话），错查 1 次，错查 1 次，对32 秒
E 必须查 + 打开思考查 1 次，错（“30 分钟内发现”）查 1 次（查成了开关），错没跑没跑122 秒
F 人写检索计划查 3 次，§4.2 拿到了，时间线没进前 2，推理仍错对（引了 §4.3 原文）部分对（“都是内存被占满”，细节不准）对18 秒

实测 2026-11-25，本机 2 核 ARM，llama-server b12618 的 /v1/messages（Anthropic SDK 调用），思考默认关；E 打开思考，每题约 2 分钟，只跑了 A1、A2。每题的检索语句、拿到的片、回答原文在 runs.json，下面的实验台可以逐题看。

⑤agentic-rag/main.py 的 agent 循环（节选）完整代码 →
def run_c(kbase, q, force_first=False, think=False):
    messages = [{"role": "user", "content": q}]
    searches = []
    for turn in range(MAX_CALLS + 1):
        tools = [TOOL] if len(searches) < MAX_CALLS else []          # 查满 4 次就把工具收走，只能回答
        choice = {"type": "any"} if (force_first and not searches and tools) else NOT_GIVEN   # 第一轮逼它查
        r = client.messages.create(model=MODEL, max_tokens=400, system=SYSTEM + "需要资料时调用 search_kb。",
                                   tools=tools or NOT_GIVEN, tool_choice=choice, messages=messages,
                                   extra_body={} if think else NOTHINK)
        uses = [b for b in r.content if b.type == "tool_use"]
        if not uses:                                                 # 不再要工具：这就是回答
            return {"searches": searches, "answer": text_of(r)}
        messages.append({"role": "assistant", "content": r.content})
        results = []
        for u in uses:
            searches.append(u.input["query"])
            idx = kbase.search(u.input["query"], k=3)                # BM25 + 向量 + RRF，前 3 片
            results.append({"type": "tool_result", "tool_use_id": u.id, "content": kbase.fmt(idx)})   # [S1]…[S3]
        messages.append({"role": "user", "content": results})
读出来的结论
  • 放权给 1.7B 模型（C）是最差的：4 题里 3 题一次都没查，直接答，还编了一个不存在的出处 [S3]；查了的那题，把用户原话整句当检索语句。
  • 逼它查（D）只是把“不查”变成“查一次就停”；本机服务端还没执行 tool_choice，A1 照样没查。打开思考（E）它会查了，可每题 2 分钟，查的话仍然不对。
  • 代码决定查什么（F）最好：A2 查到了根因和 §4.3，答出了规定原文。可 A1 即使查到了 §4.2，时间线那片没进前 2，1.7B 也没推出“42 分钟 > 30 分钟”：检索计划对了，生成能力也要够。
  • 单跳的 A4，除了不查就答的 C，哪种做法都对：Agentic RAG 的价值只在多跳题上，代价却在每一题上都要付。
到这里已经能交差了：值班助手的复盘报告用“代码决定查什么”（下一页）；开放问答先用固定流水线，同时把 search_kb 做成工具、带上上限和引用校验，等换上会用工具的模型再放权。
已知还没处理的细节：不查就答（坑 1）；原话当检索语句（坑 2）；查一次就停（坑 3）；查个不停（坑 4）；只信参数不验证（坑 5）。

⑥反例和误用

第一圈 · 套上了名字，没满足约束

1不查就答，还编出处实测← ④ 取舍 3
现象
C 组 4 题里 3 题第一轮就直接回答，A1 还引用了 [S3]，而工具一次都没被调过。
根源
“要不要查”交给了模型，模型觉得自己知道、或者不会用工具；系统提示里的“只根据检索到的资料回答”它也没当真。
做法
代码检查：一次都没调工具就回答的，退回并提示“先调用 search_kb”；回答里的编号必须是工具返回过的，否则判不合格。不要只靠提示词。
2把用户原话整句当检索语句实测← ④ 取舍 4
现象
C、D 组查了的题，query 基本就是用户的原问题；说明书里写了“一次只查一件事、规定和事件分别查”，没有用。
根源
拆分问题、换成文档的说法，需要模型懂这个领域、会用工具；说明书只能告诉它规则，给不了它能力。
做法
能事先拆的，用代码按题型拆（F 组）；必须交给模型的，换会用工具的模型，并在评测里专门量“检索语句的质量”（命中了几处要拼的资料）。
3查一次就停，多跳没走完实测← ④ 取舍 1
现象
D、E 组每题都只查了 1 次，拿到其中一处资料就回答，另一半用自己的话补。
根源
“够不够”也是模型判断的；它看到一片看起来相关的资料，就觉得够了。
做法
回答前加一步自检：问题拆成几问，每一问有没有资料撑着，没有就再查（Self-RAG、CRAG 的思路）；或者干脆按题型固定“至少查哪几类”。
4查个不停、原地打转← ④ 取舍 3
现象
强一些的模型常见的是反过来：同一句话换个说法查了七八次，或者一直“再确认一下”，延迟和费用失控。本页的 1.7B 没有出现，按文档和站 04 的经验写。
根源
停不停由模型决定，而模型没有成本的概念。
做法
次数上限（本页 4 次，到了就收走工具）、检索语句去重、总 token 预算；站 04 的停止条件那三道闸照搬。
5以为设了参数就生效实测← ④ 取舍 3
现象
D 组第一轮设了 tool_choice={"type": "any"}，本机 llama-server 照样让模型直接回答了 A1。
根源
不同的服务端、不同的版本，对 API 参数的支持不一样；本地兼容层尤其如此。按文档，Claude 的 API 会强制执行这个参数。
做法
关键约束在代码里再验证一遍（“这一轮有没有 tool_use”），不满足就重试或报错；换服务端、换模型时把这类检查加进评测。

第二圈 · 使用规范

  • 先问“问题的形状事先知不知道”：知道就让代码决定查什么，不知道再考虑放权。防的是为了“用上 agent”而放权。
  • 检索工具的说明书写清库里有什么，返回结果带编号和出处。防的是模型不知道该去查手册（全景第 6 站）。
  • 每次调用记下检索语句、拿到的片、回答，评测时单独量“该拼的几处拿到了几处”。防的是只看最终答案，分不清是查错了还是写错了。
  • 上限、去重、引用校验、至少查一次，四道代码闸都要有。防的是坑 1～4。
  • 放权之前先跑评测集：同一批多跳题，放权和不放权各跑一遍，放权要明显更好才上线。防的是“看起来更智能”。

第三圈 · 优化和深处

模型能力是门槛

Agentic RAG 的效果几乎完全取决于模型的工具使用能力：会不会在该查的时候查、会不会把问题拆开、会不会根据结果再查。本页的结论只对 1.7B 成立；换成能力强的模型，C 组很可能反过来最好。下一圈用同一套题换模型重跑，才能知道“放权”在什么模型上划得来。

检索语句由谁写

一种折中：模型决定“查不查、查哪一类”（规定 / 事件 / 笔记），代码负责把它变成具体的检索语句和过滤条件（比如事件类自动按故障编号和日期过滤，RAG 优化页机制 1）。模型做判断，代码做执行。

自检再补查

先按固定流水线查一次，让一个判别步骤看“每一问是不是都有资料”，缺哪问就针对哪问再查。它比完全放权可控，比固定流水线能多跳，是很多生产系统的选择。按文档

和多 agent 的关系

“一个 agent 专门查资料，另一个专门写”是站 08 多 agent 的话题：查资料的那个 agent 就是本页的循环，写的那个拿它的结果。每多一个 agent，就多一份上下文要重读（站 08 地图上的比方：多 agent ≈ 微服务拆分）。

自测

1. 用一句话说出这一页的精华

Agentic RAG 把检索做成工具，让模型决定查什么、查几次，能处理多跳和没想到的问题；代价是强依赖模型的工具能力、更难预测和评测。问题形状已知就让代码决定查什么，放权时用上限、至少查一次、引用校验这些代码兜底。

2. 原话只查一次的老办法，疼在哪？

多跳问题的答案分散在几处，原话只像其中一处；另一处进不了候选，模型就用自己的话补（A1 编了理由，A2 把修订记录当成被违反的规定）。

3. 为什么说明书写得很清楚，1.7B 还是不查？

说明书只能告诉模型“规则是什么”；会不会在该查的时候调用工具、会不会拆问题，是模型本身的能力。小模型的工具使用能力不够，规则写得再清楚也只是建议。

从 ④ 取舍 4 推出。

4. 预测：把 MAX_CALLS 从 4 改成 10，C 组的 1.7B 结果会变吗？

基本不变：它的问题是不查或者查一次就停，从来没碰到 4 次的上限，上限再高也用不上。上限防的是强模型查个不停，不是弱模型查得太少。

从 ④ 取舍 3 和 ⑤ 的结果推出。

5. 预测：复盘报告的“根因与处置”这一节，用 agent 循环还是代码写好的检索计划？

代码写好的计划：这一节要查什么（故障单根因、时间线、相关规定、降级开关）事先完全知道，F 组已经证明“查对了”比“让模型自己查”有用得多；放权只会增加不查、乱查的风险。下一页就是这么做的。

从 ④ 核心取舍（问题形状是否事先知道）推出。

6. 放回全景：第 6 站前后各发生什么？第 6 站漏查了手册，后面几站能补救吗？

第 6 站之前是用户的任务；之后第 7 站加过滤、第 8 站检索、第 9 站重排、第 10 站生成。第 6 站没去查手册，第 7～9 站只会把“故障单那几片”排得更好，手册的规定根本不在候选里；第 10 站只能自己补，全景实测里它就补出了“违反了运维手册中关于缓存大小限制的规定[2]”，而 [2] 是故障单的基本信息表。漏查的东西，后面每一站都只会把错往下传。

从全景第 6～10 站推出。
