业务流程自动化：写操作、审批、幂等、审计

agent 第一次替人改外部世界，要过四道关：提议、审批、执行、审计。框架给的是“至少执行一次”：崩溃重放、重复投递、重试都会让写操作再来一遍，所以不做两遍只能靠下游的幂等键和唯一约束，不能靠 state 里记一笔“做过了”。实测里，同一个批准被投递两次，“先查后写”建出了两张工单，唯一约束只建一张；而没加幂等的通知，两种都发了两次。

①为什么需要：一笔写操作要过四道关

在全景第 8～11 站，这一步要解决的是：汇总完，主 agent 提了三个写操作：建工单、发群通知、把导出接口限流到 0。前面全是只读，查错了大不了重查；从这里开始，做错了、做了两遍，都要有人收拾。

②没有它会怎样

  • 站 04 的做法是进程里同步等人点头。这十几分钟进程不能退出，发一次版，等批准的请求全没了。
  • 卡片上只有“全部批准”：张三想建工单、不想限流，只能全拒。
  • 建完工单进程崩了，检查点没来得及存：重跑时 act 节点整个再执行一遍（第 1 页坑 2）。
  • n8n 把张三那一下“批准”投递了两次，两个 worker 同时恢复同一条线程：⑤ 实测，“先查后写”的工单库建出 INC-1108 和 INC-1109 两张。
  • 只在应用日志里打一行“已建工单”：日志会轮转，没批准而跳过的、被挡下的重复，都看不到。
不懂机制时的典型误用：在 state 里加一个 ticket_created: True，以为重跑时看到它就不会再建。可这个标记要等 act 节点跑完才存进检查点，崩溃恰好发生在“建完工单、存盘之前”，标记就丢了。

③相邻方案：怎么才算“不做两遍”

做法崩溃后重跑两个 worker 同时执行代价
什么都不做不能：建两张不能：建两张—
state 里记“做过了”不能：标记在崩溃时还没存不能：两个 worker 读到的都是“没做过”看起来最省事
先查后写能（⑤ 实测 1 张）不能（⑤ 实测 2 张）查和写之间有空档
幂等键 + 唯一约束能（实测 1 张）能（实测 1 张）要设计键；下游要有唯一索引
下游 API 支持幂等键能能请求头里带 Idempotency-Key，下游替你记；只记一段时间

本页用幂等键 + 唯一约束：自己的工单库加唯一索引，调外部 API 时把同一个键放进请求头。Java 那边是老朋友：支付回调按订单号建唯一索引、Kafka 消费者按消息键去重（Kafka 消息可靠性），都是“上游保证至少一次，下游保证只生效一次”。

④原理：至少一次 + 下游去重 = 只生效一次

先知道这些
  • 至少一次（at-least-once）：框架保证批准过的写操作一定会执行，但可能不止一次：节点失败会整段重跑（检查点那页机制 3），批准可能被投递两次，重试策略也会再调一次。
  • 幂等：同一个意图执行 N 次，效果和执行 1 次一样。“建一张叫 X 的工单”本身不幂等；“建一张幂等键为 K 的工单，已有就返回那张”是幂等的。
  • 唯一约束是原子的：INSERT … ON CONFLICT DO NOTHING（SQLite 写 INSERT OR IGNORE）由数据库保证同一个键只有一行，两个连接同时插也只成功一个。
  • interrupt 和 Command(resume)：停下时请求存进检查点，恢复时节点从头重跑（第 1 页）。

机制 2 · 幂等键怎么定：一个意图，一个键

拿什么当键崩溃重跑重发的告警（新线程）同一事件里第二次合法的同类动作
随机 UUID、时间戳每次重跑都是新键，挡不住挡不住能区分
thread_id + 动作名挡得住新线程新键，挡不住（全景预测题 3）会被误挡：参数不同也当成重复
告警指纹 + 动作名 + 参数摘要挡得住挡得住：指纹不变参数不同，摘要不同，是新意图

⑤ 里的键长这样：7f3a:create_ticket:868b4ec4，最后一段是参数 JSON（键排序后）的 SHA-256 前 8 位。键要在提议的那一刻就定下来、跟着动作走，执行时不能现算现用随机数。

为什么这样设计：幂等只能放在下游

state 里记“做过了”

  • 标记要等节点跑完才存盘；“写完、存盘前”崩了，标记就没了。
  • 两个 worker 同时恢复，读到的都是“没做过”。

下游唯一约束 + 幂等键

  • “写”和“判断写没写过”是同一个原子操作，在同一个数据库里。
  • 崩溃重跑、重复投递、重试，全部挡住（⑤ 实测）。
  • 代价：下游要配合；调外部系统时对方得支持幂等键，不支持就自己先记一张发件表。

把写操作和存盘放进一个事务

  • 理论上最干净：要么都成，要么都不成。
  • 工单系统、IM、限流配置在别的服务里，没法和检查点库开同一个事务。
决定胜负的约束：副作用发生在下游，检查点存在自己的库里，两边不在同一个事务里，所以框架最多只能做到“至少一次”。能把“写”和“判断写过没有”放进同一个原子操作的，只有下游自己，所以幂等必须放在下游：唯一索引，或者对方 API 认的幂等键。

机制 3 · 审计表：每一笔都记，只追加不修改

字段为什么要
时间、worker、thread_id哪个进程、替哪件事做的；配合 trace id 能串起整条链路（站 09）
动作、参数做了什么，参数原样记下
批准人责任在人：谁批的、几点批的
幂等键同一个意图的几次尝试能对上
结果，包括“未批准，跳过”和“已存在，没再建”只记成功的，复盘时说不清限流为什么没做、为什么有两次尝试

审计和检查点分开存：检查点是图的运行状态，线程结束就该清（检查点那页坑 5）；审计要按公司规定留几年，只追加、不更新、不删除。

class Approval(TypedDict):                                   # 卡片能勾的只有这三项
    approved: list[Literal["create_ticket", "notify", "throttle_export"]]
    by: str

def approve(s):
    d = interrupt({"actions": s["actions"]}, response_schema=Approval)   # 格式不对，resume 时报错
    return {"approval": d}

def idem_key(fp, action):                                    # 一个意图一个键
    digest = sha256(json.dumps(action["args"], sort_keys=True).encode()).hexdigest()[:8]
    return f"{fp}:{action['name']}:{digest}"

-- 下游：插入本身就是判断（Postgres 写 ON CONFLICT DO NOTHING）
INSERT OR IGNORE INTO tickets(idem_key, no, title) VALUES (?, ?, ?);

读出来的结论
  • 一个接一个的重跑，“先查后写”也挡得住；两个 worker 同时执行，只有唯一约束挡得住（2 张对 1 张）。
  • 建工单有幂等键，通知没有：两种工单库下通知都发了两次。每一种写操作都要有自己的幂等，不是给最显眼的那个加上就完事。
  • 审计表把“已存在，没再建”“未批准，跳过”都记下了：从审计能看出这件事被执行过两次、哪一次被挡下。
  • 批准里带了清单外的动作，框架按 schema 直接拒，线程原地不动，等一个合法的批准。
到这里已经能交差了：过关条件二做到了：同一个写操作重放两次（崩溃重跑、重复投递），不会建出两张工单，审计里看得到第二次被挡下。

⑥细节

第一圈 · 注意事项

1先查后写，并发时建两张实测← ④ 为什么这样设计
现象
批准被投递两次，两个 worker 同时 SELECT 都没查到，各 INSERT 一张：INC-1108、INC-1109。
根源
“查”和“写”是两个操作，中间有空档；只有放进同一个原子操作，才挡得住并发。
做法
幂等键建唯一索引，INSERT … ON CONFLICT DO NOTHING，插不进去再查已有的那一行。
2只给建工单加了幂等，通知发了两次实测← ④ 机制 2
现象
工单只有一张，群里却收到两条一样的通知。
根源
每一种写操作都会被重跑，幂等要一个动作一个动作地做；IM 一般不替你去重。
做法
给通知也记一张“已发送”表，主键是它的幂等键；或者用 IM 支持的消息去重字段。限流、重启这类改配置的动作，写成“设成某个值”而不是“加一减一”，天然幂等。
3幂等键用了随机数、时间戳或线程 id按设计← ④ 机制 2
现象
崩溃重跑建出第二张（随机数、时间戳）；或者同一个告警重发时起了新线程，又建一张（线程 id）。
根源
键要代表“意图”，不能代表“这一次尝试”。
做法
告警指纹 + 动作名 + 参数摘要，在提议时算好，跟着动作走。全景第 1 站的去重键、第 2 站的 thread_id、第 10 站的幂等键，最好都从同一个业务键来。
4批准过期了还在执行按设计← ④ 机制 1
现象
告警 20:25 已经恢复，张三 22:30 才看到卡片点了批准，导出接口被限流到 0，业务方的导出全挂了。
根源
批准针对的是 20:18 那一刻的结论，十几分钟到几小时以后，前提可能已经不成立。
做法
审批请求带过期时间；act 执行前重新检查前提（告警还在不在、参数还对不对），不成立就记一行“已过期，没执行”并通知人。
5批准结果用了自定义类，存进检查点会被警告实测← ④ 机制 1
现象
response_schema 用 Pydantic 的 BaseModel，恢复时日志里出现：Deserializing unregistered type … from checkpoint. This will be blocked in a future version.
根源
校验后的对象进了 state，每一步都要序列化存盘；读回自定义类型就是检查点那页说的代码执行入口，框架正在收紧。
做法
用 TypedDict 当 schema（校验完是普通 dict）；非要用自定义类，就把它登记进 allowed_msgpack_modules。
6审计只记成功，或者记在检查点里按设计← ④ 机制 3
现象
复盘时问“限流为什么没做”“工单为什么尝试了两次”，查不到；或者线程清理时，检查点连同“审计”一起删了。
根源
审计要回答“没做”和“做了几次”，检查点是运行状态、会被清理。
做法
单独一张只追加的表，跳过的、被挡下的、过期的都记；保留期按公司规定，和检查点的清理策略分开。

第二圈 · 使用规范

  • 写操作只在主 agent、只在 interrupt 之后的单独节点里：子 agent 只读，防决定打架（多 agent 坑 3）。
  • 每个写操作在提议时就带上幂等键，下游建唯一索引：防坑 1、坑 3。
  • 审批卡片按动作逐项勾选，用 response_schema 校验：清单外的动作、格式不对的批准直接拒。
  • 审批带过期时间，执行前复查前提：防坑 4。
  • 按风险分级：建工单、发通知可以一人批；重启、限流、回滚要两人批或者只能人来做。
  • 审计单独一张表，只追加：防坑 6。

第三圈 · 优化和深处

发件表（outbox）：下游不支持幂等时

act 节点不直接调外部系统，而是往自己库里一张“待发送”表插一行（幂等键做主键），这一步是本地事务、天然幂等；另一个发送进程负责把它们发出去、失败重试、记下对方返回的单号。外部系统重复收到时，靠这张表里记的单号去对。Java 里做订单消息的同学对这个模式不陌生。

审批也能交给低代码

全景第 9 站的卡片和“点了以后调 resume 接口”，在 n8n 里就是一个 Wait 节点加一个 HTTP Request 节点。哪些放低代码、哪些写代码，是本站最后两页的事。

下一圈

  • 多步写操作失败要撤回：先限流，再回滚版本，回滚失败把限流撤掉。补给站里待做的“Saga 与长事务”。
  • 审计和可观测串起来：每一笔写操作带 trace id，在 trace 里点进去就能看到是哪次模型调用提的（站 09）。
  • 权限：值班 agent 用谁的身份调工单系统，最小权限怎么给（站 07 的 MCP 安全、站 10 的网关）。

↺回到⑤：改一改

  1. 给通知加幂等：加一张 sent 表，主键是通知的幂等键，再跑 twice，通知应该只发一次。（坑 2）
  2. 换掉幂等键：把 idem_key 改成返回 uuid4()，跑 replay，数工单。（坑 3）
  3. 加过期：审批请求里带 expires_at，act 里过期就只记审计不执行，用一个已经过期的时间跑一遍。（坑 4）

自测

1. 用一句话说出这一页的精华

框架只能做到至少执行一次，所以不做两遍要靠下游：每个写操作带一个代表意图的幂等键，下游用唯一约束去重；批准要能逐项勾、要校验、会过期；每一笔都记进只追加的审计表。

2. 站 04 那种进程内等人点头，到了站 08 疼在哪？

进程要一直挂着等十几分钟，重启就丢；只能全批或全拒；批准没有持久的记录。

3. 为什么不能在 state 里记“已建工单”来防重复？

副作用和检查点不在一个事务里：标记要等节点跑完才存盘，崩溃正好发生在“建完、存盘前”时标记就没了；两个 worker 同时恢复时读到的也都是“没建过”。

从 ④ 为什么这样设计推出。

4. 预测：⑤ 的 twice 里，如果两个 worker 不是同时、而是隔了 1 秒先后到，“先查后写”会建几张？

1 张：第二个 worker 查的时候第一张已经写进去了，和 replay 剧本一样。“先查后写”只在两次执行在时间上重叠时出事，所以测试环境很难发现，生产上偶尔冒一张。

从 ④ 机制 2 和 ⑤ 的 replay 推出。

5. 预测：张三把“限流到 0”改成“限流到 10”再批准，会被当成重复挡掉吗？

不会。参数变了，参数摘要就变了，幂等键是新的，下游当作一个新意图执行。这正是要在键里放参数摘要的原因。

从 ④ 机制 2 推出。
