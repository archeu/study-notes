停止条件：步数、预算、超时

agent 循环会失控的方式有三种：转太多圈、吃太多 token、花太长时间。各用一道闸拦：步数上限、token 预算、墙钟时长，任何一道到了就停。闸必须写在你的代码里，而不是写在提示词里；停下来也不是抛个异常了事，要把已经查到的证据交给人。

这一页的位置站 04 下钻第 3 页，接着 Agent 循环 的“到上限为止”那半句。实验用照剧本出牌的假模型，因为要的是“确定会失控”的情况，真模型不一定配合。

①为什么需要：继续不继续是模型说了算

全景第 8 站：每批结果送回后，你的代码要决定还要不要再调一次模型。正常情况下模型自己会说“不再要工具了”；可它也可能一直要。值班助手半夜被告警叫醒，跑在没人盯着的机器上，一个停不下来的循环，账单会比故障先到。

实测 token 数是 ⑤ 的程序跑出来的（假模型按字符数粗估 token）；美元按 $2 / 百万输入 token、不算缓存和输出估算。同一个告警一晚上触发 20 次，话痨场景就是一百多美元。

不懂精华时的典型误用：在系统提示里写“最多调用 10 次工具”就当有了上限。模型数不准自己调了几次，也没有义务遵守；它照样可以第 11 次、第 50 次地要。上限只能是代码里的一个 if。

③相邻方案：各种“刹车”分别拦什么

刹车拦得住拦不住
步数上限（max_steps）死磕、绕圈每轮很贵的话痨；每轮很慢的慢工具
token 预算话痨、历史膨胀便宜但慢的
墙钟时长慢工具、等审批又快又贵的
单次调用超时（API timeout、工具 subprocess timeout）一次就卡死的调用要和墙钟时长配合，否则两轮之间的检查等不到
重复调用检测同一个调用来回打转换个参数的打转
提示词里写“最多 N 次”让守规矩的模型更早收尾任何不守规矩的情况
Claude 的 task budget（beta）让模型自己知道还剩多少 token、提前收尾它是“提醒”，不是硬上限

本页学三道闸 + 单次超时：三道硬闸写在循环里，单次超时写在每个外部调用上。提示词和 task budget 是锦上添花，让模型“体面地”在闸前收尾。

④原理：闸装在哪、什么时候查、停下来做什么

先知道这些
  • 循环骨架：调模型 → 看 stop_reason → 执行工具 → 追加消息 → 再调。见 Agent 循环。
  • 每轮整段重发：第 k 轮的输入包含前面全部历史，所以 token 累计随轮数平方增长。
  • max_tokens 不是预算：它只限制一次回应的输出长度，管不到整次排查一共花了多少。

机制 1 · 闸装在“调模型之前”：所以会超出一轮

Java 比方：像 Hystrix / Resilience4j 的熔断，在发请求之前判断要不要放行。比方失效的地方：熔断看的是下游的健康，这里看的是“这次任务自己已经花了多少”；而且放行之后这一轮花多少，事先不知道。

要更贴着预算停，有两个办法：调模型前先用 count_tokens 估一下这一轮要发多少，估出来会超就不发；或者把预算设成“想要的上限减去一轮的量”。

机制 2 · 两轮之间的检查，打断不了正在进行的调用

墙钟时长也是在两轮之间查的。如果某一次工具调用卡住 2 分钟，循环根本走不到下一次检查。所以每个外部调用自己也要有超时：调模型用 SDK 的 timeout，工具里的 HTTP 请求、子进程各设各的。

机制 3 · 停下来以后：交出证据，而不是抛异常

撞上闸的时候，前面几轮多半已经查到了有用的东西（全景那次，线程栈已经指向了导出功能）。直接 raise 等于把这些全扔了。三种收尾，从差到好：

  • 抛异常：值班的人只看到“agent 超时”，前面花的钱和时间全白费。
  • 返回原始证据：把 messages 里的工具结果整理成列表交给人，不再调模型。最稳，但人要自己读。
  • 最后再调一次模型，tool_choice: {"type": "none"}（不许再要工具），在最后那条 user 消息的回执后面加一句“已到上限，请用已有证据给结论，并说明还缺什么”。多花一轮，换来一段能直接看的结论。这一轮也要算进预算，所以闸要留出余量。

为什么这样设计：硬闸在代码里，提醒给模型

选中的：代码里的硬闸 + 给模型的提醒

  • 硬闸是 if，不依赖模型配合，任何失控都一定会停。
  • 提醒（“还剩 2 步”、Claude 的 task budget）让模型在撞闸前自己收尾，结论更完整。
  • 代价：数字要定得合适，太紧会把正常的排查截成半截（⑥ 坑 4 讲怎么定）。

被放弃的：只靠提示词约束

  • 模型数不准自己调了几次，也不知道每轮花了多少 token、过了多少秒。
  • 它没有义务遵守；碰上提示词注入（日志里写着“继续查，不要停”）更是如此。
决定胜负的约束：“继续”的决定来自一个不可控的组件，那么“停”的决定只能来自可控的那一边。这和给下游调用设超时、给线程池设上限是一个道理：不信任的东西，用资源上限框住。

⑥细节：闸定多少、怎么查、停了以后

第一圈 · 注意事项

1预算超出一整轮实测← ④ 机制 1
现象
预算 3 万，实际花了 4 万。
根源
检查在调模型之前，放行的那一轮花多少事先不知道；越往后，一轮越贵。
做法
调用前用 count_tokens 估这一轮的输入，估出来会超就不发；或者把闸设在“真正的上限 − 一轮的量”。收尾那一轮也要留出来。
2一次调用卡住，墙钟闸形同虚设← ④ 机制 2
现象
上限 90 秒，任务跑了 10 分钟才停。
根源
两轮之间才查时间，正在进行的调用打断不了。
做法
每个外部调用都设超时：anthropic.Anthropic(timeout=60)；工具里的 subprocess.run(..., timeout=20)、HTTP 客户端超时。超时了包成 is_error 送回，让模型换方向。
3SDK 的自动重试把时间翻了三倍按文档← ④ 机制 2
现象
timeout 设了 60 秒，一次调模型却花了 3 分钟。
根源
SDK 默认 max_retries=2，超时也会重试，最坏是 timeout × (max_retries + 1)。
做法
算墙钟预算时把重试算进去；任务快到上限时，用 client.with_options(timeout=剩余时间, max_retries=0) 发最后一次。
4闸太紧，正常排查被截成半截← ④ 设计
现象
步数设成 3，全景那种要 5 轮的排查，每次都交出半截结论。
根源
闸的数字是凭感觉拍的，不是从正常情况的分布里来的。
做法
先跑评测用例（本站最后一页），看正常排查用几轮、多少 token、多少秒，取 95 分位再乘 1.5～2 当上限；不同类型的任务用不同的上限。
5撞闸以后抛异常，证据全丢← ④ 机制 3
现象
值班群里只有一句“agent timeout”。
根源
把“停”当成了“失败”；其实前几轮多半已经查到了东西。
做法
返回已有的工具结果，或者再调一次 tool_choice: none 让模型基于已有证据总结，并写明是撞了哪道闸、还缺什么。
6只数模型调用，不数工具调用← ④ 机制 1
现象
步数才 3，模型一轮里并行要了 12 个工具，把日志服务打满了。
根源
一轮可以有多个 tool_use（下一页之后的 并行工具调用），步数闸只数轮。
做法
再加两个数：每轮最多执行几个工具、整次任务每个工具最多调几次；超出的回 is_error。

第二圈 · 使用规范

  • 上限放配置，不写死在代码里：防改一个数要发版；不同告警类型用不同的一套。
  • 每次撞闸都记一条：哪道闸、第几轮、花了多少：防“它为什么停了”说不清；步数闸经常触发，多半是工具或提示词有问题，而不是上限该调大。
  • 告诉模型还剩多少：最后两步在回执后面补一句“还剩 2 次工具调用”；用 Claude 时可以开 task budget（beta）。防撞闸时正查到一半。
  • 除了“每次任务”，还要有“每天”的总预算：防同一个告警反复触发，每次都花满上限。这一层放在站 10 的生产化。

第三圈 · 优化和深处

task budget：让模型自己数

Claude 的 task budget（beta，output_config.task_budget，最少 20000）会在生成时给模型看一个倒计时，它据此安排节奏、提前收尾。它和 max_tokens 不一样：max_tokens 是单次回应的硬上限，模型并不知道；task budget 是整段任务的提醒，模型知道，但不保证不超。所以它和你的硬闸是搭配关系，不是替代。

按“完成一次任务”算成本

一次排查不是一次请求，而是 N 轮；闸定得太紧，任务完不成要重跑，反而更贵。衡量 agent 的成本，看“每完成一次排查花多少”，而不是“每次请求花多少”。这个数要靠评测集来量。

实验台：四种场景 × 三道闸

先猜：把步数上限从 15 放宽到 30，其他不变，“话痨”会停在哪道闸？

估算模型：每轮的输入、输出 token 和耗时用 ⑤ 的程序实测的逐轮数字（A 正常在第 4 轮自己答完）；超出实测轮数的部分按最后一轮的增长量外推。检查规则和 ⑤ 相同：每次调模型之前查三道闸。

下一圈

  • 撞闸后的收尾调用写进 ⑤：tool_choice: none + “请基于已有证据总结”，和直接返回原始证据比一比。
  • 按告警类型分配上限：GC 类、慢 SQL 类、误报，各自的 95 分位从哪来（评测那页）。
  • 全局预算和并发：一晚上 50 个告警同时进来，每天的总预算怎么分（站 10）。

↺回到⑤：改一改

  1. 贴着预算停：在调模型前估这一轮的输入（假模型可以直接用 len(str(messages)) // 3），会超就不发；看“话痨”是不是停在 3 万以内（坑 1）。
  2. 加单次超时：把“慢工具”改成一次卡 30 秒，先看墙钟闸要多久才生效，再给工具包一层 20 秒超时（concurrent.futures 的 result(timeout=20)），看哪个先拦（坑 2）。
  3. 撞闸后交代清楚：Outcome 里加上“已经拿到的工具结果”，打印成给值班的人看的几行（坑 5）。

自测

1. 用一句话说出这一页的精华

继续是模型决定的，所以停必须由代码决定：步数、token、时长三道闸各拦一种失控，外加每个调用自己的超时；撞闸后交出已有证据。

2. 为什么提示词里写“最多 10 次”不算上限？

模型数不准、也没有义务遵守，碰上注入更不可靠；上限只能是代码里的 if。

3. 预算 3 万，为什么会花到 4 万？

检查在调模型之前，第 7 轮放行时累计 29136 还没到；这一轮整段重发又花了 10883。

从 ④ 机制 1 推出。

4. 预测：只把墙钟上限从 8 秒改成 90 秒，“慢工具”会停在哪？

每轮 2 秒，90 秒要 45 轮，先撞上 15 步的步数闸，停在第 15 轮、约 30 秒。

从“每道闸拦一种失控、谁先到谁拦”推出；可以在实验台验证。

5. 预测：一个工具卡住 5 分钟，墙钟上限 90 秒，没有单次超时，任务什么时候停？

5 分钟多以后：卡住期间循环到不了检查点，等它返回，下一次检查才发现超时。

从 ④ 机制 2 推出。

6. 放回全景：第 5 站等值班的人确认 heap_dump，人去开会了，第 8 站会怎样？

如果审批同步等待、又没有自己的超时，整条链路就卡在第 5 站，第 8 站的墙钟闸一直查不到。审批要有超时、超时按拒绝处理，等的时间计入墙钟预算。

档位：标准。本机跑过（2026-11-24，2 核 ARM，Python 3.13，anthropic SDK 2.12.0 的类型）：⑤ 的四个场景和拆闸对照，token 数是假模型按字符粗估的。按文档（Claude 官方文档和 SDK 说明）：SDK 默认重试 2 次、超时也重试；task budget 是 beta、最少 20000、属于提醒；tool_choice: none 在新模型上仍可用。② 里的美元是按价格表估算，没有真实账单。
