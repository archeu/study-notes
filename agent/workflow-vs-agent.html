工作流还是 Agent：五种常见模式怎么选

区别只有一条：下一步做什么，是你的代码定的，还是模型定的。你定的叫工作流（workflow），模型定的叫 agent。步骤能事先写清楚的，就写成工作流：更快、更便宜、每次都一样；只有真的没法事先知道下一步时，才把方向盘交给模型。值班助手最合适的形状往往是两者混合：路由把常见告警分进固定流程，分不进去的再交给 agent。

①要解决的问题：前面两次 agent 实测，暴露了什么

实测轮数用时（本机 CPU）值得注意的
全景页5 轮349 秒第 1 轮把时间填成 20:16，日志和 GC 都落空
Agent 循环页10 轮约 681 秒连调 7 次同一个 search_notes，最后交了个空答案

可“接口变慢”这类告警，值班老手的前三步从来都一样：看报错和上线、看 GC、看线程栈。既然每次都一样，为什么要让模型每次重新决定？决定一次就要一轮完整的请求，每一轮还可能决定错。这一页要回答：哪些步骤该写死，哪些该交给模型，以及中间有哪几种常见的形状。

②不用它会怎样：什么都上 agent

  • 慢：固定的三步，agent 要转三轮才做完；工作流一次并发就查齐了。
  • 贵：每一轮整段重发，轮数越多越贵（Agent 循环 · 机制 2）。
  • 不稳：同一个问题，两次跑出 5 轮和 10 轮；参数填错、绕圈都是“每一步都由模型决定”带来的。
  • 难测：路线每次不同，出了问题不好复现，评测也只能看结果。
  • 但也有它的好：碰上从没见过的告警，agent 能自己找路，写死的流程只能说“不会”。
不懂精华时的典型误用：因为“agent”听起来更高级，把一个三步就能写死的流程交给模型自由发挥；或者反过来，为了“可控”把一个分支很多、要边查边想的排查硬写成几十个 if，结果哪个分支都覆盖不全。

③几种流派：从全写死到全放手

Anthropic 的工程文章《Building effective agents》把常见做法排成了一条线：最底层是“增强过的模型”（能检索、能调工具、有记忆）；往上是五种工作流，路线由你的代码定；最上面是 agent，路线由模型定。文章的核心建议是：先找最简单的方案，只在确实需要时才往上加复杂度。

模式谁定路线一句话值班助手里的样子
提示链 prompt chaining代码固定的几步，每步一次调用，上一步的输出喂下一步，中间可以加检查分诊 → 排查 → 写交接报告
路由 routing代码（或一次分类调用）先判断输入属于哪一类，再走那一类专门的流程按告警类型分：接口变慢 / 错误率 / 资源打满 / 其他
并行 parallelization代码拆成互不依赖的几份同时做（分段），或同一件事做几次投票同时查日志、GC、线程栈；让三次分诊投票定级别
编排者-工人 orchestrator-workers模型拆任务，代码执行一个模型临时决定拆成哪些子任务，分给“工人”，再汇总一次影响多个服务的故障，拆给几个子 agent 各查一个（站 08）
评估-改进 evaluator-optimizer代码定循环，模型打分一个生成，一个按标准评价，不合格就带着意见重写结论写完，另一次调用检查“每个数字是否出自工具结果”
agent模型模型在循环里自己决定下一步，直到完成或撞上限没见过的告警，或者固定流程查完仍没结论

值班助手用“路由 + 并行的固定流程 + agent 兜底”：常见告警走写死的流程，分不进去的、或者流程查完还没结论的，才交给前几页做好的 agent。

④核心取舍：可预测换灵活

先知道这些
  • agent 的每一步都是一轮完整请求，并且带随机性（Agent 循环）。
  • 并行执行：互不依赖的调用可以同时做（并行工具调用）。

Java 比方：工作流像 Spring Batch 或审批流引擎，步骤和分支事先画好；agent 像让一个新同事“你自己看着办”。比方失效的地方：新同事至少会记得上一步做了什么、不会无缘无故绕圈，模型的每一步却都可能偏，偏一点后面会接着偏（错误会累积）。

取舍 1 · 同一条轴：谁决定下一步

取舍 2 · 四个问题决定要不要上 agent

Claude 官方的开发指南给过一张检查单：四个问题有一个答“否”，就停在更简单的那一层。拿值班助手对一遍：

问题“接口变慢”这类常见告警没见过的告警
复杂度：步骤多、事先说不清？否：前三步每次都一样是：查什么要看查到什么
价值：结果值得多花的时间和钱？是：半夜省值班的人十几分钟是
可行：模型擅长这类任务？是：读日志、总结证据要看模型：小模型容易绕圈（实测）
出错代价：错了能被发现和挽回？是：只读 + 审批 + 人看结论是
结论工作流agent（带沙箱、审批、上限）

取舍 3 · 混合：路由在前，agent 兜底

为什么这样设计：确定的部分不该交给概率

选中的：能写死的写死，剩下的才交给模型

  • 固定步骤由代码执行：参数（比如 since）用行规算，不会填错；并发执行，一次查齐。
  • 模型只做它擅长、又没法写死的那一步：读证据、下结论；或者在没见过的情况里找路。
  • 代价：路由和流程要你维护；告警类型变了，流程要跟着改。

两个极端

  • 全写死：没见过的告警只能回“不会”，几十个 if 也覆盖不全。
  • 全交给 agent：固定的部分每次也要模型重新决定，慢、贵、偶尔还决定错。
决定胜负的约束：模型的每一次决定都有成本（一轮请求）和出错概率（实测的填错、绕圈），而且错误会沿着循环累积。所以只在“必须由模型决定”的地方让它决定，其余地方用确定的代码，把模型的决定次数压到最少。

⑤套进场景：同一个告警，写成“路由 + 固定流程”

同一台机器、同一个模型、同一份现场数据。路由用三条正则；“接口变慢”的流程把 SOP 前几步写死：since 按“告警时间往前 15 分钟”算，四样证据并发查，然后只调一次模型写结论。

读出来的结论
  • 对这类告警，工作流快了 4～8 倍，模型调用少了 4～9 次；证据一次查齐，since 不会填错，也不会绕圈。
  • 两条没匹配的告警说明了工作流的边界：支付回调没有对应流程，只能交给 agent；它不会“不会装会”。
  • 结论里“使用 CMS 收集器”是个过时的建议（CMS 在 JDK 9 标为废弃、JDK 14 移除）。写死流程解决的是“查什么”，“说得对不对”仍要靠评估-改进那一步或评测去抓（下下页）。

⑥反例和误用

第一圈 · 常见反例

1为了“是个 agent”而上 agent← ④ 取舍 2
现象
一个三步就能写死的流程，交给模型自由发挥，延迟和账单都翻了几倍，偶尔还走错路。
根源
没过“复杂度”那一问：步骤事先说得清，就不需要模型决定。
做法
先写单次调用和工作流版本，量过不够用再往右挪。
2为了“可控”把开放问题写成几十个 if← ④ 取舍 1
现象
排查规则越写越多，新类型的故障还是落在“其他”里，没人处理。
根源
开放问题的分支是写不完的。
做法
常见的写死，长尾交给 agent；看日志里哪类长尾多了，再把它升格成固定流程。
3路由分错了，后面全错← ④ 取舍 3
现象
“下游超时导致 P99 升高”被正则分进了“接口变慢”，流程只查本服务的 GC 和线程栈，结论说“一切正常”。
根源
路由是所有后续步骤的前提，它错了后面都白做。
做法
路由要有“不确定”这个出口，拿不准就交给 agent；用评测集专门测路由的准确率。
4固定流程查完没结论，就此结束← ④ 取舍 3
现象
GC 正常、线程栈正常，流程交出一句“未发现异常”，值班的人只能自己从头查。
根源
工作流只会它写好的那几步。
做法
让总结那一步也能回答“证据不足”，然后把已有证据作为第一条消息交给 agent 继续查，而不是从零开始。
5写死了流程，就以为结论一定对实测← ④ 设计
现象
⑤ 的结论证据全对，下一步却建议“使用 CMS 收集器”。
根源
工作流管的是查什么、怎么查；最后那次模型调用照样会编、会过时。
做法
加一步评估-改进：另一次调用按清单检查（数字出自证据、建议适用于当前 JDK 版本），不合格带着意见重写；更系统的做法是评测（先写 10 条评测用例）。

第二圈 · 使用规范

  • 先写最简单的版本当基线：单次调用、工作流各跑一遍评测，agent 要比它们好得足够多才值得。防“为了 agent 而 agent”。
  • 路由的每个出口都要能落到一个流程或 agent：防告警掉进没人处理的缝里。
  • 固定流程的参数在代码里算，不让模型填：防 工具怎么设计 里那种落空。
  • 记录每次走的是哪条路：哪类告警总落到 agent，就是下一个该写成流程的候选。

第三圈 · 深处

编排者-工人什么时候值得

当子任务事先列不出来、但拆开后彼此独立时：比如一次故障同时波及订单、库存、支付三个服务，编排者先判断要查哪几个，再并行派出去。它比单个 agent 快，但多了一层“拆错了”的风险和汇总的成本。值班助手 v1 用不上，站 08 多 agent 再展开。

评估-改进和评测的区别

评估-改进是线上的一步：每次结论出来都检查、不合格当场重写，多花一次调用。评测是线下的：拿固定的用例集批量跑，衡量整体好坏、比较两个版本。前者兜住单次的错，后者告诉你改动有没有让整体变好。站 04 的最后一页讲评测。

实验台：这件事该用哪种模式？

先猜：“每天早上把夜里的告警汇总成一份交接报告：先按服务分组，每组写摘要，最后合成一份”，该用哪种？

↺回到⑤：改一改

  1. 加评估-改进：总结之后再调一次模型，按清单检查（每个数字是否出现在证据里、建议是否适用于 JDK 17），不合格带着意见重写一次；看 CMS 那条能不能被抓到（反例 5）。

自测

1. 用一句话说出这一页的精华

工作流和 agent 的区别是谁决定下一步；能写死的写死（更快、更便宜、可预测），真的没法事先知道下一步的才交给模型，常见做法是路由在前、agent 兜底。

2. 什么都上 agent，疼在哪？

慢、贵、每次路线不同难测；固定的步骤也要模型每次重新决定，还会决定错（实测的填错时间、绕圈）。

3. 为什么工作流版的 since 不会填错？

它由代码按“告警时间往前 15 分钟”算出来，根本不经过模型。

从 ④ 为什么这样设计推出。

4. 预测：告警写的是“order-svc 调用 inventory-svc 超时”，⑤ 的路由会怎样？

“超时”命中“接口变慢”的正则，走本服务的 GC 和线程栈流程，很可能查不出问题（真正的原因在下游）。路由需要“下游”这类信号，或者在拿不准时交给 agent。

从反例 3 推出。

5. 预测：把 ⑤ 的工作流换成每样证据查一次、各调一次模型解读，再调一次汇总（提示链），会怎样？

模型调用从 1 次变成 5 次，时间接近 agent；好处是每次调用的输入更短、更专注。只有证据很长、一次读不下时才值得。

从 ④ 取舍 1 推出：往右挪一格要有理由。

6. 放回全景：第 1 站决定用“路由 + 工作流 + agent 兜底”，第 3～8 站会有什么变化？

常见告警根本不进 agent 循环：第 3 站的“模型提议”换成代码直接并发查证（第 4、6 站照样要沙箱），第 8 站的守门只剩一次调用的超时；只有落到 agent 的那部分，才走完整的 10 站。

档位：标准。本机跑过（2026-11-24，2 核 ARM，llama.cpp b12618 的 llama-server，Qwen3-1.7B Q4_K_M，anthropic SDK 2.12.0，Python 3.13）：路由 + 固定流程一次（81 秒），以及两条别的告警的路由结果；agent 的两组数字来自全景页和 Agent 循环页的实测。按文档：五种模式和“先找最简单的方案”出自 Anthropic 工程文章《Building effective agents》（2024-12）；四个问题的检查单出自 Claude 官方开发指南；CMS 在 JDK 9 废弃、JDK 14 移除（JEP 363）。
