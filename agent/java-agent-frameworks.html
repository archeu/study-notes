④原理：同一套概念，三种 Java 写法

先知道这些
  • Spring AOP 的环绕通知：一串拦截器按顺序包住目标方法，每一层都能在调用前后做事（AOP 拦截器链、AOP 代理原理）。Spring AI 的 Advisor 就是这个模型，包住的是“调一次模型”。
  • 自动配置：spring-ai-starter-model-anthropic 按 application.properties 装好 ChatModel 和 ChatClient.Builder（Spring Boot 自动配置）。
  • 反射读参数名：@Tool 方法的参数名会成为工具说明书里的字段名。编译时不带 -parameters，反射只拿得到 arg0、arg1。
  • 前几页的概念：model + tools 的循环（LangGraph 上手）、状态图和检查点（检查点）、主从和并行（多 agent）。

为什么这样设计：循环放进拦截链，还是藏在代理里

Spring AI：循环在 Advisor 链里

  • 排在里面的 Advisor 每一轮都会被调到：记日志、计量、记忆、护栏，在每次模型调用上都生效，⑤ 的 RoundLogger 看到了 3 轮。
  • Advisor 能改请求和响应，不只是看。
  • 代价：顺序要想清楚。排在 ToolCallingAdvisor 外面的 Advisor 只看到一头一尾（↺ 练习 2）。

LangChain4j：循环在 AiServices 代理里

  • 用起来最省事：一个接口、一行 AiServices.builder。
  • ChatModelListener 每一轮都会被回调，但只能看，不能改请求。
  • 要在轮与轮之间改东西，得用它自己的钩子（工具执行前后、输入输出护栏）。
决定胜负的约束：日志、计量、记忆、护栏这些横切关注点要在每一轮模型调用上生效，循环就得在拦截链里面；放在链外（或者藏在代理里），拦截器只能管到一头一尾。Spring 选了前者，因为它本来就有 AOP 这套“按顺序包一层又一层”的模型；LangChain4j 选了用起来最短的写法。

读出来的结论
  • 两个 Java 框架走的路和 Python 版（LangGraph 上手 ⑤）一模一样：先 searchLogs(P99) 落空，再 parseGcLog，结论只到 Full GC。路是模型定的，不是框架定的。

⑥细节

第一圈 · 注意事项

1工具参数名成了 arg0、arg1实测← ④ 先知道这些
现象
Spring AI 版第 1 轮要的是 searchLogs{"arg0":"20:00","arg1":"20:16"}：模型把时间填进了关键字，什么都没查到，最后给了一句“没有匹配的日志”就结束了。
根源
工具说明书里的字段名来自反射读到的参数名。不带 -parameters 编译，反射只拿得到 arg0；描述还在，可这个小模型还是照着字段的顺序乱填。继承 spring-boot-starter-parent 的项目默认开着，study-labs 的父 pom 不是它，所以中招。
做法
pom 里 <maven.compiler.parameters>true</maven.compiler.parameters>（Gradle 是 options.compilerArgs << '-parameters'），改完 mvn clean。LangChain4j 也一样靠参数名。
2两个框架报的 token 差十几倍实测← ④ 机制 1
现象
同一个问题，Spring AI 报累计输入 2007，LangChain4j 报 148。
根源
Anthropic 接口的 input_tokens 只算没命中缓存的部分。Spring AI 的 getPromptTokens() 把 cache_read_input_tokens 加了回去（99 + 504 = 603），Python 的 langchain-anthropic 也是（多 agent 那页核对过）；LangChain4j 的 inputTokenCount() 没加，命中的要从 AnthropicTokenUsage.cacheReadInputTokens() 另取。
做法
做成本统计、比较框架前，先对齐口径：未命中、命中、写缓存三个数分开记，再按各自的价格算钱。
3Advisor 排错了位置，只看到一头一尾按设计← ④ 机制 2
现象
写了个计量 Advisor，结果每次请求只记了一次调用，token 也只记了最后一轮。
根源
getOrder() 数字小的在外层。排在 ToolCallingAdvisor 外面，就包住了整个循环，只看到进去的第一次请求和出来的最终回答。另外 Spring AI 2.1 只允许有一个工具 Advisor，自己挂的会替掉自动注册的那个。
做法
每一轮都要生效的（计量、日志、护栏），getOrder() 返回比 ToolCallingAdvisor.DEFAULT_ORDER 大的数；只管整次对话的（记忆、整体超时），放外面。
4Spring AI Alibaba 和 Spring AI 的版本对不上历史原因
现象
在 Spring AI 2.1 的工程里加 spring-ai-alibaba-graph-core:1.1.2.3，依赖树里冒出一串 Spring AI 1.1.2 的包，和 2.1 的同名类冲突。
根源
Spring AI Alibaba 跟着 Spring AI 的大版本走：1.1.2.x 配 Spring AI 1.1.x（Spring Boot 3）；配 Spring AI 2.x 的 2.0.0 截至 2026-11 还是里程碑版（M1.1）。
做法
要么整个工程停在 Spring Boot 3 + Spring AI 1.1.x + Spring AI Alibaba 1.1.2.x，要么像 ⑤ 这样把图放在单独的模块里；生产上别混用里程碑版。
5图跑完了，JVM 不退出实测← ④ 机制 1
现象
Spring AI Alibaba Graph 的并行节点跑完、main 也走完了，mvn exec:java 一直挂着，本机等到 10 分钟超时。
根源
不指定线程池时，并行节点跑在框架自建的 parallel-node-action-thread-N 上（日志里写着核心 4、最大 8），这些线程不是守护线程，JVM 要等它们。
做法
RunnableConfig.builder().defaultParallelExecutor(pool) 传自己的线程池，用完关掉；在 Spring 应用里就交给容器管理的线程池。

第二圈 · 使用规范

  • 打开 -parameters，工具参数再写清 @ToolParam 描述：防坑 1。
  • 工具类无状态、线程安全，业务逻辑放在已有的 Service 里，@Tool 方法只做转发：工具会被并行调用，也方便单测。
  • 每个 Advisor 都写明 getOrder()，在代码里注释它在工具循环里面还是外面：防坑 3。
  • 版本用 BOM 锁死：spring-ai-bom、langchain4j-bom，Spring AI Alibaba 跟着 Spring AI 的大版本选：防坑 4。
  • token 计量统一成“未命中 / 命中 / 写缓存”三个数：防坑 2。

第三圈 · 优化和深处

Spring AI 里没有的，去哪找

检查点和停下等人，Spring AI 本身不管：对话记忆 ChatMemory 只存消息，不存“走到哪一步”。要全景那样的流程，配 Spring AI Alibaba Graph；或者把审批交给已有的流程引擎（Flowable 的 UserTask），agent 只负责提议。MCP 服务端和客户端 Spring AI 都有，见写 MCP 服务端。

LangChain4j agentic（beta）

1.24.0-beta34 的 agentic 模块里有 SequentialAgentService、ParallelAgent、LoopAgent、ConditionalAgent、SupervisorAgent，几个 agent 通过共享的 AgenticScope 传数据。思路和多 agent 那页一样，只是还在 beta，接口可能变。

自测

1. 用一句话说出这一页的精华

Python 学过的概念 Java 都有：Spring AI 管模型、工具和 Advisor 链（工具循环就在链里转），Spring AI Alibaba Graph 是 Java 版 LangGraph，LangChain4j 不依赖 Spring、一个接口就是一个 agent；差别在默认值和口径。

2. 在 Java 系统里单独起一个 Python agent 服务，疼在哪？

鉴权、事务、追踪、发布、监控都要再搭一套；写操作还得回调 Java 那边的工单客户端；两种语言、两套依赖。

3. 工具参数名成了 arg0，根源是什么？

Spring AI 和 LangChain4j 都靠反射读参数名生成工具说明书，编译时没带 -parameters，反射只拿得到 arg0、arg1。

从 ④ 先知道这些推出。

4. 预测：再加一个 MessageChatMemoryAdvisor（排在 ToolCallingAdvisor 外面），连问两次，第二次的第 1 轮输入会变成多少？

会多出第一次的问题和最终回答（几百 token），因为记忆 Advisor 在整次对话外面，把上一次的问答拼进这一次的请求；它排在外面，只在第一轮请求前拼一次，工具循环里的每一轮都带着这些历史。
