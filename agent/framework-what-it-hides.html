框架替你做了什么、藏了什么

框架替你接管的是控制流和状态：一步步往下跑、并行、存盘、停下等人、从断点接着跑。它藏起来的是这些事的默认值和语义：什么时候存盘，恢复时哪段代码会重跑，并行跑在哪个线程上，死循环要转多少圈才停。这几条不摸清就上线，等于让框架的默认值替你做了生产决策。

④核心取舍：交出控制流，换来存盘和恢复

先知道这些
  • 状态图：节点是你写的普通函数，收到当前 state，返回要改的那几个键；边说明下一步去哪个节点。下一页细讲。
  • superstep（一步）：框架一步一步地跑，同一步里的节点并行跑完，返回值一起合进 state，然后存一次盘。全景第 4 站的三个子 agent 就在同一步里。
  • Java 比方：LangGraph 像嵌在进程里的 Flowable，流程实例每走一步落一次库，可以停下等人审批。比方失效的地方：Flowable 的节点是确定的代码，LangGraph 的节点里是概率模型；Flowable 有数据库事务做边界，LangGraph 的边界是 superstep。

为什么这样设计：恢复的最小单位是节点

第 7 步那个“整个节点重跑”最容易出事。为什么框架不从 interrupt() 那一行接着往下跑？看三种做法：

LangGraph：按节点存盘

  • 节点里写普通 Python，随便调模型、读时间、用随机数，没有额外的规矩。
  • 存盘点清清楚楚：每个 superstep 结束一次，存的是 state 和“下一步是哪个节点”。
  • 代价：节点内部没人记账，恢复时整个节点从头跑，节点里的副作用会再发生一次（⑤ 实测：通知发了 2 次）。

Temporal 式：给每个副作用记账

  • 每次外部调用（activity）的结果都记进事件历史，恢复时重放代码，做过的调用直接拿记下的结果，不再做。
  • 工作流代码必须是确定的：不能直接读时间、用随机数、调模型，这些都得包成 activity。
  • 要另外部署一套服务端，团队要学一套新的编程模型。

手写：存“走到第几步”

  • 每一行都看得见，出了事好查。
  • 并行任务各自的结果、等人、历史版本都要自己写；写完就是 ② 里那个小号工作流引擎。
决定胜负的约束：Python 没办法把一个执行到一半的函数（它的栈帧）存进数据库。能存的只有“state + 下一步是哪个节点”，所以恢复的最小单位只能是节点。想要更细，就得像 Temporal 那样给每个副作用记账，代价是代码要守确定性的规矩。LangGraph 选了前者，另外留了一个口子：函数式 API 的 @task 会把结果存进检查点，恢复时不重跑（本机探针实测：调用 1 次）。

最少的写法：把藏起来的默认值写出来

把默认值写在代码里每个参数的坑见 ⑥
builder.add_node("investigate", investigate,
    retry_policy=RetryPolicy(max_attempts=3),  # 默认不重试
    timeout=120)                               # 默认不限时（秒）
graph = builder.compile(
    checkpointer=PostgresSaver(conn))          # 不写就不存盘
graph.invoke(inp, {
    "configurable": {"thread_id": "alert-7f3a"},  # 用业务键
    "recursion_limit": 40,                     # 默认 10007
    "max_concurrency": 4},                     # 同一步最多几个线程
    durability="sync")                         # 默认 async

这些默认值在源码哪里

recursion_limit：langgraph/_internal/_config.py，DEFAULT_RECURSION_LIMIT，环境变量 LANGGRAPH_DEFAULT_RECURSION_LIMIT 可改。

durability：pregel/main.py 里 stream() 的文档字符串，三种取值 sync / async / exit。

retry_policy、timeout：graph/state.py 里 add_node() 的参数，不传就是不重试、不限时。

读出来的结论
  • 并行是真的线程并行。节点里碰共享的可变对象就要自己加锁，框架不管（①）。
  • durability 的差别要等进程被杀才看得出来：节点抛异常时三种模式都存下了第 3 步；kill -9 时，exit 模式什么都没留下（②、②b）。
  • 恢复时节点整个重跑，interrupt 前面的副作用发生了两次（③）。
  • 没有出口的循环，默认要转 10007 步才停。换成真模型，每步按 5 秒算，就是十几个小时的 token（④，后半句是估算）。
  • 你写了 5 个节点函数，一行存盘代码都没写；框架调了 8 次函数、存了 17 次盘（⑤）。

⑥反例和误用

第一圈 · 注意事项

1以为框架会替你拦住死循环实测← ④ 机制 1
现象
模型反复调同一个工具、条件边永远回到同一个节点，图一直跑，账单一直涨。
根源
步数上限归框架管，默认值是 10007（langgraph 1.2.24）。网上很多教程写的是 25，那是 langchain_core 里的同名常量，也可能是更早的版本。
做法
每次 invoke 都显式传 recursion_limit；站 04 的守门（步数、token、时长）照样写在图里，不只靠框架。
2恢复时副作用又发生一次实测← ④ 为什么这样设计
现象
批准以后群里收到两条一样的通知；或者节点超时重试，工单建了两张。
根源
恢复的最小单位是节点。interrupt 恢复、retry_policy 重试、进程崩溃后接着跑，节点都是从第一行重新执行。
做法
副作用单独放一个节点，放在 interrupt() 之后，并且带幂等键（全景第 10 站）。
3并行节点改同一个对象实测← ④ 机制 2
现象
计数少了（600 变 201）；写全景页实验时，三个子 agent 往同一个 JSON 文件里记次数，文件直接被写坏，报 JSONDecodeError。
根源
同一步里的同步节点跑在线程池上。框架只保证返回值经 reducer 安全合并，不管你在节点里碰了什么。
做法
节点只通过返回值改 state；非碰外部共享资源不可时，自己加锁。
4没配检查点，也能“停下来”实测← ④ 机制 2
现象
开发时 invoke 照样返回 __interrupt__，一切正常；等到恢复时才报 RuntimeError: Cannot use Command(resume=...) without checkpointer。
根源
停下只需要抛一个异常；接着跑需要存过的 state。没配 checkpointer，框架什么都没存。
做法
有 interrupt 的图，compile 时一定传 checkpointer；单测里用 InMemorySaver，生产用 Postgres。
5长任务用了 durability="exit"实测← ④ 机制 2
现象
调查跑到一半进程被 OOM Killer 杀了，重启后这条线程什么都没留下，只能从头再查一遍。
根源
exit 模式只在图退出时存一次。节点抛异常也算退出，所以开发时看不出问题；被 kill -9 时框架根本没有机会存。
做法
短小、无状态、丢了就重跑的图才用 exit；有副作用、要等人的图用 sync，或者用默认的 async。
6以为框架把提示词处理好了按文档← ④ 机制 1
现象
用现成的 agent 封装（预制好的 ReAct agent 之类），效果不对，却不知道模型实际收到了什么。
根源
封装越高，藏起来的提示词、工具格式、消息裁剪就越多。Anthropic 在《Building effective agents》里说，对底层到底做了什么的错误假设，是客户出错的常见来源。
做法
至少打开一次 trace，看模型真实的输入输出（站 09 的可观测会细讲）；拿不准的就用底层的 StateGraph 自己写节点。

第二圈 · 使用规范

  • 每张图都显式写出 checkpointer、durability、recursion_limit、retry_policy、timeout：防升级时默认值悄悄变了，也让读代码的人一眼看到。
  • 有副作用的操作单独成节点，放在 interrupt 之后，带幂等键：防重跑。
  • 节点只通过返回值改 state，不碰全局可变对象：防线程竞争。
  • thread_id 用业务键（告警指纹、工单号）：防同一件事起两条线程。
  • 锁死版本（uv.lock），升级时读 release notes 并 grep ④ 里那三处源码：框架迭代很快，默认值会变。

第三圈 · 优化和深处

存盘是有成本的

5 个节点的图存了 17 次（⑤ 实测）。换成 Postgres，每次都是一次网络往返和一次写入。短小、无状态的图用 durability="exit" 只存一次；要等人、有副作用的图别省这个钱。默认的 async 是折中：在下一步执行的同时写上一步，进程正好在那一刻被杀，上一步可能还没写完（按文档）。

什么时候干脆不用框架

只有一个循环、不用等人、跑几秒就完的 agent，站 04 那 100 多行更清楚。框架值钱的地方是 ② 表里那几行：并行、存盘、等人、恢复。用不到它们，就是白交了控制流。

下一圈

  • LangGraph 的 Pregel 循环源码（pregel/_loop.py）：一个 superstep 里，任务调度、写入合并、存盘的顺序。
  • Temporal、Restate 这类“持久执行”引擎和 LangGraph 对比：记账粒度、确定性约束、部署成本。
  • 框架的可观测：callbacks、LangSmith、OpenTelemetry，怎么看到被藏起来的提示词（站 09）。

自测

1. 用一句话说出这一页的精华

框架接管控制流和状态（循环、并行、存盘、等人、恢复），藏起来的是这些事的默认值和语义；用之前要把它们摸清并写进代码。

2. 站 04 的手写循环，到了站 08 疼在哪？

它只答应了“一个进程从头跑到尾”。并行、每步存盘、停下等人、失败只重跑失败的，都得自己写，写完就是一个小号工作流引擎。

3. 批准以后通知发了两次，根源是哪条原理？

恢复的最小单位是节点：Python 存不下执行到一半的函数，框架只能存 state 和“下一步是哪个节点”，恢复时从节点第一行重跑。
