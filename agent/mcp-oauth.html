远程 MCP 的鉴权（OAuth）

远程 MCP 服务端是一个 OAuth 的资源服务器：没带令牌就回 401，并在响应头里写明“去哪儿找授权服务器”。客户端顺着元数据找过去，弹浏览器让你登录（授权码加 PKCE），换到一个只对这一个服务端有效的短期令牌，之后每个请求都带上它。精华是：令牌绑死在一个服务端上，服务端只认发给自己的令牌，也绝不把它转给下游。

①为什么需要：内网的 tickets 要知道“是谁、能干什么”

在全景第 3 站，这一步要解决的是：tickets 跑在内网，全组的 Claude Code、值班助手都连它。它要回答三个问题：这次调用是谁发起的（值班的你）？他允许 Claude Code 替他做什么（只读工单，还是也能写评论）？这个凭证要是被偷了，坏人能拿去干多少事？

②没有它会怎样：在配置里写一个 API key

最省事的做法：tickets 发一个 API key，大家写进 .mcp.json 的 headers 里（"Authorization": "Bearer ${TICKETS_KEY}"，Claude Code 支持这种写法）。和 OAuth 对照几条要求：

要求全组共用一个 key每人一个 keyOAuth
知道是谁在操作不能：工单上只看得到“tickets-key 写了评论”。能。能：令牌里带着你是谁（⑤ 实测查询人 oncall-you）。
只给需要的权限不能：一个 key 通常什么都能干。差一点：要服务端自己按 key 配权限。能：tickets:read 和 tickets:write 分开，要写的时候再升级。
被偷了能用多久、用在哪一直有效，直到有人发现并换掉。同左。⑤ 里的令牌 5 分钟过期，而且只对 tickets 有效，拿去调别的服务端会被拒。
有人离职换 key，通知所有人改配置。吊销他那一个。在 SSO 停掉账号，所有令牌都拿不到了。
第一次用的麻烦把 key 贴进配置就行。要找人申请 key。第一次弹浏览器登录一次，之后自动刷新。

API key 并非一无是处：机器对机器、没有“人”参与的调用（比如定时巡检的脚本），用 key 或 OAuth 的 client credentials 模式更合适。MCP 规范说授权是“可选的”，HTTP 传输上“应当”遵守它；人通过 agent 去操作公司系统，就是它要管的场景。

不懂精华时的典型误用：tickets 收到用户的令牌以后，原样带着它去调后面的工单系统 API（令牌透传）。这样工单系统分不清请求来自 tickets 还是用户本人，审计和限流都失效，tickets 一旦被攻破，攻击者手里的令牌能直接用在工单系统上。规范明令禁止：MCP 服务端不得透传它收到的令牌，调下游要用自己的凭证（坑 5）。

③相邻方案：几种认人的办法

办法怎么认适合
API key / 共享密钥请求头里带一串固定的字符个人小工具、机器对机器
mTLS（双向证书）客户端也出示证书服务和服务之间，证书由运维统一发；不适合每个人的笔记本
OAuth client credentials客户端拿自己的 id 和密钥换令牌，没有用户参与后台任务、巡检脚本
OAuth 授权码 + PKCE用户在浏览器里登录并同意，客户端换到代表这个用户的令牌人通过 agent 操作公司系统：MCP 规范为 HTTP 传输选的就是它

本页学授权码 + PKCE：规定动作，Claude Code 这类客户端都按它实现；学会了，接任何一个支持 OAuth 的远程 MCP 服务端都是同一套流程。

④原理：从一个 401 走到一个 Bearer 令牌

先知道这些
  • 授权码模式：客户端不碰你的密码。它把你的浏览器送到授权服务器，你在那里登录、点同意；授权服务器把浏览器跳回客户端的回调地址，带一个一次性的授权码；客户端再拿授权码去换访问令牌。
  • PKCE：客户端先随机生成一个秘密 code_verifier，只把它的 SHA-256 摘要 code_challenge 放进授权请求；换令牌时再出示原文。授权码就算在跳转途中被截走，没有原文也换不到令牌。方法要用 S256。
  • Java 比方：Spring Security 的 oauth2Login() 就是客户端这一侧，oauth2ResourceServer() 就是 tickets 这一侧；见 Spring Security 认证与授权。比方失效的地方：Web 应用的客户端是你自己写的、你信它；MCP 的客户端是 Claude Code 这类第三方程序，服务端事先并不认识它，所以多了“发现”和“注册”两步。

机制 3 · 用令牌：服务端验三样，权限不够就要求升级

tickets 收到请求时查什么不满足时回什么⑤ 实测
有没有令牌，令牌还有效吗（没过期、没吊销）401，WWW-Authenticate 里给出资源元数据地址不带令牌、令牌放在查询串里：都是 401（规范只认请求头里的 Bearer）
令牌是不是发给我的（audience / resource）401授权服务器给 :9999 发的令牌拿来调 tickets：401
权限（scope）够不够403，error="insufficient_scope"，并写出需要的 scope没有 tickets:read：403；add_comment 没有 tickets:write：403，客户端随即升级授权

令牌的 audience 从哪来：客户端在授权请求和换令牌请求里都带上 resource=https://…/mcp（RFC 8707），授权服务器把它写进令牌。规范要求两处都必须带，不管授权服务器支不支持。

为什么这样设计：一个令牌只对一个服务端有效

令牌绑定受众，服务端不透传

  • tickets 被攻破，攻击者拿到的令牌只能调 tickets，调不了工单系统、也调不了别的 MCP 服务端。
  • 一个恶意的 MCP 服务端收到你的令牌，拿去调 tickets 也会因为 audience 不对被拒（防“借刀”）。
  • 代价：每个服务端各走一次授权（第一次各弹一次浏览器），服务端调下游要另有自己的凭证。

一张全公司通用的令牌

  • 登录一次，到处能用。
  • 任何一个拿到它的服务端都能冒充你去调别的系统。你装的 MCP 服务端越多，泄露的口子越多。
  • 下游分不清请求是你本人发的，还是某个服务端拿着你的令牌发的。
决定胜负的约束：MCP 服务端不全是你公司写的，有的来自第三方，有的可能不可信（下一页）。用户会把同一个身份交给很多个服务端，任何一个都不能拿着它去碰别人的地盘。

读出来的结论
  • 客户端事先只知道 tickets 的网址，第 1～3 步自己找到了授权服务器；第 4 步动态注册了自己。
  • 授权请求里有 code_challenge_method=S256 和 resource=…/mcp：PKCE 和受众绑定，规范的两个“必须”都在。
  • 第一次只要了 tickets:read：客户端按规范取服务端给的 scope（401 里没写，就用资源元数据里的 scopes_supported），而不是自己配置里写的 read + write。写评论时被 403，带着 read + write 重新授权，拿到新令牌后成功，这就是“按需升级”。
  • 令牌的三道检查都是真的：别处的令牌 401、权限不够 403、不放请求头 401。

⑥细节

第一圈 · 注意事项

1issuer 多一个斜杠，客户端拒绝实测← ④ 机制 1
现象
第一次跑，第 3 步就失败：“Authorization server metadata issuer mismatch: http://127.0.0.1:9000/ != http://127.0.0.1:9000”。资源元数据里写的是不带斜杠的，授权服务器元数据里的 issuer 被 URL 类型自动补了一个斜杠。
根源
RFC 8414 要求 issuer 逐字符比较，MCP 规范也说不一致就不能用这份元数据。这是防“混淆攻击”的：一个授权服务器不能冒充另一个。
做法
issuer 在三处写成完全一样的字符串：授权服务器配置、它的元数据、资源服务器的 authorization_servers。用 URL 类型时注意它会不会补斜杠（演示代码用了 url_preserve_empty_path）。
2客户端只要了读权限，写操作被拒实测← ④ 机制 3
现象
客户端配置里写的是 tickets:read tickets:write，授权请求里却只有 tickets:read，第一次调 add_comment 失败。
根源
规范规定客户端选 scope 的顺序：先用 401 挑战里的 scope，没有就用资源元数据的 scopes_supported。服务端只公布了 read，客户端就只要 read。这是有意的：先给最小权限，需要时再升级。
做法
服务端在 401 里写 scope="tickets:read"，在需要写的地方回 403 insufficient_scope 并写全需要的 scope，客户端会自动升级。别为了省事把 tickets:write 也放进 401 的默认 scope，那样每个人一上来就拿到写权限。
3动态注册时申报的 scope，卡住了后来的升级实测← ④ 机制 2
现象
403 之后客户端带着 read + write 重新授权，授权服务器回 invalid_scope：“Client was not registered with scope tickets:write”。
根源
客户端第 4 步动态注册时，只申报了当时要的 tickets:read；SDK 的授权服务器按注册信息限制这个客户端以后能申请的 scope。
做法
授权服务器按自己的策略决定一个客户端能申请哪些 scope（演示里放宽成两种，给不给仍由用户同意时决定）；或者用预注册、客户端元数据文档（CIMD）把能申请的范围一次写清。另外，2026-07-28 起动态注册已标为弃用，新实现优先用 CIMD。
4只验“令牌有效”，不验“是不是发给我的”实测← ④ 机制 3
现象
同一个授权服务器给 :9999 那个服务端发的令牌，拿来调 tickets：开了 validate_token_resource 时 401；不开，这个令牌就能用。
根源
令牌有效只说明“授权服务器发过它”，不说明“它是给我的”。规范要求服务端必须校验受众，只接受明确发给自己的令牌。mcp 2.3.0 里这个开关没设时会警告，并且行为等于关闭，它的说明里写着 3.0 会改成默认打开。
做法
Python 显式写 validate_token_resource=True；用 JWT 的服务端校验 aud（Spring Security 里给 JwtDecoder 加 audience 校验器）。
5拿用户的令牌去调下游（令牌透传）← ④ 为什么这样设计
现象
tickets 收到你的令牌，原样带着它去调公司工单系统的 REST API。功能正常，直到安全审计发现工单系统的日志里全是“用户本人”在操作。
根源
令牌是发给 tickets 的，工单系统本不该接受它；透传让下游分不清是谁在调用，限流和审计失效，tickets 一旦被攻破，令牌能直接用在下游。规范原话：MCP 服务端不得透传它从 MCP 客户端收到的令牌。
做法
tickets 调下游用自己的服务账号凭证；需要“以用户身份”调下游时，用令牌交换（RFC 8693）向授权服务器换一张发给下游的新令牌。

第二圈 · 使用规范

  • stdio 服务端不走 OAuth：规范说 stdio 不应该用这一套，凭证从环境变量来。防的是：给本机工具硬套一个浏览器登录。
  • 访问令牌要短：演示是 5 分钟，配刷新令牌；公开客户端的刷新令牌要轮换（演示里每次刷新都换新的）。防的是令牌被偷后长期可用。
  • scope 按读写拆开，按需升级：tickets:read 默认给，tickets:write 用到才要。防坑 2 那种“一上来就全权”。
  • 只认请求头里的 Bearer：不接受查询串里的令牌（实测 401），因为网址会进日志、浏览器历史、代理记录。
  • 回调地址只用 localhost 或 HTTPS，授权服务器精确匹配：防授权码被跳到别人的地址。
  • 客户端按 issuer 分开存凭证：换了授权服务器就重新注册，不复用。防一个授权服务器的凭证被拿到另一个那里用。

第三圈 · 优化和深处

客户端身份：CIMD 取代动态注册

动态注册（RFC 7591）让任何客户端都能来注册，授权服务器最后攒了成千上万个一次性的客户端。2026-07-28 版把它标为弃用，推荐客户端元数据文档（CIMD）：client_id 就是一个 HTTPS 网址，指向客户端自己发布的一份 JSON（名字、回调地址），授权服务器去取。同一个客户端在所有授权服务器上用同一个 id。顺序是：预注册 → CIMD → 动态注册 → 让用户手填。

防混淆：iss 参数

客户端同时连好几个授权服务器时，回调里拿到的授权码到底是谁发的？RFC 9207 让授权服务器在回调里带上 iss，客户端和跳转前记下的 issuer 逐字比较，不一致就丢弃，连错误信息都不显示。演示的授权服务器带了 iss，SDK 客户端做了这个校验。

Java 那一侧：Spring Security 资源服务器

第 4 页的 Java tickets 要加鉴权，就是给它配 oauth2ResourceServer：用 JWT 时配授权服务器的 issuer，并加上 audience 校验；还要自己提供 /.well-known/oauth-protected-resource 和 401 的 WWW-Authenticate。这一页没在本机跑 Java 版，做法按 Spring Security 和 MCP 规范的文档。

升级授权的分寸

规范要求客户端升级时申请“已有的 + 挑战要求的”的并集，重试几次还不行就当作永久失败，并记录升级次数，防止服务端和客户端互相踢皮球、无限弹浏览器。Claude Code 里，远程服务端的登录和重新登录在 /mcp 命令里操作。

自测

1. 用一句话说出远程 MCP 鉴权的精华

MCP 服务端是 OAuth 资源服务器：401 里指路，客户端自己发现授权服务器、让你登录换令牌；令牌短期、按 scope 授权、只对这一个服务端有效，服务端只认发给自己的令牌，也不转给下游。

2. 全组共用一个 API key，疼在哪？

不知道是谁在操作、权限没法拆、被偷了一直能用、有人离职要全员换配置。

3. 头号坑“issuer 差一个斜杠就失败”，根源是哪条？

④ 机制 1：客户端必须核对授权服务器元数据里的 issuer 和资源元数据里写的逐字一致，这是防一个授权服务器冒充另一个的。

4. 预测：你装了一个第三方的“日志美化”MCP 服务端，它也用公司 SSO 登录。它拿到你的令牌后去调 tickets，会怎样？

被拒，401。那张令牌是授权服务器发给“日志美化”这个资源的，audience 不是 tickets；tickets 校验受众，只认发给自己的。前提是 tickets 开了受众校验（坑 4）。

从 ④ 机制 3 和 ④ 为什么这样设计推出。

5. 预测：把访问令牌的有效期从 5 分钟改成 30 天，流程上会少什么、风险上会多什么？

少的是刷新：一个月内都不用再换令牌。多的是：令牌一旦从日志、内存转储、某个不可信的服务端那里漏出去，30 天内都能冒充你调 tickets；有人离职，停掉 SSO 账号也挡不住已经发出去的令牌。

从 ② 的对照和 ⑥ 第二圈“访问令牌要短”推出。

6. 放回全景：第 3 站前后各发生了什么？如果第 3 站的授权服务器挂了，整条链路会怎样？

前面是第 1 站 Claude Code 读到 tickets 的配置；后面是第 4 站带着令牌发 server/discover。授权服务器挂了，第一次连 tickets 拿不到令牌，tickets 对它一直是 401，它的两个工具进不了第 5、6 站的清单；手里已有未过期令牌的会话不受影响，直到令牌过期要刷新时才失败。oncall 走 stdio，完全不受影响。

从全景第 1～6 站和 ④ 机制 2 推出。
