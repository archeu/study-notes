可靠性：超时、重试、熔断、降级到备用模型

供应商一定会出事：过载回 529、连接卡住、越等越慢。精华是四件事：每个调用都有往下传的截止时间（SDK 默认要等 10 分钟）；重试只放一层（三层叠起来一次故障放大到 27 倍）；熔断：明知它坏了就别再去撞，直接走备用；降级是事先排好、评测过的菜单：主模型 → 备用模型 → 只分诊 → 转人工。

①要解决的问题：20:03，主模型开始回 529

在全景第 ⑥ 站，这一步要解决：20:03 到 20:06:20，主模型七成的请求回 529（过载）；整夜还有 3% 的请求连接卡住，5 分钟才回。这时第 ② 站还压着几十个事件，P0 要在 3 分钟内出报告。

②不用它会怎样：用默认值，或者多加几层重试

两种最常见的做法，⑤ 都按 30 倍速重演过：一是全用 SDK 默认值（超时 10 分钟、重试 2 次）；二是“为了稳”，SDK、网关、worker 每层都加重试。

  • 默认超时 10 分钟：23 个卡住的请求每个都干等 5 分钟才回，P95 被拖到 12 分钟以上；三次都失败的那一轮直接让事件转人工，3 个 P0 就这么丢了。
  • 三层重试：一个事件都没丢，可故障期间打到主模型的请求是单层的 9 倍。假供应商的故障不会因为负载变重而加重，真实的过载会：站 03 实测过，重试风暴能把刚恢复的服务再打趴下。
  • 两种做法都只有一条路：主模型坏了，就只能在它身上反复试，P0 也得和 P2 一起排在重试后面。
  • D 熔断以后不再去撞主模型，调用走备用；P2 降级成只分诊，把额度让给 P0；P0 最长 3.1～3.2 分钟出报告，超过 3 分钟还没结论的那 1～2 个，到点带着证据转给值班的人，而不是让人干等。
不懂精华时的典型误用：把“可靠性”理解成“多重试几次”。重试只救得了一两秒就过去的错；故障持续几分钟时，它让每个调用都失败得更慢，还把坏掉的服务压得更死。

③几种流派：出了错，除了重试还能做什么

手段解决什么解决不了什么代价
重试（退避 + 抖动）偶发的、一两秒就过去的错持续几分钟的故障：重试只是把失败往后推，还给坏掉的服务加压多等几秒
截止时间卡住的连接、越等越晚的任务：到点就停，把剩下的时间留给别的办法本身不让任何调用成功要定每类任务的时间预算
熔断持续故障：明知它坏了就别再去撞，失败从“等 60 秒才失败”变成“立刻知道”没有备用时，只是失败得快一点阈值要调，调不好会来回开关
备用模型主模型不可用时照样出结果两个模型一起坏（同一家供应商整体过载）要提前评测；备用的额度通常小得多
降级（功能变少）额度和时间都不够时，先保要紧的：P2 只分诊、不深查—报告变粗，要在页面上标出来
对冲请求尾延迟：一个请求慢了就再发一个，谁先回用谁故障：两个一起失败花双份钱，还吃双份额度
舱壁（隔离并发）一个慢依赖占满所有 worker依赖本身的故障池子分开，总利用率低一点

本页学四件套：截止时间 + 一层重试 + 熔断 + 降级菜单。重试只管“一两秒就过去的错”，持续几分钟的故障交给熔断和备用模型；时间和额度都不够时，按事先排好的菜单降级，最后一道是转人工。对冲和舱壁放进 ⑥ 第三圈。

④核心取舍：失败要快，退路要事先排好

先知道这些
  • 退避、抖动、retry-after：站 03 讲过一次调用失败后怎么等：429、529 和超时怎么重试。这一页不重讲。
  • 429 和 529 不是一回事：429 是“你的额度用完了”，等一等就好，归限流管（上一页）；529 是“供应商自己过载了”，和你用多少无关。
  • 熔断器：像电路里的保险丝，故障多到一定程度就“断开”，一段时间内不再把请求送过去。

机制 1 · 截止时间：每个调用都要有，而且往下传

官方 SDK 默认的超时是 10 分钟（连接 5 秒），这是为了不误杀生成很长回答的请求。对值班助手来说，一个 P0 等 10 分钟等于没等：报告早就该出了。所以超时分两级：每个事件一个截止时间（P0 3 分钟、P1 6 分钟、P2 15 分钟），每次调用的超时 = min(单次上限 60 秒, 离截止还剩多少)。剩下的时间不够跑完一轮，就别再发了，带着已经查到的证据转人工。

机制 2 · 重试只放一层

每一层都觉得“我多试两次更稳”：SDK 默认重试 2 次（一共 3 次），网关再包 3 次，worker 发现这一轮失败又重跑 3 次。一次调用最多变成 3 × 3 × 3 = 27 个请求，而且全打在那个已经过载的模型上。规矩是只在一层重试，选知道最多的那一层：网关知道熔断器的状态、额度桶的余额、事件的截止时间，所以重试放在网关；网关里的 SDK 设 max_retries=0，worker 不重跑这一轮。

三层叠起来27 倍一次调用最多 27 个请求
只在网关重试3 倍而且熔断打开后就不再试主模型
重试只管几秒的抖动；几分钟的故障交给熔断
429 和 529分开429 等 retry-after，529 算熔断

机制 3 · 熔断器：关、开、半开

熔断器给主模型记一个滑动窗口：最近 20 次调用里，至少有 10 次、失败过半，就打开；打开的 30 秒里一律不放行，调用直接走备用模型；30 秒到了进半开，只放 3 个试探请求去主模型，全成功才关上，有一个失败就再打开 30 秒。下面是 ⑤ 实测里熔断器真实的一生。

两个细节决定它好不好用。第一，什么算失败：只算“供应商那边坏了”，即 529、5xx、超时、连不上。429 是自己额度的问题，算进来的话，自己的限流就能把熔断器打开，白白切到备用；400 是请求写错了，换谁都一样错。第二，窗口不能太小：最近 3 次里 2 次超时就打开，熔断器会在偶发抖动下来回开关。Resilience4j 的默认值偏保守：窗口 100 次、至少 100 次才判断、打开 60 秒、半开放 10 个试探；值班助手一分钟只调七十来次，照搬默认值，故障开始一分多钟以后它才会动。

机制 4 · 降级是一张事先排好的菜单

熔断器只负责“别去撞”，撞不了以后去哪，要事先排好。值班助手的菜单从上往下：

  1. 1 主模型正常情况，6 轮深查。
  2. 2 备用模型熔断打开时。有自己的令牌桶，额度只有主模型的三分之一多一点，所以同时只够跑 4 个左右的调查。
  3. 3 只分诊备用也挤不下、或者事件优先级低时：P2 只跑一轮，给出“像什么问题、该找谁”，页面上标明“降级报告”。
  4. 4 转人工截止时间到了还没结论：把已经查到的证据（第几轮、调了哪些工具、结果是什么）推给值班的人。

备用模型不是随便找一个。同一家的另一个型号接入最省事，但供应商整体过载时可能一起不可用（文档说 529 可能出现在“所有用户流量都高”的时候）；另一家供应商更独立，代价是接口、提示词、工具调用格式都要再适配一遍；本地小模型最独立，质量最低。不管选哪个，都要先过一遍评测（站 09 的 换模型怎么回归），知道降级以后报告会差多少。

为什么这样设计

截止时间 + 一层重试 + 熔断 + 降级菜单

  • 失败要快：熔断打开后，调用不再等 60 秒超时或几次退避才失败，立刻走备用。
  • 不给坏掉的服务添乱：⑤ 里故障期打到主模型的请求从 229 个降到 24 个。
  • 时间花在有用的地方：截止时间到了就转人工，不在一个注定失败的调用上耗光 P0 的预算。
  • 代价：多一个要调的状态机、一个要评测的备用模型、一张要维护的降级菜单。

每一层多加几次重试

  • 故障持续几分钟时，重试只是把失败往后推；每一次重试都在吃截止时间和额度。
  • 三层叠起来放大到 27 倍，全打在已经过载的服务上；供应商恢复的那一刻，又被积攒的重试压回去。
  • 好处是代码最简单，偶发错误也确实能救回来。
决定胜负的约束：一次模型调用要几秒到几十秒，而故障往往持续几分钟。在这个时间尺度上，“再试一次”很贵、也很少成功；手里有一个评测过的备用模型时，换路比等待划算得多。

不像：Java 里的 fallback 多半返回缓存或默认值，结果是确定的；这里的 fallback 是另一个模型，给出的答案不一样，要先评测；而且备用模型有自己的额度，熔断一开，全部流量挤过去，它也会被打满。

⑤套进场景：把 20:03 那次故障重演 4 遍

假供应商有两个模型：main 在 20:03～20:06:20 有 70% 的请求回 529，全程 3% 的请求卡住 5 分钟；backup 不出故障，但额度只有 15 万/分钟、生成也慢一点。调用方用官方 anthropic SDK。87 个事件按全景的节奏到达，16 个 worker，每个调查 6 轮。时间压缩 30 倍（场景 1 分钟 = 墙上 2 秒）。

class CircuitBreaker:
    def __init__(self, window=20, min_calls=10, threshold=0.5, open_sec=30.0, probes=3): ...

    def allow(self) -> bool:
        if self.state == "OPEN" and now() - self.opened_at >= self.open_sec:
            self._to("HALF_OPEN"); self.probe_sent = self.probe_ok = 0
        if self.state == "CLOSED":
            return True
        if self.state == "HALF_OPEN" and self.probe_sent < self.probes:
            self.probe_sent += 1                    # 只放几个试探
            return True
        return False                                # 调用方改走备用

    def record(self, ok: bool) -> None:
        if self.state == "HALF_OPEN":               # 试探：一个失败就再打开，全成功才关上
            ...
        self.calls.append(ok)                       # 最近 20 次
        fails = self.calls.count(False)
        if len(self.calls) >= self.min_calls and fails / len(self.calls) >= self.threshold:
            self._to("OPEN"); self.opened_at = now()

⑥反例和误用

第一圈 · 注意事项

1用 SDK 默认的 10 分钟超时实测← ④ 机制 1
现象
大部分调查正常，少数几个一卡就是好几分钟；⑤ 里 A 的 P95 被拖到 12.2～12.7 分钟。
根源
默认超时是给“可能生成很长回答”的通用场景定的，不知道你的 P0 只有 3 分钟。
做法
每个事件一个截止时间，每次调用 timeout = min(60, 剩余时间)，用 client.with_options(timeout=…) 传下去。
2每一层都加重试实测← ④ 机制 2
现象
故障期间打到主模型的请求是单层的好几倍（⑤ 里 B 是 224～229 个，C 是 24 个）；供应商恢复后又被一波积攒的重试打回去。
根源
3 × 3 × 3 = 27，每一层都看不见别的层也在重试。
做法
只在网关重试；网关里的 SDK 设 max_retries=0，worker 不重跑整轮。
3429 也算进熔断← ④ 机制 3
现象
主模型明明好好的，熔断器却在流量高峰打开，调用全切到了又小又慢的备用模型。
根源
429 是自己的额度用满了，不是供应商坏了；把它算成失败，自己的限流就能把熔断器打开。
做法
熔断只数 529、5xx、超时、连接错误；429 照 retry-after 等，交给限流那一层。
4窗口太小，熔断器来回开关← ④ 机制 3
现象
看板上熔断器一会儿开一会儿关，报告一会儿来自主模型、一会儿来自备用。
根源
最近 3 次里 2 次超时就打开，偶发抖动也够条件。
做法
窗口和最少调用数按调用量定（一分钟七十来次，窗口 20、至少 10 次）；超时比例单独设阈值（慢调用比例）。
5备用模型没评测过← ④ 机制 4
现象
熔断打开的那 3 分钟，报告“看起来正常”，第二天复盘才发现结论错了一大半。
根源
降级换的是另一个模型，答案不一样；提示词是为主模型调的。
做法
备用模型也进评测集，评测分数写进降级菜单；降级报告在页面上标出来（站 09 的 换模型怎么回归）。
6备用模型没有自己的桶← ④ 机制 4
现象
熔断一开，16 个 worker 全部涌向备用模型，备用模型立刻 429，降级也降不下去。
根源
额度按模型给，备用的额度通常小得多：全景里只够每分钟 4～5 个调查。
做法
备用模型单独一个令牌桶；挤不下的按菜单继续往下降：P2 只分诊，再不行转人工。
7截止时间不往下传← ④ 机制 1
现象
值班的人已经点了“转人工”、事件早就超时，后台还在为它一轮一轮地调模型、花 token。
根源
每一层只知道自己的超时，不知道上游已经放弃了。
做法
截止时间跟着任务走（写进任务和检查点），每一层调用前先看还剩多少；取消也走同一条路。
8半开时一下子全放← ④ 机制 3
现象
熔断器一进半开，几十个排队的调用一起涌向刚恢复的主模型，它又倒了。
根源
半开的意思是“试探”，放多少要有上限。
做法
半开只放几个试探（⑤ 用 3 个），关上以后再借限流慢慢放量（上一页坑 7：ramp limit）。

第二圈 · 使用规范

  • 每个事件都有截止时间，按优先级定：防一个卡住的连接吃光 P0 的预算。
  • 重试只在网关一层，SDK 设 0，最多 2～3 次：防 27 倍放大。
  • 熔断按模型分，只数供应商的错：防自己的限流把它打开。
  • 降级菜单写进配置并评测过：防临时拍脑袋换模型。
  • 降级报告在页面上打标：防值班的人把粗报告当深查报告用。
  • 熔断状态、降级次数、转人工次数进看板并告警：防故障期间悄悄降级，没人知道。

第三圈 · 优化和深处

对冲请求：用钱换尾延迟

一个调用超过 P95 还没回，就向另一个模型（或同一个模型）再发一份，谁先回用谁，另一个取消。它治的是“偶尔慢”，不治故障；代价是双份的钱和额度，所以只给 P0 开，而且要从额度桶里扣。

舱壁：按优先级分 worker

16 个 worker 共用时，一个慢依赖能把它们全占住。给 P0 留 4 个专用 worker，其余共用：哪怕 P2 全卡在备用模型上，P0 也有人做。Resilience4j 的 Bulkhead 就是这个意思。

熔断器按“模型 × 地域”分

供应商的故障常常只影响一个模型或一个地域。一个模型一个熔断器，比“整个供应商一个开关”切得更细：主模型坏了，同一家的备用型号可能还好。

最便宜的降级：已有的答案

同一个服务、同一种告警，知识库里有一周前的排查结论。模型全挂时，先把它和“这次的原始指标”一起推给值班的人，比一句“服务不可用”有用得多。

↺回到⑤：改一改

  1. 把 429 也算进熔断：把主模型的令牌桶从 36 万调到 50 万（超过供应商的 40 万），再让 provider_down() 把 429 也算失败。做对了会看到：没有故障的 20:00～20:03 熔断器也会打开。（坑 3）
  2. 窗口改小：CircuitBreaker(window=3, min_calls=2)，把 HANG_RATE 调到 0.1，看熔断器在故障之外开关了几次。（坑 4）
  3. 备用模型不设桶：去掉 backup 的令牌桶，看熔断打开的 3 分钟里备用模型吃了多少 429。（坑 6）

自测

1. 用一句话说出这一页的精华

每个调用都有往下传的截止时间；重试只放一层、只管几秒的抖动；持续故障交给熔断，打开了就走评测过的备用模型；再不行按菜单降级，最后转人工。

2. 为什么“多重试几次”在这里是坏主意？

故障持续几分钟，重试只是把失败往后推，每次都在吃截止时间和额度；三层叠起来放大 27 倍，全压在已经过载的服务上，恢复时还会被积攒的重试再压回去。

3. 熔断器为什么不能把 429 算成失败？

429 说的是“你的额度用完了”，主模型本身是好的；算进去的话，流量一高自己的限流就把熔断器打开，调用被白白切到小得多的备用模型。

从 ④ 机制 3 推出。

4. 预测：把熔断器的打开时长从 30 秒改成 5 分钟，⑤ 里 C 会怎样？

20:03 打开后要到 20:08 才第一次试探，而故障 20:06:20 就结束了：多用了将近 2 分钟的备用模型，备用每分钟只能做 4 个左右，积压和 P95 都会变差。打开时长短一点、试探少一点，恢复得快又不添乱。

从 ④ 机制 3、4 推出。

5. 预测：主模型和备用模型是同一家供应商，这次是整个供应商过载，C 会怎样？

两个模型一起回 529，熔断器打开后走备用也失败，备用也该有自己的熔断器；菜单要继续往下走：P2 只分诊也调不了，就按知识库里已有的结论和原始指标转人工。“备用”要尽量和主模型不共享故障。

从 ④ 机制 4 推出。

6. 放回全景：第 ⑥ 站前后是什么？如果第 ⑥ 站没有熔断、只有三层重试，20:03 那次故障时整条链路会怎样？

前面是第 ⑤ 站网关选好模型，后面是第 ⑦ 站供应商。三层重试时，故障期间打到主模型的请求是单层熔断的好几倍，worker 全卡在等重试上，第 ② 站的积压越堆越高；P0 也要排到重试后面；故障一结束，积攒的重试又一起涌向第 ⑦ 站。看板上 529 和请求数一起飙高，P95 拉长。

从全景第 ②⑥⑦ 站和 ④ 机制 2、3 推出。

档位：标准。本机跑过（2026-11-28，2 核 ARM，Python 3.13.18，anthropic 2.12.0，FastAPI 0.165.0）：⑤ 的 4 种做法各三遍；假供应商的故障是按全景设定注入的，不随负载加重，数字只用来比较几种做法。看过源码：anthropic SDK 2.12.0 的 _constants.py（默认超时 10 分钟、连接 5 秒、默认重试 2 次）和 _exceptions.py（529 是 OverloadedError，继承 InternalServerError）；Resilience4j master 的 CircuitBreakerConfig.java（失败率 50%、窗口 100、至少 100 次、打开 60 秒、半开 10 个试探、慢调用 60 秒、默认按次数计）。按文档：Claude API errors 页（529 overloaded_error，可能出现在所有用户流量都高的时候），2026-11-28 查。
