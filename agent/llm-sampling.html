采样：temperature 和 top_p 改的是什么

模型每一圈只给出一张概率表，采样决定从表里挑谁。temperature 把表压尖或摊平：0 永远挑第一名，越高，小概率的越有机会；top_p 先把长尾砍掉，只在头部挑。实测温度 1 问 10 次出了 7 种回答。而温度 0 也不保证每次一样：4 个请求同时发，有 3 个写出了不同的句子。

全景：一句话怎么变成模型的回答 · 第 7 站地图：站 02 · 采样：temperature 和 top_p 改的是什么深度：懂机制

这一页的位置站 02 第 4 个知识点。下一个词预测讲了“算出概率表”，这一页讲“从表里挑”。地图上第一条过关题“温度设成 0，为什么也不保证每次一样”，答案在 ④ 机制 4 和 ⑤ 第三个实验。

①为什么需要：概率表有了，到底写哪个字

在全景第 7 站，这一步要解决：第 6 站给了 151936 个候选各自的概率，“是”0.707、“不是”0.205、“否”0.018……这一圈只能写一个，写谁？挑法不同，值班助手的回答就会不同，而且每次问都可能不同。

②没有它会怎样：两种最朴素的挑法

要求永远挑第一名（贪心）完全按原概率抽
同一个问题答得稳能：单独发时 10 次一字不差（⑤ 实测）不能：每次都可能不同
不陷进重复不能：一旦写进套路就出不来，第 1 页强制开头后反复写“时间差：……”直到截断能：随机性会把它带出循环
不冒出离谱的词能：冷门词永远轮不到不能：15 万个候选，每个都有一点点概率，写几百圈总会抽中几个怪的
写东西有变化（起名字、写文案）不能能

两头都有硬伤，于是有了中间的旋钮：temperature 决定“多敢抽冷门”，top_p 决定“冷门冷到什么程度就直接不要”。

不懂精华时的典型误用：以为“温度 0 = 确定性”，把模型输出当缓存键、或者在测试里断言输出逐字相等；再反过来以为“温度高 = 更聪明”，在判断类任务上调高温度，换来的是更多编造。

③相邻方案：几种挑法

挑法做什么弱点
贪心（温度 0）永远取第一名呆板，容易重复；而且照样不保证逐字一样（机制 4）
temperature按 p1/T 调整形状再抽只改形状，不砍尾巴：温度高时冷门词一起被抬高
top_k只留前 k 名k 是死的：分布很尖时留了 39 个废候选，很平时 40 个又可能不够
top_p（nucleus）只留累计概率到 p 的头部按形状自适应：尖时只留一两个，平时多留几个
min_p只留概率不低于“第一名 × min_p”的较新，开源推理框架常用，商用 API 少见

本页学 temperature 和 top_p：OpenAI 兼容接口、本地推理服务里最常见的就是这两个旋钮。Claude 新一代模型则把它们收走了（⑥ 坑 4）。

④原理：调形状、砍尾巴、抽签，以及温度 0 为什么还会变

先知道这些
  • 概率表：第 6 站给每个候选打分（logit），softmax 换成加起来是 1 的概率（下一个词预测 ④）。
  • 浮点数加法不满足结合律：(a+b)+c 和 a+(b+c) 在 float 上可能差最后一位。Java 里 0.1+0.2+0.3 和 0.1+(0.2+0.3) 就不相等。

机制 1 · temperature：把每个概率开 1/T 次方，再归一化

做法是把打分除以 T 再做 softmax，等价于把每个概率开 1/T 次方、再除以总和。T 小于 1，大的更大、小的更小；T 大于 1，差距被拉平；T 趋近 0，第一名的概率趋近 1，就是贪心。用 ⑤ 实测的第一个 token 算一下（只取前 20 名重新归一化）：

机制 2 · top_p：按概率从高到低累加，够 p 就截断

机制 3 · 抽签：累积概率 + 一个随机数

剩下的候选排成一段 0 到 1 的线段，各占自己概率那么长，掷一个 [0,1) 的随机数，落在谁那一段就是谁。Java 里就是 ThreadLocalRandom.current().nextDouble() 加一个累加循环。seed 固定的是这个随机数序列：seed 一样、概率表一样，抽出来就一样。

机制 4 · 温度 0 为什么也会变：概率表本身在晃

为什么这样设计：为什么要随机，为什么用 top_p 而不是 top_k

温度 + 头部截断

  • 有随机性，能跳出重复，写出来的话更像人写的（Holtzman 等人 2019 年提出 top_p 时的论文，标题就叫“神经网络文本的退化”，讲的正是贪心和纯随机各自的毛病）。
  • top_p 按分布形状自适应：该确定的地方只留一个，该犹豫的地方留几个，冷门长尾一律不碰。
  • 代价：输出不可复现，需要稳定时要另想办法（⑥）。

只用贪心，或只用 top_k

  • 只用贪心：结果稳，但呆板、易陷循环，而且服务端批处理下照样不能逐字复现，稳也稳得不彻底。
  • 只用 top_k：k 是固定的，在“20:15”这种几乎确定的位置也留了 k 个候选，温度一高就可能抽出错的数字。
决定胜负的约束：每一圈的不确定程度差别极大，数字和语法几乎是定的，措辞和判断才有悬念。能按形状自适应的截断（top_p），配一个控制胆量的温度，比任何固定的规则都更贴这个现实。

Claude 新一代模型：收走了

按 Claude API 文档：Opus 5.5 收到 temperature 或 top_p 直接返回 400；API 版本 2026-10-21 起，所有模型都不再接受 temperature、top_p、top_k。要让输出稳，靠提示词、结构化输出和校验（站 03）。

⑤亲眼看到：温度 0 和 1 各跑 10 次，再同时发 4 个

这是站 02 地图上的第二个小实验。同一个问题（3 行 GC 日志 + “是不是 GC 导致的，说出依据”），连本机 llama-server。为了只看温度一个变量，把 llama.cpp 默认开着的 top_k=40、top_p=0.95、min_p=0.05 全部关掉。

  1. 1 看概率表python main.py probs：第一个 token 的前 20 名。
  2. 2 各跑 10 次python main.py runs：温度 0 和温度 1，seed 从 0 到 9，数有几种不同的回答。
  3. 3 同时发python main.py batch：温度 0、不走缓存，先一个一个发两次，再 4 个线程同时发（服务端开了 4 个并发槽，会拼成一批算）。
⑤main.py（核心）完整代码 →
def gen(temperature, seed, cache=True, n=48):
    r = post("/completion", {"prompt": PROMPT, "n_predict": n,
                             "temperature": temperature, "seed": seed,
                             "top_k": 0, "top_p": 1.0, "min_p": 0.0,   # 关掉默认的截断
                             "cache_prompt": cache})
    return r["content"].strip()

with ThreadPoolExecutor(4) as ex:                                  # 4 个同时发
    together = list(ex.map(lambda i: gen(0.0, i, cache=False), range(4)))

读出来的结论
  • 温度 1 的开头分布（“是”6、“不是”2、“不”1、“Y”1）大体对得上概率表（“是”0.707、“不是”0.205）：采样就是照着表抽签。
  • 温度 1 冒出了“GC 渲染”“8:15”“不可以”这样的怪话：长尾里的候选被抽中一次，后面就顺着它往下写。
  • 温度 0 一个一个发，10 次加 2 次全都一字不差；4 个同时发，3 个在“慢 / 多”那一圈翻了，后半句完全不同。没有改任何参数，只是服务端把请求拼成了一批。
  • 温度 0 那句回答本身是错的（日志里根本没有 20:14、20:15 的记录）：稳定不等于正确，采样只管“挑”，不管“对”。

⑥细节：采样参数的几个坑

第一圈 · 注意事项

1指望温度 0 逐字复现实测← ④ 机制 4
现象
本地调试时每次一样，上线后同样的输入偶尔给出不同的句子；用输出做缓存键的命中率很低；断言“输出等于某个字符串”的测试时好时坏。
根源
温度 0 只保证每圈取当时的第一名；概率表本身会随批处理、缓存状态有千分之几的晃动，两名并列时就会翻。seed 只固定随机数，管不了这个。
做法
要稳定的地方用结构化输出 + 校验（站 03），断言比较“字段和含义”而不是整段文字；缓存键用输入，不用输出。
2温度调高“更聪明”，结果编得更多实测← ④ 机制 1
现象
温度 1 时冒出“GC 渲染”“8:15”这种日志里没有的东西。
根源
温度只放大模型已有的“次要想法”，不会增加知识；长尾候选被抽中一次，后面就顺着它写下去（开头一错一路错）。
做法
判断、分类、抽取：能调的模型用低温（0～0.3）。需要多样性（起名、写文案、出几个备选方案）才调高，并配上 top_p 砍尾巴。
3不传参数就以为是“确定的”实测← ④ 机制 2
现象
本地起的模型服务，同一个问题每次答得不一样。
根源
llama-server 不传参数时默认温度 0.8，还开着 top_k=40、top_p=0.95、min_p=0.05（读自它的 /props）；各家默认值和先后顺序都不一样。
做法
采样参数在调用层显式写全，不依赖服务端默认值；换推理框架时对一遍默认值。
4往 Claude 新模型传 temperature，直接 400← 产品决定
现象
从别家模型迁到 Claude Opus 5.5，原来带着的 temperature: 0 让每个请求都失败。
根源
不是机制推出来的，是产品决定：按 Claude API 文档，Opus 5.5 不接受 temperature 和 top_p，API 版本 2026-10-21 起所有模型都不接受这三个采样参数。文档没有展开原因。
做法
在模型抽象层里按模型能力过滤参数（站 03 “换模型只改一层”）；稳定性靠提示词、结构化输出和 effort。

第二圈 · 使用规范

  • 按任务定温度：判断和抽取低温，创作高温，写进配置而不是散在代码里。防坑 2、坑 3。
  • 代码里不假设确定性：任何依赖“同输入同输出”的逻辑（缓存、去重、测试断言）都要改成比较结构化字段。防坑 1。
  • 只调一个旋钮：temperature 和 top_p 一般只调其中一个，另一个保持默认；两个一起调，效果难以预测。
  • 参数按模型能力过滤：调用层维护“哪个模型接受哪些参数”的表。防坑 4。

第三圈 · 采样的进阶用法

多次采样再投票

同一个问题用较高温度问 5 次，取出现最多的结论（自洽性投票）。⑤ 里温度 1 的 10 次，“是”占 6 次。代价是 5 倍的钱，适合关键判断。

约束解码

采样前先把“不合语法”的候选概率置零：比如只允许输出合法的 JSON，或只允许“是 / 否”。llama.cpp 的语法约束、各家的结构化输出都是这一路（站 03 结构化输出）。

要真正的逐位确定

得让服务端的计算和批的形状无关（批不变的算子），代价是吞吐下降。少数推理框架提供这种模式；商用 API 一般不承诺。

推理模型和温度

会“先思考”的模型，思考那一段同样是采样出来的，每次思路都可能不同。Claude 用 effort 调思考深浅，而不是让你调温度（推理模型那一页）。

自测

1. 用一句话说出这一页的精华

temperature 调概率表的形状、top_p 砍掉长尾、最后按概率抽签；温度 0 只是每圈取第一名，概率表本身会随服务端批处理晃动，所以也不保证每次一样。

2. 温度 0，为什么也不保证每次一样？

服务端把多个请求拼成一批算，矩阵运算的累加顺序随批的形状变，浮点加法不满足结合律，概率末几位跟着变；遇到两名几乎并列的圈，第一名就换人，之后整句不同。seed 管不了这个。

从 ④ 机制 4 推出，⑤ 第三个实验实测

3. 为什么 top_p 比 top_k 更合理？

每一圈的不确定程度差别很大：数字位置几乎是定的，措辞位置才有悬念。top_p 按累计概率截断，确定时只留一个、犹豫时留几个；top_k 固定留 k 个，确定的地方也塞进一堆废候选。

从 ④ 为什么这样设计 推出

4. 预测：温度 0.3、top_p 1，“不是”开头的概率大约是多少？比温度 1 时高还是低？

低得多：概率开 1/0.3 ≈ 3.3 次方，0.707 和 0.205 的差距从 3.4 倍拉大到约 60 倍，“不是”只剩约 1.6%（实验台可以验证）。

从 ④ 机制 1 推出

5. 预测：把温度调到 2，模型会说出它“不知道”的事吗？

不会多出知识。温度不改排名，只把模型原本就有的冷门候选抬高；抽中冷门候选后，它会顺着往下写，看起来像“新想法”，其实大多是编造（⑤ 温度 1 已经出现了“GC 渲染”）。

从 ④ 机制 1 和第 1 页“开头一错一路错”推出

6. 放回全景：第 7 站前后各发生了什么？如果第 7 站坏了，变成每次都从全部 15 万个候选里平均随机挑一个，整条链路会怎样？

第 7 站之前是第 6 站算出概率表，之后是第 8 站把挑中的接上再来一圈。平均随机挑就完全扔掉了模型的判断：每圈都是随机字符，写出的是乱码；结束符被抽中的机会只有十五万分之一，几乎每次都写满 max_tokens 才停，按满额计费，stop_reason 是 max_tokens。
