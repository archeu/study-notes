换模型只改一层：模型抽象层

业务代码只说“我要做哪一类事”（分诊、诊断、写报告），用哪家、哪个模型、什么参数、挂了换谁都写在配置里，由一层很薄的代码翻译成各家接口。模型几个月一换代、价格常调、某家服务会出故障，有了这一层，换模型就是改配置。实测同一行 layer.complete("triage", …)，三份配置分别跑在 Claude 格式、OpenAI 兼容格式和“主服务挂了自动切备用”上。代价是：各家独有的好功能（缓存、思考、引用）不能被抹平，抽象层要给它们留口子。

①要解决的问题：模型变得比业务快

在全景第 2 站，这一步要解决：分诊这类调用今天用 Sonnet 5.5，下个月可能换成新出的模型、换成国内服务、或者在 Claude 过载时临时切到备用。值班助手里有十几处调用模型的地方，不能每次都改十几处代码。

②不用它会怎样：模型名和 SDK 写死在业务里

要求业务代码直接调 SDK经过抽象层
换模型十几处 model="claude-…" 逐个改，漏一处就混着用改配置里一行
换一家服务请求格式、响应格式、错误类型全不一样，要重写换适配器，业务不动（⑤ 实测配置 B）
主服务挂了每处都要自己写降级逻辑，往往没人写按配置的备用顺序自动切（⑤ 实测配置 C）
模型的参数规则变了新模型不收 temperature，所有带它的调用一起 400按模型能力过滤，记日志
算钱、看延迟各处各记各的，或者不记一处统一记用量和耗时
不懂精华时的典型误用：为了“随时能换”，把抽象层做成只剩各家都支持的最小公分母：只有文字进、文字出。结果 Claude 的提示缓存、思考、引用、结构化输出全都用不上，换来的灵活性还没省下的钱多。

③几种流派：抽象到哪一层

流派做法取舍
不抽象业务直接用官方 SDK功能最全、最简单；只用一家、调用点很少时合适
自己写一层薄的按任务配置，几个适配器，统一结果和错误百来行，完全可控，能给各家特性留口子（本页）
用现成的多模型库LiteLLM（Python）这类，一个接口对上百家接得快；新特性跟进有延迟，排查要多看一层
框架自带的抽象Spring AI 的 ChatClient、LangChain 的模型接口和框架其他部分（工具、记忆、检索）一体；被框架的节奏绑定（下一页）
网关所有调用都经过一个内部 HTTP 网关多语言、多团队共用，集中限流和计费；多一跳延迟，要运维

本页学“自己写一层薄的”：它最能讲清抽象层到底在做什么；懂了它，再去用库或框架，就知道它们替你做了哪些、没做哪些。

④核心取舍：抹平什么，保留什么

先知道这些
  • 适配器模式：把不同的接口包成同一个接口，Java 里 JDBC 的 Driver、SLF4J 的日志门面都是它。
  • 两种主流格式：Claude 的 Messages（system 顶层、content 块）和 OpenAI 兼容的 Chat Completions（system 是一条消息、choices[0].message）（Messages API ③）。

取舍 1 · 按“任务”配置，而不是按“模型”调用

config_c.json⑤ 实测用的配置
{
  "providers": {
    "primary-down":   {"kind": "anthropic", "base_url": "http://127.0.0.1:8099"},
    "local-messages": {"kind": "anthropic", "base_url": "http://127.0.0.1:8090"}
  },
  "models": {
    "main":   {"provider": "primary-down",   "model": "claude-sonnet-5-5"},
    "backup": {"provider": "local-messages", "model": "qwen2.5-0.5b",
               "unsupported": ["temperature", "top_p"]}        // 能力表
  },
  "tasks": {
    "triage": {"primary": "main", "fallbacks": ["backup"],      // 任务 → 主 + 备
               "params": {"max_tokens": 60, "temperature": 0}}
  }
}

三层名字各管一件事：provider 是“连到哪、用哪种格式”，model 是“哪个模型、它不支持什么”，task 是“这类业务用谁、备用是谁、参数多少”。站 02 选模型的结论“按调用分配”，就落在 tasks 这一段。

取舍 2 · 参数按模型能力过滤，并且留痕

同一个任务的参数，换了模型可能就不合法：按 Claude 文档，Opus 5.5 收到 temperature、top_p 会 400；本机模型却认它们。抽象层按 unsupported 表把它们拿掉，并在结果里记下“丢了哪些”。静默丢弃会让人以为设置生效了，所以一定要留痕。

取舍 3 · 错误统一分类：可重试的换下一个，不可重试的直接抛

原始错误统一成抽象层的动作
连接失败、429、5xx、529ModelError(retryable=True)试备用列表里的下一个
400 参数错、401、404ModelError(retryable=False)直接抛：换谁都没用，而且多半是配置错了
所有目标都失败ModelError，带每一个的失败原因交给业务降级（规则兜底、稍后补）

重试只在一层做（出错那页的误用 1）：本页让 SDK 自己重试 1 次（处理瞬时抖动），抽象层负责“换一家”，业务层不再重试。

取舍 4 · 统一常用的，给独有的留口子

统一（所有家都有）

  • system + user 文字进，文字出。
  • 用量：统一成 input / cached / output 三个数。
  • 错误：可重试 / 不可重试。
  • 耗时、实际用了哪个模型、是不是走了备用。

留口子（各家不同）

  • Claude 的缓存断点、思考的 effort、引用、output_config.format。
  • OpenAI 兼容服务的 response_format、本地框架的 chat_template_kwargs。
  • 做法：配置里的 params 原样透传给适配器（⑤ 配置 B 就是这样关掉 Qwen3 的思考的）。

核心取舍：薄而透明，还是厚而统一

薄的一层 + 透传

  • 换模型、换家、加备用都只改配置；各家的好功能照样能用。
  • 代码少（本页约 120 行），出了问题一眼看到底。
  • 代价：透传的参数是“各家方言”，换家时要连同 params 一起改；业务不完全和厂商无关。

厚的一层，什么都抽象

  • 业务代码完全不知道底下是谁。
  • 只能用最小公分母；新特性要等抽象层跟进；抽象本身的 bug 和概念要额外学。
决定胜负的约束：各家模型的差异不只是“格式不同”，还有“能力不同”（缓存、思考、结构化输出的做法都不一样），而这些能力恰恰是省钱和提质量的关键。所以抽象层的目标不是“抹平一切”，而是“让最常变的东西（模型名、参数、备用）可配置”，同时不挡住各家的长处。

最少的语法

llm_layer.py 的主循环⑤ 原样跑过
def complete(self, task, system, user):
    t = self.cfg["tasks"][task]
    failed = []
    for target in [t["primary"], *t.get("fallbacks", [])]:      # 主 → 备
        m = self.cfg["models"][target]
        params, dropped = self._params(m, t.get("params", {}))   # 按能力过滤
        try:
            text, usage = self.providers[m["provider"]].call(m["model"], system, user, params)
        except ModelError as e:
            failed.append(target)
            if not e.retryable: raise                            # 400 之类，换谁都没用
            continue
        return Result(text, m["provider"], m["model"], usage, dropped=dropped, fallback_from=failed)
    raise ModelError("所有目标都失败了", retryable=True)

⑤套进场景：同一行业务代码，三份配置

业务代码固定是 layer.complete("triage", system=SYSTEM, user=f"<alert>{alert}</alert>")，只换配置文件。A：本机 Qwen2.5-0.5B，走 Claude 的 Messages 格式（官方 anthropic SDK）；B：本机 Qwen3-0.6B，走 OpenAI 兼容格式（标准库 HTTP），并透传 chat_template_kwargs 关掉它的思考；C：主模型的地址故意写错（模拟主服务挂了），备用模型在能力表里标了“不收 temperature”。

⑤main.py完整代码 →
for name in ("config_a.json", "config_b.json", "config_c.json"):
    layer = LLMLayer.from_file(name)
    r = layer.complete("triage", system=SYSTEM, user=f"<alert>{alert}</alert>")   # ← 业务代码只有这一行
    print(r.provider, r.model, r.ms, r.usage, r.text, r.dropped, r.fallback_from)

读出来的结论
  • 换家不改业务：A 和 B 背后是两种完全不同的请求格式（system 的位置、响应的结构、用量字段名都不同），业务代码一行没动，拿到的用量也统一成了 input / cached / output。
  • 主服务挂了自动切：C 的主模型连不上（SDK 自己先重试了 1 次），抽象层把它归为“可重试”，换到备用，结果里写明了“先失败、已跳过”的是谁。
  • 参数按能力过滤并留痕：备用模型不收 temperature，被拿掉了，结果里记着。
  • 抽象层不管质量：两个小模型的回答一个照抄了类别列表，一个把 GC 答成了数据库，一个写超了长度。抽象层让“换”变得便宜，“换成谁”仍要靠评测（站 02 选模型）。
到这里已经能交差了：你能写一层按任务配置、带适配器、能过滤参数、能切备用、统一用量和错误的抽象层，并说清它该抹平什么、该透传什么。
反例和误用：最小公分母（误用 1），静默降级（误用 2），备用模型没评测过（误用 3），缓存被切换打散（误用 4）。

⑥反例和误用

第一圈 · 常见误用

1只剩最小公分母← ④ 取舍 4
现象
抽象层只支持“文字进、文字出”，提示缓存、思考设置、结构化输出都用不上，账单比直接用 SDK 还高。
根源
把“可替换”当成了唯一目标，抹掉了各家最值钱的能力。
做法
统一最常变的（模型名、参数、备用、用量、错误），各家特性通过 params 或专门的可选字段透传。
2静默降级，没人知道切了实测← ④ 取舍 3
现象
主模型挂了三天，所有分诊都悄悄跑在备用小模型上，质量下降，没有任何报警。
根源
备用切换只在内部发生，结果里没有标记，监控也没采集。
做法
结果里带上实际用的模型和“跳过了谁”（⑤ 的 fallback_from），按它打指标；走备用的比例超过阈值就报警。
3备用模型从没在评测集上跑过← ④ 取舍 1
现象
切到备用后，结构化输出大量校验失败，比“直接报错”还糟。
根源
同一份提示词在不同模型上效果差很多（站 02 选模型那页，两个小模型偏向完全不同的类别）。
做法
每个任务的主模型和备用模型都要在评测集上跑过、达标；必要时给备用模型单独一份提示词（配置里按模型覆盖 system）。
4在几个模型之间轮流用，缓存都攒不起来← ④ 核心取舍
现象
为了“负载均衡”，把分诊请求轮流发给两个模型，缓存命中率掉到一半以下。
根源
缓存按模型隔离（省钱那页），轮流用等于每个模型只拿到一半流量。
做法
同一类任务平时固定一个主模型，备用只在故障时用；真要分流，按用户或会话粘住同一个模型。

第二圈 · 使用规范

  • 业务里不出现模型名：代码评审时，claude-、gpt- 这类字符串只允许出现在配置里。防的是写死。
  • 配置变更走发布流程：换模型是“改配置”，但影响和发版一样大；要有评测结果、灰度和回滚。
  • 统一记录：任务、实际模型、是否备用、耗时、四个用量、错误类别，一处采集（站 09 可观测）。
  • 能力表放在配置里：哪个模型不收哪些参数、支不支持结构化输出、窗口多大，换代时更新一处。

第三圈 · 更深一层

服务端的备用

按 Claude 文档，新一代模型的请求可以在服务端声明备用（fallbacks，beta），主要用于安全分类拒答时自动换模型。它和抽象层的“故障切换”目的不同，可以叠加，但要清楚哪一层在换。

“兼容接口”不等于“行为一致”

本机 llama-server 同时实现了 Claude 和 OpenAI 两种格式，但 ⑤ 前几页也看到：它的 /v1/messages 不认 output_config.format。“格式兼容”只保证请求不报错，功能是否生效要逐项验证。

↺回到⑤：改一改

  1. 不可重试的错误：在适配器里加一个测试开关：模型名是 bad-model 时直接 raise ModelError("400", retryable=False)；把配置 C 的主模型改成它，确认抽象层直接抛错、不去试备用。（取舍 3）
  2. 按模型覆盖提示词：给配置加 models.backup.system，抽象层在用这个模型时用它的 system；为 Qwen3 写一份更短的提示词。（误用 3）
  3. 记指标：每次 complete 往一个列表里追加（任务、模型、是否备用、毫秒、用量），跑 10 次后打印“走备用的比例”。（误用 2）

自测

1. 用一句话说出这一页的精华

业务按任务调用，模型、参数、备用写在配置里，由薄薄一层适配器翻译成各家格式、过滤参数、统一用量和错误、失败切备用；统一最常变的，透传各家独有的能力。

2. 为什么抽象层要按“任务”而不是按“模型”配置？

业务关心的是“分诊”“诊断”这类事，用哪个模型是会变的实现细节；按任务配置，换模型、加备用、调参数都不用碰业务代码。

从 ④ 取舍 1 推出

3. 为什么 400 不该触发切备用？

400 说明请求本身不对（多半是配置或参数错），换一个模型照样错，而且会掩盖真正的问题。

从 ④ 取舍 3 推出

4. 预测：把分诊的主模型从 Sonnet 5.5 改成 Opus 5.5，配置里 params 带着 temperature: 0，没有能力表，会怎样？

按 Claude 文档，Opus 5.5 收到 temperature 会 400；没有能力表就不会过滤，所有分诊请求立刻失败，而且 400 不会触发备用。所以能力表要随模型一起维护，换模型前要跑一遍评测和冒烟测试。

从 ④ 取舍 2、3 推出

5. 预测：用了一个支持上百家模型的通用库，Claude 的提示缓存还能省钱吗？

要看这个库是否把 cache_control 透传过去。不透传，缓存就不生效，每次全价（甚至没开）；用之前要看 usage 里的缓存字段来验证。

从 ④ 取舍 4 和误用 1 推出

6. 放回全景：第 2 站前后是什么？如果第 2 站的配置把分诊指向了一个窗口只有 8192 的本机小模型，链路会怎样？

之前是第 1 站组装提示词，之后是第 3 站 SDK 拼请求。指向小模型后：带 61 行日志的请求在第 5、6 站可能直接超窗口报 400（不可重试，不会切备用）；装得下的，第 9 站的类别正确率也会明显下降（站 02 选模型实测）。换模型是一行配置，后果却贯穿整条链路，所以要评测和灰度。

档位：标准。本机跑过（2026-11-22，2 核 ARM，官方 anthropic SDK 2.12.0 与 Python 标准库，llama.cpp b12618 上的 Qwen2.5-0.5B 和 Qwen3-0.6B）：三份配置下同一行业务代码的结果、用量、耗时、参数过滤和备用切换。按文档（Claude API，2026-11）：Opus 5.5 不收采样参数、服务端 fallbacks（beta）。按项目说明：LiteLLM 是多模型统一接口的 Python 库（没有在本机试用）。
