上下文工程：放什么、放哪、放多少

模型每一轮只看得见这一次请求里的东西，而且每一轮都要从头读一遍。所以上下文是一张按 token 计价、越堆越不好用的桌子：只放下一步决策要用的（放什么），不变的在前、会变的在后（放哪），每一块都有预算（放多少）。

①要解决的问题→ ②不用它会怎样→ ③几种流派→ ④核心取舍→ ⑤套进场景→ ⑥反例和误用→ ↺回到⑤

全景：第二天再问同一个服务 · 第 3、4、7 站地图：站 05 · 上下文工程：放什么、放哪、放多少深度：懂设计

这一页的位置站 05 的第 1 个知识点。站 02 讲过窗口有多大、装满会怎样，站 03 讲过提示词缓存；这一页把它们合起来，回答“一次请求该怎么拼”。下一页讲桌子快满时怎么腾地方。

①要解决的问题：新会话的第一次请求怎么拼

在全景第 3 站，这一步要解决：新会话里要把系统提示、5 份工具说明、3 条记忆、你的问题拼成一次请求。放哪些、按什么顺序、各给多少 token？到了第 4 站，工具结果一轮轮堆上来，同样的问题每一轮都要再答一次。

这件事有个名字：上下文工程（context engineering）。提示词工程管“系统提示这段话怎么写”，上下文工程管的是更大的问题：每一次调用模型时，整个窗口里应该装着什么。Agent 跑很多轮，每轮都要重新回答一次，所以它是一个循环里的持续决策，不是写一次就完的文案。

②不用它会怎样：能塞就塞

最省事的做法：窗口很大，那就把手头有的全放进去。昨晚的整段会话、记忆表里交易组的 41 条、工具返回的原文，都塞给模型，让它自己挑。

塞进去的大约多少 token这次真正用得上的
昨晚整段会话（5 轮）2,387（站 04 最后一轮请求，实测）只有结论那一句：导出读 41 万行进内存
交易组全部 41 条记忆约 2,800（每条约 70，估算）3 条
一次 parse_gc_log 的原文，3000 行107,998（实测）几个数字：Full GC 几次、最长多久、回收后还剩多少
按本页拼法：系统提示 + 工具说明 + 3 条记忆 + 问题1,248（实测）都用得上
  • 钱和时间都乘以轮数：Agent 循环跑 5 轮，第 1 轮塞进去的每个 token 要被读 5 次、付 5 次钱。本机读 1,248 token 要 15 秒，读 10 万 token 就是二十分钟量级。
  • 越长越抓不住重点：Anthropic 把这叫 context rot，token 越多，模型从中准确找回某条信息的能力越差。41 条记忆里真正相关的 3 条，被另外 38 条稀释。
  • 新旧混在一起分不清：昨晚“修复待发布”和今天“10:00 已发布”同时在桌上，没有日期，模型不知道信哪个（全景第 7 站）。
  • 一次大工具结果就把窗口撑爆：10 万 token 的 GC 日志，在 32K 预算下根本放不进去，在 100 万的窗口里也会让后面每一轮都变贵。
  • 好处只有一个：实现最简单，第 1 轮什么都有。
不懂精华时的典型误用：以为上下文工程就是“把提示词写好”。系统提示改得再漂亮，每次请求把当前时间写在最前面、工具结果原样塞回，账单和速度照样崩，答案还会引用过时的病历。

③几种流派：东西什么时候进桌子

“放什么”有四种常见答法，差别在于谁来决定、什么时候放进来。拿全景第 3、4 站的五样东西逐条对照：

要求全塞滑动窗口预取（代码先查好再放）按需取（给工具，模型自己查）
第 1 轮就有关键线索能：什么都在不能：新会话窗口是空的能：M1、M2 一开始就在差一点：要先猜到该查记忆，多一轮
每轮 token 少不能：几万 token，每轮重发能：只留最近 N 轮能：只放前 3 条能：只放查过的
不会漏掉要紧的能（但会被淹没）不能：早期的规矩会被挤出去差一点：取错了就漏能：漏了可以再查
适合大、变得快的东西（日志）不能不能不能：不知道要哪段能：带关键字、时间段去查
实现和轮数最简单，1 轮简单要写检索，0 轮额外开销轮数多，每轮都要模型决定

本页用“预取一点 + 按需取其余”：几乎每次都要用、又很小的（规矩、最相关的 3 条记忆）在第 1 轮就放进来；大的、变得快的（日志、GC、线程栈）只给工具和线索，让模型带着条件去查。规则一句话：放进来的成本 × 每轮重发的次数，比不上“没有它要多跑的轮数”时，才预取。

Anthropic 在《Effective context engineering for AI agents》（2025-09）里把后一种叫 just-in-time：Claude Code 不把整个代码库塞进上下文，只拿文件路径这类轻量线索，需要时用 grep、glob 去读。值班助手的日志工具是同一个思路。

④核心取舍：一张按 token 计价、每轮重读的桌子

先知道这些
  • token 和窗口：模型按 token 读写、按 token 收钱，一次请求最多装窗口那么多。见 上下文窗口、token 与计费。
  • 每轮整段重发：Messages API 是无状态的，第 5 轮请求里带着前 4 轮的全部内容。见 Messages API。
  • 前缀缓存：服务端把算过的前缀留一会儿，下次一字不差的前缀不用重算。原理见 注意力与 KV 缓存，用法见 提示词缓存。

Java 老朋友：上下文窗口 ≈ 堆内存上限。像的地方：装满了要出事，所以要给各块分配大小，像给新生代、老年代定比例。不像的地方：堆满了会报 OOM，窗口快满时不报错，模型只是悄悄抓不住重点；而且堆里的对象只分配一次，上下文里的每个 token 每一轮都要重新“分配”一次、重新付一次钱。

机制 1 · 放什么：每一块都要回答“下一步决策要用它吗”

块回答模型什么问题值班助手里是多久变一次
指令我是谁、规矩是什么、怎么答系统提示发版才变
能力我能做什么5 份工具说明发版才变
知识以前发生过什么、资料怎么说3 条记忆（站 06 还会有知识库片段）每个会话不同
状态到现在为止查到了什么对话和工具结果每一轮都变
任务这次要什么你的问题每次不同

Anthropic 的说法是：找最小的一组高信号 token。每多放一样东西，都要说得出它会改变模型的哪个决定；说不出来的就不放，或者换成一条线索（路径、ID、关键字），等需要时再查。

机制 2 · 放哪：按变化频率排，稳定的在前，任务在最后

两个原因把顺序定死了：

  • 缓存只认前缀。模型从左往右算，每个位置的结果都依赖它前面的全部内容。所以服务端只能复用“和上次一字不差”的那段开头；开头变一个字，后面全部重算。会变的东西必须排在所有不变的东西后面。
  • 长上下文的中间最容易被忽略。研究（Liu 等，《Lost in the Middle》，2023）发现，关键信息放在开头或结尾时模型用得最好，放中间最差。所以规矩放系统提示，这次的任务放最后一条消息。

机制 3 · 放多少：先定总预算，再给每一块分额度

预算是这个服务自己定的，不是模型的上限：一次请求最多 32K，用到 75%（24K）就开始压缩（下一页）。分法像给堆分代：固定部分和记忆有上限，给回答留出位置，剩下的都给最占地方、也最该管的工具结果和对话。

系统提示 + 5 份工具说明992token，每轮都在，靠缓存省钱
3 条记忆（带日期、来源）208token，上限 1K，取前 3 条
GC 日志原样 3000 行107,998token，是整个预算的 3.4 倍
同一份日志，留头留尾 40 行1,472token，占剩余额度的 5%

实测 用 count_tokens 逐块量（Qwen3 分词器；Claude 的分词器数出来会不同，量级一样）。全景页按估算写的是“约 2.8K”，本机实测整个第 1 次请求是 1,248 token：系统提示 598 个字，比估算时设想的短。一份工具结果的上限定在 1.5K 左右：超了就让工具先汇总，或者留头留尾。

为什么这样设计

预算 + 分层 + 按需取

  • 每轮重发的部分最小，钱和延迟跟着小；稳定前缀每次命中缓存。
  • 关键规矩和任务在两头，模型最容易用上。
  • 代价：要写拼装代码、记账，要决定什么预取什么按需取。

窗口够大，能塞就塞

  • 成本 = 上下文长度 × 轮数，循环跑 5 轮，塞进去的每个 token 付 5 次钱。
  • 越长越难抓重点（Anthropic 叫它 context rot：token 越多，从中准确找回信息的能力越差）。
  • 旧的、无关的和新的混在一起，模型分不清该信哪个。
决定胜负的约束：模型无状态，每一轮都要把整张桌子从头读一遍，而注意力是有限的。窗口从 8K 涨到 100 万，“装不下”的问题没了，这两条一条都没变。

三句话记住

放什么：说不出它改变哪个决定的，不放。

放哪：工具 → 系统提示 → 记忆 → 历史 → 本次问题，越往后越常变。

放多少：每块有上限，超了先汇总或截断，再进来。

⑤套进场景：给值班助手写一个拼装器

  2. 2 量每一块uv run python context-engineering/main.py：工具说明、系统提示、记忆和问题逐块累加，用 count_tokens 数。

def build_request(question, memories, now, layout="good", history=None):
    if layout == "good":
        system = [{"type": "text", "text": SYSTEM,
                   "cache_control": {"type": "ephemeral"}}]
        first_user = {"role": "user", "content": [
            {"type": "text", "text": render_memories(memories)},
            {"type": "text", "text": f"现在是 {now}。\n{question}"}]}
    else:  # bad：很常见的写法
        system = f"现在是 {now}。\n\n{render_memories(memories)}\n\n{SYSTEM}"
        first_user = {"role": "user", "content": question}
    return {"system": system, "tools": TOOLS,
            "messages": [first_user, *(history or [])]}

def truncate_tool_result(text, max_lines=40, keep_tail=10):
    lines = text.splitlines()
    if len(lines) <= max_lines:
        return text
    head, tail = lines[:max_lines - keep_tail], lines[-keep_tail:]
    cut = len(lines) - len(head) - len(tail)
    return "\n".join([*head, f"……（中间省略 {cut} 行，共 {len(lines)} 行；"
                      "要看可以换更窄的关键字或时间段再查）", *tail])

读出来的结论
  • 同样的内容、同样多的 token，只是记忆和时间放的位置不同，第 2 次请求要重算的 token 差 7.5 倍（1124 对 149），耗时差 5.4 倍（13.4 秒对 2.5 秒）。
  • 真正的大头不是系统提示，而是工具结果：一份没处理的 GC 日志比整个固定部分大 100 多倍。放多少，主要是管它。
  • 在 Claude API 上，命中的部分按输入价的一小部分计费，所以位置不只影响速度，还直接影响账单。

⑥反例和误用

第一圈 · 注意事项

1系统提示开头放了时间戳实测← ④ 机制 2
现象
账单里缓存命中一直是 0，每次请求都按全价算、每次都慢；代码里找不到任何报错。
根源
前缀缓存只认一字不差的前缀。“现在是 10:42”放在最前面，每分钟都变，后面所有内容都跟着重算。
做法
时间、请求 ID、用户名这类每次不同的东西，放进最后一条 user 消息；用 usage.cache_read_input_tokens 连续几次为 0 来报警。
2工具列表每次顺序不同← ④ 机制 2
现象
同一个用户连着问，有时命中缓存有时不命中。
根源
工具说明在渲染顺序的最前面。按权限动态增减工具、从 set 里生成列表、JSON 键顺序不固定，都会让前缀变掉。
做法
工具列表写成固定顺序的常量；按权限不同的，拆成几套固定组合，不要每次现拼。
3记忆当成事实放进去← ④ 机制 1
现象
全景第 7 站的反例：模型直接回“和昨天一样，是导出”，其实导出 10:00 已修好。
根源
模型分不清哪段是事实、哪段是旧线索，除非你在上下文里写清楚。没有日期和来源的一句话，和工具刚返回的结果看起来一样可信。
做法
每条记忆带 date、source；系统提示写明“和工具结果冲突时以工具为准，并点出和上次不同”。
4工具结果原样塞回实测← ④ 机制 3
现象
一次 parse_gc_log 返回 3000 行，一轮就吃掉大半预算；后面每一轮还要为它再付一次钱。
根源
工具结果没有预算。它进了对话历史，就会被每一轮重发，直到被压缩或清掉。
做法
工具自己先汇总（返回“Full GC 3 次、最长 1966ms”而不是原始行）；实在要原文就留头留尾，写明删了几行、怎么缩小范围再查。

第二圈 · 使用规范

  • 按变化频率分层：工具 → 系统提示 → 记忆 → 历史 → 本次问题：防缓存失效，也让人一眼看出哪块是会变的。
  • 系统提示写原则和例外，不写长长的 if-else：太细的规则又长又脆，模型照抄字面；太空泛（“请认真排查”）等于没写。Anthropic 那篇文章把这叫找准“高度”。
  • 工具少而不重叠：两个工具都能“查日志”，模型就会选错；每多一份工具说明，每一轮都多付一次它的 token。
  • 每块有上限，超了先截断或汇总，再进上下文：防一次大结果把预算吃光。
  • 记账：每次请求记下各块的 token 数和缓存命中，像记 GC 日志一样，不然不知道钱花在哪。

第三圈 · 优化和深处

Claude API 上的几条硬规定（按文档）

  • 渲染顺序固定为 tools → system → messages；前缀里任何一个字节变了，它后面的缓存全部失效。
  • 一次请求最多 4 个 cache_control 断点；缓存默认活 5 分钟，可选 1 小时，读一次就续期。
  • 最短可缓存长度随模型不同，从 512 到 4096 token；前缀短于它不会报错，只是 cache_creation_input_tokens 一直是 0。
  • 命中缓存的部分按输入价的一小部分计费（多数模型约 0.1 倍），写入缓存要多付一点（5 分钟档 1.25 倍）。

会话中途要加指令怎么办

改系统提示会让整个缓存重来。较新的 Claude 模型支持在 messages 里追加一条 role: "system" 消息，前缀不动，新指令接在后面。这和本页“会变的往后放”是同一个思路。

本机的 llama.cpp 用 Qwen3 的聊天模板，渲染顺序是系统提示在前、工具说明跟在系统提示里。顺序和 Claude 不同，原则一样：会变的东西必须排在所有不变的东西后面。

自测

1. 用一句话说出上下文工程的精华

上下文是一张每轮都要从头读、按 token 计价、越堆越不好用的桌子：只放下一步决策需要的，按变化频率从稳定到易变排列，每一块都给预算。

2. “全塞”这个老办法疼在哪？窗口有 100 万 token 了，为什么还要管？

疼在三处：每一轮整段重发，钱和延迟都乘以轮数；越长越容易漏掉中间的关键行；过时的东西和新的混在一起，模型分不清。窗口变大只解决了“放不下”，这三处一个都没解决。

3. 坑 1（时间戳放开头）的根源是哪条原理？

④ 机制 2：每个位置的计算结果依赖它前面的全部内容，所以缓存只能复用一字不差的前缀；最前面变一个字，后面全部重算。

4. 预测：把 M2“晚高峰不 dump”从记忆挪进系统提示里（写死），缓存和行为各会怎样？

缓存：系统提示变长但仍然不变，前缀照样命中，反而多缓存了一点。行为：这条规矩每次都在，不再依赖召回取没取到它。代价是它对所有团队、所有服务都生效了。规矩稳定、适用面广，就该从记忆升级成系统提示。

从 ④ 机制 1（按变化频率分层）和机制 2（稳定的在前）推出。

5. 预测：本机实验里，如果第 2 次请求只改了问题、时间和记忆都不变，bad 拼法能命中多少？

几乎全部命中：系统提示开头的时间和记忆都没变，前缀一直延续到最后一条 user 消息。bad 拼法的问题不在“放进系统提示”本身，而在放进去的东西每次都变。

从 ④ 机制 2 推出：缓存只看字节是否相同，不看你把它叫什么。

6. 放回全景：第 3 站前后各发生了什么？这一页讲的东西坏了，整条链路会怎样？

前面是第 2 站：按团队和服务从记忆表取回 3 条。后面是第 4 站：带着这次请求进循环，工具结果一轮轮往后堆。拼法坏了有三种走向：记忆不带日期，第 7 站照抄旧原因；会变的放在前面，第 4 站每一轮都全价重算，又贵又慢；工具结果没有预算，第 5 站很快就得压缩，压缩丢掉的东西又会让第 7 站缺证据。

从全景第 2、3、4、5、7 站和本页 ④ 三个机制推出。
