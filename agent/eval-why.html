为什么必须评测：输出不确定，改一处坏一片

agent 的输出是一个分布，提示词又是所有用例共用的一处依赖。所以判断一次改动，不能靠试几条：要拿一套固定的用例跑出通过率，逐条和基线配对，并且先量出同一版自己和自己比会差多少。

①要解决的问题：@4 到底变好还是变坏

在全景第 7 站，这一步要解决的是：PR #57 只改了提示词的一行，@4 比 @3 好还是坏？差出来的那几条，是改动造成的，还是碰巧？写 Java 时这不是问题：改一个方法，跑覆盖它的那几个单元测试，红了就是有 bug。到了 agent 这里，这套直觉有两处不成立。

②不用它会怎样：改完试几条看看

③几种流派：怎么判断一次改动

四种做法放在一起比，看它们对两个要求各做得怎么样：能不能发现“改一处坏一片”，能不能分清是改动造成的还是碰巧。

做法能发现“改一处坏一片”吗能分清噪声吗代价
人工试几条（凭手感）不能：只看了自己记得的几条，坏掉的那几条多半不在里面不能：试一次只抛一次硬币几分钟
断言式单测：全过才绿能看到有条红了，但说不清是变坏还是碰巧不能：10 条每条 p = 0.9，全过的概率只有 0.9¹⁰ ≈ 35%，什么都没改也常红，很快就被关掉和评测集一样
固定评测集 + 通过率 + 逐条配对能：逐条列出谁变好、谁变坏，按故障类型汇总能：先量出同一版两次之间翻面多少条，差值超过它才算数本机 10 条约 15 分钟；用云端 API 是几块钱的事
只看线上指标能，但要等几天，用户已经受了影响样本大，但和流量变化、告警难度混在一起不花额外的钱，可代价是先上线

本页讲第三种：凡是改了提示词、工具说明、模型、检索参数，都先过一遍固定的评测集，和基线逐条配对。线上指标不是替代，而是离线过了以后的第二道关（全景第 10 站）。断言式单测留给确定性的那部分，比如工具函数、日志解析。

④核心取舍：把每条用例当成一枚硬币

先知道这些
  • 采样：模型每写一个 token 都是按概率抽出来的，温度越高越随机。见采样那页。
  • 评测用例：一条 = 问题 + 现场 + 标准答案，代码判分。站 04 写了 10 条，见先写 10 条评测用例。
  • 通过率：通过的条数除以总条数。这一页只用“通过 / 不通过”两种结果，打分细节放到“怎么打分”那页。

机制 1 · 每条用例是一枚硬币：同一版跑两次也不一样

对固定的模型、提示词和用例，回答不是一个，而是一个分布。把“这条用例通过”的概率记作 p，跑一遍评测，就是每枚硬币各抛一次。p 接近 0 或 1 的用例很稳，接近 0.5 的用例次次在翻。同一版跑两次，这条用例结果不同的概率是 2p(1−p)，加起来就是同一版两次之间平均会翻面的条数，也就是噪声底。

p = 0.959.5%两次结果不同的概率
p = 0.742%两次结果不同的概率
p = 0.550%最摇摆，每次都在赌
50 条，2 成在摇摆≈ 9 条同一版两次之间平均翻面

温度设成 0 也不等于每次一样：服务端把几个请求拼成一批算、复用前缀缓存，浮点运算的顺序就变了，结果跟着变；用云端 API 还有后台模型和部署的变化。站 06 在本机就遇到过温度 0、同一提示两次输出不同。所以噪声要实际量出来，不能靠调参数假设它不存在。

机制 2 · 提示词是全局依赖：改一处，所有硬币一起动

提示词、工具说明、模型，每条用例都要读一遍。改一行，每条用例的 p 都可能变，有的升、有的降，而且从 diff 上看不出哪条会动。总分是所有用例加起来的，变好的和变坏的会互相抵消：总分没变，可能是一类故障全坏了、另一类刚好变好。

Java 比方

提示词像所有 Service 都读的那个全局配置项，或者所有类都继承的基类：改了它，整套回归测试都要跑。评测集就是这套回归测试，只是每条的结果是比例，不是全绿全红。

比方失效的地方

Java 里能用 IDE 查出“谁调用了这个配置”，只跑受影响的那部分测试。提示词没有调用关系可查，每条用例都受影响，影响大小也只能跑出来看。而且测试红了不再等于有 bug，可能只是这次抛出了反面。

机制 3 · 逐条配对：只有翻面的那几条带着信息

同一条用例在基线 A 和改动 B 下各跑一次，结果只有四种。两边都过、两边都不过的，说明不了两版谁好。有用的只有翻面的：A 过 B 不过的记作 b（变坏），A 不过 B 过的记作 c（变好）。净变化是 b − c。

为什么这样设计

固定题目 + 通过率 + 逐条配对

  • 承认结果是概率：看的是通过率和翻面数，不要求全过，所以 p = 0.9 的用例不会让门禁天天误报。
  • 配对把两版都稳过、稳不过的用例自动剔掉，只看翻面的那几条，比直接比两个总分灵敏得多。
  • 结果是逐条的，能按故障类型拆开看，“改一处坏一片”藏不住。
  • 代价是要有足够多的题、有时还要多跑几遍，评测本身就要花时间和钱。

被放弃的：断言式单测、凭手感

  • 全过才绿：每条都有一点失败概率，条数一多几乎必红，团队很快就把它关了。
  • 凭手感试几条：只抛了几次硬币，又总是挑自己记得的那几条，坏掉的那类故障根本没被试到。
  • 只比两个总分：变好的和变坏的互相抵消，而且总分的波动包含所有用例的噪声，小变化淹没在里面。
决定胜负的约束：输出是分布，改动是全局的。两条加起来，判断一次改动只能靠统计：题目要固定（才能配对），题目要够多（噪声线才够窄），还要先量出同一版自己和自己比的翻面数。
配对比较的核心几行完整的在 ⑤ 的 diff
b = sum(1 for i in ids if A[i] and not B[i])   # 变坏
c = sum(1 for i in ids if B[i] and not A[i])   # 变好
noise = 2 * (b + c) ** 0.5
if b - c > noise:   verdict = "变坏"
elif c - b > noise: verdict = "变好"
else:               verdict = "分不出"
# 同一版跑两遍的 b+c，就是这套用例的噪声底

三个数一起报

每次评测的结论都写成三样：净变化 b − c、翻面数 b + c、噪声线。只报“通过率 60% → 64%”，读的人没法判断这 4 个点值不值得信。

实验台：一次评测抓得住多大的变坏

先猜：50 条用例，大多数很稳；改动让其中 5 条（一成）的通过概率掉了 0.6。两版各跑一遍、逐条配对，能判出“变坏”的机会有多大？

估算模型，不是实测：每条用例按设定的通过概率抛硬币（多数很稳 = 4 成 p=0.95、4 成 p=0.05、2 成 p=0.5），改动让最稳的那几条掉 0.6；每种设置模拟 2000 次评测，用上面的 2√(b+c) 规则判。数字是让你感受量级的，真实的噪声要按 ⑤ 的办法量。

⑤套进场景：先量噪声，再判 v1 → v2

拿站 04 那次真实的改动（v1 → v2，只改工具说明）来判。先量噪声：v2 一字不改，10 条原样再跑一遍，和 11-24 那遍逐条对照；再把 v1 → v2 的翻面和它比。被测系统、用例、判分全部复用站 04 的代码，一行不改。

到这里已经能交差了：拿到一次改动，你能用数字说出它在哪个指标上真变好、在哪个指标上分不出，而不是“看着更好了”。
已知还没处理的细节：10 条太少，噪声线太宽（坑 1）；只按指标看、没按故障类型看（坑 2）；基线只存了一遍（坑 3）。

⑥反例和误用

第一圈 · 套上了“评测”的名字，却没满足它的约束

1通过率多了两条就宣布变好实测← ④ 机制 3
现象
“64% → 68%，提示词优化有效”，下周再跑又回到 64%。
根源
两条的差距没超过噪声线。⑤ 里同一版原样重跑，本身就翻了好几条。
做法
结论写成三个数：b − c、b + c、噪声线；在线内就写“分不出”。
2只看总分，没看是哪一类坏了← ④ 机制 2
现象
总分没变，上线后连接池类的告警一条都答不对了。
根源
提示词是全局依赖，变好的一类和变坏的一类在总分里抵消了。
做法
报告按故障类型拆开（下一页给 50 条打了类型标签），每一类单独看翻面。
3温度设成 0 就当它是确定的← ④ 机制 1
现象
只跑一遍，把一次结果当成这条用例的“真值”，基线也只存了一次。
根源
批处理、前缀缓存、后台模型变化都会让输出变；而且温度 0 只是让每一步都挑最可能的 token，这一版的“最可能”本身也可能是错的。
做法
新基线至少跑两遍，把同一版的翻面数记下来当噪声底。
4改提示词的同时改了用例← ④ 机制 3
现象
一个 PR 里既改提示词，又删掉了两条“总是不过的”用例，通过率涨了 4 个点。
根源
配对的前提是两边考的是同一套题。题目变了，涨的那 4 个点里分不出哪些是删题删出来的。
做法
评测集有自己的版本号；改评测集单独提 PR，改完用基线重跑一遍，再拿新基线和改动比。
5写成断言式单测，要求全过← ④ 机制 1
现象
CI 里放了 20 条“必须过”的用例，没人改东西也隔三岔五变红，两周后被加进了忽略列表。
根源
每条都有一点失败概率，20 条每条 0.95，全过只有 0.95²⁰ ≈ 36%。
做法
门禁比的是“和基线的差有没有超出噪声”，不是“是不是全过”。只有安全类的硬规则（不许编数字、不许擅自做危险操作）才要求零容忍。
6盯着评测集调提示词，调到过拟合← ④ 设计
现象
为了让 02 过，在提示词里写“看到 HikariPool 就说是连接池”；评测分数一路涨，线上没变好。
根源
评测集只是线上问题的一个样本。把样本里的答案写进提示词，分数涨的是“背题”，不是排障能力。
做法
留一部分用例不看（只在合并前跑），提示词里只写通用的方法，不写某条用例的答案；线上指标做第二道关。

第二圈 · 使用规范

  • 一次只改一处：一个 PR 只动一个变量（提示词、工具说明、模型、检索参数之一）。防的是改好了说不清是谁的功劳，改坏了不知道该回滚哪个。
  • 结果按条存，不只存总分：每条的对话、判分都留下。防的是只剩一个百分比，没法配对、没法回头看。
  • 先量噪声底：每换一次基线，原样跑两遍，记下翻面数。防的是把噪声当成改进。
  • 结论写三个数：净变化、翻面数、噪声线，外加按类型的明细。防的是“64% → 68%”这种看不出可信度的报告。
  • 安全项零容忍，其他项比基线：编造数字、违规调用危险工具，出现一次就红；通过率这类比例指标和基线比。防的是两种指标用同一把尺子。

第三圈 · 要多少条、跑几遍

加用例，还是多跑几遍

多跑几遍只减小“抛硬币”的噪声，能看清某条用例的 p；加用例能覆盖更多种故障，也让噪声线相对变窄。实验台里两样都试一下：50 条只坏 5 条时，跑 3 遍比跑 1 遍好得多，但仍抓不全。实际做法是两头都要：用例尽量多、类型尽量全；改动小的时候每版多跑几遍。

摇摆的用例本身就是信号

像 02 这样 5 次只过 1 次的用例，说明值班助手在这类问题上“会，但不稳”。它是最该修的地方，也是最先暴露改动影响的地方。τ-bench 用 pass^k（同一题 k 次全过的概率）来衡量这种可靠性：p = 0.2 的用例，pass^5 只有 0.03%。

下一圈

  • 够用的统计：置信区间怎么算、翻面很少时的精确二项检验、bootstrap，补给页“样本量和置信区间”。
  • 评测集怎么长：从 10 条到 50 条，按故障类型分层、标来源，下一页。
  • 分数怎么判：规则断言、参考答案、LLM 当评委，评委自己也要被评测。
  • 可靠性指标：pass@k（k 次里至少过一次）和 pass^k（k 次全过）各回答什么问题。

↺回到⑤：改一改

  1. 量出一条用例的 p：same 02 --times 10，再挑一条你觉得最稳的（比如 08）也跑 10 遍。做对了会看到：两条的通过次数差很多，02 的 2p(1−p) 接近最大值。（坑 3）
  2. 判一次真改动：把 oncall-system 里“只用工具拿到的事实，不要猜数字”删掉，跑一遍 10 条，用 diff 和今天的 repeat 比。做对了会看到：“没编造数字”那一列的 b 变多；再用 2√(b+c) 判它是不是超出了噪声。（坑 1）
  3. 按类型拆开：在 cmd_diff 里给每条用例加上故障类型，按类型汇总翻面。做对了会看到：“GC 类”和“非 GC 类”的翻面方向不一样。（坑 2）

自测

1. 用一句话说出这一页的精华

agent 的输出是分布，提示词是所有用例共用的依赖，所以判断一次改动只能靠统计：固定的一套题、逐条和基线配对、先量出同一版自己和自己比的噪声。

2. “改完试几条”具体疼在哪？

两处：试的那几条只抛了一次硬币，结果可能是碰巧（02 五次只过一次）；坏掉的往往是你没去试的那一类（v1 → v2 时，01、03、10 开始编数字）。

3. 断言式单测为什么在这里会被团队关掉？根源是哪条原理？

每条用例都有失败概率，条数一多“全过”的概率很低（20 条每条 0.95，全过约 36%），没改东西也常红，于是没人信它。根源是机制 1：每条用例是一枚硬币。

4. 预测：用例从 10 条加到 50 条，同样是“通过多了 2 条”，算不算变好？

更不算。条数越多，同一版两次之间的翻面数越多，噪声线 2√(b+c) 越宽，净变化 2 条更容易落在线内。加用例是为了让真实的大变化能被看清、覆盖更多类型，不是为了让小差距变显著。

从 ④ 机制 1、机制 3 推出：翻面数随条数增长，噪声线随翻面数的平方根增长。

5. 预测：所有用例的 p 都接近 0 或 1（很稳），同一版跑两次会翻几条？这时改动好判吗？

几乎不翻，2p(1−p) 接近 0，噪声底很低，改动只要让任何一条从稳过变成稳不过，马上就能看出来。所以把摇摆的用例修稳，评测本身也会变灵敏。

从 ④ 机制 1 推出。

6. 放回全景：第 7 站前后各发生了什么？这一页的东西没做，整条链路会怎样？

前面是第 5、6 站：每条用例的结果和轨迹已经判好；后面是第 8 站：门禁按差值判红绿。不量噪声、不配对，门禁只能比两个总分：门槛定紧了天天误报，定松了 @4 这种坏 8 条的改动也能混过去，第 9 站的 trace 也就没人去看。
