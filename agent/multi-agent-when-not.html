什么时候不该拆多 agent

拆多 agent 换来的是上下文隔离和并行，付出的是更多调用、更多输出、交接走样和决定打架。所以先问三件事：裁短工具、开了缓存以后，一个 agent 装不装得下？各块是不是互不依赖？任务书写不写得清楚？装得下、有依赖、写不清，任何一条成立就别拆。真正该拆的，是“每块原文都大到裁不动、彼此又不相干”的活。

①要解决的问题：上一页的账，到底划不划算

在全景第 5 站，这一步要回答的是：值班助手要不要拆成主 agent 加三个子 agent。上一页用本机小模型把同一个问题跑了两种方法，账本是这样的：

模型调用3 → 7一个 agent → 主从
输出 token177 → 641每个子 agent 都要写结论
主 agent 最大一次输入856 → 395上下文确实省了
用时（本机 2 核）34s → 100s并行没省时间

数字来自上一页 ⑤的实测（Qwen3-1.7B，人写任务书那一组）。只看这四个数，拆了不划算；可这个现场是玩具，原文才几百字。换成真实规模，账会翻过来吗？这一页就算这个。

②不想清楚就拆，会怎样

  • 花得多：Anthropic 自己的数据，agent 用的 token 约是普通对话的 4 倍，多 agent 系统约 15 倍。拆一次，账单就上一个台阶。
  • 交接走样：上一页实测，主 agent 把笔记里的建议写成了“jmap 显示……”，又把线程栈的位置写错了。
  • 决定打架：Cognition 的原话是“行动里带着隐含的决定，决定冲突就带来坏结果”。并行的子 agent 看不到彼此的决定。
  • 更慢：本机算力有限时，并行变成排队，7 次调用比 3 次慢得多。
  • 调试更难：出了错要分清是任务书、子 agent 还是汇总的问题，评测也要分三层做。
不懂精华时的典型误用：按“组织架构”拆，日志一个 agent、指标一个 agent、笔记一个 agent，只因为听起来像一个团队；不看每块原文多大、彼此有没有依赖、一个 agent 是不是本来就装得下。

③几种流派：拆派、不拆派、先省再拆

流派主张依据它也承认的边界
拆：Anthropic 多 agent 研究系统（2025-06-13）主 agent 规划，多个子 agent 并行搜、各自读一大堆资料，只交回要点内部研究类评测上，Opus 4 当主、Sonnet 4 当子，比单个 Opus 4 高 90.2%；BrowseComp 上 token 用量一项就解释了 80% 的表现差异需要所有 agent 共享同一份上下文、或 agent 之间依赖很多的领域，目前不适合；大多数编程任务里真正能并行的子任务比研究少
不拆：Cognition《Don't Build Multi-Agents》（2025-06-12）最简单的做法是单线程、线性的 agent；历史太长就用一个模型把它压缩成关键细节、事件和决定两条原则：共享上下文，而且共享完整的 agent 轨迹，不只是单条消息；行动带着隐含的决定，决定冲突就带来坏结果压缩本身要做好，做不好会丢信息
先省再拆（本页的做法）先让工具只返回相关的几十行、开提示缓存、按站 05 压缩上下文；做完这些一个 agent 还装不下，再把“读得多、交得少、互不依赖”的那几块拆出去⑤ 的估算：工具裁短、开了缓存以后，一个 agent 只要 6.6K 上下文，这时拆开反而多花 11%估算模型很粗，要拿自己的账本校准

本页的选择：两派说的其实是同一件事的两头。研究类任务要读的东西多、各块独立，拆了划算；编程、排障这类前后环环相扣的任务，共享上下文更要紧。分界线不是“拆不拆”的信仰，是 ④ 那张图上的几个变量。

④核心取舍：一张账，三个问题

机制 1 · 拆换来什么、付出什么

换来的付出的
上下文原文留在子 agent 那里，主 agent 只读结论（上一页实测最大一次输入 856 → 395）每个子 agent 都要重读一遍自己的系统提示和工具说明
时间互不依赖的几块能同时跑，耗时约等于最慢的那一块算力不够时并行变排队；有依赖时只能串行
token原文很大时，省掉“一个 agent 每轮重读前面所有原文”的那部分调用次数和输出都翻倍（3 → 7 次，177 → 641 token）
质量每个子 agent 工具少、任务窄，选错工具的机会少任务书和结论都是压缩，会丢、会走样；并行的决定会打架

机制 2 · token 账的形状：一个 agent 每轮都在重读

一个 agent 查 3 块材料，每块查 2 轮：第 1 轮读第 1 块的一半，第 2 轮读一整块，……，第 6 轮把三块全读一遍。原文只要留在对话里，后面每一轮都要再读一遍前面所有的。拆开以后，每个子 agent 只重读自己那一块。所以原文越大，拆开越省；开了提示缓存，重读只按 1/10 算，拆开省的就少了很多。

为什么这样设计：默认一个 agent，满足三条才拆

默认一个 agent

  • 上下文完整，没有交接走样，决定不会打架。
  • 调试简单，一条轨迹看到底。
  • 代价：原文真大到裁不动时装不下，也没法并行。

默认拆

  • 小任务也付交接和重读背景的钱（玩具现场多花 36%，见 ⑤）。
  • 有依赖的任务硬拆，只能串行，还要把前面的结论抄进后面的任务书。
决定胜负的约束：上下文窗口和注意力有限，这是拆的唯一硬理由；拆的成本却是确定的：更多调用、更多输出、压缩带来的走样。所以默认值只能是“不拆”，等裁工具、缓存、压缩这些更便宜的手段都用完了，上下文还是装不下，才拿拆去换。

⑤套进场景：值班助手到底拆不拆

先量真实规模。玩具现场的日志才几百字；生产上一份线程栈、一段日志有多大？合成一份 200 个 Tomcat 线程的 jstack 和 2000 行访问日志，用本机模型的分词器数一下：

实测uv run python multi-agent-when-not/jstack_tokens.py完整代码 →
jstack，200 个线程     180189 字符    65301 token
应用日志，2000 行      211981 字符   129981 token

2026-11-26，llama-server 的 /tokenize，Qwen3 的分词器；Claude 的分词器数出来会不一样，量级相同。两样加起来接近 20 万，一个 agent 读完就快满了。

再把几种做法代进估算模型（3 块材料，每块查 2 轮；玩具现场每块 1 轮）：

读出来的结论
  • 玩具现场：拆了多花 36%，时间不省。不拆。
  • 真实规模、什么都不做：一个 agent 的上下文到了 19.6 万，快撑满 20 万的窗口，拆开只要 0.43 倍、快 5 倍多。这时候看起来非拆不可。
  • 但先裁工具（日志只返回匹配的几十行，线程栈只返回非空闲的线程）、再开缓存：一个 agent 只要 6.6K 上下文，拆开反而多花 11%。该做的是裁工具，不是拆。
  • 真正该拆的：材料大到裁不动（比如要通读整份线程栈找规律）、几块之间不相干、而且有云端的并行算力。

实验台：拆不拆计算器

先猜：每块原文 6.5 万 token、不开缓存、云端并行，拆成 3 个子 agent，总输入比一个 agent 多还是少？

估算模型，公式和 study-labs 的 cost_model.py 一样：背景 600 token、子 agent 背景 400、每段结论 150；每次调用 2 秒加每 4000 个要现算的 token 1 秒；缓存命中按 1/10 算；“装得下”按不超过 10 万 token（20 万窗口的一半）算。用来比方向，不用来报预算；要报预算，拿自己的账本（上一页的 Ledger）校准。

过关条件三：说得出省了什么、多花了什么

  1. 1 省了什么主 agent 的上下文：实测最大一次输入 856 → 395 token；原文规模大时，省掉一个 agent 每轮重读前面所有原文的那部分（估算 0.43～0.85 倍）；有并行算力时省时间。
  2. 2 多花了什么调用 3 → 7 次，输出 177 → 641 token（实测）；每个子 agent 重读背景；交接走样两次（实测）；本机算力下更慢（34 → 100 秒）。
  3. 3 结论玩具现场不该拆；生产规模先裁工具、开缓存，一个 agent 装得下就不拆；只有“通读整份线程栈”这类裁不动的活，才拆成只读的子 agent。
到这里已经能交差了：能用三个问题判断拆不拆，能用账本和估算说清省了什么、多花了什么。
已知还没处理的细节：为了并行而拆（坑 1）、按组织架构拆（坑 2）、拿拆代替裁工具（坑 3）、有依赖硬拆（坑 4）、没账本就下结论（坑 5）。

⑥反例和误用

第一圈 · 注意事项

1为了并行而拆，结果更慢实测← ④ 机制 1
现象
本机拆成三个子 agent，34 秒变 100 秒。
根源
拆了以后总活变多（3 次调用变 7 次）；算力不够时并行变排队。云端 API 有限流时也一样。
做法
在真实部署环境量墙钟时间；算力或限流是瓶颈时，拆不会更快。
2按组织架构拆按设计← ④ 为什么这样设计
现象
“产品经理 agent、架构师 agent、程序员 agent、测试 agent”，听起来像个团队，实际是一条前后依赖的流水线，每一棒都在转述上一棒。
根源
拆的理由应该是上下文装不下、各块互不依赖，而不是“现实里这是几个人干的”。按角色拆正好撞上 ④ 第 ② 条：有依赖。
做法
按“要读的材料”拆，不按“角色”拆；前后依赖的流程用一个 agent，或者用写死的工作流（工作流还是 Agent）。
3拿拆 agent 代替裁工具估算← ④ 机制 2
现象
search_logs 一次返回 2000 行，上下文爆了，于是拆出一个“日志 agent”去读这 2000 行。
根源
上下文爆的根源是工具返回太多。⑤ 的估算：裁到 2000 token 以内、再开缓存，一个 agent 只要 6.6K 上下文，拆开反而多花 11%。
做法
先改工具：只返回匹配的行、加 limit、线程栈只返回非空闲线程（精简的返回）；改完还装不下再谈拆。
4有依赖的子任务硬拆按文档← ④ 为什么这样设计
现象
“先查是哪个服务慢，再查那个服务的 GC”拆成两个子 agent 并行跑，第二个不知道查谁，只好全查。
根源
Anthropic 自己也写了：需要共享同一份上下文、或者 agent 之间依赖很多的领域，目前不适合多 agent；Cognition 的“决定冲突带来坏结果”说的是同一件事。
做法
有依赖就串着做；真要拆，前一个的结论写进后一个的任务书（估算里依赖会让耗时从 35 秒变 97 秒）。
5没有账本就说“多 agent 效果更好”按设计← ④ 机制 1
现象
拆完觉得结论“更全面了”，可说不出多花了多少 token、慢了多少、哪一步走了样。
根源
Anthropic 的数据里 token 用量一项就解释了 80% 的表现差异：多 agent 变好，很大一部分是因为花得多。不记账就分不清是拆的功劳还是钱的功劳。
做法
按 agent 记账（上一页的 Ledger），和“一个 agent 给同样多的 token 预算”比，才是公平的对照。

第二圈 · 使用规范

  • 默认一个 agent，拆要写理由：理由只能是 ④ 的三条，防坑 2。
  • 拆之前先做三件便宜的事：裁工具、开缓存、压缩上下文：防坑 3。
  • 拆出去的子 agent 只读，写操作留在主 agent：防决定打架。
  • 上线前用自己的账本跑一组 A/B：同一批问题，一个 agent 和多 agent 各跑一遍，比质量、token、耗时，防坑 5。

第三圈 · 优化和深处

主强子弱，省钱的常见搭法

Anthropic 那套系统是 Opus 4 当主 agent、Sonnet 4 当子 agent。读大量原文、交回要点这种活交给便宜的模型，规划和汇总留给强模型，拆开以后反而可能比“一个强模型读完全部”便宜。选模型的账见站 02 怎么选模型。

估算模型漏掉的东西

没算输出 token（拆开以后多 3 倍多，⑤ 页实测）、没算写缓存的加价、没算质量。工具裁短也不是免费的：裁错了，关键的那一行就没了。估算只告诉你方向，拍板要靠自己的账本。

下一圈

  • 同样的 token 预算给一个 agent（更多轮、更长思考）和给多 agent，在自己的评测集上比一次（站 09）。
  • Claude Code 的子 agent 什么时候自动派出去：看它在代码库里“通读一大片、交回几行”的用法。
  • 上下文编辑：不拆 agent，只把用过的工具结果从上下文里清掉，能省多少。

↺回到⑤：改一改

  2. 真去裁工具：把 jstack_tokens.py 里的线程栈只保留非 WAITING 的线程，再数 token，能裁掉多少？（坑 3）

自测

1. 用一句话说出这一页的精华

默认一个 agent；先裁工具、开缓存、压缩，之后还装不下、各块互不依赖、任务书写得清楚，三条都满足才拆。

2. 不想清楚就拆，会多付哪几样？

更多调用和输出 token、每个子 agent 重读背景、交接走样、并行决定打架、算力不够时更慢、调试和评测更难。

3. 为什么原文越大，拆开越省 token？

一个 agent 的原文留在对话里，后面每一轮都要把前面所有原文再读一遍，总量按块数的平方长；拆开后每个子 agent 只重读自己那一块。

从 ④ 机制 2 推出。

4. 预测：开了提示缓存，上面那条还成立吗？

成立，但差距小得多：重读按 1/10 算，估算里每块 6.5 万 token 时比值从 0.43 变成 0.85；每块 2000 token 时反过来，拆开多花 11%（还要算上裁短）。

从 ④ 机制 2 的图推出。

5. 预测：五块材料、每块 2 万 token、各块前后依赖、云端算力，拆成并行的子 agent 吗？

不拆成并行的。依赖让子 agent 只能一个接一个跑，后面的任务书还要带前面的结论。实验台上看，串行的子 agent 仍比一个 agent 省（比值 0.29，耗时 161 → 75 秒），省在每块原文看完就丢、只留结论；可这正是“一个 agent 按顺序做、每做完一块压缩一次”。所以答案是一个 agent、按顺序、块与块之间压缩，不需要多 agent 那套交接。

从 ④ 为什么这样设计的第 ② 条推出，数字来自 ⑤ 的实验台。

6. 放回全景：第 5 站前后各发生了什么？如果值班助手决定不拆，全景图哪几站会变？
