线上指标：成功率、成本、P95 延迟、转人工率

离线评测过了，线上还要再证一次。四个数：成功率（值班同学采纳了结论）、每次排障的成本、P95 延迟、转人工率。它们按提示词版本拆开，灰度时新旧并排比。要记住两件事：成本和延迟马上就有，成功率要等人反馈，天然慢一拍；5% 灰度一天只有二十几次请求，成功率的波动比差别还大。

全景：改了一句提示词之后 · 第 10 站地图：站 09 · 线上指标深度：会用

这一页的位置站 09 第 8 个知识点。Java 板块讲过Prometheus 指标和告警、日志、指标、链路三件套；这一页是同一套东西用在 agent 上：指标还是计数器和直方图，只是数的东西换成了 token、采纳、转人工。

①为什么学：50 条用例代表不了线上所有的告警

在全景第 10 站，@5 过了门禁、合并了，先只给 5% 的告警用。这一步要回答：@5 在真实流量上是不是不比 @3 差？离线评测只有 50 道题，线上一天几百次告警，故障五花八门；而且线上没有标准答案，只能看值班同学的反应。

②老办法：看服务的健康度，等用户来投诉

  • 只看接口的 5xx 和延迟：值班助手每次都按时返回了一段像模像样的话，服务“很健康”，可结论一半是错的。
  • 等值班同学来抱怨：等到有人说“最近助手老往 GC 上推”，@5 已经全量好几天了。
  • 从 trace 里加总：线上 trace 一般只采一部分，加出来的 token 和请求数都偏小；约定里专门写了，token 用量要用指标来算，因为指标不受采样影响。
  • 只看一个总的成功率：灰度的 5% 和全量的 95% 混在一起，新版本就算差很多，总数也只动一点点。
不懂精华时的典型误用：灰度一天，看到 @5 的成本和 P95 都比 @3 好看，就全量了。成本和延迟是马上能看到的，可它们不是“答得对不对”；成功率要等人反馈，又只有二十几个样本，这一天根本看不出它是变好还是变坏。全景的预测题 3 说的就是这个。

③选谁：OpenTelemetry 指标 + Prometheus

做法好处代价
OpenTelemetry 指标 SDK → Prometheus / Grafana（本页）和 trace 同一套 SDK、同一套属性；Java 服务的指标、告警、看板都在这里，值班的人不用多开一个系统“采纳”“转人工”这类业务结局要自己埋点
LLM 观测平台的看板（Langfuse 等）成本、token、延迟按提示词版本拆开，开箱即用；还能把用户反馈挂到 trace 上告警、值班流程要和现有的 Prometheus 体系打通
从日志里统计不用改代码延迟分位数、按版本拆分都要写复杂查询；日志量大了又贵又慢
从采样后的 trace 里加总不用另外埋点采样后的数偏小，比例也可能偏（出错的被优先留下）

本页用 OpenTelemetry 指标：名字照 GenAI 约定，属性里带 prompt_version；本机用 SDK 自带的内存读取器把数拿出来，按 Prometheus 的算法求分位数。线上换成 Prometheus 导出器即可。

④原理：四个数怎么定义、怎么记、怎么比

先知道这些
  • 计数器和直方图：计数器只增不减，求速率；直方图把每个样本落进预先划好的桶里，分位数从桶里插值估出来。见 Java 板块的 Prometheus。
  • 为什么 P95 而不是平均：慢请求藏在平均数里看不见。见响应时间为什么越压越长。

机制 1 · 四个数的定义：线上没有标准答案，只能看人的行为

指标定义从哪来多快能看到
成功率值班同学采纳了结论（点了“有用”，或按建议处理后告警恢复）的比例业务结局计数 oncall.requests{outcome="adopted"}慢：几分钟到几小时，要等人处理完
每次排障的成本输入 token（分缓存命中、未命中）和输出 token，各乘各的单价gen_ai.client.inference.usage.* 计数器马上
P95 延迟从收到告警到给出结论，95% 的排障在这个时间内完成gen_ai.invoke_agent.duration 直方图马上
转人工率值班同学放弃助手、自己从头查的比例业务结局计数 outcome="escalated"较慢

“采纳”只是“答对了”的代理：值班同学可能采纳了一个错结论，也可能没点按钮。所以成功率要和转人工率一起看，并且定期抽一批线上的回答拿人工判一遍（站 09 的评测集就是这样长大的）。

机制 2 · P95 是从桶里估出来的：桶划得粗，估得就偏

直方图不存每个样本，只存每个桶里有几个。分位数的算法是：找到第 95% 的样本落在哪个桶，再在桶的上下界之间线性插值。约定给 gen_ai.invoke_agent.duration 建议的桶边界是 0.1、0.25、0.5、1、2.5、5、10、30、60、120、300 秒……照顾的是从毫秒级到几小时的各种 agent。值班助手在本机一次 60～110 秒，全挤在 60～120 这一个桶里，桶内插值就会偏：⑤ 里实测，真实 P95 是 93 秒，直方图估出来是 115 秒。桶边界要按自己的耗时分布加密。

机制 3 · 按版本拆开：属性带 prompt_version，别带用例编号

每个样本都带上 prompt_version（和 span 上的 gen_ai.prompt.version 是同一个值），查询时按它分组，@5 和 @3 就能并排。可以带的属性：版本、模型、告警类型这种取值少的；不能带的：告警编号、用户、会话这种取值无穷多的，每多一个取值，Prometheus 就多一条时间序列，很快就撑爆。要追到某一次，用 trace。

机制 4 · 先动的和后动的：灰度要看够样本、看够时间

成本、延迟在请求结束时就记下了，灰度几分钟就能比；成功率、转人工率要等人反馈，而且每一次只是一枚硬币（为什么必须评测）。5% 灰度、一天 480 次告警，@5 一天只分到二十几次，成功率的 95% 区间有正负十几个百分点，比两版的真实差别还大。要么加大灰度比例，要么多等几天，要么先用离线评测把大的变坏拦在门外（这正是门禁的意义）。

为什么这样设计

指标、trace、离线评测，三样各管一段

  • 指标：每次都记、不采样、便宜，回答“整体怎么样、哪个版本更好”。
  • trace：有采样、贵，回答“这一次为什么”。
  • 离线评测：有标准答案，回答“改动有没有把已知的题答坏”，在上线之前。
  • 代价：三样东西要用同一套版本号和属性名，才能互相跳转。

被放弃的：只靠其中一样

  • 只看指标：知道 @5 的成功率低了，不知道是哪类告警、哪一步出的错。
  • 只看 trace：采样后的数加不准，也不适合做告警。
  • 只靠离线评测：50 道题之外的线上问题、真实的成本和延迟，它都看不到。
决定胜负的约束：线上的“对不对”只能靠人的行为间接看到，又慢又少；成本和延迟又快又准，却说明不了对错。所以既要按版本并排看四个数，又要知道哪几个数在灰度的头一天根本没有发言权。

实验台：灰度要多大、看几天

先猜：一天 480 次告警，@5 灰度 5%。@3 的成功率约 30%，@5 真实比它低 10 个百分点。要等多少天，成功率的 95% 区间才窄到能看出这 10 个点？

估算：成功率按二项分布算 95% 区间（正态近似），两版之差的区间半宽 ≈ 1.96 × √(p₁(1−p₁)/n₁ + p₂(1−p₂)/n₂)；半宽小于真实差别，才算“有可能看出来”（这时也只有一半左右的把握，想要更稳还得再多几天）。@3 的成功率取 30%，和 ⑤ 回放里的量级一致。

⑤跑起来：用真实的评测结果回放一天的线上流量

本机没有真的线上流量，就用评测存下来的结果“回放”：一天 480 次告警，95% 走 @3、5% 走灰度版本；每次请求随机抽一条用例，再从这个版本真跑过的结果里抽一次，耗时、token、对错都是真的。值班同学的反应是假设的（写在代码开头）：判分全对 90% 采纳，说中了但没全对 50%，其余 15%。指标用 OpenTelemetry 指标 SDK 按约定的名字记，P95 照 Prometheus 的算法从直方图里插值。

读出来的结论
  • @5 灰度一天，什么也看不出来：23 次请求，成功率的区间从 13% 到 46%，@3 的 22% 整个落在里面；看七天，区间缩到 20%～34%，仍然和 @3 重叠。离线评测说 @5 和 @3 分不出高下，线上一周也分不出，这是一致的。
  • 假如 @4 上了线，第一天它的成功率反而“更高”：34.8%，可区间是 19%～55%，纯属运气。先露馅的是延迟：P95 真实值从 109 秒涨到 132 秒（直方图估成 197 秒，桶太粗放大了它）。质量的信号被噪声盖住、甚至方向相反，这正是离线门禁存在的理由。
  • P95 的误差看分布：耗时挤在 60～120 秒一个桶里时，估出来的 P95 比真实的高 20 多秒；有一部分落进下一个桶时又差不多准。指标看板上的分位数是估计值，桶要照自己的分布划。
  • 成功率的“绝对值”别当真：它取决于假设的采纳率；能比的是同一天、同一个假设下两个版本的差，以及这个差的区间有多宽。真实线上要用真实的反馈。

⑥细节·规范·优化

第一圈 · 注意事项

1直方图的桶太粗，P95 估偏了实测← ④ 机制 2
现象
看板上 P95 是 115 秒，可抽查的真实耗时没有一次超过 110 秒。
根源
耗时全挤在 60～120 秒一个桶里，分位数在桶内线性插值，桶越宽误差越大。
做法
按自己的耗时分布加密桶边界（比如 60 到 120 秒之间每 10 秒一个）；OpenTelemetry 用 View 改桶，或者用指数直方图。
2把告警编号放进了指标的标签← ④ 机制 3
现象
Prometheus 内存一周涨了十倍，查询越来越慢。
根源
每个不同的标签组合是一条时间序列，告警编号、用户编号取值无穷多，序列数跟着无穷多。
做法
标签只放取值少的：版本、模型、告警类型、结局；要追到某一次，用 trace 的编号。
3灰度第一天就下结论← ④ 机制 4
现象
灰度一天，@5 的成功率比 @3 高出一截，于是全量；一周后整体成功率反而降了。
根源
5% 灰度一天只有二十几次请求，成功率的区间比差别还宽；成功率又要等反馈，最后几个小时的请求还没算进去。
做法
先用实验台算出要几天；全量的条件写成“成本和 P95 不变坏，且成功率之差的区间不再覆盖‘明显变坏’”。
4把“采纳”当成“答对”← ④ 机制 1
现象
成功率一直很高，复盘时发现有一类故障，值班同学照着助手的错结论处理了，后来才发现。
根源
线上的“成功”只能看人的行为，人也会被说得很笃定的错结论骗过去。
做法
定期从线上抽样，拿参考答案或人工判一遍（就是把线上问题变成评测用例）；转人工率、告警是否复发一起看。
5刚切版本那一阵又慢又贵实测← ④ 机制 4
现象
切到 @5 的头几分钟，P95 和成本都冲高。
根源
提示词变了，前缀缓存全部失效（Tracing 那页实测：第 1 轮缓存 0，耗时是平时的五倍）。
做法
比较新旧版本时跳过切换后的头一段；或者先拿几条请求把缓存“预热”一下。

第二圈 · 使用规范

  • 四个数并排、按版本拆：看板上每个指标都按 prompt_version 分两条线。防的是灰度被全量的数淹没。
  • 成本分三档记：缓存命中、未命中、输出各自计数。防的是缓存命中率一掉，成本翻倍却找不到原因。
  • 告警看比例，也看样本数：“成功率低于 X”的告警同时要求样本数大于 N。防的是夜里两次请求一次失败就把人叫醒。
  • 全量的条件写下来：灰度前就约定看几天、看哪几个数、各自允许多大的变化。防的是看到对自己有利的数就全量。

第三圈 · 优化和深处

给 agent 定 SLO

和 Java 服务一样，可以给值班助手定目标：比如“99% 的排障 3 分钟内给出结论”“转人工率低于 30%”，用错误预算决定什么时候可以继续上新版本、什么时候要先修。区别是成功率要按天、按周算，不能按分钟。

线上评测

线上没有标准答案，但可以每天抽一批 trace，交给带细则的评委判一遍（怎么打分那页的方法），得到一个比“采纳”更直接的质量信号；评委判错的、值班同学投诉的，回流进评测集。

下一圈

  • 换模型：模型变了，四个数全会动，回归方法见最后一页。
  • A/B 而不只是灰度：两版按用户或按告警类型随机分流，样本更均衡，结论更可信。
  • 指数直方图：OpenTelemetry 的 exponential histogram 不用预先划桶，分位数误差有上界。
  • 反馈怎么收：按钮、告警是否恢复、工单里的处理记录，哪个更接近“答对了”。

↺回到⑤：改一改

  1. 加密桶边界：在 main.py 的 View 里把 60～120 秒之间每 10 秒加一个边界，重跑 buckets。做对了会看到：直方图估出的 P95 和真实 P95 的差从 20 多秒缩到 10 秒以内。（坑 1）
  2. 灰度跑三天：replay --days 3，和一天的结果比。做对了会看到：@5 的成功率区间明显变窄，成本和 P95 的数几乎不变。（坑 3）
  3. 换一种反应模型：把 REACT 里“没说中”的采纳率从 15% 改成 40%（值班同学更容易被说服），重跑。做对了会看到：两版的成功率都涨了，差距却变小了：采纳率越不挑剔，越分不出好坏。（坑 4）

自测

1. 用一句话说出这一页的精华

线上看四个数（成功率、成本、P95、转人工率），按提示词版本拆开并排比；成本和延迟马上有，成功率靠人反馈、慢且样本少，灰度要先算清楚看几天，P95 要注意直方图的桶。

2. 只看服务的 5xx 和延迟，疼在哪？

值班助手每次都按时返回了一段话，服务很健康，可结论对不对完全看不出来。

3. 为什么 token 用量要从指标算，而不是从 trace 加总？

线上 trace 一般要采样，加出来的数偏小，比例也可能偏；指标每次都记，不受采样影响。OpenTelemetry 的约定里专门写了这一点。

4. 预测：假如 @4 没被门禁拦下，直接灰度 5%，第一天看板上哪几个数会先动？方向呢？

成本和 P95 先动，而且是变差：离线评测里 @4 的输出 token 是 @3 的 1.29 倍、耗时 1.28 倍。成功率要等反馈，一天二十几个样本，看不出来。所以这次 @4 在线上也能很快被发现，但靠的是成本，不是质量。

从 ④ 机制 4 和门禁那页的 @4 数字推出。

5. 预测：把灰度比例从 5% 提到 50%，“要几天才看得出 10 个点的差别”会怎样？代价是什么？
