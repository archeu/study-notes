Agent 循环：调到不再要工具或到上限为止

把上一页的一来一回放进 while：模型要工具，就执行、送回、再问一次；它不再要工具（stop_reason 变成 end_turn），或者到了你定的上限，就停。和普通循环最大的不同是：继续不继续由模型决定，最多转几圈由你决定。代价是 messages 每转一圈就长一截，而且每圈都整段重发。

这一页的位置站 04 下钻第 2 页。上一页 工具调用的一来一回 是一次；这一页是很多次。下一页 停止条件 专讲“到上限为止”那半句。

①为什么需要：查完第一样，才知道该查第二样

全景那次实测：第 1 轮模型要了日志和 GC，两样都“没查到”（它把时间填错了）；第 2 轮它改看线程栈，看到导出线程卡在写 Excel；第 3 轮去知识库搜“导出 Excel”；第 4 轮想 dump 堆……每一步查什么，都取决于上一步看到了什么。你没法事先写死要调几次。

②没有它会怎样：写死轮数

最省事的写法是 for i in range(2)：固定来回两次。对照几条要求：

要求写死 2 轮while：模型说停才停（再加上限）
查完就停，不多花钱不能：第 1 轮就够了，也要硬转第 2 轮；第 2 轮模型没要工具，你还得特判能：end_turn 就出循环
没查完不会半途交卷不能：全景那次要 5 轮，2 轮时它还在看线程栈，交出去的是半截能：要工具就继续
出了意外能停能：最多 2 轮，天然有上限要自己加：步数、预算、时长三道闸（下一页）
不懂精华时的典型误用：从一个极端跳到另一个极端，写成 while resp.stop_reason == "tool_use" 就上线，没有任何上限。普通 while 的条件是你写死的，迟早会变；这里的条件是模型给的，它可能永远不变。

③相邻方案：循环由谁来写

做法循环在哪你能控制的什么时候用
手写 while（这一页）你的进程每一行：怎么拼消息、何时停、怎么记日志学习；或者要非常规的控制流
SDK 的 Tool Runner你的进程，SDK 写好的每轮有钩子：审批、改结果、换参数、max_iterations产品里常用的默认选择
框架（LangGraph、Spring AI）你的进程，框架的图或链按框架的抽象：节点、边、状态多 agent、复杂分支（站 08）
托管（Claude Managed Agents）Anthropic 那边，连沙箱一起配置和工具结果，循环本身不归你不想自己托管循环和执行环境

本页手写：后三种都是在替你写这 30 行。先自己写一遍，才看得懂它们的参数在控制什么，出了问题也知道去哪一层找。

④原理：一个由模型推动的状态机

先知道这些
  • 一来一回：模型回 tool_use 就停下，你执行后把 tool_result 放进下一次请求。见上一页 工具调用的一来一回。
  • 无状态、整段重发：每次请求都要带上前面全部消息。见 Messages API。
  • 提示词缓存：前缀没变的部分按很低的价格算。见 省钱：提示词缓存和批处理。

机制 1 · 循环的骨架：看 stop_reason 走哪条边

Java 比方：一个 while 包着的状态机，像订单状态流转。比方失效的地方：订单从“已支付”到“已发货”的条件是你的代码写的；这里“继续还是结束”是模型的回应里带出来的 stop_reason，你只能读它，改不了它。所以出口有两种：模型给的（end_turn），和你给的（上限）。

机制 2 · messages 越滚越长：每一轮都为前面所有轮付钱

每转一圈，messages 多两条（assistant 的调用单 + user 的回执），而下一次请求要把它们全部带上。所以第 k 轮的输入 ≈ 固定部分（tools + system + 问题）+ 前面 k−1 轮攒下的历史。全部轮加起来，是一个随轮数平方增长的数。

机制 3 · stop_reason：模型给的六种信号

stop_reason意思循环里怎么办
tool_use写了调用单，等你执行执行全部调用，回执放进一条 user，继续
end_turn说完了取文字，出循环
max_tokens被你给的输出额度截断不能当答完；调大 max_tokens 重发这一轮，或者让它接着写
stop_sequence碰到你设的停止串按你设它的目的处理
pause_turn服务端工具（如 web_search）在服务端转太久，暂停了把这次回应原样放回，再发一次，服务端会接着做
refusal安全分类器拒答不能当答完；记录、换说法或换模型兜底

按 Claude 官方文档“Handling stop reasons”整理。这一站只用到前两行；客户端工具不会出现 pause_turn。

为什么这样设计：循环放在你这边

选中的：API 只管一轮，循环归你

  • 每两轮之间你都能插手：审批、截断结果、换模型、记日志、按预算喊停。
  • API 保持无状态，一次请求一次回应，重试、限流、超时都和普通 HTTP 调用一样处理（出错怎么办）。
  • 代价：messages 整段重发，靠缓存才不贵；你得自己保存对话，进程挂了就从头来。

另一种：服务端替你转圈

  • 服务端工具（web_search 等）和托管 agent 就是这样：调用方只发一次，省事。
  • 碰到你自己的工具就做不到：执行必须回到你这边，服务端只能停下来等你（这正是 tool_use 和 pause_turn 的由来）。
  • 每一步的控制点变成别人的配置项，能做什么取决于对方开放了什么。
决定胜负的约束：工具在你这边执行，一次 HTTP 回应又不能等你执行完，所以每一轮必然在“提议”处断开；既然每轮都要回到你这边，循环放在你这边最自然。“想一步、做一步、看结果再想”这种写法，论文里叫 ReAct（推理 + 行动）；原生工具调用加上模型的思考，就是它的内置版。

⑥细节：循环转起来以后的坑

第一圈 · 注意事项

1只写了 while tool_use，没有上限← ④ 机制 1
现象
某个工具一直返回“没查到”，模型一直换关键字查；一晚上跑了几百轮。
根源
继续的条件是模型给的，它可能一直给“继续”。
做法
步数、token 预算、墙钟时长三道闸，任何一道到了就停，并把已有证据交给人。下一页 停止条件。
2只把文字放回历史← ④ 机制 2
现象
为了“省 token”，只把 assistant 的文字存进 messages，下一轮 400，或者模型重复要同一个工具。
根源
回执要对上历史里的调用单；模型也只能从历史知道自己查过什么。
做法
assistant 的 content 整个原样放回（含 thinking）；要省，省在工具结果上（截断、精简）。
3每轮往 system 里塞“当前轮次 / 当前时间”← ④ 机制 2
现象
开了缓存，cache_read_input_tokens 却一直是 0，账单没降。
根源
缓存按前缀匹配，顺序是 tools → system → messages。system 每轮变一个字，后面整段都要重算。
做法
tools 和 system 每轮一字不改；会变的信息放进 messages 末尾。
4把 max_tokens、空回答当成答完了实测← ④ 机制 3
现象
值班的人收到一段说到一半的结论。
根源
只判断了“不是 tool_use 就结束”，把 max_tokens、refusal 都当成了 end_turn。本机 Qwen3 一次思考就能写几百 token。
做法
只有 end_turn 走正常出口；其他值单独处理，至少明确告诉用户“没答完”。end_turn 也要检查文字是不是空的（⑤ 实测就碰上了：只写了思考就结束），空的就追问一句“请给出结论”。
5第 4 轮一个 429，前三轮白干← ④ 设计
现象
排查进行到一半，API 限流或超时抛异常，整个排查从头来，前面花的钱和时间都没了。
根源
循环在你的进程里，对话只存在内存的 messages 变量里。
做法
每次调模型走带退避的重试（出错怎么办，SDK 默认重试 2 次）；每轮结束把 messages 写盘，挂了能接着跑。
6历史越来越长，答案越来越差← ④ 机制 2
现象
转到二三十轮以后，模型开始忘了最初的问题、重复查过的东西，或者直接超出上下文窗口报错。
根源
每轮的回执都留在历史里，提示越来越长；长上下文里中间的内容最容易被忽略（上下文窗口）。
做法
工具结果在源头就精简（工具怎么设计）；旧的回执可以清掉或总结。系统的办法在站 05 上下文工程。
7在同一个调用上打转实测← ④ 机制 1
现象
⑤ 实测：第 3～9 轮连调 7 次 search_notes，每次结果一模一样，它还在调。
根源
状态机里没有“这一步刚做过”的记忆，判断全靠模型读历史；小模型尤其容易绕圈。
做法
记下做过的 (工具名, 参数)，重复时不执行，回一条 is_error：“这个调用第 2 轮已经做过，结果是……，请换个方向或给结论”。

第二圈 · 使用规范

  • 每轮记一行日志：轮次、stop_reason、调了什么、输入输出 token、耗时：防“出了事说不清它干了什么”。站 09 的可观测从这一行长出来。
  • 调模型、执行工具、守门写成三个函数：防循环体越写越长；审批、并行、沙箱以后都只改其中一个。
  • tools 和 system 整个循环里不变：防缓存失效（坑 3）。
  • max_tokens 给足：思考和调用单都吃输出额度，防坑 4；Claude 文档建议非流式请求给到约 16000。
  • 循环结束时保存完整 messages：防复盘时无据可查；它也是站 04 最后一页评测要读的东西。

第三圈 · 优化和深处

平方增长怎么压

三条路，按代价从小到大：① 缓存，重复的前缀按缓存价计费，不改变任何行为；② 精简工具结果，让每轮新增的那截变短；③ 清理旧回执（Claude 的 context editing 可以按阈值自动清掉早先的工具结果）或者压缩成摘要（compaction）。后两条会让模型“忘掉”东西，要用评测确认没变差。

思考也在循环里

开着思考的模型，每轮先写一段思考再决定调什么（本机 Qwen3 每轮 250～460 个输出 token，大半是思考）。Claude 的自适应思考会在工具调用之间穿插思考；它的思考块要原样放回历史，否则推理接不上。

实验台：转 N 轮，一共发出多少输入？

先猜：其他条件不变，转 10 轮的总输入 token，是转 5 轮的几倍？

估算模型：第 k 轮输入 = 固定部分 + (k−1) × 每轮新增。带缓存时，每轮的前缀（上一轮发过的全部）按缓存读价，新增的部分按缓存写价（输入价的 1.25 倍，5 分钟缓存）。价格按 2026-11 官方价：Sonnet 5.5 输入 $2 / 百万、缓存读 $0.10；Opus 5.5 输入 $4、缓存读 $0.20。只算输入，不算输出；前缀短于模型的最小缓存长度（512～4096 token，因模型而异）时实际不会缓存。

下一圈

  • 停下来的三道闸怎么定数（停止条件）。
  • 一轮里同时执行几个工具（并行工具调用）。
  • 循环写盘、断点续跑：进程挂了从第 k 轮接着来。
  • Message Threads（Claude 的 beta 功能）：服务端短时间记住对话，后续请求只发新消息，请求变小、首字更快。

自测

1. 用一句话说出这一页的精华

agent 循环就是把一来一回放进 while：模型说要工具就继续，说完了（end_turn）就停，但一定要有你给的上限，因为“继续”是模型决定的。

2. 写死 2 轮有什么问题？

该停的时候停不下（多花钱），该继续的时候被截断（全景那次要 5 轮）。

3. 为什么普通 while 可以不加上限，agent 循环必须加？

普通 while 的条件是你的代码，能推出它会结束；agent 的继续条件来自模型输出，没法证明它会变成 end_turn。

从 ④ 机制 1 推出。

4. 预测：每轮新增 400 token，固定部分 792，转 20 轮，总输入大约多少？

20 × 792 + 400 × (0+1+…+19) = 15840 + 76000 ≈ 9.2 万 token；最后一轮自己只有约 8400。轮数翻倍，总量约变成 3～4 倍。

从 ④ 机制 2 推出：总量随轮数平方增长。

5. 预测：第 3 轮模型回了 stop_reason: "max_tokens"，⑤ 的代码会怎样？

走“异常结束”分支返回，不会执行半截的调用单，也不会把半截话当结论。只写 if != tool_use: return text 的版本会把半截话交给用户。

6. 放回全景：第 8 站守门只有步数上限，第 6 站的 search_logs 每次要 20 秒，会怎样？
