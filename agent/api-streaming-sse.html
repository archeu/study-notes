流式输出：SSE 一边生成一边推

打开 stream，Claude 的回答就变成一串 SSE 事件：先 message_start，再每写一段推一个 content_block_delta，最后 message_delta 带上 stop_reason 和用量、message_stop 收尾。流式不会让模型写得更快，只让第一个字更早到：实测同样 74 个 token，非流式 2.84 秒后一次到，流式 0.06 秒就出第一个字、2.86 秒收完。代价是错误也可能在流到一半时才来，而那时 HTTP 状态码早已是 200。

①为什么需要：诊断报告写一分钟，用户不能盯一分钟白屏

在全景第 7 站，这一步要解决：模型在第 6 站一圈写一个 token，值班助手和页面要能“写一点收一点”。分诊结果只有几十个 token，等一等无所谓；可故障诊断、复盘报告动辄几千 token，Claude 也要写几十秒，再加上思考（Opus 5.5 关不掉），不流式的话，用户面对的是一段很长的空白，HTTP 客户端和网关还可能先超时。

②没有它会怎样：非流式调用

要求非流式 messages.create()流式 messages.stream()
用户早点看到东西不能：首字时间 = 总时间（实测 2.84 s）能：实测 0.06 s
长输出不撞超时难：几千 token 的请求一挂几十秒，HTTP 超时、网关超时谁先到算谁；按 SDK 文档，max_tokens 很大时 SDK 会要求你用流式能：字节一直在流，连接不会因为“没数据”被掐
能中途停不能：要么等完，要么整个丢掉能：用户关页面就停止读取
代码简单能：一个返回值多一层事件处理；SDK 的 get_final_message() 能把流拼回同一个 Message
出错一定在开头报能：HTTP 状态码就是结果不能：可能先 200、流到一半才来一个 error 事件（⑤ 实测）
不懂精华时的典型误用：以为开了流式“模型会更快”，用它来优化总耗时；或者只在后端开流式，然后在后端把全部事件攒齐再一次性返回给前端，用户看到的仍是白屏。流式要一路通到用户眼前。

③相邻方案：几种接流的写法

写法拿到什么适合
with client.messages.stream(...) as s: for t in s.text_stream只有文字增量边收边显示的大多数场景
for ev in s每个事件（含工具调用、思考增量）要处理思考块、工具参数流的 agent
s.get_final_message()拼好的完整 Message只想要流式的“不超时”，不需要边收边显示（Claude 的 SDK 指南推荐的默认写法）
messages.create(..., stream=True)原始事件迭代器，自己拼要完全控制、或者转发原始事件

本页学 messages.stream()：它在原始事件上帮你维护“当前拼好的消息”，既能边收边用，又能在最后拿到完整的 Message。

④原理：一条 Message 被拆成一串事件，客户端再拼回来

先知道这些
  • SSE 格式和分块传输：event: / data: / 空行；每层都不能攒（补给页）。
  • Message 的结构：content 是块数组，最后有 stop_reason 和 usage（Messages API ④）。

机制 1 · 事件顺序：外层是消息，里层是一个个内容块

机制 2 · 拼回去：SDK 维护一份“当前快照”

messages.stream() 每收到一个事件就更新手里的 Message：message_start 建骨架，content_block_start 加一个空块，每个 delta 往对应块里追加字，message_delta 填上 stop_reason 和用量。流结束时 get_final_message() 返回的，和非流式调用拿到的是同一种对象。Python SDK 还会为每个文字增量额外合成一个 text 事件（实测 54 个 delta 对应 54 个 text），那是 SDK 的便利，不是服务端发的。

机制 3 · 中途出错：状态码早就是 200 了

流式响应一开头就要发出状态行和响应头（200、text/event-stream），之后才开始推内容。如果服务端在第 30 秒过载，它已经没法把状态码改成 529，只能在流里发一个 event: error。实测 官方 Python SDK 遇到它会抛 APIStatusError，但 status_code 是 200，而且不会自动重试（SDK 的自动重试只发生在拿到响应之前）。已经收到的那几段文字还在你手里，要你决定扔掉还是接着用。

为什么这样设计：为什么拆成这么多种事件

分层的事件：消息 / 内容块 / 增量

  • 一个回答里可以有好几块不同类型的内容（思考、文字、工具调用），各自开始、增长、结束，客户端能分别处理：思考显示进度，文字直接渲染，工具参数攒齐再执行。
  • 用量和停因到最后才知道，放在单独的 message_delta 里，不用等。
  • 代价：客户端要维护状态、按 index 拼；所以 SDK 都提供了“拼好的快照”。

每个事件就是“新的一小段文字”

  • 最简单，前端直接追加。
  • 分不清这段是思考、回答还是工具参数；停因和用量也没地方放；工具调用一多就乱。
决定胜负的约束：模型的输出不只是一段文字，还有思考和工具调用（站 04 的主角），而且它们要在“写的过程中”就被区分开。事件按“消息 → 内容块 → 增量”分层，正好对上 Message 的结构。

最少的语法

⑤亲眼看到：首字时间、事件清点、流到一半出错

前两个实验连本机 llama-server（它实现了 Claude 的流式格式）；第三个连一个 80 行的“假 Claude”（fake_server.py，只用标准库），它推完 3 段文字后发一个 overloaded_error：真服务很难按需复现这种情况。

⑤main.py（对比首字时间）完整代码 →
t0 = time.perf_counter()
m = c.messages.create(model=MODEL, max_tokens=200, system=SYSTEM, messages=ASK, extra_body=EXTRA)
print("非流式", time.perf_counter() - t0)                # 首字时间 = 总时间

t0, first = time.perf_counter(), None
with c.messages.stream(model=MODEL, max_tokens=200, system=SYSTEM, messages=ASK, extra_body=EXTRA) as s:
    for text in s.text_stream:
        if first is None: first = time.perf_counter() - t0
    final = s.get_final_message()
# EXTRA = {"temperature": 0}：本机服务默认 0.8，两次输出不同就没法比；SDK 2.x 没有 temperature 参数

读出来的结论
  • 流式不省总时间：2.84 秒对 2.86 秒，几乎一样；省的是等第一个字的 2.78 秒。
  • 事件就是那几种：一头一尾各一个消息级事件，中间一个块的 start / 54 个 delta / stop，停因和输出用量在 message_delta 里（这次是 max_tokens，因为只给了 60）。
  • 中途出错不重试：设了 max_retries=2，SDK 照样直接抛错，状态码 200；已收到的“是，GC 导致的。”是半截话。要不要重试、要不要把这半截展示给用户，都得你的代码决定。
到这里已经能交差了：你能用 SDK 流式调用、边收边推、最后拿到完整 Message，并知道流中途出错长什么样。
已知还没处理的细节：后端攒齐再返回（坑 1），中途出错的半截内容（坑 2），用户走了模型还在写（坑 3），工具参数按 delta 解析（坑 4）。

⑥细节：把流一路送到用户眼前

第一圈 · 注意事项

1后端流式收，再一次性返回给前端← ④ 机制 2
现象
后端日志里字一个个来，页面上还是憋一阵再整段出现。
根源
后端用了 get_final_message() 再返回 JSON；或者转发时中间层在攒（补给页的缓冲问题）。
做法
后端接口本身也做成 SSE（FastAPI 的 StreamingResponse、Spring 的 SseEmitter），每收到一段文字就转发一段并 flush；关掉这条路由的代理缓冲。
2流到一半出错，半截内容当成完整结果实测← ④ 机制 3
现象
页面上显示了“是，GC 导致的。”就没了下文；或者重试后前端出现两遍开头。
根源
错误以 error 事件到来，HTTP 已是 200，SDK 不自动重试；已推给前端的内容收不回来。
做法
前端区分“生成中 / 完成 / 失败”三种状态，失败时明确提示；重试时先清空已显示的内容再重新流；只有收到 message_stop 且停因正常，才把结果落库。
3用户关了页面，模型还在写← ④ 机制 1
现象
用户点了“停止”或关掉标签页，后端仍把整段读完，日志和账单上都有这次的满额输出。
根源
前端断开只影响“后端到浏览器”那一段；后端到模型的那条流，要你自己关。
做法
后端检测到前端断开，就退出 with ... stream() 块（关掉上游连接）。已经生成的 token 怎么计费，以 Claude 文档为准；至少不要再继续读、继续转发。
4按 delta 解析工具参数或 JSON 结果← ④ 机制 1
现象
每来一个 input_json_delta 就 json.loads，频繁报解析错误。
根源
增量是 JSON 字符串的片段，不是一个个完整的 JSON。
做法
先累积，等这个块的 content_block_stop 再解析；或者直接用 get_final_message() 里拼好的 tool_use.input（站 04）。

第二圈 · 使用规范

  • 长输出、开思考、大 max_tokens 一律流式：哪怕最后只要 get_final_message()，也能避开 HTTP 超时。防的是长请求被掐断后重跑。
  • 记两个时间：首字时间和总时间分别进监控；用户体验看前者，成本和容量看后者。
  • 落库只认完整消息：收到 message_stop、检查过停因之后再存。防坑 2。
  • 转发时带上类型：思考摘要、文字、工具状态用不同的事件名转给前端，前端分别渲染。

第三圈 · 更深一层

首字时间由什么决定

排队 + 读输入（预填充）+ 思考。站 02 实测读 455 个 token 要 9.5 秒（本机），命中缓存降到 0.07 秒；开着思考时，第一个“文字”要等思考写完。所以首字时间的优化手段是：短提示、提示缓存、低 effort。

思考块的流

开着思考时，先来 thinking 块的增量；按 Claude 文档，新模型默认不返回思考内容（display: "omitted"），流里先来的是“空”的思考块，看起来像卡住了。要给用户看进度，可以要摘要（display: "summarized"）。

实验台：首字时间和超时

先猜：一份 3000 token 的诊断报告，每秒写 50 个，首字前要读输入 2 秒。网关的读超时是 60 秒。非流式会怎样？

简化模型：非流式在“首字前等待 + 输出 ÷ 速度”之后一次返回，期间连接上没有字节；流式第一个字之后持续有字节。思考时若不返回内容，流里也可能长时间只有心跳。除 26 个/秒（本机实测）外，速度都是为了算账假设的。

自测

1. 用一句话说出这一页的精华

流式把一条 Message 拆成“消息开始 → 每个内容块的 start / delta / stop → 停因和用量 → 结束”一串 SSE 事件，让第一个字早到、长输出不超时，但不缩短总时间，错误也可能在 200 之后才来。

2. 为什么 stop_reason 和输出用量在最后的 message_delta 里？

它们要等生成结束才知道；放在单独的事件里，前面的内容可以照常先推。

从 ④ 机制 1 推出

3. 为什么流到一半的错误状态码是 200？

流式响应一开始就把状态行和头发出去了，之后只能在正文里用 error 事件报错。

从 ④ 机制 3 推出，⑤ 实测

4. 预测：开流式后，同一个请求的账单会变吗？

不会。流式只改变传输方式，输入和输出 token 数一样（⑤ 实测两种都是 74 个输出）。只有用户中途停止、你关掉流的情况下，输出才可能少。

从 ④ 机制 2 推出

5. 预测：开着思考（display 默认 omitted）的 Opus 5.5，流式时用户会先看到什么？

先是一段没有文字的空白：最先到的是思考块的事件，内容为空；等思考写完，文字块才开始流。要缓解，就在界面上显示“正在分析”，或者要思考摘要、调低 effort。

从 ④ 机制 1 和第三圈推出

6. 放回全景：第 7 站前后是什么？如果第 7 站换成非流式，诊断报告写了 90 秒，链路会怎样？

之前是第 6 站模型生成，之后是第 8 站收齐。非流式时第 7 站 90 秒没有任何字节：若第 4 站的客户端超时或中间网关的读超时短于 90 秒，请求会被掐断，SDK 再重试一次（从头生成，钱花两遍），用户一直看着空白；就算没超时，首字时间也从几秒变成 90 秒。

档位：标准。本机跑过（2026-11-22，2 核 ARM，官方 anthropic Python SDK 2.12.0，llama.cpp b12618 的 /v1/messages，Qwen2.5-0.5B-Instruct Q4_K_M，Python 3.13）：流式和非流式的首字时间与总时间、事件清点、流中途 overloaded_error 时 SDK 抛 APIStatusError（status 200）且不重试（这个用的是本页的假服务）。按文档（Claude API，2026-11）：事件类型和顺序、ping 和 error 事件、thinking_delta 和 input_json_delta、思考默认不显示、大 max_tokens 要用流式。
