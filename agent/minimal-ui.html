最小交互界面：流式输出、反馈按钮、转人工

值班的人不用终端，他们要的是一个页面：看得见每个事件跑到哪一步，报告一段段地出来，觉得不对能点一下，觉得不行能一键转给人。精华是三条：用 SSE 一条条推，带 id，断了能接上；“开始调查”必须幂等，刷新和双击都不能再起一次；反馈要连同报告和理由一起存，才能变成评测用例。再加一条底线：模型的输出只当文字显示，不当 HTML。

①为什么学：87 个事件，值班的人要一眼看清

在全景第 ⑨ 站，这一步要解决：大促夜里值班的人同时盯着 87 个事件。他要知道哪个在查、查到第几轮；点进一个，报告最好边写边看；报告不对，要能说一句“不对、为什么”；觉得 agent 搞不定，要一键把它交给人，而且接手的人不用从头查。

②老办法：群里发一段长文字，或者页面每两秒刷一次

  • 报告查完发到值班群：87 个事件就是 87 段长文字刷屏；查的过程中什么都看不到，只能干等一分钟，以为它卡住了。
  • 页面每 2 秒轮询一次进度：87 个事件 × 每个人开的标签页，后端被一堆“没变化”的请求打着；报告要么整篇出来，要么自己切段拼。
  • 没有反馈入口：报告错了，值班的人在群里骂一句就过去了，这句话永远进不了评测集，同样的错下次还犯。
  • 没有转人工：agent 查不出来，值班的人要自己重新打开日志、从头查，前面 4 轮查到的东西全浪费。
  • 换成这一页的做法：进度和报告用 SSE 推，一个事件一条连接；👎 带理由存成评测用例候选；转人工把已有的证据一起交过去。
不懂精华时的典型误用：把“开始调查”挂在打开详情页的 GET 上。值班的人一刷新，就又起了一次调查，花双份额度，两份报告还交错着推到页面上（⑤ 的第一版就是这么坏的）。

③选谁：怎么推，用什么写页面

推送方式方向断线要什么
SSE（Server-Sent Events）服务器 → 浏览器，单向浏览器自己重连，并带上最后收到的 id普通 HTTP，浏览器自带 EventSource
WebSocket双向要自己写重连和续传网关、负载均衡要支持升级连接
轮询浏览器一次次问无所谓断线大部分请求白问；进度有延迟
页面用什么写适合代价
原生 HTML + JS（⑤）最小可用，看清每一步页面复杂了就难维护
Streamlit、Gradio、ChainlitPython 几十行出一个能用的界面，做内部工具、演示很快样式和交互受框架限制；多人同时用、接公司登录要另外做
公司自己的前端（React 等）长期产品，和别的系统放一起要前端的人
接进已有的值班平台（飞书、钉钉的消息卡片）值班的人本来就在那里卡片的交互有限，流式要靠不断更新卡片

本页学 SSE + 一个原生页面：进度和报告都是服务器往浏览器单向推，SSE 正好，而且自带“断线带着 id 重连”。页面先用原生 JS 写到能用，等值班的人真用起来、提了需求，再决定是做进公司的前端，还是接进值班平台的卡片。

④原理：一条连接、一串带 id 的事件

先知道这些
  • SSE 的格式：一个不结束的 HTTP 响应，Content-Type: text/event-stream，每个事件是几行 id:、event:、data:，空一行结束。站 03：SSE 流式。
  • 进度从哪来：worker 每轮往这个事件的进度流里追加一条（长任务架构 ④ 机制 5）。
  • 幂等：同一个操作做一次和做多次，结果一样。

机制 1 · SSE：浏览器自己重连，并且记得收到哪了

浏览器的 EventSource 打开一条长连接，服务器每有一条进度或一段报告就写一个事件。关键在 id：浏览器记住最后收到的 id，连接断了（网络抖一下、负载均衡切了一台）它会自己重连，并在请求头里带上 Last-Event-ID；服务器从这个 id 之后接着发。前提是服务器那边的事件是存着的、按 id 能续读的（⑤ 里每个事件一个列表，线上就是那条 Redis 进度流），只在内存里广播一下就接不上。下面这个小台子模拟同一份报告的三种收法。

实验台：断线以后，页面上是什么样

先猜：报告推到一半断线，浏览器重连时没有带 Last-Event-ID（服务器从头再发一遍），页面上的报告会怎样？

不流式：等整篇写完

SSE 流式

模拟：3 条进度 + 38 段报告（比 ⑤ 的报告短一点），节奏和 ⑤ 的假 agent 一样（进度每条 0.4 秒，报告每段 0.02 秒）；断线以后 0.5 秒重连。不是实测，⑤ 里有用真服务跑出来的数字。

机制 2 · “开始调查”必须幂等

看页面用 GET，开始调查用 POST，这是第一条。第二条是 POST 也会被重复：双击、网络超时后前端重试、刷新页面。光靠前端带一个幂等键还不够：刷新时如果键没存住（换了个新键），服务器就又起一次。⑤ 的第一版就栽在这里：它判断“这个事件是不是已经开始了”的依据是“有没有吐出过事件”，agent 还没吐出第一条的那 0.4 秒里刷新，又起了一次，进度变成 6 条，两份报告交错着推到页面。修法是服务器按事件的状态去重：同一个事件同一时间只允许一个调查，幂等键只是第一道。

机制 3 · 反馈要能变成一条评测用例

一个 👎 本身几乎没用：不知道哪里错、错的是哪一份报告。存下来的东西要够“重放”：事件 id、当时的报告全文、提示词版本（站 09 的 提示词版本）、谁投的、一句理由。⑤ 里只有写了理由的 👎 才导出成评测集候选，同一个人改票只算最后一次。按钮要尽量省事（一次点击），理由要尽量具体（一句话），这两者之间的平衡是这个界面最值得花心思的地方。

机制 4 · 转人工：交过去的是证据，不是一句“我不会”

转人工有两个入口：值班的人自己点；系统自动转（截止时间到了、模型的把握太低，见 可靠性 的降级菜单）。不管哪种，呼出去的消息里都要带上 agent 已经查到的东西：跑了几轮、调了哪些工具、拿到了什么、写到一半的结论。接手的人从第 4 轮接着查，而不是从第 1 轮。

机制 5 · 模型的输出只当文字

报告里会出现日志原文，日志里可能有别人写的一段 HTML，或者一个 Markdown 图片。前端如果用 innerHTML 或者把 Markdown 渲染成带图片的 HTML，前者能执行脚本，后者会让浏览器去请求一个外部地址，地址里可以拼着从报告里偷来的数据（这就是提示注入那页“危险三件套”里的“往外发的通道”）。⑤ 的页面一律用 textContent；真要渲染 Markdown，就过一遍白名单清洗，并且不加载外部图片。

为什么这样设计

SSE + 存着的事件流 + 幂等的开始

  • 断线、刷新、换标签页都不丢进度、不重复，因为“发过什么”存在服务器，id 由服务器给。
  • 一个事件一条长连接，没有轮询的空请求；普通 HTTP，网关不用特别配置升级连接。
  • 代价：要关掉代理的缓冲（Nginx 的 X-Accel-Buffering: no）；HTTP/1.1 下每个域名的连接数有上限，开很多标签页要上 HTTP/2。

前端轮询 + GET 里顺手开始

  • 写起来最快，不用懂 SSE。
  • 刷新就是一次新调查；进度有延迟；大部分请求白问。
  • 报告要么整篇等，要么自己切段拼，断了就不知道拼到哪。
决定胜负的约束：一次调查要几十秒、花真钱，而人会刷新、会双击、网络会断。所以“发过什么”和“有没有在查”都必须由服务器记着，页面只是一个随时可以重开的窗口。

Java 老朋友：SseEmitter

像：Spring MVC 的 SseEmitter、WebFlux 返回 Flux<ServerSentEvent>，就是 ⑤ 里 FastAPI 的 StreamingResponse；ServerSentEvent.builder().id(…) 给每条事件编号。

不像：SseEmitter 本身不帮你续传，读 Last-Event-ID 头、从存着的事件里接着发，要自己写；而且 Java 里一个请求通常一两秒就结束，这里一条连接要挂一分钟，线程模型（Servlet 线程会不会被占住）要提前想好。

⑤跑起来：一个 FastAPI 文件，一个 HTML 文件

app.py 是后端：事件列表、开始调查、SSE 流、反馈、转人工、导出评测集候选；报告由一个假 agent 按固定剧本一段段吐（里面故意混了一段 <img onerror> 和一个 Markdown 图片）。static/index.html 是页面，原生 JS。demo.py 用 httpx 当浏览器走一遍。

@app.post("/api/incidents/{inc}/start", status_code=202)
async def start(inc: str, idempotency_key: str = Header(...)):
    if idempotency_key in runs or inc in running:      # 幂等键 + 按事件状态去重
        return {"started": False, "reason": "already running"}
    runs[idempotency_key] = inc; running.add(inc)
    asyncio.get_running_loop().create_task(fake_agent(inc))
    return {"started": True}

@app.get("/api/incidents/{inc}/stream")
async def stream(inc: str, last_event_id: int = Header(0)):
    async def gen():
        sent = last_event_id                           # 浏览器重连时带回来的
        while True:
            for e in events[inc][sent:]:               # 事件是存着的，按 id 续读
                yield f"id: {e['id']}\nevent: {e['event']}\ndata: {e['data']}\n\n"
                sent = e["id"]
                if e["event"] == "done": return
            await asyncio.sleep(0.02)
    return StreamingResponse(gen(), media_type="text/event-stream",
                             headers={"X-Accel-Buffering": "no"})   # 别让 Nginx 攒着

  • 第一条进度 0.4 秒就到了：哪怕报告还要 2 秒多，值班的人也知道“它在查、查到哪了”。真实的调查一分钟，这个差别更大。

⑥细节

第一圈 · 注意事项

1刷新一下，又起了一次调查实测← ④ 机制 2
现象
进度条一会儿 3/4 一会儿 1/4，报告两份交错在一起，额度花了双份。
根源
开始调查挂在 GET 上；或者 POST 只靠前端的幂等键，刷新时键丢了。
做法
GET 只读；POST 带幂等键，服务器再按事件状态去重。
2用 innerHTML 显示报告← ④ 机制 5
现象
某个报告一打开，页面弹了个框；或者浏览器悄悄请求了一个陌生的图片地址。
根源
报告里有日志原文，日志里有别人写的 HTML 和 Markdown 图片。
做法
一律 textContent；要渲染 Markdown 就白名单清洗、不加载外部图片，再加一条严格的内容安全策略（CSP）。
3上了 Nginx 以后不“流”了← ④ 机制 1
现象
本地好好的，部署以后报告还是要等很久才一整篇出来。
根源
反向代理默认会攒着响应再发；有的还会压缩、按块缓冲。
做法
响应头 X-Accel-Buffering: no、Cache-Control: no-cache，或者在代理上对这个路径关掉缓冲；隔十几秒发一行注释（: ping）防止空闲连接被掐。
4开了几个标签页，后面的连不上← ④ 机制 1
现象
值班的人开了 7 个事件的详情页，第 7 个一直转圈。
根源
HTTP/1.1 下浏览器对同一个域名的并发连接有上限（通常 6 个），SSE 长连接会一直占着。
做法
上 HTTP/2（一条连接多路复用）；或者列表页只开一条 SSE，推所有事件的进度。
5反馈只有 👍👎，没有理由← ④ 机制 3
现象
一个月攒了几百个 👎，评测集一条也没长。
根源
不知道错在哪，没法变成“输入 → 期望”的用例。
做法
👎 之后给三个固定选项（结论错、证据不够、建议危险）再加一行可选的话；每周把这些整理进评测集（站 09）。
6反馈存得不够重放← ④ 机制 3
现象
拿到一条 👎，想复现，却不知道当时用的是哪个版本的提示词、模型看到了哪些日志。
根源
只存了“哪个事件、赞还是踩”。
做法
存事件 id、报告全文、提示词版本、模型别名和真模型、工具调用轨迹的引用（站 09 的 追踪）。
7转人工只发一句“请处理”← ④ 机制 4
现象
接手的人重新打开日志，从头查一遍，前面 4 轮白做。
根源
呼叫消息里没有 agent 的工作成果。
做法
带上每一轮调了什么、拿到了什么、写到一半的结论；附上详情页链接。
8只显示一个“处理中”← ④ 机制 1
现象
一分钟的转圈，值班的人以为卡死了，刷新、再刷新（然后撞上坑 1）。
根源
只推最终结果，不推过程。
做法
每一轮推一条进度（第几轮、调了什么工具）；报告边写边推。

第二圈 · 使用规范

  • 看用 GET，开始用 POST + 幂等键，服务器按状态去重：防刷新重复调查。
  • 每个 SSE 事件带 id，事件存在服务器能续读：防断线丢进度、重复。
  • 模型输出一律 textContent：防脚本执行和图片外传。
  • 👎 带理由和上下文存下来，每周进评测集：防反馈白收。
  • 转人工带证据：防接手的人从头查。
  • 页面上标出“降级报告”“已自动转人工”：防值班的人把粗报告当深查报告用。

第三圈 · 优化和深处

一条连接推所有事件

列表页每个事件开一条 SSE，87 个事件就是 87 条连接。改成列表页只开一条“所有事件的进度”流，详情页再开那个事件的报告流：连接数和服务端的压力都小一个数量级。

接进值班平台的卡片

值班的人本来就在飞书、钉钉的群里。把报告做成可更新的消息卡片：进度一更新，卡片改一次；卡片上放 👍 / 👎 / 转人工三个按钮，回调到同一套接口。流式不再是一个字一个字，而是一轮一轮。

开放提问以后

页面加一个输入框，让值班的人追问，就有了直接注入：问的人本身可能想越权。输入走同一个租户上下文（多租户），而且追问也要有截止时间和 token 预算。

无障碍和手机

报告区加 aria-live="polite"，读屏软件会念出新内容；手机上值班的人更多，列表要能单手点，报告字号不能太小。

自测

1. 用一句话说出这一页的精华

进度和报告用带 id 的 SSE 推、断了能接上；开始调查要幂等、由服务器按状态去重；反馈连同报告和理由一起存，才能变成评测用例；模型输出只当文字。

2. 群里发长文字、页面轮询，缺的是什么？

看不到过程、刷屏或白请求；没有反馈入口，错的报告进不了评测集；没有转人工，接手的人要从头查。

3. 浏览器断线重连时，为什么报告不会重复？

每个事件带 id，浏览器记住最后收到的那个，重连时放进 Last-Event-ID 头；服务器的事件是存着的，从这个 id 之后接着发。

从 ④ 机制 1 推出。

4. 预测：服务器只在内存里广播事件、不存，值班的人在报告推到一半时刷新页面，会看到什么？

刷新后新开的连接只能收到“此刻以后”的事件：进度条从中间开始，报告缺了前半段；如果开始调查还挂在 GET 上，又会起一次新调查。

从 ④ 机制 1、2 推出。

5. 预测：前端带幂等键，但键存在 JS 变量里而不是 sessionStorage，服务器只按键去重，刷新会怎样？

刷新后 JS 变量没了，前端生成一个新键，服务器认不出是同一次，又起一个调查：⑤ 第一版的 bug 就是这样。所以服务器要按事件状态再去重一次。

从 ④ 机制 2 推出。

6. 放回全景：第 ⑨ 站前后是什么？如果第 ⑨ 站的反馈按钮一个月没人点，第 ⑩ 站和站 09 的评测会怎样？

前面是第 ⑧ 站过完护栏的报告，后面是第 ⑩ 站的看板。没人点：看板上“报告有用率”这一项是空的，只剩成本和耗时；站 09 的评测集长不出新用例，线上出了新的错法也发现不了。所以按钮要省事，理由要尽量引导。
