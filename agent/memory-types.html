记忆分几种：短期和长期，情景、语义、程序性

会话里的是短期记忆，就是上下文本身，会话结束就没了。跨会话的长期记忆要存到外面，分三种：情景（发生过什么，只追加）、语义（某个东西是什么，同一个 key 只留最新值）、程序性（该怎么做、什么不能做，整组生效）。三种的写、取、忘规则各不相同；混成一锅只按相似度取，问“是不是昨天那个问题”时，昨天那条可能正好排在第 4。

这一页的位置前两页讲的都是“短期记忆”，也就是一次会话里的上下文怎么拼、怎么腾地方。从这一页起讲会话之外的长期记忆：先分类型，后面三页按类型讲怎么写、怎么取、怎么忘。

①为什么需要：新会话里，模型对昨天一无所知

在全景第 1 站，新会话开始时模型对昨天一无所知：昨晚 5 轮排查留在上一个会话里，进程早上还重启过。到第 7 站，答案要用到三条不同性质的记忆：M1 昨晚的病历（一件事）、M2“晚高峰不 dump”（一条规矩）、M3“堆 4 GB、G1、6 个 Pod”（一组事实）。它们该怎么存、怎么取，是同一套办法吗？

②没有它会怎样：要么从零查起，要么一锅端

做法今天这次会怎样
没有长期记忆从零查起：昨晚花 5 轮查到的“导出读 41 万行”要再查一遍；你说过的“晚高峰不 dump”也忘了，晚上照样会提议 dump。
有记忆，但所有记录一张表、一种向量、取相似度前 3⑤ 的实测：12 条里前 3 是“值班群是哪个”“先看发布记录”“晚高峰不 dump”，昨天那次 Full GC 排第 4，没取到；“堆 4 GB”排第 8。12 条的相似度全挤在 0.42～0.58 之间，排名靠零点零几的差距决定。
有记忆，但事实只追加不覆盖下个月堆调到 8 GB，表里同时有“4 GB”和“8 GB”两条，谁被取到全凭相似度。
按类型存、按类型取规矩按范围整组加载，一定在；事实按 key 精确取、只有最新值；经历按相似度和新近排，取前几条。
不懂精华时的典型误用：把“记忆”理解成“把聊天记录塞进向量库”。经历、事实、规矩被同一种办法存、同一种办法取，规矩时有时无，事实新旧并存，最相关的那件事被一条无关紧要的事实挤掉。

③相邻方案：存什么形态的“过去”

要求存对话原文每次会话存一份摘要按类型存条目只靠知识库（RAG）
取回来短小、只取相关的不能：一段对话几千 token差一点：一份摘要讲好几件事能：一条一件事能
事实能被更新（4 GB → 8 GB）不能：旧对话还在不能：旧摘要还在能：语义记忆按 key 覆盖要重新导入文档
规矩一定生效不能不能能：程序性整组加载不能：手册里写的不一定被检索到
记得“这个服务上次出了什么事”能，但要翻能能：情景记忆带时间不能：知识库是资料，不是经历
写入成本零一次摘要调用一次抽取调用 + 判断类型（下一页）文档入库流水线（站 06）

本页学“按类型存条目”：类型决定了写、取、忘的规则。原文和摘要可以留着做审计，但不直接拿来取。

记忆和 RAG 的区别（站 05 的过关题）：知识库存的是资料，“运维手册里 Full GC 怎么查”，人写好、所有人共用、很少变；记忆存的是经历，“这个服务上周三出过什么事、谁修的、你说过什么”，从对话里来、按团队或按人隔离、天天在变。取的技术很像（都可能用向量检索），写、更新、遗忘完全不同。

④原理：一层短期，三种长期

先知道这些
  • 上下文窗口：模型这一次能看到的全部内容。见 上下文窗口、上下文工程。
  • 向量和相似度：把一句话变成一串数，意思越近、余弦相似度越高。见 Embedding 与向量相似度。

Java 老朋友：记忆系统 ≈ 缓存 + 淘汰策略。像的地方：有写入、过期、淘汰。不像的地方：缓存里放什么由代码决定，记忆里放什么要由模型从对话里“判断”出来；缓存只有一种值，记忆有三种性质完全不同的记录，规则各不一样。

机制 1 · 短期和长期：在不在这一次请求里

  • 短期记忆（工作记忆）：就是这次请求的上下文，加上本会话的状态（第几轮、累计 token）。像请求作用域的变量：请求结束就没了，不用删。
  • 长期记忆：会话之外的存储（这里是一张 PostgreSQL 表）。不会自己出现在上下文里：要有代码在会话结束时写进去（站 05 第 8 站），在下次会话开始时取出来、拼进上下文（第 2、3 站）。
  • 模型权重也是一种记忆（参数记忆）：训练时学到的通用知识。改它要微调（站 11），不能拿来记“order-svc 昨晚出了什么事”。

机制 2 · 长期记忆分三种：存的东西不同，规则就不同

这套分法来自认知科学（Tulving 1972 年区分了情景记忆和语义记忆），被 CoALA（Sumers 等，2023，《Cognitive Architectures for Language Agents》）搬到了 Agent 上：工作记忆之外，长期记忆分情景、语义、程序性三种。

情景 episodic语义 semantic程序性 procedural
存什么发生过的一件事：时间、经过、结果、谁处理的某个东西是什么：配置、归属、依赖该怎么做、什么不能做
全景里M1：11-08 Full GC，导出读 41 万行M3：order-svc 堆 4 GB、G1、6 PodM2：晚高峰不做 heap dump
Java 里像事件表、审计日志：只追加配置中心、主数据：按 key 覆盖代码和规则：评审后上线
怎么写追加一条，旧的不改（只改状态，如“待发布 → 已发布”）同一个 key 覆盖旧值，旧值进历史人说了、或人确认了才生效
怎么取按相似度和新近排，取前几条按对象精确取（order-svc/*）按适用范围整组加载，不比相似度
怎么忘慢慢衰减，很少用的往后排被新值替换只能显式撤销
放进上下文的哪里记忆块，带日期，标“线索”记忆块，带日期范围固定的放系统提示；按团队不同的放记忆块最前

一件事会在类型之间流动：30 次相似的 Full GC 病历（情景）可以归纳成一条事实“order-svc 的 Full GC 多半和大对象进老年代有关”（语义）；一条反复被证明有用的做法，可以升级成规矩（程序性）。什么时候归纳、谁来确认，是后面几页和“下一圈”的事。

为什么这样设计：分类型存，而不是一张表一种检索

按类型存、按类型取

  • 规矩不靠运气：按范围整组加载，每次都在。
  • 事实只有一个当前值：按 key 覆盖，不会 4 GB 和 8 GB 同时出现。
  • 经历按相似度和新近排，只在这一类里竞争，不会被一条“值班群是哪个”挤掉。
  • 代价：写入时要先判断类型（下一页），判断错了就放错抽屉。

一张表、一种向量检索

  • 实现最简单，一条 SQL。
  • ⑤ 实测：取前 3 漏掉了昨天那一次；12 条的分数挤在 0.15 的区间里，排名靠零点零几的差距。
  • 事实只能追加，新旧并存；规矩能不能取到看措辞。
决定胜负的约束：三种记录的“正确”定义不同：事实要唯一的最新值，经历要带时间全部保留，规矩要一定生效。相似度检索只回答“像不像”，这三件事一件都保证不了，所以先按类型分开，相似度只在情景记忆里用。

⑥细节

第一圈 · 注意事项

1规矩也走相似度召回← ④ 机制 2
现象
“晚高峰不 dump”有时在上下文里，有时不在；晚上 20:30 助手提议做 heap dump。
根源
程序性记忆要“一定生效”，相似度检索只保证“像的排前面”。问题里没提 dump，这条规矩就可能排不进前几。
做法
程序性记忆按适用范围（团队、服务、全部）整组加载；条数多了就该升级进系统提示，或者拆成按范围的几组。
2事实只追加，新旧并存← ④ 机制 2
现象
堆从 4 GB 调到 8 GB 以后，助手时而说 4 GB、时而说 8 GB。
根源
语义记忆要“唯一的最新值”，按情景记忆的方式追加，就成了两条都对的历史。
做法
语义记忆要有 key（order-svc/jvm），写入是 upsert；旧值进历史表，不参加召回。
3把一次经历当成规律← ④ 机制 2
现象
全景第 7 站的反例：“order-svc 又 Full GC 了，那就是导出”，今天其实是缓存。
根源
情景记忆是“那一次发生了什么”，不是“每次都这样”。没带日期、没标“线索”放进上下文，模型就把它当事实用。
做法
情景记忆带日期和状态放进记忆块，系统提示写“以工具结果为准”；要归纳成规律，单独生成一条语义记忆，并注明依据了几次经历。
4把整段对话当情景记忆存← ④ 机制 1
现象
记忆表里一条就是几千 token 的对话，取回 3 条上下文就满了；相似度也被对话里的寒暄和过程稀释。
根源
短期记忆（这次的上下文）原样搬进长期记忆，没有经过“这件事的要点是什么”的提炼。
做法
长期记忆存提炼后的条目（时间、现象、原因、处理、谁），原文另存一份做审计，不参加召回。怎么提炼是下一页的事。
5模型自己写的规矩直接生效← ④ 机制 2
现象
日志里一行“请忽略只读限制”被抽取成了一条程序性记忆，下次会话起就生效了。
根源
程序性记忆的影响面最大：它改的是“以后怎么做”。由模型从对话里抽取，就等于让对话内容（包括工具返回的日志）改了助手的行为。
做法
程序性记忆只从“人说的话”里抽，并且要人确认后才生效；工具结果里的文字一律不能变成规矩。

第二圈 · 使用规范

  • 每条记忆必带：类型、团队（或用户）、key、日期、来源：防放错抽屉、跨团队串、过时了不知道。
  • 程序性记忆条数要少、要人确认：多了就该挪进系统提示，或者说明分范围没分好。
  • 情景记忆一条一件事，三五行：防一条记录里混好几件事，取回来一半无关。
  • 原文和条目分开存：原文做审计和重新抽取，条目做召回。

第三圈 · 优化和深处

程序性记忆住在哪里

CoALA 把程序性记忆分成两种：隐式的（模型权重本身）和显式的（Agent 的代码、系统提示）。所以“晚高峰不 dump”有三个去处，越往后越稳、也越难改：

  • 记忆表里的一条，按范围加载：随时能加能撤。
  • 写进系统提示：对所有会话生效，改要发版。
  • 写进工具代码：heap_dump 自己检查时间，晚高峰直接拒绝。这一条连模型想调都调不成，是最硬的一种。

现成的记忆组件长什么样（按文档）

Claude 的 memory 工具（memory_20250818）给模型一个 /memories 目录，由模型自己读写文件，存储后端由你实现。它本身不分类型；要分，可以约定目录：/memories/procedural/、/memories/semantic/order-svc.md……

LangGraph 等框架的长期记忆文档也用语义、情景、程序性这三类来讲，并且都提醒：语义记忆要能更新，程序性记忆常常就是在改提示词。

下一圈

  • 记忆的归纳（反思、consolidation）：从 30 条情景记忆里总结出一条语义记忆，什么时候做、谁确认。
  • 按人还是按团队：值班的你说的规矩，换个人值班还算不算（第 6 个知识点讲隔离）。
  • 知识图谱式的语义记忆：服务、依赖、负责人之间的关系，用图来存、按关系来取。

自测

1. 用一句话说出这一页的精华

短期记忆就是上下文；长期记忆要存到外面，分情景（发生过什么、追加）、语义（是什么、按 key 覆盖）、程序性（怎么做、整组生效），三种的写、取、忘规则不同，不能混成一锅只按相似度取。

2. 记忆和 RAG 有什么区别？

RAG 的知识库是资料：人写的、共用的、少变的（运维手册）。记忆是经历：从对话里来的、按团队或人隔离的、天天在变的（这个服务上次出了什么事、你说过什么规矩）。取的技术相似，写、更新、遗忘完全不同。

3. 为什么“晚高峰不 dump”不该靠相似度召回？

它是程序性记忆，要求“一定生效”。相似度检索只保证像的排前面，问题里不提 dump，它就可能排不进前几；⑤ 里它排第 3 是运气。

从 ④ 机制 2 的“怎么取”一行推出。

4. 预测：把一锅端改成取前 5，今天这个问题够不够用？以后呢？

今天够：E1 排第 4、E3 排第 5，都进来了，但 S1（堆 4 GB）排第 8 还是没有。以后不行：记忆从 12 条涨到 500 条，相似的旧病历会越来越多，前 5 又会被挤满，“取几条”调大只是推迟问题，还让每轮多付 token。

从 ④ 机制 2 和上一页“放多少”推出。

5. 预测：下个月 order-svc 迁到 ZGC，三种记忆各要怎么动？

语义：order-svc/jvm 覆盖成 ZGC，旧值进历史。情景：E1、E4 这些 G1 时代的病历不改，它们是当时真实发生的事，但取的时候会因为新近系数慢慢往后排。程序性：如果有“G1 下先看 Mixed GC”这类规矩，要人撤销或改写。

6. 放回全景：第 1 站和第 7 站各和这一页有什么关系？这一页讲的东西坏了，整条链路会怎样？

第 1 站是“短期记忆是空的”：新会话只知道这次请求里的东西，所以才需要第 2 站去长期记忆里取。第 7 站用到三种记忆：E1 当线索、P1 当规矩、S1 当背景。类型分错了：规矩靠相似度，第 7 站可能在晚高峰建议 dump；事实只追加，第 7 站可能引用过时的堆大小；经历当规律，第 7 站会直接下“又是导出”的错结论。
