知识库运维：增量同步、权限、版本

知识库不是建一次就完事：每天都有新手册、改错字、出新版、换团队、删文件。运维的核心是认清三个身份：文件（哈希没变就跳过）、文档（按“名字 + 版本号”认，不按路径认）、片（按“标题路径 + 正文”的哈希认，没变就不重算向量）。再给每片一个状态：现行、下线、删除，检索只查现行；权限是一列，改权限只改这一列。实测：加一份新手册 1.9 秒就能查到，改一处只重算 1 片向量，同样的库全量重建要 53 秒。

这一页的位置站 06 第 8 个知识点。前面几页都假设资料是静止的；这一页让它动起来，并交付这一站的第二条过关条件：“加一份新手册，不重建索引就能查到”。Java 里的同一件事是 MySQL 到 ES 的同步：增量 ≈ binlog，全量 ≈ 重新导一遍。

①为什么学：知识库每天都在变

在全景第 1 站，同步任务要回答：这次上传的东西，哪些是新的、哪些变了、哪些不该再被查到、谁能看。下面是实测里“一天”的 8 次变更，每次跑一遍同步：

加一份新手册1.9 秒3 片入库，HNSW 不重建，马上能查到
手册改一处1 / 17 片只重算变了的那一片
改权限0 片只改 team 这一列
全量重建53 秒49 片全部重算；资料多了是小时级

②老办法：每晚全量重建

最省心的做法：每天夜里把目录里的文件全部重新解析、切块、算向量，换掉旧库。Java 里就像每晚把 MySQL 整表重新导进 Elasticsearch。

  • 简单，永远和目录一致：删掉的文件第二天自然消失，不会有残留。
  • 慢，而且和库的总量成正比：这里 7 个文件 53 秒；几百份手册、几十页扫描件，一夜都跑不完（OCR 一页 3 秒、向量一片 1 秒）。
  • 白天上传的手册要等到明天才查得到：这一站的过关条件“不重建索引就能查到”直接不满足。
  • 改一个错字也要全部重算，改一个团队权限也要等一夜；而权限收回慢一天，就是一天的泄露窗口。
  • 反过来只做“追加”（新文件来了就加，从不删除、从不下线）：旧版本和删掉的文件永远留在库里，第 7 站的旧版问题就是这么来的。
不懂精华时的典型误用：用文件路径当文档的身份。文件挪了个目录（比如为了改权限），同步程序以为是“删了一份、新加了一份”，全部重算向量，还可能把同一份内容标成删除。本页代码最初的设计就是这样，写完复查时才发现（⑥ 坑 1）。

③选谁：五种同步方式

评判要求：新文件多久能查到；改一处要花多少；删除和下线干不干净；改权限要不要重算；换 Embedding 模型时怎么办。

要求每晚全量重建文件级增量
文件哈希变了就整份重做		片级增量
片哈希没变就复用向量		事件驱动
上传、编辑时推送变更		蓝绿两套库
新库建好再切
新文件多久可查最长一天下一次扫描下一次扫描（实测 1.9 秒）几秒新库建完才行
改一处的成本全库重算整份文档重算（17 片）只算变了的片（1 片）看配合哪种全库重算
删除、下线自然干净要比对“目录里没了的”要比对，并用状态字段软删收到删除事件才删，丢事件就残留新库里本来就没有
改权限等一夜能：只改元数据能：只改 team 列（实测 0 片）能，最快等新库
换 Embedding 模型能，就是全量不能：新旧向量混在一起不能：同上不能：同上能：新库用新模型，评测过了再切
值班助手怎么选只做每周的“对账”—选：日常同步以后接 Confluence、Git 的变更通知换模型时用

本页学片级增量同步 + 状态字段 + 权限列：日常变更都只碰变了的部分；换 Embedding 模型这种“全部向量作废”的事，用蓝绿两套库；再定期全量对账一次，兜住漏掉的变更。

④原理：三层身份、三种状态、一列权限

先知道这些
  • 内容哈希：把一段内容算成一个短串（这里取 sha256 的前 16 位），内容一样哈希就一样，改一个字就完全不同。Java 里的 ETag、Maven 依赖的校验和都是它。
  • 软删除：不真删行，而是把 status 改掉，查询时带上 WHERE status = 'current'。
  • HNSW 可以一条条插入：新片插进图里就能被查到，不用重建索引；删除的点要等 VACUUM 才真正清掉（HNSW 页）。

机制 1 · 三层身份：文件、文档、片，每层都能跳过

文档按名字 + 版本号认，而不是按路径：挪目录（改权限）时内容一样、身份一样，只改一列；同一个名字出了新版本号，才是“新版本”。

机制 2 · 三种状态：现行、下线、删除

机制 3 · 权限：一列 team，过滤在检索之前

每片带一个 team（这里取自团队目录名，public 表示所有人可见）。检索时 WHERE team = ANY(用户所在团队 + public)，团队来自登录身份。改权限 = 改这一列，向量不用动。实测：

谁问手册在哪个团队“inventory-svc 怎么回滚？”的第 1 片
供应链组supplyinventory-svc 手册 §2 发布与回滚（0.779）
交易组supplyorder-svc 手册 §4.2 回滚（0.607）：看不到对的那份，拿到了别的服务的回滚命令
交易组public（挪了目录，0 片重算）inventory-svc 手册 §2 发布与回滚（0.779）

第二行是权限做对了以后的副作用：对的文档“隐身”了，检索照样会交出最像的几片，这里是 order-svc 的回滚。生成那一步要能识别“问的是 inventory-svc，资料讲的是 order-svc”，否则会把 kubectl rollout undo deploy/order-svc 当成答案（⑥ 坑 4）。

为什么这样设计

三条约束：算向量是最贵的一步（每片约 1 秒，CPU）；资料的变化大多是局部的（加一份、改一处、挪一下）；“该不该被查到”比“像不像”更重要（旧版本、删掉的、没权限的，一旦被查到就是带着真实出处的错答案）。

片级增量 + 状态 + 权限列（选）

  • 变化多小，工作就多小：改一处 1 片、改权限 0 片。
  • 新片插进 HNSW 立刻可查，不用停服务、不用重建。
  • 旧版本软下线，审计和“当时怎么写的”还能查。
  • 代价：同步程序变复杂（身份、比对、状态机），要有定期全量对账兜底。

全量重建

  • 程序最简单，永远和目录一致。
  • 成本和库的总量成正比，不和变化量成正比。
  • 新资料、权限收回都要等下一次重建。
决定胜负的约束：算向量和 OCR 贵，变化又是局部的，所以要让工作量跟着“变化”走，而不是跟着“总量”走；“该不该查到”交给确定的状态和权限字段，不交给相似度。

读出来的结论
  • 过关条件之二达成：供应链组的新手册放进目录，下一次同步 1.9 秒，同一个 HNSW 索引上马上查得到，没有重建。
  • 工作量跟着变化走：改一处只重算 1 片向量；改权限、删文件 0 片；什么都没变 0 秒。全量重建同样的库要 53 秒，而且和库的总量成正比。
  • 改一处的 7 秒大部分花在重新解析整份 PDF（第 12 页要 OCR）：片级增量省掉了向量，没省掉解析。
  • 权限对了，检索不会越权，但会退而求其次：交易组看不到 inventory-svc 手册时，拿到的是 order-svc 的回滚，生成那一步要能认出“服务对不上”。
到这里已经能交差了：一个定时或事件触发的 sync()：哈希比对、片级复用向量、按版本号下线旧版、文件消失就软删、目录即权限。

⑥细节

第一圈 · 注意事项

1用文件路径当文档的身份← ④ 机制 1
现象
本页代码最初就是按路径认文档的，写完复查时发现：把 inventory-svc 手册从 supply 挪到 public，同步会以为“旧路径的文档被删了、新路径来了一份新文档”，处理旧路径时把同名同版本的片全标成 deleted，新路径那份的权限也没更新。
根源
路径同时编码了“这是哪份文档”和“谁能看”，挪目录只改了后者，却被当成了前者。
做法
文档按“名字 + 版本号”（或者源系统里的文档 ID）认；路径、团队都是它的属性。挪目录时只改 team 列，实测 0 片重算。
2谁最后被处理，谁就成了现行版← ④ 机制 2
现象
本页代码第一版在处理一个文件时，把同名的其他版本都下线；第一次跑完复查时发现：旧版 v3.1 的文件被改了个错字、重新处理一遍，就会把 v3.2 挤下线；版本号按字符串比，v3.10 还会被当成比 v3.9 旧。
根源
“现行”应该是版本号最大的那个，和处理顺序无关；字符串比较又不是数字比较。
做法
每次都用 max(所有版本, key=按数字比) 算出现行版；实测加了“旧版改错字”这一步来验证：v3.1 重新处理，v3.2 仍是现行。
3改一个字，整份文件重新解析实测← ④ 机制 1
现象
手册改了一处，向量只重算 1 片，同步却用了 7 秒：整份 12 页 PDF 重新解析，扫描页重新 OCR。
根源
文件哈希变了，就不知道变的是哪一页，只能从头解析；片哈希要在解析之后才算得出来。
做法
把解析结果按页缓存（页的哈希 → 块），只重新解析变了的页；至少把 OCR 结果按图片哈希缓存，扫描页几乎从来不变。
4权限让对的文档隐身，检索交出别的服务实测← ④ 机制 3
现象
交易组问“inventory-svc 怎么回滚”，看不到 supply 团队的手册，第 1 片是 order-svc 的 §4.2 回滚（0.607）；生成如果照着写，就是一条错的回滚命令。
根源
检索永远会交出“可见范围里最像的”，它不知道“对的那份我看不到”。
做法
生成前检查问题里的实体（服务名）是否出现在资料里，对不上就答“你可能没有权限看到相关资料，或者库里没有”；必要时提示去找资料的属主团队。不要为了“答得出来”放宽权限。
5换 Embedding 模型，所有向量作废← ④ 为什么这样设计
现象
换了更好的 Embedding 模型，片级增量只给新片用了新模型：新旧向量在一个库里，距离没有意义（全景预测题 4），命中率塌掉，不报错。
根源
片哈希只看内容，不看是哪个模型算的向量；而向量只在同一个模型里能比。
做法
每片记 embed_model（本页实测 49 片都是 Qwen3-Embedding-0.6B-Q8_0）；换模型时建一套新库全量重算（蓝绿），跑评测集过了再切流量，旧库留几天可回滚。
6软删除留下“墓碑”← ④ 机制 2
现象
删掉的笔记还占着表里的行和 HNSW 里的点；如果删除是因为“这份资料不该存在”（误传了含密码的文件），软删除根本不够。
根源
软删除只改状态，数据还在；HNSW 的点要等 VACUUM 才清。
做法
按原因分两种：版本下线、文件移除用软删（可审计、可恢复）；隐私和误传用硬删（DELETE + VACUUM），并清掉缓存和日志里的副本。定期清理很久以前的 deleted 行。

第二圈 · 使用规范

  • 每次同步记一行日志：扫了几个文件、算了几片、删了几片、失败的文件和原因、用时。防的是某份文件一直解析失败、悄悄没进库。
  • 每周全量对账一次：把目录（或源系统）和库里的 current 文档逐个比，补漏、清残留。防的是事件丢失、程序 bug 造成的长期不一致。
  • 权限只从身份来，团队目录或源系统的 ACL 同步成 team 列；改权限后立刻同步，并清掉相关的回答缓存。防的是权限收回了，缓存里的答案还在。
  • 评测集跟着资料一起版本化：手册出了新版，标准答案也要改（评测页练习 5）。防的是用旧答案去评新库。
  • “最久没同步的文件有多旧”做成监控指标。防的是同步任务挂了没人知道，库停在三天前。

第三圈 · 优化和深处

从“扫目录”到“收事件”

扫目录要逐个算哈希，文件多了也慢。Confluence、Git、对象存储都能在变更时发通知（webhook、push 事件、存储事件），同步任务只处理收到的那几份；再用每周的全量对账兜底。和 MySQL 用 binlog 增量同步到 ES 是同一个思路。

文档级的权限不够细时

同一份手册里，大部分人能看，“应急联系人”那一节只有值班的人能看。权限可以下沉到片：每片自己的 team / 角色列表；代价是同步更复杂，过滤条件更多，HNSW 的过滤问题更明显（HNSW 页坑 1）。

按版本查询

retired 的片留着，就能回答“v3.1 当时是怎么规定的”：检索时把条件从 status = 'current' 换成 version = 'v3.1'。复盘报告引用“当时有效的手册”时会用到。

多副本和一致性

同步写库和检索读库是同一张表，一次同步只做了一半（新片插了、旧片还没下线）时，检索可能同时看到新旧两版。可以把一份文档的变更放进一个事务里，或者先写好再一次性切换状态。

实验台：一次变更，增量和全量各要做多少

先猜：手册 v3.2 改了一处（版本号不变），片级增量同步要重算几片向量？

实测 每一步的数字来自 kb-ops/main.py（ops.json）；“全量”是同一时刻的库从零重建的估算：按实测的全量重建 53.1 秒 / 49 片折算到当时的片数。

下一圈

  • 按页缓存解析结果：改一处时只重新解析那一页，把 7 秒降到 1 秒以内。
  • 接 Confluence / Git 的变更事件：不扫目录，收到通知才同步。
  • 片级权限：同一份手册里不同章节给不同的人看。
  • 蓝绿换模型：用新的 Embedding 模型建第二套库，评测集过了再切。

↺回到⑤：改一改

  1. 缓存 OCR：在 kb.ocr_page 前面按渲染图的哈希查缓存，重跑 main.py，看“改一处”“旧版改错字”两步的秒数降了多少。（坑 3）
  2. 服务名对不上就拒答：在检索结果上加一道检查，问题里的服务名不在任何一片里出现，就返回“没有找到 inventory-svc 的资料，可能没有权限”。用交易组在“改权限”之前那一步验证。（坑 4）
  3. 模拟换模型：把 EMBED_MODEL 环境变量改个名字再同步，写一个检查：库里出现两种 embed_model 就报警并拒绝检索。（坑 5）
  4. 按版本查：给 kb_ops.search 加一个 version 参数，问“v3.1 的 P99 告警阈值是多少”，应该拿到 1000 ms 那张表。（第三圈）

自测

1. 用一句话说出这一页的精华

让同步的工作量跟着变化走：文件哈希没变就跳过、按名字加版本号认文档、片哈希没变就复用向量；用 current / retired / deleted 三种状态决定谁能被查到，现行版按版本号比；权限是一列，从身份来，过滤在检索之前，改权限不用重算。

2. 每晚全量重建的老办法，疼在哪？

成本跟着库的总量涨（这里 53 秒，资料多了是小时级）；白天的新手册要等一夜才查得到，不满足“加一份新手册不重建就能查到”；权限收回也要等一夜。

3. 为什么挪了一下目录，第一版代码会把文档标成删除？

它按路径认文档：旧路径不见了，就认为那份文档被删了，而新旧路径其实是同一份内容、同一个名字和版本。身份应该是名字 + 版本号，路径和团队只是属性。

从 ④ 机制 1 推出。

4. 预测：手册里把 §4.3 整节挪到了 §6（文字一个字没改），片级增量会重算几片？

至少 1 片：片哈希包含标题路径，从“4 发布与变更规范 › 4.3”变成“6 …”，哈希就变了，算作新片，旧片删掉；而且它算向量时前面的标题路径也变了，确实应该重算。如果后面的章节编号跟着变，受影响的片会更多。

从 ④ 机制 1（片哈希 = 标题路径 + 正文）推出。

5. 预测：同步任务在处理 v3.2 时挂了：17 片插进去了 10 片，v3.1 还没下线。这时问 P99 阈值会怎样？

v3.2 的部分片和 v3.1 的全部片都是 current，可能同时拿到 800 ms 和 1000 ms；更糟的是 v3.2 的“告警与阈值”那片可能还没插进去。所以一份文档的变更要么放在一个事务里，要么先全部写好、最后一次性切换状态；下次同步要能从中断处恢复（重新处理这份文件即可，片哈希会跳过已插入的）。

从 ④ 机制 1、2 推出。

6. 放回全景：第 1 站前后各发生什么？如果第 1 站没有把 v3.1 下线，报告会怎样？

第 1 站之前是交易组把文件放进目录；之后是第 2 站解析、第 3 站切块。v3.1 没下线，第 8 站的候选里新旧两版几乎一样像，RAG 优化页实测 30 题里 26 题的前 3 片混进了旧版；报告里“违反了手册哪条规定”可能引用 v3.1 的“建议设上限”，结论从“违规”变成“没违规”。

从全景第 1、7、8、10 站推出。

档位：标准。实测 2026-11-25，本机 2 核 ARM：PostgreSQL 17.11 + pgvector 0.8.7（容器）、Qwen3-Embedding-0.6B Q8_0；一天 8 次变更（首次入库、上传新版、无变更、原地修订、加新手册、改权限、旧版改错字、删一篇）和一次全量重建对照，每步带一次查询。“用路径当身份”和“按处理顺序定现行版”是本页代码最初写错、复查时发现的（错误本身没有跑出来），修好后用“改权限”“旧版改错字”两步验证了修好的版本。按文档：事件驱动同步、片级权限、蓝绿换模型。实验台里的“全量”是按实测速度折算的估算。
