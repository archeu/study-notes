文档解析：PDF、Word、表格、扫描件

PDF 里没有“段落”和“表格”，只有“用某个字体、在坐标 (x, y) 画第几号字形”的指令。解析就是把这些指令重新拼回带结构的文字：先后顺序、标题、表格的行和列；扫描页连字形都没有，只能 OCR。解析时丢了的字和结构，后面哪一站都找不回来。

本页学“版面规则 + OCR”：先弄懂 PDF 里存了什么、规则是怎么拼回结构的，换成版面模型时才知道它替你做了哪一步、会在哪一步出错。

④原理：从“画字的指令”拼回结构

先知道这些
  • 字体和字形（glyph）：字体文件里每个字的形状叫一个字形，有自己的编号。PDF 画字时写的是字形编号，不是字符；另有一张 ToUnicode 表，告诉解析器“几号字形是哪个字”。
  • PDF 的坐标：单位是 pt（1/72 英寸），A4 页面约 595 × 842 pt。字号 10.5 pt，就是字高约 10.5 pt。
  • dpi：把页面变成图片时，每英寸多少像素。72 dpi 时 1 pt 就是 1 像素，10.5 pt 的字只有十来个像素高。
  • OCR：从图片里认字。现在的 OCR 是两个小神经网络：一个找“哪里有字”（检测），一个认“这一条是什么字”（识别）。
  • .docx：一个 ZIP 包，正文在 word/document.xml 里，Java 里用 Apache POI 读的就是它。

这里面没有的东西

  • 没有“这是标题”：只能从字号 14 比正文的 10.5 大推出来。
  • 没有“段落”和“行”：只有一个个定位点，换行是因为下一段文字的 y 变了。
  • 没有“表格”：只有一些 1 pt 粗的细长矩形，恰好围成了格子。
  • 没有字符：0cc8 是 Droid Sans Fallback 里的字形编号，要查 ToUnicode 表才知道是“告”。“Caffeine”里的 ff 画的是一个连字字形，查出来是 U+FB00“ﬀ”。
  • 中文、西文、标点分属三种字体（F0、F1、F2），同一个词会被拆成几段分别画。

两者用的是同一批字形、同一组格子，差别只在“格子里的字按什么顺序拼起来”：extract() 把句点、短横线挪到了格子末尾，还吃掉了空格；get_text(clip=…) 走的是机制 2 那套按行拼字的路，顺序就对了。实测 PyMuPDF 当前版本；为什么 extract() 会这样排，没有追到源码，只记现象和绕法。

跨页的表：第二页没有表头

JVM 参数表从第 10 页跨到第 11 页。第 11 页的表被当成一张新表，第一行是 -XX:HeapDumpPath | /data/dump | 挂了持久卷，Pod 重启不丢：表头“参数 | 值 | 为什么”留在了第 10 页。单看这一块，模型不知道第二列是什么。

没有框线的表

很多文档的表只靠对齐，没有线。find_tables() 也能按文字对齐来猜（strategy="text"），但容易把两段并排的正文当成表。这种表是规则方法最弱的地方，也是版面模型工具最值钱的地方。

和 PDF 正好相反

坑在“显示时才算出来的东西”：自动编号的“1. 2. 3.”存在 numbering.xml 里，正文里没有；修订记录、文本框、页眉页脚也各在别处。实测用 List Number 样式写的三步，读出来没有编号。

为什么 PDF 要这样设计

PDF（1993 年，从 PostScript 演化来）要解决的是：同一份文件，在任何电脑、任何打印机上印出来都一模一样。要做到这一点，就得把排版的最终结果存下来：每个字形画在哪、用哪个字体（连字体一起嵌进去）、线画在哪。至于“这是标题”“这是表格”，打印机不需要知道，于是就没存。

PDF：存排好版的结果

  • 换一台机器、换一个字体环境，打开还是一模一样，适合发布、归档、打印。
  • 嵌入字体子集，不依赖对方电脑装了什么字体。
  • 语义丢了：标题、段落、表格、阅读顺序都要从坐标反推；扫描件连字都没有。
  • PDF 也能带一棵结构树（Tagged PDF，给读屏软件用），但很多工具导出的 PDF 不带，我们这份就没有。

Word、HTML、Markdown：存结构

  • 标题、段落、表格、列表都是写明的元素，解析就是读。
  • 能编辑、能按屏幕宽度重排。
  • 换一台机器显示得不一样（字体、分页、编号都可能变）。
  • 自动编号这类“显示时才算出来”的东西，也要额外处理。
决定胜负的约束：PDF 为“印出来一样”而设计，结构只是排版的副产品。所以能拿到源文件（Word、Markdown、Confluence 页面）就别去解析导出来的 PDF；只有 PDF 的，才用版面分析和 OCR 把结构猜回来，并且记住“猜”的那部分可能错。

for pno, pg in enumerate(pymupdf.open(path), start=1):
    if not pg.get_text().strip():              # 没有文字层：扫描件，走 OCR
        blocks += ocr_page(pg, pno)
        continue
    tabs = pg.find_tables().tables
    boxes = [pymupdf.Rect(t.bbox) for t in tabs]
    # 表格：按格子的坐标框重新取字，不用 t.extract()
    items = [(t.bbox[1], Block("table", table_text([[pg.get_text("text", clip=c) if c else "" for c in row.cells]
                                                    for row in t.rows]), pno)) for t in tabs]
    for b in pg.get_text("dict")["blocks"]:
        if b.get("type") != 0 or any(pymupdf.Rect(b["bbox"]).intersects(r) for r in boxes):
            continue                               # 图片块、表格里的字跳过
        text = "\n".join("".join(s["text"] for s in ln["spans"]) for ln in b["lines"])
        size = max(s["size"] for ln in b["lines"] for s in ln["spans"])
        if size >= 13:   blk = Block("heading", join_lines(text), pno, level=1 if size < 18 else 0)
        elif size >= 11.2: blk = Block("heading", join_lines(text), pno, level=2)
        else:            blk = Block("text", join_lines(text), pno)
        items.append((b["bbox"][1], blk))
    blocks += [blk for _, blk in sorted(items, key=lambda x: x[0])]   # 按纵坐标排顺序

读出来的结论
  • 有文字层的页，三种取法取到的字几乎一样；差别在结构：纯文本取法把 24 行表格全部拆散，版面块 + 表格保住了 23 行（剩下 1 行是扫描页的表头被 OCR 拆开了）。
  • 扫描页决定了全书的 7%：不做 OCR 就整页消失；做了，234 个字错 4 个左右，5 个关键字段（3 个开关名、2 个群名）全对。
  • 时间：纯文本 12 页 0.02 秒；版面块 + 找表格 11 页约 2.6 秒（找表格最费时）；OCR 1 页约 2.9 秒，第一次还要 1.8 秒加载模型（所以上面那次是 7.0 秒）。一页扫描件比 11 页文字页加起来还贵。
  • 表格取字换一个办法，正确率从 31/59 到 59/59；跨页续表的表头丢了，要自己接。

⑥细节

第一圈 · 注意事项

1扫描页 0 字，不报错实测← ④ 机制 1
现象
第 12 页 get_text() 返回空字符串，整本手册少了一页，解析“成功”。
根源
扫描页里只有一条“在这里画一张图”的指令，没有任何画字的指令，自然取不出字。
做法
逐页检查：没有文字、却有一张铺满页面的图，就走 OCR；OCR 也没认出字，就报警，不要静默跳过。混合文档（一部分页是扫描的）很常见，所以要按页判断，不要按文件判断。
2表格自带的取字把标点挪到了末尾实测← ④ 机制 3
现象
“v3.0”变“v30.”，“2025-03-10”变“2025 03 10- -”；59 个格子只对 31 个。版本号、日期、参数正好是问答里最常问的。
根源
格子找对了，格子里的字形排序错了；同一批字形按机制 2 的版面分析去拼，顺序就对。
做法
按格子的坐标框用 page.get_text("text", clip=cell) 取；换了解析库，先拿带版本号、日期的表格抽查几格。
3跨页的表，第二页没有表头实测← ④ 机制 3
现象
第 11 页的续表第一行就是数据，“参数 | 值 | 为什么”留在第 10 页；如果两页切进不同的片，第 11 页那片里的 /data/dump 没人知道是什么。
根源
PDF 是一页一页画的，表格在分页处被截成了两张独立的“格子网”。
做法
一页顶部的表，如果列数和上一页底部的表相同，就接上去，并把表头复制到续表前面；或者干脆把表格的每一行写成“列名：值”的形式（第三圈）。
4分辨率太低，OCR 整页全错实测← ④ 机制 4
现象
72 dpi 的扫描件，字错率 0.944，开关名一个都没认出来；110 dpi 就降到 0.017。
根源
72 dpi 时 10.5 pt 的字只有 10 个像素左右高，检测模型找不到字，识别模型也认不清笔画；OCR 不是“越清楚越好”，而是低于某个门槛就突然失效。
做法
渲染给 OCR 时用 150～200 dpi；扫描纸质件要求 ≥ 200 dpi。开关名、命令、IP 这类关键字段用正则核对格式，对不上就标出来人工看；OCR 来的块在元数据里记 src=ocr。
5“Caffeine”取出来是“Caﬀeine”实测← ④ 机制 1
现象
第 9 页 §4.3 里的“Caffeine”取出来中间是一个字符 ﬀ（U+FB00）。搜“Caffeine”，关键字检索找不到这一节。
根源
排版时 ff 被画成了一个连字字形，ToUnicode 表把它映射到连字字符 U+FB00，而不是两个 f。
做法
清洗时只对连字和全角字母数字做 Unicode NFKC 还原；整段 NFKC 会把中文的“，”“：”也变成半角，见下一页。
6Word 的自动编号读不出来实测← ④ 机制 5
现象
“1. 看 GC 日志 / 2. 关闭开关 / 3. 观察 P99”读出来是三段没有编号的话；正文里如果写着“见第 2 步”，就对不上了。
根源
编号是显示时按 numbering.xml 算出来的，正文的 w:t 里没有。
做法
按样式（List Number）或 numPr 自己补上序号；或者用 pandoc 先把 docx 转成 Markdown，它会输出编号列表 按文档。

第二圈 · 使用规范

  • 每块带上页码、坐标框和来源（text / ocr / docx）。防的是引用点不回原文的位置，以及 OCR 来的内容被当成和原文一样可信。
  • 解析结果存成中间文件（JSON，一块一行），切块、清洗的策略改了直接从这里重来。防的是每调一次切块就重新 OCR 一遍。
  • 能拿到源文件就不解析导出的 PDF：Word、Markdown、Confluence 页面优先。防的是把结构先扔掉、再花力气猜回来。
  • 每来一种新文档，先抽 3 页人工看：有没有扫描页、双栏、无框表、跨页表。防的是一种从没见过的版式整批进库。
  • 解析器和版本记进元数据。防的是升级解析库以后，新旧两批片的格式不一样还查不出原因。

第三圈 · 优化和深处

表格交给模型时写成什么样

“Old 区占用 | > 85% 持续 5 分钟 | P2”对人好读，单独一行时却不知道哪列是什么。常见做法是把每一行写成“指标：Old 区占用；阈值：> 85% 持续 5 分钟；级别：P2”，表头跟着每一行走，跨页也不怕。代价是片变长。

OCR 是解析里最贵的一步

本机一页 2～3 秒（150～200 dpi），一份 300 页的扫描预案就是十几分钟。整批入库前先按页判断哪些需要 OCR；有 GPU 时检测和识别都能快一个数量级。分辨率不是越高越好：300 dpi 比 110 dpi 多用六成时间，字错率没有更低。

规则不够用的时候

双栏、无框表、公式、图里的字，靠坐标规则很难做对。这时换版面模型工具（Docling、MinerU 一类：先用模型把页面分成标题、正文、表格、图，再分别处理），或者把那一页渲染成图交给多模态模型转成 Markdown，代价是慢和贵。按文档

倾斜要不要先摆正

实测 0°、1.2°、3° 的字错率差不多（0.017～0.021），但 3° 时有一行开关表的说明被拆成了两个框（好在还在同一行里）。倾斜再大，同一行的文字框纵坐标差会超过半个字高，就会被拆成两行；那时要先检测角度、把图转正再识别。

自测

  

    
1. 用一句话说出这一页的精华
PDF 只存“在哪儿画几号字形”，没有段落、标题、表格；解析就是按坐标、字号、框线把结构猜回来，扫描页要先 OCR 认字再拼行。解析丢了的字和结构，后面哪一站都补不回来，所以能拿到源文件就别解析 PDF。

    
2. “PDF 能复制出字”的老办法，疼在哪？
字基本都在（有文字层的页 97% 以上），但结构没了：24 行表格没有一行还在一起，标题和正文分不出来，页眉页脚夹在正文里；扫描页直接是空字符串，还不报错。

    
3. 为什么扫描页 get_text() 是空的？
扫描页的内容流里只有“在这里画一张图”，没有画字的指令；PDF 的文字只能从画字指令加 ToUnicode 表里来。
从 ④ 机制 1 推出。

    
4. 预测：一份双栏排版的 PDF，用纯文本取法会怎样？用我们的版面块按纵坐标排序呢？
纯文本取法如果按行走，会把左右两栏同一高度的两行拼在一起，句子交错。我们按块的纵坐标排序：左栏一段和右栏一段如果起点高度差不多，也可能交错。正确做法是先判断分栏（块的横坐标聚成两堆），再先左后右。
从 ④ 机制 2 推出：顺序是从坐标反推的，PDF 本身不记录“先读哪一栏”。

    
5. 预测：扫描仪自带 OCR，导出的 PDF 已经有一层文字（但认得不好），我们的代码会怎么处理？
不会再做 OCR：get_text() 不为空，代码就信了那层文字，扫描仪认错的字原样进库。要判断文字层的质量（比如乱码比例、和渲染图 OCR 的结果比对），差的就重新 OCR。
从 ④ 机制 1 和 ⑤ 里的判断条件推出：我们只按“有没有字”来决定，不按“字对不对”。

    
6. 放回全景：第 2 站前后各发生什么？如果第 2 站没做 OCR，报告会怎样？
第 1 站同步任务发现 v3.2 是新版本，交给第 2 站；第 2 站之后是第 3 站清洗切块。没做 OCR，附录 C 那一页一个块都没有，第 3 站切不出片，第 8 站怎么查都查不到降级开关；报告里“怎么止血”那句要么写“资料未提及”，要么从故障单里抄出开关名却给不出手册出处。
从全景第 2、3、8、10 站推出。
