上下文窗口：输入输出共用，越长越慢越贵

上下文窗口是模型一次能“看见”的 token 上限：系统提示、历史、这次的日志，加上它要写的回答，全挤在里面。超了直接报错；没超，也是越长越慢、越贵，而且埋在长文中间的关键一行更容易被漏掉。窗口装得下，不等于看得全。

全景：一句话怎么变成模型的回答 · 第 3 站地图：站 02 · 上下文窗口：输入输出共用，越长越慢越贵深度：懂机制

这一页的位置站 02 第 3 个知识点，接着token 和计费：上一页数清了一次请求有多少 token，这一页看这些 token 装不装得下、装进去要付出什么。站 02 的第三个小实验“把关键报错埋进长日志”在 ⑤。

①为什么需要：日志从 10 分钟改成 60 分钟，会发生什么

在全景第 3 站，这一步要解决：值班助手到底能往一次请求里塞多少日志。10 分钟的 GC 日志约 5000 个 token；有人说“多给点上下文，模型判断更准”，改成 60 分钟，约 3 万个 token。

Java 里最像的是堆内存上限：放不下就失败。但比方有两处失效：窗口超了不会像 OOM 那样在运行中途崩溃，而是请求一进门就被拒；没超但塞得很满时，也不会报任何错，只是悄悄地抓不住重点。

②没有它会怎样：“全塞进去，让模型自己看”

不了解窗口时，最自然的做法是能塞就塞。对照地图上那句话“输入输出共用，越长越慢越贵”，一条一条看这个做法撞上什么：

以为的实际的后果
窗口是输入的上限输入和输出共用一个窗口：输入占满了，输出就没地方写回答写到一半被截断，或者请求直接被拒
超了会自动截掉一点本机 llama-server 直接 400（⑤ 实测）；也有服务会按配置悄悄从开头丢掉一部分，不报错要么一个字没有，要么丢的正好是系统提示
长度只影响钱读输入的时间随长度增长，写每个字也变慢值班时多等几十秒
装得下就看得全埋在长文中间的一行，比放在开头结尾的更容易漏关键的 Full GC 没被引用，结论跑偏
不懂精华时的典型误用：把“上下文越多越准”当成规律，每次都塞满窗口。多给的那些不相关日志不但花钱、拖慢，还稀释了模型的注意力，结果往往更差。

③相邻方案：材料比窗口大时怎么办

做法怎么做适合代价
换大窗口，全塞Claude 这类模型窗口 100 万材料确实都相关，比如一份完整的合同慢、贵，中间的内容容易被忽略
先过滤，再塞用程序先挑出相关的时间段、相关的行日志、监控数据这类“大部分无关”的材料便宜、快；要写过滤规则
分块总结再汇总每块单独问一次，再把几个小结论合起来问每块能独立判断的长材料调用次数多，跨块的联系会丢
检索：先查再答建索引，按问题只取最相关的几段知识库、历史工单（站 06）要建索引，取错了就答错
压缩历史多轮对话里把早先的轮次换成摘要长对话、agent 跑很多步（站 04、05）摘要会丢细节

本页先学窗口本身：它是怎么被占满的、为什么越长越慢、为什么中间会丢。懂了这些，才判断得了什么时候该过滤、什么时候该检索。

④原理：窗口里每个 token 都要占内存、都要被回看

先知道这些
  • 生成循环：模型一圈写一个 token，每圈都要读全部前文（下一个词预测）。
  • 注意力：每个 token 在每一层都会去“看”前面所有 token，按相关程度取信息。这里只用到结论，细节在注意力和 KV 缓存。

机制 1 · 共用：窗口 = 输入 + 已经写出的输出

所以有两条硬规则：输入加上要写的输出不能超过窗口，发请求时就要给输出留够格子，否则写到带子尽头就只能停（不同服务是提前拒绝还是写到一半停下，做法不一，见 ⑥ 坑 2）；输出也有自己的上限，Claude Opus 5.5 的窗口是 100 万个 token、单次最多写 12.8 万个（按文档）。

机制 2 · 越长越慢：读一遍要按长度付时间，写每个字也要回看全部

读输入（预填充）

每个输入 token 都要穿过全部层，所以首字出来之前的等待，大体和输入长度成正比；注意力那部分要两两配对，长度翻倍，这部分的计算翻四倍，越长越显眼。

写输出（解码）

每写一个新 token，它都要回看窗口里前面所有 token 的 K、V。前文越长，每圈要读的 KV 越多，每秒写出的 token 就越少。

⑤ 里实测了本机 500 到 4000 个 token 的输入，看这两个数怎么变。

机制 3 · 中间容易丢：注意力是一份要分出去的“预算”

注意力在每个位置上算的是一组加起来等于 1 的权重（softmax）：前文越长，分到每个 token 头上的就越薄。训练语料里，问题的答案大多就在附近或在开头，所以模型更习惯看开头和结尾。公开研究（Liu 等人 2023 年的 “Lost in the Middle”）测过多个模型：关键信息放在长文中间时，答对率明显低于放在开头或结尾，曲线呈 U 形。新一代模型在这类测试上好了很多，但“材料越长、越杂，越容易漏”的方向没变。

Claude 官方的提示建议正是从这里来的：长材料放在提示的前面，问题和指令放在最后；多份材料用标签分开（站 03 提示词那一页）。

为什么这样设计：要能精确回看任何一个字，就得把它们都留着

定长窗口 + 全部 KV 留着（Transformer）

  • 窗口里任何一个 token 都能被原样回看：第 4000 个 token 照样能精确引用第 12 行日志里的“1873.412ms”。
  • 训练时所有位置并行算，训练快。
  • 代价：内存随长度线性涨，注意力计算随长度平方涨，所以窗口必须有上限，越长越贵。

固定大小的“记忆”（循环网络这一类）

  • 不管读多长，记忆大小不变，没有窗口上限，每步代价也不变。
  • 前面读过的东西被不断压缩进同一块记忆，细节会被冲掉：读到第 4000 个 token 时，很难再精确说出第 12 行的那个数。
决定胜负的约束：问答、写代码、调工具都要求“原样引用前面某处的细节”，精确回看比无限长度更重要。于是主流模型选了前者，再用工程手段（KV 缓存、提示缓存、更省内存的注意力变体）把窗口一代代做大。

⑤亲眼看到：装不下、变慢、埋在中间

三个实验都连本机的 llama-server（Qwen2.5-0.5B，窗口开的是 8192），日志由脚本按固定随机种子生成，每次一样。

  1. 1 装不下python main.py overflow：120 行 GC 日志，超过 8192。
  2. 2 变慢python main.py speed：同样的问题，日志从 6 行加到 52 行，关掉缓存（cache_prompt: false），每次固定写 32 个 token。
  3. 3 埋针python main.py needle：38 行普通的 Young GC（停顿都在 240ms 以下），把那行 1873ms 的 Full GC 分别插在第 2 行、第 20 行、第 38 行，问“最长的一次停顿是多少毫秒，是哪种 GC”。

读出来的结论
  • 装不下就是 400：不截断、不降级，一个字都不写。
  • 读输入比长度涨得还快：输入是 8.2 倍（519 → 4232），读的时间是 10.1 倍（11 秒 → 110 秒），每秒能读的 token 从 47.5 降到 38.3。多出来的那部分就是注意力的两两配对。
  • 写输出也被拖慢：前文 4232 个 token 时，每秒只写 11.2 个，不到 519 时的一半。每写一个字都要回看全部前文的 KV。
  • 只有放在末尾的那次找到了：放在开头和中间时，它答的 194.897ms、196.218ms 都是日志前几行里的数（第 3、4 行），连 Young GC 里最长的 239.518ms 都不是。

埋针的结果要打折扣看：这是 5 亿参数的小模型，只有 3000 多个 token，只跑了一次，也只放了三个位置。它明显偏爱离问题最近的末尾；Claude 这类大模型在这种长度上基本都能找到，但在几十万 token、材料又杂的时候，“中间更容易漏”的方向依然成立（④ 机制 3 的研究）。值班助手不要赌这个，用 ⑥ 的做法：先让程序把可疑的行挑出来。

到这里已经能交差了：你能说清窗口是输入输出共用的，能估出塞进去之后慢多少，也知道关键信息别埋在中间。
已知还没处理的细节：超长时的两种下场（坑 1），给输出留位置（坑 2），关键行被漏（坑 3），多轮越聊越长（坑 4）。

⑥细节：窗口怎么被撑爆、怎么被浪费

第一圈 · 注意事项

1超长：要么直接报错，要么悄悄丢掉开头实测← ④ 机制 1
现象
本机输入 9716 个 token，llama-server 直接返回 400 exceed_context_size_error，一个字都不写。换一个默认窗口很小、配置成自动截断的推理服务，同样的请求会“成功”，但系统提示被截掉了，模型开始不按规矩回答。
根源
窗口是定长的，装不下的部分只有两种处理：拒绝，或者扔掉。
做法
发之前自己量长度（count_tokens），超了就先过滤；自建推理服务时把窗口大小显式写进配置，并确认超长时的行为。
2输入塞到快满，输出没位置了← ④ 机制 1
现象
输入 8000、窗口 8192，max_tokens 给了 1000：有的服务直接拒绝，有的写到 192 个 token 就停下，回答缺了后半截。
根源
输出一格一格往窗口后面长，长到尽头就只能停。
做法
输入预算 = 窗口 − 输出预留（含思考）。检查 stop_reason，不是正常结束就别当完整结果用。
3关键一行埋在长日志中间，被漏掉实测← ④ 机制 3
现象
见 ⑤ 第三个实验：同一行 Full GC，放的位置不同，小模型的回答不同。
根源
注意力权重要在全部前文上分，越长分得越薄；模型更习惯关注开头和结尾。
做法
先用程序把可疑的行挑出来，单独放在“重点”标签里；长材料放前面、问题放最后；能用程序判断的（停顿是否超过 1 秒）别交给模型去找。
4多轮对话越聊越慢、越贵，最后撑爆← ④ 机制 2
现象
值班助手连续追问二十轮后，首字要等很久，账单翻了几倍，最后报超长。
根源
每轮都把全部历史重发一遍，窗口里的东西只增不减；读输入的时间和费用跟着涨。
做法
历史里的大段日志只保留第一次，后面用摘要代替；轮数多了就压缩早先的对话（Claude 有服务端的压缩功能，站 05 讲）；固定的前缀配合提示缓存。

第二圈 · 使用规范

  • 算预算，不靠感觉：输入预算 = 窗口 − 输出预留 − 安全余量，发送前用 count_tokens 检查。防坑 1、坑 2。
  • 只给相关的：时间窗口、服务、日志级别先用程序筛。防的是慢、贵，也防关键行被稀释（坑 3）。
  • 材料在前、问题在后，用标签分段：<gc_log>…</gc_log> 后面再写问题。防坑 3。
  • 长对话要有“遗忘”策略：保留最近几轮原文，更早的换成摘要。防坑 4。

第三圈 · 窗口为什么能越做越大

省 KV 内存

让多个注意力头共用同一份 K、V（分组查询注意力）。本页的模型 14 个查询头只配 2 个 KV 头，KV 缓存因此只有“每头一份”时的七分之一。

位置编码能外推

模型靠位置编码知道每个 token 在第几格。主流做法（旋转位置编码 RoPE）配合缩放技巧，能把训练时的长度往外推几倍；推得太远，质量会掉。

长提示单独定价

有的模型对超长提示加价：Claude Haiku 5.5 提示不超过 10 万 token 时 0.1 / 0.5，超过后 0.5 / 2.5（按文档）。算长文档的成本时要看清分档。

窗口大不等于该塞满

“窗口 100 万”说的是装得下，不是看得好。材料越杂，越该先过滤、先检索；站 06 的“先查再答”就是为此而来。

实验台：这次请求装不装得下、要等多久

先猜：本机读 519 个 token 的输入用了 11 秒。读 4232 个（8.2 倍）要多久？

口径：10 分钟 GC 日志按上一页实测的约 5000 token 折算（每分钟约 500）；系统提示和问题 100 个，每轮追问的历史 600 个。本机耗时用 ⑤ 的四个实测点拟合 t = 0.0203·n + 1.36×10⁻⁶·n² 秒，只在 8192 窗口下给出；Claude 的速度取决于服务端，不在这里估。费用按 Opus 5.5 输入单价 4 美元每百万。

自测

1. 用一句话说出这一页的精华

窗口是输入和输出共用的定长带子，每格都要占内存、都要被回看：超了就报错，越长越慢越贵，中间的内容还容易被漏，所以要先过滤再塞。

2. 为什么窗口不能无限大？

窗口里每个 token 在每一层都要存一份 K、V，内存随长度线性涨；注意力要两两配对，计算随长度平方涨。想让模型能精确回看任何一个字，就得把它们都留着。

从 ④ 机制 1 和为什么这样设计 推出

3. 为什么关键一行埋在中间容易被漏？

注意力权重在全部前文上加起来等于 1，越长分得越薄；训练语料里答案多在附近或开头，模型更习惯看两头。

从 ④ 机制 3 推出

4. 预测：输入从 4000 个 token 加到 8000 个，本机读输入的时间大约变成多少？写输出的速度呢？

读输入超过两倍：按 ⑤ 拟合的公式，4232 个是 110 秒，8000 个约 250 秒，因为注意力那部分是平方增长的。写输出会继续变慢，低于每秒 11 个，因为每写一个字要回看的 KV 翻了一倍。

从 ④ 机制 2 推出，数字用 ⑤ 的实测点外推（未实测，估算）。

5. 预测：同一段日志，把窗口从 8192 换成 100 万的模型，“埋在中间找不到”的问题会消失吗？

不会因为窗口变大而消失。窗口大小决定装不装得下，不决定注意力怎么分配；能不能找到取决于模型本身的长文能力和材料有多杂。大模型在 3000 个 token 上基本没问题，是因为它更强，不是因为窗口大。

从 ④ 机制 1 和机制 3 的区别推出

6. 放回全景：第 3 站前后各发生了什么？如果第 3 站的检查不存在（没人量长度），值班助手把一整天的日志发出去，整条链路会怎样？

第 3 站之前是第 2 站把文字切成 token，之后是第 4、5 站查向量、读输入。一整天的日志约 70 万个 token：本机 8192 的窗口在入口就返回 400，后面所有站都不会发生；换 100 万窗口的 Claude 能装下，第 5 站读输入要很久，第 10 站光输入就约 2.9 美元一次，而那一行 Full GC 夹在几千行中间，第 6～8 站写出的回答很可能没引用它。

档位：标准。本机跑过（2 核 ARM，llama.cpp b12618，Qwen2.5-0.5B-Instruct Q4_K_M，窗口 8192，Python 3.13，2026-11-22）：超长 400 的返回、四个长度下的读输入耗时和写输出速度、三个位置的埋针（各一次）。按文档：Claude Opus 5.5 窗口 100 万、单次最多输出 12.8 万，Haiku 5.5 长提示分档价格，models.retrieve 的 max_input_tokens 字段，Claude 把长材料放前面、问题放最后的提示建议。按公开研究：Liu 等人 2023 “Lost in the Middle”。按模型配置估算：KV 缓存每个 token 12 KB。实验台的本机耗时是拟合公式，超出 4232 个 token 的部分是外推。
