改了一句提示词之后

值班助手的提示词里改了一行：排查第 1 步从“先看日志”换成“先查知识库”。这张全景回答两件事：评测怎么发现它变差了，trace 怎么指出是哪一步出的错。从改动、CI、评测、门禁，一直走到灰度上线后看线上指标。

场景：PR #57，一行“省 token”的改动

谁
你，值班助手的开发者。值班助手就是站 04 起一直在长的那个排障 agent：5 个工具，查日志、解析 GC、看线程栈、查知识库、堆转储（要人点头）。
改了什么
PR #57 只动了 prompts/oncall-system.md 的一行，版本号 @3 → @4。SOP 第 1 条从“先看这段时间的报错和慢请求日志”改成“先到知识库找相似经验，有现成结论就直接用”。
为什么改
知识库查一次就够，能省两三轮工具调用。看上去是个降本的好改动。
期望
评测分数不比 @3 差，每次排障的 token 少一些。

结果：CI 里的评测 job 红了。本想省 token，@4 的平均输出 token 反而从 291 涨到 376、耗时从 64 秒涨到 81 秒；“怪错方向”逐条配对变坏 11 条、变好 3 条，超出了噪声线。trace 显示：47 条用例第 1 轮就去翻了知识库，知识库里全是 GC 经验，结论跟着往 GC 上推。

这次改动的几个数（实测）

同一套 50 条用例、同一个本机模型（Qwen3-1.7B），只差提示词这一行，各跑一遍。

指标@3（基线）@4（PR #57）门禁怎么看
通过2 / 503 / 50变坏 1、变好 2：分不出（基线太低，这项比不出差别）
第 1 轮就看现场50 / 504 / 50轨迹指标，单独报
怪错方向3038逐条配对变坏 11、变好 3，超出噪声线 7.5：红
平均输出 token / 条291376×1.29，超过 ×1.2：红
平均耗时 / 条64 秒81 秒×1.28：红

用例 03-slow-sql（索引被删的慢 SQL）是最典型的一条：@3 第 1 轮查日志，看到慢 SQL，判分通过；@4 第 1 轮拿告警原文“P99 4.2 秒”去翻知识库，最后才查到那行慢 SQL，结论却写成“GC 导致的停顿”。第 9 站就打开它的 trace。

1提示词 @4：SOP 第 1 条改了

PR #57 只改了 prompts/oncall-system.md 的一行：第 1 步从“先看这段时间的报错和慢请求日志”换成“先到知识库找相似经验，有现成结论就直接用”。文件头的版本号从 @3 变成 @4。

为什么要它提示词就是值班助手的代码。放进 git、带版本号，后面的分数、trace、线上指标才说得清是哪一版跑出来的。

往下一层提示词和 Skill 的版本管理

常出的事提示词写在代码里的字符串常量里，改了不留版本；线上变差时，说不清当时跑的是哪一版。

2CI 评测 job：PR 一开就跑

CI 看到 prompts/ 下有改动，起评测 job：拉起值班助手和模型，用 @4 跑整套用例，再把基线 @3 的分数取来对照。

为什么要它没有人会每次手动跑 50 条。评测不自动跑，迟早会被跳过。

往下一层评测进 CI：改提示词要过门禁

常出的事一次评测要一小时、花几十块钱，大家开始在提交信息里写“跳过评测”；或者只跑 5 条冒烟用例，这种改动根本抓不到。

3评测集：50 条，每条带现场

读出 50 条用例。每条有三样：问题（告警原文）、现场（这条用例专用的日志、GC 日志、线程栈）、标准答案（结论里必须说中的词、“原因”里不许怪的方向）。10 条是站 04 的第一批，另外 40 条从值班记录、被点了 👎 的回答和故意造的边角情况里收来。

为什么要它两次分数能比，前提是考的是同一套题。

往下一层评测集：从真实问题里收，扩到 50 条

常出的事50 条里 40 条都是 GC 问题，分数很好看，其实只考了一类故障。

4值班助手 ×50：每次调用记一个 span

每条用例先布置现场，再跑一遍值班助手 @4。每次模型调用、每次工具调用各记一个 span，里面有耗时、输入和输出 token、调了哪个工具、带了什么参数、返回了什么。这些 span 挂在同一个 trace 下，trace 上标着提示词版本 @4 和用例编号。

为什么要它只留最终回答，就只知道“答错了”，不知道错在哪一轮。span 把过程留了下来，第 6 站和第 9 站都要用它。

往下一层Tracing：每次模型和工具调用的耗时、token

常出的事只记了最终回答；或者 span 上没有提示词版本，灰度时两版的数据混在一起分不开。

5打分器：规则断言、参考答案、LLM 评委

每条回答过三道关。规则断言：有没有空回答，有没有编出现场里没有的数字。对照参考答案：结论说中了没有，“原因”那句有没有怪错方向。LLM 当评委：结论和引用的证据对不对得上。

为什么要它回答是自然语言，assertEquals 用不上。能用代码判的先用代码判，判不了的才请评委。

往下一层怎么打分：规则断言、参考答案、LLM 当评委

常出的事评委和被测的是同一个小模型，看不出自己编的数字；评委的打分从来没和人工标注对过。

6轨迹检查：先看现场了吗

从 span 里取出工具调用的顺序，逐条检查：第一次查现场是在第几轮，有没有查空了就开始猜，有没有提议危险操作，几轮收的尾。@4 的轨迹里，大多数用例第 1 轮调的都是 search_notes。

为什么要它结论碰巧对了，过程可能是猜的，换个现场就会错。看过程才能发现“对得不稳”。

往下一层不只看结果，也看过程（轨迹评测）

常出的事把轨迹规定得太死，比如“必须先查日志再查 GC”，另一种同样合理的查法也被判成错。

7对比基线：逐条配对，看是不是噪声

同一批 50 条，@3 和 @4 逐条对照：@4 修好了几条，弄坏了几条，净变化多大，有没有超出噪声。同一版提示词跑两次，本来就会有几条结果翻面，所以先要量出噪声有多大。

为什么要它模型的输出不确定，一次分数说明不了什么。改一处提示词，常常这几条变好、那几条变坏，只看总分会互相抵消。

往下一层为什么必须评测：输出不确定，改一处坏一片

常出的事通过率多了 2 条就宣布“变好了”；或者总分没变，没发现坏掉的那几条全是同一类故障。

8门禁：低于基线就红

门禁有几条规则：不许新增违规调用；通过、没怪错、没编造数字、看过现场逐条配对，变坏不能超出噪声线；平均输出 token 和耗时不能超过基线的 120%。@4 红在三处：“没怪错”变坏 11 条、变好 3 条（噪声线 7.5），输出 token ×1.29，耗时 ×1.28。PR 合不进去。

为什么要它评测跑完没人看，就等于没跑。红了合不进去，才真正挡得住。

往下一层评测进 CI：改提示词要过门禁

常出的事门槛写死成“80 分”。换了模型、加了用例，要么全红要么全绿，大家很快就不看它了。

9trace 后台：定位到第 1 轮

在 trace 后台按 prompt.version = @4、用例 03-slow-sql 筛出这一条：第 1 轮模型就调了 search_notes，查询词是告警原文“P99 4.2 秒”，知识库返回的都是 GC 经验；接着看了 GC 日志和线程栈，最后一轮才查到 SlowSqlInterceptor SQL 耗时 4210ms，结论却写成“GC 导致的停顿”。于是改成 @5：知识库挪回第 4 步，加一句“知识库只给方向，结论必须引用现场证据”，再跑一遍。

为什么要它评测只能说“变坏了”，trace 才能说“坏在哪一步、为什么坏”。没有它，只能凭感觉改提示词。

往下一层Tracing；轨迹评测

常出的事trace 只采样 1%，偏偏没采到出事的那条；工具的返回内容没记下来，看不出模型当时看到了什么。

10灰度 5%：看四个线上指标

@5 合并后，先只给 5% 的告警用，24 小时里和 @3 对照四个数：成功率（值班同学采纳结论的比例）、每次排障的成本、P95 延迟、转人工率。都没变坏，再全量。

为什么要它评测集只有 50 条，线上的问题比它多样得多。离线过了，线上还要再证一次。

往下一层线上指标：成功率、成本、P95 延迟、转人工率 待做

常出的事只盯成本和延迟，@4 这种省钱的改动看上去全是好处；成功率要等值班同学反馈，总是慢一拍才掉。

这张全景没走到的

  • 换模型、升级模型怎么回归：这张全景只改了提示词。换模型走的是同一条链路，只是第 1 站改的是模型名，而且 50 条用例几乎每条的回答都会变，噪声比改一行提示词大得多。它是这张全景的“下一圈”，知识点页里用本机的两个模型实际换一次。
  • 补给：够用的统计（样本量和置信区间）：第 7 站“是不是噪声”要用到。学习地图上它是站 09 的补给页，还没做。

预测题

1. 评测集从 50 条砍到 10 条，同样是 @4 这个改动，门禁还拦得住吗？

很可能拦不住。10 条里 @4 只坏掉一两条，而同一版跑两次本来就会翻一两条，差值落在噪声里，门禁要么放过，要么为了拦它把门槛定得太紧、天天误报。

从第 3、7、8 站推出：门禁比的是“差值有没有超出噪声”，样本越少，噪声范围越宽。

2. 第 5 站的评委就用被测的那个 1.7B 小模型，会出什么事？

它和被测模型错在同一处：看不出现场里没有的数字是编的，也偏爱和自己写法相近的回答。分数会虚高，而且 @3 和 @4 一起虚高，差值反而被压小。

从第 5 站推出：评委本身也要拿人工标注对一遍，并且最好比被测模型强。

3. 如果 @4 没过评测就直接全量，线上哪个指标先动？方向是好是坏？

成本和 P95 先动，而且是“变好”：少调了两三轮工具。成功率和转人工率要等值班同学按结论去查、发现不对，才会慢慢变坏。只看先动的那两个，会把这次改动当成功。

从第 4、10 站推出：成本和延迟在 span 里马上就有；成功率要靠人反馈，天然滞后。离线评测存在的意义就在这里。

4. span 上没记提示词版本，灰度期间成功率掉了，能看出是新提示词的锅吗？

看不出。5% 灰度和 95% 老版本的请求混在一起，只能看到总的成功率掉了一点，分不开是哪一版、也可能只是那天的告警更难。

从第 1、4、10 站推出：版本号写进每个 span，指标才能按版本拆开对照。

5. 把第 4 站的采样温度设成 0，是不是同一版跑两次就一模一样，不用量噪声了？

不是。服务端的批处理、前缀缓存会让同一个提示在温度 0 下也给出不同的输出（站 06 在本机就遇到过）；用云端 API 时还有后台模型的变化。更重要的是，“改一处坏一片”说的是不同用例之间的此消彼长，和温度无关。

从第 4、7 站推出：噪声要量出来，不能靠参数假设它不存在。

下一圈

  • 换模型：Qwen3-1.7B 换成另一个模型，同一套 50 条跑完，能不能换？难在每条回答都会变，成本和延迟也一起变，要在质量、成本、速度三个方向上一起下结论。
  • 线上回流：把线上被点 👎、被转人工的 trace 自动变成新用例，评测集自己长大。难在每条都要补标准答案，还有日志里的隐私数据。
  • 长任务和多 agent：站 10 的任务要跑几十分钟、分给几个 agent。难在一次评测的成本和时长都翻了几十倍，轨迹也从一条线变成了一棵树。
