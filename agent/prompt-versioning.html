提示词和 Skill 的版本管理

提示词就是 agent 的代码，要像代码一样管：发布过的版本不许原地改，每个版本带一个内容指纹；线上用标签指向某个版本，上线和回滚都只是移动标签；分数、span、线上指标都盖上版本戳。还要记住，决定行为的不只是系统提示词：工具说明、Skill、模型和参数要打成一个发布包一起管。

全景：改了一句提示词之后 · 第 1 站地图：站 09 · 提示词和 Skill 的版本管理深度：会用

这一页的位置站 09 第 6 个知识点。全景第 1 站看着最简单，所以放在评测和 trace 之后学：版本号只有写进了每份分数、每个 span，才派得上用场。Java 板块的配置中心和灰度发布是它的老朋友。

①为什么学：出了事，先要知道跑的是哪一版

在全景第 1 站，PR #57 改了一行提示词，从 @3 变成 @4。之后的每一步都要用到这个版本号：CI 要拿 @4 的分数和 @3 比；trace 后台要按 prompt.version = @4 筛出那条用例；@5 灰度时，线上指标要按版本拆开；万一 @5 上线后出事，要能一条命令退回 @3。版本号没管好，这几件事一件都做不成。

②老办法：提示词是代码里的一个字符串常量

站 04 的值班助手就是这么写的：oncall.py 里一个 SYSTEM = """…"""，工具说明是同一个文件里的 TOOLS 列表。能用，可一到这一站的场景就处处卡住：

  • 没有版本号：改提示词就是改代码，评测分数、trace 上只能记 git 提交号；同一个提交里改了五个地方，分不清是哪个。
  • 回滚要重新发布：提示词出事，要回滚整个服务的代码，连带回滚了别人的改动。
  • 灰度做不了：一个进程里只有一个 SYSTEM，没法让 5% 的告警用新提示词。
  • 只管了一半：站 04 那次 v1 → v2 只改了 TOOLS 里的说明，系统提示词一个字没动，可行为变化比改提示词还大；只给系统提示词编版本，这类改动照样是“无版本”的。
  • 谁都能悄悄改：常量改一个字，代码评审时看着像是改错别字，评测没跑就合进去了。
不懂精华时的典型误用：给提示词文件起名 v1、v2，然后为了“改个小地方”直接编辑 v2。版本号还在，可它已经不能代表一份确定的内容了：上周用 v2 跑出来的分数、trace，和今天的 v2 不是同一个东西。

③选谁：四种放法

放在哪好处代价
代码里的常量最简单，和代码一起评审没有独立版本，回滚要整体发布，不能灰度
文件 + git，版本写在文件名里（本页）一个版本一个文件，内容不可变、带指纹；评审、diff、历史都靠 git；评测直接读文件线上切换要再加一层“标签 → 版本”的指针
配置中心（Nacos、Apollo）热更新，按实例、按比例灰度，Java 团队很熟配置中心本身的“版本”常常就是最后一次修改，要自己约定不可变
提示词管理平台（Langfuse 等）版本自动递增、标签（production、staging）、按标签取、和 trace 打通提示词不在代码仓库里，评测和代码评审要另外接

本页用文件 + git 做唯一的源头，再用一个 labels.json 当“标签 → 版本”的指针。线上把这个指针放进配置中心或提示词平台都可以，规矩不变：版本不可变，上线和回滚只移动指针。

④原理：不可变的版本、指针一样的标签、一个发布包

先知道这些
  • 内容指纹：对文件内容算 sha256，取前 12 位。内容改一个字，指纹就完全不同；内容一样，在哪台机器上算都一样。
  • Skill：一个文件夹，里面一个带 name、description 头的 SKILL.md，外加脚本和资料，agent 需要时才加载。见Skill 那页。
  • span 上的版本属性：OpenTelemetry 约定里有 gen_ai.prompt.name、gen_ai.prompt.version。见上两页的 Tracing。

机制 1 · 版本不可变：版本号 + 指纹，两样一起记

版本号（@4）是给人看的，指纹（951128fb010d）是给机器核对的。规矩只有一条：一个版本号一旦登记，内容就不许再变。prompts.lock.json 记着每个版本登记时的指纹，CI 里跑 check：有人原地改了 @3，文件指纹和登记的对不上，PR 直接红。这和 Maven 仓库里已发布的 1.2.0 不许覆盖、Docker 镜像用 digest 而不只用 tag，是同一个道理。

机制 2 · 发布包：决定行为的东西要一起编版本

值班助手的行为由一整包东西决定：系统提示词、工具说明、Skill 文件、模型名、温度、是否思考、最多几轮。只给系统提示词编版本，站 04 那种“只改工具说明”的改动就漏网了。做法是把这些全列进一个清单，对清单算一个总指纹。⑤ 里真算了一次：系统提示词同样是 @3，工具说明从 v1 换成 v2，发布包的指纹就从 55f946871efa 变成了 c7a96dce9f2a。评测分数和 trace 上记这个总指纹，才能说清“这个分数是哪一整套配置跑出来的”。

机制 3 · 标签是指针：上线、灰度、回滚都只移指针

线上代码不写死版本号，而是按标签取：load(label="production")。production → @3、canary → @5，灰度就是让 5% 的请求按 canary 取。全量是把 production 挪到 @5，回滚是挪回 @3，每次移动都记一条历史（谁、什么时候、从哪到哪）。版本文件一个字没动，所以回滚后的行为和当初的 @3 一模一样。线上进程一般会缓存取到的提示词，标签挪了以后，要等缓存过期或收到通知才生效，回滚时要算上这段时间。

机制 4 · 每条记录盖版本戳，Skill 的版本靠来源地址

分数文件里记 提示词 和 sha，span 上记 gen_ai.prompt.name、gen_ai.prompt.version（约定里要求：用了有名字的提示词模板时必填版本），线上指标按 prompt_version 打标签。Skill 不太一样：约定里有 gen_ai.skill.name，没有 skill 的版本属性，版本要靠 gen_ai.skill.source.uri 表达，约定特意写了它应该指向 Skill 的来源，而不是运行时临时解压到的目录。最稳妥的写法是指到带提交号或 tag 的 git 地址。

为什么这样设计

不可变版本 + 标签指针

  • 一个版本号永远对应同一份内容，历史上的分数、trace 永远解释得通。
  • 上线、灰度、回滚都是改一个指针，几秒钟，不用重新发布代码。
  • 指纹让“偷偷改了”无处藏身，CI 一跑就红。
  • 代价：版本文件越攒越多；每个改动都要起新版本号、登记、过评测。

被放弃的：可编辑的“当前版本”

  • 只有一份“现在的提示词”，改了就覆盖：上周的分数对应的内容已经找不回来。
  • 回滚靠“改回去”：凭记忆改，很难一字不差。
  • 灰度时两个版本必须同时存在，一份可编辑的文件做不到。
决定胜负的约束：评测、trace、线上指标都是“事后对账”：要拿一个版本号去找当时的内容和结果。版本一旦可变，对账就对不上；所以版本不可变，变化全放在“哪个标签指向哪个版本”上。

实验台：改了这个，要不要重跑评测？

先猜：系统提示词、工具说明都不动，只把温度从 0.8 改成 0（想让输出更稳定）。要不要重新跑评测？

页面里的指纹是用一个简单的字符串哈希模拟的，只用来演示“任何一项变了，总指纹就变”；真正的 sha256 指纹在 ⑤ 的运行输出里。基线是线上那一包：@3 + 工具说明 v2 + 现在的 Skill + qwen3-1.7b + 温度 0.8。

⑤跑起来：登记、核对、标签、发布包

提示词文件就放在评测运行器读的地方：eval-dataset/prompts/oncall-system@3.md、@4.md、@5.md。版本管理的脚本只做五件事：登记指纹、核对、看 diff、移标签、算发布包。

⑥细节·规范·优化

第一圈 · 注意事项

1原地改已发布的版本实测← ④ 机制 1
现象
今天跑 @3 的分数和上周的 @3 对不上，以为是噪声，查了半天，原来有人往 @3 里加过一句。
根源
版本号还在，内容已经变了，历史分数和现在的 @3 对不上。
做法
指纹登记 + CI 跑 check；⑤ 的 demo 里这种改动当场变红。
2只给系统提示词编版本← ④ 机制 2
现象
@5 上线后出事，回滚到 @3，问题还在：同一次发布里工具说明也改了，它没有版本，没跟着回去。
根源
行为由一整包配置决定，只管其中一样，回滚就只回了一半。
做法
发布包清单列全：系统提示词、工具说明、Skill、模型、温度、轮数上限；标签指向发布包，而不只是提示词。
3标签挪了，线上还在用旧版本← ④ 机制 3
现象
回滚命令几秒就执行完了，可接下来十分钟 trace 里还有新版本的请求。
根源
线上进程按标签取到提示词后会缓存，标签变了，要等缓存过期或收到推送。
做法
缓存时间写进回滚手册；配置中心用推送（Nacos 的监听）；用 span 上的 gen_ai.prompt.version 确认切换真的生效了。
4Skill 的来源记成了临时目录← ④ 机制 4
现象
span 上 gen_ai.skill.source.uri = /tmp/skills-8f3a/oncall-triage，事后根本不知道加载的是哪一版。
根源
约定里没有 skill 的版本属性，版本只能靠来源地址；记成运行时解压的目录，等于没记。
做法
来源写成带提交号的地址，比如 git+https://…/skills/oncall-triage@a1b2c3d；Skill 文件夹也算进发布包指纹。
5模板变量让同一个版本说出不同的话← ④ 机制 1
现象
提示词里有 {today}、{oncall_name} 这类变量，同一个 @5，周一和周五的行为不一样。
根源
指纹只管模板，渲染后的内容每次不同。
做法
变量尽量少、尽量放进用户消息而不是系统提示词；评测用例里把变量固定住；span 里记模板版本，必要时再记渲染后的指纹。

第二圈 · 使用规范

  • 一个 PR 只改一个版本：新版本文件、登记、评测结果一起提交。防的是一次改动说不清是谁的功劳。
  • 版本说明写在 PR 里：为什么改、期望哪个指标变好、评测结果。防的是半年后没人知道 @4 为什么存在。
  • 线上只按标签取：代码里不出现具体版本号。防的是回滚要改代码、重新发布。
  • 标签的每次移动都留历史：谁、什么时候、从哪到哪。防的是事故复盘时说不清什么时候切的版本。
  • 已发布的版本不删：历史 trace 和分数还在引用它。防的是事后复现不了。

第三圈 · 优化和深处

按标签灰度，按版本出报表

灰度时 canary 和 production 同时在线，线上指标按 prompt_version 拆开，两版的成功率、成本、P95 并排比（全景第 10 站，后面“线上指标”那页）。这就是 Java 里的金丝雀发布，只是比的指标换成了 agent 的。

谁能改提示词

提示词放进 git 以后，产品和运营同学也想改。可以给他们一个只能“提新版本”的入口（平台界面或模板 PR），评测和评审照走；不要给“直接改线上”的入口。改提示词的权限，本质上就是发布权限。

下一圈

  • 评测进 CI：check 只是第一步，下一页把评测本身接进 CI，新版本不比基线差才放行。
  • 提示词平台：接 Langfuse 这类平台，标签、版本、trace 在一个界面里，并和 git 双向同步。
  • 多语言、多租户：同一个提示词有中英文两版、不同客户不同版本时，版本号怎么设计。
  • 换模型：模型名也在发布包里，换模型就是发一个新包，回归方法见最后一页。

↺回到⑤：改一改

  1. 把发布包接进评测：在 eval-dataset/harness.py 的 run_suite 里，把 bundle() 的总指纹写进 scores.json。做对了会看到：只改工具说明再跑，分数文件里的指纹变了，系统提示词的版本没变。（坑 2）
  2. CI 第一步：写一个 GitHub Actions 的 job，只跑 check。做对了会看到：原地改 @3 的 PR 变红，另起 @6 的 PR 变绿。（坑 1）
  3. Skill 进 span：在 tracing 那页的 run_traced 里，给根 span 加上 gen_ai.skill.name 和带提交号的 gen_ai.skill.source.uri。做对了会看到：瀑布图上能看出用的是哪一版 Skill。（坑 4）

自测

1. 用一句话说出这一页的精华

发布过的版本不可变、带指纹，线上用标签指向版本，上线和回滚只移标签；版本要覆盖整个发布包，并盖在每份分数、每个 span 上。

2. 提示词写成代码常量，疼在哪？

没有独立版本号，分数和 trace 只能记提交号；回滚要整体重新发布；一个进程只有一份，灰度做不了；改一个字在代码评审里很容易被放过。

3. 为什么版本号之外还要指纹？

版本号是人起的，可能被原地改了内容却没改号；指纹由内容算出来，内容一变就变。两样一起记，CI 才能发现“号没变、内容变了”。

4. 预测：线上 production 从 @5 回滚到 @3 以后，trace 里马上就全是 @3 了吗？

不一定。线上进程缓存了取到的提示词，要等缓存过期或收到推送；这段时间里还会有 @5 的请求。看 span 上的 gen_ai.prompt.version 才能确认切换完成。

从 ④ 机制 3 推出：标签是指针，可读指针的人可能还拿着旧值。

5. 预测：只把模型从 qwen3-1.7b 换成 qwen3-0.6b，提示词版本号不变，评测分数还能和以前的比吗？

能比，但比的是两个不同的发布包：提示词版本一样，发布包指纹不一样。如果分数只记了提示词版本，两次分数看起来是“同一个 @3”的，就会把模型的差别误当成噪声。

从 ④ 机制 2 推出：模型也在发布包里。

6. 放回全景：第 1 站前后各发生了什么？版本没管好，整条链路会怎样？

第 1 站之后是 CI 起评测（第 2 站），评测拿新版本和基线比；第 10 站灰度时按版本拆指标。版本没管好：CI 不知道该和哪个基线比，第 9 站按版本筛 trace 筛不出来，第 10 站两版指标混在一起，出事了也退不回确定的上一版。
