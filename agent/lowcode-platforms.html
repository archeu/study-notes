低代码平台：Dify、Coze、n8n

低代码平台把控制流画在画布上：节点是一步，连线是顺序，节点之间传的数据用表达式取。n8n 擅长连系统、搬数据，全景第 1 站“接告警、去重、转发”在它上面是 4 个节点、零行服务代码；Dify 和 Coze 擅长做 LLM 应用（对话、RAG、Agent、工作流）。省掉的是服务的样板代码；交出去的是测试、代码评审和细节的控制权。本机实测还撞上一个和平台无关、却很容易踩的坑：只按告警指纹去重，下周同一个告警再响会被当成重复丢掉。

①为什么学：连线活不值得写服务

在全景第 1 站，这一步要解决的是：Alertmanager 会把告警 POST 过来，而且会重发（告警状态变化、到了 repeat_interval）。要有人接住它、按告警去重、再转给值班助手；第 9 站张三点批准，也要有人把点击转成 /resume 请求。这些活没有业务逻辑，写成服务却要建工程、写测试、上流水线。地图上这一站的要求里还有一句：“再用 Dify 搭一个分诊流程对比”。26 份 Agent 岗位 JD 里，9 份提到低代码平台。

②老办法：写一个小服务

  • 写代码的做法：一个 FastAPI 或 Spring Boot 服务，收 Webhook、拆告警、用 Redis 的 SET NX 去重、再调值班助手，加上重试、日志、部署。几十行逻辑，外面包一整套工程。
  • 没有业务逻辑的胶水代码最没人愿意维护：告警格式改了、要多转发一个地方，都得走一遍开发、评审、发布。
  • 好处是测试、评审、版本管理全在熟悉的流程里，出了问题能断点调试。
不懂精华时的典型误用：把低代码当成“不用想”：拖几个节点就上线，去重键、失败重试、谁来看执行记录都没想。平台省的是样板代码，不省设计；⑥ 的头号坑就是去重键选错，和用不用平台无关。

④原理：节点、连线、表达式，外加一个执行记录库

先知道这些
  • n8n 的数据单位是“项”（item）：每个节点收一组项、吐一组项。Webhook 收到一次 POST 是一项；Split Out 把里面的 alerts 数组拆成每条告警一项；后面的节点对每一项各跑一次。某个节点吐出 0 项，它后面的节点这次就不执行。
  • 表达式：{{ $json.fingerprint }} 取当前这一项的字段，写在节点参数里，像模板引擎。
  • 执行记录存库：每次触发是一次 execution，输入输出都存进 n8n 自己的数据库（默认 SQLite），编辑器里能回看。跨执行的状态（比如去重时“见过哪些值”）也存在这里。
  • 2.x 的发布：工作流分草稿和已发布版本，只有已发布的版本会注册生产 Webhook。CLI 是 n8n import:workflow 再 n8n publish:workflow --id=…；启动日志里写着“Processed 0 draft workflows, 1 published workflows”。
  • Alertmanager 的 fingerprint：按告警的标签集算出来的。标签一样，指纹就一样，不管是哪一天响的。

机制 2 · 去重键：同一件事，还是同一类事

拿什么去重同一次触发的重发下周同一个告警再响
fingerprint挡住（实测）也被挡住：真故障没人管（实测）
fingerprint@startsAt挡住（实测）放行，thread_id 是新的（实测）

指纹标识的是“哪一类告警”，startsAt 标识的是“这一次触发”。去重、thread_id、写操作的幂等键要用的都是“这一次”，也就是事件键：指纹 + 触发时间。这一站前面几页（全景、写操作）原来只写了指纹，发现这个问题后已经一并改正。

为什么这样设计：把控制流画出来

画布：节点 + 连线 + 表达式

  • 流程一眼看得见，不写代码的人也能改：告警要多转发一个地方，加一个节点就行。
  • 每次执行的输入输出都存着，出了事在编辑器里点开就能看到每个节点收到了什么。
  • 代价：逻辑散在一个个节点的配置和表达式里；测试、代码评审、合并冲突都比代码难。工作流导出是一大段 JSON，⑤ 里手改时就撞上了“节点 id 重复，导入失败”。

代码：LangGraph、Spring AI

  • 单测、评审、版本管理、断点调试，全在熟悉的流程里。
  • 细节都能控制：去重键、重试、幂等、审计怎么做，全由自己定。
  • 代价：没有业务逻辑的胶水也要建工程、走发布。
决定胜负的约束：改得最频繁、最不需要深度测试的部分（接谁、转给谁、通知谁）放在画布上最划算；出错代价高、要测试和审计的部分（分诊、审批、写操作）放在代码里。全景就是这么切的：第 1、9 站在 n8n，其余在值班助手里。最后一页专门讲这条线怎么划。

⑤跑起来：全景第 1 站搭在 n8n 上

  1. 1 镜像docker pull n8nio/n8n:2.49.7（1.32 GB，本机拉了 1 分 40 秒）。数据目录挂到宿主机，用 host 网络，n8n 在 5678 端口，值班助手的桩在 8099。
  2. 2 导入并发布工作流写成 JSON（4 个节点），n8n import:workflow 导入，n8n publish:workflow --id=… 发布。在编辑器里拖也一样，导出来就是这段 JSON。
  3. 3 桩和告警oncall_stub.py 收 POST /incidents 并记下来；send_alerts.py 照 Alertmanager 的 Webhook 格式发：同一告警三次（首次、状态变化重发、repeat_interval 重发）+ 另一个告警。

读出来的结论
  • 4 个节点、零行服务代码，全景第 1 站就有了：接住、拆开、去重、转发，Webhook 二三十毫秒就回应。
  • 按指纹去重挡住了重发，也挡住了下周那次真故障；改成“指纹 + 触发时间”两头都对。这是事件键的设计问题，换成代码照样会错。
  • Webhook 收到就回 200，后面转发失败了 Alertmanager 也不知道（⑥ 坑 2）。
  • 修正版是导入第二个工作流、发布，正在跑的 n8n 十几秒后就接上了新的 Webhook，没重启。改流程比改服务快得多，这正是低代码的卖点。
到这里已经能交差了：会在 n8n 上搭“触发 → 处理 → 调接口”的工作流，会导入、发布、看执行记录；知道 Dify、Coze 各适合做什么。
已知还没处理的细节：去重键（坑 1）、收到就回 200（坑 2）、去重历史的上限和存放位置（坑 3）、手改 JSON（坑 4）、许可证（坑 5）。

⑥细节

第一圈 · 注意事项

1只按告警指纹去重，下次再响被丢掉实测← ④ 机制 2
现象
同一个告警下周又响了，n8n 把它当成重复丢掉，值班助手什么都没收到。
根源
Alertmanager 的 fingerprint 按标签集算，同一类告警永远是同一个指纹；它标识“哪一类”，不标识“哪一次”。
做法
去重、thread_id、写操作的幂等键都用事件键：fingerprint@startsAt。
2收到就回 200，后面失败了没人知道实测← ④ 机制 1
现象
值班助手挂了，n8n 转发失败，可 Alertmanager 拿到的是 200。更糟的是去重节点在转发之前就记住了这个事件键：实测值班助手停着时进来一个新告警，恢复后 Alertmanager 重发，值班助手收到 0 次。
根源
Webhook 节点设的是 responseMode: onReceived：收到就回应（实测二三十毫秒），后面的节点在回应之后才跑。
做法
要么改成等最后一个节点跑完再回应（失败就回错误，让 Alertmanager 重发；这时去重也得挪到转发成功之后，或者交给下游的幂等），要么给工作流配错误处理流程，失败时发通知；定期看执行记录里的失败项。
3去重的记忆存在哪、能记多少按源码← ④ 机制 1
现象
换了一个 n8n 实例、清了库，或者见过的值超过了上限，之前去过重的告警又被转发一遍。
根源
“见过的值”存在 n8n 自己的库里；去重节点的选项里有作用域（节点 / 工作流）和历史条数上限（historySize），这些在节点包的参数定义里能看到。
做法
去重只当第一道筛子，真正挡重复的是下游（值班助手按 thread_id 恢复同一条线程、写操作的幂等键）；n8n 的数据目录要备份，多实例要用共享的数据库。
4手改工作流 JSON，导入失败实测← ④ 为什么这样设计
现象
复制一份工作流改成修正版时，四个节点的 id 被改成了同一个，导入报 duplicate_node_id。
根源
画布上的东西落到文件里是一段结构化 JSON，节点 id、连线按节点名引用，手改很容易改出不一致；也很难在代码评审里看出改了什么。
做法
改流程尽量在编辑器里改，导出的 JSON 进 Git 当版本记录；要批量生成就写脚本，并在导入前校验 id 唯一。
5拿来做对外的产品，许可证不允许按文档
现象
想把 n8n 或 Dify 包一层卖给客户，或者给多个客户各开一个空间。
根源
n8n 是 Sustainable Use License：只能为自己的内部业务或非商业用途使用和修改。Dify 是修改版 Apache 2.0：未经书面授权不能用源码运营多租户服务，不能去掉控制台里的 logo 和版权信息。
做法
公司内部自用一般没问题；要对外提供、多租户，先找法务看许可证或买商业授权。Coze Studio 是 Apache 2.0。

第二圈 · 使用规范

  • 工作流导出进 Git，改动走评审：画布方便改，也方便悄悄改坏。
  • 每个工作流配错误处理和失败告警：防坑 2。
  • 低代码只放“连线活”：触发、转发、通知、搬数据：判断和写操作留在代码里（最后一页细讲）。
  • 凭据（API key、token）放平台的凭据管理里，不写进节点参数：导出 JSON 时不会把密钥带出去。
  • 自部署先看许可证：防坑 5。

自测

1. 用一句话说出低代码平台的精华

把控制流画在画布上，节点之间用表达式传数据，执行记录存库；省掉胶水服务的样板代码，交出测试、评审和细节控制权。

2. 全景第 1 站自己写服务，疼在哪？

几十行没有业务逻辑的代码要包一整套工程、测试、发布，改个转发目标也要走一遍流程。

3. 下周同一个告警被当成重复丢掉，根源是哪条？

Alertmanager 的指纹按标签集算，标识的是“哪一类告警”；去重要的是“哪一次触发”，键里要带上 startsAt。

从 ④ 先知道这些和机制 2 推出。

4. 预测：Alertmanager 一次 POST 里带了两条不同的告警，修正版工作流会转发几次？

两次：Split Out 把它们拆成两项，两项的事件键都没见过，各自往下走，HTTP Request 节点对每一项各执行一次。

从 ④ 先知道这些里“项”的规则推出。

5. 预测：值班助手挂了 10 分钟，这期间 Alertmanager 重发了三次同一告警，恢复以后值班助手会收到吗？

收不到。第一次转发失败，但去重节点在它之前已经把这个事件键记成“见过”；后面的重发都被丢掉了，Webhook 又一直回 200。要么失败时不记、要么等最后一个节点再回应，要么靠失败告警让人补。

从 ④ 机制 1 和坑 2、坑 3 推出；本机实测过：值班助手停着时进来的新告警，恢复后重发收到 0 次。
