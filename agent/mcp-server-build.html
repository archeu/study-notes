写 MCP 服务端：Python 和 Java 各一个

写 MCP 服务端，就是把普通函数登记成工具：Python 用 MCPServer 加装饰器，Java 用 Spring AI 的 starter 加 @McpTool。工具名、说明、参数 schema 都从函数签名和注释生成，所以签名和注释就是模型读到的接口文档。这一页 Python 写 oncall（本机 stdio），Java 写 tickets（远程 HTTP），两个都被 Python SDK 和 Claude Code 连通。

①为什么学：值班助手的工具要变成别人也能接的服务

在全景第 9 站，这一步要解决的是：tools/call 到了服务端，要有人按名字找到函数、校验参数、执行、把结果包好。地图上这一站的任务写得很具体：把工具拆成 MCP 服务端，Python 一个、Spring AI 一个，接进 Claude Code 直接用。

②老办法：照着协议手写

第 1 页的 gateway_server.py 就是手写的：40 行，从 stdin 读一行、按方法名分派、往 stdout 写一行。能跑，但把它当正式服务端，要补的东西一条条对照：

要求手写（gateway_server.py）用 SDK
两个年代的协议都接不能：它只会 initialize，第 1 页实测只认新协议的客户端连它直接失败。Python 的 mcp 2.3.0 能，两种都接（第 3 页实测）。Spring AI 2.1.0 要在配置里选一种：MODERN 只接新协议，STREAMABLE 走老协议、新客户端会回退过来（⑥ 坑 3，实测）。
参数的 JSON Schema手写一份，和函数签名分开维护，改了一边忘了另一边。从类型注解或方法签名生成。
调用前校验参数没有：模型传错类型，函数里直接抛异常。按 schema 先校验，错了回一句说明。
HTTP 那一套请求头比对、Origin、202、SSE，全要自己写。第 3 页那几道关，SDK 都做了。
出错时给模型什么自己拼 isError 结果。抛异常就行，SDK 包成 isError（Python 要用 ToolError 才带原因，⑥ 坑 2）。
不懂精华时的典型误用：以为 SDK 生成了 schema 就万事大吉，函数名叫 query、参数叫 q、docstring 空着。生成出来的工具定义同样是 query(q)，模型照样不知道什么时候该调。SDK 省掉的是协议的活，接口文档还是要你写：签名和注释就是那份文档。

③选谁：Python 用官方 SDK，Java 用 Spring AI

候选是什么什么时候选
Python 官方 SDK（mcp 2.x）协议的参考实现之一；高层 API 是 MCPServer（1.x 里叫 FastMCP，2.x 改名）。Python 写服务端的默认选择，新协议跟得最快。
Spring AI 的 MCP 服务端 starter在官方 MCP Java SDK 之上做的自动配置：扫描 @McpTool，按配置选传输（stdio、WebMVC、WebFlux）。团队本来就用 Spring Boot；要接 Spring Security、Actuator、现成的 Service 层。
直接用 MCP Java SDK不带 Spring 的底层库（io.modelcontextprotocol.sdk:mcp 2.2.0）。不用 Spring 的项目，或者要嵌进别的框架。
手写按协议自己读写 JSON-RPC。只为了理解协议（第 1 页的 gateway），不用于正式服务。

本页学两个：Python 的 MCPServer 写 oncall，Spring AI 的 @McpTool 写 tickets。两者生成的工具定义、走的协议完全一样，客户端分不出谁是 Python 谁是 Java。

官方 SDK 还有 TypeScript、Kotlin、C#、Go 等语言。Spring AI 2.1.0 依赖的是 MCP Java SDK 2.2.0（本机 Maven 依赖树里看到的）。

④原理：签名生成定义，SDK 替你走完一次调用

先知道这些
  • 装饰器和注解扫描：Python 的 @mcp.tool() 在模块加载时把函数登记进服务端；Spring 启动时扫描带 @McpTool 的 Bean 方法，和 @RequestMapping 被扫成路由是同一个套路，见 Spring Boot 自动配置。
  • 从类型生成 JSON Schema：Python 靠类型注解（pydantic 在背后做），Java 靠反射拿方法参数的类型和名字。Java 的参数名默认不进 class 文件，要编译时加 -parameters（⑥ 坑 1 实测）。
  • Java 比方：@McpTool 方法 ≈ 一个 @PostMapping，@McpToolParam ≈ @RequestParam 加 Swagger 的 @Schema(description)；区别是“调用方”是模型，它只看得懂你写的说明。

机制 3 · 生命周期：进程什么时候起、资源什么时候建

Python：lifespan

一个 async 上下文管理器：yield 之前建资源（打开日志、连数据库），之后收尾。每次调用用 ctx.request_context.lifespan_context 拿到它。stdio 下每个客户端一个进程，所以 lifespan 也是每个窗口跑一遍；实测 Python 版从拉起到能答话约 0.68 s，常驻 67 MB。

Java：Spring 容器

工具类就是普通 Bean，构造器注入 Service、@PreDestroy 收尾，和写一个 Controller 没区别。实测 tickets 启动 3.1～3.5 s、常驻 183 MB，适合做长期跑着的 HTTP 服务，不适合做每个窗口都要拉起一次的 stdio 服务（⑥ 第三圈）。

为什么这样设计：定义从代码生成，而不是先写接口文件

代码即定义（SDK 的做法）

  • 定义和实现永远一致：改了参数，schema 跟着变，不会出现“文档说有 since、函数里没有”。
  • 写一个工具就是写一个函数，门槛最低，这正是规范的第一条设计原则“服务端要极容易写”。
  • 代价：命名和注释的质量直接成了接口质量；Java 还得记得 -parameters；生成的 schema 有时啰嗦（since 生成了 anyOf [string, null]）。

先写定义文件（OpenAPI 优先那种）

  • 定义能单独评审，适合跨团队约定的大接口。
  • 两份东西要同步，工具一多就漂移，模型读到的说明和实际行为对不上。
  • 一个只有三五个工具的服务端，要多维护一套文件和生成流程。
决定胜负的约束：MCP 服务端多是“把已有能力包一层给模型用”，工具小而多、改得勤。定义和实现分开维护，漂移是迟早的事；而对模型来说，说明和实际行为对不上，比没有说明还糟。

@asynccontextmanager
async def lifespan(server: MCPServer) -> AsyncIterator[Logs]:
    logs = Logs(app=oncall.APP_LOG.splitlines(), gc=oncall.GC_LOG.splitlines())
    log.info("载入日志：应用 %d 行，GC %d 行", len(logs.app), len(logs.gc))   # logging 默认写 stderr
    yield logs

mcp = MCPServer("oncall", version="1.0.0", lifespan=lifespan, instructions="…时间参数用 HH:MM…")

@mcp.tool(annotations=ToolAnnotations(read_only_hint=True, open_world_hint=False))
async def search_logs(keyword: str, ctx: Context, since: str | None = None, limit: int = 20) -> str:
    """在 order-svc 应用日志里按正则查某段时间的日志行。……"""
    _since_ok(since)                                    # 不合格 → raise ToolError("since 要写成 HH:MM……")
    try:
        pat = re.compile(keyword)
    except re.error as e:
        raise ToolError(f"keyword 不是合法的正则：{e}。要查字面上的括号请写成 \\(") from e
    logs: Logs = ctx.request_context.lifespan_context  # 启动时建好的东西
    rows = [r for r in logs.app if pat.search(r) and (since is None or r[11:16] >= since)]
    more = f"\n……还有 {len(rows) - limit} 行没显示，缩小时间或换关键字" if len(rows) > limit else ""
    return "\n".join(rows[:limit]) + more

            annotations = @McpTool.McpAnnotations(readOnlyHint = true, openWorldHint = false))

                             @McpToolParam(description = "评论正文：结论 + 证据") String text) { … }
}

⑥细节

第一圈 · 注意事项

1Java 的参数名变成 arg0、arg1实测← ④ 机制 1
现象
第一次启动 tickets，get_incident 的 schema 里参数叫 arg0。客户端按 {"id": "INC-1108"} 调，每次都回 “required property 'arg0' not found”。
根源
schema 靠反射拿参数名，而 javac 默认不把参数名写进 class 文件。用 spring-boot-starter-parent 当父工程时它会替你打开 -parameters，study-labs 的父工程不是它，所以没开。
做法
maven-compiler-plugin 配 <parameters>true</parameters>（Gradle 是 options.compilerArgs << '-parameters'），改完重编，启动后先列一次清单看参数名。
2异常给模型看多少：Python 太少，Java 可能太多实测← ④ 机制 2
现象
Python 里没接住的异常，模型只看到 “Error executing tool search_logs”；Java 里抛的 IllegalArgumentException，消息原样到了模型那边。要是 Java 那边抛的是 JDBC 异常，SQL、表名、内网地址也会一起过去。
根源
两个 SDK 对“没预料到的异常”默认做法不同：Python SDK 只给笼统一句、细节写服务端日志；这次实测的 Spring AI 把异常消息放进了 isError 结果。
做法
两边都只把“写给模型看的人话”当结果：Python 用 ToolError，Java 抛自己的业务异常、在工具方法里接住底层异常再换成人话。底层细节写服务端日志。
3Spring AI 一次只能讲一个年代的协议实测← ④ 机制 3
现象
protocol=MODERN 时，只会老协议的客户端发 initialize，回 400 和 “Missing required header: Mcp-Method”。换成 STREAMABLE 后，老客户端能连，Python SDK 的自动模式和 Claude Code 也都回退过来连上了（协商出 2025-11-25）。
根源
Spring AI 2.1.0 的 spring.ai.mcp.server.protocol 只能取一个值（SSE、STREAMABLE、STATELESS、MODERN），本机没有找到“两种都接”的选项；Python SDK 2.3.0 则是同一个端点两种都接。
做法
还有老客户端要接时用 STREAMABLE：新客户端会自己回退。确认所有客户端都升级了再切 MODERN，换来无会话、好扩容。
4多实例部署时，一台封的请求状态另一台解不开实测← ④ 机制 3
现象
启动日志的警告原话：没有配置密钥，生成了一个每个进程随机的密钥；这个实例封装的状态，别的实例打不开，多实例部署请配置共享密钥。
根源
新协议里服务端要客户端补输入时（input_required），会把“做到哪了”封成一段 requestState 交给客户端带回来，自己不存。带回来时如果落到另一台实例，它没有那把密钥就验不过。无会话的代价，就是状态要能被任何一台解开。
做法
多实例时配 spring.ai.mcp.server.modern.request-state-secret，所有实例用同一个值，放配置中心或密钥管理里，别写死在代码里。

第二圈 · 使用规范

  • 函数名就是工具名，写成“动词_名词”；说明写清“什么时候用、返回什么”；每个参数都写说明：防的是模型挑错工具、填错参数。站 04 的工具怎么设计全部适用。
  • 能预料的失败都写成人话：Python 用 ToolError，Java 用业务异常。防坑 2。
  • 结果要能截断：给 limit 参数，超出时告诉模型“还有多少行、怎么缩小”。防一次结果塞满上下文。
  • 日志只走 stderr 或自己的日志系统：协议里的 logging 在 2026-07-28 已标为弃用（实测 ctx.info() 会报弃用警告），排查靠服务端自己的日志和监控。
  • 每个工具一个内存测试：Client(mcp) 起步，至少测“正常、参数错、找不到”三种。防改说明或签名时把接口改坏。
  • 版本号写进 serverInfo：MCPServer(..., version=)、spring.ai.mcp.server.version。客户端日志里能看到对面是哪个版本，排查时省一半力气。

第三圈 · 优化和深处

Java 做 stdio 服务端的三件事

Spring AI 打开 spring.ai.mcp.server.stdio=true 就能走 stdio，但 Spring Boot 默认往 stdout 打 banner 和控制台日志，正好踩第 3 页的“stdout 只许走协议”：要关 banner、把日志改写文件，并设 spring.main.web-application-type=none。另外每个窗口都要起一次 JVM（实测 3 秒多），可能撞上 Claude Code 的启动超时 MCP_TIMEOUT。所以 Java 服务端更适合走 HTTP。

同步函数在哪个线程跑

Python SDK 把同步工具函数丢进线程池跑（第 2 页实测的异常栈里能看到 anyio.to_thread.run_sync），所以同步函数里做阻塞 IO 不会卡住别的请求，但线程池有上限；async def 的工具则绝不能写阻塞调用，否则整个服务端一起卡。Spring AI 有 spring.ai.mcp.server.type（SYNC / ASYNC），WebMVC 下用默认的 SYNC 就好。

手动调试：MCP Inspector

官方的 Inspector 是一个网页小工具（npx @modelcontextprotocol/inspector），连上你的服务端后能列清单、手填参数调工具、看原始报文。自动化测试用 Client(mcp)，手动看效果用 Inspector，两样配合。

怎么分发

Python 服务端可以发成一个包，用户的配置里写 uvx 包名 当命令，第一次运行时自动装；Java 打成可执行 jar（这一页的 pom 没配 repackage，正式发布时要加），配置里写 java -jar。远程的 HTTP 服务端就照普通服务部署，客户端只需要一个网址。

自测

1. 用一句话说出写 MCP 服务端的精华

把普通函数登记成工具，SDK 从签名和注释生成定义、替你走完协议；所以你的函数名、参数名、注释就是模型读到的接口文档。

2. 手写协议（gateway_server.py 那种）当正式服务端，缺什么？

不会两个年代的协议、schema 要手写并和代码同步、调用前不校验参数、HTTP 那一整套检查要自己写、出错要自己拼 isError。

3. 头号坑“Java 参数名变 arg0”的根源是哪条？

④ 机制 1：schema 是从方法签名反射生成的，而 javac 默认不保存参数名，要 -parameters。

4. 预测：把 oncall 的 search_logs 改成 def search_logs(q: str)、删掉 docstring，测试会挂吗？模型会受什么影响？

测试里用 keyword 调的会挂（参数名变了，校验不过）。模型那边：工具说明空了，参数叫 q 没有说明，它不知道这个工具是查日志的、也不知道该填正则，挑错工具和填错参数的次数都会上去。

从 ④ 机制 1（签名和注释就是定义）推出。

5. 预测：tickets 部署两台、配 MODERN、没配共享密钥，平时都正常，什么时候会出错？

只在服务端用到 input_required（比如写评论前要你确认）时：第一台把状态封进 requestState 交给客户端，客户端补完输入重发，负载均衡把它送到第二台，第二台解不开，这次调用失败。普通的一问一答不受影响。

从坑 4 和第 1 页“新协议无会话”推出。

6. 放回全景：第 9 站前后各发生了什么？如果第 9 站的函数抛了一个没接住的异常，整条链路会怎样？

前面是第 8 站 Claude Code 查权限放行、发出 tools/call；后面是第 10 站结果作为 tool_result 回到模型。Python 服务端没接住的异常会变成 isError: true 加一句笼统的话，第 10 站模型收到它，不知道原因，多半换个参数再试或者放弃这个工具；进程不会崩，服务端还在会话里。

从全景第 8～10 站和 ④ 机制 2 推出。
