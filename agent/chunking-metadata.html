清洗、切块策略和元数据

检索的单位是“片”，一片只有一个向量，那个向量代表这一片的平均意思。所以片要小而完整：一片讲一件事，边界跟着文档的标题走；再给每片贴上“出自哪份文档、哪一版、哪一节、哪一页、谁能看”的标签，过滤和引用都靠它。同样的资料和模型，只换切法，前 1 片命中率从 0.53 到 0.77。

①为什么学：96 个块，要变成能被查到的片

在全景第 3 站，这一步要解决：解析出来的 96 个块里混着页眉、页码、目录的点线，“Caffeine”中间是个连字；块的大小从一行到一整张表不等，也不知道自己属于哪一节。要把它们变成大小合适、一片一件事、带着出处的片，第 4 站才能算向量，第 7 站才能按版本和权限过滤，第 10 站才能写出“手册 v3.2 §4.3 第 9 页”。

②老办法：不清洗，每 200 个字切一刀

问“11 月 9 日 P99 升高时是怎么止血的？”，左边那片排第 16（全库只有 28 片），右边那片排第 3。左边丢了表头、故障编号、日期，又混进了下一节的半句话；它的向量是这几件事的平均，哪件都不像。

  • 片里混了几件事：时间线的后半截 + “根因”标题 + 半句根因，向量被平均掉了，30 题前 1 片命中率只有 0.53。
  • 片不知道自己是谁：没有故障编号、没有“时间线”这个标题，问题里的“11 月 9 日”“止血”都对不上。
  • 噪声没清：不清洗时有 10 片带着页眉，2 片是目录的点线；“Caffeine”在 2 片里是“Caﬀeine”，按字面搜不到。
  • 加 50 字重叠能补一点（前 1 片 0.53 → 0.60），但近似重复的片多了，前 5 片反而从 0.97 掉到 0.90。
不懂精华时的典型误用：把切块当成“控制长度”的事，只调 chunk_size 和 overlap。片的好坏首先看一片是不是一件完整的事，长度是第二位的。

③选谁：五种切法

评判要求：一片讲一件事；不把答案切断；片能独立看懂（知道自己出自哪）；大小可控；实现简单。手册和故障单都有清楚的标题，这一条决定了选择。

要求固定长度（可重叠）递归按分隔符
段落 → 句子 → 字		一页一片按标题结构，超长再拆语义切块
相邻句子向量差得远就断
一片一件事不能：时间线和根因混在一片差一点：尊重段落，不认标题不能：一页常有两三节能：边界就是作者的标题能，但断点由模型定，不稳定
片知道自己是谁不能不能差一点：知道页码能：带着标题路径不能
30 题前 1 / 3 片命中0.53 / 0.80（重叠 0.60 / 0.87）没测0.67 / 0.93，但每片 186 token0.77 / 0.90，每片 86 token没测
实现几行现成（LangChain 等）几行要解析出标题（上一页）每句都要算一次向量
值班助手怎么选没有标题的纯文本才用Markdown 以外的长文本兜底不选选：手册、故障单、笔记都有标题没有结构、话题又多变的长文才值得

固定长度、一页一片、按标题三列是 实测；递归和语义切块 按文档。一页一片只有 16 片，前 3 片已是全库的近五分之一，命中率看着高是因为“库小、片大”，见 ⑥ 坑 5。

本页学“按标题结构切 + 标题路径 + 元数据”：有结构就用结构，作者已经替你把话题分好了；切出来的片再用标签补上它离开原文后丢掉的上下文。

④原理：一片一个向量，所以片要小而完整

先知道这些
  • 一片只有一个向量：Embedding 模型把整片读一遍，输出一串数（Qwen3-Embedding 取的是最后一个 token 的状态，它“看过”整片）。可以把它理解成这一片的平均意思：片里讲了三件事，向量就落在三件事中间。Embedding 那页讲过怎么来的。
  • 块和片：块是解析出来的版面单位（一个标题、一段、一张表），片是检索的单位（几个块拼成）。上一页产出块，这一页产出片。
  • 元数据：片的正文以外的字段，存在数据库的列里（全景里是 chunks 表的 version、team、status 等列），可以用 WHERE 过滤，也可以拼进提示。

机制 1 · 清洗：删掉“不属于内容”的东西，改掉“写法不一样”的字

机制 2 · 边界跟着标题走：一节一片，太长再拆，表格不拆

kb.chunk() 从头到尾走一遍块：遇到标题就把手里攒的正文收成一片，并更新“当前在哪一节”；正文攒到 360 字就先收一片；表格不管多长都不拆开。手册第 8～10 页这样走：

为什么片要“小而完整”

两条约束互相拉扯：一片只有一个向量，片越大、讲的事越多，向量越模糊，越难被某个具体问题找到；模型只读到片，片越小，越可能缺了理解它所需要的上下文（这是哪个服务、哪一版、这一列是什么）。

按标题、一节一片（选）

  • 作者已经按话题分好了节，一节通常就是一件事：前 1 片命中 0.77，最高。
  • 标题路径补上了离开原文后丢掉的上下文。
  • 节的长短不一：手册里最短的一片 67 字，最长到 360 字封顶；一节特别长时还是要按段落拆，拆开的后半段要带同样的标题路径。

大片（一页一片）或碎片（固定 200 字）

  • 一页一片：一页常有两三节，向量被平均；每片 186 token，k 片送进提示的 token 是按节切的两倍多。
  • 固定 200 字：一片可能是上一节的尾巴 + 下一节的开头，0.53。
  • 两者都简单，没有标题的资料只能从它们开始。
决定胜负的约束：检索要小片（找得准），生成要大片（看得全）。按标题切是在一个尺寸上取折中；更彻底的办法是把两件事拆开：用小片检索，交给模型时换成它所在的整节，这就是第 7 个知识点里的“父子块”。
kb.chunk()（全景实验里那份的简化）细节放到 ⑥
MAX_CHARS = 360

def chunk(doc, blocks):
    chunks, path, buf, page = [], {}, [], None
    def flush():
        if buf:
            sec = " › ".join(path[k] for k in sorted(path))
            chunks.append(Chunk(f"{doc.key}@{doc.version}#{len(chunks)+1}",
                                doc.key, doc.version, doc.team, sec, page, "\n".join(buf)))
        buf.clear()
    for b in blocks:
        if b.kind == "heading":                   # 标题：收片，换路径
            flush(); page = None
            path = {k: v for k, v in path.items() if k < b.level}
            path[b.level] = b.text
            continue
        if buf and sum(map(len, buf)) + len(b.text) > MAX_CHARS and b.kind != "table":
            flush(); page = None                  # 太长：先收一片；表格不拆
        page = page or b.page
        buf.append(b.text)
    flush()
    return chunks

# 算向量时：标题路径 + 正文
def embed_text(self):
    return f"{self.doc_key} {self.version} › {self.section}\n{self.text}"

⑥细节

第一圈 · 注意事项

1页眉页脚混进片里实测← ④ 机制 1
现象
不清洗时 33 片里有 10 片带着“order-svc 运维手册 v3.2 · 交易组 · 内部资料”，2 片是目录的点线。这几个词出现在每一片里，关键词检索时失去区分度，向量也被拉向“手册封面”的意思。
根源
页眉页脚在 PDF 里就是普通的文字块，解析器分不出来；只能按“很多页都出现”来认。
做法
数字换成 # 后数出现的页数，超过一半就删；页眉带章节名、每页都不一样的资料，改按位置认（页面最上、最下 5% 的块）。删之前打印出来看一眼，别把每页都有的正文（比如表头）当页眉删了。
2重叠不是越多越好实测← ④ 机制 2
现象
固定 200 字加 50 字重叠：前 1 片 0.53 → 0.60，前 5 片却 0.97 → 0.90；“找 DBA 应急去哪个群”从第 1 掉到第 15。
根源
重叠是为了不把一句话切断，代价是相邻两片有四分之一是一样的，向量也很像；前 k 名被近似重复的片占掉，别的候选进不来。
做法
按结构切时一般不需要重叠（边界本来就在节与节之间）；用固定长度时，重叠取 10%～20%，并在检索结果里把来自同一位置的相邻片合并或去重。
3片离开原文，不知道自己是谁实测← ④ 机制 3
现象
不带标题路径时，“OrderDetailCache 打算怎么修？”排第 16，“OOM 时的堆转储放在哪”排第 6；带上路径后是第 8 和第 4。
根源
“补上 maximumSize(50000)…计划随 v2.3.2 发布”这一片里没有“修复”二字，也没有故障编号；它是“修复和改进”这一节，这个信息在标题里，不在正文里。
做法
算向量时在正文前加“文档 版本 › 各级标题”；还不够的（表格续页、代词多的段落），用模型给每片写一两句“这一片在讲什么”再加在前面（第三圈）。
4元数据塞进向量，有好有坏实测← ④ 机制 3
现象
给故障单的片加上“2026 年 11 月 9 日 order-svc 故障”：Q27 第 3 → 2、Q29 第 8 → 4，Q28 却第 3 → 7，总的命中率一点没变。
根源
向量只有一个，前缀和正文一起被平均；三片故障单都带上了同样的日期和服务名，彼此更像了，正文的差别反而被冲淡。
做法
能用过滤做的（团队、版本、时间范围、服务名）放进数据库的列，用 WHERE 筛；进向量的只放能帮“理解这一片”的东西（标题路径）。每加一个前缀都跑一遍评测集。
5一页一片“看着最好”实测← ④ 为什么这样设计
现象
一页一片前 3 片 0.93、前 5 片 1.00，比按标题切还高。
根源
只有 16 片，前 5 片就是全库的 31%；每片 186 token，k 片送进提示的字是按标题切的两倍多。命中率要和“片数、片大小、送进提示多少 token”一起看。
做法
比较切法时固定“送进提示的 token 预算”（比如 600 token）而不是固定 k；评测集和库一起长大，31 片的结论到 3 万片未必成立。
6整段 NFKC 把中文标点变成半角实测← ④ 机制 1
现象
为了还原 ﬀ 对整段做 unicodedata.normalize("NFKC")，“位置：/data/logs”变成“位置:/data/logs”，“（Caffeine、Guava Cache）”变成“(Caffeine、Guava Cache)”；引用原文时和 PDF 对不上。
根源
NFKC 把“兼容字符”都折成标准形式，全角标点 U+FF1A“：”也在其中。
做法
只对连字（U+FB00～FB4F）和全角字母数字做 NFKC，见全景 kb.fold()；或者存两份：原文用来引用和展示，规范化后的用来检索。

第二圈 · 使用规范

  • 片 id 用“文档@版本#序号”，同一份文件重新入库时 id 可预测。防的是增量同步时找不到该删哪几片。
  • 切块参数（上限、重叠、标题层级）写进配置并记进元数据。防的是改了参数，新旧两批片混在一个库里还说不清。
  • 表格不拆；一张表太长时按行拆，每片都带表头。防的是“/data/dump”那种没有列名的半张表。
  • 清洗规则先打印再删：每条规则删了哪些行，抽查一遍。防的是把每页都有的正文当成页眉删掉。
  • 改切法必跑评测集：30 题的命中率前后对比，片数和平均大小一起记。防的是凭一两个问题拍板。

第三圈 · 优化和深处

片的上限从哪来

三个上限取最小：Embedding 模型的输入上限（超了会被截断，后半段等于没进向量）；重排模型的输入上限（问题 + 片一起算）；提示预算（k × 片大小）。这里 360 字约 210 token，离前两个上限都很远，是按“一节通常多长”定的。换模型时先查它的最大长度。

给每片写一句“它在讲什么”

Anthropic 2024 年发表的 Contextual Retrieval：入库时让模型读整篇文档，给每片写一两句上下文说明，加在片前面再算向量和建关键词索引；他们的测试里，检索失败率下降 35%，再加 BM25 和重排一共下降 67%。代价是入库时每片多一次模型调用。按文档

语义切块

没有标题的长文：每句算一个向量，相邻两句差得远就断开。断点会随模型和阈值变化，片的大小也不受控；有结构的资料用不上它。按文档

小片检索，大片阅读

按句子或小段检索（找得准），命中后把它所在的整节交给模型（看得全）。这是第 7 个知识点“父子块”的内容，也是解决 ④ 那对矛盾最直接的办法。

实验台：换一种切法

先猜：同样按标题切，只在算向量时给每片前面加上“文档 版本 › 各级标题”，30 题的前 1 片命中率会？

实测 数字全部来自 chunking-metadata/main.py 的输出（chunks.json）；“平均 token”是算向量时的文字长度。

  • Markdown 和 HTML 的切法：学习笔记站本身是 HTML，按 h2 / h3 切，代码块和图怎么处理。
  • 表格专门的片：一张表一片、一行一片、还是“列名：值”展开，对表格题的影响。

自测

1. 用一句话说出这一页的精华

一片只有一个向量，代表它的平均意思，所以片要小而完整：边界跟着作者的标题走，一片一件事；离开原文丢掉的上下文用标题路径和元数据补回来，元数据另外还管过滤和引用。

2. 固定 200 字一刀的老办法，疼在哪？

片里混进上一节的尾巴和下一节的开头，向量被平均，又不知道自己出自哪；实测前 1 片命中 0.53，时间线那题排第 16（共 28 片）。

3. 为什么不带标题路径，“OrderDetailCache 打算怎么修”会排到第 16？

那一片的正文是“补上 maximumSize(50000) 和 expireAfterWrite…随 v2.3.2 发布”，没有“修”“改进”这类词，也没有故障编号；“修复和改进”这个意思只在标题里。不带路径，向量里就没有它。

从 ④ 机制 3 推出。

4. 预测：把 MAX_CHARS 从 360 改成 2000，手册会切成几片？前 1 片命中率会怎样？

片数基本不变：手册每一节的正文都没到 360 字（5.1 那片 372 字是因为表格不拆），切块边界本来就是标题，上限没起作用（只有超长的节才会被它拆）。命中率也基本不变。要让上限起作用，得换一份有长章节的资料。

从 ④ 机制 2 推出：先按标题断，上限只是兜底。

5. 预测：给所有片都加上同一句前缀“交易组内部资料”，会怎样？

不会帮任何一题：这句话在每一片里都一样，不能区分片；它还占了向量的一部分“注意力”，片与片之间更像了，命中率可能小幅下降。和坑 4 里日期的道理一样，能区分的才值得放进向量。

从 ④ 机制 3 和坑 4 推出。

6. 放回全景：第 3 站前后各发生什么？如果第 3 站没记 version 和 status，第 7 站会怎样？

第 2 站交来 96 个块；第 3 站之后，第 4 站给每片算向量、第 5 站入库。没记版本和状态，第 7 站就没法过滤旧版：v3.1 的 16 片和 v3.2 的 17 片一起被检索，“P99 告警阈值”会同时拿到 1000 ms 和 800 ms，模型挑哪个都标着真实出处。

从全景第 1、3、7 站推出。
