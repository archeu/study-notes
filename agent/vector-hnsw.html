向量检索和 HNSW 索引

“找最像的 10 片”就是在几十万个点里找离问题最近的 10 个。挨个比太慢，B+ 树又帮不上忙。HNSW 把点连成一张多层的近邻图：上层点少、跨得远，几步就到附近；底层在附近攥着一池候选慢慢展开，只算几百个点的距离。代价是近似：召回率靠 ef_search 换；带 WHERE 过滤时结果可能凑不满。

①要解决的问题：库一大，“比远近”就成了瓶颈

在全景第 5 站，片和向量存进了 pgvector；第 8 站每条检索语句都要来这里“取离问题最近的 20 片”。全景的库只有 31 片，怎么做都快；值班助手要接整个交易组的手册、故障单、笔记，再加上其他团队的，片数会到几十万。要解决的问题是：在 N 个 1024 维的点里，找离一个点最近的 k 个，而且不能每次都把 N 个点看一遍。

实测 2026-11-25，本机 2 核 ARM，容器里的 PostgreSQL 17.11 + pgvector 0.8.7，100 个问题。向量是合成的（1000 个话题、每个约 50 条），真实 Embedding 的召回率要用真实数据重测，见 ⑥。

②朴素做法：挨个比，再排序

前三页的 M @ qv 就是这个：问题和每一条都算一次余弦，排序取前 10。在 PostgreSQL 里不建索引，ORDER BY emb <=> $1 LIMIT 10 也是这么执行的：

实测没有向量索引时的执行计划5 万条 × 1024 维
Limit
  ->  Sort                       Sort Method: top-N heapsort
        Sort Key: (emb <=> '[…]'::vector)
        ->  Seq Scan on items        5 万行，每行读出 4 KB 的向量，算一次距离
p50 228 ms，p95 237 ms   召回 1.0（它就是标准答案）
  • 结果是精确的，召回率 1.0；不用建任何东西，数据一写进去就能查。
  • 每个问题都要读完全部 5 万行：PostgreSQL 里每行的向量是 4 KB，存在 TOAST 里，要一行行取出来再算，单核 228 ms。
  • 和条数成正比：库涨 10 倍就慢 10 倍，并发时数据库 CPU 先满。
  • 同样的 5 万次点积，numpy 一次矩阵乘法只要 9 ms：暴力本身不一定慢，慢在“逐行从表里取”。小库（几万条以内）放内存里暴力算，是正经的选项。
  • B+ 树帮不上忙：它靠比大小排成一条线，向量既没有大小，1024 维也排不成一条线。
不懂精华时的典型误用：把向量索引当成 B+ 树：以为建了就“查得准”，以为 WHERE 和 LIMIT 还像普通索引那样工作。HNSW 查的是“大概率是前 10”，而且 WHERE 是在它交出一批近邻之后才过滤的（⑥ 坑 1）。

③几种思路：少看一点，怎么少看

评判要求：召回率（找回真正的前 10 的比例）、单次查询延迟、内存、建索引时间、能不能一条条加数据、带过滤好不好用。

④关键洞察：近的点连成图，分层，沿着边贪心走

先知道这些
  • 余弦距离：pgvector 的 <=> 算的是 1 − 余弦相似度，越小越近。向量都归一化过时，它和欧氏距离排出的先后一样，所以下面的图用平面上的远近来画。
  • 近似最近邻（ANN）：不保证找到真正最近的那几个，换来不用和每一条都比。好坏用召回率@10量：真正的前 10 名里，找回来了几个。
  • 跳表：一条有序链表上面再架几层“快速通道”，上层节点少、跨得远，查找时从最上层往下走。Redis 的 zset、Java 的 ConcurrentSkipListMap 都是它：B+ 树与跳表。HNSW 就是“图上的跳表”。
  • 为什么 B+ 树帮不上忙：B+ 树靠“比大小”把数据排成一条线；向量没有大小可比，1024 维里也排不出一条线。按某一维切分的树（KD 树）到了几百维以上，几乎每个分支都要进去看，退化成暴力扫描。

洞察 1 · 把每个点和它附近的点连起来，沿着边一步步走近

先不管分层。把每条向量当成一个点，和离它最近的十几个点连上边，得到一张图。查询时从任意一个点出发：看看它的邻居里谁离问题更近，就走过去；走到“没有哪个邻居更近”为止。每一步只算当前这个点的十几个邻居的距离，而不是全部 5 万条。

为什么走得到

邻居之间的边让“局部”很准：已经到了答案附近，下一步总能再近一点。只要图里还有少数连得很远的边，从任何地方出发，跳几步就能到另一头，这叫小世界图（六度分隔说的就是它）。

为什么不保证对

贪心会停在“局部最近”：当前点的邻居都比它远，可真正最近的点在别处，中间隔着一个“坑”。这就是近似的来源，召回率 < 1。补救有两招：分层（洞察 2）让起点更好；候选池（洞察 3）让它别太早停下。

洞察 2 · 分层：上面几层是快速通道

只有一层时，从远处出发要走很多步。HNSW 给每个点随机抽一个“最高能到第几层”：越高的层点越少。上层点少、边跨得远，几步就能到答案所在的区域；然后下一层，在更密的点里继续走；最后在包含全部点的第 0 层收尾。

层一个点能到这一层的概率（m = 16）5 万个点里大约像什么
第 0 层150,000 个，每个最多 2m = 32 条边街道：每一户都在
第 1 层1/16约 3,100 个主干道
第 2 层1/256约 200 个城市快速路
第 3 层1/4096约 12 个高速，入口就在这一层

层的分布按论文（Malkov & Yashunin）的规则：层号 = ⌊−ln(随机数) × mL⌋，mL = 1/ln(m)，所以每往上一层，点数大约少到 1/m。pgvector 照这个实现 按文档。表里的点数是按概率算的，不是从索引里读的。

洞察 3 · ef：手里攥着几个候选，决定会不会走进死胡同

上面几层只留 1 个候选，贪心往下走就行（只是为了找一个好起点）。到了第 0 层，手里同时攥着 ef 个“目前最近的点”，每次从中挑一个还没展开的，把它的邻居都看一遍，更近的换进来；直到“最近的未展开候选”比“池里最远的”还远，才停。ef 越大，看的点越多、越不容易停在局部最近，也越慢。

  • hnsw.ef_search（查询时，pgvector 默认 40）：召回率和延迟的旋钮，可以按会话、按事务调，不用重建索引。
  • m（建索引时，默认 16）：每个点连几条边。边多，图更“通”、召回更高，索引更大、建得更慢；改它要重建。
  • ef_construction（建索引时，默认 64）：插入新点时为它找邻居的候选池。大了邻居选得更好，建得更慢。
  • ef_search 同时是“最多返回几行”：带 WHERE 过滤时，索引先交出 ef_search 个近邻，再被过滤掉一大半，结果可能凑不够 LIMIT（⑥ 坑 1）。

为什么这样设计

逼出 HNSW 的约束有三条：维度高（几百上千维，按维切分的树失效）；不能每次都看全部（库越大，暴力越慢，见 ②）；数据会一条条加进来（知识库在增量同步，不能每加一条就重建）。

图：HNSW（选）

  • 只看几百个点就能找到前 10，召回和延迟的平衡最好。
  • 新点插进来就是“在图里找邻居、连上边”，不用训练，空表也能先建索引。
  • 边要占地方：每个点几十条边，索引常常和表一样大；建得慢。

分桶：IVFFlat

  • 先把向量聚成 lists 个桶，查询时只看离问题最近的 probes 个桶；建得快、占地小。
  • 桶的中心是用建索引那一刻的数据算的，之后大量新数据进来，桶就不准了，要重建；空表上建出来的桶没有意义。
  • 召回靠 probes：开多了接近暴力。

树：KD 树等

  • 低维（二三维的地图坐标）里又快又精确。
  • 几百维时，一个问题的“最近邻球”会穿过几乎所有分割面，每个分支都要进去看，退化成暴力。
决定胜负的约束：高维 + 增量写入。图结构只依赖“谁离谁近”，不依赖坐标轴，维度再高也能走；插入一个点只改它附近的边。代价是内存和建索引的时间，这在知识库这种“读多写少”的场景里划得来。
pgvector 里用到的全部 SQL参数细节放到 ⑥
CREATE EXTENSION vector;
CREATE TABLE chunks (id text PRIMARY KEY, team text, status text,
                     text text, emb vector(1024));
-- 建索引：余弦距离；m、ef_construction 不写就是 16、64
CREATE INDEX ON chunks USING hnsw (emb vector_cosine_ops)
       WITH (m = 16, ef_construction = 64);
-- 查询：ORDER BY 距离 + LIMIT，才会走索引
SET hnsw.ef_search = 100;                 -- 默认 40
SELECT id, 1 - (emb <=> $1) AS cos
FROM chunks ORDER BY emb <=> $1 LIMIT 10;
-- 带过滤时（pgvector 0.8 起）
SET hnsw.iterative_scan = relaxed_order;

Java 老朋友：向量索引 ≈ 数据库索引

像：建在列上、对 SQL 透明、能用 EXPLAIN 看走没走索引、要在写入速度和查询速度之间取舍。

不像：B+ 树查出来的就是答案，HNSW 查出来的是“大概率是答案”；而且它的结果数受 ef_search 限制，后面再加 WHERE 会变少。这两点在 B+ 树上都不会发生。

⑤toy_hnsw.py 的搜索部分完整代码 →
cur = ENTRY                                   # 最高层的入口
for l in (2, 1):                              # 上层：只留 1 个候选，贪心
    while True:
        best = min(g[l][cur], key=lambda x: d(x, q))
        if d(best, q) >= d(cur, q): break       # 邻居都更远：下一层
        cur = best
visited = {cur}
cand = [(d(cur, q), cur)]                     # 小根堆：待展开，近的先展开
res  = [(-d(cur, q), cur)]                    # 大根堆：结果池，堆顶是池里最远的
while cand:
    dc, c = heapq.heappop(cand)
    if dc > -res[0][0] and len(res) >= ef: break   # 最近的候选都比池里最远的远：停
    for n in g[0][c]:
        if n in visited: continue
        visited.add(n)
        if len(res) < ef or d(n, q) < -res[0][0]:
            heapq.heappush(cand, (d(n, q), n))
            heapq.heappush(res, (-d(n, q), n))
            if len(res) > ef: heapq.heappop(res)   # 挤掉池里最远的
top = sorted((-x, n) for x, n in res)[:k]

手推出来的结论
  • 上两层一共只走了 2 步，就从左上角的 K 到了问题附近的 N：快速通道的作用是找一个好起点。
  • 第 0 层在 N 附近展开了 5 个点，看了 12 个点的距离就停了；左上角的 A、B、F、G、K、R 一个都没算。18 个点里省 6 个不算什么，5 万个点里，ef_search = 40 时也只算几百到一两千个（② 的实测）。
  • 停下的条件是“最近的未展开候选，比池里最远的还远”：再展开下去，也不可能找到能进池子的点了，前提是图是连通的、近的点之间有边。这个前提不总成立，所以是近似。

⑥边界和变体

第一圈 · 注意事项

1带 WHERE 过滤，结果凑不满 LIMIT实测← ④ 洞察 3
现象
5 万条里 10% 属于 risk 团队，WHERE team = 'risk' ORDER BY emb <=> $1 LIMIT 10：平均只返回 4.0 条，有的问题一条都没有，召回 0.40。不报错。
根源
HNSW 先按 ef_search 交出 40 个最近的，再逐行过滤；40 × 10% ≈ 4。EXPLAIN ANALYZE 里看得到：Index Scan，Rows Removed by Filter: 38。
做法
pgvector 0.8 起 SET hnsw.iterative_scan = relaxed_order：凑不满就接着往下扫，实测返回满 10 条、召回 0.68、5.2 ms；再把 ef_search 调大，召回还能往上走。过滤条件固定的（团队、状态），用部分索引（CREATE INDEX … WHERE team = 'trade'）或按团队分区，让索引里只有能被查到的行。
2过滤很狠时，规划器自己会放弃 HNSW实测← ④ 为什么这样设计
现象
只有 2% 的行满足（trade 团队 1017 行）时，规划器选了 Seq Scan + Sort：返回满 10 条，召回 1.0，11 ms。强制走 HNSW（enable_seqscan = off）反而平均只回来 0.9 条。
根源
满足条件的行少到排序它们比走图还便宜，规划器按代价选了精确的路；10% 时它估计走索引更便宜，于是掉进了坑 1。
做法
别为了“用上索引”强制走 HNSW；有向量查询的表要 ANALYZE，让规划器知道每个 team 有多少行。上线前用 EXPLAIN ANALYZE 按几种典型的过滤条件各看一次计划。
3LIMIT 比 ef_search 大，最多只回来 ef_search 条← ④ 洞察 3
现象
想一次取 100 个候选给重排，LIMIT 100，默认 ef_search = 40 时最多只回来 40 条。
根源
第 0 层的候选池就 ef_search 那么大，池子装满了，搜索就结束了。按文档
做法
ef_search 至少设成 LIMIT；或者打开 iterative_scan。
4索引比表还大，建得也慢实测← ④ 为什么这样设计
现象
表 268 MB，HNSW 索引 391 MB；2 核建了 84 秒（m = 8 时 46 秒，索引一样 391 MB）。IVFFlat 只要 11 秒，但索引也是 392 MB。
根源
索引里每个点都存一份完整的向量（1024 × 4 字节 = 4 KB），再加上邻居列表；两个 m 一样大，说明大小主要由向量本身决定（推测：一个 8 KB 的页大约只放得下一个点，没有逐页核对）。建图要为每个点搜一遍邻居，所以慢。
做法
建索引前把 maintenance_work_mem 调到放得下整张图（不够时 pgvector 会提示图放不进内存，建得更慢 按文档），max_parallel_maintenance_workers 按核数开；向量换成 halfvec（2 字节一维）能把表和索引都砍一半，召回通常只掉一点点，要用评测集量。
5IVFFlat 的桶会过时← ④ 为什么这样设计
现象
建索引时库里只有一部分数据，之后大量新片进来，召回率慢慢往下掉；空表上建的 IVFFlat 基本没用。
根源
桶的中心是建索引那一刻用 k-means 算的，新数据只是被分到最近的旧桶里，桶不会重新划分。按文档
做法
用 IVFFlat 就定期重建（REINDEX）；知识库这种持续增量写入的场景，默认用 HNSW。
6写法不对，不走索引实测← ④ 为什么这样设计
现象
ORDER BY 1 - (emb <=> $1) DESC（按相似度从大到小）走了 Seq Scan；索引是 vector_cosine_ops，查询却用了 <->（欧氏距离），也走 Seq Scan。
根源
索引只认“按某个距离运算符升序取前几个”这一种形状；运算符要和建索引时的操作符类对应（余弦 <=>、欧氏 <->、内积 <#>）。
做法
固定写成 ORDER BY emb <=> $1 LIMIT k，相似度在 SELECT 里另算；上线前 EXPLAIN 确认是 Index Scan。
过滤条件（5 万条里满足的比例）规划器选的路iterative_scan = offiterative_scan = relaxed_order
team = 'trade'（2%）Seq Scan + Sort（精确）10 条，召回 1.00，11 ms同左
同上，强制走 HNSWIndex Scan平均 0.9 条，召回 0.0910 条，召回 0.65，18 ms
team = 'risk'（10%）Index Scan平均 4.0 条（最少 0），召回 0.4010 条，召回 0.68，5.2 ms
team = 'ops'（30%）Index Scan平均 9.5 条（最少 5），召回 0.9310 条，召回 0.98，2.6 ms

实测 100 个问题，ef_search = 40。召回是和“先过滤、再精确排序”的结果比。测这张表时踩了一个坑：psycopg 3 会把同一条 SQL 执行 5 次后自动改成服务端预编译，计划被缓存，之后 SET enable_seqscan = off 不起作用；改成 prepare=False 才测准。pgjdbc 的 prepareThreshold 默认也是 5，Java 里一样会遇到。

第二圈 · 使用规范

  • 查询固定写成 ORDER BY emb <=> $1 LIMIT k，并用 EXPLAIN ANALYZE 留一份典型计划。防的是改了一个排序表达式就退回暴力扫描。
  • ef_search 按场景在会话或事务里设：给重排取 20～50 个候选时，ef_search 至少等于 LIMIT。防的是结果条数被悄悄截断。
  • 有过滤就打开 iterative_scan，固定的过滤维度用部分索引或分区。防的是坑 1 那种“返回 4 条不报错”。
  • 召回率要用自己的数据量：从库里抽几百个问题，用暴力扫描的结果当标准答案，算 HNSW 的召回@k。防的是拿别人的基准数字当自己的。
  • 建索引放在批量导入之后，并调好 maintenance_work_mem。防的是边导边建，每插一条都要在图里找邻居，导入慢好几倍。

第三圈 · 优化和深处

m 和 ef_search 怎么一起调

m 定了图有多“通”：m = 8 时 ef_search 要到 160 才有 0.99，m = 16 时 40 就到了。所以 m 小省的是建索引时间（46 秒对 84 秒），查询时要拿更大的 ef 补回来。知识库读多写少，m 用默认 16，按召回目标调 ef_search。

插入时的“邻居启发式”

真实的 HNSW 给新点挑邻居时，不是简单取最近的 m 个，而是跳过“已经能通过别的邻居到达”的点，让边朝不同方向伸出去。这样图里少了冗余的短边，多了能跨过空白区域的边，贪心不容易困在局部。⑤ 的小图没有这一步。按文档（Malkov & Yashunin）

删除和更新

pgvector 里删一行，索引里的点要等 VACUUM 才真正清理；图里的边会绕开它。知识库按版本整批下线时（第 8 个知识点），大量删除后的 VACUUM 会比较重，可以考虑按版本分区直接删分区。

合成数据和真实数据

本页的点是“1000 个话题中心加噪声”，问题和第 1 近的余弦平均只有 0.38，比真实 Embedding 散。真实的文本向量更挤（全景的 31 片里前几名余弦都在 0.6 附近），同样的 ef_search，召回可能更高也可能更低，只能用真实的问题量。

自测

1. 用一句话说出这一页的精华

HNSW 把向量连成多层的近邻图：上层点少、跨得远，用来快速找到起点；第 0 层攥着 ef 个候选在附近展开，只算几百上千个点的距离就找到前 10。它是近似的：召回率靠 ef 换，带过滤时结果会变少。

2. 朴素做法（暴力扫描）疼在哪？

每个问题都要和全部向量算一次距离：本页 5 万条时 PostgreSQL 顺序扫描要几百毫秒（见 ②），而且和条数成正比，库涨 10 倍就慢 10 倍；B+ 树这类按大小排序的索引帮不上忙。

3. 为什么 HNSW 的结果不保证是真正的前 10？

它沿着边贪心地走，停下的条件是“最近的未展开候选比池里最远的还远”。如果真正最近的点和当前区域之间没有边相连（图在那里“断开”了），就会停在局部最近。ef 越大，池子越大，越不容易早停。

从 ④ 洞察 1、3 推出。

4. 预测：把 ef_search 从 40 调到 400，召回率和延迟各会怎样？要重建索引吗？

召回率会更接近 1（本页 160 和 320 时已经很高），延迟大致跟着 ef 涨，但远到不了暴力扫描那么慢。不用重建：ef_search 是查询时的参数，SET 一下就生效。要重建的是 m 和 ef_construction。

从 ④ 洞察 3 推出。

5. 预测：知识库里 98% 是别的团队的片，交易组的人查“本地缓存规范”，带着 WHERE team = 'trade' 走 HNSW，会怎样？

如果走 HNSW：索引先交出 ef_search = 40 个最近的，再按 team 过滤，平均剩不到 1 条，LIMIT 10 拿不满，还不报错（实测强制走索引时平均 0.9 条）。实际上规划器看到只有 2% 的行满足，会改走顺序扫描再排序，结果反而是精确的（坑 2）。最危险的是 10% 上下那种“规划器觉得走索引划算”的过滤（坑 1）：要打开 hnsw.iterative_scan，或者用部分索引、按团队分区。

从 ④ 洞察 3（ef_search 同时是“最多返回几行”）推出。

6. 放回全景：第 5 站前后各发生什么？如果第 5 站没建 HNSW、只靠暴力扫描，整条链路会怎样？

第 4 站把每片变成向量交给第 5 站存起来；第 8 站检索时来第 5 站取最近的 20 片。全景只有 31 片，暴力扫描毫秒级，看不出差别；库涨到几十万片，第 8 站每条检索语句要几百毫秒到几秒，一节报告查 4 次就是几秒的额外等待，并发一上来数据库 CPU 先满。反过来，建了 HNSW 却带着过滤查，第 8 站可能拿到不足 20 片的候选。
