部署：容器、扩容、密钥管理、私有化

把值班助手装进容器、放上 K8s，大部分是 Java 后端的老本行；和普通 Web 服务不一样的地方有三处，正是这一页的精华：一个请求要跑一分钟，所以停机时要让 worker 把手上这一轮做完再走（SIGTERM 要真能送到）；扩缩看的是积压和额度，不是 CPU；真 key 只进网关，worker 只拿虚拟 key，镜像里一个都不放。数据不能出公司时，再把模型也搬进机房，这叫私有化。

①为什么学：worker 要能扩、能停、拿不到真 key

在全景第 ⑪ 站，这一步要解决：大促前要把 worker 和网关部署上 K8s；20:00 积压涨起来时 worker 要能扩，可扩多少由额度定；扩完了要缩，滚动发布也会换掉 Pod，可这时 worker 手上可能正跑着第 4 轮；供应商的 key 一旦漏了，87 个调查的花费会算到别人头上。

②老办法：一个“能跑就行”的 Dockerfile

网上最常见的写法：完整版的 Python 基础镜像，pip install，图省事把 key 写进 ENV，最后一行 CMD python worker.py。⑤ 把它和多阶段的写法放在一起比：

不懂精华时的典型误用：把 agent 的 worker 当成普通 Web 服务部署：默认 30 秒宽限期、shell 形式的 CMD、按 CPU 扩缩。缩容和发布时，正在跑的调查被一刀砍断；CPU 一直不到一成，积压再高也不扩。

③选谁：放在哪、怎么扩

形态适合要留意
一台机器 + docker compose试点、一个团队在用扩不了、单点
K8s Deployment + HPA（按 CPU、内存）普通 Web 服务worker 大部分时间在等模型，CPU 不到一成：积压再高也不扩
K8s Deployment + KEDA（按 Redis Stream 的积压）队列驱动的 worker：全景这一夜多装一个 KEDA；上限要按额度算
每个事件一个 K8s Job（或云上的任务型服务）量少、每个任务很长、要彻底隔离每次起 Pod 要几秒到几十秒；87 个事件就是 87 个 Pod
私有化：模型也部署进机房（vLLM、llama.cpp 服务）数据不能出公司、要离线要 GPU 和运维；开源模型的效果要重新评测

本页学 Deployment + KEDA 按积压扩缩，上限按额度定：worker 是“从队列拉活”的，最好的扩缩信号就是“队列里还有多少没人领”。私有化放在 ④ 机制 5：它不是部署方式的变化，而是把第 ⑦ 站从公网搬进机房。

④原理：一分钟的请求，怎么停、怎么扩、怎么藏 key

先知道这些
  • 镜像分层、多阶段构建：补给页 Docker 镜像分层与多阶段构建。
  • Deployment、Pod、Secret：补给页 Kubernetes 核心对象；配置和密钥的老办法见 配置和密钥。
  • 至少一次：worker 没 XACK 就走了，任务留在待确认列表里，别人会认领（长任务架构）。

机制 1 · 镜像：两段构建，按锁文件装，不带 key

第一段用 uv 按 uv.lock 装依赖（版本和哈希都锁死，AI 网关那页的供应链投毒就是这么防的），第二段只拷虚拟环境和代码到 slim 镜像里，⑤ 实测 1.14 GB 变成 153 MB。key 一律不进镜像：ENV、ARG、COPY .env 都会留在某一层里，docker history 就能看到；运行时由 K8s 从 Secret 注入成环境变量。

机制 2 · 停机：SIGTERM 要真能送到，宽限期要够一轮

K8s 删一个 Pod（缩容、滚动发布、节点排空）时，先给容器的 1 号进程发 SIGTERM，等 terminationGracePeriodSeconds（默认 30 秒），到点还没退就 SIGKILL。这里有两个坑，⑤ 都实测到了：

  • shell 形式的 CMD（CMD python worker.py）：1 号进程是 /bin/sh -c …，它不把 SIGTERM 转给 python，python 什么也不知道，照常往下跑，等满宽限期被强杀。
  • python 是 1 号进程但没装处理函数：Linux 不会把“默认动作”的信号送给 1 号进程，于是 SIGTERM 被直接忽略，结果和上一条一样。
  • exec 形式 + 处理函数：收到 SIGTERM 只设一个标志，把手上这一轮做完、写好检查点，然后退出，不 XACK，任务留给别人用 XAUTOCLAIM 接着从下一轮跑。⑤ 里 2.1 秒就退了。

宽限期要比“最长的一轮”还长：一轮最长是一次模型调用的超时（可靠性那页定的 60 秒）加上工具时间，所以清单里设 90 秒。不够的话会被强杀在半轮，好在有检查点和至少一次，最多重做这一轮。

机制 3 · 扩缩：看积压，按额度封顶

worker 大部分时间在等模型，CPU 很低，按 CPU 扩等于不扩。KEDA 的 Redis Streams 扩缩器能直接读队列：lagCount 是“还没分给任何人的”条数，pendingEntriesCount 是“已经在 worker 手上、还没确认的”条数。拉模式下后者最多就是 worker 的并发数，积压再高它也涨不上去，所以要按 lagCount 扩。上限不看机器，看额度：限流那页算过，36 万 ITPM 只够 12 个调查同时跑，2 个 Pod × 8 个协程已经够了，再多只是在令牌桶前面排队。

机制 4 · 密钥：真 key 只进网关，Secret 也不等于加密

worker 拿的是网关发的虚拟 key，泄露了只影响一个团队、随时能吊销；真的供应商 key 只挂进网关的 Pod。再加一条出网规则（NetworkPolicy）：worker 只许连网关和 Redis，连不到公网，被注入了也没法把东西直接发出去（提示注入那页的“往外发的通道”）。另外要知道，K8s 的 Secret 默认只是 base64，etcd 里是明文（J14 那页在 kind 里实测过）：生产上要开静态加密，或者从外部密钥库取（External Secrets、云厂商的 KMS）。

机制 5 · 私有化：把第 ⑦ 站搬进机房

有的客户（或者有的数据）不能发给公网上的供应商。做法是在机房里起一个模型服务（vLLM、llama.cpp 的 llama-server），它们大多提供和主流供应商兼容的接口，网关里把某个别名指过去就行，worker 不用改。代价写在明处：要 GPU 和运维；开源模型的效果要用评测集重新量；额度变成了自己的显卡算力。这个站里的 提示注入 实验就是这么跑的：一个 1.7B 的模型、两核 CPU 上的 llama-server，每次调用 6～9 秒，能演示机制，远不够排障用。

为什么这样设计

能被打断的 worker + 按积压扩 + key 不出网关

  • 缩容、发布、节点排空随时会发生；worker 被设计成“随时可以停”，停了最多重做一轮。
  • 扩缩信号和瓶颈对得上：队列里没人领的才是真积压，额度才是真上限。
  • key 漏了也只漏一个团队的虚拟 key；出网被限死，注入了也发不出去。
  • 代价：多一个 KEDA；每个 worker 要正确处理 SIGTERM；网关的 Pod 要单独加固。

按普通 Web 服务部署

  • 默认 30 秒宽限期、shell 形式 CMD：一分钟的调查被砍在中间。
  • 按 CPU 扩：worker 一直很闲，积压 38 个也不扩；或者反过来无上限地扩，扩出来的都在等令牌。
  • 每个服务都拿真 key，镜像里、环境变量里到处都是。
决定胜负的约束：一个请求要跑一分钟、花真钱，而 Pod 随时会被换掉；瓶颈在供应商的额度上，不在 CPU 上。部署要围着这两点设计，而不是照搬 Web 服务的默认值。

Java 老朋友：优雅停机

像：Spring Boot 的 server.shutdown=graceful 和 spring.lifecycle.timeout-per-shutdown-phase，就是“收到 SIGTERM 后等正在处理的请求做完”；Java 里用 exec java -jar 或 exec 形式的 ENTRYPOINT，也是为了让 JVM 当 1 号进程收到信号。

不像：Web 请求几百毫秒，30 秒宽限期绰绰有余；这里一轮就可能一分钟，而且“做完”的定义是“这一轮写好检查点”，不是“整个调查做完”。Kafka 消费者停机前提交 offset 的那一步，在这里换成了“不确认、留给别人”。

⑤跑起来：两个镜像，三次 docker stop

worker 简化成一个文件：从 Redis Stream 领任务，每轮睡 4 秒（假的模型调用）、写检查点；收到 SIGTERM 就把这一轮做完退出。两个 Dockerfile：“能跑就行”的那个和多阶段的那个。demo.py 让 worker 跑到第 2 轮时 docker stop，看它怎么退。

读出来的结论
  • 同样的代码，多阶段 + slim 只有原来的 13%；这里只装了一个 redis 客户端，真的 worker 依赖多，差距还会更大。
  • key 一旦写进 ENV，任何能拉镜像的人用 docker history 就能看到，删掉那一行重新构建以前，所有旧镜像里都还有。
  • 后两种情况，worker 根本不知道自己该停了：收到 stop 以后还接着跑了两轮多，第 5 轮做到一半被强杀。docker stop 默认等 10 秒，K8s 默认等 30 秒，道理一样。
  • 三种情况下任务都还在待确认列表里，别人都能接手：至少一次和检查点保证了“不丢”；SIGTERM 处理保证的是“不白做、不拖时间”。
到这里已经能交差了：153 MB 的镜像、key 不进镜像、收到 SIGTERM 做完这一轮再走；K8s 清单里有 Secret、90 秒宽限期、按积压扩缩、出网限制。

⑥细节

第一圈 · 注意事项

1shell 形式的 CMD实测← ④ 机制 2
现象
每次发布，worker 都要等满宽限期才被强杀，日志里没有“收到 SIGTERM”。
根源
1 号进程是 /bin/sh，它不转发信号。
做法
exec 形式 CMD ["python", "worker.py"]；必须用脚本启动时，最后一行写 exec python worker.py，或者加一个小的 init（tini、docker run --init）。
2python 是 1 号进程，但没处理 SIGTERM实测← ④ 机制 2
现象
和坑 1 一样：等满 10 秒，退出码 137。
根源
Linux 不把“默认动作”的信号送给 1 号进程，没装处理函数就等于忽略。
做法
装处理函数；处理函数里只设标志，在每轮结束时检查。
3宽限期比一轮还短← ④ 机制 2
现象
装了处理函数，还是偶尔被强杀，刚好都是在等一个很慢的模型调用时。
根源
K8s 默认 30 秒，而一轮最长可以到 60 秒（模型调用的超时）。
做法
terminationGracePeriodSeconds 设成最长一轮 + 余量（清单里 90 秒）；收到 SIGTERM 后的那次模型调用可以用更短的超时。
4按 pendingEntriesCount 扩缩← ④ 机制 3
现象
队列里积了 38 个事件，worker 一直是 1 个 Pod。
根源
待确认列表里只有“已经分出去的”，最多等于 worker 的并发数，和积压无关。
做法
按 lagCount（还没分出去的，Redis 7 以上）扩；上限按额度定，别让它无限扩。
5存活探针把正在等模型的 worker 杀了← ④ 机制 2
现象
大促时供应商变慢，worker 一个接一个地被 K8s 重启，积压更高了。
根源
存活探针检查的是“最近一次调用模型成功了吗”，供应商慢，探针就失败。
做法
存活探针只查进程自己（事件循环还在转）；依赖的健康放进就绪探针或者干脆不查；供应商慢交给熔断和降级。补给页：资源和探针。
6只读根文件系统，库要写临时文件← ④ 机制 1
现象
加了 readOnlyRootFilesystem 以后，某个库一启动就报 Read-only file system。
根源
不少库会往 /tmp 或家目录写缓存。
做法
给 /tmp 挂一个 emptyDir；能关的缓存关掉。
7以为 Secret 是加密的← ④ 机制 4
现象
安全审计说 etcd 的备份里能看到所有 key。
根源
Secret 默认只是 base64；静态加密要另外开。
做法
开 etcd 的静态加密，或者用外部密钥库（External Secrets、KMS）；按命名空间限制谁能读 Secret；真 key 只给网关。
8镜像用 latest、依赖不锁← ④ 机制 1
现象
同一个版本号，昨天能跑，今天重建以后报错；或者装进来一个被投毒的新版本。
根源
基础镜像和依赖都在悄悄变。
做法
基础镜像写到小版本（python:3.13.18-slim-bookworm），依赖按锁文件装（uv sync --frozen），自己的镜像用不可变的版本号或摘要。

第二圈 · 使用规范

  • 多阶段 + slim + 锁文件 + 非 root：防镜像臃肿、防供应链、防容器逃逸后的权限。
  • exec 形式 CMD，worker 处理 SIGTERM，宽限期 ≥ 最长一轮：防发布和缩容时砍断调查。
  • 按积压扩，按额度封顶：防扩不起来，也防扩出来全在排队。
  • key 不进镜像；worker 只拿虚拟 key；真 key 只给网关：防泄露面太大。
  • 出网白名单：防被注入以后把数据发出去。
  • 存活探针只查自己：防依赖变慢时被连环重启。

第三圈 · 优化和深处

缩到零

夜里没有告警时，KEDA 可以把 worker 缩到 0 个（minReplicaCount: 0），来了第一条再起。代价是第一条要多等一次 Pod 启动（这里是几秒）。P0 不能等的话，保留 1 个常驻。

发布：先让 worker 不再领新活

滚动发布前，可以先给旧版本发一个“排空”信号：不再领新任务，手上的做完就退。再配合 maxSurge 先起新版本，切换期间吞吐不掉。

私有化要算的账

机房里的模型，额度变成了显卡的吞吐：一块卡每秒能生成多少 token、能同时服务几个请求。限流那页的“并发上限 = 额度 ÷ 用量”照样成立，只是额度要自己压测出来（下一页）。

多地域

两个机房各一套 worker 和网关，队列和额度怎么分，故障时谁接管：属于下一圈。

  • External Secrets 从密钥库同步网关的真 key，轮换时网关不重启。
  • vLLM 在一块 GPU 上起一个开源模型，网关把 triage 别名指过去，跑一遍站 09 的评测。

  2. 宽限期太短：ROUND_SEC=15、docker stop -t 5，有处理函数也会被强杀吗？检查点停在第几轮？（坑 3）
  3. tini：给 naive 镜像加 docker run --init，看 1 号进程变成了什么、SIGTERM 能不能传到 python。（坑 1）
  4. 只读根文件系统：docker run --read-only 跑 slim 镜像，看 worker 能不能起来；不能的话缺什么。（坑 6）

自测

1. 用一句话说出这一页的精华

worker 一个请求要跑一分钟，所以 SIGTERM 要真能送到、宽限期要够一轮、退出前写好检查点不确认；扩缩看积压、按额度封顶；真 key 只进网关，镜像里一个都不放。

2. 为什么按 CPU 扩 worker 不行？

worker 大部分时间在等模型，CPU 不到一成；瓶颈在供应商的额度上。按 CPU 永远扩不起来，按积压扩才对，而且上限按额度定。

3. 为什么装了 SIGTERM 处理函数，shell 形式的 CMD 还是被强杀？

1 号进程是 /bin/sh，K8s 和 Docker 只把 SIGTERM 发给 1 号进程，sh 不转发，python 根本收不到。

从 ④ 机制 2 推出。

4. 预测：worker 被强杀在第 5 轮中间，这个调查会怎样？

任务没 XACK，还在待确认列表里；别的 worker 用 XAUTOCLAIM 认领，从检查点读到第 4 轮，重做第 5 轮。不丢，只是第 5 轮白做了一次、晚了一点；第 5 轮如果是建工单，要靠幂等键不重复。

从 ④ 机制 2 和长任务那页推出。

5. 预测：KEDA 按 pendingEntriesCount 扩，阈值 8，每个 Pod 8 个协程，积压 38 个时会扩到几个 Pod？

不会扩：待确认列表里只有已经分出去的，最多 8 条（1 个 Pod × 8 个协程），平均每个副本 8，刚好不超过阈值。38 个积压在“没分出去”那边，它看不见。要按 lagCount 扩。

从 ④ 机制 3 推出。

6. 放回全景：第 ⑪ 站托着哪几站？如果 20:04 正好在滚动发布 worker、SIGTERM 又没处理，会怎样？

托着第 ③ 站的 worker 和第 ⑤ 站的网关。没处理 SIGTERM：每个旧 Pod 都要等满宽限期才被强杀，手上那一轮白做；新 Pod 起来以前，第 ② 站的积压继续涨；被强杀的任务靠 XAUTOCLAIM 被新 Pod 接走，P0 的报告会晚上一两分钟。发布最好避开大促，或者先排空再换。

从全景第 ②③⑪ 站和 ④ 机制 2 推出。

档位：标准（这个知识点的深度是“会用”）。本机跑过（2026-11-28，2 核 ARM，Docker 27.3.1，Python 3.13.18，Redis 8.12.0）：⑤ 的两个镜像和三次 docker stop；构建时间包含拉基础镜像，不能直接比。按文档：K8s 删除 Pod 时先发 SIGTERM、等 terminationGracePeriodSeconds（默认 30 秒）再 SIGKILL；KEDA 2.21 的 Redis Streams 扩缩器（pendingEntriesCount、lagCount，后者要 Redis 7 以上）。k8s/worker.yaml 按文档写，没有在集群上跑过。
