什么时候用低代码，什么时候写代码

不是选一边，是划一条线：改得勤、谁都能改、只读或只转发、走直线的“连线活”放在低代码画布上；要测试和审计、会改外部系统、有状态要等人的“核心”写在代码里。低代码的价值是改得快、谁都能改，代价是难测试、难评审、难审计，所以线按“改动频率 × 出错代价”来划。全景就是这么切的：第 1、9 站在 n8n，分诊、调查、审批、写操作在值班助手里。

①要解决的问题：线划在哪

在全景第 1 站，这一步要回答的是：值班助手这一整套，哪些放 n8n、哪些写代码？业务同学说“能不能我自己拖”，开发说“全写代码才放心”，两种说法都对一半。这一站的过关条件一，也是要交一张四种实现的对比表：手写、LangGraph、Spring AI、Dify，比代码量、可控性、调试难度、token 成本。

②不划线会怎样

做法会出什么事
全写代码告警格式改一次、多通知一个群，都要建分支、评审、发布；没有业务逻辑的胶水服务越积越多，没人愿意维护。
全放画布分诊提示词、审批、写工单也拖成节点：没法单测，改动看不出 diff，出了事审计只能翻执行记录；幂等、检查点这些画布上很难做细（写操作那页的四道关，几乎每一道都要代码）。
两边各写一份同一个规则去重在 n8n、幂等在代码，键各定各的：这一站就踩了，n8n 按指纹去重、代码按指纹建幂等键，下周同一告警再响，两边一起把它挡掉（低代码那页实测）。
不懂精华时的典型误用：按“谁的技术栈”划线（运维会 n8n 就全放 n8n），而不是按“这一块改得多勤、错了代价多大”。

③几种流派

流派主张好处代价
全代码平台只是原型工具，上线一律重写成代码测试、评审、审计都在熟悉的流程里改动慢，业务同学永远在排队等开发
全平台业务自助，开发只提供插件和接口改得最快，开发最省事核心逻辑没法测试和审计；平台成了单点
分层（本页）画布管边：触发、转发、通知、搬数据；代码管核：判断、状态、写操作。边和核之间只用 HTTP 接口说话改得勤的地方快，出错代价大的地方稳要维护一条清楚的接口；同一个规则（比如事件键）只能在一边定义

本页选分层：判断一块东西放哪边，不看它“是不是 AI”，看 ④ 的五个问题。

④核心取舍：改动频率 × 出错代价

机制 1 · 五个问题

问题偏低代码偏写代码为什么这个问题要紧
多久改一次每周都改很少改画布最大的好处是改得快；不常改的东西，这个好处用不上
谁来改业务或运维同学开发让不写代码的人自己改，是平台存在的理由
改不改外部系统只读或只转发写操作，尤其撤不回的写操作要幂等、审批、审计（写操作那页），画布上很难做细
要不要测试和审计不需要要单测、评审、审计画布的改动没有 diff、难单测；出了事要能说清改了什么
逻辑长什么样直线：触发 → 处理 → 转发有状态、要等人、要断点续跑检查点、interrupt、恢复这些机制在画布上要么没有，要么很粗

机制 2 · 把全景各站摆进四个格子

为什么这样设计：按改动频率和出错代价划，不按技术栈划

低代码画布

  • 改得快：⑤ 里修正去重键，导入、发布，正在跑的 n8n 十几秒后就接上了，没重启。
  • 谁都能改，每次执行的输入输出都存着。
  • 代价：难单测，改动没有 diff，评审和审计都靠翻记录；状态和恢复做不细。

代码

  • 测试、评审、审计、断点调试都在熟悉的流程里；检查点、幂等、审批能做到很细。
  • 这一站的五个真坑（参数名 arg0、token 口径、线程池、事件键、reducer）都是靠读代码和打日志查出来的。
  • 代价：改一个转发目标也要走一遍发布。
决定胜负的约束：低代码省的是“改动的成本”，丢的是“验证的能力”。改得越勤，省的越多；错了代价越大，丢的越要命。所以线只能按这两个量划：改得勤又代价小的放画布，代价大的写代码，两者都大的写代码并把常改的那一块配置化。

机制 3 · 什么时候该从画布“毕业”成代码

  • Code 节点越写越长：画布上一半是 JavaScript，测试、评审、复用一样都没有，两边的坏处全占了。
  • 开始有写操作、要审批、要审计，或者出了一次说不清“是谁改了什么”的事故。
  • 流程里出现了状态：要等人、要重试、要断点续跑。
  • 同一个规则在画布和代码里各定义了一份（比如事件键），开始不一致。

反过来也成立：代码里那些只是“收一个请求、转给另一个地方”的小服务，没人愿意维护，可以考虑搬到画布上。

实验台：划线器

先猜：全景第 9 站，“张三在审批卡片上点批准，转成值班助手的 /resume 请求”，放哪边？

打分规则写在页面脚本里：每个问题一个分，正分偏低代码、负分偏写代码，合计 ≥ 2 放低代码，≤ −2 写代码，中间是混合。权重是这一页的经验取舍，不是行业标准；换成你团队的实际情况调一调，比结论更有用。

到这里已经能交差了：能用五个问题判断一块东西放画布还是写代码，能拿这一站的实测填出四种实现的对比表（Dify 那一格自己做）。
已知还没处理的细节：Code 节点越写越长（坑 1）、同一规则两边各定义一份（坑 2）、平台成了单点（坑 3）、画布上的提示词没人评审（坑 4）。

⑥反例和误用

第一圈 · 注意事项

1画布上的 Code 节点越写越长按设计← ④ 机制 3
现象
为了做一个判断，在 n8n 或 Dify 的代码节点里写了一百多行 JavaScript / Python，没有测试，复制到另一个工作流里又改了一份。
根源
画布的好处是“不写代码也能改”；一旦主要逻辑在代码节点里，这个好处就没了，代码的好处（测试、评审、复用）也没有。
做法
代码节点只放几行数据变换；超过这个量就把它做成一个服务，画布上用 HTTP 节点调它。
2同一个规则在两边各定义一份实测← ④ 为什么这样设计
现象
这一站就踩了：n8n 按指纹去重，代码按指纹建幂等键，下周同一告警再响，两边一起把它挡掉；改的时候还得两边一起改。
根源
边和核之间的接口没约定清楚，规则散在两边。
做法
像事件键这样的业务规则只在一边定义：值班助手的 /incidents 接口收原始告警、自己算事件键，n8n 只转发；或者反过来由 n8n 算好、作为接口字段传进来，代码只认这个字段。
3平台成了单点，挂了没人知道实测← ④ 机制 1
现象
n8n 收到就回 200、去重又在转发之前记了键：值班助手停着时进来的告警，恢复后重发也收不到（低代码那页实测，0 次）。
根源
边放在画布上，并不意味着边不重要；告警接入错了，后面整条链路都白搭。
做法
画布上的流程也要有监控、失败告警和高可用；关键路径（告警接入）上的失败要回错误让上游重试。
4业务同学改了画布上的提示词，没人评审按设计← ④ 机制 2
现象
FAQ 机器人的提示词被改了一句，回答风格变了，还开始编造制度条款；没人知道是哪天、谁改的。
根源
提示词是“改得勤、错了代价不小”的东西，落在四象限的右上，不该只放在谁都能改、没有评测门禁的地方。
做法
提示词也版本化，改动走评审，改完跑一遍评测集再上线（站 09）。

第二圈 · 使用规范

  • 边和核之间只用 HTTP 接口说话，接口写成文档（OpenAPI）：防坑 2，换平台时核不用动。
  • 画布上不放写操作、不放状态：写操作和等人留给代码（检查点、幂等、审计）。
  • 画布导出进 Git，代码节点不超过十几行：防坑 1。
  • 画布流程和服务一样配监控和失败告警：防坑 3。
  • 每半年按五个问题复查一次：改得少了的搬回代码，没人维护的小服务搬上画布。

第三圈 · 优化和深处

“配置化”是第三条路

四象限右上（改得勤、代价大）既不适合画布，也不想每次都发版：把常改的那一小块抽成配置，比如提示词、任务书模板、审批规则表、通知列表，配置有版本、有评审、改完跑评测。这比“全放画布”稳，比“全写死在代码里”快。

低代码的位置会继续变

n8n、Dify、Coze 都在往 agent 方向长（AI Agent 节点、MCP、插件）。判断规则不会变：看改动频率、出错代价、要不要状态。平台能做的事变多了，右下角那些写操作和状态，仍然要能测试、能审计。

自测

1. 用一句话说出这一页的精华

按“改动频率 × 出错代价”划线：改得勤、代价小、直线的连线活放画布；要测试审计、写外部系统、有状态的核心写代码；两者都高的写代码并把常改的部分配置化。

2. 不划线，两种极端各疼在哪？

全写代码：胶水服务越积越多，改一点都要发版。全放画布：核心逻辑没法测试和审计，状态和幂等做不细，平台成单点。

3. 为什么不按“团队会什么”来划线？

低代码省的是改动成本、丢的是验证能力；放哪边该由“这一块改得多勤、错了代价多大”决定，和谁熟悉什么工具无关。

从 ④ 为什么这样设计推出。

4. 预测：给第 1 站加一个需求“凌晨的 P3 告警先不转发，攒到早上 9 点一起发”，还放 n8n 吗？

还可以放：仍是只读和转发，改动由运维决定；但多了“攒着等”这个状态，要用定时触发和一张暂存表。如果再加上“攒的时候要能撤回、要审计谁放行了”，就该把它搬进代码。划线器上把“逻辑形状”从直线改成有状态，分数就掉下来了。

从 ④ 机制 1 的第五个问题推出。

5. 预测：值班 FAQ 机器人后来加了“答不上来就自动建一张工单”，它的位置怎么变？

从“全放低代码”变成“混合”或“写代码”：多了写操作（建工单），要幂等和审计。常见做法是问答留在 Dify，建工单那一步调值班助手的接口，由代码负责幂等和记录。

从 ④ 机制 1 的第三个问题推出。

6. 放回全景：第 1 站和第 9 站都在 n8n 上，它们和值班助手之间靠什么连接？这条连接坏了会怎样？

靠两个 HTTP 接口：/incidents（第 1 站转发告警）和 /resume（第 9 站转发批准）。第一个坏了，告警进不来（还可能因为去重被永久丢掉）；第二个坏了，线程一直停在第 8 站等人，写操作不会执行。所以这两个接口要写成契约，两边都要监控。

从全景第 1、2、8、9 站推出。
