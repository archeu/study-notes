长任务架构：队列、工作者、状态存储、进度推送

一次调查要一分钟、调 6 次模型，不能塞进一个 HTTP 请求里。精华是四件东西各管一摊：队列把“来得快”和“做得慢”隔开；worker 自己来拉，有空才拉；状态存储让中途被杀的任务从上一轮接着跑；进度推送让人看得见。队列只保证“至少送到一次”，所以写操作必须幂等。

全景：大促夜里 1000 个告警同时涌进来 · 第 1、2、3 站地图：站 10 · 长任务架构深度：懂设计

这一页的位置站 10 第 1 个下钻知识点。站 04 的 agent 循环、站 08 的 LangGraph 检查点讲的是“一个调查怎么跑”；这一页讲 87 个调查一起来时，怎么排队、怎么分给 worker、挂了怎么接着跑、人怎么看到进度。

①要解决的问题：一分钟的活，不能塞进一个请求里

在全景第 1～3 站，这一步要解决：20:00 起 6 分钟里涌进 1000 条告警，去重合并后是 87 个事件；每个事件要一次调查，平均 6 轮模型调用、约一分钟；而供应商的额度只够 12 个调查同时跑。上面那一行是直接在请求里做，下面那一行是这一页要搭的样子。

6 分钟里涌进1000条告警，合并成 87 个事件
一次调查≈60 秒6 轮模型调用
额度只够同时跑12个调查，其余要排队
回执2.8 ms写进队列就回 202（实测 p50）

所以要的不是“快一点”，而是五条要求同时满足：

  1. R1 回执要快：推送方毫秒级拿到 202，不会因为等不住而重发。
  2. R2 削峰：来 87 个也只同时跑得动的那几个，其余排队，不把额度和下游一起压垮。
  3. R3 挂了不丢、不白花：worker 中途被杀，任务有人接手，已经花过 token 的轮次不重来。
  4. R4 看得见进度：值班的人知道每个事件跑到第几轮，刷新页面也接得上。
  5. R5 要紧的先做：P0 不排在 P2 后面。

②不用它会怎样：同步做，或者“开个后台任务”

Java 后端最顺手的两种做法：在 Controller 里直接做完；或者加个 @Async，丢进线程池（Python 里是 asyncio.create_task 或 FastAPI 的 BackgroundTasks）。拿 ① 的五条要求逐条对：

要求同步做完再回进程内后台任务（@Async / create_task）队列 + worker + 状态存储
R1 回执要快不能：要等 60 秒，推送方当失败重发能：丢进线程池马上回能：XADD 之后就回，实测 2.8 ms
R2 削峰不能：来几个并发几个，87 个一起打到供应商差一点：线程池满了就拒绝或无限排在内存里，而且每个副本各排各的能：worker 数就是并发上限，多出来的在队列里等
R3 挂了不丢、不白花不能：请求断了就没了不能：任务只在内存里，Pod 一重启，排着的和跑到一半的全没了，也没人知道能：没确认的消息留在待确认列表，别人认领后从检查点接着跑
R4 看得见进度不能：只有最后一个响应差一点：进度在本进程内存里，网页连到另一个副本就看不到能：进度写进 Redis，任何副本都能推给网页
R5 要紧的先做不能：先到先做不能：线程池先进先出能：P0、P1、P2 三条流，先看 p0

后台任务只解决了 R1。它真正缺的那一块，是任务和进度不在 worker 进程的内存里：任务放在一个独立、持久的队列里，做到哪一步也写在外面。这一块就是长任务架构的精华。

不懂精华时的典型误用：以为“加了 @Async 就是异步架构”。大促当晚扩容滚动重启了一次，内存里排着的 30 个调查没了，告警方早就拿到了 202，谁也不会再发一遍。

③几种流派：从“开个线程”到“工作流引擎”

流派适合worker 挂了怎么办代价
进程内后台任务
@Async、create_task、BackgroundTasks		几秒的小活，丢了也无所谓（发个通知）丢了最便宜，不多一个组件
消息队列 + worker + 自己存状态
Redis Stream、Kafka、RabbitMQ、Celery		分钟级、要实时看进度、千级并发：大促夜的调查没确认的消息重投给别人，从检查点接着跑检查点和幂等要自己写
持久化工作流引擎
Temporal、LangGraph 的持久执行		小时到天、几十步、要补偿和人工等待引擎按记下的事件历史重放，做完的步骤不重做多一套服务；流程代码要守“可重放”的规矩
供应商的批处理接口
Message Batches		不急：一天之内出结果就行（离线跑评测、批量打标签）供应商负责不实时：多数一小时内完成，最长 24 小时，换来价格减半

本页学 Redis Stream 消费组 + 每轮检查点 + 幂等的写工具：要分钟级出结果、要看进度、量在千级时，队列 + worker 最合适；流程长到小时级、要补偿，再换工作流引擎；不急的活交给批处理接口省一半钱。全景里用 Redis Stream，是因为一个 Redis 就够、进度流也能放在同一处；换成 Kafka，下面的道理一条不变。

④核心取舍：至少一次 + 每轮检查点 + 幂等

先知道这些
  • 消费组和待确认列表（PEL）：一条 Redis Stream 可以挂一个消费组，组里每条消息只分给一个消费者；分出去以后记在 PEL 里（在谁手上、投递过几次），消费者 XACK 了才删。补给页：Redis Stream 与消息队列。
  • 检查点：把“跑到第几轮、消息历史是什么”存到进程外面，重启后读回来接着跑。站 08 讲过 LangGraph 怎么做：LangGraph 检查点。
  • 幂等：同一个操作做一次和做三次，结果一样。查日志天然幂等；建工单、发通知不是。
  • SSE：服务器沿一条 HTTP 响应不停地往下写事件，每个事件可以带 id。站 03 讲过：SSE 流式。

机制 1 · 一个任务的一生：领走不等于做完

跟着实验里那个 P0 事件走一遍。它在第 5 轮被杀，看它怎么被别人接走、接着跑。

图比屏幕宽，左右滑动看全图 →

准备点“下一步”。

要点只有一句：消息被领走时并没有删，只是挪进了 PEL；做完、XACK 了才删。所以 worker 死了，任务还在，别人可以把它认领过来。代价是同一个任务可能被做不止一次，这叫“至少一次”。

机制 2 · worker 自己来拉：拉模式就是背压

worker 只在手上空了的时候才去领下一个，所以同时在跑的调查数 = worker 数，多出来的都在队列里等，这就是 R2 的削峰。反过来，如果有个调度中心往 worker 推任务，调度中心就得知道每个 worker 忙不忙，推多了 worker 里又堆起一个看不见的内存队列。优先级也放在“拉”这一侧：worker 每次先看 oncall:p0，空了才看 p1、p2。⑤ 里 87 个调查，最后一个 P0 是第 9 个做完的，第一个 P2 是第 41 个（9 + 31 + 1）。

worker 数该设多少，不看 CPU：调查的时间几乎都在等模型。上限由第 ④ 站的额度定（全景里是 12 个），下一页“限流和配额”专门讲。

机制 3 · 检查点存在哪一刻：崩溃窗口

每一轮的顺序是：调模型 → 执行工具 → 写检查点 → 发进度。检查点写在工具执行之后，所以中间那一小段如果崩了，副作用已经发生，检查点却不知道。

机制 4 · 至少一次 + 幂等 = 效果上恰好一次

崩溃窗口躲不掉，“只投一次”在分布式系统里也做不到：worker 做完了、XACK 之前断网，队列只能当它没做完，再投给别人。能做的是让重做无害：查日志这种只读工具天然幂等；建工单这种写工具，带一个幂等键，工单系统看到同一个键就返回已有的那张。

幂等键用什么重放时模型换了说法结论
模型生成的参数做哈希（标题、正文）不能防：第一次标题是“order-04 P99 2.1 秒”，重放时变成“订单接口 P99 升高”，哈希不同，又建一张别用
业务键：事件 id（+ 工具名）能防：一个事件只该有一张工单，跟模型怎么措辞无关首选
事件 id + 第几轮能防同一轮重做；如果重放时模型把建工单挪到了第 6 轮，就防不住业务上没有天然键时的退路

这是 agent 和普通消息消费最不一样的地方。Kafka 消费者重放一条订单消息，代码是确定的，同样的输入做同样的事；agent 重放一轮，模型可能做出不同的决定，参数、顺序都可能变。所以幂等键要从业务里找，不能从模型的输出里算。

机制 5 · 进度：写进流，而不是广播出去

worker 每轮往 progress:{事件 id} 这条流追加一条；接入服务的 /incidents/{id}/events 用 XREAD 读这条流，原样用 SSE 推给网页，流的条目 id 直接当 SSE 的 id。浏览器断线重连时会自动带上 Last-Event-ID，服务端从这个 id 之后接着读，一条不丢、不重（⑤ 实测：断在第 3 条，重连补上后 3 条，重复 0）。换成 Redis Pub/Sub 就不行：它只推给“此刻在线”的订阅者，断线那几秒的进度就没了。

为什么这样设计

拉模式 + 每轮存检查点 + 至少一次和幂等

  • worker 有空才领，并发上限就是 worker 数，不需要谁去盯着每个 worker 忙不忙。
  • 崩了最多重做一轮：一轮是几秒和几分钱，比从头 6 轮便宜得多。
  • 不追求“只投一次”，而是让重做无害，这在网络会断、进程会死的环境里做得到。
  • 代价：每个写工具都要想清楚幂等键；每轮多一次写库（毫秒级）。

调度中心推任务 + 只在做完时存结果 + 想要“只投一次”

  • 推多了 worker 里堆起看不见的内存队列，重启全丢，又回到 ② 的老问题。
  • 只在最后存：第 5 轮崩了，前 4 轮的模型调用全部重花，实测多了 4 次。
  • “只投一次”要求投递和执行在一个事务里，可调模型、建工单都在别的系统里，这个事务开不出来。
决定胜负的约束：一轮模型调用要几秒、花真钱，写一行状态只要几毫秒，所以每轮都存；而工具的副作用发生在队列管不到的系统里，没法和确认放进一个事务，所以只能“至少一次 + 幂等”。

Java 老朋友：Kafka 消费组

像：XACK ≈ 提交 offset；worker 挂了由别人接手 ≈ 消费组再平衡；“处理完再提交”≈“做完才 XACK”。地图上那句比方“断点续跑 ≈ Kafka 的 offset 提交”说的就是这个。

不像：Kafka 按分区记一个 offset，一条卡住整个分区都等；Redis Stream 每条消息单独确认、单独认领。更大的不像在 ④ 机制 4：Kafka 重放的是确定的代码，agent 重放的是会换主意的模型，工具必须幂等。

⑤套进场景：87 个事件、4 个 worker、一次被杀

把全景第 1～3 站搭出来：FastAPI 接入服务、三条 Redis Stream、几个 worker 进程、SQLite 当检查点库。没有真模型：假模型按固定剧本走 6 轮（前 4 轮查东西，第 5 轮建工单，第 6 轮出报告），每轮睡一会儿，并把“调了一次模型”记进库里，方便数次数。不需要 API key。

def investigate(c, con, stream, msg_id, fields, a):
    incident = fields["incident"]
    done_rounds, messages = load_state(con, incident)   # 检查点：跑到第几轮了
    for rnd in range(done_rounds + 1, 7):
        decision = fake_model(con, incident, rnd, a.name)
        if decision["type"] == "final":
            save_state(con, incident, rnd, messages + [decision])
            progress(c, incident, rnd, "报告已出")
            break
        result = run_tool(con, incident, decision["tool"], decision["args"],
                          a.name, idempotent=True)        # 建工单带幂等键
        if a.crash_at == rnd:
            os._exit(1)                                  # 模拟 Pod 被杀：工具做了，检查点没写
        messages.append({"round": rnd, "tool": decision["tool"], "result": result})
        save_state(con, incident, rnd, messages)          # 每轮存一次
        progress(c, incident, rnd, f"第 {rnd}/6 轮：{decision['tool']}")
    c.xack(stream, GROUP, msg_id)                         # 做完才确认

读出来的结论
  • 接入服务只做三件事（认租户、按指纹去重、按“租户 + 服务 + 告警名 + 5 分钟窗口”合并），p99 也不到 7 毫秒；1000 条里 120 条是重发，793 条被合并，剩 87 个事件。
  • 优先级靠“先看 p0”就够了：9 个 P0 全部最先做完，P2 平均要等到 19.9 秒。全景时间线上 P2 排队 4.8 分钟，是同一个现象放大到真实耗时。
  • 检查点省的是模型调用（7 次对 11 次），幂等键省的是重复副作用（1 张对 2 张）。两样缺一样，都会出事，而且出的是不同的事。
  • min-idle 比一轮还短，任务还在跑就被别人认领走了，一个调查做了两遍（12 次调用）；加心跳以后回到 6 次。
到这里已经能交差了：告警进来 3 毫秒回执，P0 先做，worker 被杀能接着跑，网页断线能接上，工单不重复。
已知还没处理的细节：先确认再做会丢任务（坑 1）；min-idle 和心跳（坑 3）；一直失败的毒消息（坑 6）；队列和进度流要设上限（坑 8）。

⑥反例和误用

第一圈 · 注意事项

1先 XACK 再干活← ④ 机制 1
现象
worker 被杀以后，那个调查再也没人做，PEL 里也找不到它。
根源
XACK 就是“删掉”。先删再做，“至少一次”变成了“至多一次”。
做法
做完（报告写进状态库）以后最后一步才 XACK。
2只读 ">"，从不捡 PEL← ④ 机制 1
现象
崩掉的任务一直挂在 PEL 里，XPENDING 的数字只涨不降，告警方以为早就处理了。
根源
">" 只领“还没分给任何人”的消息；分出去又没确认的，要有人用 XAUTOCLAIM 去认领。
做法
每次领新任务前先 XAUTOCLAIM 一下；或者单独跑一个“清道夫”定时认领。
3min-idle 比最长的一轮还短实测← ④ 机制 1
现象
同一个调查被两个 worker 同时在做：⑤ 里 12 次模型调用、“做完”记了 2 次。
根源
PEL 只看“多久没被投递”，不知道 worker 是死了还是在等一个 30 秒的模型调用。空闲超过 min-idle 就会被认领走。
做法
跑任务时定期 XCLAIM <自己的消息> … JUSTID 续租（把空闲清零、不增加投递次数）；或者 min-idle 设得比“最长一轮 + 余量”还长，代价是崩了以后接手更慢。
4写工具不幂等实测← ④ 机制 4
现象
worker 在第 5 轮被杀，接手的人重做第 5 轮，工单系统里同一个事件两张工单。
根源
崩溃窗口躲不掉，至少一次意味着工具可能被调两次。
做法
每个写工具带幂等键，工单系统按键去重；对方系统不支持幂等键时，先查“这个事件有没有工单”再建。
5幂等键用模型生成的参数算← ④ 机制 4
现象
明明加了幂等键，重放时还是多了一张工单，两张标题措辞不一样。
根源
重放那一轮模型重新生成了参数，换了说法，哈希就不一样。
做法
用业务键：事件 id + 工具名。一个事件该有几张工单，是业务规则，不是模型说了算。
6毒消息无限重投← ④ 机制 1
现象
某个事件每次跑到第 3 轮就让 worker 崩（比如日志大到撑爆内存），它被认领、崩、再认领，一个接一个地拖垮 worker。
根源
“至少一次”对必然失败的任务也一样执着。
做法
认领时看 PEL 里的投递次数（XPENDING 扩展形式的 times_delivered），超过 3 次就写进死信流 oncall:dead 并 XACK，转人工。⑤ 的 worker 就是这么写的。
7进度只走 Pub/Sub 或只在内存里← ④ 机制 5
现象
值班的人刷新一下页面，前几轮的进度就没了；网页连到另一个副本，什么都看不到。
根源
Pub/Sub 只发给此刻在线的订阅者，不留底。
做法
进度写进每个事件自己的流，SSE 的 id 用流的条目 id，重连带 Last-Event-ID 从断点读。
8队列和进度流不设上限← ④ 机制 2
现象
worker 全挂了一夜没人发现，第二天 Redis 内存告警；几千条进度流没人清。
根源
拉模式下生产者不受消费者影响，消费者停了队列就一直长。
做法
进度流 XADD … MAXLEN ~ 200，做完再给整条流设过期；任务流按积压长度和最老一条的等待时间报警，积压超过阈值时接入服务降级（只记不调查，P0 除外）。

第二圈 · 使用规范

  • 接入服务只做记账，不做调查：认租户、去重、合并、入队、回 202。防的是推送方超时重发。
  • 做完才 XACK，领新任务前先 XAUTOCLAIM：防丢任务、防任务永远挂在 PEL。
  • 每轮工具执行完立刻写检查点：崩了最多重做一轮。
  • 写工具一律带业务幂等键：防重放时重复建单、重复发通知。
  • min-idle 大于最长一轮，长任务加心跳：防两个 worker 做同一个调查。
  • 投递超过 3 次进死信并转人工：防毒消息拖垮 worker。
  • worker 并发上限按额度算，不按 CPU 算：防扩出来的 worker 全在等令牌（下一页）。

第三圈 · 优化和深处

什么时候换工作流引擎

Temporal 这类引擎把每一步的结果记成事件历史，worker 崩了，新 worker 重放历史、跳过已经记下结果的步骤，等于把 ④ 的检查点和幂等做进了框架。代价是流程代码要“可重放”：不能直接读当前时间、随机数，调模型这种不确定的事要包成“活动”（activity），结果记进历史。调查一分钟、6 轮时自己写检查点够用；流程到了小时级、有补偿和人工等待（站 08 的审批），才值得多维护一套服务。

优先级：三条流，还是一条流打分

⑤ 用三条流、先看 p0，简单、可观测（每条流的积压一目了然），缺点是 P2 可能饿死：P0、P1 一直有，P2 永远轮不到。大促夜 P2 等 4.8 分钟可以接受；要保底就按比例轮询（每领 5 个 p0/p1 至少领 1 个 p2），或者把等待时间算进分数，等得越久分越高。

状态库放哪

实验用 SQLite；线上多副本要放 Postgres 这类共享库（站 08 的 LangGraph checkpointer 有现成的 Postgres 版）。检查点只存“恢复要用的最少东西”：轮次、消息历史、工具结果；大块的日志原文存对象存储，检查点里只放引用，不然每轮都写几百 KB。

不急的活不进这条队列

大促第二天“把昨夜 87 份报告重新打标签”这种活，不需要实时：交给供应商的批处理接口，价格减半、不占实时额度，也不和当夜的调查抢 worker。

下一圈

  • Temporal 跑一遍同样的调查：看事件历史长什么样、重放时哪些步骤被跳过。
  • Kafka 版：按租户分区，对比“一条卡住整个分区”和 Redis Stream 的单条确认。
  • 多地域：两个机房各有 worker，任务流怎么复制、谁来认领。
  • 取消：值班的人点了“不用查了”，正在跑的调查怎么停、停在哪一轮。

↺回到⑤：改一改

  1. 先确认再干活：把 XACK 挪到 investigate() 开头，再跑实验 3。做对了会看到：B 等满 4 秒什么也领不到，那个调查没人做完。（坑 1）
  2. 先记意图：工具执行前先在检查点里记一笔“要调 create_ticket”，执行后再记结果；重放时看到“有意图没结果”，先去工单系统查有没有这个事件的工单再决定。做对了会看到：不靠幂等键也只建 1 张。（坑 4）
  3. 造一条毒消息：让某个事件的假工具每次都抛异常，看它第几次投递后进了 oncall:dead。（坑 6）
  4. 积压降级：给 ingress.py 加一条：同一个租户 1 分钟内超过 30 个新事件，就只记不调查，P0 例外。（坑 8）

自测

1. 用一句话说出这一页的精华

任务和进度放在 worker 进程外面：队列削峰、worker 拉取、每轮存检查点、进度写进流；队列只保证至少一次，所以写操作要用业务键做幂等。

2. 加个 @Async 不就异步了吗，老办法到底缺什么？

缺的是“任务不在内存里”：Pod 重启时排着的、跑到一半的全丢；也没法跨副本削峰、看进度、排优先级。它只满足了“回执要快”这一条。

3. 为什么检查点写在工具之后，崩溃窗口还是躲不掉？

工具的副作用发生在工单系统里，检查点在状态库里，两边开不出一个事务。写在工具之后，崩在中间会重做（可能重复）；写在工具之前，崩在中间会漏做。窗口只能挪，所以要幂等兜底。

从 ④ 机制 3、4 推出。

4. 预测：把 min-idle 从 2 秒改成 10 分钟，实验 3 会怎样？实验 4 呢？

实验 3：B 要等 10 分钟才能认领，调查晚 10 分钟出报告（demo 里 B 4 秒没活就退出，干脆就没人做完）。实验 4：一轮 1.5 秒远小于 10 分钟，不会再被别人认领，没心跳也只做一遍。min-idle 是在“接手快”和“不误抢”之间取舍，心跳让它不必取舍。

从 ④ 机制 1 推出：PEL 只看空闲多久，不知道 worker 是死是活。

5. 预测：worker 从 4 个加到 40 个，87 个调查会快 10 倍吗？

实验里会（假模型不限速），全景里不会：真实的并发上限是第 ④ 站的额度，只够 12 个调查同时跑，多出来的 28 个 worker 都在等令牌。拉模式下 worker 数是并发上限，但不是唯一的上限。

从 ④ 机制 2 和全景第 ④、⑦ 站推出。

6. 放回全景：第 1～3 站前后各发生了什么？如果第 2 站的 Redis 挂了 2 分钟，整条链路会怎样？

前面是 Alertmanager 推告警，后面是第 ④ 站按租户扣额度、第 ⑤ 站网关调模型。Redis 挂了：接入服务 XADD 失败，只能回 5xx 让推送方重发（这时候不能回 202，不然告警就丢了）；worker 领不到任务，正在跑的调查写不了进度和 XACK，网页进度停住。Redis 回来后推送方重发的告警被指纹去重挡住一部分，没确认的任务被认领接着跑。要更稳，任务流开 AOF 持久化，或者换 Kafka 这类多副本的队列。

从全景第 ①②③ 站和 ④ 机制 1 推出。

档位：标准。本机跑过（2026-11-28，2 核 ARM，Python 3.13.18，Redis 8.12.0，redis-py 8.2.0，FastAPI 0.165.0，uvicorn 0.54.0）：⑤ 的 5 个实验，页面上标“实测”的数字都来自它。按文档（已核对原文）：XAUTOCLAIM 6.2 加入、7.0 起返回第三个元素（已删除的 id）；XCLAIM … JUSTID 不增加投递次数、默认把空闲时间清零；SSE 重连带 Last-Event-ID；Message Batches 最长 24 小时、价格减半。真实模型一轮约 8 秒是全景页的设定，不是实测。
