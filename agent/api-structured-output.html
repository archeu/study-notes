结构化输出：JSON Schema、Pydantic 校验、失败重试

要一个程序能直接用的结果，有三层保险：提示词说清格式（只能提高概率）；JSON Schema 约束解码在采样时把不合格式的 token 概率置零（保证形状）；Pydantic 校验 + 带错误原因重试在你自己这边兜底（还能查 schema 管不到的规则）。实测各 100 次：只靠提示词第一次合格 98 次、重试后 99 次；约束解码 100 次全合格。可两组的类别都只对了六成左右：形状保证不等于内容正确。

①为什么需要：分诊结果要进工单系统，不是给人看的

在全景第 9 站，这一步要解决：模型返回的是一段文字，值班助手要的是一个对象：type 拿去路由给对应的值班组，level 决定打不打电话，first_check 写进工单。字段少一个、取值多一个“性能问题”、外面包一层 ```json，下游程序就会崩。

③相邻方案：拿到 JSON 的几种办法

办法保证什么说明
提示词要 JSON什么都不保证第 1 层，永远要写
“JSON 模式”是合法 JSON，但不管字段一些服务提供；字段和取值还得自己查
JSON Schema 约束（Claude 的 output_config.format）符合 schema 的形状按文档，Opus 5.5、Sonnet 5.5、Haiku 5.5 等都支持；不能和引用（citations）、预填同时用
严格工具调用（strict: true）工具参数符合 schema模型本来就要调工具时用（站 04）
Pydantic 校验 + 重试你写的所有规则第 3 层，永远要有

本页学“约束 + 校验 + 重试”的组合：Claude 上用 messages.parse(output_format=Triage) 一行拿到两层，再加你自己的业务校验和重试。

④原理：三层保险，各管一段

先知道这些
  • 采样：每一圈从概率表里挑一个 token，挑之前可以先把某些候选砍掉（采样页的 top_p 就是一种砍法）。
  • 多轮：要模型改，就把它的错回答和你的意见作为新两轮消息加上去重发（Messages API ④）。

机制 1 · 约束解码：采样前，把“不合 schema 的 token”概率置零

机制 2 · Pydantic 校验：在你自己的进程里再查一遍

一个 Pydantic 模型同时是三样东西：给服务端的 JSON Schema（model_json_schema()）、解析器（model_validate_json()）、业务代码里用的类型。Java 里最像的是 DTO 加 Bean Validation（@NotNull、@Pattern、@Valid）。比方失效的地方：DTO 的另一头通常是可靠的程序，这里的另一头是会出错、但能“改了再交”的模型，所以校验失败不是直接 400，而是带着原因让它重写。

机制 3 · 带着错误原因重试：让模型知道错在哪

多轮重试⑤ A 组的写法
for attempt in (1, 2, 3):
    text = call(msgs)
    try:
        return Triage.model_validate_json(extract(text))
    except ValidationError as e:
        msgs += [{"role": "assistant", "content": text},
                 {"role": "user", "content":
                  f"上面的输出不合格：{e.errors()[0]['msg']}。"
                  "只输出符合要求的 JSON。"}]
raise TriageFailed()

哪些情况别重试

  • stop_reason == "max_tokens"：是被截断，重试还是截断，要调大上限（站 02）。
  • stop_reason == "refusal"：拒答，按文档此时输出可能不符合 schema，换个说法或走人工。
  • 同样的错连错两次：多半是提示词或 schema 本身有歧义，再试也是浪费钱。

机制 4 · schema 管不到的：内容对不对、字段之间的规则

schema 只描述形状：字段在不在、类型对不对、取值在不在枚举里。“这条告警到底是不是 GC”“P1 必须给出 first_check”“cause 里不许出现日志里没有的数字”，schema 都管不了。按 Claude 文档，它的 schema 连 minimum、maxLength 这类数值和长度约束都不支持（SDK 会把它们从发给服务端的 schema 里去掉、改在客户端校验）。这些都要在 Pydantic 的校验器或业务代码里查。

为什么这样设计：约束解码和校验重试，为什么两个都要

约束解码（服务端）

  • 形状零失败、零重试：不合语法的 token 根本没机会被抽中。
  • 代价：只管 schema 能表达的；新 schema 有编译开销；强行掐掉模型想写的东西，偶尔会把内容挤歪（模型“想”解释两句，却只能塞进一个字段）。

校验 + 重试（调用方）

  • 什么规则都能写，包括跨字段、业务规则、和原文核对。
  • 代价：每次失败多一次调用，多花钱和时间；单靠它，第一次就失败的比例取决于提示词和模型。
决定胜负的约束：生成方是概率性的，任何一层都做不到 100%。约束解码把最常见、最便宜可防的形状错误消灭在源头，校验重试兜住剩下的规则，两层合起来，失败率是两层各自失败率的乘积。

最少的语法

Claude：用 Pydantic 模型直接要结构化结果按 Claude API 文档（Python SDK）

    level: Literal["P1", "P2", "P3"]

⑤亲眼看到：连续 100 次，能不能全部通过校验

站 03 的地图过关题 1。8 条告警轮流用，共 100 次，温度用本机服务的默认值 0.8（让每次输出有变化，更接近真实流量）。同一个 Pydantic 模型 Triage 做判卷标准。

  1. A 只靠提示词官方 anthropic SDK → 本机 /v1/messages（它会忽略 output_config.format，只能靠提示词）；Pydantic 校验，不合格就把错回答和错误原因作为两轮消息加上去重发，最多 3 次。
  2. B 约束解码把 Triage.model_json_schema() 交给本机 OpenAI 兼容接口的 response_format，llama.cpp 把它编译成语法，在采样时约束；再用 Pydantic 校验一次。
⑤main.py（B 组核心）完整代码 →
schema = Triage.model_json_schema()                    # 同一个类生成 schema
body = {"messages": [...], "max_tokens": 200,
        "response_format": {"type": "json_schema",
                            "json_schema": {"name": "triage", "schema": schema}}}
text = post("/v1/chat/completions", body)["choices"][0]["message"]["content"]
t = Triage.model_validate_json(text)                   # 再用同一个类校验

A 只靠提示词：100 次里 第一次就合格 98，重试后合格 99，类别正确 58；一共调用 103 次，用时 259 s
   第几次合格：{1: 98, 2: 1, '3 次都失败': 1}
   失败原因：{'缺字段': 3, '没有 JSON': 1}

读出来的结论
  • 提示词已经很能打：说清字段、给了示例，第一次就合格 98%。剩下 2 次：1 次重试一次就好了，1 次连错 3 次（同一类“缺字段”的错反复出现）。
  • 只靠校验重试，过不了“100 次全过”这一关：99/100，而且为此多调用了 3 次。错法顽固时，重试是在浪费钱。
  • 约束解码把形状错误清零：100/100，一次重试都没有，用时也没变慢。
  • 形状和内容是两回事：两组的类别正确率都只有 58% 和 62%。约束解码保证了“写的是四个类别之一”，没法保证“写的是对的那个”。
  • 过关题的答案：约束解码 + Pydantic 校验 + 少量重试，形状 100 次全过；内容对不对，要另外靠更强的模型、更好的证据和程序核对（站 02 幻觉）。
到这里已经能交差了：你能用一个 Pydantic 类同时生成 schema、约束输出、校验结果，并写出带错误原因的有限次重试。
已知还没处理的细节：只靠提示词（坑 1），重试不带原因或无限重试（坑 2），截断和拒答（坑 3），校验过了就当真（坑 4），schema 写法不被支持（坑 5）。

⑥细节：三层保险各自的漏洞

第一圈 · 注意事项

1只靠提示词，量一大就有漏网之鱼实测← ④ 机制 1
现象
测试时几十次都好好的，上线一天几千次，每天总有几十个“缺字段”“没有 JSON”。
根源
提示词只改变概率；98% 的单次合格率乘上几千次，失败就是几十次。
做法
能用约束解码就用（Claude 的 output_config.format / messages.parse()）；用不了时，校验加重试必须有。
2重试不说错在哪，或者无限重试实测← ④ 机制 3
现象
同一条告警连错 3 次，错法一模一样；或者重试循环没上限，一条坏数据刷掉一大笔钱。
根源
只说“请重试”，模型不知道哪里不对；有些错是提示词本身的歧义造成的，重试多少次都一样。
做法
把错回答和具体错误（哪个字段、什么问题）作为两轮消息加回去；最多 2～3 次；连续同类错误就停，记日志、走人工或降级。
3截断和拒答当成格式错误去重试← ④ 机制 3
现象
半个 JSON 解析失败，重试三次都是半个。
根源
stop_reason 是 max_tokens（上限给小了）或 refusal（按文档，此时输出可能不符合 schema），换个说法重发解决不了。
做法
校验之前先看 stop_reason：截断就调大上限，拒答就走另一条路，只有 end_turn 下的格式错误才重试。
4校验通过就当结果是对的实测← ④ 机制 4
现象
100 次全部校验通过，类别只对了六成。
根源
schema 和 Pydantic 都只查形状和取值范围，不查“是不是这一类”。
做法
内容靠另外的手段：更强的模型、多样的示例、先查证据、关键字段用程序核对；上线前在评测集上量“内容正确率”而不只是“解析成功率”。
5schema 里写了服务端不支持的约束← ④ 机制 4
现象
schema 里写了 maxLength: 50，结果 cause 写了 200 字，也没报错。
根源
按 Claude 文档：数值和字符串长度约束、递归结构不支持，每个 object 都要 additionalProperties: false；Python 和 TypeScript SDK 会把不支持的约束从发出去的 schema 里拿掉，改在客户端校验。
做法
长度、范围这类规则写在 Pydantic 里，由客户端查；手写原始 schema 时照文档补上 additionalProperties: false。

第二圈 · 使用规范

  • 一个类管到底：Pydantic 类既生成 schema、又做校验、又是业务类型；改字段只改一处。防的是 schema 和校验各说各话。
  • 先看停因，再校验，再重试：顺序固定写在一个函数里，所有结构化调用都走它。防坑 2、3。
  • 记三个数：首次合格率、最终合格率、内容正确率（抽样人工或评测集）。防坑 1、4。
  • 枚举留个“其他”：真实世界总有四类以外的告警，没有“其他”，模型只能硬塞进某一类。

第三圈 · 更深一层

约束会不会让答案变差

约束只砍掉不合语法的 token；模型原本想写一段解释、却被逼着直接写字段时，内容偶尔会受影响。缓解办法是在 schema 里留一个 reason 字段放在前面，让它先写理由、再写结论（站 02 “依据在前”）。

流式 + 结构化

结构化输出也能流式返回，但半截 JSON 不能校验；要么等完整再校验，要么用能解析“部分 JSON”的库先展示、最后再严格校验（流式那页坑 4）。

实验台：单次合格率、重试几次、一天失败几次

先猜：单次合格率 98%，最多尝试 3 次，每天 2000 次调用。假设每次失败互相独立，一天大约有几次 3 次都失败？

“互相独立”按 (1−p)k 估最终失败率；“反复错”按 ⑤ 的实测比例估：A 组 2 个首次失败里有 1 个 3 次都失败，即首次失败的一半重试也救不回来。真实情况在两者之间。

自测

1. 用一句话说出这一页的精华

结构化输出要三层：提示词提高概率、JSON Schema 约束解码保证形状、Pydantic 校验加有限次带原因的重试兜底；形状全对不代表内容正确。

2. 约束解码为什么能保证形状？

schema 被编译成语法，每一圈采样前把此刻不合语法的 token 概率置零，只在合格的候选里抽，所以写出来的一定合格。

从 ④ 机制 1 和采样页推出

3. 为什么重试时要把错回答和错误原因都发回去？

接口无状态，不发回去模型不知道自己写了什么、错在哪；带着具体的错误（哪个字段、什么问题），它才有方向去改。

从 ④ 机制 3 和 Messages API 推出

4. 预测：B 组用了约束解码，如果把 max_tokens 改成 15，100 次里会怎样？

写到一半被截断，约束解码管不了长度，拿到的是半个 JSON，校验大量失败；stop_reason 是 max_tokens，重试也一样。约束保证的是“每一步都合法”，不保证“写得完”。

从 ④ 机制 1 和坑 3 推出

5. 预测：把 type 的枚举从 4 个类别改成只有“GC”一个，约束解码后类别正确率会变成多少？

形状 100% 合格，type 全部是 GC；8 条告警里只有 2 条真是 GC，正确率约 25%。约束会忠实执行你写的 schema，哪怕 schema 是错的。

从 ④ 机制 1 和机制 4 推出

6. 放回全景：第 9 站之前和之后是什么？如果第 9 站的校验被删掉，直接把模型输出写进工单，链路会怎样？

之前是第 8 站收齐、看停因，之后是第 10 站记录并返回。没有校验：约 2% 的回答缺字段或不是 JSON，第 10 站写工单时报错或写进空值；截断的半个 JSON 也会直接进去；即使用了约束解码，内容错的那四成也照样进了工单，只是程序不会崩。
