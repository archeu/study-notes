2026-11-08 20:16，告警 OrderApiP99High：order-04 /orders/{id} P99 2.1 秒（阈值 800ms），指纹 7f3a。和站 04～07 是同一次故障。

1n8n Webhook：接住告警，去重后转给值班助手

20:16:30 Alertmanager 把 OrderApiP99High（指纹 7f3a）POST 到 n8n 的 Webhook 节点。工作流按事件键（指纹 + 触发时间）去重，再用 HTTP Request 节点 POST 给值班助手的 /incidents。整个工作流是拖出来的四个节点，没写一行服务代码。

为什么要它接告警、去重、转发、发通知这类“连线活”，拖几个节点就完了，不值得写一个服务；agent 本体要测试、要版本管理，所以写代码。分界线划在哪，是这一站的一个知识点。

往下一层低代码平台：Dify、Coze、n8n；什么时候用低代码，什么时候写代码

常出的事Alertmanager 会重发同一个告警（告警状态变化、到了 repeat_interval）。不去重，就会起两次调查、发两张审批卡。去重用的事件键（指纹 + 触发时间），和第 ⑩ 站幂等键里的是同一个。只用指纹的话，下周同一个告警再响会被当成重复丢掉（低代码那页实测）。

2LangGraph：按 thread_id 找检查点，起图

值班助手收到请求，调 graph.invoke({"alert": …}, {"configurable": {"thread_id": "alert-7f3a"}})。框架先拿 thread_id 去检查点库里找这条线程；没找到，就从 START 开始跑编译好的状态图：triage → 3×investigate → summarize → approve → act。

为什么要它站 04 手写的 while 循环里，“下一步做什么、状态放哪、失败了怎么办”全是自己写的代码。框架把这些收成一张图、一份 state 和一个检查点库。代价是有些东西你看不见了：重试、并发、什么时候存盘，都在框架里面。

往下一层框架替你做了什么、藏了什么；Python 框架主修 LangGraph（带上 LangChain 基础），AutoGen、Claude Agent SDK 了解；Java 框架：Spring AI、Spring AI Alibaba、LangChain4j（Spring AI Alibaba Graph 有同构的状态图和检查点）

常出的事thread_id 用随机 UUID，不用事件键：重发的告警会另起一条线程，前面查过的结果全都用不上，还会多出一张审批卡。

3主 agent（triage 节点）：分诊，写三份任务书

主 agent 读告警，判断是性能类，写出三份任务书：日志 agent 查 20:00 以后的 WARN/ERROR、上线记录和线程栈；指标 agent 解析 20:00 以后的 GC；笔记 agent 找 Full GC、老年代、导出相关的经验。它自己不调工具。

为什么要它分诊决定派谁去、各查什么。子 agent 看不到主 agent 的上下文，任务书就是唯一的交接文档：写不清，子 agent 就会重复查，或者漏查。

往下一层多 agent：主从编排、并行子 agent、交接

常出的事任务书只写“查一下日志”，不给时间窗：子 agent 从 20:16 开始查，正好错过 20:09 就开始的现场。站 04 第 1 轮踩的是同一个坑。

4Send 扇出：一个 superstep 里同时派出三个

triage 后面的条件边返回 [Send("investigate", 任务书) ×3]。三个任务落在同一个 superstep（框架里的“一步”）里，框架用线程池同时跑。实测三个子 agent 都在 0.63 秒那一刻开始。

为什么要它三件事互不依赖。并行时这一步花的时间等于最慢的那个（实测 1.2 秒），串行要 1.2 + 0.9 + 0.7 = 2.8 秒。

往下一层多 agent：主从编排、并行子 agent、交接；状态图和检查点：长任务断点续跑（superstep 是什么）

常出的事三个子 agent 在同一步里写 state 的同一个键，这个键却没配 reducer：框架直接报 InvalidUpdateError: Can receive only one value per step（本机实测）。

5子 agent ×3：各查各的，只交回结论

每个子 agent 只拿到自己的任务书和一两个工具，在自己的小上下文里跑循环。日志 agent 读了 1173 字的原始日志和线程栈，交回 83 字；指标 agent 交回“Full GC 3 次（每次约 1.9s），Full GC 后堆仍占 68%、71%、72%”；笔记 agent 交回《G1 和 ZGC 怎么回收》里的一条经验。

为什么要它原始材料留在子 agent 那里，主 agent 只看结论：主 agent 的上下文保持干净，三个子 agent 还能并行跑。代价是每个子 agent 都要把背景重读一遍，token 成倍增加。

往下一层多 agent：主从编排、并行子 agent、交接；什么时候不该拆多 agent

常出的事拆得太碎：这三件事一个 agent 跑两轮就能查完，拆开以后 token 多花好几倍，结论还得再对一遍。Anthropic 公开的数据是，多 agent 系统用的 token 约为普通对话的 15 倍（按文档）。

6检查点：每一步结束存一次 state

每个 superstep 结束，SqliteSaver（生产上多用 PostgresSaver）把这条线程的 state 存一份。实测里 notes 第一次超时，这时 logs 和 metrics 已经跑完，它们的结果作为 pending writes 存进了检查点。重试 graph.invoke(None) 时只有 notes 重跑：执行次数是 logs 1 次、metrics 1 次、notes 2 次。

为什么要它没有检查点，哪一步失败都得从头再跑，分诊和另外两个子 agent 花掉的 token 全部白费；也没办法停下来等人。

往下一层状态图和检查点：长任务断点续跑

常出的事生产上用了 InMemorySaver：进程一重启，所有停在“等人批准”的线程全都丢了。还有一种是往 state 里塞原始日志这样的大对象，每一步存盘、恢复都变慢，库也越来越大。

7主 agent 汇总：合并三段结论，提出写操作

三段结论经 reducer（operator.add）合进 state["findings"]。汇总节点下结论：20:00 上线的按月导出一次读 41 万行，老年代打满，20:12 起 3 次约 1.9 秒的 Full GC，/orders/{id} 跟着变慢。同时提出 3 个写操作：建工单、发群通知、把 /orders/export 限流到 0。

为什么要它交接回来的是三段话，不是三份原始日志，主 agent 的上下文只多了几百字。下结论和决定做什么，留给能看到全局的那一个。

往下一层多 agent：主从编排、并行子 agent、交接

常出的事子 agent 的结论互相矛盾，比如笔记 agent 说“像连接池耗尽”，主 agent 照单全收；或者结论里的数字没写出处，人没法核对。

8interrupt()：写操作之前停下

approve 节点调用 interrupt({结论, 3 个写操作})。框架把这份审批请求存进检查点，invoke 返回 __interrupt__，进程可以直接退出。实测这时这条线程有 5 个检查点，next=['approve']。

为什么要它前面都是只读，从这里开始要改外部世界了。必须停下来等人，又不能让进程干等十几分钟：state 已经在库里，谁来恢复都行。

往下一层状态图和检查点：长任务断点续跑；业务流程自动化：写操作、审批、幂等、审计

常出的事恢复时，节点是从头重新执行的（LangGraph 源码里 interrupt 的文档写明了）。要是在 interrupt() 前面就发了通知，批准以后通知会再发一遍。副作用不能放在 interrupt 前面。

9值班人：在卡片上勾选、批准

20:31 张三在群里的审批卡片上勾了“建工单”“发通知”，没勾“限流导出接口”（要先问业务方）。点击经 n8n 转成 POST /incidents/alert-7f3a/resume，后端调 graph.invoke(Command(resume={"approved": [...], "by": "张三"}), 同一个 thread_id)。实测这一步是在另一个进程里恢复的。

为什么要它写操作的责任在人。谁批的、批了哪几项，都记进 state，第 ⑪ 站的审计要用。

往下一层业务流程自动化：写操作、审批、幂等、审计

常出的事卡片上只有一个“全部批准”按钮：人没法只批一部分，结果要么全拒，要么连限流也一起做了。

10act 节点：带幂等键执行写操作

对每个批准了的动作，拿 alert-7f3a:create_ticket 当幂等键去调工单系统，建出 INC-1108。实测：建完工单进程就崩了，检查点还没来得及存；重跑时 act 节点整个再执行一遍，工单系统发现这个幂等键已经有了，没建第二张。

为什么要它框架保证的是“至少执行一次”，不是“恰好一次”：节点失败了就整段重跑。不重复执行，得靠写操作自己做到幂等。

往下一层业务流程自动化：写操作、审批、幂等、审计

常出的事幂等键用了时间戳或随机数，每次重跑都是一个新键，崩一次就多一张工单。这一站的过关条件二考的就是这个。

11审计日志：谁批的、做了什么、结果如何

每个写操作都追加一行：线程、动作、参数、批准人、结果。没批准而跳过的、重跑时被幂等键挡下的，也都记。实测审计日志共 4 行：建工单 2 行（第二行写着“幂等键已存在”），通知 1 行，限流 1 行（“未批准，跳过”）。

为什么要它出了事要答得上来：agent 替谁做了什么。检查点记的是图的状态，不是业务审计，两样要分开存。

往下一层业务流程自动化：写操作、审批、幂等、审计

常出的事只记成功的写操作：被拒的、被幂等键挡下的都看不到，复盘时说不清限流为什么没做。

预测题

1. 第 ⑤ 站的日志 agent 不是偶尔超时，而是每次都超时。值班人会看到什么？哪些结果还在？

值班人看不到结论，也收不到审批卡：invoke 每次都抛异常，汇总节点永远跑不到。指标和笔记两个 agent 的结果还在，存在那一步检查点的 pending writes 里，重试时不会重跑它们。要么给节点配重试次数上限，要么让日志 agent 超时后交回“没查到”，让主 agent 带着两段结论先汇总。

从第 ④、⑤、⑥ 站推出：同一步的任务各自存结果，一个失败不会冲掉别的。

2. 张三两个小时后才点批准，这期间值班助手发了一次版、进程重启了两次。还能接着跑吗？

能。state 在检查点库里，thread_id 是事件键，哪个进程来恢复都一样。要当心的是新版本改了图：检查点里记着“下一步是 approve”，新版要是把这个节点改了名，或者改了 state 的结构，旧线程就可能恢复不了。发版时要考虑还在等人的旧线程。

从第 ②、⑥、⑧、⑨ 站推出：恢复靠的是检查点里存的“下一步”和 state，图本身不存。

3. n8n 没去重，同一个告警 20:21 又来了一次，值班助手给它用了一个新的随机 thread_id。会怎样？两张卡片张三都点了批准呢？

会再完整调查一遍，token 再花一次，群里出现第二张审批卡。两张都批准的话，如果幂等键是“thread_id + 动作”，两条线程的键不一样，就会建出两张工单。所以幂等键要用业务上的唯一标识，也就是事件键（告警指纹 + 这次触发的时间），不能用每次都会变的东西。

从第 ①、②、⑩ 站推出：去重、线程 id、幂等键，三处最好用同一个业务键。

4. 把三个子 agent 改成一个接一个地串行跑，哪几站会变？结论会变吗？

第 ④、⑤ 站变了：这一步的时间从最慢的那个（实测 1.2 秒）变成三个相加（2.8 秒），用真模型就是从一两分钟变成三四分钟；检查点也从一个 superstep 变成三个。结论不变，因为三件事本来就互不依赖。如果后一个子 agent 要用前一个的结果，那就不该并行。

从第 ④、⑥ 站推出。
