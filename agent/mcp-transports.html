两种传输：stdio 和 Streamable HTTP

同一套 JSON-RPC 消息，有两种送法。stdio：主机拉起一个子进程，一行一条走管道，一个客户端一个进程，不开端口，靠操作系统的进程权限。Streamable HTTP：一个 POST /mcp 端点，一条消息一个 POST，回 JSON 或 SSE 流，一个进程服务很多客户端，能远程，但鉴权和防护要自己做。选哪个，看服务端放在哪、给几个人用。

①为什么需要：一个在本机，一个在机房

在全景第 2、3 站，这一步要解决的是：oncall 要读你本机的日志、跑本机的 jstack，只给你一个人用；tickets 跑在内网服务器上，整个交易组的 Claude Code 和值班助手都要连它。同一套消息，一个要走“进程之间”，一个要走“网络”。

②没有它会怎样：2024 年的 HTTP+SSE，两个端点一根长连接

MCP 第一版（2024-11-05）的远程传输叫 HTTP+SSE：客户端先 GET /sse 开一根长连接，服务端从这根连接里告诉它“往 /messages 发”；客户端的请求 POST 过去，响应却从那根长连接里回来。2025-03-26 起它被 Streamable HTTP 取代，现在标为弃用。对照三条要求：

  • 每个客户端都要一直占着一根长连接，哪怕一整天只调一次工具。服务端要同时撑住成千上万根，代理、负载均衡还常常把空闲连接掐掉。
  • 请求走 POST、响应走另一根连接，两头必须落在同一台机器上，负载均衡要做粘性，扩容、重启都很麻烦。
  • 一个工具调用的结果要在长连接里按 id 去找，一旦长连接断了，所有在途请求的结果都丢在半路。
  • 好处是服务端随时能往下推消息（进度、通知），这正是 SSE 的长处，新传输把它留了下来，但只在需要的时候用。
不懂精华时的典型误用：给本机才用的工具也起一个 HTTP 服务，还监听 0.0.0.0，图的是“方便调试”。结果是局域网里的人、甚至你浏览器里打开的恶意网页，都可能调到它（⑥ 坑 2）。本机工具用 stdio，连端口都不开，这类问题就不存在。

③相邻方案：两种标准传输怎么选

服务端放在哪只能在主机同一台机器上，由主机拉起。哪里都行：本机、内网、公网。同左。
几个客户端一个客户端一个进程。10 个 Claude Code 窗口就是 10 个 oncall，实测每个 67 MB。一个进程服务所有客户端（⑤ 实测两个客户端同时连）。能，但每个客户端常驻一根长连接。
谁能连上只有拉起它的那个进程，靠操作系统隔离，不用登录。知道网址的都能来：要 OAuth、要查 Origin、本机的要绑 127.0.0.1。同左。

选择规则：只给自己用、要碰本机的东西，用 stdio；要给一群人或很多 agent 共用、要跑在服务器上，用 Streamable HTTP，并且一定配上鉴权。全景里 oncall 走 stdio，tickets 走 HTTP，就是这么分的。

规范只定义了这两种标准传输；自己做别的传输（比如 WebSocket）也可以，规范建议复用 stdio 那种“一行一条”的分帧。两种传输上，消息的含义完全一样，换传输不用改一行工具代码（⑤ 的 oncall_http.py 只换了 run() 的参数）。

④原理：管道上一行一条；HTTP 上一条一个 POST

先知道这些
  • stdin / stdout / stderr：每个进程生来就有三根管道，标准输入、标准输出、标准错误。父进程拉起子进程时可以拿住这三根，往 stdin 写、从 stdout 读。Java 里就是 ProcessBuilder.start() 返回的 Process 的 getOutputStream() / getInputStream() / getErrorStream()。管道和网络 IO 的关系见 网络 IO 模型。
  • SSE（Server-Sent Events）：一种 HTTP 响应，Content-Type: text/event-stream，服务端不一次写完，而是一段一段地推 data: …，客户端边收边处理。Spring 里对应 SseEmitter。站 03 的流式输出用的就是它。
  • Java 比方：stdio 传输 ≈ 用 ProcessBuilder 起一个子进程、按行读写它；Streamable HTTP ≈ 一个 @PostMapping("/mcp")，按情况返回 JSON 或 SseEmitter。

机制 1 · stdio：一行就是一条消息，stdout 只许走协议

  • 谁拉起谁：客户端把服务端当子进程拉起。服务端不监听任何地址，所以也只有这一个客户端。
  • 分帧：消息之间用换行分开，消息里面不许有换行（JSON 里的换行要写成 \n），UTF-8 编码。读的一方按行切就行。
  • stdout 只许走协议：服务端不许往 stdout 写任何不是 MCP 消息的东西；日志写 stderr，客户端可以收集、转发或者不理，而且不该把 stderr 有输出当成出错。
  • 怎么挂断：客户端关掉服务端的 stdin，等它退出；等不到就先 SIGTERM，再 SIGKILL。服务端读到 EOF 应该马上退出。服务端崩了，客户端应当重启它，在途的请求就丢了，可以重发。

机制 2 · Streamable HTTP：一个端点，一条消息一个 POST

  • 一个端点：比如 https://mcp.ops.internal/tickets/mcp，只认 POST。每个请求或通知单独一个 POST，请求体就是那一条 JSON-RPC 消息。
  • 必带的请求头：Accept 里同时写 application/json 和 text/event-stream；MCP-Protocol-Version 和 body 里 _meta 的版本一致；Mcp-Method 就是方法名；tools/call、resources/read、prompts/get 还要 Mcp-Name（工具名或资源 URI）。
  • 回什么由服务端每次自己选：一个 application/json 响应，或者一个 text/event-stream 流。流里可以先推和这次请求有关的通知（进度、日志），最后一条是响应，然后流结束。客户端两种都必须会收。
  • 通知：服务端收下就回 202 Accepted，没有 body。
  • 长期的变更通知：没有单独的 GET 长连接了。客户端 POST 一个 subscriptions/listen，它的响应是一条一直开着的 SSE 流，只推客户端订阅过的那几种通知。
  • 断了就是取消：响应流断开，服务端要当成这次请求被取消；不支持断点续传，客户端要用新的 id 重发。

为什么这样设计：请求头为什么要把 body 再写一遍

Streamable HTTP（2026-07-28）：无会话，关键字段抄到请求头

  • 网关、负载均衡、监控不用拆 JSON，看 Mcp-Method: tools/call、Mcp-Name: add_comment 就能路由、限流、记日志，比如“写工单的调用每人每分钟 10 次”。
  • 没有会话、没有长连接，任何一台实例都能接任何一个请求，按普通 HTTP 服务扩容。
  • 代价：同一个信息写两遍，服务端必须逐个比对，否则网关按头放行了 search_logs，服务端却按 body 执行了 heap_dump。规范为此定了 -32020，⑤ 实测不一致就回 400。

HTTP+SSE（2024）：长连接加会话

  • 服务端随时能推消息，不用客户端先开口。
  • 中间层要看清一个请求是什么，只能拆 body；响应从另一根连接回来，监控很难把一问一答对上。
  • 每个客户端一根长连接加一个会话，必须粘在一台机器上。
决定胜负的约束：远程 MCP 服务端要跑在公司现成的 HTTP 基础设施后面（网关、负载均衡、可观测），这些东西都只看请求头、都假设请求之间没有关系。协议去迁就基础设施，比让每家公司改基础设施便宜得多。

读出来的结论
  • 换传输，工具代码一行不改；消息本身也一样，只是外面套的是管道还是 HTTP。
  • 三道检查真的在：Origin 不对 403，请求头和 body 对不上 400 加 -32020，版本不认识 400 加 -32022 并告诉你它支持哪些。
  • 这个服务端两个年代都接：老客户端发 initialize 照样能用，还拿到一个 Mcp-Session-Id，那是老协议的会话。
  • stdio 连上慢（每次起进程 0.68 s），调用快 1 ms；HTTP 连上快（服务端早就在跑），每次多出约 1 ms 的本机 TCP 和 HTTP 开销。都和模型一轮的秒级没法比。

⑥细节

第一圈 · 注意事项

1stdout 被弄脏，一条消息整条作废实测← ④ 机制 1
现象
服务端里一句没带换行的调试输出，粘在下一条响应前面。全景页实测：discover 的回复丢了，Claude Code 等了约 3 s 才回退握手；要是丢的是 tools/call 的回复，这次调用就一直等到超时。
根源
stdio 一行就是一条消息，读的一方按行切、按 JSON 解析；多出来的字节让那一行解析失败，整条消息就没了。
做法
日志一律写 stderr。Java 写 stdio 服务端时，System.out.println 和默认输出到控制台的日志配置都要改走 stderr；Python 用 SDK 2.x 有改道兜底，手写的没有。
2本机 HTTP 服务端被浏览器里的网页打到实测← ④ 机制 2
现象
为了调试，oncall 起成 HTTP、监听 0.0.0.0:8765、没有登录。你在浏览器里打开一个恶意网页，它用 DNS 重绑定把自己的域名解析到 127.0.0.1，就能从你的浏览器里调你的工具。
根源
HTTP 端点谁知道地址谁就能来，浏览器会替网页把请求发到本机。规范为此要求：所有请求都校验 Origin，不对回 403；本机用的服务端只绑 127.0.0.1。
做法
本机工具优先用 stdio；非要 HTTP，绑 127.0.0.1，保持 SDK 默认打开的防护（⑤ 实测 Origin: https://evil.example 被 403），远程的再加 OAuth。
3断线重发，写操作做了两遍← ④ 机制 2
现象
add_comment 执行到一半，SSE 流被代理掐断。客户端按规范用新 id 重发，工单 INC-1108 上出现两条一模一样的评论。
根源
2026-07-28 去掉了断点续传：流断了就当这次请求取消，客户端只能重发。可服务端那边可能已经做完了，“取消”只是没把结果送回来。
做法
会改东西的工具要做成幂等：让调用方带一个去重键（比如 client_request_id），服务端记住处理过的键；或者先查后写。和接口幂等是同一件事。
4进度通知被代理攒着，最后一起到← ④ 机制 2
现象
一个要跑 30 秒的导出工具每 5 秒发一次进度，经过 nginx 反代后，客户端 30 秒里什么都没收到，最后进度和结果一起涌过来，期间还可能被判超时。
根源
SSE 要求边写边送，而反代默认会把响应攒成块再发。
做法
服务端在 SSE 响应上带 X-Accel-Buffering: no（规范要求，⑤ 实测 SDK 已经带了），反代侧关掉缓冲（nginx 的 proxy_buffering off），长流里定期发 SSE 注释行保活。

第二圈 · 使用规范

  • 本机工具用 stdio，共享服务用 HTTP：防的是坑 2，也省掉一套登录。
  • HTTP 服务端一律配鉴权：内网也一样，规范要求“应当”做认证。第 5 页讲 OAuth。
  • 写 stdio 服务端时，第一件事就是把日志配到 stderr：防坑 1。
  • 会改东西的工具带去重键：防坑 3。
  • 超时分开设：启动超时和工具调用超时是两回事。Claude Code 分别用 MCP_TIMEOUT 和 MCP_TOOL_TIMEOUT 两个环境变量调。防的是：起得慢的 stdio 服务端被判死，或者慢工具被误杀。

第三圈 · 优化和深处

stdio 的账：进程数 × 内存

stdio 是一个客户端一个进程。实测用 Python SDK 写的 oncall 每个 67 MB（标准库手写的 gateway 只有 16 MB）。一个人开 5 个 Claude Code 窗口、每个接 3 个 Python 服务端，就是 15 个进程、约 1 GB。服务端多了，要么换更省的实现，要么把共用的那些改成一个 HTTP 服务。

HTTP 的账：扩容和缓存

没有会话，扩容就是多起几个实例挂到负载均衡后面；跨调用的状态放外部存储，用句柄传。tools/list 这类结果带 ttlMs 和 cacheScope，客户端和网关可以缓存，private 表示不同令牌之间不能共用。

老客户端怎么办

⑤ 里的服务端是“两个年代都接”：新请求按新规矩无状态处理；老客户端发 initialize，它就开一个老式会话、回 Mcp-Session-Id。对 GET 和 DELETE，mcp 2.3.0 回的是 400“缺会话 ID”，规范建议回 405，客户端别依赖具体状态码。

网关能多做什么

有了 Mcp-Method、Mcp-Name，网关不拆包就能：按工具限流、按工具记审计日志、把写操作路由到单独的实例、拦下不认识的老版本请求（规范说中间层“应当”拒绝版本更老或没写版本的请求）。站 10 的 AI 网关会接着讲。

自测

1. 用一句话说出两种传输怎么选

只给自己用、要碰本机的东西用 stdio（主机拉起子进程，一对一，不开端口）；要多人或多个 agent 共用、跑在服务器上用 Streamable HTTP（一个 POST 端点，一对多，要自己做鉴权和防护）。

2. 2024 年的 HTTP+SSE 疼在哪？

每个客户端常驻一根长连接；请求走 POST、响应从另一根 SSE 连接回来，两头要粘在同一台机器上；长连接一断，在途结果全丢。

3. 头号坑“stdout 被弄脏”的根源是哪条？

④ 机制 1：stdio 上一行就是一条消息，stdout 只许走协议。多出来的字节让某一行解析失败，那条消息就整条丢了。

4. 预测：网关按 Mcp-Name 放行“只读工具”，有人发了一个头写 search_logs、body 写 heap_dump 的请求，会怎样？

网关放行，但服务端比对请求头和 body 发现不一致，回 400 和 -32020，工具不会执行（⑤ 实测）。如果服务端不做这个比对，就会按 body 执行 heap_dump，网关的限制形同虚设。

从 ④ 为什么这样设计（头和 body 必须一致）推出。

5. 预测：交易组 20 个人都用 Claude Code，tickets 如果做成 stdio 服务端发给每个人，和做成一个 HTTP 服务比，差在哪？

stdio 版：每个人机器上一个进程（每个窗口还各一个），20 份工单系统的账号密码散在各人电脑上，升级要每个人重装。HTTP 版：一个服务端进程（或一组），一份到工单系统的凭证放在服务端，每个人用自己的 OAuth 令牌，升级只发一次。代价是要做鉴权和防护。

从 ③ 的对照表和 ④ 机制 2 推出。

6. 放回全景：第 2、3 站前后各发生了什么？如果第 2 站 oncall 起不来，整条链路会怎样？

前面是第 1 站 Claude Code 读配置、建客户端；后面是第 4 站 discover 协商。oncall 起不来（命令写错、启动超时），它的客户端就没有可说话的对象，第 4、5 站对它都不会发生，第 6 站模型的工具清单里没有 oncall 的 4 个工具；tickets 不受影响，因为两个客户端互不相干。

从全景第 1～6 站和 ④ 机制 1 推出。

档位：标准。本机跑过（2026-11-26，2 vCPU ARM，Python 3.13.18，官方 Python SDK mcp 2.3.0 + uvicorn，Claude Code 2.1.332）：⑤ 的 curl 各种请求、stdio 和 HTTP 各 100 次调用的计时、两个 HTTP 客户端同时连、stdio 服务端的内存；stdout 弄脏的三种情况来自全景页的实测。按文档（已核对原文）：MCP 规范 2026-07-28 版 transports 总览、stdio（分帧、stdout/stderr 规则、关闭顺序）、Streamable HTTP（单端点、必带请求头、JSON 或 SSE、202、subscriptions/listen、断流即取消、Origin 校验和 403、-32020、请求头为中间层而设、HTTP+SSE 已弃用）。Claude Code 的两个超时环境变量名在本机 2.1.332 的程序里确认存在，默认值没有核对。
