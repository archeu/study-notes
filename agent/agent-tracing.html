Tracing：每次模型和工具调用的耗时、token

一次排障是一个 trace，里面每次模型调用、每次工具调用各是一个 span：记下开始结束时间、输入输出 token、调了什么工具、带了什么参数、提示词是哪一版。评测只能说“这条变坏了”，trace 能指出坏在第几轮、模型当时看到了什么，也能算出时间和钱花在了哪。

①为什么学→ ②老办法→ ③选谁→ ④原理→ ⑤跑起来→ ⑥细节→ ↺回到⑤

全景：改了一句提示词之后 · 第 4、9 站地图：站 09 · Tracing深度：会用

这一页的位置站 09 第 4 个知识点。Java 板块讲过链路追踪：一个 HTTP 请求穿过几个服务，每段一个 span。这一页是同一套东西用在 agent 上，区别是每个 span 多了 token、提示词版本，以及模型看到的内容。下一页的轨迹评测和后面的线上指标，都从这里记下的 span 取数。

①为什么学：评测说“变坏了”，但没说坏在哪

在全景第 4 站，这一步要解决的是：值班助手跑 50 条用例时，把每一步都留下来；到了第 9 站，评测说 @4 的 02 号用例错了，要能打开它，看到第 1 轮模型调了什么、拿到了什么、第 2 轮为什么就下了结论。另一个需要来自账单：一次排障花了多少 token，花在哪一轮，缓存命中了多少。

②老办法：打日志、存对话

站 04 起，评测已经把每条的完整对话存成 JSON。对话里有模型说了什么、调了什么工具、工具返回了什么，看上去够用了。缺的是这些：

  • 没有时间：对话里看不出第 6 轮花了 52 秒，也就不知道该优化哪一轮。
  • 没有 token 明细：一共花了多少，每轮多少，缓存命中多少，对话里都没有，账单对不上。
  • 没有版本：这段对话是哪一版提示词、哪个模型跑出来的，要靠文件名去猜；灰度时两版混在一起就分不开。
  • 串不起来：线上一次排障还会调到日志平台、知识库服务、MCP 服务器，各自打各自的日志，没有一根线把它们连成一次请求。
  • 没法汇总：几千次排障的对话文件，想知道“第 1 轮就调知识库的占几成”“P95 多少秒”，要自己写脚本一个个读。
不懂精华时的典型误用：把 trace 当成“更结构化的日志”，只在入口记一个大 span，里面塞整段对话。精华在于每次模型调用、每次工具调用都是独立的 span，挂在同一棵树上：这样才能按轮次看时间、按工具做汇总、按版本做对比。

③选谁：埋点用 OpenTelemetry，后台随便换

做法好处代价
OpenTelemetry SDK + GenAI 语义约定（本页）和 Java 那套是同一个标准，span 能和网关、日志平台、MCP 服务器的 span 串成一棵树；导出成 OTLP，Jaeger、Grafana Tempo 能收，Langfuse、Arize Phoenix 这类 LLM 观测平台也能收GenAI 约定还是 Development 状态，属性名可能还会改
Langfuse、LangSmith 自己的 SDK提示词管理、评测、成本统计一条龙，界面为 LLM 定制埋点绑在一家平台上；和 Java 服务的链路要另外打通
框架自带的追踪（LangGraph、Spring AI 的 Observation）不用自己埋点，开个开关就有只覆盖框架管到的那部分；名字和属性按框架的来
自己写 JSON 日志最简单，站 09 的评测运行器就是这么记的没有父子关系，串不起跨服务的调用；每个团队格式都不一样

本页学 OpenTelemetry：值班助手本身就是一个服务，以后要和告警系统、工单系统（站 08）串在一起，用和 Java 服务同一套标准最省事。导出到哪个后台是配置问题，埋点代码不用改。

④原理：一棵 span 树，三种 span，一套约定的名字

先知道这些
  • trace、span、父子关系：一次请求是一个 trace，里面每段工作是一个 span，span 记着自己的父 span，连成一棵树。见 Java 板块的链路追踪和三件套。
  • agent 循环：调模型 → 模型要工具 → 执行工具 → 把结果交回模型 → 再调模型……直到模型不再要工具。见站 04 的agent 循环。

机制 1 · agent 循环的每一圈，就是两层 span

根 span 是这次排障 invoke_agent oncall。循环每转一圈，先有一个模型调用的 span chat qwen3-1.7b，模型要了几个工具，就跟着几个 execute_tool … span。它们都挂在根 span 下面，按时间排开就是瀑布图。工具 span 下面还可以再挂：工具如果是 MCP 服务器、或者要调日志平台的 HTTP 接口，靠 traceparent 头把同一个 trace id 传过去，对方的 span 就接在这棵树上（和 Java 微服务之间传 trace id 是同一个机制）。

机制 2 · GenAI 语义约定：名字和属性统一叫法

OpenTelemetry 给生成式 AI 定了一套约定（原来在 semantic-conventions 主仓库里，现在搬到了单独的 semantic-conventions-genai 仓库，2026-11-21 发了 v0.1.0，状态是 Development）。照着它起名，任何后台都认得出哪个是模型调用、哪个是 token：

span名字本页记的属性
一次排障invoke_agent {gen_ai.agent.name}gen_ai.operation.name=invoke_agent、gen_ai.prompt.name、gen_ai.prompt.version，再加自定义的 eval.case.id、eval.passed
一次模型调用{gen_ai.operation.name} {gen_ai.request.model}，即 chat qwen3-1.7bgen_ai.usage.input_tokens、gen_ai.usage.cache_read.input_tokens、gen_ai.usage.output_tokens、gen_ai.response.finish_reasons
一次工具调用execute_tool {gen_ai.tool.name}gen_ai.tool.name、gen_ai.tool.call.id；参数和返回值 gen_ai.tool.call.arguments、…result 是 opt-in，要显式打开

按文档：以上名字和属性都在 semantic-conventions-genai 仓库的 client-inference.md、execute-tool.md、client-invoke-agent.md 和属性注册表里核对过。

机制 3 · token 要记对：缓存命中算不算在输入里

约定规定 gen_ai.usage.input_tokens 要包含缓存命中的部分，cache_read.input_tokens 是它的一个子集。可 Anthropic 的 API 把这两个分开报：usage.input_tokens 只算没命中的部分。约定的 Anthropic 那一节专门写了：要把 cache_read_input_tokens 加回去。llama.cpp 的 /v1/messages 也是这样报的。少加这一步，⑤ 里那条 02 号用例的第 1 轮会被记成 32 个输入 token，而实际是 946 个。

机制 4 · 内容要不要记：有用，但贵，也敏感

排查“模型当时看到了什么”，最有用的是提示词全文、工具参数和返回值。可它们又大（一轮上千 token）、又敏感（日志里有用户手机号、订单号）。所以约定把这些都设成 opt-in：默认只记名字、耗时、token；要内容时显式打开，最好只在评测环境、或者给被点了 👎 的那几条打开。本页的评测环境里全开（现场是假数据），线上只记前 300 字。

为什么这样设计

每次调用一个 span，挂成一棵树

  • 按轮次看时间：一眼看出 52 秒花在最后写结论那轮。
  • 按工具、按版本汇总：“第 1 轮就调知识库的占几成”变成一条查询。
  • 能跨服务：工具背后的服务用同一个 trace id，接在同一棵树上。
  • 代价：span 多，存储贵；内容要不要记得一条条决定。

被放弃的：一次请求一条大日志

  • 整段对话塞进一条日志，时间只有一个总数，看不出是哪一轮慢。
  • 工具背后的服务各打各的日志，拼不回同一次排障。
  • 字段每个团队各起各的名字，换个观测平台就要重写解析。
决定胜负的约束：agent 的一次请求是一个循环，次数不定，每一圈的成本和对错都不一样。只有把每一圈拆成独立的 span，才能回答“哪一圈慢、哪一圈贵、哪一圈走错了”。
埋点的核心几行完整的在 ⑤
with tracer.start_as_current_span("invoke_agent oncall", attributes={
        "gen_ai.prompt.version": version, "eval.case.id": case_id}):
    while True:
        with tracer.start_as_current_span(f"chat {MODEL}") as sp:
            r = client.messages.create(...)
            sp.set_attribute("gen_ai.usage.input_tokens",
                r.usage.input_tokens + r.usage.cache_read_input_tokens)
        if r.stop_reason != "tool_use": break
        for c in tool_calls(r):
            with tracer.start_as_current_span(f"execute_tool {c.name}"):
                run_tool(c)

⑥细节·规范·优化

第一圈 · 注意事项

1输入 token 少算了缓存那部分实测← ④ 机制 3
现象
按 span 汇总出来的输入 token 只有实际的十分之一，成本报表好看得不正常。
根源
Anthropic 和 llama.cpp 的 usage.input_tokens 只算没命中缓存的部分；约定要求的 gen_ai.usage.input_tokens 要包含命中的部分。基线里平均 1169 个输入 token，命中缓存的就有 1077 个。
做法
记的时候把 cache_read_input_tokens 加回去，另记一个 cache_read.input_tokens；算钱时两部分按各自的单价算。
2把提示词全文、工具返回全记进 span← ④ 机制 4
现象
trace 存储一个月涨了几十倍；安全审计发现日志平台里存着用户手机号。
根源
每轮的提示词上千 token，工具返回里有业务数据；约定把它们设成 opt-in 就是这个原因。
做法
默认只记名字、耗时、token、版本；原文只在评测环境，或者只给被点了 👎、转了人工的那几条打开，并做脱敏。
3按比例采样，偏偏漏掉出事的那条← ④ 机制 1
现象
线上只采 1% 的 trace，值班同学说“刚才那次排障结论很离谱”，trace 后台里找不到。
根源
开头采样（head sampling）在请求一进来就决定留不留，那时还不知道它会出事。
做法
评测环境 100% 采；线上用尾部采样（collector 里等 trace 结束再决定）：出错的、慢的、被点踩的全留，其余按比例。算 token 总量用指标（下一页），不用从采样后的 trace 里加总。
4并行的工具调用挂错了父 span← ④ 机制 1
现象
模型一轮要了三个工具，并行执行，瀑布图里三个工具 span 挂在了彼此下面，或者全挂到根上、分不清是哪一轮要的。
根源
OpenTelemetry 靠“当前上下文”找父 span；换了线程、协程又没把上下文带过去，就找错了。
做法
并行前先拿到这一轮的上下文，每个任务里显式用它开 span（Python 里 asyncio 会自动带上 contextvars，线程池要手动传）；工具 span 上记 gen_ai.tool.call.id，和模型那轮的 tool_use 对得上。
5新版本刚上线，又慢又贵实测← ④ 机制 3
现象
@4 这一跑的第一条，第 1 轮 31 秒、缓存命中 0，同样的位置 @3 只要 6 秒。
根源
系统提示词在最前面，改一个字，整段前缀的缓存就失效了，要从头算一遍。
做法
比较新旧版本的耗时和成本时，跳过刚切换时的那一小段；提示词里经常变的部分（日期、用户信息）往后放，不常变的放前面。

第二圈 · 使用规范

  • 根 span 上必须有版本和业务编号：gen_ai.prompt.version、模型、用例或告警编号。防的是 trace 有了，却不知道是哪一版、哪一次请求。
  • 名字照约定，自定义属性加前缀：约定里有的用 gen_ai.*，自己的用 oncall.*、eval.*。防的是换后台以后字段对不上，或者和约定以后的新字段撞名。
  • 工具出错要标 span 状态：status=ERROR 加 error.type。防的是在 trace 后台里筛不出“工具坏了”的那些请求。
  • 评测和线上用同一套埋点：评测环境的 span 和线上长得一样，评测里写的查询线上直接能用。

第三圈 · 优化和深处

流式输出怎么记

流式调用时，span 的结束时间是最后一个 chunk 到达的时刻；约定里还有首个 chunk 的时间（gen_ai.response.time_to_first_chunk），用户感受到的“开始回答”看它。值班助手最后一轮写结论占了一半以上的时间，改成流式后，用户等的主要是首字时间。

跨进程串起来

工具背后是 MCP 服务器或 HTTP 接口时，调用方把 traceparent 带过去，对方用它当父上下文开 span。站 07 的 MCP 调用、站 08 的工单系统，都能接到同一棵树上：一次排障从告警进来，到工单建好，一个 trace id 看到底。

下一圈

  • 拿 span 判过程：工具调用序列、参数、返回都在 span 里了，下一页轨迹评测拿它们打分。
  • 指标：P95、成本、成功率要从指标里算（不受采样影响），全景第 10 站。
  • 接一个真后台：把导出器换成 OTLP，起一个 Jaeger 或 Langfuse，看界面里的瀑布图和按属性筛选。
  • Java 一侧：Spring AI 的 Observation 已经按 GenAI 约定出 span，和本页 Python 的埋点能混在一棵树里。

↺回到⑤：改一改

  1. 只在出事时记原文：改 run_traced，工具参数和返回值先不记，等这条没通过（eval.passed=false）再补记到根 span 的事件里。做对了会看到：通过的 trace 里没有原文，没通过的才有。（坑 2）
  2. 算一次排障多少钱：在 where 里按“缓存命中、未命中、输出”三档单价算每条的成本，单价写成参数。做对了会看到：缓存命中占了输入的九成，成本主要由输出决定。（坑 1）
  3. 挑一条“没认出来”的：用 show 打开一条 @4 里看到了关键日志却仍怪 GC 的用例，指出是第几轮的哪段返回里有关键证据。（下一页的四格）

自测

1. 用一句话说出这一页的精华

一次排障一个 trace，每次模型调用、每次工具调用各一个 span，按 GenAI 约定记耗时、token（含缓存）、工具、版本，挂成一棵树：评测说变坏了，trace 指出坏在哪一轮、为什么。

2. 存了完整对话，为什么还要 trace？

对话里没有每轮的耗时、token 明细和缓存命中，没有版本，串不起工具背后的服务，也没法汇总查询。

3. gen_ai.usage.input_tokens 最容易记错在哪？

Anthropic 和 llama.cpp 报的 input_tokens 不含缓存命中；约定要求含。不加回去，输入 token 会少算九成。

4. 预测：把系统提示词最前面加一行“今天是 2026-11-26”，每天换日期，trace 里会看到什么？

每天的第一批请求第 1 轮缓存命中为 0、耗时暴涨；更糟的是，如果服务端缓存按前缀匹配，日期一变全部前缀都对不上，缓存几乎没用了。经常变的内容要放到后面。

从 ④ 机制 3 和 ⑤ 里 @4 第一条“缓存 0、31 秒”推出。

5. 预测：值班助手改成先流式输出结论，P95 耗时会变吗？用户的体感呢？

整条 trace 的耗时基本不变（还是要生成那么多 token），可首个 chunk 的时间会从几十秒降到几秒，用户感觉快多了。所以要同时看总耗时和首字时间两个数。

从 ⑤ 的“写结论那一轮占 55%”推出。

6. 放回全景：第 4、9 站前后各发生了什么？没有 trace，整条链路会怎样？

第 4 站在第 3 站取到用例之后、第 5 站打分之前：跑的同时记 span；第 9 站在门禁变红之后：打开 trace 找原因，再回到第 1 站改提示词。没有 trace，第 6 站的轨迹评测没有数据，第 9 站只能凭感觉改提示词，第 10 站的线上指标也拆不出版本。
