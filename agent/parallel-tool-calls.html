并行工具调用

模型一轮可以写好几张调用单（默认就开着）。你要做两件事：互不依赖的只读调用同时执行，总耗时等于最慢的那一个；所有回执放进同一条 user 消息，失败的也要回。省下的不只是工具的时间，更大头是少转了几轮模型。

全景：一次排障提问，agent 来回了几轮 · 第 3、4 站地图：站 04 · 并行工具调用深度：会用

这一页的位置站 04 下钻第 5 页，“会用”档：讲清怎么写、哪里会错就够。前置：工具调用的一来一回、Agent 循环；Python 的并发写法见 asyncio。

①为什么学：模型已经在一轮里要好几个了

两次实测，第 1 轮模型都没有一个一个地要：全景那次同时要了 search_logs 和 parse_gc_log，Agent 循环那页那次同时要了三个（再加 search_notes）。值班 SOP 的头两步“看日志、看 GC”本来就互不依赖。你的代码要接得住：怎么执行、怎么送回。

②老办法：for 循环一个个执行，或者干脆关掉并行

写法3 个工具（0.8 / 1.5 / 0.4 秒）要多久疼在哪
关掉并行（disable_parallel_tool_use），模型分三轮要3 轮模型 + 2.7 秒工具；每轮模型 3 秒就是约 11.7 秒多转两轮：多两次整段重发，多付两轮的钱
一轮要三个，for 循环串行执行1 轮模型 + 2.7 秒能用；工具一慢（20 秒的 jstack）就明显
一轮要三个，并发执行1 轮模型 + 1.5 秒，约 4.5 秒只受最慢那个限制

实测 工具耗时是 ⑤ 里模拟的延迟、实测的总时间；“每轮模型 3 秒”是连 Claude 时的假设量级（本机 CPU 上一轮要 40～80 秒，差距更大）。这张表只算“拿到三个结果”为止，不算最后交答案那一轮；⑥ 的实验台算上了。

不懂精华时的典型误用：执行是并发了，回执却是“哪个先回来就先发一条 user 消息”。官方文档点名这是并行调用变少的头号原因：拆开送回等于在历史里“教”模型别一次要多个。

③选谁：Python 里三种并发写法

写法适合注意
ThreadPoolExecutor.map工具是普通的阻塞函数（读文件、subprocess、requests）map 按传入顺序返回；max_workers 就是并发上限
asyncio.gather整个 agent 已经是 async 的（FastAPI 里跑），工具用 httpx.AsyncClient阻塞的工具要包 asyncio.to_thread，否则会卡住事件循环
多进程 / 交给任务队列工具是 CPU 密集的（解析几 GB 的 GC 日志）开销大，值班助手 v1 用不上

本页用线程池：v1 的工具都是阻塞的 I/O，线程池最直接；对照 Java，就是 ExecutorService.invokeAll。站 01 学过的 asyncio 写法放在 ⑤ 里一起比。

④原理：执行顺序你定，送回格式是死的

规则 1 · 怎么执行由你决定

官方文档原话：API 不规定执行顺序，可以并发、可以按出现顺序串行、也可以混着来。按工具的性质选：互不依赖的只读操作通常可以并发；有副作用、共享状态、有先后要求的最好串行。

  • 值班助手 v1 的 4 个只读工具（日志、GC、jstack、知识库）：可以并发。
  • heap_dump 和 thread_dump 同一轮：都会停顿 JVM，同时做等于叠加停顿，应该串行，甚至只做一个。
  • “改配置”和“重启”同一轮：有先后，必须串行；前一个失败了，后一个不执行，回一条 is_error：“没有执行：前一步改配置失败”。

这也是“专门工具优于万能 bash”的一个理由（工具怎么设计 · ③）：工具名就告诉你它是只读的，能放心并发；一串 shell 命令，你分不清哪个是 grep、哪个是 git push，只能全部串行。

规则 2 · 送回只有一种格式

正确：一条 user 消息，每张单一个回执，回执在文字前面顺序靠 id 配对，按原顺序排最省心
{"role": "assistant", "content": [tool_use A, tool_use B, tool_use C]},
{"role": "user", "content": [tool_result A, tool_result B, tool_result C(is_error)]}   # ✓

{"role": "user", "content": [tool_result A]},
{"role": "user", "content": [tool_result B]}, ...                                       # ✕ 拆开送回：文档点名的头号错误

为什么拆开会让模型“学坏”：模型看历史学样。历史里每次“一次要三个”之后都跟着一次凌乱的回执，或者干脆每轮只有一个回执，它后面就更倾向一次只要一个。

规则 3 · 开关和提示

  • 默认开着。要关：tool_choice: {"type": "auto", "disable_parallel_tool_use": true}，每次回应最多一个工具（它不是顶层参数，在 tool_choice 里面）。
  • 想让它更多地并行：系统提示里加一句。官方给的写法是“需要做多个互不依赖的操作时，同时调用所有相关工具，而不是一个接一个”。值班助手的 SOP 里那句“能同时查的就在一轮里同时调用多个工具”就是这个作用。
为什么这样设计：一个回应里可以有多张调用单，是因为“模型想好要什么”和“你去执行”是分开的两步；既然执行在你这边，并发不并发就由懂工具性质的你来定。送回格式固定，是因为 API 要靠它把一批调用和一批结果对齐，模型也要靠它从历史里学会“一次要多个是可以的”。

⑤跑起来：同一轮三个工具，四种执行方式

假模型一轮要三个只读工具，执行时各自睡 0.8 / 1.5 / 0.4 秒模拟真实延迟（查日志服务、读 GC 文件、jstack）。--fail 让 jstack 超时，看回执怎么写。

⑤parallel-tool-calls/main.py（节选）完整代码 →
def run_tool(block) -> dict:
    try:
        return {"type": "tool_result", "tool_use_id": block.id, "content": oncall.IMPL[block.name](**block.input)}
    except Exception as e:                                   # 失败也回一条，不能丢
        return {"type": "tool_result", "tool_use_id": block.id, "is_error": True,
                "content": f"{type(e).__name__}: {e}。可以先用另外两个结果下判断，或稍后重试。"}

blocks = [b for b in resp.content if b.type == "tool_use"]
with ThreadPoolExecutor(max_workers=4) as pool:
    results = list(pool.map(run_tool, blocks))               # map 按传入顺序返回
messages.append({"role": "user", "content": results})        # 三个回执，一条消息

# async 版本：工具是阻塞的，要包进线程
results = await asyncio.gather(*(asyncio.to_thread(run_tool, b) for b in blocks))

  2. 2 制造失败uv run python parallel-tool-calls/main.py --fail

读出来的结论
  • 并发后总时间 = 最慢的那个（1.5 秒），串行是三个相加（2.7 秒）。max_workers=1 的线程池就是串行。
  • 两种并发写法的回执顺序都和调用单一致：map 和 gather 都按传入顺序返回，不是按完成顺序。
  • 一个失败了，照样三个回执、一条消息；失败那条带 is_error 和下一步建议，另外两条照常用。
  • 真正的大头在模型：少转两轮，比工具并发省得多。
到这里已经能交差了：把 Agent 循环里的 [run_tool(b) for b in calls] 换成线程池的 map，回执照旧放进一条消息。

⑥细节

第一圈 · 注意事项

1把有副作用的工具也并发了← ④ 规则 1
现象
模型同一轮要了 heap_dump 和 thread_dump，两个一起跑，order-svc 停了两次叠在一起。
根源
并发只对互不影响的只读操作安全；API 不替你判断。
做法
工具表里给每个工具标 parallel_safe；一批里有不安全的，就把它们按出现顺序串行，其余照常并发。
2模型一轮要 15 个，全打到同一个服务上← ④ 规则 1
现象
日志服务被值班助手自己打出了 429。
根源
一轮能有多少张调用单，没有天然上限。
做法
max_workers 设成下游扛得住的数；每轮超过 N 个调用，多出来的回 is_error“这一轮最多执行 5 个，请挑最重要的”（停止条件 · 坑 6）。
3一个慢的拖住整批← ④ 规则 1
现象
日志和 GC 一秒就回来了，jstack 卡了 60 秒，整轮等 60 秒。
根源
下一轮要等所有回执齐了才能发。
做法
每个工具自己的超时（future.result(timeout=20)），超时回 is_error，别让一个拖死整批。
4谁先回来先送谁按文档← ④ 规则 2
现象
开了并发以后，模型反而越来越少一次要多个。
根源
回执拆成了几条 user 消息；官方文档把它列为并行调用变少的头号原因。
做法
等一批全齐了，放进一条 user 消息再发。
5以为模型会把有依赖的调用分到两轮← ④ 规则 1
现象
模型一轮要了“查订单 id”和“按订单 id 查明细”，后者的参数是它猜的。
根源
模型通常会把有依赖的调用分开，但不保证；猜参数是它的老毛病。
做法
执行端校验参数是否来自已知结果；描述里写清“id 要先用 xxx 查出来”。

第二圈 · 使用规范

  • 工具表带两个属性：只读 / 有副作用、能否并发：防坑 1；审批那页也要用“有副作用”这个标记。
  • 线程池放在循环外面复用，max_workers 进配置：防每轮新建线程池，也防打爆下游。
  • 每轮日志记一个数：这一轮几个调用：官方文档也建议量“平均每条回应几个工具调用”，它掉下来说明哪里把模型“教坏”了。

第三圈 · 深处

比并发更省的：让模型写脚本

Claude 的“程序化工具调用”（programmatic tool calling）让模型在代码执行容器里写一段脚本去调你的工具，循环、过滤都在脚本里做，只有最后的结果回到上下文。几十次调用、中间结果很大时用；值班助手 v1 用不上。

流式时更早开工

流式输出时，第一张调用单的参数一收齐就可以先执行，不必等整条回应结束。省的是“模型还在写第二张单”的那几秒；代价是要自己处理参数一段段到达（input_json_delta）。

实验台：三种要法，一次排查要多久

先猜：本机 CPU 上（每轮模型约 50 秒），把“一轮要三个、串行执行”改成“并发执行”，总耗时大约省下多少？

估算模型：除最慢的那个外，其余工具各按 0.6 秒算；“分 N 轮要”= N 轮模型 + 工具时间之和 + 最后一轮交答案；“一轮串行”= 2 轮模型 + 工具时间之和；“一轮并发”= 2 轮模型 + 最慢的那个。不算 token 费用。

  • 多个 agent 并行：一个查 GC、一个查数据库，最后汇总（站 08）。

自测

1. 用一句话说出这一页的精华

一轮多张调用单时，互不依赖的只读调用同时执行，所有回执（含失败的）放进同一条 user 消息；最大的收益是少转几轮模型。

2. 为什么回执拆成几条消息会让模型以后少并行？

模型照着历史学样，历史里“多张单”之后总跟着拆开的回执或单个回执，它会更倾向一次只要一个；官方文档把这列为头号原因。

3. heap_dump 和 thread_dump 同一轮来了，能并发吗？

不能：两个都会停顿 JVM，并发等于叠加停顿；而且 heap_dump 还要先过审批。按顺序串行，或者只做一个。

从 ④ 规则 1 推出。

4. 预测：本机每轮模型 50 秒，工具 0.8 / 1.5 / 0.4 秒，串行改并发能省多少？

约 1.2 秒，占一百多秒总时长的 1% 左右；真正省时间的是“一轮要三个”比“分三轮要”少了两轮模型，约 100 秒。

从 ② 的对照和实验台推出。

5. 放回全景：第 3 站模型要了两个工具，第 4 站拆成两条 user 消息送回，第 7、8 站会怎样？

按文档这不符合“一批回执放一条消息”的要求；就算能过，以后的排查里模型会越来越少一次要多个，第 8 站看到的轮数变多，时间和 token 都上去。

档位：标准（会用）。本机跑过（2026-11-24，2 核 ARM，Python 3.13，假模型 + 模拟延迟）：四种执行方式的耗时、回执顺序、失败时的回执。全景页和 Agent 循环页的真模型运行里，第 1 轮分别要了 2 个和 3 个工具。按文档（Claude 官方 “Parallel tool use”）：执行顺序由你定、只读可并发有副作用宜串行、回执放一条消息、拆开送回会减少并行、disable_parallel_tool_use 在 tool_choice 里、鼓励并行的系统提示写法。
