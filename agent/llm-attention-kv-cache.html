注意力和 KV 缓存（只讲到够用）

注意力：每个位置拿自己的“查询”去和前文每个位置的“键”做点积，softmax 成权重，再按权重取前文的“值”，于是“20:15 变慢”能联系上几十行前的 Full GC。KV 缓存：前文每个位置的键和值算过一次就存着，下一圈只给新 token 算。实测没有它写 20 个字要 128 秒，有它 0.8 秒。同一招做到服务端就是提示缓存：前缀一字不差才能复用，所以别把时间戳放在开头。

①为什么需要：两件事，一个快一个准

在全景第 5 站和第 8 站，这一步要解决两件事。准：读输入时，“20:15 变慢”这几个 token 要能从 61 行之外的“Pause Full 1873ms”那里取到信息，否则模型只能看到眼前几个字。快：写回答时每圈都要“看全部前文”，如果每圈都把几千个 token 从头算一遍，一个字要等好几秒。

②没有它会怎样

少了什么会怎样实测 / 例子
没有注意力（只看最近几个字）远处的信息取不到，n-gram 和早期循环网络就卡在这里“20:15 变慢”和 61 行前的 Full GC 连不上（第 1 页 ②）
没有 KV 缓存（每圈全部重算）写第 n 个字要把前面 n 个位置全算一遍，总量随长度平方增长⑤ 实测：写 20 个 token，每个 6.4 秒，共 128 秒；有缓存每个 40 ms，0.8 秒
没有提示缓存（每个请求从头读）值班助手每次带同样的系统提示和日志，每次都重读⑤ 实测：同一段日志换个问题，6.1 秒变 0.2 秒
不懂精华时的典型误用：为了“让模型知道现在几点”，在系统提示第一行写上当前时间、请求号。每个请求的前缀都不一样，提示缓存一次也命中不了，每次都按全价、全时长重读（⑤ 实测 293 个 token 全部重算）。

③相邻方案：怎么联系前文，怎么不重复算

问题做法取舍
联系前文循环网络：一路读一路更新一个固定大小的记忆记忆大小不变，但细节会被冲掉（上下文窗口 ④）
注意力：每次都回看全部前文能精确取到任何位置；代价是计算和内存随长度增长
不重复算KV 缓存：一个请求之内，前文的 K、V 存着每个推理框架都默认开着
提示缓存：跨请求，相同前缀的 K、V 留在服务端要求前缀逐字相同；Claude 命中部分按 5%～10% 计价（按文档）

本页学注意力、KV 缓存和提示缓存：三者是一条线，后一个都建立在前一个的“只往前看”上。

④原理：查询找键，按权重取值；键和值只往前看，所以能存

先知道这些
  • 点积、softmax、矩阵乘：够用的数学，那页最后的“迷你注意力”就是本页机制 1 的简化版。
  • 层：模型是 24 层（本页的 Qwen2.5-0.5B）一样的结构叠起来，每层都做一次注意力，上一层的输出是下一层的输入。

机制 1 · 注意力：Q 问，K 答“我像不像”，V 给出内容

和迷你注意力只差两处：Q、K、V 是三个不同矩阵乘出来的；以及因果遮罩：每个位置只能看自己和前面的位置，后面的分数直接当成负无穷，softmax 后权重是 0。生成时后面的字还没写出来，训练时就得照这个规矩练。

机制 2 · KV 缓存：旧位置的 K、V 永远不变，算一次就存着

关键一点：因为只往前看，第 i 个位置在每一层的 K、V 只取决于第 1～i 个 token。后面接上再多的字，它们也不会变。所以每圈只需要给新 token 算 Q、K、V，旧的 K、V 从缓存里读。下面一步一步看 6 个输入 token、再写 4 个，两种做法各算了多少：

准备点“下一步”。

代价是内存：每个位置每层都要存一份 K、V，本页模型一个 token 12 KB，8192 个约 96 MB（上下文窗口 ④）。服务端同时跑几十个长请求时，限制并发的往往不是算力，而是 KV 缓存占的显存。

机制 3 · 提示缓存：把 KV 缓存留到下一个请求；从第一个不同的字起，后面全作废

Claude 的提示缓存是同一个道理，只是做成了要显式打开、按 token 计价的功能：命中部分 Opus 5.5 按输入价的 5% 收，写入按 1.25 倍收，默认保留 5 分钟，前缀至少 512 个 token 才缓存；拼接顺序是 tools → system → messages（按 Claude API 文档）。站 03 “省钱”那一页实测。

为什么这样设计：只往前看，才能缓存

因果注意力（只看前面）

  • 旧位置的 K、V 永远不变，可以缓存：写每个新字只算一个位置。
  • 训练和生成的规矩一致：训练时每个位置也只看前面，一段文本里每个位置都是一道“猜下一个”的题（第 1 页机制 3）。
  • 代价：前面的字看不到后面的字。读输入时，“order-04”这个位置不知道后面问的是 GC，只有靠后的位置才“看到了问题”。这也是把问题放在材料后面更好的原因之一。

双向注意力（BERT 那类，前后都看）

  • 每个位置都能看到全文，理解类任务（分类、做向量）效果好。
  • 接上一个新字，所有位置的表示都要变，没法缓存；每写一个字都得全部重算，不适合生成长回答。
决定胜负的约束：对话模型的主业是一个字一个字往外写。只有“只往前看”能让旧位置的计算结果一直有效，生成的代价才从“每圈重算全部”降到“每圈只算一个”。用前向看不到后文换来可缓存，对生成是划算的。

读出来的结论
  • 没有 KV 缓存时，第 n 圈要重算 297+n 个位置，20 圈一共 6130 个；有缓存只算 20 个。耗时差 160 倍（127.6 秒对 0.8 秒），回答越长差得越多。

⑥细节：缓存为什么不命中

第一圈 · 注意事项

1当前时间、请求号、用户名放在提示开头实测← ④ 机制 3
现象
每次请求都按全价、全时长读输入；Claude 的 cache_read_input_tokens 一直是 0。
根源
缓存按前缀匹配，第一个不同的字之后全部作废。
做法
顺序固定成“不变的在前、易变的在后”：工具定义、系统提示、参考材料、历史，最后才是这次的问题和时间。
2内容没变，但序列化出来的字节变了← ④ 机制 3
现象
明明每次带的是同一份配置、同一组工具，缓存就是命中不了。
根源
用 HashMap 拼 JSON，键的顺序每次可能不同；工具列表按条件动态增减；日志里混进了每次都变的字段。对缓存来说，差一个字节就是不同的前缀。
做法
序列化时排序键（Jackson 的 ORDER_MAP_ENTRIES_BY_KEYS、Python 的 sort_keys=True）；工具集合固定；上线后盯着 cache_read_input_tokens。
3长请求一多，服务端并发上不去← ④ 机制 2
现象
自建推理服务，平时很快，一来几个 10 万 token 的长请求，其他请求开始排队甚至被拒。
根源
每个进行中的请求都要为每个 token 存一份 K、V；显存被几个长请求的 KV 占满，新请求放不进来。
做法
限制单请求的最大长度；按“KV 显存”而不是“请求数”做容量规划；用支持分页管理 KV 的推理框架（vLLM 等）。
4前缀太短、换了模型，缓存悄悄不生效← 产品规则
现象
加了 cache_control，没报错，但也没省钱。
根源
按 Claude 文档：前缀短于模型的最小值（Opus 5.5 是 512 token）不会缓存，也不报错；缓存按模型隔离，换模型就是全新的缓存；默认 5 分钟没人读就过期。
做法
看 cache_creation_input_tokens 和 cache_read_input_tokens 两个数；同一路流量固定一个模型；请求间隔超过 5 分钟的考虑 1 小时档（写入 2 倍价）。

第二圈 · 使用规范

  • 提示词分区：固定区（工具、系统提示、规则）→ 半固定区（这次的日志）→ 易变区（问题、时间）。防坑 1。
  • 序列化必须确定：同样的内容永远序列化成同样的字节。防坑 2。
  • 缓存命中率进监控：cache_read_input_tokens ÷ 总输入 按接口画曲线，掉到 0 就报警。防坑 1、2、4。
  • 长请求单独限流：自建推理时，长请求走单独的队列和配额。防坑 3。

第三圈 · KV 缓存的工程优化

共用 KV 头（分组查询注意力）

14 个查询头只配 2 组 K、V，KV 缓存缩到七分之一，效果损失很小。本页的模型就是这样（读自模型配置）。

分页管理

像操作系统管内存一样，把 KV 切成固定大小的页按需分配，不再给每个请求预留整段最大长度；多个请求的相同前缀还能共用同一批页。vLLM 的 PagedAttention 是这个思路。

少读显存的注意力算法

注意力的瓶颈常常是读写显存而不是乘加。分块计算、不把整个分数矩阵写出来（FlashAttention 这一类），长序列快很多。

KV 量化

把缓存里的 K、V 用 8 位甚至更低精度存，长上下文能多装一倍以上，代价是一点点精度。

自测

1. 用一句话说出这一页的精华

注意力让每个位置用查询去匹配前文的键、按权重取值；因为只往前看，旧位置的 K、V 永远不变，所以能存下来（KV 缓存），跨请求留着就是提示缓存，但只认逐字相同的前缀。

2. 为什么旧位置的 K、V 可以缓存，而双向的 BERT 不行？

因果注意力里第 i 个位置只看 1～i，后面接上新字不影响它；双向注意力每个位置都看全文，接上一个字所有位置都要变。

从 ④ 为什么这样设计 推出

3. 预测：把日志中间某一行改一个数字，提示缓存能复用多少？

只能复用改动位置之前的部分：系统提示加改动行之前的日志。改动行和它后面的所有 token 都要重算，因为它们的 K、V 依赖前面每一个字。

从 ④ 机制 3 推出

4. 预测：没有 KV 缓存时，写 40 个 token 比写 20 个慢多少？有缓存时呢？

有缓存：大约 2 倍，每圈只算 1 个位置，约 1.6 秒。没有缓存：第 n 圈要算 297+n 个位置，40 圈一共约 12700 个，是 20 圈（6130）的 2 倍多一点，约 260 秒以上；前文更长时，平方那部分会让差距越来越大。

从 ④ 机制 2 推出，数字用 ⑤ 的实测外推（估算）

5. 为什么问题放在材料后面更好？说出两条理由。

一是缓存：材料在前不变，换问题只重算问题那几个 token。二是注意力只往前看：问题在后时，问题的位置能看到全部材料，回答时也“带着问题”回看材料；问题在前时，读材料的那些位置看不到问题。

从 ④ 机制 1 的因果遮罩和机制 3 推出

6. 放回全景：第 5 站和第 8 站之间靠什么连着？如果第 5 站读完输入后 KV 缓存没有保存下来，整条链路会怎样？

靠第 5 站存下的 KV 缓存：第 6、7、8 站每转一圈，新 token 都要用它回看前文。缓存没存下来，第 8 站每圈都得把 4950 个输入 token 重算一遍；全景里本机读一遍要 133 秒，28 个 token 的回答就要一个多小时，第 9 站停下之前用户早就放弃了，服务端的超时也会先到。
