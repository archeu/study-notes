多 agent：主从编排、并行子 agent、交接

多 agent 的本质是上下文隔离：主 agent 只写任务书、只收结论，原始日志留在子 agent 自己的上下文里。拆法有三种：派出去再收回来（主从），同一步派好几个（并行），把控制权整个交出去（交接）。决定成败的是交接的那两张纸：往下的任务书，往上的结论。实测里同一个小模型，任务书含糊时没找到根因，任务书写清楚就找到了。

①为什么需要：一个 agent 读完所有原文，上下文会被撑满

在全景第 3～7 站，这一步要解决的是：排障要看日志、线程栈、GC、笔记，原文加起来很长。全塞给一个 agent，它的上下文每查一样就胖一圈，后面每一轮都要把前面的原文再读一遍；四样东西还只能一样一样查。

②没有它会怎样：一个 agent 查到底

⑤ 实测了同一个问题让一个 agent 带四个工具查（本机 Qwen3-1.7B）：3 次模型调用，最大一次输入 856 token，34 秒，结论只讲到 Full GC，没找到导出接口。这个现场是玩具，日志加线程栈才一千多字；真实的线程栈有 200 个线程，一次就是几万 token。

  • 上下文随原文线性变胖，后面每一轮都把前面的原文再付一次钱、再分一次注意力（上下文窗口）。
  • 工具全挂在一个 agent 上，说明书越来越长，选错工具的机会也越来越多（工具怎么设计）。
  • 四样东西只能一样一样查，没法同时开工。
  • 好处也是真的：一个上下文里什么都看得见，不会有“交接时信息走样”的问题。下一页专门算这笔账。
不懂机制时的典型误用：以为“多几个 agent 就更聪明”。拆开以后每个子 agent 只看得到任务书里写的东西，任务书写得含糊，子 agent 就在黑暗里瞎查；⑤ 里指标子 agent 一个工具都没调就交了卷。

③相邻方案

做法上下文控制权能并行适合
一个 agent + 压缩一个，满了就摘要（站 05）一直在它手里不能步骤前后依赖、要通盘考虑
写死的工作流每步一个提示代码定死能步骤固定（工作流还是 Agent）
主从 + 并行子 agent主 agent 一个，每个子 agent 各一个派出去，收回来能（Send）能拆成互不依赖的几块调查
子 agent 当工具同上主 agent 在循环里“调用”子 agent看主 agent 一轮要几个不知道要派几个、派谁，让模型自己定。Claude Code 的子 agent 就是这样
交接（handoff）整段对话跟着走交出去就不回来不能前台分诊后转给专家，由专家直接回复

本页讲主从、并行和交接：全景第 3～7 站用主从加并行；交接用在“分诊完发现是数据库的事，整个转给 DBA agent”这种场景。Java 比方：主从像线程池提交任务再 Future.get()；交接像 Servlet 的 forward，请求转过去就由对方响应。

④原理：拆上下文，靠两张纸交接

先知道这些
  • 子 agent 就是一个完整的 agent：自己的系统提示、自己的工具、自己的循环、自己的上下文。⑤ 里每个子 agent 都是一个 create_agent（LangGraph 上手）。
  • 它看不到主 agent 的上下文：子 agent 知道的全部，就是任务书和它自己查到的东西。
  • Send：同一步里派出多个任务，并行跑，结果经 reducer 合并（检查点那页机制 1）。
  • Java 比方：子 agent 像提交给线程池的任务，任务书是构造参数，结论是 Future 的返回值。比方失效的地方：线程池里的任务是确定的代码，子 agent 会理解错任务书、会编数字，交回来的东西要核对。

机制 1 · 三种拓扑：控制权去了哪、回不回来

机制 2 · 交接的两张纸：任务书往下，结论往上

子 agent 只看得到任务书，主 agent 只看得到结论。两张纸都是“压缩”：任务书把主 agent 脑子里的判断压成一行，结论把几百字原文压成几十字。压缩就会丢东西、会走样。下面是 ⑤ 的真实运行（本机 Qwen3-1.7B），先看模型自己写任务书，再看人写好任务书。

为什么这样设计：子 agent 只交结论

交回原文

  • 主 agent 什么都看得见，不会走样。
  • 主 agent 的上下文又变回 ① 左边那一摞，拆了等于没拆。

只交结论（全景的做法）

  • 主 agent 的上下文小：⑤ 里最大一次输入 395 token，一个 agent 查到底是 856。
  • 子 agent 互不打扰，能并行。
  • 代价：压缩会丢、会走样，⑤ 里两次都出了错。

共享完整上下文

  • Cognition 的主张：子 agent 要看到完整的上下文和别人的决定，否则各自的隐含决定会打架。
  • 每个子 agent 都背着全部历史，贵；也很难再并行。
决定胜负的约束：上下文窗口和注意力都有限，原文必须有人替主 agent 读，所以只能交结论；交结论就一定会压缩、会丢。解法不在拓扑，在两张纸的写法：任务书写清目标、交回格式、该用的工具和来源、范围边界（Anthropic 在多 agent 研究系统的文章里列的就是这四样），结论里带原文数字和出处，主 agent 才核对得了。

读出来的结论
  • 拆开以后，主 agent 的上下文小了一半多（最大一次输入 856 → 395 token），原文留在子 agent 那里：日志子 agent 读 763 字，只交回 90 字。
  • 代价是调用次数翻倍多（3 → 7），输出 token 翻三倍多（177 → 641）：每个子 agent 都要自己读一遍说明、自己写一遍结论。
  • 同一个模型，任务书写清楚了就找到了根因，没写清楚就没找到。拓扑一样，差别全在任务书。
  • 两次汇总都走了样：一次把建议当成证据，一次把线程栈的位置写错。结论里不带原文出处，主 agent 核对不了。
  • 本机只有 2 核，模型服务同一时刻算不动几个请求，所以并行反而更慢（34 秒 → 100 秒）；连云端 API 时三个子 agent 才真的同时算。

⑥细节

第一圈 · 注意事项

1任务书含糊，子 agent 在黑暗里瞎查实测← ④ 机制 2
现象
指标子 agent 收到“关注响应时间、QPS、错误率”，可它手里只有 GC 工具，于是一个工具都没调，交回 10 个字。
根源
子 agent 看不到主 agent 的上下文，任务书就是它知道的全部。主 agent 不知道子 agent 有哪些工具，也会写出它做不到的任务。
做法
任务书写四样：目标、交回格式、该用的工具和来源、范围边界（时间窗、只读）。主 agent 的提示里列出每个子 agent 有哪些工具；关键字段（时间窗）可以由代码补，不全靠模型写。
2结论没出处，主 agent 把建议当证据实测← ④ 为什么这样设计
现象
笔记里写的是“先 jmap -histo 看谁最多”，汇总里成了“jmap -histo 显示有大量大对象”；另一次把线程栈的位置写错了。
根源
结论是压缩过的二手信息，主 agent 分不清哪句是工具查到的、哪句是建议、哪句是子 agent 自己推的。
做法
结论用固定格式交：每条事实附上工具名和原文片段；汇总提示里要求“只引用带出处的事实”。评测时专门查这一条（站 09）。
3并行的子 agent 各做各的决定按文档← ④ 为什么这样设计
现象
两个子 agent 都觉得该“重启服务”，各自动手；或者一个按“像 GC”查、一个按“像数据库”查，结论对不上。
根源
Cognition 在《Don't Build Multi-Agents》里说的：行动里带着隐含的决定，并行的子 agent 看不到彼此的决定，决定冲突就出坏结果。
做法
子 agent 只读；写操作、对外动作一律收回主 agent（全景第 8～10 站）。互相依赖的子任务不要并行，串起来做。
4以为并行一定更快实测← ④ 机制 1
现象
本机拆成三个子 agent 并行，34 秒变 100 秒。
根源
总活变多了（3 次调用变 7 次），而本机模型服务只有 2 核，几个请求挤在一起算。并行只在“算力不是瓶颈”时省时间，比如云端 API。
做法
在真正的部署环境上量，不在笔记本上下结论；看墙钟时间也看总 token，下一页细算。
5交接转圈按设计← ④ 机制 1
现象
JVM agent 觉得是数据库的事，交给 DBA agent；DBA agent 觉得是 JVM 的事，又交回来。
根源
交接没有“回到主 agent”这一步兜底，谁都可以把球踢走。
做法
state 里记交接次数，超过 2～3 次就转人；或者改用主从，让主 agent 拍板。recursion_limit 是最后一道闸。

第二圈 · 使用规范

  • 任务书四要素：目标、交回格式、工具和来源、范围边界：防坑 1。
  • 结论带出处：工具名 + 原文片段 + 数字：防坑 2，也让评测有据可查。
  • 子 agent 只读，写操作只在主 agent：防坑 3。
  • 每个子 agent 只挂它需要的工具，设自己的 recursion_limit：工具少，选错的机会少；上限防一个子 agent 拖垮全局。
  • 按 agent 记账：调用次数、输入输出 token、耗时，像 compare.py 的 Ledger。不记账就没法回答下一页的问题。

第三圈 · 优化和深处

子 agent 的上下文也要设计

⑤ 里日志子 agent 最大一次输入 912 token，比主 agent 还大：原文都在它那里。子 agent 内部同样适用站 05 的那一套：工具返回先裁短，只留和任务书相关的行（精简的返回）。

别家框架里的同一件事

Claude Code 和 Claude Agent SDK 的子 agent 是 ② 那种：主 agent 发一次工具调用，子 agent 在独立上下文里跑完，只把最后结果交回来。OpenAI Agents SDK 的 handoff 是 ③。名字不同，看的都是控制权回不回来、交接时带什么。

  • 子 agent 当工具（②）的完整实现：让主 agent 自己决定派几个、派谁，和 ① 比一比调用次数。
  • 主 agent 的“回查”：结论可疑时，带着具体问题再派一次子 agent。
  • 多 agent 的评测：分别评任务书、子 agent 结论、最终结论三层（站 09）。

↺回到⑤：改一改

  1. 逼主 agent 写清任务书：在 triage 的提示里列出三个子 agent 各有什么工具，要求每份任务书写时间窗和关键字，再跑 multi，看指标子 agent 会不会调工具。（坑 1）
  2. 结论带出处：把 SUB_RULE 改成交回 JSON（事实、工具名、原文片段），汇总时只许引用这些事实，看还会不会把建议当证据。（坑 2）
  3. 多拆一个：把 thread_dump 从日志子 agent 拆成第四个子 agent，记下调用次数和 token 的变化，结论有没有变好。（为下一页准备数据）

自测

1. 用一句话说出多 agent 的本质

上下文隔离：原文留在子 agent 那里，主 agent 只写任务书、只收结论；成败看这两张纸写得好不好。

2. 一个 agent 查到底，疼在哪？

原文全堆在一个上下文里，后面每轮都要再读一遍；工具越挂越多；只能串行查。

3. 指标子 agent 一个工具都没调，根源是哪条原理？

子 agent 只看得到任务书。任务书让它查 QPS，它手里却只有 GC 工具，主 agent 不知道这一点。

从 ④ 机制 2 推出。

4. 预测：把 ① 的主从改成 ② “子 agent 当工具”，模型调用次数会变多还是变少？

多半变多：主 agent 自己有循环，每派一次子 agent 就多一轮主 agent 的调用（发出 tool_use、读回 tool_result），而 ① 里派活是代码做的，主 agent 只在开头和结尾各调一次。换来的是灵活：派几个、派谁由模型定。

从 ④ 机制 1 推出。

5. 预测：把日志子 agent 的结论上限从“三句话”放宽到“不限”，主 agent 的最大输入和走样会怎么变？

主 agent 的最大输入变大，朝一个 agent 查到底的 856 token 靠近；走样会少一些，因为压得没那么狠。这就是“只交结论”和“交回原文”之间的那根滑杆。

从 ④ 为什么这样设计推出。

6. 放回全景：第 5 站前后各发生了什么？任务书写错了，整条链路会怎样？
