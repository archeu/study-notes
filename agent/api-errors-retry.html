429 rate_limit_error · 529 overloaded_error · retry-after · 超时 · 指数退避 · 抖动 · 假服务 30 个客户端实测

出错怎么办：429 限流、过载、超时，退避加抖动

模型调用是个又慢又会失败的远程调用：会被限流（429）、会遇上整体过载（529）、会超时。该重试的要重试，但不能一起、立刻重试：一群客户端同时被拒、同时重来，又同时撞上限流。办法是退避（每次多等一会儿）加抖动（等多久带点随机，把大家错开），服务端给了 retry-after 就听它的。实测 30 个客户端撞上每秒 5 个的限流：立即重试 1 秒内打出 413 次请求、只成功 10 个；按 retry-after 加抖动，78 次请求全部成功。

①要解决的问题：晚高峰，20 个分诊实例一起被限流

在全景第 4、5 站，这一步要解决：请求被拒、服务过载、半天不回时，值班助手该怎么办。晚高峰告警成片涌进来，几十个分诊请求几乎同时发出，账号的每分钟限额一下就用完了，网关开始回 429。

②不用它会怎样：两种极端

做法会怎样⑤ 实测（30 个客户端，限流每秒 5 个）
不重试，一次失败就报错晚高峰大量分诊直接失败，值班页面一片“分诊失败”；其实等一两秒就能成功按限流规则，第一轮只有 5 个能过，另外 25 个直接失败
失败了立刻重试，直到成功失败的请求马上变成新的请求，限流越撞越狠，服务端被自己的重试淹没（重试反馈环）1 秒内打出 413 次请求，429 有 403 次；最挤的 100 毫秒里 160 个请求，服务端连接被重置；最后只成功 10 个
不懂精华时的典型误用：每一层都加重试。SDK 自己重试 2 次，你的代码包一层重试 3 次，上游网关再重试 2 次，一次失败最多变成 3 × 4 × 3 = 36 次请求，在服务最脆弱的时候把它压垮。重试只在一层做，其他层透传。

③几种流派：失败以后等多久

流派第 n 次失败后等问题
立即重试0放大故障
固定间隔每次 1 秒大家同时失败、同时等 1 秒、同时再来，永远同步
指数退避0.2 × 2ⁿ 秒，有上限压力降了，但同一时刻失败的仍然同一时刻重来，成群地撞
指数退避 + 全抖动在 0 到 0.2 × 2ⁿ 之间随机把同一批失败的请求在时间上摊开
听服务端的 retry-after（+ 抖动）服务端说等几秒就等几秒，再加一点随机服务端最清楚什么时候有余量
熔断 / 降级一段时间内不再调，直接走备用持续故障时用，配合备用模型（站 03 抽象层）

本页学“有上限的指数退避 + 全抖动，优先听 retry-after”：这也是各家 SDK 默认的做法（按 SDK 文档：自动重试并带退避）；你要做的是别在它外面再乱加一层。

④核心取舍：重试是在“成功率”和“给服务端添乱”之间找平衡

先知道这些
  • 令牌桶限流：桶里的令牌按固定速率补充，每个请求拿一个，拿不到就被拒（限流算法）。
  • 重试反馈环：失败 → 重试 → 负载更高 → 更多失败（响应时间为什么越压越长）。

取舍 1 · 先分清：哪些该重试，哪些重试也没用

错误重试理由
429 限流要，按 retry-after 等暂时的，过几秒就有额度
529 过载、500 等 5xx要，退避；持续就切备用模型服务端的问题，可能很快恢复
连接错误、连接超时要请求多半还没到服务端
读超时（生成太慢）谨慎服务端可能已经在生成、在计费；重试是从头再来一遍。长输出用流式
400 参数错、401 鉴权、404 模型名错不要请求本身是错的，再发一万次也是错
200 但内容不合格另一种重试是结构化输出那一层的事，要带着错误原因重发

取舍 2 · 退避：失败越多，等得越久

第 n 次失败后等 min(上限, 基数 × 2ⁿ)：0.2、0.4、0.8、1.6 秒……服务越是持续出问题，客户端越是退得远，给它喘息的空间；上限防止等到地老天荒。退避解决的是“压力”，没解决“同步”：30 个同一时刻失败的客户端，按同一个公式等，就会在同一时刻一起回来。

取舍 3 · 抖动：把同一批失败的请求在时间上摊开

“全抖动”是在 0 到退避时长之间均匀随机，比“退避时长再加一点随机”散得更开。它的代价是有些客户端会运气好、几乎不等就重试；但从整体看，单位时间内撞上服务端的请求数被压平了，这正是限流最想要的。

取舍 4 · 能听服务端的，就听服务端的

429 响应里的 retry-after 是服务端告诉你“多久以后有额度”，比客户端自己猜的准。在它的基础上再加一点抖动，避免所有人在同一秒回来。⑤ 里这一种的 429 次数最少（48 次，其他退避策略都在一百次以上）。

核心取舍：为什么不是“越快重试越好”，也不是“越晚越好”

有上限的退避 + 抖动，只在一层做

  • 短暂故障时，几秒内就恢复成功；持续故障时，自动退得越来越远，不添乱。
  • 抖动让同一批失败的客户端不再同步，服务端的负载曲线被压平。
  • 代价：单个请求的最坏耗时变长；要给整体设一个截止时间，超过就放弃或降级。

立即重试，或者每层都重试

  • 单个请求看起来“最积极”。
  • 把一次短暂的限流放大成长时间的过载；多层重试相乘，压力成倍放大（② 的误用）。
决定胜负的约束（过关题 3 的答案）：服务端的余量是所有客户端共享的。重试的目标不是“让我这个请求最快成功”，而是“让大家在余量里尽快都成功”：退避降低总压力，抖动打散同步，retry-after 让客户端按服务端的节奏来。不加退避，失败立刻变成新的负载；不加抖动，大家成群地撞，每一波都大部分落空。

最少的语法

官方 SDK：用它自带的重试按 Claude SDK 文档

自己写：有上限的指数退避 + 全抖动⑤ 的策略之一
def backoff(attempt, base=0.2, cap=8.0):
    return random.uniform(0, min(cap, base * 2 ** attempt))

for attempt in range(MAX_TRIES):
    code, retry_after = call()
    if code == 200: break
    if code not in (408, 409, 429, 500, 502, 503, 529): raise
    time.sleep(float(retry_after) + random.uniform(0, 1)
               if retry_after else backoff(attempt))

读出来的结论
  • 立即重试是在攻击自己的服务：1 秒内 413 次请求，最挤的 100 毫秒里 160 个，服务端开始重置连接；20 次额度很快耗光，30 个里只成功 10 个。
  • 指数退避不加抖动，拖得最久：30 个客户端同一时刻失败、按同一个公式等，于是在 0.2、0.6、1.4 秒……一波一波地一起回来，每波只有 5 个能过，剩下的等得越来越久，最后一个 20.6 秒才成功。
  • 加上全抖动，同样的退避快了一倍多：8.0 秒，请求被摊开了。
  • 听 retry-after 最省：服务端说 1 秒后有额度，客户端就在 1～2 秒之间随机回来，请求最少（78 次），时间也接近理论下限（30 个 ÷ 每秒 5 个 ≈ 5 秒）。
  • “固定 1 秒”在这里看起来不错，是因为它的间隔恰好等于令牌桶的补充周期；换一个限流节奏，它就和“不加抖动”一样一直同步地撞。
  • SDK 已经替你做了退避：两次 529 之后间隔 0.45 秒、0.75 秒（递增且带随机）。超时也会重试：单次 1 秒超时、最多重试 2 次，4.38 秒后才最终抛错，墙钟时间约是“超时 ×（重试次数 + 1）”加上退避。
到这里已经能交差了：你能说清哪些错误该重试、退避和抖动各解决什么，并能用假服务亲手验证。
反例和误用：多层重试相乘（误用 1），重试不该重试的（误用 2），超时设得比生成还短（误用 3），没有总截止时间（误用 4）。

⑥反例和误用

第一圈 · 常见误用

1每一层都加重试← ④ 核心取舍
现象
一次 529，日志里出现几十次请求；故障恢复后又被自己的重试打趴下。
根源
SDK 默认重试 2 次（共 3 次），外面再包 3 次、网关再 2 次，次数相乘。
做法
只在一层重试：要么用 SDK 的（调 max_retries），要么把它设成 0、自己写；网关层对模型调用关掉重试。
2400、401 也去重试← ④ 取舍 1
现象
参数写错（比如给 Opus 5.5 传了 temperature）后，重试 3 次都是 400，浪费时间还刷屏报警。
根源
请求本身是错的，重发不会变对。
做法
按状态码分类：只对 408、409、429、5xx、连接错误重试；用 SDK 的具体异常类（RateLimitError、APIConnectionError…）分开处理，别用一个大 except 全兜住。
3超时设得比生成时间还短实测← ④ 取舍 1
现象
诊断报告总是写到一半就超时，重试又从头写，钱花两三遍，最后还是失败。
根源
读超时掐断的是“正在生成”的请求；⑤ 实测 1 秒超时、服务要 3 秒，SDK 重试 3 次全部超时，4.38 秒后报错。
做法
连接超时短（几秒），读超时按最长输出估；长输出用流式（字节一直在流，不会触发读超时）。
4只有重试次数，没有总截止时间← ④ 取舍 2
现象
退避上限 60 秒、重试 5 次，一个分诊请求最坏要等好几分钟，用户早就走了，后台还在等。
根源
指数退避让最坏耗时迅速变长；“次数”控制不了“时间”。
做法
给整个调用一个截止时间（比如分诊 30 秒），到点就放弃并降级：换备用模型、走规则兜底，或者在页面上显示“稍后自动补上”。

第二圈 · 使用规范

  • 重试只在一层，策略写进配置：次数、基数、上限、截止时间都在配置里。防误用 1、4。
  • 按状态码和异常类分流：可重试的退避重试，不可重试的立刻报错，内容不合格的交给结构化输出那一层。防误用 2。
  • 监控 429 和 529 的比例：429 多说明自己用量超了（该申请额度或削峰），529 多说明服务方有问题（该切备用）。
  • 削峰比重试更根本：不急的调用（夜里的复盘报告）走批处理或排队，别和白天的分诊抢额度（省钱那页）。

第三圈 · 更深一层

自适应限流

客户端自己维护一个发送速率，收到 429 就降、成功就慢慢升（类似 TCP 拥塞控制的加性增、乘性减），比被动重试更早地把压力压下来。

熔断和备用模型

连续一段时间 529 就打开熔断，直接走备用模型或降级逻辑，过一会儿再试探（Sentinel 熔断那页；站 03 抽象层负责“换谁”）。

实验台：重试策略模拟器

先猜：100 个客户端同时撞上每秒 5 个的限流，用“指数退避，不加抖动”，全部成功大约要多久？

按 ⑤ 的规则在页面里模拟（令牌桶、同样的五种等法、最多 20 次、每次往返 5 毫秒，固定随机种子）。数字和 ⑤ 的实测在同一个量级，但不会完全一样：真实服务还有线程调度和网络的抖动。

下一圈

  • 站 10：多个服务共享一个模型账号的额度怎么分（配额、优先级队列）。
  • 幂等：模型调用本身无副作用，但调用之后“写工单”有，重试时怎么不写两次。
  • 对冲请求（hedged request）：慢了就同时发第二个，谁先回用谁，用钱换尾延迟。

↺回到⑤：改一改

  1. 加截止时间：给 client() 加一个 10 秒的总截止时间，超时就记为失败；用“指数退避”跑一次，看有几个客户端会被截掉。（误用 4）
  2. 两层重试：在 cmd_sdk 的 529 场景外面再包一层 3 次的循环，数一数服务端一共收到多少次请求。（误用 1）
  3. 自适应：给 30 个客户端共享一个“允许速率”，收到 429 减半、成功加 0.5，和“按 retry-after+抖动”比请求数。（第三圈）

自测

1. 用一句话说出这一页的精华

只对暂时性错误（429、5xx、连接错误）重试，而且只在一层做；用有上限的指数退避降低压力、用抖动打散同步、优先听 retry-after，并给整体设截止时间和降级。

2. 重试为什么要退避？不加会怎样？

失败的请求立刻变成新的请求，限流越撞越狠，服务被自己的重试淹没；⑤ 实测立即重试 1 秒 413 次请求，只成功 10 个。

从 ④ 取舍 2 和 ⑤ 推出

3. 已经有退避了，为什么还要抖动？

同一时刻失败的客户端按同一个公式等，会在同一时刻一起回来，每一波都远超余量、大部分落空；抖动把它们摊开。⑤ 实测：不加抖动 20.6 秒，加了 8.0 秒。

从 ④ 取舍 3 推出

4. 预测：SDK 设 max_retries=3、timeout=60，服务一直不回，最坏多久才报错？

大约 4 × 60 秒再加上几次退避，四分钟出头。按 SDK 文档，超时也会重试，墙钟时间可以达到“超时 ×（重试次数 + 1）”。要另设总截止时间。

从 ⑤ 的 sdk 实测和误用 4 推出

5. 预测：429 越来越多，是该把重试次数调大，还是调小？

先看原因：持续的 429 说明自己的用量就是超了，调大重试只会更堵；该削峰（排队、批处理）、申请更高额度，或者把一部分调用换到别的模型或账号。重试只适合“短暂”的超额。

从 ④ 核心取舍和第二圈推出

6. 放回全景：第 4、5 站前后是什么？如果第 5 站持续回 529 十分钟，而第 4 站只有 SDK 默认重试，链路会怎样？

前面是第 3 站 SDK 拼好请求，后面是第 6 站模型生成。持续 529 时，每个分诊请求重试 2 次后失败，第 8～10 站都不会发生，值班页面十分钟内全是“分诊失败”。需要抽象层（第 2 站）在连续失败后切到备用模型，或者走规则兜底。
