一次商品详情查询

用户 1024 打开 88 号商品的详情页。缓存都是热的时候，这次查询在 JVM 里 4 µs 就回来了；可 88 号的缓存刚好过期、而且是第一次被查到时，它要走本地缓存 → Redis → 数据库 → 再一层层填回去，约 2～4 ms，中间还要防着几百个请求一起冲进数据库。过一会儿运营把价格从 399.00 改成 359.00，四台机器上的缓存又得在 1 秒内一起跟上。这张全景回答：一次读、一次改价，各经过哪 12 站；J07 的 8 个知识点各管哪一站。

场景：88 号商品，先查一次，再改一次价

谁
交易靶场的商品服务，4 个实例。用户 1024 打开 88 号商品的详情页（就是 J06 全景里他买了 2 件的那个，单价 399.00），请求落在实例 A 上。A 刚重启过，本地缓存是空的；Redis 里 88 号的缓存也刚好过期。
读法
先读缓存、没有再查库、查完填回缓存（Cache-Aside）。两级：进程内的 Caffeine（最多 1 万条，写入后 5 秒过期），和 Redis（30 分钟再加 0～5 分钟随机）。Redis 没有时，先问布隆过滤器“有没有这个商品”，再抢一把重建锁，抢到的才去查库。
改价
运营把 88 号从 399.00 改成 359.00：先改库提交，再删 Redis，再 PUBLISH 一条失效消息，各实例收到后丢掉本地那条。
部署
Redis 8.10.3 单节点，打开了 AOF，其余默认；MySQL 8.4，trade.product 1 万行。应用端 JDK 21 + Caffeine 3.3.1 + Lettuce 7.9.0 + HikariCP 6.3.3 + Connector/J 9.7.0。
期望
大多数读不出 JVM；88 号缓存失效那一刻，数据库只被查一次；改价后 1 秒内，4 个实例都卖 359.00（这是地图上给靶场定的标准）。

实测 全冷的第一次查询走完第 1～8 站一共 2.0～4.2 ms，其中 6 次网络往返（Redis 5 次、MySQL 1 次），每次 0.3～0.6 ms；Redis 服务端执行一条 GET 只要 2 µs。之后本地命中 p50 4.1 µs。200 个线程同时冲一个刚过期的 key：不防，数据库被查 1～26 次；加了重建锁，每轮 1 次。改价后 11～26 ms 两个实例都读到 359.00；去掉失效广播，要 3.3～4.0 秒。

实测环境：本机 2 核 ARM，Redis 和 MySQL 各一个 Docker 容器，应用和它们之间走本机回环。“4 个实例”是同一个 JVM 里的 4 组对象，各有自己的 Caffeine、Redis 连接和连接池。单次追踪跑 6 次，表里取范围。

1Caffeine 查本地：能在 JVM 里答的，就不出进程

请求进了 ProductService.getDetail(88)，先查本实例的 Caffeine：product:88 没有，因为 A 刚重启。要是有，到这一步就结束了，连网络都不碰。

实测 这次没命中，2～6 µs；之后命中 5000 次，p50 4.1 µs，p99 22 µs（含两次计时调用本身）。

为什么要它88 号是热门商品，每秒几千次读要是都去 Redis，就是几千次网络往返，而且全压在 Redis 里存 88 号的那一个节点上。本地一份副本把绝大多数读挡在进程里。代价是 4 个实例各有一份，改价时得一起作废（第 11 站）。

往下一层88 号过期那一刻：穿透、击穿、雪崩与大 key、热 key · 多级缓存：Caffeine 加 Redis · 第一圈相关：MyBatis 缓存与 Caffeine · 热 key 为什么要靠本地缓存：Redis 大 key 与热 key

常出的事本地缓存不设条数上限，商品一多就把老年代占满，开始 Full GC（接 J03 全景）；设了过期时间却没有失效广播，各实例最长会卖过期时间那么久的旧价。

2Lettuce 发 GET：全实例共用一条连接

Lettuce 把 GET product:88 编成一段 RESP 协议的字节，写进这个实例唯一的那条 TCP 连接，由 Netty 的 IO 线程发出去；调用线程拿到一个 future，等结果回来。200 个请求线程同时查，也只是在这一条连接上排队发、按顺序收。

实测 4 个实例 × 50 个线程同时在查时，Redis 的 connected_clients = 4。客户端看到的一次 GET 往返：p50 279 µs，p99 1.26 ms。

为什么要它Redis 允许在一条连接上连着发好几条命令、按顺序回结果，所以 Lettuce 不需要连接池。连接少，Redis 那边的事件循环也只要盯几个 socket。

往下一层Redis 线程模型与 IO 多路复用 · 第二圈：279 µs 里只有 2 µs 在 Redis

常出的事在这条共享连接上跑阻塞命令（BLPOP 这类），或者取一个巨大的返回值，后面所有线程的命令都跟着排队；MULTI/WATCH 事务也不能放在共享连接上，会和别的线程的命令搅在一起。另外 Lettuce 默认命令超时是 60 秒，Redis 一卡，请求线程就挂 60 秒，Tomcat 的线程很快被占满；线上要配成几百毫秒。

3Redis 主线程：醒来、读命令、查字典

Redis 的主线程平时睡在 epoll_wait 上。这条连接一可读，它就醒来，读出 GET product:88，到全局字典（一张大哈希表）里找这个 key。找到了还要先看它过没过期，过期就当场删掉、当它不存在，这叫惰性删除。这里没找到，回 nil。

实测 服务端执行 GET 平均 2.0 µs 一次（INFO commandstats），客户端却等了 279 µs：99% 的时间花在网络、系统调用和线程调度上，不在 Redis 里。multiplexing_api:epoll，io-threads=1。

为什么要它一个线程按顺序执行命令，数据就不用加锁，每条命令天然是原子的。第 5 站的 SET NX 能当锁用、第 7 站的 Lua 脚本执行时不会被别的命令插进来，靠的都是这一点。

往下一层Redis 线程模型与 IO 多路复用 · 第二圈：279 µs 里只有 2 µs 在 Redis · 字典里的值怎么存：Redis 数据结构与编码（第二圈：648 字节的详情占 805 字节） · 惰性删除和定期删除：Redis 过期删除与内存淘汰（第二圈：第 617 个商品写不进去）

常出的事任何一条慢命令都会堵住所有客户端，比如 KEYS *、一次删掉一个百万元素的大 key、一段跑很久的 Lua。慢日志 SLOWLOG 只记执行时间，不记排队时间，所以被堵住的那些命令在慢日志里看起来都很快。

4布隆过滤器：查库之前，先问“有没有这个商品”

Redis 里没有，查库之前先问一句：BF.EXISTS bf:product 88，回“可能有”，继续往下走。要是有人拿 id=99999999 这种不存在的商品反复刷，过滤器回“一定没有”，直接返回 404，碰都不碰数据库。

实测 一次往返 332～394 µs，服务端 4～5 µs。过滤器里放了 1 万个 id，按 10 万容量、0.1% 误判率建的：拿 10 万个不存在的 id 去问，误判 0 个。Redis 8 起自带 BF.* 命令，不用再装模块。

为什么要它缓存只存“有的东西”。查不存在的 id，Redis 永远没有，每次都直落数据库，这叫穿透。布隆过滤器用很少的内存，回答“一定没有”。它放在 Redis 没命中之后，所以缓存命中的请求不用多付这一次往返。

往下一层88 号过期那一刻：穿透、击穿、雪崩与大 key、热 key · 缓存穿透、击穿与雪崩 · 布隆过滤器与 HyperLogLog

常出的事新商品上架忘了 BF.ADD，就被当成不存在，详情页 404。布隆过滤器删不掉元素，商品下架以后它还说“可能有”，好在后面还有数据库兜底。另一种防穿透的做法是把“查无此商品”也缓存几十秒，也就是缓存空值。

5抢重建锁：几百个请求一起没命中，只放一个去查库

确定要查库了，先 SET lock:product:88 <随机 token> NX PX 3000：这个 key 不存在才设得上，3 秒后自动过期。抢到的线程去查库；没抢到的每 10 ms 回头 GET 一次缓存，等抢到的那个把缓存建好。

实测 一次往返 332～422 µs。击穿测试：88 号缓存刚过期，4 个实例 × 50 个线程同时查，共 10 轮。裸查，数据库被查 1～26 次；只靠 Caffeine 的 get(key, loader) 在实例内合并，2～3 次；再加这把锁，每轮 1 次。代价是最慢的请求要等 18～36 ms，它在等锁。

为什么要它热门 key 过期的那一刻，几百个请求同时没命中，同时去查同一行，这叫击穿。一个实例里面，Caffeine 已经保证同一个 key 只放一个线程去加载；跨 4 个实例，就得靠 Redis 上的一把锁。

往下一层锁过期时 A 还在查库：看门狗、fencing token 与 Lua 条件写 · 88 号过期那一刻：穿透、击穿、雪崩与大 key、热 key · Redis 分布式锁 · 缓存穿透、击穿与雪崩

常出的事锁不设过期时间，拿锁的实例刚好挂了，锁永远不放，88 号的缓存再也建不起来；过期时间比查库还短，锁提前没了，第二个线程也进来查库。本机只有 2 个核，这 200 个线程实际是轮流跑的；真实机器核多，裸查同时打进数据库的会更多。

6MySQL 主键查一行：缓存里的一切，都是它的副本

拿到锁的线程向 HikariCP 借一条连接，执行 SELECT id, name, price, stock, detail FROM product WHERE id = 88。走主键，一行，price = 399.00，拼成 648 字节的 JSON。

实测 单次 0.56～2.2 ms，多数 0.6 ms。5000 次：p50 358 µs，p99 1.0～1.2 ms（本机回环，数据全在 buffer pool 里）。

为什么要它88 号到底卖多少钱，以数据库为准。缓存里的都是副本，副本丢了随时能从这里重建，这也是后面第 10 站敢直接删缓存的底气。

往下一层这一行在 MySQL 里怎么找到的：J06 全景第 4、5 站 · 索引与 B+ 树 · 连接池与事务性能

常出的事本机上 Redis GET（279 µs）和主键查询（358 µs）差不多快，可见缓存省的主要不是单次延迟，而是数据库的连接和 CPU。真正可怕的是成千上万次同时查：每个实例的池子只有 10 条连接，一瞬间就排满了（接 J06 第 1 站）。

7回填 Redis，再解锁：过期时间加点随机，解锁先认人

SET product:88 <JSON> EX 1843：30 分钟再加 0～5 分钟的随机数。然后用一段 Lua 解锁：锁里存的 token 还是自己的，才 DEL。

实测 SET 378～497 µs，EVAL 317～381 µs（服务端第一次执行 54 µs，含编译脚本）。OBJECT ENCODING product:88 = raw，648 字节的值实际占 805 字节（MEMORY USAGE）。顺手发现 Redis 8 的一处变化：key 和值放进了同一块内存，短字符串用 embstr 的门槛不再是固定的 44 字节。key 只有 3 个字节时，36 字节的值还是 embstr；key 有 24 个字节时，20 字节的值就已经是 raw 了。

为什么要它随机过期时间，让同一批预热进来的 key 不在同一秒一起过期，否则它们会同时变成第 5 站那种击穿，这叫雪崩。解锁要先比 token，因为锁可能已经过期、被别的线程拿走了，直接 DEL 会把别人的锁删掉；比较和删除放进同一段 Lua，执行时不会有别的命令插进来。

往下一层锁过期时 A 还在查库：看门狗、fencing token 与 Lua 条件写 · 88 号过期那一刻：穿透、击穿、雪崩与大 key、热 key · Redis 数据结构与编码 · 第二圈：648 字节的详情占 805 字节· Redis Lua 脚本与事务 · 缓存穿透、击穿与雪崩

常出的事整个商品存成一个 JSON，改一下库存也得整条重写；详情越堆越长，就成了大 key，一次 GET 把网卡和主线程都占住。商品要按字段改，就改用 Hash 存。

8放进本地，返回：先填 Redis，再填本地

JSON 放进 Caffeine，返回给详情页。同一实例下一次再查，第 1 站就命中了；实例 B 第一次查，本地没有，Redis 有，一次往返就拿到。

实测 第 1～8 站合计 2.0～4.2 ms；300 次全没命中的查询，p50 2.3 ms。A 再查一次 33～52 µs（单次，还没热透）；B 从 Redis 拿到 523～598 µs。

为什么要它本地缓存的数据只从 Redis 或数据库来。作废的时候也按同一个顺序，先删 Redis，再让本地作废（第 10、11 站），这样本地重新加载时，拿不到 Redis 里残留的旧值。

往下一层多级缓存：Caffeine 加 Redis

常出的事把 Caffeine 的过期时间设得和 Redis 一样长（30 分钟），又没有失效广播：改价以后，哪个实例都可能卖半小时旧价。

9改价并提交：先改数据库

运营在后台把 88 号从 399.00 改成 359.00：UPDATE product SET price = 359.00 WHERE id = 88，自动提交。从这一刻起，数据库里是新价，Redis 和 4 个实例的 Caffeine 里还都是 399.00。

实测 UPDATE 加提交 3.7～5.4 ms，大头是提交时等 redo、binlog 落盘（J06 全景第 9 站）。

为什么要它先改库，因为数据库是准的：改库成功了，再去让缓存跟上；改库失败，缓存什么都不用动。

往下一层缓存一致性：先改库还是先删缓存、延迟双删、订阅 binlog

常出的事顺序反过来，先删缓存再改库：删完到提交之间，来了一个读请求，没命中，从库里读到旧价 399.00 又写回 Redis。等改库提交以后，Redis 里一直是旧价，要到 30 分钟后过期才好。

10删 Redis 缓存：删，不是改成新值

提交后 DEL product:88。不是 SET 成 359.00，而是删掉：下一次读没命中，就按第 2～7 站从数据库重建。

实测 客户端 1.4～2.9 ms（这是运营后台这条连接上的第一次调用），服务端 3 µs。

为什么要它删比改安全：两次改价一前一后，各自去 SET，后发出的可能先到，Redis 里最后留下的就是旧的那次；删掉，就只剩数据库这一个来源。

往下一层缓存一致性：先改库还是先删缓存、延迟双删、订阅 binlog

常出的事改库成功、DEL 失败（网络抖了一下，或者服务正好重启），Redis 里的旧价要等 30 分钟。补救办法是重试，或者干脆不在业务代码里删，改成订阅 binlog（Canal 这类工具）统一删。还有一个更窄的窗口：一个读请求在提交前读到旧值，却在 DEL 之后才写回 Redis。“延迟双删”补的就是它。

11广播失效：Redis 管不着各实例自己的那份

PUBLISH cache:evict product:88。4 个实例都订阅了这个频道，各自的订阅连接收到消息，把 Caffeine 里的 product:88 作废。下一次读，本地没有，Redis 也没有，按第 2～8 站拿到 359.00。

实测 提交后 5.9～7.3 ms 两个实例都收到了消息；读线程（每 1 ms 读一次）在提交后 11～26 ms 读到 359.00。去掉广播只靠本地 5 秒过期：3.3～4.0 秒后才读到，这期间旧价被读了 3000 多次。

为什么要它Redis 里那份删掉了，可每个实例 JVM 里还各存着一份，Redis 管不着，只能发消息通知。

往下一层多级缓存：Caffeine 加 Redis · 可靠的失效消息用什么发：Redis Stream 与消息队列

常出的事Redis 的 Pub/Sub 最多投递一次：订阅连接断开重连的那几秒里发出的消息，就丢了，这个实例会一直用旧值，直到本地过期。所以本地缓存一定要配一个短的过期时间兜底（这里是 5 秒），要求更高就改用 Stream 或 MQ 发失效消息。

12后台：落盘、复制、过期、淘汰

这一站不在任何一次请求的路上，但一直在跑：每条写命令（第 5、7、10 站的 SET、DEL）追加进 AOF，每秒 fsync 一次；有从库的话，异步发给从库；每秒 10 轮，抽一批带过期时间的 key，过期的删掉（定期删除）；内存到了 maxmemory，按策略淘汰。

实测 appendonly=yes（我们打开的，默认是 no）、appendfsync=everysec、hz=10、maxmemory=0、maxmemory-policy=noeviction，后面四个都是默认值。

为什么要它重启后缓存还在不在（AOF、RDB）、主机挂了有没有人顶上（复制、哨兵、集群）、内存会不会无限涨（过期和淘汰），这三件事决定了缓存出问题时，数据库要多扛多少。

往下一层Redis 持久化 RDB 与 AOF · Redis 主从、哨兵与集群（第二圈：88 号的锁有了两个主人）· Redis 过期删除与内存淘汰（第二圈：第 617 个商品写不进去）

常出的事maxmemory 默认 0，64 位系统上就是不设上限，淘汰策略默认 noeviction。有人配了上限却没改策略，内存一满，所有 SET 都报 OOM 错误：第 7 站回填失败，第 5 站的锁也抢不到，请求全落到数据库。纯做缓存的实例，要配 allkeys-lru 或 allkeys-lfu。

预测题

1. Redis 整个挂了 30 秒，88 号的详情页会怎样？哪里先报警？

头 5 秒，本地缓存里还有 88 号的实例照常返回，只有本地没有的请求出错。5 秒后本地也过期了，每个请求都卡在第 2 站：Lettuce 连不上，要是超时还是默认的 60 秒，请求线程就一直挂着，Tomcat 线程池很快被占满，连不用缓存的接口也一起变慢。代码要是在 Redis 出错时直接降级查库，压力就全部转到第 6 站，每个实例 10 条连接的池子瞬间排满。最先报警的是应用的 Redis 连接错误和接口 p99，然后是数据库连接池的等待数。

从第 1、2、6 站推出：本地缓存只能顶住它的过期时间那么久；Redis 后面那一层要靠超时和降级来保护。

2. 改价时，实例 C 的订阅连接正好在重连，没收到那条 PUBLISH。C 会卖多久旧价？

最多 5 秒，也就是 C 的本地缓存里那条还剩多少过期时间。Redis 里那份已经在第 10 站删掉了，所以 C 本地过期以后，重新加载拿到的就是 359.00。要是本地过期时间设成 30 分钟，C 就会卖半小时旧价，而且别的实例都正常，很难查。

从第 8、10、11 站推出：Pub/Sub 最多投递一次，本地缓存的过期时间就是它丢消息时的上限。

3. 有人拿 id = 1～1000 万挨个刷详情接口。数据库会被查多少次？去掉布隆过滤器呢？

有布隆过滤器：存在的那 1 万个商品各查一次库，之后都在缓存里；剩下 999 万个不存在的 id，几乎都在第 4 站被挡掉（按 0.1% 的误判率，最多漏过去 1 万个左右，实测 10 万个一个都没漏）。去掉它：每个不存在的 id 都穿过第 3 站直落第 6 站，999 万次查库；而且查不到的结果不会被缓存，下一轮再刷还是一样。

从第 3、4、6 站推出：缓存只存“有的东西”，“没有”要靠布隆过滤器或者缓存空值来记。

4. 有人给 Redis 配了 maxmemory 1gb，没改淘汰策略。内存满了以后，详情页会怎样？

已经在缓存里的商品照常读得到（GET 不受影响）。新没命中的商品：第 5 站的 SET NX 报 OOM，代码要是把报错当成“没抢到锁”，所有线程都在那里等 10 ms 一轮地重试，等到 1 秒后各自去查库；第 7 站的回填也报 OOM，查完的结果存不进去，下一次照样没命中。结果是缓存命中率越来越低，数据库压力越来越大，而 Redis 自己看起来很健康。

从第 5、7、12 站推出：noeviction 下内存满了是“写失败”，不是“自动腾地方”。

Redis 集群里主节点宕机

3 主 3 从，88 号所在的主节点挂了，从节点顶上之前的十几秒里发生了什么：刚写进去还没复制过去的缓存和锁丢了，两个实例可能同时以为自己拿到了重建锁。难在弄清哪些丢了没关系（缓存），哪些丢了会出错（锁）。
