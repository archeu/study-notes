一次下单跨三个库

用户 1024 下单：订单 9527，2 件 88 号机械键盘，用一张满减券 MINUS20。订单、库存、券分别在三个服务、三个 MySQL 里，一个本地事务装不下。这张全景回答：三个库各写一笔，怎么做到要么都成、要么都没发生；订单服务在半路被 kill -9，数据靠哪几站对齐；J09 的 7 个知识点各管哪一站。

场景：订单 9527 要在三个库里各写一笔

谁
交易靶场。20:00:00，用户 1024 在 App 上点“提交订单”，手一抖点了两下。订单 9527 就是 J01 全景里那一单：2 件 88 号机械键盘，用满减券 MINUS20。
三个库
order_db（订单服务）、inventory_db（库存服务，88 号可售 50 件）、coupon_db（券服务，1024 有一张没用过的 MINUS20）。三个服务各连各的 MySQL 8.4，谁也开不了别人库上的事务。
方案
Apache Seata 2.6.0 的 TCC 模式：订单、库存、券各是一个分支，每个分支写好 Try、Confirm、Cancel 三个方法，打开 TCC fence（防重复、空回滚、悬挂）。协调者 TC 是 3 个节点的 Raft 集群。订单确认时，在同一个本地事务里写一行 outbox，后面发到 Kafka（J08 全景第 1 站）。全局事务超时用默认的 60 秒。
期望
要么三笔都成：订单待支付、库存 48、券已用；要么三笔都没发生：订单取消、库存 50、券没用。不能出现“库存扣了、券还在”。双击只生成一张单。
演练
订单服务在第 5 站库存冻结成功以后、第 6 站券的 Try 还没返回时，被 kill -9。

按设计推演 正常路径：第 8 站以后三个库一致，从点击到返回大约是 4 次 RPC 加 4 次本地提交。演练路径：约 60 秒后 TC 发现全局事务超时，往三个分支推 Cancel，库存回到 50、券回到没用、订单变成已取消。中间这 60 秒，那 2 件是冻结的，别人买不到；券是锁着的，1024 自己也用不了。这种“暂时不一致、最终会一致”的中间状态，就是 BASE 里的软状态。

本页没跑实验：这一站的事务、幂等、超时三个知识点页会在交易靶场里把正常路径和演练路径真跑一遍。

1订单服务：用幂等键挡掉双击的第二下

App 每次打开结算页时生成一个幂等键 req-7f3a，两次 POST 都带着它。订单服务先往 idem_key 表插一行，这一列有唯一索引：第一下插进去了，状态是“处理中”；180 ms 后第二下插入时撞上唯一键，直接返回“这单已在处理”，不再往下走。

为什么要它后面每一站都会写库、冻结库存、锁券。重复的请求如果进来，会生成第二张单去抢同一张券。在入口挡掉最便宜。

往下一层幂等设计：唯一键、状态机、去重表 · 第一圈相关：幂等消费与顺序消息（消费端的去重表）

常出的事用“先查有没有、再插入”代替唯一索引，两下同时到时都查到“没有”。幂等键由服务端按“用户 + 时间”生成，结果用户真想买两单也被挡了。

2发号：订单号 9527 从号段里取

订单服务启动时，执行一次 UPDATE id_alloc SET max_id = max_id + 1000 WHERE biz_tag = 'order'，领到 [9001, 10000] 这一段，放在内存里一个个发。9527 就是这一段里的一个，不用访问任何库。全局事务的 XID 则由 TC 生成，格式是 TC 的 IP:端口:事务号，事务号来自 Seata 自带的雪花算法变种。

为什么要它订单号要在第 4、5、6 站同时写进三个库，各库自己的自增 ID 互相会撞号，所以要一个跨库唯一的号，而且要在第一次写库之前就定下来。

往下一层MyBatis-Plus 原理里的雪花 ID 一节（第一圈）· 号段和雪花怎么选、时钟回拨 待做

常出的事雪花算法依赖本机时钟，NTP 把时钟往回拨了，就可能发出重复的号。号段模式不看时钟，但实例重启会丢掉没发完的号，号就不连续（订单号本来也不该要求连续）。

3Seata TC：开全局事务，记录要写进多数派

placeOrder() 上有 @GlobalTransactional，进入方法时订单服务（TM）找 TC 要一个 XID。TC 集群是 3 个节点，用 Raft 选出 tc-1 当 leader。“新增一个全局事务”这条记录先写进 tc-1 的日志，复制到 tc-2 也写下了，2/3 过半，才算记住，XID 返回给订单服务。

为什么要它后面要靠 TC 来决定“三个分支是一起转正，还是一起退回”。只有一台 TC 的话，它的磁盘坏了，这个决定就没了；多台又可能各说各的。多数派保证：任何时候最多有一个 leader 能写，而且写下的记录挂一台也丢不了。

往下一层共识：Raft 怎么选主、怎么复制日志 待做 · CAP、BASE 与一致性模型 · 第一圈相关：Kafka 的 ISR、ELR 与 unclean 选举（另一种“谁有资格当 leader”）

常出的事3 个 TC 挂了 2 个，剩下的那个凑不够多数派，开不了新事务：下单直接报错。这是 CAP 里选了 C：宁可不可用，也不让一台孤立的节点自己拍板。

4订单分支 Try：先插一行用户看不到的 CREATING

订单服务带着 XID，调自己的 TCC 方法 OrderTcc.tryCreate()。Seata 的代理先向 TC 登记“订单分支”，再在一个本地事务里做两件事：往 orders 插 9527，状态是 CREATING；往 tcc_fence_log 插一行“tried”。

为什么要它TCC 模式只回滚登记过的分支。订单服务如果直接写一行“待支付”而不当成分支，后面回滚时这一行没人管，就成了库存已退、订单还在。所以订单自己也要分 Try 和 Confirm：Try 只留个占位，Confirm 才让它对用户可见。

往下一层分布式事务：2PC、TCC、Saga、本地消息表、Seata 待做

常出的事在 @GlobalTransactional 方法里直接 orderMapper.insert()，以为 Seata 会回滚它。TCC 模式下不会，只有走了 TCC 代理（或 AT 模式的数据源代理）的写入才是分支。

5库存分支 Try：冻结 2 件，可售 50 → 48

就是 J04 全景里那次 Reserve(9527, 88, 2)，只是 RPC 的请求头里多了 XID。库存服务的 TCC 代理先登记“库存分支”，再在本地事务里执行 UPDATE stock SET available = available - 2, frozen = frozen + 2 WHERE sku_id = 88 AND available >= 2，同时插 fence。

为什么要它直接扣减的话，后面券锁不上就得“加回去”，可这中间别人可能已经看到、甚至买走了。冻结是一个能干净撤销的中间态：Confirm 时 frozen - 2，Cancel 时 available + 2, frozen - 2。

往下一层分布式事务（TCC 的资源预留）待做 · 时钟、超时与重试 待做 · 回顾：J04 全景的 deadline 300 ms

常出的事RPC 300 ms 超时了，订单服务以为“失败”，其实库存服务在 400 ms 时冻结成功了。超时只说明“不知道”，不说明“没做”。这个分支已经登记过，回滚时 TC 照样会给它发 Cancel，冻结的 2 件能退回来。

6券分支 Try：把 MINUS20 锁给 9527

券服务登记“券分支”，执行 UPDATE user_coupon SET status = 'LOCKED', order_id = 9527 WHERE id = … AND status = 'UNUSED'，影响 1 行才算成功，同时插 fence。演练就在这里：券服务刚收到请求、本地事务还没提交，订单服务实例 A 被 kill -9，再也没人会发 commit。

为什么要它用 WHERE status = 'UNUSED' 做条件更新，等于用状态机挡并发：两张单同时抢这张券，只有一张能影响 1 行。

往下一层分布式事务 待做 · 幂等设计里的“状态机”

常出的事Try 失败（券已被用）时，订单服务要抛异常，让 TC 回滚前面两个分支；把异常吞掉、照样往下走，就会发 commit，变成“没用券也打了折”。

7Seata TC：写下“要提交”的决议

正常路径上，三个 Try 都成功，placeOrder() 正常返回，TM 向 TC 发 commit。TC 把全局状态从 Begin 改成 Committing，这次修改同样要复制到多数派，然后就可以回复订单服务“成功”，用户看到“下单成功，请付款”。

为什么要它这是整个事务的“拍板”时刻：从这以后，哪怕订单服务、哪个参与者、甚至 tc-1 挂了，新 leader 读到的状态都是 Committing，结局只能是提交。

往下一层共识：Raft 待做 · 分布式事务里的 2PC：协调者的决议写在哪 待做

常出的事决议只记在协调者一台机器的内存里（经典 2PC 的老问题），它在“有的分支收到提交、有的还没收到”时挂了，没收到的那些只能一直锁着等。

8Seata TC：往三个分支推 Confirm，失败就一直重试

TC 逐个调三个分支的二阶段提交（Seata 里默认方法名叫 commit，就是 TCC 说的 Confirm）。订单：CREATING → WAIT_PAY，同一个本地事务里往 outbox 插一行 ORDER_CREATED；库存：冻结的 2 变成真扣，库存 50 → 48；券：LOCKED → USED。每个分支先查 fence：已经是 committed 的直接返回成功。

为什么要它决议已定，资源要转正。Confirm 失败（比如券库重启）不能回头，只能重试：TC 的恢复任务每 1 秒捞一次没提交完的事务，默认不设上限。所以 Confirm 必须能重复执行。

往下一层分布式事务（TCC fence：幂等、空回滚、悬挂）待做 · 时钟、超时与重试 待做 · 幂等设计：去重表

常出的事Confirm 里写了“库存再减 2”这种不幂等的逻辑，又没开 fence，一次重试就多扣 2 件。Confirm 依赖的东西被人工删了，重试永远失败，TC 日志里每秒报一次错，没人看。

9订单服务：抢到锁的那个实例把 outbox 发到 Kafka

两个订单服务实例都有扫描任务，每秒扫一次 outbox 里 NEW 的行。为了不让两个实例都去发，任务开始前抢一把锁（数据库里一行锁记录，或者 Redis 的 SET NX PX），抢到的实例发出 ORDER_CREATED 9527，收到 Kafka 的 ACK 后把这一行标成 SENT。notify-svc 收到后提醒 1024 去付款，30 分钟没付就取消订单。

为什么要它这是本地消息表：发消息这件事和 Confirm 在同一个本地事务里落了库，就不会“订单成了、消息丢了”。通知不需要和下单一起成败，最终发到就行，用不着再上 TCC。

往下一层Redis 分布式锁 · 下一圈：锁过期与 fencing token · Redis、ZooKeeper、数据库三种锁怎么选 待做 · 消息这一侧：J08 全景第 1、8 站

常出的事锁的租期 30 秒，持锁的实例 Full GC 停了 40 秒，醒来接着发；另一个实例早就拿到锁也在发：同一条消息发了两遍。锁只能减少重复，挡不住所有重复，下游照样要去重。

10演练：订单服务死在第 6 站，TC 等满 60 秒自己回滚

实例 A 被 kill -9，TC 里这个全局事务停在 Begin。TC 每 1 秒检查一次：开始时间加 60 秒（@GlobalTransactional 默认超时）已经过了，状态改成 TimeoutRollbacking，给登记过的三个分支推 Cancel：订单 CREATING → CANCELLED，库存冻结的 2 件退回，可售回到 50。券分支看 fence：Try 已提交的，LOCKED → UNUSED；Try 还没提交的，找不到 tried 记录，就是空回滚，什么也不改，但记下一行 suspended。之后那个迟到的 Try 想插 fence 会冲突，失败，这叫防悬挂。

为什么要它发起方死了，就没人说“提交”还是“回滚”。TC 不能永远等，只能拿“超时”当作“已经死了”的判断，而超时是它按自己的时钟量的。

往下一层时钟、超时与重试：分布式里为什么不能信时间 待做 · 分布式事务（空回滚、悬挂）待做

常出的事没开 fence：Cancel 先到、什么都没改，迟到的 Try 随后把券锁上，再也没人来解，这张券永远“已锁定”。另一种：业务真需要 90 秒（比如调外部风控），默认 60 秒的超时会把正常的单回滚掉。

11对账任务：每 10 分钟按单号比一次三个库

独立的对账任务扫最近一段时间的订单，按单号去库存和券库里找对应的冻结、扣减、锁定记录。9527 在演练后三边都是“没发生”，对得上。如果发现“订单 CANCELLED、券还 LOCKED 超过 10 分钟”这种组合，就报警，或按规则自动修。

为什么要它前面每一站都尽量保证一致，但人工改库、bug、重试被关掉，都可能留下对不上的数据。最终一致说的是“最终会一致”，得有一个东西去确认它真的一致了。

往下一层CAP、BASE 与一致性模型 · 分布式事务（各方案的兜底）待做

常出的事对账用的是从库，复制延迟让刚提交的单看起来“对不上”，误报一大片（主从复制延迟）。只报警没人处理，问题单越积越多。

知识点地图

知识点名照抄学习地图。J09 的 7 个知识点里，分布式锁和分布式 ID 在 Redis 和 MyBatis-Plus 那几页里讲过第一圈；剩下 5 个都没有页，而这张全景最要紧的 4 站（④⑤⑥⑧）全挂在“分布式事务”上。下钻顺序是：先给一点词汇（CAP、BASE），再学入口的幂等，然后啃分布式事务，最后补“它为什么靠得住”的两块：超时和 Raft。

这张全景没走到的

  • Seata AT 模式：国内项目最常见，靠代理数据源自动记 undo 日志、自动回滚。这里用 TCC，是因为库存要“冻结”这种业务语义，AT 只会把行改回去。两者的对比在下钻第 3 步。
  • Saga：适合没法 Try 的长流程，比如退款要调第三方支付，只能“先做，失败了再补偿”。到下一圈“退款跨支付、库存、积分”里出场。
  • XA 和经典 2PC：这张图的第 3、7、8 站其实就是 2PC 的骨架（准备、决议、提交），只是 TCC 的“准备”由业务自己写。数据库层的 XA 会把行锁一直持有到第二阶段，在下钻第 3 步对比。

预测题

1. 订单服务在第 7 站把 commit 发出去以后、收到回复之前被杀了。9527 最后是成了还是没成？用户看到什么？

看 commit 有没有被 TC 写进多数派。写进去了：状态已是 Committing，TC 自己会把三个 Confirm 推完，9527 是待支付，库存 48，券已用；用户的 App 因为连接断了显示失败，刷新订单列表才会看到这张单。没写进去（请求丢在路上）：状态还是 Begin，60 秒后超时回滚，三个库都退回。所以“下单失败”的提示不一定准，App 要提供“查一下这单到底成没成”的入口。

从第 7、8、10 站推出：结局由 TC 里那条记录决定，不由发起方是否活着决定。

2. 3 个 TC 节点里，tc-1（leader）和网络断开了，tc-2、tc-3 还能互通。正在路上的事务会怎样？新的下单呢？

tc-2、tc-3 等不到 leader 的心跳，超过选举超时（Seata 默认 1 秒）后选出新 leader，新的下单可以继续。tc-1 一个人凑不够多数派，它手上没复制出去的写入不会生效：订单服务在 tc-1 那边开的事务会失败或超时，重新连到新 leader 再来。已经写进多数派的事务，新 leader 都有，照常推 Confirm 或 Cancel。

从第 3、7 站推出：只有多数派那一边能写，少数派那一边宁可不可用（CAP 里选了 C）。

3. 大促时有人把全局事务超时从 60 秒改成 5 秒，想让冻结的库存早点释放。会出什么事？

平时没事；一旦库存服务或券服务慢到几秒，大量本来能成功的单会在第 10 站被回滚，而发起方可能还在等 Try 返回，回来以后发 commit，TC 已经在回滚，commit 失败，用户看到下单失败。库存被反复冻结、释放，热门商品的可售数来回跳。超时设短了，误判“死了”的情况就多。

从第 5、10 站推出：超时只是猜测，猜得越急，错得越多。

4. 券服务的 Confirm 有 bug，每次都抛异常。一天以后会看到什么？哪里先报警？

订单早就是待支付、库存早就扣了，用户也付了款，只有券一直停在 LOCKED。TC 每秒重试一次，默认没有上限，日志里每秒一条失败；TC 里未完成的全局事务越积越多。最先该报警的是 TC 的“二阶段重试”监控和第 11 站的对账（订单已支付、券还 LOCKED）；没配的话，要等 1024 发现那张券“用了却还占着”来投诉。

从第 7、8、11 站推出：决议之后只能往前推，不能回头，卡住的分支只会一直重试。

第三方支付没有 Try，只能“先退钱，失败了再补偿”，这是 Saga 的地盘。难在补偿本身也会失败、退款和付款消息还可能乱序（接 J08 的退款比付款先到）。

TC 的 leader 所在机房断网 30 秒

正在第 7 站和第 8 站之间的几百个事务怎么办，30 秒后旧 leader 回来会不会“说两句话”。难在把 Raft 的任期、日志截断和 Seata 的恢复任务对上。这是下钻第 5 步 Raft 的下一圈。

JDK 版本约定：交易靶场和 Java 地图的全景页用 JDK 21；单个知识点页的实验用 JDK 17。

档位：标准（全景页），没有做本机实测；时间线和各库的状态是按 Seata TCC 的设计推演的，下钻的事务、幂等、超时三页会在靶场里真跑。

按文档和源码（Apache Seata 2.6.0，2026-01 发布的最新稳定版；2.7.0 还是候选版）：@GlobalTransactional 的 timeoutMills 默认 60000；超时后 TC 把全局状态改成 TimeoutRollbacking 再回滚；恢复任务的提交、回滚、超时检查周期默认都是 1000 ms，max-commit-retry-timeout 和 max-rollback-retry-timeout 默认 -1，即一直重试；TCC fence 从 1.5.1 开始有，表名 tcc_fence_log，状态 tried=1、committed=2、rollbacked=3、suspended=4，useTCCFence 默认关；@TwoPhaseBusinessAction 的二阶段方法默认叫 commit、rollback；分支在参与者执行 Try 之前登记；TC 的 Raft 集群模式从 2.0.0 开始（store.mode: raft，election-timeout-ms 默认 1000），复制全局会话、分支会话和锁的释放，写入要过半节点确认；XID 是 IP:端口:事务号，事务号来自雪花算法的变种 IdWorker。TCC 模式下发起方自己直接写的库不会被 Seata 回滚，是从“只回滚登记过的分支”推出来的。

按设计：号段的发号方式、对账任务、outbox 扫描锁，是交易靶场的设计，不是 Seata 的功能。
