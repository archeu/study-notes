订单表从一张到八张

交易靶场的订单表 t_order 长到 1.2 亿行，决定按用户 ID 拆成 2 个库、8 张表。这张全景回答三件事：按用户查（1024 看“我的订单”）在拆完以后怎么只碰一张表；按商家查（商家 301 看本店订单）为什么不再走 MySQL，而是交给 Elasticsearch；迁移那几周，双写、搬数据、校验、切换各在哪一步，为什么任何时刻都能回滚。最后一站看另一条路：不自己拆，换成 TiDB、OceanBase、GoldenDB 这类分布式数据库。

场景：一张表装不下了

谁
交易靶场的订单服务 order-svc。订单表 t_order 在一主一从的 MySQL 8.4 上，1.2 亿行，表空间约 140 GB，每天新增约 60 万单。用户 1024 的历史订单里有 J06 那一单 id = 9527；商家 301 卖 88 号机械键盘。
为什么要动
不是“单表超过 2000 万就得拆”这种口诀。真正的信号是三条：给 shop_id 补一个索引跑了 2 小时 40 分；整库恢复演练要 4 小时，超过了 1 小时的 RTO；大促写入峰值 3200 行/秒，主库 CPU 到了 85%。
拆成什么样
按 user_id 拆成 2 个库、8 张表：t_order_${user_id % 8}，偶数表在 ds_0，奇数表在 ds_1。1024 % 8 = 0，他的订单都在 ds_0.t_order_0。应用里接 ShardingSphere-JDBC 5.5.3，业务 SQL 照旧写 t_order。
两种查法
按用户查（“我的订单”、订单详情）走分片键，只碰一张表。按商家查（“本店待发货”“搜收货人”）没有分片键，交给 Elasticsearch 9.5，数据由 Canal 读 binlog 同步过去。
期望
迁移几周里 App 不停服、用户无感；任何一步发现问题，改一个开关就能退回旧表。切换后“我的订单”更快，商家搜订单在 1～2 秒内能看到新单。

按设计推演 拆完以后每张表约 1500 万行。1024 打开“我的订单”只查 ds_0.t_order_0 一张表；商家 301 搜本店订单，查的是 ES 里的 orders 索引，一单从提交到能被搜到，要经过 binlog → Canal → Kafka → 同步程序 → ES 刷新，大约 1～2 秒。不带分片键的查询（运营后台翻全站订单、客服只拿着老订单号查）会被改写成 8 条 SQL，是拆分以后的主要代价。

本页没跑实验：分库分表、跨片查询、迁移、ES、同步几个知识点页会在交易靶场里把路由改写、双写校验、binlog 同步真跑一遍。

1单表到顶：先看清是哪里扛不住

t_order 1.2 亿行。按主键或 idx_user 查一单，B+ 树也就四层，单次查询并不慢。慢的是别的事：给 shop_id 补索引要重建整棵二级索引，跑了 2 小时 40 分；整库恢复演练 4 小时；大促时所有写入挤在一台主库上，CPU 85%。

为什么要它拆分是最贵的一招，会给后面每一站带来麻烦。所以先确认便宜的招用完了：冷数据归档、读写分离、加缓存、优化慢 SQL。只有“一台主库的写入、单表的运维时间”这类问题，才非拆不可。

往下一层分库分表：什么时候拆、分片键怎么选、ShardingSphere · 第一圈：索引与 B+ 树（为什么 1.2 亿行点查还快）

常出的事按“单表 2000 万”的口诀提前拆，拆完发现慢的是一条没走索引的 SQL；或者反过来，等到主库扛不住才开始拆，迁移要好几周，这几周只能硬扛。

2定分片键和规则：user_id % 8，2 库 8 表

统计查询日志：九成以上的订单查询带着 user_id。所以分片键选 user_id：t_order_${user_id % 8}，ds_${user_id % 2}。表号和库号用的是同一个余数，偶数表都在 ds_0、奇数表都在 ds_1。新订单号用雪花算法生成，再把最低 3 位换成 user_id % 8（基因法）。

为什么要它分片键决定了以后哪些查询便宜、哪些昂贵：带它的查询只碰一张表，不带它的要问遍 8 张。选错了，迁移完还得再迁一次。

往下一层分库分表：什么时候拆、分片键怎么选、ShardingSphere · 订单号基因：分布式 ID

常出的事库用 user_id % 2、表用 user_id % 4，两个余数相关：ds_0 里只会出现偶数用户，它的 t_order_1、t_order_3 永远是空的，一半表白建。还有选了会变的字段当分片键，比如订单状态。

3双写：旧表为主，新表跟着写

D-14 发版。下单、改状态的代码先写旧表 t_order，成功后再写一遍新表（经 ShardingSphere 落到 8 张表之一）。新表写失败只记一条补偿日志，不影响下单。订单 id 由应用生成，两边用同一个 id。

为什么要它迁移要几周，这期间订单还在不断产生和变化。双写让新表从这一刻起不再落后；旧表仍是唯一的“真相”，所以任何时候都能放弃新表。

往下一层不停机数据迁移：双写、校验、灰度切换、回滚

常出的事两个库之间没有本地事务：旧表写成功、新表写失败，或者两次更新到达新表的顺序反了。双写本身不保证一致，要靠第 4 站的比对和修复兜底。另一种常见做法是不改代码、用 binlog 同步代替双写，效果一样，坑也一样。

4搬历史 + 校验：搬到差 0 才往下走

搬运任务按主键分批读旧表（每批 5000 行），按 user_id 算出目标表写进去，盯着主从延迟限速。已经被双写写过的行不覆盖。搬完 1.2 亿行，再按 id 区间比行数和校验和，对不上的区间逐行比：发现 312 行不一致，以旧表为准修好，再比一遍，差 0。

为什么要它双写只管 D-14 以后的变化，以前的 1.2 亿行要搬。校验是迁移里最重要的一步：它是“能不能切”的唯一依据。

往下一层不停机数据迁移：双写、校验、灰度切换、回滚

常出的事搬运读到一行旧值，写进新表时覆盖了双写刚写好的新值（订单状态倒退回“待支付”）。搬太快把主库或从库打满。只比行数不比内容。

5灰度切换：先切读，再切写，每一步都能拨回去

D 日 10:00，读开关按用户灰度：user_id % 100 < 1 的用户读新表，同时对比新旧结果；10:30 放到 10%，14:00 全量。D+3 切写：新表为主，旧表改成被反向双写。D+14 停写旧表，留只读备份。

为什么要它一次全切，出问题时影响所有人，也分不清是数据错了还是代码错了。先读后写：读切错了随时可以切回去，数据不会坏；写切过去之后，旧表还靠反向双写跟着，回滚才仍然可能。

往下一层不停机数据迁移：双写、校验、灰度切换、回滚

常出的事读写同时切；切写的同时停掉旧表的写入，回滚的路就断了；切换开关做在各个实例的本地配置里，几个实例状态不一致。

6按用户查：ShardingSphere 把一条 SQL 改写到一张表

14:20，1024 打开“我的订单”。order-svc 执行的仍是 SELECT … FROM t_order WHERE user_id = 1024 ORDER BY created_at DESC LIMIT 0, 20。ShardingSphere-JDBC 解析出 user_id = 1024，算出 ds_0.t_order_0，把表名改写后只发这一条。

为什么要它业务代码不想知道有 8 张表。分片中间件在 JDBC 这一层拦下 SQL，做解析、路由、改写、执行、归并五步，应用还像在用一张表。

往下一层分库分表：什么时候拆、分片键怎么选、ShardingSphere · 第一圈：MyBatis 执行流程（SQL 在哪一层被拦下）

常出的事SQL 里分片键套了函数、写成了范围或者干脆没写，路由就退化成查 8 张表，功能没错，只是悄悄慢了 8 倍。分片键的值写入以后不能再改。

7按订单号查：新单号带基因，老单号 9527 没有

1024 点开订单 9527。接口从登录信息里拿到 user_id，SQL 写成 WHERE id = 9527 AND user_id = 1024，只查一张表。客服后台只拿着订单号：新订单号的最低 3 位就是 user_id % 8，自定义的分片算法能直接算出表；9527 是拆分前的老单号，9527 % 8 = 7，可它其实在 t_order_0，只能查全部 8 张表。

为什么要它按订单号查是第二常见的查法。能带上 user_id 的地方都带上，带不上的靠订单号里的基因；历史数据没有基因，要另想办法。

往下一层分片以后的难题：跨片查询、分页、全局表 · 分布式 ID（雪花号的低位为什么不能直接取模）

常出的事按基因直接算老订单号，路由到 t_order_7，查不到，返回“订单不存在”。常见做法：老单号走广播查询，或者建一张“订单号 → user_id”的映射表，或者让客服查 ES。

8跨片分页和全局表：8 张表各取一批，在内存里归并

运营后台看全站订单，按时间倒序第 3 页，每页 20 条：LIMIT 40, 20。没有分片键，ShardingSphere 发 8 条 SQL，每条都改成 LIMIT 0, 60，拿回 480 行，按 created_at 归并后取第 41～60 行。列表里要显示省份名，t_region 配成全局表，两个库各有一份完整的，可以在本库里 JOIN。

为什么要它每张表只知道自己那一部分，谁是全局第 41 名，只能把每张表的前 60 名都拿来比。小表复制到每个库，就不用跨库 JOIN。

往下一层分片以后的难题：跨片查询、分页、全局表

常出的事翻到第 500 页：每张表各取 10000 行，8 张表一共拉回 8 万行，只为了 20 行。要么禁止跳页、改成“下一页”游标（WHERE created_at < 上一页最后一条），要么把这类查询交给 ES 或离线数仓。

9按商家查：shop_id 不是分片键，交给 ES

14:21，商家 301 打开“待发货”，再搜收货人“张”和商品“键盘”。shop_id = 301 的订单散在全部 8 张表里，模糊搜索 MySQL 又不擅长。所以商家后台查的是 Elasticsearch 里的 orders 索引：shop_id 精确过滤、标题和收货人全文检索、按时间排序，拿回订单号，详情再按订单号回 MySQL 查。

为什么要它一份数据只能按一个键分片。按用户分了，按商家查就得另存一份按商家能查的数据：可以是按 shop_id 再分一套的“异构索引表”，也可以是搜索引擎。要全文检索和多条件组合，ES 更合适。

往下一层Elasticsearch：倒排索引、分片、写入和查询过程 · 分片以后的难题：跨片查询、分页、全局表

常出的事把 ES 当成真相：根据 ES 里的“已支付”去发货，而它可能还停在 1 秒前。ES 只用来“找”，要做决定的那一刻，回 MySQL 按订单号查一次。

10binlog → Canal → Kafka：把订单变更搬到 ES

1024 下单这一行写进 ds_0.t_order_0，MySQL 记下一条 ROW 格式的 binlog。Canal 1.1.8 装成一台从库，向 ds_0、ds_1 各要 binlog，解析出“哪张表、哪一行、改前改后”，按订单号发到 Kafka。同步程序消费消息，把一行拼成一个文档，批量写进 ES。

为什么要它在下单代码里顺手写 ES，会把 ES 的慢和失败带进下单，而且漏写了没人知道。binlog 是数据库已经提交的事实，从它同步，代码不用改，也不会漏掉别的服务和手工 SQL 改的数据。

往下一层MySQL 到 ES 的同步：binlog、Canal、一致性 · 第一圈：缓存一致性（同样是订阅 binlog 删缓存）

常出的事同一订单的两条变更进了不同分区，后到的旧状态把新状态覆盖了；Canal 停了几天，要的 binlog 已经被清掉，只能全量重灌。还有第 4 站：如果 ES 从新库同步，搬运 1.2 亿行时产生的 binlog 会全部涌进 ES。

11ES 写入和搜索：倒排索引、分片，1 秒后才搜得到

文档按 _id 的哈希落到 orders 的某个主分片：先写内存缓冲和 translog，再复制到副本，然后确认。默认每秒一次 refresh，把缓冲里的文档变成一个可搜索的段，这时商家才搜得到。搜“键盘”时，协调节点问每个分片要前几名，归并排序后再去取文档内容。

为什么要它倒排索引把“哪些订单里有‘键盘’”预先算好，搜索不用逐行扫描。分片让一个索引分散到多台机器上；refresh 用 1 秒的延迟换来了写入吞吐，这就是“近实时”。

往下一层Elasticsearch：倒排索引、分片、写入和查询过程

常出的事同步程序把 shop_id、订单号当字符串发过去，被动态映射成了 text，精确过滤和排序都不对；中文用默认分词器，被切成一个一个字；商家一页一页往后翻，超过 1 万条以后 from + size 直接报错，要改用 search_after。

12另一条路：不自己拆，换分布式数据库

第 2～8 站的事，换个数据库也能交给它做。TiDB、OceanBase 是原生分布式：数据自动切成很多小块，每块多副本，用 Raft 或 Paxos 保证一致，SQL 层兼容 MySQL。GoldenDB 走的是另一条路：底下仍是多个 MySQL 分片，上面加计算节点和全局事务管理器（GTM）。银行核心系统在用它们，看中的是多副本不丢数据和国产化。

为什么要它自己拆要改 SQL、做迁移、养中间件。换库把这些复杂度交给数据库，但换来的是另一套运维和一组和 MySQL 不一样的行为。

往下一层待做 分布式数据库：TiDB、OceanBase 原生分布式，GoldenDB 分片加全局事务，金融行业为什么在用 · 待做 从 MySQL 换过去要注意：自增 ID、写热点、大事务、隔离级别 · 相关：Raft 共识

常出的事以为“兼容 MySQL”就是原样搬：自增 ID 不再连续，主键单调递增导致写入集中在一块数据上，一次删几千万行的大事务被拒绝，REPEATABLE READ 的加锁行为也和 InnoDB 不一样。

知识点地图

知识点名照抄学习地图。J11 的 7 个知识点都还没有页。下钻顺序大体跟着站走，只有一处调换：跨片查询（第 7～9 站）排在迁移（第 3～5 站）前面，因为迁移之前要先把不带分片键的 SQL 找出来改掉，不然切读那天就会出事。

站知识点状态下钻顺序和理由

这张全景没走到的

  • 垂直拆分：按业务把订单、商品、用户放进不同的库，J10 拆微服务时已经做了；这张图只讲水平拆分，一张表拆成很多张。
  • 分布式事务：拆完以后同一个用户的订单在同一个库，第 6～8 站都用不到跨库事务；跨服务、跨库的事务在 J09 分布式事务。
  • 扩容再拆：8 张表也有装满的一天。从 8 扩到 16 要再迁一次，下钻第 1、3 步会讲为什么一开始常按 2 的幂规划，以及一致性哈希为什么在数据库分片里用得不多。
  • ShardingSphere-Proxy、读写分离、数据加密：ShardingSphere 的其他功能，这张图只用了 JDBC 形态的分片。

预测题

1. 切读到 100% 的第二天，有用户投诉“刚付完款，订单列表里还是待支付”。可这时候写还没切，旧表是主。最可能是哪一站出的问题？

读已经切到新表，写还是先写旧表、再跟着写新表。如果新表那一次写失败了（只记日志、等补偿），或者两次更新到达新表的顺序反了，新表上的状态就落后于旧表，而用户读的正是新表。这就是为什么切读期间仍要持续比对新旧数据（第 4 站的校验不是只做一次），以及为什么切读阶段要能马上拨回旧表。

从第 3、4、5 站推出：切读以后，新表成了用户看到的数据，但还不是写入的主。

2. 有人提议：“分片键改成 shop_id，商家查询就不用 ES 了。”会怎样？

商家查询便宜了，用户查询变贵了：1024 买过几十个商家的东西，“我的订单”要查 8 张表再归并，而这是 App 里最频繁的查询。还有热点：大商家一天几十万单，全挤进同一张表，分片就不均了。分片键要按最主要、最均匀的那个查询维度选，其他维度另存一份。

从第 2、6、9 站推出：一份数据只能按一个键分片。

3. Canal 挂了 10 分钟，恢复后从断点接着读。这 10 分钟里，用户和商家各看到什么？

用户没有感觉：下单、“我的订单”都走 MySQL（第 6、7 站），和同步链路无关。商家搜不到这 10 分钟里的新订单，状态也停在 10 分钟前；Canal 恢复后积压的 binlog 被追上，ES 慢慢变新。只要 binlog 还没被清理，就不会丢；如果挂的时间超过了 binlog 的保留期，就只能全量重灌。

从第 9、10、11 站推出：搜索链路是 MySQL 之后的一份异步副本，坏了只影响“找”，不影响“下单”。

4. 两年后 8 张表又快满了，要扩到 16 张。如果当初规则是 user_id % 8，扩成 % 16 时要搬多少数据？如果当初就建了 16 张表、先放在 2 个库里呢？

从 % 8 到 % 16：每张旧表里大约一半的用户要换到新表（余数 r 的用户会分成 r 和 r+8 两半），等于再做一次第 3～5 站。如果一开始就建 16 张表、2 个库各放 8 张，扩容时只要把一部分表整张挪到新库，用户到表的映射不变，不用逐行重新路由。这就是常说的“表多建一些，库少放一些”。

从第 2 站推出：路由规则里的数字一改，就是一次迁移。
