拆成微服务后的一次下单

还是用户 1024 下单 9527：2 件 88 号机械键盘，用券 MINUS20。交易靶场拆成了网关、商品、券、库存、订单五个服务，每个服务跑好几个实例，地址随时在变。这张全景回答：一个请求从 App 进来，网关、注册中心、配置中心、服务调用、限流熔断各在哪一跳出手；库存服务的一个实例卡住时，靠哪几站让下单“还能降级”，而不是整个订单服务被拖死。

场景：一个请求要穿过五个服务

谁
交易靶场。20:00:00，用户 1024 在 App 上提交订单 9527：2 件 88 号机械键盘，用满减券 MINUS20。1024 在新版下单逻辑（order-svc v2）的灰度名单里。
五个服务
网关 gateway ×2；订单 order-svc ×3（两个 v1、一个 v2）；商品 product-svc ×2；券 coupon-svc ×2；库存 inventory-svc ×2。各有各的库，互相只通过 HTTP 调用。
技术栈
和前几站一样用 Spring Boot 3.5.16、JDK 21。Spring Cloud 2025.0（Gateway、OpenFeign、LoadBalancer）加 Spring Cloud Alibaba 2025.0.0.0（Nacos 客户端 3.0.3、Sentinel 1.8.9）。Nacos 服务端是 3 个节点的集群，同时当注册中心和配置中心。
期望
正常时：0.05 秒内返回“9527 待支付”。库存服务出问题时：下单可以失败，但要很快失败、给一句人话；不能让订单服务的线程全卡在等库存上，连查订单、查物流这些不碰库存的接口也跟着挂。
演练
20:05，inventory-2 被一条慢 SQL 拖住，每个请求要 3 秒才回；进程还活着，和 Nacos 的连接也还在。

按设计推演 正常路径：网关 3 站加订单服务里 3 次串行调用，大约 40 ms。演练路径：第 1 秒里，落到 inventory-2 的那一半请求等满 800 ms 超时才失败；Sentinel 看到慢调用占比超过 40%，把“调库存”这条资源熔断 10 秒，这 10 秒里所有下单都直接降级，连本来会落到健康的 inventory-1 的请求也一样。直到第 11 站把 inventory-2 的流量摘掉，熔断器的半开探测才稳定成功。

本页没跑实验：Nacos、OpenFeign、Sentinel 三个知识点页会在交易靶场里把注册、摘流量、熔断真跑一遍。

全景图：十一站

每一跳的超时：外层要比里层的总和长

这一跳靶场的配置不配会怎样
App → 网关App 等 5 s用户自己会放弃，重点是别让后端在用户走了以后还在干活
网关 → order-svc路由 response-timeout 3 sGateway 默认不设响应超时，后端卡多久网关就陪多久
⑥ order → product连接 200 ms · 读 300 msOpenFeign 底层 feign.Request.Options 的默认值是连接 10 s、读 60 s。演练里不配的话，一个线程要陪 inventory-2 等满 3 s
⑦ order → coupon连接 200 ms · 读 300 ms
⑧ order → inventory连接 200 ms · 读 800 ms（⑤ 推来的）
⑧ 慢调用线Sentinel：RT > 500 ms 算慢比读超时短：还没超时、只是慢，也要算进熔断的统计

算一下：⑥⑦⑧ 是串行的，最坏 0.3 + 0.3 + 0.8 = 1.4 s，小于网关的 3 s；网关又小于 App 的 5 s。外层超时比里层的总和长，里层先放弃、先返回明确的错误，外层才不会在里层还在重试时就把请求丢掉。再算线程：每个 order-svc 实例每秒约 200 单，一半落到 inventory-2。读超时 800 ms 时，占着的线程约 200 × (0.5 × 0.8 + 0.5 × 0.04) ≈ 84 个，200 个还够；用默认的 60 s 读超时，就是陪着等满 3 s，200 × 0.5 × 3 = 300 个，线程池打满，连查订单这些不碰库存的接口也会排队。这就是三高地图里的 Little 定律。

一步一步走

图比屏幕宽，左右滑动看全图 →

1Nacos：每个实例启动时登记自己、订阅别人、拉配置

19:00，inventory-1 启动。Spring Cloud Alibaba 在应用就绪后，用 Nacos 客户端把“inventory-svc，10.0.1.31:8080，元数据 version=v1”注册成一个临时实例，和 Nacos 保持一条 gRPC 长连接。order-svc 启动时还会订阅 product、coupon、inventory 三个服务的实例列表，并从配置中心拉 order-svc.yaml。

为什么要它五个服务十几个实例，IP 随扩缩容、发版一直在变。把地址写死在配置里，每次变动都要改所有调用方。注册中心让“谁在哪”变成运行时查得到、变了会通知的数据。

往下一层注册发现与配置中心：Nacos · 部件来自哪个家族：待做 Spring Cloud 与 Spring Cloud Alibaba 怎么选 · 第一圈：RPC 原理里的服务发现

常出的事Nacos 2.x 起，临时实例靠这条长连接判断死活：进程被杀、连接断了，实例很快被摘掉；但进程卡住、连接还在时，Nacos 仍认为它健康（第 9 站就是这样）。注册中心只知道“活着”，不知道“好不好”。

2网关：验一次 JWT，把“你是谁”交给后面

请求先到 gw-1。一个全局过滤器（GlobalFilter）验 Authorization: Bearer … 的签名和过期时间，取出 sub=1024；先删掉请求里外部带进来的 X-User-Id，再写上 X-User-Id: 1024，往后转发。

为什么要它没有网关，五个服务各验一遍 token、各配一遍跨域和黑名单，规则一改要发五个版本。入口收拢以后，后面的服务只信网关传来的头。

往下一层网关：Spring Cloud Gateway、路由与鉴权 · 第一圈相关：Spring Security 与 token（单体里怎么验）、Spring MVC 请求关卡（过滤器链）

常出的事忘了先删外部传来的 X-User-Id，谁都能冒充 1024；或者后端服务直接暴露在公网，绕过网关就没人验。网关是 WebFlux 写的，在过滤器里调阻塞的 JDBC 或 Redis 同步客户端，会卡住 Netty 的事件循环线程。

3网关限流：先挡掉超出容量的那部分

网关上接了 Sentinel 的网关适配，给路由 order-create 配了 2000 QPS（压测得出的下单容量，再留余量）。20:00 这一秒是 1.2k，放行；大促峰值超过 2000 的部分直接回 429。

为什么要它在入口挡最便宜：被挡的请求不占订单服务的线程，也不碰数据库。等到第 8 站才发现扛不住，前面几跳的资源已经花掉了。

往下一层限流、熔断、降级：Sentinel、Resilience4j · 第一圈：三高知识地图（超时、舱壁、降级为什么缺一不可）

常出的事两台网关、每台配 2000，加起来就放进 4000（单机限流是按实例算的，要么除以实例数，要么用集群限流）。阈值拍脑袋定，不看压测，要么挡掉正常流量，要么根本挡不住。

4路由 + 灰度：lb://order-svc 落到哪一台

路由断言 Path=/api/orders/** 命中，目标是 lb://order-svc。网关的负载均衡器从本地缓存里拿 order-svc 的 3 个实例（Nacos 有变化会推过来）。灰度规则：X-User-Id 在 gray.users 里，只在 version=v2 的实例里挑，于是转到 10.0.1.13。

为什么要它新版下单逻辑先让 1% 的人用，出问题只影响他们，回滚就是改一行灰度名单，不用重新发版。路由和挑实例分开：路由决定“去哪个服务”，负载均衡决定“去这个服务的哪一台”。

往下一层灰度发布与流量治理 · 网关：Spring Cloud Gateway、路由与鉴权

常出的事灰度只做在网关这一层：1024 进了 v2 的订单服务，可订单服务再调库存时，又随机落到了旧版本，新老逻辑混着跑。全链路灰度要靠把灰度标记一路往下传（请求头），每一跳都按它挑实例。

5订单服务：读到的超时 800 ms，是 10 分钟前推来的

19:50，运维在 Nacos 控制台把 order-svc.yaml 里的 inventory.timeout 从 2 s 改成 800 ms。Nacos 通过长连接通知各个 order-svc 实例“配置变了”，客户端拉回新内容，Spring Cloud 发出刷新事件，绑在 @ConfigurationProperties 上的值被换成新的。第 8 站建 Feign 请求时读到的就是 800 ms。

为什么要它超时、开关、灰度名单、限流阈值，这些要在半夜出事时立刻改，不能等打包、发版、重启十几台。

往下一层注册发现与配置中心：Nacos（配置推送和刷新）

常出的事值改了却没生效：字段用 @Value 注入在普通单例 Bean 里，启动后就不会再变；或者值被复制进了一个启动时就建好的对象（比如已经创建的 HTTP 客户端）。配置中心挂了的时候，客户端靠本地快照照样能启动和运行。

6调商品服务：一个接口方法，变成一次挑实例的 HTTP 调用

代码里只写了 productClient.getSku(88)。OpenFeign 在启动时给这个接口生成了动态代理，调用时把方法和参数拼成 GET http://product-svc/skus/88；product-svc 不是域名，Spring Cloud LoadBalancer 从缓存的实例列表里按轮询挑出 product-1，换成真实 IP 发出去。

为什么要它不想在业务代码里拼 URL、挑实例、处理序列化。和 J04 全景的 gRPC 比，OpenFeign 走普通 HTTP + JSON，调试方便、跨语言简单，代价是报文更大、没有 HTTP/2 的多路复用（看用哪个底层客户端）。

往下一层服务调用：OpenFeign、Dubbo、负载均衡 · 拆成这几个服务的理由：服务怎么拆

常出的事LoadBalancer 默认把实例列表缓存 35 秒：Nacos 已经知道某台下线了，调用方可能还要往那台发一会儿。轮询不看对方快慢，一台慢的照样分到一半的请求。

7调券服务：同一套 Feign，第二次串行调用

couponClient.lock("MINUS20", 9527) 落到 coupon-2，把券锁给 9527。这一步和第 8 站在 J09 全景里是 TCC 的 Try，这里只看“调用”这一层。

为什么要它券是单独的服务，是因为营销规则变得最快、由另一个小组负责，和订单的发布节奏不一样。这就是“按领域、按团队拆”。拆开以后，原来的一次方法调用变成了一次可能超时、可能失败的网络调用。

往下一层服务怎么拆：按领域拆、拆多细、什么时候不该拆 · 服务调用：OpenFeign、Dubbo、负载均衡

常出的事拆得太细：一次下单要串行调七八个服务，每多一跳，延迟加一截，可用率再乘一个 99.9%。或者两个服务每次都得一起改、一起发布，说明边界划错了。

8调库存：这一次调用被 Sentinel 包着

inventoryClient.reserve(9527, 88, 2)。打开 feign.sentinel.enabled 以后，每次 Feign 调用外面都包了一层 Sentinel：资源名是 POST:http://inventory-svc/stock/reserve，进去前先问熔断器“现在能不能放行”，出来后记下这一次花了多久、有没有异常。20:00 这次落到 inventory-1，16 ms，冻结 2 件。

为什么要它超时只能限制“一次”等多久；对面持续出问题时，还是每次都要等满超时。熔断器要靠这里攒下的统计，才能判断“对面已经不行了，先别调了”。

往下一层限流、熔断、降级：Sentinel、Resilience4j · 服务调用：OpenFeign、Dubbo、负载均衡 · 超时的本质：时钟、超时与重试

常出的事给“冻结库存”这种写操作开自动重试：第一次其实成功了只是超时，重试又冻结一次。写接口重试前先要有幂等（9527 当幂等键），见 幂等设计。

9演练：inventory-2 卡住了，注册中心却说它健康

20:05，inventory-2 上一条没走索引的 SQL 把连接池占满，每个请求 3 秒才回。进程没死，和 Nacos 的长连接也在，所以它在实例列表里还是“健康”。order-svc 照样按轮询把一半的库存调用发给它，每次等满 800 ms 读超时，抛异常。

为什么要演它真实故障里，“慢”比“死”多得多，也难办得多：死了的实例注册中心很快会摘，慢的实例只有调用方自己看得见。

往下一层注册发现与配置中心：Nacos（健康检查到底查什么）· 慢 SQL 本身：J06 全景

常出的事如果读超时还是默认的 60 秒：每个 order-svc 实例要有约 300 个线程陪 inventory-2 等，200 线程的 Tomcat 被占满，连查订单都排队，网关那边 3 秒超时成片报错。一台库存实例拖垮了整个订单服务，这就是雪崩。

10熔断打开：后面的下单不再调库存，直接降级

规则是：统计窗口里至少 10 个请求、RT 超过 500 ms 的占比大于 40%，就熔断 10 秒。20:05:01 占比约 50%，熔断器从 CLOSED 变成 OPEN。这 10 秒里调用 reserve 时，Sentinel 直接抛 DegradeException，Feign 的 fallback 立刻返回“库存服务繁忙”，订单服务回一个 503 和“下单人数较多，请稍后再试”，2 ms 就结束，线程马上还回去。

为什么要它快速失败保护的是调用方自己：线程、连接不再被一个坏掉的下游占住，不碰库存的接口照常可用。降级保护的是用户体验：给一句人话，而不是转圈 5 秒后报错。

往下一层限流、熔断、降级：Sentinel、Resilience4j（熔断器状态机）

常出的事熔断是按资源算的，不是按实例：inventory-1 好好的，这 10 秒里的请求也一起被挡了。10 秒后半开，只放一个探测请求：落到 inventory-2 就立刻再熔断 10 秒；落到 inventory-1 就关上，可一半请求马上又慢，1～2 秒后再次熔断（下钻第 5 步实测来回了三轮）。降级逻辑里再去调一个远程服务，或者 fallback 偷偷返回“成功”，比不降级更糟。

11摘流量、恢复：把 inventory-2 从名单里拿掉

20:05:40，值班的人在 Nacos 控制台把 inventory-2 的权重调成 0（或者“下线”）。Nacos 推给订阅者的实例列表里就不再有它：Nacos 客户端挑实例时会去掉不健康、已下线和权重为 0 的。各 order-svc 的 LoadBalancer 缓存最多再用 35 秒，之后只会挑到 inventory-1；下一次半开探测成功，熔断器回到 CLOSED。

为什么要它熔断只是止血，解决不了“流量还在往坏实例上走”。真正的修复是不让流量去那台机器（再去查那条慢 SQL）。同一个动作，平时就是“灰度发布时先摘流量再停机”。

往下一层灰度发布与流量治理（摘流量、优雅上下线）· 注册发现与配置中心：Nacos

常出的事发版时直接 kill 实例：Nacos 摘掉它要一会儿，调用方的缓存还要再用一会儿，这段时间里调过去的请求全失败。正确顺序是先从注册中心下线，等调用方缓存过期，再停进程。

知识点地图

知识点名照抄学习地图。J10 的 7 个知识点里，只有“限流、熔断、降级”在三高地图里有过第一圈，其他 6 个都是新页。下钻顺序：先想清楚“为什么拆、怎么拆”；再学拆了以后最底下那一层，注册中心；然后是每一跳都在用的服务调用；网关和熔断都建立在这两样上；灰度要把网关、负载均衡、注册中心的元数据串起来，放后面；最后对照两套全家桶，把前面学到的部件归位。

站知识点状态下钻顺序和理由
6、7、8服务怎么拆：按领域拆、拆多细、什么时候不该拆 懂设计有页1先回答“为什么一次下单要穿过五个服务”。拆分决定了后面所有站存在的理由，也决定了第 7 站那种跳数会不会失控。
1、5、9、11注册发现与配置中心：Nacos 懂机制有页2管 4 站，是整张图的地基：网关和 Feign 挑实例用的列表、熔断规则和超时都从这里来。第 9 站“卡住却健康”要靠它的健康检查机制解释。
6、7、8服务调用：OpenFeign、Dubbo、负载均衡 懂机制有页3接口方法怎么变成一次挑实例的 HTTP 调用，和 Dubbo 的思路差在哪；负载均衡的缓存和策略是第 9、11 站的伏笔。J04 的 RPC 原理是它的第一圈。

预测题

1. 3 个 Nacos 节点全挂了 10 分钟。这 10 分钟里下单还能成功吗？新扩出来的 inventory-3 能接到流量吗？

已经在跑的实例照常下单：网关和 order-svc 手里都有缓存的实例列表，Nacos 客户端在本地还有一份快照，调用不经过 Nacos。不能做的是“变化”：inventory-3 注册不上，没人知道它；某台实例死了也没人通知调用方，只能靠超时、熔断在调用方这边自己扛。配置也改不了。注册中心是控制面，不在每个请求的路上。

从第 1、4、6、11 站推出：请求走的是本地缓存，Nacos 只负责“通知变化”。

2. 演练时，如果熔断规则从“慢调用比例”换成“异常比例 > 40%”，结果有什么不同？

因为配了 800 ms 读超时，落到 inventory-2 的调用最后都会抛超时异常，异常比例也是约 50%，同样会熔断，只是要等 800 ms 后异常出来才算数。如果没配读超时（默认 60 s），这些调用 3 秒后会成功返回，异常比例是 0，熔断永远不会打开，线程照样被占满。慢调用比例能看到“慢但没错”，这就是第 8 站慢调用线要比读超时短的原因。

从第 8、9、10 站推出：熔断器只能根据它统计到的东西做判断。

3. 有人为了“提高成功率”，给 reserve 打开了 LoadBalancer 的重试：失败后换一台实例再试一次。演练时会发生什么？

表面上成功率变高了：落到 inventory-2 的请求 800 ms 超时后换到 inventory-1 成功。但这一单的耗时变成 0.8 s 以上；更危险的是 inventory-2 其实可能在第 3 秒把冻结做完了，于是同一单冻结了两次（4 件）。重试写操作之前，库存服务要按 9527 去重；另外重试会让一个慢实例收到的请求不减反增。

从第 8、9 站推出：超时不等于没做，重试要以幂等为前提。

4. 运维把 inventory-2 的权重调成 0 以后，熔断器一直在“打开 → 半开 → 打开”之间来回跳了半分钟才稳定。为什么不是立刻恢复？

Nacos 很快把新列表推给了 order-svc，但 Spring Cloud LoadBalancer 自己还缓存着旧列表（默认 35 秒）。缓存过期前 inventory-2 还在列表里：半开时那一个探测落到它就再熔断 10 秒；落到 inventory-1 虽然会关上，可一半请求马上又慢，1～2 秒后又熔断。缓存过期后探测才一定落到 inventory-1。想更快，可以把 spring.cloud.loadbalancer.cache.ttl 调短；代价是每次挑实例更常去问 Nacos 客户端。

从第 6、10、11 站推出：变化要经过“Nacos → 客户端快照 → LoadBalancer 缓存”三层才到挑实例那一步。
