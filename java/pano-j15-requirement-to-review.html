一个需求从一句话到方案评审

交易靶场 11 月 30 日周一的周会上，运营说了一句话：“12.12 上满 300 减 40，要能和券叠加。”开发当场估了 3 天。五个工作日以后，这句话变成了 6 条规则、1 个三方签字的算例、2 个限界上下文、3 条 ADR 和一份过了评审的 8 页方案，业务代码一行还没写。这张全景回答三件事：一句话需求里没说出来的东西怎么问出来；服务的边界凭什么划在那里；怎么把选了什么、放弃了什么、为什么写下来，让别人能挑错，让半年后的人看得懂。

场景：一句话里藏着 4 块钱

谁
交易靶场，五个服务：网关、订单 order-svc、商品 product-svc、券 coupon-svc、库存 inventory-svc。你是开发小林，负责订单服务。出场的还有运营小周、架构师老陈，以及财务、客服、测试。
一句话
11 月 30 日周一周会，小周：“12.12 上满 300 减 40，要能和券叠加。”离 12.12 还有 12 天。小林当场估：“calcPrice 里加个 if，3 天。”
现状
下单时 order-svc 调 coupon-svc 验券，然后在 OrderService.calcPrice() 里自己算优惠，420 行。orders 表只记整单优惠一个数。
没说的事
这句话至少藏着三件事。先减哪个：右边那一单，两种顺序差 4 块钱。退一件怎么退：现在的表答不出来。满减不是券，没有人“持有”它，它该归哪个服务管。
期望
周五评审通过一份方案和 3 条 ADR。讲得清每个服务的边界为什么划在这；方案里写出被放弃的方案，以及它输在哪（地图上的两条过关标准）。

按设计推演 如果真的“加个 if，3 天”：if 加在券分支后面，等于先打折后满减，每单比运营想的多减 4 元。12.12 当天 3 万单同时用了满减和券，多让出去 12 万元，财务三天后对账才发现。12.15 用户 1024 退保温杯，退款补偿那段复制粘贴的代码不认识满减，按 9 折重算，退了 116.10，应该退 104.49。

本页没跑实验，人物、日期、金额都是交易靶场的设计。下钻的几页会在靶场代码里把这次改造真做一遍：补特征测试、搬算价、写 ADR。

1需求澄清：把一句话问成 6 个答案

周会后小林没有开工，约了运营、财务、客服一小时，拿用户 1024 那一单当例子，问了六个问题。为什么要叠加（目标是把客单价从 260 元拉到 300 元以上）？先减哪个？一单最多叠几个？退一件怎么退？预算多少，烧完怎么办？算不出价的时候怎么办？六个问题里，小周当场答得出的只有两个，其余的要回去和财务商量。

为什么要它一句话需求说的是业务方已经想到的那个解法，不是问题本身。先问出目标和边界情况，才知道这是 3 天的活还是 3 周的活。同一个问题，现在问是一小时的会，上线后才冒出来就是改数据、赔钱。

往下一层需求分析与业务建模：从业务问题到系统方案 待做

常出的事把一句话当需求直接开工。或者只问正向流程，不问退款、取消、改价这些逆向流程，而和钱有关的麻烦大多出在逆向。

2业务建模：规则表、算例、事件

六个答案落成三样东西。一张规则表：R1 先满减后用券；R2 一单最多 1 个活动加 1 张券；R3 优惠按行金额比例分摊到分，尾差归金额最大的一行；R4 退一件，退这一行的实付；R5 整单退才退券；R6 活动预算 50 万，烧完自动停。一个算例：用户 1024 那单应付 324.00，退 B 退 104.49，运营、财务、开发三方签字。再把流程按“发生了什么”排成一串事件：已算价、已下单、已支付、券已核销、已退款、预算已回补。

为什么要它规则表给人看，算例以后直接变成测试，事件序列里“谁先谁后、谁听谁的”是第 4 站划边界的原料。这一站全程用业务方的词，不出现表名和字段名，业务方才看得懂、纠得了错。

往下一层需求分析与业务建模 待做；事件怎么排、怎么用：DDD：限界上下文、聚合、领域事件 待做

常出的事规则只有文字没有算例。“按比例分摊”六个字，每个人心里是不同的算法，尾差给谁更是没人想过，到联调才发现三个人写出三个数。

3看现状：算价写在订单服务里，420 行

OrderService.calcPrice() 里是 7 种券类型的 if/else：下单时先调 coupon-svc 验券，再由订单服务自己算优惠。小林让 AI 助手梳理“所有读写优惠金额的入口”，它列出 6 处。自己再全仓库搜一遍 discount_amount，多出第 7 处：退款补偿的 MQ 消费者里，有一份复制粘贴的“按券重算”。然后给 calcPrice 补了 23 个特征测试，把现在的行为连同两处已知的错一起钉住。

// order-svc · OrderService.calcPrice()，节选
if (coupon.getType() == 3) {            // 折扣券
    discount = total.multiply(ONE.subtract(coupon.getRate()));
} else if (coupon.getType() == 7) {     // 去年双 11 的临时券，活动早结束了
    ...
}                                        // 满减该加在哪？加在这后面，就是先打折后满减

为什么要它方案要从现状出发。不知道营销规则已经漏进订单服务几处，划出来的边界只在纸上成立。没有测试钉住旧行为，后面搬代码时搬坏了也没人知道。

往下一层重构与偿还技术债 待做；AI 辅助研发：给足上下文、校验产出、对结果负责 待做

常出的事AI 给的调用链看着完整就信了。它漏掉的往往是 MQ 消费者、定时任务、反射调用这些不在主调用链上的入口。它的产出要用搜索和测试再核一遍，核的人对结论负责。

4划边界：同一个词“优惠”，两边是两个东西

运营说的优惠是一条规则：门槛、力度、能和谁叠、预算、有效期，天天在改。订单和财务说的优惠是一个事实：这一单的这一行便宜了多少钱，下了单就不能变。于是划成两个限界上下文。营销上下文管规则和算价，里面是活动 Promotion、用户券 Coupon 两个聚合，加一个算价的领域服务。订单上下文管事实，Order 聚合里新增每一行的价格快照，订单行只记 promotionId、couponId，不引用营销的对象。

两边靠两样东西连起来。下单前，订单问营销“这一车东西怎么算”。下单后，靠 OrderPaid、OrderRefunded 两个领域事件，通知营销去核销券、回补预算。

为什么要它边界划在“同一个词意思变了”的地方，两边才能各改各的。运营加一种活动，订单服务一行不用动；订单改退款流程，不用懂营销规则。

往下一层DDD：限界上下文、聚合、领域事件 待做；事件怎么可靠地送到：J08 全景：一条订单消息的一生

常出的事按数据表划边界（“优惠相关的表都归营销”），结果一个 Discount 类两边共用，谁改都要先问对方。或者聚合划得太大，改一行订单要把整个活动锁住。

5定形态：放进现有服务的模块，还是新建一个服务

营销上下文的算价部分落在哪，有三个候选。A：继续写在 order-svc 的 calcPrice 里。B：新建一个 pricing-svc。C：放进现有的券服务 coupon-svc，做成和抢券并列的独立模块。选了 C。下单本来就要调一次 coupon-svc 验券，把这次调用换成“算价加锁券”，链路不多一跳；也不用在 12 天里新建仓库、流水线、数据库和值班表。模块之间只许走公开接口，用 Spring Modulith 的 verify() 在测试里查越界引用。

同时写下什么时候走下一步：抢券高峰把算价的 P99 拖过 200 ms，而且把两个模块分开部署也压不住；或者营销分成了两个小组，发布要互相排队。

为什么要它限界上下文是逻辑边界，服务是部署边界，两者不必一一对应。先把逻辑边界划对、用工具守住，拆不拆服务可以等证据出现再定。反过来，边界没划对就拆，得到的是几个必须一起发布的服务。

往下一层架构演进：单体、模块化、微服务，什么时候走下一步 待做；多一跳要付什么代价：J10 全景：拆成微服务后的一次下单

常出的事为了“用上微服务”而拆。或者相反：模块之间没人守，半年后互相伸手调内部类，真到该拆的那天已经拆不动了。

6做取舍：三个难改的决定，写成 3 条 ADR

这一周做了三个以后很难改的决定，每个写成一页“架构决策记录”，放进仓库的 docs/adr/。ADR-007：算价放进 coupon-svc 的独立模块，不新建服务。ADR-008：叠加规则用“策略类加数据库里的活动配置”实现，不引入规则引擎。ADR-009：每一行的分摊结果在下单时存进订单，退款按它算，不回头找营销重算。

# ADR-009 分摊结果存订单快照，退款不重算
状态：已接受（2026-12-04 评审）
背景：部分退款要知道每一行当时便宜了多少；活动会结束，规则会改
决定：下单时把每行分摊写进 order_line.discount_share，退款只读它
放弃：退款时调营销重算。输在：活动结束或规则改过以后，算不回当时的数
后果：order_line 多 3 列；老订单没有快照，上线前要回填一次

为什么要它代码看得出“现在是什么样”，看不出“当时为什么不那样做”。半年后新来的人想去掉快照、想换规则引擎，翻到这一页就知道当时比过什么，在什么条件下可以推翻。

往下一层技术选型与架构决策记录（ADR） 待做

常出的事只写选中方案的优点，不写放弃了谁、什么情况下要重新看。上线后才补 ADR，写成了结果通报。决定被推翻时直接改旧的那条：应该新写一条，把旧的标成“已被取代”。

7细化设计：一种优惠一个类，按顺序挨个过

算价在营销模块里这样搭：每种优惠是一个 DiscountRule 实现，Spring 把它们全部注入成一个列表，一次算价就是让报价按 R1 的顺序依次经过这些规则，最后统一分摊。订单这边加一个 PricingGateway 接口，它的实现负责调营销，并把返回的报价翻译成订单自己的价格快照，订单的代码里不出现营销的类。这一层叫防腐层。表上，order_line 加三列：discount_share、promotion_id、coupon_id。

public interface DiscountRule {            // 策略：一种优惠一个实现类
    int order();                           // R1：满减 10，券 20
    Quote apply(Quote quote, Cart cart);   // 只改自己负责的那部分金额
}
// 责任链：Spring 注入全部实现，排好序挨个过
for (DiscountRule rule : rules) quote = rule.apply(quote, cart);

为什么要它420 行 if/else 的毛病是每加一种优惠都要改同一个方法、重测全部分支。换成策略以后，加“满减”是新增一个类，旧的 7 种一行不动。这两个模式并不新鲜：Spring MVC 的拦截器链、AOP 的拦截器链、MyBatis 的插件链都是这么搭的，学的时候就到这些源码里去认。

往下一层设计模式：在 Spring、MyBatis 里找到它们 待做；已有页里现成的链：代理里那十几层在干什么、MyBatis 插件与分页

常出的事为了模式而模式：只有两种情况，也建一套工厂加策略。或者规则之间偷偷共享状态，执行顺序一变结果就变，却没有一个算例测试能发现。

8写方案文档：8 页，下班前发出去

周四把前面七站的产出装进一份文档。目录八节：背景和问题（那句话加算例）、目标和非目标、现状、方案（上下文图、接口、数据模型、下单和退款两张时序图）、放弃的方案（指向三条 ADR）、风险和降级、上线灰度回滚和老订单回填、排期和待定问题。非目标写了三条：这次不做跨店满减，不让运营自己配规则，不改服务名。下班前发给评审人，请大家直接在文档上写批注。

为什么要它写文档是把脑子里“大概想清楚了”的东西，逼成别人能挑错的样子。非目标挡住范围越做越大；放弃的方案让评审不必把你走过的弯路再走一遍；回滚方案现在不写，出事那天就得现想。

往下一层技术方案文档与评审 待做；灰度和回滚怎么做：J14 全景：一次发布，从合并到回滚

常出的事通篇只有“怎么做”，没有“为什么不那样做”。没有非目标，评审会上被一句“顺便把那个也做了吧”带走。文档写了 30 页，没有人读完。

9评审会：45 分钟，只谈没谈拢的 3 件事

周五下午，架构师老陈、订单和营销两边的开发、测试、运营小周到场。批注在会前已经回完 14 条，会上只谈剩下的三个问题。“为什么不直接拆个新服务？”ADR-007 里写了，过。“老订单没有快照，12.12 之后退 12.11 的单怎么算？”文档漏了，补：上线前按老算法回填一次。“12.12 高峰算价超时怎么办，按原价下单，还是不让下单？”没有人能替业务回答，小周当场定：宁可提示稍后再试，也不能按原价扣钱。

结论是有条件通过：三条修改写进 v2，不再开会。纪要当天发出，每一条有负责人。

为什么要它评审是在写代码之前，让站在不同位置的人各挑一遍：架构师看边界和以后怎么演进，测试看怎么验，运营看规则对不对。一个漏洞在这里补是改几行字，上线后补是改数据、赔钱。

往下一层技术方案文档与评审 待做；会怎么组织、结论怎么落地：技术领导：规范、Code Review、带人 待做

常出的事没有人会前读文档，评审会开成了宣讲会。一小时都在争命名和框架，没人问“挂了怎么办”。会开完没有结论、没有负责人，下周同样的问题再吵一遍。

10落地：先搬后改，一串小 PR

任务拆成一串小 PR，分两段做。前一段只搬不改：把 calcPrice 的算价逻辑原样搬进 coupon-svc 的算价模块，订单改成调 PricingGateway，第 3 站那 23 个特征测试一个不改、全部通过；线上用开关控制新旧两条路，先两边都算，比对金额。后一段才加新东西：满减规则、叠加顺序、分摊快照，每个 PR 带着第 2 站的算例当测试。每个 PR 不超过 400 行，一个工作日内有人看完；AI 写的代码一样走 Code Review，提交的人对它负责。12.11 灰度 5%，12.12 零点活动开始。

为什么要它重构和加功能是两顶帽子，一次只戴一顶。搬的时候行为不变，金额出了差异一定是搬坏了；加的时候结构已经顺了，新规则只是多一个类。混在一个 PR 里，金额对不上时分不清是哪一半的错。

往下一层重构与偿还技术债 待做；技术领导：规范、Code Review、带人 待做；AI 辅助研发 待做

常出的事赶工期，把“搬”和“加”揉成一个 1800 行的 PR，没人审得动，只能点通过。欠下的债没有记下来（服务名还叫 coupon-svc、第 7 种过期的券类型还没删），过了 12.12 就真的没人还了。

预测题

1. 跳过第 1、2 站，周一下午直接在 calcPrice 里加 if。哪一天出事，出什么事，谁先发现？

12.12 当天什么事都没有：下单成功，优惠也减了，监控全绿。先出的是钱的事：if 加在券分支后面，每单多减 4 元，3 万单就是 12 万元，要等财务按运营的口径对账才发现，那是三天以后。再出的是退款的事：12.15 起有人退单件，补偿路径不认识满减，一笔多退 11.61 元，先发现的是客服或者财务，不是任何一条技术告警。

从第 1、2、3 站推出：没问顺序，就没有 R1；没问退款，就没有 R3、R4；没看现状，就不知道第 7 处入口。这类错不抛异常，技术监控看不见，只有业务对账看得见。

2. 评审会上有人说：“趁这次把算价拆成独立的 pricing-svc 吧，反正以后总要拆。”你怎么答？什么情况下答案要变？

现在不拆。拆了以后下单要先调券服务锁券、再调算价服务算价，算价服务又要回头查券，一次下单多出两跳，12.12 高峰多一个会挂的点；12 天里还要新建仓库、流水线、数据库和值班表。现在放进 coupon-svc 的独立模块，边界由 verify() 守着，以后要拆，搬的是一个接口干净的模块。ADR-007 里写了什么时候重新看：抢券高峰把算价的 P99 拖过 200 ms 而且分开部署也压不住，或者营销分成两个组、发布互相排队。出现任何一条，就新写一条 ADR 把 007 取代掉。

从第 5、6 站推出：“以后总要拆”不是现在拆的理由，要看的是证据有没有出现，以及到时候拆起来贵不贵。

3. 12.13 运营把活动改成满 400 减 50。12.15 用户 1024 退 B，退多少？如果当初 ADR-009 选的是“退款时重算”呢？

按快照，退 104.49：下单时 B 这一行分摊了 24.51，已经存在订单里，活动后来怎么改都和这一单无关。如果是重算：这一单 400 元，在新规则下正好满 400 减 50，(400 − 50) × 0.9 = 315，优惠变成 85，B 分摊 27.41，只退 101.59，用户少拿 2.90 元。要是活动这时已经下线，重算时只剩 9 折，退 116.10，平台多退 11.61 元。同一笔退款，三种时间点三个数。

从第 4、6 站推出：营销那边的优惠是规则，会变；订单这边的优惠是事实，不能变。退款读的应该是事实。

4. 为了赶 12.12，“搬算价”和“加满减”合成了一个 PR。灰度时比对发现 0.3% 的订单金额差 1 分钱。怎么查？分开做的话呢？

合在一起，嫌疑有两类：搬的时候把舍入方式搬变了（比如原来每步四舍五入，现在最后才舍入），或者新加的分摊把尾差分错了行。两类都会表现成差 1 分钱，只能一单一单对。分开做的话，第一段只搬不改，新旧两条路比对应该一分不差，有差异就一定是搬坏了，而且 23 个特征测试大概率在合并前就拦住了；第二段出的差异只可能来自新规则，拿第 2 站的算例一对就知道。

从第 3、10 站推出：特征测试钉住旧行为，“先搬后改”让每一步只有一个变量。

5. AI 助手写好了满减规则的实现和测试，测试全部通过。能合吗？

还不能。实现和测试出自同一个理解，如果它把 R1 理解反了，实现和测试会一起错、一起通过。要拿独立的标准来验：第 2 站三方签字的算例（应付 324.00，分摊 37.81、24.51、13.68，退 B 退 104.49），再补它没想到的边界：正好 300 元、299.99 元、分摊除不尽时尾差归谁、预算刚好烧完的那一单。然后照常走 Code Review。合进去以后，线上出了错，负责的是提交的人。

从第 2、3、10 站推出：给足上下文（规则表和算例要喂给它）、校验产出（用不是它写的标准）、对结果负责。

下一圈

算价真的要拆出去了

半年后 ADR-007 写的条件出现了：抢券高峰拖慢了算价。这次要学怎么把一个模块搬成一个服务而不停机：数据怎么分、流量怎么一点点切、旧路什么时候删，以及怎么写一条新 ADR 取代旧的。

营销和订单分成两个组

边界两边换成了两拨人。接口谁说了算，算价出错谁值班，一个需求跨两个组怎么排期。系统的边界和团队的边界会互相拉扯，难在两边都要动。

周三，需求变了

方案写到一半，运营说“券也要能叠两张”。哪些产出要重做，哪些因为边界划对了一个字不用改？这是对第 4 站最直接的检验。

按文档（已核对原文）：ADR 的写法出自 Michael Nygard 2011 年的《Documenting Architecture Decisions》：标题、背景、决定、状态、后果五节，状态有 proposed、accepted、deprecated、superseded，全文一到两页，放在项目仓库里顺序编号、编号不复用，被推翻的保留并标为 superseded。本页 ADR 里“放弃”那一行是按地图过关标准加的，对应 MADR 模板的 Considered Options。方案文档的结构参考 Malte Ubl《Design Docs at Google》：背景和范围、目标和非目标、设计本身、考虑过的其他方案、横切关注点；非目标指“本来可以算目标、但这次明确不做”的事。Martin Fowler《MonolithFirst》（2015）：成功的微服务大多是从长得太大的单体拆出来的，一开始就按微服务建的多数遇到大麻烦，有经验的架构师一开始也很难把边界划对。Spring Modulith 参考文档：ApplicationModules.of(…).verify() 检查模块之间没有环、只能访问对方的 API 包、（可选）只能依赖显式允许的模块。Google Engineering Practices：一个改动只要确实让代码整体更健康，即使不完美，评审人也应该倾向于通过。

出自书里的概念，下钻页再逐条引原文：限界上下文、聚合、领域事件、防腐层（Eric Evans《领域驱动设计》）；聚合之间只按 id 引用（Vaughn Vernon）；事件风暴（Alberto Brandolini）；用算例对齐需求（Gojko Adzic《实例化需求》）；重构的“两顶帽子”（Martin Fowler《重构》）；特征测试（Michael Feathers《修改代码的艺术》）。
