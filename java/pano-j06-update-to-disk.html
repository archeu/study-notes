一条 UPDATE 从应用到磁盘

用户 1024 付款成功，订单服务发出一条 UPDATE orders SET status='PAID' … WHERE id=9527。应用这边 7～9 ms 就拿到了“提交成功”，可实测提交两分钟后，磁盘上数据文件里的 9527 还是 CREATED：改过的那一页一直躺在内存里没写回去。这张全景回答：这条 UPDATE 在 MySQL 里经过哪 12 站，没写回数据文件凭什么也不会丢，从库又是怎么跟上的；J06 的 10 个知识点各管哪一站。

场景：订单 9527 改成已付款

谁
交易靶场的订单服务。用户 1024 买了 2 件 88 号商品，订单 9527，798.00 元，状态 CREATED。支付回调到了，付款接口要把它改成 PAID（接 J05 全景第 9 站）。
SQL
UPDATE orders SET status='PAID', paid_at=NOW(6) WHERE id=9527 AND status='CREATED'，在一个事务里，随后 COMMIT。
部署
MySQL 8.4.13 一主一从（两个容器，GTID 复制），InnoDB，默认配置：16 KB 页、buffer pool 128 MB、可重复读、binlog 为 ROW 格式、innodb_flush_log_at_trx_commit=1、sync_binlog=1。orders 表 100 万行，主键索引约 72 MB，另有二级索引 idx_user(user_id)。应用端 JDK 21 + HikariCP 6.3.3 + Connector/J 9.7.0。
期望
commit() 返回就算数：这之后主库断电、进程被杀，9527 都得是 PAID；从库很快也是 PAID；别的事务在提交前看不到半截状态，也改不了这一行。

实测 主库重启后的第一单：UPDATE 从磁盘读进 3 个页（根页 → 内节点页 → 叶子页，树高 3），服务器执行 2.3～3.9 ms；COMMIT 3.0～3.4 ms，几乎全在等 redo 和 binlog 落盘。应用这边借连接到还连接一共 7.4～9.3 ms。提交后 18～24 ms 从库读到 PAID。那一页提交 120 秒后仍是脏页，数据文件里还是旧值，靠 redo 兜底。

实测环境：本机 2 核 ARM，两个 MySQL 8.4.13 容器在同一台机器上，应用和数据库之间走本机回环。主库重启 3 次、各追踪一次，数字取 3 次的范围。

1HikariCP 借连接：事务从一条现成的连接开始

@Transactional 的事务拦截器向 HikariCP 借一条连接。这条连接在池子启动时就建好了：TCP 握手、认证都做过。然后调 setAutoCommit(false)，驱动给 MySQL 发一句 SET autocommit=0。从这一刻起，这条连接上的语句都属于同一个事务，直到 commit。

实测 借连接 6～9 µs，只是从池子里拿一条现成的；setAutoCommit(false) 0.30～0.74 ms，是一次网络往返。

为什么要它新建一条连接要握手、认证，毫秒级，池子把这笔开销挪到了启动时。事务必须绑在一条连接上，因为 MySQL 把事务状态存在这条连接对应的服务端会话里。

往下一层连接池与事务性能 · HikariCP 借连接为什么快 · 事务怎么借到这条连接：J05 全景第 7 站

常出的事事务里夹了慢操作，比如调第三方支付、发 HTTP，连接就被一直占着。池子默认 10 条，占满以后，后来的请求卡在借连接这一步，默认等 30 秒才报错。

2MyBatis → Connector/J：参数拼进 SQL，整条文本发出去

Mapper 方法变成一个 PreparedStatement，绑上 'PAID'、9527、'CREATED' 三个参数。Connector/J 默认不用服务端预处理（useServerPrepStmts=false），而是在客户端把参数转义后拼进 SQL，装进一个 COM_QUERY 包发给 MySQL。

实测 服务器语句历史里看到的就是拼好的整条：UPDATE orders SET status = 'PAID', paid_at = NOW(6) WHERE id = 9527 AND status = 'CREATED'。

为什么要它客户端拼接省掉了“先发模板、再发参数”的一次往返。转义由驱动来做，照样防得住 SQL 注入，前提是别自己拼字符串。

往下一层MyBatis 执行流程 · J05 全景第 9 站

常出的事MyBatis 里写 ${} 而不是 #{}，参数原样进了 SQL，这就是注入漏洞。另外，慢查询日志里记的是拼好的文本，同一个模板的语句要靠 performance_schema 的 digest 才能归成一类。

3连接线程：一个连接，服务端一个线程

MySQL 社区版默认“一个连接一个线程”。这条连接对应的服务端线程一直阻塞在读 socket 上，收到 COM_QUERY 就开始干活：语句的第一个阶段 starting 从这里计时。

实测 performance_schema 里这条语句的 starting 阶段 49～62 µs；查语句历史用的 THREAD_ID，就是这条连接专属的那个线程。

为什么要它每个连接的会话状态，包括事务、会话变量、临时表，都在这个线程手里，处理语句时不用到处去找。代价是连接越多，线程越多。

往下一层连接池与事务性能：池子开多大，和 max_connections、服务端线程数是什么关系

常出的事应用扩到 50 个实例，每个池子 20 条，就是 1000 个服务端线程，超过 max_connections（默认 151）直接报 Too many connections。池子不是越大越好。

4解析器 + 优化器：读懂 SQL，决定走哪个索引

解析器把文本变成语法树，检查表和列是否存在、有没有权限，然后打开表（Opening tables）。优化器看 WHERE id = 9527：id 是主键，又是等值，最多 1 行，直接定位，用不着比较其他索引。

实测 EXPLAIN：key=PRIMARY type=range rows=1。对照：WHERE user_id=1024 走 idx_user，估 6 行；WHERE sku_id=88 没有索引，type=index，要扫整个主键索引，估 995720 行。

为什么要它同一条 SQL 有很多种执行方式，差别可能是 1 行和 100 万行。优化器用统计信息估算每种方式的代价，挑最便宜的那种。

往下一层执行计划与 SQL 调优 待做 · 索引与 B+ 树 待做

常出的事WHERE 条件上没有索引，或者索引失效（对列套了函数、隐式类型转换），UPDATE 就要扫 99.6 万行。可重复读下，扫过的行都会被加锁，付款请求互相等成一串。

5InnoDB 沿 B+ 树找页：根 → 内节点 → 叶子

主键索引就是表本身，叫聚簇索引：整行数据存在叶子页里。InnoDB 从根页出发，按 9527 往下找：根页 4 指向内节点页 134，内节点页再指向叶子页 75。每个页 16 KB，先在 buffer pool 里找，找不到就从 orders.ibd 读进来。

实测 主库刚重启，buffer pool 是空的：Innodb_buffer_pool_reads +3，正好是根、内节点、叶子三页，updating 阶段 2.1～3.7 ms。同一页上再改订单 9530：读盘 +0，executeUpdate 0.81～0.99 ms。

为什么要它100 万行只要三层。一个非叶子页能放几百个指向下一层的指针（实测根页 6 条、内节点页 439 条），所以树又矮又胖，读三个页就能定位任何一行。

往下一层索引与 B+ 树 待做

常出的事buffer pool 太小，或者被一次大查询冲掉，热数据只能反复从磁盘读，所有 SQL 一起变慢。主键用 UUID 这类随机值时，插入会让页不停分裂，树变得又大又散。

6行锁：先锁住 9527，再动它

动手改之前，InnoDB 给这个事务加两把锁：表上一把意向锁 IX，意思是“我要锁表里的某些行”；主键索引里 9527 这条记录上一把 X 记录锁，REC_NOT_GAP 表示只锁这条记录，不锁它前后的间隙。锁一直持有到事务结束。

实测 data_locks：TABLE IX GRANTED，RECORD PRIMARY X,REC_NOT_GAP 9527 GRANTED。这时另一个事务想改 9527：等了 1.07 s，报 1205 Lock wait timeout。为了不久等，我们把它的等待上限设成了 1 秒，默认是 50 秒。

为什么要它两个事务同时改同一行，后一个必须等前一个提交或回滚，否则会互相覆盖。主键等值只命中一条，所以只锁这一条，不锁间隙。

往下一层事务、MVCC 与锁

常出的事事务开着迟迟不提交，比如在事务里等第三方回调，这一行就一直锁着，后面改它的请求全部等到超时。两个事务按相反的顺序锁两行，就是死锁，InnoDB 会挑一个回滚。

7undo：改之前，先把旧值记下来

InnoDB 把 9527 的旧值（status=CREATED、paid_at=NULL）写进 undo 日志。改完的新行里留一个指针指向这份旧版本，并记下是哪个事务改的。

实测 事务还没提交，另一个连接用普通 SELECT 读 9527，读到 CREATED：InnoDB 顺着 undo 指针，拼出了它应该看到的旧版本。INNODB_TRX：trx_rows_modified=1，隔离级别 REPEATABLE READ。

为什么要它一份旧值管两件事：事务回滚时照着它改回去；别的事务读这一行时不用等锁，直接读旧版本，这就是 MVCC。

往下一层事务、MVCC 与锁 · 日志：redo、undo、binlog 与两阶段提交 待做 · 对照 PostgreSQL：旧版本不放 undo，直接留在表里，所以要 VACUUM 待做

常出的事有个事务开着很久不结束，比如一个跑了一小时的报表查询，它可能还要读的旧版本都不能清理，undo 越积越多，别的读要沿着版本链走很远。

8改 buffer pool 里的页，写 redo

在内存里的叶子页 75 上把 status 改成 PAID，这一页成了“脏页”：内存里是新值，磁盘上还是旧值。同时把“页 75 的哪个位置改成了什么”写成一条 redo 记录，放进 log buffer。binlog 这时还不写，先攒在这个事务自己的 binlog cache 里。

实测 redo LSN +228～244 字节；页 75 变脏；binlog 位点不动。UPDATE 刚返回时，redo 有 1 次已经被后台线程 fsync，另外 2 次还没有：提交前落没落盘都行，提交时一定要落。

为什么要它把 16 KB 的页随机写回磁盘很慢；redo 只有几百字节，而且是顺序追加。先写小的 redo，页以后再慢慢写，崩溃了就靠 redo 重做。这个思路叫 WAL：先写日志，再写数据。

往下一层日志：redo、undo、binlog 与两阶段提交 待做

常出的事redo 容量太小（8.4 的 innodb_redo_log_capacity 默认 100 MB），写入高峰时很快写满一圈，InnoDB 只好急着刷脏页腾地方，所有写入一起卡顿。

9两阶段提交：redo 和 binlog 必须说法一致

应用调 commit()。MySQL 有两本账：InnoDB 的 redo 用来崩溃恢复，server 层的 binlog 用来复制和按时间点恢复。两本账必须一致，所以分两步走：InnoDB 先写 redo 的 prepare 记录并 fsync；再把 binlog cache 里的事件写进 binlog 文件并 fsync；最后 InnoDB 标记 commit。

实测 COMMIT 在服务器上 2.95～3.40 ms，其中 waiting for handler commit 2.87～3.32 ms，几乎全是在等落盘。redo 又写了 396 字节；binlog 多了 5 个事件、423 字节：Gtid、BEGIN、Table_map、Update_rows（147 字节，改前改后两份整行）、Xid。

为什么要它假如 binlog 写完就崩溃、redo 却没提交，从库有这条改动，主库没有；反过来也一样糟。有了两阶段，崩溃恢复时 InnoDB 看到 prepare 状态的事务，就去 binlog 里找它的 Xid：找到就提交，找不到就回滚。

往下一层日志：redo、undo、binlog 与两阶段提交 待做

常出的事为了快，把 innodb_flush_log_at_trx_commit 改成 2、sync_binlog 改成 0：实测每次提交从 4.2 ms 降到 1.2 ms，可机器一断电，最近约一秒内提交的事务可能丢掉，主库和从库也可能对不上。

10回 OK，连接还给池子

MySQL 给 UPDATE 回一个 OK 包（1 行受影响），给 COMMIT 再回一个。commit() 返回后，事务拦截器把连接还给 HikariCP。Hikari 发现 autocommit 被改过，会在收回前把它恢复成默认值。

实测 close() 0.41～0.76 ms。应用这边借连接、开事务、UPDATE、提交、还连接，一共 7.4～9.3 ms，不算旁边观察用的查询。

为什么要它commit() 返回，就是对用户的承诺：之后不管主库出什么事，9527 都是 PAID。这个承诺靠的是第 9 站已经落盘的 redo 和 binlog，而不是数据文件。

往下一层连接池与事务性能 · J05 全景第 10、11 站

常出的事OK 包回来之前网络断了：应用收到异常，可事务其实已经提交了。重试付款时，要靠 WHERE status='CREATED' 这样的条件和幂等号挡住重复。

11从库回放：binlog 推过去，再改一遍

主库的 binlog dump 线程把这 5 个事件推给从库。从库的 IO 线程收下，写进 relay log；applier 线程按 Update_rows 里的行，把从库的 9527 也改成 PAID。默认是异步复制：主库提交时不等从库。

实测 从库 applier 的记录：这个 GTID 从主库提交到在从库回放完，7.7～9.4 ms；应用轮询从库，18～24 ms 后读到 PAID。另外，主库重启时从库会断开，按 SOURCE_CONNECT_RETRY 重连，默认 60 秒。第一次实测就卡在了这里，后来改成了 2 秒。

为什么要它读请求可以分给从库，主库挂了从库能顶上。ROW 格式记的是“哪一行改前、改后是什么”，从库照着改就行，不用重新执行 SQL、重新判断条件。

往下一层主从复制、读写分离与复制延迟 待做 · 8.4 里的命令变化（SHOW BINARY LOG STATUS、SOURCE / REPLICA 新名字）见“版本：8.0 已停止维护，升级到 8.4 LTS 要注意什么” 待做

常出的事付完款马上跳转订单页，而订单页读的是从库：哪怕只延迟几十毫秒，用户也可能看到“待付款”，再点一次付款。一个改 100 万行的大事务，能让延迟涨到分钟级。

12刷脏页：数据文件里的旧值，迟早会被改过来

页 75 还在 buffer pool 里，是脏页。后台的 page cleaner 线程按脏页比例和 redo 用量，决定什么时候把它写回 orders.ibd。写回以后，检查点才能往前推，检查点之前的 redo 空间才能复用。

实测 提交后每 0.1 秒查一次，3 次运行都是：120 秒时页 75 还是脏的，检查点停在这条 UPDATE 之前的 LSN。这段时间里，磁盘上的数据文件写的是 CREATED，PAID 只在内存和 redo 里。

为什么要它同一页上的订单会被反复修改（实测里 9530 就在同一页），攒一阵一起写，比每改一次就写一次 16 KB 省得多。崩溃也不怕：重启时从检查点开始重放 redo，把页改回最新。

往下一层日志：redo、undo、binlog 与两阶段提交 待做 · buffer pool 和页：索引与 B+ 树 待做

常出的事崩溃后重启，要把检查点之后的 redo 全部重放一遍，脏页积得越多，恢复越久。写入压力大时脏页刷不过来，redo 快写满，InnoDB 只能同步刷页，所有写入一起卡住。

预测题

1. 第 9 站写 binlog 的时候 mysqld 被 kill -9，重启以后 9527 是 PAID 还是 CREATED？

看崩溃时 binlog 写到了哪儿。redo 的 prepare 已经落盘，可这个事务的 binlog 事件没写完整：重启后 InnoDB 发现一个 prepare 状态的事务，去 binlog 里找不到它的 Xid，就回滚，9527 还是 CREATED，从库也没收到，两边一致。binlog 已经完整写入并 fsync、只差 InnoDB 标记 commit：恢复时在 binlog 里找到了 Xid，就把它提交，9527 是 PAID，从库稍后也会收到。不管哪种，应用都没收到 OK，所以要按“结果未知”处理，去查一次再决定要不要重试。

从第 9、10 站推出：两阶段提交的意义，就是让“在不在”只由 binlog 里有没有这个事务说了算。

2. 提交后两分钟，页 75 还没写回数据文件，这时整台机器断电。重启后 9527 是什么？

PAID。数据文件里的页 75 确实还是旧的，但第 9 站提交前，这次修改的 redo 已经 fsync 过了。重启时 InnoDB 从检查点（实测停在这条 UPDATE 之前）开始重放 redo，把页 75 改回 PAID。代价是恢复时间：检查点之后的 redo 越多，重放越久。

从第 8、9、12 站推出：commit 的承诺落在 redo 上，不在数据文件上。

3. 有人把付款 SQL 写成 WHERE sku_id = 88 AND user_id = 1024 AND status = 'CREATED'，结果别的用户付款也开始变慢。为什么？

先看第 4 站：user_id 有索引，优化器多半会走 idx_user，问题不大。可如果条件只剩 sku_id（实测 EXPLAIN 是 type=index，估 995720 行），UPDATE 就要扫整个主键索引。可重复读下，InnoDB 给扫过的每一条记录加 next-key 锁，而且不满足条件的行也不会提前放锁，相当于把整张表锁住；别的用户改自己的订单，在第 6 站排队等这把锁。

从第 4、6 站推出。“扫到就锁、不提前放”是按文档的说法，这次没有实测锁的数量，留给靶场任务 2。

4. 从库因为一个大事务落后了 5 秒。用户付完款刷新订单页（读从库），会看到什么？哪里的监控先报警？

看到“待付款”，5 秒后自己变成“已付款”。有些用户会再点一次付款：这次请求走主库，WHERE status='CREATED' 不成立，影响 0 行，接口要能把这种情况当成“已经付过”处理，而不是报错。先报警的是从库的复制延迟监控（applier 的提交时间戳和当前时间之差）；主库和应用看起来一切正常。

从第 10、11 站推出：异步复制下，主库提交不等从库，读从库就要接受“读到旧值”。

下一圈

同一行被两个事务同时 UPDATE

用户连点两次付款，退款和付款同时到。第 6 站变成主角：谁先拿到锁、后到的那个等多久、等到以后它的 WHERE 还成立吗。再加一行就会碰上死锁。这是下钻第 3 步的下一圈。

主库宕机，从库顶上时，刚才那条 UPDATE 还在不在

异步复制下，commit 已经返回、binlog 还没推到从库时主库挂了，这一单就丢在旧主库上。难在怎么发现、怎么补：半同步复制、GTID 对账，以及切换以后旧主库怎么回来。

1000 万行上的一条慢 UPDATE

交易靶场这一站的任务。树变高一层，buffer pool 装不下热数据，第 5 站从读 3 页变成反复读盘；没索引的条件让第 6 站锁住一大片。难在要用慢查询日志、EXPLAIN 和锁视图三样东西，把“慢”拆到具体的站。

JDK 版本约定：交易靶场和 Java 地图的全景页用 JDK 21；单个知识点页的实验用 JDK 17。

档位：标准（全景页），做了一次真实链路实测：本机 2 核 ARM，Docker 里两个 MySQL 8.4.13 容器（GTID 异步复制，除下面两项外都是默认配置），应用端 JDK 21.0.13 + HikariCP 6.3.3 + Connector/J 9.7.0。为了让重启后的 buffer pool 真的是空的，主库关掉了 innodb_buffer_pool_load_at_startup 和 innodb_buffer_pool_dump_at_shutdown（8.4 默认都开，重启会自动把热页读回来）；从库的 SOURCE_CONNECT_RETRY 改成了 2 秒。程序 UpdateToDisk 用 JDBC 模拟 MyBatis 发出的同一条 UPDATE，另开一条连接旁路查询 performance_schema（打开了 stage 计时）、information_schema.INNODB_BUFFER_PAGE、data_locks、INNODB_TRX、SHOW ENGINE INNODB STATUS 的 LOG 段和 SHOW BINLOG EVENTS。主库重启 3 次、各追踪一次，表里的数字是 3 次的范围；耗时分段图用第 1 次；300 次自动提交的对比跑了 1 次。旁路观察本身会多占一点时间，所以“应用一共”只加了应用自己的 5 段计时。注意：Innodb_redo_log_current_lsn 这个状态变量在实测里没有跟着变，LSN 一律取自 INNODB STATUS。

按文档：两阶段提交和崩溃恢复时按 Xid 查 binlog 的做法；innodb_flush_log_at_trx_commit=2 时，mysqld 崩溃不丢、操作系统崩溃或断电可能丢最近约一秒的事务；可重复读下 UPDATE 对扫过的行加 next-key 锁；Connector/J 默认 useServerPrepStmts=false；max_connections 默认 151、innodb_lock_wait_timeout 默认 50 秒；HikariCP 默认池大小 10、借连接等 30 秒；8.4 删除了 SHOW MASTER STATUS，改用 SHOW BINARY LOG STATUS。代码：study-labs/java/java/pano-j06-update-to-disk。
