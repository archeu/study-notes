场景：用户 1024 给订单 9527 付款

谁
交易靶场的订单服务。用户 1024 买了 2 件 88 号机械键盘，订单 9527，应付 798.00 元，状态 CREATED。他在 App 上选支付宝，点“付款”。
请求
POST /orders/9527/pay，请求体 {"channel":"alipay","amountCents":79800}，带 HTTP Basic 认证头。
部署
Spring Boot 3.5.16（Spring Framework 6.2.19，内嵌 Tomcat），Spring Security，MyBatis（mybatis-spring-boot-starter 3.0.5），HikariCP 连接池。为了一条命令跑完，库用 H2 的 MySQL 兼容模式；J06 再换真 MySQL。JDK 21。
期望
返回 200 {"orderId":9527,"status":"PAID"}；金额对不上就整单回滚；“付款成功”短信只在事务提交以后发，而且不拖慢付款接口。

实测 SQL 发出时调用栈 131 层：Tomcat 30、Security 32、Spring MVC 34、AOP 和事务 7、MyBatis 10、JDK 反射和代理 11，我们写的 5。热身后每次付款 p50 87 ms，其中 82.7 ms 花在第 3 站算 BCrypt；去掉它，整段只要 2.4 ms，UPDATE 本身 0.1 ms。Controller 换成调 this.pay() 的那条路，金额错了订单照样变成 PAID。

实测环境：本机 2 核 ARM，JDK 21.0.13。程序在同一个 JVM 里启动应用，再用 JDK 的 HttpClient 走本机回环发请求。完整跑了 6 次：默认配置 3 次，把密码编码器换成不加密的 3 次。

1启动装配：请求来之前，舞台已经搭好

这一站不在请求里，但后面每一站用到的对象都是这时建好的。@SpringBootApplication 打开自动配置：classpath 上有 Tomcat 和 Spring MVC，就建内嵌 Tomcat 和 DispatcherServlet；有 HikariCP，就建 dataSource；有 MyBatis 的 starter，就建 SqlSessionFactory，并给 OrderMapper 接口生成一个 JDK 动态代理。OrderService 上有 @Transactional，它在初始化的最后一步被 BeanPostProcessor 换成了 CGLIB 子类，放进容器的是这个子类。

实测 启动 3.4～3.8 s，249 个 bean。orderService → OrderService$$SpringCGLIB$$0，orderMapper → jdk.proxy3.$Proxy100。我们只写了 6 个类。

为什么要它请求路上不能再去 new 对象、读配置、建连接池：这些又慢又容易出错，启动时做一次，之后每个请求只是在现成的对象之间调用。

往下一层IoC 与依赖注入 · Bean 生命周期（代理在哪一步换进去、循环依赖） · Boot 自动配置 · Boot 启动流程

常出的事以为自己拿到的是 OrderService，其实是代理：在 @PostConstruct 里调本类的 @Transactional 方法，这时代理还没换进去，调的又是 this，事务不生效。Boot 2.6 起默认禁止循环依赖，启动直接报错；硬打开以后，碰上 @Async 这类代理还会报“注入的是原始版本”。

2Tomcat：一个工作线程接下这个请求

Tomcat 的 Poller 线程用 epoll 发现连接上有数据，把它交给工作线程池里的一个线程 http-nio-exec-1。这个线程解析 HTTP 报文，包成 HttpServletRequest，然后进入过滤器链。从这里到第 11 站，全程都是这一个线程，中间没有换过。

为什么要它Servlet 规范规定了“一个请求交给一个线程，从头处理到尾”。Spring MVC 跑在这个模型上，所以后面的事务、安全上下文才能放进 ThreadLocal。

往下一层Spring MVC 请求处理 · 线程池参数（默认最多 200 个线程）回看 J02 线程池全景 · Poller 和 epoll 回看 网络 IO 模型

常出的事请求里有一步变慢（比如第 3 站的 BCrypt、第 9 站的慢 SQL），工作线程就被占住；200 个都占满以后，新请求在 Tomcat 的队列里排队，表现为“接口超时，但 CPU 和数据库都不忙”。

3过滤器链：先认出你是谁

先过我们自己的 TimingFilter，再过 Spring Security 的 FilterChainProxy：它对外只是一个 Servlet 过滤器，里面套着 11 个安全过滤器。BasicAuthenticationFilter 解出 Authorization 头里的用户名和密码，交给 DaoAuthenticationProvider 校验，通过后把“用户 1024”放进 SecurityContextHolder（一个 ThreadLocal）；最后 AuthorizationFilter 检查这个 URL 是否允许他访问。

实测 热身后每个请求 87 ms，其中这一站 82.7 ms。原因：第一次登录成功后，Security 发现密码是 {noop}，自动升级存成了 {bcrypt}$2a$10…，之后每个请求都要做一次 BCrypt 校验（单独量 82～85 ms）。不带账号的请求在这里就被 401 挡回，Controller 根本没进。

为什么要它安全检查必须在业务代码之前，而且要对所有 URL 统一生效，所以放在最外层的过滤器里，而不是让每个 Controller 自己判断。

往下一层Spring Security：认证与授权 · 过滤器和拦截器的区别：过滤器、拦截器与 AOP

常出的事每个请求都校验一次慢哈希：BCrypt 故意设计得慢，是为了防暴力破解，只该在登录时算一次，之后用会话或 token。按实测的 82 ms 推算，2 核机器光这一项就把吞吐压到每秒 24 个左右，CPU 打满而数据库很闲。

4DispatcherServlet：找到该调哪个方法

DispatcherServlet 是 Spring MVC 唯一的 Servlet。它问 HandlerMapping：POST /orders/9527/pay 归谁管？得到 OrderController#pay，路径变量 id=9527。调方法之前，先过一遍注册的拦截器 preHandle；拦截器已经知道要调哪个 Controller 方法，过滤器不知道。

实测 拦截器打印 preHandle：要调的是 OrderController#pay。

为什么要它一个统一入口，把“URL 对应哪段代码”“调之前之后做什么”“结果怎么写回去”这些每个接口都要做的事集中起来，Controller 只写业务。

往下一层Spring MVC 请求处理流程 · 过滤器、拦截器与 AOP 三道门

常出的事出了异常 Spring Boot 会把请求再转发到 /error，拦截器会被再调一次（实测里 400 那一次就是这样），在拦截器里计数、扣配额的代码要防重复。

5参数解析：把 JSON 变成 Java 对象，再校验

参数解析器挨个准备 pay() 的参数：@PathVariable 取出 9527；@RequestBody 交给 HttpMessageConverter，由 Jackson 把请求体读成 PayRequest(alipay, 79800)；有 @Valid 就用 Hibernate Validator 检查 @Positive 这些注解；Authentication 从第 3 站放进 ThreadLocal 的安全上下文里拿。

实测 热身后这一站 0.47～0.72 ms，是去掉 BCrypt 后最慢的一段。amountCents=-1 时返回 400，Controller 方法没有被调用。

为什么要它Controller 拿到的就是类型正确、校验过的对象，不用自己解析字符串、写一堆 if。

往下一层Spring MVC 请求处理（参数解析器、消息转换器） · Boot 4 把这里的 Jackson 换成了 Jackson 3（包名改成 tools.jackson）：待做 Spring Boot 3 到 4 升级

常出的事请求体里多了字段、日期格式不对、long 精度在前端 JS 里丢失，都出在这一站的 Jackson 配置上；升级 Jackson 大版本时，默认行为的变化也集中在这里。

6AOP 代理：你调的不是 OrderService 本身

Controller 里的 orderService 字段，指向的是第 1 站换进去的 CGLIB 子类 OrderService$$SpringCGLIB$$0。调用 pay() 先进这个子类，它查出这个方法上挂着哪些“通知”（这里是事务拦截器），排成一条链依次调用，最后才调到真正的 OrderService.pay()。

实测 调用栈里，OrderController.pay（第 103 层）和 OrderService.pay（第 114 层）之间隔着 CglibAopProxy$DynamicAdvisedInterceptor.intercept、TransactionInterceptor.invoke 等 10 层。

为什么要它事务、权限、缓存、重试这些横切的逻辑，不用写进每个业务方法里，加个注解，由代理在方法前后插进去。

往下一层AOP 与代理（JDK 代理和 CGLIB 怎么选、通知链怎么排）

常出的事代理只拦得住“从外面调进来”的调用。同一个类里 this.pay() 不经过代理（实测：事务没开）；private、final 方法 CGLIB 也覆盖不了。

7事务拦截器：借一条连接，绑到当前线程

TransactionInterceptor 读出 @Transactional 的属性（传播行为 REQUIRED、默认隔离级别），交给 JdbcTransactionManager：从 HikariCP 借一条连接，setAutoCommit(false)，把连接放进 TransactionSynchronizationManager 的 ThreadLocal。之后这个线程上谁要连接，拿到的都是这一条。

实测 进入 pay()：事务已开启=true，连接#548033506 autoCommit=false。走 this.pay() 时：事务已开启=false … autoCommit=true，金额不符照样把 9529 改成了 PAID。

为什么要它一个事务里的多条 SQL 必须用同一条数据库连接，而业务代码和 MyBatis 之间并不传连接参数，只能靠“绑在线程上”来对上号。

往下一层事务：传播、隔离、失效场景 · MyBatis 怎么接上 Spring 事务 · 连接池本身：连接池与事务性能

常出的事事务失效五兄弟：自调用（实测）、private 或 final 方法（CGLIB 覆盖不了；Spring 6 起 protected 和包级可见的方法已经能生效）、异常被自己 catch 掉、抛的是受检异常（默认只回滚 RuntimeException 和 Error）、在新线程里干活（ThreadLocal 带不过去）。还有一种是事务范围太大：在事务里调远程接口，连接和行锁跟着一起被占住。

8Mapper 代理：从接口方法找到 SQL

orderMapper 是 JDK 动态代理。调 changeStatus() 进入 MapperProxy，它按“接口名 + 方法名”找到启动时解析好的 MappedStatement（SQL 模板和参数映射），再交给 SqlSessionTemplate。后者看当前线程上有没有事务：有，就复用绑在事务上的那个 SqlSession，它底下用的正是第 7 站借来的连接。

实测 Service 里看到连接 #548033506，插件里发 SQL 用的也是 #548033506。

为什么要它业务代码只调一个接口方法，不写 JDBC 的打开、设参、关闭；而 SqlSessionTemplate 让 MyBatis 守 Spring 的事务规矩，不自己开连接。

往下一层MyBatis 执行流程 · MyBatis 接 Spring 事务 · 一级、二级缓存 · MyBatis-Plus

常出的事同一个事务里同样的查询查两次，第二次不发 SQL，直接拿一级缓存（SqlSession 跟着事务活）；没有事务时每次调用都是新的 SqlSession，行为就变了。

9Executor 和插件：SQL 真正发出去

CachingExecutor（二级缓存那一层）→ SimpleExecutor 准备 PreparedStatement，ParameterHandler 把 to=PAID, id=9527, from=CREATED 填进三个问号。StatementHandler 被插件包了一层：我们的 SqlTracePlugin 就挂在这里，分页插件、SQL 审计插件也挂在这类位置。最后 executeUpdate() 把 SQL 交给 JDBC 驱动。

实测 UPDATE orders SET status = ? WHERE id = ? AND status = ?，在驱动里 0.09～0.14 ms（内存库）。调用栈到这里一共 131 层。

为什么要它Executor 管缓存和批量，StatementHandler 管怎么发，插件让你不改 MyBatis 源码就能在这几个点上插逻辑。

往下一层MyBatis 执行流程 · 插件与分页 · SQL 到了数据库以后：J06 全景（待做）

常出的事WHERE status = 'CREATED' 这个条件是防重复付款的关键：影响行数是 0 就说明已经付过，必须检查返回值。分页插件拦错了方法、改写 SQL 出错，也在这一站。

10提交 + 事件：先提交，再发短信

pay() 正常返回，事务拦截器调 commit()，再把连接还给 HikariCP，解除和线程的绑定。pay() 里 publishEvent 发出的 OrderPaid，被 @TransactionalEventListener 暂存着，等到提交成功以后才分发；监听器上有 @Async，于是交给 task-1 线程去发短信，付款接口不用等它。如果抛了异常：回滚，事件直接丢掉。

实测 提交和还连接 0.19～0.24 ms。[task-1] 收到 OrderPaid(9527)，此时库里状态=PAID。金额不符的 9529：回滚后状态 CREATED，监听器没被调用。自调用那次没有事务，事件也被丢了。

为什么要它短信要是在提交前发，可能发出去了事务却回滚，用户收到“付款成功”而订单还是待付款。放在提交以后，再换个线程，就既不会说错话，也不拖慢主流程。

往下一层事务 · Spring 事件 · @Async 与线程池

常出的事提交以后、短信发出之前进程挂了，这条通知就丢了：进程内事件不可靠，要可靠就写本地消息表再投 MQ（J08、J09）。@Async 默认的线程池配置也要看一眼，别让它无限堆积任务。

11回程：返回值变成 JSON，一层层退出来

PayResult(9527, "PAID") 回到 DispatcherServlet，由同一个消息转换器（Jackson）写成 {"orderId":9527,"status":"PAID"}；拦截器的 afterCompletion 被调用；调用栈一层层退回过滤器，TimingFilter 记下总时长；Tomcat 把响应写回 socket，这个工作线程回到池里等下一个请求。

实测 写 JSON 加 afterCompletion 0.41～0.56 ms；服务端整段 85.3 ms（默认）、2.36 ms（去掉 BCrypt）。

为什么要它业务代码返回的是 Java 对象，HTTP 只认字节；而且请求里放进 ThreadLocal 的东西（安全上下文、事务资源）必须在线程还回池子之前清干净。

往下一层Spring MVC 请求处理 · ThreadLocal 为什么要清：ThreadLocal 泄漏

常出的事自己往 ThreadLocal 里放了东西却没在 finally 里清，下一个用到这个线程的请求会读到上一个用户的数据。异常没被 @ExceptionHandler 接住，用户看到的是 Boot 默认的错误 JSON（timestamp、status、error、path），前端拿不到能展示的原因。

预测题

1. 把监听器上的 @Async 去掉、注解换成普通的 @EventListener，短信服务卡了 3 秒后抛异常。用户会看到什么？

付款接口卡 3 秒，然后失败，订单还是 CREATED。普通 @EventListener 在 publishEvent 那一刻、在同一个线程里同步执行，这时还在 pay() 里面、事务没提交：连接和 9527 这一行的行锁被多占 3 秒；监听器的异常从 publishEvent 抛出，穿过 pay()，事务拦截器看到 RuntimeException 就回滚了。一个“发短信”的故障，变成了“付不了款”。

从第 7、10 站推出：事件默认是同步的，提交后执行和换线程，都是靠 @TransactionalEventListener 和 @Async 显式要来的。

2. 压测付款接口：50 个并发，订单服务 CPU 100%，数据库几乎空闲，QPS 只有二十几。最可能是哪一站？

第 3 站。每个请求都做一次 BCrypt，实测 82 ms 纯 CPU，2 核机器每秒最多算 2 ÷ 0.082 ≈ 24 次。Tomcat 的工作线程都在算哈希，后面的站根本没机会跑。修法是只在登录时校验密码，之后每个请求只验 token 或会话；要验证，在压测时抓一次线程栈，满屏都会是 BCrypt。

从第 2、3 站推出，数字来自实测的分段图；24 是推算，没有压测过。

3. 在 changeStatus() 之前再调一次 findById(9527)，数据库会收到几条 SELECT？走 this.pay() 那条路呢？

正常走代理：1 条。有事务时，SqlSessionTemplate 在整个事务里复用同一个 SqlSession，第二次同样的查询命中一级缓存，不发 SQL。走 this.pay()：2 条。没有事务，每次 Mapper 调用都新开一个 SqlSession、用完就关，缓存跟着没了，每次还各借一次连接（实测里两处看到的连接号就不一样）。

从第 7、8 站推出：MyBatis 的一级缓存活多久，取决于 Spring 事务活多久。

4. HikariCP 只有 5 条连接，第 9 站的 UPDATE 突然要 2 秒，同时来了 20 个付款请求。哪一站在等？会不会报错？

前 5 个请求在第 7 站各借走一条连接，在第 9 站等 2 秒；后 15 个卡在第 7 站借连接，而不是第 9 站，因为连接是在开事务时借的。它们排成三批，最后一批大约要等 6 秒再加自己的 2 秒，都在 HikariCP 默认的 30 秒借连接超时之内，所以不报错，只是慢。如果慢到 30 秒以上，报的是借连接超时，看起来像“连接池不够”，根子却在第 9 站的慢 SQL。

从第 7、9 站推出；连接池的超时参数见连接池与事务性能。

下一圈

用户手抖，连点两次付款

两个请求在两个 Tomcat 线程里同时走这十一站。WHERE status = 'CREATED' 能保证只有一个 UPDATE 成功，但第三方支付可能已经扣了两次钱。难在幂等要从哪一站开始做：网关、Controller、还是数据库的唯一约束。这要 J06 的行锁和 J09 的幂等。

付款后还要扣库存、发券、加积分

扣库存是 J04 那次 RPC，发券和积分在别的服务里，一个本地事务装不下了。第 10 站的“提交后发事件”要换成本地消息表加 MQ，难在哪一步失败了怎么补。这是 J08、J09 的全景。

升到 Boot 4，再打开虚拟线程

每个请求一个虚拟线程，第 2 站的 200 线程上限没了。第 7 站绑在 ThreadLocal 上的连接、第 3 站的安全上下文还成立吗？第 3 站那种纯 CPU 的活，换成虚拟线程会不会更快？

JDK 版本约定：交易靶场和 Java 地图的全景页用 JDK 21；单个知识点页的实验用 JDK 17。

档位：标准。做了一次真实链路实测：本机 2 核 ARM，JDK 21.0.13，Spring Boot 3.5.16（Spring Framework 6.2.19、Spring Security、内嵌 Tomcat），mybatis-spring-boot-starter 3.0.5，HikariCP，H2 内存库（MySQL 模式）。程序 RequestThroughSpring 在同一个 JVM 里启动应用，用 JDK HttpClient（HTTP/1.1）走本机回环发请求；默认配置跑 3 次，加 -Dlab.fast-auth=true（不加密、不升级的密码编码器）跑 3 次。分段时间是请求里打的计时点，取热身后 300 次的中位数；调用栈在 MyBatis 插件里用 Thread.getStackTrace() 抓取。表里和各站的输出原样摘自这几次运行。

按源码：spring-tx 6.2.19 的 ProxyTransactionManagementConfiguration 用 new AnnotationTransactionAttributeSource(false)，所以非 public（但不是 private）的方法上的 @Transactional 在 CGLIB 代理下也生效；spring-boot-jackson 4.1.2 依赖 tools.jackson.core:jackson-databind 3.x。按文档：@TransactionalEventListener 默认在提交后执行、没有事务时默认不执行；Boot 2.6 起默认禁止循环依赖；Tomcat 默认最多 200 个工作线程；HikariCP 借连接默认等 30 秒。代码：study-labs/java/java/pano-j05-request-through-spring。
