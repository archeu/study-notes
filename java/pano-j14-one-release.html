一次发布，从合并到回滚

交易靶场 11 月 26 日下午，订单服务从 1.8.3 发到 1.8.4。14:02 合并代码，7 分钟后 4 个 Pod 全部换成新版，探针全过，大盘一切正常；到了 17:41 晚高峰，Pod 开始被一个接一个杀掉，日志里却没有一行 OutOfMemoryError。这张全景回答三件事：代码怎么变成镜像，镜像又怎么一个个替换掉线上的老 Pod 而不断流；容器的边界（requests、limits、cgroup）和 JVM 怎么对上；出了事，怎么在 1 分钟内回到上一个好版本。

场景：发布时一切正常，晚高峰才出事

谁
交易靶场的订单服务 order-svc，跑在 Kubernetes 上：一个 Deployment，4 个副本，每个 Pod 的 requests 是 CPU 500m、内存 1Gi，limits.memory 也是 1Gi。Spring Boot 3.5、JDK 21。前面是 Ingress，后面是 J13 那套 Prometheus 告警。
怎么发
GitHub Actions 跑测试、打镜像，推到 Harbor；流水线最后改部署仓库里的镜像 tag，Argo CD 把它同步进集群。滚动策略 maxSurge: 1、maxUnavailable: 0：先多起一个新的，新的 Ready 了再停一个老的。
埋了什么雷
1.8.4 的合并请求顺手改了一行环境变量：JAVA_OPTS=-Xmx1g，是从老虚拟机的启动脚本里抄来的。1.8.3 用的是 -XX:MaxRAMPercentage=75，堆上限 768 MiB。现在堆一个人就能占满 1 GiB 的 limit，元空间、线程栈、直接内存都没地方放了。
期望
发布全程不断流；出事时说得清 Pod 被 OOMKilled 和 Java 抛 OutOfMemoryError 的区别，1 分钟内发出回滚（地图上的两条过关标准）。

按设计推演 下午流量小，堆只用到四五百 MB，探针、错误率、P99 都和 1.8.3 一样，发布“成功”。17:30 晚高峰，HPA 把副本扩到 6 个，扩出来的也带着 -Xmx1g。堆跟着流量涨过 800 MB，整个进程的内存越过 1Gi，内核直接把它杀掉：退出码 137，JVM 连抛异常、写堆转储的机会都没有。被杀的 Pod 上正在处理的下单请求全部断掉。

本页没跑实验：Docker、Kubernetes、资源与探针几个知识点页，会在本机的 kind 集群里把这次发布真做一遍，把这颗雷真踩一次。

1CI 流水线：先证明这次提交配得上一个版本号

14:02 合并请求进了 main，GitHub Actions 起一台干净的机器，跑 mvn -B verify：编译、单元测试、用 Testcontainers 起 MySQL 的集成测试，一共 3 分 10 秒。全绿才往下走，任何一步红了，流水线停在这里。

为什么要它在每个人自己的电脑上“能跑”不算数。每次合并都在同一个干净环境里从头构建、从头测试，坏的提交停在离它最近、修起来最便宜的地方。

往下一层CI/CD 与发布策略 待做

常出的事测试慢到大家想跳过，于是加一个“紧急发布跳过测试”的开关，然后它变成常态；或者没配依赖缓存，每次都从 Maven 中央仓库重新下载，3 分钟的流水线变成 10 分钟。

2docker build：多阶段构建，按层拆 jar

Dockerfile 分两个阶段。第一阶段在带 Maven 和 JDK 的镜像里打出 jar；第二阶段从 eclipse-temurin:21-jre 开始，用 Spring Boot 的分层模式把 jar 拆成四层依次 COPY：dependencies、spring-boot-loader、snapshot-dependencies、application。这次只改了业务代码，前三层命中缓存，50 秒构建完。

# 第二阶段：只要 JRE 和拆好的四层，变得最少的放最下面
FROM eclipse-temurin:21-jre
COPY --from=build /x/dependencies/ ./
COPY --from=build /x/spring-boot-loader/ ./
COPY --from=build /x/snapshot-dependencies/ ./
COPY --from=build /x/application/ ./     # 只有这一层每次都变

为什么要它镜像是一层层叠起来的，某一层变了，它上面的层全部重建。Maven、源码、测试报告留在第一阶段，不进运行镜像；依赖放下面、业务代码放最上面，改一行代码只重建最上面那一层。

往下一层Docker：镜像分层、多阶段构建 待做

常出的事整个 fat jar 一层 COPY 进去，改一行代码就是几十 MB 的新层，推、拉都慢；基础镜像写 latest，昨天能构建的今天行为变了。

3推到 Harbor：只推变了的那一层

docker push harbor.lab/trade/order-svc:1.8.4-3f9c2ab。仓库按每一层内容的摘要（digest）判断有没有，只有 application 那一层是新的，几秒就推完。tag 写版本号加 git 提交号，不用 latest。

为什么要它镜像是“构建一次，到处运行”的那个包：测试环境验过的，就是生产上跑的，一个字节不差。同一个 tag 永远指向同一份内容，回滚时才有一个确定的东西可以回。

往下一层Docker：镜像分层、多阶段构建 待做

常出的事用会被覆盖的 tag（latest、1.8）发布：有的节点缓存着旧内容、有的拉到了新内容，同一个 Deployment 里跑着两份代码，还很难看出来。

4部署清单：新 tag、环境变量、密钥，交给 Argo CD 同步

流水线最后一步，把部署仓库里 values.yaml 的 image.tag 改成新的，提交。Argo CD 收到 webhook，对比 Git 和集群，把 Deployment、ConfigMap、Secret 同步进去。这次合并请求还改了一行 env：JAVA_OPTS=-Xmx1g，雷就是这时候进集群的。数据库密码在 Secret 里，以环境变量注入 Pod，不进镜像，也不以明文进 Git。

为什么要它部署仓库是“集群应该长什么样”的唯一来源，这叫 GitOps：谁、什么时候、改了什么，都在 Git 历史里，回滚就是 revert 一个提交。镜像管“跑什么代码”，配置和密钥管“在哪个环境、用什么参数跑”，两样分开，同一个镜像才能从测试一路发到生产。

往下一层CI/CD 与发布策略 待做；Linux、脚本与配置密钥管理 待做

常出的事把密码写进 ConfigMap 或镜像；以为 Secret 是加密的，其实默认只是 base64，Git 里要用 Sealed Secrets 或 External Secrets 这类方案。还有：只改 ConfigMap，Pod 不会自己重启，新配置要等下次重建才生效。

5Deployment 控制器：建新 ReplicaSet，一个一个换

API Server 收到的新 Pod 模板里，镜像和 env 都变了。Deployment 控制器按模板算出一个哈希，新建 ReplicaSet order-svc-7c9d5f；按 maxSurge: 1、maxUnavailable: 0，先把新的扩到 1 个，老的保持 4 个。后面每有一个新 Pod Ready，就把老的缩 1、新的扩 1，直到 4:0 换成 0:4。

为什么要它这是声明式：只说“我要 4 个 1.8.4”，控制器不停地对比“想要的”和“现在的”，一步一步逼近。老的 ReplicaSet 缩到 0 但不删（默认留 10 个历史版本），回滚就是把它再扩回来。

往下一层Kubernetes 核心：Pod、Deployment、Service、Ingress 待做

常出的事不写策略就用默认的 25% / 25%：4 个副本时允许先停 1 个，发布那几分钟只剩 3/4 的容量，赶上高峰就被压垮。新 Pod 一直起不来时，滚动会停在半路，要到 progressDeadlineSeconds（默认 600 秒）才标记失败，它不会自己回滚。

6调度器：按 requests 挑一个节点

新 Pod 刚建出来时没有节点。调度器先过滤：哪些节点上还没被预订的 CPU 有 500m、内存有 1Gi；再给剩下的节点打分（比如尽量分散到不同节点），挑出一个，把节点名写回 Pod。

为什么要它调度只看 requests，不看实际用了多少，也不看 limits。requests 是“预订”，保证每个 Pod 至少有这么多；limits 是“上限”，超了 CPU 会被限速，超了内存会被杀。

往下一层弹性与资源：HPA、requests 和 limits、探针 待做

常出的事requests 写得比实际小，节点被超卖，大家一起挤；写得太大，Pod 一直 Pending，滚动卡在第 1 个新 Pod 上。

7kubelet 起容器，JVM 按 cgroup 定堆

选中节点上的 kubelet 让 containerd 拉镜像（节点上已经有前三层，只拉 application 那一层），再建一个 cgroup，把内存上限设成 1Gi，然后起进程。JVM 启动时读 cgroup，知道自己只有 1Gi 内存。1.8.3 按 MaxRAMPercentage=75 算出堆上限 768 MiB，剩下 256 MiB 给元空间、代码缓存、线程栈和直接内存；1.8.4 的 -Xmx1g 把堆写死成 1 GiB，剩下的是 0。Spring Boot 22 秒启动完。

为什么要它容器不是虚拟机，它的边界是内核的 cgroup 划出来的。JVM 要按这个边界定堆、定 GC 线程数和 availableProcessors；按宿主机的 64 GB 来算，就会一启动就越界。

往下一层Java 在容器里：内存、CPU（有页）；启动速度 待做

常出的事堆加上堆外超过 limit，内核直接 SIGKILL，Java 来不及抛 OutOfMemoryError，也不会写堆转储，这就是今晚的雷。反过来，堆真的满了，Java 抛 OOM，进程还活着、容器状态还是 Running，探针要是不查这个，Pod 就半死不活地挂着。

8探针：先等它启动完，再让它接流量

startupProbe 每 5 秒问一次 /actuator/health/liveness，最多等 2 分钟；它通过之前，另外两个探针都不开始。通过以后，readinessProbe 问 /actuator/health/readiness，回 UP，Pod 变成 Ready，被加进 Service 的 EndpointSlice；livenessProbe 接着定期问，连续失败就重启容器。1.8.4 启动正常，探针全过，内存的雷要到晚上才响。

为什么要它“进程起来了”不等于“能干活”。三种探针各管一件事：startup 管“启动完了没有”，免得启动慢被误判成死了；readiness 管“现在接不接流量”；liveness 管“要不要重启”。

往下一层弹性与资源：HPA、requests 和 limits、探针 待做

常出的事liveness 里也去查数据库，MySQL 抖 30 秒，所有 Pod 被一起重启，小抖动变成大事故；没有 startupProbe、liveness 又设得急，启动慢的应用还没起完就被杀，进入 CrashLoopBackOff。

9Service 和 Ingress 切流量，老 Pod 优雅退出

新 Pod 进了 EndpointSlice，Ingress 控制器和各节点的 kube-proxy 看到变化，开始把请求分给它。控制器随即把老 ReplicaSet 缩 1：被选中的老 Pod 先从 EndpointSlice 摘掉，preStop 里 sleep 10 秒，等各处都更新完，再收到 SIGTERM；Spring Boot 优雅停机，不接新请求、处理完手上的再退出。四轮下来约 2 分半。

为什么要它“从 EndpointSlice 摘掉”和“给进程发 SIGTERM”是同时开始的两件事，各节点和 Ingress 更新转发表要一点时间。不等一等，就会有请求被发到一个已经在关门的进程上。

往下一层Kubernetes 核心 待做；信号和退出码在 Linux、脚本与配置密钥管理 待做

常出的事没有 preStop，每次发布都有零星 502，大家习惯了，以为是网络抖；terminationGracePeriodSeconds（默认 30 秒）比 preStop 加应用停机的时间还短，到点被 SIGKILL，手上的请求照样断。

10发布后观察，晚高峰 HPA 扩容

14:09 换完，大盘上 1.8.4 的错误率、P99 和 1.8.3 一样，看了 15 分钟，发布单关掉。17:30 晚高峰，HPA 看到平均 CPU 超过 requests 的 70%，把副本从 4 扩到 6。扩出来的 2 个 Pod 用的是同一份模板，也带着 -Xmx1g。流量大了，堆一路涨，17:41 第一个 Pod 被杀。

为什么要它探针只能证明“能启动、能回健康检查”，内存、连接池、慢查询这类问题要真实流量压上来才显形，所以发布后要有一段观察。HPA 让副本数跟着负载走，不用为高峰常年多养机器。

往下一层弹性与资源：HPA、requests 和 limits、探针 待做；观察看什么在 J13 Prometheus 告警（有页）

常出的事只盯错误率，不看容器重启次数和内存曲线；HPA 按 CPU 扩，可瓶颈在数据库连接，越扩连接越多，数据库先倒。

11回滚：先回到上一个好版本，再查原因

17:45 告警“order-svc 10 分钟内重启 ≥ 2 次”响了。值班 kubectl describe pod，看到 Last State: Terminated, Reason: OOMKilled, Exit Code: 137，Java 日志里干干净净，没有 OutOfMemoryError。问“变了什么”：14:06 那次发布。17:47 在部署仓库 git revert 那个提交，Argo CD 同步，老镜像都还在节点上，6 个 Pod 不到 3 分钟全换回 1.8.3。

# 137 = 128 + 9，9 号信号是 SIGKILL：进程是被别人杀的
Last State:  Terminated
  Reason:    OOMKilled
  Exit Code: 137

为什么要它回滚比修 bug 快，也比修 bug 确定：先回到已知的好版本让用户恢复，原因明天再查。GitOps 下回滚就是 revert，有记录，也不会被下一次同步改回去。

往下一层CI/CD 与发布策略 待做；OOMKilled 和 Java OOM 的区别在 Java 在容器里（有页）

常出的事图快直接 kubectl rollout undo：Argo CD 开了自动修正（selfHeal）就会马上改回 1.8.4，没开也会一直显示不同步，下次同步照样回去。另外，rollout undo 只回退 Pod 模板，JAVA_OPTS 要是放在 ConfigMap 里，Pod 换回去了，雷还在。

知识点名照抄学习地图。6 个知识点里只有“Java 在容器里”已经有页（内存和 CPU），这次补它“下一圈”里的启动速度；其余 5 个都是新页。下钻顺序从下往上：先有镜像，再有 Pod，再给 Pod 定资源和探针；容器和 JVM 怎么对上放在资源之后；最后把这些串成流水线和发布策略，再收一页 Linux 和配置密钥的基本功。

这张全景没走到的

  • 服务网格（Istio、Linkerd）：交易靶场的服务治理在 J10 用的是 Spring Cloud，网格放进下一圈，和 J10 对照着学。
  • Helm 和 Kustomize 的模板写法：CI/CD 那页用到多少讲多少，不单独做页。
  • 集群本身怎么搭、怎么升级（控制面高可用、etcd 备份、节点升级）：那是平台团队的活，业务开发要懂的是“节点被腾空时，我的 Pod 会怎样”，放进下一圈。
  • 多集群、多机房发布：在 J12 多活容灾 那页。
  • 部署 AI 服务（GPU 节点、几个 GB 的模型镜像）：是 AI 地图站 10 的事，这一站打好 Docker 和 K8s 的底子。

复述练习

  1. 合上页面，画出 11 站，分成三组：流水线（1～4）、集群里（5～8）、上线以后（9～11）。
  2. 每站一句话，再把“同一份东西换了几次形态”讲出来：源码 → jar → 镜像层 → 带 tag 的镜像 → Pod 模板 → 绑了节点的 Pod → cgroup 里的进程 → EndpointSlice 里的一个地址。每一次是谁把它变过去的？

动手：交易靶场这一站

地图上 J14 给靶场的任务：靶场全部上 K8s（本机用 kind 或 k3s），配好探针、HPA 和滚动发布，演练一次发布回滚。下钻的几页会这样埋雷：

  1. 给 order-svc 写多阶段 Dockerfile，改一行代码重新构建，数一数哪几层变了、推了多少字节（第 2、3 站）。
  2. 在 kind 里部署 4 个副本，一边压测一边发布，数错误数；把策略换成默认的 25% / 25% 再发一次（第 5、9 站）。
  3. 去掉 preStop 再发一次，看错误数有没有变（第 9 站）。
  4. 让 liveness 检查数据库，停 MySQL 30 秒，看所有 Pod 会不会一起重启（第 8 站）。
  5. 埋这次的雷：-Xmx 等于 limit，压测到 OOMKilled；再换成堆真的泄漏，对比两种 OOM 留下的痕迹（第 7、11 站）。
  6. HPA 按 CPU 扩容，压测看副本数怎么变、多久扩上去（第 10 站）。
  7. 1 分钟内回滚：git revert 和 kubectl rollout undo 各做一次，计时（第 11 站）。

预测题

1. 如果 1.8.4 的问题是一个没上限的本地缓存，堆真的被占满，而 JAVA_OPTS 没改（还是 MaxRAMPercentage=75），你会看到什么？和今晚有什么不同？

堆上限是 768 MiB，进程总内存到不了 1Gi，内核不会出手。先是 GC 越来越频繁，接口越来越慢；然后 Java 抛 OutOfMemoryError: Java heap space，日志里看得到，开了 HeapDumpOnOutOfMemoryError 还会留下堆转储。进程不一定退出，容器状态还是 Running。如果 liveness 只看端口通不通，这个 Pod 就半死不活地一直挂着、一直接流量。今晚是反过来：进程被内核从外面杀了，Java 什么都没留下，只有 describe pod 里的 OOMKilled 和 137。

从第 7、8、11 站推出：OOMKilled 是 cgroup 的 limit 被越过，内核动手；Java OOM 是堆满了，JVM 自己报。所以要用 MaxRAMPercentage 把堆限在 limit 以内，把“越界”变成 Java 自己能报的错。

2. 发布策略换成默认的 maxSurge 25%、maxUnavailable 25%，并且挑在 17:35 晚高峰发。会怎样？

4 个副本时两个 25% 都是 1：控制器可以先停一个老的，同时起一个新的。新 Pod 要 35 秒才 Ready，这 35 秒里只有 3 个 Pod 在接流量，每个多扛三分之一。晚高峰每个 Pod 的 CPU 已经在 70% 上下，3 个 Pod 就要各扛 90% 以上，P99 明显变长，HPA 又要过一会儿才扩，扩出来的新 Pod 也要 35 秒。滚动的每一轮都重复一次。

从第 5、8、10 站推出：maxUnavailable: 0 用多一个 Pod 的资源换“容量不降”；Pod 启动越慢，这一点越要紧。

3. 有人在 readinessProbe 里加了“检查 MySQL 能不能连上”。某天 MySQL 主从切换，40 秒连不上。会怎样？

几十秒内所有 order-svc 的 Pod 都不 Ready，被从 EndpointSlice 里摘光，Service 后面一个地址都没有，Ingress 对所有请求回 503，连不碰数据库的接口（比如查商品快照的缓存）也一起挂了。MySQL 回来后，探针要再通过几次才把 Pod 加回去，恢复比 MySQL 本身还慢。要是写在 liveness 里更糟：40 秒后所有 Pod 被一起重启，又是 22 秒启动、一起冷启动。

从第 8、9 站推出：探针只回答“我自己还行不行”，依赖挂了应该由应用降级、由告警通知，不该让 Kubernetes 把整个服务下线。

4. 17:46 值班的人觉得 git revert 太慢，直接 kubectl rollout undo deployment/order-svc。会怎样？

先是生效的：Deployment 把上一个 ReplicaSet 扩回来，Pod 开始换回 1.8.3。但集群和 Git 不一致了。Argo CD 开了 selfHeal 的话，会很快把 Deployment 改回 Git 里的 1.8.4，又开始被杀；没开 selfHeal，界面上一直挂着 OutOfSync，下次有人同步时 1.8.4 又回来。正确做法是 revert 部署仓库；实在要先用 rollout undo 抢时间，就先关掉这个应用的自动同步，事后补上 revert。

从第 4、11 站推出：GitOps 下集群只是 Git 的投影，绕过 Git 改集群，改动迟早会被“纠正”回去。
