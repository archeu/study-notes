IO 与 NIO 基础：字节怎么进来，怎么出去

Java 的 IO 只在做两件事：搬字节，以及把字节和字符互相翻译。搬字节最贵的不是搬，而是每次找操作系统要数据的那一下（系统调用），所以永远要成块地搬：一次一个字节复制 2 MB 要 200 多万次系统调用、2 秒多，加一层 8 KB 缓冲就只剩两三百次。翻译这一步唯一要做对的是：写和读用同一个字符集，否则就是乱码。NIO 的 ByteBuffer 和 Channel 把“成块”这件事摆到了台面上，还能让内核直接在文件之间搬（transferTo），数据都不进 JVM。

①为什么需要：65 个字节进来，172 个字节出去

在全景第 1 站，这一步要解决的是：Tomcat 的 NIO 线程从 SocketChannel 把字节读进一个 ByteBuffer，交给业务的是一个 CoyoteInputStream；Jackson 再把这 65 个字节按 UTF-8 翻译成字符、解析成 record。第 11 站反过来，172 个字节的 JSON 写回连接。上一圈的网络 IO 模型讲的是“一万个连接要几个线程”；这一圈讲手里那几个字节：用什么搬、怎么翻译、怎么不出错。交易靶场里自己写 IO 的地方也不少：导出对账 CSV、读商品导入文件、复制上传的附件。

需求工作要用：导出、导入、上传、下载、读配置、调外部接口，每一个都在写 IO；最常见的线上问题是乱码、慢、文件句柄泄漏。⑤要能直接抄，⑥先讲这三个坑。

②没有它会怎样：一次一个字节地搬

最直白的写法：while ((b = in.read()) != -1) out.write(b);。能用，结果也对。可每一次 read() 都要穿过 JVM、进内核拿 1 个字节，再回来。

实测 复制同一个 2 MB 文件。系统调用次数用 strace -c 数，已减去 JVM 启动本身的那几十次；耗时是不带 strace 时单次运行。条形按对数刻度画。

Files.copysendfile 2 · 2.8 ms

  • 贵的不是字节，是“进内核”这一下：一次系统调用要切换到内核态再回来，搬 1 个字节和搬 8192 个字节，这部分成本差不多。
  • BufferedInputStream 读的时候还是一次一个字节，但它背后一次向内核要 8 KB，于是系统调用从 200 万次降到两三百次。它比自己用数组慢（64 ms 对 2.4 ms），是因为 Java 这边仍然调了 200 万次方法。
  • 缺的那一块：成块地搬（缓冲）；能让内核直接搬的，就别让数据进 JVM（Files.copy、transferTo 底下是 Linux 的 sendfile）。

不懂精华时的典型误用：给 FileReader 套了 BufferedReader，却没指定字符集。开发机是 UTF-8，部署到一台默认 GBK 的 Windows 服务器上，导出的对账文件全成了乱码（⑥ 坑 1）。

④原理：搬字节、翻译字符、三个指针

先知道这些
  • 系统调用：程序要读文件、读网络，只能请内核代劳（read、write），每次都要从用户态切到内核态再切回来。详见网络 IO 模型④的“一次读分两段”。
  • 字符集：同一个字“机”，在 UTF-8 里是 3 个字节，在 GBK 里是 2 个字节。字节本身不带“我是什么编码”的标记。
  • try-with-resources：见异常那页④-1。

④-1流：一层层套起来的装饰器

④-2字符集：同样的字节，换个字典就是乱码

  • 1“机械键盘”用 UTF-8 编码是 12 个字节（每个汉字 3 个）。实测 同一份对账文件的字节，用 UTF-8 读是 机械键盘，用 GBK 读是 鏈烘閿洏，用 ISO-8859-1 读是一串带重音的拉丁字母。字节一个没变，变的是“查哪本字典”。
  • 2按字节切断会切坏字符：实测 只拿前 4 个字节解码，得到 机�，第二个字只剩 1/3，变成替换字符 �。所以“按 1024 字节分块读，每块各自 new String”是错的，解码必须交给 Reader（它会把半个字符留到下一块）。
  • 3没写字符集时用“平台默认字符集”。JDK 17 及以前，它取决于操作系统和 locale（本机是 C.UTF-8，所以是 UTF-8；中文 Windows 默认是 GBK）；JDK 18 起默认一律 UTF-8（JEP 400）。靠默认值，代码换台机器就可能乱码。

④-3ByteBuffer：一块数组，加上三个指针

点按钮操作一个 16 字节的 ByteBuffer，看 position、limit、capacity 怎么动。先想好再点：flip 之后 limit 是几？

  • 1写模式：position 是下一个要写的位置，limit = capacity。put 一次，position 往后挪。
  • 2flip()：limit = position; position = 0，切到读模式：从头读，读到刚才写到的地方为止。忘了 flip，就会从写到的位置往后读，读到的是没写过的 0（实测 还剩 12 字节“可读”）。
  • 3compact()：把没读完的字节挪到最前面，切回写模式，接着往后写。网络读写里“一条消息没收完整”时就用它，Tomcat 解析 HTTP 请求头时也会遇到这种半截数据。clear() 不清数据，只是把指针复位，旧数据会被覆盖。
  • 4为什么一个 Buffer 读写共用、要手动 flip？因为它要直接交给 Channel 和内核：Channel 从 position 读到 limit、或者从 position 写到 limit，指针本身就是和内核交接的“这次搬多少”。代价是使用者必须自己记得切模式。

模拟和 ⑤ 的 JDK 17 实测一致（allocate(16) → put 5 字节 → flip → get 4 → compact，指针依次是 0/16、5/16、0/5、4/5、1/16），逻辑在 node 里跑过。

④-4Channel 和零拷贝：让内核自己在两个文件之间搬

  • 1堆内缓冲 vs 直接缓冲：ByteBuffer.allocate 在 Java 堆上，背后是一个 byte[]（实测 hasArray=true）；allocateDirect 在堆外，没有 array（hasArray=false）。做系统调用时，内核要一块地址不会被 GC 挪动的内存，堆内缓冲会先被 JDK 拷进一块临时的直接缓冲再交给内核，所以网络框架（Netty、Tomcat）都自己管理直接缓冲。代价是分配和回收慢，大小受 -XX:MaxDirectMemorySize 限制，泄漏了也不在堆转储里（⑥ 坑 4）。
  • 2为什么这样设计：java.io 的流是一个字节一个字节的抽象，好用但离操作系统远；NIO 把“一块内存 + 一个通道”直接摆出来，和操作系统的 read / write / sendfile 一一对应。业务代码不需要这么底层，所以 JDK 7 又在上面加了 Files 这一层“一行搞定”的工具，底下再按平台选最快的实现（比如 Linux 上用 sendfile）。

第一圈

注意事项：不知道就会出事故

坑 1没写字符集，换台机器就乱码← ④-2 默认字符集看平台
现象
new FileReader(f)、new String(bytes)、getBytes() 在开发机正常，部署到 Windows 或 locale 不对的容器里，中文全成了“鏈烘閿洏”。⑤ 实测 GBK 读
根源
不写字符集就用平台默认值，JDK 17 及以前它跟着操作系统走。
做法
所有字节和字符的转换都显式写 StandardCharsets.UTF_8；JDK 18 起默认就是 UTF-8，但写明仍然是好习惯（老代码可能跑在 8、17 上）。
坑 2UTF-8 的 CSV，Excel 打开是乱码历史原因
现象
对账文件在代码里读、在 Mac 上看都正常，财务用 Windows 版 Excel 双击打开全是乱码。
根源
Excel 打开 CSV 时，没有 BOM（文件开头的 EF BB BF 三个字节）就按系统的本地编码读，中文 Windows 上是 GBK。这是 Excel 的约定，和 Java 无关。
做法
给财务的 CSV 开头先写一个 '﻿'；或者直接导出 xlsx。程序之间交换的 CSV 不要加 BOM。
坑 3Files.lines、流、Channel 没关：文件句柄耗尽← ④-1 流背后是系统资源
现象
服务跑几天后报 Too many open files，新连接也接不进来（socket 也占句柄）。
根源
每个打开的流背后是一个操作系统文件描述符，数量有上限（常见 1024 或 65535）；Files.lines 是惰性的，不关就一直开着；GC 回收对象时不保证及时关闭。
做法
一律 try-with-resources；排查用 ls /proc/<pid>/fd | wc -l 和 lsof -p。
坑 4readAllBytes / readAllLines 读大文件← ④-1 一次读进内存
现象
导入一个 2 GB 的商品文件，OOM；或者上传接口用 getInputStream().readAllBytes()，被人传了个大文件拖垮。
根源
这两个方法把整个文件读进一个数组 / List，文件多大就占多少堆。
做法
大文件用 Files.lines 或 BufferedReader 一行行读，或者按块读；上传接口限制大小（Spring 的 spring.servlet.multipart.max-file-size）。
坑 5写完没关、没 flush：文件尾巴丢了← ④-1 缓冲攒着还没写
现象
导出的对账文件少了最后几十行，或者是 0 字节。
根源
BufferedWriter 攒满 8192 个字符才真正往下写，最后不满的那一截要等 flush() 或 close()。
做法
try-with-resources 关闭时自动 flush；要在中途让别人看到，手动 flush。
坑 6直接缓冲区用满或泄漏：堆没满却 OOM← ④-4 直接缓冲在堆外
现象
OutOfMemoryError: Direct buffer memory，可堆转储里看不到大对象；容器的内存用量比 -Xmx 大很多，被 OOM Killer 杀掉。
根源
直接缓冲区占的是堆外内存，Java 堆里只有一个很小的 DirectByteBuffer 对象指着它；要等这个小对象被 GC 回收，堆外那块才释放。
做法
不要频繁 allocateDirect，复用；设 -XX:MaxDirectMemorySize；容器内存要给堆外留余量（J03、J14 会再讲）。

第三圈

深处

为什么 BufferedInputStream 比自己用数组慢 25 倍

系统调用一样多（都是两三百次），差别在 Java 这一侧：buffered 模式仍然是 read() 一次一个字节，200 万次方法调用，每次都要进 BufferedInputStream.read，它是 synchronized 的（JDK 17 源码；JDK 21 源码里改成了内部锁，为的是不卡住虚拟线程），还要检查指针、边界。自己用数组则是 263 次 read(byte[])，每次一块。所以“包了 Buffered 就够了”只对了一半：能按块读的地方，就按块读。

内存映射文件：MappedByteBuffer

FileChannel.map 把文件映射进进程的地址空间，读写这块内存就是读写文件，由操作系统按页加载、回写，适合大文件的随机读写（数据库、搜索引擎的索引文件常用）。代价：映射期间文件删不掉（尤其 Windows），JDK 里没有正式的 unmap API（要等 GC），映射大小受地址空间限制。Kafka 的索引文件、RocketMQ 的 CommitLog 都用它。

Tomcat 里的这一层（接全景第 1、11 站）

Tomcat 的 NIO 连接器用 SocketChannel 把字节读进它自己管理的 ByteBuffer（读请求头时会遇到“半个请求”，就是④-3 的 compact 场景）；给业务的 request.getInputStream() 是一层 InputStream 包装（CoyoteInputStream），读的是同一块缓冲。写响应时，response.getOutputStream() 也先写进缓冲（默认 8 KB 左右），满了或请求结束才真正写回 socket。所以第 11 站那 172 字节是在请求结束、缓冲被 flush 时一次写出去的。

面试官会怎么问
字节流和字符流有什么区别？

字节流搬原始字节；字符流在字节流外面加一层按字符集的编解码。读写文本用字符流并写明字符集，读写图片、压缩包等二进制用字节流（④-1）。

为什么要用缓冲流？

每次 read / write 都是一次系统调用，成本主要在进出内核；缓冲把很多次小读写合并成一次 8 KB 的大读写（实测 200 万次 → 两三百次）（②、④-1）。

ByteBuffer 的 flip、clear、compact 有什么区别？

flip：limit = position，position = 0，写完转读；clear：position = 0，limit = capacity，不清数据，转写；compact：把没读完的挪到最前面，再转写（④-3）。

什么是零拷贝？Java 里怎么用？

数据在内核里直接从一个文件（或页缓存）搬到另一个文件或 socket，不拷进用户态。Java 用 FileChannel.transferTo / transferFrom，Linux 上底层是 sendfile；Files.copy 在 Linux 上也走 sendfile（实测）（④-4）。

堆内缓冲和直接缓冲怎么选？

短命的、小的用堆内；长期复用、频繁做 IO 的用直接缓冲（省掉一次拷贝），但分配回收慢、在堆外，要设上限、要复用（④-4、坑 6）。

自测

1. 用一句话说出这页的精华。

IO 就是成块地搬字节、用对字符集翻译字符；贵的是系统调用，所以要缓冲，能让内核直接搬就别让数据进 JVM。

2. 一次一个字节地 read，疼在哪？

每个字节一次系统调用，2 MB 就是 200 万次，2 秒多（②）。

3. 换台服务器导出文件就乱码，根源是哪条原理？

没写字符集时用平台默认，JDK 17 及以前它跟操作系统走；字节本身不带编码信息（④-2）。

4. 预测：⑤的 ByteBuffer 在 flip 之后又调一次 flip，再读，能读到几个字节？

第二次 flip 时 position 是 0（如果还没读），于是 limit 变成 0、position 变成 0，一个字节都读不到；如果已经读了 4 个，limit 变成 4，只能再读 0～3 这 4 个（④-3：flip 就是“limit = position，position = 0”）。

5. 预测：把⑤的 Copy 换成复制一个 2 GB 的文件，五种写法哪两种还能在几秒内完成？

byte 模式大约是 2 MB 的 1000 倍，半个多小时；buffered 大约一分钟（系统调用不多，但 Java 这边要 40 亿次方法调用）；array、Files.copy、transferTo 都只做几十万次以内的系统调用或 sendfile，受磁盘速度限制，几秒到十几秒。注意 transferTo 单次可能搬不完，要像⑤那样循环（②、④-4）。

6. 放回全景：第 1 站前后各发生了什么？这一页讲的东西坏了，整条链路会怎样？

第 1 站前面是客户端发出 65 字节，后面是第 2 站 Jackson 解码、反序列化。如果客户端用 GBK 发了 JSON，而服务端按 UTF-8 解，商品名就成了乱码，严重时 JSON 解析直接失败，返回 400；如果第 11 站的响应流没 flush 就被提前断开，客户端拿到半截 JSON。服务端自己读写文件时漏关流，句柄耗尽后连第 1 站的新连接都 accept 不进来，因为 socket 也占句柄。

档位：标准。实验在本机 JDK 17.0.20（2 核 ARM，locale C.UTF-8）：⑤ 的 Demo 4 段跑一次；Copy 对同一个 2 MB 随机文件五种模式各跑一次计时，再在 strace -f -c -e trace=read,write,sendfile,copy_file_range,pread64,pwrite64 下各跑一次数系统调用，并跑一次只启动 JVM 的基线相减。标“实测”的都来自这些运行。

按源码（本机 JDK 17 src.zip）：BufferedInputStream、BufferedReader、BufferedWriter 默认 8192，Files 内部 BUFFER_SIZE 8192，FileChannelImpl 的 transferToDirectly。按文档：JEP 400（JDK 18 默认 UTF-8）、NIO / NIO.2 的版本、Excel 打开 CSV 依赖 BOM 的行为、-XX:MaxDirectMemorySize。⑥-3 的“Tomcat 响应缓冲默认 8 KB 左右”按 Tomcat 文档写，没有在本机核对。
