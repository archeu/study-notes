Lambda、Stream、record、模式匹配：编译后变成了什么

这四样新语法有一个共同点：javac 只在字节码里留一条 invokedynamic，真正的实现等到运行时第一次执行那一行，才由 JDK 里的引导方法现场生成。Lambda 由 LambdaMetafactory 生成一个隐藏类；record 的 equals、hashCode、toString 由 ObjectMethods 生成；模式匹配的 switch 由 SwitchBootstraps 生成类型分派。Stream 不靠 indy，它的关键是“先搭流水线，终端操作一来，每个元素从头走到尾，再轮到下一个”。懂了这两条，就能推出它们各自的快慢和坑。

③相邻方案：它们分别替代了什么

新特性替代谁还在用旧办法的时候
Lambda / 方法引用匿名内部类需要多个方法、需要自己的状态字段时，还是写类
Streamfor 循环 + 临时集合热点路径、要提前 break 带复杂条件、要改外部变量时，for 循环更直接
record手写值对象 / Lombok @Value需要继承、可变字段、JPA 实体（要无参构造器和 setter）时，用普通类
sealed + 模式匹配instanceof 链、访问者模式、在类里写多态方法类型族要对外开放扩展（插件）时，用普通接口 + 多态

本页学四样的底层机制。选择规则：值对象一律 record；集合变换用 Stream，热点循环和基本类型大批量运算用 for 或 IntStream / LongStream；封闭的类型族用 sealed + switch，开放的用多态。

④原理：一条 invokedynamic，和一条流水线

先知道这些
  • 字节码和 javap：javap -c -p 能看到方法调用指令，见面向对象那页④-2（invokevirtual / invokeinterface）。
  • 函数式接口：只有一个抽象方法的接口，比如 Supplier、Function、Runnable。Lambda 只能赋给它。
  • MethodHandle：可以把它理解成“一个指向方法的、能被 JIT 内联的指针”，比反射的 Method 轻得多。

④-1invokedynamic：字节码里只写“到时候问引导方法”

为什么不直接编译成固定代码？如果 javac 把 Lambda 编译成匿名内部类、把 record 的 equals 写死成字节码，那这些实现就永远冻结在你的 class 文件里。用 indy，实现在 JDK 里：JDK 以后换更快的策略（比如 JDK 9 把字符串拼接从 StringBuilder 改成更快的拼法），老 class 文件不用重新编译就能享受到。代价是第一次执行要引导：实测 一个 Lambda 第一次求值 7.6 ms，下一处 0.4 ms，之后几乎为零。

④-2Lambda：一个私有静态方法，加一个运行时生成的隐藏类

LambdaJDK 8 起

  • 方法体被 javac 搬进本类的 private static lambda$main$0（捕获了 this 就是实例方法）
  • 运行时第一次执行时，LambdaMetafactory 生成一个实现 Supplier 的隐藏类，实测 类名 Demo$$Lambda$1/0x…，isHidden=true，不落成 class 文件
  • 没捕获变量：每次求值返回同一个对象（实测 == 为 true）
  • 捕获了变量：每次 new 一个，把捕获的值存进字段（实测 false）
  • 捕获的局部变量必须是 effectively final：存的是值的拷贝，允许改就会和外面对不上

匿名内部类JDK 1.1 起

  • javac 生成一个真实的 Demo$1.class 文件，一个匿名类一个文件
  • 每次求值都 new 一个对象
  • 总是隐式拉着外部类的 this（哪怕没用到），容易造成内存泄漏
  • this 指匿名类自己，不是外部类，容易写错
  • 能有自己的字段和多个方法

④-3Stream：先搭流水线，终端操作一来，元素一个一个从头走到尾

  • 1中间操作只是在搭链：filter、map、peek 每调一次，只是在后面接一个新的流水线阶段（源码里的 AbstractPipeline），什么都不执行。实测 搭好以后，peek 里一行都没打印。
  • 2终端操作才开工：findFirst、toList、reduce 一调用，流水线从尾往头把每个阶段包成一个 Sink（一个 Consumer），串成一条链，然后从数据源一个个推元素进去。
  • 3一个元素先走完整条链：66 过 filter 被拦下，88 过 filter、过 map、到 findFirst，拿到了就叫停，99、12、7 根本不碰（短路）。不是“先全部 filter，再全部 map”。
  • 4有状态的操作会打断这种流动：sorted、distinct 要看完所有元素才能决定第一个输出，于是在那里“蓄水”，前面的阶段要把全部元素都处理完。实测 加了 sorted 后，5 个元素全被 filter 看过。

订单行按顺序是 66（19.90）、88（299.00）、99（129.00）、12（9.90）、7（599.00），filter 留下单价大于 100 的，sorted 按单价从高到低。模拟和 ⑤ 的 JDK 17 实测输出一致，逻辑在 node 里跑过。

④-4record：编译器生成的类，和它的边界

  • 1record OrderLine(long skuId, String name, BigDecimal price, int qty) 编译成一个 final class OrderLine extends java.lang.Record：四个 private final 字段、一个按组件顺序的规范构造器、四个同名访问方法 skuId()……
  • 2equals、hashCode、toString 不是写死的字节码，而是一条 indy，引导方法 ObjectMethods.bootstrap 按组件列表生成（④-1）。所以“改了组件，三件套自动跟着变”。
  • 3紧凑构造器 OrderLine { if (qty <= 0) throw … }：只写校验和规范化，参数到字段的赋值由编译器补在最后。
  • 4class 文件里多了 Record 属性，列出组件名和类型。反射 getRecordComponents() 读的就是它，Jackson 靠它把 JSON 的键对上规范构造器的参数（全景第 2 站）。
  • 5只是浅不可变：字段是 final，可字段指向的 List 自己能变。实测 外面往原列表加一行，Cart 里跟着变成 3 行；在紧凑构造器里 List.copyOf 的 SafeCart 还是 2 行。

第一圈

注意事项：不知道就会出事故

坑 1在 Stream 里改外部集合、指望 peek 一定执行← ④-3 惰性和短路
现象
在 map 或 peek 里往外部 List 加东西、记日志、扣库存，结果有时没执行（短路了，或者 JDK 9 起 count() 能直接算出大小就跳过整条流水线），并行时还会丢数据。
根源
中间操作执不执行、对哪些元素执行，由终端操作决定；Stream 不保证副作用。
做法
中间操作只做无副作用的变换；要收集结果用 collect / toList；要做事用终端的 forEach。
坑 2parallelStream 占满全服务共用的线程池← ④-3 并行靠 ForkJoinPool
现象
某个接口用 parallelStream() 调了个慢的远程服务，结果其他所有用到并行流、CompletableFuture 默认池的地方一起变慢。
根源
并行流默认跑在 ForkJoinPool.commonPool()，全 JVM 共用一个，线程数是 CPU 核数减一，调用线程自己也干活。实测 2 核机器上只有 worker-1 和 main。阻塞在 IO 上就把这几个线程全占住了。
做法
并行流只用于纯 CPU 计算、数据量大（几万以上）、没有 IO；有 IO 的并发用自己配的线程池或虚拟线程（J02）。
坑 3大批量数字用 Stream<Long>，慢 40 多倍← ④-3 每个元素走一遍 Sink 链
现象
1000 万个数求和：for 循环 3.6 ms，LongStream 17.9 ms，Stream<Long>.reduce 160.9 ms。⑤ 第 4 段
根源
泛型流的元素是对象，每个数都要装箱成 Long、拆箱、产生垃圾；还要穿过一层层 Sink。
做法
数字用 mapToLong / LongStream；真正的热点循环用 for。业务里几十几百条订单行用 Stream 完全没问题，可读性更重要。
坑 4record 当 JPA 实体、当可变对象用← ④-4 final 字段、浅不可变
现象
Hibernate 要无参构造器和可写字段、要做懒加载代理（生成子类），record 都给不了，启动报错；或者 record 里放了可变 List，被外面改了。
根源
record 是 final 类、字段 final、只有规范构造器；不可变只到字段这一层。
做法
实体用普通类，DTO、命令、值对象、投影查询结果用 record；集合组件在紧凑构造器里 List.copyOf。
坑 5switch 遇到 null 直接 NPE；加了 default 就失去穷举检查← ④-5 穷举检查
现象
apply(null, sum) 抛 NullPointerException。⑤ 实测 为了“保险”加了 default -> sum，后来新增 Coupon 没处理，编译器不再提醒，悄悄不打折。
根源
为了兼容老 switch 的行为，没写 case null 时遇到 null 就抛 NPE；default 能匹配一切，编译器自然认为已经穷举了。
做法
sealed 类型族的 switch 不写 default；可能为 null 就显式写 case null -> 或在入口校验。
坑 6Lambda 里拉着大对象或外部 this← ④-2 捕获的值存在字段里
现象
注册了一个回调 Lambda 存进全局监听器列表，里面用到了某个大对象的一个字段，结果整个大对象（甚至整个外部实例）都回收不了。
根源
Lambda 捕获的是引用，存进生成类的字段里；用到实例字段等于捕获了 this。
做法
先把要用的值取到局部变量里再捕获；监听器记得注销。

第三圈

深处

Stream 源码里的那条 Sink 链

每个中间操作都是 AbstractPipeline 的一个子类实例，链表一样指向上游。终端操作调用 wrapSink，从最后一个阶段往前，把每个阶段包成 Sink：filter 的 Sink 在 accept 里判断一下再交给下游，map 的 Sink 变换后交给下游。然后数据源的 Spliterator 逐个 tryAdvance，把元素推进第一个 Sink。

短路靠 Sink.cancellationRequested()：findFirst 拿到元素后返回 true，源头就停止推送。sorted 的 Sink 在 accept 里只是攒进列表，在 end() 时才排序并把元素往下推，这就是“蓄水”。（按 JDK 17 本机源码 java.util.stream）

为什么第一次执行 Lambda 要几毫秒

第一次遇到 indy，JVM 要调 LambdaMetafactory：解析方法类型、用 ASM 风格的字节码生成器拼出一个隐藏类、定义它、链接。整个 JVM 里第一个 Lambda 还要初始化 java.lang.invoke 那一整套基础设施，所以最慢（实测 7.6 ms）。这也是 Spring Boot 启动时间的一小部分来源；JDK 的 CDS / AOT 缓存能把这些生成好的类存下来，下次启动直接用（见上一圈 JDK 页的“下一圈”）。

record 的 equals 为什么不写死

写死的话，每个 record 的 class 文件里都有一份逐字段比较的字节码。用 indy，所有 record 共用 ObjectMethods 里的一份实现，它按组件列表组合 MethodHandle，JIT 照样能内联。JDK 以后换更快的实现（比如对基本类型字段特化），已编译的 record 自动受益，这是 ④-1 那个设计理由的又一个例子。

面试官会怎么问
Lambda 和匿名内部类有什么区别？

匿名内部类编译期生成真实的 class 文件、每次 new 对象、隐式持有外部 this；Lambda 的方法体编进本类的私有静态方法，运行时由 invokedynamic + LambdaMetafactory 生成隐藏类，不捕获变量时复用同一个实例，只在用到时才捕获 this（④-2）。

Stream 是怎么执行的？中间操作和终端操作的区别？

中间操作只搭流水线，惰性；终端操作把各阶段包成 Sink 链，元素逐个从源头推到底；有短路操作时提前停止；sorted、distinct 这类有状态操作要先收齐（④-3、⑥-3）。

parallelStream 有什么风险？

默认用全 JVM 共享的 ForkJoinPool.commonPool，线程数是核数减一；里面做 IO 或耗时操作会拖慢所有用这个池的代码；数据量小、操作轻时，并行的拆分合并开销反而更大（坑 2）。

record 和 Lombok @Data 有什么区别？

record 是语言级的不可变值类型：final、字段 final、规范构造器、equals 等由 JDK 在运行时生成，反射能识别（isRecord、组件）；@Data 是编译期往普通类里插可变的 getter / setter，类型系统不知道它是“值”（④-4）。

switch 模式匹配为什么要配合 sealed？

sealed 的 permits 让编译器知道全部子类型，不写 default 时能检查是否穷举，新增类型时所有 switch 都编译失败、逼你处理（④-5，坑 5）。

自测

1. 用一句话说出这四样的共同点。

Lambda、record、模式匹配 switch 都编译成一条 invokedynamic，实现由 JDK 的引导方法在第一次执行时生成；Stream 是惰性搭链、终端操作时逐元素推过 Sink 链。

2. JDK 7 写同样的逻辑，最疼在哪？

匿名内部类、手写值对象、instanceof 加强转的样板太多，漏改 equals、漏处理一种类型都不报错（②）。

3. 在 map 里扣库存，有时没扣，根源是哪条原理？

中间操作是否执行由终端操作决定：短路时后面的元素不会进来，某些终端操作能直接算出结果就整条跳过（④-3，坑 1）。

4. 预测：⑤第 2 段如果把 findFirst 换成 anyMatch(l -> true)，peek 会打印几行？

anyMatch 也是短路操作，拿到第一个通过 filter 的就停：filter 看到 66、filter 看到 88、map 看到 88，三行，和 findFirst 一样。

5. 预测：把⑤第 2 段的 sorted 换成 limit(1)，filter 看到几个元素？

limit 是短路的有状态操作，但不用看完全部：88 通过 filter 后 limit 拿够 1 个就叫停，所以 filter 只看到 66 和 88 两个（④-3 第 3、4 条的区别：limit 不蓄水）。

6. 放回全景：第 6 站前后各发生了什么？这一页讲的东西用错了，整条链路会怎样？

前面是第 5 站 new 出 Order，后面是第 7 站扣库存。如果算价用 parallelStream，订单行只有一两行，拆分合并的开销反而更大，而且占用公共池，高峰时拖慢所有用到它的请求；如果在 map 里顺手扣库存，短路或跳过时就漏扣，第 7 站的条件更新也救不回来；如果优惠 switch 加了 default，新上线的优惠券类型悄悄不打折，第 10 站返回的金额就错了。第 2 站的 PlaceOrderCmd 若不是 record 而是普通类，Jackson 就得靠无参构造器和 setter，对象就成了可变的。
