压出来的才算数：全链路压测与容量规划

测试环境压出来的数，换到生产就不成立：机器规格、数据量、缓存命中率、下游依赖都不一样。所以大促前要在生产环境里压真实的链路。压测请求带一个标记，网关、RPC、MQ、线程池一路往下传，到了存储层就写进影子表，不碰真数据。压完读数时，单台容量不是“吞吐的最高点”，而是响应时间还满足目标时的最大 QPS；机器数 = 峰值 ÷（单台容量 × 安全水位），还要算上一个机房挂掉的情况。

②常见笨办法：在测试环境压一个接口，取平均值

笨办法为什么看起来对错在哪
在测试环境压安全，不影响用户测试机 4 核、生产 16 核；测试库 10 万行、生产 1 亿行，缓存命中率、索引深度都不同；结论没法按比例外推
只压抢券这一个接口它最热生产里同时还有下单、查订单、刷页面，它们共享网关、Redis、数据库连接；单接口压出来的容量偏高
看平均响应时间一个数，好汇报平均 20 ms 时 P99 可能已经 300 ms；用户体验和超时由尾部决定
用闭环工具（等回来再发）JMeter 线程组默认就这样服务一慢，压测端就自动发得少，排队被藏起来了（上一页讲过）
直接在生产压，不做隔离数据最真压测下的单、领的券写进真表：真用户收到压测券、报表多出几万单
不懂精华时的典型误用做了影子表，却只在 Controller 入口判断压测标记。业务里有一步“异步发券”放进了线程池，标记在那里丢了，压测券写进了真表。⑤ 的实验 2 用 100 个请求复现了这件事：100 行全进了真表。

③工具和路线

要做的事常用工具

一次全链路压测的路线

  1. 1 定模型从去年大促或线上日志里取接口比例：抢券 60%、看页面 25%、下单 10%、查订单 5%；按这个比例造流量，不是只压一个接口。
  2. 2 打标透传压测请求带 x-pt: 1，每一跳都把它带下去，见 ④ 标记怎么传。
  3. 3 影子存储MySQL 影子表、Redis key 前缀、MQ 消息属性，见 ④ 影子存储。
  4. 4 挡板短信、支付、第三方物流这些出了公司的调用，压测流量一律走假实现（挡板），直接返回固定结果。
  5. 5 阶梯加压低峰时段（如凌晨）从 10% 目标量开始，每级稳定几分钟再加；设好熔断条件（错误率、真实用户 RT 超标就自动停）。
  6. 6 读数、算容量找拐点、定单台安全容量、算机器数和限流值，见 ④ 容量怎么算。
  7. 7 复盘瓶颈修了再压一轮，直到容量够；结论写进容量报告，限流值写进配置中心。

④背后的机制：标记怎么传、数据写到哪、容量怎么算

先知道这些 为什么能在生产压：压测流量和真实流量走同一套机器、同一个数据库实例，所以测出来的才是真容量；只在“最后写到哪”上分开。 ThreadLocal：每个线程一份的变量。请求在哪个线程上，标记就跟着哪个线程；换了线程就看不到了。

机制一：标记要跨过每一跳

标记在一个进程内靠线程上下文（ThreadLocal）带着走，跨进程靠“请求里的某个位置”带着走。任何一跳漏了，后面的数据就写错地方。

这一跳标记放在哪谁来搬容易漏的地方
App → 网关HTTP 头 x-pt: 1压测工具网关要校验来源，防止外部伪造这个头
网关 → 券服务HTTP 头，进程内放 ThreadLocal网关过滤器、服务端 Filter请求结束要清掉，否则线程复用时“传染”给下一个真实请求
进程内换线程提交任务时拷贝一份包装 Executor、TransmittableThreadLocal、Agent@Async、CompletableFuture、自建线程池（⑤ 实验 2）
服务 → 服务Feign 请求头、Dubbo attachmentRPC 拦截器新接入的 HTTP 客户端没加拦截器
服务 → MQ → 消费者消息属性（user property）发送拦截器写入，消费拦截器读出消费者的线程是 MQ 客户端的，入口要重新设置上下文
→ Rediskey 前缀 pt:封装的 Redis 客户端Lua 脚本里写死的 key 名
→ MySQL表名后缀 _pt 或另一个库数据源路由、ShardingSphere 影子规则手写 SQL、存储过程、定时任务（定时任务根本没有入口请求）

为什么 InheritableThreadLocal 也不行：它只在创建子线程的那一刻拷贝父线程的值。线程池里的线程早就创建好了，被反复复用，拿到的是创建时那个请求的值，或者什么都没有。所以正确的拷贝时机是提交任务时，不是创建线程时。

机制二：影子存储三种隔离程度

影子表影子库独立影子实例
做法同一个库里建 t_coupon_user_pt同一个 MySQL 实例，另一个 schema另一套 MySQL
测得准不准最准：共享 buffer pool、redo、连接较准：共享实例资源不准：压不到真库
风险路由错一次就写进真表；压测会真实地挤占真实请求的资源同左，但误写真表要跨库，概率小一些最安全
适合核心链路、要测真容量多数团队的折中只验证功能、或者不敢在真库上压

影子表要提前灌入和真表量级相近的数据：空表的 B+ 树只有一两层，压出来的查询比生产快得多。热点行例外：抢券的库存行本来就只有一行，影子表里也只放一行。

机制三：容量怎么从曲线上读出来

数据来自 ⑤ 的实验 1（同一台 2 核机器上既压又被压，只看形状）。左轴实际 QPS（实线），右轴 P99（虚线，对数刻度）。

  • 吞吐峰值约 1590 QPS，再加压吞吐不升反降：线程和 CPU 都满了，多出来的请求只在排队。
  • 安全容量P99 < 50 ms 这条线在 800～1200 之间被突破。单台容量取 800，只有峰值的一半。容量要按目标定，按峰值定就是让系统常年在排队边缘。
  • 为什么拐得这么急利用率越接近 100%，排队时间增长得越快（响应时间那一页的排队曲线）。从 1200 到 1500，QPS 只多了 25%，P99 涨了 50%；到 1700，P50 都过了 160 ms。

容量计算器：从单台容量到机器数

默认值是全景的数：峰值 2 万、单台 4000。计算方式写在页面脚本里，在 node 里跑过几组数。

static Runnable wrap(Runnable r) {
    Boolean captured = PT.get();                 // 提交时（还在请求线程上）拍一张快照
    return () -> {
        Boolean old = PT.get();
        PT.set(captured);                        // 执行时放进工作线程
        try { r.run(); } finally { if (old == null) PT.remove(); else PT.set(old); }   // 用完还原
    };
}

⑥刻意练习

第一圈 · 压测事故

1压测数据写进了真表⑤ 实验 2← ④ 标记要跨过每一跳
现象
真用户收到压测券，报表多出几万单。
根源
标记在线程池、MQ 消费者或新接入的客户端上断了，DAO 以为是真实请求。
做法
所有线程池统一包装；存储层“看不到标记就拒绝写影子之外的压测账号数据”双保险：压测用户 ID 段固定，写真表时发现是压测账号就报警。
2标记“传染”给真实请求← ④ ThreadLocal
现象
压测结束后，零星的真实订单出现在影子表里，用户说“下的单不见了”。
根源
入口设了标记却没在 finally 里清掉，线程被下一个真实请求复用。
做法
设置和清除成对写在同一个 Filter 的 try/finally 里；包装任务执行完还原旧值（⑤ 的 wrap）。
3影子数据是空的，压出来的数偏乐观← ④ 影子存储
现象
压测说能扛 5000，大促当天 3000 就慢了。
根源
影子表几千行，全在 buffer pool 里；Redis 影子 key 少，命中率 100%；真实环境不是这样。
做法
影子表按真表量级造数据（脱敏复制或按分布生成）；缓存要预热到和生产相近的命中率再开始读数。
4压着压着，真实用户受影响了← ④ 共享资源
现象
真实请求的 P99 从 30 ms 涨到 800 ms，客服电话打进来。
根源
影子表和真表共享实例：压测本来就是在真实地挤占资源。
做法
低峰时段压；阶梯加压；自动熔断条件看的是真实流量的错误率和 RT，超了立刻停施压机。
5定时任务、回调没有入口请求← ④ 容易漏的地方
现象
压测下的单到了“30 分钟未支付自动取消”的定时任务里，任务按真实单处理，回补了真实库存。
根源
定时任务从数据库里捞数据，没有 HTTP 入口，标记只能从数据本身判断。
做法
影子表的数据由单独的影子任务处理；或者在数据上带压测标识列，任务按列区分。
6把吞吐峰值当容量⑤ 实验 1← ④ 容量曲线
现象
报告写“单台 1588 QPS”，按这个数配机器，大促时 P99 上秒。
根源
吞吐峰值处已经在大量排队，响应时间不可接受。
做法
容量 = 满足 RT 目标的最大 QPS；报告里同时写目标（P99 < 50 ms）和对应的 QPS。

第二圈 · 练习（由易到难，做对了会看到什么）

  1. 换成闭环：把 CapacityLab 改成 64 个线程“发一个等一个”。你会看到 P99 远低于开环的数、QPS 自动停在 1500 左右：闭环把排队藏起来了。
  2. 线程数翻倍：工作线程从 8 改到 16 再压。拐点会右移，但不会翻倍：CPU 只有 2 核，0.3 ms 的 CPU 开始成为瓶颈。说出新瓶颈是什么。
  3. CompletableFuture：在 ShadowTagLab 里加一种 CompletableFuture.runAsync（默认用 ForkJoinPool）的写法，预测影子表几行，再跑。
  4. 传染：把入口的 PT.remove() 去掉，压测请求和真实请求交替各 100 个走线程池，数真实请求有几行进了影子表。（坑 2）
  5. 算一份容量报告：用实验 1 的数据，假设峰值 1 万 QPS、两个机房要能单独扛，用 ④ 的计算器算机器数，写成三句话：目标、单台容量、台数。

第三圈 · 深处

  • 流量录制回放用 TCPCopy、GoReplay 或网关日志把真实流量录下来，加速回放；比手写脚本更接近真实的接口比例和参数分布，但要处理写请求的幂等和脱敏。
  • 容量的“木桶”全链路里每一层都有自己的拐点：网关、券服务、Redis 分片、MQ、数据库。整条链路的容量是最小的那个，所以报告要列每一层在目标流量下的水位，而不是只写入口 QPS。
  • 常态化压测只在大促前压一次，中间几十次发版可能已经把容量改了。大厂会在每周低峰时段自动跑一轮小规模全链路压测，容量变化当作回归问题处理。
  • ShardingSphere 影子库它的 shadow 规则可以按列值（如 user_id 在压测号段）或 SQL 注释里的 hint 把 SQL 路由到影子数据源，适合已经用了 ShardingSphere 的项目（接 J11 分库分表）。

自测

1. 用一句话说出这一页的精华

容量要在生产环境的真实链路上压出来：压测请求带标记，每一跳（含线程池、MQ、定时任务）都把它带下去，到存储层写进影子表；读数时单台容量取满足响应时间目标的最大 QPS，而不是吞吐峰值，机器数再按水位和机房故障算。

2. 在测试环境压，疼在哪？

机器规格、数据量、缓存命中率、下游依赖、混合流量都和生产不同，压出来的数不能按比例外推；而大促出问题的恰恰是这些差异。

3. 坑 1（写进真表）的根源是 ④ 的哪一条？为什么 InheritableThreadLocal 救不了？

机制一：标记在进程内靠 ThreadLocal 跟着线程走，换了线程就丢。InheritableThreadLocal 只在创建线程时拷贝，而线程池的线程是复用的，早在压测前就创建了；正确的拷贝时机是提交任务时。

4. 预测：⑤ 实验 1 的服务，工作线程从 8 改成 200，拐点会到多少？

不会到 8 → 200 的 25 倍。线程多了以后，瓶颈换成 CPU：每个请求 0.3 ms CPU，2 核理论上限约 6600 QPS，压测端还在同一台机器上抢 CPU，实际会低得多；线程太多还会增加切换开销。加线程只能把瓶颈推到下一个资源，这就是“木桶”。

5. 预测：两个机房各 4 台、单台 4000，峰值 2 万。机房 A 挂了，B 会怎样？要多少台才稳？

B 只有 4 × 4000 = 1.6 万的安全容量，扛 2 万已经超出，P99 会像实验 1 的 1500 那一级一样上涨，网关限流必须同时降到 1.6 万以下。要让 B 单独扛住 2 万且水位不超过 95%，每个机房要 6 台，共 12 台（计算器默认值就是这个结果）。

6. 放回全景：第 2 站前后各发生了什么？如果跳过第 2 站，后面哪几站的参数就没有依据了？

前面是第 1 站算账（按假设估），后面是活动当天的第 3～10 站。跳过压测，第 5 站的限流值、第 6 站券服务的台数、第 9 站消费者的速度、第 12 站每个机房要放几台，都只能靠拍；第 1 站发现的热点行问题也不会暴露，直到开抢那一秒。

档位：标准。本机跑过（2 核 ARM 虚拟机，JDK 17）：⑤ 的两个实验各跑 1 次，页面上的 QPS、P50、P99 和行数都来自这次输出；④ 的容量曲线按这组数据画；容量计算器的算法在 node 里跑过几组数。压测端和服务在同一台机器上，绝对数字只代表这台机器。

按文档：InheritableThreadLocal 在创建子线程时拷贝父线程的值（JDK Javadoc）；ShardingSphere 提供影子库功能，按列值或 SQL hint 路由。全链路压测的标记透传、影子表、挡板是业界通行做法，各公司的实现细节不同，本页不对应某一家的产品。
