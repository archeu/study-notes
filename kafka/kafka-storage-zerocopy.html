KAFKA · SEGMENT · .INDEX · .TIMEINDEX · PAGE CACHE · SENDFILE · RETENTION

只往文件末尾追加，缓存和搬运都交给内核

Kafka 把每个分区存成一串只追加的段文件（segment），每段配一本稀疏索引：按 offset 找消息，先二分索引，再往后扫几 KB。它自己几乎不缓存数据。写进来的数据先留在操作系统的页缓存里；发给消费者时调用 sendfile，内核直接把页缓存里的数据交给网卡，数据不进 JVM，这就是零拷贝。“Kafka 为什么快”的答案，就是这几件事配合起来。

②老办法：自己设计会怎样

存储是 Kafka 里的一个机制，没有现成的“老技术”可替换。那就假设没有 Kafka，用手上会的东西存消息、发消息。最先想到的四种做法都能跑，但各疼一处，Kafka 的设计正好是冲着这几处去的。

试 1 · 存进 MySQL一条消息一行

  • 每条消息一次随机写，还要写 redo log 和 binlog
  • 消费完 delete，表里留下空洞，还得定期整理
  • 多一个下游，就要多记一份“谁读到哪了”

Kafka：不建表，只往文件末尾追加；删除就是删掉最老的整段文件。

试 2 · 一个大文件只追加写是快了

  • 旧数据删不掉，除非把整个文件重写一遍
  • 想读第 1 亿条，只能从文件头一条条数过去

Kafka：切成一段一段（segment），文件名就是这段第一条消息的 offset。

试 3 · 每条消息记一条索引找得快了

  • 索引条数和消息一样多：10 亿条消息，每条 8 字节，索引就是 8 GB
  • 索引放不进内存，查索引本身又要读盘

Kafka：稀疏索引，每攒够 4 KB 数据才记一条。查找时二分到附近，再往后扫几 KB。

试 4 · JVM 里缓存，读出来再发热数据快了

  • 几十 GB 数据放在堆里，GC 停顿受不了
  • 进程一重启，缓存全空
  • 同一份数据，堆里一份，操作系统的页缓存里还有一份
  • 发给消费者：内核拷到 JVM，JVM 再拷回内核

Kafka：不在堆里缓存消息，全靠页缓存；发送用 sendfile，数据不进 JVM。

精华：Kafka 的存储很“笨”。写只往段文件末尾追加，查靠稀疏索引定位到几 KB 以内，缓存交给页缓存，发送交给 sendfile。JVM 只管协议、校验和元数据，消息本身很少经过它。

所以调 Kafka 的性能，很多时候是在调操作系统：内存留给页缓存、磁盘别和别人抢、文件句柄够用。

不懂精华时的典型误用
  • 给 Broker 开 32 GB 堆，想“多缓存点消息”。Kafka 不在堆里缓存消息，堆越大，留给页缓存的越少。官方文档给的参考配置是 -Xmx6g。
  • 为了“更安全”把 flush.messages 设成 1，每次写都 fsync。本机实测吞吐从 16.6 MB/s 掉到 4.5 MB/s。不丢消息靠的是副本，见上一页。
  • 一个集群建几万个分区。每个分区一串文件，写入点被打散，文件句柄和内存映射也跟着成倍涨。
  • 把 retention.ms 当成“到点就删”。删除按段来，看的是段里最新一条消息的时间。

③选谁：几种消息系统的存法

存消息不止 Kafka 一种做法。比四件事：写入是不是顺序的，怎么找到一条，怎么删，怎么发出去。最值得对照的是 RocketMQ，两边都是只追加日志，分法不同。

选择规则
  1. 要回放历史、多个组各读一份、量大：选只追加日志（Kafka、RocketMQ，或 RabbitMQ 3.9 起的 Stream 类型）。
  2. 单个 Broker 上分区或队列特别多（几千到上万）：RocketMQ 的单 CommitLog 更稳；用 Kafka 就要控制分区数。
  3. 量不大、已经有 Redis、数据能全放内存：Redis Stream 就够。

本页学 Kafka 的存储：段文件、稀疏索引、页缓存、sendfile。把这四样连起来，就能回答“Kafka 为什么快”。

④原理：一串段文件、一本稀疏目录、交给内核搬

打个比方：一本只往后写的流水账，写满一本换新的（段）；每本前面有一张“每隔几页记一次页码”的目录（稀疏索引）；账本摊在操作系统的桌上（页缓存），有人来借，管理员直接把那几页递出去，不经过你的手（零拷贝）。比喻就到这里，下面看真东西。

① 分段

一个分区是一串段文件，文件名是这段第一条消息的 offset（20 位补零）。写满 1 GiB（segment.bytes）或满 7 天（segment.ms）就换新段，只有最后一段在写。

按段删除 → ⑥ 坑 1

② 稀疏索引

.index 每攒够 4 KB 数据（index.interval.bytes）记一条“offset → 文件位置”。找一条消息：选段 → 二分索引 → 从记下的位置往后扫。按时间找先查 .timeindex。

③ 页缓存

写入只是 write() 进页缓存就返回，默认不 fsync，刷盘交给操作系统。消费者读刚写的数据，基本都直接从页缓存拿。

5Java 里摸一下零拷贝：同一个 1 GiB 文件发给 socket，两种写法比 CPUZeroCopyDemo.java，JDK 11 以上直接 java ZeroCopyDemo.java
import java.io.*;
import java.lang.management.ManagementFactory;
import java.net.*;
import java.nio.channels.*;
import java.nio.file.*;

public class ZeroCopyDemo {
    public static void main(String[] args) throws Exception {
        Path file = Path.of("big.bin");
        if (Files.notExists(file)) {                          // 准备一个 1 GiB 的文件
            try (OutputStream out = Files.newOutputStream(file)) {
                byte[] mb = new byte[1 << 20];
                for (int i = 0; i < 1024; i++) out.write(mb);
            }
        }
        for (int round = 1; round <= 3; round++) {
            send("read+write", file, false);
            send("transferTo", file, true);
        }
    }

    static void send(String name, Path file, boolean zeroCopy) throws Exception {
        try (ServerSocket server = new ServerSocket(0)) {
            Thread sink = new Thread(() -> {                  // 接收端：读到就扔
                try (Socket s = server.accept(); InputStream in = s.getInputStream()) {
                    byte[] b = new byte[64 * 1024];
                    while (in.read(b) != -1) { }
                } catch (IOException e) { throw new UncheckedIOException(e); }
            });
            sink.start();
            var mx = ManagementFactory.getThreadMXBean();
            long cpu0 = mx.getCurrentThreadCpuTime(), t0 = System.nanoTime();
            if (zeroCopy) {                                   // 零拷贝：FileChannel.transferTo → sendfile
                try (FileChannel ch = FileChannel.open(file);
                     SocketChannel sock = SocketChannel.open(new InetSocketAddress("localhost", server.getLocalPort()))) {
                    long size = ch.size();
                    for (long pos = 0; pos < size; ) pos += ch.transferTo(pos, size - pos, sock);
                }
            } else {                                          // 老办法：读进 byte[]，再写给 socket
                try (InputStream in = Files.newInputStream(file);
                     Socket sock = new Socket("localhost", server.getLocalPort());
                     OutputStream out = sock.getOutputStream()) {
                    byte[] buf = new byte[64 * 1024];
                    for (int n; (n = in.read(buf)) != -1; ) out.write(buf, 0, n);
                }
            }
            sink.join();
            System.out.printf("%s  发送线程 CPU %4d ms  总耗时 %4d ms%n", name,
                    (mx.getCurrentThreadCpuTime() - cpu0) / 1_000_000, (System.nanoTime() - t0) / 1_000_000);
        }
    }
}

注意事项：不知道就出事

坑 1retention 设了 7 天，磁盘上有 12 天前的数据 实测
现象
流量小的 topic，老数据迟迟不删，磁盘一直涨。
原因
删除按段来，要等段里最新一条超过 retention.ms 才删整段。正在写的段要满 7 天（segment.ms）或写满 1 GiB 才滚出来。一段攒了 7 天，再等 7 天才删，最老的消息最多活 14 天。另外每 5 分钟才检查一次（log.retention.check.interval.ms），删前先改名，1 分钟后才真删（file.delete.delay.ms）。
实测
retention.ms=60000，每 10 秒写一条：4 分多钟后第 1 条还在，停写 1 分多钟后才整段删掉。再加 segment.ms=20000，只留最近 70 秒左右。
做法
流量小的 topic 设 segment.ms（比如 1 天）；磁盘按“保留时长 + 一个段”预留；合规上“到点必须删”的数据别指望 retention。
坑 2报表组一回放，实时消费跟着变慢 实测
现象
回放开始后磁盘读 IO 飙升，实时组的 lag 上涨，生产延迟也可能跟着变高。
原因
实时组读刚写的数据，在页缓存里；回放读几天前的段，只能读盘，读进来的旧数据还会占页缓存，把新数据挤出去。
实测
写入 963 MB 后把页缓存清掉再从头读：Broker 从磁盘读了 963 MB（/proc/<pid>/io 的 read_bytes），73 MB/s；马上再读一遍：磁盘读 0 MB，152 MB/s。
做法
给回放的客户端配限速配额（consumer_byte_rate），错开高峰；大规模回放从 follower 读（replica.selector.class + client.rack）或上分层存储。实时组的落后时间要远小于下面算出的“热窗口”。
坑 3Broker 的堆开得越大越好？
现象
32 GB 的机器给 Broker 开了 24 GB 堆，结果磁盘读变多，消费反而慢了。
原因
消息不缓存在堆里。堆占走的内存，页缓存就用不上；索引的 mmap、发送的 sendfile 也都靠页缓存。
做法
堆按官方文档的参考配置给 6 GB 左右（-Xmx6g -Xms6g，G1），剩下的内存留给页缓存。用下面的页缓存实验台估一下够不够。
坑 4开了 TLS，Broker CPU 涨了好几倍 实测
现象
读流量不变，开 TLS 后 Broker CPU 明显上涨，吞吐下降。
原因
加密只能在用户态做。Kafka 的 SslTransportLayer 先把数据从页缓存读进 JVM 的直接缓冲区，用 SSLEngine 加密，再写给 socket，用不上 sendfile。官方文档也写明 SSL 时不用 sendfile。
实测
热读同一份 963 MB：明文 Broker CPU 约 1.0 秒，TLS 约 5.9 秒；消费速度 152 MB/s 降到 86 MB/s。strace 计数：明文 25 次 sendfile，TLS 0 次。
做法
容量规划把加密的 CPU 算进去；不同 listener 可以配不同协议，内网可信链路走明文、对外的走 TLS；CPU 选带 AES 指令的。
坑 5为了不丢消息，设成每条都刷盘 实测
现象
吞吐掉一大截，延迟抖动。
原因
flush.messages=1 让每次追加后都 fsync。fsync 会阻塞写，操作系统也没法再合并、排序写入。
实测
10 万条 1 KB：默认 16.6 MB/s，flush.messages=1 只有 4.5 MB/s。默认配置下生产 2 万条，.log 只在滚段时 fsync 了 4 次（每段一次），正在写的段一次没刷。
做法
保持默认，不主动 fsync。不丢消息靠 3 副本 + acks=all + min.insync.replicas=2（上一页），官方文档也推荐默认刷盘设置。
坑 6分区太多，Broker 起不来或重启很慢
现象
报 Too many open files 或 Map failed；异常关机后要恢复很久。
原因
每段有 .log、.index、.timeindex 三个文件，索引用 mmap。官方文档按每段 2 个内存映射算，会撞上 vm.max_map_count（很多发行版默认 65530 左右）。异常关机后，没确认刷过盘的段要逐批校验 CRC、重建索引。
做法
文件句柄至少 100000（文档建议）；调大 vm.max_map_count；控制每个 Broker 的分区数；num.recovery.threads.per.data.dir 按磁盘数调大（4.x 默认 2，3.x 默认 1）。
坑 7带着旧时间戳写进来，转眼就被删了 实测
现象
迁移、回放数据时保留了原始时间戳，写进去没多久就没了；或者时间戳在未来，直接写不进去。
原因
按时间删看的是消息里的时间戳，默认是生产者填的 CreateTime。8 天前的时间戳，段的最新时间就是 8 天前，下次检查就删。4.x 默认拒收比 Broker 时钟晚 1 小时以上的消息（message.timestamp.after.max.ms），3.x 默认不限。
实测
时间戳是 8 天前的一条写成功（offset 0），25 秒后最早 offset 变成 1；时间戳是 2 小时后的一条报 InvalidTimestampException。
做法
迁移、回放时用当前时间，原始时间放进消息体或 header；或者 topic 设 message.timestamp.type=LogAppendTime，用 Broker 写入的时间。
坑 8segment.bytes 调得太小或太大 实测
现象
太小：文件数爆炸，句柄和映射跟着涨。太大：删除粒度粗，磁盘回收慢。
实测
4.x 设 100 KB 直接报错，最小 1 MiB；3.x 最小只要 14 字节，所以老集群上能看到很小的段。
做法
默认 1 GiB 大多合适。想让小 topic 删得及时，调 segment.ms，别把 segment.bytes 调得很小。
第二圈

使用规范：团队里怎么配

topic存储相关配置模板
# 普通业务 topic：段大小用默认，保留时间按业务定
retention.ms=604800000      # 7 天
segment.bytes=1073741824    # 1 GiB（默认）

# 每天写不满 1 GiB 的小 topic，再加：
segment.ms=86400000         # 每天滚一段，删除最多晚 1 天

# 保持默认，不要改：
# flush.messages / flush.ms    不主动 fsync，靠副本
# index.interval.bytes=4096    索引大小和扫描长度的平衡点
# compression.type=producer    原样存生产者压好的批
磁盘容量这样估

写入速率 × 保留时长 × 副本数，再加余量。比如订单写入 5 MB/s、保留 7 天、3 副本：

5 MB/s × 604800 s ≈ 2.9 TiB    # 一份
2.9 TiB × 3 副本   ≈ 8.7 TiB    # 整个集群

再留两块余量：每个分区最多多留一个段（坑 1），磁盘水位别超过 70%～80%。

内存先留给页缓存

堆 6 GB 左右；页缓存至少装得下“写入速率 × 30 秒”，这是官方文档给的估算法。实时消费者落后得越多，要的越多。

数据盘单独用

不和应用日志、系统盘混用。文件系统用 XFS 或 ext4，官方文档的对比测试里 XFS 更好。

系统参数一次配好

ulimit -n 至少 100000；调大 vm.max_map_count；常见做法是关掉 swap 或把 vm.swappiness 调到很低。

回放和实时分开管

回放用单独的 client id 配限速；大回放走 follower 读或分层存储；回放前看一眼页缓存够不够。

盯这三个指标

分区磁盘占用（kafka-log-dirs.sh --describe）；磁盘读 IO（iostat 的 rMB/s，以实时消费为主时应接近 0）；消费 lag 换算成时间后和热窗口比。

别碰的开关

不改刷盘参数、不调小 index.interval.bytes、不把 segment.bytes 调到几 MB，除非有压测数据撑着。

第三圈

优化和深处：拷贝细账、页缓存、索引源码

零拷贝实验台：一次发送，数据走了几趟

发送方式
数据在不在页缓存

Java 和 Kafka 源码里对应什么

  • FileChannel.transferTo 在 Linux 上走 sendfile；FileChannel.map 就是 mmap，返回 MappedByteBuffer。
  • Kafka 4.1.2 的字节码里：PlaintextTransportLayer.transferFrom 调的是 FileChannel.transferTo；SslTransportLayer.transferFrom 先 ByteBuffer.allocateDirect，把文件读进来再加密。
  • 老办法在 Java 里比教科书还多拷一次：堆里的 byte[] 不能直接交给系统调用，JDK 先读进一块本地内存，再拷进数组。⑤ 里 read+write 多花的 CPU 有一部分在这。

零拷贝只在“读”这一侧

  • 生产者发来的数据要进 JVM：校验 CRC、分配 offset，然后 write() 进页缓存。这一侧没有零拷贝，靠的是批量和顺序写。
  • 批量：一批（RecordBatch）共用一个批头，⑤ 里 4 条 200 字节的消息一批 897 字节。topic 的 compression.type=producer（默认）时，Broker 原样存生产者压好的批，消费者拿到的也是同一份压缩数据。
  • Netty 说的“零拷贝”是另一回事：CompositeByteBuf、slice 是在 JVM 里少拷贝；它的 DefaultFileRegion 才是走 transferTo。

页缓存实验台：最近多久的数据还在内存里

库存组固定落后 2 秒，代表一直跟得上的实时组。

    粗算：页缓存 ≈ 内存 − 堆 − 2 GB；按最简单的“最近用过的留下”来估。只有写入时，热窗口 = 页缓存 ÷ 写入速率；有回放时，回放读进来的旧数据也要占地方，热窗口 = 页缓存 ÷（写入 + 回放）。Linux 实际用两条链表管理页缓存，结果会比这个好一些，方向一样。

    索引的源码细节

    • 条目格式：.index 每条 8 字节 = 相对 offset 4 字节 + 文件位置 4 字节；.timeindex 每条 12 字节 = 时间戳 8 字节 + 相对 offset 4 字节。存的是减掉段起始 offset 的相对值，4 字节就够。
    • 预分配 + mmap：活跃段的索引一创建就是 10 MiB（segment.index.bytes），用 MappedByteBuffer 映射进内存；滚段时截到实际大小（⑤ 实测 1864 字节）。索引写满（10 MiB ÷ 8 字节，约 131 万条）也会触发滚段。
    • 热区二分：多数查找是追尾读，落在索引最后面。AbstractIndex 先在最后 8 KB（offset 索引就是 1024 条）里二分，这一块总被访问，一直在内存里，不会缺页。4.1.2 字节码里能看到常量 8192。
    • 旧段的索引用到时才打开映射（源码里的 LazyIndex），所以平时占的映射比“每段 2 个”少，回放老数据时才会打开。

    段、文件和刷盘

    • 所有段按起始 offset 放在一个 ConcurrentNavigableMap（跳表）里，选段就是一次 floor 查找。
    • 其他文件：.snapshot 是生产者状态，滚段时写；.txnindex 有被中止的事务才出现；.deleted 是删除前的改名。
    • 刷盘：默认 log.flush.interval.messages 是 Long 最大值，不主动 fsync；滚段时把旧段 fsync 一次（⑤ 生产 2 万条，4 次滚段 4 次 fsync）。
    • 异常关机：recovery-point-offset-checkpoint 记着刷到哪了，之后的段要逐批校验 CRC、重建索引。
    • 敢不刷盘的前提是副本：一台机器掉电丢的页缓存数据，别的副本上还有。

    版本差异

    2.x / 3.x老集群上常见
    • segment.bytes 最小 14 字节，能看到很小的段
    • num.recovery.threads.per.data.dir 默认 1，恢复慢
    • 不限未来时间戳（message.timestamp.after.max.ms 默认 Long 最大值）
    • 还要给很老的客户端转换消息格式，转换的那部分在 JVM 里做，没有零拷贝
    4.0+Broker 要 JDK 17
    • segment.bytes 最小 1 MiB（实测）
    • 恢复线程默认 2
    • 默认拒收晚 1 小时以上的时间戳（实测）
    • Fetch 请求最低 v4，老消息格式的转换没有了
    • 只有 KRaft，元数据也是一份日志（__cluster_metadata）
    没变的从早期一直这样
    • 段 1 GiB、索引每 4 KB 一条、索引预分配 10 MiB
    • 默认不主动 fsync
    • 明文连接用 sendfile，TLS 不用
    • 按段删除，看段里最新的时间戳

    面试官会怎么问

    Kafka 为什么这么快？
    • 写：只往段文件末尾顺序追加；按批写，一批共用一个批头，压缩后原样存；只 write() 进页缓存，不等 fsync。
    • 读：稀疏索引二分 + 往后扫几 KB 就能定位；追尾读命中页缓存；明文连接用 sendfile，数据不进 JVM。
    • 并行：一个 topic 分成多个分区，分散到多块盘、多台机器。
    稀疏索引怎么查一条消息？为什么不每条都建索引？

    跳表里 floor 找到段 → 在 .index 里二分，找不超过目标的最大一条 → 从它记的位置往后扫批头，直到某批的 lastOffset ≥ 目标 → 整批返回。稀疏是为了让索引小到能常驻内存：1 GiB 的段只有约 26 万条、2 MiB。代价是每次最多多扫约 4 KB。

    零拷贝具体少了什么？

    read + write：2 次 DMA、2 次 CPU 拷贝、4 次用户态和内核切换。sendfile（网卡支持 gather）：2 次 DMA、0 次 CPU 拷贝、2 次切换。数据已在页缓存时，读盘那次 DMA 也省了。开 TLS 就退回到用户态加密，CPU 拷贝和加密都回来了。

    Kafka 默认不刷盘，不怕丢消息吗？

    单机掉电会丢页缓存里还没刷的数据。Kafka 靠副本：acks=all + min.insync.replicas=2 时，一条消息至少在两台机器的页缓存里，同时掉电才会丢。官方文档也认为副本比本机 fsync 更可靠，推荐默认刷盘设置。

    为什么不把消息缓存在 JVM 堆里？

    GC 停顿；进程重启缓存清空；和页缓存重复存两份；Java 对象还有额外开销。页缓存自动用掉所有空闲内存，Broker 重启后还在。

    Kafka 和 RocketMQ 的存储有什么不同？

    Kafka 每个分区一串文件，分区多了写入点多，磁盘上接近随机写。RocketMQ 所有消息写一个 CommitLog，再给每个队列建 20 字节一条的 ConsumeQueue，写入点只有一个，但读一条要多查一次。发送上，Kafka 用 sendfile，RocketMQ 用 mmap。

    retention 为什么不准？

    按段删，要段里最新一条过期；活跃段要先滚出来（满 1 GiB 或 7 天）；每 5 分钟检查一次；删除前改名再等 1 分钟。还有时间戳：按消息里的时间戳算，生产者填错了也会删早或删晚。

    自测

    1. 用一句话说出 Kafka 存储的精华。

    只往段文件末尾追加，用稀疏索引定位，缓存交给页缓存，发送用 sendfile，JVM 基本不碰消息本身。

    2. 自己在 JVM 里缓存消息，疼在哪？

    GC 停顿、重启后缓存全空、和页缓存重复存两份、发给消费者要在内核和 JVM 之间多拷两次。

    3. 要从 1 小时前开始重新消费，Java 里怎么写？

    consumer.offsetsForTimes(Map.of(tp, 一小时前的毫秒时间戳)) 拿到 OffsetAndTimestamp，不为 null 就 consumer.seek(tp, hit.offset())。Broker 先查 .timeindex 再查 .index。

    4. 把 index.interval.bytes 从 4 KB 调到 64 KB，会怎样？

    索引条数变成 1/16，更省内存；但每次查找最多要往后多扫约 64 KB。④ 的查找实验台切到 16 KB 就能看到扫的批数变多。

    5. retention.ms 是 7 天，为什么磁盘上有 12 天前的数据？（头号坑）

    删除按段来，要等段里最新一条超过 7 天。流量小的 topic，一段要满 7 天才滚出来，再过 7 天才删，最老的数据最多留约 14 天。设 segment.ms 可以缩短。

    6. 开 TLS 以后 Broker CPU 为什么会涨？

    加密只能在用户态做，数据要先读进 JVM 的缓冲区加密再写出去，用不上 sendfile。本机实测同样读 963 MB，Broker CPU 从约 1 秒涨到约 5.9 秒。

    测试环境：Kafka 4.1.2 单节点（KRaft，broker 和 controller 合在一个进程）· OpenJDK 21 · Linux 6.8 · 2 核 11 GB 的云主机。实测数字只代表这台机器，换了硬件要自己量。默认值来自 4.1.2 自带的文档和 jar 包，3.x 的差别来自 4.0 的升级说明。
