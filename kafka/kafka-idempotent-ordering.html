积分加了两次，退款跑到了付款前面：幂等消费与顺序消息

Kafka 对消费者只承诺两件事：每条消息至少送到一次；同一个分区里按写入的顺序送。“只生效一次”和“按业务发生的顺序生效”，都得消费端自己做到。前一件靠把“这条处理过了”和业务改动写进同一个本地事务；后一件靠让同一个订单的事件始终只有一条处理线。对“改状态”这类事件还有更省事的做法：事件自带版本号，消费端只认更新的版本，重复和乱序就都不怕了。

全景：一条订单消息的一生 · 第 8、2 站地图：J08 · 幂等消费与顺序消息

接着全景全景页已经给出三个结论，这里不再重讲：Kafka 的消费是“至少一次”；去重表要和业务改动放在同一个事务里；outbox 重发时换了 producerId，broker 认不出来。这一页往下再走一层，讲四件事：Kafka 为什么不替你去重；几种去重写法各适合哪类事件；顺序会在哪几处被打乱；有没有一个办法把两件事一起管住。

①要解决的问题：同一条消息生效两次，三条消息生效的顺序不对

在全景第 8 站，积分服务处理完 evt-9527-paid、还没提交位点就被杀了，同组的新实例又收到同一个 offset。在第 2 站，订单 9527 的“已支付”“已发货”“已退款”三条事件都用 "9527" 做 key，进了同一个分区，可是消费端要是并行处理，最后生效的顺序就不一定是这个了。

②不用它会怎样：在交易靶场里真跑一遍

“它”指消费端的去重和保序。下面三个数都是本机 Kafka 4.4.0 上跑出来的，代码见 ⑤：1000 个订单，每单三条事件，交错着发。

不懂精华时的典型误用“我们开了 acks=all 和幂等生产者，Kafka 4 还支持 exactly-once，所以不会重复。”幂等生产者只保证同一个生产者重发的批次不会在日志里写两份，管不到消费端“处理完了、位点还没提交”这一段。Kafka 的事务也只覆盖“读 Kafka、写 Kafka”。积分写的是 MySQL，重复只能在积分服务自己这里挡。

③几种流派：去重有四种写法，保序有四种做法

两张表各回答一个问题。第一张：消费端怎么认出“这条处理过了”。第二张：同一个订单的事件，怎么保证按顺序生效。

认出“处理过了”

写法怎么认出来适合代价和限制
去重表（消费记录表）eventId 做主键，和业务改动同一个事务里先插入；撞了唯一键就是处理过任何事件，尤其是“加 798 分”这种累加型每条多一次写；表会一直长，要按时间清理
业务唯一键业务表本来就有“一单只能一次”的约束，比如积分流水表 UNIQUE(source_event_id)业务里天然有唯一性的地方不用额外的表；前提是业务模型里真有这个约束
条件更新（状态机）UPDATE … SET status='DEDUCTED' WHERE id=? AND status='RESERVED'，更新了 0 行就是处理过改状态的事件，比如库存从“预占”转成“扣减”只能表达“往前走一步”，表达不了“再加一次”
位点存业务库不判断事件，而是把“读到哪了”和业务改动写进同一个事务，重启时从库里的位置 seek只写一个库、按分区成批处理，比如往 ES 或数仓同步Kafka 自带的 LAG 工具看不到真实进度；一个分区的结果只能写在一个库里

不在表里的两种：用 Redis SETNX 去重，它和 MySQL 里的业务改动不在一个事务，崩在两者之间就会丢消息，和 ⑤ 里的 split 是同一个坑；Kafka 事务只覆盖“读 Kafka、写 Kafka”的流处理，见 ⑥ 第三圈。

同一个订单，按顺序生效

做法顺序怎么来的并行度适合
只有一个分区所有消息排成一队1 个消费者在干活量很小、又要全局顺序（比如对账流水）
按 key 分区（Kafka 默认）同一个订单进同一个分区，一个分区在组里只给一个实例，一条条处理最多等于分区数大多数场景的起点
按 key 分区 + 按 key 分车道消费端再按订单号哈希到 N 条单线程车道，同一个订单永远走同一条可以超过分区数每条处理慢（调外部接口），分区又不想加
不依赖顺序：版本号事件带上版本号，消费端只接受比当前更新的版本，旧的直接丢随便并行改状态、覆盖写的事件；累加型不行，见 ④

两个对照：RocketMQ 的顺序消息是另一套机制，发送时指定队列、消费时锁住队列，见 RocketMQ 的事务消息、定时消息、顺序消息；Kafka 4.2 起正式可用的 Share Group（队列语义）走的是反方向，用顺序换并行，见 ⑥ 第三圈。

选择规则：先看事件是覆盖型（把状态改成 X）还是累加型（加 798 分、扣 2 件）。覆盖型：按 key 分区，加版本号守卫，消费端随便并行。累加型：用去重表或业务唯一键，和业务改动放进同一个事务；要并行，就按 key 分车道。本页的交易靶场两样都做：积分服务用“去重表，同一个事务”，订单视图服务比较“车道”和“版本号”两种做法。

④核心取舍：两个系统没有共同的事务；顺序只活在一条管子里

先知道这些
  • 位点（offset）：消费组在每个分区记一个“下一条该读第几条”，存在 Kafka 的内部 topic __consumer_offsets 里。实例重启或者分区换了人，都从这个位置接着读。见 Kafka 可靠性与消费组。
  • 本地事务和唯一键：同一个 MySQL 事务里的几条写，要么都生效，要么都不生效；插入撞了唯一键会报错（MySQL 1062），整个事务可以回滚。见 MySQL redo、undo 与 binlog。
  • 分区器：有 key 时，murmur2(key) % 分区数 决定进哪个分区（全景第 2 站）；没有 key 时，一批写满就换一个分区（粘性分区）。

为什么 Kafka 不替你去重：结果和位点存在两个地方

至少一次投递 + 消费端幂等选中的设计

约束：下游是各式各样的系统，积分写 MySQL、通知调短信平台，它们大多不支持 XA 两阶段提交。“至少一次 + 幂等”只要求下游有一个唯一键，或者能带着 eventId 去重。

中间件保证“恰好一次投递”放弃的设计

输在哪：覆盖不了大多数下游，又把每条消息的延迟和锁的时间拉长。Kafka 的 exactly-once 走的是另一条路：它只在 Kafka 内部做事务，把“写结果”和“写位点”都变成写 Kafka，下游一出 Kafka 就不管了。

这个设计带来的后果重复不是小概率的异常，而是常规路径：每次重平衡、每次发布重启、每次处理超时被踢出组，都会把“上次提交之后处理过的那一批”再送一遍。所以幂等要当成每个消费者的默认写法，不能当成补丁。

顺序在哪几处被打乱：它只在“一个分区 × 一条处理线”里成立

一个办法管住两件事：事件自带版本号

怕重复吗怕乱序吗怎么办
覆盖型：状态改成 X、库存改成 N、ES 文档整篇覆盖重复的若是最新那条，不怕；重放出来的是旧的，就怕怕版本号守卫，一招两用；之后随便并行
累加型：积分 +798、库存 −2、发一条短信怕多数不怕：加减可以交换先后（中途可能出现负数）去重表或业务唯一键，和业务改动同一个事务；要保序就按 key 分车道

最少的写法

消费端三件套MySQL 语法；⑤ 里用 H2 的 MySQL 模式跑
-- 累加型：去重表和加积分在同一个事务里，先插去重表
CREATE TABLE consumed_event(event_id VARCHAR(64) PRIMARY KEY, at TIMESTAMP);
BEGIN;
INSERT INTO consumed_event VALUES('evt-9527-paid', NOW());   -- 1062 撞键 → ROLLBACK，当处理过
UPDATE points SET total = total + 798 WHERE user_id = 1024;
COMMIT;                                                        -- 然后才 commitSync()

-- 覆盖型：版本号守卫，0 行 = 旧事件或重复
UPDATE order_view SET status = 'REFUNDED', ver = 3 WHERE id = 9527 AND ver < 3;
// 要并行又要按订单有序：按 key 分车道，同一个订单永远进同一条单线程车道
ExecutorService[] lanes = new ExecutorService[8];          // 每条都是 newSingleThreadExecutor()
for (ConsumerRecord<String, String> r : consumer.poll(Duration.ofMillis(200)))
    lanes[Math.floorMod(r.key().hashCode(), 8)].execute(() -> handle(r));

车道之后，位点怎么提交才不会把没处理完的也提交掉，放到 ⑥ 第三圈；去重表要留多久、怎么清，放到 ⑥ 第二圈。

⑤套进场景：交易靶场里的积分服务和订单视图服务

两段实验。dup 是全景第 8 站的积分服务：处理完、提交位点前崩溃，四种写法各跑一次。order 是一个订单视图服务（把订单最新状态同步到查询库，相当于第 8 站的第四个下游）：1000 单 × 3 条事件，按第 t 轮发“订单 t 的 PAID、订单 t−1 的 SHIPPED、订单 t−2 的 REFUNDED”这样交错发出，五种消费写法各跑一次。

跑起来Kafka 4.4.0 单节点（KRaft，broker 和 controller 同一进程）+ kafka-clients 4.4.0 + H2 2.4.240，JDK 17；完整代码 →
# study-labs/java/kafka/kafka-idempotent-ordering
./run.sh                 # 下载并起 Kafka，dup 四种 + order 五种全跑
./run.sh dup split       # 只跑一种：dup none|split|same|offset，order seq|nokey|pool|lanes|guard
./run.sh clean           # 停掉 Kafka，删 data/
// dup 的骨架：实例 1 处理完就“崩溃”（关掉消费者、不提交位点），同组实例 2 接手
for (int inst = 1; inst <= 2; inst++) {
    KafkaConsumer<String, String> c = consumer("points-svc");    // enable.auto.commit=false
    ConsumerRecord<String, String> rec = pollOne(c);
    handle(strategy, rec, /*crash=*/ inst == 1);                  // none / split / same / offset
    if (inst == 2 && !strategy.equals("offset")) c.commitSync();
    c.close();
}

看到了什么对应的原理
split 比不去重还糟：一分都没加，而且不报错④ 两个系统：去重表和积分又成了“两个地方”，只是这回两个地方都在 MySQL 里
offset 根本没有重投：实例 2 从库里读到位置 1，seek 过去，没东西可读④ 位点存业务库：Kafka 那边的位点一直没提交过，真实进度只在 MySQL 里
lanes 和 pool 一样快（约 0.59 s，一条条处理的 1/5），却一单都没错④ 一条处理线：并行的单位从“每条消息”换成了“每个订单”

到这里已经能交差了：积分服务用“去重表 + 同一个事务”，订单视图用“按 key 分区 + 版本号守卫”，处理完再 commitSync()。已知还没处理的细节：车道模式下位点怎么提交（⑥ 第三圈）；去重表留多久（⑥ 第二圈）；eventId 是谁生成的（⑥-4）；加分区那一刻（⑥-5）。

第一圈 · 注意事项：不知道就会出事故

1以为生产端配好了，消费端就不会重复← ④ 两个系统
现象
开了 acks=all、幂等生产者，代码评审时认为“Kafka 保证不重复”，消费端没做去重。一次发布滚动重启，积分多发了一批。
根源
幂等生产者只让 broker 丢掉同一个生产者会话重发的批次，管的是“日志里有几份”。消费端的重复来自“业务结果已经提交、位点还没提交”，发生在 Kafka 之外。
做法
把“消费端幂等”写进每个消费者的默认模板；评审时专门问一句：这里处理两次会怎样。
2去重写成“先查有没有，没有再插”← ④ 同一个事务
现象
平时没事，一到重平衡就偶尔重复：两个实例都查到“没处理过”，都处理了一遍。
根源
“查”和“插”之间有空档。重平衡时，旧实例可能还在处理（比如处理超时被踢出了组，但线程还在跑），新实例已经拿到了同一个分区，两边同时查。只有唯一键能把两者排成先后。
做法
直接 INSERT，靠唯一键冲突判断；和业务改动放在同一个事务里，而且先插去重表，后改业务，撞键时什么都还没做。
3丢进线程池提速，顺序和位点一起坏← ④ 一条处理线
现象
积压时给消费者加了线程池，LAG 降下来了，订单视图里却出现“已退款的单显示已发货”。⑤ 实测 487/1000
根源
并行的单位成了“每条消息”，同一个订单的三条落到不同线程，谁先做完谁先生效。另外 poll() 线程会接着往前提交位点，还没处理完的也被提交了，进程一崩，这批就丢了（全景第 9 站讲过）。
做法
按 key 分车道；位点只提交“连续处理完”的那一段，见 第三圈。覆盖型事件也可以改用版本号守卫。
4eventId 在发送时才生成← ④ 去重靠的那个键
现象
去重表一直在写，重复照样发生。
根源
eventId 是投递线程每次 send() 前 UUID.randomUUID() 出来的。outbox 重发同一行时生成了新 ID，下游看来就是两件不同的事。用 offset 当去重键也一样：同一个事件被重发，会落在新的 offset 上。
做法
eventId 在写 outbox 那一刻生成，和业务一起落库，之后原样带到底：消息体、header，再到下游调用的第三方。
5给 topic 加分区，在途订单乱一阵← ④ 分区器
现象
大促前把 order-events 从 6 个分区加到 12 个，当天少数订单的状态倒退了。
根源
murmur2(key) % 6 变成了 % 12，加分区之后的事件可能进新分区；同一个订单前后两条分属两个分区，两个分区之间没有先后。只影响加分区那一刻正“在路上”的订单，所以数量少、很难复现。
做法
分区数一开始按峰值定；非加不可，就挑低峰、先停发或者等积压清零再加；覆盖型事件用版本号兜底。
6版本号守卫用在累加型事件上← ④ 覆盖型和累加型
现象
积分服务照搬订单视图的“只认更新的版本”，退款先到、付款后到的那些单，付款的 +798 被丢掉了。
根源
版本号守卫的前提是“最后一条说了算”。累加型每一条都要算，丢掉旧的就是少算一笔。实验台选“记积分 + 池子 + 版本号守卫”，约一半订单记错。
做法
累加型用去重表或业务唯一键；真要保序，按 key 分车道。
7处理失败的消息丢进重试 topic← ④ 一条处理线
现象
PAID 处理时数据库抖了一下，被转进重试 topic；SHIPPED、REFUNDED 照常处理完，几秒后 PAID 从重试 topic 回来，把状态改回“已支付”。
根源
重试 topic 是另一条管子，它里面的消息和原分区之间没有先后。反过来，原地阻塞重试能保住顺序，代价是整个分区都停下来等它。
做法
覆盖型：转去重试也没关系，靠版本号挡住迟到的旧事件。累加型、要保序：原地有限次重试；还不行就把这个订单的后续事件也暂存起来，或者人工处理。
8外部调用放进了“同一个事务”← ④ 两个系统
现象
通知服务把“插去重表 + 调短信接口”包在一个 @Transactional 里，短信接口超时，事务回滚，重投以后又发了一条，用户收到两条短信。
根源
短信平台是第三个系统，回滚不了已经发出去的短信。本地事务只管得住本地库里的东西。
做法
把 eventId 作为幂等键传给短信平台；平台不支持，就先在本地记“待发送”，由一个发送任务按 eventId 去重地发。

第二圈 · 使用规范

eventId 在写 outbox 时生成，一路带到底

消息体和 header 各放一份，下游调第三方时也带上。防的是 ⑥-4。

去重靠唯一键插入，和业务同一个本地事务，先插后改

防的是 ⑤ 的 split 和 ⑥-2。

去重表按天分区或定期删，保留期大于最长的重投窗口

重投最远能回到多久以前，取决于 topic 的保留期（默认 7 天）和你会不会手动重置位点回放。保留期内的记录不能删，删了，回放时就会重复生效。

key 用“需要保序的那个东西”的 ID

订单事件用订单号，账户流水用账户号。用户 ID 能保序，但大客户会成为热点分区；不填 key 就不保序。防的是 ② 的第三种。

同一个订单的事件，从同一个地方发出

支付服务和物流服务各发各的，就没有“发出顺序”可言。都经过订单服务的 outbox，或者每条带上订单版本号。

覆盖型事件带版本号，消费端条件更新

版本号用订单表的 version 列或 outbox 里按订单递增的序号，不用 offset 和时间戳。防的是 ⑥-5、⑥-7。

要并行，按 key 分车道，不按条丢进池子

车道数可以超过分区数。防的是 ⑥-3。

“处理两次会怎样”写进消费者的评审清单

每个新消费者上线前，在测试环境里杀一次进程看结果，就是 ⑤ 的 dup 段。防的是 ⑥-1。

第三圈 · 深处：车道下的位点、位点存哪、Share Group、Kafka 事务

车道模式下，位点只能提交“连续完成”的前缀

分区 3 的 offset 10、11、12 分到三条车道，12 先做完，不能提交 13：要是 10 还没做完进程就崩了，10 就丢了。做法是每个分区记下已完成的 offset，只提交从头开始连续完成的最大 offset + 1。代价是崩溃后会重做 11、12 这些已经完成的，所以车道模式下去重仍然要做。Confluent 的开源库 Parallel Consumer 就是按这个思路实现的，支持按分区、按 key、不保序三种模式。

位点存业务库，要接上重平衡

KafkaConsumer 的 javadoc 有专门一节“把位点存在 Kafka 之外”：订阅时传一个 ConsumerRebalanceListener，在 onPartitionsAssigned 里从库里读位置、seek 过去，⑤ 的 offset 写法就是这么做的。Kafka 那边看不到进度，kafka-consumer-groups.sh 里 LAG 会一直很大；想要监控，就在本地事务提交之后，再把同样的位点异步提交给 Kafka 一份，只给监控看。

Share Group：用顺序换并行（Kafka 4.2 起正式可用）

KIP-932 的“Kafka 队列”：一个分区可以同时分给多个消费者，消费者数可以超过分区数，按条确认，broker 记着每条投递了几次。4.2 的升级说明原话是：用于“一条条处理，而不是作为有序的流”。它适合 notify-svc 这种每条独立、不在乎先后的下游，不适合订单视图。投递仍然是至少一次，幂等照样要做。

Kafka 事务管到哪：只到 Kafka 为止

读 Kafka、写 Kafka 的流处理里，生产者开事务，用 sendOffsetsToTransaction 把“输出消息”和“消费位点”放进同一个事务，下游用 isolation.level=read_committed 只读已提交的。原理和 ④ 一样：把两件事搬到同一个地方，只不过这个地方是 Kafka。下游是 MySQL 时，这个事务就管不到了。

1. 用一句话说出这一页的精华

Kafka 只给“至少一次”和“分区内有序”。只生效一次，靠把“处理过了”或“读到哪了”和业务结果写进同一个本地事务；按顺序生效，靠同一个 key 只有一条处理线；覆盖型事件带上版本号，两件事一起管住。

2. 老办法（不去重、按条并行）疼在哪？

不去重：每次重平衡、重启都会把上次提交之后的那一批再生效一遍，⑤ 实测积分 1596。按条并行：同一个订单的事件被不同线程处理，谁先做完谁先生效，⑤ 实测 1000 单错 487 单。根子都在 ④：结果和位点不在一个事务里；顺序只活在一条处理线上。

3. 为什么 Kafka 自己不做消费端去重？

④ 两个系统：消费的结果写在你的 MySQL 里，位点写在 Kafka 里，Kafka 看不到你的事务，没法把这两件事做成原子的。它能做的只有两种：把位点也存进你的库（Kafka 文档推荐的写法），或者两边都在 Kafka 里（Kafka 事务）。前者要你来做，后者只适合输出也是 Kafka 的场景。

4. 预测：积分服务用了“去重表 + 同一个事务”，但把 commitSync 改成在处理之前调。进程在处理途中被杀，会怎样？

这条丢了，去重表救不了。位点先提交，就是 ④ 图里的“先提交位点，再处理”，至多一次；新实例从下一条开始读，这条再也不会来。去重表只挡得住“来了两次”，挡不住“一次都没来”。

5. 预测：订单视图用“按 key 分区 + 一条条处理”，没加版本号。消费者在处理到一半时被杀，从上次提交的位置重放。最终状态会错吗？中途呢？

最终不会错：重放是按 offset 顺序把那一段从头再做一遍，最后一条还是 REFUNDED。但中途会倒退：已经是 REFUNDED 的单，重放到它的 PAID 时会短暂变回“已支付”，实验台里能看到“新状态被旧事件盖掉”有几十次。如果状态变化会触发动作（推送、发短信），这些动作会重来一遍。④ 里说的“重复本身就是一种乱序”就是这个意思；加上版本号，这些倒退就都被挡住了。

6. 放回全景：第 8 站前后各发生了什么？这一页讲的东西坏了，整条链路会怎样？

第 8 站之前：第 7 站三个组各自拉到这条消息，消息只有一份，三个组各有自己的位点。之后：第 9 站处理完才提交位点，第 10 站的心跳和重平衡决定这个分区接下来归谁。去重坏了：第 10 站每次重平衡、每次发布，都会让第 8 站多生效一批，积分多发、库存多扣、短信多发，而且 Kafka 这边一切正常，LAG 也是 0。顺序坏了，根子往往在第 2 站（key 不对、加了分区）或第 8 站自己（线程池、重试 topic）：已退款的单显示已发货，库存被重复扣减或释放。第 1 站 outbox 的重发、第 6 站 ACK 丢失后的重试，最终也都要靠第 8 站的去重来挡。

档位：标准。Kafka 4.4.0 单节点（KRaft，broker 和 controller 同一进程，group.initial.rebalance.delay.ms=0），kafka-clients 4.4.0、H2 2.4.240（MySQL 模式），JDK 17.0.21，本机 2 核 ARM。Kafka 4 的客户端要求 Java 11 以上，所以这一页的代码按 JDK 17 编译，没有按 JDK 8 写。

标“实测”的都在本机跑过：dup 四种写法；order 五种写法各跑两遍。实验台是按 ⑤ 的发送顺序和处理时间写的模拟，在 node 里校过。“让消费者把位点和输出存在同一个地方”、恰好一次只覆盖 Kafka 到 Kafka，出自 4.4.0 发行包里的设计文档（Message Delivery Semantics 一节）；Share Group 的状态和原话出自 4.4.0 的升级说明；幂等生产者在途请求数和顺序的关系出自 4.4.0 的生产者配置文档。
