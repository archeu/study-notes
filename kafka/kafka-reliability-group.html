KAFKA · ACKS · ISR · MIN.INSYNC.REPLICAS · OFFSET · CONSUMER GROUP · REBALANCE

写够副本才算数，处理完了再挪书签

Kafka 把消息记在一本只往后追加、存好几份的日志里，消费者只记“读到哪了”（offset）。不丢消息要三段一起守：生产者等 ISR 里的副本都写到（acks=all），Broker 保证同步副本够数（min.insync.replicas），消费者处理完再提交 offset。消费组让一个分区同一时间只归组里一个实例，组和组之间各读一份。

①为什么学→ ②老办法→ ③选谁→ ④原理→ ⑤跑起来→ ⑥细节→ ↺回到⑤

假设场景你在订单服务里接 Kafka：下单后通知库存、积分、短信三个下游，一条都不能丢。这也是 Kafka 面试问得最多的两块，第⑥步末尾附了面试题。页面里标“实测”的地方，都在本机的 Kafka 4.1.2 集群和 Spring Boot 3.5.16 上跑过。

①为什么要学：下单之后，三个下游都要知道

订单服务直接调三个下游，一个慢就全慢，一个挂就下单失败。换成发一条“订单已创建”的消息，各下游自己去取。

1一条都不能丢

库存少扣一次就超卖，积分少发一次就有人投诉。服务器宕机、网络抖动时也一样。

消费组和 rebalance

②老办法行不行

先用已经会的东西做一遍：直接调接口，或者用学过的 Redis Stream。都能做，但疼的地方正好是 Kafka 的精华。

同步调接口能做，耦合太紧

订单→库存50ms→积分80ms→短信超时
  • 下单接口至少 430 ms，最慢的那个说了算
  • 短信服务挂了，下单跟着失败，或者要自己写重试
  • 加一个下游，就要改一次订单服务、发一次版
  • 大促时流量直接压到每个下游，没有缓冲

Redis Stream能做，不够稳、扩不开

订单→Stream内存→库存组积分组
  • 有消费组、ACK、待确认列表，组内分活、组间各一份都能做
  • 消息在内存里，下游停几个小时，积压就可能把内存撑爆
  • AOF 每秒刷盘，断电丢约 1 秒；主从异步复制，切换时丢最后一点（WAIT 能等从节点，但官方说它不能让 Redis 变成强一致）
  • 一个 Stream 是一个 key，只在一个节点上，要扩容得自己拆成多个 key
缺的那块
就是精华

写到磁盘、等够几份副本才算成功：机器挂一台，消息还在别处，而且“成功”的标准可以配。

按分区并行，每个组自己记读到哪：消息读完不删，加下游、回放历史只是多一个书签；组内按分区分活，加分区就能扩。

不懂精华时的典型误用
  • 当成普通队列用，以为“消费完就删了”。其实消息一直在，默认存 7 天，别的组照样能读，也能重读。
  • 以为加实例就能提速。实例数超过分区数，多出来的拿不到分区，白开着。
  • 以为配了 acks=all 就一定不丢。Broker 默认 min.insync.replicas=1，同步副本只剩 leader 时，它和 acks=1 一样。

选择规则
  1. 同一条消息要被好几个系统各读一份、量大、还想回放：Kafka。
  2. 要按规则路由，每条单独确认、重试：RabbitMQ。

④基本原理：一本账存三份，每个组夹自己的书签

把一个 topic 想成几本账（分区）。每本账复印三份放在三台机器上（副本），只有一份是正本（leader），写和读都找它。每个部门（消费组）在每本账里夹自己的书签（offset），部门里的人分账来看，一本账同一时间只归一个人。

一条消息的一生

生产者：等够了再说成功

  • acks=all：ISR 里的副本都写到才回成功
  • 失败自动重试，开幂等防重复
  • 回调里看结果，失败要处理
漏在这：acks=1、发了不管
→

Broker：副本要够

  • 每个分区 3 个副本
  • min.insync.replicas=2：同步副本不到 2 个就拒写
  • 落后的副本不许当 leader（默认）
漏在这：只剩 leader 还照收
→

消费者：做完再挪书签

  • 处理完再提交 offset
  • 崩溃后会重来一遍，业务要幂等
  • 同一组的实例分摊分区
漏在这：先提交后处理

4src/main/java/demo/OrderApp.java生产者和两个消费组都在这一个类里
package demo;

import org.apache.kafka.clients.admin.NewTopic;
import org.apache.kafka.clients.consumer.ConsumerRecord;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;
import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.kafka.config.TopicBuilder;
import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.kafka.support.Acknowledgment;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RestController;

@SpringBootApplication
@RestController
public class OrderApp {

    private static final Logger log = LoggerFactory.getLogger(OrderApp.class);
    private final KafkaTemplate<String, String> kafka;

    public OrderApp(KafkaTemplate<String, String> kafka) {
        this.kafka = kafka;
    }

    public static void main(String[] args) {
        SpringApplication.run(OrderApp.class, args);
    }

    /** 启动时建 topic：3 个分区。单机只能 1 个副本，生产环境是 3 */
    @Bean
    NewTopic orderCreated() {
        return TopicBuilder.name("order-created").partitions(3).replicas(1).build();
    }

    /** 生产者：订单号当 key，同一个订单永远进同一个分区 */
    @PostMapping("/orders/{id}")
    public String create(@PathVariable String id) {
        kafka.send("order-created", id, "{\"orderId\":\"" + id + "\"}")
             .whenComplete((r, ex) -> {
                 if (ex != null) {
                     log.error("发送失败 order={}", id, ex);          // 第⑥步：落库，稍后重发
                 } else {
                     log.info("已写入 order={} 分区={} offset={}", id,
                             r.getRecordMetadata().partition(), r.getRecordMetadata().offset());
                 }
             });
        return "ok\n";
    }

    /** 消费组 inventory：开几个实例，3 个分区就在它们之间分 */
    @KafkaListener(topics = "order-created", groupId = "inventory")
    public void deductStock(ConsumerRecord<String, String> rec, Acknowledgment ack) {
        log.info("[库存] 扣减 order={} 分区={} offset={}", rec.key(), rec.partition(), rec.offset());
        ack.acknowledge();                                           // 处理完再提交
    }

    /** 消费组 points：另一个组，每条消息再收一份 */
    @KafkaListener(topics = "order-created", groupId = "points")
    public void addPoints(ConsumerRecord<String, String> rec, Acknowledgment ack) {
        log.info("[积分] 加积分 order={} 分区={}", rec.key(), rec.partition());
        ack.acknowledge();
    }
}

已知还没处理的细节
  • 发送失败只打了日志，没补发 → ⑥ 发了不管
  • 单机只有 1 个副本，acks=all 还没真正起作用 → ⑥ min.insync.replicas
  • 崩溃重启会重复消费，扣库存没做幂等 → ⑥ 一定会重复
  • 处理抛异常时，默认重试 10 次后直接跳过 → ⑥ 坏消息
  • 分区数 3 定死了，开到第 4 个实例就闲着 → ⑥ 加实例不变快

    第一圈

    注意事项：不知道就会出事故

    01发了就不管，失败没人知道
    现象
    Broker 出问题时接口照样返回成功，消息却没进 Kafka。
    原因
    send() 是异步的，消息进了内存批次就返回。失败要重试到 delivery.timeout.ms（默认 2 分钟）才交给回调。实测同步副本不够时，日志里反复打 NOT_ENOUGH_REPLICAS … retrying，回调最后拿到的是 TimeoutException。实测
    做法
    回调里处理失败：记录、落本地表、定时补发。关键消息用第二圈的事务发件箱。
    02acks=1，leader 一挂就丢最后一段
    现象
    实测：acks=1 发 200 条，全部回成功；follower 还没拉走时 kill -9 leader，新 leader 上一条都没有。实测
    原因
    acks=1 只等 leader 写进自己的日志。kafka-clients 2.x 默认就是 1，Spring Boot 2.5 及更早带的是 2.x。
    做法
    用 acks=all。别为了快改回 1：实测显式写 acks=1 时，默认开着的幂等会被悄悄关掉；再写 enable.idempotence=true 直接启动报错。
    03acks=all 也会丢：min.insync.replicas 还是 1
    现象
    实测：两个 follower 掉出 ISR 后，acks=all 照样回成功；leader 再一挂，分区下线，这些消息只在那一台上。实测
    原因
    “all”指的是 ISR 里的全部。ISR 缩到只剩 leader，就只等它自己。Broker 的 min.insync.replicas 默认是 1。
    做法
    topic 3 副本 + min.insync.replicas=2：同步副本不到 2 个就拒写，宁可报错也不假装成功。
    04自动建出来的 topic 只有 1 个副本、1 个分区
    现象
    往一个还不存在的 topic 发消息，没报错；后来那台 Broker 坏了，消息全没了。死信 topic 也一样，实测被自动建成 1 分区 1 副本。实测
    原因
    auto.create.topics.enable 默认 true，自动建时用 num.partitions=1、default.replication.factor=1。
    做法
    生产环境关掉自动建；用 kafka-topics.sh 或 NewTopic 显式指定分区数和副本数，死信 topic 也提前建。
    05先提交再处理，消息丢了还看不出来
    现象
    消费者重启后，有一段消息没处理过，消费进度却显示早读完了。
    原因
    offset 先交了，处理到一半崩溃。常见写法：手动提交写在业务前面；或者开自动提交，又把消息丢给线程池异步处理，下一次 poll() 就把 offset 交掉了。
    做法
    处理完再提交。Spring Kafka 2.3 起默认关掉 enable.auto.commit，按 AckMode.BATCH 在一批处理完后提交，别自己改回去。
    06处理完再提交，就一定会重复
    现象
    库存偶尔被扣两次。
    原因
    处理完、提交前崩溃或 rebalance，这批会被重新投递。Kafka 默认给的是“至少一次”。
    做法
    消费端幂等：订单号做唯一键；或建去重表，和业务在同一个事务里先插入再处理；或用状态机 UPDATE … WHERE status='待扣减'。
    07一批处理太久，被踢出组，越踢越乱
    现象
    日志里反复 rebalance，同一批消息被不同实例处理好几遍，积压越来越多。
    原因
    两次 poll() 间隔超过 max.poll.interval.ms（默认 5 分钟），就被认为卡死、踢出组；这批没提交，交给别人重做；它回来又触发一次 rebalance。一次最多拉 max.poll.records（默认 500）条。
    做法
    调小 max.poll.records，让一批在时限内做完；外部调用加超时；确实慢再调大 max.poll.interval.ms。
    08一条坏消息，默认重试 10 次后被跳过
    现象
    实测：某条消息一直抛异常，同一条连着处理 10 次，然后一行 Backoff FixedBackOff{interval=0, currentAttempts=10, maxAttempts=9} exhausted，这条就过去了。实测
    原因
    Spring Kafka 的 DefaultErrorHandler 默认不等待、再试 9 次，之后只记日志、提交 offset、跳过。
    做法
    配 DeadLetterPublishingRecoverer 把它转进死信 topic，加退避间隔，给死信 topic 配告警（配置见第二圈）。
    09新消费组上线，之前的消息一条没收到
    现象
    新加的短信组上线后，只收到上线之后的订单。
    原因
    一个组第一次消费、还没提交过 offset 时，按 auto.offset.reset 决定从哪读，默认 latest，只读新的。
    做法
    要补历史就设 earliest；或上线前用 kafka-consumer-groups.sh --reset-offsets 指定位置。
    10加了实例，消费速度没变
    现象
    积压了，把库存服务从 3 台加到 6 台，还是 3 台在干活。
    原因
    一个分区同一时间只归组里一个消费者。分区只有 3 个，多出来的拿不到。Spring 的 concurrency: 3 也算 3 个消费者。
    做法
    分区数按“高峰要几个消费者”提前定好、留余量。临时加分区会改变 key 到分区的映射，同一订单的新旧消息可能落在两个分区，顺序会乱一阵。
    11停了一周的消费组，回来时位置没了
    现象
    一个组停了 8 天，重启后要么跳过一大段，要么从头全部重放。
    原因
    消息默认保留 7 天（log.retention.hours=168）。组里没有活跃实例时，提交过的 offset 也只保留 7 天（offsets.retention.minutes=10080），过期后按 auto.offset.reset 重来。
    做法
    积压告警要远早于保留期；长期下线的组，恢复前先确认并手动设好 offset。

    第三圈

    优化和深处：副本怎么对齐、组怎么分、精确一次管到哪

    ISR 怎么进出，切换时怎么对齐

    • follower 超过 replica.lag.time.max.ms（默认 30 秒）没追上，leader 把它踢出 ISR；追上了再加回来。KRaft 下 Broker 心跳断了超过 broker.session.timeout.ms（9 秒），控制器直接把它移出 ISR，实测十几秒内就只剩 leader。
    • Leader Epoch（0.11 起）：每任 leader 有个任期号。切换后副本按“上一任写到哪”截断对齐，修掉了只靠 HW 截断时丢数据、副本不一致的问题。
    • ELR（KIP-966）：ISR 掉到 min.insync.replicas 以下时，被踢出的副本记进 ELR，表示“它有全部已提交的数据”，leader 挂了它能干净接班。实测 4.1 新集群默认开启：min.insync.replicas=2 时 kill -9 leader，follower 自动接班；=1 时分区直接下线。
    • unclean.leader.election.enable=true：没有合格副本时，让落后的副本当 leader，换回可用性，代价是丢数据。

    不刷盘，靠副本

    • log.flush.interval.messages 默认是 Long 的最大值：消息写进操作系统的页缓存就算写入，不等 fsync。
    • 所以“不丢”靠的是多份副本同时在内存或磁盘里。三个副本放在同一个机架、同一路电上，一起断电时，没刷到磁盘的部分可能一起没了。
    • 用 broker.rack 让副本分散到不同机架或可用区；真要每条刷盘，代价是吞吐大降。

    消费组怎么分区，rebalance 时谁停

    实例加入、离开、心跳超时（session.timeout.ms，3.0 起 45 秒，之前 10 秒）、处理超时、分区数变化，都会触发 rebalance。默认的 partition.assignment.strategy 是 [RangeAssignor, CooperativeStickyAssignor]，实际用 Range，走 eager 协议：所有实例先交出全部分区，⑤ 里实测看到的 revoked 全部 3 个就是它。

    少停一点

    • CooperativeSticky：只交出要挪的分区，其余照常消费。从 Range 换过来要分两次滚动发布，按官方升级说明做。
    • 静态成员 group.instance.id（2.3 起）：实例在 session.timeout.ms 内重启回来，不触发 rebalance，适合 K8s 滚动发布。
    • 新协议 KIP-848（Kafka 4.0 起正式可用）：消费者设 group.protocol=consumer，分配挪到 Broker 端做（默认 uniform 分配器），增量调整，不再整组停下。实测 kafka-clients 4.4.0 的默认值仍是 classic，要自己打开。

    “精确一次”管到哪

    • 幂等生产者：每个生产者有 Producer ID，每个分区的批次带序列号，Broker 丢掉重复的。只管同一个生产者实例、同一个分区的重试，进程重启换了 ID 就管不到。
    • 事务：transactional.id（Spring 里是 transaction-id-prefix），消费者设 isolation.level=read_committed（默认 read_uncommitted）。适合“读 Kafka → 处理 → 写 Kafka”，offset 和输出一起提交。
    • 管不到的：写数据库、调外部接口。Kafka 事务和数据库事务是两个事务，这部分还是靠业务幂等。

    batch.size16384一个分区一批最多 16 KB；调大能多攒，延迟略升
    linger.ms3.x：0 · 4.x：5等多久再发；攒批越多，请求越少

    面试官会怎么问

    Kafka 怎么保证消息不丢？
    • 生产者：acks=all、重试、处理回调里的失败。
    • Broker：3 副本、min.insync.replicas=2、不开 unclean 选举、副本跨机架。
    • 消费者：处理完再提交 offset。
    • 再补一句：acks=all 单独用不够，ISR 只剩 leader 时它等于 acks=1。
    怎么保证不重复消费？
    • 做不到“不投递重复”，只能做到“重复了不重复生效”。
    • 生产端开幂等（Producer ID + 序列号）挡住重试造成的重复。
    • 消费端是至少一次，崩溃和 rebalance 都会重投，用唯一键、去重表或状态机做业务幂等。
    • Kafka 事务的精确一次只覆盖 Kafka 到 Kafka。
    怎么保证顺序？
    • 只有分区内有序。要求有序的消息用同一个 key（订单号）。
    • 开幂等时 max.in.flight.requests.per.connection 不超过 5，重试也不乱序；没开幂等又要严格有序，得设成 1。
    • 消费端多线程处理时，按 key 分到固定线程；加分区会打乱 key 的映射。
    消费者比分区多会怎样？rebalance 有什么影响？
    • 多出来的消费者闲着。
    • rebalance 在实例进出、心跳超时、处理超时、分区变化时发生。eager 协议下整个组先交出全部分区，期间都停；还会造成重复消费。
    • 减少：CooperativeSticky、静态成员、控制单批处理时长、正常停机，Kafka 4 可以换 KIP-848 新协议。
    ISR、HW、LEO 是什么？
    • ISR：跟得上 leader 的副本集合（含 leader）。
    • LEO：每个副本下一条要写的位置。HW：ISR 里所有副本都有的位置，消费者只能读到 HW 之前。
    • acks=all 等的是 ISR 里的全部，所以 ISR 的大小决定了它有多可靠。
    线上积压了怎么办？
    • 先看是不是卡住了：消费报错重试、慢的外部调用、反复 rebalance。
    • 分区够就加实例或调大 concurrency；分区不够，加分区（注意顺序），或临时建一个分区更多的 topic，把消息转过去并行消费。
    • 同时确认积压不会超过 7 天的保留期。

    自测

    用一句话说出 Kafka 可靠性的精华。

    写够副本才算成功（acks=all + min.insync.replicas），处理完再挪书签（提交 offset），三段一起守，少一段都会丢。

    用 Redis Stream 做订单消息，疼在哪几处？

    消息在内存里，积压多了撑爆内存；AOF 每秒刷盘、主从异步复制，断电或切换会丢最后一点；一个 Stream 只在一个节点上，扩容要自己拆 key。

    想让两个实例分摊消费，最少要做什么？

    两个实例用同一个 groupId，topic 的分区数至少 2。分区数决定了组内最多几个实例能同时干活。

    头号坑：acks=all 为什么还会丢？

    “all”是 ISR 里的全部。Broker 默认 min.insync.replicas=1，follower 掉队后 ISR 只剩 leader，它写完就回成功，leader 再挂就丢了。要配 3 副本 + min.insync.replicas=2。

    改成“处理完再提交”之后，还剩什么问题？

    会重复：处理完、提交前崩溃或 rebalance，这批会再来一次。消费端要幂等。

    库存服务从 3 台加到 6 台没变快，为什么？

    topic 只有 3 个分区，一个分区同一时间只归组内一个消费者，多出来的 3 台拿不到分区。要先加分区（注意顺序会乱一阵），或者一开始就按高峰规划分区数。
