退款比付款先到：状态机、跳号暂存与过期副作用

去重表只认得“同一条来了两次”，认不出“两条换了顺序”。第一圈的版本守卫让订单状态只升不降，可积分这种每条都要算的、短信这种发了就收不回的，旧事件不能直接丢。办法是让订单服务给每一单的事件编连续序号，消费端按“已经处理到第几号”把来的事件分三类：旧的确认掉，下一号就做，跳号的先暂存，位点照常往前。暂存和放行要在同一把行锁下做；等不来的那一号，超时后去订单服务回查。

下一圈第一圈讲了去重表怎么写、顺序在哪几处被打乱、覆盖型用版本守卫、累加型只去重不能丢。留下一个口子：累加型事件先到的是退款怎么办？积分还没加，先扣就扣成负数；短信已经发了“付款成功”，退款又先到了。这一圈把加分区、重复、重平衡、并发、丢一条放在一起，看谁还站得住。

在全景第 8 站，三个服务各自处理订单事件。9527 付款后 10 分钟申请了退款，订单服务按顺序发出三条；积分服务收到的却是这样：

+798 和 −798 都得生效一次，而且余额不能为负（表上有 CHECK (points >= 0)）。退款先到，没东西可扣。

退款都已经知道了，再发一条“付款成功，积分已到账”，用户会以为退款没成。

订单视图：最后一条说了算

只要最终是 REFUNDED。第一圈的版本守卫就够用，这一页顺带复核。

还要扛住并发

重平衡时新旧两个消费者可能同时处理 9527 的两条事件，谁都不能把对方的结果盖掉。

②没有它会怎样：1000 单一起乱，第一圈的写法也错几十单

把 9527 的情况放大成 1000 单：30% 的单内部乱序，15% 的事件重复，10% 的事件在重平衡后重投，1% 的退款单丢了付款事件，两个线程并发处理（⑤ 有完整输出）。

S1 去重表 + 状态直接覆盖179～183 单26～29 单56～59 次后到的 PAID、CREATED 把 REFUNDED 盖掉；退款先到时扣成负数被 CHECK 拒绝，重试 3 次后放弃，付款后到又加上了 798

错在把“早到”当成了“失败”。退款没做错什么，只是来早了；重试几次就放弃，等于把一条合法事件扔掉了。第一圈“累加型只能去重，不能丢”这条规则，在乱序时被重试策略悄悄破坏了。

③相邻方案：六种写法，各管住了什么

写法重复覆盖型乱序累加型乱序副作用代价
去重表管住不管不管不重发，但顺序乱一张表
版本守卫（第一圈）管住管住旧的不能丢旧的不发，但跳号时会先发后面的一列版本号
可交换账本去重后管住不适用+798、−798 先后无所谓不管业务得允许余额暂时为负
事件只当通知，回查最新状态管住管住要自己算差额按最新状态发每条事件一次 RPC，订单服务被下游压
一单只走一条线（单分区单线程）不管源头之后都不乱就行同左同左加分区、重试 topic、重平衡一来就破
状态机 + 连续序号 + 暂存（本页）管住管住管住按序放行，可跳过过期的一列序号、一张暂存表、一把行锁、一个回查接口

选择规则：只有覆盖型（订单视图、搜索索引）就用版本守卫，别上暂存。累加型而且业务允许暂时为负，用可交换账本最简单。累加型不允许为负，或者有发了收不回的副作用，用本页的暂存。事件少、订单服务扛得住，回查最新状态也行。

④原理：按号排队，跳号的先存着

先知道这些
  • 连续序号和版本号的区别：版本号只要求“新的比旧的大”，跳着长也行；连续序号要求每单从 1 开始、每次只加 1。只有连续，消费端才看得出“中间缺了一号”。
  • outbox：改订单和写一行“待发事件”在同一个本地事务里，再由转发器发到 Kafka。见改库和发消息怎么一起成功。
  • SELECT … FOR UPDATE：读这一行的同时给它加行锁，别的事务想锁同一行就得等到本事务提交。
  • 重平衡时的“僵尸”消费者：处理太慢超过 max.poll.interval.ms 被踢出组，分区给了别人，它手上那批还在跑。同一单的事件就会被两个进程同时处理。见积压那页。

机制 1：来一条，先和“处理到第几号”比

机制 2：状态机管“能不能”，序号管“轮没轮到”

  • 序号告诉你这条是第几步：旧的、正好、早到。
  • 状态机告诉你这一步从当前状态走不走得通。序号对上了、转换却不合法（比如 CREATED 直接到 REFUNDED），说明上游有 bug：进死信并告警，不暂存，暂存了也永远等不到。
  • 只有状态机不够：PAID 之后可能是 SHIPPED 也可能是 REFUNDED，当前是 PAID 时来了 REFUNDED，分不清是“中间还缺一个 SHIPPED”还是“本来就直接退款”。
  • 只有序号也不够：上游编错了号、漏发了一种状态，序号照样连续，错的转换会被照单全收。

机制 3：暂存和放行，必须排在同一把锁后面

只靠 CAS提交时 WHERE last_seq = 旧值

CAS 只防住“两个人都改 last_seq”，防不住“一个改、一个往暂存里写”。B 读到的 1 是旧的，它的判断在 A 提交那一刻就过期了。

先锁这一单SELECT … FOR UPDATE

同一单的所有判断排成一列，判断用的 last_seq 永远是最新提交的那个。不同订单之间不互相等。

约束：“该暂存还是该生效”取决于 last_seq，而 last_seq 随时会被别人改。读和据此做的写之间不能让别人插进来，所以要锁。实测：只靠 CAS 每次有 3～6 单卡在暂存里，加了行锁一次都没有（⑤）。

机制 4：等不来的那一号，超时回查

暂存只解决“来晚了”。要是 2 号永远不来（转发器那条卡住了、进了上游的死信），9527 就永远停在 1 号。所以暂存表每一行都要记进来的时间，后台定时扫：最老的暂存超过阈值（比如 5 分钟），就调订单服务 GET /orders/9527/events?afterSeq=1，把缺的那几条拿回来，按同一套逻辑处理一遍。重复的会被当成旧的确认掉，所以补多了也没事。

机制 5：发了收不回的事，在同一个事务里只“登记”

  • 先登记，后发送：短信不在处理逻辑里直接调接口，而是往本库的 sms_outbox 写一行，和积分、last_seq 同一个事务提交；另一个线程再去真正发送。CAS 失败回滚，这一行也跟着没了，不会多发。
  • 放行时往后看一眼：放行 2 号（PAID）时，暂存里已经躺着 3 号（REFUNDED），说明“付款成功”已经过期，就不登记这条短信，只发“退款成功”。⑤ 实测 1000 单里有 80～83 条因此没发。
  • 看不到的就管不了：2 号生效时 3 号还没来，“付款成功”照发；10 分钟后再发“退款成功”是正常的业务顺序，不算错。

为什么这样设计：序号只能在源头编

源头编号本页

订单服务改 9527 那一行时，seq = seq + 1，和 outbox 那行一起提交。数据库的行锁已经把同一单的修改排成一列，这个顺序就是真相。消费端只是照着号重排。

消费端自己排按事件时间戳或到达顺序

两台订单服务实例的时钟差几毫秒，同一毫秒还有两条；到达顺序本身就是被打乱的那个东西。消费端拿不到真相，只能猜。

约束：只有写订单那一行的事务知道真正的先后。所以序号必须在那个事务里生成，而且每次状态变化都必须发一条事件（漏发一种，消费端就会永远等那一号，见 ⑥ 坑 4）。

积分服务处理一条事件一个本地事务；超时、监控和回查放到 ⑥
-- 1. 锁住这一单，拿到处理到第几号
SELECT status, last_seq FROM order_progress WHERE order_id = ? FOR UPDATE;
-- 2. 分三类
--    n <= last_seq      ：什么也不做
--    n >  last_seq + 1  ：INSERT INTO pending(order_id, seq, payload, arrived_at) …
--    n =  last_seq + 1  ：状态机检查 → 生效 → 循环放行 pending 里的 last_seq + 1
UPDATE order_points SET points = points + ? WHERE order_id = ?;      -- 有 CHECK (points >= 0)
INSERT INTO sms_outbox(order_id, kind) VALUES (?, ?);                -- 暂存里有更新的就不登记
DELETE FROM pending WHERE order_id = ? AND seq = ?;
UPDATE order_progress SET status = ?, last_seq = ? WHERE order_id = ?;
COMMIT;
-- 3. 然后才确认 Kafka 位点（或者位点也存这个库，见第一圈）

⑥细节·规范·优化

第一圈

注意事项：不知道就会出事故

1早到的事件按“失败”重试，几次后扔进死信← ④ 三种情况
现象
退款先到，扣成负数被拒，重试 3 次进死信；付款后到加上 798，积分多给了。⑤ S1、S2 积分错 25～29 单
根源
早到不是错误，是跳号，应该暂存。
做法
按序号分三类；只有“序号对上了、转换不合法”才进死信。
2一条事件的几件事放在一个事务里，一件失败全回滚← ④ 三种情况
现象
版本守卫写对了，状态还是停在 PAID。⑤ S2 状态错 35～37 单
根源
扣积分违反 CHECK，把同一事务里“改成 REFUNDED”也回滚了。
做法
同一事务没问题，前提是不让合法事件失败：先分类，再生效。
3暂存和放行不在一把锁下← ④ 机制 3
现象
没有丢事件，也有单卡在暂存里，直到回查才动。⑤ S3 每次 3～6 单
根源
判断“该不该暂存”用的 last_seq 被别的事务改了。
做法
SELECT … FOR UPDATE 锁住这一单再判断；或者保证同一单永远只在一个线程里处理。
4序号不连续← ④ 机制 2
现象
用 updated_at 或全库自增 id 当序号，消费端分不清是跳号还是本来就不连续；或者有人直接改库没发事件，这一单永远等那一号。
根源
看出“缺了一号”的前提，是每单从 1 开始、每次加 1、每次变化都发事件。
做法
序号在改订单的同一个事务里 +1 并写进 outbox；禁止绕过服务直接改订单表。
5暂存没有超时← ④ 机制 4
现象
丢了一条事件，这一单永远停着，用户的积分一直不到账；暂存表越来越大。⑤ 丢的 10 单靠回查才补齐
根源
暂存只能等“晚到的”，等不到“不会来的”。
做法
暂存记进来的时间；最老一条超过阈值就回查订单服务补拉。
6处理逻辑里直接调短信接口← ④ 机制 5
现象
CAS 失败或锁等待超时，事务回滚重来，短信已经发出去了，重来一次又发一条。
根源
外部调用不跟着本地事务回滚。
做法
只往本库的 sms_outbox 登记，事务提交后另一个线程去发，发送端再按 (order_id, kind) 去重。
第二圈

使用规范

事件里带 orderId 和每单连续的 seq

在订单服务改那一行的同一个事务里生成，和 outbox 一起提交。

防的是消费端只能猜先后（坑 4）。

消费端三张表放同一个库

order_progress（last_seq、状态）、pending（暂存）、业务表和 sms_outbox，一个事务里改。

防的是暂存了、进度却没跟上，或者反过来。

先锁这一单，再判断

判断和写之间不让别人插进来。

防的是坑 3 的竞态。

暂存要有三个监控

暂存总条数、最老一条的年龄、回查次数。最老年龄超过阈值就告警。

防的是悄悄卡住几千单没人知道。

订单服务提供“按序号补拉”接口

GET /orders/{id}/events?afterSeq=n，从 outbox 或事件表里查。

防的是丢了一条只能人工改数据。

非法转换进死信并告警

序号对、转换不对，是上游的 bug，不是乱序。

防的是把 bug 当成早到，暂存到天荒地老。

第三圈

深处：什么时候值得，代价在哪

行锁的代价：热点订单

同一单的事件排队处理，不同订单互不影响。普通订单一单只有几条事件，排队几乎没有代价；一个大客户的“批量订单”如果共用一个聚合 id，所有事件都排在一把锁后面。按真正的业务聚合（一个订单）编号，别按客户编号。

暂存放在哪

放业务库最稳：和进度同一个事务。放内存：重平衡一来就丢了。放一个 Kafka 重试 topic：又回到了“重试 topic 打乱顺序”（第一圈坑 7），等于把问题挪了个地方。

和 TCP 是同一个结构

每单一个接收窗口：序号、重复丢弃、乱序缓冲、超时重传（这里是回查）。不同的是 TCP 的缓冲在内存里，丢了能让对方重发；这里的“对方”是订单服务，所以补拉接口是必需的。

什么时候别用这一套

只有覆盖型下游，版本守卫就够；积分允许暂时为负，可交换账本更简单；一单的事件一天就一两条，事件只当通知、回查最新状态最省事。这一套的价值在“累加 + 不许为负 + 有副作用”同时出现的地方，比如积分、余额、库存、券。

用到 ⑥ 坑 5、第二圈监控

自测

1. 用一句话说出这一页的精华

订单服务给每单的事件编连续序号；消费端按“处理到第几号”分三类：旧的确认掉、下一号经状态机检查后生效并放行暂存、跳号的暂存且照常确认位点；暂存和放行锁住同一单再做，等不来的超时回查。

2. 第一圈的版本守卫已经管住了状态，为什么积分还会错？

版本守卫的做法是“旧的丢掉”，只对覆盖型成立。积分是累加型，每条都要算，退款先到时既不能丢也不能先扣（余额不许为负），只能等付款来了再做。

3. S2 状态错 35～37 单，根源是哪条原理？

④ 机制 1：早到的退款被当成失败处理。扣积分违反 CHECK，同一事务里的状态更新一起回滚，重试几次后放弃，状态就停在了 PAID。

4. 预测：S4 去掉 FOR UPDATE，但保证同一个订单永远只在一个线程里处理（按 orderId 取模分线程），还会卡住吗？

不会因为竞态卡住。机制 3 的竞态需要同一单的两条事件被两个事务同时判断；同一单只在一个线程里处理，判断天然排成一列，效果和行锁一样。但重平衡时新旧两个进程仍可能同时处理同一单（僵尸），所以跨进程时还是要锁。

5. 预测：订单服务漏发了 SHIPPED（直接改库），9527 的序号变成 1、2、4（REFUNDED 是 4 号），积分服务会怎样？

4 号到了，last_seq 是 2，判定为跳号，暂存。3 号永远不来，超时后回查订单服务：如果事件表里也没有 3 号，回查也补不上，只能告警人工处理。这就是坑 4：每次变化都必须发事件、序号必须连续。

6. 预测：9527 的 2 号和 3 号被两个线程同时处理，S4 里谁先拿到锁会影响最终积分吗？

不影响。2 号先拿到锁：生效，查暂存没有 3 号，提交；3 号接着拿到锁，读到 2，正好是下一号，生效。3 号先拿到锁：读到 1，暂存；2 号接着拿到锁，生效后放行暂存里的 3 号。两条路最后都是 last_seq = 3、积分 0。区别只在“付款成功”短信：后一条路会因为暂存里已有退款而不发。

7. 放回全景：第 8 站前后各发生了什么？这一页的东西坏了，整条链路会怎样？

第 8 站之前，第 7 站的消费组按位点从分区拉到这批消息；第 8 站之后，第 9 站提交位点。这一页让第 8 站对“乱序、重复、并发”免疫：位点可以照常往前提交，不会因为一条早到的事件卡住分区（第 10 站不涨 LAG）。如果暂存没有超时、序号不连续，第 9 站照样提交了位点，消息在 Kafka 里已经“处理完”，可业务状态卡在暂存里：Kafka 的监控一切正常，用户的积分却一直没到账，只有暂存表的监控能看出来。

档位：标准。实测：H2 2.4.240 内存库代替 MySQL（唯一键、CHECK 约束、行锁、READ COMMITTED 语义一致），代码按 JDK 17 编译运行（H2 2.x 需要 Java 11，所以没有按 JDK 8 编译），本机 2 核 ARM。ReorderChaos 用固定种子 42 造事件流，两个线程并发处理，四种写法各跑 4 次；事件流每次相同，线程调度不同，页上给的是 4 次的范围。Kafka 本身怎么打乱顺序（加分区、重试 topic、线程池），见第一圈页面的 Kafka 4.x 真集群实测。

按文档和推理：Resequencer 出自 Hohpe 和 Woolf 的《企业集成模式》；SELECT … FOR UPDATE 的行锁语义在 MySQL InnoDB 和 H2 中一致；“僵尸”消费者的来由见 Kafka 文档 max.poll.interval.ms 一节。
