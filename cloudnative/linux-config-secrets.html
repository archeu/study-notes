137、143 和那份没加密的密码：Linux 信号、启动脚本、配置和密钥

放进容器以后，Java 进程还是一个普通的 Linux 进程：它怎么被启动（谁是 1 号进程）、怎么被叫停（信号和退出码）、怎么拿到配置和密码（环境变量、文件、ConfigMap、Secret）。前几页的优雅停机、回滚、OOM 排查能不能按设计工作，最后都落在这几件基本功上。本机 kind 实测：启动命令少写一个 exec，删一个 Pod 要等满 30 秒再被强杀；改了 ConfigMap，挂成目录的文件 60 秒左右才变，环境变量和 subPath 挂载永远不变；Secret 在 API 里只是 base64，在 etcd 里直接搜得到明文。

②常见笨办法，以及它们为什么看起来没问题

笨办法为什么看起来没问题真正的后果
启动脚本最后一行 java $JAVA_OPTS -jar app.jar，没有 exec应用照常启动、照常服务shell 是 1 号进程，SIGTERM 到不了 java；实测 每删一个 Pod 都要等满 30 秒被强杀，优雅停机从没跑过
停服务先 kill -9停得快关闭钩子、优雅停机、刷日志、提交位点全部跳过
数据库密码写在 application-prod.yml，提交进 Git部署方便，“仓库是私有的”所有能读仓库的人、所有 CI 日志、所有 fork，都拿到了生产密码；改密码要改代码

进容器 apt-get install 排查工具装上就能用非 root 用户装不了；装了也只在这个 Pod 里，重启就没了，还改动了正在跑的生产容器
不懂这一点时的典型误用：以为 Kubernetes 的 Secret 是加密的，于是放心地把它提交进部署仓库。它只是 base64 编码，任何人 base64 -d 一下就是明文（⑤ 第 3 步）。

③工具和路线

要做的事用什么记住一句话
让 java 收到信号启动脚本最后一行 exec java …；或者 Dockerfile 用 exec 形式；需要回收子进程时用 tini1 号进程必须是 java，或者是会转发信号的 init

④背后的机制：进程只认信号、环境变量和文件

先知道这些
  • 信号：内核发给进程的一个编号。SIGTERM（15）是“请你退出”，进程可以接住它、收拾完再走；SIGKILL（9）是“立刻消失”，进程接不住。kill -l 能列出全部。
  • 退出码：进程结束时留下的 0～255 的数字，0 表示正常。被信号杀死的进程，按惯例报告为 128 + 信号号。
  • 1 号进程：容器里第一个进程，在它自己的 PID 命名空间里编号是 1。容器运行时只给它发信号，它退出，容器就结束。

kubectl delete pod 以后：同一个 SIGTERM，三种结局

为什么 sh 当 1 号进程就收不到？Linux 对 PID 命名空间里的 1 号进程有一条特殊规则：从外面（容器运行时）发来的信号，只有它自己装了处理函数的才会投递，否则直接丢弃（SIGKILL 除外）。普通 sh 没给 SIGTERM 装处理函数，也不会把信号转给子进程 java。exec 让 java 直接替换掉 sh、继承 1 号进程的位置，而 JVM 一启动就给 SIGTERM 装了处理函数（关闭钩子就挂在它上面）。JVM 处理完 SIGTERM 退出，退出码按“被信号结束”报成 128 + 15 = 143。

配置怎么到进程手里：三条路，三种更新方式

环境变量是进程启动那一刻由内核复制进去的，进程活着时外面改不了它，这是 Linux 的规矩，不是 Kubernetes 的限制。目录挂载能更新，是因为 kubelet 每隔一段时间（同步周期加上缓存时间，⑤ 实测一分钟左右）把新内容写进一个新目录、再原子地切换符号链接，所以应用不会读到写了一半的文件。subPath 是在创建容器时把一个具体的文件绑定挂载进去，原子切换的那个符号链接它跟不上。Secret 走的是同一套机制，区别是挂载在 tmpfs（内存）里，不落节点磁盘。

Secret 在哪几处是明文

在哪样子谁能看到怎么收紧
部署仓库（Git）你提交什么就是什么所有能读仓库的人，永远（历史里删不掉）只提交加密后的（Sealed Secrets）或只提交引用（External Secrets）
API（kubectl get secret -o yaml）base64：czNjcjN0LXB3 实测有这个命名空间 get secrets 权限的人RBAC 收紧；base64 不是加密
etcd 磁盘实测 直接搜到 s3cr3t-pw能读 etcd 或它的备份的人开静态加密（EncryptionConfiguration，最好接 KMS）
Pod 里的文件明文，挂在 tmpfs 上 实测能 exec 进容器的人只读挂载，文件权限收紧
Pod 里的环境变量明文 实测能 exec 的人；还会出现在 /proc/<pid>/environ、子进程、崩溃转储和“打印全部环境变量”的日志里能用文件就别用环境变量

为什么这样设计

选中的：平台只用 Unix 的老原语和进程打交道

信号、环境变量、文件，是所有语言、所有程序都懂的接口。Kubernetes 用它们给配置、发停止指令，应用不用引入任何平台 SDK，同一个镜像放在 Docker、虚拟机、Kubernetes 里都能跑（十二要素应用里“配置放在环境里”就是这个意思）。

被放弃的：应用直接调平台 API

应用自己调 Kubernetes API 读 ConfigMap、监听变化（Spring Cloud Kubernetes 能这么做），更新可以秒级、也更灵活；代价是应用和平台绑在一起，每个 Pod 都要有读 API 的权限，平台一换，代码就要改。

决定胜负的约束：平台要能管住任何语言写的任何程序。代价是这些原语都很朴素：信号只是一个数字，1 号进程有特殊规则；环境变量启动后不能改；文件更新要等同步、要应用自己重读；Secret 默认只是编码。每一条朴素，都需要你知道并补上。

看懂这次运行
  • 第 1 步：三个 Pod 收到的是同一个 SIGTERM。sh 那个整整等了 30 秒，最后是 SIGKILL 结束的，Spring 的优雅停机根本没机会跑；加了 exec，0.6 秒；脚本用 trap 自己处理，2.3 秒里做完了“收尾”（这里是 sleep 1）。
  • 第 2 步：同一个 Pod 里，同一个键，三种读法给出了不同的答案：env=off dir=on subpath=off。全景第 4 站要是靠改 ConfigMap 来改 JAVA_OPTS（环境变量），不重建 Pod 就永远不生效。
  • 第 3 步：base64 一行命令就解开了；etcd 的数据文件里也是明文，kind 默认没开静态加密，很多自建集群也一样。
  • 第 4 步：kubectl debug --target 起的临时容器和应用容器共享进程空间，自带工具，不用往生产镜像里装东西。要用 jcmd，就用一个带 JDK 的镜像当临时容器，而且要和应用同一个用户（Arthas 那页坑 4）。

⑥刻意练习：由易到难，做对了会看到什么

练习 1 · 易写一个合格的 entrypoint.sh← ④ 1 号进程的规则
要求
第一行 set -euo pipefail；按环境变量 APP_ENV 拼出 JAVA_OPTS（prod 加 -XX:MaxRAMPercentage=75 -XX:+ExitOnOutOfMemoryError）；最后一行 exec java $JAVA_OPTS -jar order-svc.jar。
做对了
kubectl exec … cat /proc/1/cmdline 是 java；time kubectl delete pod 在 2 秒以内；日志里能看到 Spring 的 “Commencing graceful shutdown”。
练习 2 · 易看懂一个进程接住了哪些信号← ④ 只投递装了处理函数的
要求
用临时容器看 /proc/1/status 里的 SigCgt（接住的信号的位图），分别对 sh 和 java 当 1 号进程的两个 Pod 看一次。
做对了
java 那个的位图里第 15 位（SIGTERM）是 1；sh 那个是 0。这就是 ⑤ 第 1 步一个 0.6 秒、一个 30 秒的原因。
练习 3 · 中改配置就自动滚动← ④ 环境变量启动后不变
要求
给 order-svc 的 Pod 模板加一个注解 checksum/config，值是 ConfigMap 内容的 sha256（Helm 里常用的写法）。改 ConfigMap 时同时更新这个注解。
做对了
改完配置 kubectl apply，Deployment 开始滚动；新 Pod 里环境变量是新值。没加注解时，同样的操作什么都不会发生。
练习 4 · 中密码从环境变量换成文件← ④ 环境变量会被到处带走
要求
Secret 挂到 /etc/secrets，Spring Boot 加 spring.config.import=optional:configtree:/etc/secrets/，配置里用 ${password} 读取；删掉 DB_PASSWORD 环境变量。
做对了
应用照常连上数据库；kubectl exec … env 里找不到密码；/actuator/env 里这一项显示为 ******。
练习 5 · 难给 etcd 里的 Secret 加密← ④ etcd 默认存明文
要求
用 kind 的 kubeadmConfigPatches 给 API Server 配一个 EncryptionConfiguration（aescbc 或 secretbox），重建集群，重新创建 Secret。
做对了
⑤ 第 3 步的 etcdctl 搜不到 s3cr3t-pw，看到的值以 k8s:enc:aescbc:v1: 开头；kubectl get secret 照样能读出来（加密的是存储，不是 API）。

顺手记住的几个坑

  • 脚本里起了后台进程（java … & 再 wait）：1 号进程是 shell，信号照样到不了 java；真要多个进程，用 tini 当 1 号进程转发信号、回收僵尸进程。
  • 137 有两种来历：Reason: OOMKilled 是内核因为内存杀的，Reason: Error 多半是宽限期满被强杀的（比如 ⑤ 的 sh 那个）。先看 Reason，再看退出码。
  • Secret 和 ConfigMap 的大小上限约 1 MiB：大的证书链、模型文件别往里塞。
  • 打印全部配置的调试日志：环境变量里的密码会跟着进日志平台。

自测

1. 用一句话说出这一页的精华

平台只通过信号、环境变量和文件这几个 Unix 原语管理进程：1 号进程必须是能处理 SIGTERM 的那个，退出码大于 128 先想是哪个信号；环境变量启动后不变，挂载的文件延迟更新；Secret 默认只是编码，Git、etcd、环境变量里都可能是明文。

2. 启动脚本不写 exec，为什么平时看不出问题？

启动、服务都正常，只有“停”的时候不正常：SIGTERM 被 sh 丢掉，等满宽限期被 SIGKILL。平时发布只是慢一点、偶尔断几个请求，很容易被当成网络抖动。

3. 为什么改了 ConfigMap，JAVA_OPTS 不变？根源是 ④ 的哪一条？

环境变量是进程启动（exec）那一刻复制进去的，进程活着时外面改不了。要生效只能重建 Pod，所以要么让配置变更触发滚动（练习 3），要么把配置改成挂载文件、应用自己重读。

4. 预测：preStop 写成 sleep 40，terminationGracePeriodSeconds 保持默认 30，删除 Pod 会怎样？

preStop 的时间算在宽限期里。30 秒到了 preStop 还没跑完，kubelet 只再给一次大约 2 秒的延长：这时 java 才收到 SIGTERM，2 秒内停不下来就被 SIGKILL。优雅停机多半做不完，退出码可能是 143，也可能是 137。所以宽限期要大于 preStop 加优雅停机的时间。

5. 预测：Exit Code 134、Reason: Error，日志最后几行是 A fatal error has been detected by the Java Runtime Environment。发生了什么，去哪找线索？

134 = 128 + 6，SIGABRT：JVM 自己崩了（常见于本地代码、JNI、某些 JVM bug），它会写一个 hs_err_pid<pid>.log。在容器里这个文件默认写在工作目录，容器一重启就没了，所以要用 -XX:ErrorFile= 指到挂载的卷上。

6. 放回全景：第 4 站前后各是什么？如果 JAVA_OPTS=-Xmx1g 放在 ConfigMap 里（通过环境变量注入），而 17:47 值班用的是 kubectl rollout undo，会怎样？换成 git revert 呢？

前面是第 3 站推镜像，后面是第 5 站 Deployment 建新 ReplicaSet。rollout undo 只把 Pod 模板换回 1.8.3，ConfigMap 不在它管的范围里；新起的 Pod 启动时读到的还是 -Xmx1g，雷还在。git revert 会把镜像 tag 和 ConfigMap 一起改回去，镜像 tag 变了就会滚动，新 Pod 读到老配置，这次能回去；但如果那次提交只改了 ConfigMap、模板没变，就不会滚动，已经在跑的 Pod 的环境变量还是 -Xmx1g，要靠练习 3 的注解。全景第 11 站“常出的事”说的就是这件事。

档位：标准。本机跑过（2 核 ARM 虚拟机，kind v0.33.0 / Kubernetes v1.37.0，busybox:1.37.0，order-svc 镜像来自 Docker 那页）：./run.sh 完整两次（第一次改了第 4 步的说明文字后重跑），⑤ 的输出来自第二次；两次唯一不同的是 ConfigMap 生效时间，67 秒和 60 秒。练习 2～5 的“做对了会看到什么”按文档和机制写，本页没有逐一跑过。退出码解码器的规则在 node 里跑过。

按文档：Linux 的 pid_namespaces(7)：命名空间的 init 进程只接收它装了处理函数的信号（从祖先命名空间发来的 SIGKILL、SIGSTOP 除外）；Pod 删除时先跑 preStop、再发 SIGTERM，宽限期默认 30 秒，preStop 的时间算在宽限期里；ConfigMap 卷按 kubelet 同步周期加缓存时间更新，以环境变量或 subPath 使用的不会更新；Secret 默认以 base64 存在 API 里，需要 EncryptionConfiguration 才会在 etcd 里加密；ConfigMap 和 Secret 单个大小上限 1 MiB。
