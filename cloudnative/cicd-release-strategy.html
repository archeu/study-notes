换版本不断流、出事能秒回：CI/CD 与滚动、蓝绿、金丝雀

一次发布要同时做到三件事：交出去的东西可信（每次合并都走同一条流水线，产出一个不可变的镜像）；换的时候用户无感（不断流）；出了事能马上回到上一个好版本。滚动、蓝绿、金丝雀三种策略，是在“多花多少机器”“出事影响多少人”“回滚有多快”之间做的不同取舍。本机 kind 集群实测：滚动发布没有 preStop 时失败 5 次，加上 5 秒的 preStop 降到 0；滚动回滚要 27 秒；蓝绿要同时跑 8 个 Pod，但切换和回切都在 1 秒内、0 失败；按副本数做金丝雀，4 + 1 个 Pod，新版实际分到 19.7% 的请求。

全景：一次发布，从合并到回滚 · 第 1、4、11 站地图：J14 · CI/CD 与发布策略：滚动、蓝绿、金丝雀过关标准：发布出问题时 1 分钟内回滚

这一页的位置J14 第 5 个知识点，把前四页串起来：镜像由流水线产出，Deployment 负责滚动，探针决定新 Pod 什么时候接流量，启动速度决定每一轮多久。J10 的灰度发布是在网关和注册中心层面按标签分流，这一页从 Kubernetes 这一层看同一件事。

①要解决的问题：全景第 1、4、11 站

第 1 站 · CI交出去的可信每次合并都同一条路：编译、测试、打镜像，坏的停在这里
第 4、9 站 · CD换的时候无感部署是改 Git 里的一行，集群自己把版本换过去，不断流
第 11 站 · 回滚1 分钟内回去17:46 定位到是 14:06 的发布，下一分钟就要回到 1.8.3

②不用它会怎样

做法疼在哪
在自己电脑上 mvn package，传到服务器线上跑的是谁电脑上、哪次改动打出来的包，说不清；测试有没有跑过，也说不清
停机发布：凌晨两点挂公告，全停、全换、全起每次发布都是一次计划内的故障；发布越少越怕，攒的改动越多，出事越大
出了问题“往前修”：现场改代码，再发一版在最紧张的时候写最没把握的代码；修的这一版本身也没走完整的测试
CI 里直接 kubectl apply 到生产流水线手里攥着生产集群的最高权限；集群里现在是什么样，只能去集群里看，Git 里没有

缺的是：一条每次都一样的流水线（构建一次，同一个镜像一路发到生产），一种“新旧版本可以同时在线”的替换方式，以及一个随时能回去的上一版。

不懂这一点时的典型误用：说是“金丝雀”，其实只是先发一个 Pod，然后没人盯它的指标，十分钟后照样全量。这只是一次慢一点的滚动，出事时影响面一点没小。金丝雀的精华不在“先发一个”，而在“用指标决定继续还是撤”。

③几种流派

策略怎么换额外资源出事影响面回滚新旧并存
重建（Recreate）先全停，再全起0全部，而且有停机再重建一次不并存
滚动一个个替换（Deployment 默认）maxSurge 个逐步扩大到全部再滚一遍：实测 27 s并存几分钟
蓝绿新的一套全起好，入口一下切过去再来一整套切过去就是全部切回去：实测 < 1 s切换那一瞬间
金丝雀先给一小部分流量，看指标，逐步放大几个只有那一小部分撤掉金丝雀：秒级并存到放完
特性开关代码先上线但关着，开关决定谁能用0按用户、按比例关开关新旧逻辑一直在代码里

选择规则：日常发布用滚动（便宜，Deployment 自带）；改动风险大、有可靠指标的用金丝雀；资源充足、要求回滚瞬间完成的关键服务用蓝绿；业务功能的开关交给特性开关，和部署解耦。它们可以叠加：全景里 order-svc 用滚动，回滚走 git revert。本页学这三种部署策略和它们背后的流水线。

④核心取舍：构建一次、拉式部署、渐进替换、随时可退

先知道这些
  • CI（持续集成）：每次合并都自动编译、测试，保证主干随时可发布。CD（持续交付 / 部署）：把通过的产物自动送到环境里，生产这一步可以要人点批准。
  • GitOps：集群该是什么样，写在一个 Git 仓库里；集群里的控制器（Argo CD、Flux）不停地把集群对齐到 Git。这就是 控制循环 再往外推一层。

流水线：构建一次，集群自己来拉

Git 历史就成了发布记录：谁、什么时候、把哪个 tag 发到了哪个环境，一目了然；回滚就是 git revert 那个提交，Argo CD 把集群对齐回去。这也是全景第 11 站不用 kubectl rollout undo 的原因：集群只是 Git 的投影，绕过 Git 改集群，迟早被改回去（K8s 那页坑 3）。

三种策略：流量怎么从老版本挪到新版本

三种策略回答的是同一个问题：新版本有问题、而告警还没响的这段时间里，有多少用户在用它。滚动让这个比例一级级涨上去，涨到 100% 往往只要几分钟，比告警快；蓝绿一切就是 100%，但退回去最快；金丝雀把比例压在一个小数上，直到指标证明没问题。

滚动和金丝雀还有一个共同的前提：新旧版本同时在线。同一时刻，有的请求被 1.8.3 处理、有的被 1.8.4 处理，它们读写同一张表、同一个缓存、同一个队列。所以接口和数据结构必须前后兼容：新版本加的列，老版本要能忽略；新版本写的状态值，老版本要能读懂（⑥ 坑 2）。

为什么这样设计

选中的：小步、可观察、可撤回

不可变的镜像保证“回去”有一个确定的目标；拉式部署和 Git 保证“回去”只是一个提交；渐进替换和探针保证换的过程中容量不降；金丝雀把“出了事影响多少人”变成一个你能设定的数字。每一步都可以停下来、退回去。

被放弃的：一次换完，出事再修

停机发布、一次性全量替换、出事往前修：前提是“这次改动没问题”。可发布之所以危险，正是因为没人能保证这一点。把赌注压在“不会出事”上，出事时就只剩手忙脚乱。

决定胜负的约束：测试永远测不全，有些问题只在真实流量下出现（全景里的内存雷到了晚高峰才响）。所以不追求“发布不出错”，而追求“出错时影响小、退得快”。代价是：新旧并存要求兼容，蓝绿要双倍资源，金丝雀要有靠得住的指标和足够的流量。

实验台：同一个 bug，三种策略各让多少订单失败

先猜：1.8.4 有个 bug，会让 5% 的下单失败；告警要 5 分钟才响，响了马上回滚。4 个副本，每个新 Pod 23 秒 Ready。哪种策略失败的订单最少？

估算模型：滚动按 maxSurge 1 / maxUnavailable 0，每轮一个新 Pod，回滚也一轮一个；蓝绿在新的一套全部 Ready 后一次切换，回切按 1 秒；金丝雀固定 1 个新 Pod，按副本数分到 1/(n+1) 的流量，撤掉按 1 秒。“受影响的请求”= 新版本拿到的流量占比在时间上的累计 × 每秒下单 × 5%。⑤ 实测的是切换、回切的耗时和失败数，不是这张表。

⑤套进场景：三种策略在 kind 里各发一次、回一次

还是 Docker 那页的两个镜像（1.8.3、1.8.4），还是那个三节点 kind 集群。集群里放一个 busybox 当用户，每 50 毫秒调一次接口，记下拿到的版本号或者失败。依次做：滚动发布（没有 preStop、有 preStop）和回滚，蓝绿切换和回切，按副本数的金丝雀。流水线和 Argo CD 的配置作为示例放在仓库里，没有在本机跑：本机没有 GitHub Runner，也没有装 Argo CD。

== 1. 滚动发布：没有 preStop 对 有 preStop（4 副本，maxSurge 1 / maxUnavailable 0）
没有 preStop：1.8.3 → 1.8.4 用了 26.7 s；共 281 次：1.8.3=176 1.8.4=100 fail=5
有 preStop（sleep 5）：1.8.3 → 1.8.4 用了 28.1 s；共 485 次：1.8.3=214 1.8.4=271 fail=0
回滚（rollout undo，有 preStop）：用了 27.0 s；共 500 次：1.8.3=267 1.8.4=233 fail=0

== 2. 蓝绿：两套各 4 个都起好，改 Service 的 selector 一下切过去，再切回来
同时在跑的 Pod：8 个（平时的两倍）
切到绿：1 秒内连续拿到 1.8.4；10 秒里 共 177 次：1.8.3=15 1.8.4=162 fail=0
切回蓝（回滚）：1 秒内连续拿到 1.8.3；10 秒里 共 170 次：1.8.3=166 1.8.4=4 fail=0

== 3. 金丝雀（按副本数）：4 个 1.8.3 + 1 个 1.8.4，同一个 Service
30 秒里 共 506 次：1.8.3=406 1.8.4=100 fail=0
新版占比 19.7%（按副本数应为 20%）
看懂这次运行
  • preStop 只多花了 1.4 秒的滚动时间，却把失败从 5 次降到 0：老 Pod 先从地址表里摘掉，各节点的 kube-proxy 有 5 秒时间更新规则，之后进程才收到 SIGTERM。老 Pod 终止中不算在 maxSurge 里，所以下一轮不用等它，总时间几乎不变。
  • 滚动回滚和滚动发布一样慢（27 秒），因为它就是反方向再滚一遍。蓝绿的回切是改一个字段，客户端在 1 秒内全部拿到老版本，代价是那 8 个 Pod。
  • 蓝绿切换后还有 15 次请求拿到 1.8.3：各节点 kube-proxy 更新规则要一点时间，而且已经建立的 keep-alive 连接还连着老 Pod。没有失败，是因为老的那套还在跑。
  • 金丝雀的 19.7% 很接近 1/5，但“按副本数分”只能做到这么粗：要 5% 就得 1 个新的配 19 个老的。要精确的比例或者“只给内部员工”，得在入口按权重或按请求头分（Gateway API 的 HTTPRoute 权重、J10 的网关灰度）。

到这里已经能交差了：滚动加 preStop 做到发布不断流，蓝绿做到秒级回切，金丝雀先让一小部分流量试。已知还没处理的细节：新旧并存时数据兼容（坑 2），回滚回不去的东西（坑 3），蓝绿里的后台任务（坑 4），金丝雀看不出问题（坑 5）。

⑥反例和误用

第一圈 · 不知道就会出事的

1滚动发布没有 preStop实测← ④ 新旧交接的那一瞬间
现象
每次发布都有零星的 502 或连接被拒，⑤ 里 281 次请求失败 5 次。大家习惯了，以为是网络抖。
根源
摘地址和发 SIGTERM 同时开始，各节点更新转发规则有延迟（K8s 那页坑 5）。
做法
preStop 等 5～10 秒，应用开优雅停机，terminationGracePeriodSeconds 大于两者之和。
2新旧版本不兼容← ④ 滚动和金丝雀都要新旧并存
现象
1.8.4 给订单加了一个新状态 PARTIAL_REFUND，滚动的那几分钟里，1.8.3 读到它直接抛异常；或者 1.8.4 的迁移脚本删了一列，还没换掉的 1.8.3 全挂。
根源
同一时刻两个版本读写同一份数据，任何一方不认识对方写的东西，都会出错。回滚时方向反过来，问题再来一遍。
做法
“先扩展、后收缩”：先发一个只加不删、两边都兼容的版本，等老版本全部下线，再发删除旧结构的版本。数据库变更和代码发布分开。
3以为回滚能回到一切← ④ 回滚的是镜像和清单
现象
代码回到了 1.8.3，可 1.8.4 跑的那几小时已经改了表结构、写进了新格式的数据、发出了新格式的消息，老代码照样出错。
根源
git revert 回退的是部署清单，数据库、缓存、消息队列里的数据不在 Git 里。Flyway 这类迁移工具的社区版也只往前走。
做法
每次发布前问一句“回滚以后数据怎么办”；不可逆的变更单独发、单独评审；配置放在 Git 里一起回退（全景第 11 站坑：放在 ConfigMap 里的 JAVA_OPTS）。
4蓝绿的“绿”在后台偷偷干活← ④ 蓝绿两套同时在跑
现象
还没切流量，绿的那 4 个 Pod 已经在消费 Kafka、跑 03:00 的对账任务（J13 那个），同一批消息被两个版本各处理一次。
根源
Service 只管 HTTP 流量进不进来；消费者、定时任务、主动连出去的东西不受 selector 控制。
做法
后台任务加开关，只在“当前颜色”上打开；消费者用不同的消费组时想清楚位点；或者这类服务干脆不用蓝绿。
5金丝雀看不出问题实测← ④ 金丝雀要有靠得住的指标
现象
⑤ 里 1 个金丝雀拿到约 20% 的流量。凌晨每秒 2 单，20% 就是 0.4 单，5% 的失败率要几个小时才攒够一次失败，看了十分钟“没问题”就全量了。
根源
金丝雀靠统计：流量太少、指标没有按版本拆开，就分不出新旧版本的差别。
做法
指标按版本打标签（J13 的 Prometheus，version 标签）；按“攒够多少请求”而不是“过了多少分钟”判断；让 Argo Rollouts 或 Flagger 按查询结果自动决定继续还是撤。
6为紧急发布开的“跳过测试”开关← ④ 每次都走同一条路
现象
开关是为了线上救火加的，后来谁赶时间都用，主干慢慢就不再“随时可发布”了。
根源
流水线的价值就在于“每次都一样”，例外一多，它保证的东西就没了。
做法
救火优先用回滚（几秒到几十秒），而不是带着没测过的代码往前冲；流水线慢就去优化它（依赖缓存、并行测试），而不是绕过它。

第二圈 · 团队里该怎么写

  • 构建一次，到处晋级：同一个镜像（同一个摘要）从测试发到生产，环境差异只在配置里：防“测的不是发的”。
  • 部署走 Git，生产要审批：防误操作，也让每次发布都有记录、能 revert。
  • 每次发布都写清回滚方式，并且定期演练一次（J12 的故障演练）：防真出事时才发现回不去。
  • 发布避开高峰，发布后有观察期：按版本看错误率、P99、重启次数和内存：防全景那颗雷在晚高峰才被发现。
  • 数据库变更向后兼容、单独发布：防新旧并存和回滚时出错。

第三圈 · 深一层

自动化金丝雀

Argo Rollouts 用一个 Rollout 对象代替 Deployment，写成步骤：放 20%、跑一段 Prometheus 查询、通过再放 50%……查询不通过就自动回滚。没有配流量路由时，它按副本数近似比例，和 ⑤ 一样粗；配了 Gateway API、服务网格或 Ingress 控制器，才能按精确权重分。Flagger 是同类的另一个实现。

衡量发布能力：DORA 四个指标

部署频率、变更前置时间（从提交到上线）、变更失败率、故障恢复时间。前两个看快不快，后两个看稳不稳。这一页的东西，基本都是在同时改善这四个数：流水线让前两个变好，渐进发布和回滚让后两个变好。

特性开关和部署解耦

代码先上线、功能先关着，想让谁用就对谁打开。发布（部署新代码）和上线（让用户用到新功能）变成两件事：部署可以天天做，功能可以按用户、按比例慢慢放，出事关开关比回滚还快。代价是代码里同时留着新旧两条路，要定期清理。

流水线本身的安全

流水线能把任何代码送进生产，它就是攻击者最想要的东西：依赖被投毒、Action 被篡改、凭据泄露。常见做法是固定第三方 Action 的版本、镜像签名和来源证明、用短期凭据代替长期密钥。拉式部署让 CI 不再持有集群凭据，本身就是一层防护。

↺回到⑤：改一改

  1. preStop 要多久：把 sleep 改成 1 秒和 15 秒各跑一次，失败数和滚动时间怎么变？最短多少秒能做到 0 失败？（坑 1）
  2. 精确的 5%：用 Gateway API 的 HTTPRoute 给 1.8.4 配 5% 的权重（kind 里要先装一个 Gateway 实现），和按副本数的 20% 对比。（坑 5）
  3. 回滚计时：在全景的设定下（6 个副本、每个 23 秒），算一算滚动回滚、蓝绿回切、撤掉金丝雀各要多久，再用实验台验证。（过关标准）

自测

1. 用一句话说出这一页的精华

测试测不全，所以发布追求的不是“不出错”，而是出错时影响小、退得快：构建一次产出不可变镜像，部署走 Git 由集群自己拉，用滚动、蓝绿或金丝雀渐进替换，随时能回到上一个已知的好版本。

2. 停机发布、往前修、CI 直接 apply 各疼在哪？

停机发布每次都是计划内的故障，越怕越少发、越攒越大；往前修是在最紧张的时候写最没把握的代码；CI 直接 apply 让流水线握着生产最高权限，集群状态也不在 Git 里。

3. 坑 2（新旧版本不兼容）的根源是 ④ 的哪一条？

滚动和金丝雀都要新旧版本同时在线，读写同一份数据；回滚时方向反过来再并存一次。所以每次变更都要对两个方向都兼容。

4. 预测：告警 1 分钟就响，4 个副本、每个新 Pod 23 秒 Ready。滚动和蓝绿谁让更少的订单失败？

滚动。1 分钟时滚动只换了两个 Pod，新版本只拿到一半流量，而且前 23 秒还是 0；蓝绿一切就是 100%，满满 60 秒。回滚上蓝绿快，但这时滚动要回的也只有两个 Pod。告警越快，滚动越占优；告警越慢，蓝绿和滚动越接近，金丝雀一直最少。在实验台里把告警调到 1 分钟看看。

5. 预测：蓝绿切到绿以后，你马上把蓝的 4 个 Pod 删了省资源。半小时后发现 1.8.4 有问题，会怎样？

回切的那个“秒级”没了：要先重新起 4 个蓝 Pod，等它们 Ready，再改 selector，和滚动回滚差不多慢。蓝绿的回滚优势来自老的那套还在跑，所以要留到观察期结束再删。

6. 放回全景：第 11 站前后各是什么？17:46 定位到是发布的问题，为什么全景选的是 git revert，而不是蓝绿回切或者 rollout undo？

前面是第 10 站晚高峰 HPA 扩容、Pod 开始被 OOMKilled；第 11 站之后是复盘。全景里的 order-svc 用的是滚动，没有留着一套老版本，所以没有蓝绿回切可用；集群由 Argo CD 按 Git 同步、开着 selfHeal，rollout undo 会被改回去。git revert 在 1 分钟内能发出，6 个副本一轮轮换回去大约要两分多钟（启动速度那页算过）；要更快，就得缩短启动、加大 maxSurge，或者对这个服务改用蓝绿。

档位：标准。本机跑过（2 核 ARM 虚拟机，kind v0.33.0 / Kubernetes v1.37.0，镜像来自 Docker 那页）：./run.sh 完整一次，⑤ 的数字都来自这次运行；蓝绿切换的时刻按秒取整，所以写成“1 秒内”。GitHub Actions 流水线和 Argo CD 的 Application 是示例文件，没有在本机运行。实验台是估算模型，在 node 里跑过。

按文档：Kubernetes 1.37 的 lifecycle.preStop.sleep（用 kubectl explain 查过字段在）；Argo CD 的 syncPolicy.automated 的 prune、selfHeal；Argo Rollouts 没有配置流量路由时按副本数近似金丝雀比例；DORA 的四个关键指标。
