改一行代码，只推一层：Docker 镜像分层与多阶段构建

镜像是一叠按内容寻址的只读层，Dockerfile 里每一条改文件的指令就是一层。哪一层的内容变了，只有它和它上面的层要重建；推送和拉取时，仓库和节点上已经有的层一个字节都不用再传。所以Dockerfile 怎么写，决定了每次发布要搬多少东西。本机实测：同一个 order-svc，改一行代码，整个 fat jar 一层 COPY 要重新推 21.3 MB，按 Spring Boot 的四层拆开只推 3.9 KB；多阶段构建把 Maven 和源码留在构建阶段，镜像从 650 MB 降到 336 MB。

①为什么需要：在全景第 2、3 站，要把代码变成一个“搬到哪都一样”的包

全景第 2 站，14:05，测试刚过。接下来这个包要走很远：推到 Harbor，再被第 7 站几个节点各拉一份，晚高峰 HPA 扩容时还要再拉。它要同时做到三件事：

到哪都一样一字节不差测试环境验过的，就是生产跑的：JRE、系统库、时区、字体一起带上
每次发布只搬变了的依赖一个月才变一次，业务代码一天变几次
第 7 站拉得快、起得快扩容时新节点要在几秒内拿到镜像

②没有它会怎样：老办法，和“用了 Docker 但写错了”

做法能做到放到第 2、3 站
scp 一个 jar，机器上装好 JDK，start.sh 启动包小，二十几 MBJDK 小版本、时区、系统字体、启动脚本各台机器不一样，“测试环境好好的”；加一台机器要先装一遍环境
虚拟机镜像整台机器一起带上，一致性有了几个 GB，改一行代码也要整盘重做、整盘分发，扩容要几分钟
Docker，单阶段：FROM maven，COPY . .，RUN mvn package一致性有了，也能分发实测 镜像 650 MB，里面躺着 Maven、源码和整个本地依赖仓库；改一行代码，COPY . . 那层变了，下面的 mvn package 跟着重跑，依赖重新下载，要重新推 68 MB
Docker，多阶段，但整个 fat jar 一层 COPY镜像降到 336 MB实测 改一行代码，21.3 MB 的 jar 整层重推、整层重拉，其中 99.9% 是没变过的依赖

缺的那一块：把“变得慢的”和“变得快的”分到不同的层里，让每次只有变了的那一层被重建、被搬运；同时让构建用的工具不进最终镜像。这就是分层加多阶段的全部用意。

不懂这一点时的典型误用：把 Dockerfile 当成一个 shell 脚本来写，COPY . . 放第一行，后面一个 RUN 里装工具、编译、清理全做完。能跑，可每次构建都从头来，每次发布都搬几十上百 MB。

③相邻方案：谁来把 jar 变成镜像

方案怎么做适合
Dockerfile 多阶段 + 分层 jar自己写 Dockerfile；第一阶段编译，第二阶段按 Spring Boot 的四层 COPY要完全控制基础镜像、用户、启动参数；团队里已经有 Dockerfile 的习惯
Jib（Maven / Gradle 插件）不写 Dockerfile，也不需要 Docker 守护进程，直接把依赖、资源、class 分层推到仓库纯 Java 项目，CI 里没有 Docker；分层规则它已经替你定好
Cloud Native Buildpacks（mvn spring-boot:build-image）按约定自动探测、自动选 JRE、自动分层平台统一构建、统一打补丁，不想让每个团队维护 Dockerfile
虚拟机镜像、裸机 jar见②还没上容器的老系统

选择规则：后两种自动做的，其实就是“按变化频率分层”这件事。先把 Dockerfile 这条路弄懂，换成 Jib 或 Buildpacks 时就知道它们替你做了什么、出问题去哪看。本页学 Dockerfile 多阶段构建，配 Spring Boot 3.5 的分层 jar。

④原理：按内容寻址的一叠层，加一条“一层失效，上面全失效”的缓存链

先知道这些
  • 容器就是一个普通的 Linux 进程，只是内核给它套了两样东西：namespace 让它只看见自己的文件系统、进程号和网卡；cgroup 限制它能用多少 CPU 和内存。cgroup 那一半在 Java 在容器里；这一页讲它看见的那个文件系统从哪来，也就是镜像。
  • sha256 摘要（digest）：对一段内容算出的 64 位十六进制串，内容差一个字节，摘要就完全不同。下面说的“按内容寻址”，就是用摘要当名字。

镜像是什么，容器又多了什么

按内容寻址是整个设计的地基：每一层用它内容的 sha256 当名字，镜像的 manifest 只是一张“我由哪几个摘要组成”的清单。推送时，仓库说“这个摘要我有了”，这一层就跳过；拉取时，节点上已经有的摘要也跳过。⑤ 里两个空层的摘要完全一样，仓库里也只存了一份。tag 只是指向某个 manifest 的指针，可以挪；摘要不能，order-svc@sha256:… 永远是同一份东西。

构建缓存：一层失效，上面全部重来

缓存全废的写法
FROM maven:3.9.16-eclipse-temurin-21-noble
WORKDIR /src
COPY . .                    # 任何文件变了，这层就变
RUN mvn -B package          # 于是它也重跑：重新下载依赖
ENTRYPOINT ["java","-jar","target/order-svc.jar"]
本页的写法（节选）
COPY --from=build /x/dependencies/ ./           # 依赖不变 → 命中缓存
COPY --from=build /x/spring-boot-loader/ ./
COPY --from=build /x/snapshot-dependencies/ ./
COPY --from=build /x/application/ ./           # 只有这层变

BuildKit 给每条指令算一个缓存键：父层是谁 + 指令文本 + （COPY、ADD 还要加上）被复制文件内容的校验和。三样都没变，直接用上次的层；有一样变了，这一层重做，而它上面的每一层父层都变了，也只能跟着重做。所以 Dockerfile 的顺序就是一句话：变得越少的放越下面。注意 RUN 的缓存键里只有命令文本，不看它会下载什么：RUN apt-get update 命中缓存时，用的是很久以前那次的结果（⑥ 坑 1）。

多阶段：构建工具留在前面，最后一个阶段才是镜像

为什么这样设计

选中的：分层，按内容寻址，只读叠加

一台节点上几十个容器、一个仓库里几千个镜像，大部分内容是重复的：同一个 Ubuntu、同一个 JRE、同一批 Spring 依赖。按内容命名，重复的东西天然只存一份、只传一次；层只读，所以可以放心共享；容器要写，就在最上面单独加一层，改动不碰共享的部分。

被放弃的：整盘快照（虚拟机镜像）

把整个文件系统打成一个文件：简单，但两个只差一行代码的版本是两个几 GB 的文件，存储、传输、启动都按整盘算，什么都共享不了。按文件同步差量（rsync 那样）也不行：要先比较两端的状态，结果没法缓存成一个不可变、可以校验的对象。

决定胜负的约束：同一份内容要在成千上万台机器之间反复搬，而且搬过去必须和原来一字节不差。按内容寻址同时解决了去重、增量和校验三件事。代价是：层只能往上叠，下面的层删不掉东西（⑥ 坑 2），顺序一旦写错，缓存就全废。

先猜：用本页的写法（多阶段 + 分层），改一行业务代码，第 3 站要往 Harbor 推多少？

Dockerfile 写法
这次改了什么

“改一行业务代码”三种写法的数字是 ⑤ 实测；“加一个依赖”按新 jar 1 MB 估算；“改 README”按缓存规则推出来。大小都是推送时的压缩后大小。

⑤亲眼看到：同一个 order-svc，三种 Dockerfile，改一行代码

一个最小的 order-svc（Spring Boot 3.5.16，web + actuator），三份 Dockerfile：单阶段、多阶段整 jar、多阶段四层。run.sh 先各构建一次 1.8.3，把 VERSION 改成 1.8.4 再各构建一次，比较两版之间哪些层的摘要变了；然后起一个本地镜像仓库（registry:3.0.0），两版都推上去，按 manifest 算第二次推送真正传了多少。最后顺手测了 ⑥ 的三个坑。

⑤docker/Dockerfile.layered完整代码 →
FROM maven:3.9.16-eclipse-temurin-21-noble AS build
WORKDIR /src
COPY pom.xml .
COPY src ./src
RUN --mount=type=cache,target=/root/.m2 mvn -B -q package -DskipTests
# Spring Boot 3.3 起的写法：拆出瘦 jar + lib/，按层分到四个目录
RUN java -Djarmode=tools -jar target/order-svc.jar extract --layers --destination /x

FROM eclipse-temurin:21.0.13_9-jre-noble
WORKDIR /app
RUN useradd --system --uid 10001 app
COPY --from=build /x/dependencies/ ./
COPY --from=build /x/spring-boot-loader/ ./
COPY --from=build /x/snapshot-dependencies/ ./
COPY --from=build /x/application/ ./
USER app
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "order-svc.jar"]

== 3. 推到本地镜像仓库：第二次推送真正传了多少（压缩后）
single:  1.8.4 共 313.2 MB，要新传 2 层 68.23 MB
fatjar:  1.8.4 共 120.7 MB，要新传 1 层 21.30 MB
layered: 1.8.4 共 120.5 MB，要新传 1 层 3905 字节
看懂这次运行
  • 单阶段的 650 MB 里，有 572 MB 是 maven 镜像本身，剩下的是源码、target/ 和 Maven 下载的依赖仓库。多阶段把这些都留在了构建阶段，最终镜像就是 JRE 基础镜像加 24 MB。
  • fatjar 和 layered 一样大，层数不同。区别全在“改一行代码”时：fatjar 那一层就是整个 jar，21.3 MB 整层换掉；layered 把 jar 拆开，变的只有 5.6 KB 的瘦 jar，压缩后 3.9 KB。依赖那 21.1 MB 的层摘要没变，仓库说“已经有了”。
  • 单阶段重建要 17.5 秒，大半时间在重新下载依赖：COPY . . 那层变了，下面的 RUN mvn package 就不能用缓存，而且它下载的依赖还被写进了层里。多阶段用 --mount=type=cache 把 /root/.m2 挂成缓存，重建只要 5 秒左右。
  • 这台机器上 Harbor 换成了本地 registry:3.0.0，原理一样：按层的摘要判断有没有。

到这里已经能交差了：一份多阶段、分层的 Dockerfile，改代码只重建、只推送几 KB。已知还没处理的细节：.dockerignore 和指令顺序（坑 1），删文件不会让镜像变小（坑 2），密码别进构建参数（坑 3），ENTRYPOINT 的写法决定了能不能优雅停机（坑 4）。

⑥细节·规范·优化

第一圈 · 不知道就会出事的

1指令顺序写反，或者没有 .dockerignore← ④ 一层失效，上面全失效
现象
每次构建都从头来，十几分钟；改了 README 也要重新打包、重新推几十 MB。
根源
COPY . . 的缓存键包含所有被复制文件的校验和，.git/、target/、README 任何一个变了，这层和上面所有层都失效。反过来，RUN apt-get update 的缓存键只有命令文本，可能一直用着几个月前的软件源。
做法
写 .dockerignore；先 COPY pom.xml，再 COPY src；apt-get update 和 install 写在同一个 RUN 里；基础镜像定期升级，而不是指望缓存失效。
2在后一层删掉大文件，以为镜像变小了实测← ④ 层只能往上叠
现象
本机实测：基础镜像 312 MB，一层生成 50 MB 的文件，下一层 rm 掉，镜像变成 362 MB。
根源
下面那层的 tar 包里还有这 50 MB；上面那层只是放了个 whiteout 标记，让合并后的视图里看不见它。推、拉、存都照样算。
做法
在同一个 RUN 里下载、使用、删除；或者放进构建阶段，只把结果 COPY --from 过来。
3密码当构建参数传进去实测← ④ 每一层的来历都记在镜像里
现象
docker build --build-arg DB_PASSWORD=…，任何能拉到镜像的人 docker history --no-trunc 一看：RUN |1 DB_PASSWORD=s3cr3t-pw /bin/sh -c …，明文。
根源
镜像的 config 里记着每一层是哪条指令生成的，用到构建参数的 RUN 会把参数值一起记下来。COPY 进去再删，文件也还在下面的层里（坑 2）。
做法
构建时要用的密钥走 RUN --mount=type=secret，不落到任何一层；运行时要用的密码根本不进镜像，由全景第 4 站的 Secret 注入成环境变量或文件。
4ENTRYPOINT 写成 shell 形式，停一次要 10 秒实测← ④ 容器就是一个进程
现象
本机实测：ENTRYPOINT java $JAVA_OPTS -jar order-svc.jar，1 号进程是 /bin/sh -c …，docker stop 等了 10.2 秒，退出码 137；写成 ["java","-jar","order-svc.jar"]，1 号进程就是 java，0.2 秒优雅退出，退出码 143。
根源
停容器是给 1 号进程发 SIGTERM。shell 当 1 号进程时不把信号转给 java，等到超时，只能 SIGKILL（137 = 128 + 9）。Spring Boot 的优雅停机根本没机会跑。到了全景第 9 站，就是每个老 Pod 都要等满 30 秒被强杀，手上的请求全断。
做法
用 exec 形式；要拼 $JAVA_OPTS 就用 JVM 自己认的 JAVA_TOOL_OPTIONS 环境变量，或者在启动脚本最后一行写 exec java …。信号和退出码在 J14 最后一页细讲。
5用 latest 或会被覆盖的 tag 发布← ④ tag 是指针，摘要才是内容
现象
同一个 Deployment 里，有的 Pod 跑旧代码、有的跑新代码；回滚到“1.8”，回到的不知道是哪一次构建。
根源
tag 可以被重新指向别的 manifest。节点按 IfNotPresent 缓存了旧内容，就不会再去拉。
做法
一次构建一个新 tag（版本号 + git 提交号），不覆盖；要绝对确定就用 @sha256:… 摘要引用。基础镜像也写到小版本：21.0.13_9-jre-noble。
6在 Mac（ARM）上构建，推到 x86 集群← ④ 层里是编译好的二进制
现象
本地好好的，到了集群里容器一启动就退出，日志只有一行 exec format error，Pod 反复重启。
根源
JRE 和系统库是按 CPU 架构编译的，镜像有架构之分。本页的镜像是 linux/arm64（这台机器是 ARM）。
做法
在 CI 里构建；要多个架构就 docker buildx build --platform linux/amd64,linux/arm64，推成一个多架构清单，节点自己挑。

第二圈 · 团队里该怎么写

  • 多阶段，运行阶段只用 JRE：防构建工具和源码进生产镜像。要排查时再用临时容器带 JDK 工具上去（Arthas 那页坑 4）。
  • 按变化频率排顺序：基础镜像 → 系统包 → 依赖 → 应用。防一次小改动把缓存全废掉。
  • 基础镜像写到小版本，定期主动升级：防“昨天能构建、今天行为变了”，也防安全补丁永远不进来。
  • 非 root 用户运行（USER app）：防容器被攻破后直接拿到 root。
  • ENTRYPOINT 用 exec 形式，一个容器一个进程：防信号到不了 java，防一个进程挂了另一个还假装活着。
  • tag 用版本号 + 提交号，镜像里写上来源标签（org.opencontainers.image.revision）：防线上镜像说不清是哪次提交打的。

第三圈 · 优化和深处

缓存挂载：依赖下载不进层，也不白下

RUN --mount=type=cache,target=/root/.m2 让 BuildKit 在构建之间保留这个目录，但它不属于任何一层。实测 单阶段每次改代码重建 17.5 秒、依赖全部重新下载；多阶段带缓存挂载约 5 秒。CI 的机器每次都是新的时，还要把 BuildKit 缓存导出到仓库（--cache-to / --cache-from），否则缓存挂载每次都是空的。

压缩后的摘要和解压后的 diffID

同一层有两个名字：docker image inspect 里的 RootFS.Layers 是解压后 tar 的摘要（diffID），仓库 manifest 里的是压缩后的摘要。同样的文件用不同的压缩参数，压缩后摘要就不同。⑤ 里两个空层压缩后都是 93 字节、摘要相同，仓库只存了一份。

基础镜像怎么选

这里用的 eclipse-temurin:…-jre-noble 解压后 312 MB，其中 Ubuntu 和系统包占 147 MB。更小的选择有 Alpine（musl libc，和 glibc 有细微差别）、distroless（没有 shell，排查不方便），或者用 jlink 只打包用到的 JDK 模块。越小越快，但排查手段越少；本页没有实测这几种。

版本差异

Docker 23.0 起 Linux 上默认用 BuildKit，RUN --mount 才能直接用。Spring Boot 2.3 起支持分层 jar，3.3 起推荐 -Djarmode=tools … extract --layers，原来的 -Djarmode=layertools 被标为过时；不加 --launcher 时拆出来的是“瘦 jar + lib/”，直接 java -jar 启动。

  • 把 CDS / AOT 缓存放进镜像，加快第 7 站的启动（J14 第 4 个知识点）。
  • containerd 和 OCI 规范：Kubernetes 节点上没有 Docker，镜像是怎么被拉下来、解开的。
  • 大镜像的懒加载（eStargz、镜像预热）：AI 服务几个 GB 的模型镜像怎么办，接 AI 地图站 10。

↺回到⑤：改一改

  1. 顺序写反：把 Dockerfile.layered 里 application 那行挪到 dependencies 前面，改一行代码重建、重推。这次推了多少？（坑 1）
  2. 加一个依赖：在 pom.xml 里加 spring-boot-starter-validation，看 layered 哪几层变了，和实验台的估算对一对。
  3. 把密码藏好：用 RUN --mount=type=secret,id=db 改写坑 3 的 Dockerfile，构建时 --secret id=db,src=…，再 docker history --no-trunc 确认看不到了。（坑 3）

自测

1. 用一句话说出这一页的精华

镜像是按内容寻址的一叠只读层，每层用摘要当名字；构建时一层失效、上面全部重做，推拉时已有的摘要直接跳过。所以把变得少的放下面、把构建工具留在前一个阶段，每次发布就只搬变了的那几 KB。

2. 老办法（jar + 装好环境的机器、虚拟机镜像、单阶段 Dockerfile）各疼在哪？

jar 加机器：环境各不相同，扩容要先装环境。虚拟机镜像：一致了，但每次整盘几个 GB，什么都不能共享。单阶段 Dockerfile：一致、能分发，但镜像里带着 Maven 和依赖仓库，改一行代码缓存就废掉，每次重推几十 MB。

3. 坑 2（删了文件镜像不变小）的根源是 ④ 的哪一条？

层只能往上叠：每一层是相对下面那层的差异，删除只是在上层放一个 whiteout 标记，下面那层的 tar 包里内容还在，推、拉、存都照算。

4. 预测：节点上已经有 order-svc 1.8.3（layered 写法），第 7 站拉 1.8.4 要下载多少？如果是 fatjar 写法呢？

layered：只差 application 那一层，压缩后约 3.9 KB，几乎瞬间拉完。fatjar：要拉整个 jar 那层，约 21.3 MB。基础镜像层两种写法都已经在节点上了。推导和推送一样：按摘要比，有的跳过。

5. 预测：基础镜像从 21.0.13 升到 21.0.14，用本页的写法重建，会发生什么？要推多少？

JRE 那层内容变了，它和上面所有层在构建时都要重做（父层变了，缓存键全变）。但 COPY 进去的依赖和应用文件内容没变，重做出来的层多半和原来一样，仓库里已经有，不用再推；真正要推的主要是新的 JRE 层，压缩后约 50 MB。这里是按机制推出来的，本页没有实测。

6. 放回全景：第 2、3 站前后各是什么？如果 1.8.4 的镜像是在 ARM 笔记本上打的、集群是 x86，整条发布链会怎样？

前面是第 1 站 CI 跑测试，后面是第 4 站改部署清单、Argo CD 同步。镜像架构不对时，第 5、6 站都正常（控制器和调度器不看镜像内容），到第 7 站容器一启动就 exec format error，第 8 站的探针永远过不了，新 Pod 反复重启。因为 maxUnavailable: 0，老 Pod 一个都不会被停，用户没感觉；滚动卡在第 1 个新 Pod 上，到 progressDeadlineSeconds 才报失败，要靠人回滚。

档位：标准。本机跑过（2 核 ARM 虚拟机，Docker 27.3.1 + BuildKit，Spring Boot 3.5.16，基础镜像 eclipse-temurin:21.0.13_9-jre-noble，构建阶段 maven:3.9.16-eclipse-temurin-21-noble，本地仓库 registry:3.0.0）：./run.sh 完整一次，⑤ 和坑 2、3、4 的数字都来自这次运行，application 层 3905 字节是又推了一次、从 manifest 读出来的。“加一个依赖”和“升级基础镜像”是按机制估算。实验台的模拟逻辑在 node 里跑过，“改一行代码”三种写法和实测一致。

按文档：BuildKit 的缓存键由父层、指令和 COPY/ADD 文件的校验和决定；RUN --mount=type=cache 和 type=secret 的内容不进层；多阶段构建的最终镜像只包含最后一个阶段；Spring Boot 分层 jar 默认四层 dependencies、spring-boot-loader、snapshot-dependencies、application；Docker 23.0 起 Linux 默认构建器是 BuildKit；容器停止时向 1 号进程发 SIGTERM，超时（docker stop 默认 10 秒）后发 SIGKILL。
