装得下、活着、能干活：requests、limits、探针和 HPA

给 Kubernetes 的每个容器回答四个问题：要预订多大的位置（requests，调度只看它，HPA 的百分比也是相对它算的）；最多能用多少（limits：CPU 超了被限速，内存超了内核直接杀）；现在能不能干活（startup、readiness、liveness 三种探针各管一件事）；人多了要不要加副本（HPA）。本机 kind 集群实测：limit 384Mi，-Xmx384m 的容器被内核杀掉，退出码 137，日志里一行 OutOfMemoryError 都没有；同样的 limit 用 MaxRAMPercentage=75，Java 自己抛 OutOfMemoryError，进程还活着、还在接流量。启动要 40 秒的应用只配 liveness，100 秒里被重启 5 次；加上 startupProbe，48 秒 Ready。

②没有它会怎样

不配会怎样
不写 requests 和 limits调度器以为它不占地方，一台节点塞二十个；高峰时一起抢内存，节点内存耗尽，内核挑进程杀，杀到谁算谁。这种 Pod 的服务质量等级是 BestEffort，节点紧张时第一个被驱逐
不配探针容器进程一启动就算 Ready：JVM 还在初始化 Spring，流量已经进来，前 20 秒全是 502；进程死锁了但没退出，Kubernetes 永远不知道要重启它
副本数写死按晚高峰配 6 个，一天 20 个小时闲着；按平时配 4 个，晚高峰扛不住（全景第 10 站扩到 6 个）

缺的是一套容器和平台之间的约定：容器声明“我要多少、最多用多少、怎么问我还行不行”，平台据此调度、限制、摘流量、重启、扩缩。

不懂这一点时的典型误用：照着虚拟机的习惯写 -Xmx 等于容器的内存上限，以为“堆就是全部内存”；或者把 liveness 当成“全面体检”，里面查数据库、查 Redis，依赖一抖，全部 Pod 被一起重启。

④原理：预订和上限分开，CPU 能挤、内存不能挤

先知道这些
  • cgroup：内核给一组进程设的资源账本和上限。Kubernetes 把 limits 写成 cgroup v2 的 memory.max 和 cpu.max，JVM 也从这里读自己有多少内存和 CPU（Java 在容器里）。
  • kubelet：每个节点上的代理，负责起容器、跑探针、上报用量。探针是 kubelet 发起的，不是控制面。

requests 是预订，limits 是上限

为什么 CPU 和内存待遇不同？CPU 时间可以往后挪：这 100 毫秒不给你，下 100 毫秒再给，进程只是慢一点。内存不行：已经写进去的数据不能“先拿走一会儿”，内核唯一能做的就是杀掉一个进程把内存要回来。所以 limits 对 CPU 是一道限速带，对内存是一堵墙。

requests 和 limits 的组合还决定了 QoS 等级：每个容器的 CPU 和内存都是 requests = limits，是 Guaranteed；写了 requests 但不全相等，是 Burstable；什么都没写，是 BestEffort。节点内存紧张时，kubelet 按 BestEffort → 超出 requests 的 Burstable → Guaranteed 的顺序驱逐。实测 ⑤ 里内存 requests = limits，但 CPU 是 100m 对 1 核，得到的是 Burstable。

两种 OOM：谁发现、谁动手

容器里的内存不只是堆。JVM 进程 = 堆 + 堆外（元空间、JIT 代码缓存、每个线程的栈、GC 自己的数据结构、直接内存……）。cgroup 只看这个总数。

Pod 被 OOMKilledJava 抛 OutOfMemoryError
谁发现内核：cgroup 里的总内存要超过 memory.maxJVM：堆里分配不出这个对象
谁动手内核 OOM killer 发 SIGKILL，进程立刻没了JVM 把异常抛给正在分配内存的那个线程
看得到什么应用日志里什么都没有；kubectl describe pod：Reason: OOMKilled、Exit Code: 137日志里 java.lang.OutOfMemoryError: Java heap space；开了 HeapDumpOnOutOfMemoryError 还有堆转储
之后kubelet 重启容器，重启次数 +1进程还在，Pod 还是 Running；别的线程可能也开始失败，服务半死不活
通常意味着配置问题：堆 + 堆外 > limit代码问题：泄漏，或者堆真的不够

三种探针各管一件事

startupProbe：起完了没成功之前，另外两种探针都不开始。失败次数 × 间隔就是“最多给你多久启动”。成功一次以后就不再跑。
readinessProbe：接不接流量失败只把 Pod 从 Service 的地址表里摘掉，不重启。一直跑，随时可能摘下、再加回来。
livenessProbe：要不要重启连续失败 failureThreshold 次，kubelet 杀掉容器重来。只该在“进程卡死、只有重启能好”时失败。

Spring Boot 在 Kubernetes 里运行时，自动打开两个探针组：/actuator/health/liveness 只反映应用自己的状态，/actuator/health/readiness 反映能不能接流量（启动完成、没在关）。默认都不包含数据库这类外部依赖。

HPA 怎么算

每 15 秒算一次
期望副本 = ceil( 当前副本 × 当前利用率 / 目标利用率 )
利用率   = 各 Pod 的 CPU 用量平均值 / requests.cpu

# ⑤ 实测：1 个副本，压测一上来
ceil( 1 × 786% / 50% ) = 16  → 上限 maxReplicas 5
# 默认扩容速度：每 60 秒最多 +4 个或翻倍，取大的 → 5

几个让它不抖的设计

容差：比值在 0.9～1.1 之间不动。缩容稳定窗口：默认 300 秒，取这段时间里算出来的最大值，免得流量一降就缩、一涨又扩（⑤ 里缩短成 30 秒）。扩容速度上限：默认每 60 秒最多加 4 个或翻倍。数据来自 metrics-server，它从各节点 kubelet 拉 CPU 和内存用量。

为什么这样设计

选中的：预订和上限分成两个数

requests 让调度器能“按预订装箱”，limits 只用来防止失控。两者之间的空间允许超卖：大部分服务大部分时间用不满上限，节点可以多放几个 Pod，平时省钱，偶尔有人冲高也有余量。

被放弃的：只有一个“大小”

只按上限装箱：每个 Pod 都按峰值占位，节点利用率很低。只按平均值装箱、又不设上限：一个 Pod 失控就拖垮整台节点。同理，探针分成三种，是因为“没起完”“暂时忙不过来”“已经卡死”三种情况该做的事完全不同；只有一种健康检查，就只能在“摘流量”和“重启”之间二选一。

决定胜负的约束：CPU 可以压缩，内存不能；启动、过载、卡死三种状态需要不同的处理。代价是：配的人要分别理解这几个数，配错一个就是全景里那颗雷。

⑥细节·规范·优化

第一圈 · 不知道就会出事的

1-Xmx 等于 limit实测← ④ cgroup 看的是总数
现象
平时没事，流量一大 Pod 一个个重启，describe 里是 OOMKilled、137，应用日志干干净净，也没有堆转储（全景第 10、11 站）。
根源
limit 管的是进程总内存，堆只是其中一块。堆上限占满 limit，堆外就没地方放。
做法
不写 -Xmx，用 -XX:MaxRAMPercentage=70～75；堆外大的应用（Netty、很多线程）再往下调，或者看 NMT 的实际数字定。
2Java OOM 以后，Pod 还是 Running实测← ④ JVM 只把异常抛给一个线程
现象
⑤ 里抛了 OOM 之后，普通接口照样回 200；可泄漏还在，接下来各个线程轮流分配失败，服务时好时坏，重启次数却一直是 0，没人报警。
根源
OutOfMemoryError 只是一个异常，被框架接住就过去了；liveness 问的是 actuator，它还能回 UP。
做法
加 -XX:+ExitOnOutOfMemoryError：JVM 打印一行 “Terminating due to java.lang.OutOfMemoryError” 后以退出码 3 直接退出，交给 Kubernetes 重启；同时 -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps，路径挂一个卷，堆转储才不会随容器一起消失。
3liveness 查依赖，或者没有 startupProbe实测← ④ liveness 只为“卡死”而设
现象
MySQL 主从切换 30 秒，所有 order-svc 一起被重启，切换完了它们还在冷启动；或者 ⑤ 第 3 组：启动慢一点，就永远起不来。
根源
liveness 失败的后果是重启，可依赖挂了重启毫无用处；启动期间 liveness 一直在问，问不通就判死。
做法
liveness 只看进程自己（Spring Boot 的 liveness 组默认就是这样）；依赖的状态放 readiness 也要慎重（全景预测题 3）；JVM 应用一律配 startupProbe，按最慢的一次启动再留余量。
4CPU limit 太紧← ④ CPU 超了被限速
现象
CPU 平均才 30%，P99 却忽高忽低；GC 停顿变长。⑤ 里 limit 1 核，JVM 的 availableProcessors 就是 1，GC 线程、ForkJoin 池都按 1 核配。
根源
限速按 100 毫秒一个周期算：一个周期里 JIT、GC、业务线程一起把额度用完，剩下的时间全部等着，平均值看不出来。
做法
很多团队对在线服务只设 CPU requests、不设 CPU limit，或者把 limit 设得比 requests 宽很多；要设就看 container_cpu_cfs_throttled_periods_total 有没有在涨。
5HPA 看的指标和瓶颈不是一回事← ④ 利用率 = 用量 / requests
现象
requests 写得很小，利用率动不动 700%，一点流量就扩到顶；或者瓶颈在数据库连接，按 CPU 扩出来的副本越多，数据库连接越多，先倒的是数据库（全景第 10 站的常出的事）。
根源
HPA 只会按你给的指标做比例运算，不知道瓶颈在哪。
做法
requests 按真实平均用量定；minReplicas 至少 2；瓶颈不在 CPU 的服务，按请求量或队列积压扩（KEDA），并给 maxReplicas 算好下游能扛多少。
6不写 requests，或者以为写了就是 Guaranteed实测← ④ QoS 等级
现象
节点内存紧张时，最先被驱逐的总是那几个服务；⑤ 里内存 requests = limits 的 Pod，QoS 也只是 Burstable。
根源
Guaranteed 要求每个容器的 CPU 和内存都 requests = limits；有一项不等就是 Burstable，什么都不写是 BestEffort。
做法
内存一律 requests = limits（内存不能压缩，超卖内存就是在赌）；核心服务需要 Guaranteed 时，CPU 也写成相等。

第二圈 · 团队里该怎么写

  • 每个容器都写 requests；内存 requests = limits：防超卖内存、防 BestEffort 被先驱逐。
  • JVM 用 MaxRAMPercentage，不写死 -Xmx，加 ExitOnOutOfMemoryError 和挂卷的堆转储：防两种 OOM 各自的后遗症。
  • 三种探针都配：startup 按最慢启动留余量，readiness 看能不能接流量，liveness 只看自己：防误杀和重启风暴。
  • HPA 的 minReplicas ≥ 2，maxReplicas 按下游容量算，缩容稳定窗口保持默认 300 秒：防单点、防把数据库扩垮、防来回抖。
  • requests 按监控里的真实用量定，季度复盘一次：防一开始拍脑袋的数字一直沿用。

第三圈 · 深一层

堆外到底有多少：NMT

加 -XX:NativeMemoryTracking=summary，用 jcmd <pid> VM.native_memory summary 能看到堆、类元数据、线程、代码缓存、GC、内部各占多少；这是定 MaxRAMPercentage 最可靠的依据。NMT 之外还有 glibc 的 malloc 区（MALLOC_ARENA_MAX），在 Java 在容器里 的“下一圈”。

原地调整资源

以前改 requests、limits 都要重建 Pod。Kubernetes 1.37 里容器已经有 resizePolicy 字段，可以原地改 CPU 和内存（本页的 kubectl explain 查过字段在）。注意 JVM 的堆上限是启动时定的，内存改大了，堆不会跟着变，要重启才生效。

重启和退出码

⑤ 里出现了三个退出码：137（SIGKILL，OOMKilled）、143（SIGTERM，liveness 失败后 kubelet 先礼后兵）、3（ExitOnOutOfMemoryError，按 JDK 源码 os::_exit(3)）。看退出码就能先分出是谁动的手，J14 最后一页细讲信号。

HPA 和启动慢的 JVM

新扩出来的 Pod 要 20～40 秒才 Ready，这段时间老 Pod 还要硬扛；JIT 没热起来，刚 Ready 的 Pod CPU 也偏高。所以扩容要早一点（目标利用率别设太高）、启动要快一点，这就是下一页“启动速度”要解决的事。

自测

1. 用一句话说出这一页的精华

requests 是给调度器的预订、也是 HPA 的分母，limits 是上限：CPU 超了限速，内存超了内核直接杀；三种探针分别回答“起完没有、接不接流量、要不要重启”；HPA 按“用量 / requests”成比例地加减副本。

2. 说清 Pod 被 OOMKilled 和 Java 抛 OOM 的区别（地图过关标准）

OOMKilled：内核发现容器总内存（堆 + 堆外）要超过 memory.max，发 SIGKILL，进程立刻没了，退出码 137，应用日志里什么都没有，kubelet 重启它，通常是配置问题（堆上限留的余量不够）。Java OOM：JVM 发现堆里分配不出对象，把 OutOfMemoryError 抛给那个线程，日志里看得到，进程还活着、Pod 还是 Running，通常是代码问题（泄漏或堆不够）。

3. 坑 3（liveness 查数据库）的根源是 ④ 的哪一条？

三种探针各管一件事：liveness 失败的后果是重启，它只该在“只有重启能好”的时候失败；数据库挂了，重启 order-svc 一点用都没有，反而把所有 Pod 同时拖进冷启动。

4. 预测：limit 1Gi，什么都不写（默认 MaxRAMPercentage=25），会怎样？

堆上限只有 256 MiB，加上堆外一百来 MiB，1Gi 里有一大半一直闲着。流量一大，堆先满，GC 越来越频繁，然后 Java OOM。不会被 OOMKilled，但钱白花了，服务还更容易 OOM。可以在实验台里选“什么都不写”看看。

5. 预测：HPA 目标 50%，现在 4 个副本、平均利用率 80%，下一次计算后是几个？如果是 53% 呢？

ceil(4 × 80 / 50) = ceil(6.4) = 7，再看扩容速度限制（每 60 秒最多 +4 或翻倍，取大的，允许到 8），所以是 7。53% 时比值 1.06，在 10% 的容差以内，不动，还是 4 个。

6. 放回全景：第 8 站前后各是什么？如果 1.8.4 的 startupProbe 被人删了，而 1.8.4 启动比 1.8.3 慢了 30 秒，第 9 站会怎样？

前面是第 7 站 kubelet 起容器、JVM 按 cgroup 定堆，后面是第 9 站进 EndpointSlice、切流量。没有 startupProbe，liveness 在启动期间就开始问，新 Pod 起不来就被杀，反复重启（⑤ 第 3 组那样）。因为 maxUnavailable: 0，老 Pod 一个都不会被停，用户无感；滚动卡在第 1 个新 Pod，等到 progressDeadlineSeconds 报失败，要人来回滚或者补上探针。

档位：标准。本机跑过（2 核 ARM 虚拟机，kind v0.33.0 / Kubernetes v1.37.0，metrics-server v0.9.1，镜像基于 eclipse-temurin:21.0.13_9-jre-noble）：./run.sh 完整一次，⑤ 的输出都来自这次运行（QoS 那一行的说明文字是跑完后改正的，数字没变）。堆外 80～110 MiB 是从两次 OOM 的结果反推的估算，不是测量值；实验台按它估算。实验台的计算在 node 里跑过，384Mi 的两种设置和实测结论一致。

按文档和源码：kubectl explain（1.37）里 HPA 默认扩容策略是“每 60 秒最多加 4 个或翻倍，取大的”，缩容稳定窗口默认 300 秒；HPA 每 15 秒同步一次、容差 10%；startupProbe 成功之前 liveness 和 readiness 不执行；QoS 的三个等级按 requests 和 limits 判定；Spring Boot 在 Kubernetes 上自动启用 liveness 和 readiness 探针组。JDK 21 的 debug.cpp 里 ExitOnOutOfMemoryError 打印 “Terminating due to java.lang.OutOfMemoryError” 后调用 os::_exit(3)。
