只说想要什么：Kubernetes 核心对象与控制循环

Kubernetes 的核心不是“帮你启动容器”，而是声明式 + 控制循环：你只把“想要 4 个 1.8.4”写进 API Server，一群各管一件事的控制器不停地对比“想要的”和“现在的”，差多少补多少。对象之间也不互相点名，而是用标签去选：ReplicaSet 按标签数 Pod，Service 按标签找 Pod。Pod、ReplicaSet、Deployment、Service、Ingress 这几个对象，就是这套思路在“跑副本、发新版、接流量”三件事上的样子。本机 kind 集群实测：删掉一个 Pod，0.3 秒后新的就被建出来；改掉一个 Pod 的标签，它立刻不接流量、也不归 Deployment 管了；4 个副本滚动发布 26 秒，回滚 24 秒。

①要解决的问题：在全景第 5、9 站，4 个副本要一直是 4 个，换版本时流量不能断

全景里 order-svc 有 4 个副本，分在几台节点上。平时节点会宕、Pod 会被杀、进程会崩；14:06 要把 4 个 1.8.3 一个个换成 1.8.4；17:47 又要换回来。这些事要在凌晨三点没人盯着的时候也成立。

一直保持 4 个少了自动补，多了自动删，不用人值守
发布、回滚一个个换新旧版本按比例替换，随时能回去
流量只给健康的Pod 换来换去，调用方只认一个名字

②不用它会怎样：一份发布脚本加一个手改的 Nginx

deploy.sh：命令式，说“怎么做”
for host in app1 app2 app3 app4; do
  ssh $host "docker stop order-svc; docker rm order-svc"
  ssh $host "docker run -d --name order-svc order-svc:1.8.4"
  until curl -sf http://$host:8080/actuator/health; do sleep 2; done
done
# 再去改 Nginx 的 upstream，reload
Kubernetes：声明式，说“要什么”
spec:
  replicas: 4
  template:
    spec:
      containers:
        - image: order-svc:1.8.4
# kubectl apply 一下，剩下的交给控制器
  • 脚本只在跑的那一刻是对的。半夜 app3 宕机，没人把它上面的 order-svc 挪到别处；脚本早就跑完了。
  • 中途失败就是半成品。换到第 3 台时 ssh 超时，现在是两台 1.8.4、两台 1.8.3，脚本不知道该从哪继续，也不知道该怎么回去。
  • 状态散在各处。哪台机器跑哪个版本、Nginx 里写了哪些地址，只能一台台去问；先停再起，那几秒这台的流量就断了。
不懂这一点时的典型误用：上了 Kubernetes，却把 kubectl 当 ssh 用：线上 kubectl edit、kubectl scale、kubectl set image 一通改，YAML 和 Git 里还是老样子。下一次 apply 或者 Argo CD 同步，改动被悄悄“纠正”回去（全景第 11 站的坑，⑤ 第 6 步实测）。

③几种流派

流派怎么做赢在输在
命令式编排（脚本、Ansible 推送）按步骤去每台机器执行直观，现有机器就能用执行完就不管了，出了偏差没人纠正
声明式 + 控制循环（Kubernetes）存一份期望状态，控制器持续对齐自愈、滚动、回滚、扩缩容都是同一个机制；状态集中在一个 API 里概念多，YAML 多；简单应用显得重
PaaS（交一个 jar 就行）平台替你决定怎么跑上手最快能调的东西少，被平台绑住
Serverless（按请求起实例）没请求时缩到 0不用管实例Java 冷启动慢，长连接、本地缓存都不合适

选择规则：服务一多、要自愈和滚动发布，就用声明式；很多公司的 PaaS 和 Serverless 平台底下其实也是 Kubernetes。本页学 Kubernetes 的那几个核心对象，以及它们背后同一个设计：期望状态 + 控制循环 + 标签选择。

④核心取舍：存期望，各自对齐，用标签挑人

先知道这些
  • API Server 和 etcd：集群里所有对象（Deployment、Pod、Service……）都存在 etcd 这个键值库里，谁要读写都只能通过 API Server。每个对象都分成两半：spec 是“想要的”，status 是“现在的”。
  • watch：组件可以对 API Server 说“某类对象有变化就告诉我”，不用一遍遍轮询。下面所有的箭头都是 watch 加写回。

谁在干活：都只和 API Server 说话

每个控制器都在跑同一个循环：读期望 → 读现状 → 算差距 → 做一小步 → 再来一遍。ReplicaSet 控制器看到“期望 4、现在 3”，就建一个 Pod；它不管那个 Pod 是被删的、被驱逐的，还是节点宕机没的。这叫水平触发：按“现在差多少”行动，而不是按“刚才发生了什么事件”行动。事件丢了、控制器自己重启了都没关系，下一轮一比就知道还差什么。

这一站的五个对象

对象它保证什么全景里是
Pod一个或几个容器共享网络和存储，一起调度到一个节点上。短命：挂了不会原地复活，只会被换成一个新的（新名字、新 IP）order-svc-9f74c49d-xs76w
ReplicaSet带某组标签的、照同一个模板做出来的 Pod，始终是 N 个1.8.3 一个、1.8.4 一个
Deployment管理 ReplicaSet 的版本：模板一变，新建一个 ReplicaSet，按策略把副本从老的挪到新的；留着老的，回滚就是把它扩回来第 5 站、第 11 站
Service一个稳定的名字和虚拟 IP。背后的 EndpointSlice 跟着标签和 Ready 状态自动更新第 9 站：http://order-svc
Ingress / Gateway API集群外的 HTTP 入口：按域名、路径把请求路由到 Service第 9 站：网关到 order-svc

Ingress 这个 API 还在，但已经冻结不再加功能；社区最常用的实现 ingress-nginx 在 2026 年 3 月停止维护，仓库已归档（最后一版 controller-v1.15.1）。新集群的入口一般用 Gateway API（2026-10 发布 v1.7.0），由 Envoy Gateway、Istio、Cilium 等实现。本页的实验用集群内的客户端直接调 Service，不装入口。

对象之间不点名，用标签挑

标签是贴在对象上的键值对，选择器是一句查询：“所有 app=order-svc 的 Pod”。ReplicaSet 和 Service 用的都是查询，而不是一张写死的 Pod 名单，因为 Pod 本来就是来来去去的。一个 Pod 也可以同时被好几个 Service 选中：给金丝雀版本贴上同样的 app 标签，它就自动分到一部分流量。Deployment 给自己的 Pod 额外贴一个 pod-template-hash，这样新老两个 ReplicaSet 的 Pod 不会互相数错。

为什么这样设计

选中的：声明式 + 水平触发 + 标签选择

只存“要什么”，每个控制器只管一件事、只和 API Server 说话。任何组件挂了、重启了、漏了几个事件，回来再比一遍就能接着干；新加一种对象（比如数据库的 Operator），只要写一个新的控制器，不用改别人。

被放弃的：命令式调用 + 事件驱动

“Pod 挂了这个事件来了，就去起一个新的”：事件丢一个，这个副本就永远少一个；处理到一半进程重启，不知道做到哪一步了。组件之间直接互相调用，一个变了接口，一串都要改。

决定胜负的约束：几千个 Pod、几百台机器，随时有东西在坏，任何一步都可能失败，网络还会分区。在这种环境里，“记住刚才发生了什么”不可靠，“看看现在差多少”永远可靠。代价是一切都是最终一致的：改了 spec，不会立刻生效，要等几个控制器各自转一圈（⑥ 坑 5 就是这么来的）。

Deployment 怎么一个个换：maxSurge 和 maxUnavailable

滚动发布时，Deployment 控制器同时盯着两个约束：Pod 总数不超过 replicas + maxSurge，能接流量的不少于 replicas − maxUnavailable。在这两条之间，它尽量快地扩新的、缩老的。百分比换成个数时，maxSurge 向上取整，maxUnavailable 向下取整；两个都算出 0 的话，maxUnavailable 按 1 算，不然就动不了。

实验台：滚动发布每一轮的样子

先猜：4 个副本，不写策略（默认 maxSurge 25%、maxUnavailable 25%），滚动过程中能接流量的 Pod 最少剩几个？

每一轮 = 新 Pod 从创建到 Ready 的那段时间。实测 ⑤ 里 1 / 0 的设置，4 个副本走了 4 轮，每轮约 6.5 秒，共 26.4 秒。终止中的老 Pod 不算进总数，所以节点上实际同时存在的 Pod 会比表里多一个（⑤ 里 EndpointSlice 有一刻是 5 个地址）。

⑤套进场景：在本机 kind 集群里，把全景第 5、9、11 站做一遍

kind 用 Docker 容器当节点，在本机起了一个三节点的集群（1 个控制面、2 个工作节点，Kubernetes 1.37.0）。把上一页的两个镜像装进去，部署 4 个 order-svc，再放一个 busybox 当“用户”，每 50 毫秒经 Service 调一次接口、记下成败。然后依次：删一个 Pod、改一个 Pod 的标签、滚动发布到 1.8.4、回滚、有人手动改副本数。

⑤k8s/order-svc.yaml完整代码 →
apiVersion: apps/v1
kind: Deployment
metadata: { name: order-svc }
spec:
  replicas: 4
  selector:
    matchLabels: { app: order-svc }   # 管哪些 Pod
  strategy:
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }
  template:                            # 改它 = 新版本
    metadata:
      labels: { app: order-svc }
    spec:
      containers:
        - name: app
          image: lab/order-svc-layered:1.8.3
          readinessProbe:
            httpGet: { path: /actuator/health/readiness, port: 8080 }
---
apiVersion: v1
kind: Service
metadata: { name: order-svc }
spec:
  selector: { app: order-svc }         # 流量给哪些 Pod
  ports: [{ port: 80, targetPort: 8080 }]

看懂这次运行
  • 第 2 步：删除命令一发出，ReplicaSet 控制器 0.3 秒内就建了替补；剩下 6.8 秒是调度、起容器、JVM 启动、readiness 通过。客户端一次都没失败，因为被删的 Pod 先从 EndpointSlice 里摘掉，另外 3 个在接流量。
  • 第 3 步最能说明“用标签挑人”：Pod 本身一点没变，还在运行，只是标签变了，ReplicaSet 和 Service 的查询结果里就没有它了。线上排查时常这样把一个 Pod “摘出来”保留现场。
  • 第 4、5 步：时间表和 ④ 实验台里 1 / 0 那一行一模一样，4 轮，每轮一个新 Pod。但客户端有 4 次和 3 次失败：老 Pod 被缩掉时，“从地址表摘掉”和“给进程发 SIGTERM”是同时开始的，kube-proxy 还没更新完的那一小会儿，请求被发到了正在关的进程上。下一页的 preStop 就是治这个的。
  • 第 5、6 步：kubectl 1.37 在 rollout undo 时主动提醒：这样回滚会让集群和你手里的 YAML 不一致。第 6 步就是后果：任何人再 apply 一次，以 YAML 为准。所以全景里回滚走的是 git revert。

⑥反例和误用

第一圈 · 不知道就会出事的

1直接建一个裸 Pod，没有控制器← ④ 控制循环才会补
现象
节点一重启，这个服务就没了，也没人报警；手动 kubectl run 起的“临时”服务，一跑就是半年。
根源
Pod 本身不会复活。补副本的是 ReplicaSet 控制器，没有它，就没有人在乎这个 Pod 还在不在。
做法
长期运行的服务一律用 Deployment（有状态的用 StatefulSet，每个节点一个的用 DaemonSet，跑完就退的用 Job）。
2标签和选择器写得太宽← ④ 用标签挑人
现象
两个 Deployment 都选 app: order，Service 把下单请求发给了订单报表服务的 Pod；或者一个 Pod 被两个 ReplicaSet 来回争。
根源
选择器就是查询，查询写宽了，就会选中不该选的。Deployment 的 selector 创建后还不能改。
做法
至少用 app.kubernetes.io/name + app.kubernetes.io/instance 两个标签；一个命名空间里不复用同样的标签组合。
3线上用 kubectl 改，YAML 没跟着改实测← ④ 声明式：最后写进去的期望就是真相
现象
⑤ 第 6 步：有人 scale 到 2，下一次 apply 又变回 4；rollout undo 回到了 1.8.3，下一次 apply 又回到 YAML 里写的版本。kubectl 1.37 回滚时会直接提醒这件事。
根源
控制器只认 spec，谁最后写，谁说了算。命令式改动不留在 Git 里，下一次声明式同步就把它覆盖。
做法
生产只通过 Git 改（全景第 4、11 站）；紧急时可以先用命令止血，但要马上把同样的改动提交回去。
4以为 Service 会按请求均衡← ④ Service 是连接级转发
现象
扩容到 6 个副本，新的 2 个几乎没流量；gRPC 或 HTTP keep-alive 的调用方，所有请求都压在最早那几个 Pod 上。
根源
Service 的虚拟 IP 由各节点上的 kube-proxy 做四层转发，在建连接时挑一个 Pod；连接一直不断，就一直是它。
做法
长连接的客户端定期重建连接，或者用客户端负载均衡（J10 的 LoadBalancer）、服务网格、Gateway 在七层按请求分。
5只配了 readiness，滚动时还是零星失败实测← ④ 最终一致，各自异步
现象
⑤ 里滚动 317 次请求失败 4 次、回滚 280 次失败 3 次。readiness 管的是“新的什么时候接流量”，管不了“老的什么时候停”。
根源
缩掉一个老 Pod 时，EndpointSlice 控制器摘地址、各节点 kube-proxy 更新转发规则、kubelet 发 SIGTERM，这几件事同时开始、各走各的。规则还没更新的节点，会把请求发给已经在关的进程。
做法
给容器加 preStop（比如 sleep 5～10 秒），让摘流量先跑完；应用开优雅停机。下一页实测加上之后还有没有失败。
6新集群还在装 ingress-nginx← ④ Ingress 和 Gateway API
现象
网上教程大多是 ingress-nginx，装上能用，但 2026 年 3 月以后它不再发布新版本，也不再修安全漏洞。
根源
历史原因：Ingress API 只定义了很少的东西，大量功能靠各家注解实现，难以继续演进；社区把精力转到 Gateway API。
做法
新集群选一个 Gateway API 的实现；老集群的 ingress-nginx 列进迁移计划。

第二圈 · 团队里该怎么写

  • 所有对象的 YAML 都在 Git 里：防“集群里有、仓库里没有”的东西，谁也说不清它从哪来。
  • 一个服务一个 Deployment、一个 Service，用推荐标签（app.kubernetes.io/name、/version、/part-of）：防选择器误伤，也让监控按标签聚合。
  • 滚动策略显式写出来：副本少的服务用 maxSurge: 1, maxUnavailable: 0；防默认的 25% 在小副本数时意外少掉一个。
  • 不同环境用不同命名空间，生产的写权限只给流水线：防在测试环境的终端里误操作生产。
  • 改 Pod 模板时带上 change-cause（或者靠 Git 提交记录）：防 rollout history 里一列 <none>，回滚时不知道该回到哪一版。

第三圈 · 深一层

控制器怎么“看”：List + Watch + 本地缓存

控制器启动时先 List 一遍拿全量，记下版本号（resourceVersion），之后从这个版本开始 Watch 增量，存在本地缓存（informer）里。真正干活时读的是本地缓存，不打扰 API Server；处理逻辑只拿到对象的 key，再从缓存里读最新的状态去比较。所以它天然是“水平触发”的：同一个对象连变五次，可能只处理一次最新的。

回滚的真相：再发一次老模板

Deployment 用 Pod 模板的哈希给 ReplicaSet 起名（order-svc-9f74c49d）。rollout undo 把上一版 ReplicaSet 的模板拷回 Deployment 的 spec，于是哈希又对上了那个老 ReplicaSet，它被扩回 4 个；版本号不倒退，而是 +1（⑤ 里 1 号变成了 3 号）。历史版本留几个由 revisionHistoryLimit 决定，默认 10。

终止中的 Pod 不算数

计算 maxSurge 时，正在终止的老 Pod 不算在总数里，所以节点上实际同时存在的 Pod 会比 replicas + maxSurge 多：⑤ 里 EndpointSlice 有一刻是 5 个地址。老 Pod 的优雅停机越长，重叠越多，节点就要多留资源。

API Server 挂了会怎样

已经在跑的 Pod 照跑，kube-proxy 的转发规则也还在，用户基本无感；但不会自愈、不能发布、不能扩容，直到它回来。控制面和数据面是分开的，这也是“各自对齐”这个设计带来的好处。

自测

1. 用一句话说出这一页的精华

只把期望状态存进 API Server，让一群只管一件事的控制器按“现在差多少”反复对齐，对象之间用标签查询而不是互相点名；自愈、滚动、回滚都是这个循环的不同用法。

2. 发布脚本加手改 Nginx，疼在哪？

脚本只在跑的那一刻是对的，之后机器坏了没人纠正；中途失败留下半成品，不知道怎么继续或回去；状态散在各台机器和 Nginx 配置里。

3. 坑 5（只配 readiness 还零星失败）的根源是 ④ 的哪一条？

最终一致、各自异步：摘地址、更新各节点转发规则、给进程发 SIGTERM 是几个组件同时各自做的，没有谁等谁。

4. 预测：API Server 停了 5 分钟，这期间 order-svc 的一个 Pod 所在节点宕机了。用户会看到什么？API Server 回来以后呢？

宕机节点上那个 Pod 的连接会失败；各节点的转发规则还指着它（没人更新 EndpointSlice），所以落到它上面的请求持续失败，大约四分之一。API Server 回来后，节点被判定为不可用，Pod 被标记删除，EndpointSlice 摘掉它，ReplicaSet 在别的节点补一个。从 ④ 推出：数据面能独立运行，但纠错要靠控制面。

5. 预测：4 个副本，maxSurge: 0、maxUnavailable: 1，滚动时最少几个能接流量？节点要不要多留资源？

最少 3 个；不用为新 Pod 多留资源，因为总数不超过 4（但终止中的老 Pod 还占着资源，见第三圈）。先停一个老的、再起一个新的，轮流进行。可以在实验台里验证。

6. 放回全景：第 5 站前后各是什么？如果第 4 站同步进来的 YAML 把 selector 写成了 app: order，而集群里还有一个 order-report 服务也用这个标签，会怎样？

前面是第 4 站 Argo CD 把部署清单同步进来，后面是第 6 站调度器给新 Pod 挑节点。selector 一旦改了，Deployment 会被 API Server 拒绝（Deployment 的 selector 不能修改）；如果是新建的 Service 用了 app: order，它会把 order-report 的 Pod 也选进来，第 9 站切流量时，一部分下单请求被发到报表服务上，返回 404 或 500。

档位：标准。本机跑过（2 核 ARM 虚拟机，kind v0.33.0，节点镜像 kindest/node:v1.37.0，kubectl v1.37.0，镜像来自上一页）：./run.sh 完整两次（第一次 version 检查偶尔超时，加了重试后重跑），⑤ 的输出来自第二次；两次的数字接近（删 Pod 后 0.3 s 建替补、7.1～7.7 s Ready；滚动 26.3～26.4 s，失败 4～5 次；回滚 22.7～23.8 s，失败 3～6 次）。实验台的滚动模拟在 node 里跑过，1 / 0 那一行和实测的 4 轮一致。

按文档：kubectl explain（1.37）里 maxSurge 默认 25%、按百分比算时向上取整，maxUnavailable 默认 25%、向下取整，两者不能同时为 0；revisionHistoryLimit 默认 10；Deployment 的 selector 创建后不可修改。ingress-nginx 的 README 写明 2026 年 3 月后不再维护，GitHub 仓库已归档；Gateway API 最新版本 v1.7.0（2026-10-29）。
