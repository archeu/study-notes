五个部件来自两个家族：Spring Cloud 与 Spring Cloud Alibaba 怎么选

它们不是二选一。Spring Cloud 定接口（服务发现、注册、负载均衡、熔断的抽象），并自带网关、OpenFeign、LoadBalancer 这些通用部件；Spring Cloud Alibaba 用 Nacos、Sentinel、Seata、RocketMQ 去实现其中一部分接口。交易靶场就是混着用的：网关、Feign、LoadBalancer 来自前者，注册配置、熔断来自后者。真正要选的是版本：Boot、Spring Cloud、Spring Cloud Alibaba 三条线必须对齐。实测五种组合，错配的两种在启动时就因为找不到类而失败。

①为什么学：新项目的第一个决定

在全景第 1 站之前，有一个更早的决定：pom 里引哪几个 BOM、哪几个 starter、各用什么版本。招聘要求里常写“熟悉 Spring Cloud / Spring Cloud Alibaba”，指的就是能说清楚：全景里每个部件来自哪儿，换一个行不行，升级时三条版本线怎么一起动。

②老办法：各挑各的库，各配各的版本

  • 不用 BOM，每个依赖自己写版本：Nacos 客户端、Sentinel、Spring Cloud Commons 各升各的，运行时才发现类找不到（⑤ 的 B、E 就是这种错）
  • 2018 年前后的老项目：Eureka + Ribbon + Hystrix + Zuul 一套 Netflix，后三个先后进入维护、2020.0 被移除，升级 Spring Cloud 时一次要换三个部件
  • “用 Alibaba 就不用 Spring Cloud” 的误解：SCA 本身就是建在 Spring Cloud Commons 上的，它没有网关和 HTTP 客户端
  • 做对的那一半：用三个 BOM 管版本，自己一个版本号都不写

这个“技术”的精华就是一句话：Spring Cloud 定接口和通用部件，SCA 提供中间件实现，版本由 Boot 牵头、三条线一起走。不懂这一点，就会出现“为了用 Nacos 3 单独把客户端升到最新”“Boot 先升到 4、Spring Cloud 下个月再说”这种事。

③选谁：三种组合

注册 / 配置熔断限流网关 / 调用适合
纯 Spring CloudEureka 或 Consul；Config Server（配置放 Git）Spring Cloud CircuitBreaker + Resilience4jGateway、OpenFeign / HTTP Service Clients海外项目、不想引入阿里中间件
Spring Cloud + SCA（交易靶场）Nacos 一套两用Sentinel（规则放 Nacos 动态下发）Gateway、OpenFeign国内大多数团队；中文资料最多
Kubernetes 原生K8s Service + ConfigMap（Spring Cloud Kubernetes 接入）Resilience4j，或网格Ingress / Gateway API，或 Gateway已经全面上 K8s 的团队（J14）

选择规则：注册、配置、熔断这三样按团队的中间件选（有 Nacos 运维能力就用 SCA）；网关、HTTP 调用、负载均衡一律用 Spring Cloud 官方的；版本按 Boot 定，查对应表，三条线一起升。

为什么这样设计：为什么不能各升各的

如果每个组件独立发版、独立兼容

Spring Cloud 的自动配置大量直接用 Boot 的内部类（Web 服务器事件、属性类），Boot 一个大版本挪了包，Spring Cloud 就得跟着改；没有统一的版本列车，用户就得自己去试几十个组件的组合。

版本列车 + BOM

Spring Cloud 把十几个子项目按一个年份号打包发布，一个列车只对应一两条 Boot 小版本线；SCA 再跟着 Spring Cloud 的列车发版。用户只需要选 Boot，剩下的查表。代价：升级是“三条线一起”的大动作，SCA 跟得慢时（比如没有 2024.0 那一条），用户就卡在上一个 Boot 版本。

决定胜负的约束：Spring Cloud 和 Boot 的内部结构耦合得很深。⑤ 的两个失败组合都不是“功能不兼容”，而是类在 Boot 3 和 Boot 4 之间换了包，启动时直接找不到。

最少的写法

pom.xml：三个 BOM，自己不写一个版本号交易靶场的组合
<properties>
  <spring-boot.version>3.5.16</spring-boot.version>
  <spring-cloud.version>2025.0.3</spring-cloud.version>
  <spring-cloud-alibaba.version>2025.0.0.0</spring-cloud-alibaba.version>
</properties>
<dependencyManagement><dependencies>   <!-- 顺序：Boot → Spring Cloud → SCA，先声明的优先 -->
  spring-boot-dependencies / spring-cloud-dependencies / spring-cloud-alibaba-dependencies（type=pom, scope=import）
</dependencies></dependencyManagement>

⑥细节：版本、配置入口、老组件

第一圈 · 注意事项

1只升一条线← ④ 机制 2 三条线一起走
现象
⑤ 的 B（只升 Boot）、E（只升 Spring Cloud）：启动时 ClassNotFoundException，没有一句“版本不兼容”的提示。
根源
Spring Cloud 直接用 Boot 的内部类，Boot 3 到 4 挪了包；兼容性检查来不及执行，容器就因为找不到类崩了。
做法
升级是一次提交里同时改三个版本属性；先查对应表，在预发跑通再合并。
2为了用新版 Nacos，单独把客户端版本写死← ④ 机制 1 SCA 填实现
现象
在 pom 里单独写 nacos-client 的新版本，SCA 的自动配置调用的方法在新客户端里改了签名，启动或运行时报 NoSuchMethodError。
根源
SCA 的 Nacos 适配层是按它 BOM 里那个客户端版本写和测的（2025.0.0.0 对 3.0.3，2025.1.0.0 对 3.1.1）。
做法
客户端版本跟 SCA 走；服务端可以比客户端新（本站的实验都是 3.0.3 / 3.1.1 客户端连 3.3.0 服务端）。
3还在用 bootstrap.yml，配置中心的配置读不到← 版本差异
现象
从老项目拷来的 bootstrap.yml 里写了 Nacos 配置中心地址，启动后 @Value 全是默认值。
根源
历史原因：Spring Cloud 2020.0 起默认不再读 bootstrap 上下文。
做法
改用 spring.config.import: optional:nacos:xxx.yaml（本站 Nacos 页就是这么配的）；实在要兼容，引 spring-cloud-starter-bootstrap。
4Boot 4 上不带 web 的服务，注册中心起不来← ⑤ 第一次跑踩到
现象
一个只消费 MQ、不对外提供 HTTP 的服务，引了 Nacos 注册，Boot 4 下启动报 ClassNotFoundException: …web.server.context.WebServerInitializedEvent（本机实测）。
根源
Boot 4 把 Web 服务器相关的类拆成了单独的模块；Spring Cloud 的自动注册类引用了它。
做法
这类服务要么不注册（它本来就不被调用），要么带上 web 起步依赖；升级 Boot 4 时把“没有 web 的服务”单独列出来测。
5Boot 升到 3.4，SCA 跟不上← ④ 为什么是版本列车
现象
Maven Central 上 SCA 没有对应 Spring Cloud 2024.0 的版本，从 2023.0.x 直接跳到了 2025.0.0.0。
根源
SCA 跟随 Spring Cloud 的列车发版，但不保证每一班都跟。
做法
用 SCA 的项目，升级节奏按 SCA 的版本线来定：要么停在 3.3，要么直接跳到 3.5。

第二圈 · 使用规范

  • 团队有一个父 POM，只在这里管三个 BOM 的版本；各服务不写版本号。防：坑 1、坑 2。
  • 升级 Boot 的工单必须同时列出 Spring Cloud 和 SCA 的目标版本，以及本次升级的依据（对应表、兼容性检查的默认值）。防：只升一条线。
  • 新项目的配置中心接入一律用 spring.config.import。防：坑 3。
  • 中间件服务端独立升级：Nacos、Sentinel 控制台、Seata TC 的服务端版本和客户端版本分开管理，先升服务端。防：客户端被服务端拖着走。
  • 每次升级跑一遍 ⑤ 那种“起得来吗”的冒烟测试，再跑接口回归。防：类找不到这种问题拖到上线时才发现。

自测

1. 用一句话说出这一页的精华

Spring Cloud 定接口和通用部件（网关、Feign、LoadBalancer），Spring Cloud Alibaba 用 Nacos、Sentinel、Seata、RocketMQ 实现其中一部分，两者混着用；版本由 Boot 牵头，Boot、Spring Cloud、SCA 三条线按对应表一起升。

2. 各挑各的库、各写各的版本，疼在哪？

组件之间依赖彼此的内部类，版本错一点就运行时类找不到；Netflix 那一套先后停更，升级时要一次换好几个部件；BOM 把这些组合关系固定下来。

3. ⑤ 的 B 为什么失败？根源是 ④ 的哪条？

机制 2：Spring Cloud 2025.0 是按 Boot 3.5 的类结构写的，Boot 4 把 ServerProperties 挪了包，启动时找不到类。三条线必须一起走。

4. 预测：交易靶场想把注册中心从 Nacos 换成 Consul，要改哪些地方？网关和 Feign 要改吗？

换依赖（去掉 SCA 的 nacos-discovery，加 spring-cloud-starter-consul-discovery）、换配置（地址、健康检查），实例元数据和灰度用的 hint 要在 Consul 里重新配；网关的 lb:// 和 Feign 都只依赖 DiscoveryClient 接口，不用改（机制 1）。配置中心那部分如果也在 Nacos，要另选（Consul KV 或 Config Server）。

5. 预测：一个用 SCA 的项目在 Boot 3.3 上，要升级到最新，最少要动几次大版本？

SCA 没有 2024.0 那一条（坑 5），所以一步是 Boot 3.3 → 3.5（Spring Cloud 2023.0 → 2025.0，SCA 2023.0.x → 2025.0.0.0），下一步 3.5 → 4.x（Spring Cloud 2025.1，SCA 2025.1.0.0）。也可以一步跳到 4.x，但要同时处理 Boot 4 的大量变化，风险更集中。

6. 放回全景：第 1 站用到了哪几个家族的哪些部件？如果三个版本没对齐（比如 ⑤ 的 E），整条链路会怎样？

第 1 站：Spring Cloud Commons 的 ServiceRegistry 接口 + SCA 的 NacosServiceRegistry 注册，SCA 的 nacos-config 拉配置。没对齐：每个服务都在启动阶段就因为找不到类崩溃，第 1 站根本走不完，后面 10 站都不会发生；这类问题在本地起一次就能发现，所以必须有“起得来吗”的冒烟测试。

档位：标准。本机跑过（2 核 ARM 虚拟机，JDK 17，Nacos 3.3.0 容器）：⑤ 的 run.sh demo 跑了 3 次，前两次分别踩到 mvn -pl 带着整个父工程解析、没带 web 起步依赖两个坑，第三次是页面上的输出。版本对照器是查表（node 里跑过），实测结论来自 ⑤。

按源码和 POM：spring-cloud-commons 4.3.3 / 5.0.4 的 CompatibilityVerifierProperties（默认 3.5.x / 4.0.x, 4.1.x）；Spring Cloud Alibaba 2023.0.3.4、2025.0.0.0、2025.1.0.0 根 POM 的父工程（spring-cloud-build 4.1.3 / 4.3.0 / 5.0.0）和 BOM 里的 Nacos、Sentinel、Seata 版本；Maven Central 上的版本列表和发布时间。

按文档：Spring Cloud Alibaba 版本说明 wiki（2021.0、2022.0 两条线）；Spring Cloud 2020.0 移除 Hystrix、Ribbon、Zuul 并默认不再读 bootstrap。
