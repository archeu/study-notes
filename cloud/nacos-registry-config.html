inventory-2 下线了，订单服务多久知道：Nacos 注册发现与配置中心

Nacos 做两件事：注册中心记着“inventory-svc 现在有哪几台”，变了就推给订阅的调用方；配置中心记着“inventory.timeout 现在是多少”，变了也推。它判断一台实例死没死，看的是那条 gRPC 长连接还在不在：进程被杀、连接断了，半秒多就摘掉；进程卡住但连接还在，它就一直说“健康”。所以注册中心只回答“谁活着”，回答不了“谁好用”，后者要靠调用方自己的超时和熔断。

这一页的位置J10 下钻第 2 步。服务发现的第一圈在 RPC 原理里讲过“为什么要有注册中心”；这一圈用 Nacos 3.3.0 真跑：实例出了各种事，调用方多久知道；配置改了，哪种写法不重启就生效。

①为什么需要：订单服务要知道库存服务“现在”在哪

在全景第 1 站，这一步要解决：五个服务十几个实例，IP 随扩容、发版、宕机一直在变；订单服务第 8 站调库存时，手里得有一份此刻可用的 inventory-svc 地址列表。第 5 站还有一件同类的事：读超时要从 2 秒改成 800 毫秒，不能为此重启三台订单服务。

②没有它会怎样：写死、DNS、前面挂一台 Nginx

地址写在配置文件里

  • 扩容一台，所有调用方改配置、重启
  • inventory-2 挂了，调用方不知道，照样发
  • 简单，实例几乎不变时够用

内网 DNS：inventory.svc → 多个 IP

  • JVM 和操作系统都缓存 DNS，改了以后多久生效说不准
  • DNS 不知道实例死活，也带不了“版本、权重”这些元数据
  • Kubernetes 的 Service 就是这条路的加强版（J14）

中间放一台负载均衡（Nginx、SLB）

  • 每次调用多一跳，它自己也要高可用
  • upstream 列表还是要有人维护，扩容时改它
  • 对外入口仍然这么做（网关前面那层）

缺的那一块：实例自己报到、死了自动除名、变化主动通知调用方，调用方拿到列表后直接连实例，不多一跳。这就是注册中心的精华。配置也一样：配置文件写死、改了重启，是“改得慢”；配置中心让改动几百毫秒内推到每个实例（⑤ 实测 0.16 秒）。

不懂精华时的典型误用以为“注册中心里显示健康 = 这台能用”，于是调用方不配超时、不配熔断。⑤ 里那台每次要 3 秒才回的 inventory-2，在 Nacos 里一直是健康的。

③相邻方案：Eureka、ZooKeeper、Consul、Nacos、Kubernetes

怎么判断实例死活网络分区时配置中心现在的位置
Eureka客户端每 30 秒续约，90 秒没续约才剔除倾向可用（AP），有自我保护没有，配 Spring Cloud ConfigSpring Cloud Netflix 里还在维护，新项目少用
ZooKeeper会话超时，临时节点随会话消失倾向一致（CP），少数派那边不可写能当，但要自己封装Dubbo 老项目、Kafka 老版本
Consul本机 agent 主动检查 HTTP、TCP 等CP（Raft）有 KV多语言、跨机房场景
Nacos临时实例：gRPC 长连接在不在；持久实例：服务端主动探测临时实例 AP，持久实例和配置 CP一个服务两样都有国内 Spring Cloud Alibaba 的默认选择

本页学 Nacos 3：交易靶场用 Spring Cloud Alibaba，一个 Nacos 集群同时当注册中心和配置中心，国内招聘里出现得最多。CAP 的两种取舍在 CAP、BASE 与一致性模型里讲过：注册中心多半选 A，宁可列表旧一点，也不能因为注册中心分区就全站调不通。

④原理：一条长连接，三件事

先知道这些 临时实例（默认）：实例的存在绑在客户端连接上，连接没了实例就没了，数据只在 Nacos 内存里。持久实例：实例信息落盘，客户端走了也还在，由 Nacos 主动去探测它的端口。Spring Cloud 应用注册的都是临时实例。 Nacos 2.x 起客户端和服务端之间是 gRPC 长连接，端口 = 主端口 + 1000（8848 → 9848）。注册、订阅、推送、配置通知都走这一条连接。1.x 是每 5 秒一次 HTTP 心跳。

机制 1：注册和订阅，变化靠推

机制 2：死活看连接，而不是看业务

客户端这条连接空闲满 5 秒，就发一个健康检查请求；服务端每 3 秒扫一遍所有连接，某条连接 20 秒没有任何动静，就发一个探测请求过去，等不到回复就关掉连接、注销它名下的实例。连接如果是被对方关掉的（进程退出时操作系统会关 socket），服务端立刻就知道。

机制 3：配置也是推，但只有“会重新绑定”的值才会变

  1. 启动时，spring.config.import: nacos:inventory-svc.yaml 把这份配置拉进 Spring 的 Environment，客户端记下它的 MD5，并在长连接上登记“我在听这个 dataId”。
  2. 有人发布新内容，服务端在长连接上发一个“变了”的通知，客户端再去取新内容（⑤ 实测：发布成功后 0.16 秒监听器就收到）。
  3. Spring Cloud Alibaba 发出 RefreshEvent，ContextRefresher 重新加载 Environment，算出变了哪些 key（日志：Refresh keys changed: [inventory.timeout]），再发 EnvironmentChangeEvent。
  4. ConfigurationPropertiesRebinder 听到这个事件，把所有 @ConfigurationProperties Bean 重新绑定一遍（⑤：0.47 秒变成 800）；@RefreshScope 的 Bean 被清掉，下次用到时重新创建。普通单例里的 @Value 字段是创建时注入一次的，不会变（⑤：还是 2000）。

为什么这样设计：1.x 的 HTTP 心跳为什么被换掉

1.x：每个实例每 5 秒发一次 HTTP 心跳

15 秒没心跳标为不健康，30 秒删除。1 万个实例就是每秒 2000 次 HTTP 请求，每次都要建连接或占一个连接、走一遍过滤器；推送走 UDP，丢了要靠客户端定时拉来兜底。

2.x 起：一条 gRPC 长连接，活着就是“连接在”

心跳、注册、推送、配置通知共用一条连接；连接自己断了服务端立刻知道，不用等三个心跳周期。空闲时才发轻量的健康检查。代价：判断依据从“定时报到”变成了“连接状态”，进程冻住而连接没断时，要靠 20 秒的探测兜底。

决定胜负的约束：实例数量上去以后，心跳本身就是负载。用连接状态代替心跳，开销和实例变化量成正比，而不是和实例数量成正比。两种设计都看不到“业务慢”，这一点交给调用方。

⑥细节：Nacos 看不见的，和它看见了但调用方还不知道的

第一圈 · 注意事项

1卡住的实例一直“健康”← ④ 机制 2 看连接
现象
inventory-2 每次 3 秒才回，30 秒里一次推送都没有，调用方照样分一半流量给它（⑤ 第 ③ 项）。
根源
临时实例的死活看 gRPC 连接；业务线程池满了、慢 SQL 卡住，Nacos 客户端的线程照常收发。
做法
调用方必须有读超时、熔断（全景第 10 站）；需要时让实例自己“认怂”：业务健康指标坏了，调 /actuator/serviceregistry 把自己设成 DOWN（⑤ 第 ④ 项：0.58 秒生效）。
2冻住或断网的实例，有 20 多秒的黑洞← ④ 机制 2 20 秒探测
现象
长时间 Full GC、虚拟机被挂起、网络单向不通：23～25 秒里它还在列表上，发过去的请求全部等到超时（⑤ 第 ⑥ 项）。
根源
连接没有被关掉，服务端只能等 20 秒没动静再探测。
做法
调用方读超时要短（800 ms 而不是默认 60 s），超时后对幂等请求换一台重试；这 20 多秒由调用方的熔断和重试兜住。
3Nacos 已经摘了，调用方还在发← ④ 机制 1 本地缓存
现象
⑤ 里订阅方 0.58 秒就拿到新列表，但 OpenFeign 背后的 Spring Cloud LoadBalancer 自己还缓存一份，默认 35 秒，这段时间里还会挑到已下线的实例。
根源
“Nacos 客户端缓存”和“LoadBalancer 缓存”是两层，后一层不听推送，只按时间过期。
做法
发版先 DOWN、等一个缓存周期再停进程（全景第 11 站）；或者调短 spring.cloud.loadbalancer.cache.ttl。下钻第 3 步实测。
4@Value 改了配置不生效← ④ 机制 3 第 4 步
现象
日志里明明打了 Refresh keys changed: [inventory.timeout]，byValue 还是 2000（⑤ 第 ② 项）。
根源
@Value 在 Bean 创建时注入一次；刷新只会重新绑定 @ConfigurationProperties、重建 @RefreshScope Bean。
做法
会热更新的配置一律用 @ConfigurationProperties；值被复制进了启动时建好的对象（比如 HTTP 客户端的超时），要监听 EnvironmentChangeEvent 自己重建，或者每次用时去读属性对象。
5连上了，却注册不上、发布返回 false← 版本差异
现象
本机实测：不带账号密码调 publishConfig，返回 false，没有异常。
根源
官方 3.3.0 镜像默认开鉴权，第一次还要先给 nacos 用户设密码。历史原因：1.x、2.x 的镜像默认不开。
做法
客户端配 username、password；生产给每个应用单独的账号，只授权自己的命名空间。
6只开了 8848，客户端一直连不上← ④ 先知道：+1000 端口
现象
Docker 只映射了 8848，或者 K8s Service 只暴露了 8848：客户端日志反复重连，注册失败。
根源
2.x 起客户端用主端口 + 1000 的 gRPC 端口；集群之间还要 +1001。映射成 18848 时，gRPC 也必须是 19848。
做法
主端口和 +1000 一起开；前面挂负载均衡时，gRPC 端口要按 TCP 转发。

掐表台：出了事，调用方多久不再往坏实例上发

先猜：inventory-2 被 kill -STOP 冻住，Nacos 大约多久把它从列表里拿掉？

inventory-2 出了什么事

调用方 LoadBalancer 缓存

Nacos 那一段用的是 ⑤ 的实测中位数；缓存那一段按最坏情况（刚刷新完就出事）算；每台订单服务每秒 200 次 reserve，轮询，一半落到 inventory-2，3 台订单服务。

第二圈 · 使用规范

  • 命名空间（namespace）按环境分：dev、test、prod 各一个，ID 写进各环境的启动参数。防：测试环境的实例注册进生产，被生产流量调到。
  • dataId 用 ${spring.application.name}.yaml，公共配置单独一个 dataId 用 optional: 引入。防：一个大文件谁都改，改一处刷新所有服务。
  • 生产 Nacos 至少 3 节点，配置存外部 MySQL；客户端 server-addr 写多个地址或一个内网域名。防：单点。
  • 敏感配置（库密码、密钥）不明文放：用 Nacos 的配置加密插件或外部密钥服务。防：控制台能看到的人都知道密码。
  • 配置改动走审核，Nacos 的历史版本用来回滚。防：半夜手抖改坏全站超时。
  • 发版顺序：DOWN → 等调用方缓存过期 → 停进程 → 起新进程 → 健康检查通过 → UP。防：坑 3 的 35 秒（下钻第 6 步灰度页细讲）。

第三圈 · 版本差异和深处

1.x2.x3.x（本页 3.3.0）
客户端和服务端HTTP；实例每 5 s 心跳，15 s 不健康，30 s 删除gRPC 长连接（+1000 端口），连接即心跳同 2.x
变化推送UDP 推送 + 客户端定时拉兜底长连接推送，服务端延迟 500 ms 合并同 2.x
一致性协议临时实例 Distro（AP）；持久实例 Raft临时 Distro；持久实例和内置存储的配置用 JRaft同 2.x
鉴权默认关默认关官方镜像默认开，要先设管理员密码
控制台和服务在一个端口同左控制台单独 8080 端口，管理接口改成 /nacos/v3/admin/…

两条深处的结论：为什么临时实例用 AP：注册中心分区时，与其让一半调用方拿不到列表（全站调不通），不如让它们拿到可能旧几秒的列表，再靠超时、重试兜住；Distro 让每个节点负责一部分客户端，写在本节点、异步同步给别的节点。为什么推送要延迟 500 ms：发版时几十台实例在几秒里先后上下线，每变一次推一次会把订阅者冲垮，合并以后一批变化只推一次。

自测

1. 用一句话说出这一页的精华

Nacos 用一条 gRPC 长连接做注册、订阅、推送和配置通知：实例死活看连接，连接断了半秒多就推给调用方，冻住要二十多秒，业务变慢它永远看不见；配置变了也是推，但只有 @ConfigurationProperties 和 @RefreshScope 会跟着变。

2. 写死地址、DNS、中间挂 Nginx 各疼在哪？

写死：扩缩容要改所有调用方并重启，挂了也不知道。DNS：多层缓存，生效时间说不准，不知道死活、没有元数据。Nginx：多一跳，它自己要高可用，upstream 还是要人维护。

3. 坑 1（卡住却健康）的根源是 ④ 的哪条？

机制 2：临时实例的健康就是“gRPC 连接活着”。业务线程卡住不影响 Nacos 客户端的线程和连接，所以服务端没有任何信号。

4. 预测：Nacos 三个节点全部挂掉 1 分钟，订单服务调库存还能不能调通？这期间 inventory-2 被 kill -9 呢？

能调通：调用方用的是本地缓存的列表（机制 1）。但 inventory-2 被杀以后没人通知调用方，列表里还有它；请求发过去会立刻连接被拒（端口没人监听），快速失败，靠重试换到 inventory-1。Nacos 恢复后客户端重连、重新注册，列表才更新。

5. 预测：一次 Full GC 停顿了 8 秒，这台实例会被摘掉吗？

不会。8 秒小于服务端 20 秒没动静才探测的门槛；停顿结束后客户端继续发健康检查，连接恢复活跃。但这 8 秒里发给它的请求都会超时，靠调用方的超时和熔断处理。

6. 放回全景：第 1 站和第 11 站分别发生了什么？如果 Nacos 推送坏了（只能注册、推不出去），整条链路会怎样？

第 1 站：各实例启动时注册、订阅、拉配置。第 11 站：把 inventory-2 权重调 0 或下线，推给调用方。推送坏了：调用方的列表停在旧状态，新扩的实例拿不到流量，下线的实例还在挨调用；发版时（第 11 站那种先下线再停）就会出现成片失败，只能靠超时和熔断硬扛；第 5 站的配置改动也推不下去。
