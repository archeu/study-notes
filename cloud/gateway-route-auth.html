1024 的请求进门之前：Spring Cloud Gateway、路由与鉴权

网关是所有外部请求的唯一入口：按路由（路径、头、参数这些断言）决定转给哪个服务，在转发前后跑一串过滤器（验 JWT、改头、限流、改路径），最后用 lb:// 交给负载均衡挑实例。它跑在 WebFlux 和 Reactor Netty 上，几个事件循环线程就扛住成千上万个连接，代价是过滤器里一行阻塞代码就能把整个网关拖慢：实测吞吐从 200 个/秒掉到 19 个/秒。

这一页的位置J10 下钻第 4 步。单体里的请求入口是 Spring MVC 的过滤器链，token 怎么验在 Spring Security 与 token；网关把这两件事挪到所有服务前面。挑实例那一步和上一页 OpenFeign 与负载均衡 是同一个 LoadBalancer。第 3 站的限流留给下一页 Sentinel。

①为什么需要：五个服务，一个门

在全景第 2～4 站，这一步要解决：App 只认一个域名，后面却是五个服务、十几台实例。每个请求都要先验一次“你是谁”，把 /api/orders/** 送到订单服务、/api/skus/** 送到商品服务，还要能按用户把一部分流量送到灰度版本（全景第 4 站）。

②没有它会怎样：每个服务各自对外，或者只有一台 Nginx

每个服务自己对外

  • 五个服务各验一遍 token、各配一遍跨域和黑名单，规则一改发五个版本
  • App 要知道五个地址；内部怎么拆的全暴露给外面
  • 库存服务这种只该内部调的，也得想办法挡住外部

前面一台 Nginx

  • upstream 是写死的 IP 列表，不认识 Nacos 里的服务名（要插件或脚本同步）
  • 验 JWT、按用户灰度要写 Lua，Java 团队维护不动
  • 做 TLS 卸载、静态资源、全站限流很合适，所以常常留在网关前面当第一层

缺的那一块：一个懂服务名、能用 Java 写过滤逻辑的入口，身份验一次，后面的服务只信它传来的头。网关的精华是“收拢”：入口收拢、横切逻辑收拢。不懂这一点的典型误用，是把订单列表拼装、跨服务聚合这些业务逻辑也塞进网关（坑 5），让入口变成最难改、最容易拖死全站的地方。

③相邻方案：Nginx、APISIX / Kong、Spring Cloud Gateway、K8s Ingress

写扩展用什么认不认服务名常见位置
Nginx / OpenResty配置文件、Lua不认，要同步最外层：TLS、静态、粗粒度限流
APISIX、KongLua 插件（APISIX 也支持外部插件），规则存 etcd 或数据库，动态生效有 Nacos、Consul 等服务发现插件多语言团队的统一 API 网关
Spring Cloud Gateway（WebFlux）Java：断言、过滤器、全局过滤器lb://服务名 直接走 LoadBalancerJava 团队的业务网关，在 Nginx 后面
Spring Cloud Gateway Server MVCJava，Servlet 模型，可配虚拟线程同上团队不熟响应式时的选择
Zuul 1Java，Servlet 阻塞认（Ribbon）已从 Spring Cloud 2020.0 移除，老项目才见到

本页学 Spring Cloud Gateway 4.3（WebFlux 版）：交易靶场是 Spring Cloud 栈，过滤器能直接用 Java 和团队的现有代码；它也是最能逼你搞懂“事件循环里不能阻塞”的那个。

④原理：找路由 → 排过滤器 → 挑实例 → 转发

先知道这些 WebFlux 和事件循环：不是“一个请求一个线程”。少数几个线程（Reactor Netty 默认 max(CPU 核数, 4) 个）轮流处理所有连接上的事件：读到请求、后端回包了、定时到了。线程从不等待，等待的事交给回调。所以过滤器返回的是 Mono<Void>，而不是直接干完活。 JWT：头.载荷.签名 三段，签名用密钥算出来；网关只要有密钥（或公钥）就能本地验证，不用每次去问认证服务。

机制 1：一个请求在网关里走过的路

机制 2：四个线程扛所有连接，前提是谁都不阻塞

⑤ 里在 2 核机器上连发 40 个请求，响应头里只出现了 4 个线程名 reactor-http-nio-1～4，各处理了 10 个。网关大部分时间在等后端，等待不占线程：发出请求后注册一个回调，线程马上去处理别的连接。可如果过滤器里写了 Thread.sleep(200)、同步查 Redis、JDBC，这个线程就真的停在那里，4 个线程全停住，整个网关每秒最多 4 ÷ 0.2 = 20 个请求（⑤ 实测 19 个/秒），不管是哪条路由。

机制 3：鉴权在网关，信任边界在网络

  1. 验签名和过期时间（本页用 HS256 共享密钥演示；生产用 RS256/ES256，网关只拿公钥，从认证服务的 JWKS 地址拉取并缓存）。
  2. 先删再写：删掉请求里所有外部可能带进来的身份头（X-User-Id），再写上验出来的值。⑤：客户端自己带 X-User-Id: 2048，后端收到的仍是 1024。
  3. 后端服务只信网关传来的头，前提是外面绕不过网关：服务只监听内网、安全组或 K8s NetworkPolicy 只放网关进来。
  4. 网关只做“认证”（你是谁）和粗粒度的“这个接口要登录”；“1024 能不能看订单 9527”这种业务授权留在订单服务里。

为什么这样设计：网关为什么选了事件循环

一个请求一个线程（Zuul 1、Servlet）

网关的活几乎全是等后端。后端慢到 3 秒时，每秒 1000 个请求就要 3000 个线程挂着等；线程栈、上下文切换先把网关拖垮。Zuul 1 就是这么被替换掉的。

事件循环（Spring Cloud Gateway WebFlux）

等待不占线程，几个线程扛上万个连接，后端慢了只是挂着的回调多一些。代价：所有过滤器都必须写成非阻塞的，一处阻塞拖累全部（⑤）；调试和栈跟踪也更难读。

决定胜负的约束：网关的工作是 I/O 等待，不是计算。等待的成本要和“线程数”脱钩。JDK 21 的虚拟线程提供了第三条路：Gateway Server MVC 配虚拟线程，用阻塞写法也不用为每个等待付一个平台线程，但要注意虚拟线程被 pin 住的情况。

public Mono<Void> filter(ServerWebExchange ex, GatewayFilterChain chain) {
    String user = verify(ex.getRequest().getHeaders().getFirst("Authorization"));
    if (user == null) {
        ex.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
        return ex.getResponse().setComplete();              // 不往后转发
    }
    ServerHttpRequest req = ex.getRequest().mutate()
        .headers(h -> { h.remove("X-User-Id"); h.set("X-User-Id", user); }).build();
    return chain.filter(ex.mutate().request(req).build());  // 之后的代码就是“后半段”
}

⑥细节：入口上的坑，影响的是全站

第一圈 · 注意事项

1过滤器里一行阻塞代码，全网关变慢← ④ 机制 2 事件循环
现象
⑤：过滤器里同步等 200 ms，吞吐从 201 个/秒掉到 19 个/秒，p50 从 218 ms 变成 2.6 s；不带这个逻辑的路由也一起排队。
根源
4 个事件循环线程被占住，所有连接上的事件都没人处理。
做法
用响应式客户端（Lettuce reactive、WebClient、R2DBC）；实在只有阻塞 API，用 Mono.fromCallable(…).subscribeOn(Schedulers.boundedElastic()) 挪到别的线程池；开发期用 BlockHound 抓阻塞调用。
2网关默认不设响应超时← ④ 机制 1 NettyRoutingFilter
现象
⑤：后端卡 5 秒，网关陪着等满 5 秒才回 200；设了 response-timeout: 3s 后 3.2 秒回 504。
根源
httpclient.response-timeout 没有默认值；后端卡多久，网关的连接和内存就占多久，App 那边早就放弃了。
做法
全局配一个比 App 超时短、比后端最长链路长的值（全景表：3 s），个别慢接口在路由的 metadata 里单独配 response-timeout。
3身份头没先删，谁都能冒充← ④ 机制 3 第 2 步
现象
只在“验出用户”时 set 头，某条免登录路由没走鉴权，外部带的 X-User-Id: 2048 原样传到后端。
根源
后端无条件信任这个头，而外部可以随便加头。
做法
在所有路由最前面统一删掉身份类请求头，再由鉴权过滤器写入；免登录路由也要删。⑤ 的写法是在鉴权过滤器里先 remove 再 set。
4后端服务能被直接访问← ④ 机制 3 第 3 步
现象
订单服务的 8080 端口在公网或办公网能直接连，带上 X-User-Id 就是任何人。
根源
信任边界靠的是网络隔离，不是代码。
做法
服务只绑内网，安全组 / NetworkPolicy 只放网关；重要服务内部再验一次签名（或网关签发内部短期令牌）。
5把业务逻辑写进网关← ④ 为什么是事件循环
现象
“订单详情页”的拼装（调订单、商品、物流再合并）写在网关过滤器里；改一次详情页要发网关，网关一发版全站抖一下。
根源
网关是所有流量的必经之路，放进去的逻辑越多，发布越频繁、出问题的影响面越大；聚合逻辑还容易写成阻塞的（坑 1）。
做法
网关只做横切的事（鉴权、限流、路由、灰度、协议转换）；聚合放到单独的 BFF 服务。
6升级到 4.3 后配置“失效”或一堆废弃警告← 版本差异
现象
依赖还是 spring-cloud-starter-gateway、配置还是 spring.cloud.gateway.routes：4.3 起这些名字被标为废弃；同时把 spring-boot-starter-web 也带进来时，网关启动直接报不兼容。
根源
历史原因：4.3 把 WebFlux 版和 Server MVC 版拆成对称的两个 starter 和两套属性前缀；WebFlux 网关不能跑在 Servlet 容器里。
做法
用 spring-cloud-starter-gateway-server-webflux 和 spring.cloud.gateway.server.webflux.*（本页实验就是这么配的）；网关工程里不要引 starter-web。

实验台：过滤器里多等一下，网关还剩多少吞吐

先猜：4 个事件循环线程，过滤器里阻塞地等 200 ms，并发 50，网关每秒最多处理多少个请求？

过滤器怎么等

每次等多久

同时在途的请求

模型：4 个事件循环线程；“不等”时这台机器的上限按 ⑤ 实测取 200 个/秒；阻塞时上限是 线程数 ÷ 等待时长；非阻塞时上限是 在途数 ÷ 等待时长；延迟按 Little 定律 = 在途数 ÷ 吞吐。用 ⑤ 的三组实测校过：模型 200 / 200 / 20，实测 201 / 151 / 19。

第二圈 · 使用规范

  • 网关前面留一层 Nginx 或云负载均衡做 TLS 和粗限流，网关至少两台。防：网关成为单点，或被大流量直接打满。
  • 全局过滤器的 order 写成常量并集中管理：删头 → 鉴权 → 限流 → 灰度 → 其他。防：限流先于鉴权执行，拿不到用户维度。
  • 路由配置放进配置中心，变更走审核；路由 id 有意义，日志和监控按 id 聚合。防：改错一条路由全站 404，还查不出是哪条。
  • 网关打访问日志时带上链路 ID 并向下透传。防：一次下单穿过五个服务，出事时串不起来（J13）。
  • CI 里跑 BlockHound 或压测，专门盯过滤器有没有阻塞调用。防：坑 1 在上线后才发现。

自测

1. 用一句话说出这一页的精华

网关是唯一入口：按断言找路由，全局和路由过滤器按 order 排成一条链做鉴权、改头、限流，lb:// 交给 LoadBalancer 挑实例，Reactor Netty 转发；几个事件循环线程扛所有连接，所以过滤器里绝不能阻塞，响应超时要自己配。

2. 每个服务各自对外、前面只放 Nginx，各疼在哪？

各自对外：鉴权等横切逻辑重复五遍、内部结构暴露、内部服务难挡。Nginx：不认服务名、按用户的逻辑要写 Lua，Java 团队维护不了；适合做最外层。

3. 坑 1 的根源是 ④ 的哪条？

机制 2：所有请求共用 max(核数, 4) 个事件循环线程，线程不能等；阻塞会让这个线程上排着的所有连接一起等，上限变成 线程数 ÷ 阻塞时长。

4. 预测：把网关机器从 2 核换成 16 核，坑 1 那个阻塞过滤器的吞吐会怎样？

事件循环线程数变成 16，上限变成 16 ÷ 0.2 = 80 个/秒，好了 4 倍，但还是远低于不阻塞时的水平；问题的根源没变，只是被核数稀释了。

5. 预测：鉴权过滤器的 order 从 -100 改成 10200（排在挑实例之后、转发之前），会出什么问题？

功能上仍然能挡住没 token 的请求，但每个非法请求都先走了一遍 LoadBalancer 挑实例；如果限流过滤器按用户限流、排在鉴权之前，它拿到的用户是空的（RequestRateLimiter 默认直接 403）。顺序决定了每个过滤器能看到什么。

6. 放回全景：第 2、3、4 站前后各发生了什么？网关的鉴权过滤器坏了（比如密钥配错，全部 401），整条链路会怎样？

之前：App 发出 POST /api/orders；之后：第 5 站订单服务读配置、第 6～8 站调三个下游。鉴权全部 401：所有请求在第 2 站就结束，后面的服务一个请求都收不到，监控上看是后端流量归零、网关 401 飙升；比后端挂掉更彻底，所以密钥轮换要两把钥匙并存一段时间。

档位：标准。本机跑过（2 核 ARM 虚拟机，JDK 17，Spring Boot 3.5.16 + Spring Cloud 2025.0.3，Gateway 4.3.5，Reactor Netty 1.2.18，Nacos 3.3.0 容器）：⑤ 的 run.sh demo 跑了 2 次，第二次加了预热，鉴权、改头、超时两次一致，阻塞压测两次 18～19 个/秒。实验台是按页面写明的模型推算的（node 里跑过），用实测校过。

按源码：spring-cloud-gateway-server 4.3.5 ReactiveLoadBalancerClientFilter.LOAD_BALANCER_CLIENT_FILTER_ORDER = 10150、NettyRoutingFilter 排在最后、RequestRateLimiterGatewayFilterFactory.denyEmptyKey = true（空 key 返回 403）、GatewayClassPathWarningAutoConfiguration。

按文档：Reactor Netty 事件循环线程数默认 max(CPU 核数, 4)（⑤ 在 2 核机器上看到 4 个）；Spring Cloud 2020.0 移除 Zuul；Gateway 4.3 的新 starter 名和属性前缀。
