inventory-2 慢了，下单怎么还能降级：限流、熔断、降级与 Sentinel

三件事，各管一头：限流管“进来的太多”，超出容量的直接挡在门口；熔断管“依赖坏了”，统计到对面慢或错得太多，就先别调它，直接失败；降级管“失败时给什么”，一句人话或一个兜底值。熔断的本质是一笔交换：用“这段时间全部很快地失败”，换“线程不被坏掉的依赖占住、整个服务不被拖死”。实测：熔断打开后每次 0 ms 降级，可连健康的那台库存也一起挡了。

①要解决的问题：一台库存变慢，订单服务被拖死

在全景第 9、10 站，这一步要解决：inventory-2 被慢 SQL 拖住，每次 3 秒；Nacos 还说它健康（上一页坑 1），轮询照样分一半流量给它（坑 3）。订单服务的线程一个个挂在 reserve() 上，连查订单这些不碰库存的接口也开始排队，网关那边成片超时：一台库存实例拖垮了整条链路，这叫雪崩。

②不用它会怎样：只有超时，实测吞吐掉到 6%

⑤ 的对照组 B：只配 800 ms 读超时，不配熔断规则，20 个调用线程不停地下单。第 5 秒 inventory-2 变慢：

结果两台各一半，全成功每秒 20 个成功（落到 inventory-1），20 个等满 800 ms 失败
  • 每个落到 inventory-2 的请求都要陪 800 ms，线程被占住，健康的那一半也排不上队
  • 加重试更糟：失败的再试一次，坏实例收到的请求不减反增
  • 把超时调得更短？太短会误伤正常的慢请求；而且再短，每次也要等一会儿
  • 超时仍然必须有：它是熔断器能“看到慢”的前提（坑 3）
不懂精华时的典型误用以为熔断是“提高成功率”的。⑤ 实测正好相反：熔断打开的那些秒，一单都没成，连本来会落到健康 inventory-1 的也被挡了。它保护的是调用方自己，不是成功率。

④核心取舍：拿“全部快速失败”换“不被拖死”

先知道这些 资源：Sentinel 统计和保护的单位，就是“调用方的一个调用点”。打开 feign.sentinel.enabled 后，每个 Feign 方法自动成为一个资源，名字是 POST:http://inventory-svc/stock/reserve。注意：它是服务名，不区分是哪台实例。 滑动窗口：把最近一段时间（statIntervalMs，默认 1 s）切成几个小格，各格计数，过期的格子丢掉；这样任何时刻都能算出“最近 1 秒的请求数、慢调用数”。

机制 1：熔断器状态机（Sentinel 1.8.9 源码）

机制 2：熔断按“资源”挡，不按实例

资源名里只有服务名。inventory-2 慢，统计的却是“调 inventory-svc 的所有请求”：轮询让一半是慢的，占比约 50% > 40%，熔断器打开后，落到 inventory-1 的那一半也被挡了（⑤：熔断那些秒成功数是 0）。半开时那一个探测按轮询落到哪台全看运气：落到 inventory-1 就关上，紧接着一半请求又慢，1～2 秒后再次打开。要只摘坏的那一台，得靠实例级的机制：负载均衡跳过它、注册中心下线它（全景第 11 站）、或者网格里的异常实例驱逐。

机制 3：限流和降级各自在算什么

限流（第 3 站）

Sentinel 用同一套滑动窗口数 QPS（或在途线程数），超过阈值时按 controlBehavior 处理：直接拒绝（默认）、预热（冷启动时阈值从低慢慢升到满）、排队匀速通过（漏桶）。阈值来自压测，不是拍出来的；它是每个实例的阈值，两台网关各 2000 就是放进 4000，要么除以实例数，要么用集群限流。

降级（第 10 站）

fallback 返回什么是业务决定：快速失败加一句人话（下单）；给个兜底值（推荐位给热门商品）；先跳过、事后补（送积分）。两条底线：降级逻辑要比原调用便宜得多（不再调别的远程服务），并且不能谎报成功（库存没冻结就不能返回“已下单”）。

为什么这样设计：Sentinel 和 Resilience4j 在哪几处做了不同的选择

半开只放 1 个（Sentinel）

试探成本最低，对面真恢复了能最快关上。代价：样本太小，像 ⑤ 这种“一半实例坏着”的情况，探测结果全凭运气，状态来回抖。

半开放 N 个（Resilience4j）

样本大，判断稳；一半实例坏着时，10 个里大约 5 个慢，占比超过阈值，就不会误关。代价：每次试探多放几个请求去碰运气，恢复时也要等它们都回来。

决定胜负的约束：熔断器只看得到它统计的东西。统计按资源、半开看几个样本、慢调用线设多少，决定了它在“部分实例坏掉”这种最常见的故障里是稳、是抖、还是根本不动。

最少的写法

DegradeRule r = new DegradeRule("POST:http://inventory-svc/stock/reserve")
    .setGrade(RuleConstant.DEGRADE_GRADE_RT)   // 慢调用比例
    .setCount(500)                             // RT > 500 ms 算慢
    .setSlowRatioThreshold(0.4)
    .setMinRequestAmount(10)
    .setStatIntervalMs(1000)
    .setTimeWindow(10);                        // 打开 10 s
DegradeRuleManager.loadRules(List.of(r));

⑥反例和误用：配上了规则，没满足它的前提

第一圈 · 注意事项

1一台坏了，熔断把健康的那台也挡了← ④ 机制 2 按资源挡
现象
⑤ A：第 6～14 秒每秒近 2000 次全部降级，inventory-1 一个请求都没收到。
根源
资源名是服务名，统计的是这个服务的全部调用；熔断器不知道慢的只是其中一台。
做法
熔断管“止血”，摘坏实例交给实例级机制：调用方的负载均衡跳过连续失败的实例、发版和故障时先 DOWN（全景第 11 站）、网格的异常实例驱逐。告警要能从熔断事件直接跳到“是哪台慢”。
2半开一次就关，关上又开，来回抖← ④ 机制 1 只看一个探测
现象
⑤ A：15.9 s 探测落到 inventory-1，关上；1.7 秒后又被慢调用拖回 OPEN；27.6 s 同样。每次关上的那一两秒里，一半请求又要陪 800 ms。
根源
Sentinel 1.8 的半开只放一个请求，样本只有 1；坏实例还在列表里，探测结果全凭轮询转到哪。
做法
尽快把坏实例摘掉（⑤：DOWN 后第一次半开就稳定了）；或者换成半开放多个请求的实现（Resilience4j 默认 10 个）；timeWindow 不要太短。
3只配了异常比例，没配读超时，熔断永远不开← ④ 机制 1 只统计看得到的
现象
（按机制推演，没单独跑）读超时是默认的 60 s，inventory-2 每次 3 秒后成功返回：异常比例是 0，熔断器纹丝不动，线程照样被占满。
根源
熔断器只能根据它统计到的东西判断；“慢但没错”只有慢调用比例看得到，而且前提是请求能结束。
做法
先配读超时，再配慢调用比例；慢调用线要比读超时短（500 ms < 800 ms），这样“还没超时、只是慢”也会被算进去。
4fallback 谎报成功，或者在里面调远程服务← ④ 机制 3 降级的两条底线
现象
库存降级返回“冻结成功”，订单照常创建，付完款发现没货；或者 fallback 里改调“备用库存服务”，它也慢，降级本身成了新的雪崩点。
根源
降级是在“对面不可用”时执行的，它必须比原调用便宜，而且不能假装事情做成了。
做法
写接口的降级 = 明确失败（订单不创建、给一句人话）；读接口的降级 = 本地缓存或兜底值，并在响应里标明“这是降级数据”。
5两台网关各配 2000，实际放进 4000← ④ 机制 3 单机阈值
现象
按下单容量 2000 QPS 配了限流，扩到 2 台网关后订单服务被打满。
根源
限流规则在每个实例的内存里各自计数。
做法
单机阈值 = 总容量 ÷ 实例数，扩缩容时跟着改；要精确就用 Sentinel 集群流控（有一个 token server）或网关的 Redis 令牌桶。
6所有异常都走了 fallback，真错误被吞掉← ⑤ B 组也有 FALLBACK
现象
⑤ B 没有任何熔断规则，超时的请求照样返回 FALLBACK；同理，库存服务返回 400“参数错”也会变成“稍后再试”，排查时看不到原因。
根源
feign.sentinel.enabled 让 Feign 调用的任何异常都进入 fallback。
做法
用 fallbackFactory 拿到异常，区分业务错误（直接抛出）和故障（降级）；fallback 里打日志、打指标。

第二圈 · 使用规范

  • 规则放 Nacos，用 Sentinel 的 Nacos 数据源加载；控制台改规则要回写 Nacos（默认的推送模式只在内存里）。防：重启后规则全丢；多实例规则不一致。
  • 每个下游依赖一组规则：读超时、慢调用线（比读超时短）、熔断阈值、timeWindow，一起写进依赖清单。防：坑 3。
  • 限流阈值来自压测，按实例数折算，扩缩容时一起改。防：坑 5。
  • fallback 用 fallbackFactory，按异常类型分流，并打日志和指标。防：坑 4、坑 6。
  • 熔断状态变化接告警，告警里带资源名和最近一分钟各实例的 RT。防：只看到“熔断了”，不知道是哪台（坑 1）。
  • 定期演练：在预发环境让一个依赖变慢，看规则是不是按预期开、关。防：规则配了但从没被验证过。

第三圈 · Sentinel 里面，和版本

责任链：每次进入资源，Sentinel 按顺序走一串 slot：建调用树节点、统计（StatisticSlot，写滑动窗口）、系统保护、授权、流控（FlowSlot）、熔断（DegradeSlot）。熔断器的状态判断在 DegradeSlot 里，完成时的计数在请求结束（exit）时做，所以一个请求“慢不慢”要等它结束才算数，这也是坑 3 的另一面。滑动窗口的实现叫 LeapArray：固定数量的桶循环复用，时间到了就把最老的桶清零重用，统计开销和 QPS 无关。

  • 重试预算：重试也要限流，避免故障时重试把下游打得更死。

↺回到⑤：改一改规则

  1. 异常比例：把规则换成 DEGRADE_GRADE_EXCEPTION_RATIO 0.4，再跑 A；然后把读超时删掉（默认 60 s）再跑。熔断器还开不开？（坑 3）
  2. 半开放 10 个：换成 Spring Cloud CircuitBreaker + Resilience4j（permittedNumberOfCallsInHalfOpenState=10），A 里那两次“关上又打开”还在不在？（坑 2）
  3. fallbackFactory：让库存替身对 qty > 10 返回 400，看 fallback 能不能区分它和超时。（坑 6）
  4. 流控：给 reserve 加 QPS 500 的流控规则，B 的前 5 秒会发生什么？被流控挡下的请求和被熔断挡下的，在 fallback 里怎么区分？（机制 3）

自测

1. 用一句话说出这一页的精华

限流挡住超出容量的流量，熔断在依赖坏掉时直接快速失败，降级决定失败时返回什么；熔断用“这段时间全部很快失败”换“调用方的线程不被拖死”，它按资源统计、只看得到它统计的东西。

2. 只靠超时疼在哪？

超时只限制一次等多久，对面持续坏着时每次都要等满；线程被占住，健康的请求也排不上队（⑤ B：吞吐 700 → 40，平均 400 ms）。

3. 坑 1（健康实例也被挡）的根源是 ④ 的哪条？

机制 2：熔断按资源统计，资源名是服务名，不区分实例；一半实例坏就让整个资源的慢调用占比超过阈值。

4. 预测：inventory-2 不是变慢，而是直接被 kill -9 了，A 组的时间线会怎样？

落到它的请求会立刻连接被拒（异常，不慢），慢调用比例为 0，这条慢调用规则不会打开；如果有异常比例规则，约 50% 的异常会让它打开。同时 Nacos 0.6 秒就推出下线，LoadBalancer 缓存（这里 2 s）过期后就不再挑它，所以几秒内自己就好了，熔断几乎派不上用场。

5. 预测：把 timeWindow 从 10 s 改成 2 s，⑤ A 的成功下单数和抖动次数会怎样？

抖动更频繁：每 2 秒就半开一次，一半概率关上、接着又被拖回去；每次关上的那一两秒，一半请求又要陪 800 ms。成功数可能略多（关上的时间段里 inventory-1 的那一半能成），但代价是更多请求在等超时、线程更忙。timeWindow 是“试探频率”和“试探代价”的取舍。

6. 放回全景：第 10 站前后各发生了什么？熔断器坏了（规则没加载上），整条链路会怎样？

之前：第 9 站 inventory-2 变慢、Nacos 仍说健康；之后：第 11 站运维摘流量、半开探测成功后恢复。规则没加载：就是 ⑤ 的 B 组，一半请求陪 800 ms，订单服务线程被占；如果读超时也没配，每台订单服务约 300 个线程才够陪，Tomcat 200 线程被占满，查订单也排队，网关 3 秒超时成片 504，这就是雪崩。

档位：标准。本机跑过（2 核 ARM 虚拟机，JDK 17，Spring Boot 3.5.16 + Spring Cloud 2025.0.3 + Spring Cloud Alibaba 2025.0.0.0，Sentinel 1.8.9，Nacos 3.3.0 容器）：⑤ 的 A、B 各跑了 1 次。调参台是模拟（node 里跑过），时间线和实测对过。坑 3 是按机制推演的，没有单独跑。

按源码：Sentinel 1.8.9 ResponseTimeCircuitBreaker（占比严格大于阈值才打开、半开按一个请求的 RT 决定）、AbstractCircuitBreaker（OPEN 到期后下一个请求转半开）、DegradeRule 默认 minRequestAmount = 5、statIntervalMs = 1000；Spring Cloud Alibaba SentinelInvocationHandler（资源名 = 方法 + URL + 路径）、feign.sentinel.enabled。

按文档：Resilience4j CircuitBreaker 默认值（失败率 50%、慢调用线 60 s、按次数窗口 100、最少 100 次、打开 60 s、半开放 10 个）。
