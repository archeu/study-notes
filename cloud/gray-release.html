1024 先用上新版：灰度发布与流量治理

灰度发布就是让新版本先只接一小部分流量。它要三步配合：在入口按规则给请求打标（1024 在名单里 → v2），每一跳挑实例时按标记选版本（实例注册时带上 hint=v2 元数据），标记还要一路往下传，否则后面几跳又回到随机。流量治理的另一半是“把流量从一台实例上拿走”：先下线、等调用方缓存过期、再停进程。实测：直接 kill 失败 295 次，按顺序来失败 0 次。

①为什么需要：新版下单逻辑先给 1% 的人用

在全景第 4 站，这一步要解决：订单服务 v2 改了算价逻辑，库存服务 v2 配合加了新接口。想先让灰度名单里的人（1024）用新版，其他人照旧；出问题时改一行名单就能撤回，不用回滚发版。第 11 站则是反过来：要把某一台实例的流量安全地拿走（坏了、或者要发版）。

②没有它会怎样：直接发、或者只发一台

全量发布（滚动替换所有实例）

  • 新版有 bug，所有用户一起遇到
  • 回滚要再发一遍旧版本，几分钟到几十分钟
  • 简单，K8s Deployment 的默认就是滚动

只把一台换成新版

  • 按轮询，谁落到它全凭运气：同一个用户这次新版、下次旧版
  • 后面几跳照样随机，新版订单可能调到旧版库存
  • 比例只能是 1/实例数，没法按用户、按地区挑

缺的那一块：按规则选人，并且同一个人在每一跳都落到同一个版本。这要入口打标、每一跳按标选实例、标记透传三件事一起做。不懂这一点的典型误用是“网关做了灰度就算灰度了”（⑤ 第 ③ 项：订单 v2 调库存时一半落到 v1）。

③相邻方案：滚动、蓝绿、金丝雀、功能开关

怎么做出问题时的影响面回滚额外资源
滚动发布一台台替换成新版替换过程中新老混跑，按实例比例再滚一遍旧版几乎没有
蓝绿发布整套新环境准备好，入口一次切过去切过去就是全部切回来，秒级两套环境
金丝雀 / 灰度新版几台，按规则（名单、比例、地区、头）分一部分流量只有被选中的人改规则，秒级新版那几台
功能开关（feature flag）新旧逻辑都在一个版本里，按开关走不同分支按开关规则关开关代码里两套逻辑要清理
全链路灰度 / 泳道标记一路透传，每一跳都按标选版本只有被选中的人改规则每个服务都要有灰度实例（或者没有时回退）

本页学基于标记的金丝雀发布 + 全链路透传：交易靶场已有网关、LoadBalancer、Nacos 三件套，正好拼起来；最后再加上“优雅上下线”，它是每种发布方式都要用的底座。

④原理：打标、按标挑实例、透传，再加上摘流量

先知道这些 实例元数据：注册到 Nacos 时可以带一组键值（hint=v2、zone=sh），调用方拿到的 ServiceInstance.getMetadata() 里就有。Spring Cloud Alibaba 用 spring.cloud.nacos.discovery.metadata.hint=v2 配。 LoadBalancer 的实例列表是一层层包出来的：最里层从注册中心拿列表，外面可以一层层套缓存、按区过滤、按 hint 过滤、健康检查（上一页 机制 2）。

机制 1：只在入口打一次标

  1. 网关的全局过滤器（排在挑实例之前）按规则决定版本：名单、userId % 100 < 5、地区、App 版本号，规则放 Nacos 配置，改了热更新（⑤：1.4 秒生效）。
  2. 先删再写：外面带进来的 X-Gray 一律删掉（⑤：2048 自己带 X-Gray: v2 照样落到 v1），和上一页删 X-User-Id 是同一个道理。
  3. 后面的服务不再重新判断，只认这个标。规则只在一处，同一个人在每一跳看到的才是同一个结论。

机制 2：按标挑实例，以及“找不到就退回全部”

HintBasedServiceInstanceListSupplier 还有一条规则：没有任何实例的 hint 匹配时，返回全部实例。好处是灰度实例全挂了，灰度用户自动退回旧版，不至于下不了单（⑤ 第 ④ 项实测）；坏处是这一切悄无声息，你以为 1024 在用新版，其实早退回了旧版。没有标记的请求也会拿到全部实例，包括 v2，所以 v1 请求要显式打上 v1（或者配 spring.cloud.loadbalancer.hint.default）。

机制 3：标记一路往下传

网关只管第一跳。订单服务调库存时，要把收到的 X-Gray 原样带上（Feign 用一个 RequestInterceptor），库存那一跳的 LoadBalancer 才能按它挑。跨线程（线程池、@Async）要把标记从 ThreadLocal 带过去；跨 MQ 要写进消息头，消费者再放回上下文。⑤ 第 ③ 项：order v2 不往下传时，1024 的 10 次里 5 次落到 inventory v1。

机制 4：摘流量，要等调用方都知道了再停

为什么这样设计：标记为什么只在入口算一次

每个服务自己判断“这个用户该不该灰度”

每个服务都要读名单、规则要同步到所有服务；名单改的那一刻，订单服务已经读到新名单、库存服务还是旧名单，同一个请求前后两跳结论不同。

入口算一次，后面只认标记

规则只在网关一处，改了只有一处生效时刻；一个请求从进门起结论就定了。代价：每一跳都要老老实实把标记传下去，传丢一处就混跑（机制 3）。

决定胜负的约束：同一个请求在所有跳上必须看到同一个版本结论。分散判断做不到“同一时刻”，所以把判断收拢到入口，把一致性问题变成“传不传得下去”的工程问题。

最少的写法

LoadBalancer 配置 + 元数据GrayGateway.HintLbConfig
@LoadBalancerClients(defaultConfiguration = HintLbConfig.class)
public static class HintLbConfig {
    @Bean ServiceInstanceListSupplier hintSupplier(ConfigurableApplicationContext ctx) {
        return ServiceInstanceListSupplier.builder()
            .withDiscoveryClient().withCaching().withHints()   // 顺序见机制 2
            .build(ctx);
    }
}
spring.cloud.loadbalancer.hint-header-name: X-Gray          # 默认 X-SC-LB-Hint
spring.cloud.nacos.discovery.metadata.hint: v2              # 实例这一侧（v2 实例上配）

// Feign 透传：订单服务里
@Bean RequestInterceptor grayRelay() {
    return t -> t.header("X-Gray", currentRequest().getHeader("X-Gray"));
}

⑥细节：灰度最常见的失败，是“以为在灰度”

第一圈 · 注意事项

1过滤层和缓存层写反，灰度悄悄失效← ④ 机制 2 一层套一层
现象
⑤ 第一次跑：withHints().withCaching()，1024 落到三台 order 上，日志里没有任何报错。
根源
缓存层只实现了不带请求的 get()，请求头传不到里面的 hint 层。
做法
按文档：发现 → 缓存 → 各种过滤；上线前用两个用户各打 10 次，确认版本分布。
2标记没往下传，新老混跑← ④ 机制 3 透传
现象
⑤ 第 ③ 项：order v2 调库存时一半落到 v1，新算价逻辑配上了旧库存接口。
根源
只有入口打了标；每一跳的调用、每一个线程池、每一条 MQ 消息都要自己带上它。
做法
Feign 拦截器、RestClient 拦截器统一透传；线程池用能传递上下文的包装（如 TransmittableThreadLocal）；MQ 写消息头。用链路追踪的 baggage 带标记，一处配置全链路生效（J13）。
3灰度实例全挂了，用户悄悄回到旧版← ④ 机制 2 找不到就退回全部
现象
⑤ 第 ④ 项：inventory v2 下线后，1024 的请求全部落到 inventory v1，没有任何提示；你以为新版在被验证，其实没人在用。
根源
HintBasedServiceInstanceListSupplier 没有匹配时返回全部实例。
做法
监控按版本拆分的流量和错误率，v2 流量掉到 0 要告警；需要严格隔离的场景（比如 v2 改了数据格式）自己写过滤层：没有匹配就失败，不回退。
4按比例灰度，同一个人一会儿新一会儿旧← ④ 机制 1 规则只在入口
现象
用 random() < 0.05 选 5% 的请求：1024 刷新一次页面，前后两次看到的价格不一样。
根源
灰度单位应该是“人”（或设备、店铺），不是“请求”。
做法
按 hash(userId) % 100 选；扩大比例时只增不换（5% 的人始终在 10% 里）。
5发版直接 kill，失败持续半分钟← ④ 机制 4 等调用方都知道
现象
⑤ 第 ⑤ 项：kill -9 一台 order，之后约 30 秒里发给它的请求全失败，共 295 次；先下线、等 40 秒再停是 0 次。
根源
调用方的 LoadBalancer 缓存默认 35 秒，不听 Nacos 推送。
做法
发版脚本固定成：下线 → 等缓存过期 → 停进程；K8s 里用 preStop 钩子做前两步，terminationGracePeriodSeconds 要比等待时间长。
6代码灰度了，数据没法灰度← ④ 为什么只在入口算一次
现象
v2 往订单表写了一个新状态值，v1 读到不认识的状态直接报错；灰度用户的订单被普通用户的后台任务处理，又走回 v1 逻辑。
根源
新老版本共用同一个库和同一个 MQ，数据是全局的，标记管不到。
做法
数据结构变更要向前兼容：先发能读新格式的版本，再发写新格式的版本（两步走）；后台任务和消费者也要按标记或按数据上的版本字段分流。

模型：Nacos 推送 0.6 s（Nacos 页实测）；每个调用方的缓存在 0～ttl 秒之间随机到期，“最坏”取刚刷新完，“平均”按均匀分布积分；只算进程停掉以后还发给它的请求。用 ⑤ 校过：kill -9、缓存 35 s、每秒 10 个，模型最坏 356、平均 181，实测 295。

第二圈 · 使用规范

  • 灰度规则只放网关一处，放 Nacos 配置，改动有审核和记录。防：多处判断不一致。
  • 灰度单位是人（userId 哈希），比例只增不换，从 1% → 5% → 20% → 全量。防：坑 4。
  • 每个阶段有观察指标和时长：错误率、RT、关键业务量按版本拆开看，达标才放大。防：灰度变成“发了就不管”。
  • 回滚 = 把名单清空（秒级），而不是回滚发版。防：出事时手忙脚乱重新打包。
  • 发版脚本：下线 → 等 ≥ 缓存 ttl → 停 → 起新版 → 自检 → 注册 → 预热（Nacos 权重或 Sentinel 预热流控）。防：坑 5，以及冷启动的新实例被一下子打满。
  • 数据结构变更两步走：先兼容读，再改写。防：坑 6。

第三圈 · 更深的几处

泳道：把“全链路灰度”推到极致，每个服务都部署一套灰度实例，组成一条和主干并行的“泳道”，按标记进泳道；没有灰度实例的服务回退到主干。代价是实例数翻倍，常用于测试环境的多分支并行联调。MQ 灰度：消息带上标记，灰度消费者只消费带灰度标记的消息（不同消费组或按标签过滤），否则灰度订单会被旧版消费者处理（J08）。服务网格：Istio 的 VirtualService 按头、按权重分流，DestinationRule 按 subset（版本标签）选实例，打标和按标挑实例都挪到 Sidecar 里，业务代码只负责透传头（J14）。

下一圈

  • MQ 和定时任务的灰度：灰度订单的后续处理也要走 v2。
  • 预热：新实例刚注册时按权重从小到大放流量（Nacos 权重、Sentinel warm-up）。
  • K8s 上的无损发布：preStop、readiness、terminationGracePeriodSeconds 和注册中心怎么配合（J14）。
  • A/B 测试：和灰度共用打标机制，但目标是比较业务指标，要做统计显著性。

自测

1. 用一句话说出这一页的精华

灰度 = 入口按规则打一次标、每一跳按标从实例元数据里挑版本、标记一路透传；摘流量 = 先下线、等所有调用方缓存过期、再停进程。两件事都栽在“看不见”上：顺序写错、标记传丢、找不到就回退，都不报错。

2. 只把一台换成新版，疼在哪？

轮询决定谁落到新版，同一个人前后不一致；后面几跳照样随机，新版调到旧版下游；比例只能是 1/实例数，也选不了人。

3. 坑 5（kill 后失败半分钟）的根源是 ④ 的哪条？

机制 4：调用方的 LoadBalancer 缓存只按时间过期（默认 35 s），进程停了以后，缓存里还有它的调用方会继续发过来。

4. 预测：网关和订单服务的 LoadBalancer 缓存都是 35 s，发版先下线 inventory 的一台，要等多久才能安全停进程？

还是约 35 s 加余量：库存只被订单服务调，看的是订单服务那一层缓存；网关的缓存管的是 order-svc 的列表，和库存无关。要等的是“所有调用这台实例的调用方”里最长的那一层。

5. 预测：灰度名单里删掉 1024 的那一刻，1024 正在处理中的下单请求会怎样？

不受影响：标记在进门时就定了（v2），这个请求后面每一跳都按 v2 走完；名单只影响之后进门的请求。这正是“只在入口算一次”的好处，也说明撤灰度有一个“在途请求走完”的尾巴。

6. 放回全景：第 4 站和第 11 站分别做了什么？如果打标的过滤器坏了（所有请求都没有 X-Gray），整条链路会怎样？

第 4 站：网关按名单把 1024 标成 v2，LoadBalancer 只在 v2 实例里挑。第 11 站：把 inventory-2 权重调 0 或下线，等调用方缓存过期。打标坏了：没有标记的请求在 hint 过滤里拿到全部实例，v1、v2 混着接所有用户的流量，灰度变成了按实例比例的随机发布；如果 v2 有 bug，影响面从 1% 变成 1/3。

档位：标准。本机跑过（2 核 ARM 虚拟机，JDK 17，Spring Boot 3.5.16 + Spring Cloud 2025.0.3，Gateway 4.3.5，Nacos 3.3.0 容器）：⑤ 的 run.sh demo 跑了 2 次，第一次 LoadBalancer 顺序写反、灰度没生效（坑 1 的实测），第二次是页面上的输出。计算器按页面写明的模型推算（node 里跑过），用实测校过。

按源码：Spring Cloud LoadBalancer HintBasedServiceInstanceListSupplier（读 hint-header-name 指定的头，匹配 metadata 里的 hint，没有匹配就返回全部）、CachingServiceInstanceListSupplier 与 DelegatingServiceInstanceListSupplier 只实现 get()、ServiceInstanceListSupplier.get(Request) 默认调 get()；LoadBalancerProperties.hintHeaderName 默认 X-SC-LB-Hint。

按文档：Spring Cloud Commons LoadBalancer 参考文档（Hint-Based Load-Balancing 一节的示例顺序 withDiscoveryClient().withCaching().withHints()；缓存要紧跟取实例那一层、在任何过滤层之前）。
