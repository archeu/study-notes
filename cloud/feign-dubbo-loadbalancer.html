inventoryClient.reserve() 背后：OpenFeign、Dubbo 与负载均衡

业务代码里写的是一个接口方法，OpenFeign 在启动时给它生成一个 JDK 动态代理；调用时代理把方法和参数拼成一个 HTTP 请求，URL 里的主机名是服务名 inventory-svc，交给 Spring Cloud LoadBalancer 从本地缓存的实例列表里按轮询挑一台，换成真实 IP 再发。挑实例发生在调用方，所以不多一跳；代价是每个调用方看到的列表可能是旧的（实测：下线后又被调了 32 秒），而且轮询不看对方快慢。

这一页的位置J10 下钻第 3 步。远程调用的底层（序列化、协议、连接、负载均衡算法）在 RPC 原理和 J04 全景讲过第一圈；这一圈看 Spring Cloud 这一层：一个接口方法怎么变成一次挑实例的 HTTP 调用，挑实例用的列表从哪来、多旧。上一页 Nacos 的坑 3 在这里实测。

①为什么需要：业务代码只想写一行方法调用

在全景第 6、7、8 站，这一步要解决：订单服务连着调商品、券、库存三个服务。业务代码只想写 inventoryClient.reserve(9527, 88, 2)，可实际要发生的是：拼 URL 和参数，从 inventory-svc 的两台里挑一台，发 HTTP，等不超过 800 ms，把响应转成 Java 对象，出错了转成异常。这些事三个服务、几十个接口都要做一遍。

②没有它会怎样：手写 RestClient

老办法：每个调用点自己来Spring 6.1+ 的 RestClient

疼在哪

  • 挑实例的代码散在几十个地方，各写各的
  • URL、参数拼接写错只能运行时发现
  • 想加统一的超时、鉴权头、熔断，要一个个改
  • 中间方案：给 RestClient.Builder 加 @LoadBalanced，直接写 http://inventory-svc/…，挑实例交给 LoadBalancer；但拼 URL 和解码还在业务代码里

缺的那一块：把“怎么调”声明在接口上，调用点只剩一行方法调用；挑实例、超时、编解码在一个地方统一配。这就是 OpenFeign 的精华。它的代价也来自这里：远程调用长得和本地方法一模一样，很容易忘了它会慢、会失败（坑 1）。

④原理：代理 → 方法处理器 → 挑实例 → 发 HTTP

先知道这些 JDK 动态代理：给一个接口在运行时造一个实现类（$Proxy89），所有方法调用都转到一个 InvocationHandler.invoke()。Spring AOP 的接口代理也是它，见 Spring AOP 代理。 客户端负载均衡：挑实例这件事在调用方进程里做，拿着实例列表直接连目标实例；对比 Nginx 那种“中间放一台转发”的服务端负载均衡。

机制 1：启动时，接口变成代理

  1. @EnableFeignClients 扫描到 @FeignClient(name = "inventory-svc") 的接口，为它注册一个工厂 Bean。
  2. 每个 Feign 客户端有一个按名字隔离的子容器：这个客户端的编码器、解码器、拦截器、超时都放在里面，spring.cloud.openfeign.client.config.inventory-svc.* 就是配给它的。
  3. SpringMvcContract 把接口上的 @PostMapping、@RequestParam 解析成每个方法的元数据：HTTP 方法、路径、参数放哪。
  4. ReflectiveFeign 为每个方法建一个 SynchronousMethodHandler，再用 JDK 代理把接口包起来，注入到 OrderApp 里的就是这个代理（⑤ 实测类名 jdk.proxy2.$Proxy89）。

机制 2：调用时，一路往下走到真实 IP

机制 3：挑哪台——轮询只数次数

RoundRobinLoadBalancer 维护一个计数器，每次 +1 再对实例数取模，起点随机。它不知道对面忙不忙、快不快、刚刚失败过没有。⑤ 里 18082 每次慢 300 ms，200 次照样一边 100 次。还可以换成 RandomLoadBalancer；打开 spring.cloud.loadbalancer.nacos.enabled 后用 Nacos 的权重；也可以叠加“优先同区”“健康检查”这些过滤层。要“谁快给谁”，得用 Dubbo 的最少活跃那一类，或者交给熔断把慢的那台摘出去。

为什么这样设计：调用方自己挑，而不是中间放一台转发

服务端负载均衡（中间一台 Nginx）

列表只有一份，改了立刻对所有人生效；但每次调用多一跳网络，这一层自己要做高可用，所有流量都压在它身上。

客户端负载均衡（LoadBalancer 在调用方里）

直接连目标实例，不多一跳，没有中间单点；代价是每个调用方各有一份列表，更新有延迟、彼此不一致，挑实例的策略也只看得到自己发出去的那部分请求。

决定胜负的约束：服务之间的调用量是入口流量的好几倍（一单就是三次），每次多一跳、所有调用压在一层代理上，代价太大。所以内部调用选客户端负载均衡，列表旧一点由超时、熔断兜住。把这一层再挪出进程、放到每个 Pod 旁边，就是服务网格（J14）。

⑥细节：一行方法调用里藏着的五个默认值

第一圈 · 注意事项

1不配超时，等于 60 秒← ④ 机制 2 最底层的 HTTP 客户端
现象
对面卡住时，订单服务的线程一个个挂在 reserve() 上，Tomcat 200 个线程被占满（全景第 9 站算过：每台约 300 个线程才够陪）。
根源
最底层 feign.Request.Options 的默认是连接 10 s、读 60 s；接口长得像本地方法，很容易忘了它会等。
做法
每个 @FeignClient 按名字配 connect-timeout、read-timeout，再配一个 default 兜底；值比上游的超时短（全景“每一跳的超时”表）。
2实例下线了，还被调 35 秒← ④ 机制 2 两层缓存
现象
⑤ 实测：Nacos 0.6 s 就推出了新列表，订单服务又往 18082 发了 32 秒，每秒 22 次。
根源
LoadBalancer 外面包了一层按时间过期的缓存（spring.cloud.loadbalancer.cache.ttl，默认 35 s），不听 Nacos 的推送。
做法
发版先 DOWN、等 40 秒再停进程；或者把 ttl 调到几秒（⑤：2 s 时 1 秒内就绕开），并按 WARN 的建议换成 Caffeine 缓存。
3慢的那台照样分一半← ④ 机制 3 轮询只数次数
现象
⑤：18082 每次 300 ms，200 次里还是 100 次给它；在线程数固定时，整体吞吐被拖到原来的几分之一（下面的实验台）。
根源
轮询、随机只看次数，不看响应时间和在途请求数。
做法
靠熔断把慢的那台快速失败掉（下钻第 5 步）；或者换成看在途请求数的策略（Dubbo 最少活跃，自定义 ReactorServiceInstanceLoadBalancer）。
4写接口被自动重试，库存冻了两次← ④ 对照 Dubbo failover
现象
Dubbo 默认 failover，或者给 Feign 打开了重试：第一次其实成功了，只是超时，重试又冻结一次。
根源
超时只说明“不知道”（时钟、超时与重试）；框架分不清读接口和写接口。
做法
写接口要么不重试（Dubbo 设 cluster=failfast 或 retries=0），要么带幂等键（9527）让对面去重（幂等设计）。
5参数名丢了，启动不报错、调用才报← ④ 机制 1 解析注解
现象
本机实测（上一页）：编译没开 -parameters，@RequestParam long ms 不写名字，调用时 500。Feign 接口上同样的写法会在解析时出错。
根源
注解没写名字时，要靠字节码里的参数名；Spring Boot 的父 pom 默认帮你开了 -parameters，自己管 pom 时就没有。
做法
Feign 接口和 Controller 的 @RequestParam、@PathVariable 一律写上名字。

实验台：一台变慢时，四种挑法差多少

先猜：两台库存，18082 每次慢到 300 ms，订单服务 20 个线程一直在调。用最少活跃（谁手上在途请求少给谁），18082 大约分到多少？

挑法

18082 每次多慢

模拟：18081 每次 5 ms，18082 按选的值；20 个调用线程各自一个接一个地发，一共 4000 次；没有超时和熔断。数字来自页面里的模拟，不是实测；轮询那一行和 ⑤ 第 ③ 项的实测一致（一边一半）。

第二圈 · 使用规范

  • 每个 Feign 客户端单独配超时；default 配一个保守值兜底。防：坑 1。
  • 底层换成 Apache HttpClient 5（加 feign-hc5 依赖即生效），配连接池大小和空闲回收。防：默认的 HttpURLConnection 难以控制连接复用（HTTP 客户端连接池与超时）。
  • LoadBalancer 换 Caffeine 缓存，ttl 和发版流程一起定。防：坑 2。
  • 写接口不开自动重试，读接口重试要有次数上限和退避。防：坑 4 和重试风暴。
  • Feign 接口由调用方维护，别把提供方的 Controller 接口打成 jar 给大家依赖。防：共享 jar 的变更耦合。
  • 用 RequestInterceptor 统一传链路 ID、灰度标记、用户 ID。防：全景第 4 站说的“灰度标记传丢了”（下钻第 6 步）。

自测

1. 用一句话说出这一页的精华

OpenFeign 把接口变成 JDK 代理，调用时拼出以服务名为主机的 HTTP 请求；Spring Cloud LoadBalancer 在调用方进程里从本地缓存的列表按轮询挑一台换成真实地址；不多一跳，但列表会旧（默认最多 35 秒）、轮询不看快慢、默认读超时 60 秒。

2. 手写 RestClient 调用疼在哪？@LoadBalanced 解决了哪一半？

挑实例、拼 URL、解码、超时、错误处理散在每个调用点。@LoadBalanced 让 URL 能直接写服务名，挑实例统一了；拼 URL 和解码还在业务代码里，这一半由 Feign 或 HTTP Service Clients 的声明式接口解决。

3. 坑 2（下线后还被调 35 秒）的根源是 ④ 的哪条？

机制 2 的两层缓存：Nacos 客户端那层会被推送更新，LoadBalancer 自己那层只按 ttl 过期，挑实例只读后者。

4. 预测：把 ttl 设成 0（不缓存），会有什么代价？

每次挑实例都要去 DiscoveryClient 取列表。Nacos 客户端那层本身是内存缓存，代价不大，但每次都要走一遍过滤和拷贝；换成每次都要远程查询的注册中心客户端，就会把注册中心打爆。所以 ttl 是在“新鲜”和“开销”之间取舍，常见做法是几秒。

5. 预测：同样一台变慢 300 ms，订单服务用 Dubbo 默认配置调它，会和 OpenFeign 有什么不同？

Dubbo 默认加权随机，分布和轮询差不多（一半）；默认超时 1000 ms，300 ms 不会超时，所以不会触发 failover 重试，表现和 Feign 一样慢一半。如果它慢到 3 秒：Dubbo 1 秒超时后换一台重试（最多再 2 次），写接口就有重复执行的风险；Feign 默认要等满 60 秒。

6. 放回全景：第 6、7、8 站前后各发生了什么？如果 LoadBalancer 挑实例这一步坏了（比如列表为空），整条链路会怎样？

之前：第 5 站读到 800 ms 的超时配置；之后：第 9、10 站一台变慢、熔断降级。列表为空时 LoadBalancer 返回“没有可用实例”，Feign 直接抛异常（503 类），三次调用都失败，下单直接报错，快速失败而不是等超时；这时要查的是 Nacos 订阅和命名空间（上一页坑 5、坑 6），不是库存服务本身。

档位：标准。本机跑过（2 核 ARM 虚拟机，JDK 17，Nacos 3.3.0 容器，Spring Boot 3.5.16 + Spring Cloud 2025.0.3 + Spring Cloud Alibaba 2025.0.0.0）：⑤ 的 run.sh demo 跑了 2 次，调用栈、轮询分布两次一致；缓存掐表第一次窗口太短（30 s），第二次拉长到 50 s。实验台的数字来自模拟（node 里跑过），不是实测。

按源码：Spring Cloud LoadBalancer 5.0.4 / 4.3 LoadBalancerCacheProperties.ttl = 35s、RoundRobinLoadBalancer（起点随机，position.incrementAndGet() % 实例数）；feign-core 13.6 Request.Options() 默认连接 10 s、读 60 s。
