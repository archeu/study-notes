@Bean
SqlSessionFactory sqlSessionFactory(DataSource ds) throws Exception {
    SqlSessionFactoryBean f = new SqlSessionFactoryBean();
    f.setDataSource(ds);                  // 和事务经理用同一个
    // 不设 transactionFactory，默认就是 SpringManagedTransactionFactory
    return f.getObject();
}

@Bean
PlatformTransactionManager txManager(DataSource ds) {
    return new DataSourceTransactionManager(ds);   // 同一个 DataSource
}

@Bean
SqlSessionTemplate sqlSessionTemplate(SqlSessionFactory f) {
    return new SqlSessionTemplate(f);         // 你的 Mapper 都通过它干活
}
  • 用 Spring Boot 时，这三个 Bean 都由自动配置给你造好（Spring 第 03 篇）：MyBatis 的 starter 造前一个和最后一个，Spring 的 JDBC 自动配置造事务经理。
  • @MapperScan 登记的每个 Mapper，底下用的都是这个 SqlSessionTemplate。
  • JdbcTemplate 取连接也走 DataSourceUtils，所以和 MyBatis 混用时，同一个事务里拿到的是同一个连接。

    ① SqlSessionTemplate每次 Mapper 调用都会走进这个拦截器
    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
    SqlSession session = getSqlSession(factory, executorType, translator);  // 拿会话，见 ②
    try {
        Object result = method.invoke(session, args);                       // 真正执行 SQL
        if (!isSqlSessionTransactional(session, factory)) {
            session.commit(true);                                          // 不在事务里：自己提交
        }
        return result;
    } catch (Throwable t) {
        throw translate(t);   // MyBatis 异常 → Spring 的 DataAccessException
    } finally {
        closeSqlSession(session, factory);   // 在事务里：只是还回柜子；不在：真的关掉
    }
}

    ③ SpringManagedTransactionMyBatis 眼里的“事务”，其实处处让着 Spring
    public Connection getConnection() throws SQLException {
    if (connection == null) {
        connection = DataSourceUtils.getConnection(dataSource);    // 柜子里有 Spring 的连接，就拿它
        autoCommit = connection.getAutoCommit();
        isConnectionTransactional = DataSourceUtils.isConnectionTransactional(connection, dataSource);
    }
    return connection;
}

public void commit() throws SQLException {
    if (connection != null && !isConnectionTransactional && !autoCommit) {
        connection.commit();     // 只有连接不归 Spring 管时，才自己提交
    }
}

    JDK 8 和 JDK 17：机制一样，包名和版本不同

    柜子、会话复用、谁来提交，这一套在两个版本里完全相同。

    Spring 5 · Boot 2

    JDK 8+
    • mybatis-spring 2.x（starter 2.3.x）
    • 除了 Spring 自己的 @Transactional，也认 javax.transaction.Transactional
    • CGLIB 代理下，@Transactional 只对 public 方法生效

    Spring 6 · Boot 3

    JDK 17+
    • mybatis-spring 3.x（starter 3.0.x），要求 Spring 6
    • JTA 注解换成 jakarta.transaction.Transactional；还写 javax 版的，不报错，也不开事务
    • 6.0 起，CGLIB 代理下 protected 和包可见的方法上的 @Transactional 也生效
    没变的：同一个 DataSource 是纽带线程储物柜SqlSessionTemplate 复用会话Spring 提交连接，MyBatis 只清缓存

    常踩的坑

    先看日志里那几句，再对照柜子想：这次调用时，柜子里有没有东西。

    加了 @Transactional，出错了还是没回滚

    事务压根没开：同一个类里自己调自己、方法不是 public、异常被 catch 吞了、抛的是受检异常。原因都在 Spring 第 02 篇。

    线程池、@Async、parallelStream 里的 SQL 不归这个事务

    那个线程的柜子是空的，用的是另一个自动提交的连接。要么放回当前线程做，要么让它自己开事务，并接受两边不一致的可能。

    多数据源：一个库回滚了，另一个库没回滚

    事务经理按它自己那个 DataSource 存连接，另一个库的 Mapper 拿到的是别的连接。用 @Transactional("reportTxManager") 指定事务经理；真要跨库一起成败，得上分布式事务。

    Connection is not available, request timed out after 30000ms

    连接从开事务一直占到提交。事务里调远程接口、发消息、做大计算，连接池很快被占满。把慢操作挪到事务外面。

    BATCH 执行器下，insert 返回 -2147482646

    批量模式先攒着，到提交前（收尾清单通知会话时）才真正发出去，所以拿不到影响行数。要结果就在事务里手动调用 flushStatements()。

    Cannot change the ExecutorType when there is an existing transaction

    同一个事务里，先用普通的 SqlSessionTemplate，又用了 BATCH 的。柜子里那个会话类型已经定了，不能换。把批量操作放进单独的事务。

    同一个事务里，读不到别人刚提交的数据

    两个原因叠在一起：会话复用，一级缓存命中了；MySQL 默认的可重复读隔离级别，本来就看不到。

    升级 Boot 3 后，javax.transaction.Transactional 不生效

    Spring 6 只认 jakarta 版。换成 jakarta.transaction.Transactional，或者直接用 Spring 自己的 @Transactional。
