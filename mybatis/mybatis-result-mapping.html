①为什么需要：数据库给的是表，业务要的是对象

在全景第 9 站，这一步要解决的是：JDBC 的 ResultSet 只会“往下一行、按列取值”，业务代码要的却是对象树。交易靶场里有两种最常见的查询：订单列表要“订单连明细”，一对多；日终对账要导出 20 万条流水，行特别多。前一种难在“几行拼成一个对象”，后一种难在“这么多对象放不放得下”。

②没有它会怎样：自己写 while (rs.next())

不用 MyBatis 的结果映射，一对多只能手写：边读边按订单 id 去重，再把明细挂上去。这段循环每个查询都要写一遍。

JDBC手写一对多
Map<Long, Order> byId = new LinkedHashMap<>();
try (ResultSet rs = ps.executeQuery()) {
  while (rs.next()) {
    long id = rs.getLong("id");
    Order o = byId.get(id);              // 这一行的订单见过没有？
    if (o == null) {
      o = new Order(id, rs.getString("status"), rs.getLong("amount"));
      byId.put(id, o);
    }
    if (rs.getObject("i_id") != null)   // LEFT JOIN：没有明细的订单
      o.items().add(new Item(rs.getLong("i_id"), rs.getInt("i_qty")));
  }
}
return new ArrayList<>(byId.values());

疼在哪

  • 每个查询一段循环，列名写成字符串，改了列编译器不报错
  • “这行属于哪个订单”要自己用 Map 认，三层嵌套（订单 → 明细 → 商品）就三层 Map
  • 流水导出想省内存，就得自己控制“读一条处理一条”，还要自己管连接什么时候关
  • 好处是什么都看得见：发了几条 SQL、Map 里存了什么、对象活多久，一清二楚

MyBatis 把这段循环做成了配置：<resultMap> 里的 <id> 就是左边的 byId 的 key，<collection> 就是“挂上去”那一步。不懂这一点时的典型误用：以为 resultMap 只是“列名对属性名”，一对多图省事写成 <collection select="..."/>，于是列表页每笔订单多发一条 SQL。

③相邻方案：一对多有四种装法，大结果有三种读法

同一个需求“100 笔订单连明细”，MyBatis 里能写成四种。表里的条数和借连接次数是 ⑤ 里实测的。

选择规则：列表页用两步法，或者先分页再 JOIN；单条详情用 JOIN；嵌套查询只在“明细很少被用到”时配懒加载。大结果用 Cursor 或 ResultHandler，并且确认驱动真的在流式读。本页重点学 JOIN 是怎么折叠的、懒加载代理怎么工作、Cursor 为什么离不开事务，四种装法的利弊都是从这三件事推出来的。

④原理：一张 Map 认身份，一个代理管懒加载，一个会话管寿命

上一圈把“把行变成对象”画成了一格。这一圈打开它：DefaultResultSetHandler 一行一行读，用一张 Map 认出“这一行属于哪个对象”；懒加载靠给对象套一层代理；对象和游标能活多久，由 SqlSession 也就是事务说了算。

先知道这些
  • ResultSet 是个游标：next() 往下挪一行，getLong("id") 取这一行的列。行是不是已经全在 JVM 里了，由驱动决定，MyBatis 管不着（④-3）。
  • MapperMethod 看返回类型选路：返回 List 走 selectList，返回 Cursor 走 selectCursor，参数里有 ResultHandler 走 select(…, handler)（执行流程）。
  • CacheKey：MyBatis 拿来当 Map key 的类，往里 update() 几个值，值都相等的两个 key 就相等。一级缓存的 key 也是它（缓存）。
  • 不在事务里，每次 Mapper 调用一个新 SqlSession：SqlSessionTemplate 调完就关，连接还给 HikariCP；在事务里，SqlSession 绑在线程上活到提交（MyBatis 接 Spring 事务）。

JavaCursor 必须在事务里读完
@Transactional(readOnly = true)
public void export(Writer out) {
  try (Cursor<PayFlow> c = mapper.cursorFlows()) {   // 会话活到方法结束
    for (PayFlow f : c) write(out, f);                // 读一条写一条，写完就扔
  }
}

参数默认值、resultOrdered、safeResultHandlerEnabled 这些细节，放到第 ⑥ 步。

为什么这样设计：MyBatis 不认识实体，只认识行

选中的：按行流式映射，身份由你用 <id> 告诉它

  • SQL 是你写的，MyBatis 不解析它，也不知道哪一列是主键，所以“哪几行是同一个对象”只能由 <id> 告诉它
  • 认身份的 Map 只在这一个结果集里活着，读完就清空，下一条 SQL 从零开始，没有全局状态
  • 一行一行处理，所以能自然地接上 Cursor 和 ResultHandler，不必先攒齐
  • 代价：一对多装成什么样、发几条 SQL，全看你怎么写 resultMap；写错了不报错，只是慢或者少数据

放弃的：JPA 那样的持久化上下文

  • 实体有 @Id，会话里有一张身份表（identity map），同一行在一个会话里永远是同一个对象，自动去重
  • 要一直开着会话，还要做脏检查、管实体状态；出了会话再碰懒加载属性，直接 LazyInitializationException
  • SQL 由框架生成，“到底发了几条”反而更难看清，N+1 一样会发生

决定胜负的约束是：MyBatis 的定位是“SQL 你写，映射你说”。它不拥有实体模型，就只能把身份、加载时机、流式这些决定都做成可配置的，交回给写 resultMap 的人。⑥ 里所有的坑，都是这些配置没写对。

1SqlCounter：插件数 SQL、数借连接
@Intercepts(@Signature(type = StatementHandler.class, method = "prepare",
        args = {Connection.class, Integer.class}))
public class SqlCounter implements Interceptor {
  static int sql;
  static final Set<Integer> conns = new HashSet<>();
  public Object intercept(Invocation inv) throws Throwable {
    sql++;
    // HikariCP 每借一次连接都给一个新的代理对象：
    // 不同的代理有几个，就是借了几次
    conns.add(System.identityHashCode(inv.getArgs()[0]));
    return inv.proceed();
  }
}

第一圈

注意事项

坑 1列表页 100 笔订单，发了 101 条 SQL← ④-2 嵌套查询实测
现象
⑤：嵌套查询 101 条、8.9～10.9 ms，JOIN 1 条、1.7～2.1 ms。这还是内存库；真 MySQL 每条至少一个网络往返，同机房按 0.2～0.5 ms 算，多出来 100 条就是 20～50 ms（估算）。
根源
<collection select> 的意思就是“每建好一个父对象，拿它的 column 去执行一次子查询”。父对象有几个，子查询就有几次。
做法
列表页用两步法（IN）或 JOIN；嵌套查询只留给单条详情。上线前开 SQL 日志，或者用 ⑤ 的计数插件跑一遍接口。
坑 2懒加载在事务外：每碰一次，借一次连接← ④-2 newExecutor实测
现象
⑤：事务外碰 100 笔订单的 items，借连接 101 次；放进 @Transactional 只借 1 次。并发高时，每个请求在循环里反复借还，池子周转变慢。
根源
Mapper 方法返回时 SqlSession 已经关了，ResultLoader 发现原 Executor 关了，就 newExecutor() 走 SpringManagedTransaction 再借一条，查完就关。
做法
要用懒加载，就在 Service 的 @Transactional(readOnly = true) 里把需要的属性碰完；更好的是一开始就按需要的形状查（JOIN 或两步法）。
坑 3打一行日志、返回给前端，懒加载就被触发了← ④-2 触发方法实测
现象
⑤：toString() 根本不碰 items，照样多发 1 条 SQL。把代理对象直接交给 Jackson：InvalidDefinitionException: No serializer found for class …EnhancedResultObjectProxyImpl，引用链停在 ["handler"]。
根源
lazyLoadTriggerMethods 默认是 equals,clone,hashCode,toString，调到它们就加载全部懒属性；代理类多了一个 handler 字段，Jackson 不知道怎么序列化它。
做法
Controller 返回 DTO，不返回带懒加载的实体；日志里打 id，不打整个对象。实在要改，把 lazyLoadTriggerMethods 设成空，或给 Jackson 配 @JsonIgnoreProperties("handler")。
坑 4JOIN 回来了，明细字段全是 null← ④-1 嵌套 resultMap实测
现象
⑤：明细的 resultMap 只写了 <id>，指望 i_sku_id 自动映射成 skuId，结果 Item#95271(sku=null, qty=null, price=null)。不报错。
根源
autoMappingBehavior 默认 PARTIAL：只给“没有嵌套映射”的 resultMap 做自动映射。源码 shouldApplyAutomaticMappings：嵌套的那层只有 FULL 才自动映射。打开 mapUnderscoreToCamelCase 也救不了，它只管列名怎么转，不管做不做。
做法
嵌套那层的列全写出来，或者只在这个 <collection> 上加 autoMapping="true"。不建议全局 FULL：父子表都有 id、status 时容易映射串。
坑 5JOIN 之后分页：要 10 笔，拿到 6 笔，最后一笔还缺明细← ④-1 LIMIT 管的是行实测
现象
⑤：LIMIT 10 拿到 9501～9506 共 6 笔，9506 只有 1 件（实际 3 件）。PageHelper 一类插件给外层 SQL 拼 LIMIT，结果一样；RowBounds 默认也不报错（safeRowBoundsEnabled 默认 false）。
根源
数据库按行截断，不知道哪几行属于同一个订单；MyBatis 只能折叠它收到的行（上面实验台的“JOIN 后 LIMIT 4”）。总数也会算成行数。
做法
先在子查询里对订单分页再 JOIN（⑤ 的 listOrdersPageThenJoin，10 笔都对），或者两步法：先分页查订单，再 IN 查明细。
坑 6Cursor 一迭代就报 A Cursor is already closed← ④-3 会话寿命实测
现象
⑤：没加 @Transactional 的方法里，for (PayFlow f : m.cursorFlows()) 抛 IllegalStateException: A Cursor is already closed.
根源
不在事务里，SqlSessionTemplate 在 Mapper 方法返回前就关了 SqlSession，DefaultSqlSession.close() 会把它打开过的所有 Cursor 一起关掉（closeCursors）。
做法
用 Cursor 的方法加 @Transactional(readOnly = true)，或者用 TransactionTemplate 把读的循环包起来；读完用 try-with-resources 关。
坑 7换成 MySQL，Cursor 照样 OOM← ④-3 驱动那一层按文档
现象
代码和 H2 上一模一样，导出几百万行时堆还是涨满，因为执行查询那一刻，驱动已经把所有行读进了内存。
根源
Connector/J 文档：“By default, ResultSets are completely retrieved and stored in memory.” MyBatis 的 Cursor 只保证自己不攒，管不到驱动。
做法
语句上加 fetchSize="-2147483648"（Integer.MIN_VALUE，配合默认的只进只读结果集，一行一行读），或者 URL 加 useCursorFetch=true 再设 fetchSize="1000"。流式读完之前，这条连接上不能再发别的 SQL。PostgreSQL 要在事务里且 fetchSize>0。
坑 8嵌套 resultMap 配 ResultHandler，直接报错← ④-1 resultOrdered实测
现象
⑤：ExecutorException: Mapped Statements with nested result mappings cannot be safely used with a custom ResultHandler…
根源
嵌套结果要等同一个订单的所有行都读到才算完整。不保证有序时，MyBatis 不知道什么时候能把一个订单交给你，所以 safeResultHandlerEnabled（默认 true）直接拦下。
做法
SQL 按 <id> 列 ORDER BY，语句上加 resultOrdered="true"（实验台第三种模式）。Cursor 配嵌套 collection 也要这样，Cursor 接口的 Javadoc 里写明了。
第二圈

使用规范

  • 每个 resultMap 都写 <id>，嵌套那层也写。防的是：用所有列拼 key，又慢；两行全同时被并成一个。
  • 列表接口不用嵌套查询，默认两步法；单条详情可以 JOIN。防的是：N+1。
  • 全局 lazyLoadingEnabled 保持默认 false，需要时用 fetchType="lazy" 单点打开。防的是：全局打开后，所有关联都变成代理，日志和序列化到处触发。
  • Controller 返回 DTO，不返回 Mapper 查出来的实体。防的是：坑 3。
  • 大结果导出：@Transactional(readOnly = true) + Cursor（或 ResultHandler）+ 驱动流式参数，循环里不做远程调用。防的是：坑 6、坑 7；流式期间连接和数据库里的语句一直占着。
  • 导出不要在一个大事务里循环 selectList 分页。防的是：每页都留在一级缓存里（第三圈）。
第三圈

优化和深处

分页导出包在事务里，每一页都没被回收 实测

⑤ 的 pages：分 10 页、每页 2 万条，每页用完就扔。不在事务里，循环结束时堆只多 0～0.9 MB；包进一个 @Transactional，多了 34.3 MB，事务一结束又回到 0。原因在 BaseExecutor.queryFromDatabase：每次查完都 localCache.putObject(key, list)，而 SqlSession 跟着事务活，10 页的 List 都被一级缓存拽着。Cursor 走 queryCursor，不进一级缓存，所以没有这个问题。实在要分页：设 localCacheScope=STATEMENT（每条语句结束就清，代价是同一事务里重复查询不再命中），或者换成 Cursor。

源码：一次 JOIN 查询在 DefaultResultSetHandler 里走过的方法

handleResultSets(stmt)                      // 可能有多个结果集，逐个处理
└ handleResultSet(rsw, resultMap, …)
  └ handleRowValues(…)                       // resultMap.hasNestedResultMaps() ? 嵌套 : 简单
    └ handleRowValuesForNestedResultMap(…)
      ├ createRowKey(resultMap, rsw, null)   // resultMap id + <id> 列值；没有 <id> 就用全部普通列
      ├ nestedResultObjects.get(rowKey)      // 已有 → partialObject
      ├ getRowValue(…, partialObject)        // 没有就 createResultObject + 自动映射 + 显式映射
      │ └ applyNestedResultMappings(…)       // 明细：combineKeys(子 key, 父 key) 去重后 linkObjects
      └ storeObject(resultHandler, …)        // 新父对象才调；List 用 DefaultResultHandler 收
  └ cleanUpAfterHandlingResultSet()          // nestedResultObjects.clear()

两点值得记住：一，明细也有自己的 key（子 key 合并父 key），所以同一件明细在 JOIN 结果里重复出现，也只挂一次；二，没开 resultOrdered 时，这张 Map 要到整个结果集读完才清，所以“Cursor + 嵌套 collection + 不排序”时，内存还是会随订单数涨。

JOIN 和两步法，传输量差多少

JOIN 让订单列在每一行重复：订单行宽 1 KB、平均 5 件明细，JOIN 回来约 5 KB 的订单列，两步法只有 1 KB 再加一次往返（估算）。明细多、订单宽时两步法省带宽；明细少、往返贵时 JOIN 更快。MyBatis-Plus 没有一对多 JOIN 映射，项目里通常就是两步法。

↺回到 ⑤：在订单列表和导出上改三处

都在 mybatis-result-mapping 上改，改完跑对应的场景。

练习 1 · 用两步法消掉 N+1

把 listOrdersNested 改成：先查订单，收集 id，再 WHERE order_id IN (…) 查明细（<foreach>），在 Java 里 groupingBy 装回去。跑 nplus1，预期 SQL 2 条，9527 还是 3 件。

练习 2 · 让嵌套结果也能流式交出去

给 scanOrdersJoin 加上 resultOrdered="true"（SQL 已经 ORDER BY o.id），handler 里每收到一个订单打印 id 和件数。跑 handler，预期不再报错，100 笔都完整。再去掉 ORDER BY 看看会怎样（坑 8）。

练习 3 · 让分页导出在事务里也不攒

在 application.properties 加 mybatis.configuration.local-cache-scope=statement，跑 pages，预期事务里也降到 1 MB 以下。改回来，只在 listFlowsPage 上加 flushCache="true"：查之前清，查完还会放进去，预期剩一页的量，约 3.4 MB。

自测

1. 用一句话说出这一页的精华。

MyBatis 一行一行读结果集，用 <id> 算出的 rowKey 在一张 Map 里认出“这一行属于哪个对象”；发几条 SQL 由 resultMap 怎么写决定，对象和游标活多久由 SqlSession（也就是事务）和驱动决定。

2. 手写 JDBC 装一对多，最疼的是哪两点？

每个查询都要自己写“按 id 去重再挂明细”的循环，列名是字符串、改了不报错；想省内存还得自己控制读一条处理一条、自己管连接什么时候关。

3. 明细字段全是 null，根源是哪条原理？

autoMappingBehavior 默认 PARTIAL，嵌套的那层 resultMap 不做自动映射（④-1 里“新建对象 + 自动映射 + 显式映射”，嵌套层只剩显式映射）。只写了 <id>，就只有 id 有值。

4. 预测：订单的 resultMap 去掉 <id>，只留几个 <result>，JOIN 查询还能折叠成 100 笔吗？什么时候会出错？

能。没有 <id> 时 rowKey 用全部普通 <result> 列（④-1 图下的说明），同一订单的几行这些列都相同，照样折叠。出错的情况是两笔不同的订单在这些列上完全相同，比如只映射了 status 和 amount，两笔都是 CREATED、239400，就会被并成一个，明细也挂到一起。

5. 预测：把懒加载那个场景改成在 @Transactional 里查订单，但在事务提交以后（方法返回给 Controller 之后）再碰 items，借连接几次？

每笔一次。事务一提交，SqlSession 就关了，原来的 Executor 也关了，ResultLoader 只能 newExecutor() 再借（④-2 右下）。决定借几次的不是“查的时候在不在事务里”，是“碰的时候原 Executor 还开没开”。

6. 预测：MySQL 上，导出用 Cursor，语句加了 fetchSize="-2147483648"，循环里每读一条流水又调一次 orderMapper.selectById 查订单。会怎样？

报错。Connector/J 流式读时，这条连接在结果集读完或关闭之前不能再发别的查询；在同一个事务里，selectById 用的正是这条连接（④-3、坑 7）。要么先把需要的订单查好放进 Map，要么把查订单挪到流式循环之外。

7. 放回全景：第 9 站前后各发生了什么？这一页讲的东西坏了，整条链路会怎样？

第 9 站之前是第 8 站：Mapper 代理按方法名找到 MappedStatement，看返回类型决定走 selectList 还是 selectCursor，SqlSessionTemplate 从第 7 站绑在线程上的事务里拿到 SqlSession 和连接。第 9 站 Executor 发出 SQL，结果回来交给 DefaultResultSetHandler；之后第 10 站提交事务、关会话，第 11 站把返回值写成 JSON。结果映射写坏了：N+1 让第 9 站发 101 条 SQL，请求变慢、连接占得更久，第 7 站后面排队的请求借不到连接；懒加载对象漏到第 11 站，Jackson 序列化时要么再借连接查库，要么直接 500；Cursor 用在事务外，在第 9 站之后一迭代就抛异常。

档位：标准。本机实测：2 核 ARM Linux，OpenJDK 17.0.21，Spring Boot 3.5.16（Spring Framework 6.2.19），mybatis-spring-boot-starter 3.0.5（MyBatis 3.5.19），HikariCP，H2 内存库（MySQL 模式）。⑤ 的 8 组场景完整跑了 1 次、nplus1 和 stream 又跑了 2 次、pages 跑了 1 次（每次 2 轮），条数和次数每次一样；耗时和堆是 GC 后的 MemoryMXBean 读数，只看相对大小。真 MySQL 上的网络往返（坑 1）是估算，Connector/J 和 PostgreSQL 驱动的流式行为（坑 7）按官方文档，没有在本机跑。
