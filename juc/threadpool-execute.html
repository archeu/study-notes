JDK 21 · THREADPOOLEXECUTOR · CTL · ADDWORKER · RUNWORKER · GETTASK · WORKER · MAINLOCK

三个 if、一个 int、一把不可重入的锁

execute 只有三个分支：核心名额没满，就开线程，把任务直接交给它；否则放进队列，放完再看一眼池子还开着没有、还有没有线程；放不进就开临时线程，开不了就拒绝。池子的运行状态和线程数挤在一个 int（ctl）里，所以“看状态、占名额”一次 CAS 就能做完。线程要退出时，也会回头看一眼队列。两边各查一次，任务就不会卡在没人取的队列里。

①为什么需要→ ②没有它会怎样→ ③相邻方案→ ④原理→ ⑤亲眼看到→ ⑥细节→ ↺回到⑤

这是下一圈线程池“先补核心、再排队、再加临时线程、最后拒绝”的四步规则，在 Spring @Async 与线程池 讲过，还有模拟器。这一页接着往下：execute 的源码为什么是这三个 if，线程怎么被造出来、怎么取任务、怎么退出。所以 ①～⑤ 都很短，篇幅给 ⑥ 的源码和实验台。假设场景是面试被追问“讲讲 execute 的源码”，以及线上遇到几件只有看源码才说得清的怪事。源码以 JDK 21u 为准，标“实测”的在本机跑过：JDK 11.0.32 和 21.0.12。

①为什么需要：四步规则背不出来的几件事

只记四步规则，下面这几件事都解释不了。它们都是本页 ⑥ 实测过的：

?核心数设成 0、最大数 10、无界队列

10 个任务进来，自始至终只有 1 个线程在干活。第 1 步跳过、第 3 步走不到，那这 1 个线程是谁建的？

?任务里抛了个异常

线程名从 pool-1-thread-1 变成了 pool-1-thread-2。换成 submit 提交，异常却连日志都没有。

?配了 CallerRunsPolicy，说好“满了让调用方自己跑”

关池以后提交的 100 个任务，一个都没跑，也没有异常。

?“核心线程”不会被回收

可实测里先建的那个线程被回收了，留下来的是后建的“临时线程”。

②没有它会怎样：每个任务一个新线程

不用线程池，每来一个任务就 new Thread(task).start()：建线程、销毁线程都要进内核，突发流量时线程数没有上限。线程池的四步规则就是在“复用线程”和“限住总数”之间找平衡，旧页有完整的图和模拟器，这里不重讲。

③相邻方案：JDK 里还有哪些执行器

执行器线程从哪来任务放哪适合
ThreadPoolExecutor按核心数、最大数造，闲久了回收你给的 BlockingQueue一般的业务异步、IO 任务
ForkJoinPool固定并行度，每个线程一个双端队列，空闲的去偷别人的各线程自己的队列能拆分的计算任务；parallelStream、CompletableFuture 默认用它
Executors.newVirtualThreadPerTaskExecutor()每个任务一个虚拟线程，不复用不排队JDK 21 起，大量阻塞 IO 的任务
Spring ThreadPoolTaskExecutor里面就是一个 ThreadPoolExecutor同左Spring 里配置更方便，规则完全一样

本页学 ThreadPoolExecutor：Spring 的线程池、Executors.newFixedThreadPool、newCachedThreadPool 背后都是它，execute 是所有任务的入口。

④原理：四步规则落到源码里是什么样

四步规则在 旧页讲过：先补满核心线程，再排队，队列满了加临时线程，再不行就拒绝。这一圈先认识源码里撑起这四步的几样东西，再看三个 if 怎么排。

这一圈要用到的四样东西

ctl

一个 AtomicInteger，高 3 位是池子的运行状态，低 29 位是线程数。看状态、改线程数都是对它做 CAS。

Worker

一个工作线程的“外壳”：里面有真正的 Thread、一个 firstTask（建它时顺手带来的第一个任务），自己还是一把锁。

workers + mainLock

所有 Worker 放在一个普通的 HashSet 里，进出都要先拿 mainLock（一把 ReentrantLock）。

workQueue

你给的阻塞队列。工作线程空闲时停在它的 take() 或 poll(keepAlive) 上等任务。

为什么这样设计：状态和线程数必须一起 CAS

被放弃的：两个变量runState 一个、workerCount 一个

  • addWorker 要做的是“还在 RUNNING、名额没满，才 +1”；tryTerminate 要做的是“已经关了、线程数是 0，才进 TIDYING”。两件事都是“看两个值，再改其中一个”
  • 两个变量各自 CAS，挡不住这样的交错：一边刚判定可以终止，另一边同时把线程数 +1，后面只能靠别处再补救
  • 想不交错，就得每次都拿一把锁，提交任务、线程退出都要排队

JDK：一个 ctl，一次 CAScompareAndIncrementWorkerCount(c)

  • CAS 的期望值 c 里同时带着状态和线程数：状态一变，+1 就失败；线程数一变，进 TIDYING 的 CAS 也失败。两件事最多成功一件
  • 失败了就重读 ctl 再判断，不用拿锁
  • 代价：线程数上限从 2^31 − 1 降到 2^29 − 1。源码注释说真不够用时改成 AtomicLong 就行，现在用 int 更快更简单

决定胜负的约束：“加线程”和“关池子”必须互斥，又不想让每次提交、每次线程退出都去抢锁。把两样东西塞进一个 int，一次 CAS 就同时检查了两样。这个 CAS 只管名额；真正建线程、放进 workers，是之后在 mainLock 里做的，锁里还会再查一次状态，算第二道保险。

⑤亲眼看到：三个 if、插队、ctl 的位

核心 2、最大 4、队列容量 2，连续提交 8 个各跑 300 ms 的任务。每次提交后打印线程数和队列长度，再用反射读出 ctl 的 32 位。最后顺带验证 ① 里“核心数 0 只有 1 个线程”。

1TpePeek.java单文件，JDK 11+；读私有字段 ctl 要加 --add-opens
import java.lang.reflect.Field;
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

// 看 execute 的三步判断、任务的实际执行顺序、ctl 的位
// 运行：java --add-opens java.base/java.util.concurrent=ALL-UNNAMED TpePeek.java
public class TpePeek {
  static Field CTL;
  static String ctl(ThreadPoolExecutor p) throws Exception {
    int c = ((AtomicInteger) CTL.get(p)).get();
    String[] names = {"RUNNING", "SHUTDOWN", "STOP", "TIDYING", "TERMINATED"};
    int rs = c >> 29;                                   // 高 3 位
    String bits = String.format("%32s", Integer.toBinaryString(c)).replace(' ', '0');
    return bits.substring(0, 3) + " " + bits.substring(3) + "  →  " + names[rs + 1] + "，线程数 " + (c & ((1 << 29) - 1));
  }
  public static void main(String[] a) throws Exception {
    CTL = ThreadPoolExecutor.class.getDeclaredField("ctl"); CTL.setAccessible(true);
    var started = Collections.synchronizedList(new ArrayList<String>());
    var pool = new ThreadPoolExecutor(2, 4, 60, TimeUnit.SECONDS, new ArrayBlockingQueue<>(2));
    System.out.println("新建：        " + ctl(pool));
    for (int i = 1; i <= 8; i++) {
      final int id = i;
      String how;
      try {
        pool.execute(() -> { started.add("#" + id); sleep(300); });
        how = "线程 " + pool.getPoolSize() + "，队列 " + pool.getQueue().size();
      } catch (RejectedExecutionException e) { how = "被拒绝"; }
      System.out.printf("execute(#%d) → %s%n", i, how);
    }
    System.out.println("此刻：        " + ctl(pool));
    sleep(1000);
    System.out.println("开跑顺序：" + started);
    pool.shutdown();
    System.out.println("shutdown 后： " + ctl(pool));
    pool.awaitTermination(5, TimeUnit.SECONDS);
    System.out.println("全部结束：    " + ctl(pool));

    // core = 0 + 无界队列：只会有 1 个线程
    var zero = new ThreadPoolExecutor(0, 10, 60, TimeUnit.SECONDS, new LinkedBlockingQueue<>());
    long t0 = System.nanoTime();
    for (int i = 0; i < 10; i++) zero.execute(() -> sleep(100));
    zero.shutdown(); zero.awaitTermination(10, TimeUnit.SECONDS);
    System.out.printf("core=0、max=10、无界队列：最多同时 %d 个线程，10 个 100 ms 的任务用了 %d ms%n", zero.getLargestPoolSize(), (System.nanoTime() - t0) / 1_000_000);
  }
  static void sleep(long ms) { try { Thread.sleep(ms); } catch (InterruptedException e) { } }
}

第一圈

注意事项

坑 1核心数 0 + 无界队列：永远只有 1 个线程← ④ 第 ② 个 if 的复查
现象
核心 0、最大 10、LinkedBlockingQueue：10 个 100 ms 的任务排着队一个个跑，用了 1003 ms，最多同时 1 个线程。实测
根源
第 ① 个 if 永远不成立（线程数不会 < 0），第 ② 个 if 永远能放进去，第 ③ 个 if 永远走不到。唯一建线程的地方是放进队列后的复查：“线程数是 0 就补一个”。补了 1 个之后，复查看到的就是 1，再也不补。
做法
想“空闲时缩到 0、忙时开到 10”，写成核心 10 + allowCoreThreadTimeOut(true)：实测 10 个任务 117 ms 跑完，闲 1.5 秒后线程数回到 0。
坑 2execute 的任务抛异常：线程被换掉；submit 的：异常悄悄没了← ④ 工作线程的一生
现象
单线程池里一个任务抛异常，控制台打一行 Exception in thread "pool-1-thread-1"，下一个任务跑在 pool-1-thread-2 上。换成 submit：线程名不变，什么也不打印，只有调 get() 才抛 ExecutionException。实测
根源
runWorker 不吞异常：调完 afterExecute 就原样抛出，线程走到 processWorkerExit，因为是异常退出，一定会补一个新线程。submit 先把任务包成 FutureTask，它自己 catch 住异常存起来，所以对线程池来说任务“正常结束”。
做法
任务里自己 try / catch；用 submit 就一定要处理返回的 Future；统一记日志可以覆写 afterExecute（submit 的任务在这里拿到的 Throwable 是 null，要从 Future 里取）。
坑 3CallerRunsPolicy 在池子关了以后，直接丢任务源码细节
现象
关池后提交 100 个任务：一个没跑，没有异常，没有日志。实测
根源
它的源码只有一句：if (!e.isShutdown()) r.run();。关了就什么也不做。默认的 AbortPolicy 关池后仍会抛 RejectedExecutionException。
做法
停机流程里先停止提交、再关池；或者自己写一个拒绝策略，关池时至少打日志。
坑 4shutdown 不停正在跑的，shutdownNow 也只是“打招呼”← ④ 工作线程的一生
现象
1 个线程、队列里 5 个任务：shutdown 后 6 个全跑完；shutdownNow 后正在 sleep 的那个被打断，退回 5 个没跑的。一个不看中断标志的忙循环，shutdownNow 之后 1 秒也没结束。实测
根源
shutdown 只中断“空闲”的线程（能 tryLock 到 Worker 的，就是没在跑任务的）；shutdownNow 中断所有已启动的线程，可中断只是设一个标志，任务自己不检查就停不下来。
做法
任务里响应中断；关闭按 shutdown → awaitTermination → 超时再 shutdownNow 的顺序来。
坑 5忘了 shutdown：JVM 退不出，池子也不会被回收← ④ 核心线程停在 take 上
现象
main 里用 newFixedThreadPool(2) 跑一个任务就返回：进程不退出，6 秒后被 timeout 强行杀掉。实测
根源
核心线程空闲时停在 take() 上一直等，它们是非守护线程，JVM 不会退出；Worker 是内部类，持有池子的引用，活着的线程又是 GC Root，所以池子也回收不了。JDK 8 的 finalize() 会调 shutdown，但根本轮不到它执行；JDK 11 起它是空方法，JDK 27 删掉了。
做法
在 finally 里关；Spring 管理的池子交给容器关；JDK 19 起 ExecutorService 是 AutoCloseable，可以写 try-with-resources。
坑 6“核心线程”不是固定的那几个← ④ timed 是现算的
现象
核心 1、最大 2：先建的 T1 的任务先跑完时，10 次里留下的都是后建的 T2，T1 被回收了。实测
根源
getTask 每次都现算 timed = wc > corePoolSize：两个线程时谁进 getTask 都是“要限时”，谁先闲满 keepAlive 谁走。没有哪个 Worker 被标成核心。
做法
别在 ThreadLocal 里缓存“只给核心线程用”的东西，也别按线程名判断它是不是核心线程。
坑 7监控接口都要拿 mainLock← ④ workers + mainLock
现象
在请求路径上调 getActiveCount() 打日志，或者每 100 ms 采一次各种计数，高峰期提交变慢。
根源
getPoolSize、getActiveCount、getLargestPoolSize、getTaskCount、getCompletedTaskCount 都先拿 mainLock 再遍历 workers，和建线程、线程退出抢同一把锁。
做法
低频采样（比如 10 秒一次），别放在热路径上；队列长度 getQueue().size() 走的是队列自己的实现，不碰 mainLock。
第二圈

使用规范

自己 new ThreadPoolExecutor：有界队列 + 明确的拒绝策略

不用 Executors.newFixedThreadPool（无界队列）和 newCachedThreadPool（线程无上限）。

只剩 1 个线程干活（坑 1）

异常在任务里处理，或者 submit 后一定看 Future

统一兜底可以覆写 afterExecute。

线程被反复换掉、异常悄悄消失（坑 2）

给线程起名字

自定义 ThreadFactory，名字带上业务，如 order-notify-3。

jstack 里一堆 pool-7-thread-12，分不清是谁的

关闭三连，任务响应中断

停机丢任务、进程退不出（坑 4、坑 5）

监控低频采样，别放热路径

线程数、活跃数、队列长度、拒绝次数，10 秒一次足够。

和建线程、线程退出抢 mainLock（坑 7）

再往深一点

Worker 为什么自己写一把不可重入的锁

  • 源码注释：锁住正在跑任务的线程，是为了让“叫醒空闲线程”的中断不会打到正在跑的任务上。shutdown、调小核心数都会 tryLock 每个 Worker，锁得上的才中断。
  • 不用 ReentrantLock：任务里如果调了 setCorePoolSize，它会去中断空闲线程，可重入的锁会让当前线程 tryLock 到自己，把自己中断掉。
  • 初始 state 是 −1：线程还没真正开始跑任务前，谁也 tryLock 不到它，也就不会被中断。

workers 为什么用 HashSet + 锁，不用并发集合

  • 源码注释给的头号理由：锁让 interruptIdleWorkers 串行执行，避免关池时一大批正在退出的线程同时去中断别人，形成“中断风暴”。
  • largestPoolSize、completedTaskCount 这类统计也顺便有了锁保护。
  • 代价就是坑 7：监控接口也要拿这把锁。

终止是“一个传一个”完成的

  • tryTerminate 发现还有线程，只中断一个空闲线程（ONLY_ONE）。那个线程醒来、退出，又调 tryTerminate，再中断下一个。
  • 最后一个线程退出时线程数是 0，它用 CAS 把状态从 SHUTDOWN 推到 TIDYING，调 terminated() 钩子，再设成 TERMINATED，唤醒 awaitTermination。
  • 这个 CAS 和 addWorker 的 +1 互斥：要么终止成功，要么加线程成功。

先占名额，后建线程

  • addWorker 先 CAS 线程数 +1，再 new Worker、建线程、启动。顺序反过来的话，几个提交者可能同时建出线程，再发现名额不够，白建一场。
  • 建线程可能失败（ThreadFactory 返回 null，或者 unable to create native thread），所以要有 addWorkerFailed 回滚这个名额。
  • 名额的检查和占用一次 CAS 完成，不拿锁；只有改 workers 才拿 mainLock。

面试官会怎么问

讲讲 execute 的源码。

读一次 ctl：线程数小于核心数就 addWorker(command, true)，任务作为新线程的第一个任务直接跑。否则如果池子在跑，就 offer 进队列；放进去后复查：池子关了就撤回并拒绝，线程数为 0 就补一个不带任务的线程。放不进队列就 addWorker(command, false) 开临时线程，再失败就拒绝。

ctl 是什么？为什么把两个值放一起？

一个 AtomicInteger，高 3 位是运行状态，低 29 位是线程数。放在一起，“状态还允许、名额也够才 +1”和“已经关闭、线程数为 0 才进入 TIDYING”都能用一次 CAS 完成，两者天然互斥，不用拿锁。

放进队列后为什么还要再检查一次？

两种情况：一是放进去前后池子被关了，要撤回任务；二是这期间最后一个线程退出了，或者核心数本来就是 0，队列里的任务没人取，所以线程数为 0 时补一个。线程退出时也会检查“队列不空却没线程”，两边各查一次，保证任务不会卡在队列里。

线程池里的线程怎么复用、怎么回收？

每个 Worker 的线程跑 runWorker 循环：先跑 firstTask，然后不断 getTask。线程数不超过核心数时用 take() 一直等，超过时用 poll(keepAliveTime) 限时等；限时等没等到、线程数仍超过核心数（或允许核心超时），就 CAS 减线程数并退出。所以“核心线程”不是固定的哪几个。

任务抛异常会怎样？execute 和 submit 有什么区别？

execute：异常从 runWorker 抛出，线程退出，processWorkerExit 补一个新线程，默认的未捕获异常处理器会打印堆栈。submit：任务被包成 FutureTask，异常存在 Future 里，线程不退出，不调 get() 就永远看不到。
