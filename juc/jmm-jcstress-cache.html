JMM 下一圈：在 ARM 上把重排序真跑出来，再往下看一层 CPU 缓存

上一圈的 Java 内存模型 讲了规则：没有 happens-before，就不保证看得到、不保证顺序。这一圈往下走一层，看规则管的是什么：每个核先把写放进自己的存储缓冲，同一个地址靠缓存一致性协议对齐，不同地址之间的先后谁也不保证。用 OpenJDK 的 jcstress 跑了几亿次：库存超卖、两边都读到 0、看到标志却没看到数据，全在本机（ARM）出现了；加对 volatile 或 CAS 以后，一次也没有。最后看缓存行带来的另一个坑：两个线程改的是不同变量，也会互相拖慢。

需求地图上这一项的深度是“懂设计”：不光会用 volatile 和锁，还要说得清 JMM 为什么要这样规定，它和 CPU 的缓存、存储缓冲是什么关系，以及为什么同一段代码在 x86 笔记本上测不出问题、上了 ARM 服务器才出事。

②朴素做法：写个 main 跑几千次，没出错就当它对

  • 上一圈的 JmmDemo 就是这么写的：两个线程跑 100 万次，数一数出现几次奇怪结果。它能“碰”出问题，但说不清没碰到是因为不可能，还是因为没碰巧。
  • 线程启动有先后：一个线程起来时，另一个可能已经跑完了，两边根本没“同时”。自己写的循环还容易被 JIT 优化掉，或者被循环里的打印、加锁顺手修好（上一圈坑 6）。
  • 结果只有“出错 / 没出错”两种，没有“这个结果按规范允不允许”的判断。
  • 缺的那一块：一个专门的测试框架，让多个线程在同一时刻对同一个干净的对象动手，跑几亿次，把每种结果出现了几次列成直方图，再按你事先声明的“允许 / 禁止 / 值得注意”自动判对错。这就是 jcstress。

不懂这一点时的典型误用：在 x86 笔记本上跑了 1000 万次“先写数据再写标志”，从没看到过错，就认定不加 volatile 也行。x86 的硬件恰好不会把两次写的顺序对调；代码上了 ARM 服务器（云上越来越多），本机实测 5 亿次里出现了 36.9 万次（⑤）。

④关键洞察：同一个地址有人管，不同地址之间的先后没人管

先知道这些
  • happens-before、数据竞争：见上一圈洞察 2、3。
  • 缓存行：CPU 和内存之间按 64 字节一块搬数据，这一块叫缓存行。读一个 long，它旁边的 56 个字节也一起进了缓存。
  • 线程和核：一个线程某一刻在某个核上跑（见线程、线程状态与上下文切换）。

④-1每个核写东西，先写进自己的存储缓冲

  • 1为什么要存储缓冲：写一个不在自己缓存里的地址，要先通过一致性协议向别的核“要”这一行的独占权，可能要几十到上百个时钟周期。让核停下来干等太亏，于是先记进存储缓冲，接着执行后面的指令。失效队列同理：别人的“作废”通知先排着，晚一点再处理。
  • 2一致性协议只管同一个地址。MESI（修改、独占、共享、无效四种状态）保证一个缓存行同一时刻只有一个核能写，写完以后别的核读到的一定是新值。但 x 和 y 是两个地址，“x 的写先于 y 的写被别人看到”这件事，协议不管。JMM 里的“有序性”，管的就是不同地址之间的先后。

④-2不同 CPU 放宽的程度不一样：x86 只放宽一种，ARM 放宽很多种

两条访存指令（不同地址）x86（TSO）ARM v8Java 普通字段（JMM）本页哪个测试
写 → 读：先写后读，读能跑到前面允许允许允许SbPlain
写 → 写：两次写，后一次先被看到不允许允许允许MpPlain（写的那一边）
读 → 读：两次读，后一次读到更早的值不允许允许允许MpPlain（读的那一边）
读 → 写不允许允许允许（没测）
  • 1JMM 对普通字段放得比 ARM 还宽：除了 CPU，JIT 编译器也会重排、合并、提到循环外。所以“我在 x86 上测过没问题”不能证明代码对，只能证明 x86 加上这一版 JIT 恰好没暴露。
  • 2volatile 在不同 CPU 上翻译成不同的指令（按 HotSpot 的实现）：ARM v8 上 volatile 读用 ldar（读-获取），写用 stlr（写-释放），两者之间还保证不重排；x86 上 volatile 读就是普通读，volatile 写后面加一条带 lock 前缀的指令清空存储缓冲。写 Java 只看 JMM，翻译是 JVM 的事，这正是 JMM 存在的意义。
  • 3CAS（compareAndSet）在 ARM v8.1 以上用一条 cas 类原子指令（本机 CPU 的 atomics 标志就是这个），更老的 ARM 用“独占读 + 条件写”循环；x86 用 lock cmpxchg。它们都对同一个地址做“比较并写入”，中间插不进别人。

④-3为什么这样设计：硬件放宽，语言给一个统一的约定

JMM：只保证 happens-beforeJava 5 起（JSR-133）

  • x86、ARM、POWER、RISC-V 上同一份字节码，只要没有数据竞争，结果都一样
  • 没有 volatile、锁的地方，CPU 和 JIT 想怎么优化都行：存储缓冲、乱序执行、寄存器缓存全用上
  • 程序员要自己找出“哪里需要先后关系”，漏掉一处就是在某种 CPU 上偶发的 bug

被放弃的：所有访存都按程序顺序顺序一致性（SC）

  • 最好懂：所有线程的读写排成一条线，每个线程内部按代码顺序
  • 每次写都得等存储缓冲清空、每次读都不能提前：在 ARM 上等于每条访存都加屏障，慢几倍
  • JIT 很多优化（把读提到循环外、合并写）都不能做

决定胜负的约束：绝大多数内存访问根本不跨线程，为了少数共享变量让所有访问都变慢，不划算。所以 JMM 让你把共享的那几个地方标出来（volatile、锁、原子类、final），只在那里付屏障的钱。

④-4jcstress 怎么测：一个状态对象、几个演员、一张结果表

API最少要会的写法
@JCStressTest                                  // 这是一个测试
@Outcome(id = {"1, 0", "0, 1"}, expect = ACCEPTABLE,             desc = "只有一个人抢到")
@Outcome(id = "1, 1",           expect = ACCEPTABLE_INTERESTING, desc = "超卖")   // 或 FORBIDDEN
@State                                         // 每一轮都 new 一个新的，字段是共享的数据
public static class Plain {
    int left = 1;
    @Actor public void exec17(II_Result r) { if (left >= 1) { left = left - 1; r.r1 = 1; } }
    @Actor public void exec23(II_Result r) { if (left >= 1) { left = left - 1; r.r2 = 1; } }
}                                              // 两个 @Actor 由两个线程同时执行；@Arbiter 在它们都结束后执行

# 编译时注解处理器生成测试清单；运行
java -cp classes:jcstress-core-0.16.jar org.openjdk.jcstress.Main -m quick -t 'StockTests'

⑥边界和变体

第一圈

注意事项：不知道就会出事故

坑 1测不出来，不等于是对的← ④-2 各 CPU 放宽程度不同
现象
开发机、测试环境都是 x86，压测几天没问题；迁到 ARM 云主机（Graviton、鲲鹏、Ampere）后偶发数据错乱。⑤ MpPlain：ARM 上 0.07%
根源
x86 只放宽“写 → 读”一种，很多数据竞争在 x86 上碰不出来；JMM 允许的比 ARM 还多。
做法
先按 happens-before 推出允许什么，再测；有 ARM 机器的话，jcstress 在 ARM 上跑一遍。
坑 2伪共享：改的是不同变量，却互相拖慢← ④-1 一致性按缓存行算
现象
两个线程各自累加自己的计数器，没有任何共享数据，加了线程反而更慢。实测：挤在一行 174～316 ms，隔开 63～144 ms
根源
一致性协议以 64 字节的缓存行为单位。两个变量在同一行，核 0 写 a 要把整行抢成独占、让核 1 那份作废；核 1 写 b 又抢回去，这一行在两个核之间来回搬。
做法
热点计数用 LongAdder（它的 Cell 带 @Contended，按核分散）；自己的类可以在两个热点字段之间塞 7 个 long，或用 @jdk.internal.vm.annotation.Contended（JDK 内部注解，业务代码要加 -XX:-RestrictContended 和 --add-exports 才能用）。
坑 3只给“一半”加 volatile← ④-2 volatile 只约束它自己前后
现象
以为一个 volatile 变量能“刷新整个内存”，于是只给其中一个字段加。⑤ SbOneVolatile：10.8%
根源
volatile 只在“写它”和“读到这次写”之间建立先后关系。另一个线程如果根本不读这个 volatile 变量，它自己的普通读写照样可以重排。
做法
把要配对的读写都画出来：写的一边最后写 volatile，读的一边先读 volatile（MP 的写法）；两边都要互相看到对方（SB），两边都得是 volatile 或者用锁。
坑 4把 volatile 当原子操作← ④-1 同一地址也要“读-改-写”一步完成
现象
volatile 计数少了、volatile 库存超卖。⑤ 0.24% 和 33.6%
根源
count++ 是读、加、写三条指令。一致性协议保证每一条都看到最新值，但三条之间能插进别人的写。
做法
AtomicInteger / LongAdder，或者加锁，或者全景第 8 站的数据库条件更新。

第三圈

深处：JDK 源码里 volatile 和 CAS 怎么配合

一个模式：volatile 读看状态，CAS 改状态

AQS 的 private volatile int state：读状态用普通的 volatile 读，改状态用 compareAndSetState（底下是 U.compareAndSetInt）。ConcurrentHashMap 的桶数组是 transient volatile Node[] table，但数组元素没法声明 volatile，所以读一个桶用 tabAt（getReferenceAcquire，带获取语义的读），往空桶放第一个节点用 casTabAt（CAS），节点里的 val、next 是 volatile。（按本机 JDK 17 源码）

这就是 ⑤ 里 MP 的正经写法：发布方用一次 CAS 或 volatile 写“发布”，读取方用一次 volatile 读“接收”，之前写好的字段就都看得见。

伪共享：本机实测和 LongAdder

a、b 挤在一行174～316 ms
中间塞 7 个 long63～144 ms

实测 两个线程各写自己的 volatile long 2 亿次，跑两次、每次两轮。用 Unsafe 查过字段位置：挤在一起时 a、b 在偏移 16 和 24，隔开后在 16 和 80，正好差 64 字节。每一轮都是挤在一行的更慢，但快多少波动很大（1.3～3 倍），这是普通 main 程序，不是 JMH，只看方向。

LongAdder 把一个计数拆成 base 加若干 Cell，线程冲突时各自累加到不同的 Cell，Cell 类带 @Contended，前后自动留出空隙（JDK 17 Striped64 源码）。

面试官会怎么问

volatile 的底层原理是什么？

JMM 层面：volatile 写和读到它的 volatile 读之间建立 happens-before，并禁止和前后普通访存的某些重排。硬件层面由 JVM 翻译成屏障或带获取 / 释放语义的指令：ARM 上是 ldar / stlr，x86 上是写后加 lock 前缀指令清空存储缓冲（④-2）。

MESI 都保证了缓存一致，为什么还需要 volatile？

一致性协议只管同一个地址；存储缓冲和失效队列让不同地址之间的先后能乱，JIT 还会把读提到循环外、放进寄存器（④-1、④-2）。

什么是伪共享？怎么解决？

不同线程写的不同变量落在同一条 64 字节缓存行，这一行在核之间来回作废。填充、@Contended、LongAdder 那样按线程分散（坑 2）。

怎么测试一段并发代码是对的？

先按 happens-before 推出允许的结果，再用 jcstress 跑几亿次看实际结果的分布，并在弱内存序的机器（ARM）上也跑（③、坑 1）。

3. 伪共享换成 LongAdder

在 FalseSharing 里加一组：两个线程都往同一个 AtomicLong 加、和往同一个 LongAdder 加，各 2 亿次，比较耗时。

用到：坑 2、规范 3

自测

1. 用一句话说出这一圈的精华。

每个核先把写放进存储缓冲，一致性协议只保证同一个地址对齐，不同地址之间的先后要靠 volatile、锁、CAS 这些 happens-before 来建立；jcstress 能把这些重排序几亿次地跑出来，而且 ARM 比 x86 暴露得多。

2. 自己写 main 循环测并发，疼在哪？

线程不一定真同时、JIT 会改写循环、没碰到不说明不可能，也没有“允许 / 禁止”的判定（②）。

3. ARM 上 MpPlain 出现“看到标志没看到数据”，根源是 ④ 的哪一条？

④-2：ARM 允许两次写（data、ready）以相反顺序被别的核看到，也允许两次读（ready、data）以相反顺序取值；JMM 对普通字段同样允许。ready 改成 volatile 后，“写 data 先于写 ready”“读到 ready 的这次写先于读 data”都被固定住。

4. 预测：把 MpPlain 里的 data 改成 volatile、ready 保持普通，还会看到 (1, 0) 吗？

还会。volatile 写 data 只保证“它之前的写”不往后跑，不管它之后的普通写 ready 会不会提前；读的一边先读普通的 ready，也没有获取语义。要“看到标志就看到数据”，必须是最后写、最先读的那个变量是 volatile（④-2、坑 3）。

5. 预测：把 FalseSharing 的两个线程都绑到同一个核上（taskset -c 0），挤在一行和隔开还差那么多吗？

差距基本消失：同一个核上两个线程轮流跑，缓存行一直在这一个核的 L1 里，没有核之间来回作废（④-1）。总时间变成两个线程串行的时间。

6. 放回全景：第 5 站用 AtomicInteger 修好了单机超卖。部署到两台 ARM 服务器后，CAS 还能挡住超卖吗？“ARM 内存序更弱”会让它更糟吗？

挡不住，但原因不是内存序：两台机器各有一个 AtomicInteger，彼此根本不共享内存，各卖 100 件。ARM 的弱内存序只影响同一个 JVM 里线程之间的可见性，CAS 在 ARM 上照样是原子的（⑤ 0 次）。跨机器只能靠全景第 8 站的数据库条件更新或 Redis 这类共享的地方。

档位：标准（下一圈）。实验在本机 2 核 ARM（Neoverse-N1，带 LSE 原子指令），JDK 17.0.20，jcstress 0.16：9 个测试 -m quick 跑一次（约 6.5 分钟），3 个禁止结果的测试再带 -v 跑一次取完整结果表；FalseSharing 跑两次，每次去掉第一轮预热。标“实测”的都来自这几次运行。x86 一栏没有在 x86 上跑，是按 x86 TSO 内存模型推的。

按源码（本机 JDK 17）：AQS 的 volatile int state 和 compareAndSetState、ConcurrentHashMap 的 tabAt / casTabAt / volatile 字段、Striped64.Cell 的 @Contended。按文档：Intel SDM 和 ARM 架构手册的内存序描述、Doug Lea 的 JSR-133 Cookbook（屏障和各平台翻译）、jcstress 项目说明和样例、JLS 第 17.4 节。
