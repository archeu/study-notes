JDK 21 · DUAL QUEUE · DUAL STACK · CAS · PARK / UNPARK · SLACK · JSR-166

一条链表，排着的要么全是货，要么全是等货的人

这两个类底层是同一个算法：双重队列（dual queue）。链表里的节点要么是数据（放进来的货），要么是请求（等着取货的空位）。来一个反方向的操作，就找到第一个还没配对的节点，用一次 CAS 改掉它的 item，交接当场完成，等着的那个线程被直接叫醒。SynchronousQueue 只做同步交接，默认按栈（后来的先配），公平模式按队列；LinkedTransferQueue 让放的人自己选：放下就走（put），还是等到被取走（transfer）。

假设场景面试时被追问：“Executors.newCachedThreadPool() 为什么用 SynchronousQueue？突发流量下线程为什么会暴涨？SynchronousQueue 容量是 0，那等着的线程排在哪？”上一页里 HikariCP 递交连接用的也是它。本页偏实现和面试，源码以 JDK 21.0.2 之后的新实现为准（JDK 22 引入，回移到了 21u），也对照 JDK 8～17 的老实现。标“实测”的数字在本机跑过：2 核 ARM 虚拟机，JDK 11.0.32 和 21.0.12。

①要解决的问题：把东西亲手交给另一个线程

有一类场景不想要缓冲区：线程池把任务交给一个闲着的工作线程，连接池把刚还回来的连接交给正在等的人。没人接就别放，有人接就当面交。

和已学页面的关系线程池怎么用队列决定“排队还是加线程”，在 Spring @Async 与线程池 讲过；HikariCP 怎么用 SynchronousQueue(true) 递交连接，在 ConcurrentBag 源码 讲过。这一页往下一层，看交接点内部长什么样。

②朴素做法：一把锁、一个槽位、三个条件

用会的东西写一个“容量为 0”的交接点：一把 ReentrantLock 管一个槽位。put 放进槽位后还不能走，要一直等到对方真的取走。JDK 5 的 SynchronousQueue 就是用锁实现的，今天的源码里还为了兼容 1.5 的序列化格式，留着从来不用的 qlock、WaitQueue 字段。

朴素做法LockedHandoff能用，每次交接都要两次唤醒
final ReentrantLock lock = new ReentrantLock();
final Condition slotFree = lock.newCondition(),
                hasItem  = lock.newCondition(),
                taken    = lock.newCondition();
Object item; long putSeq, takeSeq;

void put(Object e) throws InterruptedException {
  lock.lock();
  try {
    while (item != null) slotFree.await(); // 槽里有别人的
    item = e; long my = ++putSeq;
    hasItem.signal();                      // ① 叫醒取的人
    while (takeSeq < my) taken.await();    // 等对方取走
  } finally { lock.unlock(); }
}
Object take() throws InterruptedException {
  lock.lock();
  try {
    while (item == null) hasItem.await();
    Object e = item; item = null; takeSeq++;
    taken.signalAll();                     // ② 叫醒放的人
    slotFree.signal();
    return e;
  } finally { lock.unlock(); }
}
痛 1每次交接至少两次线程切换

放的人必须等“已取走”的回信，这就多出了一次唤醒。并发一高，抢锁失败的线程还要再睡再醒，4 对时每次交接要 2.9～3.0 次切换。

痛 2所有交接挤在一把锁上

4 对同时交接，朴素做法反而比 1 对慢（每秒 7 万对 11 万）；双重栈从 1 对到 4 对涨了约 4 倍：线程一多，总有人正好在自旋等着，交接时不用睡下再叫醒（每次只有 0.04～0.05 次切换）。

精华

双重队列的精华：等着的线程自己就是队列里的一个节点，来配对的线程用一次 CAS 改掉这个节点的 item，交接就完成了，然后只需要叫醒对方一次，自己不用等回信。

不懂这一点的典型误用：把 SynchronousQueue 当成“容量为 1 的队列”，以为 offer 能先放着；或者拿 LinkedTransferQueue 的 put 当交接用，其实它放下就走、队列无界，见 ⑥ 坑 1、坑 4。

③几种思路：等的人排在哪，交接靠什么完成

“容量为 0”只是说不存元素，等着的线程总要有地方排。几种实现的区别就在这里。

④关键洞察：节点就是等着的人，CAS 就是交接

打个比方：一个交接柜台前排着一列人，要么全是拿着货等人接的，要么全是空着手等货的，不会两种人混着排。来了一个反方向的人，就直接走到队首那位面前完成交接。下面把比方换成真实的结构：每个人是一个 DualNode，“交接”是对它的 item 做一次 CAS。比方对不上的地方：真实的链表里还挂着已经交接完、还没被摘掉的节点，head 也不总指着队首（见 洞察 5）。

先知道这些

CAS

compareAndSet(期望值, 新值)：是期望值才改，一条 CPU 指令完成，两个线程同时做只有一个成功。JDK 里用的是 compareAndExchange，失败时顺便返回当前值。上一页用过。

park / unpark

LockSupport.park() 让当前线程睡下，unpark(t) 叫醒 t。先 unpark 后 park 也行：会留一张“许可”，park 立刻返回，所以不怕叫早了。

无锁链表队列

Michael & Scott 队列：用 CAS 改队尾节点的 next 来追加，用 CAS 改 head 来出队。ConcurrentLinkedQueue 就是它。

无锁栈

Treiber 栈：只有一个 head（栈顶），压栈和弹栈都是对 head 做一次 CAS。

洞察 3所有方法都是同一个 xfer(e, ns)

e 是要放的东西，null 表示要取；ns 说明配不上时怎么办。两个类的十几个方法，全落在这四种 ns 上。

ns = 0 · 立即配得上就配，配不上马上返回，不留节点SQ.offer(e) SQ.poll() LTQ.poll() LTQ.tryTransfer(e)
ns = -1 · 异步配不上就追加一个数据节点，自己不等，马上返回LTQ.put LTQ.offer LTQ.add（只有 LTQ 有）
ns = T · 限时配不上就追加节点等着，最多等 T 纳秒，到时取消SQ.offer(e, t) SQ.poll(t) LTQ.poll(t) LTQ.tryTransfer(e, t)
ns = MAX · 一直等配不上就追加节点，一直等到被配对或被中断SQ.put SQ.take LTQ.take LTQ.transfer

所以 SynchronousQueue 就是“放的一方只能选 0、T、MAX”的 LinkedTransferQueue；LinkedTransferQueue 多出来的只是 ns = -1：货可以先挂在链上，没人等它。

为什么这样设计：把“会合”压成一次 CAS

被放弃的：锁 + 槽位 + 回信

  • 放的人放进槽位后还得等回信，一次交接至少两次唤醒
  • 所有交接共用一把锁，并发越高越挤
  • 好写，好懂，用不着想内存可见性

双重队列：等的人就是节点

  • 配对的人 CAS 成功，交接就完成了，只用叫醒对方一次，自己不等回信
  • 不同的交接各 CAS 各的节点；head、tail 允许落后，热点竞争更少
  • 代价是复杂：死节点的清理、超时取消、旧节点的垃圾链，源码里一大半在处理这些

决定胜负的约束：交接是两个线程的会合，最贵的是线程切换（微秒级），CAS 只要几十纳秒。锁的方案天生要两次唤醒；双重队列让等待者把“回信”写在自己的节点上，配对者一次 CAS 就同时完成了交货和回信。② 的实测：每次交接的线程切换从 2～3 次降到 1 次以内，吞吐高 2～40 倍。

JDK 21.0.2 之后还有一个设计取舍：原来 SynchronousQueue 自己有一套 TransferStack / TransferQueue，和 LinkedTransferQueue 各写各的。现在 SynchronousQueue 的内部类 Transferer 直接继承 LinkedTransferQueue：公平模式用父类的 xfer，不公平模式只加了一个 xferLifo，节点和等待逻辑共用。SynchronousQueue.java 从 1168 行（JDK 17）缩到 590 行。代价见 ⑥ 版本差异。

一段短实现：不到 60 行的双重队列

照 JDK 6～8 里 SynchronousQueue 公平模式（TransferQueue）的经典结构写的，只保留一直等的 put 和 take，不支持超时和中断，也不做 slack。有一个哑节点当 head，判断“排着的是不是同类”看的是 tail。

1MiniDualQueue.javaJDK 11+
import java.util.concurrent.atomic.AtomicReference;
import java.util.concurrent.locks.LockSupport;

// 极简双重队列（FIFO）：只有 put（等到被取走才返回）和 take，不支持超时和中断
public class MiniDualQueue<E> {
  static final class Node {
    final boolean isData;                                  // true：数据节点；false：请求节点
    final AtomicReference<Object> item;                    // 数据节点 x→null、请求节点 null→x，就是“交接”
    final AtomicReference<Node> next = new AtomicReference<>();
    volatile Thread waiter;
    Node(Object x, boolean isData) { this.item = new AtomicReference<>(x); this.isData = isData; }
  }
  private final AtomicReference<Node> head, tail;
  public MiniDualQueue() {
    Node dummy = new Node(null, true);                     // 哑节点：isData 却没数据，算“已配对”
    head = new AtomicReference<>(dummy); tail = new AtomicReference<>(dummy);
  }
  public void put(E e) { xfer(e); }
  @SuppressWarnings("unchecked") public E take() { return (E) xfer(null); }

  private Object xfer(Object e) {
    boolean haveData = (e != null);
    Node s = null;
    for (;;) {
      Node t = tail.get(), h = head.get();
      if (h == t || t.isData == haveData) {                // 空，或者排着的是同类：排到队尾
        Node tn = t.next.get();
        if (t != tail.get()) continue;
        if (tn != null) { tail.compareAndSet(t, tn); continue; }   // tail 落后了，帮它往前推
        if (s == null) s = new Node(e, haveData);
        if (!t.next.compareAndSet(null, s)) continue;      // 别人先追加了，重来
        tail.compareAndSet(t, s);
        Object x = await(s, e);
        if (head.get() == t) head.compareAndSet(t, s);     // 帮忙把 head 推过自己
        return (x != null) ? x : e;
      } else {                                             // 排着的是异类：和第一个配对
        Node m = h.next.get();
        if (t != tail.get() || m == null || h != head.get()) continue;   // 读到的不一致，重来
        Object x = m.item.get();
        boolean ok = (haveData == (x == null)) && m.item.compareAndSet(x, e);
        head.compareAndSet(h, m);                          // 不管成没成功，m 都不再是活节点了
        if (!ok) continue;                                 // 被别人抢先配对了
        LockSupport.unpark(m.waiter);
        return (x != null) ? x : e;
      }
    }
  }
  private Object await(Node s, Object e) {                 // 先自旋，再挂起
    for (int spins = 128;;) {
      Object x = s.item.get();
      if (x != e) return x;
      if (spins > 0) { spins--; Thread.onSpinWait(); }
      else if (s.waiter == null) s.waiter = Thread.currentThread();   // 先登记，再复查一遍 item
      else LockSupport.park(this);
    }
  }
}

import java.util.*;
import java.util.concurrent.*;

// 看 SynchronousQueue 和 LinkedTransferQueue 的行为；JDK 11+ 直接 java SqPeek.java
public class SqPeek {
  // 让 n 个线程按 A、B、C… 的先后顺序停在 take() 上，再依次放入 1..n，看谁拿到几
  static String order(BlockingQueue<Integer> q, int n) throws Exception {
    var got = new ConcurrentSkipListMap<Integer, String>();
    var ts = new ArrayList<Thread>();
    for (int i = 0; i < n; i++) {
      String name = String.valueOf((char) ('A' + i));
      Thread t = new Thread(() -> { try { got.put(q.take(), name); } catch (InterruptedException e) { } });
      t.start(); ts.add(t);
      while (t.getState() != Thread.State.WAITING) Thread.sleep(1);   // 确认它已经停住
    }
    for (int v = 1; v <= n; v++) q.put(v);
    for (Thread t : ts) t.join();
    return got.toString();
  }

  public static void main(String[] args) throws Exception {
    System.out.println("JDK " + Runtime.version());
    var tr = Class.forName("java.util.concurrent.SynchronousQueue$Transferer");
    System.out.println("① SynchronousQueue$Transferer 的父类：" + tr.getSuperclass().getName());

第一圈

注意事项

坑 1newCachedThreadPool 遇到突发流量，线程数暴涨← ④ offer 是 ns = 0
现象
1000 个任务一下子进来、每个跑 200 ms：线程池开了 1000 个线程，getQueue().size() 一直是 0。实测
根源
线程池提交任务用的是 offer，在 SynchronousQueue 上就是“立即”模式：此刻没有空闲线程停在 poll 上，就失败，线程池接着新建线程。newCachedThreadPool 的上限是 Integer.MAX_VALUE。
做法
自己 new ThreadPoolExecutor，给 maximumPoolSize 一个上限，配上拒绝策略；或者换成有界队列，让任务排队。
坑 2有上限 + SynchronousQueue：满了直接拒绝，不排队← ④ offer 是 ns = 0
现象
上限 50 个线程，同样 1000 个任务：开到 50 个线程，其余 950 个全抛 RejectedExecutionException。实测
根源
同上：SynchronousQueue 不存东西，线程到上限后 offer 必然失败，只剩拒绝策略可走。
做法
想“满了先排一会儿”，就别用 SynchronousQueue；用它就要接受“满了立刻拒”，并用 CallerRunsPolicy 之类的策略把压力推回给调用方。
坑 3SynchronousQueue 的 size、isEmpty、迭代器永远是空的← ④ 等着的是节点，不是元素
现象
有线程停在 take() 上时，size() 仍是 0、isEmpty() 仍是 true（⑤ 第 ② 段）。监控线程池的“队列长度”永远是 0。
根源
链表里挂着的是等待者，不是可以拿走的元素。源码直接把这些方法写死了：size() 返回 0、isEmpty() 返回 true。
做法
监控线程池看 getActiveCount()、getPoolSize()、getLargestPoolSize() 和拒绝次数。LinkedTransferQueue 能用 getWaitingConsumerCount() 看有几个人在等。
坑 4LinkedTransferQueue 的 put 从不阻塞，队列无界← ④ put 是 ns = -1
现象
拿它当“能交接的队列”，生产比消费快时一直 put，内存越涨越高，最后 OOM。remainingCapacity() 永远是 Integer.MAX_VALUE。
根源
异步模式配不上就追加一个数据节点，然后马上返回，没有任何上限。
做法
要背压，生产者用 transfer 或 tryTransfer(e, timeout)；或者干脆用有界的 ArrayBlockingQueue。
坑 5默认模式后到先得：最早来等的人可能等最久← ④ 不公平是栈
现象
做消息传递时，几个消费者都在 poll(timeout)，新来的消费者总是先拿到，最早来的那个一直等到超时。放进线程池里却是好事：每 100 ms 来一个短任务，6 秒后不公平模式只剩 1 个线程，公平模式 10 个线程都还活着。实测
根源
不公平模式是栈，总是和栈顶（最后来的）配对。线程池里最后闲下来的线程一直接活，其他线程闲满 keepAlive 就被回收。
做法
线程池保持默认；做消息传递、要按先后服务时，用 new SynchronousQueue<>(true) 或 LinkedTransferQueue。
坑 6LinkedTransferQueue.size() 是从头数一遍← ④ 链上混着死节点
现象
在高频路径上调 size() 打日志或做判断，队列一长就明显变慢；并发修改时数出来的也只是个大概。
根源
链表里混着已配对的节点，没有计数器，size() 和 getWaitingConsumerCount() 都是 countOfMode 从 head 遍历一遍。javadoc 也写着它不是常数时间。
做法
判断空不空用 isEmpty()（找到第一个活数据节点就停）；要计数就自己在外面维护一个 LongAdder。
坑 7新实现早期版本的两个 bug历史原因 · 看版本
现象
① 21.0.2～21.0.4、JDK 22 上，不公平 SynchronousQueue 有内存泄漏（JDK-8332154），21.0.5 和 JDK 23 修复。② JDK 21.0.2 起到 JDK 25，LinkedTransferQueue.poll() 在极少数竞争下，队列不空也可能返回 null（JDK-8371740），JDK 26 修复。

用 JDK 21 的至少升到 21.0.5。② 截至 2026-11，21u-dev 和 25u-dev 的这个文件里还没有回移，依赖 poll() 结果做判断的代码要能容忍偶尔的假空。

再往深一点

为什么旧 head 要指向自己

  • 节点之间只有 next 单向链接。一个早就出队的旧节点如果还被谁引用着（比如一个停在半路的迭代器），它后面所有更新的节点都会顺着 next 被留住。
  • 源码注释引用了 Boehm 的论文：GC 晚一点发现某个老节点是垃圾，后面一串都回收不了。把旧 head 的 next 改成指向自己，链就在这里断开。
  • 代价是所有遍历都要处理“读到自链接就从头重来”，迭代器、size()、remove(o) 里都有这段。

取消的节点怎么摘：unsplice 和 sweepVotes

  • 超时的节点如果在链头附近，直接把 head 推过去；在中间，就 CAS 前驱的 next 跳过它。
  • 两种情况摘不掉：它是链尾（新节点还要往它后面挂），或者前驱自己也死了（前驱可能已经不在链上）。这时记一票 sweepVotes，攒够 16 票（SWEEP_THRESHOLD = 15，按位与判断）就从头扫一遍，统一摘掉。老实现的阈值是 32。
  • 典型触发场景：队尾的人反复 poll(短超时) 又超时，队首却有一个一直不超时的 take() 堵着。

自旋多少才合适

  • 源码注释写得很直白：太少，对方马上就来时也白白切换了一次线程；太多，烧 CPU，还挡着对方上 CPU。最优值“不可知”，现在的 128 是在测试过的平台上取的折中。
  • 只有自己是第一个等的人、或前一个等待者还没睡时才转：前面的人都睡了，说明对方一时半会儿来不了，转也白转。
  • 上面 JDK 11 / 21 的对比就是这个折中在一台 2 核机器上的样子。

Exchanger 为什么不用双重队列

  • 双重队列里两边身份不同：一边给、一边拿。Exchanger 两边都既给又拿，谁先到谁等，后到的把自己的东西放下、拿走对方的。
  • 它用一个槽位，竞争大时改用一组槽位（arena），让不同的线程对在不同的槽位上配对，减少对同一个地址的 CAS。
  • JDK-8338146 改进了 Exchanger 在虚拟线程下的性能，改动也落在 LinkedTransferQueue.java 里，可见这套节点和等待代码已经是 j.u.c 的公共件。

面试官会怎么问

SynchronousQueue 容量是 0，那等着的线程排在哪？

排在一个无锁链表里：每个等着的线程对应一个节点，节点上记着它要放的东西（数据节点）或者一个空位（请求节点）。“容量为 0”说的是没有可以被拿走、却没人等着交接的元素。默认模式这个链表当栈用，公平模式当队列用。

put 和 take 是怎么配对的？

来的人顺着链表找第一个反方向的活节点，对它的 item 做一次 CAS：取的人把货换成 null，放的人把 null 换成货。CAS 成功就算交接完成，然后 unpark 节点上等着的线程。找不到就把自己挂上去，先自旋一会儿再 park。

newCachedThreadPool 为什么用 SynchronousQueue？有什么风险？

它要的语义是“有闲线程就交给它，没有就新建”，SynchronousQueue 的 offer 正好是“此刻有人在 poll 才成功”。默认的栈模式让最近闲下来的线程先接活，其余的闲满 60 秒被回收。风险是线程上限为 Integer.MAX_VALUE，突发流量下线程数会暴涨。

LinkedTransferQueue 和 SynchronousQueue、LinkedBlockingQueue 有什么区别？

它和 SynchronousQueue 是同一个双重队列算法，多了异步模式：put 放下就走，像无界的 LinkedBlockingQueue；transfer 等到被取走，像 SynchronousQueue 的 put。和 LinkedBlockingQueue 比，它不用锁，取的人在等时来货可以直接交到手里。从 JDK 21.0.2 起，SynchronousQueue 的内部类直接继承了它。

练习 1 · 改成栈

照 xferLifo 的思路，给 MiniDualQueue 加一个不公平模式：新节点压到 head 上，来的人只看栈顶。用 SqPeek 第 ③ 段的办法测顺序。

做对了会看到：三个先后停在 take 上的线程 A、B、C，依次放 1、2、3，拿到的是 C=1、B=2、A=3；压力测试仍然一个不多一个不少。

用到：④ 洞察 6，⑥ 坑 5

练习 2 · 加上 poll(timeout)

给 MiniDualQueue 的 await 加一个截止时间：到点就把自己的 item 从 null CAS 成节点自己。CAS 失败说明刚好被配上了，要把货收下。

做对了会看到：没人放时 poll(100ms) 约 100 ms 后返回 null；在第 99 ms 放进来的货不会丢，要么被这次 poll 拿到，要么留给下一个取的人。

用到：④ 洞察 1 的“取消也是 CAS”，⑥ await 第 5 条

练习 3 · 去掉自旋看看

把 MiniDualQueue 的 spins = 128 改成 0，再改成 4096，各跑一对生产者 / 消费者，同时读 /proc/self/task/*/status 数线程切换。

做对了会看到：本机 1 对时，0 圈每次交接约 1.06 次切换、每秒 19 万次；128 圈 0.24 次、65 万次；4096 圈几乎不切换、153 万次。一直有活时转得越久越快；代价要在“对方很久才来”时才显出来：每个等着的线程都要先空转完才睡，等的人一多就把 CPU 占满。

用到：④ 洞察 4，⑥ 版本差异

1. 用一句话说出双重队列的精华。

等着的线程自己就是链表里的一个节点，来配对的人对它的 item 做一次 CAS 就完成了交接，只需要叫醒对方一次。

← ② 精华

2. 用一把锁加条件变量做交接点，痛在哪？

放的人放下后还要等回信，一次交接至少两次唤醒；所有交接挤在一把锁上。实测每次交接 2～3 次线程切换，吞吐只有双重队列的几分之一到几十分之一。

← ② 实测

3. newCachedThreadPool 线程暴涨，根源是 ④ 里的哪一条？

线程池用 offer 提交，SynchronousQueue 的 offer 是 ns = 0 的立即模式：此刻没有空闲线程停在 poll 上就失败，线程池只能新建线程。

← ④ 洞察 3

4. 预测：一个 LinkedTransferQueue 里已经有 3 份 put 进来、没人取的货，这时来一个 transfer(x)，它什么时候返回？

要等到 3 份旧货都被取走、x 也被取走之后。transfer 发现排着的全是同类（数据），只能追加到队尾，按先来先得，前面 3 份先被取。

← ④ 洞察 2 + 洞察 3

5. 预测：公平的 SynchronousQueue 上 A 在 take，B 调 poll()（不带超时），会怎样？

B 立刻拿到 null。B 也是请求，和 A 同类，没法配对；poll() 是立即模式，配不上就走，不会把自己挂到链上。A 继续等。

← ④ 洞察 2 + 洞察 3

6. 预测：线程池用 new SynchronousQueue<>(true) 代替默认的，每 100 ms 来一个很短的任务，keepAlive 2 秒，池里原本有 10 个空闲线程，过一会儿还剩几个？

10 个都在。公平模式按先来先得把任务交给等得最久的线程，10 个线程轮流接活，每个每秒都有活干，没有一个闲满 2 秒。默认的栈模式则总是交给最后闲下来的那个，其余 9 个会被回收。本机实测正是 10 和 1。

← ④ 洞察 6

7. 预测：如果去掉“旧 head 的 next 指向自己”这一步，功能会错吗？

功能不会错，配对和顺序都靠 item 的 CAS 和链表顺序保证。受影响的是内存：只要还有人引用某个很老的节点，它后面所有出过队的节点都回收不了。

← ④ 洞察 5
