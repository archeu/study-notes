一个 int，一条排队的链

AQS 只管两样东西：一个叫 state 的 int，和一条先进先出的等待队列。“现在能不能拿到”由子类回答：tryAcquire / tryRelease 用 CAS 改 state。“拿不到怎么办”全由 AQS 包办：排队、park 睡下、谁来叫醒、超时和中断怎么撤。ReentrantLock、Semaphore、CountDownLatch、读写锁、线程池的 Worker、Tomcat 的连接数闸门，都是这样搭出来的。

①为什么需要→ ②没有它会怎样→ ③相邻方案→ ④原理→ ⑤亲眼看到→ ⑥细节→ ↺回到⑤

假设场景面试被问“讲讲 AQS”，又在线上 jstack 里看到一大片 parking to wait for … ReentrantLock$NonfairSync，不知道是哪段代码在等。所以本页偏源码和排查，⑥ 末尾有面试题。版本按生产上最常见的 JDK 8、17、21 三个来讲：AQS 在 JDK 14 被重写过，所以 8 是一套写法，17 和 21 是另一套，面试资料里的 waitStatus、SIGNAL、acquireQueued 都是 JDK 8 的。标“实测”的在本机三个版本上都跑过：Temurin 8u512、17.0.21，Ubuntu OpenJDK 21.0.12，2 核 ARM 虚拟机。

①为什么需要：一次请求，路上就要过好几道 AQS

你可能从没直接写过 AQS，但一个普通的 Spring Boot 请求，从进 Tomcat 到写完日志，经过的这些地方全是它。下图里每一处都用 javap 和字节码扫描核过（版本见图下）。

和已学页面的关系ThreadPoolExecutor.execute 源码里的 Worker 就是一个 AQS 子类；SynchronousQueue 和 ConcurrentBag 是不用 AQS 的另一条路，③ 会拿它们对比。

②没有它会怎样：自己写一把锁

最直接的写法是 CAS 自旋：抢不到就一直重试。另一个现成的选择是 synchronized。拿 8 个线程抢一把锁，锁里 sleep 1 ms（模拟拿着锁做 IO），三个 JDK 各跑一次：

8 个线程抢一把锁，跑 2 秒每秒完成2 秒里用掉的 CPU锁里只做一次自增时，每秒完成
CAS 自旋锁321～330约 4.0 秒（两个核全满）490 万～680 万
synchronized934～9350.05～0.06 秒650 万～1160 万
ReentrantLock（AQS，默认非公平）932～9340.06～0.10 秒2340 万～3990 万
ReentrantLock(true)（公平）922～9290.07～0.09 秒20 万～32 万

范围是 JDK 8、17、21 三次的最小值到最大值，三个版本的结论一致。只有 2 核，同一时刻真正在跑的只有 2 个线程，所以自旋锁的“慢”主要是它抢走了持锁线程的 CPU：持锁的线程 sleep 醒来，要等别人转完时间片才轮到它。

痛 1自旋：等的人在烧 CPU

拿不到就重试，等多久就烧多久。锁里一旦有 IO，两个核全花在“等”上，干活的反而被挤慢。要省 CPU，就得让等的线程睡下，还得有人在锁放开时叫醒它。这就需要一条记着“谁在等”的队列。

痛 2synchronized：够用，但缺功能

不能“等 1 秒拿不到就算了”，等的时候不能被中断，一把锁只有一个等待集合（wait / notify），不能选公平，不分读写。JDK 21 的虚拟线程在 synchronized 里阻塞还会钉住载体线程（见 ⑥ 坑 5）。

精华

AQS 的精华：把“排队、睡下、叫醒、超时、中断”只写一遍，各种同步工具只需要回答一个问题：给定 state，现在能不能拿到、放掉以后要不要叫人。

不懂这一点的典型误用：以为 ReentrantLock 是“先来先得”的（默认是非公平的，刚放锁的线程几乎总能抢回来），或者以为 new ReentrantLock(true) 以后 tryLock() 也公平（不是），见 ⑥ 坑 3。

③相邻方案：等的线程放在哪

方案等的线程放在哪能做的例子
synchronizedJVM 里的对象监视器（ObjectMonitor）互斥、可重入、一个 wait 集合；自动释放Hashtable、JDK 8 / 17 的 PrintStream
AQS 一族AQS 的等待队列，节点上挂着线程独占和共享两种模式、超时、中断、多个 Condition、公平和非公平ReentrantLock、Semaphore、CountDownLatch、读写锁
StampedLock自己的一条等待队列，不是 AQS乐观读：读的时候不加锁，读完检查版本号读多写极少、读的代码很短的地方
不用锁没有等待；要等时用别的交接点CAS、原子类、无锁队列ConcurrentHashMap 的大部分路径、LongAdder、HikariCP 的 ConcurrentBag

选择规则：只要互斥、没有特殊需求，synchronized 就行（JDK 21 虚拟线程里阻塞例外）；要超时、可中断、多个条件、读写分离、限流计数，就用 AQS 一族；读多写极少才考虑 StampedLock。本页学 AQS。

④原理：state 说能不能拿，队列管拿不到怎么办

比方：银行一个窗口（state）加一排叫号椅（等待队列）。窗口空着就直接办；有人在办就取号坐下打盹；办完的人起身时拍一下下一位的肩膀。比方对不上的地方：默认情况下，刚走进来的人可以趁被拍的人还没站起来，直接冲到窗口前（非公平），见 为什么这样设计。

先知道这些

CAS

compareAndSetState(0, 1)：是 0 才改成 1，一条指令完成，同时只有一个线程成功。之前的页面用过很多次。

park / unpark

LockSupport.park() 让线程睡下，unpark(t) 叫醒它。先 unpark 后 park 也行，会留一张“许可”。jstack 里的 WAITING (parking) 就是它。

CLH 队列

一种排队锁：每个等待者是链表上的一个节点，只盯着自己前面那个。AQS 用的是它的变体：节点双向链接，等待者 park 而不是一直转。

模板方法

父类写好流程，留几个方法给子类填。AQS 留的是 tryAcquire、tryRelease、tryAcquireShared、tryReleaseShared、isHeldExclusively。

机制 2AQS 管排队，子类管 state 是什么意思

子类state 的意思能不能拿（tryAcquire 系列）模式
ReentrantLock.Sync重入了几次，0 是没人拿0 → CAS 成 1；已经是自己的就 +1独占
ReentrantReadWriteLock.Sync高 16 位：读锁被拿了几次；低 16 位：写锁重入次数写：整个是 0 才行；读：没有别人的写锁就 +1<<16写独占、读共享
Semaphore.Sync剩几个许可剩的 ≥ 要的，就 CAS 减掉共享
CountDownLatch.Sync还要等几次 countDown只看是不是 0，不改 state共享
ThreadPoolExecutor.Worker−1 还没启动，0 空闲，1 正在跑任务CAS 0 → 1，不可重入独占
Tomcat LimitLatch.Sync不用 state，另用一个 AtomicLong 计数计数 +1 后不超过上限才行，超了就减回去共享

每一行都只写了“能不能拿”和“放掉后要不要叫人”。排队、park、被叫醒后重试、超时撤销，这些子类一行都不用写。

开始。

为什么这样设计：三个取舍，都有实测

被放弃的：拿不到就自旋

  • 等多久烧多久，锁里有 IO 时两个核全满（② 实测约 4 秒 CPU / 2 秒）
  • 还抢走了持锁线程的 CPU，干活的反而慢（每秒 321～330 次，对 930 次）

AQS：排队，然后 park

  • 等的线程不占 CPU（0.06～0.10 秒）
  • 代价：睡下、叫醒都是线程切换，微秒级。所以 JDK 17 / 21 里，排在最前面的线程被叫醒后又没抢到时，会先短暂自旋重试几次再睡

被放弃的：一个等待集合，notifyAll 全叫醒

  • 50 个消费者等着，放一个元素叫醒一群，只有一个抢得到，其余白醒（实测平均每个元素叫醒 1.8～5.9 次）

AQS：按队列只叫醒一个

  • release 只叫醒 head 后面那一个；Condition.signal 只挪一个（实测每个元素正好 1.0 次）
  • 代价：被叫醒的人自己负责传给下一个（共享模式），逻辑更绕

被放弃的默认值：公平

  • 每次交接都必须等一个睡着的线程醒来，锁里只做自增时每秒 20 万～32 万次，每次交接约 1 次线程切换

AQS 的默认：非公平

  • 谁正在 CPU 上谁先拿，每秒 2340 万～3990 万次，约是公平锁的 100 倍
  • 代价：排队的人会被插队，尾延迟变长（⑤ 实测 1000 次里 953～995 次被插队）

决定胜负的约束：线程切换是微秒级的，CAS 是纳秒级的。AQS 每个取舍都在躲线程切换：拿不到才睡、只叫醒一个、默认让正在跑的线程直接拿。和 ConcurrentBag、SynchronousQueue 是同一个账。

自定义一次性开关AQS javadoc 里的 BooleanLatch，JDK 8 / 17 / 21 都能用
class BooleanLatch {
  private static class Sync extends AbstractQueuedSynchronizer {
    protected int tryAcquireShared(int ignore) {
      return getState() != 0 ? 1 : -1;      // 开了就放行
    }
    protected boolean tryReleaseShared(int ignore) {
      setState(1); return true;            // 打开，叫醒等的人
    }
  }
  private final Sync sync = new Sync();
  public void signal() { sync.releaseShared(1); }
  public void await() throws InterruptedException {
    sync.acquireSharedInterruptibly(1);
  }
}

⑤亲眼看到：用反射把队列打出来

一个 Java 8 语法的小程序，javac --release 8 编一次，同一份 class 在 JDK 8、17、21 上跑：让 main 重入两次，三个线程来排队，再用反射读出 state、head 和每个节点的状态。最后测一下插队。

1AqsPeek.javaJDK 8 直接 java AqsPeek；JDK 17 / 21 要加两个 --add-opens（见注释）
import java.lang.reflect.Field;
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.locks.*;

// 直接看 AQS 里面：state、排队的节点、节点状态
// 运行：JDK 8 直接 java AqsPeek；JDK 9+ 要加 --add-opens java.base/java.util.concurrent.locks=ALL-UNNAMED --add-opens java.base/java.util.concurrent=ALL-UNNAMED
public class AqsPeek {
  static Object field(Object o, String... names) throws Exception {
    for (Class<?> c = o.getClass(); c != null; c = c.getSuperclass())
      for (String n : names) try { Field f = c.getDeclaredField(n); f.setAccessible(true); return f.get(o); } catch (NoSuchFieldException e) { }
    return null;
  }
  static AbstractQueuedSynchronizer sync(Object owner) throws Exception { return (AbstractQueuedSynchronizer) field(owner, "sync"); }
  static String queue(AbstractQueuedSynchronizer s) throws Exception {
    StringBuilder b = new StringBuilder("state=" + field(s, "state") + "  队列：");
    Object n = field(s, "head");
    if (n == null) return b.append("（还没建）").toString();
    for (int i = 0; n != null && i < 10; i++, n = field(n, "next")) {
      Thread t = (Thread) field(n, "waiter", "thread");                 // JDK 14+ 叫 waiter，之前叫 thread
      Object st = field(n, "status", "waitStatus");                     // JDK 14+ 叫 status，之前叫 waitStatus
      b.append(i == 0 ? "head" : " → ").append(i == 0 ? "" : (t == null ? "?" : t.getName())).append("[").append(n.getClass().getSimpleName()).append(" ").append(st).append("]");
    }
    return b.toString();
  }
  static void waitParked(Thread t) throws InterruptedException { while (t.getState() != Thread.State.WAITING && t.getState() != Thread.State.TIMED_WAITING) Thread.sleep(1); }

  public static void main(String[] a) throws Exception {
    System.out.println("JDK " + System.getProperty("java.version"));
    final ReentrantLock lock = new ReentrantLock();
    lock.lock(); lock.lock();                                           // main 重入两次
    System.out.println("① main 重入 2 次：" + queue(sync(lock)) + "，" + lock);
    List<Thread> ws = new ArrayList<>();
    for (String name : new String[] {"T1", "T2", "T3"}) {
      Thread t = new Thread(() -> { lock.lock(); lock.unlock(); }, name); t.start(); waitParked(t); ws.add(t);
    }
    System.out.println("② 三个线程排队：" + queue(sync(lock)));
    lock.unlock();
    System.out.println("③ unlock 一次：" + queue(sync(lock)) + "（还剩 1 层，没人被叫醒）");
    lock.unlock(); for (Thread t : ws) t.join();
    System.out.println("④ 全部走完：  " + queue(sync(lock)));

    Semaphore sem = new Semaphore(3); sem.acquire(2);
    CountDownLatch latch = new CountDownLatch(2); latch.countDown();
    ReentrantReadWriteLock rw = new ReentrantReadWriteLock(); rw.readLock().lock(); rw.readLock().lock(); rw.writeLock();
    System.out.println("⑤ Semaphore(3) 拿走 2 个：state=" + field(sync(sem), "state") + "；CountDownLatch(2) countDown 一次：state=" + field(sync(latch), "state")
        + "；读锁拿两次：state=" + field(sync(rw), "state") + "（高 16 位是读锁数，" + ((int) field(sync(rw), "state") >>> 16) + "）");

    // ⑥ W 已经在排队，持锁的线程 unlock 后马上又抢：tryLock() 和 lock() 分别谁拿到？
    for (boolean fair : new boolean[] {false, true}) {
      int tryWins = 0, lockWins = 0;
      for (int i = 0; i < 1000; i++) {
        final ReentrantLock l = new ReentrantLock(fair); l.lock();
        Thread w = new Thread(() -> { l.lock(); l.unlock(); }); w.start(); waitParked(w);
        l.unlock();
        if (l.tryLock()) { tryWins++; l.unlock(); }
        w.join();
        final ReentrantLock l2 = new ReentrantLock(fair); l2.lock();
        final java.util.concurrent.atomic.AtomicBoolean wGot = new java.util.concurrent.atomic.AtomicBoolean();
        Thread w2 = new Thread(() -> { l2.lock(); wGot.set(true); l2.unlock(); }); w2.start(); waitParked(w2);
        l2.unlock();
        l2.lock(); if (!wGot.get()) lockWins++; l2.unlock();
        w2.join();
      }
      System.out.println("⑥ " + (fair ? "公平  " : "非公平") + "：放下马上再抢，1000 次里 tryLock() 抢到 " + tryWins + " 次，lock() 抢在 W 前面 " + lockWins + " 次");
    }
  }
}

第一圈

注意事项

坑 1lock 之后没在 finally 里 unlock：锁永远不放← ④ state 只有持有者能改回 0
现象
某个分支 return 或抛异常没走到 unlock，之后所有线程都停在 parking to wait for … NonfairSync。如果持锁的线程已经因为异常死掉了，jstack 里连持有者都找不到。
根源
synchronized 的释放由 JVM 保证（字节码里有异常表），AQS 的 state 只是一个 int，没人调 tryRelease 它就永远不是 0。owner 字段还指着那个线程。
做法
lock() 写在 try 外面紧挨着 try，unlock() 写在 finally 第一行。
坑 2重入次数和 unlock 次数对不上← ④ state 是重入次数
现象
⑤ 实测：重入两次只 unlock 一次，state 还是 1，排队的三个线程一个都没被叫醒。没拿锁就 unlock，三个版本都抛 IllegalMonitorStateException。实测
根源
tryRelease 只把 state 减 1，减到 0 才算释放、才叫人。
做法
一次 lock 对应一个 finally 里的 unlock；排查时看 getHoldCount()。
坑 3默认非公平，而且 tryLock() 在公平锁上也插队← ④ 非公平是故意的
现象
非公平锁刚放下马上又抢，1000 次里 953～995 次抢在排队的人前面；new ReentrantLock(true) 的 lock() 一次都没插队，可 tryLock() 1000 次里抢到 999～1000 次。实测
根源
非公平的 tryAcquire 不看队列，state 是 0 就 CAS；公平的先看 hasQueuedPredecessors()。而 tryLock() 调的是 Sync 里那个不看队列的版本，javadoc 写明了它会“打破公平”。
做法
要严格先来先得：公平锁 + lock() 或 tryLock(0, TimeUnit.SECONDS)（带超时的版本遵守公平）。多数场景用默认非公平，接受尾延迟。
坑 4await 用 if 判断条件← ④ Condition 的两条队
现象
队列空时消费者 await，被 signal 醒来直接 poll，偶尔拿到 null 或越界。
根源
signal 只是把节点挪到同步队列，醒来还要重新抢锁；抢到之前，别的线程可能已经把东西拿走了。另外还有虚假唤醒。
做法
while (条件不满足) cond.await();，ArrayBlockingQueue 的源码就是这么写的。
坑 5JDK 21 虚拟线程：在 synchronized 里阻塞会钉住载体线程← ④ park 和监视器不同
现象
100 个虚拟线程各拿各的锁、锁里 sleep 50 ms：用 synchronized 要 2517 ms（2 个载体线程一个个轮），换成 ReentrantLock 只要 66 ms。加 -Djdk.tracePinnedThreads=short 会打印 <== monitors:1。实测 JDK 21
根源
AQS 的等待是 LockSupport.park，虚拟线程 park 时会从载体线程上卸下来；JDK 21 的 synchronized 做不到，阻塞时连载体线程一起占住。JDK 24（JEP 491）修了，但 21 没有。JDK 8、17 没有虚拟线程，不涉及。
做法
JDK 21 用虚拟线程时，包着 IO 的锁换成 ReentrantLock。JDK 21 自己也这么做了：java.io 的 PrintStream、BufferedOutputStream 等改用了内部的 ReentrantLock。
坑 6jstack 里找不到“谁拿着锁”排查方法
现象
synchronized 的持有者在 jstack 里显示 - locked <0x…>；ReentrantLock 的持有者默认什么也不显示。
根源
AQS 的锁不是 JVM 监视器，只有加 -l，线程下面才会多出 Locked ownable synchronizers: - <0x…> (a …ReentrantLock$NonfairSync)。
做法
jstack -l <pid>，拿等待者的 parking to wait for <0x…> 地址去搜，同一地址出现在 ownable synchronizers 下的线程就是持有者。三个版本实测都这样；JDK 8 等待者的栈帧是 acquireQueued，17 / 21 是 acquire。
坑 7拿着读锁再要写锁：自己等自己← ④ 读写锁的 state
现象
先 readLock().lock()，再 writeLock().tryLock(1 秒)：返回 false；换成 lock() 就永远卡住。反过来，拿着写锁再拿读锁（锁降级）没问题。实测
根源
写锁要求 state 的高 16 位（读锁数）为 0，可这里面就有自己那一份读锁。
做法
要写就先放掉读锁再拿写锁，拿到后重新检查数据；或者干脆一开始就拿写锁。
坑 817 / 21 新实现修过的几个 bug历史原因 · 看小版本
现象
① JDK 17.0.11 之前：Condition 上等的线程很多时，CPU 偏高（JDK-8317960，只有 17u 有这个问题）。② JDK 17.0.13、21.0.5 之前：被取消的 ConditionNode 能熬过 Minor GC，多占内存（JDK-8325754）。③ 大量线程用很短的超时去 tryAcquire、又拿不到时，cleanQueue 可能活锁（JDK-8386085）。

再往深一点

为什么要有一个空的 head

  • “排第一”就简单定义成“前驱是 head”，不用特殊处理空队列。
  • 拿到锁的线程，它的节点直接变成 head，清掉线程引用：head 永远代表“当前持有者或者刚放手的那个位置”。
  • 队列懒建：从来没人竞争的锁，连这个空节点都不会分配（⑤ 里第 ① 行“还没建”）。

JDK 8 为什么把 SIGNAL 记在前驱上

  • 放锁的线程只看 head 一个节点的 waitStatus 就知道“要不要叫人”：是 0 说明后面没人睡，连 unparkSuccessor 都不用进。
  • 代价是理解起来绕：一个节点的状态描述的是它后面那个。JDK 14 改成节点只描述自己，再用“head.next 的 status 不为 0 才叫”达到同样效果，面试时两种都要说得出。

读写锁的 state 怎么切

  • 高 16 位是所有线程读锁的总次数，低 16 位是写锁重入次数，各自最多 65535。
  • 每个线程自己重入了几次读锁，另外记在 ThreadLocal 的 HoldCounter 里，还缓存了第一个读线程和最近一个读线程，省掉多数 ThreadLocal 查找。
  • 写锁要求高低 16 位都为 0（除了自己的写锁重入），所以拿着读锁升级会自己等自己（坑 7）。

Worker、LimitLatch：什么时候值得自己继承 AQS

  • 线程池的 Worker 要一把不可重入的锁来区分“空闲”和“在跑任务”，见 ThreadPoolExecutor 那页。
  • Tomcat 的 LimitLatch 要“计数到上限就排队”，而且上限可以运行中用 setLimit 改；它把计数放在一个 AtomicLong 里，只借用 AQS 的共享模式来排队和叫醒。
  • 共同点：现成的锁、信号量、门闩语义不对，又需要排队和超时，才值得自己写。业务代码里几乎用不到。

面试官会怎么问

讲讲 AQS 的原理。

一个 volatile int state 加一条 FIFO 的双向等待队列（CLH 的变体）。子类实现 tryAcquire / tryRelease（或共享版本）来定义 state 的含义和能不能拿到；拿不到时 AQS 负责把线程包成节点入队、park，释放时叫醒队首的后继，被叫醒的线程重新 tryAcquire。还支持超时、中断、Condition。JDK 8 里用 waitStatus 的 SIGNAL 记在前驱上表示“要叫醒后继”，JDK 14 起改成节点自己的 status。

公平锁和非公平锁的区别？为什么默认非公平？

区别只在 tryAcquire：公平锁先看 hasQueuedPredecessors，有人排队就不抢；非公平锁 state 为 0 就直接 CAS。默认非公平是因为交接给一个睡着的线程要等它醒来，这段时间锁是空的，让正在运行的线程直接拿走，吞吐高得多（本机实测约 100 倍）。代价是排队的线程可能被反复插队。另外 tryLock() 在公平锁上也不公平。

JDK 8 的 unparkSuccessor 为什么要从 tail 往前找？

入队时先设 node.prev，CAS tail 成功后才设 pred.next，next 指针有一段时间是断的；节点取消时 next 也可能被改。prev 链总是完整的，所以后继为空或被取消时，从 tail 往前找最靠前的有效节点。

CountDownLatch 和 CyclicBarrier、Semaphore 怎么实现的？

CountDownLatch 和 Semaphore 都是 AQS 共享模式：Latch 的 state 是剩余计数，归零时 releaseShared，等待者一个叫醒一个；Semaphore 的 state 是许可数，acquire 减、release 加。CyclicBarrier 不直接继承 AQS，它用一把 ReentrantLock 加一个 Condition（trip）实现，最后一个到达的线程 signalAll。

Condition 和 Object.wait/notify 有什么区别？

Condition 依附于 AQS 的锁，一把锁可以建多个 Condition，各自一条等待队列，可以精确地只叫醒等某个条件的线程；支持超时和不可中断的等待。await 时节点进条件队列并完全释放锁，signal 把节点转到同步队列，等锁释放后才真正醒来重新抢锁。

1. 用一句话说出 AQS 的精华。

2. 自己用 CAS 自旋写锁，痛在哪？

等的线程一直在烧 CPU，锁里有 IO 时两个核全满，还抢走了持锁线程的时间片；想不烧 CPU 就得有队列记住谁在等、park 和 unpark，这正是 AQS 做的。

← ② 实测

3. “ReentrantLock 锁住了一直不放”，最常见的根源是 ④ 里哪一条？

state 只是一个 int，只有持有者调 tryRelease 才会变回 0；没在 finally 里 unlock，或者重入次数和 unlock 次数不对，state 就永远不是 0。

4. 预测：Semaphore(1) 当互斥锁用，A 拿着，B 在等，A 的代码里 release 了两次。之后 B 和新来的 C 会怎样？

许可变成 2（Semaphore 不检查谁放的），B 被叫醒拿走 1 个，C 也能直接拿走另 1 个，两个线程同时进了“互斥区”。

5. 预测：一个线程 lock() 等锁时被 interrupt() 了，它会怎样？换成 lockInterruptibly() 呢？

lock()：不理会，继续排队，拿到锁后把中断标志补回去（JDK 8 的 selfInterrupt，17 / 21 在 acquire 里重设）。lockInterruptibly()：醒来发现被中断，取消节点，抛 InterruptedException。

6. 预测：CountDownLatch(1) 上有 100 个线程在 await，countDown 之后多久全部醒来？会不会一下子 100 个线程同时抢 CPU？

不会同时。countDown 只叫醒第一个，第一个通过后叫醒第二个，依次传下去，100 次叫醒是串起来的。每一棒都要一次线程切换，所以全部醒来有一个微秒到毫秒级的“传递时间”，和线程数成正比。
