同一个词，两边是两个东西：DDD 限界上下文、聚合、领域事件

DDD 那一大套名词里，真正决定系统长什么样的是两条边界。限界上下文是语言的边界：在它里面，一个词只有一个意思，一套模型只由一拨人改。聚合是一致性的边界：在它里面，规定好的不变量在每次事务结束时都成立。边界之外不共享对象，只记 id，靠领域事件慢半拍对齐。本机实测：运营把活动改成满 400 减 50 之后，订单按自己存的快照退 104.49；回头找营销重算，是 101.59。

①要解决的问题：全景第 2、4 站

规则表有了，现状也看清了：营销的规则写在订单服务的 calcPrice() 里，420 行。在全景第 4 站，这一步要解决的是：满减、叠加、分摊、退款这些东西，哪些归营销，哪些归订单，凭什么。

运营嘴里的“优惠”一条规则门槛、力度、能和谁叠、预算、有效期，天天在改
订单和财务嘴里的“优惠”一个事实这一单的保温杯便宜了 24.51 元，下了单就不能变
现在的代码混在一起运营每加一种活动，就要改订单服务、发订单服务

②不用它会怎样

做法疼在哪
一个大模型：订单和营销共用一个 Discount 类、一张优惠表两拨人对同一个类提相反的要求：运营要它随时能改，财务要它永远不变。只能靠加字段、加 if 调和
按表划：“优惠相关的表都归营销”订单退款要读营销的表才知道退多少。营销改了规则，或者营销服务挂了，退款就跟着错、跟着挂
对象只有 getter 和 setter，规则全写在 Service 里“一行只能退一次”这种规则散在好几个 Service 里，有一个入口忘了检查，就能退两次。全景第 3 站那第 7 处入口就是这样漏的
下单时在一个事务里把订单、券、活动预算全改了每张订单都要改同一行活动预算，全部排队。④ 的实验台里，每秒 200 单的需求只过得去 20 单

缺的是两条说得出理由的边界：一个词在哪个范围里只有一个意思，以及哪些数据必须在同一个事务里一起对。

不懂这一点时的典型误用：把包名改成 domain、application、infrastructure，类名加上 Aggregate、Repository 后缀，就说“我们用了 DDD”。边界一条没动，calcPrice 还在订单服务里，只是换了个目录。

③几种流派

做法规则放在哪适合代价
事务脚本一个请求一个方法，从头写到尾规则少的增删改查，后台管理规则一多，方法变长，逻辑到处重复
贫血模型 + Service对象只装数据，规则在 Service大多数 Java 项目的现状不变量没有唯一的守门人
DDD 战略设计先划限界上下文，画出它们的关系多拨人、多个系统、同一个词有歧义要和业务方一起花时间对语言
DDD 战术设计聚合自己守不变量，事件通知别人规则复杂、错了要赔钱的那一小块类变多，持久化要自己组装
六边形、洋葱、整洁架构领域代码在中间，框架和数据库在外圈常和 DDD 一起用它管的是代码怎么分层，不管边界怎么划

选择规则：战略设计只要系统不止一拨人在改，就值得做，它不要求改一行代码。战术设计只用在核心的那一小块，靶场里是算价、订单金额、退款；商品类目维护这种后台功能，事务脚本就够。本页学三样：限界上下文、聚合、领域事件。

④核心取舍：两条边界，边界之外慢半拍

先知道这些
  • 统一语言：业务方和开发用同一套词，代码里的类名、方法名也用这套词。上一页的名词表就是它的起点。
  • 不变量：无论怎么操作都必须成立的条件，比如“应付等于各行原价减各行分摊”“一张券只能核销一次”。
  • 最终一致：两份数据允许短时间对不上，但保证过一会儿会对上。J09 的 CAP 与 BASE 讲过。

限界上下文：一个词只有一个意思的范围

怎么知道边界该划在哪？找三个信号，它们通常同时出现：同一个词意思变了（规则，还是事实）；改它的人和节奏不一样（运营天天改，对订单来说永远不改）；出错的样子不一样（配错规则，还是退错钱）。划在这里，两边就能各改各的。Eric Evans 的原话是：大系统的领域模型想做到完全统一，既不可行，也不划算。

聚合：必须在同一个事务里一起对的那一小团

聚合回答的是“事务该多大”。规则是倒着推的：先列不变量，哪些数据要一起才能判断这条不变量，它们就在同一个聚合里。“一行只能退一次”只需要订单自己的数据，所以订单行在 Order 里面。“一张券只核销一次”只需要券自己的状态，所以 Coupon 单独一个聚合。订单和券之间没有哪条规则要求它们在同一毫秒一起变，就不放在一起。

Vaughn Vernon 把它收成四条：不变量放在边界里；聚合尽量小；引用别的聚合只用 id；边界之外用最终一致。

领域事件：边界之外，慢半拍对齐

事件是聚合之间唯一的“因果线”。它换来的是：订单的事务很小、很快，营销挂了也不耽误支付。它付出的是那一小段对不上的时间，以及两个必须自己保证的东西：事件不能丢（和订单状态在同一个事务里落库，再发出去，见 本地消息表），重复收到不能记两次（见 幂等设计）。

实验台：扣活动预算，放进下单事务，还是发事件

先猜：12.12 零点，每秒 200 单，都参加同一个满减活动。有人为了“预算一分钱都不能超”，把扣预算和下单放进同一个事务，每个事务要占住活动那一行 50 毫秒。会怎样？

估算模型：大聚合时，每个下单事务都要更新活动的同一行，行锁让它们一个接一个，每秒最多 1000 ÷ 占锁毫秒数 个。小聚合时订单互不相干，预算由事件事后记，从“实际花完”到“营销知道花完”之间进来的订单都会多减，最多超 每秒单数 × 延迟 × 40 元。热点行排队的实测在 J06 的 热点行那页。真要又快又不超，做法是 J12 秒杀与抢券 那页的预扣。

为什么这样设计

选中的：几个小模型，各自说得通，中间翻译

每个上下文里一个词一个意思，一拨人说了算。每个聚合守自己那几条不变量，事务小。上下文之间靠接口和事件，谁的格式变了，改防腐层。

被放弃的：一个全公司通用的大模型

一张 discount 表、一个 Discount 类，谁都能用。输在：两拨人对它的要求是矛盾的，每次改动要所有人同意；想保证一致就得开大事务，想要性能就得放弃一致。

决定胜负的约束有两条。“一个词一个意思”只在局部成立：公司一大，强行统一的成本比翻译的成本高。事务越大，能同时进行的就越少：所以只把确实要一起对的东西放进同一个事务。代价是多了翻译的代码，多了“慢半拍”要处理，还得有人持续守着边界。

最少的名词

名词一句话靶场里的例子
实体有身份的东西，属性变了还是它Order、Coupon
值对象没有身份，只看值，建好就不变PriceSnapshot、金额
聚合、聚合根一起守不变量的一小团，以及它唯一的入口Order 带着订单行和快照
领域服务一条业务规则，但放进哪个聚合都不合适PricingService：算价同时要看活动和券
领域事件业务上已经发生的一件事OrderPaid、OrderLineRefunded
仓储把聚合整个取出来、整个存回去OrderRepository，一次读写订单加订单行
防腐层把别的上下文的说法翻译成自己的PricingGateway 和它的实现

细节先不讲：上下文之间还有哪几种关系、聚合怎么存进 MySQL、乐观锁，放到第 ⑥ 步。

⑤套进场景：用户 1024 那一单，在两个上下文里走一遍

三个包：promotion（营销）、ordering（订单）、app（把两边接起来）。ordering 包里没有一行 import 营销的类。为了一个进程里能跑，接口调用和消息队列都换成了直接调方法，边界和真的一样。

// 聚合根：没有 setter，只有业务动作
public OrderLineRefunded refundLine(int line) {
  if (status != Status.PAID)
    throw new IllegalStateException("还没付款，不能退");
  if (refunded[line])
    throw new IllegalStateException("这一行已经退过");
  refunded[line] = true;
  // 退的是这一行的实付：读自己的快照，不问营销
  return new OrderLineRefunded(id, line,
      prices[line] - snapshot.lineDiscounts()[line]);
}

// 值对象：下单那一刻的事实，只记营销的 id
public record PriceSnapshot(long[] lineDiscounts,
    String promotionId, long promotionAmount,
    String couponId) { ... }
app/PromotionPricingAdapter.java：防腐层
// 整个工程只有这一个类同时认识两边
public class PromotionPricingAdapter
    implements PricingGateway {     // 接口属于订单
  public PriceSnapshot priceFor(String orderId,
                                long[] prices) {
    Quote q = pricing.quote(prices, promotion, coupon);
    if (coupon != null) coupon.lock(orderId);
    // 营销的 Quote → 订单的 PriceSnapshot
    return new PriceSnapshot(q.lineDiscounts(),
        q.promotionId(), q.promotionAmount(),
        q.couponId());
  }
}

O2 应付 350.00；付款前预算剩 60.00，付款后已用 90.00 / 100.00
O3 应付 350.00；付款前预算剩 10.00，付款后已用 140.00 / 100.00，超 40.00，活动结束
O4 应付 400.00（活动已结束，不再减）
看懂这次运行
  • 第 3 段是这一页的中心。活动改了以后，营销那边的“优惠”已经是另一条规则，订单这边的“优惠”还是下单时的那个数。退款读的是事实，所以是 104.49。这就是全景 ADR-009 的理由。
  • 第 2 段，同一个事件来两次，预算还是 40.00：Coupon 认得锁它的那张订单，Promotion 记着哪些订单记过账。幂等是聚合自己的不变量，不是消费者代码外面包的一层判断。
  • 第 4 段四次都被拒绝，拒绝的地方都在聚合里面。不管从哪个入口进来（接口、消息消费者、定时任务），都绕不过去。
  • 第 5 段是最终一致的代价：预算设成了 100 元，O3 付款时只剩 10 元，照样减了 50 元。超多少、能不能接受，要回到上一页的 R6 去问运营。

到这里已经能交差了：两个上下文、三个聚合、一层防腐、两个事件，边界为什么在这，每条都说得出理由。已知还没处理的细节：事件怎么保证不丢（坑 4）；两个请求同时改同一张订单（乐观锁）；聚合怎么存进 MySQL（仓储）；这两个上下文要不要拆成两个服务（下一页）。

⑥反例和误用

第一圈 · 不知道就会出事的

1按表、按名词划上下文← ④ 边界看的是词义和谁改
现象
“带 discount 的表都归营销”。订单退款要跨服务读营销的表；营销想删一个过期字段，要先问订单组。
根源
表名里的同一个词，装的是两个意思。按词面划，把规则和事实又绑回了一起。
做法
对每个名词问三句：在这里指什么，谁改它，多久改一次。答案不同就是两个东西，各给各的名字。
2聚合划得太大估算← ④ 聚合就是事务的大小
现象
Order 里直接持有 Promotion 对象，下单时顺手把预算改了。高峰期下单接口大量超时，数据库里一堆事务在等同一行。
根源
放进一个聚合，就是承诺它们在同一个事务里一起改。实验台里每秒 200 单只过得去 20 单。
做法
只为“必须同一瞬间成立”的不变量画圈。预算晚一秒记行不行？问业务，行就用事件。
3聚合之间直接引用对象← ④ 引用别的聚合只用 id
现象
order.getCoupon().setStatus(REDEEMED)。订单的代码绕过了券自己的检查，一张券被核销了两次。
根源
拿到了对象，就拿到了改它的能力。别的聚合的不变量，从此靠调用方自觉。
做法
只存 couponId。想让券变，发事件，由 Coupon 自己的方法决定接不接受。
4事件在事务外面发，或者当命令用← ④ 事件不能丢，只说事实
现象
订单提交了，发消息那一步进程挂了：券一直锁着，预算没记。或者事件叫 RedeemCoupon，订单在指挥营销，营销加一步“发积分”还得改订单。
根源
改库和发消息是两件事，中间能断。命令式的事件把下游的流程写死在了上游。
做法
事件和订单状态同一个事务落库，再由发件箱或事务消息发出去。命名用过去时，只带事实。
5有聚合的名字，没有聚合的门实测← ④ 不变量要有唯一的守门人
现象
类叫 OrderAggregate，字段全有 setter。退款的三个入口里有一个没检查“这一行退过没有”，同一件商品退了两次。
根源
规则写在 Service 里，每个入口都要记得调。⑤ 第 4 段四次拒绝都发生在聚合里面，入口再多也绕不过。
做法
聚合根只暴露业务动作（pay()、refundLine()），不暴露 setter；检查写在动作里。
6两个上下文共用一个 jar 里的领域类，或者同一张表← ④ 各用各的模型，中间翻译
现象
营销给 Quote 加了个字段，订单服务没改代码却要跟着重新发布；或者两个服务都在写同一张表，谁也不敢改列。
根源
共享的类和表，就是没有画出来的耦合。
做法
订单只依赖自己的 PricingGateway 和 PriceSnapshot；营销的返回格式是它公开的契约，变更要打招呼、要兼容。
7到处上 DDD← ④ 代价是类变多、要翻译
现象
商品类目的增删改查，也配齐了聚合根、工厂、仓储、领域服务、防腐层，改一个字段要动六个类。
根源
战术设计的成本是固定的，那块业务没有复杂的不变量，成本就收不回来。
做法
先问这一块有哪些不变量、错了赔什么。答不上来，用事务脚本。

第二圈 · 团队里该怎么写

  • 每个上下文一张名词表，类名照着它起：防两拨人用同一个词说两件事。
  • 一个事务只改一个聚合：防事务越写越大；确实要一起改的，说明聚合划错了，回去重划。
  • 跨聚合只存 id：防别人的不变量被你的代码绕过。
  • 聚合根的方法用业务动词（refundLine，不是 setStatus）：防规则漏在入口外面。
  • 事件过去时命名、带事实、消费者幂等：防丢、防重复、防上游指挥下游。
  • 别的上下文的类不进领域包：用构建工具或测试守住（下一页的 verify()）：防边界被悄悄穿透。

第三圈 · 深一层

上下文之间的几种关系

画上下文图时，每条线都要标是哪一种。客户和供应商：下游提需求，上游排期（靶场的订单和营销）。遵奉者：上游不理你，你照它的模型用。防腐层：不想被上游的模型带着走，自己翻译。开放主机服务：上游提供一套公开、稳定的接口给所有下游。共享内核：两边共用一小块模型，改它要双方同意。各行其道：干脆不集成。

核心域、支撑域、通用域

不是每一块都值得精雕细琢。核心域是公司靠它赚钱、和别人不一样的部分，放最好的人、做战术设计。支撑域是自己业务特有但不出彩的，够用就行。通用域是谁家都一样的，比如短信、支付通道，能买就买。靶场里，算价和订单金额是核心，类目维护是支撑。

聚合怎么存进 MySQL

仓储按聚合整个读、整个存：OrderRepository.find(id) 一次把订单和订单行都取出来组装好，save(order) 在一个事务里写回去。用 MyBatis 就是在仓储的实现里调两三个 Mapper 再组装，Mapper 和表对应，仓储和聚合对应。聚合小，这件事才不贵，这也是“聚合尽量小”的另一个理由。

两个请求同时改同一个聚合

用户连点两次“退保温杯”，两个请求各自读到“没退过”，各自通过检查。聚合里的检查只管单次事务内，并发要靠版本号：聚合根带一个 version，保存时 where version = 读到的值，后到的那个更新不到行，重读再试。这就是乐观锁，J06 的 事务、MVCC 与锁 讲过原理。

自测

1. 用一句话说出这一页的精华

限界上下文是语言的边界，划在同一个词意思变了、改它的人变了的地方；聚合是一致性的边界，只圈住必须在同一个事务里一起成立的不变量；边界之外只存 id，靠领域事件最终一致。

2. “一个大模型”和“按表划”各疼在哪？

一个大模型里，运营要 Discount 随时能改，财务要它永远不变，只能靠加字段和 if 调和，每次改动要所有人同意。按表划，退款要读营销的表，营销改规则或挂掉，退款跟着错、跟着挂。

3. 坑 2（聚合太大）的根源是 ④ 的哪一条？

聚合就是事务的大小。把活动放进订单聚合，等于承诺每次下单都在同一个事务里改活动那一行，所有订单在这一行上排队。

4. 预测：把“每行分摊”不存在订单里，退款时调营销的接口现算。12.20 活动下线以后，用户退 12.12 那一单的保温杯，会怎样？

营销那时已经没有这条满减规则，只剩 9 折券，现算出来这一行只便宜 12.90，退 116.10，比当初实付多退 11.61。如果营销服务那一刻恰好不可用，退款干脆做不了。订单把一个本该属于自己的事实，放在了别人会改、会挂的地方。

5. 预测：订单发出 OrderPaid 以后，营销的消费者挂了 10 分钟。用户、运营、财务各看到什么？恢复以后呢？

用户什么都感觉不到：支付成功，订单正常。运营看到的预算消耗比实际少，活动可能在预算花完后还多开了 10 分钟，超支按实验台的算法是每秒单数 × 600 秒 × 40 元。那些券停在“锁定”，没变成“已核销”，不能再用，所以不会出现一张券用两次。恢复以后积压的事件逐个处理，重复的会被跳过，两边重新对上。这就是最终一致：对不上的时间变长了，但不丢、不重。

6. 放回全景：第 4 站前后各是什么？边界划错了，后面哪几站会跟着坏？

前面是第 2 站的规则表和事件序列、第 3 站的现状；后面是第 5 站定形态、第 6 站写 ADR。如果按表划成“优惠都归营销”，第 5 站无论放进模块还是拆成服务，订单退款都要同步依赖营销；第 6 站就不会有 ADR-009；第 10 站“先搬后改”搬过去的会包括订单自己的事实，以后营销每次改规则，都要担心历史订单的退款。

档位：标准。本机跑过（2 核 ARM 虚拟机，OpenJDK 17.0.21）：Walkthrough，⑤ 的输出是这次运行的原样。实验台是估算模型，在 node 里跑过；坑 2 的数字来自它，不是实测。预算设成 100 元是为了看到超支那一刻，不是靶场的真实配置。

按文档（已核对原文）：Martin Fowler《BoundedContext》（2014）：限界上下文是 DDD 战略设计的核心模式，并引 Eric Evans 的话，大系统的领域模型完全统一既不可行也不划算；《DDD_Aggregate》（2013）：聚合是可以当作一个整体的一组领域对象，外部引用只能指向聚合根，事务不应跨聚合边界，聚合整个加载、整个保存。出自书里的概念，没有逐句核对：聚合设计的四条规则（Vaughn Vernon《实现领域驱动设计》）；上下文映射的几种关系、核心域和通用域（Eric Evans《领域驱动设计》）；事务脚本（Martin Fowler《企业应用架构模式》）。
