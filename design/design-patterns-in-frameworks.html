420 行 if/else 怎么拆：设计模式，到 Spring 和 MyBatis 里去认

设计模式不是 23 张要背的类图。它们是同一个手法的几种样子：找出会变的那一块，把它做成一个对象，让不变的骨架去调用它。所以学一个模式，先问它管的是“什么在变”：算法在变是策略，某一步在变是模板方法，处理者的个数和顺序在变是责任链，想在别人前后加东西是代理。这些你每天都在用：Spring MVC 的拦截器、@Transactional、MyBatis 的 Mapper 和插件，全是。本机实测：三种券从 if/else 搬成三个类，30 组输入结果全部一致；再加满减，只新增一个类。

②不用它会怎样

做法疼在哪
接着加 else if新分支加在哪，就是什么顺序。全景那颗雷就是这么来的：if 加在券后面，等于先打折后满减
复制一份 calcPriceV2()，新活动走新的两份代码各改各的。修一个舍入的错要改两处，忘了一处就是全景第 3 站那第 7 个入口
加一个 type 参数，方法里到处 if (type == 8)一种优惠的逻辑被切成好几段，散在方法各处。想下线去年的临时券，要找遍整个方法
想给算价加耗时统计、加缓存，就直接写进 calcPrice()业务规则里掺进了和业务无关的代码，方法越来越长，换个地方还得再抄一遍

四种做法是同一个毛病：会变的东西和不变的东西长在一起。每次变化都要动同一块代码，而那块代码里还住着别人。

不懂这一点时的典型误用：把模式当成“高级写法”，背下类图往代码里套。只有两种情况、以后也不会多，照样建一个工厂、一个策略接口、两个实现、一个上下文。类多了四个，变化点一个没有。

④核心取舍：把会变的做成对象，让不变的去调它

先知道这些
  • 多态：对着接口调方法，实际跑的是哪个实现类，运行时才定。四个模式都靠它，是它们共同的下面一层。
  • 开闭原则：加新功能靠加代码，不靠改已有的代码。它是目标，模式是达到它的手段。
  • JDK 动态代理：运行时生成一个实现了指定接口的类，对它的每次调用都先交给你写的一段处理逻辑。AOP 代理那页讲过。

策略加责任链：从一个大方法，到一串小对象

Spring MVC 的拦截器是同一个结构：HandlerExecutionChain 里有一个 List<HandlerInterceptor>，applyPreHandle() 挨个调。AOP 也是：ReflectiveMethodInvocation.proceed() 每调一次往后走一个拦截器。差别在于那两处的链，每一环可以决定“到此为止，不往下传了”（拦截器返回 false、切面不调 proceed()）；算价的链每一环都会走到。

模板方法：骨架写死，留一两个空

策略和模板方法管的东西很像，分法不同。策略是整件事换一种做法，用组合：链手里拿着一组规则对象。模板方法是一件事里的一步换一种做法，用继承：子类填父类留的空。算价两个都用了：每条规则是一个策略；所有规则共同的“适用吗、减多少、封顶、记账”这个骨架，是模板方法。

代理：长得一样的替身，站在真身前面

在哪调用方拿到的替身在前后做了什么真正干活的
靶场 TraceProxy一个 $Proxy 类，实现了 Pricing打印调用前、调用后PricingChain
Spring AOPJdkDynamicAopProxy 生成的代理（没有接口时是 CGLIB 生成的子类）把这次调用交给一串拦截器：开事务、查缓存、记日志你写的 Service
MyBatis 的 MapperMapperProxy 生成的代理按方法名找到那条 SQL，交给 SqlSession没有真身：接口没有实现类，替身自己把活干了
MyBatis 的插件Plugin.wrap() 包出来的代理先过你写的 Interceptor，比如改写 SQL 加分页Executor、StatementHandler 等

代理解决的是 ② 的最后一行：耗时、事务、缓存这些事和业务规则无关，却要包在它外面。把它们放进替身，业务代码一行不用改，替身还能给一百个类共用。代价是一条有名的规矩：只有从外面经过替身进来的调用才会被加上这些东西。类里面 this.xxx() 自己调自己，走的是真身，替身不知道。

装饰和代理的结构一模一样，都是“包一层、接口不变”。分别在意图：代理替你控制对真身的访问，调用方通常不知道有它；装饰是调用方自己一层层叠上去的能力，比如 MyBatis 给缓存依次套上 LruCache、LoggingCache。认不清哪个是哪个没关系，认得出“这里包了一层”就够用。

实验台：链的顺序换一换

先猜：假设以后放开限制，用户 1024 那单（400 元）能同时用上满减（减 40，门槛看原价）、9 折券、一张 10 元现金券。三条规则有 6 种先后顺序。应付金额会算出几个不同的数？

算法和 ⑤ 的 Java 代码一样：满减的门槛看原价，所以它总是减 40；折扣券在“当时该付的”上打 9 折；现金券减 10。减法之间换顺序不影响结果，乘法夹在中间就不一样了。这就是为什么 order() 必须是规则表里写明的一条（R1），而不能是“谁先被加载谁在前”。

为什么这样设计

选中的：变化点做成对象，骨架调用它

加一种优惠是加一个类，下线一种是删一个类。每个类小到一眼看完，单独测。顺序、封顶、记账这些所有规则共有的东西只写一遍。

被放弃的：分支集中写在一个方法里

if/else 或者 switch。分支只有两三个、几年不变的时候，它其实是更好的写法：一眼看全，不用跳来跳去。输在分支会不断增加的时候：每次变化都改同一个地方，重测全部。

决定胜负的约束：这个地方到底变不变、多久变一次。优惠的种类每个大促都在变，所以值得拆。代价是实打实的：类变多；一次算价的逻辑分散在好几个文件里，读代码要跳着读；流程藏在链和代理里，断点不好打。所以判断标准不是“能不能用模式”，而是“它已经变过几次了”。

最少的写法：在 Spring 里把链装起来

规则是 Bean，链靠注入拿到全部
@Component
class PromotionMinusRule extends AbstractRule {
  public int order() { return 10; }
  ...
}

@Service
class PricingChain implements Pricing {
  private final List<DiscountRule> rules;

  // 构造器参数写 List<接口>，
  // Spring 把所有实现都放进来
  PricingChain(List<DiscountRule> rules) {
    this.rules = rules.stream()
      .sorted(comparingInt(DiscountRule::order))
      .toList();           // 顺序自己排，写明
  }
}
按名字挑一个策略
// 参数写 Map<String, 接口>：
// 键是 Bean 的名字，值是实现
@Service
class RefundService {
  private final Map<String, RefundPolicy> policies;

  RefundService(Map<String, RefundPolicy> policies) {
    this.policies = policies;
  }

  long refund(Order o, String policyName) {
    RefundPolicy p = policies.get(policyName);
    if (p == null) throw new IllegalArgumentException(
        "没有这种退款口径：" + policyName);
    return p.refund(o);
  }
}

细节先不讲：规则类里能不能放成员变量、链断了怎么办、lambda 能不能代替这些类，放到第 ⑥ 步。

⑤套进场景：先搬后改，把算价拆开

分两步，和全景第 10 站一样。第一步只搬：三种券各搬成一个类，拿 30 组输入和老代码逐个比，一分钱不许差。第二步才加：满减是一个新类。为了不拉 Spring 进来，链是手工装的，结构和上面一样。

⑤rule/AbstractRule.java：模板方法完整代码 →
public abstract class AbstractRule
    implements DiscountRule {
  @Override
  public final Quote apply(Quote q, Cart c, Offer o) {
    if (!matches(c, o)) return q;      // 不适用，原样放过
    long amount = Math.min(q.payable(),
        discount(q, c, o));            // 不许减成负数
    return q.minus(name(), amount);    // 记一笔
  }
  protected abstract String name();
  protected abstract boolean matches(Cart c, Offer o);
  protected abstract long discount(Quote q,
                                   Cart c, Offer o);
}
rule/PromotionMinusRule.java：新需求就是这一个类
public class PromotionMinusRule extends AbstractRule {
  public int order() { return 10; }  // R1：排在券前面
  protected String name() { return "满减"; }
  protected boolean matches(Cart c, Offer o) {
    return o.promotion()
        && c.total() >= 300_00;      // 门槛看原价
  }
  protected long discount(Quote q, Cart c, Offer o) {
    return 40_00;
  }
}

看懂这次运行
  • 第 1 段是“搬”的验收：6 个购物车乘 5 种券的情况，新旧一致才往下走。这 30 组里有 5 元、99.99 元、正好 100 元这些边界。重构那一页会把它叫特征测试。
  • 第 2 段，报价自己带着一路的明细（满减减 40，折扣券减 36）。这份明细再往前一步，就是上一页 ADR-0009 要存进订单的分摊来源。
  • 第 3 段只改了一个数字，结果差 4 元。顺序现在是一个能评审、能测试的数，不再是“if 写在第几行”。
  • 第 4 段的类名 $Proxy25 是运行时生成的，编号每次可能不同。这就是你在 Spring 里打断点时，在调用栈上看到的那种类。

到这里已经能交差了：算价从一个大方法变成四个小类加一条链，加优惠不动旧代码，顺序写在明处。已知还没处理的细节：规则类里能不能存状态（坑 3）；顺序相同的两条规则谁先（坑 2）；类里自己调自己不走代理（坑 5）；规则多了类太多怎么办（lambda）。

⑥反例和误用

第一圈 · 不知道就会出事的

1为了模式而模式← ④ 看它变过几次
现象
“是否包邮”只有包和不包两种，写了 ShippingStrategy 接口、两个实现、一个 ShippingStrategyFactory。读的人跳了四个文件，才看到一个 if (total >= 99)。
根源
模式的成本是固定的（类变多、要跳着读），收益要等变化真的发生才有。
做法
先写成 if。同一个地方第三次因为同一类原因被改，再拆。
2链的顺序没有写明实测← ④ 责任链管的就是谁先谁后
现象
本地算出 324，线上算出 320。原因是 List<DiscountRule> 直接拿来用，规则在列表里的先后跟着 Bean 的注册顺序走，两个环境不一样。⑤ 第 3 段，一个数字的差别就是 4 元。
根源
顺序是业务规则。没有地方明写它，它就由某个你没注意的实现细节决定。
做法
每条规则有明确的 order()，链自己排序；顺序相同的再按名字排，保证每次一样；用上一页的算例把顺序钉成测试。
3策略类里放了成员变量← ④ 规则是 Spring 的单例 Bean
现象
规则类里有个字段 private long discountSoFar，算的时候往里累加。压测时金额偶尔对不上，单线程怎么测都是对的。
根源
Spring 的 Bean 默认只有一个实例，所有请求的线程共用它。成员变量就成了多个线程同时读写的共享数据。
做法
规则类不存任何一次请求的数据。状态放在参数和返回值里传，⑤ 的 Quote 是不可变的，每条规则返回一个新的。
4模板方法的继承越叠越深← ④ 模板方法用的是继承
现象
AbstractRule → AbstractCouponRule → AbstractPercentCouponRule → 具体类。想知道一条规则到底做了什么，要从下往上翻四个类；改最上面的骨架，下面全受影响。
根源
继承把子类和父类的实现绑死。每多一层，就多一层“父类改了我不知道”。
做法
骨架只留一层。还想复用的部分，做成另一个对象传进去（组合），不要再继承一层。
5类里自己调自己，代理加的东西没生效← ④ 只有经过替身的调用才算
现象
placeOrder() 里直接调 this.saveSnapshot()，后者标了 @Transactional(propagation = REQUIRES_NEW)，结果并没有新开事务。
根源
this 是真身，不是替身。事务是替身加的。
做法
把那个方法挪到另一个 Bean 里，从外面调。AOP 代理和事务传播两页有实测。
6用模式名代替业务名← ④ 模式是手段
现象
DiscountStrategyFactoryManager、AbstractPromotionHandlerAdapter。类名里全是模式，看不出它在业务上是什么。
根源
把“用了什么手法”当成了这个类最重要的事。
做法
类名说它是什么：PromotionMinusRule、PricingChain。用了什么模式，写在类注释的第一行。

第二圈 · 团队里该怎么写

  • 先写直白的代码，第三次改同一处再拆：防过度设计。
  • 链的顺序用数字写明，并且有测试：防顺序跟着环境变。
  • 策略类、拦截器不存请求数据：防并发下串数据。
  • 模板方法的骨架标 final，继承只留一层：防子类改掉不该改的流程。
  • 需要代理生效的方法，从别的 Bean 调：防 this 调用绕过事务、缓存。
  • 类名用业务词，模式写在注释里：防名字只有手法、没有含义。

第三圈 · 深一层

lambda 让很多模式变轻了

只有一个方法的策略接口，就是一个函数式接口。简单的规则不必单独一个类：Map<Integer, LongUnaryOperator>，或者一个带 lambda 的枚举，就是一组策略。Spring 的 JdbcTemplate.query(sql, rowMapper) 是模板方法的回调版：骨架（拿连接、执行、关连接、翻译异常）在 JdbcTemplate 里，那个空用一个 lambda 传进去，不用继承。规则有自己的依赖、要单独测的时候，再升成类。

结构一样、意图不同的几对

策略和状态：都是把分支换成对象；策略由外面挑，彼此不知道对方，状态自己决定下一个是谁（券的 未使用 → 锁定 → 已核销）。代理、装饰、适配器：都是包一层；代理接口不变、管访问，装饰接口不变、加能力，适配器是把接口变了。看代码时先认结构，再问意图。

MyBatis 一次查询里的四层包装

你调 Mapper 的方法：MapperProxy（代理）接住，交给 SqlSession；里面的 Executor 外面先包着 CachingExecutor（装饰，二级缓存），再外面可能包着插件生成的 Plugin（代理加责任链）；最里面 BaseExecutor.query()（模板方法）查一级缓存，最后才是 SimpleExecutor.doQuery()（策略之一）。执行流程那页的调用栈，对着这四个词再看一遍。

Spring Boot 自动配置是放大了的策略加工厂

“用哪个数据源、哪个 JSON 库、哪个 Web 服务器”，都是同一件事的不同做法。Spring Boot 的做法是每种做法一个配置类，用条件注解（类路径上有没有某个类、你有没有自己定义）决定哪个生效。你自己声明一个同类型的 Bean，默认的那个就让位。自动配置那页讲过它怎么挑。

自测

1. 用一句话说出这一页的精华

设计模式是同一个手法的几种样子：找出会变的那一块，做成对象，让不变的骨架去调它；所以先问什么在变，再选模式，没有变化点就不用。

2. “接着加 else if”和“复制一份 V2”各疼在哪？

接着加 else if，新分支的位置就是执行顺序，没人明确决定过；每次都要改同一个大方法、重测全部。复制一份，同一个逻辑有两处，修错要改两遍，漏一处就是一个隐藏的入口。

3. 坑 3（策略类里放成员变量）的根源是哪一条？

规则类是 Spring 的单例 Bean，所有请求线程共用同一个对象，成员变量就成了并发读写的共享数据。所以状态要放在参数和返回值里。

4. 预测：有人觉得 AbstractRule.apply() 里“不许减成负数”多余，在自己的规则类里重写了 apply()。能编译过吗？如果骨架方法没标 final 呢？

编译不过，apply() 是 final 的。如果没标 final，能编译过，这条规则就绕开了封顶和记账：5 元的订单用一张 10 元现金券会算出负 5 元，明细里也没有这一笔。模板方法的骨架标 final，就是为了让“每条规则都必须遵守的事”不掌握在子类手里。AbstractPlatformTransactionManager.getTransaction() 标 final 是同一个道理。

5. 预测：给 PricingChain.quote() 加了 @Cacheable。同一个类里另一个方法 quoteAll() 循环调 this.quote()。缓存会生效吗？从 Controller 直接调 quote() 呢？

循环里的不生效，this 是真身，缓存逻辑在代理里。从 Controller 调的生效，因为 Controller 拿到的是 Spring 注入的代理。要让循环里的也走缓存，把 quote() 留在这个 Bean，quoteAll() 挪到另一个 Bean 里去调它。

6. 放回全景：第 7 站前后各是什么？如果这一站没拆，还是在 if/else 里加满减，后面哪几站会变难？

前面是第 6 站的 ADR-0008（用策略类），后面是第 8 站写方案、第 10 站落地。不拆的话：第 8 站的方案里写不出“加活动只动营销模块的一个类”；第 10 站“先搬后改”没法分两步，搬和加搅在一个大方法里，金额差 1 分钱时分不清是哪一半的错；以后每个大促加活动，都要重新回归全部 7 种券。
