让一个组都这样做：技术领导的规范、Code Review、带人

前八页讲的是一个人怎么把事做对。带一个组，产出不再是你自己写的代码，而是整个组写出来的代码。能用的杠杆有三根，做的是同一件事：把你脑子里的判断，变成不依赖你在场的东西。规范把反复做的决定变成默认值，能让机器查的就让机器查。Code Review 让每次改动都有第二个人看懂，顺便把标准传过去。带人是把你会的变成别人会的。本机实测：把五条合并请求的约定写成检查，三个样例里一个通过，另外两个在评审人打开之前就被挑出了 7 个问题。

①什么时候用得上：全景第 9、10 站

12.12 的改造，方案是小林一个人想的。落地时来了两个新同事，小吴和小郑，各分了几种券去搬。在全景第 9、10 站，这一步要解决的是：小林知道“先搬后改、测试不许动、表结构单独提”，怎么让另外两个人也这样做，而且不靠他每天盯着。

全景里的约定每个 PR ≤ 400 行一个工作日内有人看完；AI 写的一样走评审
周三收到的1418 行，一个 PR搬和加混在一起，特征测试的期望值被改了
小林的时间还是每天 8 小时组从 1 个人变成 3 个人，他不能把每行代码都重写一遍

不带人也用得上。你是组里被评审的人、评审别人的人、被带的人，这一页讲的是这三件事为什么要这样做，以及怎么判断你所在的组做得好不好。

②常见笨办法

做法疼在哪
“他们写得不行，我自己来更快”这一次确实快。但只有你懂这段代码，你休假它就没人敢动；另外两个人一直学不会，下次还是你来
写一份 80 页的开发规范没人读完。评审时每个人按自己记得的那几条执行，同样的写法今天被打回、明天被放过
评审就是点个“看起来没问题”1418 行，十分钟通过。评审这道关还在，但已经不拦东西了
评审时逐行挑风格，一个 PR 来回五轮三天都在争括号和命名，没人问“算价超时了怎么办”。写代码的人开始躲评审
出了事才教：“这个我不是说过吗”说过一次的事，对方未必知道为什么。下次换个样子，他照样踩
大事小事都要你点头你成了全组的瓶颈。你开一天会，三个人等一天

六种做法是同一个毛病：判断只在一个人脑子里。要么这个人亲自做，要么亲自盯，要么事后亲自纠正。人一多，他就不够用了。

不懂这一点时的典型误用：把“技术领导”理解成“技术最好的人，继续写最难的代码，另外兼着审批”。半年后他比以前更累，组的产出没涨，其他人的水平也没涨。

③工具和路线

杠杆工具管什么
规范自动检查：格式化、静态检查、架构规则、本系列那几个 Lint机器查得了的，一条都不留给人
模板和清单：PR 模板、方案八节、评审清单机器查不了、但每次都该想到的
文字约定：命名、分层、每条带一句“防什么”要靠判断的；数量越少越好
Code Review小 PR + 一个工作日内回复让评审真的看得完，也让写的人愿意拆小
评论分级：必须、建议、疑问；风格问题加个“小事”前缀让作者知道哪些不改不能合
结对：两个人一起写难的、新人不熟的部分，评审提前到写的时候
带人委派阶梯：从“我做你看”到“你做，不用告诉我”一件事放手到什么程度
具体的反馈：什么情况、做了什么、造成什么让对方知道下次该怎么做
让他讲一遍检验是真懂了，还是点头了

选择规则：一条约定，先问能不能让机器查；不能，问能不能进模板或清单；还不能，才写成文字，并且写上理由。评审先把“小”和“快”做到，别的才谈得上。带人按人、按事分别定放手的程度。本页学标蓝的三样。

④背后的机制：把一个人的判断，变成不依赖这个人的东西

先知道这些
  • 巴士因子：一段代码、一件事，有几个人懂。等于 1 的时候，这个人请假，事情就停。
  • PR：合并请求，一次提交评审的改动。有的地方叫 MR 或 CL，是一回事。
  • 委派：把一件事交给别人做，同时说清做到什么程度要回来找你。

三根杠杆，同一个机制

三条路的成本和可靠程度不一样。机器最便宜、最不会忘，但只查得了形式。第二个人能判断内容，但他得有时间、得看得完。让对方自己会最慢，可只有这一条能应付规范里没写到的新情况。所以顺序是：能交给机器的先交给机器，把人的注意力省下来，用在只有人做得了的事上。

规范：把反复做的决定变成默认值

规范的用处不是“统一”，是省掉重复的决定和重复的争论。括号放哪、重构能不能改测试，这类事每次都争一遍，没有任何产出。定下来，写进工具，以后再也不用想。反过来，规范也有成本：每多一条，新人要多记一条，评审要多看一条。所以只收两种：出过事的，和反复争过的。每条都带上它防的是什么，没人说得出防什么的，删掉。

Code Review：不只是找错

它实际在做的四件事

拦错：有用，但别指望太多，逐行读能发现的问题有限，这是测试的主场。让第二个人懂：这段代码以后有两个人能改，巴士因子从 1 变成 2。对齐标准：什么算“够好”，在一次次评审里变成共识。教：对新人，评审意见是最贴身的教材。后三件，测试替代不了。

先看什么，后看什么

Google 的评审指南把要看的东西排了序，第一条是设计：这个改动该不该做、放的地方对不对。然后是功能对不对、是不是太复杂（“读的人不能很快看懂”就算太复杂）、测试、命名、注释。风格放最后，并且说照规范就行，规范没写的属于个人偏好，评论前加个“小事”的前缀。它还专门有一条：看到做得好的地方要说出来。

评审有两个硬条件，缺一个就走样。小：一次要看的改动得是一个人坐下来一口气看得完的。快：Google 的指南写的是，回复一个评审请求最长不超过一个工作日；理由是评审慢了，整个组的速度下降，写代码的人开始抵触评审，代码质量也受影响。这两个条件互相咬着，下面的实验台就是算这个。

实验台：评审多久回，决定了 PR 有多大

先猜：组里约定“每个 PR 不超过 400 行”。但评审的人都忙，平均要等 3 个工作日才回。三个月后，PR 的大小会怎样？

估算模型：几个 PR 一个接一个提，每个都要等一轮评审；一天按 8 个工作小时算。每个 PR 不超过 400 行算“看得完”，不超过 1000 行算“只能扫一眼”，再多算“基本是盖章”。这几个门槛是交易靶场的约定，不是研究结论；想说明的只是等待时间怎么随拆分变化。

带人：一件事放手到第几级

两种常见的错在阶梯的两头。一直停在第 1 级，是 ② 的“我自己来更快”。从第 1 级直接跳到第 5 级，是“这个你负责”然后不管了，对方不知道哪些事该回来问，周三收到的那个 1418 行的 PR 就是这么来的。交代一件事时，把放手到第几级说出口：“你来做，写完方案先给我看，再动手”。

挑什么活给他，也有讲究：比他现在会的难一点，够得着，但要踮脚。太容易学不到东西，太难只会让他卡住、最后还是你来收尾。反馈要具体到一次行为：不说“你的 PR 质量要提高”，说“周三那个 PR，搬和加放在了一起，我看了 40 分钟还分不清哪些行为变了；下次先提只搬的那一半”。前一句他不知道明天该做什么，后一句知道。

为什么这样设计

选中的：把判断搬到人外面去

搬进工具，搬进第二个人的脑子，搬成对方自己的能力。你不在场，事情照常；你在场，时间花在新的、还没人会的问题上。

被放弃的：最强的人自己顶上

每一次都是最快的选择。输在：他的时间不会随着组变大而变多，组的产出被他一个人的上限卡住；别人的能力不涨，他就永远脱不开身。

决定胜负的约束：一个人每天只有 8 小时，而判断不传出去，就得每次亲自到场。代价是眼前慢：教一个人搬第一种券，比自己把 7 种全搬完花的时间还多。回本在后面，和上上页的技术债一个算法：这件事以后还要做多少次。

最少的写法

PR 描述模板
标题: refactor: / feat: / fix: 做了什么

## 背景
为什么改。对应哪条 ADR、哪个需求。

## 怎么验证
跑了什么，结果是什么。
重构写：哪些测试没动、全部通过。

## 回滚
出了问题怎么回去。

# 约定（由 PrCheck 检查）
# - 非测试代码不超过 400 行
# - refactor 不改测试文件、不夹带行为变化
# - feat 不改已有的特征测试
# - 表结构变更单独提
评审意见：差的和好的
✗ 这里写得不对。
✓ [必须] 这里把向下取整改成了四舍五入。
  特征测试红了 10 组，说明老行为变了。
  这次先原样搬；要修，另提一个，找财务确认。

✗ 你怎么又把迁移脚本和代码放一起了？
✓ [必须] 迁移脚本请单独提、先上线。
  滚动发布那几分钟老代码还在跑，
  新列和用新列的代码同时上，回滚会很难。

✗ 变量名不好。
✓ [小事] d 改成 discountShare 会更好读，
  不改也行。

✓ 这个 order() 用常量写明了顺序，很清楚。

细节先不讲：规范怎么改、怎么废，评审里起了争执怎么办，怎么看一个组带得好不好，放到第 ⑥ 步。

⑥刻意练习：坑、规范和更深的一层

第一圈 · 不知道就会出事的

1“我自己来更快”← ④ 一个人每天只有 8 小时
现象
难的都是小林写。他请一周假，算价模块出了问题，没人敢改，等他回来。
根源
每次都选眼前最快的，判断始终没有传出去。巴士因子一直是 1。
做法
每个模块至少两个人改过。难的活和别人结对做，键盘在对方手里。自己写的也照常提给别人评审。
2规范只在文档里实测← ④ 能往上挪一层就挪
现象
“重构不许改测试”写在规范第 37 页。pr-103 的作者没读到，评审的人那天也没想起来。
根源
靠人记得的规则，在最忙的时候最先被忘掉，而最忙的时候最容易出事。
做法
写成检查放进流水线（⑤ 的 PrCheck）。写不成检查的，进模板或清单。
3评审盖章← ④ 小和快互相咬着
现象
1418 行，十分钟后一句“看起来没问题”。
根源
改动大到看不完，评审的人只剩两个选择：卡住它，或者放过它。大多数人选后者。
做法
超过约定大小的直接请作者拆，不用逐行看。评审人至少写出一句“我确认了什么”，比如“特征测试没动、全绿”。
4评审变成挑风格、对人不对事← ④ 先设计，风格放最后
现象
20 条评论，18 条是空格和命名，语气是“你怎么又……”。作者改了三轮，开始尽量绕开这位评审人。
根源
风格谁都能挑，设计要动脑子；没有分级，作者分不清哪些是必须改的。
做法
风格交给格式化工具。评论写“这段代码怎样”，不写“你怎样”；标上必须、建议、小事；看到好的地方说出来。
5评审慢，PR 就变大估算← ④ 一个工作日
现象
约定是 400 行，实际的 PR 越来越大。问起来：“拆成三个要等九天，一个只等三天。”
根源
拆小的代价是多等几轮评审。评审慢，这个代价就大到没人愿意付。
做法
把“一个工作日内回复”当成和“不超过 400 行”同等的约定，并且带头做到。来不及细看，先回一句大方向的意见。
6要么不放手，要么一步放到底← ④ 委派阶梯
现象
“这个你负责”，然后三天没问。第四天收到一个方向就不对的大 PR，只能重来。
根源
没有说清哪一步要回来对一下。对方不知道该问，你以为他会问。
做法
交代时说出级别和第一个检查点：“你来做，动手前先把要拆成哪几个 PR 发我看一眼。”
7反馈含糊，或者只在出事后才给← ④ 具体到一次行为
现象
“代码质量要再提高一点。”“多想想边界情况。”对方点头，下次一样。
根源
没有指向任何一次具体的行为，对方不知道哪里不对、下次该怎么做。
做法
当天说，说那一次：什么情况、他做了什么、造成了什么、下次可以怎么做。做得好的也这样说。
8所有决定都等你点头← ④ 判断只在一个人脑子里
现象
小林开了一天会。小吴的 PR 等了一天，小郑的技术选型等了一天。
根源
没有说清哪些事不用问。于是所有事都来问。
做法
按“好不好改”分：好改的自己定，事后说一声；难改的写 ADR，大家一起评。评审不指定非你不可，谁有空谁看。

第二圈 · 团队里该怎么做

  • 能让机器查的约定，不留给人：防最忙的时候被忘掉。
  • 每条约定带一句“防什么”，说不出的删掉：防规范只增不减。
  • PR 小到一口气看得完，评审一个工作日内回：两条一起定，防盖章，也防 PR 越攒越大。
  • 评论分级，说代码不说人，好的也说：防评审变成挑刺。
  • 每个模块至少两个人改过：防巴士因子为 1。
  • 交代任务时说出放手到第几级、第一个检查点在哪：防不放手，也防放过头。
  • 反馈当天给，指向一次具体的行为：防对方不知道明天该怎么做。

第三圈 · 深一层

规范怎么改、怎么废

规范和 ADR 一样，是在某组约束下做的决定。“PR 不超过 400 行”定的时候，评审靠人逐行读；哪天大部分机械改动由工具生成、由测试验证，这个数就该重新看。做法也一样：每条有主人，有“防什么”，有人觉得不合理就提出来改，而不是悄悄绕过。被绕过的规范比没有规范更糟，它让别的规范也显得可以不遵守。

评审时意见不一致

先分清是哪一种。有规范或者 ADR 的，照它来，不服的去改规范。属于个人偏好的，听作者的。真是设计上的分歧，别在评论里来回十轮，当面聊十分钟，把结论写回评论里。Google 的指南有一条底线可以借用：这个改动只要确实让代码整体变好了，哪怕不完美，就该让它过；不要为了“更好”把“好”卡在门外。

出了事，对事不对人

pr-103 如果没被拦住、上了线，复盘时问“小吴为什么改测试”得不到有用的东西，他只会下次更不敢说。该问的是：为什么改测试这件事能通过评审，流水线为什么没拦。答案是加一条检查。只有当说出“是我弄错的”不会带来惩罚时，问题才会被早早说出来，评审和待定问题清单才不会变成走过场。

怎么知道带得好不好

别数代码行数和 PR 个数，会把人往错的方向引。看这几样：评审请求平均等多久；PR 的中位数大小；每个模块有几个人改过；同一类问题在评审里出现的次数是不是在减少。还有一个最直接的检验：你休一周假，回来时事情是不是照常在走。

自测

1. 用一句话说出这一页的精华

带一个组，产出是整个组的代码；规范、Code Review、带人做的是同一件事：把一个人脑子里的判断变成不依赖他在场的东西，能交给机器的先交给机器，再靠第二个人，最后变成对方自己的能力。

2. “我自己来更快”和“80 页规范”各疼在哪？

自己来，这一次快，但判断没传出去，只有你懂，别人不长，组的产出被你一个人卡住。80 页规范没人读完，执行靠每个人的记忆，同样的写法今天被打回、明天被放过。

3. 坑 5（评审慢，PR 变大）的根源是 ④ 的哪一条？

评审的两个条件，小和快，互相咬着。拆小的代价是多等几轮评审，评审慢，这个代价就大到没人愿意付，于是大家攒成一个大的提。

4. 预测：组里把“一个工作日内回复评审”做到了，但没有任何自动检查，约定全靠评审人把关。半年后最可能出什么问题？

评审人的时间被形式问题吃掉：每个 PR 都要人去看描述全不全、大小超没超、重构有没有动测试。看得多了就开始漏，漏得最多的是最忙的那几周。评论里也全是这类问题，设计和正确性反而没人顾得上，作者觉得评审就是挑格式。⑤ 里那 7 个问题如果都要小林自己发现、自己写评论，他那天两个小时不够。

5. 预测：小吴搬规则类已经很熟了（第 4 级）。小林让他负责下个活动的数据库表结构变更，说了句“这个你也负责”。会发生什么？该怎么交代？

小吴会按“搬规则类”那件事的放手程度去做：自己写完、自己提。可表结构变更他没做过，不知道要先扩展后收缩、不知道迁移脚本要单独提先上线，多半又是一个混在一起的大 PR，或者更糟，上线时新旧版本互相看不懂。放手的程度是跟着事走的。该这样交代：“表结构你来做。这件事你是第一次，我们先结对把方案写出来，脚本你写，提之前我看一遍。”

6. 放回全景：第 9、10 站各用到了这一页的什么？把整个全景的十站再看一遍，哪些站的产出后来变成了“不依赖某个人的东西”？

第 9 站用的是评审怎么组织：提前发、点名、按风险排议程、散会前有结论和负责人。第 10 站用的是小 PR、一个工作日内评审、AI 写的也走评审。回头看十站：规则表和算例（第 1、2 站）变成了测试；特征测试（第 3 站）变成了每次重构的验收；上下文边界（第 4、5 站）变成了 verify()；三个决定（第 6 站）变成了 ADR；方案（第 8 站）变成了八节的模板和检查；落地的做法（第 10 站）变成了 PrCheck。小林一个人想清楚的东西，到这一站都不再只在他脑子里。

档位：标准。本机跑过（2 核 ARM 虚拟机，OpenJDK 17.0.21）：PrCheck 检查三个样例合并请求，⑤ 的输出是这次运行的原样。实验台是估算模型，在 node 里跑过。人物、日期、400 行和各级“看得完”的门槛是交易靶场的设计。

按文档（已核对原文）：Google Engineering Practices 评审指南。要看的方面按顺序是设计、功能、复杂度、测试、命名、注释、风格、一致性、文档等，并说评审里最重要的是改动的整体设计；“太复杂”通常指读代码的人不能很快看懂；规范没规定的风格偏好，评论前加 “Nit:”；告诉开发者哪里做得好，有时对带人更有价值。回复一个评审请求最长不超过一个工作日；评审慢了，团队整体速度下降、开发者开始抵触评审、代码健康受影响；正在专注做事时不要为评审打断自己；改动太大时请开发者拆成几个小的。一个改动只要确实改善了整体代码健康就应倾向通过。没有逐句核对：委派的分级、“够得着但要踮脚”的任务难度、对事不对人的事故复盘，是通行的说法，没有引哪一处原文。
