它写得很快，你得知道哪里不能信：AI 辅助研发

AI 助手读得快、写得快，通用知识比谁都多。它不知道的是你这个系统里没写下来的事，它给出的是看起来最合理的，不是验证过的，它也不为结果负责。所以用好它是三件事：把它不知道的喂给它（规则表、算例、ADR）；用不是它自己出的题去验（签字的算例、老代码的特征测试、每个入口都跑一遍）；提交的人照常对这段代码负责。本机实测：四份有错的满减实现，各自带的 12 个测试全部通过；换成三种独立的验收，四份全被拦下。

①什么时候用得上：全景第 3、10 站

全景里 AI 助手出场两次。在第 3、10 站，这一步要解决的是：哪些活可以交给它，交出去时要带上什么，拿回来时凭什么信。

第 3 站 · 读老代码列出 6 处，漏 1 处漏的是消息队列回调进来的那个退款补偿，没有任何代码调用它
第 10 站 · 写满减规则测试全绿实现和测试出自同一个理解，理解错了，会一起错、一起通过
不变的一条提交的人负责线上出了错，值班、赔钱、复盘的是你

②常见笨办法

做法疼在哪
一句话交代：“在算价里加一个满 300 减 40”这和运营在周会上说的那句话一模一样，是压缩过的。先减哪个、门槛看哪个金额，它会用最常见的做法补上，不会来问你
看着像那么回事，就合了它写的代码整洁、有注释、有测试，比很多人写的都像样。“像样”和“对”是两回事
让它写实现，再让它写测试，测试绿了就算验过自己出题自己答。⑤ 里四份错的实现，自测都是 12/12
把它当搜索引擎：“这个参数的默认值是多少”它会给一个很确定的答案，版本不对或者干脆是编的，语气都一样
因为出过一次错，就不用了读老代码、补特征测试、机械地搬代码、起草文档，这些又苦又适合它的活，全留给了自己

缺的是三样：它不知道的上下文，不是它自己出的验收题，没有被稀释的责任。

不懂这一点时的典型误用：出了问题说“这段是 AI 生成的”。这句话在复盘会上没有任何意义：它不值班，不赔钱，也不会因此下次写得更小心。合并请求上是谁的名字，就是谁写的。

③工具和路线

这类活交给它合适吗拿回来怎么验
读老代码：梳理调用关系、列出所有入口合适，它读得快全仓库文本搜索再核一遍；重点找不在调用链上的入口
给老代码补特征测试很合适：输入由你定，期望值由老代码自己吐测试是不是只断言输入输出；有没有覆盖边界金额
只搬不改：把 if 分支搬成规则类合适，机械、量大特征测试一个不改、全绿；测试文件没被它动过
写新规则的实现可以，但规则表和算例要先给它签字的算例，不是它自己写的测试
起草 ADR、方案、评审意见合适当初稿、当第一轮评审约束和“输在哪”是不是你系统的事实，还是通用的套话
定业务口径：先减哪个、超时怎么办不合适这不是它能知道的事，要业务方定
划边界、做难改的决定可以让它列候选、挑毛病，不能让它定决定写成 ADR，由人署名
回答事实：默认值、版本行为可以当线索查官方文档或源码，或者直接跑一下

选择规则：看这件事的“对错标准”在哪。标准在仓库里、能自动跑（编译、测试、搜索）的，放心交。标准在某个人脑子里的（业务口径、取舍），先把标准问出来、写下来，再交。本页学标蓝的四类，正好是全景第 3、10 站用到的。

④背后的机制：它知道什么，它给的是什么，谁来兜底

先知道这些
  • 上下文：这一次对话里它能看到的全部东西：你的话、它读过的文件、命令的输出。窗口有限，而且不同的会话之间不共享。
  • 它怎么干活：模型提议下一步（读文件、改代码、跑命令），外面的程序去执行，结果送回来，再提议下一步。详见 用 AI 编程工具干活。
  • 特征测试、签字的算例：前面两页的产出。特征测试钉住老行为，算例是业务方点过头的对错标准。

它知道的只有两样：通用知识，和你这次给它的

这和第一页讲的是同一件事。业务方的一句话是压缩过的，开发用自己的默认值解压；你给 AI 的一句话也是压缩过的，它用通用知识里最常见的做法解压。区别只在于：开发还会觉得“这里好像该问一下”，它通常不问，直接给你一个完整、自信的答案。

它给的是“最合理的”，不是“和你的系统一致的”

上一页的那颗雷，在这里几乎一定会踩：让它搬折扣券的代码，它很可能顺手把 total * pct / 100 写成四舍五入，甚至在说明里告诉你“顺便修正了一个精度问题”。从通用知识看，它是对的。从你的系统看，13% 的订单金额变了。它的“合理”来自所有它见过的代码，你的系统只是其中很不典型的一个。所以不能问“它写得合不合理”，要问“和我这里现有的行为、定好的规则一不一样”，而这个问题只有测试能答。

验收要用不是它自己出的题

实验台：你开了哪几道关，四种错各漏过去几种

先猜：AI 助手交回了满减规则的实现和 12 个测试。编译通过，12 个测试全绿。下面四种典型的错里，这两道关能拦住几种？

点按钮开关每一道关。哪道关拦哪种错，前四列和 ⑤ 的实测输出一致；双跑那一列按上一页的结果填（顺手改舍入，一万笔里差 1298 笔）。人评审没放进来：它拦得住什么，取决于改动有多大、评审的人手里有没有规则表，不是一个确定的开关。

责任不会跟着代码一起生成

代码可以让它写，这三件事转不出去。决定：先减哪个、要不要快照，是业务方和 ADR 署名的人定的。验收：拿什么判断对，是你选的；它过了你选的关，才算过。后果：上线后出错，查的是合并请求上的名字。所以团队里对 AI 产出的要求和对人的一样，甚至该更严一点：一样走评审，一样要有测试，改动一样要小到评审的人看得完。它一次能写 2000 行，不等于一次该合 2000 行。

为什么这样设计

选中的：人定目标和验收，它来做，独立的关卡验，人负责

把它的长处（快、不嫌烦、读得多）用在标准明确的活上。它不知道的事由写下来的东西补，它会错的地方由不是它出的题拦。责任链条和没有它的时候一样清楚。

被放弃的：它写、它测、它评审，绿了自动合

最省人。输在：同一个理解上的错，会在每一道它自己把的关上都亮绿灯。⑤ 里的 12/12 就是这样来的。出了事也没有人能回答“当时为什么觉得这是对的”。

决定胜负的约束：它不知道没写下来的事，而写代码的成本降到接近零以后，贵的变成了验证。所以值得投入的是两头：把上下文写下来，把验收做成能自动跑的。代价是你得先有规则表、算例和测试，这些东西它替你写不出来，或者说，它写出来的你还得找业务方签字。

⑤跟着做一遍：全景里的两个任务

任务一：让它列出所有碰优惠金额的入口，再自己核一遍

样例工程里有 7 个入口。从接口、定时任务这些“看得见的起点”顺着调用往下找，能到前 6 个。第 7 个是消息队列回调进来的退款补偿，没有任何代码调用它。核的办法很土：全仓库搜字段名。

任务二：让它写满减规则，用不是它出的题验

下面四份有错的实现是手写的，模拟 AI 助手在任务说明不清楚时常见的四种产出，不是某个模型的真实输出。每一份都带着按自己的理解写的 12 个测试。

⑤AcceptanceGate.java：四份实现（节选）
// A：满减加在了券后面
long p = t * pct / 100;
return promo && t >= 300_00 ? p - 40_00 : p;

// B：顺序对了，门槛拿折后金额比
return promo && t * pct / 100 >= 300_00
    ? (t - 40_00) * pct / 100 : t * pct / 100;

// C：逻辑全对，顺手改了舍入
return ((promo && t >= 300_00 ? t - 40_00 : t)
    * pct + 50) / 100;

// D：下单入口全对；退款补偿入口没人告诉它
refundLine(...) { return cart[line] * pct / 100; }
三种独立的验收
// 1 签字的算例，走下单入口
c.pay(ORDER_1024, true, 90) == 324_00   // E3
c.pay({200_00, 100_00}, true, 90)
                            == 234_00   // E5

// 2 特征测试：不参加满减时和老代码一分不差
c.pay({t}, false, pct) == legacyPay(t, pct)

// 3 同一个算例，走退款补偿入口
c.refundLine(ORDER_1024, true, 90, 1)
                            == 104_49   // E6

// 运行（JDK 17）：
mvn -q -pl design/ai-assisted-dev compile exec:java \
 -Dexec.mainClass=labs.design.ai_assisted_dev.AcceptanceGate

看懂这次运行
  • 第一列全是 12/12。这一列的期望值是每份实现按自己的理解算的，它只能说明“没有自相矛盾”。只看这一列，五份分不出高下。
  • 四种错，各被不同的关拦住：A、B 被算例拦住（B 只有踩在门槛上的 E5 拦得住）；C 的算例全过，因为签字的那几个金额恰好都除得尽，只有特征测试看得出来；D 前两关全过，只有把算例拿到退款入口去跑才现形。

到这里已经能交差了：读代码让它找、用搜索核；写代码先给规则表和算例，用算例、特征测试、逐入口三道关验；合并照常走评审。已知还没处理的细节：每次都要重新交代背景（项目说明文件）；它编出不存在的方法和参数（坑 4）；什么不能贴给它（坑 6）；一次改太多（坑 5）。

⑥刻意练习：坑、规范和更深的一层

第一圈 · 不知道就会出事的

1一句话交代任务← ④ 它用通用知识里最常见的做法补空
现象
“加个满减”，它把 if 加在券后面。和周会上小林的第一反应一样，只是它更快。
根源
顺序、门槛、舍入这些规则没在它的上下文里。它不会停下来问，会挑最常见的写法。
做法
任务说明写齐五样：目标、上下文（指给它读哪些文件）、约束、验收、输出格式。加一句“拿不准的业务规则列成问题，不要猜”。
2自己出题自己答实测← ④ 验收要用不是它出的题
现象
⑤ 的第一列：四份错的实现，自测全是 12/12。合并请求里“新增 12 个测试，全部通过”，看着很踏实。
根源
实现和测试来自同一个理解。测试验证的是“代码和这个理解一致”，不是“这个理解对”。
做法
期望值从它够不着的地方来：业务方签字的算例，老代码的实际输出。可以让它把算例写成测试代码，数字必须是你给的。
3它顺手“改正”了老行为实测← ④ 合理不等于和你的系统一致
现象
⑤ 的 C：算例全过，特征测试红 10 组。它的说明里可能还写着“修正了舍入精度”，读的人会觉得赚到了。
根源
它按所有见过的代码判断什么是对的。你系统里那个别人已经依赖的“错”，在它看来就是该修的。
做法
约束里写明“不改任何现有行为，包括你认为有问题的；发现了列出来”。搬代码的任务，测试文件不许它动。
4它说得很确定，其实是编的← ④ 看起来最合理的
现象
它用了一个名字很合理、但这个版本里并不存在的方法或配置项。或者告诉你某个默认值是多少，说的是三个大版本以前的。
根源
它生成的是“这里最可能出现什么”。真的 API 和编的 API，对它来说只是可能性高低不同，语气上没有区别。
做法
让它能自己编译、跑测试，错的 API 当场就红。事实类的结论，查官方文档、源码，或者写三行代码跑一下。
5一次交回来 2000 行← ④ 改动要小到评审的人看得完
现象
一个下午它把“搬”和“加”全做完了，一个合并请求，40 个文件。评审的人翻了翻，点了通过。
根源
写的速度变成原来的十倍，读的速度没变。瓶颈从写挪到了评审，而评审被绕过去了。
做法
让它先出计划，按上一页的小步拆：一种券一次提交，搬和加分两批。每批小到一个人十几分钟看得完。
6把不该出门的东西贴给了它← ④ 你给它的都进了上下文
现象
为了让它查问题，把带着数据库密码的配置、带手机号的线上日志整段贴进去。或者给了它能连生产库的终端。
根源
贴进去的内容离开了你的机器；它能执行的命令，就是它能造成的后果的范围。
做法
密钥和个人数据先脱敏；给它的环境只连测试库；会删数据、会推代码、会发布的命令，保留人工确认。公司对用哪些工具、哪些代码能给，有规定的按规定。
7它只改了它看到的那个入口实测← ④ 没给它的，它不知道
现象
⑤ 的 D：下单全对，退款补偿还是老逻辑，一笔多退 11.61 元。grep 一下就能看到的第 7 个入口，没人让它看。
根源
它顺着你指的地方往下读。不在那条线上的代码，等于不存在。
做法
动手前先做任务一：让它列入口，用全文搜索核，把完整清单写进任务说明。验收时每个入口都跑一遍算例。

第二圈 · 团队里该怎么做

  • AI 的产出和人的一样走评审、一样要测试：防“它写的应该没问题”。
  • 验收用签字的算例和特征测试，期望值不由它定：防自己出题自己答。
  • 规则表、算例、ADR 放在仓库里，任务说明里指给它读：防它用通用做法补空。
  • 先计划后动手，小步提交：防一次交回来没人看得完的改动。
  • 搬代码时不许它改测试文件：防它为了让测试通过去改测试。
  • 密钥、个人数据不进对话，危险命令人工确认：防泄露和误操作。
  • 合并请求署谁的名，谁负责；用了 AI 如实注明：防责任被稀释，也让评审的人知道该多看哪里。

第三圈 · 深一层

给项目写一份常驻的说明文件

每次新会话它都不记得上一次。多数编码助手会在开工时自动读仓库里一个约定好的说明文件（比如 Claude Code 读 CLAUDE.md）。里面只放它每次都需要、又猜不到的：怎么构建和跑测试；模块边界（“ordering 包不许 import 营销的类”）；不许动的地方；规则表和 ADR 在哪。写短一点，写成它能照着做的话。这份文件对新来的同事同样有用。

让它自己看到红

最有效的一招是把验收交到它手里：让它能自己跑编译、跑 ExampleTable、跑特征测试。它提议改动、执行、看到失败、再改，这个循环转起来以后，④ 的前四道关在它交回来之前就已经过了。你要盯的只有一件事：它是把代码改对了，还是把测试改松了。

让它当第一轮评审人

把方案文档和上上页的评审清单一起给它，让它按清单逐项挑。它擅长发现缺了什么：没写回滚、没提老数据、风险表少一列。它不擅长判断业务口径对不对。把它挑出来的当成“会前批注”的一部分，人的评审时间留给它判断不了的那些。

它改变了什么，没改变什么

变了的：写样板、读陌生代码、补测试的成本大幅下降，所以“没时间补测试”不再成立。没变的：需求要问清、边界要划对、决定要有人做、上线要有人负责。前七页讲的东西，没有一样因为它而过时；反过来，规则表、算例、ADR、特征测试这些以前“有空再做”的东西，现在成了能不能把它用起来的前提。

  • 怎么评估它在你的仓库上靠不靠谱：攒一小组做过的真实任务当回归题（接 AI 地图的评测那一站）。

  • 团队层面：新人怎么带，才不至于只会让它写、自己读不懂（下一页）。

自测

1. 用一句话说出这一页的精华

AI 助手不知道你系统里没写下来的事，给的是看起来最合理的而不是验证过的，也不为结果负责；所以要把上下文写下来给它，用不是它自己出的题验收，提交的人照常负责。

2. “一句话交代”和“它写实现它写测试”各疼在哪？

一句话是压缩过的，它用通用知识里最常见的做法补空，而且不会来问。它写实现再写测试，两者出自同一个理解，理解错了会一起错、一起通过，测试全绿没有信息量。

3. 坑 3（顺手改正老行为）的根源是 ④ 的哪一条？

它给的是“最合理的”，判断依据是它见过的所有代码。你系统里别人已经依赖的那个老毛病，在它看来就是该修的错。只有老代码的特征测试能发现这种改动。

4. 预测：你只有签字的算例，没有特征测试。⑤ 的四种错里，哪一种会一路通过、直到上线？它最先被谁发现？

C，顺手修了舍入。签字的算例金额都除得尽，五个全过；评审的人看到四舍五入，只会觉得改得好。上线后 13% 的折扣券订单和支付流水差 1 分，最先发现的是对账系统或者财务，不是任何技术告警。如果连“退款入口也跑一遍算例”都没做，D 也会过，最先发现的是客服。

5. 预测：让它“把 calcPrice 搬成规则类，保证特征测试全过”。它交回来说全过了。你最该先看合并请求里的哪个文件？

测试文件有没有被改。让测试通过有两条路：把代码改对，或者把测试改松（改期望值、删掉失败的那几组、把断言换成更宽的）。它不是故意作弊，只是“让测试通过”这个目标两条路都能达到。所以搬代码的任务要写明测试文件不许动，评审时先看这一条。

6. 放回全景：第 3 站和第 10 站，AI 助手各做了什么、各靠什么校验？如果前面几站没有产出规则表和算例，第 10 站用 AI 会怎样？

第 3 站它梳理入口，靠全仓库搜索核出漏掉的第 7 处；第 10 站它搬代码、写规则，靠 23 个特征测试和第 2 站的算例验收，再走评审。没有规则表和算例的话，第 10 站给它的只能是那句话，它会像 ⑤ 的 A、B 那样用默认值补空；拿回来以后，手里也没有任何不是它出的题可以验，只剩“看着像不像”。它越快，这个缺口暴露得越快。

档位：标准。本机跑过（2 核 ARM 虚拟机，OpenJDK 17.0.21）：AcceptanceGate 和 grep，⑤ 的两段输出来自这次运行。四份有错的实现是手写的，模拟任务说明不清时常见的四种产出，不是某个模型的真实输出；“AI 列出 6 处、漏第 7 处”是交易靶场的设计，实测的只是全文搜索确实能找到第 7 处。本页没有调用任何模型做实验。实验台的拦截关系在 node 里跑过，和 ⑤ 的输出一致。

关于工具的说法是写这一页时的一般情况：这类助手按“提议、执行、看结果、再提议”的循环工作；每个会话的上下文互不共享；Claude Code 会读仓库里的 CLAUDE.md。具体到某个工具、某个版本的行为，以它自己的文档为准。
