先把边界守住，再决定拆不拆：单体、模块化、微服务的演进

逻辑上的边界、代码里的边界、部署上的边界，是三样东西。前两样便宜，在一个进程里就能有，改错了是一次重构。第三样贵：多一次网络调用，多一个库，多一套流水线和值班，改错了是一次数据迁移。所以顺序是：先把逻辑边界划对，用工具在代码里守住，等证据出现再加部署边界，并且事先写下什么算证据。本机实测：抢券模块伸手调了算价模块的内部类，Spring Modulith 的 verify() 一次报出两个问题：成环，以及依赖了没公开的类型。

①要解决的问题：全景第 5 站

靶场已经是五个服务。算价属于营销上下文，边界上一页划好了。在全景第 5 站，这一步要解决的是：这条边界落成什么样。三个候选，12 天后就是 12.12。

A · 不动留在订单里继续写在 order-svc 的 calcPrice()，运营每加一种活动都要发订单服务
B · 拆新建 pricing-svc新仓库、流水线、数据库、值班表；下单链路多一跳
C · 模块进 coupon-svc和抢券并列的独立模块；把原来的验券调用换成算价加锁券

②不用它会怎样

做法疼在哪
单体里不分模块，包之间随便调改一处，不知道会坏哪。真到该拆的那天，发现每个类都被别人直接用着，拆不动
一上来就一个功能一个服务边界刚开始多半划不准。划错了，在进程里是改几个包，跨了服务就是迁数据、改接口、几个团队一起排期
“反正以后要拆，现在就拆”多一跳的超时、重试、熔断，多一个库的一致性，多一套运维，从第一天起就要付；好处要等量大了、人多了才有
拆了服务，但共用一个库，或者要按顺序一起发布进程是分开了，谁也不能单独发、单独挂。分布式的成本全付了，独立的好处一样没拿到

缺的是两样：一种在不拆的时候也能守住边界的办法，和一张“出现什么就该走下一步”的清单。

不懂这一点时的典型误用：把“微服务”当成“架构好”的同义词，服务个数当成绩。评审时没人问“这两个服务能不能各发各的”，只问“为什么不再拆细一点”。

③几种流派

形态进程边界靠什么守发布适合
大泥球单体1 个没人守一起几个人的小项目，或者活不过半年的原型
模块化单体1 个构建时检查：模块只能走对方的公开接口一起一个团队，边界还在摸索；大多数系统的大多数时候
分组部署同一份代码，几组实例同上，再加路由规则一起两个模块流量和资源差别大，怕互相拖累
微服务每个服务各一组网络：只有接口够得着各发各的多个团队，要独立发布、独立伸缩
函数、Serverless按调用起网络各发各的事件触发、用量很不均匀的零散任务

选择规则：默认停在模块化单体。出现“资源要隔离、故障要隔离”的证据，先走分组部署。出现“两个团队发布互相排队”的证据，再拆成服务。本页学这三级台阶，以及台阶之间看什么证据。“分组部署”不是一个有标准叫法的模式，指的就是同一个镜像起两组实例、各接各的流量。

④核心取舍：三种边界，便宜的先要，贵的等证据

先知道这些
  • 限界上下文：一个词只有一个意思的范围，上一页讲的。它是逻辑边界，和代码怎么放、部署成几个进程无关。
  • 模块：代码里的一组包，对外只露一小部分。它是编译和构建时的边界。
  • 分布式单体：拆成了多个服务，却必须一起改、一起发布、一起挂。

三种边界不是一回事

边界是什么买到什么要付什么划错了怎么改
逻辑边界限界上下文：营销管规则，订单管事实两拨人各改各的概念一起对语言的时间改图、改名词表
代码边界模块：pricing 包只露 PricingFacade能单独理解、单独测试；越界在构建时就红要有工具守，不能图省事直接调内部类一次重构，IDE 能帮大半
部署边界进程：pricing-svc 自己一组实例、自己的库独立发布、独立伸缩、挂了不连累别人网络一跳（超时、重试、熔断）；跨库一致；接口版本兼容；多一套流水线、监控、值班迁数据、改协议、几个团队一起排期

微服务把三种边界一次全要了。可是前两种不需要第三种就能有。把它们分开看，“要不要拆”就变成一个更小的问题：部署边界买到的那三样东西，现在用得上吗。

四级台阶

什么算“该走下一步”的证据

算证据的

发布排队：两个小组改同一个服务，一个的发布总被另一个卡住。伸缩特征差得远：抢券的峰值是平时的几十倍，算价跟着下单走，比较平。互相拖累：抢券高峰把算价的 P99 拖长了，有监控数字。必须隔离：安全、合规要求某一块单独部署。

不算证据的

“以后总要拆。”“别的公司都是微服务。”“代码太乱了，拆了就干净了。”最后一条最常见：乱是因为没有代码边界，拆成服务只会把乱搬到网络上，先做第 1 级。

全景的 ADR-007 就是照这个写的：现在放进 coupon-svc 的独立模块；出现“抢券高峰把算价 P99 拖过 200 ms，分组部署也压不住”，或者“营销分成两个小组、发布互相排队”，再重新决定。决定里带着推翻它的条件，半年后的人才知道什么时候该动。

实验台：现在该站在第几级

先猜：12.12 之后复盘，抢券高峰那 10 分钟，算价的 P99 从 30 ms 涨到了 400 ms。营销还是一个小组，模块边界 verify() 是过的。下一步最便宜又管用的是什么？

这是一张把 ④ 的判断规则写死的清单，不是测量：有拖累就要资源隔离（第 2 级），多个小组发布排队就要独立发布（第 3 级）；往上走之前，下面的台阶要先站稳。门槛是定性的，真实系统要换成自己的监控数字。

为什么这样设计

选中的：先单体里划模块，有证据再拆

边界先在进程里试。划错了，改几个包、跑一遍测试就回来了。模块守得住，说明边界是真的，以后拆出去搬的是一个接口干净的整体。

被放弃的：一开始就按微服务建

要在最不了解业务的时候，做最难反悔的决定。Martin Fowler 的观察是：成功的微服务大多是从长得太大的单体拆出来的；一开始就按微服务建的，多数遇到了大麻烦；有经验的架构师在熟悉的领域里，一开始也很难把边界划对。

决定胜负的约束：边界一开始划不准，而改部署边界比改代码边界贵得多。所以把贵的决定往后放，放到有证据的时候。代价是：模块化单体里大家仍然一起发布、一起挂，而且边界必须有工具守，靠自觉守不住。

最少的写法：让构建来守模块边界

包结构就是模块声明
coupon-svc
└─ com.lab.coupon            ← 启动类在这
   ├─ coupon                 ← 模块：抢券
   │  ├─ CouponQuery           根包里的 = 公开接口
   │  └─ CouponGrabService

      ├─ PricingFacade         公开
      └─ internal              子包里的 = 内部，
         └─ RuleChain          别的模块不许碰
一个测试，CI 每次都跑

⑤套进场景：coupon-svc 里的两个模块，守得住和守不住

同一份代码放了两遍。good：pricing 通过 coupon 的公开接口 CouponQuery 查券。bad：有人想在抢到券以后顺手提示“现在用能省多少”，图省事在 CouponGrabService 里直接 new 了算价模块的内部类 RuleChain。代码能编译，功能也对。

⑥反例和误用

第一圈 · 不知道就会出事的

1分布式单体← ④ 部署边界不等于逻辑边界
现象
五个服务，每次需求都要改三个，还得按固定顺序发布。一个挂了，其余的接口全超时。
根源
逻辑边界没划对就加了部署边界。一件事被切在几个进程里，它们之间的调用和单体里的方法调用一样密，只是变慢、变得会失败了。
做法
数一数最近十个需求各改了几个服务。总是一起改的，合回去，或者按上一页重新划边界。
2模块边界只写在文档里实测← ④ 第 1 级靠工具守
现象
文档写着“模块之间只能调公开接口”。半年后 grep internal，跨模块的引用有四十多处。⑤ 里那一行 import 能编译、功能也对，没有任何东西拦它。
根源
Java 的 public 管不到“对别的模块不公开”。规则没有进构建，就只是建议。
做法
verify() 写成一个测试放进流水线。存量的越界先列清单逐个还，新的一处都不许进。
3拆了服务，没拆库← ④ 部署边界包括数据
现象
pricing-svc 和 coupon-svc 读写同一张券表。一边加了列，另一边的查询报错；谁也不敢动表结构。
根源
共用的表是一条不走接口的通道，两个服务通过它耦合在一起，而且没有版本、没有契约。
做法
一张表只有一个服务能写。别人要数据，走接口或者订阅事件。拆服务之前，先在模块阶段把表分清楚。
4没有证据就拆← ④ “以后总要拆”不算证据
现象
三个人的小组维护九个服务。一半时间花在联调、对版本、查“是哪一跳超时了”。
根源
部署边界的成本从第一天起付，好处要到多个团队、流量差异大的时候才有。
做法
评审时问三句：要独立发布吗，要独立伸缩吗，要隔离故障吗。三个都答不上来，留在模块里。
5该走不走← ④ 第 1 级的代价是一起挂
现象
抢券高峰，线程池和数据库连接被抢券占满，同一个进程里的算价跟着超时，全站下不了单。
根源
一个进程里的模块共用线程池、连接池、堆内存。逻辑上分开了，资源上没有。
做法
先在进程内隔离（J10 的 限流、熔断和隔离）；不够就走第 2 级，两组实例各接各的流量；还不够再拆。
6模块之间用 SQL 偷偷连着← ④ 1 守得好，3 才拆得动
现象
代码上 verify() 全过。真要拆的时候发现，算价的一条 SQL join 了抢券的三张表。
根源
verify() 查的是 Java 类型之间的依赖，看不到 SQL 里的表名。
做法
每个模块的表用自己的前缀，Mapper 只放在所属模块里；跨模块要数据，调对方的公开接口。

第二圈 · 团队里该怎么做

  • 默认先做成模块，拆服务要有 ADR：防没有证据就拆。
  • 边界检查进流水线：防边界只活在文档里。
  • 一张表一个主人，不跨模块 join：防数据上的暗耦合。
  • 模块之间的调用，当它是远程的来设计：传值不传内部对象，一次问清不来回问：防拆的那天发现接口没法走网络。
  • 每个“不拆”的决定都写上重新看的条件，并且给它配上监控：防该走的时候没人知道。
  • 往上走一级之前，先确认下面一级站稳了：防把乱搬到网络上。

第三圈 · 深一层

真要拆：绞杀者模式

不停机、不一次切换。在入口加一层路由，新服务先接一小部分请求，和旧路比对结果；比对稳了，逐步把流量挪过去；最后删掉旧代码。数据也是先双写、再切读、最后停旧写。全景第 10 站“先搬后改、新旧两边都算”用的就是它的前半段。

模块之间发事件

同一个进程里，模块之间也可以不直接调用：抢券模块发一个 Spring 的应用事件，算价模块监听。Spring Modulith 为此提供了事件发布登记：事件和业务数据在同一个事务里落库，监听方处理成功才标记完成，进程中途挂了能补发。以后拆成服务，把它换成消息队列，两边的代码基本不动。

拆服务的前提

Martin Fowler 列过走微服务之前要先有的能力：很快能开出一套新环境，基本的监控，很快能把一个服务部署上线。没有这些，每多一个服务，就多一份手工活。J13 的可观测和 J14 的流水线，就是在凑这几样。

不用 Spring Modulith 怎么守

它底下用的是 ArchUnit：把“..pricing.internal.. 只能被 ..pricing.. 访问”写成一条规则，在单元测试里跑。Maven 多模块也能守：每个模块一个 jar，不该依赖的就不写进 pom，编译直接过不了。Java 9 的模块系统（module-info.java）能精确到“这个包不导出”，但对老项目改动大。

下一圈

  • 把靶场的算价模块真的拆成 pricing-svc：路由、双写、比对、切流，做一遍绞杀者。
  • Spring Modulith 的事件发布登记：进程在处理事件时被杀，重启后怎么补发。
  • 分组部署实操：同一个镜像两个 Deployment，网关按路径分流，压测看抢券还拖不拖累算价（接 J14）。
  • 康威定律和团队拓扑：团队怎么分，系统就会长成什么样。
  • 反过来的路：把拆得太碎的服务合回去，怎么合。

↺回到⑤：改一改

  1. 把 bad 改对：让“省多少”由调用方去问 PricingFacade，CouponGrabService 不再碰算价。做对了的样子：verify() 通过，两个模块之间只剩 pricing → coupon 一个方向。（坑 2）
  2. 显式声明依赖：在 pricing 包加 package-info.java，写 @ApplicationModule(allowedDependencies = "coupon")；再给 coupon 写一个空的 allowedDependencies = {}。做对了的样子：bad 版多报一条“不在允许的依赖里”。（坑 2）
  3. 写 ADR-007：照 ④ 的证据清单，写出“放进模块、暂不拆”的决定，和两条重新看的条件，每条配一个能监控的数字。（坑 4、5）

自测

1. 用一句话说出这一页的精华

逻辑边界、代码边界、部署边界是三样东西；前两样便宜，先要，用工具守住；部署边界贵而且难退，等出现要独立发布、独立伸缩或隔离故障的证据再加，并把这些条件事先写下来。

2. “一上来就微服务”和“单体里不分模块”各疼在哪？

一上来就微服务，是在最不了解业务的时候做最难反悔的决定，边界划错要迁数据、改协议。单体里不分模块，改一处不知道坏哪，到该拆的时候每个类都被别人直接用着，拆不动。

3. 坑 1（分布式单体）的根源是 ④ 的哪一条？

部署边界不等于逻辑边界。逻辑边界没划对就拆，一件事被切在几个进程里，它们必须一起改、一起发布；付了网络和运维的成本，没拿到独立的好处。

4. 预测：营销拆成“活动组”和“券组”两个小组，都改 coupon-svc，每周发布互相卡一两次。模块边界是过的，但算价的 SQL join 着抢券的表。现在能直接拆服务吗？

该拆了，但还不能直接拆。证据有了（两个小组、发布排队），第 3 级是对的方向；可是数据没分开，拆出去以后那条 join 要么变成跨库查询，要么两个服务共用一张表，变成坑 3。先在进程里把 join 改成调对方的公开接口，表各归各的，再拆。在实验台里把“两个小组”“每周都有”“混着用”选上看看。

5. 预测：算价留在 order-svc 里（候选 A），12.12 之后运营每周要上一种新活动。半年后会怎样？

订单服务每周都要为营销的需求发布一次，而订单是最不该频繁动的核心链路；每次发布都要回归下单、支付、退款。营销的同学要改订单的代码库，订单组成了营销需求的瓶颈。这正是“发布排队”的证据，只不过是因为逻辑边界划错了才出现的，解法是把算价搬回营销，而不是把订单服务再拆细。

6. 放回全景：第 5 站前后各是什么？这一站选错了（选了 B，新建 pricing-svc），后面哪几站会变难？

前面是第 4 站划好的两个上下文，后面是第 6 站把决定写成 ADR。选 B 的话：第 7 站多出一套服务间的超时、重试、降级设计；第 8 站的方案要多写新仓库、流水线、库、值班；第 9 站评审会被问“12 天够不够”“高峰多一跳挂了怎么办”；第 10 站“先搬”变成跨服务迁移，12.12 之前很难做完双跑比对。

档位：标准。本机跑过（2 核 ARM 虚拟机，OpenJDK 17.0.21，Spring Modulith 1.4.14，Spring Boot 3.5.16）：VerifyDemo，⑤ 的输出来自这次运行，包名前缀缩短、依赖明细每组只留一行。实验台是一张写死规则的清单，在 node 里跑过。P99 200 ms、8 台这些数字是交易靶场的设计。

按文档（已核对原文）：Spring Modulith 参考文档：启动类所在包的每个直接子包是一个模块；模块根包里的公开类型是它的 API，子包是内部的，别的模块不能引用；verify() 检查模块间无环、只访问对方的 API 包、（声明了的话）只依赖 allowedDependencies 列出的模块；@NamedInterface 可以额外公开一个子包。Martin Fowler《MonolithFirst》（2015）的两条观察和“边界一开始很难划对”。没有逐句核对：Fowler《MicroservicePrerequisites》列的三项前提；Spring Modulith 的事件发布登记（Event Publication Registry）；绞杀者模式（Fowler，Strangler Fig）。
