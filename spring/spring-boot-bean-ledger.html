249 个 bean 是谁建的：两道筛子定下装哪些，“你没写我才写”定下默认值

订单服务启动完，容器里有 249 个 bean，我们写的只有 10 个。剩下的，自动配置直接建了 193 个，又顺手打开了 30 个。决定装哪些的是两道筛子：158 个候选，第一道只查一个属性文件，连类都不加载，就刷掉 115 个；第二道等我们的配置都登记完，再判条件注解，又刷掉 8 个，最后装上 35 张。默认值怎么来的，看的是同一条规矩：你没写，我才写；你写了，它整张让位，连身上的属性绑定一起让位，而且不报任何错。3.8 s 的启动里，最大的一格是解析配置类和判条件（1.2 s），懒加载省不掉它。

①为什么需要：请求来之前，249 个对象得有人决定建哪些、怎么建

在全景第 1 站，这一步要解决的是：请求还没来，第 2～11 站要用的 Tomcat、过滤器链、DispatcherServlet、事务代理、连接池、Mapper 代理都得已经建好、接好。全景实测：启动 3.4～3.8 s，装好 249 个 bean，而我们只写了 6 个类。上一圈讲了“按 classpath 配”这条原理；这一圈拿交易靶场记一本账，回答三个更具体的问题。

实测 数字全部来自 ⑤ 的 LedgerLab：把全景页的订单服务原样搬过来，启动一次，逐个看 bean 定义是哪个类、哪个 @Bean 方法登记的。不知道这三个问题的答案，平时也能用；出事时就只能猜：改了 yml 不生效、加一个 bean 别处坏了、启动慢了不知道慢在哪。

②没有它会怎样：35 张图纸自己抄，换一个依赖就改一遍代码

上一圈讲过手写配置的样子（Boot 自动配置）。放到订单服务上，账是这样的：

只用 Spring Framework，手写 @Configuration

@Bean TomcatServletWebServerFactory tomcat() { ... }
@Bean DispatcherServlet dispatcherServlet() { ... }
@Bean ObjectMapper objectMapper() { ... }       // 再配一遍消息转换器
@Bean HikariDataSource dataSource() { ... }    // 池名、大小自己 set
@Bean JdbcTransactionManager txManager(...) { ... }
@Bean SqlSessionFactory sqlSessionFactory(...) { ... }
@EnableTransactionManagement @EnableWebSecurity @MapperScan(...)
// ……再加错误页、文件上传、任务线程池、SSL、校验器
// 自动配置替我们建的是 193 个，外加打开的 30 个

疼在哪

  • 每个项目都抄一遍，抄的版本各不相同，升级 Spring 时每份都要改
  • 换依赖要改代码：把 Tomcat 换成 Undertow，把 Hikari 换成别的池，配置类跟着重写
  • 没有“只在需要时才建”：不用 Redis 的项目，也得记着别把 Redis 的配置抄进来，不然启动就因为找不到类而失败
  • 出了问题没有账可查：某个对象为什么是这个类型、这个参数，只能翻代码

缺的那一块：图纸由各个 jar 自己带来，按“classpath 上有什么、你配了什么、你已经建了什么”自动挑；你建了的，它就让开；每张图纸装没装、为什么，都留一份报告可查。

③相邻方案：什么时候决定“建哪些”

三种做法的差别，在于“建哪些 bean”是谁决定、什么时候决定。

做法谁决定、什么时候决定代价
手写 @Configuration
Spring Framework		人决定，写代码时就定死②里那些疼
自动配置
Spring Boot 默认		每次启动时决定：看 classpath、属性、已有的 bean，判一遍条件每次启动都要重判一遍（④-4 那 1.2 s 里有它的份）；让位是静默的，配置可能悄悄失效（⑥）
构建时决定
Spring AOT、GraalVM native		构建时把条件判完，生成登记 bean 的代码，运行时不再判按 Boot 文档：classpath 在构建时就固定；@Profile 受限，@ConditionalOnProperty 这类“改属性就改变建哪些 bean”的条件不支持

本页学第二种：交易靶场和绝大多数 Boot 项目在 JVM 上跑，用的就是它。AOT 和 native 列进“下一圈”。

④原理：两道筛子，一条让位规矩，一本时间账

先看 158 个候选怎么变成 35 张，再看为什么要分两道，然后把全景每一站的对象对回它的图纸，最后看 3.8 s 花在哪。

先知道这些
  • 图纸和成品：bean 定义（BeanDefinition）是图纸，bean 是按图纸建出来的对象。本页的 249 数的是图纸。IoC 那页。
  • 自动配置类：一个带 @AutoConfiguration 的普通配置类，上面挂着条件注解。它们登记在 jar 里的 META-INF/spring/…AutoConfiguration.imports 清单上。上一圈。
  • refresh：容器启动的主流程。先把所有配置类解析成图纸（自动配置在这一步），再建 BeanPostProcessor，再建 Tomcat，最后建其余单例。启动流程那页，代理何时换进。

④-1 两道筛子：158 → 43 → 35

实测 第一道刷掉的按条件分 {OnClassCondition=111, OnWebApplicationCondition=3, OnBeanCondition=1}，第二道 {OnPropertyCondition=4, OnBeanCondition=2, ResourceBundleCondition=1, RSocketEnabledOrReactiveWebApplication=1}。剩下的 43 个是通过 AutoConfigurationImportListener 拿到的，这是 Boot 在第一道之后发出的事件。按源码（spring-boot-autoconfigure 3.5.16）：AutoConfigurationImportSelector.getAutoConfigurationEntry 依次是读清单 → 去重 → 排除 → getConfigurationClassFilter().filter(...) → 发事件；三个过滤器登记在这个 jar 的 spring.factories 里。

④-2 为什么分两道：被判的类可能根本不存在，“你写没写”必须等你写完

被放弃的做法：把 158 个类都加载，反射读注解

  • 115 个用不上的类也要加载、链接，冷启动白花时间
  • 这些类的注解和方法签名里，引用的正是不在 classpath 上的类（RedisOperations）；反射去读，就会撞上 NoClassDefFoundError / TypeNotPresentException
  • 一边加载一边判，判 @ConditionalOnMissingBean 时，我们自己的 bean 可能还没登记，结论取决于顺序

选中的做法：查表 + 读字节码 + 排在最后

  1. 构建时，注解处理器（spring-boot-autoconfigure-processor）把每个类的 @ConditionalOnClass 等抄进 spring-autoconfigure-metadata.properties；启动时第一道只查这张表，比如 …RedisAutoConfiguration.ConditionalOnClass=…RedisOperations
  2. 第二道用 ASM 读字节码里的注解，不加载类。按 Boot 文档，正因如此，类上的 @ConditionalOnClass(Foo.class) 可以直接写类字面量
  3. AutoConfigurationImportSelector 是 DeferredImportSelector：等所有用户配置类解析完才处理，@ConditionalOnMissingBean 看到的就是“你已经写了什么”

决定胜负的约束：要判断的类恰恰可能不存在，所以不能加载它；要判断“你写没写”，所以必须排在你后面。代价是第二点里那条规矩：只在自动配置类里用 @ConditionalOnBean / OnMissingBean，自己的配置类里用，结果取决于顺序（上一圈的坑）。

④-3 默认值也是条件：全景每一站的对象，出自哪张图纸

把全景各站用到的对象逐个查出“谁登记的”。最右一列是这个默认值是怎么定下来的，都能在 spring-boot-autoconfigure 3.5.16 / mybatis-spring-boot-autoconfigure 3.0.5 的源码里找到那一行。

站bean → 实测类型出自默认值怎么定的
②tomcatServletWebServerFactory → TomcatServletWebServerFactoryServletWebServerFactoryConfiguration.EmbeddedTomcatclasspath 上有 Tomcat，而且我们没建自己的 WebServerFactory
③springSecurityFilterChain → CompositeFilterChainProxy@EnableWebSecurity，由 SecurityAutoConfiguration 打开里面装的是我们 WebConfig.api 那条链；不写的话，Boot 给一条“所有接口都要登录”的默认链
④dispatcherServlet → DispatcherServletDispatcherServletAutoConfiguration映射到 /
⑤jacksonObjectMapper → ObjectMapperJacksonAutoConfiguration@ConditionalOnMissingBean；spring.jackson.* 只作用在它建的这一个上，读请求、写响应用的都是它
⑥orderService → OrderService$$SpringCGLIB$$0我们写的；代理由 InfrastructureAdvisorAutoProxyCreator 换进去TransactionAutoConfiguration 打开 @EnableTransactionManagement(proxyTargetClass = true)，AopAutoConfiguration 再强制用类代理：两处都是 spring.aop.proxy-target-class 没配时 matchIfMissing = true
⑦dataSource → HikariDataSourceDataSourceConfiguration.Hikari按 Hikari → Tomcat → Dbcp2 → OracleUcp → Generic 的顺序 @Import，每张都带 @ConditionalOnMissingBean(DataSource)，Hikari 排第一而且 starter 带了它。池名 trade-pool、最多 5 条，是同一个 @Bean 方法上的 @ConfigurationProperties("spring.datasource.hikari") 绑上去的
⑦transactionManager → JdbcTransactionManagerDataSourceTransactionManagerAutoConfiguration有唯一的 DataSource，又没有别的事务管理器
⑧sqlSessionFactory、sqlSessionTemplateMybatisAutoConfiguration@ConditionalOnSingleCandidate(DataSource)，并且 @AutoConfigureAfter(DataSourceAutoConfiguration)：要先有池，它才判得出“有唯一一个”
⑧orderMapper → jdk.proxy2.$Proxy80MapperFactoryBean，由 MyBatis 自动配置里的扫描注册器登记扫描带 @Mapper 的接口；整个注册器挂在 MybatisAutoConfiguration 里面，它没装，Mapper 也就没了
⑩applicationTaskExecutor → ThreadPoolTaskExecutorTaskExecutorConfigurations@Async 用的就是它，所以全景第 10 站的线程叫 task-1

规矩只有一条：你没写，我才写。你写了，整张图纸让位，图纸上挂着的属性绑定、默认调优也一起让位，而且不报错、不打日志。⑥ 的前四个坑都是从这一行推出来的。

④-4 3.8 s 花在哪：最大的一格是解析和判条件

实测 用 BufferingApplicationStartup 记下的步骤：spring.context.config-classes.parse classCount=99 原样三次 1.19～1.28 s；建 bean 的步骤 spring.beans.instantiate 共 247 次，按“去掉子步骤的自身耗时”排，最慢的是 dataSourceScriptDatabaseInitializer（0.22 s，跑 schema.sql 时借第一条连接，H2 内存库在这时才真正启动）、httpSecurity、tomcatServletWebServerFactory、sqlSessionFactory。图上是原样第 2 次、懒加载第 3 次的数，其他几次差不多。“零碎”是这些步骤之间没被记进任何一步的时间。冷 JVM 里这些时间有很大一部分花在第一次加载和解释执行类上，这里没有再拆。

⑥细节：六个坑，五个出自同一条让位规矩

第一圈的坑都在交易靶场上跑过，每条都能指回 ④ 的一格。第二圈是团队里怎么写。第三圈看源码路径、启动加速的几条路，以及 Boot 4 拆模块。

第一圈

注意事项

坑 1自己 new 了连接池，yml 里的 hikari 配置全部静默失效← ④-3 绑定挂在它的 @Bean 上实测
现象
yml 里写着 spring.datasource.hikari.maximum-pool-size=5、pool-name=trade-pool，线上看连接池是 HikariPool-1，最多 10 条。没有任何报错或警告。
根源
你的 DataSource 一登记，DataSourceConfiguration.Hikari 就因为 @ConditionalOnMissingBean 整张让位；那串属性是绑在它那个 @Bean 方法上的，你的 bean 没人绑。实测：poolName=HikariPool-1 maximumPoolSize=10，bean 定义从 249 变成 246。
做法
能用属性就不 new。非 new 不可（比如多数据源），在自己的 @Bean 方法上也加 @ConfigurationProperties("spring.datasource.hikari")，或者用 DataSourceProperties.initializeDataSourceBuilder()。
坑 2排除了 DataSourceAutoConfiguration，报错的却是 OrderMapper← ④-1 第二道的条件是连着的实测
现象
启动失败：Parameter 0 of constructor in …OrderService required a bean of type '…OrderMapper' that could not be found. 看上去像 Mapper 没扫到。
根源
没有 DataSource → MybatisAutoConfiguration 的 @ConditionalOnSingleCandidate(DataSource) 不满足 → 整张跳过，挂在它里面的 Mapper 扫描注册器也没了。报错的是链条最末端那个缺东西的 bean。
做法
报“找不到 bean”时，先开 debug=true 看条件报告里它上游的那张图纸是不是没装，再顺着条件往上找，别急着加 @MapperScan。
坑 3为了让响应变成下划线，配了 spring.jackson 命名策略，接口全变 400← ④-3 进出用的是同一个 ObjectMapper实测
现象
加了 spring.jackson.property-naming-strategy=SNAKE_CASE，App 照旧发 {"channel":"alipay","amountCents":79800}，返回 HTTP 400 Bad Request。
根源
这个属性改的是容器里唯一那个 ObjectMapper，读请求体也用它。amountCents 不再被认识（它要的是 amount_cents），字段留成 0，@Positive 校验不过。实测日志：MethodArgumentNotValidException … rejected value [0] … must be greater than 0。
做法
命名策略是接口契约，不是显示格式。要改就和调用方一起改；只想改某几个 DTO，用 @JsonNaming 标在类上。
坑 4自己 new 了 ObjectMapper，spring.jackson.* 全部不生效← ④-3 你写了，它整张让位实测 + 按文档
现象
同样配着 SNAKE_CASE，又加了一个 @Bean ObjectMapper objectMapper() { return new ObjectMapper(); }：接口返回 200，响应还是驼峰，属性像没写一样。
根源
jacksonObjectMapper 带 @ConditionalOnMissingBean，让位了；实测容器里只剩我们那个 objectMapper。按 Spring 文档，Jackson2ObjectMapperBuilder 默认关掉的 FAIL_ON_UNKNOWN_PROPERTIES 也跟着回到 Jackson 自己的默认（开）：客户端多传一个字段就会 400。
做法
用 Jackson2ObjectMapperBuilderCustomizer 改一两项；真要自己建，也从注入进来的 Jackson2ObjectMapperBuilder 建。
坑 5以为关掉 proxy-target-class 就换成了 JDK 代理← AOP：没接口只能用 CGLIB实测
现象
配了 spring.aop.proxy-target-class=false，想让 OrderService 变成 JDK 代理；实测它还是 OrderService$$SpringCGLIB$$0，bean 定义少了 2 个。
根源
属性只决定“能用接口代理时用不用”。OrderService 没实现任何接口，JDK 代理没有接口可实现，只能生成子类。反过来，实现了接口的类在 false 下会变成 JDK 代理，这时按实现类注入就会启动失败。
做法
别改这个默认。Boot 从 2.0 起默认用 CGLIB，就是为了“按类注入总是行得通”。
坑 6开懒加载提速：启动快了 0.5 s，代价挪到了第一个请求和上线之后← ④-4 它只省“建单例”那一格实测 + 按文档
现象
实测 run() 从 3.79～3.86 s 降到 3.27～3.42 s，启动时建的单例从 262 个降到 154 个；第一个请求从 0.60～0.67 s 涨到 0.69～0.81 s，两个请求之后还有 65 个单例一直没建。
根源
图纸一张没少，只是单例推迟到第一次被用时建。按 Boot 文档：配置错了的 bean 也要等到被用时才失败，不会在启动时暴露；JVM 的堆也要按“全都建起来”留够。
做法
开发环境可以全局开，生产别开；只对确实很重、很少用的 bean 标 @Lazy。
第二圈

使用规范

改默认值按这个顺序：属性 → Customizer → 自己的 @Bean

自己建 bean 等于接管整张图纸，图纸上所有的属性绑定和默认调优都要自己补。防：坑 1、坑 4。

启动时留一份账，升级 Boot 前后 diff

CI 里跑一次 debug=true 或读 /actuator/conditions，把装上的图纸和 bean 数存下来。升级后多了、少了哪张，一眼就能看出来。防：静默让位、升级后静默多出一张。

排除写在一处，并注明原因

统一放 spring.autoconfigure.exclude，旁边写清“为什么排、谁依赖它”。防：坑 2 那种半年后没人知道为什么起不来。

条件注解只写在自动配置类上

自己的配置类里不用 @ConditionalOnBean / OnMissingBean，它们判断的时候，自动配置的 bean 还没登记。防：④-2 说的顺序问题。

别把“全局 JSON 命名”当显示设置

对外接口的字段名放在 DTO 上（@JsonProperty / @JsonNaming），不靠全局属性。防：坑 3。

启动变慢先看步骤，不先猜

打开 BufferingApplicationStartup（或 actuator 的 /startup），按自身耗时排出前十，再决定是删 starter、改懒加载还是改那一个 bean。防：坑 6 那种省错了地方。

第三圈

源码路径、启动加速、Boot 4

① 两道筛子在源码里的位置
  1. @SpringBootApplication → @EnableAutoConfiguration → @Import(AutoConfigurationImportSelector.class)
  2. 它是 DeferredImportSelector，用自己的 AutoConfigurationGroup：等所有用户配置类解析完才处理
  3. getAutoConfigurationEntry：ImportCandidates.load 读清单 → 去重 → 排除 → ConfigurationClassFilter.filter（第一道，三个 AutoConfigurationImportFilter 查 metadata）→ 发 AutoConfigurationImportEvent
  4. AutoConfigurationSorter 排序：先按字母，再按 @AutoConfigureOrder，最后按 after / before
  5. 剩下的交回 ConfigurationClassParser，逐个判 @Conditional*（第二道），结果记进 ConditionEvaluationReport

按源码：spring-boot-autoconfigure 3.5.16。

② 启动加速的几条路
做法省的是哪一格依据
懒加载建单例：−0.48 s；代价见坑 6本机实测
删掉用不上的 starter少装的图纸和它们建的 bean；第一道刷掉的本来就几乎不花钱按 ④-1 的账推断
CDS（类数据共享）JVM 加载类的时间，各格都受益按文档：Boot 3.3 起支持，先训练一次生成归档
AOT + native判条件、解析配置类、JVM 预热基本都挪到构建时按文档；代价见 ③
③ Boot 4：清单拆进各技术模块

按 jar 内容：spring-boot-autoconfigure 3.5.16 一个清单里有 156 个；到了 4.1.2，同名 jar 的清单只剩 12 个，其余拆进了各自的模块，比如 spring-boot-jdbc 9 个、spring-boot-webmvc 6 个、spring-boot-tomcat 5 个。没引入的模块，清单上根本没有那几行，第一道要查的候选也就更少。starter 也跟着拆细了（如 spring-boot-starter-webmvc）。交易靶场在 J05 末尾升 4.x 时再实测。

④ 版本差异
版本自动配置登记在哪
Boot 2.6 及以前META-INF/spring.factories 的 EnableAutoConfiguration 键
Boot 2.7新增 AutoConfiguration.imports 和 @AutoConfiguration；旧写法还认
Boot 3.x只认 AutoConfiguration.imports；spring.factories 里登记的自动配置不再加载（上一圈的坑）
Boot 4.x同上，但按技术拆成多个模块，各带一份清单

    练习 1 · 用坑 1 的做法

    给 Overrides.dataSource() 加上 @ConfigurationProperties("spring.datasource.hikari")。预期：own-ds 场景的连接池变回 poolName=trade-pool maximumPoolSize=5。

    练习 2 · 用坑 4 的做法

    把 Overrides.objectMapper() 换成一个 Jackson2ObjectMapperBuilderCustomizer，只关掉 WRITE_DATES_AS_TIMESTAMPS。预期：jackson-own 场景变得和 jackson 一样返回 400，说明 spring.jackson 的属性又生效了；容器里的 bean 叫回 jacksonObjectMapper。

    练习 3 · 用第二圈“留一份账”

    让 LedgerLab 把装上的 35 张图纸写进 applied.txt（已经写了），再往 pom 里加 spring-boot-starter-actuator 重跑。预期：diff 能列出多出来的那一批 …actuate.autoconfigure…，bean 数明显变多。

    1. 用一句话说出这一页的精华。

    自动配置用两道筛子决定装哪些图纸：第一道查构建时生成的属性文件，不加载类；第二道排在用户配置之后、读字节码判条件。装上的图纸都守一条规矩：你没写我才写，你写了它整张让位，连属性绑定一起让位，而且不报错。

    2. 不用自动配置、手写配置，最疼的是哪一点？

    每个项目都要自己抄一遍几十个 bean 的配置，换依赖就要改代码，也没有“只在 classpath 上有这个类时才建”的机制（②）。

    3. 坑 1 里，为什么 hikari 的属性会悄悄失效，而不是报错？

    ④-3：那串属性是 DataSourceConfiguration.Hikari 里那个 @Bean 方法上的 @ConfigurationProperties 绑的。我们建了 DataSource，这张图纸因为 @ConditionalOnMissingBean 整张不装，属性也就没有绑定的对象；Spring 不检查“有没有属性没被用到”。

    4. 预测：给 OrderService 加一个接口 PayService，再配 spring.aop.proxy-target-class=false，Controller 仍然按 OrderService 类型注入。会怎样？

    启动失败。有接口可用、又要求不用类代理，代理就是实现 PayService 的 JDK 代理，它不是 OrderService 的子类，按类注入找不到合适的 bean（类型不匹配）。坑 5 的根源反过来用。

    5. 预测：想给连接池做个“兜底”，在自己的 @Configuration 里建一个 DataSource，方法上加 @ConditionalOnMissingBean(DataSource.class)，意思是“自动配置没建，我再建”。实际谁赢？

    永远是我们的赢，兜底变成了顶替。④-2：自动配置是 DeferredImportSelector，排在所有用户配置之后才处理；判我们这个条件的时候，Hikari 那张图纸还没登记，条件总是成立。我们的 DataSource 一登记，Hikari 那张反而让位，于是又回到坑 1：hikari 的属性全部失效。这就是“条件注解只写在自动配置类上”的原因。

    6. 放回全景：第 1 站前后各发生了什么？这一页讲的东西坏了，整条链路会怎样？

    第 1 站之前，JVM 刚起来，SpringApplication.run 准备环境、读 yml；第 1 站之后，Tomcat 开始接请求，第 2～11 站全靠这里建好的对象。自动配置出问题有两种：一种是缺了图纸，比如排除了数据源，第 1 站就起不来，不会上线；更麻烦的是静默让位，比如自己 new 了连接池，第 7 站借连接时池子是 10 条而不是 5 条，压测和线上表现跟配置文件对不上；自己 new 了 ObjectMapper，第 5 站读请求体时多一个字段就 400。

    档位：标准。本机实测：2 核 ARM Linux，OpenJDK 17.0.21，Spring Boot 3.5.16（Spring Framework 6.2.19），mybatis-spring-boot-starter 3.0.5，H2 内存库（MySQL 模式）。⑤ 和实验台的七个场景（原样、proxy-target-class=false、自建连接池、排除数据源、懒加载、Jackson 命名策略、再自建 ObjectMapper）每个单独起 JVM 跑 3 次，bean 数、筛子数、类型、状态码三次一致，时间取范围；另跑了一次 -Xlog:class+load 对照哪些候选类被加载过，和一次 load-on-startup=1。
