测试全绿，付款照样没回滚：JUnit 5、Mockito 与 Testcontainers

给交易靶场的付款埋了三颗事务雷，Mockito 单测全绿，@WebMvcTest 也全绿；换成 @SpringBootTest 加 Testcontainers 起的真 MySQL，三颗雷全部现形（本页实测）。测试的精华是一句话：一层测试只能抓到它让“真东西”跑过的那几站。Mockito 把依赖换成假货换来 0.2 秒，也把代理、事务、SQL 一起换掉了；所以要分层，每一层只负责它真正跑过的那几站。

①为什么学：十一站的付款链路，每改一行都要重新证明一遍

在全景这条十一站的付款链路上，要证明每一段都对：请求进得来、参数挡得住、失败时钱和状态一起撤回、SQL 在真 MySQL 上对。而且不是证明一次，是每次改代码、每次升级（下一页就要把靶场升到 Boot 4）都自动再证明一遍。一次请求里不会跑测试，测试站在链路外面，把它切成几段分别验。

  • 工作要用。地图给 J05 靶场的任务：关键流程补单元测试，用 Testcontainers 起 MySQL 做集成测试，再升 Boot 4。没有测试兜底，升级只能靠手点。
  • 面试会问。“单测和集成测试怎么分”“Mock 了数据库还算测试吗”“事务失效怎么测出来”，答案都在④的那张切片图里。

②老办法：Postman 点一遍，H2 跑一遍

不写测试也能“验证”：启动应用，Postman 发几个请求，再打开数据库看状态。或者写几个 main，连 H2 内存库跑一下。能做，但不完美，有两处疼。

不懂精华时的典型误用：给 PaymentService 写满 Mockito 单测，覆盖率 90%，觉得“付款已经测过了”。⑤ 实测：对的写法和三颗事务雷，在 Mockito 单测里表现完全一样，4 个用例全绿。单测里没有 Spring，也就没有代理，@Transactional 只是一个没人读的注解。

③选谁：三个问题，各挑一个

“测试”其实是三个独立的选择：用什么框架组织和运行测试、依赖拿什么替身、数据库用什么。Spring Boot 的 spring-boot-starter-test 已经替你做了前两个选择。

④原理：四个零件，各管一件事

JUnit 5 负责“跑”，Mockito 负责“假”，Spring Test 负责“起多少容器”，Testcontainers 负责“库是真的”。先一个个看清它们怎么工作，最后放回全景：哪一层让哪几站真的跑过。

先知道这些
  • 注入进来的 Service 是代理：容器里放的是 PaymentService$$SpringCGLIB$$0，@Transactional 靠代理里的拦截器生效；this.xxx() 不经过代理。见 AOP 与代理。
  • 事务默认只对运行时异常回滚：受检异常照常提交，自己 catch 掉的异常拦截器看不见。见 事务传播、隔离与失效。
  • Docker 容器：一个隔离的进程，带着自己的文件系统（镜像）。mysql:8.4 镜像里就是一个装好的 MySQL，起一个容器就是起一个 MySQL 进程，删掉就干净了。

④-1 JUnit 5：一个平台，加上可插拔的扩展

④-2 Mockito：一张答案表，一盘录像带

④-3 Spring Test：按需建一部分容器，建好就缓存

④-4 Testcontainers：Java 代码当 Docker 客户端

④-5 为什么这样设计：真实度要用时间买，所以分层

一层到底 每个测试都起全部 + 真库

分层 每层只证明它真跑过的那几站

决定胜负的约束：一个测试的“真实度”和“速度”不能同时最高，因为真实就意味着要把 Spring、代理、连接池、MySQL 都建起来，而这些就是那十几秒。所以不是选一层，是每层只负责它真跑过的那几站，别指望单测去抓事务，也别为了验一个 if 去起 MySQL。同理，库用 Testcontainers 而不用 H2：库的行为（排序规则、锁、SQL 方言）本身就是被测对象，H2 只能模仿语法（②实测）。

⑥细节：测试自己也会骗人

第一圈是不知道就会出事的坑，每条都能指回 ④ 的某张图；第二圈是团队里怎么写；第三圈往下挖一层，再加 Boot 4 的版本差异。

第一圈 · 注意事项

坑 1测试类上加 @Transactional，事务测试全部失真← ④-1 SpringExtension实测
现象
同样四个场景，测试类加上 @Transactional 后，对的写法查出来也是 PAID，和三颗雷一模一样，四条全分不出来。第 10 站的 @TransactionalEventListener（默认提交后才触发）也永远不会被调用（按文档）。
根源
SpringExtension 在测试方法外面开了一个测试事务，结束才回滚。pay() 的 REQUIRED 加入了它，抛异常只是把它标成“只能回滚”，真正的回滚推迟到测试结束；断言走的是同一条连接，看到的是还没撤掉的数据。
做法
测事务行为的类不加 @Transactional，用 @BeforeEach 自己清表、造数据（⑤ 就是这样）。只测查询、不关心提交的类可以加，图它自动清理。
坑 2单测里 @Transactional、@Async、@Cacheable 都是空气← ④-2 没有代理实测
现象
⑤ 的参数化单测：对的写法和三颗雷，4 条全绿。覆盖率很好看，事务一条都没测到。
根源
@InjectMocks 是直接 new 的，没有 Spring，就没有把注解变成行为的代理。这些注解在单测里只是元数据。
做法
单测只测判断和调用顺序；凡是靠代理生效的东西（事务、异步、缓存、权限注解），放到 @SpringBootTest 那一层去证明。
坑 3多一种配置，就多一个上下文、多一个 MySQL← ④-3 上下文缓存实测
现象
两个 @SpringBootTest 类共用一个上下文，第二个 0.22 s；@MybatisTest 的配置不同，又建一个上下文、又起一个容器，多花 13.2 s。套件越写越慢，常见原因就是每个类的 @MockitoBean 组合都不一样。
根源
缓存 key 包含 @MockitoBean、@TestPropertySource、@Import 这些定制，差一个就是另一个 key；容器是上下文里的 bean，跟着上下文走。
做法
所有集成测试 @Import 同一个容器配置，替身的组合收敛到一两个基类；真要全局只起一个容器，用单例写法（第三圈）。
坑 4H2 上绿，MySQL 上红← ④-5 库的行为就是被测对象实测
现象
流水号 CH-9527-a 和 CH-9527-A：H2 插进两条；MySQL 8.4 抛 DuplicateKeyException。
根源
MySQL 8 默认排序规则 utf8mb4_0900_ai_ci 不分大小写，唯一索引按它比较；H2 默认区分。MySQL 模式只让 H2 认得 MySQL 的语法。
做法
碰到 SQL 的测试用和生产同大版本的 MySQL（Testcontainers）；H2 只留给和库无关的快速测试，或者干脆不用。
坑 5@WebMvcTest 里，自己的 SecurityConfig 没生效：POST 一律 403← ④-3 切片只扫一部分实测
现象
去掉 @Import(SecurityConfig.class)：带 @WithMockUser 的付款请求 403，没登录的也是 403，不是预期的 401。
根源
SecurityConfig 是 @Configuration，Web 切片不扫它；Boot 换上默认安全配置，CSRF 是开着的，POST 没带 token，在第 3 站就被 CsrfFilter 拦了，连认证都没轮到。
做法
切片里 @Import 自己的安全配置，测的才是线上那条过滤器链；确实要开 CSRF 的接口，请求上加 .with(csrf())。
坑 6多写一个用不上的 when，测试直接报错← ④-2 答案表实测
现象
UnnecessaryStubbingException: Unnecessary stubbings detected.，测试本身的断言都过了。
根源
MockitoExtension 默认是严格模式：测试结束时对账，答案表里写了却没人问过的条目算错。它在提醒你：这条 stub 是多余的，或者代码没走到你以为的分支。
做法
删掉多余的 stub；@BeforeEach 里给多个测试共用、个别用不上的，单条改成 lenient().when(...)，不要整个类关掉严格模式。

第二圈 · 使用规范

别人的系统用替身，自己的用真的

支付渠道、短信、库存服务用 @MockitoBean；自己的 Mapper、Service、数据库在集成测试里用真的。

替掉自己的 Mapper 之后，SQL 和事务一条都没测到。

一条测试只证明一件事，名字写成“条件_结果”

中文方法名完全可以：金额为0_校验挡在第5站_400。参数化测试用 @ParameterizedTest(name = …) 写清每一组。

红了以后还要读半天代码才知道坏在哪。

测试数据自己造、自己清

@BeforeEach 清表、插入这个测试要的那几行，不依赖执行顺序，不依赖别的测试留下的数据。

单独跑绿、一起跑红；换个顺序又绿了。

镜像钉死版本，和生产同一大版本

写 mysql:8.4，不写 mysql:latest。生产升级时，测试的镜像跟着改。

某天镜像更新，测试无缘无故变红。

CI 上要有 Docker，本地没有时显式跳过

CI 用带 Docker 的执行器；本地没有 Docker 的同事，用 @Testcontainers(disabledWithoutDocker = true) 让这些类跳过，而不是一片红。

“我这跑不了”变成理由，最后谁都不跑集成测试。

雷先写成“断言雷炸了”，修好再反转

⑤ 的三颗雷都断言 PAID；修好一颗，就把那条断言改成 CREATED，留作回归测试。

修好以后有人改回去，没有任何东西报警。

第三圈 · 优化和深处

上下文缓存有多大、怎么看

  • 默认最多缓存 32 个上下文（spring.test.context.cache.maxSize），超了按最久未用淘汰；被淘汰的上下文关闭时，里面的容器也停掉，下次再用又要重起。
  • 把 org.springframework.test.context.cache 的日志调到 DEBUG，能看到命中、未命中次数，用来找是哪个类在建新上下文。
  • 每个缓存着的上下文都占着连接池和容器：一个套件里十几个上下文，内存和 Docker 都会吃紧。

容器的三种生命周期

  • bean + @ServiceConnection（本页）：跟上下文走，上下文复用它就复用。
  • @Testcontainers + @Container 静态字段：由 JUnit 扩展管，按测试类起停，一个类一个容器。
  • 单例：基类的 static 块里 start()，整个 JVM 一个，退出时 Ryuk 收尸。最快，但所有类共享一个库，数据要自己隔离。
  • 本地还可以 withReuse(true) 加 testcontainers.reuse.enable=true，容器跨多次 mvn test 保留，Ryuk 不管它；CI 上别开。

Mockito 5 的替身是怎么造出来的

  • Mockito 5 起默认 inline mock maker：用 Byte Buddy 的 Java agent 在运行时改写类的字节码，所以 final 类、final 方法也能替。
  • JDK 21 起，运行时动态挂载 agent 会打印警告（JEP 451），以后的 JDK 计划默认禁止。Mockito 的文档建议在 surefire 的 argLine 里用 -javaagent 显式挂上。本页用 JDK 17 跑，没有这条警告。
  • 静态方法也能替：mockStatic(Clock.class)，要在 try-with-resources 里用，出了块就恢复。

雷 1 的全局解法：Spring 6.2

  • Spring Framework 6.2 给 @EnableTransactionManagement 加了 rollbackOn = RollbackOn.ALL_EXCEPTIONS：全局改成受检异常也回滚，不用每个方法写 rollbackFor（本机核对：spring-tx 6.1.21 里没有 RollbackOn，6.2.19 里有）。
  • 开了以后，雷 1 那条“断言 PAID”的测试会变红：这正是回归测试该做的事，提醒你行为变了。

自测

1. 用一句话说出这一页的精华。

一层测试只能抓到它让真东西跑过的那几站：Mockito 用替身换来速度，也换掉了代理、事务和 SQL，所以要分层，每层只证明它真跑过的那几站。

2. 只用 H2 和 Postman 验证付款，疼在哪？

手点靠人记得点什么，三颗事务雷要专门构造“渠道拒绝”才会触发；H2 只模仿 MySQL 的语法，排序规则这类行为不一样（②实测流水号大小写，两边结果相反）。

3. 为什么 Mockito 单测抓不到事务失效？根源是哪条原理？

④-2：@InjectMocks 是 new 出来的普通对象，没有 Spring 就没有 CGLIB 代理，事务拦截器根本不存在。对的写法和三颗雷在这一层只剩“抛了异常 / 返回 FAILED”，看起来一样。

4. 预测：PaymentTxMySqlTest 里把 @MockitoBean PaymentGateway 换成 @MockitoBean OrderMapper（也把 Mapper 替掉），三颗雷的测试会怎样？

先是全红，补好 stub 以后变成“测不了”。Mapper 成了替身，findById 默认返回 null，doPay 直接抛“不是你的订单”，类型断言就红了；渠道也变回了总是成功的 FakeGateway，根本不会拒绝。就算给 Mapper 补齐答案表，changeStatus 也不再写库，库里的订单永远是 CREATED，回滚不回滚都看不出来。真实度来自“哪些是真的”，不是来自 @SpringBootTest 这个注解（④-3、④-5）

5. 预测：TransactionalTestTrapTest 和 PaymentTxMySqlTest 只差一个类上的 @Transactional，跑整个套件时会起几个 MySQL 容器？

一个（实测就是这样）。@Transactional 只影响每个测试方法怎么包事务，不进上下文缓存的 key；两个类的配置类、@Import、@MockitoBean 都一样，所以共用一个上下文、一个容器（④-3）。

6. 预测：CI 换了一台没有 Docker 的机器，mvn test 会怎样？哪几个类还能绿？

用到 MySqlContainerConfig 的三个类在建上下文时报错（找不到可用的 Docker 环境）；单测、Web 切片、H2 那三个类不碰容器，照样绿。加了 @Testcontainers(disabledWithoutDocker = true) 的类会被跳过而不是报错。

7. 放回全景：这几层测试分别兜住哪几站？第 7 站事务失效时，哪一层先红、哪一层测不出来？

单测兜住业务判断（第 8、9 站是替身）；@WebMvcTest 兜住第 3、4、5、11 站（不起 Tomcat，第 2 站不在）；@MybatisTest 加真库兜住第 8、9 站；@SpringBootTest 加真库兜住第 6～9 站。第 7 站坏了，只有 @SpringBootTest + 真库、且测试类不加 @Transactional 的那一层会红；单测和 Web 切片照样绿（前者没有代理，后者 Service 是替身），@MybatisTest 根本不调 Service，加了 @Transactional 的测试类连对的写法都会误报。线上的后果：渠道拒绝了，订单却是“已付款”，钱没收到，货照发；按全景的代码，雷 1、雷 2 的事务照常提交，第 10 站的“付款成功”短信也会发出去。
