代理是哪一刻换进容器的：先把对象建完，最后一步才换成代理，引用发早了就出事

容器建一个 bean 分两半：前一半建的是原始对象（new、注入、@PostConstruct），最后一步才由 BeanPostProcessor 把它换成代理。这一页的坑全是同一个原因：最后一步之前，引用已经被别人拿走了。比如 @PostConstruct 里的 this，循环依赖里提前给出去的半成品，被某个 BeanPostProcessor 提前拉起来的 bean。为了循环依赖，Spring 只开了一个口子：自动代理创建器可以提前把代理造出来。@Async 不走这个口子，就会撞上 “raw version” 启动失败。到了 Spring 6.2，这个失败有时会被悄悄跳过，于是同一份代码能不能启动，要看哪个 bean 先建。

①为什么需要：Controller 手里必须是代理，不能是原始对象

全景第 1 站要做两件事。第一件是把 249 个 bean 按依赖建好、接上，这是上一圈讲过的（IoC、一生十四站）。第二件是这一圈的重点：OrderService 上有 @Transactional，要被换成 CGLIB 代理，而所有拿着它的人，手里都必须是这个代理。第 6 站能把调用拦下来开事务，靠的就是这一点。

这一页回答：代理到底在哪一刻换进去；在那一刻之前，引用可能从哪几条路漏出去；漏出去会怎样；Spring 又是怎么补漏的。

②没有它会怎样：手工装配，包代理和发引用谁先谁后全靠记

不用容器，在 main 里自己 new、自己包事务代理。几行就能写完，难的是顺序。

手工装配订单服务

OrderService raw = new OrderService(mapper);
raw.warmUp();                 // 预热：这时还没包事务
OrderController c = new OrderController(raw);
                              // ↑ 引用先发出去了
OrderService tx = TxProxy.wrap(raw);
                              // c 手里还是 raw，事务对它无效

// 再来个环：通知服务要订单服务，订单服务也要通知服务
NotifyService n = new NotifyService();
OrderService o = new OrderService(mapper, n);  // 要 n 的成品？
n.setOrder(o);                                 // 还是 o 的成品？
NotifyService nAsync = AsyncProxy.wrap(n);     // o 手里的 n 又过期了

疼在哪

  • 包代理必须在“把引用交给别人”之前，晚一步，别人手里就是原始对象，事务、异步全部失效，而且不报错
  • 每多一种增强（事务、异步、缓存、权限），就多一处要记着顺序的包装
  • 有环时没有正确顺序：A 要 B 的最终版本，B 也要 A 的最终版本，谁先包都不对
  • 出了错只能靠打日志看类名，没有任何地方检查“大家手里是不是同一个对象”

缺的那一块：一个统一的“最后一步”，所有包装都在这里做完，然后才把引用交出去；环出现时，有办法提前拿到“将来的那个代理”；万一拿不到，宁可启动失败，也不让两个版本同时在线上。典型误用：以为注入进来的就是自己 new 的那个对象，直接读它的字段。CGLIB 代理是个子类实例，里面的业务字段全是 null（⑤ 的实验里真读到过，见 坑 2）。

③相邻方案：增强也可以不靠“换对象”

“先建原始对象、最后换成代理”只是做法之一。另外两种做法根本没有“换”这一步，所以也就没有这一页的坑，代价在别处。

做法增强在什么时候加上“引用发早了”的问题代价
运行时容器 + 运行时代理
Spring 默认		启动时，每个 bean 初始化的最后一步，生成 JDK 代理或 CGLIB 子类有：本页全部的坑自调用不增强；final、private 方法拦不住；最后一步之前的引用是原始对象
字节码织入
AspectJ 编译期或加载期，@EnableTransactionManagement(mode = ASPECTJ)		编译或类加载时，直接改 OrderService 自己的字节码没有：根本没有代理对象，this.pay() 也有事务要 ajc 编译器或 -javaagent，构建和排查都更复杂，团队里很少用
编译期 DI
Dagger、Micronaut		构建时生成装配代码和增强代码依赖图在构建时就检查完，环直接编译失败注入点、作用域都要在编译期能确定，不能运行时按条件换实现

本页学第一种：交易靶场和绝大多数 Spring Boot 项目用的就是它。Spring 6 的 AOT 会在构建时提前算好 bean 定义，但运行时还是按同一套生命周期建 bean、换代理，这一页讲的时机不变。

④原理：refresh 分三段，代理在每个 bean 的最后一格

先看整次启动，再放大到一个 bean，再看循环依赖时开的那个口子，最后看为什么非这样设计不可。

先知道这些
  • BeanDefinition 和 bean：前者是图纸（类名、作用域、依赖），后者是按图纸建出来的对象。IoC 那页讲过图纸从哪来。
  • 一个 bean 的一生：上一圈拆成了十四站，这页压成三段：实例化 → 填属性 → 初始化。初始化里依次是 Aware 回调、BPP 的 before、@PostConstruct、afterPropertiesSet、BPP 的 after。生命周期那页。
  • 三级缓存：一级放成品，二级放已经给出去的早期引用，三级放“需要时才造早期引用”的工厂。为什么要三级，上一圈讲过。
  • 代理：JDK 代理实现同样的接口，CGLIB 代理是子类。两者都是另一个对象，手里拿着原始对象（target），自己身上的业务字段是空的。AOP 代理那页。

④-1 一次 refresh：先画图纸，再建“加工厂”，最后才建普通 bean

④-2 放大一个 bean：原始对象阶段，和引用漏出去的三条路

④-3 循环依赖时开的口子：getEarlyBeanReference，只有自动代理创建器走了它

漏口 ② 是 Spring 自己开的：为了让 setter 和字段注入的环能起来，它允许别人在我初始化完之前先拿走一个早期引用。可我最后一步还要换成代理，所以 Spring 给 BeanPostProcessor 加了一个钩子，SmartInstantiationAwareBeanPostProcessor.getEarlyBeanReference，意思是：有人现在就要我，你要包的话，现在就包。

@Transactional：自动代理创建器实现了这个钩子

  1. 库存服务要订单服务的早期引用 → 三级缓存里的工厂调 getEarlyBeanReference → 自动代理创建器现在就造出代理，并把 bean 名记进 earlyProxyReferences
  2. 订单服务走到最后一步，postProcessAfterInitialization 查到“已经提前造过”，原样返回，不再包第二次
  3. doCreateBean 末尾：最后一步返回的还是原始对象 → 改用早期代理放进容器 → 大家手里是同一个代理

实测 库存服务手里的 order：Cycles$OrderService$$SpringCGLIB$$0，和容器里是同一个对象=true

@Async：它的处理器没有实现这个钩子

  1. 订单服务要通知服务的早期引用 → AsyncAnnotationBeanPostProcessor 没覆盖 getEarlyBeanReference（6.2 里它实现了这个接口，但只覆盖了 determineBeanType）→ 给出原始对象
  2. 通知服务走到最后一步，它包了一层新代理
  3. doCreateBean 末尾：最后返回的 ≠ 原始对象，而且已经有 bean 拿过早期引用 → 抛 BeanCurrentlyInCreationException：“has been injected into other beans [orderService] in its raw version … but has eventually been wrapped”

Spring 发现不一致时宁可启动失败，也不让两个版本同时在线上。这个检查只有一个开关 allowRawInjectionDespiteWrapping，默认关着。

④-4 为什么这样设计：先建完、最后换，而且换代理只是一个插件

Spring 的做法：建完原始对象，最后一步由 BPP 换

  • 代理要包的是一个已经能用的对象：事务拦截器最终要调 target，target 必须注入完、初始化完
  • 要不要代理、代理哪些方法，要看最终的类和注解，前面的 BPP 可能已经把对象换过
  • 容器核心不认识事务、异步、缓存。它们各是一个 BPP，加一种增强就是加一个 BPP，容器核心一行不改

放弃的做法：实例化时直接 new 出代理子类

  • 容器在 new 的那一刻就得知道这个 bean 需要哪些增强：事务、异步、缓存的规则全要写进实例化策略
  • 注入、@PostConstruct 都发生在代理子类实例上；增强逻辑在对象还没初始化完时就生效，调用会进到半成品
  • 多种增强叠加（先事务还是先异步）只能由容器硬编码，第三方框架没法插进来

决定胜负的约束：增强要作用在完整的对象上，又要能由第三方插进来，所以只能“最后一步，由插件换”。代价是最后一步之前，谁拿到引用谁就拿到原始对象，⑥ 第一圈的坑都出在这。Spring 为此补了三样：给环开的早期引用口子（④-3），raw version 一致性检查（宁可起不来），以及 BPP 提前建 bean 时的警告（BeanPostProcessorChecker）。Boot 2.6 更进一步，默认不许有环，等于把这个口子关上了。

⑤亲眼看到：订单服务启动时，orderService 在哪一格变了身

交易靶场的订单服务，只留启动装配这一段：一个带 @Transactional 的 OrderService，@PostConstruct 里做预热；一个不排序的 BeanPostProcessor 在旁边看着；启动完成后再从外面调一次。

⑥细节：五个坑，同一个根

第一圈的五个坑，每个都能指回 ④ 里的一条漏口。第二圈是团队里该怎么写。第三圈看源码里那两个检查，以及 Spring 6.2 带来的一个变化：同一份代码，换个建 bean 的顺序，启动结果就不一样。

第一圈

注意事项

坑 1@PostConstruct 里调本类的 @Transactional / @Async，不生效← ④-2 漏口 ①实测
现象
启动时补偿未支付订单，日志说成功了，数据却是半截：中途异常没回滚。@Async 的预热方法在 main 线程里同步跑，启动慢了几秒。
根源
@PostConstruct 在“BPP after”之前，这时代理还不存在；就算存在，this 也是原始对象。⑤ 实测：事务已开启=false，this 的类=OrderService。
做法
启动后才跑的业务逻辑，放到 @EventListener(ApplicationReadyEvent.class)、ApplicationRunner 或 SmartInitializingSingleton 里，通过注入进来的代理调用。
坑 2读注入对象的字段，拿到 null← ④ 代理身上没有业务字段实测
现象
写测试或排查时直接读 inventoryService.order，得到 null，以为注入失败了。我们的实验第一版就踩了：库存服务手里的 order：null。
根源
容器给的是 CGLIB 子类的实例，它只拿着 target，自己从父类继承来的字段从来没赋过值。方法调用会被转给 target，字段访问不会。final 方法同理：子类覆盖不了，会直接在代理实例上执行，读到的也是空字段。
做法
只通过 public 方法访问别的 bean；不要把要被代理的类的方法写成 final（Kotlin 要配 all-open）。
坑 3订单 ⇄ 库存，升级 Boot 2.6 后启动不了← ④-3 口子被关了实测
现象
BeanCurrentlyInCreationException: Requested bean is currently in creation: Is there an unresolvable circular reference…；Boot 会打一张 bean 环的图。
根源
Boot 2.6 起 spring.main.allow-circular-references 默认是 false，早期引用的口子不开了。打开它，字段注入的 @Transactional 环能起来，双方拿到同一个代理（实测）；构造器注入的环开了也起不来，原因见上一圈。
做法
拆环：把双方都要的那部分抽成第三个 bean，或者改成事件（下一条）。临时救急可以在一侧注入点加 @Lazy，注入的是一个延迟查找的代理。
坑 4环里有 @Async：今天能起，加了个 Controller 就起不来← ④-3 @Async 没走口子实测 + 按源码
现象
打开了循环依赖，通知服务（@Async）⇄ 订单服务。Spring 6.1：先建通知服务就报 “raw version”。Spring 6.2：同样的顺序能起来；可只要新加一个依赖通知服务的 PayController，而且它先被建，就又报同样的错。
根源
@Async 的处理器不提前造代理，通知服务先建、早期引用又被拿走时，必然不一致。6.2 起预实例化循环会吞掉“最外层那个 bean”的这条异常，换下一个 bean 从另一侧重新走进环（第三圈）。如果是 Controller 带着走进环，异常就不在最外层，照样抛出来。
做法
别让 @Async 的 bean 进环。交易靶场的写法：订单服务 publishEvent(new OrderPaid(…))，通知服务用 @Async @TransactionalEventListener 接（全景第 10 站），两边互不依赖。
坑 5自己写的 BeanPostProcessor 注入了业务 bean，事务悄悄没了← ④-1 漏口 ③，三组登记实测
现象
启动日志里一条 WARN：Bean 'orderService' … is not eligible for getting processed by all BeanPostProcessors (for example: not eligible for auto-proxying). Is this bean getting eagerly injected/applied to a currently created BeanPostProcessor [auditBpp]?。普通 BPP：事务还在（实测 事务已开启=true）。BPP 加了 PriorityOrdered：orderService 是原始类，事务已开启=false。
根源
BPP 依赖的 bean 会被提前拉到 B 段建，这时只有已经登记的 BPP 能处理它。自动代理创建器在 Ordered 组：普通组的 BPP 拉起它时，自动代理创建器已经登记了；PriorityOrdered 组拉起它时，自动代理创建器还没登记。同一条警告，后果取决于缺的是哪个 BPP。
做法
BPP 用 static @Bean 声明，不注入业务 bean；真要用，注入 ObjectProvider<OrderService>，用的时候再 getObject()。不要为了“先执行”随手加 PriorityOrdered。
第二圈

使用规范

一律构造器注入

环在启动时立刻暴露，三级缓存不会替你把它藏起来。防：带着环上线，靠顺序碰运气。

新项目不打开 allow-circular-references

老项目要开，就把环列成清单逐个拆。防：坑 4 这种启动结果取决于建 bean 顺序的情况。

@PostConstruct 只初始化自己的字段

不调业务方法，也不调别的 bean 上带增强的方法；启动任务放进 ApplicationReadyEvent 或 ApplicationRunner。防：坑 1。

BPP 和 BeanFactoryPostProcessor 用 static @Bean，不依赖业务 bean

static 才不会把所在的配置类和它的依赖一起提前拉起来。防：坑 5。

把 BeanPostProcessorChecker 的 WARN 当错误

CI 里 grep 启动日志里的 not eligible for getting processed，有就失败。防：坑 5 那种不报错、只是没事务的情况。

打日志看类名，别看字段

怀疑没走代理时，打印 getClass() 或 AopUtils.isAopProxy(bean)，不要读它的字段。防：坑 2 的误判。

第三圈

源码里的两道检查，和 6.2 的一个变化

① 一致性检查：doCreateBean 的最后几行 
Object earlySingletonReference = getSingleton(beanName, false);
if (earlySingletonReference != null) {        // 有人拿过我的早期引用
  if (exposedObject == bean) {                 // 最后一步没换对象
    exposedObject = earlySingletonReference;   // 用早期那个（可能是提前造的代理）
  } else if (!allowRawInjectionDespiteWrapping && hasDependentBean(beanName)) {
    throw new BeanCurrentlyInCreationException(… "in its raw version" …);
  }
}

按源码（spring-beans 6.2.19，AbstractAutowireCapableBeanFactory）。事务能过，是因为自动代理创建器在 postProcessAfterInitialization 里查 earlyProxyReferences，提前造过就原样返回，于是 exposedObject == bean。

② 6.2 的预实例化：吞掉一条异常，换个方向再走一遍 
// DefaultListableBeanFactory.preInstantiateSingleton（6.2.19 / 7.0.10 都有）
try { instantiateSingleton(beanName); }
catch (BeanCurrentlyInCreationException ex) {
  logger.info("Bean '" + beanName + "' marked for pre-instantiation (not lazy-init) " +
      "but currently initialized by other thread - skipping it in mainline thread");
}

从日志原文看，这是给 6.2 新加的后台初始化（@Bean(bootstrap = BACKGROUND)）准备的：别的线程正在建它，主线程就跳过。raw version 恰好也是 BeanCurrentlyInCreationException，于是也被吞掉，只留一条 INFO（Boot 默认的 INFO 级别能看到，但混在启动日志里）。失败的半成品已经销毁，下一个 bean 从另一侧重新走进环，就成功了。实测 6.1.21 报错，6.2.19 启动成功。

③ BPP 三组登记和那条警告

PostProcessorRegistrationDelegate.registerBeanPostProcessors：先建并登记全部 PriorityOrdered，再 Ordered，再其余，最后把 MergedBeanDefinitionPostProcessor（Autowired、CommonAnnotation 处理器）挪到队尾重新登记一次，所以 ⑤ 的列表里它们排在最后。开头先放一个 BeanPostProcessorChecker：B 段里每建出一个普通 bean，它就检查一次“已登记的 BPP 数量是否还不够”，不够就打那条警告。

    自测

    1. 用一句话说出这一页的精华。

    代理在 bean 初始化的最后一步由 BeanPostProcessor 换进去，在那之前漏出去的引用（@PostConstruct 的 this、环里的早期引用、被 BPP 提前拉起的 bean）都是原始对象；Spring 只给自动代理创建器开了提前造代理的口子，其余情况要么没增强，要么 raw version 启动失败。

    2. 手工装配时，包代理最难的是哪一点？

    顺序：必须在把引用交给任何人之前包好，包晚了，别人手里就是原始对象，而且不报错；有环时根本找不到对的顺序（②）。

    3. 坑 5 里，同一条 WARN，为什么普通 BPP 事务还在，PriorityOrdered 的 BPP 事务就没了？

    ④-1：BPP 分三组依次登记，被 BPP 提前拉起来的 bean 只有已登记的 BPP 能处理。自动代理创建器在 Ordered 组，普通组 BPP 建的时候它已登记；PriorityOrdered 组建的时候它还没有。

    4. 预测：订单服务（@Transactional）⇄ 库存服务（这次库存服务的方法上是 @Async），打开循环依赖，Spring 6.1，先建订单服务。能启动吗？

    能。被提前拿走早期引用的是先建的那个，也就是订单服务；它的增强是事务，自动代理创建器能提前造代理，前后一致。库存服务虽然有 @Async，但它是在环里完整建完的，没人提前拿它，最后一步包成代理再交出去，也一致。反过来先建库存服务，就是坑 4：raw version。（④-3，实验台可以用同样的规则推）

    5. 预测：把 ⑤ 的 SwapWatcher 改成实现 PriorityOrdered（不依赖任何 bean），它在 postProcessAfterInitialization 里看到的 orderService 是什么类？

    原始的 OrderService。BPP 按登记顺序依次执行：PriorityOrdered 组在 Ordered 组前面，它执行时自动代理创建器还没换。它返回的对象再交给自动代理创建器，最终容器里还是代理。（④-1）

    6. 放回全景：第 1 站前后各发生了什么？这一页讲的东西坏了，整条链路会怎样？

    第 1 站之前什么都还没有：JVM 刚起来，SpringApplication.run 读配置、准备环境；第 1 站之后 Tomcat 开始接请求，第 2～11 站全靠第 1 站建好的对象互相调用。这一页的东西坏了，大多不报错：Controller 拿到原始的 OrderService，第 6 站没有代理，第 7 站不开事务，金额不符也把订单改成 PAID；或者第 10 站的 @Async 变成同步，短信发慢了，接口跟着变慢。报错的那种（raw version、环被禁止）反而好处理，第 1 站就起不来，不会上线。

    档位：标准。本机实测：2 核 ARM Linux，OpenJDK 17.0.21，Spring Boot 3.5.16（Spring Framework 6.2.19），对照 Spring Boot 3.3.13（Spring Framework 6.1.21），H2 内存库。⑤ 和坑 1～5 的输出原样摘自 ProxySwapLab 的九个场景；同一个 JVM 里依次起九个容器，每个场景的结果跑了 2～3 次都一样。
