付款失败，流水要不要一起撕：事务的每个属性，都在问线程上那条连接

全景第 7 站，事务拦截器借来一条连接，绑在线程上。之后 pay() 里每遇到一个 @Transactional，Spring 先问一句：线程上已经有事务了没有？有的话，是接着用这条连接（REQUIRED），先收起来再借一条（REQUIRES_NEW），还是在这条上夹一个书签（NESTED）。传播行为、隔离级别、超时，还有提交后的回调，各种“失效”都能从这一问推出来。本页把交易靶场的付款按 3 种传播 × 4 种情况跑了 12 遍，又跑了 6 个坑。

①为什么需要：一笔付款里，有的要一起成败，有的不能

在全景第 7 站，这一步要解决的是：pay() 里改订单、写支付流水是两件事，大多数时候要一起成败，有时候偏偏不能。订单 9527 应付 798 元，请求里只付了 1 元：订单必须回滚成 CREATED，可风控要求这条“金额不符”的流水留下来。反过来，流水表写失败了，钱已经收到，订单得照样变 PAID。只靠一个 @Transactional，做不到“撕掉一部分、留下一部分”。

②没有它会怎样：自己另拿一条连接写流水

不用传播行为，想让流水不跟着订单回滚，最直接的办法是：写流水时绕开 Spring，自己从连接池拿一条新连接，用自动提交模式写进去。

手写：另拿一条连接

public void record(long orderId, String result) {
  try (Connection c = dataSource.getConnection()) {   // 不经过 Spring
    c.setAutoCommit(true);                              // 写完就提交
    try (var ps = c.prepareStatement(
        "INSERT INTO pay_log(order_id, result) VALUES (?, ?)")) {
      ps.setLong(1, orderId); ps.setString(2, result);
      ps.executeUpdate();
    }
  }
}

疼在哪

  • 用不了 Mapper：MyBatis 一调就会拿到线程上那条连接（MyBatis 接事务），只能手写 JDBC
  • “流水失败也别影响付款”还得自己 try/catch，流水本身要是写两张表，又得自己管提交和回滚
  • 它照样同时占着两条连接，并发一高池子会被借空（⑥ 坑 2），只是代码里看不出来
  • 想要“流水失败只撤流水，订单照常”，得自己调 setSavepoint、rollback(sp)

缺的那一块：一个统一的入口，在“线程上已经有事务”时，按声明决定怎么办：加入、另起一个、夹个保存点、还是报错。这就是传播行为（propagation）。典型误用：把 REQUIRES_NEW 当成“换个事务”这么轻巧，没意识到它要第二条连接，外层事务锁住的行也还锁着。

③相邻方案：“失败也要留下”的四种写法

需求是：订单回滚了，金额不符的流水也要留下。能做到的不止 REQUIRES_NEW。

写法流水什么时候落库连接代价
REQUIRES_NEW（另一个 bean）内层返回时立刻提交，外层回滚不影响同时占 2 条池子要按并发数翻倍算；外层锁住的行，内层改不了
NESTED（保存点）跟外层一起提交。外层回滚，它也没了1 条只能做到“内层失败不连累外层”，反过来不行；要 JDBC 保存点
@TransactionalEventListener(phase = AFTER_ROLLBACK) + REQUIRES_NEW外层回滚以后，在回调里另开事务写回调时短暂占 2 条进程在回滚和回调之间挂了，这条就丢了
不进数据库：写日志、发 MQ和事务无关0 条要另外的管道保证不丢（J08、J09）

本页学的：传播行为本身，也就是 REQUIRED、REQUIRES_NEW、NESTED 三种在线程和连接上到底做了什么。选择规则：“外层失败时它要留下”用 REQUIRES_NEW；“它失败时别连累外层”用 NESTED 就够了，而且省一条连接；能不在事务里做的，就挪到提交或回滚以后去做。

④原理：一个问题分出 7 种传播，一条连接决定所有后果

上一圈讲了两个旋钮各有哪些档位。这一圈往下一层：每个档位在线程和连接上到底做了什么，失效又是怎么从里面冒出来的。

先知道这些
  • 连接绑在线程上：事务拦截器借来的连接放在 TransactionSynchronizationManager 的 ThreadLocal 里，按 DataSource 存一格。MyBatis、JdbcTemplate 都从这一格取（全景第 7、8 站，MyBatis 接事务）。
  • 一条连接上同一时刻只有一个数据库事务。setAutoCommit(false) 以后，这条连接上的 SQL 都算进同一个事务，直到 commit() 或 rollback()。JDBC 规范还规定：事务进行到一半调 setAutoCommit(true)，当前事务会被提交。
  • 保存点（savepoint）：Connection.setSavepoint() 在事务里夹一个书签，rollback(sp) 只撤销书签之后的改动。
  • 行锁：UPDATE 会锁住改到的行，一直锁到提交或回滚，别的事务改同一行要排队（MVCC 与锁）。

最少的写法

API传播、隔离、超时、回滚规则
// 外层：事务边界。隔离、只读、超时只在这里写才生效（④-1 右边“加入”会忽略它们）
@Transactional(isolation = Isolation.READ_COMMITTED, timeout = 3)
public String pay(long orderId, long paid) { ...; payLog.record(orderId, result); ... }

// 内层：必须在另一个 bean 里，调用才经过代理
@Transactional(propagation = Propagation.REQUIRES_NEW)   // 外层回滚它也留下；占第 2 条连接
public void record(long orderId, String result) { ... }

@Transactional(propagation = Propagation.NESTED)         // 它失败不连累外层；同一条连接 + 保存点
public void recordBestEffort(long orderId, String result) { ... }

// Spring 6.2+：受检异常也回滚，整个应用统一
@EnableTransactionManagement(rollbackOn = RollbackOn.ALL_EXCEPTIONS)

参数的细节（readOnly 到底做了什么、timeout 什么时候检查、validateExistingTransaction）放到第⑥步。

为什么这样设计：事务是线程的属性，不是参数

选中的：事务挂在线程上，进门按“有没有”分派

  • 业务代码、MyBatis、JdbcTemplate 之间一个连接参数都不传，加个注解就有事务
  • “线程上已经有一个”是必然会碰到的情况，所以必须规定碰到时怎么办，传播行为就是这张规定表
  • 一个线程的一格只能放一条连接，所以“另起一个”只能先把旧的摘下来收好（挂起），用完再放回去

放弃的：把事务当参数一路传下去

  • 每个方法签名都要多一个 Connection 或 TxContext，Mapper 也得收它
  • 好处是显式：换线程、自调用都不会丢，嵌套也一目了然
  • 输在侵入：已有代码想加事务，要从 Controller 改到 Mapper；第三方库不认这个参数

决定胜负的约束：Servlet 一个请求从头到尾在一个线程上跑（全景第 2 站），而 Java 后端的数据访问层五花八门。只有“挂在线程上”能让它们不改签名就对上同一条连接。代价也从这里来：换线程（@Async、parallelStream）事务就丢；REQUIRES_NEW 要挂起、要第二条连接。还有一个设计选择：REQUIRED 的内层失败，为什么不悄悄撕掉内层就算了？因为它和外层是同一个数据库事务，没有保存点就撕不了“一部分”。Spring 宁可在提交时抛 UnexpectedRollbackException 大声报错，也不让外层以为提交成功了。

⑤亲眼看到：交易靶场的付款，3 种传播 × 4 种情况跑 12 遍

不起 Web，直接调 PayService。H2 内存库（MySQL 模式），HikariCP 故意只开 4 条连接、借不到等 1 秒。每一遍跑之前把订单 9527 重置成 CREATED、清空流水表。Spring Boot 3.5.16（Spring Framework 6.2.19），mybatis-spring-boot-starter 3.0.5，JDK 17。

1PayService.pay：改订单 → 写流水 → 金额不符就抛
@Transactional
public String pay(long orderId, long amountCents, LogMode mode, boolean logFails, boolean catchLogFail) {
    mapper.changeStatus(orderId, "CREATED", "PAID");
    long due = mapper.amountOf(orderId);
    String result = due == amountCents ? "OK" : "AMOUNT_MISMATCH";
    try {
        switch (mode) {
            case REQUIRED     -> payLog.recordRequired(orderId, result, logFails);
            case REQUIRES_NEW -> payLog.recordRequiresNew(orderId, result, logFails);
            case NESTED       -> payLog.recordNested(orderId, result, logFails);
        }
    } catch (IllegalStateException e) {
        if (!catchLogFail) throw e;                // 情况 C：想“流水失败不影响付款”
    }
    if (due != amountCents) throw new AmountMismatch("应付 " + due + "，实付 " + amountCents);
    events.publishEvent(new OrderPaid(orderId));
    return "PAID";
}

还没处理的细节

REQUIRES_NEW 并发高了会把池子借空（坑 2），改外层锁住的行会自己等自己（坑 3）；内层写的隔离级别不生效（坑 4）；timeout 不是闹钟（坑 5）；提交后监听器里写库会丢（坑 6）。

⑥细节：每个坑都在问“这一刻线程上是哪条连接”

上一圈列过失效的 10 种情况（自调用、非 public、异常被吞、受检异常、换线程……），这里不重复，见 Spring AOP 与事务。这一圈的 7 个坑，6 个在本机跑出来过，都出在传播、挂起和提交顺序上。

第一圈

注意事项

坑 1外层 catch 住了内层的异常，提交时却收到 UnexpectedRollbackException← ④-2 rollback-only实测
现象
⑤ 的 C 行 REQUIRED：pay() 明明正常返回了，调用方拿到的是 UnexpectedRollbackException: Transaction rolled back because it has been marked as rollback-only，订单还是 CREATED。
根源
内层只是加入者，事务不归它管。它抛异常时，事务拦截器只能在共用的 ConnectionHolder 上标记 rollback-only（globalRollbackOnParticipationFailure 默认 true）。外层 commit() 先看这个标记，看到了就改成回滚，再抛异常告诉你“你以为提交了，其实没有”。
做法
真想“内层失败不连累外层”，内层用 NESTED 或 REQUIRES_NEW（C 行实测两种都返回 PAID）；不然就别 catch，让整笔回滚。不要把 globalRollbackOnParticipationFailure 关掉，那会让一个声明了失败的方法，写的东西照样被提交。
坑 2REQUIRES_NEW 并发一高，连接池被借空，所有人一起等到超时← ④-2 同时占 2 条实测
现象
实测（4 条连接，借不到等 1 s；用栅栏让每个线程先占住自己那条，再一起去写流水）：3 个并发 12 ms 全成功；4 个并发 1017 ms 后全失败，CannotCreateTransactionException ← SQLTransientConnectionException: … request timed out after 1000ms (total=4, active=4, idle=0)。同样 4 个并发换成 NESTED：13 ms 全成功。生产上默认等 30 s，表现是“付款接口卡 30 秒然后报连接池不够”，CPU 和数据库都很闲。
根源
挂起不是归还：外层的 #A 只是从线程上摘下来收着，内层要另借一条。每个线程都占一条、等一条，池子一满就互相等死，直到借连接超时。
做法
能用 NESTED 就别用 REQUIRES_NEW；非用不可，按上面的公式定池子，或者给这类写入单独一个小池子（另一个 DataSource）；把“失败也要留”的写入挪到事务外（③ 第 3、4 行）。
坑 3REQUIRES_NEW 的内层改外层改过的同一行：自己等自己← ④-2 两条连接是两个事务实测
现象
外层 UPDATE 了订单 9527，内层 REQUIRES_NEW 再 UPDATE 同一行。实测（H2）：卡 2.2 s 后 CannotAcquireLockException（… is locked by tx 1 and can not be updated by tx 2），整笔付款回滚。MySQL 上要等 innodb_lock_wait_timeout，默认 50 s（按文档）。
根源
对数据库来说 #A 和 #B 是两个不相干的事务。#A 的行锁要到外层提交才放，而外层在等内层返回。这不是数据库能检测出的死锁（另一方在 Java 里等，不在锁等待图里），只能等锁超时。
做法
REQUIRES_NEW 的内层只碰外层没碰过的表或行，比如单独的流水表。要改同一行，就留在同一个事务里（REQUIRED / NESTED）。
坑 4内层写的 isolation、readOnly、timeout，悄悄不生效← ④-1 加入实测
现象
外层不写隔离级别，内层写 isolation = SERIALIZABLE。实测：内层 REQUIRED 看到的连接还是 READ_COMMITTED；内层 REQUIRES_NEW 拿到另一条连接，才是 SERIALIZABLE；事务结束还回池子再借，又是 READ_COMMITTED（Spring 用完会还原）。没有任何报错或日志。
根源
隔离级别、只读、超时都是“开事务那一刻”设到连接上的（DataSourceUtils.prepareConnectionForTransaction）。加入已有事务时不开新事务，这些属性就没机会生效。事务管理器的 validateExistingTransaction 默认 false，所以不报错。
做法
这三样只写在事务入口的方法上。测试环境把 validateExistingTransaction 打开，实测这时内层直接抛 IllegalTransactionStateException: Participating transaction with definition [PROPAGATION_REQUIRED,ISOLATION_SERIALIZABLE] specifies isolation level which is incompatible with existing transaction；外层只读、内层要写时同样会报。
坑 5@Transactional(timeout) 不是闹钟：不发 SQL 就永远不会超时← ⑥ 源码：deadline实测
现象
实测 timeout = 1：先睡 1.5 s 再 UPDATE，1510 ms 时抛 TransactionTimedOutException，订单 CREATED；先 UPDATE 再睡 1.5 s，1501 ms 后照常提交，订单 PAID。
根源
开事务时只是在 ConnectionHolder 上记一个截止时间。之后每次要发语句，MyBatis 和 JdbcTemplate 去问“还剩多少秒”（getTimeToLiveInSeconds）：已过期就抛异常，没过期就把剩余秒数设成这条语句的 setQueryTimeout。不发语句，就没人检查。
做法
它能防的是“事务里某条 SQL 太慢”。事务里调远程、睡眠、算大数，它管不了：远程调用要有自己的超时，更好的是挪出事务。数据库那头再配锁等待超时兜底。
坑 6提交后的监听器里写库：今天能落库，改个连接池配置就静默丢了← ④-3 提交顺序实测
现象
付款提交后，一个普通的同步 @TransactionalEventListener 往 notify_log 插一条。默认配置实测 1 条；同样的代码，连接池加上 spring.datasource.hikari.auto-commit=false，insert 照样返回 1，查库 0 条。监听器上加 @Transactional(REQUIRES_NEW) 的那一条，两种配置都是 1 条。
根源
监听器在 ④-3 的第 ⑤ 步跑，这时数据库事务已经提交，连接 #A 还绑在线程上、autoCommit 还是 false（实测日志里它拿到的还是 #A，事务名还是 PayService.pay）。默认配置下第 ⑥ 步 setAutoCommit(true) 顺手提交了它；池子本来就是 autoCommit=false 时没有这一步，HikariCP 还连接时把没提交的改动回滚掉。
做法
提交后要写库，监听器上加 @Transactional(propagation = REQUIRES_NEW)（这时 #A 还没还，同样要第 2 条连接），或者加 @Async 换个线程。Spring 6.1 起，@TransactionalEventListener 上挂普通的 @Transactional（REQUIRED）启动就报错：实测 IllegalStateException: @TransactionalEventListener method must not be annotated with @Transactional unless when declared as REQUIRES_NEW or NOT_SUPPORTED。
坑 7以为把隔离级别调高，就能防住“连点两次付款”← 数据库那层：MVCC按文档
现象
先 SELECT status 判断是 CREATED，再 UPDATE。两个请求同时来，在 MySQL 默认的 REPEATABLE_READ 下两边都读到 CREATED，都往下走，第三方支付扣了两次钱。
根源
Spring 的 isolation 只是在开事务时调一下 setTransactionIsolation，管什么、怎么管全看数据库。InnoDB 的普通 SELECT 是快照读，RR 保证的是“同一事务里读两次一样”，不是“别人不能同时读”。SERIALIZABLE 会把普通 SELECT 变成加共享锁，两边都持有共享锁再去改，就是死锁，一方被回滚。
做法
靠写操作本身判断：UPDATE … WHERE id = ? AND status = 'CREATED'，检查影响行数是不是 1（全景第 9 站）；或者先 SELECT … FOR UPDATE。和第三方支付之间的幂等，是 J09 的事。

使用规范

传播默认 REQUIRED。写 REQUIRES_NEW 或 NESTED 的地方，加一行注释说为什么

防：坑 2、3。用 REQUIRES_NEW 时顺手按 Tn × (Cm − 1) + 1 核一遍连接池。

“失败也要留”的写入：放另一个 bean，用 REQUIRES_NEW；只碰外层没碰过的表

防：坑 1、坑 3，以及自调用（同一个类里调，传播写什么都不生效）。

隔离、只读、超时只写在事务入口；测试环境打开 validateExistingTransaction

防：坑 4。在测试配置里用一个 BeanPostProcessor 给 AbstractPlatformTransactionManager 调 setValidateExistingTransaction(true)，示例在实验代码的 Lab.validateSwitch。

新项目打开 rollbackOn = ALL_EXCEPTIONS（Spring 6.2+），老项目写 rollbackFor = Exception.class

防：受检异常照样提交（上一圈的坑）。6.2 的文档自己也建议，除非你依赖“业务异常照样提交”的 EJB 风格。

提交后的事：发短信、发消息用 @TransactionalEventListener + @Async；要写库就加 REQUIRES_NEW

防：坑 6。全景第 10 站的写法就是这个。真要不丢，换成本地消息表（J08）。

事务超时只当兜底：远程调用自己设超时，数据库配锁等待超时

防：坑 5。最好的超时是事务里根本没有慢操作。

    练习 3 · 亲手让坑 6 丢一条数据，再修好

    在 application.properties 加 spring.datasource.hikari.auto-commit=false，跑 listener：plain 0 条。给 NotifyListeners.Plain 加 @Transactional(propagation = Propagation.REQUIRES_NEW) 再跑：1 条。最后试试改成 REQUIRED，看启动报什么错。

    自测

    1. 用一句话说出这一页的精华。

    事务挂在线程上，每遇到一个 @Transactional 先问“线程上已经有事务了吗”：没有就开新的；有就按传播加入、挂起再借一条、或者夹一个保存点。隔离、超时只在开新事务那一刻生效，提交后的回调里连接还绑着。各种失效都是这几条规则的后果。

    2. 不用传播行为，自己另拿一条连接写流水，最疼的是哪两点？

    用不了 Mapper（MyBatis 会拿到线程上那条连接），只能手写 JDBC、自己管提交；而且它同样同时占两条连接，坑 2 一个没少，只是藏起来了。

    3. 坑 1 里，外层明明 catch 住了异常，为什么还是回滚？

    ④-2：REQUIRED 的内层是加入者，和外层共用 #A 上的同一个数据库事务。它失败时不能回滚别人的事务，只能在共用的 ConnectionHolder 上标 rollback-only。外层 catch 掉的只是 Java 异常，标记还在，commit() 第一件事就是看这个标记。

    4. 预测：把 pay() 自己标成 REQUIRES_NEW，Controller 直接调它，和 REQUIRED 有区别吗？

    没有区别。Controller 调它时线程上还没有事务，走 ④-1 的左边，REQUIRED、REQUIRES_NEW、NESTED 都是“开新事务”。传播行为只在“线程上已经有事务”时才分出差别。

    5. 预测：Tomcat 200 个线程，HikariCP 默认 10 条，流水用 REQUIRES_NEW。大促时 50 个付款同时进来，会怎样？

    前 10 个请求在第 7 站各借走一条连接，进到写流水时都要第 2 条，池子已空，互相等；后 40 个卡在第 7 站借第一条。所有人等满 connection-timeout（默认 30 s），先超时的那批回滚、还连接，后面的才动起来。表现是付款接口大面积卡 30 秒，CPU 和数据库都很闲。按公式要 50 × (2 − 1) + 1 = 51 条（按 200 个线程算是 201 条）。从 ④-2 “同时占 2 条”和坑 2 推出。

    6. 预测：监听器改成 @TransactionalEventListener(phase = BEFORE_COMMIT)，里面写一条通知记录，然后抛了个异常。付款会怎样？

    整笔付款回滚，通知记录也没了。BEFORE_COMMIT 在 ④-3 的第 ① 步跑，这时事务还没提交，监听器写的东西就在 #A 的事务里，跟付款一起提交；它抛异常，processCommit 就改成回滚，异常抛给调用方。所以 Spring 6.1 的启动检查不管 BEFORE_COMMIT：它本来就在事务里。

    7. 放回全景：第 7 站前后各发生了什么？这一页讲的东西坏了，整条链路会怎样？

    第 7 站之前是第 6 站：Controller 调的 orderService 是 CGLIB 代理，链上的 TransactionInterceptor 被调到。第 7 站之后是第 8、9 站：Mapper 代理经 SqlSessionTemplate 拿到线程上那条连接，发出 UPDATE；再往后是第 10 站提交和事件。这一页的东西坏了，大多不报错：传播选错，金额不符的流水跟着撕掉（B 行），或者 catch 了还是回滚（C 行）；REQUIRES_NEW 在大促时把池子借空，第 7 站借连接的地方大面积超时；提交后监听器写库，在第 10 站静默丢数据。
