付款一次算一遍密码：密码只在登录时验一次，之后每个请求认一张“通行证”

全景实测里一次付款 87 ms，82.7 ms 在第 3 站算 BCrypt。BCrypt 是故意做慢的，慢是为了防偷库后的离线猜密码，所以不能把它改快。正确的办法是把“验密码”和“认人”拆开：登录那一刻验一次密码，换一张通行证（服务端会话或 JWT）；之后每个请求只验通行证，实测 0.5～0.6 ms。认出“你是 1024”只是第一道门，第二道门还要问“9527 是不是你的单”。

全景：一个请求穿过 Spring · 第 3 站地图：J05 · Spring Security：认证与授权上一圈：Spring Security 认证与授权（过滤器链、SecurityContextHolder、两道门、401 和 403）

①为什么学：全景里最慢的一站，慢在不该慢的地方

在全景第 3 站，这一步要解决的是：认出 POST /orders/9527/pay 这个请求来自用户 1024，并判断他能不能付这一单。全景为了一条命令跑完，用的是 HTTP Basic：每个请求都带着用户名和密码，每个请求都验一次密码。

  • 1密码为什么要算 83 ms？能不能换个快的哈希？（④-4：不能，慢是它的本事）
  • 2登录以后拿什么证明“我是 1024”？会话和 JWT 怎么选，各要付什么代价？（③、④-2、④-3）
  • 3认出是 1024 以后，“9527 是不是他的单”谁来管？（④-5）

②老办法：每个请求都带密码，或者把密码“弄快一点”

上一圈和全景都用 Basic：App 存着用户的密码，每个请求在 Authorization 头里带上 Basic base64(1024:pw)，BasicAuthenticationFilter 每次都交给 DaoAuthenticationProvider 跑一遍 BCrypt。能用，但疼在三处。

每个请求验密码 全景的做法

  • 慢：每个请求 83 ms 的 CPU。这台 2 核机器，光验密码每秒最多约 24 个请求（2 ÷ 0.083，估算）。
  • 密码满天飞：App 要一直存着明文密码，每个请求都把它送一遍，日志、代理、抓包，哪一处漏了都是真密码。
  • 收不回：想让某台手机下线，只能让用户改密码。

误用：把密码弄快 不懂精华时的典型做法

  • 每个请求快了，可一旦用户表泄露，弱密码几分钟就被猜光。慢，正是 BCrypt 在保护用户。

缺的那一块：把“验密码”和“认人”拆成两件事。密码只在登录那一刻验，慢就慢一次；验过以后发一张通行证，之后的请求只验通行证。通行证要做到：验起来快、伪造不了、能过期，最好还能收回。

③选谁：通行证放在服务端，还是让客户端带着

三种常见做法，区别只在一件事：“1024 已登录”这条记录存在哪。存在服务端，就要查；存在通行证里，就要能防篡改。

实测是本页 TokenLab bench 的“进门 → 进 Controller”，热身后 100～300 次的中位数，跑了两遍，两遍差不到 0.1 ms。会话和 JWT 都在毫秒以下，差别不在快慢，在状态放哪：放服务端，换来随时作废；放令牌里，换来哪个实例都能认，代价是发出去就收不回。

选择规则：浏览器访问、实例少、要能踢人 → 会话（多实例加 Spring Session）。App 和多个服务都要认人 → 短有效期的 JWT（5～15 分钟），配一个存在服务端、能作废的刷新令牌。交易靶场的 App 走后者，本页学 JWT，⑤ 里把会话也跑一遍做对照。

④原理：谁认得这张凭证，谁出手；认完放进 SecurityContext

一条安全链可以同时认好几种凭证。每个“认证过滤器”只看请求里有没有自己认识的那种：有就验，验过就把结果放进 SecurityContext；没有就放过，交给下一个。最后由授权的两道门拍板。

先知道这些
  • FilterChainProxy：Spring Security 在 Tomcat 眼里只是一个过滤器，里面套着一串安全过滤器。怎么挂上去、排第几，见一个 400 进了两次 DispatcherServlet。
  • SecurityContextHolder：一个 ThreadLocal，放着当前请求的 Authentication（是谁、有哪些权限）。后面的代码都从这里取“当前用户”。见上一圈。
  • 401 和 403：401 是“不知道你是谁”（没凭证或凭证不对），403 是“知道你是谁，但不让你做”。
  • 哈希和签名：哈希把密码变成一串摘要，不能倒推回来；签名（这里是 HMAC-SHA256）用一把密钥给一段数据算摘要，没有钥匙的人算不出对的签名。

④-1 一条链，三种凭证，各找各的过滤器

④-2 登录那一刻：唯一一次 BCrypt，然后发通行证

  • a全景里的 {noop} 怎么变成了 {bcrypt}：DaoAuthenticationProvider 验过密码后，如果配了 UserDetailsPasswordService，又发现存的哈希“该升级了”（upgradeEncoding：前缀不是默认的 bcrypt，或 cost 低于当前设置），就用当前的编码器重新编码并写回。Boot 的默认用户存成 {noop}，而 InMemoryUserDetailsManager 正好实现了这个接口，所以第一次登录后就被升级成 BCrypt，之后每个 Basic 请求都慢了（源码：DaoAuthenticationProvider.createSuccessAuthentication，InitializeUserDetailsBeanManagerConfigurer）。
  • b会话这条要自己存：Spring Security 6 的 SecurityContextHolderFilter 只负责请求开始时取，不再在响应时自动存。用 formLogin 这类自带的登录过滤器，它会替你存；自己写登录接口，要自己调 SecurityContextRepository.saveContext，忘了就是 ⑥ 坑 1。
  • cBasic 和 Bearer 不建会话：这两个过滤器在 6.x 默认用 RequestAttributeSecurityContextRepository，结果只放在本次请求的属性里，请求结束就没了。所以全景里每个 Basic 请求都得重新验一遍密码。

④-4 为什么这样设计

其一：为什么密码哈希要故意慢，还留一个 cost 旋钮。关键约束：用户表总有一天可能泄露，泄露后攻击者在自己机器上离线猜，猜得多快只取决于算一次哈希要多久。BCrypt 把“算一次”做成可调的慢，cost 每加 1，时间翻一倍：

cost 41.41 ms
cost 820.7 ms
cost 10（默认）82.7 ms
cost 11166 ms
cost 12331 ms

实测 BCryptPasswordEncoder.matches 各 5 次取中位数，2 核 ARM，JDK 17（⑤ bcrypt）。被放弃的设计是 MD5、SHA-256 这类快哈希：它们是为“越快越好”设计的，正好帮了猜密码的人。慢哈希的代价由服务端承担，所以只能在登录时付一次，这就逼出了“通行证”。

其二：登录结果存在哪。

存服务端：会话 有状态

  • 删掉会话，立刻作废
  • 每个请求要查表；多实例要共享存储

存令牌里：JWT 无状态

  • 哪个实例、哪个服务都能认，不查存储
  • 发出去就收不回，只能等过期（⑤ logout）

决定胜负的约束：请求要穿过多少个不共享内存的进程。只有一两台、都是浏览器访问，会话最省事；订单、支付、库存几个服务都要认同一个人，又不想每个请求都去问一次认证中心，就把“我是谁”签好名交给客户端带着。JWT 拿“不能立刻作废”换了这个，所以有效期要短。

④-5 第二道门：认出“你是谁”，还要问“这是不是你的”

URL 规则 anyRequest().authenticated() 只问“登录了没有”。1025 也是登录用户，他拿自己合法的令牌去付 1024 的订单 9527，URL 这一关照样放行。按数据授权要在方法上做：@EnableMethodSecurity 让 Spring 给带 @PreAuthorize 的 bean 套一层代理（原理同事务的那层代理），进方法前先算表达式。

这类漏洞叫 IDOR（越权访问对象）：只换了 URL 里的 id，就动了别人的数据。表达式里的 authentication.name 对会话是用户名，对 JWT 是 sub，两边都是 "1024"，所以这条规则对两种凭证一样有效。

OrderController⑤ idor
// 第一道门（URL）：登录了就放行
// 第二道门（方法）：只能付自己的单
@PostMapping("/orders/{id}/pay")
@PreAuthorize("@orderBook.ownerOf(#id) == authentication.name")
public Map<String,Object> pay(@PathVariable long id,
                              Authentication auth) { … }
// 1025 付 9527 → 403；1025 付 9528 → 200

最少的写法

SecurityConfig（节选）Spring Boot 3.5 · Security 6.5
@Bean SecurityFilterChain chain(HttpSecurity http) throws Exception {
  http.csrf(c -> c.disable())                                  // 只因客户端不是浏览器，见 ⑥ 第二圈
      .authorizeHttpRequests(a -> a.requestMatchers("/login/**").permitAll()
                                   .anyRequest().authenticated())
      .oauth2ResourceServer(o -> o.jwt(withDefaults()));         // 认 Bearer JWT
  return http.build();
}
@Bean JwtDecoder jwtDecoder() { return NimbusJwtDecoder.withSecretKey(KEY).build(); }      // 验签
@Bean JwtEncoder jwtEncoder() { return new NimbusJwtEncoder(new ImmutableSecret<>(KEY)); } // 签发

// 登录接口：唯一一次验密码，然后签 15 分钟的令牌
Authentication a = authenticationManager.authenticate(
    UsernamePasswordAuthenticationToken.unauthenticated(username, password));
JwtClaimsSet claims = JwtClaimsSet.builder().subject(a.getName())
    .expiresAt(Instant.now().plusSeconds(900)).claim("scope", "order:pay").build();
String token = jwtEncoder.encode(JwtEncoderParameters.from(
    JwsHeader.with(MacAlgorithm.HS256).build(), claims)).getTokenValue();

    ⑥细节·规范·优化

    第一圈

    注意事项：不知道就会出事故的坑

    坑 1登录接口返回成功，下一个请求还是 401← ④-2 会话要自己存实测
    现象
    自己写的 /login 验过密码、SecurityContextHolder.setContext 也调了，返回 200；响应里却没有 Set-Cookie，下一个请求 401（⑤ nosave）。从 Boot 2 升到 3 的老代码最常见。
    根源
    Security 6 的 SecurityContextHolderFilter 只在请求开始时取，请求结束就清空 ThreadLocal，不会替你存进会话。Security 5 的 SecurityContextPersistenceFilter 会自动存，所以老写法在 5 上能用。
    做法
    登录成功后调 securityContextRepository.saveContext(ctx, req, res)（HttpSessionSecurityContextRepository）；或者干脆用 formLogin / 自定义 AbstractAuthenticationProcessingFilter，它们会存。
    坑 2同一个人，带 JWT 调接口就 403← ④-3 scope 翻译成 SCOPE_实测
    现象
    取消订单写的是 @PreAuthorize("hasAuthority('order:pay')")。1024 用会话调，200；换成 JWT（payload 里明明有 scope=order:pay），403（⑤ scope）。
    根源
    JwtGrantedAuthoritiesConverter 默认读 scope 或 scp 声明，每个值加上前缀 SCOPE_，所以权限名是 SCOPE_order:pay。会话那条路的权限直接来自 UserDetails，没有前缀。
    做法
    团队定一种：表达式写 hasAuthority('SCOPE_order:pay')；或者给 JwtGrantedAuthoritiesConverter 设 setAuthorityPrefix("")（要读别的声明再加 setAuthoritiesClaimName），装进 JwtAuthenticationConverter，交给 oauth2ResourceServer(o -> o.jwt(j -> j.jwtAuthenticationConverter(…)))，让两条路的权限名一致。
    坑 3登出了，抄走的令牌照样能付款← ④-4 无状态的代价实测
    现象
    会话登出后，旧 JSESSIONID 立刻 401；JWT 的“登出”只是 App 把令牌删了，别人手里那一份在 exp 之前一直 200（⑤ logout）。
    根源
    验 JWT 只看签名和时间，不查任何存储，服务端没有地方记下“这张作废了”。这正是它快、能跨服务的原因。
    做法
    有效期短（5～15 分钟），配刷新令牌；刷新令牌存服务端，登出、改密码时删掉。必须立刻踢人的场景，见第三圈的三种撤销办法。
    坑 4令牌过期了 30 秒，还能付款← ④-3 时间偏差实测
    现象
    集成测试想验证“过期就 401”，签了一张过期 30 秒的令牌，结果 200；过期 90 秒才 401 Jwt expired at …（⑤ expired）。
    根源
    JwtTimestampValidator 默认允许 60 秒时钟偏差，因为签发和验证往往不在一台机器上，时钟总有点差。
    做法
    测试里按“过期超过 60 秒”来造；确实要收紧，自己组装校验器：new JwtTimestampValidator(Duration.ofSeconds(5))，用 JwtValidators.createDefaultWithValidators 或 DelegatingOAuth2TokenValidator 交给 jwtDecoder.setJwtValidator。
    坑 5登录前后，会话号没换← ④-2 自己写的登录实测
    现象
    用户在登录前访问过公开页，拿到会话号 462B2B…；登录后还是 462B2B…（⑤ fixation）。如果这个号是攻击者事先塞给受害人的，受害人一登录，攻击者手里的号也成了已登录。这叫会话固定。
    根源
    换号由 SessionAuthenticationStrategy（默认 ChangeSessionIdAuthenticationStrategy）做，调它的是 Security 自带的登录过滤器（AbstractAuthenticationProcessingFilter）。自己写的登录接口不经过它。
    做法
    登录成功后调 request.changeSessionId()（⑤ 里 rotate=true，换成了 455135…），或者注入并调用 SessionAuthenticationStrategy.onAuthentication。
    坑 6越权被拦了，响应头却说“scope 不够”← ④-5 第二道门实测
    现象
    1025 付 9527 被 403，响应头是 Bearer error="insufficient_scope"（⑤ idor）。前端和排查的人去查 scope 配置，其实是数据归属不对。更糟的是忘了写 @PreAuthorize：URL 规则只看登录没登录，1025 就付成了。
    根源
    资源服务器的 BearerTokenAccessDeniedHandler 对所有 403 都写 insufficient_scope，它不知道拒绝的原因是哪条表达式。
    做法
    归属检查每个按 id 操作的接口都要有，写进团队的接口模板；需要给前端明确原因的，在 @ControllerAdvice 里接 AuthorizationDeniedException 自己写错误体。
    第二圈

    使用规范

    • 密码只在登录接口验。对外 API 不开 httpBasic。防的是全景里每个请求 83 ms 和密码满天飞。
    • 密码编码器用 PasswordEncoderFactories.createDelegatingPasswordEncoder()，存带前缀的哈希；换算法、调 cost 时，靠 upgradeEncoding 在用户下次登录时逐个升级。防的是一次性迁移全库密码（做不到，原文没存）。
    • cost 在生产机器上量一次再定，让单次登录在几十到几百毫秒之间；登录接口单独限流。防的是慢哈希被人用来打满 CPU。
    • 访问令牌 5～15 分钟，刷新令牌存服务端、可作废、用一次换一个新的。防坑 3。
    • HS256 密钥至少 256 位，放配置中心或 KMS；多个服务要验签时改用 RS256 / ES256：只有认证服务拿私钥签，其余服务只拿公钥验。防的是任何一个下游服务泄露密钥，就能替任何人签令牌。
    • payload 只放身份和权限，不放手机号、余额。它只是 Base64，谁都能解开。
    • 按 id 操作的接口一律做归属检查（@PreAuthorize 或 Service 里查）。防坑 6 的越权。
    • 浏览器 + 会话 cookie 的接口保留 CSRF 防护；令牌放 Authorization 头、不放 cookie 的纯 API 才可以关。浏览器会自动带 cookie，不会自动带 Authorization 头。
    第三圈

    优化和深处

    1. CPU 账：慢哈希放在哪里付

    BCrypt 一次 83 ms 几乎全是 CPU。按每秒 50 个付款请求算（估算）：每个请求都验密码，要 50 × 0.083 ≈ 4.2 个核一直满着；改成登录验一次，假设用户平均一次登录付 10 单，验密码只剩 0.42 个核，每个请求验签名那 0.6 ms 的整段处理（含过滤器链）加起来约 0.03 个核。省下的不是“快了几十毫秒”，是机器数。

    2. 撤销 JWT 的三种办法，各退回一点“状态”

    办法怎么做代价
    短有效期 + 刷新令牌访问令牌 5～15 分钟，刷新时查服务端的刷新令牌表最长要等一个有效期才失效
    黑名单令牌里放 jti，登出时写进 Redis，过期时间 = 令牌剩余寿命；自定义 OAuth2TokenValidator 查它每个请求多一次 Redis，又回到“查存储”
    版本号用户表存 token_version，令牌里也带一份；改密码、踢下线时 +1，验证时比对每个请求要读用户的版本（可缓存），一次作废该用户全部令牌

    3. 当前用户在别的线程里是空的

    SecurityContextHolder 默认策略是 MODE_THREADLOCAL（源码 SecurityContextHolder.initializeStrategy）。付款成功后用 @Async 发通知、或者丢进自己的线程池，那个线程里 getAuthentication() 是 null（按源码推，本页没跑）。要带过去，用 DelegatingSecurityContextExecutor / DelegatingSecurityContextRunnable 包一层；MODE_INHERITABLETHREADLOCAL 只在新建线程时复制，对线程池里复用的线程不可靠。异步和线程池本身见@Async 与线程池。

    下一圈

    • OAuth2 授权服务器：用 Spring Authorization Server 签发令牌，订单服务只当资源服务器，RS256 + JWK Set 自动轮换密钥
    • 刷新令牌的轮换和重放检测：同一个刷新令牌被用两次时，怎么判断是被偷了
    • 网关统一认证：在 Spring Cloud Gateway 验一次 JWT，下游服务还要不要再验
    • 方法安全的深处：@PostAuthorize、@PostFilter，AuthorizationManager 自定义，和事务代理谁在外层
    • 登录接口防暴力破解：按账号和 IP 限流、失败锁定、验证码，和慢哈希一起算 CPU 账
    • 会话集群：Spring Session + Redis 的数据结构、过期通知，和 J07 Redis 那一站连起来

    ↺回到 ⑤：在订单服务上改四处

    1. 1配一个 JwtAuthenticationConverter（里面的 JwtGrantedAuthoritiesConverter 前缀设成空串），挂到 oauth2ResourceServer 的 jwt 上，跑 scope：带 JWT 的那一行应该从 403 变成 200（坑 2）。
    2. 2给令牌加 jti，登出接口把它放进一个内存黑名单，写一个 OAuth2TokenValidator<Jwt> 查它，跑 logout：JWT 那一行应该变成 401，error_description 里是你写的原因（坑 3、第三圈 2）。
    3. 3把时间偏差收紧到 5 秒，跑 expired：过期 30 秒那一行变成 401（坑 4）。
    4. 4让 /login/session 默认就 changeSessionId()，跑 fixation：两次的 sessionBefore 和 sessionAfter 都不一样（坑 5）。

    自测

    1. 用一句话说出这一页的精华。

    慢哈希只在登录时付一次，换一张验起来快的通行证（会话或 JWT）；认出“是谁”之后，还要按数据判断“是不是他的”。

    2. 每个请求带 Basic 头，疼在哪？为什么不能把 BCrypt 换成 SHA-256 了事？

    每个请求 83 ms CPU、App 要存明文密码、没法单独让一台设备下线（②）。SHA-256 太快，偷库的人离线猜也一样快；BCrypt 的慢是故意的，用来防这件事（④-4 其一）。

    3. 坑 1 里，Security 5 上能用的登录代码，为什么到 6 就 401？

    ④-2 b：6 的 SecurityContextHolderFilter 只取不存，请求结束 ThreadLocal 被清空，会话里什么都没有；5 的 SecurityContextPersistenceFilter 会在响应时自动存。

    4. 预测：把 BCrypt cost 从 10 调到 12，登录接口和带 JWT 的付款接口各会怎样？

    登录一次从约 83 ms 变成约 330 ms（cost 每加 1 翻倍，④-4 的实测表）；付款接口不变，它只验签名，根本不碰密码。老用户下次登录时，upgradeEncoding 发现 cost 低了，会顺手把哈希升级成 cost 12（④-2 a）。

    5. 预测：订单服务扩成两台，前面轮询负载均衡，没有 Spring Session。用会话登录和用 JWT 登录，第二个请求分别会怎样？

    会话：第二个请求有一半概率落到另一台，那台的 HttpSession 里没有这个号，401。JWT：两台用同一把密钥验签，哪台都 200。这就是 ④-4 其二里“状态放哪”的约束。

    6. 放回全景：第 3 站前后各发生了什么？如果第 3 站验签失败，或者第二道门的 @PreAuthorize 漏写了，整条链路会怎样？

    前面是第 2 站：Tomcat 工作线程接下请求、先过我们的 TimingFilter；后面是第 4 站 DispatcherServlet 找到 pay 方法。验签失败：在第 3 站就 401，第 4～10 站都不发生，不占数据库连接，Controller 根本没进。漏了 @PreAuthorize：第 3 站认出的是 1025，URL 规则放行，第 6～9 站照常开事务、发 UPDATE、提交，9527 被别人付了，日志里一切正常，只有对账时才发现。

    档位：标准。本机实测：2 核 ARM Linux，OpenJDK 17.0.21，Spring Boot 3.5.16（Spring Framework 6.2.19、Tomcat 10.1、Spring Security 6.5.11、Nimbus JOSE + JWT）。⑤ 的输出原样摘自 TokenLab，十三个场景跑了 1 遍，bench 和 bcrypt 跑了 2 遍；全景的 87 ms 和 82.7 ms 来自全景页的实测。第三圈第 1 条的 CPU 账是估算，第 3 条（异步线程拿不到当前用户）按源码推，没有跑。
