代理里那十几层在干什么：一个代理挂一条排好的链，谁在外层谁就包住谁

Controller 调 orderService.pay(9527)，中间夹了 11 层（热身后）。这些层不是一个代理套一个代理：一个 bean 只有一个 CGLIB 子类，里面挂着一条启动时就按 order 排好的拦截器链。每次调用，用一个下标从外往里走一遍，再原路退出来。所以排序决定了行为：计时切面排在事务外面，量出来的时间才包含提交；@Async 总是插在第 0 位，事务就开在 task-1 线程里。代理本身每次只花一两百纳秒，贵的是拦截器里做的事。

①为什么需要：一次调用，要按对的顺序穿过好几样横切逻辑

在全景第 6 站，这一步要解决的是：Controller 调 orderService.pay(9527) 的这一下，要把事务（第 7 站）、日志计时、权限、异步这些横切逻辑按对的顺序套上去，而且每次调用都要足够便宜。上一圈讲了替身怎么做出来（JDK 代理、CGLIB 子类）。这一圈打开替身看看：调用栈里那十几层分别是谁，谁先谁后，各花多少时间。

真正干活的只有 4、5 两层（事务），其余都是“把调用送进去、再送到原始对象”的管道。这一页要回答：管道为什么长成这样；再多加一个切面会插在哪；这些管道每次调用花多少钱。

②没有它会怎样：手写装饰器，一层套一层

不用 Spring AOP，同样想给付款加上事务和计时，最直接的办法是手写装饰器：每加一种横切逻辑，就在外面再套一个类。

手写装饰器

OrderApi api = new TimingOrderApi(        // 最外层：计时
                 new TxOrderApi(           // 中间：事务
                   new OrderServiceImpl(), txManager));
// TxOrderApi 里：
public String pay(long id) {
  var tx = txManager.getTransaction(def);
  try { var r = inner.pay(id); txManager.commit(tx); return r; }
  catch (RuntimeException e) { txManager.rollback(tx); throw e; }
}

疼在哪

  • 每个装饰器都要把接口里所有方法实现一遍，就算只想拦一个
  • N 个服务 × M 种横切，就是 N×M 个类
  • 顺序写死在 new 的嵌套里：想让计时排进事务里面，得改装配代码
  • 同一种横切（比如事务）的规则散在各个装饰器里，没法按注解统一配置

缺的那一块：横切逻辑只写一次（一个拦截器），用规则（切点）决定拦哪些方法，所有拦截器按一个全局的 order 排成一条链，挂在一个代理上。典型误用：以为加了一个 @Around 计时切面，量到的就是“整笔付款”的耗时。实际上不写 @Order 时，它排在事务里面，开事务和提交都没算进去（⑤ 实测，见 坑 1）。

③相邻方案：套壳的三种做法

都是“在方法前后插代码”，区别在插在哪：插在另一个对象上，还是直接插进这个类的字节码里。

做法顺序由谁定this.pay() 拦得住吗要额外的工具吗每次调用的开销
手写装饰器new 的嵌套顺序拦不住不要一次普通方法调用，几乎为零
Spring AOP：一个代理 + 一条链
Spring 默认		每个 Advisor 的 order，启动时排好拦不住（调用没经过代理）不要，运行时生成 CGLIB 子类一两百纳秒（⑥ 实测）
AspectJ 织入
编译期 ajc，或加载期 -javaagent；事务可以配 @EnableTransactionManagement(mode = ASPECTJ)		切面的优先级声明拦得住：通知代码直接织进了 OrderService 的字节码，没有代理对象要：编译器插件或 Java agent，外加 spring-aspects接近直接调用

选择规则：默认用 Spring AOP，它最大的好处是什么都不用装。只有必须拦住自调用、private 方法，或者不归容器管的对象时，才值得上 AspectJ 织入，代价是构建和启动都要多一道工序。本页学 Spring AOP 的那条链。

④原理：启动时排好一条链，调用时用一个下标走完它

分两个时刻看：启动时，链是怎么拼出来、怎么排序的；调用时，链是怎么被一层层走完的。最后看为什么 Spring 不用“一层套一层”的做法。

先知道这些
  • 替身：Boot 默认用 CGLIB 生成 OrderService 的子类，重写每个能重写的方法；替身手里拿着原始对象（target）。上一圈。
  • 替身什么时候换进去：在 bean 初始化的最后一步，由自动代理创建器（一个 BeanPostProcessor）完成。代理是哪一刻换进容器的。
  • Advisor = 切点 + 通知：切点（Pointcut）决定拦哪些类、哪些方法，通知（Advice）决定拦下来做什么。
  • MethodInterceptor：AOP 联盟定的统一接口，只有一个方法 Object invoke(MethodInvocation inv)。事务、@Async、缓存、方法级权限，以及 @Around 切面，最后都变成它。

④-1 启动时：过筛、加头、排序，只做一个代理

排序有两层。切面和切面之间看 order：@Order、Ordered 接口，事务的 order 用 @EnableTransactionManagement(order = …) 配，默认是 Ordered.LOWEST_PRECEDENCE。同一个切面里的几个通知，按通知类型排：Around、Before、After、AfterReturning、AfterThrowing（spring-aop 6.2.19 ReflectiveAspectJAdvisorFactory）。不写 @Order 的切面也是 LOWEST，和事务打平手：实测是事务在外层，但官方文档说两个不同切面的顺序在不指定时是未定义的，不能依赖。

④-2 调用时：一个下标，从外往里走，再原路退出来

ReflectiveMethodInvocation.proceed()spring-aop 6.2.19，删去注释
public Object proceed() throws Throwable {
  // 下标从 -1 开始；走到末尾就去调原始对象
  if (currentInterceptorIndex ==
      interceptors.size() - 1) {
    return invokeJoinpoint();   // 反射调 target
  }
  Object next = interceptors.get(++currentInterceptorIndex);
  if (next instanceof InterceptorAndDynamicMethodMatcher dm) {
    // 动态切点：拿真实参数再判一次
    if (dm.matcher().matches(method, targetClass, arguments))
      return dm.interceptor().invoke(this);
    return proceed();           // 不匹配就跳过这一层
  }
  return ((MethodInterceptor) next).invoke(this);
}
每个拦截器长这样
Object invoke(MethodInvocation inv) {
  前置();                   // 进来时做
  try { return inv.proceed(); }  // 交给下一层
  finally { 后置(); }        // 出去时做
}

这就是全部的魔法：没有递归的代理，只有一个对象（这次调用的 MethodInvocation）里的一个下标。每个拦截器调一次 inv.proceed()，下标就往里走一格。拦截器什么时候调、调不调、调几次，决定了里面的层跑不跑、跑几次：事务在 proceed() 前开、后提交；@Async 把 proceed() 打包成任务丢给线程池；@Cacheable 命中缓存就干脆不调。外层的 finally 一定比里层晚执行，所以“谁在外层谁就包住谁”。

④-3 为什么这样设计：一个代理一条链，而不是一层套一层

Spring 选的：一个代理，一条排好的链

  • 每个 bean 只生成一个子类、一个代理对象；后来的 @Async、@Validated 也只是往这条链里插一个 Advisor
  • 顺序只看 order，和“哪个 BeanPostProcessor 先执行”无关；排查时 getAdvisors() 一眼看全
  • 链按方法缓存：pay() 有计时，cancel() 没有，各查各的；空链就跳过链，直接反射调原始对象
  • 下标在运行时走，动态切点（比如 args(id, ..) 要看真实参数）才有地方判断

放弃的：每种横切各包一层代理

  • 每包一层，就多生成一个子类、多一个对象；栈里的“替身”也跟着多几层
  • 顺序由“谁最后包”决定，也就是 BeanPostProcessor 的执行顺序，切面自己的 @Order 管不着
  • 外层代理拿到的“目标”是里层代理，getClass()、按类型注入、拆代理拿原始类，越套越乱
  • 想看“这个 bean 上到底挂了什么”，得一层层剥开

决定胜负的约束：横切能力来自互不认识的模块（spring-tx、spring-context 的 @Async、Spring Security、你自己的 @Aspect），它们要能随意组合，而且顺序可配。统一成 MethodInterceptor，再按 order 排成一条链，是组合成本最低的做法。代价也正好在这里：链长在代理身上，没经过代理的调用（this.pay()）一层都碰不到。源码里也写明了这个选择：AbstractAdvisingBeanPostProcessor 碰到已经是代理的 bean，注释写的是 “Add our local Advisor to the existing proxy's Advisor chain”。

最少的 API

@Aspect @Component

public class TimingAspect {

  public Object time(ProceedingJoinPoint pjp) throws Throwable {
    long t0 = System.nanoTime();
    try { return pjp.proceed(); }           // 恰好调一次，异常原样抛
    finally { log.info("{} {} µs", pjp.getSignature().getName(), (System.nanoTime() - t0) / 1000); }
  }
}

⑥细节：顺序就是语义

上一圈列过“替身管不到的地方”（this 调用、final、private、自己 new 的对象……），这里不重复，见 AOP 代理那页。这一圈的四个坑，都出在链本身：谁在外层，链怎么拼出来，proceed() 调几次。

第一圈

注意事项

坑 1计时切面量出来的耗时，没算开事务和提交← ④-1 排序实测
现象
接口的总耗时和切面日志里 pay 的耗时对不上，中间差的那一截找不到。数据库提交变慢时，切面日志也看不出来。
根源
切面不写 @Order 就是 LOWEST，和事务打平手。平手时 Spring 的 Advisor bean 排在 @Aspect 前面，于是事务在外层、计时在里层（⑤ chain：进来时有事务=true）。全景实测，开事务约 0.07 ms、提交 0.20 ms，这两段都在计时范围之外。而且平手的顺序文档没有保证。
做法
每个自定义切面都显式写 @Order。要量整笔业务就写一个小于 LOWEST 的数（⑤ order0：进来时有事务=false）；要放进事务里面，就把事务调前，@EnableTransactionManagement(order = …)。
坑 2@Async 和 @Transactional 叠在同一个方法上，付款回滚了，通知照发← ④-1 插到第 0 位实测
现象
pay() 里调 notifyService.onPaid()，后来金额校验失败，付款整单回滚，可短信已经发出去了。
根源
AsyncAnnotationBeanPostProcessor 把 @Async 的 Advisor 插在链的第 0 位（⑤ async）。调用一进代理就被打包成任务，交给 task-1；事务拦截器在 task-1 里才执行，开的是一个新事务，和调用方的事务没有任何关系。
做法
“提交以后才做”的副作用，用 @TransactionalEventListener（默认在提交后执行）加 @Async，像全景第 10 站那样；@Async 方法自己的 @Transactional，只管它在 task-1 里写的数据。
坑 3切点写太宽：启动变慢，甚至启动失败← ④-1 过筛按源码
现象
写了 execution(* com.trade..*.*(..)) 记日志，结果配置类、各种工具 bean 也都被换成了代理。碰到 final 类（比如一个 record 被声明成了 bean），启动直接失败：Could not generate CGLIB subclass of class … Common causes of this problem include using a final class or a non-visible class。
根源
④-1 的过筛是按类做的：一个类只要有一个方法匹配，就给它生成代理。切点越宽，被代理的 bean 越多，启动时要生成的子类也越多；之后每个方法第一次被调时，还要再按方法筛一遍。
做法
用注解圈定范围：@annotation(Timed)，或者 within(com.trade.order..*) && @annotation(…)。启动后打印 AopUtils.isAopProxy 为 true 的 bean，确认没有多出来的。
坑 4重试切面放在事务里面，重试的还是同一个事务← ④-2 下标按源码
现象
自己写的 @Around 重试切面，捕获异常后再调一次 pjp.proceed()。死锁以后重试三次都失败，或者第一次写进去的半截数据和第二次的叠在了一起。
根源
pjp.proceed() 每调一次，都会把当前的调用对象克隆一份（invocableClone()），从当前下标往里再走一遍。重试切面在事务里面时，再走的只有目标方法，三次重试都在同一个事务里，而这个事务可能已经被数据库判了死刑。
做法
重试切面的 order 要小于事务的，放在外层，每次重试都是一个新事务。用 Spring Retry 或 Resilience4j 的注解时，也要检查它们和事务谁在外层。
第二圈

使用规范

每个切面都写 @Order，并写清它在事务的哪一边

防：平手时顺序未定义，升级或多加一个切面以后，顺序悄悄变了（坑 1）。

切点用注解圈定，不用整个包的 execution

防：误代理、启动慢、final 类启动失败（坑 3）。

@Around 里 proceed() 恰好调一次，异常原样抛出

防：业务跑两次；外层事务以为成功了，照常提交。重试切面是唯一的例外，而且必须放在事务外面（坑 4）。

提交后才做的事，用事务事件，不在事务方法上叠 @Async

防：回滚了，副作用照样发生（坑 2）。

排查顺序问题，先打印 getAdvisors()

防：靠猜。一行代码就能看到整条链，比读配置可靠。

第三圈

优化和深处

每多一层要多少钱：一两百纳秒，贵的是拦截器里做的事

直接调用目标0.4 ns
代理，链是空的58 ns
代理 + 1 个拦截器128 ns
代理 + 3 个拦截器135 ns
代理 + 10 个拦截器161 ns
代理 + 1 个 @Around 切面206 ns

实测 ProxyBench：ProxyFactory 直接造 CGLIB 代理，拦截器都是什么也不做的 inv -> inv.proceed()；每组预热 3 轮，再跑 5 轮、每轮 500 万次，取中位数；整组跑了 2 遍，相差不到 3%。这是粗测，不是 JMH，只看数量级。直接调用的 0.4 ns 是被 JIT 内联以后的结果。

空链也要 58 ns

按方法查链（新建一个 MethodCacheKey，查 ConcurrentHashMap），再用 Method.invoke 反射调目标，参数还要装进 Object[]。JIT 没法把这一串内联掉。

第一个拦截器 +70 ns，之后每个 +3～4 ns

有拦截器就要新建一个 ReflectiveMethodInvocation，这一下最贵；之后每加一层，只是多一次下标加一和一次接口调用。

@Around 比原生拦截器贵 80 ns

要多反射调一次切面方法，还要新建 ProceedingJoinPoint，⑤ 的栈里多出 8 层就是这些。热点上的切面可以写成 MethodInterceptor + Advisor。

放回全景算账：全景实测“第 6、7 站：代理 + 开事务”一共 0.07 ms，也就是 70 000 ns，其中代理链只占 100 多 ns，剩下的是事务借连接、关 autocommit。整个请求要 2.4 ms。要优化，看拦截器里做了什么：事务范围、连接池、缓存命中率。别去数代理有几层。

链按方法缓存；动态切点每次都要再判一次

AdvisedSupport.getInterceptorsAndDynamicInterceptionAdvice 按 Method 把算好的拦截器列表缓存在 methodCache 里：每个方法第一次被调时，遍历所有 Advisor 做方法级匹配，以后直接查表。只有一种情况每次都要重新算：切点要看真实参数，比如 args(orderId, ..) 绑定参数，或者 this(…)、target(…) 的部分写法。这类拦截器在链里会被包成 InterceptorAndDynamicMethodMatcher，每次走到它时，都用这一次的参数再判一次（④-2 代码里的那个 if）。只用注解圈定的切点，都是静态匹配。

版本差异：栈的样子会变，链的规则没变

Spring 6.1 及以前Spring 6.2 / 7.0
“调用”对象CglibAopProxy$CglibMethodInvocation，继承 ReflectiveMethodInvocation，重写了 proceed()（6.1.21 jar 里有这个类）。栈里每一格 proceed 大概会多出它这一帧，这是按字节码推的，没有实测这个类删了，直接用 ReflectiveMethodInvocation，调目标统一走 AopUtils.invokeJoinpointUsingReflection（6.2.19、7.0.10 jar 里都没有）
排序、插 @Async、Expose、按方法缓存一样（本页的规则 6.x 通用）
JDK 17JDK 18 及以后（21）
反射那几层前 15 次走 native：Method.invoke → DelegatingMethodAccessorImpl → NativeMethodAccessorImpl.invoke → invoke0，4 层；之后生成 GeneratedMethodAccessorN，3 层（阈值 inflationThreshold = 15，见 JDK 17 ReflectionFactory，实测 冷 4 层、热 3 层）JEP 416 把核心反射改成用方法句柄实现，栈里换成 DirectMethodHandleAccessor，没有“膨胀”这一步（按 JEP 文档，本页没在 21 上跑）

    ↺回到 ⑤：在订单服务上改三处

    都在 spring-aop-chain 里改，改完跑同一条命令，看输出是否和预期一致。

    练习 1 · 用坑 1 的做法，量出提交花了多少

    在 payTimed 前热身 50 次，再分别用默认顺序和 --lab.timing-order=0 各量 1000 次，取中位数。预期：order0 的数更大，两者的差就是“开事务 + 提交”的耗时，和全景里 0.07 + 0.20 ms 是一个量级（H2 内存库会更小）。

    练习 2 · 写一个重试切面，验证坑 4

    写 RetryAspect：捕获异常，最多重试 3 次。让 pay 每次先往 pay_log 表插一行，前两次插完就抛异常。预期：重试切面写 @Order(0) 时，pay_log 里只剩 1 行，前两次跟着各自的事务回滚了；不写 order 时有 3 行，三次都在同一个事务里，最后一起提交。

    练习 3 · 用坑 2 的做法，让回滚以后不发通知

    去掉 NotifyService.onPaid 上的 @Async @Transactional，pay 里改成发布 OrderPaid 事件，监听器用 @Async @TransactionalEventListener。预期：pay 抛异常回滚时，监听器一次都不执行；正常提交时，它在 task-1 上执行。

    自测

    1. 用一句话说出这一页的精华。

    一个 bean 只有一个代理，里面挂一条启动时按 order 排好的拦截器链；每次调用，ReflectiveMethodInvocation 用一个下标从外往里走，每个拦截器调一次 proceed() 交给下一层，所以外层包住里层，顺序就是语义。

    2. 手写装饰器做横切，最疼的是哪两点？

    N 个服务 × M 种横切要写 N×M 个类，每个都要实现接口的全部方法；顺序写死在 new 的嵌套里，改顺序就要改装配代码（②）。

    3. 坑 1 里，计时切面为什么量不到提交？

    ④-1 的排序：不写 @Order 就是 LOWEST，和事务平手，平手时 Spring 的 Advisor bean 排在 @Aspect 前面，所以事务在外层。按 ④-2，提交发生在事务拦截器的 proceed() 返回之后，这时计时切面的 finally 早就执行完了。

    4. 预测：在 payTimed 上再加一个什么也不做的 @Around 切面（@Order(5)），热身后 Controller 和 payTimed 之间夹几层？

    31 层。热身后原来是 22 层（实验台“加计时，不写 @Order”可以算出来）。一个 @Around 要多出 9 层：1 格 proceed、AspectJAroundAdvice.invoke、两层 invokeAdviceMethod…、3 层反射、切面方法自己、MethodInvocationProceedingJoinPoint.proceed。Expose 已经有了，不会再加一个。（④-1、⑤ 的 timed 栈）

    5. 预测：@Cacheable 和 @Transactional 叠在同一个方法上，缓存拦截器在外层，缓存命中时，这次调用会借数据库连接吗？

    不会。缓存拦截器命中时直接返回缓存值，不调 proceed()，里层的事务拦截器根本没执行，也就不会借连接。反过来，事务在外层的话，命中缓存也会先开一个空事务、借一次连接。（④-2：拦截器调不调 proceed()，决定里面的层跑不跑）

    6. 放回全景：第 6 站前后各发生了什么？这一页讲的东西坏了，整条链路会怎样？

    第 6 站之前是第 5 站：DispatcherServlet 解析完参数，用反射调了 OrderController.pay，Controller 再调它手里的 orderService，其实是代理。第 6 站之后是第 7 站：事务拦截器借连接、关 autocommit，然后才进第 8 站的 Mapper 代理。这一页的东西坏了，大多不报错。链没走到（自调用）：第 7 站不开事务，第 8、9 站每条 SQL 自动提交，金额不符时订单照样变成 PAID。链的顺序错了：计时漏算提交，监控看不出数据库变慢；@Async 叠在事务方法上，回滚了短信照发；重试切面在事务里，死锁以后重试也救不回来。
