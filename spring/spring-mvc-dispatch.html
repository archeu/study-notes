一个 400 进了两次 DispatcherServlet：过滤器链按“分派”搭，出错时同一个请求再走一遍

Servlet 容器处理的单位不是“一个 HTTP 请求”，而是一次分派。正常情况一次 REQUEST；有人调了 sendError 或者异常没人接，Tomcat 会把同一个请求对象再分派一次到 /error，这次叫 ERROR。每个过滤器登记了自己接哪几种分派，OncePerRequestFilter 还会自己跳过 ERROR；拦截器不看分派类型，只要进了 DispatcherServlet 就会被调。弄清这一层，“拦截器调了两次”“公开接口出错，用户看到 401”“过滤器的异常 @RestControllerAdvice 接不住”这些坑都能推出来。

①为什么需要：全景实测里留下了三个没解释的现象

在全景第 4、5 站，这一步要解决的是：把 POST /orders/9527/pay 变成一次方法调用，把 JSON 变成 PayRequest，出错时给 App 一个统一的错误体。上一圈讲了正常那一趟怎么走。全景实测里却有三件事，用“一个请求走一趟”解释不了。

这一圈只看 Web 这几站：同一个订单服务，去掉数据库，专门看一个请求在 Tomcat、过滤器、Security、DispatcherServlet 之间走了几遍、每遍谁出场、时间花在哪。

②没有这一层会怎样：用“一个请求走一趟”去推，会推错

上一圈的模型是一条直线：过滤器 → DispatcherServlet → 拦截器 → Controller → 原路返回。拿它预测“金额 -1”那个请求，会得出拦截器调 1 次。实测是 2 次。

第一圈的模型 一个请求，一趟

实测 ⑤ 的 bad 场景

[REQUEST] Interceptor  preHandle → OrderController#pay
[REQUEST] Interceptor  afterCompletion status=400
[REQUEST] PlainFilter  出 status=400 committed=true
[ERROR]   ErrorAwareFilter 进 原始 URI=/orders/9527/pay
[ERROR]   Interceptor  preHandle → BasicErrorController#error
[ERROR]   Interceptor  afterCompletion status=400
→ HTTP 400 {"timestamp":…,"status":400,…}
  • 第一趟走完、过滤器都退出了，同一个请求又进来一次
  • 第二趟有的过滤器出场，有的没出场
  • 那个 JSON 错误体，是第二趟里 BasicErrorController 写的

缺的那一块：“分派”（dispatch）。容器每把请求交给过滤器链和 Servlet 一次，就是一次分派，带一个类型：REQUEST、ERROR、ASYNC、FORWARD、INCLUDE。过滤器链是按分派类型现搭的。典型误用：在拦截器里给每个请求计数、扣接口配额，参数一错就扣两次；在 Security 里只放行业务 URL，公开接口一出错，匿名用户看到的是 401 而不是 500。

③相邻方案：出错时，错误体由谁来写

第二趟只在“由容器写错误页”时才发生。同一个错误，有三处可以写响应，各自接得住的范围不一样。

谁来写接得住哪里的错会不会再走一遍交易靶场里用在哪
MVC 里的异常解析器
@ExceptionHandler、@RestControllerAdvice		只有 DispatcherServlet 里面抛出的：参数解析、Controller、返回值处理不会。在第一趟里直接写好状态码和响应体（⑤ conflict：409，拦截器 1 次）业务异常：金额不符、库存不足、订单状态不对
容器错误页
Boot 注册的 /error → BasicErrorController		任何地方：过滤器、Security、没人接的异常、任何组件调的 sendError、找不到的地址会。Tomcat 把同一个请求以 ERROR 类型再分派到 /error兜底：上面没处理的，都落到这里
过滤器自己写只有它自己和它后面的链抛出的、它 catch 住的不会，只要它自己写完响应、不往外抛限流、签名校验这类在 MVC 之外就要拒绝的

选择规则：业务能预料的错，在 @RestControllerAdvice 里写完，一趟结束；/error 只当兜底，而兜底那一趟会再过一次过滤器、Security 和拦截器，这些组件都要知道自己可能被调第二次。本页学的就是这第二趟：它什么时候发生，谁会出场。

④原理：过滤器链每次分派现搭，出错时 Tomcat 再分派一次

先知道这些
  • 过滤器链：Servlet 规范的 Filter.doFilter(req, res, chain)，过滤器调 chain.doFilter 就交给下一个，不调就拦下了。三道门的分工见请求关卡。
  • DispatcherServlet：Spring MVC 唯一的 Servlet，doDispatch 八步见上一圈。拦截器是它里面的东西，不归 Tomcat 管。
  • 分派类型（jakarta.servlet.DispatcherType）：REQUEST 客户端发来的原始请求；ERROR 容器为显示错误页而分派；ASYNC 异步处理完回到容器；FORWARD、INCLUDE 由 RequestDispatcher 转发、包含。request.getDispatcherType() 能读到当前是哪种。
  • 同一个请求对象：再分派时 request、response 还是原来那两个对象，请求属性（attribute）都还在，第二趟能读到第一趟留下的东西。

两层开关叠在一起：Tomcat 搭链时按登记的分派类型筛一次，过滤器自己再判断一次。普通 Filter 交给 Boot 注册，只接 REQUEST；OncePerRequestFilter 被登记成全部类型，靠自己跳过 ERROR 和 ASYNC，想干活就覆盖 shouldNotFilterErrorDispatch() 返回 false（RequestContextFilter 就是这么做的）。Security 的 11 个过滤器对 Tomcat 来说只是第 7 个 springSecurityFilterChain，顺序是 -100（spring.security.filter.order）；里面再用 FilterChainProxy 自己的一条链挨个调。

④-3 为什么这样设计：错误页交给容器，用再分派来画

容器再分派到错误页 Servlet 规范的做法

  • 谁都能触发：过滤器、Security、任何 Servlet、Tomcat 自己（找不到地址）。只要调了 sendError 或者异常一路抛到容器，错误页都能接住
  • 错误页复用整条管道：编码、请求上下文、安全上下文、MVC 的内容协商和 JSON 写出，BasicErrorController 就是一个普通 Controller
  • 代价：所有挂在链上的东西，都可能对同一个请求被调第二次

放弃的做法：出错的地方当场写错误体

  • 每个过滤器、每个框架都得自带一套错误格式，同一个服务吐出好几种错误 JSON
  • Tomcat 不认识 Spring，它自己发现的错误（比如 Servlet 抛异常）没法交给 Spring 去写
  • 错误体还要做内容协商（浏览器要 HTML，App 要 JSON），每处都要重写一遍

决定胜负的约束：错误可能来自 Spring 之外，而只有容器看得到全部出口。所以 Servlet 规范让容器负责“出错之后怎么办”，再把画错误页这件事用一次分派交还给应用。分派类型就是为这个代价准备的标签：组件看一眼 getDispatcherType()，就知道这是同一个请求的第几趟、该不该再做一遍。Spring Security 6 起对每一种分派都做授权（5.x 只查第一趟），同时把认证结果存进请求属性（RequestAttributeSecurityContextRepository），让无状态的 Basic、JWT 请求在第二趟也认得出是谁。

⑥细节·规范·优化

第一圈

注意事项：不知道就会出事故的坑

坑 1参数一错，拦截器扣了两次配额← ④-2 再分派实测
现象
按用户计数、扣接口配额、记访问日志的拦截器，在 400、500 的请求上记了两次；第二次的 handler 是 BasicErrorController#error。
根源
拦截器在 DispatcherServlet 里面，不看分派类型：只要第二趟的 Security 放行了 /error，DispatcherServlet 第二次出场，拦截器就第二次被调（⑤ bad）。
做法
excludePathPatterns("/error")，或者在 preHandle 开头判断 getDispatcherType() != REQUEST 就直接放行。改动 server.error.path 时两处一起改。
坑 2公开接口出错，匿名用户看到的是空的 401← ④-3 每种分派都授权实测
现象
/public/** 放行了，接口里抛异常，前端收到 401，没有响应体，日志里却是 500 的堆栈。排查的人会去查登录。
根源
第二趟分派到 /error，Security 6 对 ERROR 分派照样授权；匿名用户访问 /error 不在放行规则里，被拒，原来的 500 被盖成 401（⑤ publicboom）。
做法
在安全链里加 requestMatchers("/error").permitAll() 或 dispatcherTypeMatchers(DispatcherType.ERROR).permitAll()（⑤ permit：500 和 JSON 回来了）。Boot 2 升到 3 时要专门检查这一条。
坑 3过滤器抛的异常，@RestControllerAdvice 接不住，带着账号也是 401← ④-2 第二趟谁出场实测
现象
签名校验、限流这类过滤器抛了业务异常，全局异常处理没生效；如果它排在 Security 前面，用户拿到 401，而请求明明带了正确的 Basic 头。
根源
异常抛出时还没进 DispatcherServlet，MVC 的异常解析器不在调用栈上，只能交给 Tomcat 的错误页。第一趟 Security 没走到，请求属性里没存认证结果；第二趟里认证过滤器（OncePerRequestFilter）跳过 ERROR 分派，于是是匿名用户，/error 被拒（⑤ filterboom）。
做法
过滤器自己 catch 住，直接写状态码和 JSON 错误体，不往外抛；或者把需要“当前用户”的过滤器放到 Security 后面。
坑 4一个过滤器，一个请求跑了两遍← ④-1 两处登记实测
现象
自己写的 JWT 或审计过滤器，日志一个请求打两行；token 被校验两次。
根源
类上有 @Component，Boot 把它登记到 Tomcat 的链上；又用 addFilterAfter 放进了 Security 的链。同一个对象挂在两条链上，一趟里就被调两次（⑤ audit）。
做法
只登记一处：要进安全链，就别让它成为 Boot 自动注册的过滤器（去掉 @Component，或者给它一个 FilterRegistrationBean 并 setEnabled(false)）。继承 OncePerRequestFilter 也能挡住同一趟的第二次，但那是兜底，不是解法。
坑 5错误日志里没有 traceId← ④-1 只登记 REQUEST顺序实测
现象
400、500 的请求，/error 那一趟打的日志、ErrorAttributes 里，链路 ID 是空的，和第一趟的日志对不上。
根源
放 traceId 的过滤器是普通 Filter 或默认的 OncePerRequestFilter，第二趟不出场；而第一趟它已经在 finally 里清掉了 MDC（⑤ 的输出里，PlainFilter 出 在所有 [ERROR] 行之前）。
做法
把 traceId 同时存进请求属性；过滤器登记 ERROR 分派，或者覆盖 shouldNotFilterErrorDispatch() 返回 false，第二趟从请求属性里取回同一个 ID。
坑 6chain.doFilter 返回以后，想改错误响应，改不动← ④-2 sendError实测
现象
想在过滤器里“统一包装错误体”：chain 返回后看到 status=400，往响应里写 JSON，结果写不进去，前端拿到的还是 Boot 默认的错误体。
根源
sendError 之后，应用看到的 isCommitted() 已经是 true（⑤ bad：status=400 committed=true），其实一个字节都还没发，Tomcat 留着这块地方给错误页那一趟写。
做法
要改错误格式，就在错误页那一趟改：自定义 ErrorAttributes、自己的 /error Controller，或者干脆在 @RestControllerAdvice 里把常见异常都写成统一格式，不走 sendError。
第二圈

使用规范

业务异常在 @RestControllerAdvice 里写完响应，/error 只做兜底

防：每个 400、409 都多走一趟，过滤器、Security、拦截器全部再调一遍（坑 1、坑 6）。参数校验失败也可以继承 ResponseEntityExceptionHandler 自己写 400。

过滤器一律继承 OncePerRequestFilter，要在错误页那趟干活就显式覆盖开关

防：普通 Filter 在两条链上被调两次（坑 4）；“这个过滤器第二趟到底出不出场”靠猜（坑 5）。

拦截器只做和“这次调哪个方法”有关的事，带副作用的先判断分派类型

防：计数、扣配额、写审计在错误页那趟重复（坑 1）。

安全配置里显式写出 /error 的规则，并留一个“匿名访问公开接口出错”的测试

防：升级 Boot 3 以后，真实错误被 401 盖住（坑 2）。

启动时打印一次过滤器清单：名字、顺序、分派类型

防：靠读配置推断顺序。⑤ 的 filters 场景十几行代码就能列全，比文档可靠（坑 3、坑 4）。

第三圈

优化和深处

热了 1.5 毫秒，冷的第一次 180 毫秒：时间花在哪

在过滤器、拦截器、RequestBodyAdvice、ResponseBodyAdvice 里打计时点，一个新 JVM 起服务后先测第一次请求，再热身 200 次、测 300 次取中位数。安全链用不加密的密码编码器，免得第 3 站的 BCrypt（全景实测 82 ms）盖住其他各段。跑了 2 遍，柱子是第 1 遍。热身后的数两遍每段相差不到 10%；冷的那一次波动大些，“调方法”“写 JSON”两段差到 20%～30%。

服务端合计 191 ms（第 2 遍 179 ms），客户端看到 364 ms（297 ms）。

  • 冷的贵在“第一次用到”：读 JSON 的 76 ms 是 Jackson 第一次给 PayRequest 这个 record 建反序列化器；校验的 44～49 ms 是 Hibernate Validator 第一次解析 PayRequest 上的约束、加载对应的校验器类。热了以后两段分别只剩 0.33 和 0.13 ms，说明做的是“只做一次”的事，加上类加载和 JIT。
  • 多半是 JVM 级的，不是每个容器一份：同一个 JVM 里先跑完别的场景，再新起一个 Spring 容器，它的第一次请求服务端只要 22 ms（跑过 1 次）。所以预热要在同一个进程里把真实的代码路径走一遍。
  • 客户端比服务端多出的 100 多毫秒，里面有 DispatcherServlet 的初始化（Boot 默认 spring.mvc.servlet.load-on-startup=-1，第一次请求才做）、Tomcat 和客户端第一次建连。这次没再拆开。
  • 做法：滚动发布时，就绪探针（readiness）通过之前，先在本机给关键接口发几次真实请求；load-on-startup=1 能把 DispatcherServlet 的初始化挪到启动时，但 Jackson、Validator 的“第一次”还得靠真请求触发。

↺回到 ⑤：在订单服务上改三处

都在 spring-mvc-dispatch 里改，改完跑对应的场景，看输出是否和预期一致。

练习 1 · 用坑 1 的做法，让拦截器只管第一趟

在 preHandle 和 afterCompletion 开头加分派类型判断。跑 bad npe。预期：[ERROR] Interceptor 两行消失，状态码和错误体不变。

练习 2 · 用规范第一条，让 400 在第一趟写完

加一个 @RestControllerAdvice，接 MethodArgumentNotValidException，返回 400 和 {"field":"amountCents","message":"must be greater than 0"}。跑 bad。预期：整段 [ERROR] 消失，PlainFilter 出 status=400，响应体是你写的格式。

练习 3 · 用坑 3 的做法，把限流做成过滤器

在 PlainFilter 里，请求头 X-Boom: filter 时不再抛异常，改成直接写 429 和 JSON 后 return。跑 filterboom。预期：HTTP 429，没有 [ERROR] 行，也不再是 401。

自测

1. 用一句话说出这一页的精华。

容器按“分派”处理请求，出错时把同一个请求以 ERROR 类型再分派到 /error；过滤器按登记的分派类型进链，OncePerRequestFilter 还会自己跳过 ERROR，拦截器和 Security 6 则在第二趟照样出场。

2. “一个请求走一趟”的模型，推哪件事会推错？

推出错的请求：它推不出错误体是谁写的，也推不出拦截器、Security 会被调第二次（②）。

3. 坑 2 里，为什么 500 变成了 401？

④-3：Security 6 对每种分派都授权。第二趟访问的是 /error，不在 /public/** 的放行规则里；匿名用户被 AuthorizationFilter 拒绝，入口点调 sendError(401)，原来的 500 就被盖掉了。

4. 预测：把 ErrorAwareFilter 改成继承 OncePerRequestFilter，删掉 setDispatcherTypes，金额 -1 时它出场几次？

1 次。Boot 会给它登记全部 5 种分派，第二趟它在链上；但 OncePerRequestFilter 默认 shouldNotFilterErrorDispatch() 返回 true，看到是错误分派就直接放行（④-1 的两层开关）。

5. 预测：坑 3 里，如果抛异常的过滤器排在 Security 后面（order 大于 -100），带着正确 Basic 头的用户会拿到什么？

500 和 Boot 的 JSON 错误体。第一趟 Security 已经认证过，结果存进了请求属性；第二趟认证过滤器虽然跳过，但 SecurityContextHolderFilter 从请求属性取回了用户 1024，/error 被放行（④-3），和 ⑤ 的 npe 一样。这个变体没在本机跑过，是从原理推的。

6. 放回全景：第 3 站每次 BCrypt 要 82 ms。金额 -1 的那个付款请求，一共算几次 BCrypt？第 6～10 站发生了什么？

1 次。第二趟里 BasicAuthenticationFilter 是 OncePerRequestFilter，跳过 ERROR 分派，认证结果从请求属性里取，不再校验密码。第 6～10 站什么都没发生：第 5 站校验失败，Controller 没被调用，所以没有代理、没开事务、没发 SQL、没发短信。用户看到的 400 是第 4、11 站在第二趟里由 BasicErrorController 写出来的。

档位：标准。本机实测：2 核 ARM Linux，OpenJDK 17.0.21，Spring Boot 3.5.16（Spring Framework 6.2.19、Tomcat 10.1、Spring Security 6.5.11）。⑤ 的输出原样摘自 DispatchLab，十个场景跑了 1 遍；第三圈的计时在新 JVM 里跑了 2 遍。④-2 的演示由页面里的一段规则推出，已在 node 里和八个场景的实测输出逐行对过。

按源码和文档：Tomcat ApplicationFilterFactory.createFilterChain、ApplicationFilterChain.internalDoFilter、StandardHostValve.status；Boot AbstractFilterRegistrationBean.configure、SecurityProperties.Filter、ErrorMvcAutoConfiguration.ErrorPageCustomizer、WebMvcProperties.Servlet.loadOnStartup；spring-web OncePerRequestFilter、RequestContextFilter（覆盖了两个 shouldNotFilter…Dispatch）；spring-webmvc DefaultHandlerExceptionResolver；Security AuthorizationFilter、BasicAuthenticationFilter（默认 RequestAttributeSecurityContextRepository）、SecurityContextConfigurer；Boot 3.0 迁移指南、Security 6.0 迁移文档。
