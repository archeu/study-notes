300 ms 超时，库存却冻了 2 件：时钟、超时与重试

对方没回音时，你只知道“不知道”：请求可能没到，也可能早做完了，只是回包慢。所以超时不是失败，是一次猜测；猜完只有两条路，去查，或者带着幂等键重做。重做要退避、加抖动、设上限，不然重试本身就是一场攻击。量“过了多久”只能用本机的单调时钟，墙上时钟会被 NTP 拨动，不同机器的钟也对不齐，所以比先后不能靠时间戳，要靠只增不减的版本号。

全景：一次下单跨三个库 · 第 5、8、10 站地图：J09 · 时钟、超时与重试：分布式里为什么不能信时间

这一页的位置J09 第 4 个下钻知识点。上一页分布式事务里反复出现三个时间：第 5 站 RPC 的 300 ms、第 8 站 TC 每 1 秒重推一次、第 10 站等满 60 秒判死。这一页讲它们为什么靠不住，又为什么只能这样设计。

①为什么需要：对方不回话，我等多久，等不到怎么办

在全景第 5、8、10 站，这一步要解决同一件事：隔着网络，对方没有回音。第 2 站还多一件：发号要看本机的钟，钟可能往回走。

单机里，stockService.reserve() 最坏也就是抛一个异常，你知道它没成功（事务回滚了）。跨了网络，调用多出第三种结局；跨了机器，时间也多出“谁的钟”这个问题。这一页就讲这两件事。

②没有它会怎样：把超时当失败，失败就马上重来

最自然的想法：超时就是失败，失败就重试一下。Dubbo 的默认配置就是这么做的：timeout=1000、retries=2，超时也算可重试，一次调用最多变三次。下面是⑤里的实测，库存服务每次 400 ms 才做完，订单服务 300 ms 就放弃：

  • 把超时当失败。只调一次也不对：订单服务回滚了，库存服务 100 ms 后才把 2 件冻上（⑤ 的 timeout 段）。
  • 失败就马上重来。写接口一次变三次，冻了 6 件。对方要是因为过载才慢，马上重来等于再推它一把。
  • 用 System.currentTimeMillis() 算“过了多久”。NTP 一拨，60 秒的超时可能 5 秒就到，也可能 90 秒才到。

缺的那一块：承认“不知道”是第三种结果。超时之后要么查，要么带幂等键重做；重做要有间隔、抖动、上限；量时长用单调时钟，比先后用版本号。

!不懂精华时的典型误用
一种
把超时调到 30 秒，“这样就不会超时了”。慢请求把线程、连接全占住，上游跟着一起慢，一个下游拖垮整条链路（J04 全景里的线程池）。
另一种
每一层都加“保险”的重试：网关 3 次 × 订单服务 3 次 × 库存服务调数据库 3 次，下游最多挨 27 倍的请求，偏偏发生在它最扛不住的时候。

③相邻方案：判断“死没死”，和判断“谁先谁后”

这一页其实回答两个问题。每个问题都有好几种做法，但第一个问题的做法归根到底都是超时，只是阈值怎么定不同；第二个问题的做法分成“信钟”和“不信钟”两派。

问题做法怎么做用在哪代价
它死了吗？固定超时等满 N 毫秒没回音就算失败RPC deadline 300 ms；Seata 全局事务 60 sN 要猜：短了误杀，长了干等
心跳 + 超时对方定期报平安，连续几次没收到算死Seata 客户端和 TC 的心跳；Kafka 的 session.timeout.ms还是超时，只是不用等业务请求来发现

本页学：判死用超时（固定超时最常见，心跳和租约是它的变体），判死之后用退避重试 + 幂等；量时长用单调时钟；比先后用版本号。逻辑时钟、HLC、TrueTime 列进“下一圈”。

④原理：超时只是猜测，钟只能量自己

先知道这些
  • 网络没有时间上界：同一台机器里的方法调用，最坏多久能返回心里有数；网络上的包可能排队、重传，对方进程可能在 Full GC 里停几秒。理论上叫“异步网络模型”：消息会到，但不保证多久到。
  • 两种时钟：墙上时钟（System.currentTimeMillis()、Instant.now()、new Date()）和 UTC 对齐，会被校时程序拨动；单调时钟（System.nanoTime()）只往前走，可它的起点是随意的，JDK 文档说它只在同一个 JVM 里相减才有意义。
  • NTP 校时：chrony、ntpd、systemd-timesyncd 这类程序定期和时间服务器对表。偏差小时让钟走快一点或慢一点，慢慢追上（slew）；偏差大时直接改（step），钟会一下子跳过去，或者跳回来。
  • 幂等：同一个请求做一次和做 N 次效果一样，见幂等设计。重试的前提就是它。

“不知道”之后，只有两条路：

去查读操作，总是安全

  • 调一个查询接口：“9527 冻上了吗？”查到了就当成功，查到没有再决定要不要重做。
  • 查也可能超时，所以查本身也要能重试；查不到结果的，交给对账（全景第 11 站）。

重做写操作，前提是幂等

  • 带着同一个幂等键再调一次，对方见过这个键就不再做第二遍（⑤ 实测：冻结停在 2 件）。
  • 没有幂等键就重做，就是② 里的冻了 6 件。

超时设多长？这是在两种错误里选：设短了，正常的慢请求也被判成失败，重试变多；设长了，线程和连接被慢请求占住，用户干等。常见做法是取下游的 p99 耗时再留一点余量，而且外层比内层长：网关 1 s、订单服务调库存 300 ms、库存服务查库 100 ms。更好的是把截止时间（deadline）一路传下去，下游看到“上游只剩 80 ms 了”就别再开始干活，见⑥ 坑 4。

机制 2：重试的四个零件——退避、抖动、上限、预算

重试本身没错，错在“一起、马上、不限次数”。库存服务重启 1 秒，三张单在第 0 秒同时失败，四种重试策略会这样回来：

退避一次比一次等得久给对方留出恢复的时间。常用 base × 2k，再设一个封顶 cap
抖动等多久要随机同时失败的人别同时回来。全抖动：random(0, min(cap, base·2k))
上限次数和总时长都封顶例如最多 3 次、总共不超过上游给的 deadline
预算重试占比封顶重试请求不超过正常请求的一成左右；下游大面积失败时自动停重试

再加一条前提：只重试“可能下次就好”的错误：超时、连接被拒、503 / UNAVAILABLE。“券已被用”“余额不足”这种业务错误，重试一万次结果都一样。Dubbo 就是这么分的：只有标成业务异常的 RpcException 不重试，超时会重试（FailoverClusterInvoker）。

机制 3：两种时钟。墙上时钟会跳，单调时钟只能量自己

全景第 10 站，Seata TC 判断全局事务超时的代码就一行（Seata 2.6.0 GlobalSession）：

GlobalSession.javabeginTime 在 begin() 里用 TC 自己的 currentTimeMillis() 赋值
public boolean isTimeout() {
    return (System.currentTimeMillis() - beginTime) > timeout;   // timeout 默认 60000
}

它用的是墙上时钟。平时没问题；可要是在事务进行到第 5 秒时，NTP 把 TC 那台机器的钟往前拨了 61 秒：

墙上时钟：currentTimeMillis() · Instant.now() · new Date() · LocalDateTime.now() 单调时钟：System.nanoTime() · Guava Stopwatch

跨机器呢？Seata 的 TC 是 3 台一组（全景第 3 站）。按 2.6.0 的源码，beginTime 随会话复制给 follower；leader 换了以后，新 leader 用自己的钟去减旧 leader 写下的 beginTime。两台机器的钟差多少，60 秒的判死就偏多少。为什么这样还能接受：NTP 正常时机器之间差的是毫秒级，和 60 秒差了几个数量级。阈值远大于时钟误差时，用墙上时钟可以容忍；真正危险的是 step 式的跳变，以及拿时间去比先后。

机制 4：比先后，用只增不减的数，不用时间戳

两台机器的钟哪怕只差 50 ms，“按时间戳取大的”就会把后发生的那次写丢掉：

同样的道理也解释了锁：持锁的进程 Full GC 停了 40 秒，醒来时它以为租约还在，其实早过期了，别人已经拿到锁。它自己的钟救不了它，只能让存储端检查一个只增不减的 fencing token，见锁过期与 fencing token。Raft 用 term（任期号）挡掉旧 leader，也是这个思路（J09 下一页）。

为什么这样设计：承认猜不准，让猜错变得安全

被放弃的设计：精确判断对方死没死假设网络有上界

  • 要能区分“慢”和“死”，得知道消息最多多久一定到。真实网络没有这个上界：重传、排队、对方 GC，都能把延迟拉到任意长。
  • 1985 年的 FLP 结论说的就是这件事：在异步网络里，只要可能有一个节点崩溃，就没有确定性的算法能保证大家一定在有限时间内达成一致。

选中的设计：用超时去猜，用幂等和 fence 兜住猜错全景就是这么搭的

  • 第 10 站 TC 等满 60 秒就猜“订单服务死了”，推 Cancel。猜错了（它只是停了 70 秒），它醒来发的 commit 会被 TC 拒掉，因为全局事务已经在超时回滚。
  • 第 5、8 站的命令可能被重发、可能迟到，接收方靠幂等键和 fence 表扛住（分布式事务 · 机制 3）。

决定胜负的约束：从外面看，“慢”和“死”一模一样，所以判断只能靠猜。设计的重点因此不在猜得多准，而在猜错的代价能不能承受：重做要幂等，迟到的命令要能被认出来，谁说了算要靠只增不减的数来定，不靠钟。

最少的写法

量时长、设超时、配重试、全局事务超时deadline 传递、重试预算放到 ⑥
// 1. 量时长、算超时：只用单调时钟
long start = System.nanoTime();
reserve();
long costMs = TimeUnit.NANOSECONDS.toMillis(System.nanoTime() - start);

// 2. 调用方给出截止时间（gRPC），下游在同一个 Context 里再调会自动继承
stockStub.withDeadlineAfter(300, TimeUnit.MILLISECONDS).reserve(req);

// 3. 写接口：框架别自动重试，自己在有幂等键的地方重试（Dubbo 默认 retries=2）
@DubboReference(timeout = 300, retries = 0)
private StockService stockService;

// 4. 重试：Resilience4j，指数退避 + 随机化 + 次数上限
RetryConfig cfg = RetryConfig.custom()
    .maxAttempts(3)
    .intervalFunction(IntervalFunction.ofExponentialRandomBackoff(100, 2.0, 0.5))
    .retryOnException(e -> isTimeoutOrUnavailable(e))   // 业务错误不重试
    .build();

// 5. 全局事务多久判死（Seata，默认 60000）
@GlobalTransactional(timeoutMills = 60000)
public void placeOrder(PlaceOrderCmd cmd) { ... }

同一个类里还有两段：storm 是④ 实验台的真机版（200 个线程、真的 HTTP），clock 是④ 机制 3 那次 NTP 跳变的模拟。storm 在本机跑了 3 次，稳定的结论只有三条：总请求都是 200 单的 4.9～5.7 倍；恢复后最挤的 100 ms，指数退避 52～75 次，加全抖动 30～36 次；最后一单成功，指数退避在第 3.6～3.8 秒，加全抖动在第 2.9～3.0 秒。成功了几单每次差很多（2 核机器上 200 个线程本身就把请求摊开了），不拿它下结论。

到这里已经能交差了。全景第 5 站那次调用：deadline 300 ms，框架层 retries=0；超时后带着幂等键（XID + 分支）重试最多 2 次，指数退避加全抖动；库存服务按键去重。第 10 站的 60 秒保持 Seata 默认，业务里没有超过十几秒的步骤。

已知还没处理的细节：DUPLICATE 该回什么（⑥ 坑 8）；上游已经放弃了下游还在干（⑥ 坑 4）；几层都在重试（⑥ 坑 2）；校时把钟拨了（⑥ 坑 5）。

⑥细节：注意事项、规范、深处

第一圈

注意事项：不知道就会出事故

1写接口吃了框架的默认重试← ④ 超时 = 不知道
现象
库存多冻、钱多扣、短信发三条，日志里只有一次“调用超时”。
根源
Dubbo 默认 retries=2，超时抛的是 RpcException(TIMEOUT_EXCEPTION)，不是业务异常，FailoverClusterInvoker 会换一台再调。对方第一次很可能已经做了。
做法
写接口在 @DubboReference 上设 retries = 0；要重试就自己在带幂等键的地方重试，或者让接口本身幂等。
2每一层都在重试，次数相乘← ④ 上限、预算
现象
下游抖了一下，流量反而翻了几十倍，抖动变成雪崩。
根源
3 层各重试 3 次 = 27 倍。每一层都觉得自己“只多试两次”，乘起来就是放大器。
做法
只在一层重试（通常是离故障最近、又有幂等键的那一层），其他层快速失败；再加重试预算。
3退避了，但没加抖动← ④ 抖动
现象
下游恢复的那一刻被一波请求打满，又倒下；监控上流量是一根一根的尖刺。
根源
同一刻失败的客户端，用同一个公式算出同一个等待时间，又在同一刻回来。实测恢复后最挤的 100 ms：不加抖动 52～75 次，加全抖动 30～36 次。
做法
等待时间里加随机。Resilience4j 的 ofExponentialRandomBackoff、Spring Retry 的 @Backoff(random = true) 都是。
4超时不往下传，上游放弃了下游还在干← ④ 外层比内层长
现象
订单服务 300 ms 就放弃了，库存服务还在花 2 秒查库、冻结；重试来了又干一遍，下游越忙越慢。
根源
每一层各配各的固定超时，互相不知道上游还剩多少时间。
做法
传 deadline。grpc-java 里服务端处理请求时的 Context 带着上游的 deadline，在同一个 Context 里再调下游，会自动取两者中更早的那个；把活丢进自己的线程池时 Context 不会跟过去，要用 Context.current().wrap(...)。
5用墙上时钟量时长、判超时← ④ 两种时钟
现象
偶发的“刚开始就超时”，或者超时迟迟不触发；耗时统计里出现负数。
根源
currentTimeMillis() 会被 NTP step 拨动。Seata 的 isTimeout()、很多自己写的超时判断用的都是它。
做法
自己的代码量时长一律 nanoTime()。管不到的（Seata、各种中间件）靠运维：校时只在开机时 step，运行中只 slew（chrony 的 makestep 1 3 就是“启动后前 3 次校时、偏差超过 1 秒才允许跳”）。
6雪花 ID 遇上时钟回拨← ④ 墙上时钟会跳
现象
下单偶发报错 “Clock moved backwards”，或者更糟：发出重复的 ID，插库撞主键。
根源
雪花 ID 的高位是毫秒时间戳。MyBatis-Plus 3.5.18 的 Sequence.nextId()：回拨 ≤ 5 ms 就 sleep(回拨量 × 2) 再取一次，还小就抛异常；超过 5 ms 直接抛异常。它取时间用的是 SystemClock，后台线程定期缓存的 currentTimeMillis()。
做法
先保证校时不 step；对时钟敏感的场景用号段模式（只靠数据库发号段，不看钟），全景第 2 站就是这么做的。
7拿时间戳判断新旧← ④ 比数不比钟
现象
“按 updated_at 取最新”的同步任务、缓存刷新，偶发留下旧值；券明明 Cancel 过还是 LOCKED。
根源
不同机器的钟有偏差，后发生的事可能带着更小的时间戳。
做法
用版本号（乐观锁 version）、条件更新（WHERE status = 'LOCKED'）、fencing token 判断新旧；时间戳只用来给人看。
8把“重复请求”当成“成功”← ④ 不知道
现象
⑤ 里第二次调用拿到 DUPLICATE 时，第一次的冻结还没做完；万一第一次后来失败了（库存不够），订单服务却当成了成功。
根源
“见过这个键”只说明请求到过，不说明做成了。幂等键挡住了重复执行，没解决“不知道”。
做法
幂等表里存结果：做完了就返回第一次的结果，还在做就返回 PROCESSING，调用方退避后再查（幂等设计的状态机）。
第二圈

使用规范：团队里该怎么写

  • 超时从外往里递减，能传 deadline 就传 deadline。网关 > 订单服务 > 库存服务，每层给自己留出处理时间。防的是：上游早放弃了，下游还在白干。
  • 超时按下游 p99 定，再加一点余量，写进配置并注明依据。防的是：拍脑袋的 30 秒把线程池占满，或者拍脑袋的 100 ms 天天误判。
  • 只重试可能自愈的错误。超时、连接被拒、503 / UNAVAILABLE 重试；参数错、业务规则不满足不重试。防的是：对一个注定失败的请求打满重试次数。
  • 重试四件套一起上：指数退避、全抖动、次数上限（3 次左右）、重试预算（重试不超过正常请求的一成）。防的是：重试风暴。
  • 写接口重试前必须有幂等键；幂等表存的是结果，不只是“见过”。防的是：重复扣减；以及把 DUPLICATE 当成功。
  • 代码里量时长只用 nanoTime() / Stopwatch；墙上时钟只用来记录和展示。防的是：NTP 跳变带来的误判和负数耗时。
  • 服务器校时只在开机时 step，运行中只 slew；监控各机器的时钟偏移。防的是：Seata 判超时、雪花发号这些你改不了的代码被钟坑。
第三圈

深处：几个“为什么”

Seata 的几个时间，都按 TC 的墙上时钟、从 beginTime 起算

全景里的“60 秒”“每 1 秒”都在这里（Seata 2.6.0 源码 DefaultValues、DefaultCoordinator）。max-commit-retry-timeout 默认 -1：第 8 站的 Confirm 失败了会一直重推，没有上限，所以 Confirm 里不能放会失败的逻辑。

配置默认管什么
@GlobalTransactional timeoutMills60000第 10 站：多久判死
server.recovery.timeout-retry-period1000多久查一次超时
server.recovery.committing-retry-period1000第 8 站：多久重推一次 Confirm
server.max-commit-retry-timeout-1重推多久放弃，-1 不限
client.tm.commit-retry-count5订单服务向 TC 发 commit 的重试次数
transport.rpc-tm-request-timeout30000TM 调 TC 的 RPC 超时（RM 是 15000）

为什么偏偏是“全抖动”

AWS 架构博客 2015 年那篇 Exponential Backoff And Jitter 做过模拟：在不抖动、全抖动、等抖动（一半固定一半随机）、去相关抖动几种里，全抖动的总调用次数最少、完成也最快之一。直觉是：等待时间在 [0, 上限] 里均匀分布，回来的人被摊得最开。代价是有的客户端会“很快就回来”，所以封顶和预算还得有。Resilience4j 的 ofExponentialRandomBackoff(100, 2.0, 0.5) 是在 base·2k 上下各浮动 50%，比全抖动保守一点。

重试预算长什么样

gRPC 的 retryThrottling（要在 service config 里配，默认不开）：桶里有 maxTokens 个令牌，每次失败扣 1，每次成功加 tokenRatio，令牌少于一半就停止重试。下游大面积失败时，重试会自己停下来，等成功慢慢把桶填回去。它保护的是下游，代价是那段时间里的请求不再重试，直接失败。

nanoTime 凭什么不跳

HotSpot 在 Linux 上用 clock_gettime(CLOCK_MONOTONIC) 实现它。这只钟不受 step 影响，只会被 slew 微调快慢，所以不会倒退。JDK 文档同时说清了它的边界：起点随意（可能是负数），只在同一个 JVM 实例里相减才有意义，所以它不能跨进程、跨机器比较，也不能存库。比较时写 nanoTime() - start >= timeout，不写 nanoTime() >= start + timeout，后者在溢出时会错。

版本差异

  • JDK 8 → 9+：Instant.now() / Clock.systemUTC() 的精度从毫秒提到微秒级（JDK-8068730）。精度变高不等于更可信，它照样会被 NTP 拨动。
  • Dubbo 2.x → 3.x：默认 timeout=1000、retries=2 没变（3.3.6 源码 CommonConstants）。
  • Seata 1.x → 2.x：进 Apache 孵化后，从 2.1 起包名改成 org.apache.seata；上表的默认值和判超时的写法没变。2.x 的 TC 可以用 Raft 存储，才有了“新 leader 用自己的钟”这件事。

面试官会怎么问

调用超时了，怎么知道对方到底执行了没有？

不知道，这是超时的本义。两条路：调查询接口确认（查也要能重试），或者带同一个幂等键重做；都确认不了的，交给对账。所以写接口必须设计成幂等，幂等表里存结果，重复请求返回第一次的结果。

重试为什么要加抖动？加了退避还不够吗？

退避解决的是“别太快回来”，抖动解决的是“别一起回来”。同一时刻失败的客户端，用同一个公式算出同一个等待时间，会在同一时刻回来，下游恢复的瞬间又被打满。全抖动把等待时间在 [0, 上限] 里随机，回来的人被摊开。

System.currentTimeMillis() 和 nanoTime() 有什么区别？各用在哪？

前者是墙上时钟，和 UTC 对齐，会被 NTP 拨动，可以跨机器“大致”比较、能存库；后者是单调时钟，只往前走，起点随意，只能在同一个 JVM 里相减。量耗时、算超时用 nanoTime，记录发生时间、给人看用 currentTimeMillis。

自测

1. 用一句话说出这一页的精华

超时只说明“不知道”，判死只能靠猜；所以重做要幂等、要退避加抖动加上限，迟到的命令要靠只增不减的数认出来；量时长用单调时钟，比先后不靠时间戳。

2. ② 里的老办法错在哪两处？

把超时当失败（对方可能已经做了），以及失败就马上、无条件地重做（没有幂等键就重复执行，没有退避就在对方最弱的时候加压）。

3. ⑥ 坑 1（写接口吃了 Dubbo 的默认重试）根源是 ④ 的哪条？

机制 1：超时 = 不知道。超时的那一次很可能已经执行了，框架却把它当失败、换一台再调。框架不知道你的接口幂不幂等，只能你来关掉或者保证幂等。

4. 预测：实验台里选“固定 1 秒”、重启 1 秒、最多 6 次。恢复后的第一波有多大？之后每秒呢？

几乎 200 单在第 1 秒同一刻回来（模拟里 200 次/100 ms），只能接下 20 个左右；剩下的又在第 2 秒一起回来……每秒一个尖刺，每个尖刺只进去一点点。推理来自机制 2：没有抖动，同时失败就同时回来。

5. 预测：TC 那台机器在全局事务第 5 秒时被 NTP 往回拨了 30 秒，订单服务这次真死了。TC 大约在真实第几秒回滚？库存那 2 件呢？

isTimeout() 用 currentTimeMillis() - beginTime，往回拨 30 秒后，这个差值比真实少 30 秒，所以要到真实第 90 秒左右才判超时，再加上最多 1 秒的检查周期。库存那 2 件多冻了约 30 秒，别人这段时间买不到。来自机制 3。

6. 放回全景：第 5 站前后各发生了什么？如果订单服务把第 5 站的超时当成失败、直接抛异常，整条链路会怎样？

之前：第 4 站订单 Try 插了 CREATING；之后：第 6 站要去锁券。抛异常后 @GlobalTransactional 让 TM 发回滚，TC 给登记过的分支推 Cancel。库存分支在 Try 开头就登记了，所以也会收到 Cancel：Try 已经提交的，冻结的 2 件退回；Try 还没提交的，fence 记一次空回滚，迟到的 Try 被挡掉。用户看到“下单失败”，库存短暂少了 2 件后恢复，三个库最终对得上。要是第 5 站没走 Seata 分支、也没有幂等键，就是② 里那样：订单回滚了，库存冻着，只能等第 11 站对账发现。

档位：标准。本机跑过：TimeLab 的 timeout、retry、storm 三段，JDK 17.0.21 按 --release 8 编译，2 核 ARM；timeout、retry 跑了 2 次，结果一致；storm 在“恢复后同时处理 10 个”的配置下跑了 3 次，页面只写三次都成立的结论。clock 段是用 Clock.offset 做的模拟，没有改系统时间。实验台是 JS 模拟（网络往返 2～20 ms），已在 node 里跑过，数字和真机的方向一致、大小不同，原因见⑤。
