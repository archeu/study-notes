1000 张券、10 万人：秒杀与抢券

秒杀难在所有写都挤在同一个数上：MySQL 里的一行库存，每秒只扣得动几百次。解法有两条主线：一是一层一层削，App、CDN、网关、售罄标记，每层只把下一层扛得住的量放进去；二是把“决定谁抢到”和“记账”拆开，Redis 里一段 Lua 原子地查重、扣数，在内存里快速决定；MySQL 只按自己的速度落库，用条件更新和唯一键当最后的账本。Redis 快但可能丢，MySQL 慢但可靠，两者不一致时以账本为准。

①要解决的问题：一个数，10 万人同时改

全景里 20:00:00 那一秒，1000 张券、10 万人、30 万次点击。地图给这一站的要求，拆开是五条：

要求为什么难全景里谁负责
不超发：最多 1000 张10 万个请求并发地“看库存、扣库存”第 7 站 Lua 预扣，第 9 站条件更新兜底
不少发：1000 张都发出去扣了库存、后面某一步失败，券就“丢”了第 8 站消息补发 + 对账
一人一张同一个人点 3 次，3 个请求同时到第 7 站集合查重，第 9 站唯一键
没抢到的快速知道99% 的人注定抢不到，让他们排队是浪费第 3～6 站层层快速失败
不拖累别的业务同一台机器、同一个库上还有正常下单每层削峰 + 独立部署

②不用它会怎样：直接在 MySQL 里扣

最直接的写法完全正确，不会超发：

BEGIN;
UPDATE coupon_stock SET stock = stock - 1 WHERE id = 'c88' AND stock > 0;   -- 影响 1 行才继续
INSERT INTO t_coupon_user (user_id, coupon_id) VALUES (1024, 'c88');        -- 唯一键 (user_id, coupon_id)
COMMIT;

问题在速度。所有请求都要改 id = 'c88' 这一行，行锁要等到 COMMIT 才放，于是 10 万个事务在这一行上排成一队。热点行那一页的结论：每秒最多 ≈ 1 ÷ 热点行持锁时间，持锁 2 ms 就是每秒 500 次，加连接、加机器都没用。全景第 2 站的压测正是卡在这里：同步扣 MySQL 的版本 600 QPS 就上不去了。排不上的请求占着连接池等锁，连同一个库上的正常下单也拿不到连接。

不懂精华时的典型误用把库存搬进 Redis，代码却还是“先看再扣”：GET 一下还有，再 DECR。单线程测试完全正常，并发一上来就超发。⑤ 的实验 1 里，100 张券回了 200 次“抢到了”，库存扣到 -100。搬进 Redis 解决的是速度，原子性要靠 Lua 另外保证。

③几种流派：库存扣在哪

流派做法扛得住多少代价
数据库硬扛条件更新或乐观锁（version），前面靠限流把量压到几百每秒几百（受热点行持锁时间限制）最简单、最一致；量大就排队
数据库拆热点库存拆成 10 行，随机扣一行；或者攒一批请求合并成一次扣减大约乘以拆的份数“还剩几张”要加起来算；最后几张分散在各行，有的行先扣完
Redis 预扣 + 异步落库Lua 原子查重、扣数；成功的发消息，消费者慢慢写 MySQL单个 Redis 分片每秒几万到十几万次Redis 和 MySQL 是两份数据，要处理两者不一致
令牌预分配开抢前往 Redis List 里放 1000 个券码，抢的人 LPOP 一个同上和预扣本质一样；券码天然唯一，查重仍要另做

本页学第三种：Redis 预扣 + 异步落库，加上前面几层削峰。选择规则：峰值在每秒几百以内，就用数据库条件更新，别引入第二份数据；峰值大到热点行扛不住、而且“抢到没有”必须一秒内回复，才上 Redis 预扣。

④核心取舍：削峰漏斗，和“决定”与“记账”分家

取舍一：每层只放下一层扛得住的量

越靠外的一层，挡掉一个请求越便宜；越靠里的一层，越贵、也越准。所以粗筛放在外面，精确判断放在里面。

层（全景站）进来放过去靠什么挡挡错了的代价
③ App30 万次点击10 万点一次置灰、随机延迟几乎没有；但脚本能绕过
④ CDN50 万次刷新0页面静态化，抢购地址开抢才下发页面信息有几秒延迟
⑤ 网关10 万2 万令牌桶（上一页）有人本来能抢到，被随机拒了：不公平，但券反正不够分
⑥ 售罄标记2 万约 3000本机内存里的一个布尔值标记该清没清，剩下的券发不出去
⑦ Redis Lua约 30001000原子的查重 + 扣数切主时可能丢最后几笔扣减
⑨ MySQL1000 条消息1000 行条件更新 + 唯一键没有：它就是最终答案

取舍二：“决定”在 Redis，“记账”在 MySQL

选：异步Redis 决定 → 消息 → MySQL 记账

Redis 里扣成功就回复用户，MySQL 由消费者每秒 200 条慢慢写。写库的速度不再跟着流量走：10 万人还是 100 万人，MySQL 都只写 1000 行、每秒 200 行。代价是同一份库存有了两份数据，要回答“两边对不上怎么办”。

没选：同步Redis 扣成功 → 当场写 MySQL → 回复

只有 1000 张券时其实能跑：1000 次 INSERT 不算多。但只要事务里还要更新 coupon_stock 那一行，就又回到热点行；券一多、活动一多，写库的量就跟着流量涨。MySQL 一慢，用户的响应就跟着慢，前面几层削峰换来的快速响应也就没了。

决定胜负的约束：用户要的是“一秒内知道结果”，账本要的是“绝对正确”。两件事对速度和可靠性的要求相反，放进同一个同步调用，就只能按慢的那个走。

两份数据对不上时，谁说了算

  • Redis 多了切主后新主少了最后几笔扣减，库存“回涨”，Redis 又放出几个人。落库时 UPDATE … WHERE issued < 1000 影响 0 行，不发，改发致歉。⑤ 实验 4 实测：回涨 5 张，挡下 5 人。
  • Redis 少了扣了库存、消息没发出去（进程崩了）。靠本地重试表补发，活动后再拿 Redis 的已领集合和 MySQL 对一次账，补发漏掉的。
  • 消息多了重试导致同一条消息到两次。唯一键 (user_id, coupon_id) 让第二次 INSERT 失败，消费者把这种失败当成功处理。⑤ 实验 4：投递 200 条，落库 100 行，撞唯一键 100 次。

所以回复用户时有个措辞上的选择：Redis 扣成功就说“抢到了”，体验最好，但极少数人会在切主后收到致歉；说“排队中，结果稍后通知”，等落库成功再确认，绝不会说错，用户多等几秒。

为什么非要 Lua：两个请求抢最后一张

请求 A（用户 7）

    请求 B（用户 9）

      Redis 里

      c88:stock1c88:users{ }

      库存只剩 1 张。Redis 一次只执行一条命令，但 A、B 的命令可以交错。Lua 脚本在执行期间不会插进别的命令，所以“看”和“扣”之间没有缝。

      最少的写法

      Lua：查重 + 扣数返回 0 成功、1 领过、2 售罄
      if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then return 1 end
local s = tonumber(redis.call('GET', KEYS[1]) or '0')
if s <= 0 then return 2 end
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return 0
      消费者：条件更新 + 唯一键同一个本地事务
      int n = jdbc.update("UPDATE coupon_stock SET issued = issued + 1 WHERE id = ? AND issued < ?", "c88", 1000);
if (n == 0) { notifySorry(uid); return; }                 // Redis 多放的人：不发
try { jdbc.update("INSERT INTO t_coupon_user(user_id, coupon_id) VALUES (?, ?)", uid, "c88"); }
catch (DuplicateKeyException e) { throw new AlreadyIssued(); }  // 重复消息：回滚这次 +1，当成功确认

      第二段里，撞唯一键时要让整个事务回滚（issued 的 +1 也撤销），再确认消息，所以抛异常而不是直接 return。参数细节放到第⑥步。

      • 1 和 2同样的 Redis、同样的命令，差别只在三次调用还是一段脚本。naive 超发了整整 1 倍，还有 18 个人一人两张；Lua 一张不多。naive 还更慢，因为每个请求要 3 次往返。
      • 38 个实例各有一个售罄标记。2 万个请求里，只有 137 个走到了 Redis：100 个抢到的，加上售罄那一刻已经在路上的 37 个。其余全在本机内存里结束。
      • 4重复消息被唯一键挡住，“切主回涨”多放出的人被条件更新挡住，最终发券数始终是 100。Redis 可以错，账本不能错。

      到这里已经能交差了：Lua 预扣、售罄标记、发消息、消费者条件更新加唯一键，四样东西。已知还没处理的细节：扣了没发出去、售罄标记怎么清、一个 key 扛不住、和正常业务隔离，都在⑥。

      ⑥反例和误用

      第一圈 · 套上了名字，没满足约束

      1库存放进了 Redis，还是“先看再扣”⑤ 实验 1← ④ 为什么非要 Lua
      现象
      100 张券回了 200 次“抢到了”，库存 -100。
      根源
      GET 和 DECR 之间能插进别的请求。
      做法
      查重和扣数放进同一段 Lua；或者直接 DECR 看返回值，小于 0 就 INCR 回去。
      2落库时完全相信 Redis 的结果⑤ 实验 4← ④ 谁说了算
      现象
      Redis 切主后库存回涨，消费者照单全收，发出 1037 张。
      根源
      主从异步复制，新主可能少了最后几笔写入。
      做法
      消费者用 WHERE issued < 1000 的条件更新，MySQL 才是最终的数。
      3扣了库存，消息没发出去← ④ 谁说了算
      现象
      用户看到“抢到了”，券一直没到账；活动结束库存是 0，MySQL 只有 996 行。
      根源
      Redis 扣减和发消息是两个系统，中间进程崩了。
      做法
      发送失败写本地重试表；活动后用 Redis 已领集合对账补发；或用 RocketMQ 事务消息把“扣减”和“发消息”绑在一起。
      4消费者不幂等，一人到账两张⑤ 实验 4← ④ 消息多了
      现象
      MQ 至少投递一次，重试时同一条消息到了两次。
      根源
      消息系统保证不丢，不保证不重。
      做法
      唯一键 (user_id, coupon_id)，撞键当成功；见 幂等设计。
      5售罄标记只会置位、不会清← ④ 漏斗第 6 层
      现象
      运营补了 200 张，或者切主后库存回涨，可所有实例都在回“已抢完”。
      根源
      标记是本机内存里的副本，补货时没人通知它。
      做法
      补货走同一个频道广播“清标记”；标记带过期时间（比如 5 秒后重新问一次 Redis）。
      6为了“快点到账”把消费者开到 200 线程← ④ 异步
      现象
      MySQL 又被打满，连同一个库上的正常下单都变慢。
      根源
      异步的价值就是让写库速度和流量脱钩，消费速度一放开，等于又把峰值送回了数据库。
      做法
      消费速度按数据库能力定（全景：4 线程、每秒 200 条），宁可到账晚几秒。

      第二圈 · 团队里怎么做

      • 独立部署秒杀的券服务实例、Redis、甚至网关路由单独一套，和日常下单分开。防的是一场活动拖垮全站。
      • 开抢前预热库存、券信息提前写进 Redis 和本地缓存，Lua 脚本提前 SCRIPT LOAD，应用提前 JIT 预热（压一轮）。防的是开抢第一秒冷启动。
      • 防刷抢购地址带一次性的签名参数，开抢时才下发；按用户、设备限流；风控名单在网关挡掉。防的是脚本比真人快。
      • 可降级每一层都有开关：Redis 不可用时直接回“活动太火爆”，而不是退回去扣 MySQL。防的是兜底方案把热点行重新引回来。
      • 活动后对账Redis 已领集合、消息发送记录、MySQL 发券表三方对一次，差异有人处理。防的是少发没人知道。

      第三圈 · 深处

      • 一个 key 扛不住时所有请求都打 c88:stock，在 Redis Cluster 里它只在一个分片上，单分片每秒几万到十几万次。更大的活动把库存拆成 10 个 key（c88:stock:{0..9}），请求随机挑一个，扣完了再换下一个；代价是最后几张分散在各 key，“已抢完”的判断要多问几次。见 热 key。
      • Lua 里别做慢事脚本执行期间 Redis 不处理别的命令。脚本里只放 O(1) 的几条命令；SMEMBERS 这种 O(N) 的、或者循环几千次的，会让整个 Redis 卡住。
      • Redis Cluster 下的 keyLua 里用到的多个 key 必须在同一个槽，所以写成 {c88}:stock、{c88}:users，用 hash tag 绑到一起。
      • 下单秒杀比抢券多出来的抢到以后还要建订单、等支付，30 分钟不付要把库存还回去：要用延时消息或定时任务回补 Redis 和 MySQL，这是全景“下一圈”。

      下一圈

      • 下单秒杀库存预扣 → 建单 → 支付 → 超时回补，三处库存怎么对齐，接 J09 分布式事务 和 延时消息。
      • 库存分段和热点探测开抢前不知道哪个商品会热：本地缓存 + 热点探测（如京东 hotkey 类组件）自动把热 key 推到本机。

      ↺回到⑤：改一改

      1. 只用 DECR：把 naive 改成直接 DECR，返回值 < 0 就 INCR 回去、回“已抢完”。还超发吗？一人多张的问题还在吗？（坑 1）
      2. 真 MySQL：把第 4 段换成真 MySQL（mysql:8.4 容器），建 coupon_stock 和带唯一键的 t_coupon_user，用 4 个消费线程落库，量一下每秒能写多少。（④ 取舍二）
      3. 丢消息：在发消息前随机让 1% 的请求“崩掉”，活动后写一个对账程序找出这些人并补发。（坑 3）
      4. 清标记：售罄后把库存 SET 回 20，看有多少实例还在回“已抢完”；加上“5 秒后重新问 Redis”再跑一次。（坑 5）

      自测

      1. 用一句话说出这一页的精华

      秒杀是很多写挤在同一个数上：外层一层层削峰，每层只放下一层扛得住的量；里面把“决定谁抢到”（Redis Lua，原子、快、可能丢）和“记账”（MySQL 条件更新加唯一键，慢、可靠）拆开，用消息连起来，两边对不上时以账本为准。

      2. 直接在 MySQL 里扣，疼在哪？

      不会错，但所有事务排在一行的行锁上，每秒最多约 1 ÷ 持锁时间，几百次；排不上的占着连接，连正常下单都拖慢。加机器、加连接都没用。

      3. 坑 2（落库时多发）的根源是 ④ 的哪一条？

      “决定”和“记账”分家以后有两份数据；Redis 主从是异步复制，切主可能丢掉最后几笔扣减，所以 Redis 的结果不能当最终答案，MySQL 的条件更新才是。

      4. 预测：把售罄标记去掉，⑤ 实验 3 里 Redis 要处理 2 万次。全景规模下（网关放 2 万）会怎样？

      Redis 每秒多处理 1.7 万次脚本调用，单个 key 在一个分片上，仍在它的能力范围内，结果不会错；但每个请求多一次网络往返，券服务的线程和 Redis 连接被占得更久，响应时间变长。售罄标记省下的是“结局已定的请求”的成本。

      5. 预测：Lua 脚本里漏掉了 SISMEMBER 查重，只靠 MySQL 唯一键挡，最后会发几张券？

      Redis 里同一个人能扣多次库存，1000 张库存可能被 900 个人扣完，其中有人扣了两三次。落库时唯一键挡掉重复的，MySQL 只有 900 行左右：少发了。重复的人占掉了别人的名额，所以查重必须和扣库存在同一步。

      6. 放回全景：第 7 站前后各发生了什么？如果第 7 站的 Redis 整个不可用，整条链路怎么走？

      前面是第 6 站券服务的售罄标记，后面是第 8 站发消息、第 9 站落库。Redis 不可用时预扣调用失败，熔断打开，券服务直接回“活动太火爆，稍后再试”（第 11 站的预案）；千万不能退回去直接扣 MySQL，那会把 2 万个请求引到热点行上。

      档位：标准。本机跑过（2 核 ARM 虚拟机，JDK 17，Lettuce 6.8.2，redis:8.10.3-alpine 容器）：⑤ 的四段各跑 1 次，页面上的次数都来自这次输出；第 4 段的数据库是内存里模拟的条件更新和唯一键。④ 的分步演示是按 Redis 单线程执行命令的规则手排的两种交错。

      按文档：Redis 执行 Lua 脚本期间不会执行其他客户端的命令；脚本访问的 key 在 Cluster 模式下必须落在同一个哈希槽；Redis 主从默认异步复制。漏斗各层的数字来自全景页，是交易靶场的设计。
