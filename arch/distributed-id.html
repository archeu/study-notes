订单号 9527 从哪来：分布式 ID——号段与雪花算法

多台机器各发各的号，彼此不商量，还不能撞。两条路：号段把“不撞”交给数据库里的一行，一次领一千个号放在内存里发，怕的是库慢、库挂；雪花把“不撞”拆进 64 位里，时间戳 + 机器号 + 序列号，谁也不用问，怕的是时钟往回走、两台机器拿了同一个机器号。选哪个，就看你更信得过数据库，还是更信得过时钟和机器号的分配。

①为什么需要：9527 要在写任何库之前定下来

在全景第 2 站，这一步要解决：用户 1024 下单，订单服务要在不访问任何库的情况下发出订单号 9527。后面第 3 站开全局事务，第 4、5、6 站在订单库、库存库、券库各写一笔，第 9 站发消息，第 11 站对账，用的都是这个号。所以号必须先有，而且两个实例 A、B 同时在发，谁也不能和谁撞。

不撞

两个实例、重启以后、扩到十个实例，都不发出同一个号。

先有号，再写库

号在内存里就能拿到，不等任何一次 INSERT，每单不多一次网络往返。

大体递增，发号的东西挂了别马上停

递增是给 InnoDB 主键用的（⑥ 第三圈实测）；发号依赖的库或时钟出事时，下单还能撑一会儿。

②没有它会怎样：三种老办法各疼在哪

各库自己 AUTO_INCREMENT

  • INSERT 之后才知道号，库存、券都得等订单库先写
  • 分库以后每个分片都从 1 开始；改步长（auto_increment_increment）的话，加分片要重新规划

每单问一次发号库

  • 往发号表插一行，再取 LAST_INSERT_ID()：每单多一次网络往返
  • 所有实例都压在这一个库上，它慢下单就慢，它挂下单就停

UUID

  • 36 个字符，比 BIGINT 大 28 字节，每个二级索引都要带一份
  • 随机，插进 B+ 树中间：⑥ 实测同样 30 万行，表 79.8 MB 对 39.6 MB；号上也看不出谁先谁后

精华：把“不撞”从每一单里拿出去。号段是一次向数据库批发一千个；雪花是事先给每台机器划好一块号空间，再用时间把号排开。

!不懂精华时的典型误用
做法
“MyBatis-Plus 的 ASSIGN_ID 开箱就是分布式唯一的”，不配机器号，直接扩到 5 个容器。
结果
雪花的“不撞”有一半靠机器号各不相同，机器号没分好，精华就没了。⑤ 实测两个实例用同一个机器号，低流量下各发约 1870 个，撞了 900 个。MyBatis-Plus 自己算的机器号在容器里只剩 32 种可能，见坑 1。

③相邻方案：“不撞”靠谁保证

做法“不撞”靠什么长什么样递增吗每个号要访问别人吗最怕
UUID v4122 位随机数，撞的概率小到可以忽略36 字符完全随机不用当主键：页分裂、表大一倍
UUID v748 位毫秒 + 随机数36 字符（存成 BINARY(16) 是 16 字节）按毫秒递增；毫秒内要看实现不用毫秒内随机的实现照样页分裂（⑥ 实测）
数据库自增 / 发号表库里的自增计数器BIGINT，连续严格递增每个号一次发号库慢、挂
Redis INCRRedis 单线程里的一个计数器BIGINT，连续严格递增每个号一次（可以一次 INCRBY 一段）Redis 重启丢了最后一秒的 AOF，号倒退、重复（见 Redis 持久化）
号段
美团 Leaf-segment		数据库一行 + 行锁，一次领一段BIGINT，短，段内连续每个实例内递增，实例之间交错一段一次（一千个号一次）库慢、库挂、主从切换丢更新
雪花
MyBatis-Plus Sequence、Leaf-snowflake		时间戳 + 机器号 + 序列号BIGINT，19 位十进制按毫秒递增；同一毫秒内按机器号排不用时钟回拨、机器号重复
改良雪花
Seata IdWorker		机器号 + 启动时取一次时间，之后只加 1BIGINT每个节点内严格递增，节点之间按机器号排不用机器号重复
选择规则：号只要唯一、不当主键（链路追踪 id、文件名），用 UUID。要当主键、要短、要能读、手边有稳定的 MySQL，用号段。不想让发号依赖任何服务、能管好机器号和校时，用雪花。框架内部只求唯一的号（Seata 的事务号），改良雪花最省心。
本页学号段和雪花：交易靶场的订单号用号段，MyBatis-Plus 默认给的是雪花，Seata 的 XID 用的是改良雪花，三个都在全景第 2 站出现。

④原理：一行加行锁，或者 64 位里分好地盘

先知道这些
  • InnoDB 的表就是一棵按主键排好序的 B+ 树，叶子是 16 KB 的页。新主键比谁都大，就追加在最右边；落在中间，页满了就要分裂。见 MySQL 索引与 B+ 树。
  • UPDATE 一行会给这行加行锁，到事务提交才放。两个事务改同一行，后来的那个等着。见 MVCC 与锁。
  • 墙上时钟会往回跳：NTP 一步校正（step）、虚拟机迁移、有人手动改时间。见时钟、超时与重试。
  • JavaScript 的数字是 double，只能精确表示 253 以内的整数，19 位的雪花 ID 超过了它。见第一圈 MyBatis-Plus 原理。

机制 1 · 号段：一行记着发到哪了，一次领一千个

机制 2 · 双 buffer：用掉 10% 就去领下一段

机制 3 · 雪花：64 位里分好地盘

为什么这样设计：信谁，就怕谁出事

号段：把“不撞”交给数据库

  • 号短、能读、不看钟，加实例不用分配任何东西
  • 库慢、库挂、库主从切换丢了最后一次 UPDATE，全落在发号上

雪花：把“不撞”拆进位里

  • 谁也不访问，不依赖任何服务，号自带时间
  • 机器号要有人事先分好、不能重；时钟不能往回走
决定胜负的约束：每发一个号都要排队问一个中心（发号表、INCR），中心就是瓶颈和单点。两种设计都在想办法不问中心：号段是批发，一千个号问一次，中心的压力降到千分之一，但中心还在；雪花是分地盘，地盘事先分好就一次也不问，代价是把“不撞”押在两件没人替你检查的事上：机器号和时钟。Seata 的改良版再退一步：时钟只在启动时看一次，之后靠计数器往前走，运行中回拨就伤不到它，代价是号里的“时间”不再是发号的时刻（⑥ 第三圈）。

最少的写法

号段预取、动态 step 放到 ⑥
CREATE TABLE id_alloc (
  biz_tag VARCHAR(32) PRIMARY KEY,
  max_id  BIGINT NOT NULL,
  step    INT    NOT NULL
);
INSERT INTO id_alloc VALUES ('order', 9000, 1000);

-- 领一段：UPDATE 和 SELECT 在一个事务里
BEGIN;
UPDATE id_alloc SET max_id = max_id + step
 WHERE biz_tag = 'order';
SELECT max_id, step FROM id_alloc
 WHERE biz_tag = 'order';   -- 10000, 1000
COMMIT;                     -- 段 = [9001, 10000]

SegmentIdGen 的核心双 buffer 的预取放到 ⑥ 第三圈
// 领一段：UPDATE + SELECT 一个事务，行锁保证 A、B 领到的段不重叠
Segment fetch() {
    update("UPDATE id_alloc SET max_id = max_id + step WHERE biz_tag = ?", tag);
    long max = …, step = …;   // SELECT max_id, step
    commit();
    return new Segment(max - step + 1, max);
}

long nextId() {
    while (true) {
        Segment s = cur;
        long v = s.next.getAndIncrement();
        if (v <= s.max) return v;               // 段内：纯内存
        synchronized (this) {                    // 段发完：只让一个线程去换
            if (cur != s) continue;              // 别人已经换过了
            cur = fetch();                       // 单 buffer：在这里等库
        }
    }
}

  • 按时间先后，号是 9528、10001、9529、10002……：每个实例内递增，实例之间交错。拿“id 大的更晚”去做增量同步，会漏单。

到这里已经能交差了：订单服务启动时建一个 SegmentIdGen("order")，下单先 nextId() 拿到 9527，再开全局事务、写三个库；或者实体上 @TableId(type = ASSIGN_ID)，给每个实例配好不重复的 worker-id。
已知还没处理的细节：机器号怎么保证不重（坑 1），时钟回拨（坑 2、坑 3），号段在库慢、库挂、切主时会怎样（坑 6～坑 8），双 buffer 的并发细节（第三圈），ID 的形状对 InnoDB 的影响（第三圈）。

⑥细节：机器号、时钟、库，三处各会怎么出事

第一圈 · 注意事项

1两个实例拿了同一个机器号← ④ 机制 3 三元组
现象
两个实例都配成（机房 1，机器 1）：低流量各发约 1870 个，撞了 900 个；一口气各发 50 万个，撞了 43.5 万个（⑤ 实测）。
根源
时间、机器号、序列号三样都一样就撞。MyBatis-Plus 新毫秒的序列号只从 1 或 2 起，低流量时两边同一毫秒的号有一半概率一样。不配机器号时它自己算：机房 = MAC 末两字节右移 6 位再模 32，机器 = “机房号 + 进程号”的 hashCode 模 32，进程号小于 10（容器里常是 1）就换成随机数。本机 Docker 27 按容器 IP 生成 MAC，两次起容器都是 02:42:ac:11:00:03；各台宿主机网段一样时机房号也一样，只剩 32 种机器号：5 个实例有 28% 的概率撞上，10 个是 79%。
做法
机器号由一个地方统一发，并且记账：Leaf 在 ZooKeeper 按 ip:port 建持久顺序节点；百度 UidGenerator 每次启动往 WORKER_NODE 表插一行，用自增 id 当机器号（22 位）；K8s 用 StatefulSet 的序号。拿不到号就不启动。
2运行中时钟往回拨← ④ 机制 3 时间不能回头
现象
回拨 3 ms：那一次调用多花了 6 ms。回拨 10 ms、1 s：直接抛 Clock moved backwards；1 s 那次之后，每毫秒调一次，1005 ms 里失败了 908 次（⑤ 之外的实测，snowflake ④）。
根源
MyBatis-Plus 3.5.18 的 nextId() 记着上一次的毫秒 lastTimestamp：现在比它小，差 ≤ 5 ms 就 sleep 差值 × 2 再看一次，否则抛异常。Leaf 一样，只是返回错误码。不敢接着发，是因为那段时间的号可能已经发过了。
做法
运行中校时只用 slew（慢慢调快慢），不 step；监控时钟偏移，偏得多的实例先摘流量。见时钟、超时与重试。
3重启时钟回拨：内存里的“上一次”没了← ④ 机制 3 时间不能回头
现象
实例跑了 300 ms 后重启，重启时钟往回拨了 300 ms：重启后 300 ms 发的 2810 个号里，2495 个和重启前的重复。没有任何报错（实测，snowflake ⑤）。
根源
lastTimestamp 只在内存里，重启后从 −1 开始，坑 2 那道检查形同虚设。
做法
把“最后发号的时间”存到进程外面，启动时比一比。Leaf 每 3 秒把本机时间写进 ZooKeeper，启动时那里的时间比本机还晚就拒绝启动；它最多漏掉最后 3 秒。最简单的办法：启动后先等一段比可能的回拨量更长的时间。
4低流量时按 id % 4 分库，只落两个库← ④ 机制 3 低 12 位是序列号
现象
每毫秒最多一个号，发 1000 个，按 id % 4 分到 4 个库：[0, 529, 471, 0]；按 id % 3：[328, 322, 350]（实测，snowflake ②）。
根源
对 2k 取模（k ≤ 12）只看最低 k 位，也就是序列号。MyBatis-Plus 新毫秒的序列号是 1 或 2（源码注释：“不同毫秒内，序列号置为 1 - 2 随机数”），所以只会落在 1、2 号库。它不从 0 起，本来就是为了避免低流量时 ID 全是偶数。
做法
分片别直接拿雪花 ID 对 2 的幂取模：先 hash 再取模，或者在号里嵌入用户的分片位（基因法），按用户分库。
5号段：重启丢号，订单号不连续← ④ 机制 1、2 段在内存里
现象
A 发到 9530 被 kill -9，重启领到 [12001, 13000]：9531～10000 和预取好的 [11001, 12000] 永远不会再发，一共 1470 个（⑤ 实测）。
根源
段在内存里，没发完的号不会还回 id_alloc；双 buffer 让一次重启多丢一整段。
做法
别对订单号提“连续”的要求：不拿它当“今天第几单”，对账按状态比，不按号有没有断。想少丢就把 step 调小，可这和坑 7 要的“段大一点”正好相反，按坑 7 定。
6号段：库慢了，一段卡一次← ④ 机制 2 双 buffer
现象
领号段时库慢到 200 ms，按固定速率发 3 秒：单 buffer 4000 个/秒，12 次调用各卡 211 ms；双 buffer 4000 个/秒，一次没卡；双 buffer 8000 个/秒，15 次各卡 209 ms（实测，segment ③）。
根源
双 buffer 只是把“等库”挪到了后台，前提是后台领一段比“发完剩下 90%”快。8000 个/秒时，1000 个号只够用 125 ms，比 200 ms 短。
做法
step 至少是“峰值 QPS × 库最慢一次的耗时”的几倍。Leaf 有动态 step：这一段不到 15 分钟就发完，下次 step 翻倍（上限 1,000,000）；超过 30 分钟才发完就减半。
7号段：库挂了，只能撑“手里剩的号 ÷ QPS”← ④ 机制 2 双 buffer
现象
双 buffer、4000 个/秒、step 1000，库挂了以后又发了 1800 个，撑了 430 ms，然后报“两段都发完了”；这 430 ms 里重试访问库 889 次（实测，segment ④，库挂用开关模拟）。
根源
库挂之后能发的，只有当前段的余量加上备好的下一段。
做法
按“库最长可能挂多久”定段大小：峰值 2000 个/秒、要撑 10 分钟，手里就要常备 120 万个号，这正是动态 step 在自动做的事。预取失败要退避，别每次调用都打一次库。
8号段：id_alloc 主从切换，max_id 倒退← ④ 机制 1 一行加行锁
现象
id_alloc 所在的库是异步复制。主库刚给 B 领了 [10001, 11000] 就挂了，从库还没收到这次更新；切主后 max_id 还是 10000，下一个来领的实例又领到 [10001, 11000]，两个实例同时发同一段。
根源
号段的“不撞”全靠那一行的值只往前走。切主丢了最后一次 UPDATE，值倒退了。这一条是从机制推出来的，本页没有实测。
做法
id_alloc 放在半同步复制或 MGR（多数派提交）的库上；万一异步切主，放流量之前先把每个 biz_tag 的 max_id 往前推一大段，比如加 100 万。

第二圈 · 使用规范

  • 机器号显式分配，启动时登记，拿不到就不启动。防的是：坑 1，靠网卡和进程号碰运气。
  • ID 在库里存 BIGINT，接口里转成字符串（Jackson ToStringSerializer）。防的是：⑤ 里 2121816155688669185 到了 JS 里变成 …184。
  • 不拿 ID 大小判断先后，增量同步、分页游标用更新时间加主键，或者 binlog。防的是：号段跨实例交错（⑤ 的 9528 → 10001 → 9529），“id > 上次最大值”会漏掉后发的小号。
  • 对外展示的订单编号和主键分开。防的是：号段的号连续，两天的号一减就是这两天的单量；雪花 ID 一拆就能看出下单时刻和机器号。
  • 运行中校时只 slew，并监控时钟偏移。防的是：坑 2、坑 3。
  • 号段 step 按峰值和库的故障时长定，开动态 step；id_alloc 放在不会丢更新的库上。防的是：坑 6、7、8。

第三圈 · 深处

1. ID 长什么样，决定 InnoDB 主键索引有多大

往 InnoDB 插 30 万行（主键 + 100 字节 payload，每 1000 行一个事务），只换主键（本机实测，btree 跑了 3 次，页数每次差 3% 以内）：

  • 只要单调，长短都还好：UUID v7 毫秒内用计数器递增（RFC 9562 的做法），48.7 MB，只比 BIGINT 多出主键自身的那点。
  • 毫秒内乱一点，就和完全随机一样：毫秒内用随机数的 UUID v7，81.9 MB，比随机 UUID v4 还大。这次插入速度约每毫秒 44 行，每毫秒里的几十行顺序是乱的，每次都插不到“上一次的后面”。
  • 多实例的雪花也会这样：同一毫秒里，号按机器号排，不按到达顺序；8 个实例轮流写，71.6 MB。这次是每毫秒约 60 行的极端速率；真实流量下每毫秒到达的号少得多，影响会小，本页没测（↺ 练习 4）。号段跨实例交错得更厉害：A 在 9xxx、B 在 10xxx 两处同时追加，好在两处各自都是顺序的。

2. Seata 的改良雪花：启动后不再看钟

Seata 2.6.0 的 IdWorker 把 41 位时间戳和 12 位序列号合成一个 AtomicLong，启动时用当前时间初始化，之后每发一个号 incrementAndGet()：序列号满了自然进位到时间戳上。只有当这个“逻辑时间”赶上了墙上时钟，才 sleep(5) 一下，而且只等这一次，等完照样加 1。

照着它写的 SeataStyleIdWorker，本机实测结果为什么
运行中把钟往回拨 1 秒，接着连发 1.5 秒208 万个，没有异常、没有重复、严格递增逻辑时间不跟着钟走。只有 203 次调用各 sleep 了 5 ms：这个实例刚启动，逻辑时间贴着墙上时钟，回拨后要等钟追上来
先在机器 2 发一个号，5 ms 后在机器 1 发一个18859322099458049 之后是 9852122844717057机器号在高位：跨节点按机器号排，不按时间排

代价是号里的“时间”变成了“启动时刻 + 已发数量 ÷ 4096 毫秒”，拆不出发号时刻。跑了一天、每秒 100 个号的节点，逻辑时间只比启动时刻晚 2 秒左右，远落后于墙上时钟，钟往回拨几秒根本碰不到它。Seata 的 XID 是 TC 的 IP:端口:事务号，事务号只要在这个 TC 节点内唯一，正好用得上。

3. Leaf 怎么分机器号、怎么防重启回拨

Leaf-snowflake 启动时按 ip:port 去 ZooKeeper 的 forever 目录下找自己的节点：有就沿用那个顺序号当机器号（同一个实例重启拿回原号），没有就建一个持久顺序节点 ip:port-0000000001。拿到的号写进本地文件，ZooKeeper 连不上时用文件里的号启动。启动时比较节点里记的时间和本机时间，节点里的更晚就拒绝启动；之后每 3 秒上报一次本机时间（SnowflakeZookeeperHolder）。运行中的回拨处理和 MyBatis-Plus 一样，≤ 5 ms 等两倍，否则报错；新毫秒的序列号从 0～99 里随机起。

4. 双 buffer 的并发细节：我写 SegmentIdGen 时踩的坑

第一版在两个实例 × 4 线程下，偶尔有线程报“两段都发完了”，可库明明好好的。原因：段发完时，线程 T1、T2 先后进了 synchronized 块，都 wait() 等预取；预取到了，T1 醒来换上新段，把“下一段”清空；T2 醒来一看，“下一段”是空的、也没人在领，就判了“两段都空”。wait() 会让出锁，醒来后必须重新检查当前段是不是已经被换过。补上 if (cur != s) continue; 后跑 3 次，40 万个号 0 重复、0 报错。Leaf 的写法是：等完先在写锁里从当前段再取一次号，取不到才去看下一段。

自测

1. 用一句话说出这一页的精华

分布式 ID 就是把“不撞”从每一单里拿出去：号段一次向数据库批发一段，靠一行加行锁不撞，怕库慢、库挂、切主；雪花事先给每台机器划好地盘，靠时间 + 机器号 + 序列号不撞，怕时钟回拨和机器号重复。

2. 三种老办法各疼在哪？

各库自增：INSERT 之后才有号，库存、券得等订单库先写；分库后各分片从 1 开始撞号。每单问一次发号库：每单多一次往返，发号库是单点。UUID：36 字符，随机插进 B+ 树中间，页对半分裂，表大一倍，也看不出先后。

3. 坑 1（两个实例撞号）的根源是 ④ 的哪条？

机制 3：雪花的号由（时间、机器号、序列号）三样组成，序列号只在一台机器内部排开。机器号一样，就只剩“时间不同”能把两台机器的号分开；同一毫秒里两边又都从 1 或 2 起，必然有一半撞上。

4. 预测：号段 step 1000、双 buffer，QPS 从 4000 涨到 8000，库一直正常（领一段 5 ms），会卡吗？

不会。机制 2 的条件是“后台领一段的时间 < 发完剩下 90% 的时间”：8000 个/秒发完 900 个要 112 ms，远大于 5 ms。坑 6 卡住，是因为库慢到了 200 ms，不是因为 QPS 本身。

5. 预测：雪花 ID 按 id % 4 分 4 个库，高峰期每毫秒几十单，分布会怎样？

接近均匀。机制 3：低 12 位是序列号，高峰时同一毫秒里序列号从 1 或 2 一路加上去，最低两位把 0～3 都走一遍。坑 4 只在每毫秒最多一个号的低峰出现。

6. 预测：Seata 式的节点跑了一整天，每秒 100 个号，运维把钟往回拨了 10 秒，会怎样？

照常发，一次也不 sleep。一天发了 864 万个号，逻辑时间只比启动时刻多走了 864 万 ÷ 4096 ≈ 2.1 秒，墙上时钟却已经过了 24 小时；往回拨 10 秒，墙上时钟还是远远领先，waitIfNecessary 的条件不成立。

7. 放回全景：第 2 站前后各发生了什么？发号坏了（发出重复号 / 发号依赖的库挂了），整条链路会怎样？

之前：第 1 站用幂等键 req-7f3a 判定这是一次新请求，同一个键的第二次 POST 不再下单。之后：第 3 站开全局事务拿 XID（XID 里的事务号也是一种雪花发的），第 4 站订单 Try 插入 9527，第 5、6 站按 9527 冻库存、锁券，第 9 站发 ORDER_CREATED 9527，第 11 站按 9527 对账。
发出重复号：两单都叫 9527。订单表不分库时，第 4 站主键冲突，后一单 Try 失败、整单回滚，算是被挡住了；订单表分库、两单落在不同分片时，谁也挡不住，冻结、用券、消息、对账全混在同一个号下面，对账会把两单当成一单。
号段的库挂了：内存里的号用完以前一切照常；用完以后第 2 站报错，后面的站一个都不会发生，下单整体不可用。雪花不依赖库，这种事故碰不到它，它怕的是另外两件事。

档位：标准。本机跑过（2 核 ARM，JDK 17，--release 8 编译，Docker 里的 MySQL 8.4.13，MyBatis-Plus 3.5.18）：⑤ 的 segment 跑了 4 次（第一版双 buffer 有并发 bug，见第三圈 4，修好后 3 次 0 重复），snowflake 2 次，btree 3 次（后两次修正了页分裂计数器读法、加了单调的 UUID v7 和 8 实例）。时钟回拨是覆盖 Sequence.timeGen() 拨的，库挂是用开关模拟的。Docker 容器 MAC 看了两次。
