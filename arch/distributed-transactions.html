一单写三个库：2PC/XA、TCC、Saga、本地消息表与 Seata

一个本地事务装不下三个库，“还没定下来”的那段时间就得有个去处：要么锁住别人，要么让别人看见中间态。2PC/XA 让数据库把行锁一直拿到第二阶段，隔离最好，别人等得最久；TCC 把“占住”写成业务上的冻结，锁只拿几毫秒，代价是三个方法和一张 fence 表；Saga 先做成、出错再补，最快也最“脏”；本地消息表干脆不回滚，只保证消息最终送到。选哪种，看两件事：这一步会不会因为业务原因失败，中间态能不能被人看见。

①要解决的问题：一张单，三个库，要么都成，要么都没发生

在全景第 4～10 站，订单 9527 要在 order_db、inventory_db、coupon_db 三个库各写一笔：插一张订单、扣 2 件 sku 88、用掉券 MINUS20。三个库分属三个服务，谁也开不了别人库上的事务。

单库时这件事由一个 @Transactional 搞定：三条 SQL 在一个连接上，COMMIT 一下全生效，崩了靠 undo 全撤（Spring 事务、redo、undo）。现在要找的，是跨三个连接、三个进程的“一起生效、一起撤销”。

②不用它会怎样：三个本地事务各提交各的

最自然的写法：placeOrder() 上照样挂 @Transactional，里面依次插订单、调库存、调券。可这个注解只管订单服务自己那一个连接；库存、券那边各自提交，提交了就收不回来。

  • 加 try/catch 手动补偿？券服务回一句“不行”时管用。可发起方被 kill -9 时，catch 块跟着进程一起没了，没人记得“9527 已经扣过库存”。
  • 先调远程、最后再提交本地？顺序换了，窗口还在：远程都提交了，本地提交前崩溃，结果反过来。
  • 超时就重试？第 5 站 300 ms 超时只说明“不知道”，库存可能已经扣了（幂等那一页）。

缺的那一块：一个比发起方活得久、记得这笔全局事务的东西，加上每一笔都能被撤销、或者能晚一点再生效。前者是协调者，后者是四种做法各自的办法。MySQL 自己内部也碰到过同一个问题：redo 和 binlog 是两本账，它用的是两阶段提交（两本账，一个判定）。

!不懂精华时的典型误用
一种
引入 Seata，方法上加 @GlobalTransactional，以为三个库都会自动回滚；用的却是 TCC 模式，订单那一笔直接 orderMapper.insert()，没走任何分支代理。回滚时库存、券退了，订单还在。
另一种
一律上 XA“最保险”。热门商品的那一行被全局事务锁住几百毫秒，大促时下单排成一条线；发起方一崩，锁要拿到超时那一刻。

③几种流派：“还没定下来”的那段时间，各放在哪

比的是五件事：第一阶段做了什么，sku 88 被锁或被占多久，别人能不能看见中间态，失败了谁来撤，要写多少业务代码。

做法第一阶段做了什么sku 88 被锁 / 被占中间态别人看得见吗失败了谁来撤业务代码
2PC / XA
数据库的 XA PREPARE		SQL 都执行了，没提交，行锁拿着行锁拿到第二阶段。实测别人等 286～302 ms看不见（读到旧值，写要排队）数据库自己回滚几乎不用写
TCC
Try / Confirm / Cancel		Try：冻结，本地提交行锁约 1 ms；2 件冻结到 Confirm / Cancel看得见“少了 2 件”，看不见订单你写的 Cancel每个参与方 3 个方法 + fence
Saga
正向 + 补偿		直接做成，本地提交行锁约 1 ms；没有“占”，是真扣了看得见，而且是“已售”你写的补偿，倒着跑每步 1 个正向 + 1 个补偿
本地消息表
outbox，RocketMQ 事务消息同理		只提交订单和“待发消息”不占；消息到了才扣看得见，下游随后跟上没人撤，只会重试一张表 + 投递任务 + 消费端去重
Seata AT
代理数据源，自动 undo		直接提交，同时记 undo_log；先拿全局锁全局锁拿到第二阶段（TC 上的锁，不是行锁）默认看得见（全局读未提交）Seata 按前镜像改回去几乎不用写

选择规则：先问“这一步会不会因为业务原因失败”。不会（发通知、加积分、写日志）→ 本地消息表，最便宜，J08 全景就是它。会失败、而且能“先占住” → TCC（库存冻结、券锁定）。会失败、但没法占（调第三方支付、长流程）→ Saga。参与方都是支持 XA 的数据库、并发不高、要强隔离 → XA。想少写代码、能接受全局锁和 Seata 的约束 → AT。

④核心取舍：锁住别人，还是让别人看见

先知道这些
  • 行锁拿到提交为止：InnoDB 的 UPDATE 给行加 X 锁，事务提交或回滚才放；别人来改同一行就排队，等满 innodb_lock_wait_timeout（默认 50 秒）报 1205。见锁等待与死锁。
  • 协调者和参与者：发号施令、记住结局的叫协调者（Seata 里叫 TC）；各自管一个库、执行命令的叫参与者（RM）；发起全局事务的叫 TM，这里就是订单服务。
  • 超时 ≠ 失败：只说明“不知道”。所以二阶段的命令会被重发，接收方必须幂等，见幂等设计。
  • 软状态、最终一致：中间态允许存在一会儿，但最终要收敛。见 CAP、BASE。

机制 1：两阶段提交的骨架，和它卡住的地方

四种做法的祖宗是 2PC：先问一圈“你们都能提交吗”，全说能，再下令提交。关键在中间那个点：参与者一旦投了“能”，就既不能自己提交，也不能自己回滚，只能等协调者的决定。

这就是 2PC 的“阻塞”：问题不在慢，而在不确定区里谁也替不了协调者。所以 Seata 把 TC 做成 3 节点 Raft 集群、决议写多数派（全景第 3、7 站），协调者挂一台，新 leader 读得到决议，接着推第二阶段；协调者自己的高可用，下钻第 5 步 Raft 那页讲。MySQL 这边，PREPARED 状态的 XA 事务从 5.7.7 起断开连接也不回滚；8.0.29 加的 xa_detach_on_prepare（8.4 默认 ON）让别的连接能替它 XA COMMIT / XA ROLLBACK，实测就是靠它收的尾。

机制 2：中间态放在哪——四条泳道上的 sku 88

四种做法都绕不开“还没定下来”的那几百毫秒。下面是⑤里的实测：券服务这次很慢，300 ms 才处理完；第 50 ms 有个买家来买 1 件 sku 88。

被放弃的设计：让数据库的行锁贯穿全程XA，全景没用它

  • 行锁要拿“一次跨服务下单”那么久：几百毫秒，发起方一崩就是 60 秒（TC 超时）。热门商品那一行，所有人排成一队。
  • 锁在数据库里，业务看不见也插不了手：没法说“这 2 件先冻着，别人可以买剩下的”。

选中的设计：把“占住”写成业务状态TCC 的冻结

  • Try 是一个普通的本地事务，几毫秒就提交、放锁；“占住”变成 frozen 这一列，别人照样能买剩下的 48 件。
  • 代价一：要写 Try、Confirm、Cancel 三个方法，还要扛住重发、乱序（机制 3）。代价二：冻结的东西别人看得见、买不到，隔离变弱了。

决定胜负的约束：全局事务跨了网络和慢服务，时长不可控；数据库行锁的持有时间必须可控。所以把“占住”从数据库锁挪到业务数据上——这也是 Saga、本地消息表、AT 共同的出发点，它们只是挪得更远：Saga 连“占”都不要，直接做；本地消息表连“撤”都不要。XA 也不是输家：并发低、要强隔离时（比如内部财务系统），它最省心。

机制 3：TCC 要扛住的三种乱序，和 fence 这张表

二阶段由 TC 推，网络会丢包、会重发、会迟到。Cancel 落到一个分支上时，可能是这三种情况，靠的都是同一张 tcc_fence_log：主键 (xid, branch_id)，一个分支一行，一行一个状态机。

1 · 幂等

库存 Cancel 的应答丢了，TC 1 秒后重发。没 fence：available + 2 又执行一次。实测旁边有一单 9528 冻着 2 件，重发的 Cancel 把它的也“退”了，9528 的 Confirm 随后失败。

2 · 空回滚

券的 Try 还在路上，Cancel 先到了。要回成功，否则 TC 一直重试；但什么都不能改，并留下一行 suspended。

3 · 悬挂

Cancel 之后，那个迟到的 Try 才到。没 fence：券被锁给一张已取消的单，全局事务早结束了，再没人来解。实测券停在 LOCKED → 9527。

三件事归根到底一句话：Cancel 要能留下“我来过”的记号，Try 和二阶段都先看记号再动手，而且看记号、改记号、改业务在同一个本地事务里（fence 记录和业务在同一个库，这一条和幂等那页的去重表是同一个道理）。Seata 的二阶段先 SELECT … FOR UPDATE 锁住这一行再判断，两个 Cancel 同时到也只有一个能干活。

机制 4：Seata 替你做了什么，没替你做什么

模式Seata 替你做了还得你自己做
AT（默认，最常见）代理数据源：解析你的 SQL，同一个本地事务里记前镜像、后镜像到 undo_log；提交前向 TC 拿全局锁；二阶段提交异步删 undo，回滚按前镜像改回去别绕过 Seata 改这些行（回滚时后镜像对不上就抛 SQLUndoDirtyException，要人工）；要“读已提交”得用 SELECT … FOR UPDATE
TCC（全景用的）登记分支、传 BusinessActionContext（xid、branchId、Try 的参数）、推二阶段、重试；useTCCFence = true 时管 fenceTry / Confirm / Cancel 三个方法的业务逻辑；冻结字段的设计；建 tcc_fence_log 表
Saga状态机引擎：按 JSON 定义的流程调正向服务，异常时倒着调补偿，状态日志落库每个补偿服务自己做幂等、空补偿、防悬挂（Seata 文档原话：Saga 不保证隔离）
XADataSourceProxyXA：分支里自动 XA START / END / PREPARE，二阶段 XA COMMIT / ROLLBACK数据库要支持 XA；接受锁持有时间

最少的写法：Seata TCC 的一个参与方

库存服务的 TCC 接口 + 订单服务的入口超时、fence 清理、隔离级别放到 ⑥
// 库存服务：一个接口，三个方法
@LocalTCC
public interface StockTcc {
    @TwoPhaseBusinessAction(name = "stockReserve", commitMethod = "confirm",
                            rollbackMethod = "cancel", useTCCFence = true)   // fence 默认是关的
    boolean reserve(@BusinessActionContextParameter(paramName = "orderId") long orderId,
                    @BusinessActionContextParameter(paramName = "qty") int qty);   // Try：冻结
    boolean confirm(BusinessActionContext ctx);   // 冻结 → 已售
    boolean cancel(BusinessActionContext ctx);    // 冻结 → 可售；ctx.getXid()、ctx.getBranchId()
}

// 订单服务：TM。三个 Try 都成功就提交，任何一个抛异常就回滚
@GlobalTransactional(name = "place-order", timeoutMills = 60000)
public long placeOrder(long userId, long skuId, int qty, long couponId) {
    long id = orderTcc.create(userId, skuId, qty);   // 订单自己也要是一个分支（② 的误用）
    stockTcc.reserve(id, qty);
    couponTcc.lock(id, couponId);
    return id;
}

  • hot：XA 的买家等的是整个全局事务（≈ 券服务的 300 ms），其余三种只等一个本地事务。
  • last2：只有 XA 的买家买到了，因为回滚前谁也没看见“少了 2 件”。TCC、Saga 最后都对上了，但买家已经被拒；本地消息表最后对不上：订单待支付、库存扣了、券用不了。

    ⑥反例和误用：挂着“分布式事务”的名字，没满足它的约束

    第一圈

    注意事项：不知道就会出事故

    1有一笔没登记成分支← ④ Seata 管什么
    现象
    回滚后库存、券都退了，订单那一行还在，状态“待支付”。
    根源
    TC 只给登记过的分支推二阶段。TCC 模式下直接 mapper.insert() 不是分支；AT 模式下没走代理数据源的连接也不是。
    做法
    全局事务里的每一笔写都要能说出“它是哪个分支”。订单自己也写成 TCC（Try 插 CREATING，Confirm 改 WAIT_PAY）。
    2不开 fence← ④ 三种乱序
    现象
    偶发：别的单的冻结被退掉、Confirm 失败；券、库存永远停在“锁定 / 冻结”。实测两种都出现了。
    根源
    二阶段会重发、会比 Try 先到；Cancel 不留记号，就分不清“做过”“没 Try 过”“Try 还在路上”。
    做法
    useTCCFence = true（默认 false），fence 表建在业务库里。自己实现时，照机制 3 那张图写，记号和业务同一事务。
    3Confirm 里还在做校验，会失败← ④ 决议以后只能往前
    现象
    TC 日志每秒报一次同一个 xid 提交失败，永不停止；库存一直冻着。
    根源
    决议“提交”已经写进多数派，不能回头。Seata 二阶段重试默认不设上限（maxCommitRetryTimeout = -1），恢复任务每 1 秒捞一次。
    做法
    所有“能不能”的判断放进 Try；Confirm 只做“转正”，只依赖 Try 占住的东西。重试持续失败要报警、人工介入，而不是指望它自己好。
    4把会失败的步骤放在本地消息表后面← ④ 中间态放在哪
    现象
    订单待支付了，库存扣不上 / 券用不了，消息进死信。实测 last2：订单 WAIT_PAY、库存 0、券属于别人。
    根源
    本地消息表只保证“送到”，没有“撤销”这条路。下游因为业务原因说“不行”，上游早就提交了。
    做法
    只把“下游一定能成功”的事放在消息后面（通知、积分、搜索索引）。库存、券这种会失败的，放进 TCC 的 Try；实在要异步，就配反向消息，那已经是 Saga 了。
    5XA 包着跨服务的慢调用← ④ 不确定区
    现象
    大促时热门商品下单 RT 飙升、大量 1205；某个实例崩溃后一整分钟那件商品谁也买不了。
    根源
    行锁要拿到第二阶段。实测：券服务慢 300 ms，买家就等 300 ms；协调者死在 PREPARE 之后，锁拿到有人收拾为止。
    做法
    XA 只用在并发低、调用短的地方。热点行上用 TCC 冻结，或者把热点拆出全局事务。
    6全局事务超时比业务还短← ④ 超时就是判死
    现象
    调外部风控要 90 秒的单，全部在第 60 秒被回滚；用户看到“下单失败”，风控那边却通过了。
    根源
    发起方没说结局时，TC 只能拿超时当“它死了”（全景第 10 站）。默认 timeoutMills = 60000。
    做法
    慢的外部调用挪出全局事务（先调完再开事务，或者用 Saga）；timeoutMills 显式写，比这条链路的 P99 大一截。
    7AT 模式下，有人绕过 Seata 改了同一行← ④ AT 怎么回滚
    现象
    回滚失败，TC 一直重试，日志里是 SQLUndoDirtyException: Has dirty records when undo。
    根源
    AT 回滚前要比对：当前数据等于后镜像才敢用前镜像改回去；被全局事务外的写改过（后台脚本、另一个没开全局事务的接口），就不敢动。
    做法
    会和全局事务碰同一批行的写，也加 @GlobalLock（或也纳入全局事务）；运维改数据走同一套服务。
    8Saga 的补偿写成“反向 SQL”就完事← ④ 三种乱序
    现象
    补偿跑完了，迟到的“用券”请求才执行：订单取消、券被用掉（实验台：Saga + kill -9）。
    根源
    和 TCC 一样会乱序，Saga 也没有隔离。Seata Saga 的文档专门写了三节：允许空补偿、防悬挂、幂等。
    做法
    补偿服务也按 fence 的思路留记号：补偿先到时记一笔，正向请求后到时看到记号就拒绝。
    第二圈

    使用规范：团队里该怎么写

    • 先选最弱的那一种。能用本地消息表就不用 TCC，能用 TCC 就不在热点上用 XA。防的是：为了“保险”把整条链路锁住。
    • Try 做全部检查并占住资源，Confirm 只转正，Cancel 只退回。三个方法都只改“这一单的那一份”（每单一行冻结记录，见幂等页的状态机）。防的是：Confirm 失败、重试偷走别人的冻结。
    • fence 全开，fence 表和业务表同库；那个库用读已提交。Seata 源码注释里写了：可重复读下 fence 的二阶段可能死锁。防的是：记号和业务分开提交、间隙锁死锁。
    • fence 记录要清。tcc.fence.cleanPeriod 默认 1 天，清的是已结束的旧记录；设成 0 或负数就不清，表会一直长。防的是：fence 表膨胀拖慢 Try。
    • 全局事务里不放外部调用、不放慢 IO；timeoutMills 显式写。防的是：坑 5、坑 6。
    • 对账兜底，告警有人看。按单号每 10 分钟比一次三个库（全景第 11 站）；死信、长期 suspended、重试不止的 xid 都要报出来。防的是：“最终一致”永远不到来，也没人知道。
    第三圈

    深处：几个“为什么”

    三阶段提交（3PC）为什么没人用

    3PC 在准备和提交之间加了一个“预提交”，让参与者超时后能自己猜结局。可它假设网络不会分区：一旦分区，两边各猜各的，就提交了一半。工业界的选择是不去猜，而是让协调者自己不会丢：决议写进 Raft 多数派（Seata 2.0 起 TC 支持 raft 存储），协调者换一台，接着推。参与者在不确定区里的等待并没有消失，只是等的时间变短了。

    AT 的全局锁：它在隔离上补了什么

    AT 的一阶段直接提交本地事务，行锁几毫秒就放了，那两个全局事务改同一行怎么办？提交本地事务前，要先在 TC 上拿这一行的全局锁（主键为粒度），拿不到就重试、超时回滚。所以写和写之间是隔离的；读默认读得到别的全局事务还没定下来的值（全局读未提交），要读已提交就用 SELECT … FOR UPDATE，它会去检查全局锁。@GlobalLock 是给“不开全局事务、但要和全局事务互斥”的本地操作用的，比开一个全局事务轻。

    MySQL 的 XA，两个容易被忽略的版本点

    版本变化对你的影响
    5.7.7PREPARED 的 XA 事务断开连接不再回滚，异常重启后也还在2PC 才真正成立；也意味着协调者丢了，锁就一直在（实测 xacrash B）
    8.0.29新增 xa_detach_on_prepare，默认 ON：PREPARE 后事务和会话脱钩别的连接能 XA COMMIT / ROLLBACK，恢复程序不必用原连接（实测）
    Seata 2.0.0TC 新增 raft 存储模式（之前是 file / db / redis）TC 集群不再依赖外部数据库存决议
    Seata 2.6.0写这页时的最新稳定版（2026-01）；2.7.0 还是 RC全景按 2.6.0 写

    TC 的恢复任务

    提交中、回滚中、超时检查各有一个周期任务，默认都是 1000 ms（server.recovery.committingRetryPeriod 等）；已结束事务的清理是 30 秒一次。maxCommitRetryTimeout、maxRollbackRetryTimeout 默认 -1，不设上限：Seata 的态度是“决议了就一定推到底”，推不动的交给人。

    面试官会怎么问

    2PC 的问题是什么？Seata 怎么解决的？

    同步阻塞（参与者 PREPARE 后锁一直拿着）、协调者单点（它丢了决议，参与者只能干等）。Seata 用 Raft 集群存决议解决单点；用 AT / TCC 把一阶段做成本地提交，锁只拿几毫秒，解决长时间持锁。不确定区里的“等”没有消失，只是挪到了业务层的冻结或全局锁上。

    TCC 的空回滚、悬挂是什么？怎么防？

    空回滚：Try 没执行，Cancel 先到，要回成功但什么都不改。悬挂：Cancel 之后迟到的 Try 又把资源占上，没人再来释放。都靠一张以 (xid, branch_id) 为主键的事务控制表：Try 插 tried，Cancel 没找到记录就插 suspended，Try 插入撞主键就拒绝；二阶段先查状态，已到终态直接返回（幂等）。

    本地消息表和 RocketMQ 事务消息有什么区别？什么时候不能用？

    都是“业务和发消息原子化”：前者把消息写进业务库的一张表，后者用半消息 + 回查（事务消息那页）。都只保证下游最终收到，不能回滚上游。下游可能因为业务原因失败（库存不够、券被用）时不能用。

    自测

    1. 用一句话说出这一页的精华

    跨库没有一个本地事务能兜住“还没定下来”的那段时间，只能选：用数据库锁挡住别人（XA），用业务冻结占住资源（TCC），先做后补（Saga），或者只保证最终送到（本地消息表）；协调者负责记住结局并推到底，参与者负责扛住重发和乱序。

    2. ② 里三个本地事务各提交各的，为什么 try/catch 补偿救不了？

    补偿逻辑活在发起方进程里。发起方被 kill -9，catch 块不会执行，也没有任何地方记着“9527 已经扣过库存”。缺的是一个比发起方活得久的协调者。

    3. ⑥ 坑 3（Confirm 会失败）的根源是 ④ 的哪条？

    机制 1：决议一旦写进多数派，结局就定了，只能往前推。Confirm 失败不能变成回滚，只能无限重试，所以 Confirm 不能包含任何可能失败的业务判断。

    4. 预测：XA 方案下，三个分支都 PREPARE 了，TC 刚写下“提交”决议就整个集群断电（3 台全挂）。sku 88 那一行怎样？恢复后结局是什么？

    行锁一直拿着（PREPARED 的 XA 事务断连、重启都还在，机制 1 的不确定区）。TC 恢复后读到“提交”决议，推 XA COMMIT，结局是提交。如果决议没写进多数派就断电，恢复后查不到决议，按超时回滚。关键是决议有没有落到多数派。

    5. 预测：TCC 开了 fence，库存的 Confirm 和一个迟到的 Cancel 同时到（Cancel 是上一轮超时重发的残留）。会怎样？

    二阶段先 SELECT … FOR UPDATE 锁住 fence 那一行，两个排队。Confirm 先拿到：tried → committed，后到的 Cancel 看到 committed，回失败并打 warn，业务不动。Cancel 先拿到就反过来。不会出现“既提交又回滚”。不过正常情况下 TC 不会对同一分支同时发两种命令，出现了说明有 bug，要报警。

    6. 放回全景：第 6 站 kill -9 前后各发生了什么？fence 没开会怎样？

    之前：第 3 站拿到 XID，第 4 站订单 Try（CREATING），第 5 站库存 Try（冻结 2 件），第 6 站券服务刚收到 Try。之后：没人发 commit，TC 在第 10 站等满 60 秒，给三个分支推 Cancel：订单取消、库存退回；券分支看 fence，Try 没提交就是空回滚，记 suspended，迟到的 Try 被拒。不开 fence：重发的库存 Cancel 可能把别的单的冻结也退了，迟到的 Try 把券锁给一张已取消的单，没人再解；第 11 站对账会报出“订单 CANCELLED、券 LOCKED”。
