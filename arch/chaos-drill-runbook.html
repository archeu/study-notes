预案写在纸上不算：故障演练与预案

预案回答“出了这件事，谁在什么信号下做什么、做完怎么确认、不行怎么退”。演练就是故意把这件事做出来，看预案是不是真的接得住。全景 D-3 那次演练，杀掉 Redis 主节点：哨兵判定下线的时间按示例配置写 30 秒，客户端实际停写 42 秒；改成 5 秒，7 秒就恢复。还发现了一件预案里没写的事：旧主重启以后有 10 秒还在当主，这期间写给它的数据，同步完就没了。这些都只有做一遍才知道。

①什么时候用得上：大促前三天，把要出的事先出一遍

全景第 11 站：开抢时 Redis 主节点宕机。D-3 已经演练过一次，所以当天大家知道会停多久、会看到什么、该做什么。地图给 J12 的任务是“再演练一次 Redis 主节点宕机”，过关标准是“说清 RTO、RPO 各是多少，怎么测出来的”。演练要回答四个问题：

多久恢复RTO从客户端看，不是从运维看
丢了多少RPO已确认的写入还在不在
期间用户看到什么降级快速失败，还是转圈
怎么回到正常恢复旧主回来以后怎样

②常见笨办法：预案写好放在 wiki 里

笨办法为什么看起来对出事时会怎样
写了预案，从没跑过步骤都写清楚了参数是错的（切换要 42 秒，预案写的是“秒级”）、权限没开、脚本路径变了、负责人离职了
只在测试环境演安全测试环境没有真实流量、没有真实的告警和值班链路，演不出“半夜三点谁被叫醒”
只演“切换成功”能切过去就行没演“切换以后旧主回来”“切换期间用户看到什么”，于是有了脑裂和转圈
出事现场想办法有经验的人在压力下判断慢、容易误操作；RTO 里最长的一段往往是“决定要不要切”
不懂精华时的典型误用把“故障演练”当成“我们把机器关了，服务还活着”的展示。演练的价值在于发现预案和现实的差距：如果每次演练都顺利通过、什么也没发现，要么是系统真的很好，要么是演练太保守。⑤ 里第一次演练就发现了两件事：下线判定的参数让 RTO 变成 42 秒；旧主回来的那 10 秒里，有写入会丢。

整个机房切断机房入口流量、停掉一边的数据库主平台化的演练系统，通常各公司自建

一次演练的五步（混沌工程的做法）

  • 爆炸半径从小到大先测试环境，再生产的一台机器、一个实例，最后才是一个机房；每一级都过了再放大。
  • 先写停止条件真实流量的错误率或 P99 超过某个值就立刻停止、恢复，演练不能变成事故。
  • 先写假设再动手“预计 10 秒内恢复写入、不丢已确认数据”。演完对照假设，差距就是发现。

④背后的机制：预案长什么样，RTO 由什么组成

一条预案的五个部分

部分写什么Redis 主节点宕机这一条
触发信号哪个告警、什么阈值券服务 Redis 调用失败率 > 5% 持续 10 秒；哨兵 +switch-master 事件
自动动作系统自己做的哨兵切主；券服务熔断器打开，回“排队人多，请稍后”
人工动作谁、做什么、几分钟内值班确认切主完成；若 60 秒未恢复，网关限流降到 2000/秒
验证怎么确认恢复了写入成功率回到 99% 以上；活动后对账 MySQL 发券数 ≤ 1000
回退动作本身出问题怎么办熔断器半开探测；旧主回来由哨兵降为从库，期间禁止任何程序直连旧主

RTO 是一串时间加起来的

实测 ⑤ 的两次演练。深色段是 down-after-milliseconds：哨兵要等这么久没收到回复才认为主节点下线；浅色段是剩下的时间：多数哨兵确认、选出领头哨兵、提升从库、客户端通过哨兵找到新主并重连。两段各占多少，要看哨兵日志里 +sdown、+odown、+switch-master 的时间戳（练习 1）。

判定时间越短，RTO 越短，但也越容易误判：网络抖一下、主节点做一次慢的 fork，就被当成宕机切走，切换本身又会造成几秒不可用。5 秒还是 30 秒，没有标准答案，要在演练里同时测“真宕机的 RTO”和“抖动时会不会误切”。

旧主回来的那十秒

旧主重启后，它不知道自己已经被换掉，仍以主节点身份启动、接受写入。哨兵发现它“报告自己是主、但配置里它是从”，要先等一段时间（源码里是 4 个发布周期，默认 2 秒 × 4 = 8 秒），确认没有更新的配置，再发 REPLICAOF 把它降为从库。降级以后它和新主全量同步，自己的数据被丢弃。⑤ 里这段窗口是 10.2 秒，窗口里直连旧主写进去的数据，同步完就没了。客户端如果都通过哨兵找主，就不会写到旧主上；写死 IP 的程序、手工 redis-cli 连上去的人，就是这段窗口里的风险。

⑤跟着做一遍：一次 Redis 主节点宕机演练

拓扑：1 主 2 从，3 个哨兵（quorum 2），都是 redis:8.10.3-alpine 容器。客户端用 Lettuce 通过哨兵找主，命令超时 500 ms；一个线程持续 INCR seq，失败就当作“降级”（立刻返回，不重试）。按五步走一遍，down-after-milliseconds 分别设 30000 和 5000 各演一次。

⑤RedisFailoverDrill.java演练脚本：稳态、注入、观察、验证、恢复完整代码 →
w.start(); Thread.sleep(2000);                 // 1 稳态：先确认成功率正常
sh("kill", "ch-m");                            // 2 注入：主节点宕机
while (recoverNs.get() == 0) Thread.sleep(50); // 3 观察：等客户端第一次写成功
// RTO = 恢复时刻 - 注入时刻；RPO = 客户端确认过的最大值 - 新主上的值
sh("start", "ch-m");                           // 5 恢复：旧主回来，看它多久被降级
cd study-labs/java
DOCKER="sudo docker" mvn -q -pl arch/chaos-drill-runbook compile exec:java \
  -Dexec.mainClass=labs.arch.chaos_drill_runbook.RedisFailoverDrill     # 默认演 30000 和 5000 两次，自己起、自己删容器
== down-after-milliseconds = 30000 ==
1 稳态：2 秒写入成功 737 次，失败 0 次，主节点 172.22.0.2
2 注入：docker kill ch-m
3 观察：杀主后 42.1 秒恢复写入；期间失败 81 次；单次请求最慢 523 ms（超时设 500 ms）
        新主上 seq = 1158，客户端确认过的最大值 1158 → 丢失已确认写入 0 次
4 验证预案：不可用期间每个请求最多等 523 ms 就拿到结果（降级），没有请求卡住
== down-after-milliseconds = 5000 ==
1 稳态：2 秒写入成功 723 次，失败 0 次，主节点 172.22.0.2
2 注入：docker kill ch-m
3 观察：杀主后 7.2 秒恢复写入；期间失败 14 次；单次请求最慢 524 ms（超时设 500 ms）
        新主上 seq = 1147，客户端确认过的最大值 1147 → 丢失已确认写入 0 次
4 验证预案：不可用期间每个请求最多等 524 ms 就拿到结果（降级），没有请求卡住
5 恢复：旧主重启 10.2 秒后被降为从库（此刻 orphan = written-to-old-master），16.3 秒后和新主同步完成
        同步完成后，那段时间直连旧主写的 orphan：旧主上 (没了)，新主上 (没有)

实测 2 核 ARM 虚拟机，JDK 17，Lettuce 6.8.2，Redis 8.10.3。42.1 秒和 7.2 秒在两轮完整演练里都一样；第 5 步的数字来自单独再演的一次 5000（第一轮的第 5 步只等了 20 秒，读法不对，修了脚本重跑）。

  • RTO30 秒的判定时间让客户端停写 42 秒，换成 5 秒就是 7 秒。预案里如果写着“哨兵秒级切换”，第一次演练就会被推翻。
  • RPO两次都是 0：这次是干净的宕机，复制没有落后。和上一页“专线先断、再宕机”的 11555 次对比：RPO 取决于宕机前复制落后了多少，所以演练要分别演“干净宕机”和“先断网再宕机”。
  • 降级不可用期间每个请求最多 0.52 秒就拿到结果：超时 500 ms 起了作用，用户看到“稍后再试”，而不是转圈。
  • 意外发现旧主回来的 10.2 秒里还在当主，写进去的数据同步后消失。预案要加一条：故障节点恢复期间，禁止任何程序绕过哨兵直连。

到这里已经能交差了：一份带实测 RTO、RPO 的演练报告，一条按五个部分写好的预案。已知还没处理的细节：哨兵自己挂了、抖动误切、告警没响、复盘不落地，都在⑥。

⑥刻意练习

第一圈 · 演练里常发现的事

1参数照抄示例，RTO 比预期长几倍⑤ 实测← ④ RTO 的组成
现象
预案写“秒级切换”，实测 42 秒。
根源
判定下线要等 down-after-milliseconds，示例配置是 30 秒。
做法
按 RTO 目标设参数，同时演一次“网络抖动”确认不会误切。
2旧主回来，有一段时间两个主⑤ 实测← ④ 旧主回来的十秒
现象
窗口里写进旧主的数据消失。
根源
哨兵等确认后才降级旧主，旧主并不知道自己被换掉了。
做法
所有客户端都经哨兵找主；故障节点恢复前先从负载均衡和服务发现里摘掉；Redis 可配 min-replicas-to-write 让孤立的主拒绝写入。
3哨兵和主节点放在同一台机器上← ④ 预案的自动动作
现象
那台机器宕机，主节点和两个哨兵一起没了，剩一个哨兵凑不够 quorum，不切换。
根源
“自动动作”依赖的组件和故障本身在同一个故障域里。
做法
哨兵分散在三台机器、最好三个机房；演练时专门演“杀两个哨兵”看会不会切。
4判定太敏感，抖一下就切← ④ 误判
现象
主节点一次慢 fork（几百毫秒）或网络抖动，就被切走，切换本身造成几秒不可用。
根源
判定时间短，误判概率高。
做法
用 tc netem 注入几秒延迟，确认不误切，再定参数。
5演练时告警没响，或者响给了离职的人← ④ 触发信号
现象
故障持续了 20 分钟才有人看到。
根源
告警规则、值班表、通知渠道从没被真实触发过。
做法
演练时不提前通知值班，检验从告警到有人响应的时间（这是 RTO 里“发现”那一段）。
6复盘写了行动项，没人做← ③ 第 5 步复盘
现象
下次演练发现同样的问题。
根源
行动项没有负责人和截止日期。
做法
每个行动项进任务系统，下次演练第一件事是验证上次的行动项。

第二圈 · 练习（由易到难，做对了会看到什么）

  1. 拆 RTO：演练时 docker logs -f ch-s1，记下 +sdown、+odown、+switch-master 的时间戳，把 7.2 秒拆成几段。你会看到大头是判定时间，其余各段在 1～2 秒以内。
  2. 杀两个哨兵：先杀 ch-s1、ch-s2，再杀主。预测：quorum 是 2，只剩 1 个哨兵，能判定客观下线吗？能选出领头吗？运行后应该看到写入一直失败、不会自动恢复。
  3. 先断网再宕机：把上一页的“专线断开”加进来，先让从库落后 2 秒再杀主，RPO 应该不再是 0。
  4. min-replicas-to-write：给主节点设 min-replicas-to-write 1、min-replicas-max-lag 10，重演第 5 步。旧主回来时没有从库连着它，写 orphan 应该被拒绝。
  5. 写一条预案：给“第 9 站消费者卡住、消息积压”写一条完整的五部分预案，再设计一次演练来验证它（参考上面的速查卡片）。

第三圈 · 深处

  • 混沌工程原则Netflix 提出、principlesofchaos.org 总结的几条：围绕稳态建立假设、模拟真实世界的事件、在生产环境中实验、持续自动化地跑、把爆炸半径降到最小。Chaos Monkey 每天随机关掉生产实例，逼着每个服务都能扛住单实例故障。
  • 演练平台化大规模时，演练要有统一入口：选目标、选故障类型、设停止条件、自动采集指标、自动生成报告。ChaosBlade 和 Chaos Mesh 提供注入能力，编排和报告多由各公司自建。
  • 大促前的“红蓝对抗”一组人不告知时间地注入故障，另一组人按预案处理，计时考核。考的不只是系统，还有值班的人和流程。

↺回到⑤：改一改

  1. 停止条件：给演练脚本加一个停止条件：失败持续超过 15 秒就自动 docker start ch-m 并结束。用 30000 演一次，看停止条件是否生效。（③ 先写停止条件）
  2. 报告：让脚本最后打印一份三行报告：假设、实测、差距。（③ 先写假设）
  3. 熔断：把“失败就降级”换成真的熔断器（Resilience4j 或 Sentinel），看熔断打开后 Redis 恢复时，多久才重新放流量。（④ 预案的回退）

自测

1. 用一句话说出这一页的精华

预案写清触发信号、自动和人工动作、验证和回退；演练按“稳态、注入、观察、恢复、复盘”故意把故障做出来，测出真实的 RTO、RPO 和用户看到的东西，找出预案和现实的差距，并逐步放大爆炸半径。

2. 预案写好但从没跑过，疼在哪？

参数、权限、脚本、人员、告警都可能和写的时候不一样了，出事时第一次执行就会卡住；RTO 也只是估计，可能差几倍（⑤ 的 42 秒）。

3. 坑 2（旧主回来时有两个主）的根源是 ④ 的哪一条？

“旧主回来的十秒”：旧主重启后仍以主身份接受写入，哨兵要等几个发布周期确认后才把它降为从库，降级后全量同步丢弃它的数据。

4. 预测：把 down-after-milliseconds 设成 500，RTO 会变成多少？会带来什么新问题？

真宕机时 RTO 可能缩到两三秒（判定时间之外还有选举、提升、重连），但一次几百毫秒的 fork 或网络抖动就会触发切换，切换本身造成几秒不可用，还可能来回切。参数要在“真宕机的 RTO”和“误切率”之间取舍，两种都要演。

5. 预测：⑤ 的拓扑里，只杀掉一个哨兵，再杀主，会切换吗？

会。剩 2 个哨兵，quorum 是 2，够判定客观下线；选领头需要多数（3 个里的 2 个）授权，2 个也够。杀两个就不行了（练习 2）。

6. 放回全景：第 11 站前后各发生了什么？如果 D-3 没有演练，开抢那一刻 Redis 主宕机会怎样？

第 11 站是“出事时”的一站，前面是那一秒的第 3～10 站，后面是第 12 站机房断电。没有演练时，哨兵按示例配置 30 秒判定，券服务停写 40 多秒；如果券服务的超时和熔断也没配好，请求会挂满线程池，连带页面转圈；切主后库存可能回涨，只要第 9 站有条件更新兜底就不会超发。演练过，就能提前把判定时间、超时、熔断、降级文案都调好。

档位：标准。本机跑过（2 核 ARM 虚拟机，JDK 17，Lettuce 6.8.2，redis:8.10.3-alpine 1 主 2 从 3 哨兵）：两轮完整演练（30000、5000）加一次只演 5000 的补测，页面上的秒数和次数来自这些输出。预案速查卡片的内容来自本站其他知识点页，在 node 里检查过脚本。

按源码（redis 8.0 分支 sentinel.c）：sentinel_info_period 默认 10000 ms、sentinel_publish_period 默认 2000 ms；把“自称是主的从库”降级前要等 sentinel_publish_period × 4。按文档：down-after-milliseconds 是判定主观下线的时间，示例配置为 30000；min-replicas-to-write / min-replicas-max-lag 让主节点在可用从库不足时拒绝写入。工具（ChaosBlade、Chaos Mesh、Toxiproxy）只列能力，本页没有使用。
