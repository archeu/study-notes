机房断电以后：多活与容灾，RTO 和 RPO

容灾先回答两个数：RTO，出事以后多久恢复服务；RPO，最多丢多少已经告诉用户“成功”的数据。RPO 由复制方式决定：等对面机房确认了再回复用户，就不丢，但每次写都要多等一个来回，对面一断写就失败；不等就快，断了就丢。光在光纤里跑 1000 公里要 5 毫秒，所以同城可以同步复制、做到 RPO≈0；异地只能异步，要多活就得把用户分成单元，让每条数据只在一个单元里写。

①要解决的问题：整栋楼断电，系统还在不在

全景第 12 站：开抢时机房 A 断电。同一个机房里的冗余（多台机器、主从、哨兵）都在这栋楼里，一起没了。要回答两个问题，地图“怎么算过关”第二条就是它：说清你的系统 RTO、RPO 各是多少，怎么测出来的。

RPO 往故障之前看（丢了多少），RTO 往故障之后看（停了多久）。两个数都要靠演练测出来，下一页故障演练讲怎么测。

②不用它会怎样：只有一个机房，加每天的备份

很多系统的“容灾”只是：一个机房，MySQL 一主一从，每天凌晨全量备份传到对象存储。机房 A 整个没了，要在别处新建机器、拉备份、回放 binlog。J11 的订单库（140 GB）恢复演练就要 4 小时，RTO 是小时级；备份之后的写入要看 binlog 有没有及时传出去，RPO 从几分钟到一整天。

不懂精华时的典型误用在同一个机房里做了主从、哨兵、集群，就说“高可用了”。这些挡得住一台机器挂，挡不住整栋楼断电、空调故障、光缆被挖。另一个误用是有了异地机房，复制却是异步的，还对外承诺“零丢失”：⑤ 的实验里，专线断了 2 秒，主库挂掉以后，已经回复“成功”的 11555 次写入没了。

③几种流派：从冷备到异地多活

流派做法RTORPO代价
冷备备份传到异地，出事再恢复小时级分钟到天最便宜
主备（热备）B 机房有一套随时能用的从库和应用，平时不接流量十几到几十分钟（要人决定）同城半同步≈0B 的机器平时闲着；从没接过流量，切过去常出意外
同城双活两个机房都接流量，数据库主在一边、另一边是半同步从库分钟级≈0（半同步不退化时）每边都要能单独扛峰值；跨机房调用多 1 ms 左右
两地三中心同城双活 + 异地一个灾备中心（异步复制）同城故障分钟级，城市级故障更长同城≈0，城市级秒级金融行业的常见要求
异地多活用户按 ID 分成单元，每个城市负责一部分用户的读写分钟级（改路由）秒级（单元间异步）改造最大：每条数据要能归到一个单元

看一眼各流派的时间线

各段时长是典型值，按设计估算，不是测量值；横轴是对数刻度，否则冷备的 5 小时会把其他几种挤成一条线。真实系统的数要靠演练测。

本页的重点是同城双活（全景第 12 站用的就是它），再讲清它为什么不能直接放大成异地多活。选择规则：RPO 要求为 0、RTO 要求分钟级，就做同城双活；要扛城市级灾难，加异地灾备（两地三中心）；只有业务能按用户切开、又要求城市级故障时也不停服务，才值得做异地多活。

④核心取舍：距离决定复制方式，复制方式决定 RPO

取舍一：光速是硬约束

同步复制的意思是：主库要等对面确认收到，才回复用户“成功”。每次写都多一个机房间往返。同城多 1 ms，可以接受；北京到上海多 30 ms，一个下单事务里如果有十几次写，就多出几百毫秒，接受不了。所以同城能做到 RPO≈0，异地基本只能异步，RPO 是秒级。

取舍二：等对面确认，还是先回复用户

等确认（同步 / 半同步）MySQL 半同步、Redis WAIT

回复“成功”的写入一定也在对面。代价：每次写多一个往返；对面断了，写就失败或卡住。⑤ 实验里，专线断开后 2 秒只有 9 次写入尝试，全部失败。

先回复（异步）MySQL、Redis 的默认

写本地就回复，复制在后台追。代价：对面断了也照样“成功”，主库一挂，这段时间的写入就没了。⑤ 实验里丢了 11555 次已确认的写入。

决定胜负的约束：网络断开时，系统只能二选一：继续接受写入（可用，但可能丢），或拒绝写入（不丢，但不可用）。这就是 CAP 在容灾里的样子。MySQL 半同步默认选了折中：等从库确认最多 10 秒（rpl_semi_sync_source_timeout 默认 10000 ms），超时就悄悄退化成异步继续写，见坑 3。

取舍三：异地多活为什么要单元化

异地只能异步复制。如果北京、上海两边都能改同一行数据，异步复制就会互相覆盖：北京把订单改成“已支付”，上海同时把它改成“已取消”，两边都成功，复制过去以后谁覆盖谁说不清。解决办法是让每条数据只有一个城市能写：按用户 ID 把用户分成单元，1024 号用户属于北京单元，他的订单、券、地址都只在北京写，上海只有异步复制来的副本。北京挂了，再把这个单元的路由切到上海。

  • 能按用户切开的订单、领券记录、购物车、地址：天然属于某个用户，单元化顺利。
  • 切不开的全局数据券的总库存、商品库存、商家余额：所有用户都在改同一个数。要么只放在一个“中心单元”里写（异地请求要跨城访问，多 30 ms），要么事先拆份额（北京 500 张、上海 500 张，一边抢完了再调拨）。全景的抢券恰好是最难的那种。
  • 读多写少的配置商品信息、券规则：中心写、各单元只读副本，延迟几秒能接受。

还有一个坑：两边都以为自己是主（脑裂）

机房间专线断了，但两个机房都还活着。B 联系不上 A，以为 A 挂了，把自己的从库提升为主；A 其实还在接写入。两个主同时写，数据分叉，恢复时要人工对账。防它的办法是多数派：放第三个地点做仲裁（哨兵、Raft 节点放在第三个机房），只有能联系上多数的一方才能当主；被隔离的一方要自觉停止写入（fencing），见 Raft 和 fencing。

⑤套进场景：断专线、杀主库，数一数丢了多少

两个 Redis 容器模拟两个机房：dr-a 是主，dr-b 是从。程序一直往 dr-a 写 INCR seq，记下客户端最后一次收到“成功”的值。时间线：正常写 1 秒 → 专线断了（dr-a 上禁用复制用户并踢掉复制连接，dr-b 收不到新数据，dr-a 照常接受写入）→ 再写 2 秒 → 机房 A 断电（杀掉 dr-a）→ dr-b 提升为主，读它的 seq。客户端确认过的最大值减去新主上的值，就是丢掉的已确认写入。

⑤FailoverLab.java两种写法，只差一行 WAIT完整代码 →
long v = ra.incr("seq");
if (mode.equals("wait")) {
    long n = ra.waitForReplication(1, 200);      // WAIT 1 200：至少 1 个从库确认，最多等 200 ms
    if (n < 1) { failed.incrementAndGet(); continue; }   // 告诉客户端：没写成功
}
acked.set(v);                                    // 告诉客户端：成功

实测 2 核 ARM 虚拟机，JDK 17，Lettuce 6.8.2，Redis 8.10.3 容器。具体次数每次运行都不同（写入速度、断链生效的时刻），“async 丢、wait 不丢”每次都成立。“断网前已确认”之后还有一段成功写入，是因为断链命令（docker exec）本身要几百毫秒才生效。

  • async专线断开后的约 2 秒里，dr-a 继续以每秒几千次的速度回复“成功”；dr-b 停在 2801。主一挂，这 11555 次全没了：RPO 就是“专线断开到主库挂掉”这段时间。
  • wait专线一断，每次 WAIT 都等满 200 ms 拿不到确认，写入全部按失败处理：2 秒里只尝试了 9 次。不丢，但等于停服。而且这些“失败”的 INCR 其实已经在 dr-a 上执行了：“告诉客户端失败”不等于“没写”，Redis 文档也明确说 WAIT 不会让 Redis 变成强一致的存储。

放回全景：抢券在机房 A 断电时

  • 券服务、网关无状态，两个机房各一半，入口按健康检查把流量全切到 B。B 要能单独扛 2 万：按上一页的计算器，每边 6 台；只有 4 台就要同时把限流降到 1.6 万。
  • MySQL 发券表主在 A，B 是半同步从库：已提交的发券记录在 B 上都有（只要半同步没退化），RPO≈0。从库提升为主要 1～2 分钟。
  • Redis 库存异步复制，就是 ⑤ 的 async：可能丢掉最后一两秒的扣减，库存“回涨”。不在 Redis 层追求不丢，而是靠第 9 站 MySQL 的条件更新兜底（见秒杀页坑 2）。
  • 结论这一站的 RTO 目标 5 分钟（发现 30 秒、自动切换 2 分钟、预热 2 分钟），RPO：账本（MySQL）≈0，快路径（Redis）约 1 秒、由账本纠正。这两个数要在演练里测出来，下一页做。

⑥反例和误用

第一圈 · 套上了名字，没满足约束

1“双活”，但 B 只有 30% 的机器← ④ 每边都要能单独扛
现象
A 断电后流量全进 B，B 立刻过载，跟着挂。
根源
平时按流量比例部署，没按“单独扛峰值”部署。
做法
按容量计算器配；或者预案里写明“切换的同时把限流降到 B 的容量”。
2伪双活：B 从来没真正接过写← ④ 取舍二
现象
B 平时只读，切过去以后发现配置缺了、权限没开、连接池指向 A 的 IP。
根源
没走过的路一定有坑。
做法
定期把一部分真实写流量放到 B（或定期演练切换），让 B 一直是“热”的。
3半同步悄悄退化成异步按文档← ④ 取舍二
现象
号称 RPO=0，演练时还是丢了数据。
根源
MySQL 半同步等从库确认超过 rpl_semi_sync_source_timeout（默认 10 秒）就退回异步，专线抖动一下就可能触发。
做法
监控半同步状态（Rpl_semi_sync_source_status、退化次数）并告警；要求更严的用 MGR（组复制）或 Raft 系的数据库。
4专线断了，两边都当了主← ④ 脑裂
现象
A、B 同时接受写入，恢复后两份数据对不上。
根源
只有两个地点，谁都无法判断是对方挂了还是专线断了。
做法
仲裁放在第三个地点，多数派才能当主；旧主发现自己联系不上多数就停止写入。
5异地多活了，全局数据却两边都写← ④ 单元化
现象
券库存在北京、上海各扣各的，异步复制互相覆盖，超发。
根源
切不开的全局数据没有指定唯一的写入方。
做法
全局数据放中心单元写，或事先拆份额；每张表都要标明属于哪类。
6切流量靠改 DNS，客户端半小时后才切过去← ① RTO 的“切换”段
现象
DNS 早改了，一部分用户还在连 A 的 IP。
根源
DNS 有 TTL，运营商和客户端还会自己缓存，不完全听 TTL 的。
做法
入口用两边都有的负载均衡或 Anycast，按健康检查切；App 内置多个入口地址，自己探测。

第二圈 · 团队里怎么做

  • 先定目标，再选架构每个系统分级：核心交易 RTO 5 分钟、RPO 0；报表 RTO 4 小时、RPO 1 天。不是所有系统都要多活。
  • 数据分类每张表标明：用户维度（可单元化）、全局（中心写）、配置（只读副本）。防的是坑 5。
  • 切换要自动、要有人能叫停发现和切换自动化，RTO 才可能是分钟级；但要有一键回切和人工暂停，防误切。
  • RTO、RPO 写进演练报告每次演练记录实际的发现时间、切换时间、丢失的数据量，和目标比。防的是“应该能切过去”。

第三圈 · 深处

  • Raft 系数据库的“自带容灾”TiDB、OceanBase 的每份数据有 3 或 5 个副本、多数派确认才算提交，副本放在三个机房就自动有 RPO=0、秒级切主（接 J11 分布式数据库）。代价同样是距离：副本跨城，每次提交就多一个跨城往返。
  • 单元化的路由网关按用户 ID 算出单元，请求带着单元号一路往下；RPC、MQ、数据库都要认这个单元号，和上一页的压测标记透传是同一种技术。
  • Redis 的选择Redis 主从永远是异步的，WAIT 只能降低丢失概率。要“不丢”的数据不要只放 Redis，放进有同步复制的存储，Redis 只当快路径（全景就是这么分的）。

↺回到⑤：改一改

  1. 改断开时长：把“再写 2 秒”改成 0.5 秒和 5 秒，看 async 丢失的次数是不是和时长成正比。（RPO = 断开到故障的时长）
  2. 改 WAIT 超时：WAIT 1 20 和 WAIT 1 2000，断开期间各尝试了几次？哪个对用户更友好？（④ 取舍二）
  3. 不杀主：专线断了但不杀 dr-a，5 秒后恢复复制用户，看 dr-b 能否追平；这就是“抖动”而不是“故障”。
  4. 测 RTO：加一段代码，从杀掉 dr-a 开始计时，到客户端在 dr-b 上第一次写成功为止，打印 RTO。（下一页的主题）

自测

1. 用一句话说出这一页的精华

容灾用 RTO（多久恢复）和 RPO（丢多少）衡量；RPO 由复制方式决定，等对面确认就不丢但断了就写不进，不等就快但会丢；光速让同城能同步、异地只能异步，所以同城双活能做到 RPO≈0，异地多活要靠单元化让每条数据只在一个地方写。

2. 只有单机房加每天备份，疼在哪？

整栋楼的故障会同时带走主从和哨兵；只能从备份恢复，RTO 是小时级，RPO 取决于最后一次备份和 binlog 传出的时间。

3. 坑 3（半同步退化）的根源是 ④ 的哪一条？

取舍二：网络断开时只能在“拒绝写”和“继续写但可能丢”之间选。MySQL 半同步等满超时就选了后者，退化成异步，所以 RPO=0 只在专线正常时成立。

4. 预测：⑤ 的 async 模式里，如果专线一断就立刻杀主（断开 0 秒），丢多少？

接近 0，只剩复制本身的滞后（同机器上是毫秒级）。async 的 RPO 主要取决于“复制断开或落后”持续了多久，而不是主库挂的那一下。所以监控复制延迟就是在监控 RPO。

5. 预测：异地多活下，1024 号用户属于北京单元。北京整体故障，他在上海单元能看到 3 秒前刚领的券吗？

不一定。他的数据从北京异步复制到上海，最后几秒可能没过来（RPO 秒级）。切到上海后，他可能看不到那张券；等北京恢复，要把这几秒的差异补回来或对账。这就是为什么异地多活通常只对“晚几秒、能事后修复”的数据做。

6. 放回全景：第 12 站前后各发生了什么？如果第 9 站没有条件更新，机房切换会带来什么后果？

第 12 站是“出事时”的一站，正常时第 3～10 站把流量削到 1000 行；第 11 站是 Redis 主节点单独宕机。机房切换时 Redis 库存是异步复制的，B 上的库存可能比实际多（回涨），券服务会多放出一些人；没有第 9 站 MySQL 的 issued < 1000 条件更新，这些人就真拿到了券，超发。

档位：标准。本机跑过（2 核 ARM 虚拟机，JDK 17，Lettuce 6.8.2，redis:8.10.3-alpine 容器）：⑤ 的两种模式各跑 1 次（调通前另跑过一次 wait 模式，同样丢 0），次数来自那次输出。③ 的时间线是典型值，按设计估算，脚本在 node 里跑过。

按文档：Redis 复制默认异步，WAIT 返回确认了的副本数，文档说明它不会让 Redis 成为强一致存储，故障切换时仍可能丢失已确认的写入；MySQL 半同步 rpl_semi_sync_source_timeout 默认 10000 ms，超时后切换为异步复制，从库追上后再恢复半同步。距离与时延是典型值。
