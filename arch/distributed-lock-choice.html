两个实例只许一个发：Redis、ZooKeeper、数据库三种分布式锁怎么选

三种锁回答的是同样三个问题：锁记在哪，怎么知道持锁的人死了，锁服务自己换主时会不会把锁弄丢。数据库行锁跟着连接走：人死了立刻放，人卡住就一直不放。Redis 和租约行按到期时间：到点就放，不管人还在不在干活。ZooKeeper 按会话心跳：人活着就不放，心跳停了才放；而且每次写都要过半节点确认，换 leader 不丢锁。可谁都分不清“死了”和“卡住了”，所以只要锁会自己过期，卡住后醒来的那个实例就会再发一次。锁只能减少重复，最后兜底的是下游去重。在第 9 站，outbox 本来就在订单库里，最省事的做法是连分布式锁都不用。

全景：一次下单跨三个库 · 第 9 站地图：J09 · 分布式锁：Redis、ZooKeeper、数据库怎么选

这一页的位置分布式锁的第三圈。第一圈 Redis 分布式锁讲了 SET NX PX、Lua 解锁和 Redisson；第二圈 锁过期与 fencing token讲了锁到期时持锁的人还没干完怎么办。这一圈补上另外两种锁，ZooKeeper 和数据库，再把三种放一起比，重点比两件事：持锁的实例出事时锁什么时候放，锁服务自己换主时锁还在不在。换主这件事要用到刚学的 Raft。

①为什么需要：同一条 ORDER_CREATED 只能发一次

在全景第 9 站，这一步要解决：Confirm 已经把 9527 改成 WAIT_PAY，同一个本地事务里往 outbox 插了一行 ORDER_CREATED 9527，状态 NEW。订单服务有两个实例 A 和 B，都跑着同一个扫描任务，每秒扫一次 outbox。两个都去发，1024 就会收到两条“请付款”的提醒，后面 30 分钟没付款就取消的计时也会开两份。

②没有它会怎样：20 条消息，10 条是重复的

⑤ 的实验里，两个实例同时扫 5 轮，每轮新来 2 单。不加锁：发出 20 条，重复 10 条，每一单都发了两遍。synchronized 只管一个 JVM，A 和 B 是两个进程，管不到（第一圈 为什么本地锁不够）。

缺的那一块：一个 A 和 B 都看得见的地方记着“现在谁在扫”，还要能回答：记着的那个人死了，什么时候换人。三种锁的差别几乎都在后半句。

!不懂精华时的典型误用
做法
“加了锁就不会重复发”，下游 notify-svc 就不做去重。
结果
A 拿着锁卡了 8 秒（一次长 GC），租约行和 ZooKeeper 的锁都在 5 秒时放给了 B，B 发了一次；A 醒来不知道锁已经没了，又发了一次。⑥ 实测两种锁都是 2 次。锁只能保证“大部分时候只有一个”，挡不住所有重复。

③相邻方案：锁记在哪，人死了怎么放

能让两个进程看见同一个“谁在扫”的地方，项目里现成就有三个：Redis、订单库本身，还有注册中心那一类协调服务（ZooKeeper、etcd）。另外还有一种做法：不用锁，换一种扫法。

做法锁记在哪持锁的人死了，怎么放锁服务换主时天然的 fencing token用在哪
Redis
SET NX PX、Redisson		一个 key到期自动删（PX）；Redisson 看门狗每 10 秒续成 30 秒异步复制，可能丢没有，要自己 INCR最常见；前两圈都在讲它
数据库行锁
SELECT … FOR UPDATE		一行上的 InnoDB 行锁，在事务里事务提交、回滚或连接断开就放；卡住就一直不放行锁不复制，新主上没有这把锁没有锁和要改的数据在同一个库；XXL-JOB 调度中心抢 xxl_job_lock 就是这样
数据库租约行
UPDATE … WHERE expire_at < NOW()		一行记录：owner、token、expire_at到期后别人能抢（按数据库的时钟）看复制方式：异步可能丢，半同步、MGR 不丢token 列每次 +1ShedLock 的 JDBC 版（它没有 token 列）
ZooKeeper
Curator InterProcessMutex		一个临时顺序节点会话超时后节点自动删除（心跳停了才算）过半写，不丢顺序号已经有 ZooKeeper 的系统：Kafka 老版本、Dubbo、HBase
不用锁
FOR UPDATE SKIP LOCKED		每一行 outbox 自己的行锁同上，跟着事务走和库一起切不需要资源本身就在数据库里：队列表、outbox、任务表

etcd 的锁和 ZooKeeper 是一类：租约加 Raft 多数派，号用 revision。放进下一圈。

选择规则：先看锁护的那个东西在哪。在数据库里，就用数据库自己的锁或条件更新，最好连锁都不用（SKIP LOCKED、UPDATE … WHERE status = 'NEW'）。不在数据库里：要高吞吐、能接受偶尔两个人同时持锁，用 Redis；要换主不丢、持锁时间长短不定，并且已经有 ZooKeeper 或 etcd，就用它们。三种都要配上下游去重。

本页学 ZooKeeper 的临时顺序节点和数据库的两种锁（行锁、租约行），和前两圈的 Redis 放一起比。第 9 站最后的答案是 SKIP LOCKED。

④原理：每把锁都要回答三个问题

先知道这些
  • 超时 = 不知道：等不到回应，只说明“我没听到”，不说明“它死了”。见时钟、超时与重试。
  • 租约：带到期时间的锁，到点不续就自动作废。第二圈讲过：锁是一份租约，到点就收。
  • 多数派：3 台里 2 台写下才算写成功，挂 1 台不丢。ZooKeeper 用的 ZAB 协议和 Raft 是同一类：一个 leader 排序，过半确认再提交。
  • InnoDB 行锁：FOR UPDATE 加的锁属于事务，提交或回滚才放；它只在这台 MySQL 的内存里，不写 binlog。见 MySQL 锁等待与死锁。
1 · 锁记在哪A 和 B 都能看见、同一时刻只有一个能写成功的地方：一个 Redis key、一行数据库记录（或这一行上的行锁）、一个 ZooKeeper 节点。
2 · 持锁的人死了怎么办锁不能永远占着。办法有三种：连接断开就放（行锁），到点就放（Redis PX、租约行），心跳停了才放（ZooKeeper 会话）。
3 · 锁服务换主丢不丢记着锁的那台机器自己也会挂。换上来的新主有没有这条记录，取决于“写成功”是怎么定义的：主库自己写下就算，还是过半写下才算。

机制 1 · ZooKeeper：排队的号码牌，前一个走了叫下一个

  • 临时（EPHEMERAL）：节点绑在创建它的会话上。会话正常关闭，或者服务端在会话超时内一个心跳都没收到，判它过期，这个会话的临时节点全部删除。判死看的是心跳，不看干了多久：A 发得再慢，只要 JVM 还在跳，锁就一直在。
  • 顺序（SEQUENTIAL）：创建时服务端在名字后面拼一个 10 位递增号。⑥ 实测同一把锁连着几轮拿到的号是 0、1、2、3、4，可以直接当 fencing token。
  • 过半写：create 和 delete 都经 leader 提议、过半写下才返回。A 拿到“创建成功”时，至少 2 台已经记下了这个节点，换 leader 也还在（机制 3）。

机制 2 · 数据库：一把跟着事务走的行锁，或者一行带到期时间的记录

机制 3 · 锁服务换主：“写成功”是谁说了算

为什么这样设计：死了和卡住了，从外面看是一样的

不放：等它自己说放

行锁、GET_LOCK。安全，但持锁的人卡多久，别人就等多久。机器断电时连 FIN 都没有，MySQL 要等 wait_timeout（默认 28800 秒）或 TCP keepalive 才知道它没了。

到点就收：过期了给下一个

Redis PX、租约行、ZooKeeper 会话。不会一直卡着，但卡住的人醒来还以为自己持锁。ZooKeeper 用心跳把“到点”往后推：活着但慢不会丢锁，整个进程停住（长 GC、SIGSTOP、虚拟机被暂停）心跳也停，一样会丢。

决定胜负的约束：A 不说话的时候，没人能分清它是死了还是卡住了（超时 = 不知道）。所以每把锁只能二选一：宁可一直等（左），或者宁可偶尔两个人同时以为自己持锁（右）。没有第三种锁能两头都占。右边的漏洞要靠被写的那一方补：检查 token（第二圈 fencing），或者干脆按业务 key 去重（幂等设计）。

三种锁最少的写法超时、监听连接状态、SKIP LOCKED 批量这些放到 ⑥

-- ... 扫 outbox、发、标 SENT ...
COMMIT;

-- 数据库租约行：影响 1 行就是拿到了
UPDATE lease SET owner = 'A', token = token + 1, expire_at = NOW(3) + INTERVAL 5 SECOND
 WHERE name = 'outbox-scan' AND (expire_at < NOW(3) OR owner = 'A');
// ZooKeeper：Curator 5.x
CuratorFramework zk = CuratorFrameworkFactory.newClient("zk1:2181,zk2:2181,zk3:2181",
        10_000, 3_000, new ExponentialBackoffRetry(200, 5));   // 会话 10 s、连接 3 s

InterProcessMutex lock = new InterProcessMutex(zk, "/locks/outbox-scan");
if (lock.acquire(0, TimeUnit.MILLISECONDS)) {                 // 0：抢不到就算了，下一秒再来
    try { scanAndSend(); } finally { lock.release(); }
}

交易靶场里的最小案例：一个 MySQL 8.4 容器放 outbox；ZooKeeper 用 Curator 的 TestingServer 在 JVM 里起，不用另装。两个线程当实例 A 和 B，用同一个起跑线同时扫。“发到 Kafka”换成往 kafka_log 表插一行：用单独的连接、自动提交，和真的 Kafka 一样，不会跟着业务事务回滚。

int scan(long waitMs, Runnable afterRead) throws Exception {
    long token = lock.tryLock(waitMs);            // 拿不到返回 -1
    if (token < 0) return -1;
    try {
        List<Long> ids = query("SELECT id FROM outbox WHERE status = 'NEW' ORDER BY id");
        if (afterRead != null) afterRead.run();   // ⑥ 在这里让 A 出事
        for (long id : ids) send(id, token);      // “发到 Kafka”：另一条连接、自动提交
        for (long id : ids) mark(id);             // UPDATE … SET status='SENT' WHERE id=? AND status='NEW'
        return ids.size();
    } finally { lock.unlock(); }
}

// 不用锁：每次只锁一行，别人锁着的行跳过

读出来的结论（本机 2 核 ARM，JDK 17，MySQL 8.4.13，Curator 5.9.0 + ZooKeeper 3.9.3，跑了 2 次，A、B 各发几条每次不同，发出和重复两列一样）
  • 不加锁：每一单都发了两遍。两个实例同一时刻读到同一批 NEW，谁也不知道对方也在发。
  • 三种锁都做到了 0 重复，但输的一方表现不同：租约行和 ZooKeeper 抢不到就直接回去（5 次），等下一秒；FOR UPDATE 的输家在等锁队列里排着（0 次直接回去），等 A 提交后拿到锁，一看已经没有 NEW 了，什么也不发。
  • SKIP LOCKED 不用任何锁，A、B 各发 5 条：每个实例锁住自己正在发的那一行，别人直接跳过它去拿下一行。两个实例在一起干活，而不是一个干一个等。
到这里已经能交差了：第 9 站的扫描任务改成 FOR UPDATE SKIP LOCKED，两个实例都在发，同一条只发一次；如果必须“全局只有一个在跑”（比如要按顺序发），用租约行或 ZooKeeper 锁，加上下游按 order_id 去重。
已知还没处理的细节：持锁的实例被 kill、被卡住、发得慢时锁各怎么样（⑥ 实测），ZooKeeper 会话超时被服务端改掉（坑 1），锁丢了自己不知道（坑 2），持着行锁调 Kafka（坑 3），锁服务换主（第三圈）。

⑥细节：持锁的人出事、锁服务换主，各会怎样

先看实测：A 读完 9527 之后出三种事

A 单独跑在一个 JVM 里，拿到锁、读完 outbox 就打印 READY。主进程收到后对它下手：kill -9；kill -STOP 冻住 8 秒再 kill -CONT，模拟一次长 GC；或者什么也不做，只是 A 自己发得慢，要 8 秒。B 在主进程里一直抢锁。租约行租期 5 秒，ZooKeeper 会话超时 5 秒。

锁A 被 kill -9A 被冻住 8 秒A 活着，但发了 8 秒
FOR UPDATEB 0.0 s 拿到 · 发 1 次B 8.1 s 才拿到 · 发 1 次（A）B 8.1 s · 发 1 次（A）
租约行 5 sB 5.0 s · 发 1 次B 5.0 s · 发 2 次（B#2，A#1）B 5.0 s · 发 2 次（B#2，A#1）
ZooKeeper 会话 5 sB 5.1 s · 发 1 次B 5.3 s · 发 2 次（B#3，A#2）B 8.1 s · 发 1 次（A#4）

# 后面是那次发送带的 token：租约行是 token 列，ZooKeeper 是节点顺序号。A 醒来时三种锁的 A 都“以为还持着”：租约行没人告诉它，ZooKeeper 的 isAcquiredInThisProcess() 也还是 true。本机 2 核 ARM，JDK 17，MySQL 8.4.13，Curator 5.9.0 + ZooKeeper 3.9.3。

读出来的结论
  • kill -9：行锁最快，进程一死内核关掉连接，MySQL 立刻回滚。租约行和 ZooKeeper 都要等满 5 秒，ZooKeeper 的会话在连接断开后还会保留到超时，因为客户端可能连到另一台去续上。
  • 冻住：只有行锁做到了只发 1 次，代价是 B 白等 8 秒。租约行和 ZooKeeper 都在 5 秒时换了人，A 醒来又发了一次。冻住的进程里心跳线程也停了，ZooKeeper 的心跳保护不到这种情况。
  • 活着但慢：这一列把 ZooKeeper 和租约行分开了。ZooKeeper 的心跳一直在跳，会话不过期，B 等 A 干完；租约行不管 A 在不在干，5 秒到了就给 B。Redis 的 PX 和租约行一样，Redisson 看门狗做的就是 ZooKeeper 心跳的事。

第一圈 · 注意事项

1ZooKeeper 会话超时被服务端改了← ④ 心跳判死
现象
持锁的实例被 kill 之后，四十秒都没人接着发。
根源
会话超时是客户端提、服务端定的：服务端只接受 2 × tickTime 到 20 × tickTime 之间的值，超出范围的会被改到边界上。Curator 不设时默认要 60 秒，tickTime=2000 的集群最多给 40 秒，这 40 秒里锁一直挂在死掉的实例名下。
做法
显式设 sessionTimeoutMs（10～15 秒常见），启动时打印 getZooKeeper().getSessionTimeout() 看协商结果；⑤ 实测请求 5000 ms，拿到 5000 ms。
2锁丢了，自己还以为拿着← ④ 死了和卡住分不清
现象
集群凑不够多数派，A 的连接状态变成 SUSPENDED，5 秒后变成 LOST；可 isAcquiredInThisProcess() 一直返回 true（第三圈实测）。
根源
这个方法只看本地内存里的记录，不问服务端。锁是服务端在会话过期时删掉的，客户端要等连上了才会知道。
做法
注册 ConnectionStateListener：SUSPENDED 就停止发送，等到 RECONNECTED 再继续；LOST 就当锁已经没了，重新抢。Curator 文档原话是 SUSPENDED 时“不能确定你还持有锁”。
3拿着 FOR UPDATE 去调 Kafka← ④ 行锁跟着事务
现象
Kafka 抖了 30 秒，订单库连接池被占满一条、等锁的线程一排，别的接口也开始超时。
根源
行锁要等事务提交才放，事务里有一次网络调用，锁就和这次调用一样长。机器断电或网线拔了时连 FIN 都没有，MySQL 要等 wait_timeout（默认 28800 秒，本机 8.4 实测也是）或 TCP keepalive 才回滚。
做法
事务里只放短的本地操作。要在锁里调外部服务，改用租约行或 ZooKeeper；第 9 站这种扫表，直接用 SKIP LOCKED，每一行的事务只包住那一行。
4用 GET_LOCK 当锁，配上连接池← ④ 锁跟着连接
现象
RELEASE_LOCK('outbox-scan') 返回 0，锁没放掉，之后谁也拿不到；切主之后又突然两个实例都拿到了。
根源
GET_LOCK 是会话级的命名锁，拿锁和放锁必须是同一条连接。用 JdbcTemplate 两次调用各借一条池连接，放锁那条不是拿锁那条，锁就一直挂在池里某条连接上，直到它被回收。它也只在这台 MySQL 的内存里，不复制到从库。
做法
非用不可时，拿锁、干活、放锁在同一条连接上（同一个事务，或者手动拿一条 Connection）。更推荐租约行。
5租约到期时间用应用机器的时钟算← ④ 租约行
现象
某台机器的时钟快了 3 秒，它总能“提前”抢到别人还没到期的锁。
根源
“过期了没有”是拿 expire_at 和当前时间比。A 写进去的到期时间按 A 的钟，B 判断时按 B 的钟，两台机器的钟本来就不一样（时钟、超时与重试）。
做法
写和比都用数据库的 NOW(3)，只用一个钟。Redis 的 PX 也是 Redis 自己计时，同一个道理。
6以为有了锁就不会重复，下游不去重← ④ 二选一
现象
1024 偶尔收到两条“请付款”；notify-svc 里同一单开了两份 30 分钟取消计时。
根源
会过期的锁（租约、会话、PX）在持锁者卡住时一定会换人，实测发了 2 次。fencing token 只有被写的一方检查才有用，Kafka 的 producer 不认业务 token。
做法
消息带 order_id，消费端用去重表或状态机挡住第二条（幂等设计）。锁负责“少发”，去重负责“发多了也没事”。
7自己用 ZooKeeper 写锁，所有人都 watch 父节点← ④ 只 watch 前一个
现象
200 个任务实例抢同一把锁，每放一次锁，ZooKeeper 的请求量就冲出一个尖峰。
根源
watch 父节点的话，任何一个子节点删除都会叫醒全部 199 个等待者，它们一起 getChildren，只有一个能拿到（惊群）。
做法
用 Curator 的 InterProcessMutex，它只 watch 排在自己前面的那一个。

第二圈 · 使用规范

  • 锁护的东西在哪，就先用哪里的办法：在数据库里，就用条件更新、唯一键或 SKIP LOCKED，最好不上分布式锁。防的是：多一个组件，就多一种故障，还要多想一遍它和数据库之间不一致怎么办。
  • 没有 ZooKeeper 就别为了一把锁引进它：已经有 Redis 就用 Redisson；已经有 etcd、ZooKeeper（注册中心、Kafka 老集群）再用它们。防的是：为一把锁维护一个 3 节点集群。
  • 抢锁一律带等待上限：acquire(time, unit)、tryLock(wait, lease, unit)、innodb_lock_wait_timeout。定时任务用 0：这一秒抢不到就下一秒。防的是：线程无限挂在锁上。
  • ZooKeeper 锁必须监听连接状态，SUSPENDED 就停手。防的是：坑 2，锁丢了还在发。
  • 锁名带业务前缀，粒度按要互斥的东西取：/locks/outbox-scan，按商品锁就 /locks/stock/88。防的是：一把全局大锁把不相干的事也串行了。
  • 下游永远按业务 key 去重。防的是：坑 6，任何会过期的锁都会在长 GC 时出两个持锁者。

第三圈 · 深处

1. ZooKeeper 换 leader 时锁还在吗（实测）

3 节点集群（Curator TestingCluster，tickTime 500 ms，会话 5 秒）。A 持锁后先杀 leader，再杀一台：

  [ 11.9 s] A 的连接状态 → LOST
[ 16.8 s] A 自己以为还持锁吗（isAcquiredInThisProcess）：true
  • A 正好连在 leader 上，leader 一死 A 也断了。0.6 秒后它连上另一台，会话还是原来那个，锁节点还在，B 抢不到。会话只要在超时之内换一台连上就不会过期，这是 ZooKeeper 会话和 MySQL 连接最大的不同。
  • 只剩 1 台时谁也写不进：B 抢不到锁，A 也续不上会话。这是 CAP 里选了 C：宁可没人持锁，也不让两个人都持锁。
  • A 在 SUSPENDED 满 5 秒后收到 LOST，可 isAcquiredInThisProcess() 还是 true（坑 2）。Curator 3.0 起，客户端在 SUSPENDED 持续一个会话超时后自己判 LOST，不用等服务端通知。

2. 锁服务主从切换，三种锁谁丢谁不丢

锁旧主上 A 持着锁，旧主挂了新主上 B 能拿到吗怎么补
Redis 主从 + 哨兵key 可能还没复制过去可能马上拿到WAIT 1 100 等一个副本确认，只能缩小窗口；Redlock 用 5 个独立主，争议见下一圈
MySQL 行锁行锁在旧主内存里，不复制一定马上拿到A 的事务在旧主上已经没了，它标 SENT 会失败；可它要是已经发了，下游就收到两次
MySQL 租约行异步复制：可能丢；半同步 AFTER_SYNC：提交成功的一定在从库上异步时可能；半同步时要等到期开半同步，或者用 MGR（多数派）；切主后让新主先“冷静”一个租期再发锁
ZooKeeper过半写下才回成功拿不到，要等 A 放或会话过期不用补；少数派那边干脆不能写

3. 某台 follower 落后，会不会两个人都看见自己排第一

不会。ZooKeeper 保证两件事：所有写按 leader 分配的 zxid 排成一条线；同一个客户端的请求按发出顺序执行，它连着的那台服务器回复它的写时，已经应用了这条写之前的所有写。B 的 0000000003 是在 A 的 0000000002 之后排进去的，所以 B 读到的子节点列表里一定有 A 的节点。follower 落后只会让 B 晚一点知道“轮到我了”，不会让它提前以为轮到了。

4. 顺序号当 fencing token

顺序号是父节点上的一个计数器，每建一个子节点加 1，只增不减，换 leader 也不会倒退（它本身就是过半写下的状态）。⑥ 的实测里，同一把锁先后拿到的号是 0、1、2、3、4。要用它挡住迟到的写，被写的那一方要记住见过的最大号：比如在 outbox 加一列 fence，标 SENT 时 WHERE fence < ?。这挡得住“迟到的 A 去改数据库”，挡不住“迟到的 A 去发 Kafka”，所以第 9 站最终还是靠下游去重。计数器是 4 字节有符号整数，超过 2147483647 会溢出，一把锁拿二十多亿次之前要换个父节点。

自测

1. 用一句话说出这一页的精华

每把分布式锁都要回答锁记在哪、持锁的人死了怎么放、锁服务换主丢不丢；因为死了和卡住了分不清，锁只能在“一直等”和“偶尔两个人同时持锁”里选一个，所以资源在数据库里就用数据库自己的办法，会过期的锁一定要配上下游去重。

2. 第 9 站不加锁会怎样？只加 synchronized 呢？

两个实例同一秒读到同一批 NEW，各发一遍，⑤ 实测 20 条里重复 10 条。synchronized 锁的是一个 JVM 里的对象，A 和 B 是两个进程，各有各的对象，等于没加。

3. 坑 1（ZooKeeper 实例死了 40 秒才换人）根源是 ④ 的哪条？

机制 1：临时节点靠会话心跳判死，判死要等满会话超时；而会话超时由服务端在 [2, 20] × tickTime 里裁剪，Curator 默认请求 60 秒，tickTime 2000 时被裁到 40 秒。

4. 预测：把行锁那一行的事务里加一次 3 秒的 Kafka 调用，另一个实例 B 用 innodb_lock_wait_timeout = 1，B 会看到什么？

B 每次 SELECT … FOR UPDATE 等 1 秒就报 1205（Lock wait timeout exceeded），重试第 3、4 次时 A 提交了，B 拿到锁，发现没有 NEW。期间 B 的连接一直被占着。推自机制 2：行锁属于事务，提交才放。

5. 预测：Redisson 看门狗（默认 30 秒，每 10 秒续一次）下，A 被冻住 40 秒，会怎样？发得慢 40 秒呢？

冻住：看门狗的续期线程和 A 在同一个 JVM 里，也冻住了，30 秒后 key 过期，B 拿到并发送，A 醒来再发一次：2 次。发得慢：看门狗一直在续，B 拿不到，1 次。和 ZooKeeper 心跳一模一样，推自 ④“到点就收”那一边：续期只能挡住“慢”，挡不住“停”。

6. 预测：Redis 主从，A 刚 SET 成功主库就挂了，哨兵把从库提上来。A 发得很快，200 ms 就干完了，会重复吗？

看 B 什么时候扫。B 在新主上能马上拿到锁（机制 3：key 没复制过去），但新主接手通常要几秒（哨兵判下线、选举、切换）；A 200 ms 就发完并把 outbox 标成 SENT（这一步写的是订单库，不受 Redis 切换影响），B 拿到锁时已经没有 NEW，不重复。只有 A 的活比切换时间长，才会两个人一起发。

7. 放回全景：第 9 站前后各发生了什么？锁坏了（两个实例都以为持锁）整条链路会怎样？

之前：第 8 站 TC 推 Confirm，订单 CREATING → WAIT_PAY，同一个本地事务往 outbox 插 ORDER_CREATED 9527。之后：notify-svc 收到消息提醒 1024 付款，开始 30 分钟超时取消的计时。锁坏了：9527 发两遍，订单、库存、券三个库都不受影响（它们在第 8 站就定了），坏的只是下游：重复提醒、两份超时计时，到点可能取消两次。只要 notify-svc 按 order_id 去重、取消订单是 WHERE status = 'WAIT_PAY' 的条件更新，第二份就是空操作。

档位：标准。本机跑过（2 核 ARM，JDK 17，Docker 里的 MySQL 8.4.13，JVM 里的 ZooKeeper 3.9.3，Curator 5.9.0）：⑤ 的 scan 跑了 2 次；⑥ 的 die（3 种锁 × 3 种事故，A 是单独的 JVM，真的 kill -9 / kill -STOP）和 failover（3 节点 TestingCluster）各跑 1 次。MySQL 主从、Redis 主从切换没有在本机搭，表里是按复制机制推出来的，实验台上标“推演”。
