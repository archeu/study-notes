10 万个请求，只放进 2 万：限流算法

四种算法都在回答同一个问题：“刚才这段时间放了多少”怎么数。固定窗口按整秒数，换窗口时清零，所以两个窗口交界处能放进 2 倍；滑动窗口把一秒切成小格，数最近那几格；令牌桶记一个“还能放几个”的余额，按时间补，允许把攒下的余额一次用掉（突发）；漏桶让请求排队、匀速流出，不允许突发。网关入口多用令牌桶，因为它既限住长期平均速率，又放得过正常的短时突发。

全景：10 万人抢 1000 张券的那一秒 · 第 5 站地图：J12 · 限流算法：令牌桶、漏桶、滑动窗口

这一页的位置J12 第 3 个知识点。前两个是复习：三高的账算出了容量，响应时间为什么越压越长说明了超过容量会怎样。限流就是把“容量”变成入口上的一道闸。它在 J10 的 Sentinel 和 网关页里出现过用法，这一页讲算法本身。

①为什么需要：第 5 站，10 万个请求面前只有 3.2 万的容量

在全景第 5 站，App 已经把 30 万次点击合并成 10 万个请求，都在开抢后一秒左右到达网关。后面的券服务 8 台，压测出的容量是 3.2 万/秒，而券只有 1000 张。网关要做的事是：每秒只放进一个定好的数，多出来的立刻拒掉，而且第一秒允许稍多一点，因为开抢前系统是闲着的。

到达网关10 万开抢后约 1 秒
券服务容量3.2 万/秒8 台 × 4000，压测得出
限流值1 万/秒第一秒可突发到 2 万
被拒约 8 万HTTP 429，不进机房深处

数字来自全景页，是交易靶场的设计。本页 ⑤ 的实验按 1/100 缩小：限流 100/秒，桶容量 200。

②没有它会怎样：全放进来，再“尽力处理”

不限流，10 万个请求全部进入券服务。每台只有 200 个 Tomcat 线程、几十条 Redis 连接，处理不过来的请求在线程池队列和连接池里排队。响应时间那一页讲过后果：到达速率超过处理速率时，队列每秒都在变长，响应时间跟着涨，涨到客户端超时；超时的用户再点一次，进来的请求更多。最后连和抢券无关的普通下单也被拖慢。

也就是说，超过容量的请求早晚要被拒绝。区别只在于：是在入口用 1 毫秒拒掉，还是在里面排 10 秒队以后超时，顺便拖垮别的接口。

不懂精华时的典型误用自己写一个 AtomicInteger，每秒清零一次，超过 1 万就拒。这就是“固定窗口计数器”：0.9 秒到 1.0 秒放进 1 万，1.0 秒清零，1.0 秒到 1.1 秒又放进 1 万，0.2 秒里放了 2 万。⑤ 的实验 A 量出来正好是 2 倍。

③相邻方案：限速率、限并发、熔断、排队

管的是什么典型实现在全景里
限流（限速率）每秒最多放进多少个令牌桶、漏桶、窗口计数；Gateway RequestRateLimiter、Sentinel QPS 规则、Nginx limit_req第 5 站网关
限并发（隔离）同一时刻最多有多少个在处理Semaphore、线程池大小、Tomcat maxThreads、Sentinel 线程数规则券服务内部，保护 Redis 连接池
熔断下游坏了就先别调Sentinel、Resilience4j 的断路器第 11 站 Redis 主宕机
排队削峰先收下，按自己的速度慢慢做MQ、漏桶排队第 8、9 站发券消息

它们互补，不互相替代。限速率管“进来多快”，限并发管“里面有多挤”：按 Little 定律，并发 = 速率 × 处理时间，下游一变慢，同样的速率也会让并发涨上去，所以内部还要限并发兜底。排队削峰适合“必须做完、可以晚点做”的事（发券落库），不适合“用户在等结果”的事（抢没抢到）。

本页学入口那一道：限速率的四种算法。选择规则：允许短时突发、只限平均速率，用令牌桶；要求输出绝对平滑（比如调用一个严格限 QPS 的第三方接口），用漏桶排队；只要个大概、实现越简单越好，用滑动窗口计数。

④原理：怎么数“刚才放了多少”

先知道这些 限流值是一个速率：“每秒 100 个”，可它没说是哪一秒。从 0.0 到 1.0 秒算一秒，从 0.4 到 1.4 秒也算一秒。四种算法的区别，就在于它们对“任意一秒”保证到什么程度。 突发：短时间里来的请求比平均速率多。开抢第一秒就是典型的突发。

同一份流量，四种算法放进来的不一样

限流 100/秒。流量是两波：400～499 ms 来 100 个，1000～1099 ms 再来 100 个。两波相隔 0.6 秒，都落在同一个“任意 1 秒”里，按“每秒 100 个”的本意，这一秒最多只该放 100 个。

每条竖线是一个被放行的请求。右边的数是“任意 1 秒内最多放行几个”，超过 100 的标红。图由页面里的模拟代码画出，和 ⑤ 的 Java 实验 A2 输出一致。

四种算法各自记什么

固定窗口计数器

记一个计数和当前窗口的起点。窗口一换，计数清零。

状态：1 个数。代价：窗口交界处最多放进 2 倍。

滑动窗口（分桶计数）

把一秒切成 N 小格，每格一个计数。判断时把最近 N 格加起来；最老的一格过期就复用。

状态：N 个数。格太粗（比如 2 格）仍会超；Sentinel 默认就是 1 秒 2 格。

令牌桶

记两个数：余额和上次补的时间。请求来时先按“过了多久 × 速率”把余额补上（不超过容量），够 1 个就扣掉放行。

状态：2 个数。允许一次用掉攒下的余额，最大突发 = 容量。

漏桶（排队版）

记“下一个空位是几点”。请求来了排到空位上，空位往后挪 1/rate 秒；要等太久的直接拒。

状态：1 个时间。输出绝对平滑，代价是请求要等。

为什么网关入口多用令牌桶

选：令牌桶余额能攒，突发上限 = 容量

开抢前桶是满的，第一秒放行“容量”那么多，之后回到每秒 rate 个。闲的时候攒、忙的时候用，正好对上真实流量“平时稀、偶尔挤”的样子。请求要么立刻放行、要么立刻拒绝，不增加等待，用户在等结果的接口要的就是这个。

没选：漏桶排队输出平滑，但要等

开抢第一秒也只匀速放 rate 个，多出来的排队，最长可能排到 maxWait（⑤ 里是 500 ms）。对抢券这种“晚 0.5 秒就是另一个结局”的接口，排队等于把超时往后挪。漏桶适合下游扛不住任何突发的地方：调第三方短信接口、写一个只能匀速消化的库。

决定胜负的约束：入口的调用方是在等结果的用户，等待和拒绝一样糟；而下游（第 2 站压过）能扛住“容量”那么大的短时突发。两个条件都成立，令牌桶赢；下游连短时突发都扛不住，漏桶赢。

没有后台线程在补令牌：懒计算

令牌桶看起来需要一个定时器，每 10 ms 往桶里放一个令牌。实际实现都不这么做：请求来时，用“现在 − 上次补的时间”乘速率，一次把这段时间该补的补上。Guava 的 SmoothRateLimiter 和 Spring Cloud Gateway 的 Lua 脚本都是这样。这样做有三个好处：没有定时线程；一万个桶（每个用户一个）不需要一万个定时器；状态只有两个数，可以整个放进 Redis，一段 Lua 原子地完成“补 + 扣”。

代价是时间的精度取决于“现在”从哪来。Gateway 的脚本用 Redis 的 TIME，只取秒，所以同一秒里不补令牌：⑤ 的实验 B 里，按毫秒连续补的令牌桶第一秒放了 299 个（容量 200 + 补的约 100），按整秒补的只放了 200 个。反过来，一跨秒就一次补满 rate 个，所以它在秒的交界处和固定窗口一样：⑥ 实验台选“两波”、容量调到 100，整秒补的桶在 0.7 秒里放进了 200 个。

一台还是一群：限流的状态放在哪

做法状态在哪好处代价
单机限流每台进程内存零网络开销，Guava、Sentinel 默认总量 = 单机值 × 台数；台数一变总量就变
集中式（Redis + Lua）一个 Redis key全局精确，Gateway 的 RedisRateLimiter每个请求多一次 Redis 往返；限流 key 自己成了热 key；Redis 出错时 Gateway 默认放行

最少的用法

三处常见写法Guava · Gateway · Sentinel
// Guava：单机令牌桶（SmoothBursty），新建时余额是 0，空闲时最多攒 1 秒的量
RateLimiter limiter = RateLimiter.create(100);       // 每秒 100 个
if (!limiter.tryAcquire()) return tooManyRequests();  // 拿不到立刻拒，不等

# Spring Cloud Gateway：Redis 令牌桶，全部网关共享一个桶
filters:
  - name: RequestRateLimiter
    args:
      redis-rate-limiter.replenishRate: 10000   # 每秒补多少
      redis-rate-limiter.burstCapacity: 20000   # 桶最多存多少（最大突发）
      key-resolver: "#{@grabApiKey}"             # 返回同一个 key 就是总量限流，返回用户 ID 就是按用户

// Sentinel：QPS 规则，默认“直接拒绝”；controlBehavior 改成匀速排队就是漏桶
FlowRule r = new FlowRule("grabCoupon").setGrade(RuleConstant.FLOW_GRADE_QPS).setCount(10000);

参数细节（容量怎么定、Guava 的 Warm Up、Sentinel 的排队时长）放到第⑥步。

⑤亲眼看到：同一份流量喂给五个限流器

四种算法各写一个最小实现（每个 20 行左右，纯 JDK），再加一个照抄 Gateway Lua 脚本的“按整秒补”令牌桶。时间用模拟时钟（毫秒数由调用方传入），所以每次运行结果一样。最后用 Guava 33.5 的 RateLimiter 在真实时钟上跑一次。规模按全景缩小 100 倍。

⑤Limiters.java令牌桶这一段：懒计算，不需要定时器完整代码 →
public boolean tryAcquire(long now) {
    if (started) tokens = Math.min(capacity, tokens + (now - last) * ratePerMs); // 补上这段时间的
    started = true;
    last = now;
    if (tokens >= 1) { tokens -= 1; return true; }   // 够就扣
    return false;                                       // 不够就拒，不等
}

实测 2 核 ARM 虚拟机，JDK 17，Guava 33.5.0-jre。A、A2、B 用模拟时钟，结果确定；C 用真实时钟，毫秒数会有一两毫秒的抖动。

  • A、A2固定窗口在交界处放进 2 倍；滑动窗口切 2 格，遇到 A2 这种间隔 0.6 秒的两波照样放进 2 倍，切 10 格才挡住；令牌桶放了 119、169 个，多出来的是两波之间补上的令牌，它保证的是“长期平均”，不是“任意一秒”。
  • B同样每秒 100 个，四种算法的“第一秒”完全不同：固定窗口和整秒令牌桶在前 100～200 ms 就把额度用完，之后 0.8 秒一个不放；连续补的令牌桶先放满容量，再每 10 ms 放 1 个；漏桶从头到尾每 10 ms 放 1 个，但有的请求要排 500 ms。
  • CGuava 新建的限流器余额是 0，不是满的；空闲 1.5 秒后攒满 1 秒的量（100）再加上当下这 1 个。acquire(50) 立刻放行，紧跟着的请求替它等了 0.5 秒：Guava 是“先用后付”。

到这里已经能交差了：网关上配一个 Gateway 的令牌桶，或者在服务里用 Sentinel 的 QPS 规则，限流值来自压测。已知还没处理的细节：多台机器怎么分、容量设多大、Redis 挂了怎么办、被拒的人立刻重试，都在⑥。

⑥细节

第一圈 · 不知道就会出事

1每台各限 1 万，4 台网关一共放了 4 万← ④ 状态放在哪
现象
压测时 1 台网关，限流正好；上线 4 台，券服务被打满。扩容、缩容、某台重启后，总量还会跟着变。
根源
单机限流的状态在每台进程里，互相不知道。
做法
总量限流用集中式（Redis）或集群令牌服务；坚持单机就按“总量 ÷ 台数”配，并在扩缩容时一起改。
2自己写的计数器，交界处放进 2 倍← ④ 固定窗口
现象
⑤ A：0.2 秒里放了 200 个，限流值是 100/秒。
根源
窗口一换计数清零，它不记得上一秒末尾刚放过多少。
做法
用滑动窗口（格切细一点）或令牌桶；用现成组件，别手写。
3桶容量设太大，开抢那一下直接打穿← ④ 令牌桶
现象
容量随手填成 10 万，开抢第一秒全部放行，限流形同虚设。
根源
最大突发 = 容量。连续补的桶第一秒还要再加上 rate（⑤ B：299 = 200 + 99）。
做法
容量按“下游能扛的短时峰值”定，不超过压测容量；Gateway 按整秒补，第一秒就是容量本身。
4限流用的 Redis 挂了，网关全部放行按源码← ④ 集中式
现象
Redis 抖一下，限流瞬间失效，流量全进了券服务。
根源
Gateway 的 RedisRateLimiter 调脚本出错时返回“允许”（源码注释：不想让 Redis 成为放行流量的硬依赖）。
做法
给这类日志配告警；服务内再加一层单机限流兜底，Redis 失效时至少还有“单机值 × 台数”这道闸。
5被拒的请求立刻重试，限流变成放大器← ② 排队
现象
8 万个 429，App 自动重试 3 次，网关每秒要处理的请求变成 30 万，网关自己先扛不住。
根源
拒绝只是把请求退回给调用方，调用方不退避，就会马上再来。
做法
回 429 时带 Retry-After；客户端按它退避、加随机抖动；对“已抢完”这种结果，直接告诉用户别再点。
6Guava 新建时是空的，还“先用后付”⑤ C← ④ 懒计算
现象
服务刚启动，tryAcquire 300 次只成功 1 次；一个 acquire(50) 让后面的请求多等 0.5 秒。
根源
实现上的选择：SmoothBursty 初始余额为 0；一次大请求先放行，欠下的时间记到下一个请求头上。
做法
刚启动要放行突发的场景别依赖 Guava 的攒量；单次申请多个令牌时，记得后面的人要替它等。

第二圈 · 团队里怎么配

  • 限流值从压测来容量 × 余量（全景是 3.2 万只放 1 万～2 万），写进配置中心，能在线改。防的是拍脑袋的数。
  • 分层限入口按用户、按 IP（防刷）和按接口总量；服务内按接口；调用下游按下游给的配额。防的是一层漏了全盘皆输。
  • 限流 key 选对按用户 ID 而不是 IP：公司、学校出口 NAT 后几千人共用一个 IP，按 IP 限会误伤。防的是误杀。
  • 拒绝要便宜、要说清429 + Retry-After，不查库、不打日志全文。防的是“拒绝”本身成为负担。
  • 盯被拒比例被拒比例突然变高，要么是流量变了，要么是限流值配错了，两种都要有人看。

第三圈 · 深处

  • Sentinel 的滑动窗口LeapArray 用环形数组存格子，默认 1000 ms 切 2 格（SampleCountProperty.SAMPLE_COUNT = 2）。按 ⑤ A2 的推法，2 格时边界上最多能放进接近 2 倍；要更准可以调细，代价是每格都要统计。
  • 预热（Warm Up）Guava 的 SmoothWarmingUp 和 Sentinel 的 Warm Up 都让冷系统从较低速率起步，在预热期内爬到设定值，给 JIT、连接池、本地缓存留时间。抢券这种“开抢前系统是冷的”场景值得开。
  • 漏桶的两种含义“漏桶当计量器”（满了就拒，不排队）在数学上和令牌桶等价；“漏桶当队列”（排队匀速放）才是 ⑤ 里那个。Nginx limit_req 带 burst 不带 nodelay 时排队，带 nodelay 时更像令牌桶；默认拒绝码是 503，不是 429。
  • Redis 限流 key 也是热 key全景里 10 万个请求打同一个 key，每个都要执行一次 Lua。量再大时，可以把总量拆成几个子 key 随机挑，或者各台网关先从 Redis 批量领一批令牌再在本地发。

实验台：换流量、换参数，先猜再看

“开抢”流量：每秒来 1000 个，持续 3 秒。限流 100/秒，令牌桶容量 200（连续补）。第一秒令牌桶放行多少个？

每一行是 0～3 秒，每根柱子是 100 ms 里放行的个数（漏桶按“放行时刻”计）。格数为 1 时滑动窗口就退化成固定窗口。模拟逻辑和 ⑤ 的 Java 代码同一套算法，在 node 里对过 ⑤ 的数字。

自测

1. 用一句话说出这一页的精华

限流算法的区别在于怎么数“刚才放了多少”：固定窗口在交界处会放进 2 倍，滑动窗口靠切细格子逼近“任意一秒”，令牌桶用可攒的余额允许“容量”大小的突发、只限长期平均，漏桶排队匀速放出、不许突发但要等；入口多用令牌桶，状态放在哪决定它是单机的还是全局的。

2. 不限流、“尽力处理”，疼在哪？

超出容量的请求在线程池和连接池里排队，响应时间越拉越长，超时后客户端重试，流量更大，最后拖垮同一服务里的其他接口。超出容量的请求早晚要被拒绝，在入口拒掉最便宜。

3. 坑 3（容量太大打穿）的根源是 ④ 的哪一条？

令牌桶允许一次用掉攒下的余额，最大突发等于容量；开抢前系统空闲，桶是满的。连续补的实现第一秒还要再加上这一秒补的量。

4. 预测：全景里把网关的令牌桶换成漏桶排队（每秒 1 万，最长排 500 ms），抢券用户会看到什么？

第一秒只放 1 万（不再是 2 万），前 1 万之后的请求开始排队，排得到的最多等 0.5 秒才进券服务，排不到的被拒。券在开抢后约 0.1 秒就被前 1000 个请求抢完，后面排队的请求等了半天，结果还是“已抢完”。体验变差，券服务的压力变平滑，但它本来就扛得住 2 万。

5. 预测：网关从 4 台扩到 8 台，Gateway 的 RedisRateLimiter 总量限流值要改吗？如果用的是 Sentinel 单机 QPS 规则呢？

Redis 的不用改：8 台共享同一个 key，总量仍是配置的那个数。Sentinel 单机规则要改：每台限 2500 时，4 台总量 1 万，8 台就变成 2 万，要改成 1250，或者换成集群流控。

6. 放回全景：第 5 站前后各发生了什么？如果限流在开抢时失效（比如限流用的 Redis 挂了），整条链路会怎样？

前面是第 3、4 站（App 置灰、随机延迟，CDN 接住页面），后面是第 6 站券服务。限流失效时 10 万个请求全进券服务，超过 3.2 万的容量，线程池排队，响应时间涨到秒级；售罄标记能让券抢完以后的请求快速返回，但开抢头 0.4 秒的那一波仍会把券服务打满，App 超时重试进一步放大。所以服务内部还要有一层单机限流兜底（坑 4）。

档位：标准。本机跑过（2 核 ARM 虚拟机，JDK 17，Guava 33.5.0-jre）：⑤ 的 A、A2、B、C 四组各跑 1 次，页面上的放行数都来自这次输出；④ 的时间线和⑥ 的实验台用同一套算法写在页面里，在 node 里对过 ⑤ 的数字。

按源码：Spring Cloud Gateway request_rate_limiter.lua（main 分支）新桶的余额等于 capacity，now 由 Java 传空、取 Redis TIME 的秒数，按“过去的秒数 × rate”补；RedisRateLimiter 调脚本出错时返回允许。Sentinel SampleCountProperty.SAMPLE_COUNT = 2，统计窗口默认 1000 ms。按文档：Gateway 拿不到令牌回 HTTP 429；Nginx limit_req_status 默认 503；Guava RateLimiter.create(permitsPerSecond) 空闲时最多攒 1 秒的许可。
