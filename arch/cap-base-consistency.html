3 台 TC 挂了 2 台，下单直接报错：CAP、BASE 与一致性模型

网络断开（分区）不是你能选的，它一定会发生。CAP 要你选的只是断开的那一刻：联系不上多数派的节点，是拒绝回答（选 C），还是拿手上可能过期的数据先答（选 A）。没断开时也在取舍：多等一次复制，换来读到最新（PACELC）。选了 A，就要配上 BASE：中间状态有名字、有期限、有人收尾，“最终一致”才不是一句空话。一致性模型是量“读到的有多新”的尺子：线性一致 → 顺序 → 因果 → 读己之写 → 最终一致，越往下越便宜，分区时越能继续服务，也越容易读到旧数据。

全景：一次下单跨三个库 · 第 3、7、11 站地图：J09 · CAP、BASE 与一致性模型

这一页的位置J09 的第一个下钻知识点，给后面几页发词汇。分布式事务、幂等、超时、Raft 那几页都会用到这里的词：“第 ④⑤⑥ 站那几十毫秒里三个库不一样，算不算错”“TC 为什么宁可报错”“对账看到对不上，是 bug 还是还没到”。

①要解决的问题：订单 9527 路上的三个“这算不算错”

在全景第 3、7、11 站，这一步要解决的是同一件事：几份数据暂时对不上的时候，系统该怎么表现，什么时候算出了错。先看全景里三处真实的“对不上”。

要一个词：软状态第 ④⑤⑥ 站

中间态是设计出来的，不是半截数据。要说清它对谁可见、最多挂多久、谁来收尾。

要一个判断：分区时选 C第 3、7 站

TC 记的是“这单提交还是回滚”的决议。两台各拍各的板，比开不了事务糟糕得多。

要一把尺子：最终一致第 11 站

从库“最终”会追上，但没说多久。对账要知道自己读的那份数据保证到哪一级。

②不用它会怎样：要么全锁死，要么两个决议

没有这套词，团队讨论“一致性”时常落进两个极端。两种做法都能上线，也都会在网络出问题的那天出事。

极端一：任何时刻都要一致XA 两阶段，三个库一起锁到最后

  • 任何一个库、任何一段网络慢了，整单都在等，锁住的行别人也用不了。
  • 协调者在 prepare 之后挂了，参与者只能锁着等它回来。

极端二：谁活着谁拍板两台 TC 互为主备，断网就各自当主

  • “它联系不上我”和“它挂了”在网络上看起来一模一样。
  • 同一个全局事务出现两个结局，Confirm 和 Cancel 都不能再撤回。

缺的那一块：先承认网络会断，再按数据分别决定“断开时拒绝还是先答”，以及“先答的话，中间状态怎么收尾”。这就是 CAP 和 BASE 的精华。

!不懂精华时的典型误用
一种
“我们用了 Seata 和 Raft，所以整个下单是强一致的。”TC 的决议是强一致的；三个库之间在 ④⑤⑥ 站照样有几十毫秒到 60 秒对不上，只是被设计成用户看不到。
另一种
“我们是 AP 的，最终一致就行。”结果中间状态没有超时、没人对账，那张券就一直 LOCKED。

③几种流派：四个说法，各回答一个问题

CAP、PACELC、BASE、一致性模型常被混着说，其实各管一件事。分清它们回答的问题，就知道什么时候该拿出哪一个。

说法回答什么问题什么时候拿出来局限
CAP
Brewer 2000 猜想，Gilbert、Lynch 2002 证明		网络分区时，“读到最新”（C）和“每个活着的节点都回答”（A）能不能同时做到。答案：不能。设计“断网那一刻怎么办”：TC、注册中心、主从切换只管分区那一刻；C 和 A 的定义都很严格，现实系统多数两样都不完全满足
PACELC
Abadi 2012		分区时选 A 还是 C；不分区时（Else），选低延迟（L）还是一致（C）解释“平时为什么慢”：多等一次复制、读主还是读从仍然是粗分类，说不出具体读到什么
BASE
Brewer 等人 90 年代末提出，Pritchett 2008 年展开		拆成多个库以后，怎样在不全局加锁的前提下把业务做对设计业务流程：冻结、预留、补偿、对账是做法，不是保证；“最终”多久要自己定
一致性模型
线性、顺序、因果、会话、最终		一次读最多能“旧”到什么程度，多个人看到的顺序是否相同落到具体接口：这个读要读主还是可以读从名字多，要配一张谱系图

本页学：四个都讲，主线是两件事。一是 CAP 那一刻的二选一，加上 PACELC 的平时取舍；二是一致性模型这把尺子，加上选了 A 以后 BASE 怎么收尾。

④核心取舍：断开时拒绝还是先答，平时等不等复制

先知道这些
  • 副本：同一份数据存在几台机器上，靠复制（发日志、发变更）保持一样。MySQL 主从、Kafka 分区副本、Seata TC 集群都是。
  • 网络分区：几台机器之间的消息到不了，但每台自己都还活着。交换机故障、跨机房链路断、一次很长的 GC 停顿，从对端看都像分区。
  • 多数派：N 台里超过一半，3 台要 2 台，5 台要 3 台。为什么偏偏是一半，下面机制 3 讲。
  • 复制延迟：主库提交了，从库还没应用。见付完款跳回订单页，还是待付款。

机制 1：分区那一刻，只剩两个选择

C：一致性（线性一致）

所有读写看起来像只有一份数据：写完成以后，任何人再读都读到它。

A：可用性

每个没宕机的节点收到请求，都必须给出正常回答。回一个“稍后重试”不算。

P：分区容忍

节点之间可以丢任意多的消息，系统照样要按规则工作。分布式系统没得选，P 必须要。

PACELC：平时也在选

不分区时，要读到最新就得等复制、问多数派（多花延迟 L），不等就可能旧。全景第 3 站每次开事务多一次 tc-1 → tc-2 的往返，就是这笔延迟。

所以“CAP 三选二”的说法容易误导：P 不是选项，分区一来只剩 C 和 A 二选一；而网络正常时，C 和 A 可以都要。Brewer 本人在 2012 年的回顾里也是这么纠正的。

机制 2：一致性模型，一把量“读到的有多新”的尺子

C 和 A 之间不是只有两档。从“像单机一样”到“最后会一样”，中间有好几级，越往下越便宜，分区时也越能继续服务。

  • 粘着可用（sticky available）：分区时，只要客户端一直连着同一个节点，就还能用；换了节点就可能做不到。读己之写就是这样：我刚写在 A 上，下次还去 A 读就一定读得到。
  • CAP 里的 C 就是第 ① 级。“选 A”不等于什么都不保证，可以落在 ③④⑤ 任何一级，看业务要哪一级。
  • 这一页只讲单个对象（一行、一个键）怎么读。多个对象一起改的“隔离级别”（可串行化、快照隔离），是另一条轴，⑥ 第三圈说两者的区别。

机制 3：多数派，为什么 3 台挂 2 台就停

全景第 3 站：3 个 TC 挂了 2 个，剩下的 tc-3 凑不齐 2 票，开不了新事务。这不是故障处理没做好，而是设计上宁可停，也不让一台孤立的节点自己拍板。W+R>N 保证的是“读得到最近一次完成的写”；要做成线性一致的“先读后改”，还要一个 leader 给并发的写排好先后，这是下一页 Raft 的事（⑥ 第三圈细说）。

机制 4：选了 A 以后，BASE 怎么收尾

BA · 基本可用

出问题时降级，而不是整体停下：TC 挂了开不了新单，已经在路上的单照样由恢复任务推完。

S · 软状态

允许中间态存在：CREATING、冻结、LOCKED。前提是它有名字，用户看不到或看得懂，而不是“扣了一半”。

E · 最终一致

中间态有期限（60 秒超时）、有人收尾（Confirm 重试、Cancel、对账）。少了任何一个，“最终”就可能是永远。

为什么这样设计：TC 选 C，商品详情选 A

TC 选 CRaft 多数派，Seata 2.x 的 raft 模式

TC 选 A被放弃：每台都能自己拍板

决定胜负的约束：决议错了是资金事故，补不回来；开不了事务只是这一单失败，用户可以重试。错的代价远大于停的代价，就选 C。商品详情页反过来：价格晚几秒更新没人在意，打不开才是事故，所以缓存、从库都选 A。同一个系统里，不同的数据选不同的位置。

最少的“语法”：这些开关就是在 C 和 A 之间拧

常见中间件里，决定 C 还是 A 的配置默认值和版本细节放到 ⑥
# Seata TC：决议写进 Raft 多数派（偏 C）
seata.store.mode=raft
seata.server.raft.server-addr=tc-1:9091,tc-2:9091,tc-3:9091

# Kafka：在线副本少于 2 个就拒绝写（偏 C）；不让落后的副本当 leader
acks=all
min.insync.replicas=2
unclean.leader.election.enable=false

# MySQL 半同步：等 1 个从库收到 binlog，等不到 10 秒就退回异步（先 C，后 A）

rpl_semi_sync_source_timeout=10000

# Nacos：临时实例走 AP，持久实例走 CP
spring.cloud.nacos.discovery.ephemeral=true

# 读要不要最新：etcd 默认线性一致读；ZooKeeper 先 sync 再读
etcdctl get /orders/9527 --consistency=s   # s：本地读，可能旧
zk.sync("/orders/9527", cb, null);

⑤套进场景：券 MINUS20 存 3 份，拧 W 和 R 看谁出事

交易靶场的券服务。假设券状态不放在一个 MySQL 主库上，而是存在 3 个副本里（像 Cassandra、Dynamo 那样按 W/R 读写）。1000 张券，每张都有两单来抢（同一个用户两台手机，或者两张单），抢完马上读一次“我锁到了吗”。网络时不时把一台隔开，副本之间异步复制有几片时间的延迟。分别用 5 种 W/R 组合各跑一遍。

抢券：读 R 份、写 W 份CouponQuorum.java 节选（略简化），JDK 8 写法；完整模拟约 150 行
// reach：从协调节点 c 此刻能联系上的副本（分区时被隔开的那台只能联系自己）
List<Integer> rc = reach(e.c, e.t);
if (rc.size() < r || rc.size() < w) { m.lockRejected++; continue; }       // 凑不齐：拒绝，选 C
if (readQuorum(rc.subList(0, r), k) != 0) { m.alreadyUsed++; continue; }   // 读到已被锁：券已用
int v = ++gv, ow = 2 * k + e.ord;
List<Integer> wset = rc.subList(0, w);
for (int n : wset) apply(n, k, ow, v);                                     // 同步写进 W 份
for (int n = 0; n < N; n++)
    if (!wset.contains(n)) q.add(new Msg(n, e.c, k, ow, v, e.t + lag()));  // 其余异步复制

// 分区恢复以后：把没送到的复制全补上，版本大的赢（LWW）
for (Msg x : q) apply(x.to, x.k, x.owner, x.ver);

  • W1R1 是纯 AP：2000 次抢券一次没拒，可 70 张券被两单都锁到。分区恢复后副本都一样了（最后一列 0），最终一致做到了，但那 70 单里有一单以为自己用了券，要补偿：取消订单，或者按原价补差。最终一致不等于业务正确。
  • W+R>N 的三行：双锁 0、读到旧值 0。代价是分区时被拒：W2R2 拒 53 次（只有被隔开的那台拒），W3R1 和 W1R3 要 3 台都在，拒 185 次。多数派是“够用的最小代价”。
  • W2R1 看着也像多数派，还是错了：W+R=3，没大于 N。写进的两台和读的那一台可能正好错开，284 次读到旧值。
  • 把分区调到 0%（-Dexec.args="0 5"）：W1R1 仍有 51 张双锁、539 次读旧。这是 PACELC 的 E：没断网，只因为不等复制，就已经在拿一致换延迟。

⑥反例和误用：挂着 CAP 的名字，没满足它的约束

第一圈

注意事项：说错一句话，就会设计错一个系统

1“我们的系统选的是 CA”← ④ 机制 1
现象
设计文档里写“不考虑分区”，主从之间断网时，两边都继续接写，事后数据对不上。
根源
只要数据在两台以上的机器上，分区就会发生，不是你选不选。CA 只在单机上成立。
做法
把“断网时这一边怎么办”写进设计：拒绝、只读，还是继续写并准备合并。
2“上了 ZooKeeper / etcd，读就一定是最新的”← ④ 尺子
现象
A 在 leader 上改了配置，B 连的 follower 还没同步，读到旧值。
根源
ZooKeeper 保证的是顺序一致：所有人看到同一个顺序，但可以落后；文档原话是另一个客户端“可能读到旧值”。etcd 默认是线性一致读，但改成 serializable 读就是本地读。
做法
ZooKeeper 读前先 sync()；etcd 别为了快随手改成 --consistency=s。
3“最终一致”没写多久、没人收尾← ④ BASE
现象
全景第 10 站没开 fence：Cancel 先到、什么都没改，迟到的 Try 把券锁上，再没人来解，MINUS20 永远 LOCKED。
根源
软状态少了期限和收尾人，“最终”就是永远。
做法
每个中间态配超时和负责的任务；对账任务按“LOCKED 超过 X 分钟”报警。
4读写分离以后，用户读不到自己刚写的← ④ 读己之写
现象
付完款跳回订单页，从库还没追上，显示“待付款”，用户又付了一次。见复制延迟那页。
根源
从库只给最终一致，而用户要的是读己之写。⑤ 里 W2R1 的 284 次就是这个。
做法
写后几秒内这个用户的读走主库；或者读带上版本号，从库没追到就回退到主库。不必把整个系统升到线性一致。
5两台互为主备、自动切换← ④ 多数派
现象
心跳线断了，两台都认为对方挂了，都当主：② 里的两个决议。
根源
2 台的多数派是 2，挂一台就没有多数派；不看多数派、只看心跳的切换，分区时必然脑裂。
做法
要自动切换，就用 3 台以上奇数个节点，或者加一个仲裁节点；2 台只能人工切换。
6对账读从库，误报一大片← ④ 最终一致
现象
全景第 11 站：订单刚 CANCELLED，从库上券还 LOCKED，报警。几秒后自己好了。
根源
对账读的数据本身只保证最终一致，“对不上”可能只是还没到。
做法
对账跳过最近几分钟的单；报警前回主库复查一次；或者看从库的延迟，超过阈值就暂停对账。
7以为开了半同步就不丢数据← ④ PACELC
现象
从库网络抖了十几秒，主库照常提交；这期间主库宕机切到从库，最近的事务没了。
根源
MySQL 8.4 的 rpl_semi_sync_source_timeout 默认 10000 毫秒，等不到从库确认就退回异步复制。也就是说，它先选 C，等满 10 秒后悄悄换成 A。
做法
监控半同步状态（是否退回了异步）；切主前比较位点；真要不丢，把决议放进多数派复制的系统。
第二圈

使用规范：每类数据写明要哪一级

数据（交易靶场）要哪一级怎么做到防的是什么
TC 里全局事务的状态线性一致Raft 多数派，3 或 5 台同一单两个结局
券、库存的扣减单行线性一致主库上的条件更新：WHERE status='UNUSED'、available >= 2两单抢到同一张券、超卖
用户刚下的那一单读己之写写后 N 秒内读主，或带版本号读付完款还显示待付款
订单列表、商品详情最终一致（秒级）从库、缓存，写明延迟上限并监控主库被读打满
报表、对账最终一致（分钟级）从库，跳过最近几分钟误报、拖慢主库
  • 每个“最终一致”都写上期限，比如“从库延迟 < 3 秒”，并且有监控。防：期限只存在于脑子里。
  • 每个软状态有超时和收尾的任务，有对账。防：坑 3 的“永远”。
  • 对外接口文档写清给的是哪一级，不承诺比实现更强的。防：调用方按线性一致去用一个从库接口。
  • 要自动切主的集群用奇数个节点，切主看多数派。防：坑 5 的脑裂。
第三圈

深处：几个常被说错的地方

“CP / AP”的标签太粗

CAP 的 C 是线性一致，A 是每个活节点都必须回答，两个定义都很严。MySQL 异步主从既不满足 C（从库会旧），也不满足 A（被隔开的从库不能写）。Kleppmann 2015 年的文章就建议别再给数据库贴 CP、AP 标签，直接说一致性模型和延迟。Redis 也是一例：文档明说 WAIT 不能把 Redis 变成强一致的存储，主从切换时已确认的写也可能丢。

线性一致 ≠ 可串行化

线性一致管单个对象：读要看到实时上最新的写。可串行化管多个对象的事务：结果等于某种串行执行，但不要求是实时顺序。两个都要叫严格可串行化。Seata 的全局事务两个都不保证：AT 模式文档写明默认全局隔离是读未提交；TCC 的隔离靠你自己的冻结字段。

W+R>N 不等于线性一致

⑤ 的请求是一个接一个处理的。真并发时，两个协调者可以同时读到 UNUSED、各自写进多数派，版本号一比较只剩一个，另一单的“成功”就丢了。要线性一致的“先读后改”，得有一个 leader 给写排好先后，并且换 leader 时不丢已确认的写：这是 Raft 那一页。

LWW 合并靠时钟

⑤ 恢复时“版本大的赢”，版本号是全局计数器，模拟里很干净。真实系统常用时间戳当版本：两台机器时钟差 200 毫秒，后写的反而被先写的盖掉，而且悄无声息。这是“时钟、超时与重试”那一页的事；另一条路是 CRDT，让合并不依赖先后。

自测

1. 用一句话说出这一页的精华

分区一定会发生，CAP 要你选的只是断开时拒绝（C）还是用可能过期的数据先答（A）；不断开时也在拿延迟换一致（PACELC）。选了 A 就要配上 BASE：软状态有名字、有期限、有人收尾。具体读到什么，用一致性模型那把尺子说清。

2. ② 里“两台 TC 互为主备、谁活着谁拍板”痛在哪？

分区时“对方挂了”和“联系不上对方”看起来一样，两台都当主，同一个全局事务一边提交、一边回滚。Confirm 和 Cancel 都撤不回，库存扣了券还在。

3. ⑥ 坑 5（两台主备脑裂）的根源是 ④ 的哪条？

机制 3 多数派：2 台的多数派是 2，挂一台（或断网）就没有任何一边有多数派。不看多数派的切换，分区时两边都会当主。3 台以上奇数个节点，最多一边凑得齐多数派。

4. 预测：⑤ 里把 W2R1 改成 W2R2，分区 30%，双锁和读被拒各会怎样？

双锁和读到旧值都变成 0（W+R=4>3，读写一定重叠）。代价是读也要两台：被隔开的那台连读都拒，读被拒从 0 变成 96 次。抢券被拒不变（170），因为写本来就要两台。

5. 预测：TC 从 3 台扩到 4 台，挂 2 台时还能下单吗？

不能。4 台的多数派是 3，挂 2 台只剩 2 台，凑不齐。4 台和 3 台一样只能挂 1 台，多出来的一台没有提高可用性，还让每次写多等一台。所以用 5 台。

6. 放回全景：第 3、7、11 站前后各发生了什么？这一页的东西坏了，整条链路会怎样？

第 3 站在发号之后、订单 Try 之前，TC 把“新事务”写进多数派才回 XID；第 7 站在三个 Try 之后、推 Confirm 之前，把 Committing 写进多数派；第 11 站不在单子的路上，每 10 分钟对一次三个库。如果 TC 不按多数派、谁活着谁拍板（选了 A），分区时同一单会在第 8 站收到 Confirm、第 10 站又收到 Cancel，库存和券对不上，第 11 站的对账只能报警、人工修。如果对账不知道自己读的是最终一致的从库，第 11 站会误报一大片。

档位：标准。本机跑过：CouponQuorum 是一个 3 副本 W/R 读写的模拟（不是真数据库），JDK 17 按 --release 8 编译，固定种子 42，页上实验台用同一套逻辑和同一个随机数，输出逐项一致。分区占比 10%、30% 是为了看清现象故意调高的，真实网络的分区少得多。
