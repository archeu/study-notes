tc-1 断网了，谁来接着拍板：Raft 选主与日志复制

三台 TC 要像一台那样记账。Raft 的做法是：先选出唯一的 leader，所有写入只走它；leader 把每条记录复制给其他节点，过半写下就算提交。整套算法的安全性都靠一个事实：任意两个多数派至少有一台重叠。所以同一任期不会有两个 leader（每台每任期只投一票），新 leader 一定带着全部已提交的记录（日志不够新的拿不到票）。时间只用来发现 leader 死了，谁对谁错从来不看时间。

全景：一次下单跨三个库 · 第 3、7 站地图：J09 · 共识：Raft 怎么选主、怎么复制日志

这一页的位置J09 第 5 个下钻知识点。前面几页一直默认 TC 是靠得住的：它记下“9527 要提交”，就会一直推 Confirm 直到成功。这一页回答 TC 凭什么靠得住：3 台机器怎么选出拍板的那一台，它挂了谁接手，接手的那台为什么不会忘掉已经拍过的板。

①要解决的问题：TC 记下的决议，挂一台也不能丢

在全景第 3、7 站，这一步要解决：订单服务问 TC“开一个全局事务”“9527 要提交”，TC 回了“好”，这条记录从此必须一直在。哪怕回完“好”的下一秒，那台 TC 的机器就烧了。

记得住

回过“好”的记录，挂掉少数几台（3 台挂 1 台）也不能丢。

说一样的话

每台按同样的顺序执行同样的记录，任何时候最多一台在拍板，不会出现两个“主”。

自己换人

拍板的那台挂了，剩下的自己选出新的，几秒内恢复写入，不用半夜叫人。

②朴素做法：主备复制，主挂了切备

Java 后端最熟悉的高可用就是 MySQL 主从：写主库，binlog 复制到从库，主库挂了把从库提上来。拿它来做 TC，有三种配法，每种都缺一块。

异步复制

主库写完就回“好”，再慢慢发给备库。

主库在发出去之前挂了：备库没有“9527 要提交”。新主以为 9527 还在 Begin，60 秒后回滚；可旧主已经推了一半 Confirm。决议丢了。

同步复制到所有备库

每个备库都写下才回“好”。

不丢了，但任何一台备库慢了或挂了，整个 TC 都写不进去。多一台机器，反而多一个停机的理由。

心跳断了就接管

备库收不到主库心跳，就自己升成主库。

网络断开时主库其实活着，只是两边互相看不见：两个主库同时拍板，一个说 9527 提交，一个说回滚。这叫脑裂。

缺的那一块：一条“谁说了算”的规则，它不依赖时间准不准、网络通不通，只看票数过没过半。过半写下才算数，过半同意才能当主；少数派那一边宁可停下，也不自己拍板。

做法
为了“高可用”把 TC 从 1 台加到 2 台，开 raft 模式。
结果
2 台的多数派是 2 台，挂任何一台都凑不够，整个集群停写。两台里任何一台出事都会停，比 1 台更容易停。要能挂 1 台，至少 3 台；要能挂 2 台，至少 5 台（④ 多数派）。

③几种思路：多数派共识，还是外部选主 + 复制

“几台机器对一串记录达成一致”叫共识（consensus）。业界有两大类做法：一类把选主和复制都交给多数派（Paxos、Raft、ZAB），一类让外部的协调者选主，数据面自己复制。

做法怎么选主怎么算写成功用在哪代价
Paxos / Multi-Paxos原始 Paxos 不需要固定 leader，谁都能提议；工程上的 Multi-Paxos 一般也选一个 leader 来提速每个日志位置单独做一轮多数派表决Google Chubby、Spanner 的 Paxos 组，微信 PhxPaxos论文只讲“对一个值达成一致”，变成日志要自己补很多细节，难懂，更难写对
Raft强 leader；随机超时发起选举，过半票当选leader 复制给 follower，过半写下即提交etcd、Consul、TiKV、Kafka KRaft（拉模式变体）、SOFAJRaft（Seata TC 的 raft 模式、Nacos CP 模式）、RocketMQ DLedger所有写都过 leader；leader 挂了要停 1～2 秒（⑤ 实测）
ZAB选 epoch、zxid 最大的节点提议，过半 ack，再广播提交ZooKeeper和 Raft 很像，但只有 ZooKeeper 自己在用；分布式锁那一页会再见到它
外部选主 + 主备复制交给别人：Redis Sentinel 由多数哨兵投票；Kafka 分区由 controller 指定Redis：异步复制，切换可能丢写；Kafka：ISR 里全部确认才算提交，不看过半Redis 主从、Kafka 分区副本（ISR、ELR）选主可靠了，数据面仍要自己权衡“丢”还是“等”

选择规则：要“自己选主、确认过的写一条不丢、挂少数几台照样能写”，就用多数派共识。Paxos、Raft、ZAB 能做到的事一样，按生态选：Java 里是 SOFAJRaft，Go 里是 etcd/raft。数据量大、吞吐要求高的数据面，常见做法是把元数据交给 Raft，数据本身走 ISR 一类的复制（Kafka 用 KRaft 管元数据就是这样）。

本页学 Raft：它的论文就叫《寻找一种可理解的共识算法》，设计目标是好懂；Seata TC 的 raft 模式用的 SOFAJRaft 是它的 Java 实现。Paxos 和 ZAB 放进“下一圈”。

④关键洞察：两个多数派一定重叠

先知道这些
  • 状态机复制：每台 TC 内存里都有同一张“全局会话表”。只要大家按同样的顺序执行同样的命令，表就一样。所以问题变成：让 3 台的日志一样。像 MySQL 从库按顺序重放主库的 binlog，区别在于这里谁当主、什么时候算写成功，由投票决定。
  • 多数派（quorum）：N 台里的 ⌊N/2⌋+1 台。3 台是 2，5 台是 3。
  • 超时只是猜测：等不到心跳，只说明“我没听到”，不说明“它死了”。见时钟、超时与重试。Raft 允许猜错，猜错了也不会出错，只是多一次选举。
  • CAP 里选 C：凑不够多数派的那一边宁可不可用。见 CAP、BASE 与一致性模型。

后面每一条规则都在用这个重叠：当选要过半票，提交要过半写下。于是任何“新多数派”里，至少有一台见过“旧多数派”做过的事。

机制 2 · 任期和选举：每台每个任期只投一票

为什么同一任期不会有两个 leader：每台节点把“任期 N 投给了谁”先写盘，再回复，一个任期只投一次；当选要过半票；两个过半票的集合必然重叠，重叠的那台不可能同一任期投给两个人。

为什么超时要随机：大家同时超时，就会同时参选、各投自己、1:1:1 平票，下一轮又同时超时。随机错开后，通常第一个醒来的人在别人醒来之前就拿够了票。SOFAJRaft 的选举超时是 electionTimeoutMs 加 0～maxElectionDelayMs 的随机数，默认是 [1000, 2000) ms；心跳间隔是选举超时的 1/10，即 100 ms。

机制 3 · 日志复制：一条记录怎么从“写下”变成“提交”

一致性检查是复制的关键：AppendEntries 里带着“新条目前一条的 index 和任期”。follower 对不上就拒绝，leader 把这台的 nextIndex 往前退一格再发，直到找到两边一致的位置，再把 follower 那之后的内容整段覆盖。由此得到一个不变式：两份日志只要某个 index 上的任期相同，那么从开头到这里全部相同（论文叫 Log Matching）。

机制 4 · 投票限制：日志不够新的，拿不到票

还剩一个坑：新 leader 手里有旧任期留下的、还没确认提交的记录，它不能靠“数一数有几台有”来提交它们（⑥ 第三圈讲为什么）。Raft 的规则是只按副本数提交本任期的记录，旧记录跟着一起提交。所以新 leader 上任先写一条空记录 no-op，它一提交，前面的全部跟着提交。etcd、MiniRaft 都这么做。

为什么这样设计

被放弃的：固定超时，或者按编号排队

按编号排队（编号小的先上）也不行：编号最小的那台日志可能最旧，拿不到票，大家还是要等它失败再轮到下一个。

Raft 选的：随机超时

最简单的打破对称的办法。前提是网络往返（这里 5 ms）远小于随机区间（1000 ms）。

被放弃的：谁都能当选，当选后再去补齐

Paxos 一类做法允许日志旧的节点当选，再从别人那里把缺的补回来。正确，但新 leader 上任要先跑一轮“收集”，日志要能双向流动，实现复杂。

Raft 选的：日志够新才能当选，日志只从 leader 流向 follower

投票时多比较一次 (lastTerm, lastIndex)，换来“新 leader 一定已经有全部已提交记录”。之后复制只有一个方向：follower 和 leader 不一致，就以 leader 为准覆盖。

决定胜负的约束：共识算法要在网络会断、机器会停顿、时钟不可信的环境里永不出错，同时还要让人能读懂、能写对。Raft 用“强 leader + 过半 + 任期号”把正确性只押在票数上，时间只影响多久恢复。代价是所有写都过 leader，leader 挂了要停一会儿。

// ① 投票：任期对、这任期没投过别人、你的日志不比我旧
boolean upToDate = r.lastTerm > termAt(lastIndex())
        || (r.lastTerm == termAt(lastIndex()) && r.lastIndex >= lastIndex());
boolean grant = r.term == term && (votedFor == null || votedFor.equals(r.from)) && upToDate;
if (grant) { votedFor = r.from; resetElectionTimer(); }      // 真实现里 term、votedFor 要先落盘

// ② 复制：前一条对不上就拒绝；对上了，冲突的部分删掉再追加
if (r.prevIndex > lastIndex() || termAt(r.prevIndex) != r.prevTerm) { reply(false); return; }
int i = r.prevIndex;
for (Entry e : r.entries) {
    i++;
    if (i <= lastIndex() && termAt(i) != e.term) log.subList(i - 1, log.size()).clear();
    if (i > lastIndex()) log.add(e);
}
commitIndex = Math.max(commitIndex, Math.min(r.leaderCommit, r.prevIndex + r.entries.size()));

// ③ 提交：只按副本数提交“本任期”的记录，旧的跟着一起提交
for (int n = lastIndex(); n > commitIndex; n--) {
    if (termAt(n) != term) break;
    int cnt = 1;                                              // leader 自己
    for (int m : matchIndex.values()) if (m >= n) cnt++;
    if (cnt >= majority()) { commitIndex = n; break; }
}

读出来的结论（本机 2 核 ARM，JDK 17.0.21，跑了 2 次，第二次的数字在括号里）
  • 一条记录过半提交（含 fsync）p50 约 7 ms，p99 约 25 ms（6.67 / 23.28 ms）。这是 TC 每开一个全局事务、每改一次状态都要付的钱。
  • kill -9 leader：1.1～1.6 秒选出新 leader（1.08～2.10 秒），这段时间写不进。和 [1000, 2000) ms 的随机选举超时对得上。
  • SIGTERM 优雅停机：90 ms 左右就换好了。JRaft 停机时 leader 会主动叫醒一个 follower 立刻参选，不用等超时。
  • 杀掉两个 follower：leader 约 0.9～1 秒后自己退位（910 ms），之后一条也写不进。和 900 ms 的 leader 租约对得上。
  • 3 个进程的任期在 6 轮换主后到了 7：任期只增不减，每次换主加 1（这里没有出现平票）。
到这里已经能交差了：能说清 3 台 TC 怎么选主、一条“要提交”的决议怎么变成“提交”、leader 挂了谁接手、为什么不会丢已提交的记录；也知道 Seata raft 模式那几行配置是什么意思、挂一次 leader 要付 1～2 秒的代价。
已知还没处理的细节：节点数和机房怎么摆（⑥ 坑 1），超时能不能调小（坑 2），客户端超时怎么办（坑 4），滚动重启（坑 6），为什么新 leader 要先写 no-op（第三圈），读能不能直接读 leader（第三圈）。

⑥边界和变体：注意事项、规范、深处

第一圈 · 注意事项

1两台、四台，或者三台放在两个机房← ④ 多数派
现象
部署了“高可用”的 TC，挂一台（或一个机房断网）整个集群停写。
根源
2 台的多数派是 2，4 台是 3，都只比 1 台、3 台多一个出故障的机会。3 台放两个机房，放了 2 台的那个机房一断，剩下的 1 台凑不够多数派。
做法
3 台或 5 台，分在 3 个可用区。
2嫌换主慢，把选举超时调到 100 ms← ④ 超时只是猜测
现象
大促时 leader 来回换，每次换都有一段写不进，全局事务开不了、决议写不下。
根源
一次 300 ms 的 Full GC 或磁盘卡顿，就让 follower 以为 leader 死了。Raft 不会因此出错，但会一直选举。
做法
选举超时要远大于网络往返，也要大于 leader 的最长停顿（GC、fsync）。默认 1000 ms 先别动，先看 GC 日志。
3以为 leader 说的就是最新的← ④ 任期
现象
被隔离的旧 leader 在退位前还会回答读请求，读到的是已经过时的状态。
根源
旧 leader 要过 900 ms 租约才发现自己凑不够多数派，这段时间它还以为自己是 leader。
做法
需要强一致的读走 ReadIndex（JRaft 默认 ReadOnlySafe），见第三圈。Seata 的 follower 对写请求直接拒绝（NotRaftLeader）。
4客户端超时了，就当没写进去← ④ 复制
现象
换主那 1～2 秒里，第 7 站的 commit 超时了，订单服务报“下单失败”，其实 9527 已经是 Committing，后面照样推了 Confirm。
根源
记录可能已经过半写下、只是回复丢了；新 leader 一定有它。超时只说明“不知道”。
做法
超时后去查（按 XID 查全局事务状态），或带幂等键重试。见时钟、超时与重试。
5被隔离的节点一回来，就把 leader 搅下台← ④ 看到更大任期就退位
现象
一台机器网络抖了几秒，回来以后整个集群又停了 1 秒左右。
根源
它在那边一次次超时参选，任期涨到 5；回来后 leader 看到更大的任期，只能退位重选。MiniRaft rejoin：关 PreVote 时 tc-3 任期涨到 5，回来后约 1080 ms 没有 leader；开 PreVote，任期不涨，0 ms。
做法
开 PreVote：先问“如果我参选你会投我吗”，过半同意才真涨任期。JRaft 一直开着；etcd 3.5.0 起默认开。
6滚动发布时 kill -9，或者先重启 leader← ④ 选举超时
现象
发一次版，TC 卡三次，每次 1～2 秒。
根源
⑤ 实测：kill -9 leader 要等选举超时，1.1～2.1 秒；SIGTERM 让 JRaft 正常关闭，leader 会叫醒一个 follower 立刻参选，约 90 ms。
做法
用 SIGTERM，给足优雅停机时间；先重启 follower，最后处理 leader。
7Raft 日志和别的东西挤一块盘← ④ 写下 = 落盘
现象
开全局事务的 p99 从几十毫秒涨到几百，偶尔还换主。
根源
每条记录要 leader 和至少一个 follower 都 fsync 才算写下（Seata sync 默认 true）。盘被应用日志、备份打满，fsync 变慢，提交就慢；慢到超过选举超时，心跳也会断。
做法
Raft 数据目录放独立的 SSD；监控 fsync 耗时、提交耗时、换主次数和任期增长。

第二圈 · 使用规范

  • 3 台或 5 台，分在 3 个可用区。防的是：偶数台和“两机房三节点”的假高可用（坑 1）。
  • 选举超时保持默认，先量 GC 和 fsync 再调。防的是：误判导致频繁换主（坑 2）。
  • 发布用优雅停机，先 follower 后 leader。防的是：每台都触发一次 1～2 秒的停写（坑 6）。
  • 客户端把“不是 leader”和“超时”都当成“不知道”：刷新 leader 地址、查询或幂等重试。防的是：把已提交当失败（坑 4）。
  • 只往 Raft 里放小而关键的东西：会话、决议、元数据。Seata 复制的是会话的增删改和锁的释放，业务数据还在各自的库里。防的是：拿共识日志当数据库，写入量把 leader 压垮。
  • 盯四个指标：换主次数、任期增长速度、提交耗时 p99、follower 落后的条数。任期涨得快而 leader 没变，多半有节点在反复超时。

第三圈 · 深处

1. 为什么不能靠“数一数”提交旧任期的记录（论文图 8）

2. 读：直接读 leader 不够，ReadIndex 和租约读

写要过半，读如果直接读 leader 的内存，就可能读到第一圈坑 3 说的旧数据。两种办法：

  • ReadIndex：leader 记下当前的 commitIndex，发一轮心跳确认自己仍被多数派承认，等状态机执行到这个位置再读。多一次网络往返，不依赖时钟。JRaft 默认 ReadOnlySafe 就是它。
  • 租约读（lease read）：leader 在租约内（JRaft 是选举超时的 90%，900 ms）认为没人能选出新 leader，直接读。省一次往返，但依赖各台时钟走得一样快：时钟一快一慢，两个“leader”就可能同时读写。JRaft 里叫 ReadOnlyLeaseBased。又回到了时钟那一页。

4. Seata 在 Raft 上放了什么，客户端怎么找到 leader

TC 的状态机是 RaftStateMachine，日志里的每条记录是一种 RaftSyncMsgType，一共 12 种：全局会话的新增、删除、改状态；分支会话的新增、删除、改状态；全局锁和分支锁的释放；集群元数据刷新；事务分组映射的增删改。follower 收到已提交的记录，按类型执行，把自己的会话表改成和 leader 一样。

客户端配 registry.type = raft，从 TC 的 /metadata/v1/cluster 取集群元数据，再用 /metadata/v1/watch 长轮询等变化（请求里带着各分组的任期），只把请求发给 leader。请求落到 follower 上，follower 直接拒绝，抛 NotRaftLeader（“The current TC is not a leader node”），不帮忙转发。

自测

1. 用一句话说出这一页的精华

先过半票选出唯一的 leader，写入只走 leader、过半写下才算提交；两个多数派必然重叠，所以同一任期最多一个 leader、新 leader 一定有全部已提交记录。时间只用来发现 leader 死了，不决定对错。

2. 主备复制当 TC 用，三种配法分别缺什么？

异步复制：主库挂在复制之前，决议丢。同步复制到全部备库：任何一台慢或挂就全停。心跳断了就接管：网络断开时出现两个主，各拍各的板（脑裂）。缺的都是同一块：用“过半”来决定谁说了算。

3. ⑥ 坑 1（两台 TC、两机房三台）根源是 ④ 的哪条？

机制 1 多数派：N 台的多数派是 ⌊N/2⌋+1。2 台要 2 台都在；两机房三台，大机房一断只剩 1 台，凑不够 2。容错能力只和“少数派最多几台”有关，偶数台白多一台。

4. 预测：5 台 TC，2 台在机房 A（含 leader），3 台在机房 B。A、B 之间断网 10 秒，两边各会怎样？

B 有 3 台，是多数派：1～2 秒后选出新 leader（任期 +1），可以继续开事务、写决议。A 的旧 leader 只能联系上 2 台，900 ms 租约后自己退位；在那之前它收到的写入都凑不够 3 台，不会提交，客户端超时。网络恢复后，A 的两台看到更大的任期，未提交的记录被 B 的 leader 覆盖。

从机制 1（多数派重叠）、机制 2（看到更大任期就退位）、机制 3（覆盖不一致的部分）推出。

5. 预测：投票时如果不比较日志新旧，⑤ 第 9 步会出什么事？

假如第 6 步 tc-3 恰好没收到 index 3（丢包），断网后又是它先超时。不比较日志的话 tc-2 也会投它，它当选后用自己的日志覆盖 tc-2：index 3 的 COMMITTING 9527 当时在 tc-1、tc-2 上，正好过半、已经提交，现在没了。TC 新 leader 认为 9527 还在 Begin，60 秒后回滚；可旧 leader 可能已经推过 Confirm：一半提交一半回滚。

从机制 4 推出：投票限制保证赢家有全部已提交记录。

6. 预测：把 election-timeout-ms 调到 100，TC 的 JVM 偶尔有一次 300 ms 的 Full GC。会看到什么？

每次 GC 停顿，follower 都以为 leader 死了，发起选举，任期 +1；leader 醒来看到更大任期就退位。每次换主都有一段写不进，开全局事务和写决议失败或超时。数据不会错，可用性变差。

从机制 2 推出：超时只是猜测，猜错不会出错，但会白白选举。

7. 放回全景：第 3 站前后各发生了什么？如果 3 台 TC 挂了 2 台，整条链路会怎样？

之前：第 1 站幂等键挡掉重复点击、第 2 站发出订单号 9527；之后：第 4、5、6 站带着 XID 做三个分支的 Try。挂 2 台时剩下 1 台凑不够多数派：新的 @GlobalTransactional 拿不到 XID，下单直接报错；已经写成 Committing 的事务，等多数派恢复后由新 leader 继续推 Confirm；还在 Begin 的，恢复后按超时回滚。这一段时间里各分支冻结的库存和锁住的券都卡着，直到 TC 恢复。
