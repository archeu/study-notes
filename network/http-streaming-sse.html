HTTP 流式与 SSE：一个响应怎么一块一块地推

一个 HTTP 响应不必等内容全部生成完才发：服务端先发响应头、不写总长度（HTTP/1.1 用 chunked 分块传输），之后每 flush 一次，就有一块数据上了网络。SSE 只是在这条长响应上约定的文本格式：几行 event:、data:，一个空行结束一个事件。模型的流式输出就是它。实测同样 8 个事件，服务端每个都 flush 时每 400 毫秒到一个；忘了 flush，客户端干等 2.4 秒后一次收齐。

①为什么需要：边生成边发，而不是生成完再发

补给站 03 第 7 站：模型一圈写一个 token（站 02），写 3000 个要几十秒。普通的 HTTP 响应要先知道总长度（Content-Length），等于要等全部写完才能发出第一个字节。值班页面要的是“字一个个冒出来”，HTTP 层就得支持“不知道总长度，也先发”。

②没有它会怎样：轮询

做法怎么拿到进度疼在哪
一次性返回等全部写完几十秒白屏；超时比生成时间短就整个失败（全景第 4 站）
短轮询先返回任务 id，客户端每秒问一次“写到哪了”大量空请求；延迟取决于轮询间隔；服务端要存中间结果
长轮询每次请求挂着，有新内容就返回，客户端立刻再发下一个能用，但每段内容一次请求，重连和顺序都要自己管
流式响应（SSE）一个请求、一条长响应，内容一来就推延迟最低，只要一个连接；纯 HTTP，过代理、过负载均衡都简单
不懂精华时的典型误用：后端开了流式，前端也写了 SSE，结果页面上还是“憋一会儿一次性出来”。代码没问题，问题在中间某一层（应用的缓冲区、Nginx、gzip）把块攒起来了：流式要求从模型到浏览器的每一层都不攒。

③相邻方案：服务端往客户端推，有几种办法

方案方向底层适合
SSE（text/event-stream）服务端 → 客户端，单向普通 HTTP 响应模型输出、日志尾巴、进度通知；Claude、OpenAI 的流式接口都用它
WebSocket双向HTTP 升级后的独立协议聊天、协作编辑、游戏：客户端也要随时发
gRPC 流单向或双向HTTP/2服务之间；浏览器直接用不方便
长轮询模拟单向一连串普通请求老环境、什么都不支持时的兜底

本页学 SSE：模型输出天然是单向的“服务端说、客户端听”，SSE 就是最省事的那个：不换协议、不升级连接，代理和网关不用特殊配置（缓冲除外，见 ⑥）。

④原理：分块传输、每一层的缓冲区、SSE 的文本格式

先知道这些
  • HTTP 报文：状态行、头、空行、正文，都是 TCP 上的字节（从输入 URL 到页面展示）。
  • 缓冲区：Java 的 BufferedOutputStream 攒够才写；flush() 让它立刻把手里的写下去。

机制 1 · 分块传输：先说“下面这块有多长”，再给这块

HTTP/1.1 里，响应头写 Transfer-Encoding: chunked、不写 Content-Length，正文就变成一串块：每块先一行十六进制的长度，再是这么多字节，块与块之间用 \r\n 隔开；最后一个长度为 0 的块表示结束。实测 用 curl --raw 看本页的 Java 服务：

JDK 的 HttpServer 里，sendResponseHeaders(200, 0) 的“长度 0”就是“我不知道总长度，用分块”。HTTP/2 没有 chunked 这回事：它本来就把正文切成一个个 DATA 帧，效果相同。

机制 2 · 缓冲：从模型到浏览器，每一层都可能攒着不发

机制 3 · SSE 格式：几行“字段: 值”，空行结束一个事件

text/event-stream 的正文按 HTML 标准的 SSE 规范
event: content_block_delta        ← 事件类型，可省，默认 message
data: {"delta":{"text":"是"}}      ← 数据，可以有多行 data
id: 17                            ← 断线重连时浏览器会带 Last-Event-ID
                                  ← 空行：这个事件结束
: keep-alive                      ← 冒号开头是注释，常用作心跳
retry: 3000                       ← 告诉浏览器断线后隔多久重连

谁来拆

  • 浏览器：new EventSource(url) 自动拆事件、断线自动重连；但只能发 GET，不能带请求体。
  • Claude 的流式接口是 POST（请求体里有 messages），所以浏览器里要用 fetch 读流自己拆，或者由后端转一道。
  • Java：JDK HttpClient 的 BodyHandlers.ofLines() 按行给你（⑤）；各家 SDK 都替你拆好了。

为什么这样设计：为什么在 HTTP 上约定文本行，而不另起一个协议

SSE：普通 HTTP 响应 + 文本行

  • 不用升级协议，现有的鉴权、负载均衡、网关、日志全部照用。
  • 文本格式，curl -N 就能看，排查方便。
  • 规范自带重连和断点续传（id + Last-Event-ID）。
  • 代价：只能单向；文本格式，二进制要先编码；HTTP/1.1 下浏览器对同一域名的连接数有限制。

WebSocket

  • 双向、低开销，适合频繁互发。
  • 要 HTTP 升级，代理和网关要专门支持；连接建立后就脱离了 HTTP 的那套中间件。
  • 消息边界、重连、续传都要自己设计。
决定胜负的约束：模型输出只需要服务端往客户端推，而请求本身就是一次普通的 HTTP 调用。在同一个响应上多推几块，是对现有基础设施改动最小的做法。

最少的语法（Java）

⑤亲眼看到：flush 和不 flush，同一个客户端读模型

JDK 17 自带的 HttpServer 写一个 SSE 服务（不加任何依赖）：每 400 毫秒写一个事件，一共 8 个，模仿模型一段段吐字。?flush=true 每个事件后 flush；?flush=false 写进 64 KB 的 BufferedOutputStream 不 flush。客户端用 JDK HttpClient 按行读，打印每个事件到达的毫秒数。

⑤SseServer.java（核心）完整代码 →
ex.getResponseHeaders().add("Content-Type", "text/event-stream; charset=utf-8");
ex.sendResponseHeaders(200, 0);                  // 长度 0：不知道总长度，走分块
try (OutputStream out = new BufferedOutputStream(ex.getResponseBody(), 64 * 1024)) {
    for (String p : PIECES) {
        Thread.sleep(400);
        out.write(("event: content_block_delta\ndata: {...\"" + p + "\"}\n\n").getBytes(UTF_8));
        if (flush) out.flush();                  // 不 flush，字节就躺在缓冲区里
    }
}                                                // close 时才把剩下的发出去

读出来的结论
  • 头先到：两种情况响应头都在 100～200 毫秒内到了，连接是通的，只是正文的字节还没来。
  • 不 flush 就是不流式：同样的服务端代码，少一行 flush()，前 2.4 秒客户端什么都收不到，最后 8 个事件挤在 4 毫秒里一起到，和一次性返回没有区别。
  • 格式就是那几行：模型服务推的也是 event: / data: / 空行，同一个 40 行的 Java 客户端直接能读，只是 POST 了一个请求体。
到这里已经能交差了：你能写一个真正流式的 SSE 接口，也能用 Java 客户端按事件读模型的流。
已知还没处理的细节：中间层缓冲（坑 1），代理超时（坑 2），EventSource 只能 GET（坑 3），长连接占线程（坑 4）。

⑥细节：上线以后流式为什么又不流了

第一圈 · 注意事项

1本地流式，上线后变成一次性实测← ④ 机制 2
现象
本地直连服务是一个个字出来的，经过 Nginx 或网关后，页面憋几十秒一次性出现。
根源
某一层在攒：Nginx 默认会缓冲上游响应（proxy_buffering on），开了 gzip 也要攒一段才压；⑤ 的 flush=false 就是这个效果。
做法
SSE 路由上关缓冲：Nginx 配 proxy_buffering off，或者由应用在响应头里加 X-Accel-Buffering: no；对 text/event-stream 关掉压缩；应用每个事件后 flush。
2长时间没数据，连接被代理掐断← ④ 机制 3
现象
模型思考了 70 秒才开始吐字，客户端在第 60 秒收到连接关闭。
根源
代理和负载均衡有“读超时”（Nginx 的 proxy_read_timeout 默认 60 秒）：这么久没收到任何字节就当它死了。
做法
定期发心跳注释行（: ping\n\n）；把这条路由的读超时调大；Claude 的流里也会有 ping 事件（按文档）。
3浏览器的 EventSource 发不了 POST← ④ 机制 3
现象
想在前端直接用 EventSource 调模型接口，发现没法带请求体，也加不了自定义鉴权头。
根源
规范里 EventSource 只发 GET；模型接口要 POST 一大段 messages。
做法
前端调自己的后端，后端调模型、再把事件转发给前端；或者前端用 fetch 读 ReadableStream 自己按空行拆事件。API key 永远不要放进前端。
4每个流占住一个请求线程← ④ 为什么这样设计
现象
同时有 200 个用户在看流式回答，Tomcat 的 200 个工作线程全被占住，其他接口开始排队。
根源
传统 Servlet 模型一个请求一个线程，流要持续几十秒，线程就被占几十秒。
做法
用 SseEmitter 让请求线程立刻返回、在别的线程里写；或者用 WebFlux 返回 Flux<ServerSentEvent>；JDK 21 也可以用虚拟线程扛（虚拟线程）。

第二圈 · 使用规范

  • SSE 接口三件套：Content-Type: text/event-stream、Cache-Control: no-cache、X-Accel-Buffering: no。防坑 1。
  • 每个事件后 flush，超过 15～30 秒没数据就发心跳。防坑 1、2。
  • 一个流一个超时：SseEmitter 设超时、完成和出错都要 complete，客户端断开要停掉上游调用，别让模型在没人看的情况下继续计费。
  • data 里有换行就拆成多行 data：或者统一用 JSON 编码（换行变成 \n）。防的是一条事件被拆成两条。

第三圈 · 更深一层

HTTP/2 下没有 chunked

HTTP/2 本来就把正文切成 DATA 帧，Transfer-Encoding 头不再使用；多路复用也让“浏览器每个域名最多 6 个连接”的限制不再卡 SSE。

断点续传

事件带 id，浏览器断线重连时自动带 Last-Event-ID 头；服务端据此从断点继续。模型输出要支持续传，就得把已生成的内容存下来。

实验台：事件什么时候到客户端

先猜：应用每个事件都 flush 了，但中间的代理开着 8 KB 的缓冲，每个事件约 90 字节、每 400 ms 一个。第一个事件什么时候到浏览器？

简化模型：每 400 ms 产生一个约 90 字节的事件；某一层缓冲没满且没被 flush 时就攒着，满了或流结束时一次放出。⑤ 实测了“不 flush”那一行（8 个事件，2.4 秒后一起到）；代理那一行是按这个规则推算的。

下一圈

  • WebFlux 的 Flux<ServerSentEvent>：背压和取消怎么传到上游的模型调用。
  • HTTP/2、HTTP/3 下的流式：帧、流量控制、队头阻塞。
  • WebSocket 和 SSE 在网关（Spring Cloud Gateway、Nginx）上的配置差异。

↺回到⑤：改一改

  1. 心跳：给 SseServer 加一个参数，事件之间每 200 ms 发一行 : ping，客户端忽略冒号开头的行。（坑 2）
  2. 断开就停：客户端读到第 3 个事件就关连接，服务端打印“客户端断开”，并停止后面的写入。（第二圈 规范 3）
  3. Spring 版：用 Spring Boot 写同样的接口，分别用 SseEmitter 和直接返回 String，用 ⑤ 的客户端对比到达时间。（④ 最少的语法）

自测

1. 用一句话说出这一页的精华

流式响应就是先发头、不写总长度，每 flush 一次推一块；SSE 在上面约定了 event / data / 空行的文本格式；从应用到浏览器每一层都不能攒，流式才成立。

2. 为什么 sendResponseHeaders 的长度要写 0？

写 0 表示不知道总长度，用分块传输；写一个正数就要求正文正好这么长，只能一次性写完。

从 ④ 机制 1 推出

3. 预测：应用每个事件都 flush，但 Nginx 开着默认缓冲，用户会看到什么？

还是憋一阵再出一大段：Nginx 攒满它的缓冲区或者上游结束时才往外发。flush 只管到你自己的进程边界。

从 ④ 机制 2 推出；实验台可以调出这个情况

4. 预测：模型思考了 90 秒才开始输出，中间什么都没发，经过默认配置的 Nginx 会怎样？

第 60 秒左右 Nginx 的读超时到了，连接被关，客户端报错；模型那边可能还在算、还在计费。要发心跳并调大这条路由的读超时。

从坑 2 推出

5. 为什么模型接口选 SSE 而不是 WebSocket？

模型输出是单向的；请求本身就是一次普通 HTTP 调用，SSE 只是在同一个响应上多推几块，鉴权、网关、日志都不用改；WebSocket 要升级协议、自己设计消息边界和重连。

从 ④ 为什么这样设计 推出

6. 放回全景：站 03 全景的第 7 站前后是什么？如果第 7 站中间的网关把 SSE 攒成了一次性返回，链路会怎样？

前面是第 6 站模型生成，后面是第 8 站收齐。网关攒着：第 8 站最终还是能收齐，结果不变；但用户在第 7 站看不到任何进度，首字延迟变成总耗时；如果生成时间超过网关或客户端的超时，第 4 站就会报超时并重试，钱花两遍。

档位：标准（补给页）。本机跑过（2026-11-22，2 核 ARM，OpenJDK 17，JDK 自带 HttpServer 和 HttpClient，curl）：flush 与不 flush 的事件到达时间、分块传输的原始字节、Java 客户端读 llama.cpp b12618 /v1/messages 的流。按文档 / 规范：HTTP/1.1 分块传输、HTML 标准里的 SSE 格式和 EventSource 只支持 GET、Nginx 的 proxy_buffering（默认开）和 proxy_read_timeout（默认 60 秒）、X-Accel-Buffering、Spring 的 SseEmitter、Claude 流里的 ping 事件。实验台里代理缓冲那一行是推算，没有起 Nginx 实测。
