279 µs 里只有 2 µs 在 Redis：一条连接、一个线程上的排队

Redis 执行一条 GET 不到 1 µs，时间几乎全花在路上和排队上。这里有两处“按顺序”：一个线程按顺序执行命令，一条连接按顺序回复。命令天然原子靠的是它们；任何一个慢的东西拖住排在后面的所有请求，也是因为它们。

下一圈第一圈讲了单线程为什么快、select / poll / epoll、事件循环、IO 线程、Pipeline，这些这里只用一两句带过。这一圈只盯一次 GET 的来回：时间花在哪几段，排队排在哪里，哪些东西会让后面的请求一起等，Redis 的监控为什么看不见这段等待。

①为什么需要：Redis 只干了 2 µs，客户端却等了 279 µs

在全景第 2、3 站，这一步要解决的是：4 个实例、每个 50 个线程同时查 88 号，Redis 上一共只有 4 条连接，一个线程。全景实测，服务端执行一次 GET 平均 2.0 µs，客户端等一次却要 279 µs，p99 是 1.26 ms。

要做成的事：能把 279 µs 拆成几段，说清排队排在哪里；能预先说出哪种操作会把同一个 Redis 上的所有人拖住，哪种只拖住同一条连接上的人；出事时知道该看哪个指标，不被 SLOWLOG 骗了。

②没有它会怎样：一个连接一个线程，再加一把锁

换成 Java 后端最熟的写法：像老的 Tomcat BIO 一样一个连接配一个线程，数据放在一张加了锁的 HashMap 里。第一圈讲过它输在哪，这里只看和本页有关的两点。

老办法一连接一线程 + 锁

Redis一个线程 + epoll

不懂精华时的典型误用：觉得“Redis 单线程，所以慢”，于是给每个实例配一个 200 条连接的池子，或者打开 io-threads 想让命令跑得更快。⑤会实测：200 个线程共用 1 条连接，吞吐不比 200 条连接低；Redis 主线程执行命令的时间还不到它 CPU 时间的 4%，要省也省不在这里。

③相邻方案：要用多核，还有别的做法

同样是内存 KV，有的产品让多个线程直接执行命令。差别在于：原子性靠什么保证，多核怎么用上。

谁执行命令多核怎么用上多 key 操作、脚本的原子性
Redis 7.2 及以前主线程IO 线程帮忙收发（默认只帮写回复）；更多的靠多开实例、集群天然原子：一条命令、一段 Lua 执行时没人插队
Redis 8.x主线程IO 线程各管一批连接：读、解析、写回复都在 IO 线程里做同上，执行没变
Memcached多个 worker 线程线程直接并行执行靠锁；没有脚本，多步操作靠 CAS 自己重试
Dragonfly 一类每个线程管一部分 key按 key 分片，线程之间不共享数据单分片内天然有序；跨分片的多 key 操作要额外协调

选择规则：命令都很短、又要原子性，就用“一个线程执行 + 多开实例”，这是 Redis 的选择。单机要吃满几十个核、又能接受换产品，再看多线程实现。本页学 Redis 的做法，重点看它把“排队”放在了哪里。

④原理：一次 GET 的来回，和路上的两处排队

先把一次 GET 从业务线程出发、再回到业务线程的路走一遍，标出每一段是谁在干活。然后看路上哪两处是“按顺序”的，这两处就是排队的地方。

先知道这些
  • epoll：线程把一堆 socket 交给内核盯着，调一次 epoll_wait，拿回有数据的那几个。第一圈讲过 select / poll / epoll 的区别：线程模型与 IO 多路复用，更底层的在 IO 模型。
  • RESP：Redis 的协议是纯文本加长度前缀。GET product:88 在线上就是 *2\r\n$3\r\nGET\r\n$10\r\nproduct:88\r\n 这 31 个字节，回复是 $648\r\n 加上 648 字节的 JSON。⑤的程序自己拼这串字节发出去，也能拿到回复。
  • Lettuce 基于 Netty：读写 socket 的是 Netty 的 EventLoop 线程，业务线程只拿到一个 future。EventLoop 是什么：Netty 的 EventLoop、Pipeline 与 ByteBuf。

一次 GET 的来回：8 段

  1. 业务线程调 get()：命令交给 Netty 的 IO 线程，业务线程等在 future 上。第一次线程交接
  2. IO 线程写 socket：编成 RESP 字节写进去，同时把这条命令排进“等回复”的队列尾部。同一条连接上的 50 个线程，都排在这一个队列里
  3. 内核和网络：同机房一个来回通常 100～500 µs；⑤ 在同一台机器上量到 30 µs。这一段 Redis 管不着
  4. Redis 主线程从 epoll_wait 醒来：每个可读的连接 read 一次，最多 16 KB，可能一次就读到好几条命令。
  5. 解析并执行：读到的完整命令，一条接一条在 call() 里执行，GET 只要零点几微秒。SLOWLOG、commandstats、latencystats 量的都只是这一段
  6. 写回复：回复先放进这个客户端的输出缓冲；本轮事件都处理完，在 beforeSleep 里统一 write，每个客户端一次最多 64 KB，写不完下一轮接着写。
  7. Netty 读到回复：解码出一个回复，对给队头的那条命令，没法挑。RESP 里没有请求编号
  8. 完成 future，唤醒业务线程。第二次线程交接

为什么这样设计：一个线程按顺序执行，一条连接按顺序回复

Redis 的做法选中的

多线程执行 + 回复带编号被放弃的

决定胜负的约束：执行一条命令只要零点几微秒。⑤实测，Redis 主线程的 CPU 只有约 3.5% 花在执行命令上，其余都是收发和解析。把执行拆给多个线程，省下的这一点时间，还抵不上锁的开销，还要丢掉原子性。所以 Redis 只把收发拆出去（IO 线程，见⑥），执行一直留在一个线程。连接按顺序回也是同一个思路：协议最简单，代价是队头阻塞，客户端要自己避开（⑥）。

Redis 只干了一小段

执行一次 GET 0.3～0.5 µs。全景那次量到 2.0 µs，数量级一样：都是微秒以下到几微秒。

Lettuce 多出 70 µs

裸 socket 30 µs，Lettuce 101 µs。多出来的主要是④第 1、8 段：命令交给 Netty 线程、回复回来再唤醒业务线程，两次线程交接。

200 个线程：排的是客户端的队

p50 涨到几毫秒，可 Redis 主线程 CPU 才 32%～48%，并没有忙满。等的是 2 个核上 200 个线程抢 CPU，以及连接上的等回复队列。

1 条连接不比 200 条差

两次运行，1 条连接 × 200 线程是 5.2 万、5.1 万次/秒；200 条连接是 4.0 万、4.0 万。一条连接上的命令会攒成一批一起发（自然的 Pipeline），Redis 一次 read 就读到好几条。

4 条连接 × 50 线程那一行两次差得很多（2.2 万和 5.3 万次/秒，p50 8.1 ms 和 2.9 ms），在这台 2 核机器上客户端和 Redis 抢 CPU，数字不稳，只看量级。全景那次的 279 µs 走的是端口映射（裸来回就要 62 µs），再加上两次线程交接和 200 个线程之间的排队，大致就是这个数。

到这里已经能交差了：Spring Boot 默认就是一个实例一条 Lettuce 共享连接，这正是⑤里吞吐最好的那种配法，什么都不用改。已知还没处理的细节：一条慢命令会拖住所有连接（⑥-1），Redis 的监控看不见排队（⑥-2），共享连接上的阻塞命令和大 value 只拖住同一条连接（⑥-3、⑥-4），默认超时 60 秒（⑥-5）。

⑥细节：谁会被拖住，监控为什么看不见

第一圈列过慢命令、大 key、Lua 跑太久这些坑。这一圈的坑都来自④那两处排队：在主线程上排队的，拖住所有连接；在一条连接上排队的，只拖住这条连接，可这条连接往往就是整个实例。

第一圈

注意事项：不知道就会出事故

1一条 KEYS，4 个实例一起卡← ④ 排队点 B
现象
有人在线上跑了 KEYS session:*，库里 100 万个 key，一个都没匹配上。实测：KEYS 106 ms，它前后发出的 791 个 GET 最慢 116 ms，哪条连接上的都一样。整体 p99 只有 12 ms，平均下来看不出来
根源
主线程一次只执行一条命令。KEYS 要把 100 万个 key 全看一遍，这 106 ms 里所有连接上的请求都只能排着。
做法
遍历改用 SCAN … COUNT 1000 分批：实测 1000 次 SCAN 一共 2.25 s，这期间 GET 的 p99 是 8.95 ms，和平时一样。再用 ACL 的 -@dangerous 或 rename-command 把 KEYS 禁掉。
2SLOWLOG 是空的，客户端却说慢← ④ 第 5 段
现象
上面那 116 ms，Redis 自己的数字一点都看不出来。实测：同一段时间，GET 的 latencystats p99.9 = 2 µs，commandstats 0.30 µs/次，SLOWLOG 里只有 KEYS 一条，没有一条 GET
根源
这三个数字量的都是 call() 里执行命令的那一段（源码里都取自同一个 c->duration），排队、网络、客户端都不算。被堵住的 GET，执行起来照样很快。
做法
延迟以客户端量到的为准（Lettuce 的命令延迟指标接进 Micrometer）。SLOWLOG 用来找“是谁堵的”，不是“谁被堵了”；再看主线程 CPU（used_cpu_*_main_thread）和 LATENCY DOCTOR。
3共享连接上跑 BLPOP，整个实例停 2 秒← ④ 排队点 A
现象
有人在同一条连接上等改价队列：BLPOP queue:price-change 2。实测：50 个线程共用一条连接，这 2 秒里只发出 52 个 GET，每个都等了 2026 ms，50 个线程全被挂住。换成独立连接：同样 2 秒发出 79,233 个 GET，p99 3.28 ms
根源
Redis 让这个客户端进入阻塞状态，它后面排着的命令先不处理；回复又只能按顺序回。对 Redis 来说，这 50 个线程就是同一个客户端。
做法
阻塞命令、订阅、MULTI 事务都用独立连接。走 Spring 的 RedisTemplate 时，它会自动给 BLPOP、BRPOP、BLMOVE 和事务换一条专用连接；直接用 Lettuce 原生 API，要自己另开一条。
4共享连接上取一个大 value← ⑥ 一轮事件循环
现象
88 号的图片列表塞进了一个 16 MB 的 product:88:images。实测：取一次 38 ms，这期间同一条连接上发出的 51 个 GET 都等了 38 ms；放到另一条连接上取，别的 GET 最慢 5 ms
根源
回复按顺序回，16 MB 传完、解码完，排在后面的回复才轮得到。Redis 这边每轮最多给一个客户端写 64 KB，会把大回复切成很多轮，所以别的连接只受一点影响。
做法
拆掉大 key（大 key、热 key）；实在要取的大对象，走独立连接，或者干脆换个地方存。
5超时默认 60 秒，调短了也救不回连接← ⑥ Lettuce 这一侧
现象
Lettuce 默认的命令超时是 60 秒。Redis 一卡，业务线程就挂 60 秒，Tomcat 的线程很快被占满。实测：改成 500 ms，再在共享连接上 BLPOP 2 秒。BLPOP 自己 510 ms 就超时了，可之后的 GET 还是一个接一个超时，共 157 次，一直到第 2010 ms；之后再 GET 88 号，拿到的确实是 88 号，没有错位
根源
超时只是业务线程不等了。命令已经发出去，还排在等回复的队列里，回复到了就丢掉（所以不会错位）；Redis 那边，这个客户端该堵还是堵着。
做法
spring.data.redis.timeout 配几百毫秒，超时由降级逻辑接住。超时只能止损，不能让连接恢复，根子还是⑥-1、3、4。

第三圈

深处：一轮事件循环、IO 线程、Lettuce 的队列

一轮事件循环，公平是怎么分的

主线程的 CPU 去哪了：IO 线程从 7.2 到 8.x

⑤里主线程用了 46% 的 CPU，执行命令只占 1.6%。剩下的都花在 read、write 系统调用、解析协议和事件循环上。所以 Redis 要并行，就并行这部分：这就是 IO 线程。

Redis 6.0～7.2主线程分活、原地等

io-threads-do-reads yes 才帮读。分发和等待是一轮一轮同步的。 等的时候主线程什么也不干

Redis 8.0 起每个 IO 线程管一批连接

Redis 7.2Redis 8.x
io-threads 默认1（不开）1（不开）；⑤ 的容器里读出来也是 1
IO 线程干什么默认只写回复；io-threads-do-reads yes 才读和解析读、解析、写都由连接所属的 IO 线程做
主线程怎么配合每轮分发，空转等全部 IO 线程做完异步：IO 线程解析完一条就交过来
io-threads-do-reads有，默认 no废弃，写了也被忽略
谁执行命令一直是主线程：SET NX、Lua 的原子性在两个版本里都不变

出处：Redis 8.0.0 发行说明 “A new I/O threading implementation”，PR #13695 “Async IO Threads”；iothread.c 的 assignClientToIOThread（“Find the IO thread with the fewest clients”）。按 8.2.1 和 7.2.5 的源码核对。IO 线程能省的是④第 4、6 段里主线程的系统调用，客户端那边的线程交接和排队它管不着；在 2 核的机器上，客户端和 Redis 本来就在抢 CPU，开了未必更快（↺ 练习 1）。

Lettuce 这一侧：一条队列，三个默认值

按顺序对回复

CommandHandler 里的 stack：写出时 add 到队尾，回复来了 peek 队头解码，完了 poll。没有编号，只能这样对。

超时 = 业务线程不等了

同步 API 等不到就 cancel 这条命令并抛超时。命令还留在队列里，回复到了解码后丢掉，后面的命令不会错位（⑥-5 实测）。

三个默认值

命令超时 60 秒（RedisURI.DEFAULT_TIMEOUT）；请求队列上限 Integer.MAX_VALUE，等于不限；断线自动重连。

所以要自己兜底

Redis 卡住时，命令在客户端内存里一直排着，线程一直等着。超时配短，必要时给 requestQueueSize 设个上限，让它尽早失败。

按 Lettuce 6.8.2 源码核对；Spring Data Redis 3.5.5 的 LettuceConnectionFactory 默认 shareNativeConnection = true，阻塞的 list 命令走 getAsyncDedicatedConnection()，事务（isQueueing()）也换专用连接。

1. 用一句话说出这一页的精华

Redis 执行命令只要零点几微秒，一次 GET 的时间几乎全在路上和排队上；排队有两处：主线程（一条慢命令拖住所有连接），连接上的等回复队列（一个慢的拖住同一条连接上的所有线程），而原子性正是这两处“按顺序”给的。

2. 279 µs 里大头在哪？打开 IO 线程能省掉多少？

在客户端和路上：裸 socket 来回 30 µs（经端口映射 62 µs），Lettuce 的两次线程交接约 70 µs，再加上 200 个线程抢 CPU、排在等回复队列里。Redis 执行只有微秒级。IO 线程只能分担 Redis 主线程上的收发，省的是④第 4、6 段里 Redis 那一侧的一小部分，客户端这边的排队它管不着。

3. SLOWLOG 是空的，latencystats 的 p99.9 只有 2 µs，客户端却报 100 ms。可能是什么？

被堵住的命令执行起来照样很快，所以 Redis 的三个数字都正常；它们只量执行。可能是：前面有一条慢命令（看 SLOWLOG 里有没有别的命令，比如 KEYS）；同一条连接上有阻塞命令或者大回复；客户端自己的线程或 GC；网络。先看客户端的指标在哪一段慢，再到 Redis 上找元凶。

4. 预测：有人在 Lettuce 的共享连接上直接调 multi()，还没 exec()，别的线程的 GET 这时也走这条连接。会怎样？

Redis 只认连接，不认线程：MULTI 之后，这条连接上来的命令都会被当成事务的一部分排起来，到 EXEC 才执行。别的线程的 GET 被卷进了别人的事务，拿不到正常的结果。这就是 Spring 把事务放到专用连接上的原因。从④“排队点 A”和“Redis 看到的是连接”推出来。

5. 预测：Redis 8 打开 io-threads 4 以后，第 5 站的 SET NX 还是原子的吗？一条 KEYS 还会拖住所有人吗？

还是原子的，KEYS 也照样拖住所有人：IO 线程只做读、解析、写，命令仍然由主线程一条一条执行。从④“排队点 B”和⑥第三圈的对比表推出来。

6. 放回全景：第 2、3 站前后各发生了什么？这一页讲的东西坏了，整条链路会怎样？

第 1 站本地 Caffeine 没命中，才走到第 2 站：Lettuce 把 GET 发到这个实例唯一的那条连接上；第 3 站 Redis 主线程查字典，没有 88 号，于是第 4 站查布隆过滤器、第 5 站抢重建锁、第 6 站查库、第 7 站回填。要是第 3 站有人跑了 KEYS：4 个实例的所有 Redis 请求一起等 100 多毫秒，连第 5 站的锁、第 7 站的回填也在排队，接口 p99 跟着涨，SLOWLOG 里却只有那条 KEYS。要是第 2 站的共享连接上跑了 BLPOP：这个实例的 50 个线程全挂住，默认要等 60 秒才超时，Tomcat 线程池被占满，其他 3 个实例照常。超时配短了，也要等那条 BLPOP 结束，这条连接才能恢复。
