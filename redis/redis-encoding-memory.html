648 字节的详情占 805 字节：Redis 8 的 kvobj、embstr 新门槛与存 String 还是 Hash

一个 key 占的内存 = 对象头 + key + 值 + 分配器取整，再加上对象外面字典的那一份。Redis 8.2 把 key 和 TTL 搬进了对象里，每个 key 少了一次分配，embstr 的门槛也从“值 ≤ 44 字节”变成了“key + 值 ≤ 41 字节”。选 String 还是 Hash，看的不是哪种结构省，而是数据会落进哪种编码。

下一圈第一圈按 Redis 7.2 讲了 redisObject、int / embstr / raw、listpack、渐进式 rehash、跳表，这些这里只用一两句带过。这一圈只盯全景第 7 站回填的那一条 88 号：它在内存里长什么样，805 字节一个一个算出来；Redis 8 改了什么；详情存成 String、Hash 还是 JSON，各占多少。

①为什么需要：648 字节的详情，Redis 记的是 805

在全景第 7 站，这一步要解决的是：拿到重建锁的线程查完库，把 88 号的 648 字节 JSON 用 SET product:88 … EX 1843 回填进 Redis。全景实测 OBJECT ENCODING 是 raw，MEMORY USAGE 是 805。靶场有 1 万个商品，大促前要按 100 万个估 Redis 内存：每个按 648 算，还是按 805 算？都不对的话，差在哪？

②没有它会怎样：按“值多长 × 多少个”估内存

不知道对象在内存里的样子，估内存只能拿值的字节数乘个数。值越小，估得越离谱；还有人“为了省内存”把 JSON 拆进 Hash，结果更费。

③相邻方案：88 号详情的四种存法

同一份 88 号，在 Redis 8 里能存成四种样子。先只看它们会落进哪种编码，各占多少放到⑤实测。

存法命令编码适合
String，整块 JSON（全景就是这样）SET product:88 '{…}' EX 1843raw（> 44 字节）整块读、整块写：详情页一次全要，改价时整条删掉
Hash，5 个字段HSET product:h:88 id … detail …listpack；有一个值 > 64 字节就变 hashtable字段常单独读写，而且每个值都短
Hash 放短字段 + 详情单独一个 StringHSET product:h:88 … + SET detail:88 …listpack + raw价格、库存常单独改，详情很少变
JSON（Redis 8 自带的 RedisJSON）JSON.SET product:88 $ '{…}'模块类型（OBJECT ENCODING 显示 raw）要在服务端按路径读改：JSON.SET product:88 $.price 359
选择规则：先看怎么读写，再看会落进哪种编码。整块读写用 String；字段要单独改、每个值都不超过 64 字节，用 Hash；要服务端按路径改，用 JSON。要算清它们各占多少，得知道一个 key 在内存里长什么样，这就是④要讲的。

④原理：一个 key 在内存里长什么样

一个 key 由几块内存拼起来：字典里的一格，指向一个对象头，对象头再指向值。Redis 7.2 和 8.2 之后拼法不一样，805 就是 8.10 的拼法算出来的。

先知道这些
  • redisObject（robj）：每个值外面套的 16 字节对象头，记着类型（string、hash…）、编码（int、embstr、raw、listpack…）、LRU 时间、引用计数和一个指向数据的指针 ptr。第一圈讲过：Redis 数据结构与编码。
  • SDS：Redis 自己的字符串，前面一个头记长度（短于 32 字节 1 字节，≤ 252 字节 3 字节，再长 5 字节），后面补一个 \0。
  • jemalloc 按档分配：要 654 字节，给的是 768 那一档。64 字节以内每 8 字节一档，再往上每翻一倍分 4 档：… 512、640、768、896、1024 …。多给的那部分也算占用。

同一个 product:88，两种拼法

Redis 7.2key、对象头、值、过期时间各自分配

Redis 8.2 起：kvobjkey 和 TTL 塞进对象头两边

为什么要这样改：缓存里放的是几百万、几千万个小 key，每个 key 的固定开销和查找时跟几次指针，乘起来就是几百 MB 内存和每次 GET 的缓存未命中。7.2 的字典是通用的（Hash、Set 也用它），key 和值各放一边，写起来简单，代价是每个 key 多两三次分配、多两跳。8.2 让主字典只存一个指针（no_value=1），key 跟着对象走。实测同样 5 万个 88 号这样的商品，每个从 868 字节降到 838；stock:88 = 1200 这种小 key，MEMORY USAGE 从 56 降到 27。

出处：Redis 提交 e1789e4（PR #13806 “keyspace - Unify key and value & use dict no_value=1”，2025-05-12），8.0.0 的 object.c 里还没有 kvobjCreate，8.2.0 里有。“跳”数是按结构数的，没有单独测延迟。

Hash 反而最费

detail 576 字节，超过 hash-max-listpack-value 的 64，整个 Hash 变成 hashtable：5 个字段各有自己的 key、值和字典条目。比 String 多 20%。

拆开才接近 String

4 个短字段留在 listpack 里（一块连续内存），长详情单独一个 String。853 比 838 多一点，多的是第二个 key 的开销；换来的是价格、库存能单独改。

JSON 不省

RedisJSON 把文档解析成树存，每个商品 944 字节，多 13%。它的 MEMORY USAGE 报 792，比实际少，原因在⑥。

8.10 每个 key 省 30 字节

同样的 String，8.10 比 7.2 少 30 字节：少了 dictEntry 和 expires 里那一条。key 越小，省的比例越大。

到这里已经能交差了：全景的写法（String 整块 JSON）就是四种里最省的，不用改。容量按每个商品 838 字节估：1 万个 8 MB，100 万个约 800 MiB，再给 maxmemory 留出碎片和复制缓冲的余量。已知还没处理的细节：Hash 里混进一个长字段（⑥-1），MEMORY USAGE 乘个数会估小（⑥-2），压测数据太整齐会让 JSON 显得很省（⑥-3），调大 listpack 阈值的代价（⑥-4）。

⑥细节·规范·优化

第一圈

注意事项：不知道就会出事故

1“拆进 Hash 省内存”，结果多 20%← ③ 编码按最长的那个值切换
现象
听说小 Hash 用 listpack 很省，就把 88 号的 5 个字段 HSET 进去。实测 8.10：每个商品 1004 字节，String 是 838；OBJECT ENCODING = hashtable
根源
listpack 有两个门槛：字段数 ≤ hash-max-listpack-entries（默认 512），每个值 ≤ hash-max-listpack-value（默认 64 字节）。只要有一个值超了，整个 Hash 转成 hashtable，每个字段都变成独立的 SDS 加字典条目。
做法
整块读写的详情直接存 String；字段要单独改的，把长字段拆出去，Hash 里只留短字段（⑤ 的 hash-split，853 字节）。
2拿 MEMORY USAGE 乘 key 数，内存估小← ④ 两种拼法
现象
按 805 × 100 万估，上线后 used_memory 比估的多 4%；7.2 上多 5%；JSON 多 19%。实测：8.10 String 805 → 838，7.2 824 → 868，JSON 792 → 944
根源
MEMORY USAGE 只算对象本身：字典的桶不算；7.2 的 expires 那条 24 字节不算；模块类型（JSON、Bloom）由模块自己报，报得粗。
做法
容量规划用⑤的办法：批量写 N 个真实形状的数据，看 used_memory 增量 ÷ N。MEMORY USAGE 只用来比较两种存法谁大谁小。
3压测数据都一样，JSON 看着省了 3 倍实测现象
现象
造压测数据时 5 万个商品用了同一段详情，JSON 每个商品只占 278 字节，看着比 String 省很多。实测 8.10：-DsameDetail=true 时 JSON 278 字节，详情各不相同时 944
根源
看起来是 RedisJSON 对相同的字符串只存了一份（它内部会共享字符串），String 不会。这页没有去翻 RedisJSON 的源码，只记下这个现象。
做法
估内存的数据要像真的：详情、名称各不相同。最好从线上导一批真实数据回放。
4把 hash-max-listpack-value 调到 1024 迁就详情← ④ listpack 是一整块
现象
Hash 是 listpack 了，内存也省了，可每次改价都要动整块，字段多的 Hash 读一个字段也要从头找。
根源
listpack 是一块连续内存，按顺序一个个存。HGET 要从头往后找（O(n)）；HSET 改一个字段，可能要整块重新分配、把后面的挪一遍。门槛设成 64 字节、512 个，就是为了让 n 和整块都小到无所谓。按结构推的，这页没有压测。
做法
不为了一个长字段调全局阈值，它影响实例上所有 Hash。长字段拆出去。

第一圈页把 Hash 的个数门槛写成了 128。按 7.2 和 8.10 的源码（config.c）和 redis.conf，以及这次 CONFIG GET 实测，hash-max-listpack-entries 默认是 512；128 的是 zset-max-listpack-entries 和 set-max-listpack-entries。

第二圈

使用规范：团队里怎么存、怎么估

整块读写的对象存 String

详情页一次要全量、改了整条删，就存一个 JSON String。

⑥-1：拆进 Hash 反而更费。

Hash 只放短字段

每个值 ≤ 64 字节，字段 ≤ 512 个；长的单独一个 key。上线前对样例数据跑一次 OBJECT ENCODING，确认是 listpack。

⑥-1、⑥-4：转成 hashtable，或者调大阈值。

容量按批量实测估

写 1 万～10 万个真实形状的数据，看 used_memory 增量；再给碎片、复制缓冲、AOF 重写留 30% 以上余量。

⑥-2、⑥-3：MEMORY USAGE 少算，压测数据太整齐。

key 短而有结构

product:88，别写成 trade:product:detail:prices:cache:88。

每个 key 都要多付这些字节；在 8.2 以后还挤掉 embstr 的位置（↺ 预测题 4）。

第三圈

深处：838 − 805、档位、第 3 站和第 4 站

838 − 805 = 33 字节去哪了

MEMORY USAGE 不算对象外面的东西：主字典的桶（5 万个 key 扩到 65536 个桶，每个 8 字节，平均每个 key 约 10.5 字节），桶里冲突时才分配的 dictEntry，kvobj 本身 37 字节被取整到 40。7.2 那边 868 − 824 = 44，大致是 expires 那条 24 字节，加上两个字典各自的桶。这是按结构估的，没有逐项拆开量。

jemalloc 档位：几个字节决定多付 128

88 号的值要 654 字节，落在 640～768 那一档，空着 114 字节。JSON 要是 634 字节，正好卡进 640 档，MEMORY USAGE 是 677（实测），每个省 128。一般不值得为这个改数据格式，但能解释“值只长了几个字节，内存跳了一截”。用④的计算器拖一拖值长度就能看到台阶。

第 3 站：查字典

8.10 的主字典设了 no_value=1：桶里直接放 kvobj 指针，指针低 3 位标记这一格是对象本身还是冲突链上的 dictEntry。查 product:88 时，算哈希找到桶，直接和 kvobj 里嵌着的 key 比较，比完就拿到对象头。7.2 要先经过 dictEntry，再分别去找 key 和 robj。

第 4 站：bf:product 是模块类型

Redis 8 的发行版自带 Bloom、JSON、时间序列、搜索几个模块（⑤ 的 8.10.3 容器里 MODULE LIST 能看到 bf、ReJSON）。bf:product 的类型是模块注册的，不走 String 那套编码，内存靠模块自己报。布隆过滤器本身怎么回事：布隆过滤器与 HyperLogLog。

版本和这一页有关的变化
6.x小 Hash、ZSet 用 ziplist
7.0listpack 全面替换 ziplist，配置改名 *-listpack-*（旧名还认）
7.2embstr：值 ≤ 44 字节；key、robj、dictEntry、expires 条目各自分配（第一圈页按这个版本写）
7.4Hash 字段可以单独过期（HEXPIRE），带过期字段的小 Hash 编码叫 listpackex（8.10 实测）
8.0JSON、Bloom 等模块随发行版自带
8.2kvobj：key、TTL 放进对象，主字典 no_value=1；embstr 门槛变成 key + 值（带 TTL 再加 8）凑进 64 字节（PR #13806）
8.10.3embstr 判断不再算 TTL：key + 值 ≤ 41（源码 + 实测）；MEMORY USAGE 由 kvobjAllocSize 算，含 key 和 TTL

7.4、8.0 两行来自发行说明和这次 8.10 容器的观察，没有装这两个版本逐一验证。

这一层没有尽头

用到：⑥ 第一圈 3

1. 用一句话说出这一页的精华

一个 key 的内存 = 对象头 + key + 值 + 分配器取整，再加对象外面字典的那份；Redis 8.2 把 key 和 TTL 塞进对象，每个 key 少一两次分配，embstr 门槛变成 key + 值 ≤ 41。选 String 还是 Hash，看数据会落进哪种编码。

2. 按“值多长 × 多少个”估内存，差在哪？

漏了每个 key 的固定开销（对象头 16、key、SDS 头、字典的桶，7.2 还有两个 dictEntry）和 jemalloc 的取整。值越小，固定开销占比越大：stock:88 = 1200 值 4 字节，实际 27（7.2 是 56）。648 字节的详情按 648 估，少了 29%。

3. 详情拆进 Hash，为什么比 String 还多 20%？

④ 和③：Hash 只要有一个值超过 hash-max-listpack-value（64 字节），整个就从 listpack 转成 hashtable。detail 576 字节，于是 5 个字段各自变成独立的 SDS 加字典条目，每个都有头、指针和取整的开销；String 只有一个对象头和一块值。

4. 预测：8.10 上 SET trade:product:detail:prices:cache:88 399.00 是什么编码？7.2 呢？

key 36 字节 + 值 6 字节 = 42 > 41，8.10 上是 raw（实测，MEMORY USAGE 65）；7.2 只看值 ≤ 44，是 embstr。从④的 64 字节图推：8.10 里 key 和值要一起挤进一条缓存行。

5. 预测：给 1 万个已有的 String key 都加上 TTL，7.2 和 8.10 上 MEMORY USAGE 和 used_memory 各怎么变？

7.2：每个 key 的 MEMORY USAGE 不变（expires 里的条目不算进去），used_memory 每个多 24 字节的 dictEntry 加 expires 字典的桶。8.10：TTL 要放进对象前面那 8 字节，原来的 kvobj 放不下，kvobjSetExpire 会重新分配一个（值那块不动），MEMORY USAGE 每个 +8，used_memory 大约也是 +8 再加取整。从④的“两种拼法”推。

6. 放回全景：第 7 站前后各发生了什么？这一页讲的东西估错了，整条链路会怎样？

第 6 站拿到重建锁的线程查库，拼出 648 字节 JSON；第 7 站 SET product:88 … EX 1843 回填（raw，805 字节），再用 Lua 解锁；第 8 站写进本地 Caffeine。要是按 648 估内存、maxmemory 配小了，到第 12 站：默认 noeviction 下回填报 OOM，每次请求都穿到 MySQL，击穿的压力一直在；配了淘汰策略的，热门商品被挤出去，第 3 站命中率下降。要是改成 Hash 存详情，同样的内存少装 17% 的商品。
