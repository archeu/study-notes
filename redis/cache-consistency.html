改完价，详情页还卖 399：先改库还是先删缓存、延迟双删、订阅 binlog

运营把 88 号商品从 399.00 改成 359.00，数据库一提交就是新价，Redis 里那份还是旧的。精华是：数据库和 Redis 是两个系统，没法放进同一个事务一起提交，所以缓存总有一小段时间是旧的；能设计的只有三件事：这段时间多短，旧值会不会被写回去长期留着，写路径半路出事时靠什么兜底。默认答案是先改库、再删缓存（删，不是改），缓存都带过期时间；删除要可靠，就交给订阅 binlog 的程序去删。

①要解决的问题：改价以后，Redis 里那份怎么跟上

在全景第 9、10 站，这一步要解决：运营在后台把 88 号改成 359.00，数据库提交了；可商品服务读的是 Redis 里的副本，它还是 399.00，而且还有 30 分钟才过期。地图给交易靶场定的标准是：改价后 1 秒内，所有读都拿到 359.00。本页管 Redis 这一层；4 个实例各自的 Caffeine（第 11 站）留给下一个知识点。

窗口短

提交以后，旧价还能被读到的时间，靶场标准是 1 秒以内。

旧值别写回去

最怕的不是旧几毫秒，而是旧价被写回 Redis，一直卖到 30 分钟后过期。下文管这叫“卡住”。

半路出事有兜底

改完库，删缓存那一步失败了、进程正好重启了，也不能永远旧下去。

②不用它会怎样：只靠过期时间

最省事的做法是改价时什么也不动缓存，等它 30 分钟后自己过期。代码里一行都不用加，可旧价最长能卖 30 分钟。把过期时间调短到 1 秒能达标，但缓存一秒钟就失效一次，命中率掉下来，数据库压力又回来了。

  • 只靠过期：旧价最长 30 分钟，平均 15 分钟。用户在详情页看到 399，下单时按 359 扣款，客服电话就来了。
  • 过期时间压到 1 秒：所有商品每秒失效一次，大部分读又打到数据库上，缓存等于没开。
  • 典型误用：“改完库顺手把缓存也改成新值”。看起来最直接，两个人同时改价时会把旧值留下，④ 里拆开看。

③几种流派：写路径怎么动缓存

读路径大家都一样，叫 Cache-Aside（旁路缓存）：先 GET，没命中就查库，查完 SET 回去。分歧都在写路径上：先动库还是先动缓存，动缓存是删还是改，由谁来动。

写法写路径做什么旧值会不会被写回去代价靶场实测（卡住轮数 / 20）
先删缓存，再改库DEL → UPDATE → 提交很容易：删完到提交之间来一个读就会没有15～18
先改库，再删缓存UPDATE → 提交 → DEL很难：要缓存正好空着、读又比写慢没有0
先改库，再改缓存UPDATE → 提交 → SET 新值两人同时改、SET 乱序时会没人读的商品也要算一遍新值0（人为乱序时卡住）
延迟双删DEL → UPDATE → 提交 → 等 N ms → 再 DEL读的停顿短于 N 时不会写请求多等 N ms，N 靠估0
订阅 binlog 删业务代码只改库；一个伪装成从库的程序读 binlog，看到改动就 DEL和“先改库再删”一样多一个组件要运维；延迟多几毫秒到几百毫秒提交后 0.7～1.7 ms 删掉
Read / Write-Through、Write-Behind缓存层替你读写数据库，应用只跟缓存打交道由缓存层保证Redis 不带这个能力，要自己写一层；Write-Behind 宕机会丢写—
强一致：读写加锁改价时锁住 88 号，读也要拿锁不会读要等写，缓存的快就没了—

选择规则：默认先改库、再删缓存，所有缓存都带过期时间兜底；删除必须可靠时，把删交给 binlog 订阅；连几毫秒旧值都不能容忍的数据，比如下单时的价格和库存，干脆不从缓存读。本页学这条主线，延迟双删和版本号回填当作补丁来学。

④核心取舍：两个系统，没有共同的提交点

所有写法都在同一个约束下做选择：改库和动缓存是两次独立的写，中间总有空隙，空隙里可能插进来一个读请求。

先知道这些
  • 读路径（Cache-Aside）：GET 没命中 → SELECT → SET 回 Redis，带 30 分钟过期。就是全景第 2～7 站。
  • 事务提交前，新值只有改它的那条连接看得见，别的连接 SELECT 拿到的还是旧值（MVCC）。
  • binlog 在事务提交时才写进去，没提交、回滚了的改动不会出现在 binlog 里（redo、undo、binlog 与两阶段提交）。
  • 从库比主库晚一点，刚提交的新值在从库上可能还读不到（主从复制与复制延迟）。

数据库提交 ≠ 缓存更新：两次写之间的空隙消不掉

MySQL 的事务管不到 Redis，Redis 的 MULTI 也管不到 MySQL。想让两边一起提交，只能上两阶段提交这类分布式事务，或者让读等写，代价都比“旧几毫秒”大得多。所以设计目标退一步，变成三条：空隙尽量短；空隙里的读不要把旧值写回去；空隙后面那一步（删缓存）丢了也有人补。

④-1为什么删，不改

改：SET 新值两人同时改价

  • SET 的结果由“谁最后到”决定，和数据库里谁最后提交没关系。
  • 改价后没人看的商品，也白白算了一遍新值。

删：DEL同样的先后

  • 删几次、谁先谁后，结果都是“没有”：DEL 是幂等的，和顺序无关。
  • 新值留给下一个读请求去数据库拿，只有一个来源。

决定胜负的约束：写路径之间没法保证到达 Redis 的顺序。删把“排序”这件事交还给数据库：缓存里只要不存东西，读到的就是数据库按行锁排好序的最终结果。Facebook 在 2013 年的 memcache 论文里给的理由也是这一条：选择删而不是改，因为删是幂等的。

④-2为什么先改库，再删缓存

决定胜负的约束：读一次库比写一次库快得多（写要等行锁、提交时刷 redo 和 binlog）。先删缓存，等于给最快的那个操作留了最长的窗口；先改库，要求读比写还慢，概率小了几个数量级。不是不可能，下面的推演台第三个场景就是它。

④-4订阅 binlog：让“删”不会丢

前面几种写法都假设 DEL 一定会执行。可改完库、还没删，进程就被发布系统重启了，或者 Redis 那一下超时了，旧价就留下来了。还有些写入口根本不经过商品服务：运营直接跑的 SQL 脚本、别的服务改的同一张表。这时把“删”从业务代码里拿出来，交给一个读 binlog 的程序。

为什么它和“删”是一对：订阅者为了不丢，挂了以后会从上次记下的位置重读，同一个改动可能处理两次（至少一次）。如果动作是 SET 新值，重复和乱序都会出错；动作是 DEL，重复删、乱序删都没影响。它解决的是“删会不会丢”，不解决 ④-2 那个慢读回填：删除发生在提交后约 1 ms，比业务代码自己删还早，慢读照样能在它后面写回旧值（⑤ 里实测了）。

写运营后台：先改库，提交后再删
@Transactional
public void changePrice(long id, BigDecimal price) {
    productMapper.updatePrice(id, price);
    // 不能在这里直接删：事务还没提交，等于“先删后改”
    TransactionSynchronizationManager.registerSynchronization(
        new TransactionSynchronization() {
            @Override public void afterCommit() {
                redis.del("product:" + id);   // 失败要重试
            }
        });
}

⑥反例和误用：名字叫“先改库后删”，做出来不是

第一圈 · 注意事项每条都能从 ④ 推出来，点右边的标记跳回去
坑 1在 @Transactional 方法里直接删缓存← ④-2 先删的窗口
现象
代码顺序写的是“先 update 再 del”，线上却和“先删后改”一样频繁卡住。
根源
事务要等方法返回才提交，方法里的 DEL 其实发生在提交之前。
做法
放进 afterCommit()，或者用 @TransactionalEventListener（默认就是提交后执行）。
坑 2改完库把缓存 SET 成新值← ④-1 删不改
现象
两个运营前后脚改价，库里 329，缓存里 359。
根源
数据库按行锁排了先后，到达 Redis 的顺序没人排。
做法
写路径只 DEL。确实要预热，就在 DEL 之后让读路径去重建。
坑 3DEL 失败了没人管← ④ 没有共同提交点
现象
某次发布后零星几个商品卖旧价，半小时后自己好了。
根源
库已经提交，DEL 超时或者进程正好被重启，两次写只成功了一次。
做法
失败进重试队列（Redis Stream、MQ）；更省心的是统一交给 binlog 订阅删；过期时间是最后一道兜底，不能省。
坑 4回填时读的是从库← ④-2 读比写慢
现象
先改库再删也照样卡住，而且比平时频繁得多。
根源
主库提交、DEL 都做完了，从库还没追上；读请求没命中，从从库读到 399 写了回去。复制延迟把“读比写慢”从小概率变成了常态。
做法
回填缓存的那次查询走主库；或者延迟双删，等待时间要大于复制延迟（复制延迟那页量过它能有多大）。
坑 5延迟双删的 sleep 写在请求线程里← ④-3 推演台 ③
现象
改价接口每次都慢 500 ms；有时等了也没用，照样卡住。
根源
第二刀要晚于最慢那次回填，这个时长只能估：估短了没用（实测读停 150 ms、等 100 ms 时卡住），估长了接口变慢。
做法
第二次删放进延迟队列异步执行；它是概率上的补丁，别当成保证。
坑 6缓存不设过期时间← ④ 兜底
现象
一个商品的旧价卖了三天，直到有人手动删 key。
根源
上面任何一种竞态都可能留下旧值；没有过期时间，它就永远留着。
做法
所有缓存都带过期时间，再加随机抖动，防止同时过期（缓存雪崩）。
第二圈 · 使用规范
写路径只删不改，删在提交之后

Spring 里用 afterCommit 或 @TransactionalEventListener。

坑 1、坑 2

每个缓存 key 都有过期时间，加随机抖动

比如 1800 + rnd(300) 秒。

坑 6，以及缓存雪崩

一张表的缓存只由一个地方负责删

要么业务代码删，要么 binlog 订阅统一删，别两边各删一套、出了事互相以为对方删了。

坑 3，以及 SQL 脚本改表后没人删

回填缓存的查询走主库

读从库的只能是“不往缓存里写”的查询。

坑 4

钱和库存不信缓存

详情页可以旧几毫秒；下单算钱、扣库存按数据库里的值来。

缓存旧值直接变成资损

缓存值里带上版本号或更新时间

像 359.00|v9 这样，排查时一眼看出 Redis 里是哪一次的值，也给版本号回填留了口子。

排查“到底旧了多久”时无从下手

第三圈 · 深处

把慢读回填彻底堵上：墓碑 + 版本号

写路径不 DEL，而是写一个带新版本号的墓碑 #|v9（60 秒过期）；读路径回填时用 Lua 比版本，比缓存里旧就不写。比较和写入在 Redis 里一次做完，中间插不进别的命令。

local cur = redis.call('GET', KEYS[1])
if cur then
  local v = tonumber(string.match(cur, '|v(%d+)$'))
  local tomb = string.sub(cur, 1, 1) == '#'
  local mine = tonumber(ARGV[2])
  if v and ((tomb and v > mine) or ((not tomb) and v >= mine))
  then return 0 end
end
redis.call('SET', KEYS[1], ARGV[1], 'EX', ARGV[3]) return 1

Facebook 的 memcache 用的是同一个思路，叫 lease：没命中时发一个令牌，期间来一次删除就让令牌作废，拿着作废令牌的回填被拒绝。代价是读写都要多带一个版本号，墓碑过期后的极端慢读仍然拦不住。多数业务用不着，详情页价格这种“旧几毫秒没关系”的更用不着。

binlog 订阅在生产上要多管的几件事

  • 格式：要 ROW 格式的 binlog 才拿得到行的前后值。MySQL 5.7.7 起默认就是 ROW；Debezium 还要求 binlog_row_image=FULL（也是默认值）。
  • 位点：订阅者记下读到的文件和位置（或 GTID），重启后从那里接着读。所以是“至少一次”，配上幂等的 DEL 正好。
  • 延迟：本机直连实测提交后 0.7～1.7 ms 删掉。生产上常见的链路是 Canal 或 Debezium → Kafka → 消费者删缓存，多了两跳，延迟按几十到几百毫秒估（估算，没有实测），离 1 秒的标准还有余量，但要监控它。
  • 顺序：同一个 key 的删除乱序没关系；要是想顺手做别的事（比如发改价通知），就得按主键分区保证顺序。

为什么不追求强一致

要让任何时刻读到的都是新价，只有两条路：读写互斥（改价时读请求要等），或者 Redis 和 MySQL 做两阶段提交。前者让每个读都可能被一次写卡住，后者 Redis 根本不支持。缓存的意义就是用“可能旧一点”换“快很多”，所以合理的目标是“最终一致，而且窗口有上限”：先改后删管住常态，binlog 订阅管住丢删，过期时间管住剩下的所有意外。

1 秒的预算花在哪

靶场标准是改价后 1 秒内都卖新价。Redis 这一层花掉的是“提交 → DEL”：业务代码删 1～3 ms，binlog 直连 1～2 ms，经过 Kafka 按几百毫秒估。剩下的预算要留给第 11 站：4 个实例的 Caffeine 本地缓存还没动，它们只靠 Pub/Sub 广播失效，全景里实测 11～26 ms 跟上。这是下一个知识点“多级缓存”要讲的。

版本说明：TransactionSynchronization 从 Spring 5.3 起是带默认方法的接口，可以直接 new 匿名类只重写 afterCommit；5.2 及以前要继承 TransactionSynchronizationAdapter（5.3 起已标记废弃）。

↺回到⑤：把靶场里的写路径改好

1 · 删失败要重试

在 updateDelete() 里让 DEL 有 30% 概率抛异常（模拟超时），先看卡住几轮；再加一个重试队列（失败的 key 放进 List，后台线程每 100 ms 重删），再跑。

用到：坑 3

2 · 读从库

照 复制延迟那页的实验加一个从库，让读线程回填时查从库，看 ② 先改库再删还卡不卡；再把回填改回主库，或换成延迟双删。

用到：坑 4、规范“回填走主库”

3 · 只留 binlog 删

把业务代码里的 DEL 全部去掉，只靠 binlog 组里的订阅者删，再跑第一组；再用 docker exec 直接执行一条 UPDATE，看缓存有没有被删。

用到：④-4、规范“一个地方负责删”

1. 用一句话说出这页的精华。

数据库和 Redis 没法一起提交，缓存一定会短暂地旧；设计目标是窗口短、旧值不被写回去、删除丢了有兜底，所以“先改库，提交后删缓存，删不是改，带过期时间，删除要可靠就订阅 binlog”。

2. 只靠过期时间，痛在哪？

过期时间长，旧价能卖到过期为止（30 分钟）；过期时间短，命中率掉下来，缓存失去意义。两头都不行，所以写路径得主动去让缓存失效。

3. “先删缓存再改库”为什么几乎每轮都卡住？根源是哪条原理？

④-2：删除到提交之间是整个写事务（几毫秒），这段时间里新值没提交、别人读不到（MVCC），任何一次没命中的读都会从库里读到旧值再写回去。读比写快得多，所以几乎必中。

4. 预测：把回填缓存的查询从主库改成从库，复制延迟 200 ms，“先改库再删”会怎样？延迟双删要等多久？

会频繁卡住：DEL 之后的第一个读从从库拿到 399 写回去，概率不再取决于“读停顿”，而是取决于这 200 ms 里有没有读请求。延迟双删的等待要明显大于复制延迟加一次读的耗时，比如 500 ms 以上，而且要异步做。从 ④-2 “读比写慢”这个条件推出来：复制延迟让读系统性地比写慢。

5. 预测：订阅 binlog 删缓存以后，还要不要在业务代码里删？如果两边都删会怎样？

可以不删。两边都删不会出错（DEL 幂等），只是多一次网络往返；麻烦在维护上：哪天有人只改了一边，另一边以为对方会删。规范是一张表只由一个地方负责。至于慢读回填，两边都删也堵不住，因为两次删除都早于那次慢回填（④-4）。

6. 放回全景：第 9、10 站前后各发生了什么？这一页讲的东西坏了，整条链路会怎样？

前面是第 1～8 站的读：Caffeine 没命中 → Redis 没命中 → 布隆过滤器 → 重建锁 → 查库 → 回填 Redis 和本地。第 9 站运营改库提交，第 10 站删 Redis，第 11 站 Pub/Sub 广播让 4 个实例作废本地那份。第 10 站坏了（顺序反了、删失败、改成了 SET），Redis 里留下 399，第 11 站广播之后各实例本地作废、再来读 Redis，又把 399 拿回本地。也就是说，第 11 站做得再好也救不了第 10 站，整条链路卖 399 直到 Redis 过期。

标准档。实测 的数字来自本机：2 核 ARM，JDK 17.0.21（--release 8），Lettuce 6.8.2，Connector/J 9.7.0，mysql-binlog-connector-java 0.31.0，Docker 里的 redis:8.10.3-alpine 和 mysql:8.4（8.4.13，默认配置）；第一组完整跑了两遍，两遍的数字都列出来了。生产链路（Canal / Debezium 经 Kafka）的延迟是估算。Spring 的 afterCommit 和 @TransactionalEventListener 来自 Spring Framework 参考文档；“删而不改，因为删是幂等的”和 lease 来自 Nishtala 等，Scaling Memcache at Facebook，NSDI 2013；binlog 格式要求来自 MySQL 8.4 参考手册和 Debezium MySQL 连接器文档。
