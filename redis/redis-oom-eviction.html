第 617 个商品写不进去：Redis 写满以后的 OOM、淘汰与过期

Redis 写满以后不会“变慢”，而是把命令分成两类：读和删照常执行，带 DENYOOM 标志的写（SET、SET NX、INCR、BF.ADD）一律拒绝。noeviction 下，全景第 5 站的锁和第 7 站的回填一起失败。换成会淘汰的策略，写是进得去了，可淘汰只看“多久没用、用得多不多、还剩多久过期”，不管这个 key 是不是一把正被人拿着的锁。还有，key 过期了不等于腾出了地方，要等后台扫到才真删。

下一圈第一圈讲了过期时间存在哪、定时 / 惰性 / 定期三种删法、八种淘汰策略、近似 LRU 的抽样和候选池、LFU 的对数计数，这里都只一两句带过。这一圈只盯一个时刻：交易靶场的 Redis 写满了。这时全景第 2～7 站每一站各看到什么，哪些命令照常、哪些被拒，淘汰会赶走谁，过期的 key 又是什么时候才真正腾出地方。数字都来自 Redis 8.10.3 上的实测。

①为什么需要：内存有上限，缓存却只进不出

全景里有两处在管内存。第 3 站主线程查字典，碰到一个已经过期的 key，要当场删掉、当它不存在；第 12 站在后台，每秒 10 轮检查带过期时间的 key，内存一到 maxmemory 就按策略淘汰。这两站要解决的是：缓存每次没命中都要往里回填，可机器内存是有限的。过期的 key 要真删掉，满了要有人让位。

②没有它会怎样：不设上限，或者设了不让位

“它”指的是上限加让位规则。两样各缺一样，靶场里就是下面两种结局。全景第 12 站提醒过的那个坑，就是右边这种：maxmemory 配了，策略还是默认的 noeviction。

不设 maxmemory（默认 0）

64 位系统上就是不设上限。缓存只进不出（只靠过期删），大促前预热一批商品，内存一路涨到机器的物理内存，结局是 Linux 的 OOM killer 把 Redis 进程杀掉，或者开始用交换分区，每条命令都慢上百倍。

第 3 站以后的所有站都跟着停。第一圈页的“常踩的坑”第一条。

设了 2mb，策略还是 noeviction 实测

回填 1 万个商品：前 616 个进去了，第 617 个起全部失败，9383 次 OOM，evicted_keys 是 0。之后 20 个请求同时查一个没缓存的商品：

  • 代码不降级：20 个请求全部报错，用户看到 500。
  • 代码降级（Redis 报错就直接查库）：20 个请求都拿到了详情，数据库被查了 20 次。没满的时候只查 1 次。

读照样命中，已经缓存的 616 个商品不受影响。出事的是没缓存的那些：要么报错，要么全落到库上。

不懂这一点时的典型误用以为“Redis 满了就是变慢，大不了缓存不进去，读库就是了”，于是只配了 maxmemory。实际情况是重建锁先抢不到（第 5 站的 SET NX 也是写），挡击穿的那道防线跟着失效：每个没命中的请求都会去查库。

③相邻方案：写满时让谁走

第一圈列过八种淘汰策略。放到靶场里试：先把 88 号读热（读 200 次），手里拿着一把锁 lock:product:20001（PX 10 分钟，模拟另一个请求正在重建），然后回填 1～10000 号，每回填 10 个读一次 88 号。

实测 Redis 8.10.3，maxmemory 2mb，每种策略各回填一遍约 29 秒。volatile-lru 只在带过期时间的 key 里挑，这里商品和锁都带 TTL，所以和 allkeys-lru 差不多。

怎么读这张表

  • noeviction 留下的是最早的 646 个，后面的一个也进不去。
  • LRU 留下的几乎都是最近写的，最早的全被赶走。
  • LFU 最近写的只剩 445 个，另外两百来个散在中间。新 key 的计数都从 5 起，大家一样“不常用”，挑谁差不多是随机的。
  • 88 号一直有人读，三种策略都留下了它。
  • 锁：三种会淘汰的策略都把它赶走了。

选择规则

  • 这个实例只放缓存（丢了能从库里重建）：allkeys-lfu，热点不明显就用 allkeys-lru。
  • 实例里还有丢不得的 key（锁、计数、限流令牌、会话）：不要和缓存混放。这些 key 放进单独的 noeviction 实例；实在要混放，也别指望 volatile-* 护住它们，锁本身就带 TTL。
  • 应用侧：Redis 写失败要能区分 OOM 和超时，降级查库要有限流（⑥ 第一圈第 2 条）。

本页往下讲：Redis 是怎么判断“满了”、怎么决定拒谁、淘汰谁，以及过期的 key 什么时候真走。

④原理：每条命令进门前，先看一眼内存

先知道这些
  • used_memory：Redis 通过分配器（jemalloc）记下的已分配字节数，INFO memory 里能看到。maxmemory 拿来比的就是它（扣掉少数几项，见 ⑥ 第三圈）。空库也有一千多 KB：字典、共享对象、各种缓冲。
  • 命令标志：每个命令在 src/commands/*.json 里登记了几个标志。SET 是 WRITE, DENYOOM；GET 是 READONLY, FAST；DEL 只有 WRITE；EXPIRE 是 WRITE, FAST。DENYOOM 的意思是“这条命令可能让内存变多，满了就别执行”。
  • 三种删法、八种策略、近似 LRU、LFU 计数：第一圈讲过，见 Redis 过期删除与内存淘汰。

一条命令进门：先淘汰，再决定拒不拒

带 DENYOOM：满了就拒

SETSET NX PXSETEXINCRHSETLPUSHBF.ADDBF.MADD

全景里第 5 站抢锁、第 7 站回填、上架时往布隆过滤器加 id，都在这一边。

不带：满了照样执行

GETEXISTSDELUNLINKEXPIRECONFIG SETEVAL（本身）

读不会让内存变多；DEL、EXPIRE 只会让内存变少或不变；CONFIG SET 留着让你改策略、调大上限来救场。

Lua 脚本：看的是里面那一条

EVAL 本身不带 DENYOOM。没写 shebang 的老式脚本（第 7 站解锁那段就是）会放进门，执行到 redis.call 的那一条命令时再检查：这条带 DENYOOM、执行前内存已经超了、脚本还没写过东西，三条都满足才报 OOM。解锁脚本里只有 GET 和 DEL，所以满了也能解锁（⑤ 实测）。写了 #!lua shebang 的脚本，没声明 no-writes 也没声明 allow-oom，满了在入口就被拒。

为什么这样设计

Redis：每条命令进门前就地淘汰，按命令拒选中的设计

放弃的做法：后台慢慢清，写照常进或者满了整个实例只读

决定胜负的约束有三条。第一，maxmemory 是硬上限，超出只能是一点点，所以淘汰必须发生在写之前、在同一个线程里。第二，主线程不能被淘汰卡住太久，所以限时 500 µs，剩下的交给后台。第三，Redis 不知道每个 key 是干什么的，只知道命令会不会让内存变多。所以它按命令拒，淘汰时也只能看空闲时间、访问频率和 TTL，不认得哪个 key 是锁。

过期的 key 什么时候真走

两条路合起来，会有一段时间差：key 到点了，可还没人读它，后台也还没扫到它。这段时间里它照样占着内存。performEvictions 也不会先挑已过期的 key 来删，它们只是和别的 key 一起被抽样。所以在 noeviction 下，内存被一堆已过期的 key 占满时，写入照样报 OOM，直到后台把它们扫掉（⑤ 第三段实测）。

最少的命令

CONFIG SET maxmemory 2mb                    # 0 = 不设上限（64 位默认）
CONFIG SET maxmemory-policy allkeys-lfu     # 默认 noeviction
INFO memory      # used_memory、maxmemory、mem_not_counted_for_evict
INFO stats       # evicted_keys、expired_keys、expired_stale_perc、expired_time_cap_reached_count

OBJECT FREQ product:88       # LFU 计数（LFU 策略下才能用）
OBJECT IDLETIME product:88   # 空闲秒数（LRU 策略下）

    第一圈 · 注意事项：不知道就会出事故

    1配了 maxmemory，没改策略，全站写入 OOM← ④ 按命令拒
    现象
    读都正常，凡是没缓存的商品详情全部 500；日志里是 RedisCommandExecutionException: OOM command not allowed …。实测：第 617 个起 9383 次 OOM，evicted_keys 0
    根源
    maxmemory-policy 默认 noeviction，淘汰直接返回失败，带 DENYOOM 的 SET NX（第 5 站）、SET（第 7 站）都被拒。
    做法
    纯缓存实例改成 allkeys-lfu 或 allkeys-lru，写进配置文件；监控 errorstat_OOM，有一次就报警。
    2降级写法把 OOM 变成打库← ⑤ 实测
    现象
    代码里“Redis 写报错就直接查库”，页面不报错了，数据库 QPS 翻了几十倍。实测：20 个并发请求，查库 20 次；正常是 1 次
    根源
    抢锁本身就是一条写，满了锁也抢不到，挡击穿的那道防线失效（88 号过期那一刻）。
    做法
    降级时在本机合并同一个 key 的加载：第 1 站的 Caffeine 用 cache.get(key, loader)，同一个 key 一台机器只查一次；再给降级路径加限流。区分 OOM 和超时：OOM 是配置问题，要报警，不该只是悄悄降级。
    3锁被淘汰，两个线程一起重建← ④ 淘汰不认得锁
    现象
    缓存实例开了 allkeys-lfu，偶尔看到同一个商品在同一秒被查库两次，日志里两个线程都“抢到了锁”。实测：三种淘汰策略都把拿着的 lock:product:20001 赶走了
    根源
    淘汰只看空闲时间、访问频率、TTL。LFU 下新写的 key 计数从 5 起，刚写进去的锁和一个冷门商品一样“不常用”；锁带着 TTL，volatile-* 也会挑它。
    做法
    锁放进单独的 noeviction 实例；重建结果用版本号或 fencing token 写回（锁过期时 A 还在查库），锁丢了也不会写错。
    4key 都过期了，还是写不进去← ④ 两条删除路的时间差
    现象
    一批活动商品 TTL 一样，整点一起到期，到期之后那几百毫秒照样 OOM。实测：第一批到期 225 ms 后只删了 3 个，约 0.3 s 后才恢复写入
    根源
    没人读的过期 key 要等主动过期扫到；淘汰也不会先挑过期的。noeviction 下这段时间差就是 OOM 窗口。
    做法
    缓存实例不用 noeviction；TTL 加随机数（第 7 站已经做了）；别让内存贴着上限跑，常态留 20% 以上余量。
    5maxmemory 设成“数据量”，实例一开就满← ① 空库 1386 KB
    现象
    按“100 万个商品 × 838 字节 ≈ 800 MB”配了 maxmemory 800mb，上线没多久开始淘汰。
    根源
    maxmemory 比的是整个 used_memory：Redis 自身、普通客户端的输入输出缓冲、复制 backlog 都算在里面。只扣两三项：从库输出缓冲超出 backlog 的部分、AOF 缓冲（mem_not_counted_for_evict）。
    做法
    先按数据量估（648 字节的详情占 805 字节），再加 20%～30%；客户端多、有大查询的，用 maxmemory-clients（默认 0，不限）给连接缓冲单独设上限。maxmemory 本身别超过机器内存的 60%～75%，fork 做持久化时还要写时复制。
    6开了 LFU，刚回填的 key 先被赶走← ③ 表里 LFU 那一行
    现象
    满载时，刚重建好的商品没过几秒又没了，再走一次第 5～7 站。实测：最近 1000 个 LRU 留 633 个，LFU 只留 445 个
    根源
    新 key 计数从 5 起，淘汰池按 255 − 计数排；老的热 key 计数高，新 key 和冷 key 一样排在前面。这是 LFU 的本意：热 key 不被一次性的新数据冲掉。
    做法
    长尾商品多、热点明显就接受它；如果新回填的 key 很快会被反复读（比如刚上架的活动商品），用 allkeys-lru 或预热时多读几次。

    第二圈 · 使用规范：团队里怎么配、怎么写

    一个实例一种用途

    缓存实例：maxmemory + allkeys-lfu；锁、计数、限流、会话：单独的 noeviction 实例。防的是 ⑥-1 和 ⑥-3。

    配置写进文件，启动后核对

    CONFIG GET maxmemory* 写进上线检查单。防的是“测试环境改过、生产没改”。

    四个指标进监控

    used_memory / maxmemory、evicted_keys 的速率、errorstat_OOM、expired_stale_perc（过期但没删的估计比例）。防的是 ⑥-1、⑥-4 发生了没人知道。

    Redis 写失败要分类

    OOM 报警加限流降级，超时走重试或熔断。防的是 ⑥-2。

    写缓存一律带 TTL，加随机数

    改值时用 SET … KEEPTTL 或重新带上 TTL。防的是 key 永不过期越积越多（第一圈页的坑）和整点集中到期（⑥-4）。

    新脚本写 shebang 并标 flags

    只读脚本写 #!lua flags=no-writes，满了也能跑；会写的脚本不加 allow-oom。防的是脚本在内存满时写了一半。

    第三圈 · 深处：淘汰卡不卡主线程、过期扫得够不够快

    淘汰的时间预算：500 µs，然后交给后台

    maxmemory-eviction-tenacity 默认 10，时间上限是 50 µs × 10 = 500 µs；11～99 按 500 × 1.15(t−10) µs 增长，100 不限时。每淘汰 16 个 key 才看一次表。超时后返回 EVICT_RUNNING：这条写照样执行，同时注册一个定时任务在事件循环里接着淘汰。所以 used_memory 会短暂超过上限，写入速度一直快过淘汰速度时，超出的部分会越来越多，这时可以调大 tenacity，代价是写命令的延迟变高。

    主线程释放大 key 的代价

    淘汰、过期删掉一个 200 KB 的大 key，默认在主线程里一个个释放元素。lazyfree-lazy-eviction、lazyfree-lazy-expire 打开后交给后台线程释放。8.10.3 和 7.2 的默认值都是 no（实测 CONFIG GET lazyfree*，源码对照两个版本的 config.c）。打开 lazyfree-lazy-expire 后，传给 AOF 和从库的也从 DEL 变成 UNLINK。

    主动过期：扫，不是抽

    7.x 起 activeExpireCycle 用游标顺序扫 expires 的桶（7.2 是 dictScan，8.x 是 kvstoreScan），每轮看 20 个，过期比例超过 10% 再来一轮，慢周期最多 25% CPU。active-expire-effort 调到 N，这三个数变成 20 + 5(N−1)、10 − (N−1)%、25 + 2(N−1)%。expired_time_cap_reached_count 一直涨，说明慢周期每次都用满了时间还没扫完。

    快周期的一个 bug，8.10.1 修了

    每次进事件循环前的“快周期”（最多 1 ms）本该在过期比例偏高时触发。7.2 里拿 0～1 的小数和整数 10 比，条件永远成立不了，快周期实际只在上一轮慢周期超时时才跑。8.10.1 的发行说明：#15412 Unit mismatch disables the FAST expire cycle stale trigger。⑤ 第三段用的 8.10.3 已经修过。

    这一层没有尽头

    • allkeys-lrm（8.6）放到商品缓存上：读多写少的详情，按“最近修改”淘汰会不会比 LRU 更合适
    • 从库上的过期和淘汰：replica-ignore-maxmemory 默认开，从库内存比主库大时怎么办；读从库时第 3 站看到的是什么
    • 内存碎片：大量淘汰和改价以后 mem_fragmentation_ratio 升高，activedefrag 的代价
    • 集群里每个分片各算各的 maxmemory：热 key 所在分片先满（主从、哨兵与集群）
    • Caffeine 的 W-TinyLFU 和 Redis 的 LFU 比一比：第 1 站和第 3 站各用一套淘汰，热点判断会不会打架

    ↺回到第⑤步：改一改交易靶场

    1. 锁搬家（⑥-3）：ProductCache 的锁改用第二个 Redis 实例（noeviction），缓存实例用 allkeys-lfu。重跑 policy，锁还会丢吗？OOM 又会出现在哪个实例上？
    2. 降级加单飞（⑥-2）：在降级分支前加一层 ConcurrentHashMap<Long, CompletableFuture<String>>，同一个 id 只让一个线程查库。重跑 oom，“内存满了，降级”那一行查库变成几次？
    3. 过期窗口（⑥-4）：expire 段加一行 CONFIG SET active-expire-effort 10，先猜 OOM 窗口变长还是变短，再跑，顺便看 expired_time_cap_reached_count。
    1. 用一句话说出这一页的精华

    Redis 写满后按命令拒：读、删、改配置照常，带 DENYOOM 的写被拒；会淘汰的策略能让写继续，但淘汰不认得锁；过期了的 key 要等后台扫到才腾出地方。

    2. 只配 maxmemory 不改策略，为什么挡击穿的锁也失效了？

    ④：抢锁用的 SET NX PX 也是 SET，带 DENYOOM。noeviction 下淘汰直接失败，这条写被拒，锁抢不到。代码不降级就报错，降级就每个请求各查一次库。

    3. 内存满时，第 7 站的 Lua 解锁会不会也被拒？

    不会。EVAL 本身不带 DENYOOM，没写 shebang 的脚本执行到每条 redis.call 时才检查；里面只有 GET 和 DEL，都不带 DENYOOM（⑤ 实测解锁成功）。如果脚本里有 SET，那一条会报 OOM。

    4. 预测：把策略改成 volatile-lru，但缓存都没设 TTL，只有锁带 TTL。写满以后会怎样？

    ④：volatile-* 只从带 TTL 的 key 里挑。能挑的只有锁，锁被一把把赶走；锁也没了以后淘汰不动，返回 EVICT_FAIL，带 DENYOOM 的写开始 OOM，和 noeviction 一样，还多赔了锁。

    5. 预测：写入速度一直比淘汰快（比如批量导入），used_memory 会停在 maxmemory 吗？

    不会，会持续超出。每条命令前最多淘汰 500 µs，超时就返回 EVICT_RUNNING，命令照样执行，剩下的交给后台定时任务。写得比淘得快，超出部分就越积越多；只有淘汰彻底失败（没东西可淘）才开始拒写。调大 maxmemory-eviction-tenacity 能多淘一点，代价是每条写更慢。

    6. 放回全景：第 3、12 站前后各发生了什么？这一页讲的东西出问题，整条链路会怎样？

    第 2 站 Lettuce 把 GET product:88 发过来，第 3 站主线程查字典，到期就当场删（惰性），没有就回 nil，接着第 4 站问布隆过滤器、第 5 站抢锁、第 6 站查库、第 7 站回填；第 12 站一直在后台扫过期、到上限就淘汰。这一页出问题有三种结局：noeviction 写满，第 5、7 站一起 OOM，请求要么报错要么全打到第 6 站的库；淘汰赶走了锁，第 5 站的防线漏了，同一个商品被重建两次；过期 key 没扫完，刚到期那一阵照样 OOM。
