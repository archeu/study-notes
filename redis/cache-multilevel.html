4 台机器各存一份 88 号：Caffeine 加 Redis 两级缓存

88 号商品每秒被读几千次，放在每个实例的 JVM 里，一次读只要几微秒。难的不是多存一份，是改价时让这份作废：Redis 那一份删一次就没了；4 个 JVM 里的 4 份，Redis 管不着，只能发消息让各实例自己删。消息会丢，所以本地过期时间就是旧价最多能留多久。两级缓存的设计，就是在“消息丢了”和“加载撞上删除”这两个时刻，旧价也留不下来。

①为什么需要：热门商品的读，能不能不出 JVM

在全景第 1、8、11 站，这一步要解决三件事：读 88 号时，先在本实例的 Caffeine 里找（第 1 站）；没有就从 Redis 或数据库拿，拿到后放进本地（第 8 站）；运营改价后，4 个实例本地那份都要作废（第 11 站）。地图给交易靶场定的标准是：改价后 1 秒内，所有实例都卖新价。

挡住读

热门商品的读，绝大多数在 JVM 里答完，不压 Redis 上存 88 号的那一个节点。

跟得上

改价后 1 秒内，4 个实例都卖新价。最怕的是某个实例一直卖旧价、没人知道。

出事有上限

消息丢了、连接断了、加载撞上删除，旧价也只能留一小会儿；本地缓存不能把堆撑爆。

②没有它会怎样：只用一层，或者两层不通气

只用 Redis每次读都出进程

  • 每次读一次网络往返：p50 279 µs，p99 1.26 ms。本地命中是 4 µs。
  • 88 号这个 key 只在 Redis 的一个节点上，几千个 QPS 全压在那一个节点、那一块网卡上，加分片也分不走，一个 key 只在一个分片上（热 key）。
  • 没有“各实例各一份”，改价删一次就干净。

只用 Caffeine没有共用的那一层

  • 每个实例第一次读都要查库；发布重启、扩容新加的实例，一起冷启动，一起打数据库。
  • 改价时 4 份都得删，而且实例之间根本没有通道互相通知。
  • 读最快。适合几乎不变的数据：类目树、配置、字典。

两层都有，但不广播只靠本地过期

  • 全景实测：本地过期 5 秒、不广播，改价后 3.3～4.0 秒才读到新价，这期间旧价被读了 3000 多次。
  • 本地过期设成和 Redis 一样的 30 分钟，旧价就卖 30 分钟。
  • 过期时间越短越新，命中率也越低，两头拉扯。

典型误用：以为“Redis 删了，缓存就干净了”。Redis 删的只是 Redis 那一份；每个 JVM 里的那份，得有人专门去通知。第一层的过期时间也不是随手填的，它是“通知丢了时旧价最多活多久”。

③相邻方案：失效消息谁来发

读路径大家都一样：本地 → Redis → 库。差别全在写路径：本地那份靠谁、怎么通知作废，连接断了怎么办。

Spring 的 CompositeCacheManager 不是两级缓存：它只是按顺序找“哪个 CacheManager 认识这个缓存名”，找到一个就用那一个，不会先查本地再查 Redis。

④原理：读往下找，写往上删，过期兜底

先知道这些
  • Caffeine 是 JVM 里的一个带上限、带过期的 Map；满了按 W-TinyLFU 挑“以后最不会被读”的淘汰。第一圈讲过：MyBatis 缓存与 Caffeine。
  • 改价的写路径是“先改库，提交后删 Redis，删而不改”。为什么这样排，见缓存一致性那页。本页接着它往上走一层。
  • Redis Pub/Sub：PUBLISH 把消息推给此刻订阅了这个频道的连接，返回推给了几个。不存消息，也不重发。

读：本地 → Redis → 库　　写：改库 → 删 Redis → 广播删本地　　兜底：本地短过期

两级缓存就这三行。下面四小节分别回答：为什么广播“删”而不是广播新值，为什么先删 Redis 再广播，为什么一定要用 get(key, loader)，以及消息丢了以后靠什么收场。

④-2为什么广播“删”，再配一个短过期

广播新值，本地长期有效被放弃的设计

  • 消息一丢，旧值没有任何机制收场。
  • 推的是值，就要考虑顺序和版本；推“删”，删几次、谁先谁后结果都是“没有”。

广播删除，本地 5 秒过期本页的做法

  • 新值只有一个来源（库），本地只做副本的副本。
  • 消息丢了，旧价的寿命 = 本地过期时间，有上限。

决定胜负的约束：Redis Pub/Sub 是“最多投递一次”，官方文档原话是订阅者断线时，消息 is forever lost。既然通知一定会偶尔丢，设计就得让“丢了”有上限：删比改安全，本地短过期给出上限，断线时主动清空把上限再压低（⑥ 坑 1）。

④-3为什么先删 Redis，再广播

本地那份只从 Redis 或库里来。如果先广播：A 刚把本地删掉，马上来一个读，本地没有，就去 Redis 拿，而 Redis 里还是 399，于是 399 又回到 A 的本地，这条广播白发了。先删 Redis，A 再去拿时 Redis 已经空了，只能查库拿到新价。下面推演台的场景 ③ 能一步一步看到。

④-4为什么一定要用 get(key, loader)

危险的时刻是：实例 A 正在从 Redis 加载 88 号，已经拿到 399，还没放进本地，这时失效消息到了。

getIfPresent，没有再 put先查后放，两步

  • 实测 4 轮：加载结束后旧价又留了 4981～4983 ms，被读了 4600 多次。

get(key, loader)加载在 Caffeine 里面做

  • 实测 10 轮：旧价 0 次被读到；下一次读 2～5 ms 后拿到 359（查库的时间）。

为什么能这样：同步的 Caffeine Cache.get(key, fn) 走的是底层 ConcurrentHashMap.compute，加载函数在这个 key 所在桶的锁里执行；invalidate 也走 compute，要同一把锁，只能等加载结束再删（Caffeine 3.3.1 源码 BoundedLocalCache.doComputeIfAbsent、remove）。代价是监听器线程被卡住了加载那么久，⑥ 坑 3 讲它。Caffeine 的 Javadoc 对“正在加载的 key 被 invalidate”只写了 behavior is undefined，所以这里是“源码如此、本机实测如此”，不是 API 承诺；异步的 AsyncCache 不持桶锁，行为不同。

public TwoLevelCache(String name, RedisClient client, Function<String, String> db,
                     long l1TtlMillis, boolean flushOnReconnect) {
    this.l1 = Caffeine.newBuilder().maximumSize(10_000)
            .expireAfterWrite(l1TtlMillis, TimeUnit.MILLISECONDS).build();
    this.redis = client.connect().sync();
    this.sub = client.connectPubSub();                 // 第 11 站：每个实例单独一条订阅连接
    sub.addListener(new RedisPubSubAdapter<String, String>() {
        @Override public void message(String channel, String key) { l1.invalidate(key); }
        @Override public void subscribed(String channel, long count) {   // 重连后自动补订也会回调
            if (subscribes.incrementAndGet() > 1 && flushOnReconnect) l1.invalidateAll();
        }
    });
    sub.addListener(new RedisConnectionStateListener() {
        @Override public void onRedisDisconnected(RedisChannelHandler<?, ?> c) {
            if (flushOnReconnect) l1.invalidateAll();  // 断了就别再信本地
        }
    });
    sub.sync().subscribe(CHANNEL);
}

public String get(String key) {                        // 第 1 站
    return l1.get(key, k -> {
        String v = redis.get(k);                       // 第 2、3 站
        if (v != null) return v;
        v = db.apply(k);                               // 第 6 站
        redis.setex(k, 1800 + ThreadLocalRandom.current().nextInt(300), v);  // 第 7 站
        return v;                                      // 第 8 站：Caffeine 把它放进本地
    });
}

public static long evict(RedisCommands<String, String> admin, String key) {
    admin.del(key);                                    // 第 10 站
    return admin.publish(CHANNEL, key);                // 第 11 站：返回收到的实例数
}

⑥细节：消息会丢，线程会卡，内存会涨

第一圈 · 注意事项每条都能从 ④ 推出来，点右边的标记跳回去
坑 1订阅连接断了一下，某个实例一直卖旧价← ④-2 最多投递一次
现象
改价后其他实例都对，偏偏一个实例卖旧价，直到本地过期。本机实测：订阅连接被 CLIENT KILL TYPE pubsub 断开后紧接着改价，PUBLISH 返回 0；只靠本地 5 秒过期的实例 4941～4947 ms 后才读到新价，期间旧价被读了 4600 多次（3 轮）。
根源
Pub/Sub 不存消息。Lettuce 会自动重连、自动补订频道（实测补订后 PUBLISH 又返回 2），但断线那会儿的消息不会补发。
做法
断线时（onRedisDisconnected）清空本地，补订确认时（subscribed 回调）再清一次。同样的断线，实测这个实例 0 ms 读到新价，旧价 0 次。别只挂在 onRedisConnected 上：它在 TCP 连上时就回调，比补订早（Lettuce 源码 ConnectionEventTrigger），这中间进来的值照样可能错过消息。
坑 2手写“先查本地，没有再 put”← ④-4 加载在锁里
现象
广播明明收到了，这个实例还是卖了 5 秒旧价。实测 4 轮，每轮加载结束后旧价又留了 4983 ms。
根源
失效消息落在“已经从 Redis 拿到旧值、还没 put”的空当里：删的时候本地是空的，删完它才把旧值放进去。
做法
用 l1.get(key, loader) 或 LoadingCache，让加载和删除抢同一把锁。Spring Cache 的 @Cacheable(sync = true) 在 Caffeine 上走的也是这条路。
坑 3监听器在 IO 线程上被卡住← ④-4 等锁
现象
用了 get(key, loader) 以后，监听器里一次 invalidate 要 197～199 ms（等那次慢加载结束）。10 轮里有 2 轮，写路径的 DEL + PUBLISH 也跟着变成 200 ms。
根源
Lettuce 在它的 Netty IO 线程上回调 message()；IO 线程个数默认跟 CPU 核数走，多条连接共用。监听器卡住，同一个 IO 线程上的其他连接收发也跟着等。哪两条连接分到同一个线程是运气，所以是偶发（按 Lettuce 线程模型推断，没有逐个确认分配）。
做法
监听器里只做 invalidate，别做 IO；加载函数一定要有超时（Lettuce 命令超时配几百毫秒，别用默认 60 秒）；要更稳就把 invalidate 交给一个单独的线程。
坑 4本地存的是可变对象← ④ 本地是副本的副本
现象
某个接口给商品打了个折扣标记返回给前端，结果所有人看到的 88 号都带上了折扣标记。
根源
Caffeine 里存的是对象引用，get 拿到的就是那一个对象，不是拷贝。Redis 不会有这个问题，因为每次 GET 都反序列化出一个新对象。
做法
本地存不可变对象（全 final 字段、record）或者序列化后的字符串；要改就先拷贝。
坑 5本地缓存没有上限，或者上限按条数拍脑袋← ④-6 maximumSize
现象
商品一多，老年代慢慢被占满，Full GC 越来越频繁（接 J03 全景）。
根源
本地缓存就是堆里的一张 Map，存多少堆就占多少。一条 648 字节的 JSON 字符串，里面有中文就按 UTF-16 存，算上对象头和 Caffeine 的节点，估计 1.5 KB 上下；1 万条约 15 MB（估算，没有实测）。
做法
必须配 maximumSize；值大小差得多就用 maximumWeight + weigher 按字节算。recordStats() 打开，把命中率和淘汰数上报监控。
坑 6有人绕过了 evict()← ④ 写往上删
现象
DBA 跑了一个批量改价脚本，Redis 和各实例本地都没动，旧价一直卖到过期。
根源
失效消息只在业务代码的 evict() 里发；不经过它的写，两层都不知道。
做法
失效入口收成一个：订阅 binlog，看到 product 表的改动，统一“删 Redis + 广播”（缓存一致性 ④-4）。
第二圈 · 使用规范
只给读多写少、能容忍秒级旧值的数据上本地缓存

商品详情、类目、配置可以；库存、余额、优惠券剩余量不进本地。下单算钱按数据库里的价格。

本地旧值直接变成资损

本地过期时间远短于 Redis

比如本地 5～60 秒、Redis 30 分钟。本地过期时间写进文档，它就是“消息丢了时旧价的寿命”。

坑 1 时旧价卖半小时

失效顺序固定：改库提交 → 删 Redis → 广播

广播里只放 key，不放值。

第三圈 · 深处

热 key 过期那一刻：refreshAfterWrite

expireAfterWrite 到点就删，下一个读要同步去 Redis 拿。refreshAfterWrite(4s) 配上 expireAfterWrite(5s)：过了 4 秒后的第一次读照样返回旧值，同时在后台重新加载；只有 5 秒内一次都没人读，才真正过期。热门商品的读就不会在过期那一刻卡一下。

要 LoadingCache（build(loader)），否则构建时报错。版本差异要小心：

后台刷新期间，这个 key 被……2.9.3（JDK 8）3.x（JDK 11+）
put 换了新值丢掉刷新结果丢掉刷新结果
invalidate 删掉（失效消息到了）把刷新结果写回去丢掉刷新结果（3.0.6 起确认如此）

也就是说，在 2.9.3 上用 refreshAfterWrite，失效消息要是落在刷新途中，刷新拿到的旧值会被放回去，又是坑 2。出处：两个版本 BoundedLocalCache.refreshIfNeeded 的完成回调。

让 Redis 来发失效消息：CLIENT TRACKING

  • 默认模式：Redis 6 起，客户端开了 tracking，服务端在一张 Invalidation Table 里记下“哪个客户端读过哪个 key”，key 一被改就给这些客户端推失效。表有上限，满了就假装某个 key 被改了，推一条失效腾地方。
  • BCAST 模式：服务端不记谁读过什么，只按前缀登记，比如 product: 下任何 key 改了都推。服务端不占内存，客户端多收一些用不着的消息。
  • 同一条连接上收推送要 RESP3；RESP2 得另开一条连接，用 REDIRECT 转到 __redis__:invalidate 频道。
  • 它也没法替你兜断线：官方文档原话是 Make sure that if the connection is lost, the local cache is flushed. 和坑 1 一个道理。
  • Lettuce 6.0 起有 ClientSideCaching，7.8 起整套标为废弃，说法是 “legacy and incomplete”，新 API 还在设计。生产上先别押在它上面。

消息丢不起：换一种发法

Pub/Sub 加短过期，旧价的上限是“本地过期时间”。要把上限压到 1 秒以下又不想把过期调得很短，有两条路：

  • 可续传的消息：失效消息写进 Redis Stream 或 MQ，每个实例记住读到哪条，断线回来从那里接着读。代价是每个实例一个消费者，多一套位点管理。Redisson 的 ReconnectionStrategy.LOAD 思路相近：留 10 分钟的失效日志，断线短于 10 分钟就按日志补，长了就全清。
  • 版本号对账：Redis 里给每个商品存一个版本号，改价时 INCR；本地每条带上版本，每秒批量 MGET 一次版本号，对不上就作废。不依赖消息，代价是每秒一次批量往返（↺ 练习 2）。

1 秒的预算花在哪

靶场标准是改价后 1 秒内都卖新价。一致性那页算过 Redis 那一层：提交到 DEL，业务代码里删 1～3 ms。本页这一层：PUBLISH 到各实例删完本地，全景实测提交后 6～7 ms 都收到消息，11～26 ms 读到新价。正常路径花掉的不到 3%。

预算真正被吃掉的是异常路径：消息丢了靠本地过期（5 秒，超标），所以坑 1 的“断线即清”不是可选项，它让异常路径也落回毫秒级。剩下没兜住的只有“订阅连接看起来连着、其实早就不通了”，这要靠定期 PING 订阅连接去发现，Redis 文档对客户端缓存也是这么建议的。

3 · 监听器不占 IO 线程

用到：坑 3、④-4

1. 用一句话说出这页的精华。

本地那份 Redis 管不着，只能靠广播删；广播最多投递一次，所以本地过期时间就是旧价的寿命上限，再用“断线即清”和 get(key, loader) 把消息丢失、加载撞上删除这两个时刻也堵上。

2. 只用 Redis、不要本地缓存，痛在哪？

每次读都是一次网络往返（p50 279 µs 对比本地 4 µs），而且热门商品的所有读都压在 Redis 里存它的那一个节点上，加分片也分不走，因为一个 key 只在一个分片上。

3. 订阅断线后某个实例一直卖旧价，根源是哪条原理？

④-2：Redis Pub/Sub 最多投递一次，不存消息，断线期间发的失效消息永远丢了；Lettuce 重连补订频道，但不补消息。所以要断线即清、补订再清，过期时间兜底。

4. 预测：写路径的顺序写成“先 PUBLISH，再 DEL Redis”，而且改价那一刻 88 号正被大量读，会怎样？

某些实例会把旧价重新装回本地：广播先到，本地删了，紧接着的读去 Redis 拿，Redis 还没删，拿到 399 放回本地；之后 DEL 才执行，但不会再有广播。这些实例卖旧价直到本地过期。读越密集，中招的实例越多。从 ④-3 推出：本地只从 Redis 拿，所以 Redis 必须先干净。

5. 预测：把 Caffeine 换成 buildAsync() 的 AsyncCache，坑 2 那种时序还安全吗？

不能再靠桶锁了。AsyncCache 先把一个 future 放进表里就松开锁，加载在别的线程里做；这时来的 invalidate 会直接把这个 future 移走，不会等加载完。要不要把加载结果放回去，取决于 Caffeine 的版本和实现，得查源码或实测确认。从 ④-4 推出：正确性靠的是“加载和删除抢同一把锁”，换掉这个前提，结论就要重新验证。

6. 放回全景：第 1、8、11 站前后各发生了什么？这一页讲的东西坏了，整条链路会怎样？

第 1 站查本地，没有才走第 2～7 站（Redis、布隆过滤器、重建锁、查库、回填 Redis），第 8 站把结果放进本地再返回。改价时第 9 站改库、第 10 站删 Redis，第 11 站广播让 4 个实例删本地。第 11 站坏了（广播丢了、订阅断了、手写 put 撞上失效），Redis 和数据库都是新价，只有个别实例的 JVM 里还是 399，卖到本地过期；如果本地过期设得和 Redis 一样长，就卖 30 分钟。这种“只有一台机器不对”的问题最难查，所以要监控订阅断线次数。

标准档。实测 的数字来自本机：2 核 ARM，JDK 17.0.21（--release 8），Caffeine 2.9.3，Lettuce 6.8.2，Docker 里的 redis:8.10.3-alpine（默认配置）；quick 跑 3 次，gap 3 轮，getIfPresent+put 4 轮，get(key, loader) 10 轮。①② 的 p50 和广播耗时来自全景页的实测。Caffeine 的加载与删除、refresh 的版本差异来自 2.9.3、3.0.6、3.3.1 源码；Lettuce 的重连、补订和 ClientSideCaching 废弃说明来自 6.8.2、7.9.0 源码；Pub/Sub 和客户端缓存的说法来自 redis.io 文档；Redisson、JetCache 的配置项来自各自官方文档。本地缓存内存是估算。
