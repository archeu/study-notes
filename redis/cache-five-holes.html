88 号过期那一刻：缓存穿透、击穿、雪崩与大 key、热 key

缓存挡在数据库前面，会从五个地方漏。五个病其实是一个病：很多请求在同一时刻挤到了同一个地方。穿透和击穿挤到数据库，雪崩挤到数据库的同一秒，热 key 挤到一个 Redis 节点，大 key 挤住一条连接、一个线程。防法也就四类：挡在前面、排队只放一个、打散、允许旧一点，每一类都要拿别的东西去换。

①要解决的问题：88 号不在 Redis 里的时候

在全景第 4、5、7 站，这一步要解决：Redis 没命中以后，怎么不让请求一窝蜂落到 MySQL。查的是根本不存在的商品（第 4 站），热门 key 刚好过期（第 5 站），一批 key 同一秒过期（第 7 站）。在第 1 站要解决：88 号太热，存它的那个 Redis 节点扛不住。第 7 站还埋了一个钩子：详情越堆越长，88 号自己变成大 key。地图给这一站定的过关标准是：讲清热 key 为什么加机器没用。

②不用它会怎样：在交易靶场里把三个洞造出来

同一个 ProductCache，把防线一道道关掉，量数据库被查了几次。数据库用一个查一次睡 2 ms 的函数代替，Redis 8.10.3 在同机容器里。实测

不懂精华时的典型误用：看到“穿透”就加缓存空值，觉得防住了。它防的是“同一个不存在的 id 反复查”，对随机 id 无效（上图第 3 根柱子），反而让 Redis 存满 product:随机数 = ""。挡随机 id，要靠一个回答“一定没有”的结构，也就是布隆过滤器。

③几种流派：每个洞都有好几种堵法

第一圈的十种防护按“怎么让请求不再挤到一处”分成四类。同一个洞，选哪一类，取决于你愿意拿什么去换。

洞挡在前面排队只放一个打散允许旧一点交易靶场选
穿透布隆过滤器；缓存空值；参数校验（id 超出范围直接 404）———布隆 + 参数校验
击穿热 key 永不过期重建锁 SET NX PX；实例内 get(key, loader)—逻辑过期；Caffeine refreshAfterWrite实例内合并 + 重建锁
雪崩本地缓存兜底；熔断、限流重建锁（每个 key 一把）过期时间加随机数；预热错峰—随机过期 + 本地缓存
热 key本地缓存（第 1 站）—复制成多份 product:88#0..7；读从库本地缓存本身就允许旧几秒本地缓存
大 key压缩—拆：按字段存 Hash、按页拆 key—拆，删用 UNLINK

选择规则：先问这份数据能旧多久。能旧几秒，选不让人等的（本地副本、逻辑过期）；不能旧，就排队，接受等待。本页 ⑤ 把布隆、重建锁、随机过期三道防线放进交易靶场，⑥ 再拿逻辑过期、拆热 key、拆大 key 跟它们比。

④核心取舍：同一时刻、同一个地方

五个洞的形状一样：请求本来是分散的，某个原因让它们在同一时刻挤到同一处。看清挤到了哪里、为什么同时，就知道该用哪一类防法。

先知道这些
  • Redis 一个主线程按顺序执行命令，所以 SET NX 天然是原子的，能当锁用：全景第 3 站，Redis 线程模型与 IO 多路复用。
  • 布隆过滤器回答“一定没有”或“可能有”，不会漏判、会误判、删不掉：布隆过滤器与 HyperLogLog。
  • 解锁要先比 token、比和删放进同一段 Lua：Redis 分布式锁。
  • Lettuce 一个实例只开一条连接，所有线程的命令在上面排队、按顺序回：全景第 2 站。

挡在前面

布隆过滤器、缓存空值、参数校验、本地副本。

拿什么换：多维护一份数据。布隆会误判、删不掉，上架要记得加；空值占内存，新上架的商品要等空值过期才查得到。

排队只放一个

重建锁 SET NX PX，实例内 get(key, loader)。

拿什么换：等待。没抢到的人要等抢到的那个查完；锁的过期时间定短了放进第二个，定长了拿锁的人挂掉以后大家多等。

打散

过期时间加随机数，热 key 复制多份，大 key 拆开。

拿什么换：多份就要多份一起改；拆开以后，一次读变多次读。

允许旧一点

逻辑过期，refreshAfterWrite，本地缓存。

拿什么换：一致性。在重建完成之前，人人拿到的都是过期的那份。

为什么这样设计：击穿时，让人等，还是让人拿旧值

重建锁全景第 5 站用的

  • 读到的永远是数据库里的最新值
  • 没抢到的线程干等；查库越慢，等得越久
  • 200 个线程每 10 ms 一个 GET，Redis 也跟着忙

逻辑过期值永不过期，只带一个时间戳

  • 没有人等，延迟和没过期时一样
  • 重建完成前，读到的是过期的那份
  • key 一旦被删掉（改价走第 10 站），手里没旧值可给，又退回击穿

决定胜负的约束：过期那一刻，这份数据还能不能再旧几十毫秒。商品详情能，价格最终以下单时查库为准，所以逻辑过期也站得住；但交易靶场的标准是改价后 1 秒内跟上，改价走第 10 站“删 key”，删掉以后逻辑过期就没有旧值可给了。所以全景选了锁，再用实例内合并把等锁的人从 200 个压到每实例 1 个。

⑤套进场景：交易靶场的 ProductCache

三道防线写进一个方法，每道都能单独关掉，② 那几张图就是关掉它们量出来的。依赖：Lettuce 6.8.2，按 JDK 8 写；Redis 8.10.3。

ProductCache.get第 2～7 站
public String get(long id) {
  String key = "product:" + id;
  String v = redis.get(key);                  // 第 2、3 站
  if (v != null) return v;
  if (!bloomMightContain(id)) return null; // 第 4 站：一定没有

  String lockKey = "lock:" + key;
  String token = UUID.randomUUID().toString();
  while (true) {
    if ("OK".equals(redis.set(lockKey, token,
          SetArgs.Builder.nx().px(3000)))) {   // 第 5 站
      try {
        v = redis.get(key);                   // 再看一眼
        if (v != null) return v;
        return loadAndFill(id, key);         // 第 6、7 站
      } finally {
        redis.eval(UNLOCK_LUA, INTEGER,       // 是自己的锁才删
                   new String[]{lockKey}, token);
      }
    }
    sleep(10);                                // 没抢到：等一会儿
    v = redis.get(key);
    if (v != null) return v;
  }
}

String loadAndFill(long id, String key) {
  String v = db.apply(id);
  if (v == null) return null;
  long ttl = 30 * 60_000L
      + ThreadLocalRandom.current().nextLong(5 * 60_000L + 1);
  redis.set(key, v, SetArgs.Builder.px(ttl)); // 第 7 站
  return v;
}

⑥反例和误用：防法用错了地方，或者两道防法打了架

第一圈两页的“常踩的坑”讲的是单个防法。这一圈的坑多半出在两件事上：防法没挡住它以为挡住的东西，或者一道防法拆了另一道防法的前提。

第一圈

注意事项：不知道就会出事故

1缓存了空值，随机 id 照样打穿← ④ 挡在前面
现象
有人拿随机 id 扫详情接口，数据库 QPS 不降，Redis 的 key 数却一路涨。实测：新 id 10000 次全落库，多存 2 万个 key
根源
空值只记得见过的 id。挡随机 id 需要一个能回答“一定没有”的东西。
做法
布隆过滤器放在前面；空值只存几十秒；id 超出发号范围直接 404；按来源限流。
2新上架的商品详情页 404← ④ 挡在前面
现象
新品上架，详情页说“商品不存在”；下架的商品，过滤器还说“可能有”。
根源
布隆不漏判，前提是存在的 id 都加进去了；而且它只能加、不能删。
做法
上架流程里先 BF.ADD 再提交商品：先加，误判无害；后加，中间那段会漏判。每天按库重建一份新的再 RENAME 换掉；真要删，用 Redis 8 同样自带的布谷鸟过滤器 CF.ADD / CF.DEL。
3锁比查库先过期← ④ 排队
现象
慢 SQL 要 4 秒，锁 3 秒就没了，第二个线程拿到锁，又去查一遍；数据库越慢，放进来的越多。
根源
“只放一个”靠的是锁还在。锁的过期时间是为拿锁的实例挂掉准备的，不能比正常查库还短。
做法
PX 取查库 p99 的几倍；查库自己设超时，比 PX 短；拿到锁后先再 GET 一次。实验台“慢查询”预设能看到放进来几个。
4等锁的人把 Redis 也打忙了← ④ 排队
现象
击穿那一刻，数据库只查了 1 次，Redis 的命令数却跳了一截。
根源
199 个没抢到的线程每 10 ms 一个 GET，查库 50 ms 就是每轮 1000 多条命令（估算）。排队的代价不只是等。
做法
先在实例内用 Caffeine get(key, loader) 合并，每实例只出一个线程去抢锁；全景第 5 站实测，加了它，每实例同一时刻只剩一个在查。
5随机过期救不了 Redis 整个没了← ④ 打散
现象
Redis 重启、主从切换、maxmemory 满了写不进，所有 key 同一刻“过期”，数据库被打满。
根源
随机数打散的只是“过期时间”。Redis 没了，大家同时没命中，跟过期时间无关。
做法
本地缓存兜底（第 1 站）；数据库前加限流和熔断，宁可一部分请求降级；打开 AOF，重启后缓存还在（全景第 12 站）；冷启动先预热热门商品再放流量。
688 号长成大 key← ④ 一条连接
现象
详情塞进了图文 HTML，长到 2 MB：读 88 号的线程变慢，没读 88 号的线程也变慢；删一个大 Hash，所有客户端卡一下。实测：p50 1.03 → 9.01 ms；DEL 190 ms
根源
同一条连接上回复按顺序；同一个主线程上命令按顺序。大的堵住后面所有小的。
做法
图文正文放对象存储或 CDN，Redis 里只存结构化字段；要按字段改的存 Hash；删除一律 UNLINK，或打开 lazyfree-lazy-user-del。
7逻辑过期 + 改价删 key，击穿又回来了← ④ 允许旧一点
现象
88 号改用逻辑过期，平时很稳；一改价，数据库被打了一下。
根源
逻辑过期不让人等，靠的是“手上有旧值可给”。改价走第 10 站删 key，旧值没了，所有人都走同步查库。
做法
用逻辑过期的 key，改价时直接 SET 新值和新时间戳，不删。这又和一致性页“删比改安全”冲突：两次改价并发 SET，后到的可能是旧的，所以要带版本号、用 Lua 比较版本再写。
8热 key 加了机器还是热← ④ 一个节点
现象
集群从 3 主扩到 6 主，存 88 号的那个节点 CPU 还是 100%。
根源
一个 key 只属于一个槽，一个槽只在一个主上。加机器分走的是别的 key。
做法
先上本地缓存（第 1 站，命中只要 4 µs）；还不够，把 88 号复制成 product:88#0～#7 落到不同槽，读时随机挑一份，改价时 8 份一起删。
第二圈

使用规范：团队里该怎么写

过期时间只从一个工具方法拿，里面带随机数

业务代码不出现裸的 EX 1800。

有人手写固定 TTL，一个预热任务塞进去的一批 key 又同一秒过期。

布隆按商品数上限的 2 倍建，误判率 0.1%

BF.ADD 写在上架流程里，先于提交。容量不够时 Redis 会自动加一层，查得更慢、更占内存。

漏加导致 404；容量超了以后越查越慢。

锁封进一个方法，业务不手写 SET NX

token、PX、拿锁后再看一眼、Lua 解锁，一处写对。

忘 token 删了别人的锁，忘过期时间锁永远不放。

String 不超过 10 KB，集合元素不超过 5000

常见团队规范的说法（例如阿里云 Redis 开发规范）；删除一律 UNLINK。

大 key 堵连接、堵主线程。

禁用 KEYS，大集合分批读

用 ACL 收掉 KEYS、FLUSHALL；HGETALL 换成 HSCAN。

一条慢命令把所有客户端堵住，慢日志里还看不出来。

盯四个数

缓存命中率、查库 QPS、Redis 各 key 前缀的命令数、慢日志。大 key 在从库上用 redis-cli --bigkeys / --memkeys 定期扫。

等到数据库报警才知道缓存漏了。

优化和深处

击穿的三种做法，同一场量一次

4 实例 × 50 线程，88 号刚过期，10 轮。实测

做法每轮查库p50读到旧值
没过期（对照）019.2 ms0

本机只有 2 核，200 个线程光排队就 19 ms，所以要和“没过期”比：锁多等了约 30 ms，逻辑过期几乎没多等。裸查的延迟看着不差，是因为假数据库查一次固定 2 ms、不会被挤慢；真 MySQL 会，下面实验台把这一点算进去了。

进程内也有逻辑过期：Caffeine 的 refreshAfterWrite，过了刷新时间，第一次读触发后台重载，期间照样返回旧值。

大 key 为什么拖慢别人

RESP 协议的回复不带请求编号，Lettuce 只能按发出的顺序一个个对号。2 MB 的回复要在 Netty 的 IO 线程上读完、解码完，后面排着的小回复才能交出去。换一条连接，就不受影响。实测

本机回环上，200 KB 的大 key 看不出差别，2 MB 才明显。真实网络更早出事：千兆网卡传 200 KB 要 1.6 ms，2 MB 要 16.8 ms（算出来的），而 Redis 执行一次 GET 才 0.55 µs。

热 key、大 key 怎么找

  • Redis 8.6 起：HOTKEYS。服务端自己数，按 CPU 时间和网络字节各排前 K 名，可以抽样、限定时长。下图是它的真实输出：CPU 第一是 88 号，网络字节第一是那个 200 KB 的大 key，一次把热 key 和大 key 都揪了出来。实测
  • 老办法 redis-cli --hotkeys：要先把淘汰策略改成 LFU，靠 key 上的访问频率计数；默认的 noeviction 下直接报错“An LFU maxmemory policy is not selected”。实测
  • 别用 MONITOR：每条命令都要回传一份，生产上开着会把 Redis 拖慢。
  • 客户端数：在 ProductCache 里按 key 计数、定时上报汇总。好处是能在本地缓存那一层就拦下，坏处是要每个服务都接。

1. 用一句话说出这一页的精华

五个洞都是很多请求在同一时刻挤到了同一处；防法就四类：挡在前面、排队只放一个、打散、允许旧一点，分别拿多维护一份数据、等待、多份一起改、一致性去换。

2. 为什么缓存空值挡不住穿透？

空值只记得见过的 id。攻击者每次换一个随机 id，空值一次都用不上，还让 Redis 多存一个 key。实测新 id 照样 10000 次落库，多存 2 万个 key。挡随机 id 要靠布隆过滤器这种能回答“一定没有”的结构。

从 ④“挡在前面”推出

3. 预测：把练习 1 的锁改成 1 ms，大概会发生什么？

不再是每轮 1 次。查库要 2 ms，锁 1 ms 就没了，这时还在陆续到达的线程能抢到锁；它们再看一眼缓存，回填还没完成，于是也去查库。等回填完成以后到的线程，再看一眼就拿到了。具体几次取决于那 1～2 ms 里到了多少个请求，所以每轮都不一样。

从 ④“排队只放一个”推出：只放一个，靠的是锁还在

4. 预测：Redis 集群从 3 主扩到 6 主，88 号那个节点的 CPU 会降吗？

不会。88 号只属于一个槽，一个槽只在一个主上，加机器分走的是别的 key。要么让读停在第 1 站的本地缓存，要么把 88 号复制成几份，让它们落到不同的槽。

从 ④ 图里“挤的是空间”推出

5. 预测：88 号用了逻辑过期，运营改价，第 10 站照旧 DEL，下一秒 200 个请求来了？

key 被删了，逻辑过期手里没有旧值可给，200 个请求都走“没有值、同步查库”的那条路，击穿回来了。用逻辑过期的 key，改价时要直接 SET 新值和新时间戳，并带版本号防止并发改价时旧值覆盖新值。

从 ④“允许旧一点”的前提推出：旧值必须在手上

6. 放回全景：第 5 站前后各发生了什么？这把锁坏了，比如主从切换时锁丢了，整条链路会怎样？

前面是第 4 站，布隆过滤器说 88 号“可能有”；后面是第 6 站查库、第 7 站回填并用 Lua 解锁。锁丢了，第二个实例也拿到锁，数据库多查一次，两个实例回填的是同一行数据，结果一样。所以重建锁是“省数据库”的锁，不是“保正确”的锁，丢一次只是多查几次库，不值得为它上 RedLock 那样更重的方案。

从 ④“排队只放一个”推出：放进两个，只是多查一次
