88 号的锁有了两个主人：Redis 重启、切主以后丢了什么

Redis 回给你 OK 的那一刻，这条写只在主库内存里，最多再加上操作系统的页缓存。落盘要等后台线程每秒一次的 fsync，到从库要等异步复制。所以“Redis 挂了”要分三种情况看。进程挂了原地拉起：缓存还在，但要先挨一阵 LOADING。机器挂了切到从库：从库没收到的写就丢了，丢的要是一把锁，两个请求会同时以为自己拿着它。主库不持久化又被自动拉起：从库跟着它被清空。

全景：一次商品详情查询 · 第 12 站（牵连第 2、5、7 站）地图：J07 · 持久化与高可用第一圈：RDB 与 AOF · 主从、哨兵与集群

下一圈第一圈讲过 RDB 怎么 fork 拍快照、AOF 的三种刷盘、AOF 重写、混合持久化，以及主从怎么全量和增量同步、哨兵怎么选新主、集群的 16384 个槽，这里都只一两句带过。这一圈只问一个问题：交易靶场的 Redis 挂了以后，第 5 站的锁和第 7 站的缓存还在不在，多久能再读写。数字都来自 Redis 8.10.3 上的实测：20 万个商品（used_memory 163 MB），一主一从。

①为什么需要：内存里的东西，进程一停就没了

全景第 12 站在后台做两件事：把每条写命令（第 5、7、10 站的 SET、DEL）追加进 AOF，每秒 fsync 一次；有从库的话，再把它异步发给从库。这一步要解决的是：Redis 进程或者整台机器没了以后，缓存和锁还能不能接着用，要等多久，以及数据库要多扛多少。

②没有它会怎样：不持久化，或者只有一台

“它”指的是持久化加从库。两样各缺一样，交易靶场里就是下面两种结局。

不持久化（save ""、appendonly no）实测

20 万个商品，docker stop 再 docker start：0.26 s 后就能回复，GET product:88 回的是 nil，dbsize 是 0。

  • 每个热门商品都要走一遍第 5～7 站：抢锁、查库、回填。第 5 站的锁能保证同一个商品只查一次库，但 20 万个商品就是 20 万次。
  • 大促前预热的那一批，要重新预热。

恢复得最快，代价全转给了数据库。

只有一台，没有从库

进程挂了，有人拉起来还好，最多挨一阵 LOADING。整台机器挂了（宿主机宕机、磁盘坏、网络隔离），就没有别人能顶上：

  • 第 2 站 Lettuce 一直重连，商品详情要么报错，要么全部降级查库。
  • 机器回来之前，开了 AOF 也用不上：文件在那台机器的盘上。

恢复时间取决于人和机器，按分钟算。

不懂这一点时的典型误用以为“开了 AOF、配了从库，数据就不会丢”，于是把重建锁、库存预扣、限流计数和缓存放在同一个 Redis 里。实际上，回 OK 的时候这条写还没到从库，切主时正好丢的就是最近的那几条。缓存丢了重建就行，锁丢了，两个请求就会一起去改同一份数据。

③相邻方案：四种持久化配置，各停一次再起来

同一批 20 万个商品（648 字节的 JSON，带 30 分钟 TTL），每种配置写满后 docker stop（SIGTERM，正常关机）再 docker start。一个探针每 2 ms 发一次 GET product:88，记下回了几次 LOADING、什么时候第一次读到。

怎么读这张表

  • RDB 停机慢：配了 save，正常关机时要先同步存一份快照，1.77 s。快照是“最近一次拍的照片”，进程被 kill -9 时，上次快照以后的写都没了。
  • AOF 纯命令加载最慢：要把 20 万条 SET 重放一遍，文件也最大。
  • 混合：底子是 RDB 格式，后面接着追加命令，加载比纯命令快，数据又和 AOF 一样新。同样是 RDB 格式，它比单独的 dump.rdb 还多花 0.2 s 左右，原因这页没追。
  • 不管哪种，加载期间读和写都被拒，不是“先返回 nil”。

选择规则

  • 纯缓存实例：开混合 AOF（appendonly yes，其余默认），重启后不用从头预热；或者干脆不持久化，前提是数据库扛得住一次全量回源。
  • 放锁、计数的实例：持久化救不了它，切主时丢的是复制没跟上的那一段。能丢就接受，丢不起就别只靠 Redis（⑥-2）。
  • 两种实例都要有从库加 Sentinel（或者用集群），否则整机宕机时只能等人。

④原理：回了 OK 的写在哪，重启时在忙什么，切主时丢了哪一段

先知道这些
  • write 和 fsync：write() 只是把数据交给操作系统的页缓存，进程死了它还在，机器断电就没了；fsync() 才等磁盘确认落下。一次 fsync 要几百微秒到几毫秒，比 Redis 执行一条命令慢上百倍。
  • 复制偏移量：主库把每条写命令按顺序追加进复制流，每个字节有一个编号（master_repl_offset）。从库每秒回一次 REPLCONF ACK <偏移量>，说自己收到哪儿了。
  • RDB 的 fork 和写时复制、AOF 重写、全量与增量同步、哨兵投票：第一圈讲过，见 RDB 与 AOF、主从、哨兵与集群。

一条 SET 回 OK 时，它在哪几处

RDB 不在这条路上：它是每隔一段时间 fork 一个子进程，把整个内存拍一张照。默认 save 3600 1 300 100 60 10000：60 秒内改了 1 万次就拍，写得少时可能一小时才拍一次。只开 RDB 的实例，进程被 kill -9 后会回到上一张照片。

重启：先把文件读完，读完之前只回 LOADING

加载期间被拒（回 -LOADING）

GETSETEVALDELPING

命令表里没有 LOADING 标志的都被拒，错误串是 LOADING Redis is loading the dataset in memory。连 PING 也被拒，拿 PING 做健康检查的，这段时间会判它不健康。

加载期间照样执行

INFOHELLOCLIENTCONFIG GET

INFO persistence 里能看到 loading:1、loading_loaded_perc、loading_eta_seconds。加载 RDB 时每读约 512 KB、重放 AOF 时每 1024 条，停下来处理一次网络事件，所以客户端拿到的是错误，而不是一直卡住。

为什么不边加载边服务？因为加载到一半时，内存里只有一部分 key。这时 GET product:88 回 nil，调用方会以为“没缓存”，去抢锁、查库、回填；可文件里后面还有一条旧的 SET product:88，加载到那里又会把新值盖掉。SET NX 抢锁更糟：锁其实在文件后半段，还没读到，这个请求就“抢到”了。所以 Redis 宁可整体拒绝。

切主：从“主库没了”到“新主库能写”，中间有多久，丢哪一段

主库会不会自己发现“从库跟不上了”？会，但默认什么也不做。它记着每个从库最后一次 ACK 的时间，INFO replication 里的 lag 就是距今几秒。只有配了 min-replicas-to-write N，主库才在“lag 不超过 min-replicas-max-lag 秒的从库不足 N 个”时拒绝写命令，回 NOREPLICAS。它按秒算、靠每秒一次的 ACK，所以只能把丢失窗口压到几秒，压不到零（⑤ 实测 2.95 s 才开始拒）。

为什么这样设计

Redis：先回 OK，盘和从库随后跟上选中的设计

约束：Redis 一条命令执行只要 2 µs 左右（见 279 µs 里只有 2 µs 在 Redis），一个线程顺序执行所有命令。每条写都等 fsync 或等从库确认，就是给每条写加几百微秒，吞吐掉一两个数量级。而它最常见的用法是缓存，数据的正本在数据库里。

想要更强的保证，按条单独要：WAIT 等从库确认，WAITAOF（7.2 起）等本机或从库 fsync，appendfsync always 每条都刷盘。

InnoDB：提交前先把 redo 刷盘数据的正本

innodb_flush_log_at_trx_commit=1（默认）每次提交都刷 redo：数据库存的是正本，丢一笔订单就是事故，所以宁可慢。全景第 6 站查的就是它（一条 UPDATE 从应用到磁盘）。

Redis 要是也这样做，就没法再用一个线程扛十几万 QPS 了。

这个设计带来的后果“Redis 回了 OK”只等于“写进了主库内存”。缓存丢了能重建，这个设计对它刚好合适。锁、库存扣减这类丢一次就会出错的东西，要么不放 Redis，要么让它丢了也不出错：比如 fencing token、数据库唯一约束（⑥-2）。

最少的配置和命令

redis.conf缓存实例：混合 AOF + 一个从库 + 哨兵
appendonly yes                 # 默认 no；开了以后默认 everysec + aof-use-rdb-preamble yes
appendfsync everysec           # 默认值，写出来是为了让人看见
# save 3600 1 300 100 60 10000 不写就是这个默认；只做缓存可以 save "" 关掉 RDB，停机快 1.5 s
min-replicas-to-write 0        # 默认 0 = 不检查；放锁的实例可以设 1，配 min-replicas-max-lag（默认 10 秒）
# 运行时
INFO persistence               # loading、aof_last_write_status、aof_delayed_fsync、rdb_last_bgsave_status
INFO replication               # slave0:…,offset=…,lag=秒；master_repl_offset
WAIT 1 100                     # 等至少 1 个从库确认刚才的写，最多 100 ms；返回确认的个数
WAITAOF 1 0 100                # 7.2 起：等本机 fsync 完（numlocal=1），不等从库

实测 正常复制那一行两遍分别是 p50 210 / 378 µs。第一版用 docker pause 冻住从库来模拟“从库没跟上”，结果锁没丢：进程冻住了，内核照样把主库发来的数据收进 socket 缓冲区，解冻后从库先读完缓冲区才发现主库没了。改成断开复制网络才复现出来。真实环境里对应的是网络分区或者丢包，而不是从库进程慢。

第三段 wipe：主库不持久化，被自动拉起

    主库拉起后 272 ms：从库 dbsize 10000

  从库日志：
    MASTER <-> REPLICA sync: Loading DB in memory

实测 主库重启后换了一个新的复制 ID，从库没法增量续上，只能全量同步：先清掉自己的数据，再加载主库发来的空快照。主库要是被 Sentinel 监控着，这么快就拉起来了，Sentinel 根本来不及判定它下线。官方复制文档专门有一节讲这件事，建议这种情况下关掉自动重启。

    第一圈 · 注意事项：不知道就会出事故

    1拿 PING 做健康检查，加载期间被判死← ④ 只回 LOADING
    现象
    大实例重启后，探活脚本或容器平台的存活检查一直失败，有的平台还会把它再杀一次，于是又从头加载。
    根源
    PING 的命令标志只有 FAST, SENTINEL，没有 LOADING，加载期间回 -LOADING（8.10.3 commands/ping.json）。实测：163 MB 要回 126～220 次 LOADING，0.4～0.8 s；10 GB 估算 25 s 左右
    做法
    存活检查只看端口通不通，或者把 LOADING 也算“活着”；就绪检查看 INFO persistence 的 loading:0。大实例给足启动宽限时间。
    2切主以后，一把锁有两个主人← ④ 切主丢的那一段
    现象
    主库宕机切主后，同一个商品被两个线程同时重建；要是锁护的是扣库存，就会多扣。实测：主从断网后 A 拿锁，切主后 B 的 SET NX 回 OK
    根源
    复制是异步的，主库回 OK 时从库还没收到这把锁。从库被提拔后，它的内存里根本没有这个 key。
    做法
    缓存重建：接受，最多多查一次库。要保证结果正确的：写回时带 fencing token 或版本号（锁过期时 A 还在查库），或者让数据库的唯一约束、乐观锁兜底。解锁用 Lua 比对 token（⑤ 实测 A 解锁回 0，没误删 B 的锁）。
    3主库不持久化又配了自动重启，主从一起清空← ⑤ 第三段
    现象
    主库进程崩了，守护进程马上把它拉起来，几秒后从库的数据也没了，缓存全部回源。实测：拉起后 5～6 s，从库 dbsize 从 10000 变成 0
    根源
    重启后主库换了复制 ID，从库续不上，只能全量同步，先清空自己再加载主库的空快照。拉起得太快，Sentinel 也来不及判定下线。
    做法
    主库开持久化（混合 AOF 停机和不持久化一样快，重启多等约 0.7 s 的 LOADING）；实在不开，就关掉自动重启，让 Sentinel 先把从库提上来。官方复制文档的建议原话是 “auto restart of instances should be disabled”。
    4everysec 不是“最多丢 1 秒”← ④ write 和 fsync
    现象
    磁盘忙的时候，日志里出现 Asynchronous AOF fsync is taking too long (disk is busy?)，写命令的延迟偶尔跳到秒级。
    根源
    flushAppendOnlyFile：发现上一次后台 fsync 还没做完，就连 write 也先推迟，最多推迟 2000 ms；超过以后强制 write，aof_delayed_fsync 加一。推迟期间数据还在 aof_buf 里，这时进程挂了也会丢，最多约 2 秒；强制 write 那一下还可能卡住主线程。
    做法
    监控 aof_delayed_fsync，涨了就查磁盘；AOF 别和别的重 IO 共用一块盘。
    5开着 RDB，正常关机也慢← ③ 停机 1.77 s
    现象
    发版或迁移时停 Redis，等了很久才退出；容器平台的关机宽限期到了，直接 SIGKILL。
    根源
    配了 save 规则（默认就配了），SIGTERM 走关机流程时要同步存一份完整快照；7.0 起有从库时还要先等从库追上偏移量，最多 shutdown-timeout（默认 10 s）。实测：163 MB 停机 1.77 s，不开 RDB 的约 0.2 s
    做法
    只做缓存、开了 AOF 的实例，用 save "" 关掉 RDB；宽限期按“快照时间 + 10 s”留。被 SIGKILL 也不会把文件写坏：快照先写临时文件再改名，只是会回到上一份。
    6Redis 8 镜像里关掉混合格式，起不来← ③ 纯命令那一行
    现象
    appendonly yes 加 aof-use-rdb-preamble no，用官方 redis:8.10.3-alpine 镜像启动，容器立刻退出。实测日志：<search> FATAL: aof-use-rdb-preamble required if AOF is used!
    根源
    Redis 8 的官方镜像自带 bf、search、timeseries、json 四个模块，RediSearch 初始化时检查这个配置，不满足就让整个进程退出。
    做法
    保持默认的 yes。它加载快、文件小，也没有理由关。

    第二圈 · 使用规范：团队里怎么配、怎么写

    缓存和锁分开放

    缓存实例丢了能重建；锁、计数、限流放单独的实例，并且按“会丢”来设计。防的是 ⑥-2。

    至少一主一从加三个 Sentinel

    Sentinel 放在三台不同的机器上，quorum 设 2。防的是整机宕机时只能等人。

    客户端连 Sentinel，不写死主库地址

    Lettuce 用 redis-sentinel:// 地址，Spring 用 spring.data.redis.sentinel.*。LOADING、连接断开都按“暂时不可用”处理：短暂重试，再降级限流。

    不持久化，就不自动重启

    两样只能选一样。防的是 ⑥-3。

    这几个指标进监控

    aof_last_write_status、aof_delayed_fsync、rdb_last_bgsave_status、latest_fork_usec，从库上看 master_link_status，主库上看每个从库的 lag。

    要更强的保证，就在那一条命令上要

    拿到锁以后 WAIT 1 100，返回 0 就当没拿到。这样只是缩小了丢锁的窗口，不能消除它（见第三圈）。

    第三圈 · 深处：fork、lag、WAIT 和从库

    fork 卡多久：和内存大小成正比

    BGSAVE、AOF 重写都要 fork，主线程停在 fork() 里，直到内核复制完页表，耗时记在 latest_fork_usec。4 KB 一页、一项 8 字节，24 GB 内存的页表约 48 MB。实测 163 MB 时 fork 2.7～16 ms。fork 之后靠写时复制，子进程存盘期间主进程改到哪一页就复制哪一页，写得越多，额外内存越多；开着透明大页时一次要复制 2 MB，所以 Redis 默认 disable-thp yes，给自己的进程关掉透明大页。

    min-replicas 为什么 2.95 s 才拒

    主库只记每个从库最后一次 ACK 的时间（秒），从库每秒发一次 ACK。lag = 当前秒 − 最后 ACK 的秒，lag ≤ max-lag 才算好从库。所以 max-lag 设 2，断网后要到 lag 变成 3 才开始拒，再加上 ACK 周期，实测 2.95 s。在这之前主库收下的写，切主时照样会丢。这个配置限制的是丢失窗口有多长，消除不了丢失。

    WAIT 返回 1，也不保证切主不丢

    官方复制文档：WAIT “does not turn a set of Redis instances into a CP system … acknowledged writes can still be lost during a failover”。比如两个从库，WAIT 1 只等到了一个，Sentinel 偏偏提拔了另一个。WAITAOF（7.2 起）多一层：等本机或从库把这条写 fsync 到盘。

    主库挂了以后，从库在干什么

    replica-serve-stale-data 默认 yes：和主库断开时照样回旧数据（⑤ 实测主库被 kill 后从库照样命中）。从库自己不删过期 key，等主库发 DEL；读的时候按自己的时钟判断，过期了就当不存在。

    版本和这一页有关的变化
    4.0混合持久化 aof-use-rdb-preamble（5.0 起默认 yes）；PSYNC2：复制 ID 存进 RDB，从 RDB 重启后能增量续上
    7.0多文件 AOF：appendonlydir/ 里的 base + incr + manifest；repl-diskless-sync 默认 yes；关机时等从库追上（shutdown-timeout 10 s）
    7.2WAITAOF；第一圈两页按 7.x 写，本页讲的写入顺序、LOADING 规则、min-replicas 判断和 8.10 相同
    8.0官方发行版自带查询引擎、JSON、时序、概率结构四个模块，Docker 镜像启动时默认加载
    8.10.3本页实测版本；镜像里的 RediSearch 8.10.1 要求 aof-use-rdb-preamble yes（⑥-6）

    这一层没有尽头

    • Redlock：在 5 个独立的主库上拿多数派，能不能解决 ⑥-2，以及它依赖时钟的那场争论；和 ZooKeeper、etcd 的锁比一比
    • 集群模式的切主：cluster-node-timeout（默认 15 s）、槽迁移时的 MOVED / ASK，Lettuce 的拓扑刷新（主从、哨兵与集群）
    • 从库全量同步时还能不能读：repl-diskless-load 的 swapdb 和异步加载
    • appendfsync always 和 WAITAOF 的真实代价：在本机测每秒还能写多少
    • 大实例的 fork：透明大页、vm.overcommit_memory、写时复制让内存翻倍的极端情况

    ↺回到第⑤步：改一改交易靶场

    1. 拿锁后等从库（⑥ 第二圈最后一条）：在 failover 段 A 拿锁之后加 WAIT 1 100，返回 0 就删锁、按“没拿到”处理。先猜：B 还会拿到第二把锁吗？A 那边会发生什么？
    2. 健康检查（⑥-1）：restart 段再加一个探针发 PING，另一个发 INFO persistence 读 loading_loaded_perc。先猜 PING 在加载期间回什么，再跑。
    3. 关掉 RDB（⑥-5）：把“AOF 混合”那一组的 --save "" 去掉，猜停机时间会变成多少、重启后从哪个文件加载，再跑。
    1. 用一句话说出这一页的精华

    Redis 回 OK 时，这条写只在主库内存和页缓存里：进程挂了，AOF 能救回来，但要先挨一阵 LOADING；机器挂了切主，从库没收到的就丢了，丢的是锁就会有两个主人；主库不持久化又自动重启，会把从库一起清空。

    2. 回 OK 那一刻，这条写在哪几处？进程被杀、断电、切主各丢什么？

    ④：在主库内存里，write 进了页缓存（beforeSleep 里先 write 再发回复）；还没 fsync，也还没到从库。进程被杀：页缓存还在，开了 AOF 就不丢。断电：丢没 fsync 的，通常不到 1 s，fsync 卡住时最多约 2 s。切主：丢从库没收到的，正常不到 2 ms，主从断网时断多久丢多久。

    3. 切主后锁有两个主人，根源是哪条原理？

    ④ 的异步复制：主库先回 OK，再把命令发给从库。Sentinel 提拔的从库只有它收到的那部分，新主库上没有这把锁，B 的 SET NX 自然成功。持久化帮不上忙，持久化文件在宕机的那台机器上。

    4. 预测：缓存实例开了 AOF everysec，主库进程被 kill -9，1 秒内被拉起来。Sentinel 会切主吗？A 刚拿的锁还在吗？

    不会切主：down-after-milliseconds 默认 30 s，1 秒内拉起来，Sentinel 还没判定它主观下线。锁在：进程死了，write 过的数据还在页缓存里，AOF 加载回来就有。代价是重启后要回一阵 LOADING（163 MB 实测约 0.7 s）。从库会因为主库换了复制 ID 全量同步一次。

    5. 预测：主库配了 min-replicas-to-write 1（max-lag 用默认 10），只有一个从库，从库那台机器宕机了。会怎样？

    大约 11 s 后，主库开始拒绝所有写命令，回 NOREPLICAS：第 5 站抢不到锁，第 7 站回填失败，读照常。一台从库挂了，主库就写不进去了。所以要配这个参数，至少要有两个从库、min-replicas-to-write 1；纯缓存实例一般不配。

    6. 放回全景：第 12 站前后各发生了什么？这一页讲的东西出问题，整条链路会怎样？

    第 5 站 SET NX PX 抢锁、第 7 站回填和 Lua 解锁、第 10 站改价删缓存，这些写在主线程执行完，就进了第 12 站：write 进 AOF、每秒 fsync，异步发给从库。之后第 2 站的下一次 GET 才能读到。这一站出问题有三种结局。重启时整段时间回 LOADING，第 2 站要么报错要么全部降级查库。切主时丢了最近的写：缓存回填丢了只是多查一次库，锁丢了，第 5 站的防线出现两个主人。主库不持久化又自动重启，主从一起变空，所有商品走一遍第 5～7 站，压力全落到第 6 站的 MySQL。

    档位：标准。Redis 8.10.3（本机 Docker 容器 redis:8.10.3-alpine，镜像默认加载 bf / search / timeseries / json 模块），Lettuce 6.8.2，代码按 JDK 8 写、在 JDK 17 上跑，本机 2 核 ARM。

    标“实测”的都在本机跑过：restart、failover 两段各跑了两遍以上，wipe 两遍（5.3 s、6.3 s）。第一版 failover 用 docker pause 冻从库，锁没丢，原因见 ⑤，改成断开复制网络后才复现。第一版第一步写的 key 包含 88 号，新主库上读到的是旧值，也改过。写入顺序（beforeSleep 先 write 再回复）、LOADING 规则和命令标志、everysec 推迟 2 秒、min-replicas 的判断和 ACK 周期、关机等从库、Sentinel 默认值、加载时处理事件的间隔，对照的是 redis 8.10.3 的源码（server.c、aof.c、rdb.c、replication.c、sentinel.c、config.c、commands/*.json），部分对比了 7.2；WAIT 的保证和“关掉自动重启”取自官方复制文档。InnoDB 的对照来自 MySQL 文档。
