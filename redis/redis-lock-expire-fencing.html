锁过期时 A 还在查库：看门狗、fencing token 与 Lua 条件写

Redis 上的锁其实是一份租约：时间一到就被收回，拿锁的进程自己并不知道。所以锁只能把同时查库的人减到大约一个，写得对不对，要由被写的那一方把关：写之前在那里比一下“我还算数吗”，比锁的 token，或者比数据的版本号。比和写必须一步做完，这一步用 Lua 在 Redis 里完成。

下一圈第一圈讲了锁的五次进化、Redisson 和 Lua 的基本用法；88 号过期那一刻讲了重建锁让人排队。这一圈只盯一个时刻：锁到点过期了，拿锁的 A 还没干完。A 回来写的那一下，会不会把旧价写进缓存？

①要解决的问题：A 回来的时候，锁已经不是它的了

在全景第 5 站，这一步要解决的是：88 号刚过期，4 个实例几百个请求同时没命中，只放一个去查库。第 7 站回填以后用 Lua 解锁，只删自己的锁。这两站都假定 A 在 3 秒内干完。可锁的 PX 3000 是估出来的：慢 SQL、一次长 GC、一次网络重传，都能让 A 晚回来。这期间运营刚好把 88 号从 399 改成 299，A 手里却还是 399 那一行。

要做成的事：锁过期是常态，不是事故。A 回来时，缓存里绝不能留下比数据库旧的价格。地图给 J07 定的过关标准里有一条：说出你选的一致性方案能接受的最坏情况。这一页就是把“锁过期”这条最坏情况讲完。

②不用它会怎样：三条时间线，直接写都错

在交易靶场里把 A 的慢做成三种情况，每种跑一遍回填。数据库用一个可以改的变量代替，第 1 秒改价，第 4.6 秒看缓存里最后是几块钱。

第二行是最常见的误用。看上去已经很小心了：写之前先确认锁还是自己的。可确认发生在 2.9 s，写发生在 4.0 s，中间那 1.1 s 的 GC 停顿里，锁过期了，B 进来了。客户端看到的“锁还在”，传到 Redis 时已经过时了。
T3 说明锁本来就管不着改价。A 的锁一直有效，A 照样把 399 写回去了：A 在 0 s 读库，改价发生在 1 s。这是缓存一致性那页讲的“读到旧值、晚写回去”。锁只保证同一时刻只有一个人在重建，管不着重建期间数据库变了。

③几种流派：让锁别过期，还是让迟到的写不进去

一类想办法让锁别在 A 干完之前过期，另一类承认锁会过期，改在被写的那一方挡住迟到的写。

流派做法挡得住挡不住
把锁定长一点PX 30000，估一个“肯定够”的时间偶尔的慢查询拿锁的实例挂了，锁要等 30 秒才放，这 30 秒里所有人都在等；更长的停顿照样挡不住
看门狗续期Redisson lock() 不带 leaseTime：后台每 10 秒续一次，续到 30 秒活干多久，锁就续多久；进程挂了，最多 30 秒后自动放整个进程停住（长 GC、SIGSTOP、虚机被挂起），或者连不上 Redis：续期也跟着停。实测停住 2.07 s 后锁就过期了（看门狗设的 3 s）
锁守卫回填用一段 Lua：锁里还是我的 token，才 SET 并解锁锁过期以后才到的写（T1、T2）锁没过期、但数据库已经改了（T3）
版本守卫（fencing token）回填用一段 Lua：缓存里那份的 version 不比我新，才 SET；改价时写一个带新 version 的墓碑，不 DELT1、T2、T3 全挡住，不管锁过没过期表里要有单调递增的 version；墓碑过期以后才到的写
换一种锁服务ZooKeeper、etcd：会话或租约加上单调递增的 revision；Redlock：向 5 个互相独立的 Redis 主节点加锁，过半成功才算Redis 主从切换时锁丢失停顿照样会让租约过期；写的那一方不检查编号，照样有迟到的写

选择规则：锁保护的是谁，就在谁那里把关。锁本身只用来少查几次库，写得对不对靠条件写。交易靶场的选法：看门狗减少锁过期的次数；回填用版本守卫；改价写墓碑。没有 version 列的表，退一步用锁守卫，T3 那种情况交给延迟双删或订阅 binlog。

④核心取舍：拿锁的人说了不算，被写的那一方说了算

锁一定会过期，拿锁的进程又一定会停顿，这两件事都改不了。能改的只有一件：谁来判断“这次写还算不算数”。

先知道这些
  • 重建锁是 SET lock:product:88 <token> NX PX 3000，解锁先比 token 再删：Redis 分布式锁（第一圈“五次进化”）。
  • Redis 一个主线程按顺序执行命令，一段 Lua 脚本整个算一条命令：线程模型与 IO 多路复用，Lua 脚本与事务。
  • 改价是先改库、再删缓存（全景第 9、10 站），为什么这个顺序：缓存一致性。

锁是一份租约，到点就收

为什么非过期不可

不设过期时间，拿锁的实例一挂，锁就永远不放，88 号再也建不起缓存。设了过期时间，锁就成了租约（lease）：Redis 按自己的时钟到点收回，不管 A 干完没有。

A 为什么不知道

A 能做的只是问一句：GET 一下锁，或者 PTTL 一下。答案说的是 Redis 处理这条命令那一刻的情况，等它传回 A、A 再发下一条命令，中间每一步都可能停下来。

会停多久

停顿没有上限：一次 Full GC 几百毫秒到几秒，虚机被宿主机挂起，网络重传、丢包。实测把持锁进程 kill -STOP 5 秒，它醒来时锁早就归别人了。

所以

“我还拿着锁”这句话，A 说了不算。能说了算的，只有执行写入的那一方，在执行写入的那一刻。

为什么这样设计：在 A 这边判断，还是在 Redis 那边判断

A 自己判断被放弃的

  • 比对时的答案，写入时已经过时
  • 把两条命令挨得再近也没用，停顿可能正好落在中间

Redis 那边判断锁守卫、版本守卫

  • 比和写之间没有空隙，A 停多久都不怕
  • 多一次 EVAL，服务端几十微秒
  • 脚本在主线程上跑，写长了会卡住所有人（⑥ 第一圈 5）

决定胜负的约束：A 会停多久，A 自己控制不了，也觉察不到；Redis 执行一段脚本时，却不会被别的命令插队。所以判断必须挪到 Redis 这边，跟写入放进同一段脚本。

fencing token：被写的一方要记得见过的最大号

锁守卫比的是“锁还在不在”，只管得住锁过期以后才到的写。T3 里 A 的锁一直没过期，写的却是旧数据。比锁更可靠的，是给每次写带上一个只增不减的号，被写的那一方记住见过的最大号，号比它小的写一律拒绝。Martin Kleppmann 2016 年那篇谈分布式锁的文章，管这个号叫 fencing token。在交易靶场里，这个号不用另外发：product 表每改一次价，version 就加 1，查出来的那一行本身就带着号。

为什么用 Lua：要“先读、再看着办”

⑥反例和误用：以为锁在，以为脚本快

第一圈的坑出在锁本身：没 token、没过期时间、锁在事务里面。这一圈的坑多半出在两种“以为”上：以为续期了锁就不会丢，以为一段脚本反正很快。

第一圈

注意事项：不知道就会出事故

1传了 leaseTime，看门狗就不干活了← ③ 看门狗
现象
以为用了 Redisson 就有自动续期，写的却是 lock(3, SECONDS)。查库一慢，锁照样到点没了。实测：lock(2, SECONDS) 以后 PTTL 依次是 1994 → 994 → 93 → -2，2.1 s 时 isHeldByCurrentThread() 返回 false
根源
Redisson 4.8.0 的 tryAcquireAsync：leaseTime > 0 时直接用它当过期时间，只有不传（-1）时才启动续期任务。
做法
不知道要干多久，就别传 leaseTime；要传，就设成查库超时的几倍，并且给查库本身也设一个超时。
2看门狗挡不住整个进程停住← ④ 租约
现象
持锁的进程停了一会儿，醒来接着干，可锁早就被别人拿走了，两个人都以为自己在锁里。实测：看门狗设 3 s，持锁进程被 kill -STOP，2069 ms 后锁过期，另一个进程马上 tryLock 成功；5 s 后 kill -CONT，原来那个进程解锁时抛 IllegalMonitorStateException
根源
续期是同一个 JVM 里的定时任务，每隔 lockWatchdogTimeout / 3 跑一次。进程停了，它也跟着停。默认 30 s 的租约，只要停顿超过离到期还剩的时间（20～30 s），锁就会丢。连不上 Redis 时也一样。
做法
看门狗只用来减少锁过期的次数，正确性交给条件写（④）。GC 日志里盯住长停顿，停顿长的服务不要拿锁做正确性保证。
3解锁失败，catch 一下就算了← ④ 租约
现象
日志里偶尔有一行 attempt to unlock lock, not locked by current thread，或者手写的解锁脚本返回 0，没人当回事。
根源
这说明你干活的时候锁丢过，那段时间别人也在锁里。这次侥幸没出事，靠的是条件写挡住了，或者两个人写的正好一样。
做法
打点、告警、按 key 统计次数。次数一多，说明锁的 PX 短了，或者停顿变长了。不要因为解锁失败就重试写入。
4墓碑过期得太早，迟到的写又进来了← ④ fencing
现象
用了版本守卫加墓碑，偶尔还是有旧价，而且一挂就是 30 分钟。
根源
墓碑记的就是“见过的最大号”，它一过期，缓存就把这个号忘了。A 停顿得比墓碑的寿命还长，回来一比，缓存是空的，就写进去了。DEL 等于墓碑寿命为 0，这就是 ② 里 T2 出错的原因。
做法
墓碑只有几十字节，不妨和数据存一样久（30 分钟）。至少要比“锁的 PX + 查库超时 + 可能的停顿”长。↺ 练习 1 把它改成 2 s，自己看一次。
5Lua 脚本跑太久，整个 Redis 都在等← ④ 一整块执行
现象
有人在脚本里写了循环，或者 HGETALL 一个大 key。所有客户端一起超时，过几秒开始收到 BUSY Redis is busy running a script。实测：脚本空转 6 s，第 1.0 s 发出的 PING 等到 5.0 s 收到 BUSY；只读脚本 SCRIPT KILL 能杀掉；先写过一个 key 的脚本，SCRIPT KILL 回 UNKILLABLE，只能等它跑完
根源
脚本在主线程上一整块跑完，这正是它原子的原因。超过 busy-reply-threshold（默认 5000 ms，7.0 以前叫 lua-time-limit，旧名字现在还能用），Redis 才开始给别人回 BUSY。脚本已经写过数据时，杀掉它会留下写了一半的结果，所以 Redis 不让杀，剩下的办法只有 SHUTDOWN NOSAVE，上次持久化以后的写全部丢掉。
做法
脚本只做 O(1) 的比和写，不循环，不碰大 key。用 SLOWLOG 盯 EVAL 的耗时。
6上了集群，锁和数据不在一个槽← ④ 一整块执行
现象
单机跑得好好的锁守卫，换到 Redis 集群就报错。
根源
一段脚本只能在一个节点上执行，它碰的 key 都要通过 KEYS 传进去，并且落在同一个槽。lock:product:88 和 product:88 按整个名字算槽，多半分在两个节点上。
做法
用 hash tag：起名 {product:88} 和 lock:{product:88}，槽只按花括号里那段算。Redisson 也是这么做的：它的频道、解锁记录、fencing 号这几个 key，名字都用 prefixName 拼成 redisson_lock__channel:{lock:product:88} 这种形式。
7重启或主从切换以后，EVALSHA 报 NOSCRIPT← ④ 一整块执行
现象
为了省流量改用 EVALSHA，Redis 一重启，所有带脚本的请求报 NOSCRIPT No matching script。实测：SCRIPT FLUSH 以后再 EVALSHA，就是这个错
根源
脚本缓存只在内存里，不持久化。重启、从库升为主库、SCRIPT FLUSH，都会把它清空。
做法
Spring Data Redis 的 DefaultScriptExecutor 先发 EVALSHA，收到 NOSCRIPT 再退回 EVAL（4.1.2 源码），用 RedisScript 就不用管。直接用 Lettuce 的要自己补这一步。Redis 7 起的 Functions（FUNCTION LOAD / FCALL）会跟着持久化和复制，不会出现这个问题。

锁只管“少查几次库”

评审时问一句：这把锁要是丢了，会多查几次库，还是会写错数据？答案是“会写错”，就得在被写的那一方加条件写。

把正确性押在 PX 和看门狗上。

leaseTime 要么不传，要么远大于查库超时

查库自己设超时，比锁短。

⑥-1：锁比活先到期。

解锁失败要打点

手写脚本返回 0、Redisson 抛 IllegalMonitorStateException，都算锁丢过一次。

锁过期悄悄发生，没人知道。

脚本 O(1)，key 全走 KEYS，集群用 hash tag

用 RedisScript 或 Functions 加载，不手拼 EVALSHA。

第三圈

优化和深处

Redisson 的锁长什么样（4.8.0 源码）

锁是一个 Hash：lock:product:88 里一个字段 <客户端 id>:<线程 id>，值是重入次数。加锁是一段 Lua：

if (redis.call('exists', KEYS[1]) == 0)
   or (redis.call('hexists', KEYS[1], ARGV[2]) == 1) then
  redis.call('hincrby', KEYS[1], ARGV[2], 1)
  redis.call('pexpire', KEYS[1], ARGV[1])
  return nil
end
return redis.call('pttl', KEYS[1])
  • 没抢到的人不轮询：订阅频道 redisson_lock__channel:{…}，在本地信号量上等，最多等锁剩下的 PTTL。解锁脚本删锁的同时发一条消息，把它们叫醒。“88 号过期那一刻”里是每 10 ms GET 一次。
  • 续期：RenewalTask 每 lockWatchdogTimeout / 3 跑一次，本客户端持有的锁分批续，一批一段脚本。
  • 解锁可以重试：解锁脚本顺手写一个 redisson_unlock_latch:{…}:<requestId>，网络超时后重发同一个解锁请求，能拿到第一次的结果，不会误判成“不是你的锁”。

Redlock 之争，吵完剩下的共识

Kleppmann（2016-02）antirez（2016-02）
锁拿来干什么只为效率（少干重复活），单个 Redis 就够；为正确性，Redlock 也不够Redlock 在它声明的假设下是安全的
停顿和时钟进程停顿、网络延迟、时钟跳变都没有上限，按时间算的租约挡不住停顿发生在拿到锁之后，任何租约锁都一样；时钟要求可以通过运维满足
fencing token必须有；Redlock 发不出单调递增的号随机 token 加上被写的一方做“比较再写”，也能达到同样效果

两边都同意的一点，正是本页的结论：真正把关的，是被写的那一方的条件写。交易靶场用的号，就是 MySQL 里的 version。

RFencedLock：Redisson 发的号

2022 年 12 月加进 Redisson（issue #4684）。每次加锁，对 redisson_lock_token:{…} 做一次 INCR，把结果作为 fencing token 返回。接口注释写明：被保护的服务要检查这个号不比上一个小，否则拒绝。

  • 写 MySQL 时，表里加一列 fence：UPDATE … SET …, fence = ? WHERE id = ? AND fence < ?。
  • 它的号存在 Redis 里。按 Redis 主从异步复制推断，主从切换时最近几次 INCR 可能丢失，号会重复。交易靶场的回填用 MySQL 的 version，号来自数据本身，没有这个问题。

1. 用一句话说出这一页的精华

锁是租约，会在拿锁的人不知情时过期；所以锁只用来少干重复活，写得对不对，要由被写的那一方在写的那一刻原子地比一下：比锁的 token，或者比只增不减的版本号，比和写放进同一段 Lua。

2. 写之前先 GET 一下锁、确认是自己的，为什么还会写错？

确认和写是两条命令，中间 A 可能停顿。实测 2.9 s 确认时锁还在，GC 停了 1.1 s，4.0 s 的 SET 到达时锁已经过期，B 已经填好了 299，A 把它盖成 399。

从 ④“为什么这样设计”推出

3. 用了 Redisson 的看门狗，为什么锁还会丢？

续期是持锁进程里的一个定时任务。进程整个停住（长 GC、SIGSTOP、虚机挂起）或者连不上 Redis，续期也就停了，租约照样到期。实测停住 2.07 s 锁就没了（看门狗 3 s）。另外，传了 leaseTime 的话根本没有看门狗。

从 ④“锁是一份租约”推出

4. 预测：不用看门狗，把锁的 PX 从 3 秒改成 30 秒，T1 会怎样？

A 4.0 s 回来时锁还在，T1 就变成了 T3：B 3.3 s 抢不到锁，只能等；A 写下 399，B 等来的也是 399。锁守卫拦不住，因为锁确实还是 A 的；只有版本守卫加墓碑能拒掉 A 那份 version 1。锁变长，只是把“锁过期”的问题换成了“锁没过期、数据已经变了”。

从 ④ fencing token 推出

5. 预测：改价写下墓碑后 0.5 秒，Redis 主从切换，墓碑没来得及复制过去。A 回来时会怎样？

新主上没有墓碑，缓存是空的，版本守卫比不出来，A 的 399 写进去了。这和用 DEL 是一个情况：守卫靠的是被写的一方记得最大号，Redis 异步复制丢了这份记忆，守卫也就失效了。兜底靠两样：缓存过期时间，以及订阅 binlog 再删一次。

从 ⑥-4 的根源推出

6. 放回全景：第 5、7 站前后各发生了什么？锁坏了、回填又没守卫，整条链路会怎样？

第 5 站之前，第 4 站的布隆过滤器说 88 号“可能有”；第 5 站抢锁，第 6 站查库，第 7 站回填并解锁，第 8 站再放进本地的 Caffeine。锁坏了只会多查几次库。回填没有守卫，Redis 里就会留下 399，第 8 站各实例从 Redis 加载时都拿到 399，而第 11 站的失效广播早在改价那一刻发过了，不会再发第二次：4 个实例都卖旧价，直到 30 分钟后过期。
