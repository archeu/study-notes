容器里的 JVM 怎么起得快：CDS、AOT 缓存和别的路

Spring Boot 启动慢，大头不在 JVM 本身，而在每次都要把几千个类从 jar 里找出来、解析、校验、链接，再跑一遍框架的初始化。这些工作每次结果都一样。CDS 和 JDK 24 起的 AOT 缓存做的是同一件事：训练运行一次，把“加载、链接好的类”（JDK 25 还加上方法的运行画像）存成一个文件，以后启动直接映射进内存。不用改一行代码。本机 1 核、512 MB 的容器里实测：JDK 21 从 6.2 秒降到 4.5 秒（AppCDS），JDK 25 从 6.4 秒降到 3.8 秒（AOT 缓存），7706 个类里 7438 个直接来自缓存。代价是镜像大 36～55 MB，而且缓存和 JDK 版本、类路径一一绑定，对不上就悄悄失效。

②没有它会怎样：常见的几种“加快启动”

做法效果问题
放宽 startupProbe、多留几个副本不再被误杀，扩容来得及启动本身一点没快，钱花在了闲着的副本上
启动时多给 CPU，或者干脆不设 CPU limitJVM 启动大量并行（类加载、JIT、GC 线程），多核确实快节点上的 CPU 就那么多，扩容时大家一起抢；省下来的是别人的时间
懒加载 Bean（spring.main.lazy-initialization=true）实测 6.2 秒 → 5.9 秒，快 5%只是把创建 Bean 推到第一次请求，配置错误也要到那时才暴露
精简依赖、少扫描几个包真能快一些见效慢，靠人一点点抠，几个月后又长回来

缺的是：把每次启动都重复做、而且结果每次都一样的那部分工作，做一次存起来。它们不依赖请求、不依赖配置，只依赖“哪些 jar、哪个 JDK”。

不懂这一点时的典型误用：为了启动快直接上 GraalVM Native Image，才发现反射、动态代理、某些库都要额外配置，构建要几分钟、几个 GB 内存，峰值吞吐还可能不如 JIT；其实先加一个 CDS 或 AOT 缓存，一行代码不改，就能拿到一大半收益。

③相邻方案

方案存下来的是什么效果代价
懒加载什么都不存，只是推迟实测 −5%第一次请求变慢
AppCDS（JDK 10 起；动态归档 JDK 13 起）解析好的类元数据实测 JDK 21：−28%训练一次；归档 36 MB；和 JDK、类路径绑定
AOT 缓存（JDK 24 起，Project Leyden）加载并链接好的类；JDK 25 起还有方法画像实测 JDK 25：−41%同上；缓存 55 MB
CRaC（检查点 / 恢复）整个跑热了的进程的内存快照按文档：恢复只要几十到几百毫秒，而且已经是热的要支持 CRaC 的 JDK 发行版和 CRIU；应用要在快照前关掉连接、恢复后重连；快照里有内存中的一切，包括密钥
GraalVM Native Image整个程序提前编译成本地可执行文件按文档：启动在一秒内，内存更小“封闭世界”假设：反射、动态代理要配置；构建慢、耗内存；没有 JIT

选择规则：先上 CDS 或 AOT 缓存，零代码改动、出了问题自动退回普通启动；还不够、而且团队愿意为它改代码和流程，再看 CRaC 或 Native Image。本页学前两种，后两种只按文档做对照，没有本机实测。

④原理：把“每次都一样的工作”做一次，存成文件，启动时映射进来

先知道这些
  • 类加载的三步：加载（从 jar 读出字节、解析成 JVM 内部的类结构）→ 链接（校验字节码、准备静态字段、解析常量池里的符号引用）→ 初始化（跑 static 块）。细节在 类加载 那页。一个 Spring Boot web 应用启动时要走七千多个类。
  • CDS（类数据共享）：JDK 12 起默认带一个 JDK 自己的类的归档，所以什么都不配，也有一千多个类来自归档（⑤ 里 1278 个）。AppCDS 和 AOT 缓存是把应用和依赖的类也放进去。

启动时，缓存省掉了哪段活

什么都不做每个类：在类路径的几十个 jar 里找到它 → 读字节 → 解析成内部结构 → 校验字节码 → 链接。JDK 自己的一千多个类有默认归档，应用和依赖的全靠现做。
AppCDS（JDK 21）训练时把解析、校验好的类元数据写进 app.jsa。启动时把文件映射进内存，类“已经是解析好的样子”，跳过读 jar、解析、校验。
AOT 缓存（JDK 24 / 25）在 CDS 的基础上，类在启动时就成批加载并链接好（JEP 483）；JDK 25 起一步就能训练（JEP 514），还带上训练时的方法画像，JIT 不用从零观察就知道哪些方法热（JEP 515）。

训练一次，处处映射；对不上就不用

实测 在缓存做好以后 touch 一下类路径上的 spring-web-6.2.19.jar（只改了修改时间）：AOT 缓存打印 timestamp has changed 和 shared class paths mismatch，一个类都不从缓存来（连 JDK 自带的那 1278 个也没了）；AppCDS 打印同样的警告，退回到只有 JDK 默认归档的 1278 个。两种情况进程都照常启动，只是变慢，所以不看日志很难发现。

为什么这样设计

选中的：存“结果”，Java 还是那个 Java

缓存里只是“类加载、链接到哪一步”的结果和运行画像，程序还是在普通的 JVM 上跑：反射、动态代理、运行时生成类、JIT 优化全都照旧。缓存对不上就当它不存在，最坏是回到原来的速度，不会出错。

被放弃的：把整个程序提前编译死

Native Image 要在构建时就知道会用到的所有类和反射目标（封闭世界），Java 生态里大量框架靠运行时的动态性工作，于是要补配置、换写法。CRaC 存整个进程，又要处理连接、文件、随机数种子、内存里的密钥这些“不该被快照”的东西。

决定胜负的约束：Java 的动态性不能丢，而且这件事要能在不改代码的前提下给存量应用用上。代价是：缓存只覆盖类加载和链接，Spring 自己初始化的那一大段仍然要跑；缓存和 JDK、jar 绑死，构建流程要保证两者一致。

最少的用法

JDK 21：AppCDS 动态归档
# 训练：退出时把加载过的类写进归档
java -XX:ArchiveClassesAtExit=app.jsa \
     -Dspring.context.exit=onRefresh -jar order-svc.jar
# 使用
java -XX:SharedArchiveFile=app.jsa -jar order-svc.jar
JDK 25：AOT 缓存
# 训练：一步完成（JEP 514）
java -XX:AOTCacheOutput=app.aot \
     -Dspring.context.exit=onRefresh -jar order-svc.jar
# 使用
java -XX:AOTCache=app.aot -jar order-svc.jar
# JDK 24 要分两步：-XX:AOTMode=record 再 -XX:AOTMode=create

-Dspring.context.exit=onRefresh 是 Spring Boot 3.2 起提供的：上下文刷新完就退出，正好用来训练。前提是用拆开的 jar（Docker 那页的 extract），fat jar 里嵌套的 jar 用不上这两种缓存。

实验台：启动快几秒，发布和回滚快多少

先猜：全景里 order-svc 启动 22 秒，17:47 发出回滚时 HPA 已经扩到 6 个副本，策略是 maxSurge 1、maxUnavailable 0。6 个 Pod 能在 1 分钟内全部换回 1.8.3 吗？

按 maxUnavailable: 0 估算：每轮 = 启动时间 + 1 秒（探针间隔和地址表更新），轮数 = 副本数 ÷ maxSurge 向上取整。扩容 = HPA 一个计算周期 15 秒 + 启动时间。都是估算；对照：Kubernetes 核心对象那页在 kind 里实测，4 副本（JDK 21 镜像）滚动 26 秒，每轮约 6.5 秒。

⑤亲眼看到：同一个 order-svc，五种启动方式

沿用 Docker 那页的多阶段四层 Dockerfile，加两个目标阶段：cds 在 JDK 21 上训练出 app.jsa，aot 在 JDK 25 上训练出 app.aot，训练都在 docker build 里做。每种在 --cpus=1 --memory=512m 的容器里各起 5 次，读 Spring Boot 日志里的 process running for（从 JVM 启动算起），取中位数。最后用 -Xlog:class+load 数一数多少个类真的来自归档。

⑤Dockerfile（运行阶段）完整代码 →
ARG JRE=eclipse-temurin:21.0.13_9-jre-noble
# …构建阶段同 Docker 那页：mvn package，再 extract 拆开…

FROM ${JRE} AS plain
WORKDIR /app
COPY --from=build /x/dependencies/ ./
COPY --from=build /x/spring-boot-loader/ ./
COPY --from=build /x/snapshot-dependencies/ ./
COPY --from=build /x/application/ ./
ENTRYPOINT ["java", "-jar", "order-svc.jar"]

FROM plain AS cds          # JDK 21
RUN java -XX:ArchiveClassesAtExit=app.jsa \
         -Dspring.context.exit=onRefresh -jar order-svc.jar
ENTRYPOINT ["java", "-XX:SharedArchiveFile=app.jsa", "-jar", "order-svc.jar"]

FROM plain AS aot          # JDK 25
RUN java -XX:AOTCacheOutput=app.aot \
         -Dspring.context.exit=onRefresh -jar order-svc.jar
ENTRYPOINT ["java", "-XX:AOTCache=app.aot", "-jar", "order-svc.jar"]

看懂这次运行
  • 五次测量的波动在 ±0.2 秒以内，几种方式之间的差距远大于波动。AppCDS 让 JDK 21 快了 28%，AOT 缓存让 JDK 25 快了 41%。JDK 25 普通启动比 JDK 21 略慢 0.16 秒，在这台机器上可以算持平。
  • 类的数字说明了快在哪：普通启动只有 JDK 自己的 1278 个类来自默认归档，剩下六千多个都要现做；用了缓存以后，九成以上直接映射进来。
  • 剩下的 3.8 秒里，大头是 Spring 建 Bean、起 Tomcat 这些“真正在执行代码”的工作，缓存只让它们用到的类来得更快。所以业务越重（Bean 越多），省下的比例越小。
  • 代价写在镜像大小里：多 36～55 MB。而且业务代码一变，缓存就要重新训练，这一层每次发布都是新的（坑 3）。

到这里已经能交差了：Dockerfile 里多一个训练阶段、ENTRYPOINT 多一个参数，启动快三到四成。已知还没处理的细节：缓存悄悄失效（坑 1），fat jar 用不上（坑 2），缓存层每次都变（坑 3）。

⑥细节·规范·优化

第一圈 · 不知道就会出事的

1缓存悄悄失效，没人发现实测← ④ 对不上就不用
现象
上线时快了 40%，几个版本以后又慢回去；日志里有一行 warning 没人看。
根源
启动时要核对 JDK 版本和类路径上每个 jar 的路径、大小、修改时间。基础镜像升了小版本、某个 jar 被重新打包、训练和运行用的启动参数不同，都会对不上；对不上时为了安全只告警、不报错。
做法
训练和运行放在同一个 Dockerfile、同一个运行阶段；CI 里加一步检查：用 -Xlog:class+load 数一下来自缓存的类，低于阈值就失败；启动耗时进监控。
2直接 java -jar fat jar← ④ 只认普通 jar
现象
加了参数，启动一点没快。
根源
fat jar 里的依赖是“jar 里的 jar”，由 Spring Boot 自己的类加载器读，归档机制认不出这种类路径。
做法
先用 -Djarmode=tools … extract 拆成瘦 jar + lib/，再训练、再运行（Spring Boot 文档推荐的就是这个组合）。
3缓存层让“只推一层”失效← ④ 缓存和 jar 绑定
现象
Docker 那页好不容易做到改一行代码只推 3.9 KB，加了缓存以后每次又要推几十 MB。
根源
业务 jar 一变，缓存就要重新训练，app.aot 那 55 MB 的层每次都是新的。
做法
接受它（几十 MB 换每次启动快 40%，大多数时候划算）；或者只在依赖不变时复用缓存的思路要非常小心，类路径对不上就白做。按发布频率和节点数算一笔账再决定。
4训练只跑到上下文刷新← ④ 缓存的是训练时见过的
现象
启动快了，第一批请求还是慢：处理请求要用的类（Jackson 的序列化器、某些业务类）不在缓存里，方法画像也只有启动阶段的。
根源
缓存里只有训练运行时加载过的类和跑过的方法。spring.context.exit=onRefresh 只跑到启动完成。
做法
要缓存请求路径，训练时起服务、打几下典型请求再正常退出；JDK 25 的方法画像尤其依赖训练是否像生产。
5CPU limit 卡住启动← ④ 启动是吃 CPU 的活
现象
本机实测用的是 1 核的容器；limit 再小，启动会成倍变长，startupProbe 一不留神就超时。
根源
类加载、JIT 编译、GC 在启动时都很忙，而且是多线程的；CPU 被限速时，这些工作只能排队。
做法
在线服务通常只设 CPU requests、不设或放宽 limit（资源那页坑 4）；startupProbe 按“limit 下实测的最慢启动”留余量。
6用懒加载换启动时间实测← ④ 剩下的是框架初始化
现象
启动只快了 5%，第一次请求却慢了；有个 Bean 配置错了，上线一小时后第一次被用到才报错。
根源
懒加载不省工作，只是挪到后面。
做法
生产上慎用全局懒加载；真要用，只对确实很少用到、初始化又重的 Bean 单独加 @Lazy。

第二圈 · 团队里该怎么写

  • 训练放在 Dockerfile 的运行阶段里：防训练环境和运行环境的 JDK、jar 不一致。
  • 启动耗时进监控和 CI（Spring Boot 的 application.ready.time 指标，或日志里的 process running for）：防缓存失效、依赖膨胀让启动悄悄变慢。
  • 新服务直接用 JDK 25 + AOT 缓存；还在 JDK 21 的用 AppCDS：防为了这点收益去冒升级的险，也别错过免费的收益。
  • startupProbe 按实测最慢启动留 2 倍余量：防缓存失效那天所有 Pod 起不来。

第三圈 · 深一层

Leyden 的路线

Project Leyden 想把“提前做好、存起来”一步步扩大：JDK 24 存加载和链接好的类（JEP 483），JDK 25 加上一步训练（JEP 514）和方法画像（JEP 515），JDK 26 让缓存里的对象不再挑 GC（JEP 516）。后面的方向是把 JIT 编译好的代码也存进去。每一步都保持同一个原则：缓存对不上就当它不存在。

同一节点上的多个 Pod 共享缓存

归档和缓存是只读映射进内存的。同一节点上从同一个镜像起的几个 Pod，读的是镜像同一层里的同一个文件，页缓存可以共用；理论上 Pod 越多，平均每个 Pod 为缓存付出的内存越少。本页没有实测这一点。

CRaC 和 Native Image 的位置

CRaC 恢复的是一个已经跑热的进程，连 JIT 预热都省了，适合对冷启动极敏感、又能接受改造的服务；Spring Boot 3.2 起支持它的生命周期。Native Image 适合命令行工具、函数计算这类“起来就干、干完就走”的场景。两者都改变了运行方式，要专门测一遍。

JDK 版本

JDK 8 只能对 JDK 自己的类做 CDS；JDK 10 起有 AppCDS，13 起有动态归档（ArchiveClassesAtExit），12 起默认带 JDK 的归档。AOT 缓存要 JDK 24，一步训练要 JDK 25。生产上的 8 / 17 / 21 里，17 和 21 都能用 AppCDS。

↺回到⑤：改一改

  1. CI 里的守门员：给 run.sh 加一步：来自缓存的类少于 5000 个就 exit 1。然后故意换一个 JRE 小版本只用于运行阶段，看它能不能拦住。（坑 1）
  2. 训练得更像生产：把训练改成“起服务 → 用 curl 打 20 次 /api/orders/1 → 正常退出”，比较第一次请求的耗时。（坑 4）
  3. 换个 CPU limit：把 --cpus=1 改成 0.5 和 2，各测一遍普通启动和 AOT 缓存，缓存省下的比例变不变？（坑 5）

自测

1. 用一句话说出这一页的精华

每次启动都在重复“找类、解析、校验、链接”这些结果相同的工作；CDS 和 AOT 缓存训练一次把结果存成文件，启动时映射进来，零代码改动快三到四成，对不上时自动退回普通启动。

2. 懒加载、多给 CPU、多留副本这些老办法各疼在哪？

懒加载只是把工作挪到第一次请求（实测只快 5%）；多给 CPU 是在抢节点上别人的资源；多留副本和放宽探针是花钱掩盖问题，启动本身没快。

3. 坑 1（缓存悄悄失效）的根源是 ④ 的哪一条？

训练一次、对不上就不用：启动时核对 JDK 版本和每个 jar 的路径、大小、修改时间，不一致就告警并放弃缓存，进程照常启动，所以只会变慢、不会报错。

4. 预测：用 JDK 25 训练出的 app.aot，拿到 JDK 25 的另一个小版本（比如 25.0.6）上运行，会怎样？

缓存和 JDK 版本绑定，会报告对不上、不使用缓存，回到普通启动的速度。从 ④ 推出：缓存里是这个 JDK 内部格式的类结构，换了 JVM 就不能信任它。所以升级基础镜像时要重新训练。

5. 预测：一个启动 30 秒、其中 25 秒在建几千个 Bean 的应用，加了 AOT 缓存大概能快多少？比 order-svc 的 41% 多还是少？

少。缓存省的是类加载和链接；这个应用的大头是执行初始化代码，类只是其中一部分。可能只快 10%～20%，要实测。从 ④ 第一张图推出：缓存替不了 Spring 建 Bean 那一段。

6. 放回全景：第 7 站前后各是什么？启动从 22 秒降到 13 秒，第 9、10、11 站各会怎样？

前面是第 6 站调度器选好节点，后面是第 8 站探针。第 9 站滚动每轮少 9 秒，4 个副本快半分钟以上；第 10 站 HPA 扩出来的 Pod 早 9 秒接流量，老 Pod 硬扛的时间短了；第 11 站回滚同样一轮轮起 Pod，6 个副本、maxSurge 1 时从约 138 秒降到约 84 秒，要真正在 1 分钟内换完，还得再把 maxSurge 调到 2。可以在实验台里验证。

档位：标准。本机跑过（2 核 ARM 虚拟机，Docker 27.3.1，eclipse-temurin:21.0.13_9-jre-noble 和 25.0.5_8-jre-noble，Spring Boot 3.5.16，容器 --cpus=1 --memory=512m）：./run.sh 完整一次，⑤ 的数字都来自这次运行；touch jar 的那次是单独手动跑的。CRaC、Native Image 的效果、多个 Pod 共享缓存页，都是按文档或按机制推断，没有本机实测。实验台的计算在 node 里跑过。

按文档：JEP 483（JDK 24）AOT 类加载和链接，JEP 514（JDK 25）-XX:AOTCacheOutput 一步训练，JEP 515（JDK 25）方法画像，JEP 516（JDK 26）对象缓存不挑 GC；AppCDS 来自 JEP 310（JDK 10），动态归档来自 JEP 350（JDK 13）；Spring Boot 3.2 起的 spring.context.exit=onRefresh，以及“先 extract 再用 CDS / AOT 缓存”的建议来自 Spring Boot 文档。
