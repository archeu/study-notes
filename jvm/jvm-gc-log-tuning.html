GC 日志与调优：先写下目标，再从日志里找证据，最后才动一个参数

GC 调优要在三个目标之间取舍：停顿短、吞吐高（GC 占的时间少）、内存省，三个最多同时照顾两个。所以第一步是写下要哪两个、阈值是多少。第二步看 GC 日志。日志里每次停顿一行，从中算出三样数：GC 时间占比、最长停顿、回收后的堆占用。有了这三样数，就分得清问题出在参数上还是代码上。在交易靶场的大促流量下实测：G1 用默认参数就达标；换成“吞吐量收集器” Parallel，GC 时间占比是 98.4%；代码有泄漏时，把堆加一倍，OOM 只是从第 21 秒推迟到第 54 秒。

①什么时候用得上：接口慢了，先要判断 GC 是不是凶手

场景交易靶场，大促。下单接口每秒 4000 单，每个请求解析报文、组装响应，产生约 48 KB 很快就没用的临时对象；“最近订单”缓存里常驻 160 万个订单，GC 日志显示活对象约 206 MB。容器内存 512 MB，堆给 256 MB。下面这张图是把收集器换成 Parallel 之后实际发生的事：GC 每次只停 0.2 秒，请求的延迟中位数却到了 3.3 秒。

所以看 GC 有两个层次：一次停多久（日志直接写着），以及停顿占了多少时间（要自己加起来算）。后者一旦接近 100%，系统就处理不过来了，单次停顿再短也没用。

②常见笨办法：先改参数，再看结果

这几种做法看起来都在“调优”，共同的问题是没有先写下目标，也没有拿日志证明问题在哪。

常见做法

  • 从网上抄一套“生产级参数”：-Xmn、SurvivorRatio、MaxTenuringThreshold，再加几个 CMS 时代的开关
  • 接口一慢就加堆，256 MB 改 512 MB，再不行改 1 GB
  • 听说“Parallel 吞吐量高”“ZGC 停顿短”，就换收集器碰运气
  • 只看监控上的“平均 GC 停顿”，或者用 jstat 看一眼当前的数
  • 一次改五个参数，跑一会儿“感觉快了”就上线

结果（本页实测）

  • G1 写死 -Xmn128m 以后，最长停顿从 7.9 ms 变成 15.6 ms，日志里多了一种 “Preventive Collection”，G1 只好提前做 GC
  • 泄漏时把堆加一倍，OOM 从第 21 秒推迟到第 54 秒，每次 Full GC 还更长了（117 → 140 ms）
  • 换 Parallel：GC 时间占比 98.4%，处理速度从每秒 4000 单掉到 3279 单
  • Parallel 加到 768 MB 时，停顿中位数 2.8 ms，看着很好，最长一次却是 37.9 ms，请求 p99.9 是 19 ms
  • 五个参数一起改，变好了也说不清是哪个起的作用，变坏了也不知道该撤哪个

缺的是这几样：一个可以判对错的目标，一份同样流量下的基线日志，从日志里算出来的几个数，以及一次只改一处。有了它们，调优就是一个能验证的实验，而不是凭感觉。

④背后的机制：日志里的数为什么能说明问题，收集器为什么各有各的目标

先知道这些Young GC 只回收新生代，Mixed GC 在 Young GC 的基础上再顺带回收几块老年代 region；Full GC 是兜底，停下所有业务线程，把整个堆整理一遍。G1 的 region、并发标记、为什么会退化成 Full GC，见 G1 与 ZGC；对象怎么从 Eden 熬到老年代，见全景第 5～7 站。这一页只关心这些过程在日志里留下了什么。

1一行日志怎么读

开 -Xlog:gc 时，每次停顿只记一行，就是上图这行。开 -Xlog:gc* 时，同一个 GC(100) 还会多出十来行细节，其中最有用的是各区的 region 数：

GC(100) Eden regions: 20->0(20)        # Eden 用了 20 块，全部清空；下一轮还给 20 块
GC(100) Survivor regions: 1->1(3)
GC(100) Old regions: 188->188        # 老年代 188 块，这次 Young GC 不碰它
GC(100) Humongous regions: 18->18   # 缓存那张大哈希表的数组
GC(100)   Evacuate Collection Set: 1.53ms  # 复制活对象，停顿的大头
G1 日志里的停顿是什么
Pause Young (Normal)普通的 Young GC
(Concurrent Start)顺带启动一轮并发标记
Pause Remark / Cleanup并发标记中间两次很短的停顿
(Prepare Mixed) / (Mixed)开始回收老年代 region
Pause Full整堆整理，出现就要查原因

2三样数：分别对应三个目标

GC 时间占比 → 吞吐

Σ 停顿时长 ÷ 统计时长

业务线程被停住的时间比例。接近 100% 时系统处理不过来，请求越积越多（① 的图）。

最长停顿、p99 → 延迟

把停顿时长排序取尾部

一次停顿期间到达的请求都要等它结束，所以要看尾部，平均值会把偶尔的长停顿抹平。

回收后的占用 → 内存

箭头右边的数：226M->206M

回收完还剩多少，约等于活对象有多少。它决定堆至少要多大；它要是一直涨，就是泄漏。

这三样数为什么能下结论，靠的是复制式回收的两条规律。它们能从 G1 页讲的“复制活对象”直接推出来：

一次停多久 ≈ 要复制的活对象有多少

和堆有多大、垃圾有多少关系不大。大促那一跑每秒分配 196 MB，几乎全是请求结束就没用的临时对象，所以每次 Young GC 只要 1～2 ms。预热时缓存正在装进 160 万个订单，新对象几乎全是活的，一次 Young GC 就要 27～135 ms。

多久 GC 一次 ≈ 分配速率 ÷ 新生代大小

196 MB/s ÷ Eden 20 MB ≈ 每秒 10 次，日志里 30 秒正好 300 多次 Young GC。新生代越小，GC 越频繁；新生代越大，对象在里面待得越久、越容易死掉，晋升到老年代的就越少。

据此可以分出两类问题。回收后的占用低、但 GC 很频繁或停顿长，是参数问题，可以靠堆大小、新生代大小或收集器解决。回收后的占用接近上限、而且一直在涨，是代码问题：东西还被引用着，怎么调参数都回收不掉。

3为什么这样设计：三个目标不能同时最好，收集器只能各选一个优先

每个收集器出厂时已经选好了优先照顾哪个目标，默认参数就是这个选择：

  • Parallel：吞吐优先。GCTimeRatio=99，目标是 GC 只占 1/(1+99) = 1% 的时间；不设停顿目标，一次停多久都可以。
  • G1：停顿优先，兼顾吞吐。MaxGCPauseMillis=200，GCTimeRatio=12（约 8%，Oracle 文档原话 “about 8%”）。
  • ZGC：停顿压到 1 ms 以下，代价是更多的 CPU 和内存，见 G1 与 ZGC 坑 1。

所以“调优”的第一步是确认收集器的优先目标和你的目标一致，然后在它的框架里给它足够的空间。这一点一错，后面怎么调参数都没用。

G1 为什么只要一个停顿目标：它不把新生代的大小写死，每次 GC 之后，按“上次复制了多少活对象、花了多久”预测下一次，再决定 Eden 给几块 region。被放弃的做法是 CMS、Parallel 那一代的思路：新生代和老年代按比例切死，大小由人用 -Xmn、NewRatio、SurvivorRatio 来定。流量一变，原来调好的比例就不对了。同样是 256 MB 的堆、206 MB 的活对象，两种做法实测的分法：

这里 Parallel 输掉，不是因为它“慢”，而是它的固定比例和这个场景的活对象对不上。⑤ 里把堆加到 768 MB，老年代变成 512 MB，Parallel 的 GC 时间占比反而是全场最低的 0.7%。但那样就超出了 256 MB 的内存预算。所以哪个收集器更好，要看目标是什么。

Full GC 频繁，把堆从 256 MB 加到 512 MB，好了半分钟，又开始 Full GC，最后还是 OOM，而且每次 Full GC 更长（117 → 140 ms）。
根源
回收后的占用 ≈ 活对象。活对象一直在涨，堆多大都会被填满；堆越大，整理一次要搬的越多。
先看 Full GC 那几行箭头右边的数：接近上限（253M->243M(256M)）就别动参数，直接 jcmd <pid> GC.class_histogram 或堆转储（第 9 站）。
坑 2把“换收集器”当调优← ④-3 收集器的目标⑤ 实测
现象
听说 Parallel 吞吐高，换上之后 GC 时间占比 98.4%，接口延迟到了秒级。
根源
Parallel 的目标是吞吐，不管停顿；JDK 15 起两代边界固定，老年代 = 堆的 2/3，活对象放不下就只能一直 Full GC。
换收集器之前，先确认它优先照顾的目标和你的一致，再按 ④-2 估一下活对象在它的分法下放不放得下。
坑 3只看平均停顿← ④-2 看尾部⑤ 实测
现象
监控上平均 GC 停顿 2.8 ms，看着很好，请求 p99.9 却是 19 ms（Parallel · 768 MB 那一跑，最长 37.9 ms）。
根源
每秒十几次 1～3 ms 的 Young GC 把平均值压得很低，偶尔一次长停顿被平均掉了；可停顿期间到达的请求都在等那一次。
盯三样：最长停顿（或 p99）、GC 时间占比、Full GC 次数。告警用最大值，不用平均值。
坑 4给 G1 写死新生代← ④-3 G1 靠调 Eden 达标⑤ 实测
现象
加了 -Xmn128m，最长停顿从 7.9 ms 变成 15.6 ms，日志里出现 (G1 Preventive Collection)。
根源
G1 是靠每次重新决定 Eden 的大小来满足停顿目标的。Oracle 文档原话：用 -Xmn、NewRatio 固定新生代大小，“实际上就关掉了停顿时间控制”。
G1 只留 -Xms/-Xmx 和 MaxGCPauseMillis；从别的收集器迁移过来时，先删掉所有 GC 参数。参见 G1 与 ZGC 坑 2。
坑 5把启动预热的停顿算进统计← ④-2 停顿 ≈ 活对象⑤ 实测
现象
-Xmn128m 那一跑，整份日志里最长的停顿是 135 ms，可压测期间最长只有 15.6 ms：那 135 ms 发生在启动时装缓存的阶段。
根源
装缓存时新对象几乎全是活的，Young GC 要复制一大批；正式跑起来以后，新对象大多是请求结束就没用的。
基线和对比都从同一个时刻开始统计（GcLogStats 的第 4 个参数）；生产上，启动阶段的停顿另外看，用预热或分批加载来解决。
坑 6JDK 8 的日志参数带到 17，JVM 起不来历史原因本机核对
现象
升级到 17 以后启动失败：Unrecognized VM option 'PrintGCDateStamps'，或者 'UseGCLogFileRotation'。
根源
JDK 9 起 GC 日志并入统一日志 -Xlog。-XX:+PrintGCDetails、-Xloggc 只会警告，并自动换成 -Xlog:gc* / -Xlog:gc:file；时间戳和轮转相关的参数直接不认了。
换成 ④ 里的那一行 -Xlog:gc*:file=gc-%p-%t.log:…。默认就会轮转，重启时同名的旧文件会先存成 .0；文件名带上 %p，几个实例就不会互相覆盖。

第三圈

更深一层

停顿和延迟不是一回事

同一个 Parallel 跑法里，GC 最长只停了 309 ms，请求延迟的中位数却是 3.3 秒。原因是 GC 占了 98% 的时间，请求处理不过来，越积越多。如果用“发一个、等它回来、再发下一个”的方式压测，停顿期间本来该到的请求根本没发出来，量出来的延迟会好看得多，这个现象叫 coordinated omission。OrderService 从计划到达的时刻开始算延迟，就是为了避开它。

停顿达标了，CPU 还在被 GC 占用

基线 30 秒里做了 54 轮并发标记。这部分工作和业务线程并行，不算在停顿里，但要占 CPU：本机 2 核，G1 默认用 1 个并发 GC 线程（ConcGCThreads=1，PrintFlagsFinal 核对）。所以除了停顿，还要看 CPU 使用率；用 -Xlog:gc+cpu 能看到每次 GC 的 User / Sys / Real 时间。

Preventive Collection 是什么

-Xmn128m 那一跑里出现的 (G1 Preventive Collection)，是 JDK 17 新加的（JDK-8257774）：G1 估计剩下的空 region 不够复制活对象用了，就提前做一次 Young GC，免得复制到一半失败。JDK 21 又把它删掉了（JDK-8297639）。所以同一份参数在 17 和 21 上，日志会不一样。

活对象到底多大，以哪次为准

Young GC 后的占用里还包括老年代中已经死了、但还没轮到回收的对象，所以会偏高。比较准的是 Mixed GC 或 Full GC 之后的数，以及并发标记结束时的统计。⑤ 的基线一直在 206～210 MB 之间，和缓存估算的大小（160 万 × 约 130 字节）对得上。

自测

1. 用一句话说出这一页的精华。

先写下停顿、吞吐、内存三个目标里要哪两个、阈值多少；再从 GC 日志算出占比、最长停顿、回收后占用，判断是参数问题还是代码问题；最后一次只改一处，用同样的流量对比。

2. 常见的“先改参数”的做法，疼在哪？

没有目标，就判断不了调得好不好；没有基线和日志里的数，就分不清问题在参数还是代码。⑤ 里两个反例：换 Parallel 后 GC 占比 98.4%；泄漏时加堆，OOM 只是推迟了 33 秒。

3. 泄漏时加堆没用，根源是哪条原理？

④-2：回收后的占用 ≈ 活对象。泄漏就是活对象一直在涨，堆再大也会被填满；而 Full GC 的停顿和要整理的活对象成正比，堆越大，停得越久（实测 117 → 140 ms）。

4. 预测：大促流量从每秒 4000 单翻到 8000 单，缓存大小不变，G1 的 Young GC 次数和每次停顿会怎么变？

次数大约翻倍：分配速率翻倍，Eden 大小差不多，按 ④-2 的“频率 ≈ 分配速率 ÷ 新生代大小”。每次停顿基本不变：多出来的都是请求结束就死的临时对象，要复制的活对象没变多。GC 时间占比会跟着翻倍，从 2% 到 4% 左右，离 5% 的目标近了。（这是推算，没跑。）

5. 预测：同一个大促场景，把 -Xmx 从 256 MB 改成 2 GB、收集器用 G1，三样数会怎么变？算不算调优成功？

余量从 50 MB 变成 1.8 GB，并发标记和 Mixed GC 会少很多，Young GC 次数会下降，Eden 可以给得更大；停顿依然很短，因为活对象没变。可是内存目标是 ≤ 256 MB，超了 8 倍。按第 1 步写下的目标，这不算成功：三角里拿内存换来了吞吐。

6. 放回全景：第 8 站的前后各发生了什么？读不懂 GC 日志，整条链路会怎样？

前面是第 7 站：老年代占用超过阈值，G1 启动并发标记，再用 Mixed GC 回收垃圾最多的那些 region。后面是第 9 站：回收不掉，就 OOM，然后用堆转储和直方图排查。读不懂日志，就会把第 8 站当成“参数没调好”：加堆或换收集器，结果只是把第 9 站的 OOM 往后推（实测从第 21 秒推到第 54 秒）。在那之前，每秒十几次 Full GC 会把下单接口的 p99 拖到秒级，Tomcat 线程池被占满，上游开始超时重试，问题从一个服务扩散出去。

档位：标准。本机 2 核 ARM，JDK 17.0.20.1，G1 和 Parallel；页面上的数来自这几次 OrderService 运行：大促流量下 G1 默认、Parallel 256 MB、Parallel 768 MB、G1 MaxGCPauseMillis=5、G1 -Xmn128m 各一次，泄漏实验 256 MB 和 512 MB 各一次。预热期的停顿（27 ms、135 ms）取自同一批日志里压测开始之前的部分。没有在 JDK 8、21 上跑，版本差异是按文档和提交记录写的。标“实测”的数字都来自这几次运行，“推算”的没跑。

按文档和源码：Oracle JDK 17 GC Tuning Guide（G1 的 GCTimeRatio=12，“about 8%”；“Avoid limiting the young generation size … -Xmn”；Parallel 的 GCTimeRatio 默认 99，新生代最多占堆的 1/3）；java 命令手册的统一日志一节（%p、%t，默认 5 个文件 × 20 MB 轮转）；logFileOutput.cpp（启动时存档已有的日志文件）；JDK-8228991、JDK-8257774、JDK-8297639；本机 -XX:+PrintFlagsFinal 核对了各项默认值，JDK 8 日志参数在 17 上的行为也在本机试过。
