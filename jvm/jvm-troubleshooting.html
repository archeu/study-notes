JVM 故障排查：三种现象，其实只有两个问题要回答：内存是“谁拉着、谁在猛分配”，CPU 是“哪个线程在跑哪一行”。证据要在出事之前就埋好

OOM、频繁 Full GC、CPU 飙高看起来是三种病，查起来只有两条路。内存路线先看 Full GC 之后堆降不降：不降是有东西一直被拉着（泄漏），拿堆转储顺着引用链找到 GC Root；降了是分配太猛（大对象、一阵阵的峰），拿 GC 日志和 JFR 分配采样找到是谁在分配。CPU 路线先用 top -H 看吃 CPU 的是哪个线程：是 GC 线程就转回内存路线，是业务线程就用 jstack 或 JFR 对到那一行。交易靶场订单服务里埋了三个雷，本机实测：泄漏 16 秒后 OOM，进程还活着却一个请求都不回；大导出让 30 秒里发生 401 次 Full GC；一张一分钱的优惠券让一个核一直 100%。三个雷都在 5 分钟内定位到了具体的对象和代码行。

②常见误判：每一条都“看起来对”，因为它让症状暂时消失了

排查最怕的不是不会用工具，而是一上来就下结论。下面六条在交易靶场里都能找到反例，最后一列是 ⑤ 里实测到的。

误判为什么看起来对错在哪
先重启，恢复了再说重启后服务马上正常堆里是谁、线程在跑什么，全跟着进程没了。泄漏过几小时又会回来，到时还是两手空空。
OOM 了就把堆调大OOM 确实来得晚了泄漏是只进不出，多大的堆都会填满。GC 日志页实测：同样的泄漏，256 MB 第 21.4 秒 OOM，512 MB 第 54.0 秒 OOM。
照着 OOM 的异常栈去改那一行异常栈指着一行具体代码OOM 抛给“最后一个想要内存”的线程，它多半是受害者。⑤ 里泄漏的是 /order，最先拿到 OOM 的却是 HTTP-Dispatcher、idle-timeout-task 这些线程。
CPU 高，就是业务代码慢业务一忙 CPU 就高⑤ 大导出时，两个 GC Thread 各吃掉 72% 和 71% 的核，业务线程每个才 4%。这时该查的是内存。
拍一张线程转储就下结论转储里确实有一堆 RUNNABLE一张转储只是某一瞬间。隔几秒拍两三张，同一个线程一直停在同一行，才算抓到，⑤ 里看的就是 cpu= 涨了多少。
Pod 重启了，当成堆 OOM 去查“内存不够”听起来是一回事被内核杀掉的进程没有 OutOfMemoryError，也不会留堆转储。退出码 137 先查堆外和容器限额，见 JVM 内存结构。

这六条错在同一个地方：没拿到证据就动手。所以排查路线的第 0 步一律是留现场；后面每一步都是“先看这一条证据，再决定往哪走”，不靠猜。

③排查路线：先留现场，再按证据分两条路走

从现象出发，每个岔口只看一条证据。三种现象最后只落到四个终点：谁拉着、谁在猛分配、哪个线程哪一行、堆外。CPU 高的那一路有一个回头箭头：吃 CPU 的要是 GC 线程，就回到内存路线。

OOM 冒号后面要是别的字，路线换一条：Metaspace 是类加载器被拉着，查法和“谁拉着”一样，只是看的是类加载器（见类加载页）；Direct buffer memory 和 unable to create native thread 走左列的堆外；GC overhead limit exceeded 只有 Parallel 收集器会报，按“谁拉着”查。完整的对照表在 JVM 内存结构。

选择规则：便宜的一直开（GC 日志、JFR 连续录制、OOM 时自动转储），出事时先拍一定拿得到的（线程转储、jstat），最贵的最后拍（堆转储，先摘流量）。本页的两条路线就用这几样：内存用 GC 日志 + 直方图 + 堆转储 + JFR 分配采样，CPU 用 top -H + jstack + JFR 方法采样。async-profiler、Arthas 这类第三方工具能做得更顺手，列进“下一圈”。

④背后的机制：OOM 抛给了谁，Full GC 之后的数字为什么能分出泄漏，堆转储和线程转储怎么对到“谁”

先知道这些
  • 可达性：从 GC Roots（线程栈上的局部变量、类的 static 字段、JNI 引用等）顺着引用走得到的对象就是活的，GC 不收。见 垃圾回收：分代、可达性、G1、ZGC。
  • 大对象（Humongous）：G1 里超过半个 region 的对象直接在老年代占连续的几个 region。堆 128～256 MB 时 region 是 1 MB，门槛 512 KB。见 new 一个对象的全过程。
  • HotSpot 在 Linux 上一个 Java 线程对应一个内核线程，内核线程号在线程转储里叫 nid。见 线程、线程状态与上下文切换。

④-1 OOM 是一次分配失败：抛给碰巧在分配的那个线程，进程不退出

所以 OOM 的异常栈只说明“谁最后没要到内存”，不说明“内存被谁占了”。要回答后一个问题，得看堆里还活着什么，这是 ④-2 和 ④-3 的事。JVM 也提供了“一 OOM 就退出”的开关，让编排系统拉起新实例，见 ⑥ 坑 1。

④-2 Full GC 之后剩下的，就是还活着的：降不降，分出两条路

Full GC 会把所有还走得到的对象都留下，别的都收掉，所以 GC 之后的那个数近似等于“此刻活着的总量”。泄漏时活着的总量只涨不跌，这个数一路逼近上限；分配太猛时活着的总量其实不大，只是短时间内要的太多，这个数会掉回去。第 8 站的 GC 日志页用的是同一条规则：GC 后还是满的就是代码问题，不是参数问题。

④-3 直方图只能说“什么最多”，堆转储才能说“被谁拉着”

支配树（dominator tree）是 retained size 的来源：从 GC Roots 到 B 的每一条路都必须经过 A，就说 A 支配 B，A 一旦不可达，B 必然跟着死。MAT 把整张对象图算成一棵支配树，树上每个节点的 retained size 就是它子树的总和，所以“哪个节点下面挂的最多”一眼就看得出来。直方图不做这件事，它便宜，但只能看叶子。

④-4 CPU 对到一行：内核线程号 = 线程转储里的 nid

两样工具的区别：jstack 要让所有 Java 线程停在安全点才能拍，拍到的是“停下来那一刻”的位置，一张只是一瞬间；JFR 在一段时间里按固定间隔采样，样本多了就是统计，能直接回答“这 10 秒 CPU 花在哪”。行号要看成“附近”：C2 编译后的循环只在部分位置记了行号，所以样本分到了第 14 行（for）和第 19 行（while 的回跳），都在同一个循环里（JIT 页）。

④-5 为什么这样设计：证据要在出事之前埋好

出事之后再去抓被放弃的做法

  • OOM 之后堆里全是活对象，jcmd 挂上去时 JVM 自己的挂接线程都要不到内存：⑤ 里先报了 Exception in VM (AttachListener::init) : java.lang.OutOfMemoryError，那次运气好，直方图最后还是拿到了。靠运气拿到的证据不能当流程
  • 值班的人先重启，现场就没了；CPU 高的那个请求，等你登上机器可能已经超时退出
  • 堆转储要停住整个进程写一个和堆一样大的文件，在正卡着的服务上再停一次，雪上加霜

提前埋好本页的做法

  • -XX:+HeapDumpOnOutOfMemoryError：OOM 的那一刻由 JVM 自己写转储，128 MB 堆写了 0.249 秒（⑤ 实测）
  • GC 日志、JFR 连续录制一直开着，开销小，出事后把最近一段倒出来就行
  • 出事时先拍线程转储（便宜、一定拿得到），再决定要不要重启

决定胜负的约束：现场转瞬即逝，而最有用的证据（堆转储）恰恰最贵、在出事时最难拿到。所以 JVM 把最贵的那次拍照做成“出事那一刻自动触发”，把能一直开的（GC 日志、JFR）做得足够便宜。OpenJDK 源码里还有一个细节：多个线程同时 OOM 时只转储第一次（report_java_out_of_memory 里用一个静态标志挡住），免得一次事故写出十几个几百 MB 的文件。

两种工具指到同一个循环（④-4）。这个雷不会自己好：Java 线程没法从外面安全地杀掉，这个线程会一直占着一个核和线程池里的一个位置。按推算，再来 7 个一分钱的请求，8 个 http-exec 线程就全卡死，整个服务不再响应。上线前该有的是单元测试覆盖“1 分钱、0 元商品、一件商品”这些边界，以及循环的最大轮数（⑥ 规范）。

到这里已经能交差了。三个雷各有一条证据链：泄漏是“GC 后不降 → 直方图 → MAT 指到 RECENT”，大对象是“GC 线程吃 CPU → GC 后能降 → Humongous → JFR 分配采样指到 export”，死循环是“top -H → nid → 两次 jstack 同一行 → JFR 确认”。写成排障记录，就是地图上 J03 给靶场的任务。

已知还没处理的细节：OOM 之后进程成了僵尸（⑥ 坑 1）；转储文件放在哪、会不会把盘写满（⑥ 坑 2）；在线上大堆上拍转储会停多久（⑥ 坑 3）；容器里被杀掉时这些都用不上（⑥ 坑 6）。

第一圈

注意事项

坑 1OOM 之后进程还在，健康检查也绿着，但一个请求都不处理← ④-1 OOM 只是一个异常⑤ 实测
现象
端口在监听，进程在，监控说实例存活；请求全部超时。⑤ 雷 1 里 curl 等 3 秒没回音。
根源
OOM 抛给了碰巧在分配的线程。收连接的 HTTP-Dispatcher 线程拿到它就死了，别的线程还活着，JVM 没有理由退出。
做法
加 -XX:+ExitOnOutOfMemoryError，第一次 OOM 就退出（退出码 3），让 K8s 拉新实例。它和 HeapDumpOnOutOfMemoryError 可以一起开，按源码的顺序先写转储再退出。存活探针要走一条真实的业务路径，不要只看端口。
坑 2配了 OOM 自动转储，出事时却没有文件← ④-5 只转储第一次源码核对
现象
日志里有 Dumping heap to …，后面跟着失败；或者干脆找不到文件。
根源
转储文件和已用的堆差不多大（⑤ 128 MB 堆写出 140 MB），盘不够就写不完。路径是目录时文件名是 java_pid<pid>.hprof，容器里 pid 常常都是 1，上次的文件还在就写不出来（JDK 17 源码里这里不覆盖）。Pod 被重建，本地盘上的文件也跟着没了。
做法
HeapDumpPath 指到挂载的持久卷，按 Pod 名分目录，留出一个堆大小以上的空间；拷走以后删掉。
坑 3在线上手动拍堆转储，服务卡住好几秒← ④-5 最贵的证据⑤ 实测 + 估算
现象
执行 jcmd GC.heap_dump 之后，这台实例所有请求一起超时，上游开始重试。
根源
转储期间整个进程停着。GC.heap_dump 默认只转储活对象，所以还要先做一次 Full GC。⑤ 里 128 MB 写了 0.249 秒，按同样的速度估算，16 GB 的堆是半分钟量级。直方图也会先做一次 Full GC（⑤ 实测 30.5 ms）。
做法
先把这台实例从负载均衡里摘掉再拍。要的是全部对象（包括已经不可达的）时加 -all，省掉那次 Full GC；盘紧张时加 -gz=1 压缩，代价是写得更慢。
坑 4直方图第一行是 byte[]、String，看了等于没看← ④-3 shallow 和 retained⑤ 实测
现象
⑤ 雷 1 的直方图第一行是 [B，116.7 MB。全系统都在用 byte[]，不知道是谁的。
根源
直方图只按类加总每个对象“自己”的大小，不知道谁拉着谁。
做法
往下看第一个业务类（这里是 11 万个 Order），个数往往和容器的 Node 个数对得上；要结论就拍堆转储看支配树。隔几分钟拍两次直方图做差，涨得最多的那一类最可疑。
坑 5top 里线程名只剩一半，jstack 的行号和你想的差一两行← ④-4 nid 和采样⑤ 实测
现象
top 显示 http-ex+；几个吃 CPU 的线程名字一样长，分不清。jstack 说第 19 行，JFR 多数样本在第 14 行。
根源
top 的列宽会截断名字，内核本身也只留线程名的前 15 个字符；C2 编译后的代码只在部分位置记了行号。
做法
用线程号换成 nid 去对，不要靠名字；线程池起名时把区分度放在前面（export-3 比 http-nio-8080-exec-3 好认）。行号当成“这一段”，回到源码里看整个循环。
坑 6Pod 一直重启，没有 OOM、没有转储、日志干干净净← ③ 左列：不是堆按文档
现象
容器状态 OOMKilled，退出码 137；这一页的所有工具都没留下东西。
根源
内核按整个进程的内存（堆 + 线程栈 + 直接内存 + 元空间 + 代码缓存 + GC 自己的结构）杀进程，JVM 来不及做任何事。
做法
堆只给容器上限的 60%～75%；开 -XX:NativeMemoryTracking=summary，用 jcmd VM.native_memory 看堆外各占多少。详见 JVM 内存结构，全景第 10 站。

第三圈
更深一层

  
线程转储要等安全点，采样器不用：为什么 JFR 的“热点”更可信

  
jstack 是一次安全点操作：所有 Java 线程跑到下一个安全点停下，VM 线程再逐个记下栈。所以它拍到的永远是“安全点附近”，长时间不进安全点的代码会让所有线程一起等。JFR 的方法采样按固定间隔挑几个正在跑 Java 代码的线程，暂停它、记下栈、放它走，不需要全体停下，⑤ 里 10 秒 983 个样本几乎没有影响其他请求。它仍然只采 Java 帧；要看 native 代码和内核里的时间，用 async-profiler 这类工具，列在下一圈。

  
堆转储要换个地方分析

  
MAT 解析时要建索引，内存大约要和转储文件同一量级，所以别在出事的那台机器上开。⑤ 里用的是 MAT 的命令行：ParseHeapDump.sh x.hprof org.eclipse.mat.api:suspects，140 MB 的转储 8 秒出报告（MAT 1.16.1，要 JDK 17 以上运行），解析出的索引文件留在转储旁边，之后用图形界面打开就不用再解析。大转储给 MAT 调大 MemoryAnalyzer.ini 里的 -Xmx。

3. 先猜：同时发 8 个一分钱的请求，/order 还能返回吗？再跑一次验证，然后给 split 加最大轮数④-4 · 第二圈 · 循环要有出口8 个线程全部卡住，/order 超时；修好后 cents=1 立即返回 0 1

      
    

  

  

    
1. 用一句话说出这一页的精华。
三种现象只有两个问题：内存先看 Full GC 之后降不降，不降找“谁拉着”（堆转储），降了找“谁在猛分配”（GC 日志 + JFR 分配采样）；CPU 先看是哪个线程，GC 线程就回内存路线，业务线程就对到那一行。证据要在出事之前埋好。

    
2. “先重启”和“加大堆”这两个老办法，疼在哪？
重启把现场弄没了，泄漏过一阵又回来，到时还是没有证据；加堆只是把泄漏的 OOM 往后推（GC 日志页实测 256 MB 第 21 秒、512 MB 第 54 秒），而且 Full GC 要处理的活对象更多，每次停得更久。

    
3. 为什么不能照着 OOM 的异常栈去改那一行？是哪条原理？
④-1：OOM 是一次分配失败，抛给的是碰巧在分配的那个线程。占内存的可能是另一个线程、很久以前放进去的对象。⑤ 雷 1 里拿到 OOM 的是 HTTP-Dispatcher 这类线程，雷 2 里是 JDK HTTP 服务器的写缓冲。

    
4. 预测：雷 2 把堆从 256 MB 调到 1 GB，Full GC 会怎样？这算修好了吗？
Full GC 会消失：常驻 108 MB，加上 4 个并发导出约 200 MB 的峰值，1 GB 装得下，大对象在 Young GC 里就被收掉了。从 ④-2 推出：GC 后能降，说明活对象不多，是峰值问题，这种问题加堆是对症的。本机跑过：1 GB 时 30 秒 0 次 Full GC，但 G1 Humongous Allocation 触发的 Young GC 有 514 次；吞吐 1603 个请求、p50 73.5 ms，甚至比 ⑤ 的流式写法（970 个、119 ms，逐字符拷贝更费 CPU）还快。它是合法的修法，代价是内存用量仍和导出行数、并发数成正比，导出量翻几倍又会回来；流式写法让每个请求只用 64 KB，和数据量无关。两个可以一起用。

    
5. 预测：雷 3 换成 ZGC，或者把机器从 2 核加到 8 核，会好吗？
不会。这是业务线程自己在空转，和 GC 无关（④-4：吃 CPU 的是 http-exec-5，不是 GC 线程）。加核只是让它占的那个核在总量里显得少一点，请求还是永远不返回，线程池里的位置也一直被占着。

    
6. 放回全景：第 9 站前后各发生了什么？要是把第 10 站的 OOMKilled 当成第 9 站的堆 OOM 去查，会怎样？
前面是第 8 站：GC 日志里 Full GC 越来越密、GC 之后的占用一路上涨，这是泄漏最早的信号；后面是第 10 站：容器只看整个进程的内存。把 OOMKilled 当堆 OOM 查，会去找转储（根本没有，内核直接杀的），找不到就把 -Xmx 调大，结果堆外更没有余量，被杀得更勤。正确的分岔在 ③ 左列：先看退出码 137 和容器事件，再用 NMT 看堆外。
